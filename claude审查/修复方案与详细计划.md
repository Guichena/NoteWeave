## 二、B0 先决

### E1 — Java 测试 `mvn test` OOM 崩溃
- **根因**：surefire 默认 fork JVM 未限堆，多 fork 在 15G 机器上叠加触发 G1 mmap 失败（见根目录 `hs_err_pid*.log`）。
- **方案（必须改实现）**：限制 surefire fork 数与堆。
- **步骤**：
  1. `backend/pom.xml` 的 `maven-surefire-plugin` 配置加：
     ```xml
     <configuration>
       <forkCount>1</forkCount>
       <reuseForks>true</reuseForks>
       <argLine>-Xmx1500m -XX:+UseSerialGC -XX:MaxMetaspaceSize=512m</argLine>
     </configuration>
     ```
  2. 若用到 `@SpringBootTest` 全量上下文，加 `spring.test.context.cache` 复用（默认已开），并对切片测试改用 `@WebMvcTest/@DataJpaTest` 降低单测内存。
  3. 清理根目录 `hs_err_pid*.log`、`replay_pid*.log`（属崩溃残留，非源码）。
- **验证**：`.\mvnw.cmd -f backend\pom.xml test` 全绿、无新 `hs_err`。
- **工作量**：0.5 天。**风险**：低。

## 三、B1 真实 Bug（建议必修）

### H4 — 删除被摘要覆盖的消息，派生内容仍可回放（隐私）
- **根因**：`ConversationMessageDeletionService.delete` 删消息后只把覆盖它的 summary 标 `STALE`（`:46-53`），未清空 `summary_text`、未对引用该 summary 的快照降级；快照冗余按 message id 匹配（`RunReplayRedactionService.java:68-75`），漏掉"仅经 summary revision id 引用"的快照。
- **方案（必须改实现）**：删消息时联动对**覆盖它的 summary 及其快照**降级。
- **步骤**：
  1. 在 `ConversationMessageDeletionService.delete` 中，找出覆盖该消息的 `segment_summary_revision` 后，除标 `STALE` 外，对这些 revision：
     - 复用 `SegmentSummaryPromotionService` 中已有的 `summary_text=''`（`:64-77` 的做法），或抽出公共方法 `blankSummaryText(revisionId)`。
     - 对每个 revisionId 调 `replayRedactionService.redactDeletedSummaryRevision(revisionId)`（该方法已存在，`:77-82`）。
  2. 用事务保证"删消息 + 降级 summary + 降级快照"原子。
  3. 决策点：summary 被 STALE 后是否**重建**（保留其余未删消息的摘要）——建议异步重建，删除路径只负责降级。
- **涉及文件**：`conversation/ConversationMessageDeletionService.java`、`conversation/RunReplayRedactionService.java`、`conversation/SegmentSummaryPromotionService.java`。
- **验证**：新增测试——建 3 条消息→构建并 promote summary→创建引用该 summary 的 `run_input_snapshot`→删中间消息→断言：(a) summary_text 为空；(b) 快照 `replay_availability='METADATA_ONLY'`；(c) 回放不含被删内容。
- **工作量**：1 天。**风险**：中（触及摘要/快照一致性，需覆盖"直接删 summary"既有路径不回归）。

### M5 — 回调租约任务卡死 `PROCESSING` 永不进 DLQ（存活性 Bug）
- **根因**：`DurableOutboxDispatcher.findTaskCandidates` 要求 `attempt_count < MAX_ATTEMPTS`（`:148`），而 `claim` 每次领取都 `attempt_count+1`（`:273-274`）；DLQ 仅在 publish 抛异常时触发（`:342-343`）。`LEASED_UNTIL_CALLBACK` 任务：worker 每次接受 `/run`（HTTP 200，不抛异常）但不回调 → 每次租约到期被重领 → 第 5 次后 `attempt_count=5` 被候选扫描排除 → 既不再派发也不 dead-letter → 永久 limbo。
- **方案（必须改实现）**：区分"投递尝试"与"回调等待超时"，并为耗尽的 `PROCESSING` 行提供终态出口。
- **步骤**：
  1. 语义拆分：`attempt_count` 只在**真正投递/publish**时自增；"lease 到期重领"不应无限吃 attempt。可引入 `redelivery_count` 或对 `LEASED_UNTIL_CALLBACK` 用独立的"回调超时"判定。
  2. 增加**兜底清扫**：定时任务扫描 `status='PROCESSING' AND lease_until < now AND attempt_count >= MAX_ATTEMPTS` 的行，直接转 `DEAD_LETTER` 并 `failTask`（走统一 finalizer，见 M6）。
  3. 对回调型任务设"回调最长等待"上限，超时即 fail + DLQ，而非静默滞留。
- **涉及文件**：`infra/outbox/DurableOutboxDispatcher.java`、`OutboxDispatchPolicy.java`、`worker/*`（回调超时）、迁移（若加列）。
- **验证**：故障注入测试——模拟 worker 持续接受 `/run` 不回调，推进时钟 6×lease，断言最终行进入 `DEAD_LETTER` 且 task 为 `FAILED`，不再停留 `PROCESSING`。
- **工作量**：1.5 天。**风险**：中（改 outbox 核心状态机，需回归所有既有 dispatcher 测试）。

### M12 — 自定义/系统 MCP 子进程 UTF-8 解码 Bug（2 个红测根因）
- **根因**：`custom_mcp_executor._call_custom_mcp_tool` 用 `subprocess.run(..., text=True, capture_output=True)` 未指定 `encoding`（`:123-131`）；Windows GBK 控制台下中文 stdout 触发 `UnicodeDecodeError` → `completed.stdout=None` → `.stdout.splitlines()` 抛 `AttributeError`（`:136`）。`system_mcp_executor` 复用同函数（`:111`）同缺陷。
- **方案（必须改实现）**：显式 UTF-8 解码 + 容错。
- **步骤**：
  1. `subprocess.run(...)` 增加 `encoding="utf-8", errors="replace"`。
  2. 对 `completed.stdout / stderr` 做 `or ""` 兜底再 `.splitlines()`。
  3. （可选）超时/非零退出时也走 `error_sanitizer` 脱敏。
- **涉及文件**：`workers/artifact-worker/app/custom_mcp_executor.py:123-136`。
- **验证**：`.venv\Scripts\python.exe -m pytest -q` 应从 `220 passed / 2 failed` 变为全绿；重点两条：`test_duplicate_acquisition_ack_should_retry_complete_delivery_after_transport_failure`、`test_acquisition_ack_with_callbacks_should_resume_waiting_task_and_complete_to_java`。
- **工作量**：0.5 小时。**风险**：极低。**建议最先修**（成本最低、直接消红）。

### M18 — compose 服务缺 `container_name`，smoke 脚本探活恒失败
- **根因**：`research-worker-consumer` 未设 `container_name`（`docker-compose.yml:244`），实际名带项目前缀+序号，而 `smoke-phase0a-docker.ps1:53` 按无序号名 `docker inspect`。

  - B：脚本改用 `docker compose ps -q research-worker-consumer` 解析容器 ID。
- **推荐**：A（与其余服务风格一致）。
- **涉及文件**：`docker-compose.yml:244`（或 `scripts/smoke-phase0a-docker.ps1:53`）。
- **验证**：`docker compose up -d` 后跑 smoke 脚本，该服务探活通过。

### M19（原 LOW 提级）— SSRF 字面 IP 解析可被十进制/八进制绕过
- **根因**：`ResearchExternalSnapshotArchiveService.nonPublicLiteralHost` 只识别点分四段或含冒号的字面（`:124-145`），`http://2130706433/`、`0177.0.0.1` 落到 `return false`（放行）。
- **缓解现状**：backend 不 fetch，仅把 URL 存为 provenance，真正 fetch 防护在 worker（IP pin/私网拦截）。故影响是"被污染的字面写入 provenance 元数据"，非直接 SSRF。
- **方案（改实现）**：字面 host 一律用 `InetAddress`/整数解析归一后判私网。
  1. 对非 DNS 名的 host，尝试按十进制/八进制/十六进制整数与点分变体解析为 `InetAddress`，命中环回/私网/链路本地/元数据段即拒。
  2. 保留"DNS 名不在 backend 解析"的既有设计（注释已说明），但对**纯数字 host**必须解析。
- **涉及文件**：`research/ResearchExternalSnapshotArchiveService.java:124-145`。
- **验证**：单测覆盖 `2130706433`、`0177.0.0.1`、`0x7f.1`、`127.0.0.1`、正常公网域名。
- **工作量**：0.5 天。**风险**：低。

## 五、B3 可靠性补强（按需深浅）

### M4 — Checkpoint 存了 hash 但恢复时不校验
- **方案（改实现）**：`ResearchRunQueryService`/恢复路径在读取 checkpoint 对象后，对 payload 重算 sha256 与 `row.payloadSha256()` 比对，不匹配则回退上一有效 checkpoint 或置 `RECOVERING/FAILED`；同时校验 `checkpoint_no` 单调。
- **涉及文件**：`research/ResearchRunQueryService.java:657`、`research/ResearchRunCommandService.java:100-155`、`ResearchCheckpointStore`。
- **验证**：注入损坏字节的 checkpoint，断言拒绝并回退。
- **工作量**：1 天。**风险**：中。

### M6 — 统一 Terminal Finalizer 未覆盖 source-parse 路径
- **方案（改实现）**：`TaskOutboxDispatcherService` 在 source-parse outbox 耗尽时路由到 `SourceParseFailureFinalizer`，校验 task/payload 身份并同步终态化 source、snapshot、task；当前快照才可覆盖 source 状态，陈旧快照只标记自身失败。Finalizer 先用 `TaskService.lockTaskRef` 对 task 执行 `SELECT ... FOR UPDATE`，与并发完成/取消串行化，避免先改 source 后发现 task 已终态而整体回滚或产生分裂。
- **验证**：当前版本投递耗尽后 source/snapshot/task 全部失败；陈旧版本不覆盖新 source；task 锁定查询有状态机回归测试。
- **状态**：☑ 已完成并验证。

### M7 / M8 — 退避无 jitter（outbox + Kafka 消费者）
- **方案（改实现）**：
  - M7：`OutboxDispatchPolicy.retryDelaySeconds`（`:30-32`）加随机 jitter：`base + rand(0, base*0.2)`（注意 §审查报告脚本约束：生产用注入的时钟/随机源，测试可固定）。
  - M8：`KafkaConfig`（`:174`）`FixedBackOff` 换 `ExponentialBackOffWithMaxRetries` 并配 jitter。
- **验证**：单测断言两次退避不恒等、落在期望区间。
- **工作量**：0.5 天。**风险**：低。

### M9 — 清理失败被丢弃，无可重试 Cleanup Task
- **方案（已实现）**：新增 V090 `source_cleanup_task`。`SourceDeletionCleanupListener` 在 source 删除事务的 `BEFORE_COMMIT` 持久化 ES 投影/对象清理意图，`AFTER_COMMIT` 立即尝试，定时任务持续重驱。
- **并发与存活性**：候选和 claim 统一以数据库 `current_timestamp` 判断资格；claim 同时校验旧 `attempt_count`、`attempt_count < 5` 与 lease 条件；成功/失败更新用 `lease_owner` fencing；第 5 次执行失败直接死信，第 5 次 claim 后进程崩溃则由过期耗尽租约扫描直接死信，禁止第 6 次副作用。
- **迁移约束**：目标形状 CHECK 保证 projection 与 object 字段互斥；projection 使用短字段唯一键，object 使用 `object_key_sha256` 唯一键，既规避 MySQL nullable 组合唯一键不能阻止重复，也避免 `utf8mb4 varchar(1000)` 直接建唯一索引超过 InnoDB 3072-byte key 上限。
- **验证**：覆盖即时完成、暂态失败后重试完成、第五次过期 lease 不发生第六次执行；全新 H2/Flyway 从 V001 到 V090 成功迁移；隔离 MySQL 8.4.9 实例成功创建最终表，CHECK 生效，两类重复目标均被 UNIQUE 抑制为 1 行，1000 字符 utf8mb4 object key 不再进入唯一索引。
- **状态**：☑ 已完成并验证。生产 MySQL 8.4 的现有持久卷仍停在 V089，需在下次 backend 部署启动时由 Flyway 实际应用 V090；未直接改写运行中的共享数据库。
