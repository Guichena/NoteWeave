# 本地全功能演示修复计划

日期：2026-07-24

## 1. 目标

目标不是做一个只会上传和问答的最小 Demo，而是在单机、单用户、受控资料和受控网络条件下，让 NoteWeave 当前已经设计和实现的产品功能都能跑通、能展示、能恢复到可操作状态。

本计划直接以《当前已提交代码全量审查报告》中的 F 项为修复来源。只暂时降低复杂情况的要求，不删除或回避现有产品功能。

本轮简化边界：

- 单机 Docker Compose，单个 Backend、Research Worker 和 Artifact Worker 实例。
- 单一演示用户和受控工作台资料。
- 外网抓取、Bilibili、LLM 使用已配置且可控的演示依赖；失败时应诚实显示失败，不要求自动多供应商恢复。
- 不处理公网暴露、恶意输入、多租户对抗、跨实例竞争、生产凭据轮换和高可用。

不允许的简化：隐藏入口、用硬编码假数据冒充结果、把失败任务长期留在处理中、用前端 loading 掩盖后端失败、把已实现功能从验收范围删除。

## 3. 修复优先级

### 第一批：所有功能共用的运行底座

先处理 F-41、F-42、F-47、F-48、F-49、F-52、F-56、F-57、F-58。

这些问题会造成资料永远不可用、任务永久处理中、页面停止刷新、上传失败、流式内容损坏或 Worker 无限等待。它们不属于某一个页面的边角问题，而是整个产品链路的共同底座。

验收标准：资料、Wiki、Research、Artifact 中任一任务成功时可到终态，失败时也可到明确终态；页面不因一次失败永久 busy；刷新后可从服务端读取当前状态。

### 第二批：长任务和终态一致性

处理 F-43、F-44、F-45、F-46、F-50、F-51、F-54、F-61。

这批决定长回答、Research、Artifact 和并发上传是否会重复执行、覆盖结果或锁死后续任务。单机模式不要求多实例容灾，但必须保证同一用户连续点击、刷新、重试或 callback 重放时不会产生明显错误结果。

验收标准：同一 Artifact 只有一个有效版本；取消后的 Answer 不会随后显示已完成；Research checkpoint resume 能继续执行；重复上传完成不会出现两份资料；坏的 Artifact 运行态会显示失败而不是让 Worker 起不来。

### 第三批：功能结果可信且入口完整

处理 F-07、F-09、F-27、F-30、F-31、F-33、F-34、F-35、F-37、F-39。

这批保证用户看到的是当前资料和当前配置真实产生的结果，且所有已设计的入口都能进入：会话恢复、工作台成员和设置、Wiki 搜索、Artifact 版本与下载、等待任务恢复、Skill 目录加载、LLM 模式说明。

验收标准：刷新后能回到原工作台和会话；Wiki 能查到旧资料；LLM 未配置时页面明确显示本地模式或失败，不把模板输出说成模型生成；Artifact 无法恢复时给出可重试失败；成员和检索设置可从界面完成操作。

### 第四批：Research 与历史链路收口

处理 F-10、F-22、F-25、F-26、F-40。

这批不以架构美观为目标，而是确保真实的 Research command、任务事件和报告路径只有一个演示时实际使用的执行链。保留兼容代码可以，但不能让 create、resume、callback 和页面状态分流到不同 topic 或不同 read model。

验收标准：新建和恢复 Research 都走同一当前消费链；过程事件在详情页持续更新；报告、保存为资料和后续问答可追溯到同一个 run。

## 4. 明确延期的复杂问题

以下问题仍重要，但不作为本地全功能演示的阻塞条件：

- 生产身份、安全与公开网络：F-03、F-04、F-05、F-06、F-24、F-32、F-36、F-53、F-60。
- 多实例、高可用和基础设施强韧性：F-29、F-38、F-59、F-62。
- 纯结构拆分或性能优化，前提是当前功能已正确运行：F-11、F-12，以及 F-10 的深度性能部分。

F-02、F-23 不做完整生产身份体系，但必须保留一个明确、稳定的本地演示登录或 local-user 入口，不能在启动后让用户无法进入项目。

## 5. Playwright 的作用

Playwright 只连接真实启动的 Docker 环境，不 mock API、不伪造资料、不替代业务实现。

它负责把上表的用户路径串起来：创建工作台、上传资料、Chat 三模式、Wiki、Research 完整 run 与 resume、Artifact 完整版本链、Memory 审核、设置和刷新恢复。每条路径使用真实创建的 id，并保留截图、trace 和结果 id 作为 Demo 证据。

不在第一轮自动化：真实公网内容质量、Bilibili 转写、恶意输入、并发多用户、跨浏览器和多实例故障注入。

## 6. 执行与验收顺序

1. 启动 `docker compose --profile app up --build -d`，检查所有服务健康。
2. 使用 Playwright 逐项跑完整功能清单，记录真实失败点并映射到 F 项。
3. 依照第一至第四批修复，每批完成后同时运行相关单元/合同测试和真实浏览器路径。
4. 全部功能至少连续演示两次通过。第二次不能依赖手工修改数据库或 Worker 运行态文件。
5. 演示稳定后，再回到安全、生产和多实例治理清单。

## 7. 通过标准

一个功能只有同时满足以下条件才算完成：

1. 用户可以从真实 UI 找到入口并完成操作。
2. 后端和 Worker 返回真实结果或明确失败，不留下长期处理中状态。
3. 刷新页面后，用户能看到正确的当前状态和结果。
4. 该路径至少有一条真实 Playwright 用例和对应的后端或 Worker 回归测试。
