# NoteWeave 指标可宣传性审计与补充

> 本文是对 [全项目指标体系与面试计算手册](../简历亮点八股/07-全项目指标体系与面试计算手册.md)、[质量、评测、测试与发布门禁](../测试与评测/NoteWeave-评测指标报告.md) 和 [公开 Benchmark 与简历指标宣传口径调研](公开Benchmark与简历指标宣传口径调研.md) 的补充。它回答三个问题：现有数字够不够、哪些数字可以写进简历、还缺什么证据才能与论文或产品宣传口径比较。
>
> 证据标签沿用项目约定：`[当前实现]` 是代码或测试入口存在；`[已测-模拟]` 是固定数据、Mock 或故障注入的实际结果；`[行业参考]` 是外部论文、官方 Benchmark 或产品文档；`[生产待验证]` 需要真实用户、Provider、规模和持续窗口。本文不把外部成绩移植为 NoteWeave 成绩。

## 1. 审计结论

### 1.1 现有指标体系已经充分的部分

- 公式、分母、窗口、切片、证据等级和“不能推出什么”已经覆盖得比较完整。
- QA/RAG 已经具备 Recall、MRR、nDCG、Citation、拒答、Scope 和延迟门禁；资料底座已有 Projection Ready、Outbox、Kafka Lag、重试和 DLQ 口径；Research 已有字段、Citation、Checkpoint 和失败屏障口径。
- 文档明确把当前固定回放与生产数据分开，这是面试和公开宣传最重要的真实性边界。

### 1.2 仍然不足的部分

不足不在“缺少更多指标名”，而在缺少可以把指标变成结果的四个闭环：

1. **价值闭环**：还没有真实的用户采纳、修改、节省时间或单位成功成本，因此目前不能声称业务收益。
2. **对照闭环**：4 Case Retrieval Gold、3 Case QA/Note Ablation 能证明回放和门禁，但没有足够样本区分 BM25、Vector、Hybrid、Rerank 在真实分布上的收益。
3. **统计闭环**：现有 100% 结果没有置信区间、分层样本或人工标注一致性，不能回答“行业上是不是比较好”。
4. **端到端闭环**：Research 和资料接入的主要数字还是设计口径；真实 Provider P95/P99、Projection Ready P95、每次成功成本和恢复耗时还没有绑定 Manifest 的稳定结果。

### 1.3 当前结果能否宣传

| 当前数字 | 真实含义 | 可宣传等级 | 正确说法 |
|---|---|---:|---|
| Retrieval Gold 4 Case，Macro Recall@K=1.0，Scope Violation=0，P95=900 微秒 | 固定 JSON、Mock、确定性计算器和门禁通过 | 工程回放证据 | “建立了可复现的 Retrieval Gold/Shadow/Quality Gate，并在 4 Case 固定回放中通过” |
| QA 消融 3 Case，Hybrid/Rerank/Full Pipeline=1.0 | 简单 Fixture 上各策略均命中 | 回归证据，不是 Lift | “补齐了检索消融与回归门禁；当前样本不足以证明 Rerank 收益” |
| Note 消融 3 Case，组合路径=1.0 | 固定 Source/Window 组合路径成立 | 回归证据，不是泛化准确率 | “验证了 Source、Metadata、Semantic 组合路径” |
| Backend 883 tests、Worker 393 passed 的历史记录 | 当时版本的测试/失败门禁行为 | 工程验证，非业务收益 | 必须带时间、版本、跳过数和 `NO_SUPPORTED_CANDIDATE` 边界 |
| 配置中的 Hikari 20、Worker 并发 1、文件 128 MB | 资源保护和能力上限 | 不能单独宣传 | 只能说“当前默认保护参数”，不能换算成 QPS、用户数或吞吐 |

4 Case 的 4/4 点估计并不等于 100% 真实准确率。用 Wilson 95% 区间时，4/4 的下界约为 51.0%；3/3 的下界约为 43.9%。这不是项目质量变差，而是样本量诚实地表达了不确定性。

## 2. 外部一手来源与可迁移结论

### 2.1 论文和官方 Benchmark 的共同结构

| 来源 | 公开规模/口径 | 它真正宣传的指标 | 对 NoteWeave 的迁移 |
|---|---|---|---|
| [BEIR](https://arxiv.org/abs/2104.08663) | 18 个公开数据集、10 类检索系统 | nDCG@10、Recall@K、Precision@K、MRR；BM25 是强基线，Rerank 平均更强但计算成本高 | QA 必须报告基线和绝对 Delta，并同时报告 P95/成本；不能只报一个“RAG 准确率” |
| [KILT](https://arxiv.org/abs/2009.02252) | 统一 Wikipedia Snapshot，多种知识密集任务 | 下游答案效果 + Provenance | Citation、Snapshot、Workspace Scope 是质量的一部分，不是 UI 附属字段 |
| [RAGAS](https://aclanthology.org/2024.eacl-demo.16.pdf) | 无完整 Gold Answer 也可做参考无关评估 | Context Relevance、Faithfulness、Answer Relevance 等分层代理 | 没有 Gold 时可做诊断，但不能把 LLM Judge 代理当作事实正确率 |
| [ARES](https://arxiv.org/abs/2311.09476) | KILT、SuperGLUE、AIS 上的多任务评估；用少量人工标注校准 | Context Relevance、Answer Faithfulness、Answer Relevance + PPI 置信区间 | 需要冻结 Judge、人工校准集和 CI；不能用同一个生成模型自评自证 |
| [DeepResearchBench](https://deepresearch-bench.github.io/static/papers/deepresearch-bench.pdf) | 100 个 PhD 级任务、22 个领域、中英文各 50 | RACE 报告质量；FACT 的 Citation Accuracy、有效引用数 | Research 应把报告质量、字段覆盖和 Citation Support 分开；“引用更多”不等于“引用有效” |
| [BrowseComp](https://openai.com/index/browsecomp/) | 1,266 个难检索、短答案易核验的问题 | Accuracy；官方示例给出 GPT-4o、浏览、o1 和 Deep Research 的对照 | 适合测搜索坚持和事实命中，不适合直接代表长报告质量或用户分布 |
| [GAIA](https://arxiv.org/abs/2311.12983) | 466 个工具使用问题，300 个保留答案用于榜单 | Exact-match 风格的最终答案正确率，按任务难度分级 | Agent 工具链可另设 Task Success；不能用它替代 Research 报告和引用评估 |
| [HotpotQA](https://arxiv.org/abs/1809.09600) | 约 113k 多跳 QA，提供句子级 Supporting Facts | Answer EM/F1 + supporting facts | Wiki/Note 多跳应保存 Supporting Evidence，而不只保存最终答案 |
| [LongBench](https://arxiv.org/abs/2308.14508) | 21 个数据集、6 类长上下文任务，中英文长输入 | 按任务类型报告 EM/F1/ROUGE 等自动指标 | 长文能力必须按文档长度、语言、任务切片；不能拿短 Query 均值代表长文性能 |
| [LongMemEval](https://arxiv.org/abs/2410.10813) | 500 个长期记忆问题 | 信息提取、多会话、时间推理、知识更新、拒答五类能力；论文报告商业助手在长期记忆上有明显准确率下降 | Memory 必须单列 Update、Temporal、Abstention 和污染/撤销，不只报命中率 |
| [DocLayNet](https://arxiv.org/abs/2206.01062) | 80,863 页、11 类布局标注 | layout detection mAP，并与标注者一致性比较 | 资料解析质量要有结构保真和人工基线，不能只说“支持 PDF” |
| [ParseBench](https://www.parsebench.ai/) | 2,000+ 人工验证页、169K 规则、5 个维度 | Tables、Charts、Content Faithfulness、Semantic Formatting、Visual Grounding、Overall 和 Cost/Page | 资料链路可以宣传“解析质量 + 每页成本”，但必须锁定榜单日期和输入分布 |
| [TREC RAG](https://trec-rag.github.io/) | 统一的 Retrieval + Generation 评测轨道 | 端到端答案、证据和检索子任务的组合评估 | QA 评测应同时保留检索层和生成层，不能用最终答案反推召回正确 |
| [LangSmith RAG Evaluation](https://docs.langchain.com/langsmith/evaluate-rag-tutorial) | 官方教程中的四类 Evaluator | Correctness、Relevance、Groundedness、Retrieval Relevance | 这四个对象可直接映射到 NoteWeave 的 Answer、Query、Context 和 Evidence 评测 |

### 2.2 公司/产品宣传的共同模式

- OpenAI 的 BrowseComp 将“难找但易验”作为任务设计原则，并同时披露数据规模、人工基线、模型对照和局限；这比只贴一个最高分更可信。
- LangChain 的 LangSmith 把 Response、Input、Retrieved Documents、Reference Answer 两两对照，产品宣传的是可解释的评估链，而不是一个神秘总分。
- ParseBench 的产品/公司榜单把多个厂商放在同一数据和五个维度上，并把 Cost/Page 单列；这说明成本是质量指标的护栏，不是事后补充。
- ARES/RAGAS 这类开源评测工具宣传“可自动化、可分层、可带置信度”，而不是承诺 Judge 本身等于人工真相。

### 2.3 外部数字样例与 NoteWeave 可比性

| 外部公开数字 | 对方在证明什么 | 能否与 NoteWeave 当前数字横比 |
|---|---|---|
| BrowseComp 1,266 题；官方页面披露 GPT-4o 0.6%、GPT-4o with browsing 1.9%、o1 9.9%、Deep Research 51.5% Accuracy | 难检索、短答案、可自动核验的搜索能力 | 不能。NoteWeave 当前 4 Case 是内部 Retrieval Smoke，不是同一题集、答案协议或 Agent 运行预算 |
| GAIA 466 题；论文摘要报告人类 92%、带插件 GPT-4 15% | 多模态、浏览和工具使用的通用 Agent 最终答案正确率 | 不能。NoteWeave 还没有按 GAIA 提交协议运行，也没有同难度分层结果 |
| LongMemEval 500 题；论文报告商业助手和长上下文模型在持续交互中出现约 30% Accuracy Drop | 长期记忆在信息提取、多会话、时间、更新和拒答上的退化 | 不能。它可用于设计 Memory Gold 切片，不是 NoteWeave 的当前 Memory 分数 |
| DocLayNet 80,863 页、11 类；论文报告布局模型约落后标注者一致性 10% | 文档布局检测 mAP 和人工上限差距 | 不能。NoteWeave 当前没有相同页面、标注类、检测模型和 mAP 结果 |
| ParseBench 当前公开页为 2,000+ 人工验证页、169K 规则、5 维；2026-08-16 抓取时榜首 Overall 84.9、1.3 美分/页 | 文档解析的多维质量和单位页面成本 | 不能。榜单会更新，且 NoteWeave 未按其数据、规则和计价方式提交 |
| 当前 NoteWeave Retrieval Fixture 4/4、Macro Recall@K=1.0、Scope=0 | 固定输入上的计算器、契约和安全门禁 | 只能作为 L0 机制回放证据；不能由点估计高于外部百分比推出系统更强 |

外部分数低不表示 NoteWeave 的 100% 更好，外部分数高也不表示 NoteWeave 更差。只有相同 Dataset、任务定义、Snapshot、工具预算、模型、Judge 和评分脚本下的结果才有排名意义。当前可下的结论是：NoteWeave 的评测结构与业界主流口径一致，但数据规模和评测协议尚不足以形成行业成绩。

因此 NoteWeave 适合采用 **一个主结果 + 两个护栏**：

```text
主任务质量
  + 证据/安全护栏
  + 延迟、成本或恢复护栏
```

## 3. 按功能补充的指标卡

以下每张卡都要求回答：它解决什么业务问题、分子/分母是什么、从哪里采集、变坏如何下钻、不能证明什么。`目标阈值` 是建议的启动门槛，不是行业标准；正式值必须由基线和风险分层决定。

### 3.1 总体业务结果

| 指标 | 计算方式 | 业务意义 | 当前状态/简历条件 | 面试追问 |
|---|---|---|---|---|
| 有效 Workspace 激活率 | `完成首个 READY 资料且得到一次有效回答的 Workspace / 新建 Workspace` | 是否真正进入价值路径 | `[生产待验证]`；需要事件埋点和 Cohort | 为什么不用注册或登录作激活？取消和失败如何算？ |
| Time to First Value | `首个有效结果时间 - Workspace 创建时间` 的 P50/P95 | 用户多久看到第一次价值 | `[生产待验证]`；按上传、QA、Research 分层 | 长任务如何定义“有效结果”？异步等待是否计入？ |
| 任务终态成功率 | `通过业务 Validator 的成功终态 / 已接受任务` | 结果是否真正可用 | `[生产待验证]`；取消、拒绝、未知结果单列 | 为什么 HTTP 200 不算成功？分母为何用 accepted 而不是 started？ |
| 有效结果采纳率 | `用户未在窗口内修改/重跑且标记采纳的结果 / 可采纳结果` | 结果是否减少人工工作 | `[生产待验证]`；必须定义采纳和观察窗 | 修改是失败还是正常编辑？如何避免只留下满意用户的偏差？ |
| 单位成功成本 | `(LLM + Embedding + Rerank + 搜索 + 抓取 + 存储 + 重试 + 人工审核成本) / 成功结果数` | 质量收益是否值得成本 | `[生产待验证]`；按功能和 Provider 计费 | Token 成本为何不够？失败重试和闲置资源怎么分摊？ |
| 有效结果吞吐 | `通过 Validator 的结果数 / 时间` | 比入口 QPS 更接近业务产出 | `[生产待验证]`；上传、QA、Research 分开 | 接收 QPS 和完成吞吐为何不能混用？ |

| Effective Citations per Task | `任务中支持至少一个 Claim 的唯一 Citation 数` | 证据收集是否有实质贡献 | `[生产待验证]`；不要以链接数量替代 | 一个来源支持多个 Claim 是一个还是多个？ |
| Conflict Discovery Rate | `识别并保留的冲突 Gold Case / 冲突 Gold Case` | 是否避免把矛盾证据抹平 | `[目标设计]`；按数值、日期、定义切片 | 冲突未解决时为何应降级或拒答？ |
| Checkpoint Recovery Success | `中断后在预算内恢复到相同 Canonical State 的 Run / 被中断 Run` | 长任务是否可恢复 | `[当前实现]` 有回放和测试入口；真实故障分布下的成绩属于 `[生产待验证]` | 如何证明恢复不是重新跑出另一个答案？ |
| First-pass Yield / Repair Yield | `首轮通过内容 Contract 的 Candidate / 接受首轮 Contract 判定的 Candidate`；`修复后通过最终 Contract 的 Candidate / 进入 Repair 的 Candidate` | 质量、成本和修复策略是否健康 | `[当前实现]` 当前可计算；必须与修复 Token、尾延迟一起看 | Repair 高是验证器强还是首轮生成差？ |
| Research Success Cost | `Research 总成本 / 通过完成契约的 Run` | 研究产出是否经济 | `[生产待验证]`；按失败、重试、抓取和人工复核分摊 | 失败 Run 的成本算给谁？预算熔断如何影响成功率？ |

### 3.5 Note/Wiki、Artifact 和 Memory

| 功能 | 首选主指标 | 必须的护栏 | 当前能说什么 |
|---|---|---|---|
| Note | Source Hit@K 或 Reading Window Continuity | Citation Support、跨 Snapshot 版本正确率、窗口 Token 预算 | 3 Case 组合路径通过；不能称长文准确率 |
| Wiki | Supporting Evidence F1 或 Page/Source Backlink Coverage | 当前 Page Head、旧版本拒绝、删除传播、Scope=0 | 工程正确性是当前差异化卖点，质量分数需扩 Gold |
| Artifact | Validator First-pass Yield 或 Save Success Rate | Schema、Mime/Digest、危险内容、Callback Receipt、未知状态恢复 | 可宣传“验证驱动产物链路”，数值需绑定产物类型和 Provider |
| Memory | Update Accuracy、Temporal QA、Refusal Recall/Precision | Stale Revision、Scope、Revoke/污染率 | LongMemEval 的五类能力可作任务设计参考，不能移植其分数 |

## 4. 统计和可比性：什么样的数字才够资格写简历

### 4.1 最小可比实验

每次质量实验必须冻结：`Dataset Version × Query/Task × Snapshot/Index × Chunk/TopK/RRF/Rerank × Model/Provider × Prompt/Schema × Judge/Rubric × Gate Policy`。只改变一个目标变量，保留 Baseline 和配对结果。报告绝对 Delta，不只报相对提升。

每条结果至少带：样本数、分子、分母、95% CI、语言/任务/长度/风险切片、失败样本、运行命令、环境和不能推出的结论。质量指标用 Query/Task 级宏平均；成本和线上流量用微平均或按请求量加权，不能把两者混用。

### 4.2 样本量规划（统计计划，不是行业门槛）

若只想估计一个比例的 95% 误差范围，可用最保守的 `n ≈ 1.96^2 × 0.25 / e^2`：

| 目标误差半径 `e` | 规划样本数 `n` | 适用 |
|---:|---:|---|
| ±10 个百分点 | 约 96 | 内部方向判断 |
| ±5 个百分点 | 约 385 | 对外或简历主数字的更稳起点 |
| ±3 个百分点 | 约 1,068 | 需要长期线上窗口或大规模 Benchmark |

这只是独立 Bernoulli 比例的近似；多租户、语言和任务切片会降低有效样本量。对于 Recall/nDCG 的连续或宏平均指标，应保留逐 Case 结果并使用配对 Bootstrap，而不是套用上表直接宣称准确率。

### 4.3 业界可比性分级

| 级别 | 必备条件 | NoteWeave 当前状态 |
|---|---|---|
| L0 机制回放 | 固定 Fixture、计算器、门禁和故障窗口 | 已有，适合讲工程设计 |
| L1 项目回归 | 至少覆盖历史缺陷、Hard Case、负例和版本切片 | 部分具备，需扩大 QA/Note/Research Gold |
| L2 内部评测 | 真实或脱敏分布、Baseline、配对 CI、人工校准 Judge | 尚未形成稳定窗口 |
| L3 外部可比 | 使用公开数据集和规定 Snapshot/Protocol，报告官方指标 | 当前没有，不应写“达到 BEIR/GAIA/ParseBench 水平” |
| L4 业务收益 | 用户采纳、时间节省、成本、留存或收入等对照实验 | 当前没有，不能写业务提升百分比 |

当前 4 Case/3 Case 的正确定位是 **L0，正在向 L1 过渡**。它们在机制和门禁层面是有价值的，但不能证明 NoteWeave 的质量已达到论文或产品榜单的水平。

## 5. 可以直接写进简历的表达

### 5.1 现在就能写（不需要虚构业务数字）

- 构建版本化 Retrieval Gold/Shadow/Quality Gate，统一固定 Snapshot、Strategy Tuple、Citation、拒答和 Scope 安全门禁；在 4 Case 确定性回放中验证 Recall、排名稳定性、拒答和越权阻断，避免把延迟或平均质量掩盖安全失败。
- 设计从 Upload、Parse、Chunk、Embedding 到 Projection Ready 的异步资料底座，围绕 Outbox、Kafka、幂等、版本投影和删除对账定义 Ready 延迟、最终收敛率、重试放大和删除传播指标。
- 为 Deep Research Agent 建立 Required WorkItem Completion、Citation Support、Conflict Discovery、Checkpoint Recovery 和 Repair Cost 评测契约，比较型子集另报 Matrix Cell Coverage，并把“完成”从生成文本提升为经过证据和状态验证的 Canonical Result。

### 5.2 有真实数据后再填的模板

```text
构建版本化场景化 RAG，在固定 {Dataset Version}、{N} 条 Query 和 {Model/Index} 上，Hybrid 相比 BM25 的 Recall@5 提升 {+X 个百分点}，Citation Support 为 {Y%}，Scope Violation 为 0，并将答案 P95 控制在 {Z ms}。

搭建异步资料接入链路，在 {文件矩阵/持续窗口} 下将 Upload Accepted 到 Projection Ready 的 P95 降至 {X s}，重试后的最终收敛率达到 {Y%}；指标按文件类型、大小、页数和是否 OCR 分层。

实现验证驱动的 Deep Research Agent，在 {N} 条混合 Research Gold 上达到 Required WorkItem Completion {X%}、Citation Support {Y%}、Checkpoint Recovery {Z%}，并将单位成功 Run 成本控制在 {C}；比较型子集另报 Matrix Cell Coverage。
```

### 5.3 不应写的表达

- “支持 400 QPS”：仅由连接池 20 和 50 ms 的理想除法推导，缺少压测。
- “RAG 准确率 100%”：来自 4 Case 或 3 Case Fixture，且没有答案正确性和外部数据集。
- “Rerank 提升 100%”：基线很小或 3 Case 绝对 Lift 为 0 时用相对百分比夸大。
- “线上零越权/生产可用”：当前 Scope=0 是固定回放门禁结果，不是长期生产窗口。
- “节省 80% 研发时间/成本”：没有用户对照、账单和采纳定义。

## 6. 面试官最可能追问的回答骨架

### Q1：你们的准确率是多少？

先问他指的是检索、引用、答案、Research 字段还是业务采纳。然后给分子/分母、Dataset/Bundle、窗口和当前证据等级。例如：“当前能确认的是 4 Case 固定 Retrieval Gold 的 Macro Recall@K=1.0、Scope Violation=0、P95=900 微秒；这是 Mock/确定性回放，不是线上准确率。正式评测会在同一 Snapshot 上比较 BM25、Vector、Hybrid 和 Rerank，并报告 Recall/nDCG、Citation Support、拒答和成本。”

### Q2：4/4 为什么不能说 100%？

点估计是 100%，但样本量只有 4。Wilson 95% 区间下界约 51.0%，还没有覆盖长 Query、冲突、近重复、多语言和权限边界。它证明的是回放契约和门禁正确工作，不是泛化能力。

### Q3：Recall@5 高，为什么答案还会错？

召回只回答 Gold Evidence 是否进入候选集；之后还可能出现排序下沉、Evidence Budget 截断、Citation 只挂 URL 不支持 Claim、版本/权限错误、生成不忠实或拒答门槛失效。因此必须同时看 nDCG、Citation Support、Faithfulness、Refusal Recall/Precision、Answer Coverage 和 Scope Violation。

### Q4：为什么不用一个综合分？

安全不变量不能被质量平均数抵消：一次越权引用、旧 Snapshot 泄漏或危险工具放行都应直接阻断。其余指标可以做多目标比较，但必须保留每一项的分子、分母、CI 和失败切片。

### Q5：Research 最能证明价值的数字是什么？

第一优先是 Citation Support 或 Citation Accuracy，第二是 Required WorkItem Completion，第三是单位成功成本或 Checkpoint Recovery。比较型任务可补 Matrix Cell Coverage。报告质量 Judge 分数可以作为补充，但必须披露 Judge、Rubric、参考报告和人工校准。

### Q6：如何判断 Rerank 值不值得？

在相同 Query、Snapshot、候选预算和生成策略上做配对消融，比较 Recall/nDCG、Citation Support、P95、超时降级、Provider 429 和单位成本。当前 3 Case Rerank Lift=0 只能说明 Fixture 不敏感，不足以删除或保留 Rerank。

### Q7：十倍流量如何估算？

先按 Upload、QA、Research、Artifact 分开建立到达率和服务时间，用 `L = lambda × W` 估算在途，再找最先饱和的 Provider、Hikari、Kafka Partition、Worker、ES 或 SSE 资源。扩并发前要确认不是 Provider 429、锁等待或队列毒消息。

### Q8：没有线上数据，项目结果怎么讲？

把工程结果和业务结果分开：“当前项目主要证明可恢复、可评测和可审计的工程闭环，没有线上用户收益数据；我已经定义了 Projection Ready P95、Citation Support、单位成功成本和采纳率的采集方法，下一步用固定工作负载和真实 Provider 做 L2 评测。”真实边界比补一个未经验证的百分比更可信。

## 7. 建议的下一轮验收顺序

1. **先扩 Gold**：从 4/3 Case 扩到覆盖正例、负例、跨 Workspace、长文、近重复、冲突、代码/表格和多语言的版本化集合；每个 Case 保存 Gold Evidence、Citation、拒答和切片。
2. **再做配对消融**：BM25、Vector、Hybrid、Rerank 只改变一个变量；保留 Recall、nDCG、Citation Support、拒答、P95、Token/Provider 成本。
3. **再测资料端到端**：固定 PDF/DOCX/HTML/Markdown 文件矩阵和大小/页数分布，记录 Accepted、Parsed、Chunked、Embedded、Projected、Ready、删除收敛和重试次数。
4. **再测 Research**：建立至少一批正常、证据不足、冲突、网页变化、表格和 Checkpoint 中断任务；保存 Field、Claim、Citation、Conflict、Repair、Recovery 和成本。
5. **最后接业务价值**：记录用户采纳、修改、重跑、人工接管、完成时间和单位成功成本，按 Workspace/任务类型做 Cohort；没有这一步不能写“节省时间”或“提升生产力”。

## 9. 最终判断

NoteWeave 当前在“指标设计、证据等级、故障门禁和面试可解释性”上已经达到可以展示工程方法的水平；在“与论文/产品同口径的可比较结果”和“业务收益数字”上还没有足够证据。最值得优先补齐的不是更多 QPS，而是四个能闭环的结果：

1. `QA Recall@5/nDCG@10 + Citation Support + Scope=0`；
2. `Upload Accepted -> Projection Ready P95/P99 + 最终收敛率`；
3. `Research Field Coverage + Citation Support + Checkpoint Recovery`；
4. `单位成功成本 + 用户采纳/修改率`。

这四组数字一旦绑定固定 Dataset、Baseline、Manifest、CI、真实 Provider 和时间窗口，才足以从“工程设计很好”升级为“有可量化产出、可以写进简历且经得起面试追问”。
