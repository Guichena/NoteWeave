# 资料底座演进取舍外部依据

> `[行业依据]` 本文只使用论文、标准、厂商官方文档或官方仓库，给事件驱动资料底座的设计取舍提供一手依据。
>
> `[禁止外推]` 文中的 Kafka、Amazon S3、MinIO AIStor、Elasticsearch 和 Debezium 数字都不是 NoteWeave 成绩，也不能证明 NoteWeave 达到相同吞吐、延迟或可靠性。
>
> `[项目边界]` NoteWeave 的当前实现、源码入口和故障窗口见[事件驱动资料底座详细设计](../简历亮点八股/03-事件驱动资料底座-详细架构与具体设计.md)与[面试题及参考回答](../简历亮点八股/03-事件驱动资料底座-面试题与参考回答.md)。本文不重复实现说明，只补外部依据、可比条件和面试追问。

## 1. 结论先行

NoteWeave 当前选择 Polling Outbox、Kafka 至少一次投递、业务幂等、MinIO 原件、MySQL 真源和 Elasticsearch 可重建投影，是一个有明确适用范围的工程组合，不是对“Exactly-once”的低配模拟。

一手资料支持以下六个结论：

1. Transactional Outbox 关闭的是“数据库提交成功，但发送意图丢失”的双写窗口；它本身允许重复，消费端仍需幂等。
2. CDC 可以替换 Outbox 的轮询搬运方式，但不会自动删除事件身份、顺序、重复处理、Schema 演进和恢复治理。
3. Kafka 幂等 Producer 只去除 Producer 重试在 Kafka Log 内造成的重复；Kafka Transaction 的强保证主要覆盖 Kafka 到 Kafka，不能自动把普通 MySQL、MinIO 和 Elasticsearch 纳入同一事务。
4. Amazon S3 的单 Key 强一致不等于“数据库行与对象原子提交”；S3 兼容协议也不等于继承 AWS 的服务级实现、容量或 SLA。
5. Elasticsearch 的 Refresh 只决定“已经写入的文档何时对搜索可见”，不等于整个上传、解析和投影链路在一秒内完成。
6. DLQ 是失败隔离与取证设施，不是自动修复证明；长期可靠性还要由 Redrive、对账和收敛时间证明。

因此，资料底座最值得拿到面试里讲的不是“用了四个中间件”，而是以下不变量：

```text
业务提交后存在持久发送意图
  + 重复投递不产生第二份业务结果
  + 旧版本不能覆盖新版本
  + 投影可以从真源重建
  + 失败进入可诊断终态
  + 对账能够发现并修复长期漂移
```

## 2. Transactional Outbox：它解决什么，不解决什么

### 2.1 一手资料结论

AWS Prescriptive Guidance 将 Transactional Outbox 定义为解决分布式系统 Dual Write 冲突的模式：业务数据与 Outbox 事件在同一数据库事务中提交，再由独立进程把已提交事件发送到消息系统。AWS 同时明确列出两个工程责任：

- 事件处理服务可能发送重复消息，因此 Consumer 应跟踪已处理消息并保持幂等。
- 通知顺序应与数据库更新顺序一致，尤其不能让回滚事务产生下游通知。

Debezium 的官方 Outbox Event Router 也没有承诺“只投递一次”。其默认 Outbox 表包含事件唯一 `id`，官方说明该 ID 可以用于删除重复消息。也就是说，官方方案把稳定事件身份视为消费端去重依据，而不是假设传输层不会重复。

### 2.2 对 NoteWeave 取舍的含义

`[项目映射]` 当前 Polling Outbox 的价值是让“业务状态”和“待发送命令”共用 MySQL 本地事务。Dispatcher 的 Claim、Lease、Attempt 和 Dead 状态是在解决多实例并发、崩溃恢复与运营问题，不改变 Outbox 的基本语义。

它能证明：

- 若业务事务提交，发送意图不会因为 Java 进程随后崩溃而静默丢失。
- 若业务事务回滚，不会留下一个已提交的 Outbox 行去通知下游。

它不能单独证明：

- Kafka 中只会出现一条物理消息。
- Consumer 只会执行一次。
- MinIO、MySQL 与 Elasticsearch 在同一时刻提交。
- 所有失败都会在某个固定时间内自动恢复。

### 2.3 Polling 与 CDC 的演进边界

AWS 的同一份 Outbox 指南把“扫描 Outbox 表”和 CDC 都列为实现手段。Debezium 官方文档则表明 CDC 读取数据库事务日志并保存 Offset；Connector 崩溃时，最近 Offset 可能尚未记录，恢复任务会从上一个 Offset 继续并重新生成部分事件。

因此，正确的演进关系是：

```text
Polling Outbox
  -- 搬运延迟或数据库轮询成本超预算 -->
CDC / Debezium Outbox Router

保持不变：本地事务、事件 ID、Aggregate 顺序、Consumer 幂等、DLQ、对账
新增成本：Binlog 权限、Connector 运维、Offset 与 Schema History、快照和日志保留
```

`[演进触发条件]` 只有在下列数据持续超预算时，才有证据从 Polling 迁移到 CDC：

- Outbox 最老 READY 年龄持续增加。
- 已优化索引与批量 Claim 后，轮询仍占据不可接受的 MySQL CPU、I/O 或锁等待。
- 业务确实需要低于当前 Tick 能提供的发布延迟。
- 团队能够承担 Binlog 保留、Connector Offset、Schema History 和增量快照运维。

不能把“CDC 更先进”当作迁移动机，也不能说 CDC 天然 Exactly-once。

## 3. Debezium：公开 Benchmark 实际在测什么

Debezium 官方仓库提供了 `debezium-e2e-benchmark`，其测量方式是：在数据库测试表写入一列插入时间，再与对应 Kafka Record 的时间戳比较，输出 CSV 与分布图。默认配置展示的是 `100000` 次提交，并分别使用 `1`、`100`、`1000`、`10000` 的 Commit Interval。

这是一个重要的指标定义，但不是一个可直接引用的行业成绩：官方 README 给出了 Harness 和参数，没有给出跨数据库、跨硬件都成立的固定“Debezium 每秒多少条”结论。

### 3.1 这个指标能说明什么

在固定数据库、Connector 版本、Kafka 配置、Row 大小和负载下，它可以测：

- 从数据库写入时间到 Kafka Record 时间的 CDC 延迟分布。
- Commit Interval 对吞吐与延迟的影响。
- Connector 升级前后的回归。

### 3.2 它不能说明什么

- 不能代表 Source 写入到 Elasticsearch 可查询的业务端到端延迟。
- 不能证明 Consumer 副作用没有重复。
- 不能跨 MySQL、PostgreSQL、DB2 等 Connector 直接比较。
- 不能忽略 Binlog Flush、Kafka `acks`、Batch、网络和消息大小。

### 3.3 NoteWeave 若评估 CDC，必须固定的条件

```text
数据库版本与 durability 配置
  + Debezium / Kafka Connect 版本
  + 表结构、Row 大小与事务大小分布
  + 单事务行数与 Commit Interval
  + Snapshot 是否同时运行
  + Kafka acks、复制因子与 min.insync.replicas
  + Connector Task 数、Batch、Queue 和网络
  + P50 / P95 / P99，而不是只报平均值
```

## 4. Kafka Delivery Semantics：三个“恰好一次”不能混为一谈

### 4.1 Kafka 官方语义

Apache Kafka 设计文档将消息语义区分为 At-most-once、At-least-once 和 Exactly-once。Consumer 若“先处理、后提交 Offset”，就在处理成功后、Offset 提交前存在崩溃窗口；新 Consumer 会重放部分消息，这就是至少一次。

Kafka 官方还明确限定 Exactly-once 的边界：

- Kafka Topic 读、处理、再写 Kafka Topic 时，可以把输出消息和 Consumer Offset 放进同一 Kafka Transaction。
- Consumer 需要使用 `read_committed` 才不会看到已中止事务的消息。
- 写入外部系统时，需要外部系统配合协调 Offset 与输出；Kafka Transaction 不会自动覆盖普通数据库或对象存储。

### 4.2 幂等 Producer 的准确口径

Kafka 4.2 Producer 配置文档说明：

- `enable.idempotence=true` 保证 Producer 重发不会在 Kafka Stream 中写入第二份副本。
- 它要求 `acks=all`、`retries>0`、`max.in.flight.requests.per.connection<=5`。
- 当前文档中幂等默认开启，但冲突配置可能使其关闭；显式开启且配置冲突会抛出 `ConfigException`。
- 未配置 `transactional.id` 时，Producer 只有幂等投递，不能使用事务；配置后才启用跨 Producer Session 的事务身份与 Fencing。

这里的“Exactly one copy”是 Kafka Log 写入语义，不是 NoteWeave 业务副作用语义。即使 Topic 中没有 Producer 重试副本，Consumer 仍可能在写 ES 成功、提交 Offset 前崩溃并再次处理。

### 4.3 NoteWeave 应使用的三个术语

| 术语 | 应该怎样回答 | 不能怎样回答 |
|---|---|---|
| Producer 幂等 | 消除同一 Producer Session 重试导致的 Kafka Log 重复，并保持分区内顺序条件 | “整个系统 Exactly-once” |
| Kafka Transaction | 原子提交 Kafka 输出与 Consumer Offset，配合 `read_committed` | “把 MySQL、MinIO、ES 一起提交” |
| 业务幂等 | 同一个 Message ID、Snapshot ID 或 Projection Version 重放时不产生第二个业务结果 | “物理调用只发生一次” |

### 4.4 `acks=all` 仍需继续追问

`acks=all` 表示 Leader 等待当前 ISR 中的副本确认，不等于等待所有配置副本永远落盘。可靠性还取决于复制因子、`min.insync.replicas`、Unclean Leader Election、Broker 故障模型和 Topic 配置。

面试时只说“设置 `acks=all` 所以绝不丢消息”是不合格的。更严谨的说法是：Producer 确认条件与集群允许写入的最小 ISR 共同决定 Broker 故障下的持久性；而应用层仍以 Outbox 与幂等吸收不确定结果。

## 5. Kafka 公开性能数字及不可比边界

Confluent 2020 年官方性能测试使用 OpenMessaging Benchmark 比较 Kafka、Pulsar 与 RabbitMQ。其公开结果中，Kafka Peak Stable Throughput 为 `605 MB/s`；在 `200 MB/s` 负载下，Kafka P99 端到端延迟为 `5 ms`。

这些数字有完整但非常特定的实验条件：

- 3 台 Broker，每台 AWS `i3en.2xlarge`，8 vCPU、64 GB RAM、2 块 2.5 TB NVMe、25 Gbps 网络。
- 4 个 Producer、4 个 Consumer，1 个 Topic、100 个 Partition。
- 消息大小 1 KB，吞吐测试最大 Batch 1 MB、最大等待 10 ms。
- 3 副本，Producer `acks=all`，`min.insync.replicas=2`。
- Peak Stable 的定义是 Consumer 可以持续跟上、Backlog 不会无限增长的最高平均 Producer Throughput。
- 延迟测试把 Kafka 和 Pulsar 都压到 200K Message/s，约 200 MB/s；测试不是 NoteWeave 文件解析或索引链路。

### 5.1 这个数字能说明什么

- 在该硬件、消息大小、分区、Batch 和可靠性配置下，Kafka Broker 不是低吞吐组件。
- 报吞吐时必须同时说明 Consumer 是否跟上，否则“Producer 峰值”会掩盖不断增长的 Lag。
- 吞吐与延迟必须在同一负载点讨论，不能把空载延迟和满载吞吐拼在一起。

### 5.2 它不能证明什么

- 不能证明 NoteWeave 能处理 `605 MB/s`。
- 不能证明一次资料上传在 `5 ms` 内可检索。
- 不能证明 JSON 大消息、TLS、跨机房、较少 Partition 或弱硬件有相同性能。
- 不能证明 Worker、Embedding、MinIO、MySQL 和 Elasticsearch 能跟上 Kafka。

### 5.3 NoteWeave 的可比条件

NoteWeave 只有在固定以下 Manifest 后，才能宣传 Kafka 侧数字：

```text
机器、磁盘与网络
Kafka 版本、Broker 数、Partition、复制因子、ISR 与 acks
TLS / 压缩 / Batch / linger
消息平均、P95 和最大字节数
Producer 与 Consumer 数
稳态时长、Lag 是否有界、失败率
P50 / P95 / P99 E2E Latency
```

资料底座更应优先宣传“任务每秒数”和“上传到 Projection Ready 的 P95”，而不是 Kafka 字节吞吐，因为前者才接近用户感知。

## 6. Amazon S3 与 MinIO：一致性、原子性和吞吐不是一回事

### 6.1 Amazon S3 官方一致性口径

AWS S3 User Guide 说明，S3 在所有 AWS Region 对对象 PUT 和 DELETE 提供强 Read-after-write Consistency，覆盖新对象、覆盖写和删除；对单个 Key 的更新是原子的，并发 GET 只能看到旧对象或新对象，不会看到部分写入对象。

该保证意味着成功 PUT 后不需要为了“等对象可见”而人为 Sleep，但它不意味着：

- MySQL 行与 S3 对象形成跨系统原子事务。
- 两个不同 Object Key 作为一个整体原子可见。
- 应用在收到超时后能仅凭客户端状态判断 PUT 是否成功。
- 自建 MinIO 自动继承 AWS S3 的服务实现、容量或 SLA。

对 NoteWeave 而言，Digest、对象 Key、Upload 状态与 Post-commit Cleanup 仍然必要。对象存储的单 Key 一致性不能关闭“对象成功、数据库失败”或“数据库删除已提交、对象清理失败”的跨存储窗口。

### 6.2 Amazon S3 官方性能口径

AWS 性能指南给出的当前基准是每个分区化 Prefix 至少：

- `3,500` 次每秒 PUT、COPY、POST 或 DELETE 请求。
- `5,500` 次每秒 GET 或 HEAD 请求。

AWS 同时说明 Scaling 是逐步发生而非瞬时完成，扩容期间可能出现 `503 Slow Down`，实际性能随工作负载、使用模式和系统配置变化。

这些数字测的是 S3 API Request Rate，不是文件数、业务任务数或 GiB/s。若对象大小从 4 KB 变为 128 MB，请求数相同但字节吞吐完全不同。

### 6.3 MinIO 官方公开数字

MinIO 当前 AIStor Benchmarking 文档公开了两个八节点测试：

- `268 GiB/s` Peak GET、`120 GiB/s` Peak PUT：约 24 PB Raw、8 节点、每节点 2 × 400G NIC、256 MiB Object，使用 Warp；文档称 16 个阶段无错误，并明确这些是纯 TCP 数字。
- `229 GiB/s` Average GET、`118 GiB/s` Average PUT：8 节点、每节点 2 × 400GbE、非阻塞 400G Fabric、64 MiB Object、4096 并发；Peak Second 为 237 和 126 GiB/s。

同一官方页面明确提醒：Drive、Object Size、Network 与 Client Count 都会改变结果，应把这些数字用于合理性检查，而不是预测自己的部署。

`[禁止外推]` 这些是 MinIO AIStor 在高端八节点硬件上的对象读写结果，不是 NoteWeave 所用自建 MinIO 的结果，也不包含 MySQL、Kafka、解析、Embedding、Elasticsearch 和业务状态 Finalize。不能写进 NoteWeave 简历。

### 6.4 NoteWeave 应怎样测对象存储

官方 MinIO Warp 仓库支持固定或随机 Object Size、并发、Mixed Workload、多 Client、Latency Percentile 和 TTFB。NoteWeave 应按真实资料分布而不是只用大对象顺序流：

| 指标 | 计算方式 | 业务意义 |
|---|---|---|
| PUT Success Rate | 成功 PUT / 总 PUT | 对象落盘是否可靠 |
| PUT P95 / P99 | 从请求发送到成功响应的高分位耗时 | 上传阶段尾延迟 |
| GET TTFB P95 | GET 发出到首字节的 P95 | Worker 开始解析前的等待 |
| Byte Throughput | 成功传输字节 / 稳态时间 | 大文件链路容量 |
| Object Throughput | 成功对象数 / 稳态时间 | 小文件与多资料场景容量 |
| Digest Mismatch Rate | Digest 不一致对象 / 已校验对象 | 完整性而非速度 |

测试 Manifest 至少记录 Server 数、Drive、Network、Erasure/Replica、Object Size 分布、并发、TLS、Client 数、Duration、错误率和 P50/P95/P99。

## 7. Elasticsearch：Refresh、Reindex 与业务 Ready

### 7.1 Refresh 只定义搜索可见性

Elastic 官方 Refresh 文档说明：

- Elastic Stack 的默认 `index.refresh_interval` 是 `1s`。
- Elastic Cloud Serverless 的默认值是 `5s`。
- `refresh=true` 立即 Refresh 相关 Primary 和 Replica Shard，但会产生小 Segment，对 Index、Search 和 Merge 都有成本。
- `refresh=wait_for` 等待自然 Refresh，不主动强制；Listener 用尽时也可能退化为强制 Refresh。
- `refresh=false` 是默认值，请求返回时修改可能尚不可搜索。

因此，“Elasticsearch 默认一秒 Refresh”不能推导“资料一秒内可检索”。业务端到端还包含：

```text
Upload Commit
  → Outbox Publish
  → Kafka Wait
  → Object GET
  → Parse / Chunk / Embedding
  → ES Bulk Index
  → Refresh Visibility
  → MySQL Finalize Ready
```

### 7.2 Reindex 不是复制整个 Index

Elastic Reindex API 官方文档明确：

- Source 文档必须启用 `_source`。
- Destination 应在调用前配置好。
- Reindex 不复制 Source 的 Setting 或关联 Template；Mapping、Shard 和 Replica 要提前配置。
- 默认内部版本策略会覆盖 Destination 中相同 ID 的文档；可用 External Version 或 `op_type=create` 改变冲突语义。
- 默认 Version Conflict 会中止任务；`conflicts=proceed` 只改变冲突处理，不改变其他错误。

对 NoteWeave 的含义是，Backfill 或 Rebuild 完成不能只看 `_reindex` 返回 200。至少还要验证：

- 目标 Mapping、Analyzer、Vector Dimension 和 Projection Version 正确。
- 期望 Chunk 数与实际文档数一致。
- Current Alias 只指向完成校验的新版本。
- 旧 Snapshot 的晚到事件不能覆盖新版本。
- 抽样检索能命中正确 Workspace、Source 和 Snapshot。

### 7.3 Elastic 官方 Benchmark 数字

Elastic 官方 Rally 仓库把 Rally 定义为 Elasticsearch Macrobenchmark Framework，并强调可复现数据。其 README 的 Elasticsearch 6.0 `geonames` 示例输出包括：

- `index-append` Median Throughput：`39,137.5 docs/s`。
- `index-append` P99 Latency：`1,874.89 ms`。
- Index Size：约 `2.60 GB`。

这个示例的价值在于展示正确报告格式：Throughput、Latency Percentile、Service Time、Index Size、Refresh、Merge 和 GC 应一起看。它不是当前 Elasticsearch 版本的通用性能承诺；README 片段也没有提供足够硬件条件，不能拿来与 NoteWeave 比高低。

### 7.4 NoteWeave 的可比条件

若要报告 Projection 性能，至少固定：

```text
Elasticsearch 版本、节点、CPU、内存、磁盘
Shard / Replica / Refresh Interval
Mapping、Analyzer、Dense Vector Dimension
Bulk Size、Client 并发、Document 平均字节数
是否生成 Embedding，Embedding 是否计入时间
Index-only 与 Upload-to-Searchable 两套口径
稳态时长、失败率、Merge / GC / Reject
```

只报 `docs/s` 会把 200 字节 Metadata 文档和带向量的 Chunk 当作同一工作量，不具有比较意义。

## 8. DLQ、Redrive 与 Reconciliation

### 8.1 DLQ 的官方边界

Confluent Cloud Connector 文档把 DLQ 用于隔离无效 Record，例如 Sink 期待 Avro 但收到 JSON 的 Serde Error。Connector 继续处理其他 Record，并把异常类、消息和 Stack Trace 等信息放到 DLQ Record Header 中供排障。

这说明 DLQ 的核心价值是：

- 防止一条 Poison Record 永久阻塞整条流。
- 保留原消息与失败上下文。
- 允许修复配置或数据后再处理。

它不能证明：

- 失败消息已经完成业务处理。
- Redrive 一定安全。
- 错误不会重复进入 DLQ。
- 当前真源与投影已经一致。

Confluent Cloud 的这段文档针对 Managed Sink Connector 的 Serde Error。NoteWeave 的任务 DLT 还包含解析、投影、版本或外部依赖失败，两者只能比较“隔离和诊断方法”，不能把错误语义视为相同。

### 8.2 Retry、Redrive、Compensation、Reconciliation 的区别

| 机制 | 适用问题 | 前置条件 | 完成证明 |
|---|---|---|---|
| Retry | 暂时性超时、限流、短时不可用 | 操作幂等，有限次数与退避 | 本次任务成功或进入终态 |
| Redrive | 根因修复后的 Dead Message 重放 | 保留原身份，重新校验版本和权限 | 重放后业务终态成功 |
| Compensation | 跨存储部分成功，需要撤销或失效 | 有可执行的逆操作或隔离状态 | 旧副作用不再对在线读可见 |
| Reconciliation | 真源与投影长期漂移或漏处理 | 能枚举双方、定义期望状态 | 差异归零或全部进入解释过的豁免集 |

Debezium 的 Ad hoc Incremental Snapshot 是一个可借鉴的修复机制：它可以在 Streaming 期间按 Chunk 扫描表，并用 Snapshot Window 与 Watermark 对相同 Primary Key 的 Snapshot 和 Stream Event 去重。它证明“增量回扫可以与在线流并行”，但不等于 NoteWeave 已实现相同算法。

### 8.3 NoteWeave 推荐的对账指标

以下是 `[生产待验证]` 的指标定义，不是当前成绩：

```text
ExpectedProjection
  = MySQL 中应在线可检索的 Current Snapshot 集合

Missing
  = ExpectedProjection 中不存在对应 ES 文档或完整 Chunk 集的项

Stale
  = ES 中 Projection Version 落后于 MySQL Current Version 的项

Orphan
  = ES 中仍在线可见，但 MySQL 真源不存在、已删除或已非 Current 的项

Drift Rate
  = (Missing + Stale + Orphan) / ExpectedProjection

Repair Success Rate
  = 修复后通过终态校验的差异项 / 本轮尝试修复的差异项

Convergence Time
  = 从差异首次产生到再次通过对账的时长
```

还应同时报告：

- DLQ / DLT Count 与 Oldest Age。
- Redrive Success Rate 和再次失败分类。
- Outbox Oldest READY Age。
- Projection Lag P50、P95、P99。
- 删除提交到所有在线读取不可见的 P95、P99。

## 10. NoteWeave 真正可用于简历的测量设计

外部项目的数字最适合用来选择指标，而不是充当成绩。资料底座第一轮应只测一组主指标与三组护栏：

### 10.1 主指标：Upload-to-Searchable P95

```text
Upload-to-Searchable
  = 第一条带正确权限和 Current Snapshot 的检索成功时间
    - Upload Complete 事务提交时间
```

必须说明文件类型、文件大小分布、Chunk 数、是否含 Embedding、并发上传数、机器和运行次数。

为什么比 Kafka Latency 更适合简历：它覆盖用户真正等待的完整路径，且能暴露 Worker、Provider 和 ES 的瓶颈。

### 10.2 可靠性护栏：Fault-window Recovery Rate

对固定故障注入集分别在以下窗口杀进程或制造超时：

```text
业务与 Outbox 提交后、发送前
Kafka 已接收、Outbox ACK 前
Consumer 业务写成功、Offset 提交前
ES Bulk 成功、MySQL Finalize 前
删除状态提交、MinIO / ES Cleanup 前
```

```text
Recovery Rate
  = 最终恢复为唯一正确业务终态的 Case / 总故障 Case
```

还要单列 Duplicate Delivery Count 和 Duplicate Business Effect Count。前者可以大于零，后者应为零；这比笼统说“零重复”更专业。

### 10.3 一致性护栏：Drift Rate 与 Convergence Time

故意制造 Missing、Stale 和 Orphan Projection，运行对账修复，再报告差异率、修复成功率和 P95 收敛时间。只有这样，“最终一致”才从口号变成可验证承诺。

### 10.4 资源护栏：稳态吞吐与 Backlog

```text
Stable Task Throughput
  = 在 Kafka Lag 和 Oldest READY Age 不持续增长的窗口内
    每秒进入正确终态的 Snapshot 数
```

同时报告 Worker CPU/Memory、MySQL Pool、MinIO Error、ES Reject、Provider Limit 和重试放大率。Producer 能打入多少消息不是业务吞吐。

### 10.5 成绩进入简历前的证据门槛

每个数字必须有：

- Git Commit 与配置 Manifest。
- 数据集与文件大小分布。
- 机器、中间件和 Provider 版本。
- Warm-up、稳态窗口、重复次数和统计分位。
- 成功判定与错误分类。
- 原始日志、指标快照或可复跑脚本。

当前没有这些证据时，只能写“设计并实现了可恢复链路、幂等状态机、投影补偿与对账入口”，不能写具体提升百分比、吞吐或 SLA。

## 11. 大厂面试官会继续追问什么

### 11.1 Outbox 保证消息不会丢吗

合格回答：它保证业务提交与发送意图同事务，避免提交后没有发送记录；Dispatcher 与 Kafka 仍可能处于结果未知，消息可能重复。是否长期不丢还取决于 Outbox 保留、Publisher 恢复、Kafka Durability、Consumer 终态和对账。

### 11.2 为什么当前不用 Debezium

合格回答：当前规模下 Polling 更容易控制 Claim、Lease、Attempt、DLQ 和 Redrive，部署依赖更少。迁移由 Oldest READY Age 和数据库轮询成本触发。Debezium 会减少表轮询并贴近 Binlog，但引入 Connector、Offset、Schema History、日志保留和 Snapshot 治理，Consumer 幂等仍保留。

### 11.3 Kafka Producer 已幂等，为什么 Consumer 还要幂等

合格回答：Producer 幂等只约束写入 Kafka Log 的重试；Consumer 可能在外部副作用成功、Offset 提交前崩溃。外部系统不在 Kafka Transaction 内，所以同一 Record 仍会被再次处理。

### 11.4 为什么不用 Kafka Transaction 替代 Outbox

合格回答：Kafka Transaction 擅长原子提交 Kafka 输出与 Kafka Offset，普通 MySQL 业务事务不自动参与。若先提交数据库再提交 Kafka 仍有双写窗口，先 Kafka 后数据库也一样。Outbox 用本地事务固定业务事实和发送意图。

### 11.5 S3 已经强一致，为什么还需要 Upload 状态和 Cleanup Task

合格回答：强一致是成功对象操作后的单 Key 可见性，不是数据库与对象的跨系统原子性。应用仍需区分对象存在、业务引用已提交、资料在线可见和删除清理已完成。

### 11.6 ES 默认一秒 Refresh，能否承诺一秒可检索

合格回答：不能。一秒只覆盖文档已经写入后的默认搜索可见周期，还要加 Outbox、Kafka、对象读取、解析、Embedding、Bulk 和 Finalize。业务 SLO 应实测 Upload-to-Searchable P95/P99。

### 11.7 Reindex 返回成功，为什么还要对账

合格回答：Reindex 不复制 Setting 和 Template，且版本冲突、旧事件晚到、部分业务 Finalize 都可能造成错误 Current Projection。完成条件应包含 Mapping、Version、Count、Alias 和抽样检索校验。

### 11.8 消息进了 DLQ 是否算不丢

合格回答：只能说失败 Record 被保留并可诊断，不能说业务已完成。还要看 DLQ Oldest Age、根因修复、Redrive 结果和对账差异是否收敛。

### 11.9 为什么不用外部厂商吞吐证明方案性能

合格回答：厂商数字的硬件、数据大小、并发、Batch 和统计对象不同。它们用于确定测试方法与数量级合理性；项目成绩必须来自自己的 Manifest。Kafka 605 MB/s、S3 每 Prefix Request Rate、MinIO 大对象 GiB/s 和 ES docs/s 不能互相换算。

### 11.10 如何证明“最终一致”不是无限等待

合格回答：定义最大消息年龄、Projection Lag、Drift Rate、DLQ Age 和 P95 Convergence Time；给出告警预算、对账周期、Redrive Runbook 和超过预算后的人工处置。没有收敛时间与差异检测，就只有 Eventually，没有 Consistent。

## 12. 可直接背诵的取舍回答

> 我没有把 Kafka Exactly-once 当作跨 MySQL、MinIO 和 Elasticsearch 的全局事务。AWS 的 Transactional Outbox 指南本身就提醒 Publisher 可能重复，Debezium 崩溃恢复也可能从旧 Offset 重放；Kafka 官方则明确说外部系统需要自己协调输出和 Offset。所以我选择在 MySQL 本地事务里固化业务状态与 Outbox，用 Kafka 至少一次承接跨进程传输，再以 Message ID、Snapshot Version 和条件更新做业务幂等。MinIO 保存原件，ES 只是可重建投影；DLQ 负责隔离，最终由 Redrive 和对账证明收敛。
>
> 我也不会拿厂商 Benchmark 当项目成绩。Confluent 的 605 MB/s 来自三台 NVMe Broker、100 Partition 和 1 KB Message；MinIO 的 268 GiB/s 来自八节点 400G 网络和 256 MiB Object；Elastic Rally 的 39K docs/s 是 ES 6.0 `geonames` 示例。它们告诉我如何固定硬件、消息大小、并发、可靠性和统计分位，但 NoteWeave 真正该测的是 Upload-to-Searchable P95、故障恢复率、重复业务副作用数、漂移率和收敛时间。
