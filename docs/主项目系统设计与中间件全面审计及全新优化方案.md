# NoteWeave v2 主项目系统设计与中间件全面审计及全新优化方案

> 审计日期：2026-07-12  
> 审计对象：`backend`、`frontend`、`workers/research-worker`、`workers/artifact-worker`、Flyway 迁移、`docker-compose.yml` 及相关架构文档  
> 文档性质：审计证据与架构推导来源，不再作为唯一施工入口  
> 正式目标架构：`docs/NoteWeave-v2目标系统架构与功能中间件设计.md`  
> 正式改造方案：`改造计划/NoteWeave-v2现有系统适配与改造实施方案.md`

## 1. 执行摘要

当前项目的产品方向是成立的：以 Workspace 为边界，Java 保存业务真相，Python Worker 执行重型 Research/Artifact 任务，MySQL、Kafka、MinIO、Elasticsearch 分别承担业务数据、消息、对象和检索职责。这一大方向无需推倒重来。

真正的问题是：项目在快速增加能力时，按功能纵向打通了很多闭环，但横向基础能力没有及时收敛。现在已经出现多套彼此相似但语义不同的实现：

- QA、Note、Wiki 三条回答链路共用一个入口，却没有统一的策略契约、检索计划、证据包和回答运行模型；
- Source、Wiki、Research、Artifact 都称为“Task/Outbox”，实际却有四套不同的投递、重试、状态推进和失败处理方式；
- Chat SSE 和 Task SSE 名义上是流式接口，实际均先在服务端构造完整字符串再一次性返回；
- Java 与 Python 都在保存 Artifact 运行状态或版本信息，业务真源边界不够清晰；
- MySQL、Kafka、ES、Redis 已全部引入，但有些中间件未真正承担设计中声明的职责，有些接入方式会产生数据丢失或错误状态。

因此，优化重点不应是继续添加更多 Service、DTO 和状态字段，而应先建立四个统一内核：

1. **统一执行控制面**：`Execution / Run / Attempt / Event / Outbox`；
2. **统一回答管线**：`AnswerStrategy + RetrievalPlan + EvidenceBundle + AnswerRun`；
3. **统一资料处理与检索投影**：MySQL 真源、MinIO 原文、ES 检索投影、明确的索引确认状态；
4. **明确的模块边界与端口适配器**：领域代码不直接感知 Kafka、ES、MinIO、HTTP Worker 的具体实现。

最终建议不是“大拆微服务”，而是：

> **Java 先收敛为边界清晰的模块化单体，Research Worker 与 Artifact Worker 保持独立计算平面；用版本化命令契约和统一 Execution 控制面连接两者。**

## 2. 审计方法、范围与证据口径

本次审计使用了以下方法：

- 盘点 211 个 Java 主源码文件、100 个 Python 文件、24 个 TypeScript/TSX 文件；
- 追踪 Chat、Source、Wiki、Research、Artifact、Memory、Task 的创建、执行、回调与持久化链路；
- 对照 `application.yml`、`pom.xml`、Python Settings、Docker Compose 和 Flyway；
- 检查核心类体积、依赖方向、事务边界、异常处理、状态推进、幂等与中间件降级；
- 实际执行构建与测试。

验证结果：

| 子项目 | 结果 | 说明 |
|---|---:|---|
| Java Backend | **失败** | 主代码可编译，但测试编译失败；两个 Worker HTTP Client 测试仍使用旧版 `NoteWeaveProperties` 构造参数 |
| React Frontend | **通过** | 10 个测试文件、40 个测试通过；生产构建通过，单 JS 产物约 465 KB（gzip 约 134 KB） |
| Research Worker | **通过** | 162 个测试通过 |
| Artifact Worker | **通过** | 192 个测试通过 |

文档中的问题分三类：

- **已证实缺陷**：现有代码即可证明会失败、丢消息、错误推进状态或越权；
- **结构性问题**：当前规模已经造成巨型类、重复语义或修改扩散；
- **演进风险**：单机原型可用，但进入多实例、多用户或生产负载后会失效。

## 3. 当前系统真实架构

```text
React SPA（单一 App.tsx 承担绝大多数页面与状态）
        |
        | REST + “字符串式 SSE”
        v
Java Spring Boot 主系统
  ├─ Workspace / Conversation / Chat / Note / Wiki
  ├─ Source / Upload / Citation / Memory
  ├─ Task / TaskEvent / TaskOutbox
  ├─ ResearchRun / ArtifactJob 业务真源
  └─ Worker Callback / Outbox Dispatcher
        |
        ├─ MySQL：业务表、运行表、事件、outbox
        ├─ MinIO：source / derived / export
        ├─ Elasticsearch：当前仅 QA 的 BM25 文本投影
        ├─ Kafka：资料处理、Wiki、Research 投递
        └─ Redis：已引入依赖和容器，但主代码无实际使用
             |
             ├─ Python Research Worker
             └─ Python Artifact Worker
```

### 3.1 当前设计中值得保留的部分

审计并不否定现有全部设计，以下基础应保留：

- Workspace 是资料、会话、Wiki、Research、Artifact 的统一边界；
- Citation 和 Evidence 被视为一等对象，而不是只在最终文本中拼引用；
- Java 负责业务真源、Python 负责 AI 密集型执行的分工基本正确；
- 已经引入 TaskEvent、Outbox、Worker Callback Receipt、Checkpoint、Artifact Version 等生产化概念；
- ObjectStorage 已有 `ObjectStorage` 端口和 Local/MinIO 两种实现，是少数边界清晰的基础设施抽象；
- 两个 Python Worker 的测试数量和行为覆盖明显优于普通原型项目；
- Artifact 已经开始形成 Skill、Capability、Verifier、Repair、Writeback 等可扩展模型。

问题主要在这些良好概念没有被系统级复用，导致“概念统一、代码分裂”。

## 4. P0：必须先处理的正确性与安全问题

### P0-1 Backend 当前测试无法编译

`NoteWeaveProperties` 已增加 `Llm` 配置，但 `HttpArtifactOutboxPublisherTest` 和 `HttpArtifactWorkerControlClientTest` 仍按旧构造器实例化。当前 `mvn test` 在测试编译阶段直接失败。

影响：

- Java 侧无法形成可信回归基线；
- 后续重构没有安全网；
- CI 即使存在也无法作为合并门禁。

建议：先修复测试构造器，并新增一个配置工厂/Fixture，禁止每个测试手工拼完整配置 record。

### P0-2 Chat 持久化 SQL 与数据库迁移不一致

`ChatService.persistStreamedContent` 更新 `conversation_message.updated_at`，但 `V005__create_conversation_tables.sql` 的 `conversation_message` 没有该列。

证据：

- `backend/src/main/java/com/noteweave/chat/ChatService.java:161`
- `backend/src/main/resources/db/migration/V005__create_conversation_tables.sql:23`

只要真正启用 LLM 并完成一次流式写回，就会在运行期失败。应新增后续迁移补列，不能再改已经发布的 V005。

### P0-3 Elasticsearch 关闭时的 Spring Bean 条件不完整

`ElasticsearchConfig` 在 `noteweave.elasticsearch.enabled=false` 时不创建 `ElasticsearchClient`；但 `ElasticsearchIndexer` 仍是无条件 `@Component`，并强依赖该 Client；`RetrievalService` 又强依赖 `ElasticsearchIndexer`。

证据：

- `backend/src/main/java/com/noteweave/infra/ElasticsearchConfig.java:27`
- `backend/src/main/java/com/noteweave/infra/ElasticsearchIndexer.java:31`
- `backend/src/main/java/com/noteweave/chat/RetrievalService.java:31`

这会使“关闭 ES 后降级到 MySQL”的设计在容器创建阶段就可能失败。应将 ES Adapter 整体条件化，并提供 `NoopSearchIndex`，业务层只依赖 `SearchIndex` 端口。

### P0-4 同一 Kafka Topic 上的两个不同订阅者使用同一个 Consumer Group

`KafkaTaskConsumer.onSourceIndex` 与 `ElasticsearchIndexer.onSourceIndexEvent` 同时监听 `noteweave.source.index`，且都使用 `${spring.kafka.consumer.group-id}`。

证据：

- `backend/src/main/java/com/noteweave/infra/KafkaTaskConsumer.java:66`
- `backend/src/main/java/com/noteweave/infra/ElasticsearchIndexer.java:62`

Kafka 同组消费者是竞争消费，不是广播。结果是索引事件可能被只写日志的 `KafkaTaskConsumer` 抢走，ES 根本收不到。必须删除空订阅者，或为不同投影器使用不同 group，例如：

- `noteweave-es-index-projector-v1`
- `noteweave-source-observer-v1`

### P0-5 Kafka 消费失败被吞掉，Record 仍可能被提交

`KafkaTaskConsumer.handle` 捕获全部异常后只记录日志，不重新抛出；容器使用 `AckMode.RECORD`。因此 handler 失败后消息仍会被当成已处理。

证据：

- `backend/src/main/java/com/noteweave/infra/KafkaConfig.java:76`
- `backend/src/main/java/com/noteweave/infra/KafkaTaskConsumer.java:109`

类似问题还存在于 `ElasticsearchIndexer`：索引失败被捕获，消息不重投。应统一错误处理器、指数退避和 DLT，只有业务幂等写成功后才确认消费。

### P0-6 Source 在 ES 成功前就被标记为 INDEXED

`SourceParseService` 在事务中逐 chunk 异步发布索引事件，随后立即把 `source.index_status` 和 `source_snapshot.index_status` 写成 `INDEXED`。Kafka 投递失败、事件被错误 group 消费或 ES 写入失败时，数据库仍显示已索引。

证据：

- `backend/src/main/java/com/noteweave/source/SourceParseService.java:67`
- `backend/src/main/java/com/noteweave/source/SourceParseService.java:90`

正确状态应为：

```text
UPLOADED -> PARSING -> PARSED -> INDEX_PENDING -> INDEXING -> INDEXED
                                      |             |
                                      +-----------> INDEX_FAILED
```

只有 Index Projector 完成该 snapshot 的全部 chunk 并回写确认后，才允许进入 `INDEXED/READY`。

### P0-7 Source Outbox 是“写 Outbox + 同事务直接发 Kafka”，不是 Transactional Outbox

`UploadService.completeUpload` 先写 `task_outbox`，随后直接调用 `publishSourceParse`。发送发生在数据库事务提交前，且没有统一 poller 处理 Source/Wiki topic。

证据：

- `backend/src/main/java/com/noteweave/upload/UploadService.java:142`
- `backend/src/main/java/com/noteweave/upload/UploadService.java:147`

可能出现：

- Kafka 已收到，但 DB 回滚；
- DB 已提交，但 Kafka 发送失败，READY 永久滞留；
- 同一任务既被直接发送又被未来 poller 重复发送。

正确做法是业务事务只写 Outbox，由唯一通用 Dispatcher 在事务外投递。

### P0-8 四套 Outbox 可靠性语义不一致

- Artifact Dispatcher 有 lease、attempt、backoff、dead-letter、redrive、metrics；
- Research Dispatcher 查询 READY 后直接 publish，再更新 SENT，无 lease、重试和调度器；
- Source/Wiki 写 Outbox 后又直接 publish；
- `KafkaTaskPublisher` 异步发送失败只记日志，不反馈调用者。

这不是代码重复而已，而是相同业务概念拥有不同可靠性保证。应统一为一个 `OutboxDispatcher` 内核，topic 只决定 `DeliveryAdapter`，不决定可靠性算法。

### P0-9 外部 API 没有用户认证和 Workspace 授权

主系统未引入 Spring Security；`WorkspaceService` 使用固定 `local-user`；绝大多数 API 只检查 workspace 是否存在，不检查当前主体是否为成员。

证据：

- `backend/src/main/java/com/noteweave/workspace/WorkspaceService.java:14`
- `backend/pom.xml`

在单用户本地 Demo 中可以接受，但任何多人部署都会形成 IDOR：知道 workspaceId 即可访问资料、Research、Artifact 和 Wiki。需要统一 `ActorContext` 和 `WorkspaceAuthorizer`，Controller 不再接受“裸 workspaceId 即授权”。

### P0-10 Worker 内部接口默认可能无认证

Java 和 Artifact Worker 的内部 token 默认为空；Artifact Worker 只有在 token 非空时才校验。Research Worker 的 `/debug/run-task` 与 `/tasks/{task_id}/run` 当前没有内部认证中间件。

证据：

- `backend/src/main/resources/application.yml:39`
- `workers/artifact-worker/app/main.py:125`
- `workers/research-worker/app/main.py:23`
- `workers/research-worker/app/main.py:32`

建议：非 test/dev profile 下 token 为空直接拒绝启动；Research/Artifact 共用一套 mTLS 或短期签名 token 约定；debug route 只在显式 debug profile 注册，而不是运行时返回 404。

### P0-11 已执行的 Flyway 迁移被原地修改

当前工作区修改了 V002、V004、V005、V006、V007、V008、V011、V012。已在环境中执行过的 Flyway 迁移应视为不可变，否则会产生 checksum mismatch，也无法保证新旧环境结构一致。

建议：

- 恢复历史 migration；
- 兼容性修改全部追加为 V025+；
- CI 增加“禁止修改已发布迁移”的检查；
- H2/MySQL 类型差异不要通过修改历史 SQL 解决，应使用 MySQL Testcontainers 或 Flyway placeholder/vendor migration。

### P0-12 Source 解析事务因同类自调用而不会生效（已修复，2026-07-12）

原实现中 `parseAndIndexAsync` 同类调用 `parseAndIndex`，Spring 代理无法建立事务。现已由 `TransactionTemplate` 显式包裹写入阶段，异常继续抛回 Kafka listener，使容器 retry/DLT 生效，不再吞错后提交 offset。

证据：

- `backend/src/main/java/com/noteweave/source/SourceParseService.java:46`
- `backend/src/main/java/com/noteweave/source/SourceParseService.java:100`

应把事务写入部分移到独立 `SourceParseResultCommitter`，或由 Application Handler 使用 `TransactionTemplate` 明确包裹；对象读取和解析在事务外，短事务只提交解析结果与 outbox。

## 5. P1：核心架构与代码设计问题

### P1-1 三种回答模式只有入口统一，没有管线统一

`ChatService.buildAnswerDraft` 用 switch 直接选择 `buildQaAnswer`、`buildNoteAnswer`、`buildWikiAnswer`。三条链路返回相同的私有 `AnswerDraft`，但检索、证据、Prompt、验证、引用绑定和 trace 没有正式契约。

证据：`backend/src/main/java/com/noteweave/chat/ChatService.java:195`

后果：

- 新增模式必须修改 ChatService；
- QA 调 `RetrievalService`，Wiki 直接跨到 `KnowledgeService`，Note 又在 Retrieval 内形成第二套复杂系统；
- 无法统一统计召回率、引用覆盖率、耗时、token、失败原因；
- 无法为同一请求动态选择轻/重执行路径；
- 单元测试只能围绕大 Service，而不是稳定策略合同。

应引入 `AnswerModeStrategy` 注册表，但不要把所有行为塞进一个万能接口。统一的是骨架和数据合同，差异通过可组合策略表达，详见第 9 节。

### P1-2 “生成答案”没有一等运行对象

当前用户消息和 Assistant 占位消息会被保存，但没有 `answer_run`/`execution_run` 记录。`assistant_request_id` 既像请求 ID 又像流地址，无法表达：

- PLANNING / RETRIEVING / GENERATING / VERIFYING / COMPLETED；
- 重试、取消、超时、模型与 Prompt 版本；
- 检索计划、候选证据、最终证据包；
- 首 token 延迟、总耗时、token/cost；
- 同一用户消息的重新生成版本。

建议把一次回答建模成 `AnswerRun`，同时挂接统一 `Execution`。它可以同步执行，不等于必须进入 Kafka。

### P1-3 当前 SSE 不是真流式

Chat Controller 返回 `String`；`ChatService` 等 LLM 调用完成并把所有 delta 拼进 `StringBuilder` 后，Controller 才能返回响应。Task SSE 也先把数据库中全部事件拼成 String。

证据：

- `backend/src/main/java/com/noteweave/chat/ChatController.java:29`
- `backend/src/main/java/com/noteweave/chat/ChatService.java:82`
- `backend/src/main/java/com/noteweave/task/TaskService.java:239`

这会导致首 token 延迟等于完整生成耗时，也无法持续推送新 TaskEvent。无需把整个项目改成 WebFlux，可先使用 `SseEmitter` + 独立生成线程；若后续统一 Reactive LLM Client，再局部使用 Flux。

### P1-4 Chat 在 LLM 调用前保存的是模板答案，不是运行状态

系统先拼一份很长的 Markdown 模板，写入 Assistant Message，再在 stream 请求中把它作为 LLM prompt；LLM 未启用时又把模板伪装成流式回答。

这混合了四个概念：Prompt Blueprint、Fallback Answer、Assistant Message、Run State。应分别保存：

- `prompt_snapshot`：审计用；
- `answer_run.status`：运行状态；
- `message_revision`：最终或部分输出；
- `fallback_policy`：无模型/无证据时如何回答。

### P1-5 `message_seq` 存在并发竞争

`nextMessageSeq` 使用 `max(message_seq) + 1` 后再插入。两个并发请求会得到相同序号并撞唯一约束。

证据：`backend/src/main/java/com/noteweave/chat/ChatService.java:868`

应使用 Conversation 行锁、独立 sequence 字段的原子 update，或由数据库生成单调序号。

### P1-6 多个 God Class 已经成为修改热点

当前主要巨型文件：

| 文件 | 约行数 | 主要职责混合 |
|---|---:|---|
| `frontend/src/App.tsx` | 11,799 | API、状态、路由、聊天、Wiki、Research、Artifact、视图、格式化 |
| `ResearchRunService.java` | 3,902 | 命令、查询、持久化、映射、trace、checkpoint、report、source 回写 |
| `KnowledgeService.java` | 1,915 | Note/Wiki CRUD、图谱、统计、治理、索引、版本、引用 |
| `RetrievalService.java` | 1,783 | QA 检索、Note 候选、journal、关系传播、窗口、ranking、DTO |
| `ChatService.java` | 1,222 | 消息、上下文、三模式编排、Prompt、SSE、引用、启发式 NLP |
| `ArtifactJobService.java` | 1,107 | Job、Run、Version、Worker Input、回调、回写、trace 映射 |

这不是“文件长”这么简单，而是读取模型、写入模型、业务规则和基础设施代码没有分离。建议按 use case 拆 Command Handler / Query Service / Repository / Mapper，不要只是机械切成更多 `*Helper`。

### P1-7 Java 业务层普遍直接使用 JdbcTemplate

至少 21 个主源码文件直接依赖 `JdbcTemplate`。SQL 本身不是问题，问题是 Service 同时承担 SQL、事务、状态机和对象映射，导致：

- 领域约束散落在 update where 条件中；
- 同一表在多个 Service 中被直接更新；
- 查询优化和业务重构互相影响；
- 测试需要完整数据库才能验证简单规则。

建议保留 JDBC/jOOQ 风格，不强制切 JPA；但要引入模块内 Repository 端口和明确聚合写入口。

### P1-8 Task 状态机没有统一的合法迁移保护

`startTask` 只允许 PENDING -> RUNNING，但 `completeTask`、`recordProgress`、`recordWaiting`、`failTask` 多数按 id 无条件覆盖。完成后的任务仍可能被迟到回调改成 RUNNING/FAILED，且每次都插入事件。

证据：`backend/src/main/java/com/noteweave/task/TaskService.java:43-160`

需要显式状态机与 CAS：

```text
PENDING -> DISPATCHING -> RUNNING -> WAITING -> RUNNING -> SUCCEEDED
              |              |          |          |
              +--------------+----------+--------> FAILED
                                             +---> CANCELLED / TIMED_OUT
```

每次迁移必须校验 `from_status + version`，重复回调返回幂等成功，非法迁移记录审计而不是覆盖。

### P1-9 Task、ResearchRun、ArtifactJob 的状态重复且可能漂移

同一业务执行同时保存于 `task.task_status`、`research_run.status` 或 `artifact_job.status`，部分逻辑还包含 `artifact_job_run.status`。目前靠各 Service 手工同时更新，缺乏单一状态所有者。

建议：

- `execution_run` 是调度与生命周期真源；
- Domain Aggregate 只保存领域状态与 `execution_id`；
- 对外 Query View 联合展示，不在多个表重复保存同义状态，或明确一个是投影并可重建。

### P1-10 Research 与 Artifact Outbox 设计严重不对称

Artifact 已有生产化 dispatcher，Research 仍是手工 internal endpoint 驱动的简单 READY -> SENT。`ResearchOutboxDispatcherService` 还存在先 publish 再用条件 update SENT 的并发重复发送窗口。

证据：`backend/src/main/java/com/noteweave/worker/ResearchOutboxDispatcherService.java:21-47`

这说明不应继续分别维护 `ResearchOutboxDispatcherService` 和 `ArtifactOutboxDispatcherService`，而应提炼通用实现。

### P1-11 Source 解析器把所有上传内容当 UTF-8 文本

`SourceParseService.parseAndIndex` 直接 `new String(bytes, UTF_8)`。PDF、DOCX、PPTX、图片等会成为乱码或无意义 chunk。上传接口允许大文件，但解析能力没有按 MIME/扩展名路由。

应引入：

```java
interface DocumentParser {
    boolean supports(MediaType mediaType, String fileName);
    ParsedDocument parse(SourceBlob blob);
}
```

由 PDF、Office、Markdown、PlainText、OCR Adapter 分别实现，输出统一 `ParsedDocument -> Section -> Passage -> Locator`。

### P1-12 大文件上传和解析存在明显内存放大

上传完成时先把所有 chunk 从对象存储读回内存、合并成一个 `byte[]`，再写一份完整对象；解析又整文件读入内存并转 String。当前允许 128MB 请求，多并发时会形成数倍堆占用。

应使用流式合并、分段 hash、对象存储 multipart compose 和流式 parser；解析任务不能在 Web 请求事务内执行。

### P1-13 检索设计与文档声明不一致

当前 ES 查询是 `multi_match` BM25/fuzziness，没有 embedding、KNN 或真正 hybrid fusion；Note 主要使用 MySQL 拉取有限候选后在 Java 内启发式打分；Wiki 又直接走 Knowledge 表。

证据：

- `backend/src/main/java/com/noteweave/infra/ElasticsearchIndexer.java:132`
- `backend/src/main/java/com/noteweave/chat/RetrievalService.java:40`
- `backend/src/main/java/com/noteweave/chat/RetrievalService.java:159`

因此现状应准确称为“BM25 + 内存启发式重排原型”，不能称为完整 Hybrid RAG。目标方案见第 10 节。

### P1-14 QA 的 ES 结果逐条回查 Source，形成 N+1

每个 ES hit 调用 `loadSourceMeta` 查询 MySQL；Note/Research 的多个明细构造也存在类似 per-id 查询。应让索引文档带全展示元数据，或一次按 sourceId 批量加载。

证据：`backend/src/main/java/com/noteweave/chat/RetrievalService.java:47-116`

### P1-15 按 Workspace 建独立 ES Index 不利于规模扩展

当前 index 名是 `<prefix>_<workspaceId>`。Workspace 增长后会造成大量小索引和 shard 开销。更稳妥的是共享版本化索引，例如 `noteweave_passage_v3`，以 `workspace_id` 过滤并使用 routing；超大租户再单独分片/索引。

### P1-16 Redis 是未使用中间件

项目引入 `spring-boot-starter-data-redis`，Compose 也启动 Redis，但 Java 主代码没有 Redis 访问。未使用中间件增加部署、资源、故障面和认知成本。

两种合理选择：

- 当前阶段删除 Redis；
- 明确将其用于短生命周期能力：分布式限流、SSE 跨实例事件流、幂等短锁、热点缓存，并定义 TTL/降级策略。

不建议把业务真源或 Task 状态迁到 Redis。

### P1-17 Python Worker 的持久化和真源边界不清晰

Artifact Worker 默认 `artifact_repository_backend=memory`，同时还使用多个 JSON 文件保存 runtime、customization、wait queue，并存在多个进程内全局 dict。Java 又保存 ArtifactJob/Version/File/Trace。

影响：

- 多实例 Worker 各自看到不同状态；
- 容器迁移/并发写 JSON 可能丢状态；
- rollback/version 在 Java 与 Python 两侧语义可能漂移；
- 无法明确恢复时以哪一侧为准。

建议 Worker 只持有执行期 checkpoint/cache，Java/MySQL 是业务 Job、Version、Approval、Writeback Receipt 真源；大 checkpoint 写 MinIO，MySQL 保存 locator 和 checksum。

### P1-18 Worker 契约缺少统一版本和演进规则

Java DTO、Python Pydantic Model、Kafka payload 和 HTTP callback 是手工保持一致，已经出现 Java 配置构造器改动导致测试未同步的例子。需要 `schema_version`、`command_type`、`command_id`、`correlation_id`、`idempotency_key`，并以 JSON Schema/OpenAPI contract test 校验双端。

### P1-19 Frontend 是单文件应用，不具备可持续演进边界

`App.tsx` 约 11,799 行，包含大量领域类型、请求、轮询、派生状态、视图和格式化函数。现有 40 个测试主要覆盖拆出的纯函数，无法保护主页面复杂交互。

建议按 feature 划分：

```text
src/
  app/              路由、Provider、全局错误边界
  shared/api/       API client、SSE client、contract types
  features/chat/
  features/sources/
  features/wiki/
  features/research/
  features/artifact/
  entities/task/
```

并引入服务器状态管理层（如 TanStack Query）或轻量自研 query cache，避免几十个 `useEffect + setTimeout` 手工维护一致性。

### P1-20 列表查询缺少统一分页和轻重 DTO 边界

Research/Artifact/Wiki 的多个 list 接口会加载 trace、branch、cell、version 或派生摘要；数据增长后响应和查询数会线性甚至乘法增长。应统一 Cursor Pagination、List Projection 和 `include=` 扩展字段，禁止 list 接口默认组装完整运行详情。

### P1-21 运行可观测性有数据，但缺少统一关联模型

项目已有 TaskEvent、ResearchTrace、ArtifactRuntimeTrace、Micrometer 部分指标，但没有统一 correlation/causation、trace/span、模型调用统计和阶段耗时。建议每个 Execution 贯穿：

- `execution_id / attempt_id / command_id`；
- `correlation_id / causation_id`；
- `workspace_id / actor_id`；
- `model / prompt_version / token_usage / cost`；
- `stage / elapsed_ms / retry_count / error_code`。

日志使用结构化 JSON，接 OpenTelemetry；不要继续只增加各领域自定义 Trace DTO。

### P1-22 Memory 的“门控”目前主要是固定启发式，不是完整生命周期

`MemoryCandidateService` 以单个 signal 的 confidence 是否大于 0.70 作为 evidence gate；marginal utility 主要由 sourceType 的固定分数决定；staleness 在插入时直接写 `ACTIVE`；等价与冲突判断要求规范化后的字符串完全相等。`MemoryPromotionService` 又把通过规则的 Candidate 直接晋升，并写死 `local-user`。

证据：

- `backend/src/main/java/com/noteweave/memory/MemoryCandidateService.java:34-70`
- `backend/src/main/java/com/noteweave/memory/MemoryCandidateService.java:126-170`
- `backend/src/main/java/com/noteweave/memory/MemoryPromotionService.java:32-75`

这与文档中的 Graduated Memory 目标仍有距离。目标模型应明确四个独立决策：

1. `EvidenceEligibility`：来源数量、显式反馈、置信度和可追溯性；
2. `SemanticNeighborhood`：不是只靠调用方传入字符串，应有可版本化分类器和人工修正；
3. `Conflict/Staleness`：按 subject/key 和有效时间判断 supersede、conflict、expired；
4. `PromotionPolicy`：自动、需审批、禁止晋升三种结果。

Compiler 还应定义优先级和预算：USER > WORKSPACE、NEGATIVE > PREFERENCE、具体 neighborhood > COMMON、较新有效决策 > 旧决策；超过 token/条目预算时按效用截断。`MemoryCompilerService` 不应直接依赖 `ArtifactSkillCatalogService`，Artifact 模块应把已解析的 task neighborhood 作为输入传给 Memory Port。

### P1-23 Memory 使用日志与实际效果没有闭环

当前 `memory_usage_log` 能记录哪些 object 被编译，但没有记录某条控制是否真正进入 Prompt、是否影响结果、用户是否接受或撤销，也没有基于效果降低权重或自动过期。建议在 Answer/Research/Artifact 完成后记录 `MemoryApplicationOutcome`，但只用于治理和评估，不把模型生成结论反向自动晋升成事实或偏好。

## 6. P2：设计一致性与工程质量问题

### P2-1 状态和类型大量使用裸字符串

Java 中 PENDING、RUNNING、WAITING、COMPLETED、FAILED、READY、INDEXED 等状态字面量分散在 SQL 和 Service 中，统计超过 250 处。拼写正确不代表语义一致。应使用领域枚举 + DB check constraint + 集中 transition policy。

### P2-2 JSON 大字段正在替代清晰模型

`payload_json`、`metrics`、`runtime_trace`、`inputs_json`、`result_payload` 提供了快速演进能力，但当前很多 read path 反复 `Map<String,Object>` 转换、兼容旧 key、从 trace 反推结构。应区分：

- 高频查询/约束字段：正常列和表；
- 低频审计快照：JSON；
- 大型报告/checkpoint：MinIO blob + 元数据；
- 事件 payload：版本化 schema。

### P2-3 配置默认值偏向“静默运行”而非“安全失败”

数据库、MinIO 有固定开发凭据；内部 token 默认为空；MinIO bucket 创建失败只 warn；Kafka/ES 失败多处静默降级。应按 profile 区分：dev 可便利，prod 对关键依赖 fail-fast，对可降级依赖明确暴露 DEGRADED 健康状态。

### P2-4 Docker 镜像版本不应使用 `latest`

Kafka 使用 `bitnamilegacy/kafka:latest`，构建不可重现。所有镜像应固定 digest 或精确版本，并建立升级节奏。

### P2-5 测试金字塔失衡

Python 单测很多，但大量测试聚焦纯模型/局部 harness；Java 目前连 testCompile 都未通过；Frontend 主交互缺乏组件和 E2E 测试。建议补充：

- Testcontainers：MySQL + Kafka + MinIO + ES 的关键链路；
- Contract tests：Java/Python payload 双端兼容；
- 状态机 property tests；
- Outbox crash/retry/idempotency tests；
- Playwright：上传 -> 索引 -> 三模式回答 -> Research/Artifact 的冒烟链路。

### P2-6 方法和接口的设计规则尚未统一

当前有些跨模块能力没有接口（Service 互相注入），另一些仅有一个实现却为了形式创建接口；大量方法返回 `Map<String,Object>`，方法名也难以区分查询、命令和幂等语义。建议采用以下规则：

- 只有跨模块 Port、可替换基础设施和明确策略点定义接口；模块内普通类不为“面向接口”而制造一对一接口；
- Command 方法使用动词并返回领域结果，例如 `completeAttempt(command)`，不返回裸 Map；
- Query 方法无副作用，返回专用 Projection，禁止在 list mapper 中继续发查询；
- 外部 I/O 方法显式表达超时、幂等键和错误类型；
- `catch (Exception)` 只能出现在边界 Adapter，并必须转成可判定的 typed failure；
- Controller 只做协议解析、认证授权和调用 Use Case，不直接编排多个 Service；
- 单个方法中不得同时完成外部 I/O、跨聚合写入和事件发布；
- 跨模块 API 必须有包级可见性/架构测试保护，避免任意注入实现类。

### P2-7 事务边界覆盖了不应覆盖的 I/O，也漏掉了应原子化的提交

例如 Upload 在数据库事务内读取/写入对象存储并直接发 Kafka；Source 的事务又因自调用失效；Chat 的发送事务内执行复杂检索和 Memory 编译，持锁时间随资料规模增长。目标规则应是：

```text
准备/读取外部数据（事务外）
  -> 短事务提交聚合 + outbox
  -> 外部投递（事务外）
  -> 短事务确认投影/结果
```

跨 MySQL、MinIO、Kafka 不追求分布式事务，而使用 locator、outbox、幂等和补偿任务保证最终一致。

## 7. 根因总结

上述问题可归并为六个根因：

1. **以纵向功能交付为主，横向平台能力后补**：每个功能都自己实现 Task、Trace、Outbox、状态；
2. **数据结构先于领域边界增长**：不断加表、DTO 和 JSON 字段，但聚合所有者不清晰；
3. **“接口统一”停留在 Controller 入口**：三模式共享发送接口，但没有共享运行和证据合同；
4. **基础设施直接进入业务 Service**：JdbcTemplate、Kafka、ES、MinIO 调用与业务状态机混在一起；
5. **原型降级路径进入了正式路径**：字符串 SSE、模板答案、内存仓库、MySQL scan 被长期保留；
6. **文档目标领先于代码事实**：Hybrid Retrieval、异步 Task、Outbox 等名词已存在，但实现保证尚未达到该定义。

## 8. 全新目标架构

### 8.1 总体原则

- 不把 Java 主系统拆成大量微服务；
- Java 采用模块化单体，模块间只能通过公开 Application Port 或 Domain Event；
- Python Worker 是无业务真源的计算节点；
- MySQL 是业务真源，MinIO 是大对象真源，ES 是可重建投影，Kafka 是传输，Redis 只做短期协调；
- 普通 QA 保持低延迟，不因“统一 Task”强制绕 Kafka；
- 所有长短任务共享 Execution 生命周期、事件和可观测性。

### 8.2 推荐模块边界

```text
com.noteweave
  ├─ identity         Actor、Session、Workspace Authorization
  ├─ workspace        Workspace、Member、Policy
  ├─ source           Upload、Blob、Parse、Snapshot、Passage、Index Projection
  ├─ conversation     Conversation、Message、MessageRevision、Context
  ├─ answer           AnswerRun、Strategy、RetrievalPlan、EvidenceBundle
  ├─ knowledge        Note、WikiPage、KnowledgeVersion、KnowledgeGraph
  ├─ memory           Signal、Candidate、Object、ControlPack
  ├─ research         ResearchRun 领域与 Worker Contract
  ├─ artifact         ArtifactJob、Run、Version、File、Writeback
  ├─ execution        Execution、Attempt、Event、Outbox、Lease、Retry
  └─ platform
       ├─ persistence
       ├─ messaging
       ├─ search
       ├─ objectstorage
       ├─ llm
       └─ observability
```

每个模块内部采用轻量六边形结构：

```text
api -> application -> domain <- ports <- adapters
```

不要求每个 CRUD 都建立复杂 DDD 聚合，但状态复杂、存在并发与重试的 Execution、Source、Research、Artifact 必须有明确聚合所有者。

### 8.3 控制面与计算面

```text
                         ┌─────────────────────────────┐
用户请求 ──> Java API ──>│ Execution Control Plane     │
                         │ command / run / attempt     │
                         │ state / event / outbox      │
                         └──────────┬──────────────────┘
                                    │
                    ┌───────────────┴────────────────┐
                    │                                │
             Inline Executor                  Remote Executor
        QA / 简单 Note / 简单 Wiki       Research / Artifact / 重型 Answer
                    │                                │
                    └───────────────┬────────────────┘
                                    v
                         Domain Result Committer
                    Message / Version / Report / Citation
```

统一控制面不等于所有东西都走同一队列。它统一的是：标识、状态、重试、事件、取消、幂等、预算和审计。

## 9. 三种检索与回答链路的统一方案

### 9.1 统一的数据合同

```java
public record AnswerCommand(
        String commandId,
        String workspaceId,
        String conversationId,
        String userMessageId,
        AnswerMode mode,
        String question,
        ContextSnapshot context,
        AnswerOptions options
) {}

public record RetrievalPlan(
        List<RetrievalStep> steps,
        EvidencePolicy evidencePolicy,
        Budget budget
) {}

public record EvidenceBundle(
        List<EvidenceItem> selected,
        List<EvidenceItem> rejected,
        CoverageReport coverage,
        RetrievalTrace trace
) {}

public record AnswerResult(
        String markdown,
        List<CitationBinding> citations,
        VerificationResult verification,
        List<SuggestedWriteback> writebacks
) {}
```

### 9.2 策略接口

```java
public interface AnswerModeStrategy {
    AnswerMode mode();
    RetrievalPlan plan(AnswerCommand command, MemoryControlPack controls);
    PromptBlueprint compose(AnswerCommand command, EvidenceBundle evidence);
    AnswerResult postProcess(GeneratedAnswer answer, EvidenceBundle evidence);
}
```

同时把检索器拆成可组合端口：

```java
public interface Retriever {
    RetrievalKind kind();
    CandidateSet retrieve(RetrievalQuery query);
}

public interface EvidenceRanker {
    EvidenceBundle select(CandidateSet candidates, EvidencePolicy policy);
}

public interface AnswerGenerator {
    GeneratedAnswer generate(PromptBlueprint prompt, TokenSink stream);
}

public interface AnswerVerifier {
    VerificationResult verify(GeneratedAnswer answer, EvidenceBundle evidence);
}
```

### 9.3 三种模式只定义差异

| 阶段 | QA | Note | Wiki |
|---|---|---|---|
| 主要检索对象 | Passage/Chunk | Source metadata、Journal、Relation、Window | Wiki Page、Version、Graph、Backlink |
| 延迟预算 | 最低 | 中等 | 中等 |
| 证据策略 | 多来源、直接相关 | 原文窗口、locator 完整、候选收束 | 稳定页优先、版本与网络关系 |
| 输出 | 直接回答 | 回答 + 摘录/笔记建议 | 网络综合回答 + 治理/更新建议 |
| 回写 | 可选 Note | Note Draft | Wiki Draft/Change Proposal |

共享阶段由 `AnswerPipeline` 固定：

```text
Validate Authorization
  -> Create AnswerRun
  -> Compile Context + Memory Controls
  -> Strategy.plan
  -> Execute RetrievalPlan
  -> Rank + Build EvidenceBundle
  -> Generate Streaming Answer
  -> Citation Grounding + Verify
  -> Commit Message Revision + Citations
  -> Emit Completed Event
```

这样新增模式不修改 ChatService，只注册新策略；同时所有模式天然拥有相同的运行记录、指标、引用检查和错误语义。

### 9.4 是否把生成答案包成 Task

结论：**应该任务化其生命周期，但不应全部队列化。**

推荐模型：

- 每次回答创建 `Execution(type=CHAT_ANSWER)` 和 `AnswerRun`；
- QA 默认由 `InlineExecutionHandler` 在当前节点执行并真流式输出；
- Note/Wiki 默认也可 inline，但当检索步骤、文档数量或预计 token 超预算时升级为 `Remote/AsyncExecutionHandler`；
- 客户端永远订阅 `/executions/{id}/events`，不关心执行在当前线程、线程池还是 Worker；
- 重新生成创建新 attempt 或新 AnswerRun revision，不覆盖旧结果。

这比“所有回答都发 Kafka”更合适，因为 Kafka 往返、消费排队和 Worker 冷启动会破坏普通 QA 的首 token 延迟。

## 10. 统一检索架构

### 10.1 检索分层

```text
Query Understanding
  -> Scope Filter（workspace/source/type/version/permission）
  -> Multi Retriever Recall
       ├─ BM25 Retriever
       ├─ Vector Retriever
       ├─ Metadata Retriever
       ├─ Knowledge Graph Retriever
       └─ Journal/History Retriever
  -> Fusion（RRF 或归一化加权）
  -> Rerank
  -> Diversity / Coverage / Freshness Policy
  -> EvidenceBundle
```

QA、Note、Wiki 共用 Retriever 能力，但用不同 RetrievalPlan 组合，不强制走相同算法。

### 10.2 数据职责

| 中间件 | 唯一职责 | 不应该承担 |
|---|---|---|
| MySQL | 业务真源、版本、权限、Execution、Outbox、引用关系 | 大全文扫描、事件广播 |
| MinIO | 原文件、解析产物、大 checkpoint、报告和导出 | 任务状态、可查询元数据 |
| Elasticsearch | Passage/Wiki/Artifact 的可重建检索投影、BM25 + Vector | 业务真源、权限最终判断 |
| Kafka | 跨进程命令和领域事件的可靠传输 | 保存任务当前状态、同步 RPC |
| Redis | 限流、短锁、SSE 跨节点 event stream、短期缓存 | 永久业务数据、关键 checkpoint |

### 10.3 ES 推荐模型

使用共享版本化 index：

```text
noteweave_passage_v3
  id
  workspace_id          keyword + routing
  source_id             keyword
  snapshot_id           keyword
  knowledge_item_id     keyword
  content               text
  title                 text
  content_vector        dense_vector
  source_type           keyword
  visibility            keyword
  locator               object
  version_no            integer
  updated_at             date
```

通过 alias 完成 reindex；删除 Source 发送 ProjectionEvent；所有查询仍在 Java 先做 Workspace 授权，再带强制 filter。

## 11. 统一 Execution、Outbox 与 Worker 协议

### 11.1 核心表

```text
execution
  id, workspace_id, actor_id, execution_type, target_type, target_id
  status, priority, deadline_at, cancel_requested_at, version

execution_attempt
  id, execution_id, attempt_no, executor_type, worker_id
  status, started_at, heartbeat_at, finished_at, error_code

execution_event
  id, execution_id, attempt_id, sequence_no, event_type
  schema_version, payload_json, occurred_at

outbox_message
  id, aggregate_type, aggregate_id, destination, message_key
  schema_version, payload_json, status, attempt_count
  lease_owner, lease_until, next_attempt_at, last_error

inbox_receipt
  consumer_name, message_id, processed_at, result_hash
```

### 11.2 统一处理接口

```java
public interface ExecutionHandler<C extends ExecutionCommand> {
    ExecutionType supports();
    ExecutionResult handle(C command, ExecutionContext context);
}

public interface DeliveryAdapter {
    DestinationType supports();
    DeliveryReceipt deliver(OutboxEnvelope envelope);
}
```

Artifact、Research、Source、Wiki 共用一个 dispatcher 的 claim/retry/dead-letter/redrive；不同的只是 Kafka 或 HTTP Adapter。

### 11.3 可靠性规则

- 业务事务只写业务表 + outbox，不直接调用外部系统；
- Dispatcher 使用 lease + `SKIP LOCKED`/CAS claim；
- Worker 以 `command_id` 做 inbox 幂等；
- Callback 以 `event_id/idempotency_key` 做 receipt 幂等；
- 所有 callback 携带 attemptId，旧 attempt 的迟到结果不能覆盖新 attempt；
- 先保存领域结果和事件，再确认消息；
- DLT 必须可查询、报警、人工 redrive；
- Payload 大于阈值时写 MinIO，只传 locator + checksum。

## 12. 数据、事务与版本设计

### 12.1 聚合所有权

| 聚合 | 唯一写入口 | 允许的跨模块交互 |
|---|---|---|
| Workspace | workspace module | 授权查询、policy event |
| Source/Snapshot | source module | SourceReady/SourceDeleted event |
| Conversation/Message | conversation module | Answer commit port |
| AnswerRun | answer module | Execution lifecycle、citation port |
| KnowledgeItem/Version | knowledge module | proposal/writeback command |
| ResearchRun | research module | worker result commit command |
| ArtifactJob/Version | artifact module | worker result/writeback command |
| Execution | execution module | handler command、event subscription |

跨模块禁止直接 `JdbcTemplate.update` 对方的表。

### 12.2 版本与回写

- Message 不覆盖正文，使用 `message_revision` 保存重新生成和部分输出；
- Knowledge/Artifact rollback 是“创建指向旧内容的新版本”，不是修改历史版本；
- Research checkpoint 不删除重建整棵状态，使用 checkpoint snapshot + 增量 event；
- Worker 回写先形成 Proposal，需审批的写入由 Java 领域模块执行；
- 所有生成内容保存 `origin_execution_id`、source scope snapshot 和 prompt/model version。

## 13. API 与前端方案

### 13.1 API 统一

推荐核心 API：

```text
POST /api/v2/conversations/{id}/answer-runs
GET  /api/v2/answer-runs/{id}
GET  /api/v2/executions/{id}/events        # 真 SSE，支持 Last-Event-ID
POST /api/v2/executions/{id}/cancel
POST /api/v2/executions/{id}/retry

POST /api/v2/research-runs                 # 返回 domain id + execution id
POST /api/v2/artifact-jobs                 # 返回 domain id + execution id
```

所有列表使用 cursor；所有 mutation 支持 `Idempotency-Key`；错误体固定 `code/message/details/correlation_id`。

### 13.2 前端拆分顺序

不要一次重写 UI。按低风险顺序：

1. 抽出统一 `apiClient`、`executionEventClient` 和 contract types；
2. 抽 Chat feature；
3. 抽 Research feature；
4. 抽 Artifact feature；
5. 抽 Sources/Wiki；
6. 最后让 App 只保留路由和布局。

SSE Client 必须支持断线重连、Last-Event-ID、去重和 terminal event；页面不再用多个 setTimeout 轮询同一资源。

## 14. 分阶段迁移计划

### Phase 0：止血并建立可信基线（1～3 天）

- 修复 Backend testCompile；
- 追加 migration 修复 `conversation_message.updated_at`；
- 修复 ES disabled Bean；
- 删除 source.index 的竞争消费者或拆 group；
- Kafka handler 失败重新抛出并配置 DLT；
- 禁止修改历史 Flyway；
- prod profile 强制内部 token；
- 建立一次全仓 build/test 脚本。

验收：四个子项目全绿；ES on/off 均能启动；故意让 ES 写失败时 Source 不会显示 INDEXED。

### Phase 1：统一 Execution 与 Outbox（1～2 周）

- 新建 execution/attempt/event/outbox/inbox 模型；
- 先让 Artifact 接入通用 Dispatcher；
- 再迁 Research；
- 最后迁 Source/Wiki；
- 保留旧 Task API 作为兼容读投影；
- 加入 attempt fencing、callback idempotency、cancel、timeout。

验收：四类任务共享相同状态机；进程在 publish 前后崩溃均不丢任务；重复消息不产生重复领域结果。

### Phase 2：统一三模式 Answer Pipeline（1～2 周）

- 新建 AnswerRun、AnswerStrategyRegistry、RetrievalPlan、EvidenceBundle；
- 先把 QA 迁入；
- 再把现有 Note 逻辑包装成 Note Strategy，不立即重写算法；
- 再迁 Wiki Strategy；
- Citation Persist/Verify 变成共享阶段；
- ChatService 缩减为薄 Application Facade。

验收：新增测试策略无需修改 ChatService；三模式都能输出统一 trace 和 coverage；重新生成不覆盖旧 revision。

### Phase 3：资料与检索投影重构（2～3 周）

- DocumentParser Registry；
- 流式上传/解析；
- 统一 Passage 模型与 locator；
- ES 共享版本化 index；
- 接入 embedding、BM25 + vector fusion、rerank；
- Index Projector ack 后推进状态；
- 建 gold set 测 recall@k、MRR、citation precision。

验收：PDF/DOCX/MD 至少三类解析可测；索引可全量重建；删除/更新 source 后无陈旧检索结果。

### Phase 4：模块拆分与查询优化（持续 2～4 周）

- 拆 ResearchRunService、KnowledgeService、ArtifactJobService；
- 引入 Command Handler / Query Service / Repository；
- 修复 N+1、加入 cursor pagination；
- 将大 trace/checkpoint 外置 MinIO；
- 前端按 feature 拆 App.tsx。

验收：核心 Service < 500 行不是硬指标，但每个类只有一个明确变化原因；list API 查询数与结果条数基本无关。

### Phase 5：生产化（持续）

- Spring Security + Workspace RBAC；
- OpenTelemetry、结构化日志、SLO；
- Redis 承担限流/SSE bridge，或彻底移除；
- Testcontainers + Playwright；
- 备份恢复、容量压测、故障演练；
- 固定镜像 digest、secret manager、依赖升级策略。

## 16. 不建议采用的方案

### 16.1 不建议立即拆成大量微服务

当前主要矛盾是边界和语义不统一，不是单体部署。先拆服务只会把方法调用变成不可靠网络调用，同时复制更多 DTO、鉴权和运维成本。

### 16.2 不建议让所有聊天回答强制走 Kafka

任务生命周期应统一，但 QA 的执行路径应保留 inline fast path。Kafka 适合跨进程长任务，不适合替代所有同步编排。

### 16.3 不建议创建一个万能 `TaskService` 包办所有领域

统一 Execution 只负责控制面；Research、Artifact、Answer、Source 仍保留领域聚合和专有状态。否则新的通用引擎会再次成为 God Service。

### 16.4 不建议为了“规范”把 JDBC 全部换成 JPA

当前问题不是 ORM 选择，而是写入所有权和职责混合。可继续使用 JdbcTemplate，推荐逐步使用 jOOQ/命名 SQL 提升类型安全，但先建立 Repository 和模块边界。

### 16.5 不建议在没有评测集前盲目增加检索算法

向量、reranker、graph retrieval 都应以 gold set 指标和延迟预算决定。先统一 RetrievalPlan/EvidenceBundle 和埋点，再比较算法。

## 17. 目标验收指标

### 正确性

- Backend、Frontend、两个 Worker 构建测试全部通过；
- Outbox 故障注入下任务不丢失，重复投递不重复产出；
- 非法状态迁移为 0，迟到 callback 不覆盖新 attempt；
- Source 的 INDEXED 状态与 ES 可检索事实一致；
- 所有 Workspace API 都有主体授权测试。

### 性能

- QA 首 token P95 < 2 秒（本地模型/外部模型网络耗时另行拆分）；
- Task event 推送延迟 P95 < 1 秒；
- list API 默认响应 < 200 KB 且查询数不随子项线性增长；
- 128MB 文件处理不需要在 JVM 中同时保留多份完整 byte[]。

### 质量

- 三模式统一记录 retrieval plan、selected/rejected evidence、citation coverage；
- gold set 上跟踪 Recall@K、MRR、Citation Precision/Completeness；
- 每个 Worker command 和 callback 都有 schema version 与 contract test；
- 核心跨模块写操作只能通过公开 port。

### 可运维性

- 每个 execution 可按 correlationId 查看完整阶段、attempt、事件和错误；
- READY/PROCESSING/DEAD_LETTER 队列有指标和告警；
- ES、Kafka、MinIO 降级会反映在 health/readiness，而不是只写 warn；
- Redis 若保留，有明确用途、TTL、容量与降级说明。

## 18. 最终建议

建议下一轮重构按以下主线推进：

```text
先修 P0 正确性
  -> 统一 Execution / Outbox
  -> 引入 AnswerRun 与三模式策略管线
  -> 统一 Source/Passage/Index Projection
  -> 拆分 God Class 和前端 feature
  -> 最后做 Hybrid Retrieval 与全面生产化
```

其中最值得优先落地的两个架构切口是：

1. **AnswerRun + AnswerModeStrategy + EvidenceBundle**：直接解决三种检索/回答链路只有入口统一的问题；
2. **Execution + 通用 Outbox Dispatcher**：直接解决 Source、Wiki、Research、Artifact 四套任务语义不一致的问题。

完成这两个切口后，NoteWeave 的核心不再是一批互相调用的巨型 Service，而会形成清晰的产品内核：

> Workspace 提供边界，Source 提供事实，Retrieval 生成 EvidenceBundle，Answer/Research/Artifact 产生带证据结果，Execution 负责可靠运行，Knowledge 与 Memory 负责受控沉淀。

这才是适合继续扩展新检索模式、新 Agent、新 Skill 和新中间件的长期结构。
