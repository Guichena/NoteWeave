# NoteWeave v2 产品详细设计

## 1. 产品定位

NoteWeave v2 的目标产品形态不是传统“聊天机器人”，而是更接近 NotebookLM 的知识工作台：

- 以资料为中心，而不是只以对话为中心
- 以研究工作台为基本单位，而不是让用户每次重新组织资料和 Prompt
- 以可生成、可回写、可沉淀的产物为中心，而不是只给一次性回答

产品最终要承接四类典型工作：

1. 快速问答与理解
2. 在同一聊天界面中切换问答、Note、Wiki 三种回答链路
3. 围绕资料池做跨文件比较与深度研究升级
4. 基于工作台资料池生成结构化产物
5. 用任务邻域个性化记忆保持跨会话表达口径、用户偏好和禁用路径一致

## 2. 主界面形态

推荐采用三栏式工作台：

```text
左侧：导航与资料区
中间：统一聊天区
右侧：产物栏与结果抽屉
```

### 2.1 左侧区域

左侧承载“工作范围选择”和“资料组织”：

- 研究工作台切换
- 工作台内主题范围 / 资料集合
- 资料列表
- 标签 / 文件夹 / 最近使用
- Notes / Wiki / Artifacts 快捷入口

左侧解决的问题是：

- 用户当前在处理哪一批资料
- 当前上下文边界是什么
- 哪些内容属于同一个主题

### 2.2 中间区域

中间区域默认是统一聊天界面，不因为用户选择问答、Note、Wiki 而切换成三套不同主视图。

- 顶部提供当前聊天的回答链路选择：`问答 / Note / Wiki`
- 聊天流展示本次回答、引用来源、可回写动作和任务入口
- 每个聊天会话保留自己的上下文、回答链路和运行记录；资料边界默认继承当前研究工作台
- Deep Research 结果页、Wiki 工作台、资料阅读页可以通过按钮进入，但不替代聊天主入口

中间区域必须始终围绕“当前聊天上下文”工作，而不是变成多个完全割裂的页面系统。

### 2.3 右侧区域

右侧区域是 v2 很关键的产品特征，类似 NotebookLM 的 Studio / 输出动作区。

它承担两种职责：

1. 展示基于当前工作台资料池可触发的产物按钮
2. 展示最近生成的产物结果、进度和可回写动作

这一区域也是 `Artifact Agent` 的主要产品入口：

- 用户不需要自己写 Prompt
- 系统围绕当前工作台资料池与用户选择的产物类型装配 `Production Action`
- 生成结果可以保存为笔记、沉淀为 Wiki 页面，或作为工作台资料继续复用
- 平台内置高频产物类型，也支持用户新增自定义产物形式

推荐形态：

```text
Artifact Actions Rail
  - 生成报告
  - 生成测验
  - 生成学习指南
  - 生成 FAQ
  - 生成时间线总结
  - 生成 Wiki 页面
  - 生成结构化笔记
```

默认建议先以 `Markdown` 作为中间产物格式，再支持导出 `MD / PDF`。

## 3. 三种聊天回答链路

### 3.1 问答链路

核心目标：

- 围绕当前资料做快速问答
- 结合当前会话保持上下文连续性
- 快速保存为结构化笔记或派生产物
- 通过关键词检索、向量检索、结构化过滤和证据 rerank 生成带引用回答

典型界面元素：

- Chat 输入框
- 回答区
- 引用来源卡片
- 相关 Note / Wiki / Artifact 推荐
- 右侧产物栏按钮
- 顶部 Deep Research 按钮

典型问题：

- 这个文件讲了什么？
- 这个概念是什么意思？
- 这个结论的来源在哪？
- 根据这些材料生成一个测验

具体实现上，问答链路是默认 `Workspace-bounded Conversational RAG`：

- 默认继承当前研究工作台与主题范围
- 第一阶段检索对象以当前工作台已解析资料 chunk 为主
- 其他链路产生的内容只有在用户明确保存为资料后，才按普通资料参与问答召回
- 聊天历史只用于理解上下文，不直接作为事实证据
- 事实性回答必须绑定 Citation，支持回跳原文
- 详细设计见 [问答RAG链路设计](D:/java-projects/NoteWeave-v2/docs/问答RAG链路设计.md)

### 3.2 Wiki 链路

核心目标：

- 在聊天回答时优先使用已有 Wiki 页面网络
- 基于 Wiki 页面、页面链接、索引和来源回链回答问题
- 保留一个清晰的 `进入 Wiki 工作台` 按钮，用户主动点击后再进入统一 Wiki 工作台

典型界面元素：

- Chat 输入框
- 回答区
- Wiki 来源依据摘要
- `进入 Wiki 工作台` 按钮
- 右侧产物栏按钮
- 顶部 Deep Research 按钮

典型动作：

- 基于已有 Wiki 页面回答问题
- 发现 Wiki 内容不足时提示用户进入 Wiki 工作台维护
- 从当前回答或研究报告生成 Wiki 页面

### 3.3 Note 链路

核心目标：

- 在聊天回答时进入“边回答、边整理、边沉淀”的工作方式
- 直接参考 `Marginalia-style Structured Reading Funnel`
- 先通过资料标题、摘要、标签、历史笔记、结构化元数据和关系信号定位候选资料
- 再读取原文窗口，抽取可引用摘录，最后形成结构化笔记

典型界面元素：

- Chat 输入框
- 回答区
- 候选资料卡
- 原文窗口
- 摘录卡片
- 结构化笔记
- 来源引用面板
- 保存到工作台按钮
- 右侧产物栏按钮
- 顶部 Deep Research 按钮

典型动作：

- 围绕问题先给直接回答
- 展示系统参考的候选资料
- 从原文窗口抽取关键摘录
- 生成可编辑的结构化笔记
- 将笔记保存到当前研究工作台，供后续问答、整理和知识页生成继续使用

这个链路的主要实现参考是 `Marginalia-style Structured Reading Funnel`：

- 不直接对 chunk 做 top-k 问答，而是先做资料级候选定位
- 候选定位依赖资料标题、摘要、标签、历史笔记、结构化元数据和关系信号
- 再打开原文窗口读取可验证片段，抽取摘录卡片
- 最后生成带引用的回答与结构化笔记
- 详细设计见 [Note链路设计](D:/java-projects/NoteWeave-v2/docs/Note链路设计.md)

## 4. Deep Research 独立入口

Deep Research 必须是一个独立功能入口，而不是某个模式内的隐藏流程。

推荐触发入口：

- 顶栏全局按钮：`深度研究`
- 问答结果卡片中的“升级为深度研究”
- 当前聊天中的“升级为深度研究”
- Wiki 工作台中的“围绕本页扩展研究”

### 4.1 发起方式

用户可以从以下上下文发起：

- 当前聊天问题
- 当前聊天会话上下文
- 当前 Wiki 工作台页面
- 当前选中的多个资料

系统发起时需要自动生成 `UI Context Snapshot`，把当前上下文冻结下来，供后续 `Research Run` 使用。

### 4.2 研究结果页

Deep Research 结果页建议单独呈现，至少包括：

- 研究问题
- 当前状态与进度
- Research Table
- 候选资料与已访问资料
- 低置信 / 冲突项
- 当前分支 / 恢复点
- 最终研究报告
- 回写操作按钮

### 4.3 结果回流

研究完成后，用户可以显式选择：

- 回到问答继续追问
- 保存为结构化笔记
- 生成 Wiki 页面
- 保留为 Artifact
- 让研究报告进入共享资料池参与后续检索

## 5. 右侧产物栏设计

### 5.1 按钮分组

建议把右侧动作分成三组：

1. 总结类
2. 学习类
3. 沉淀类

示例：

```text
总结类
- 报告
- 时间线总结
- 对比总结

学习类
- 测验
- 学习指南
- FAQ

沉淀类
- Wiki 页面
- 结构化笔记
```

### 5.2 按钮的本质

按钮不是直接绑定一段 Prompt，而是绑定一个 `Production Action`。

也就是说，用户点击“生成测验”时，系统内部执行的是：

- 基于当前研究工作台确定资料范围
- 选择 Quiz Action
- 装配 Style Profile / Skill Graph / Prompt Recipe
- 调用所需 MCP / 读取能力
- 通过 schema 与权限门控
- 创建 Artifact Job
- 异步执行并产出 Artifact Version

这意味着右侧产物栏的本质是“可扩展的产物生成系统”，不是固定按钮表。

### 5.3 资料范围与生成要求

右侧产物栏默认绑定当前研究工作台，而不是绑定某一次聊天。

产物生成的原材料是：

- 当前研究工作台资料池
- 工作台内已经保存为资料的系统产物
- 资料对应的解析文本、索引片段、标题、摘要、标签、元数据和引用信息

产物类型、风格配置和输出格式属于生成要求，不属于原材料。

### 5.4 产物结果形态

右侧生成的结果不应只是一段临时文字，而应支持：

- 查看版本
- 查看生成依据
- 再次生成
- 编辑草稿
- 保存为笔记 / 沉淀为 Wiki 页面
- 加入检索
- 导出 `MD / PDF`

## 6. 关键用户流程

### 6.1 问答到产物

```text
用户提问
  -> 得到回答与引用
  -> 点击右侧“生成测验”
  -> 系统基于当前研究工作台资料池创建 Artifact Job
  -> 生成测验
  -> 用户保存或继续追问
```

### 6.2 Note 到研究

```text
用户在 Note 链路中整理多份资料
  -> 浏览资料树 / 检索候选资料卡 / 阅读原文窗口
  -> 形成结构化笔记
  -> 点击 Deep Research
  -> 生成 Research Run
  -> 输出研究报告
  -> 研究报告进入共享资料池
```

### 6.3 研究到 Wiki

```text
Deep Research 完成
  -> 生成 Artifact 报告
  -> 用户点击“生成 Wiki 页面”
  -> 产出 Wiki 页面
  -> 用户编辑后发布
```

### 6.4 阅读到学习产物

```text
用户打开 PDF / 视频转写
  -> 点击右侧“学习指南”
  -> 系统识别当前阅读上下文
  -> 运行对应 Production Action 与 Style Profile
  -> 输出学习指南 Artifact
```

### 6.5 跨任务个性化记忆

```text
用户明确表达偏好 / 纠正口径 / 否定方案
  -> 系统抽取 Memory Signal
  -> 形成 Memory Candidate
  -> 进行 Semantic Neighborhood Modeling
  -> 计算 Marginal Utility
  -> 经过 Staleness Guard 与 Negative Memory Check
  -> 编译为后续任务的风格约束、结构约束、禁用路径和交互策略
```

## 7. 状态与反馈设计

### 7.1 Deep Research 状态

前端建议展示以下状态：

- 已创建
- 规划中
- 搜索中
- 阅读中
- 抽取中
- 验证中
- 冲突处理中
- 写作中
- 已完成
- 部分完成
- 失败

### 7.2 Artifact Job 状态

右侧产物任务建议展示：

- 已创建
- 排队中
- 运行中
- 等待外部能力
- 校验中
- 提交中
- 已完成
- 失败

### 7.3 用户反馈原则

- 用户始终能看到任务现在在做什么
- 用户能看到结果来自哪些资料
- 用户能知道为什么失败或停在等待状态
- 用户能知道哪些内容低置信、哪些需要人工确认

### 7.4 Memory 反馈原则

- 用户能区分“资料证据”“聊天上下文”“个性化记忆控制信号”
- 用户能看到某条 Memory 来自哪次明确反馈、项目口径或否定路径
- 用户能知道某条 Memory 适用于哪些任务邻域，是否已过期或被新口径覆盖
- Memory 不作为事实来源，不参与资料检索排序，只影响回答风格、结构约束、禁用路径和交互策略

## 8. 默认按钮与默认产物

建议默认锁定以下按钮：

- 报告
- 测验
- 学习指南
- FAQ
- Wiki 页面
- 结构化笔记

这样足够覆盖：

- 总结
- 学习
- 沉淀

而不至于默认入口过多导致认知负担。

## 9. 产品设计边界

产品设计不应追求：

- 把所有 AI 能力都塞进右侧产物栏
- 让 Deep Research 变成无约束的自治系统
- 自动把所有生成结果直接写入正式知识
- 一开始就支持非常复杂的多人协作

更重要的是：

- 入口清晰
- 上下文清晰
- 任务状态清晰
- 结果去向清晰

## 10. 产品总结

NoteWeave v2 的产品详细设计可以概括为一句话：

`以 NotebookLM 风格的研究工作台为外壳，以统一聊天区承接问答、Note、Wiki 三种回答链路，以 Deep Research 按钮和右侧产物栏承接独立智能任务，并通过显式回写、资料池复用和任务邻域个性化记忆机制，让知识结果可追溯、可维护，同时让系统在跨会话协作中保持一致的表达口径和用户偏好。`
