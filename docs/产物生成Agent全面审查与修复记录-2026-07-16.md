## 3. 修复优先级

### P0：会破坏任务终态或重试正确性

| 编号 | 问题 | 风险 | 状态 |
| --- | --- | --- | --- |
| P0-1 | Worker 将 progress/complete 回调投递异常与生成异常放在同一 `try` 中 | 成功生成遇到网络抖动后会继续发送 `fail`，把可重试任务错误终结为失败 | 已修复 |
| P0-2 | Artifact Worker 未发送 Java 已支持的 `X-NoteWeave-Idempotency-Key` | callback receipt 表未在主链路生效，并发/重试回调可能重复推进状态 | 已修复 |
| P0-3 | acquisition provider ack 不支持同 token、同终态重放 | 响应丢失后的合法重试被拒绝，破坏 at-least-once 投递 | 已修复 |
| P0-4 | System MCP 把“成功 ack 投递失败”捕获成 provider 执行失败并发送失败 ack | 网络故障会篡改真实执行结果，形成成功转失败 | 已修复 |

### P1：恢复、并发和数据完整性隐患

| 编号 | 问题 | 风险 | 状态 |
| --- | --- | --- | --- |
| P1-1 | waiting task 恢复没有原子 claim | 手工 resume 与 provider callback 并发时可重复执行同一任务 | 已修复 |
| P1-2 | File Artifact Repository 直接覆盖 JSON，且 version/retrieval 分两次写入 | 进程退出或磁盘异常可能留下截断文件或半提交结果 | 已修复 |
| P1-3 | LLM 响应、provider payload 和 provider 文本文件缺少统一硬上限 | 异常上游可造成内存、磁盘状态文件或回调体膨胀 | 已修复 |
| P1-4 | System MCP 子进程没有执行超时 | 外部工具挂死会永久占用后台线程，任务停在 RUNNING/WAITING | 已修复 |

### P2：可维护性与运行可观测性优化

| 编号 | 问题 | 收益 | 状态 |
| --- | --- | --- | --- |
| P2-1 | 后台 executor 对 ack 投递失败缺少结构化日志 | 难以区分 provider 失败和控制面不可用 | 已修复 |
| P2-2 | 文件状态加载对损坏 JSON 的报错缺少路径上下文 | 启动故障定位成本高 | 已修复 |
| P2-3 | `pytest` 位于生产 dependencies 且依赖只有无上界下限 | 镜像包含测试依赖，未来大版本升级存在漂移风险 | 已修复 |

## 4. 非问题与边界说明

- Java 是 Artifact Version 业务真源；Worker 的 memory/file repository 是 runtime/debug 快照，不能用它替代 Java 版本一致性。
- Verifier 当前把未满足项归为 `WARN` 并允许生成草稿，这是现有产品语义，不在没有新需求的情况下擅自改成任务失败。
- System MCP 的字幕/PDF 需要读取受控执行器生成的本地文件；修复应增加大小和来源约束，不能直接禁止所有本地路径。
- 生产级 mTLS、外部告警平台、数据库/MinIO 高可用和真实网络容量压测属于部署验收，不在本轮代码修复中伪造完成态。

## 5. 验收标准

1. 生成异常才发送 fail；输入获取、progress、complete 的传输异常保持可重试，不改变业务结果。
2. progress/complete/fail 均携带稳定且互不冲突的幂等键。
3. 同一个 acquisition callback token 重放同一终态返回原回执；已成功交付时不重复 resume，complete 传输失败时允许安全重试；冲突终态仍拒绝。
4. System MCP 成功结果不会因 ack 传输失败改写为失败。
5. 同一 waiting task 同时只允许一个恢复执行者。
6. runtime 文件写入使用同目录临时文件和原子替换；版本与 retrieval 快照成对提交。
7. LLM/provider 内容和外部进程执行具备可配置或明确的硬上限。
8. Artifact Worker、相关 Java 测试及必要的前端契约验证全部通过。

## 6. 完成记录

1. 将 task input 获取、runtime 执行和 callback 投递拆成不同失败域；只有 runtime 执行错误发送 `fail`，callback 发送失败保留重试语义，失败回调自身异常不再覆盖原异常。
2. progress、complete、fail 使用 task/callback type/phase 派生的稳定 SHA-256 幂等键，正式接入 Java `worker_callback_receipt`。
3. acquisition ack 支持同 token、同终态幂等重放，并保留已 dispatch/已终结 operation，防止 resume 重建状态时丢失 callback token。
4. System MCP 将 provider 执行错误和成功 ack 传输错误分开；后者只记录错误并保持 operation 可恢复，不再伪造 FAILED。
5. waiting task 增加持久化 `RESUMING` claim；并发恢复只允许一个执行者，进程重启会把中断 claim 恢复到原 waiting 状态。complete 投递成功后才删除 waiting 记录。
6. File Artifact Repository 的 version/retrieval 改为同锁、同状态、单次原子提交；所有文件状态写入使用同目录临时文件、`flush + fsync + os.replace`。损坏 repository JSON 会报告具体路径。
7. 新增统一 I/O 上限：provider JSON 1 MB、provider 文本文件 4 MB、LLM HTTP 响应 1 MB；MCP structured/text content 同样校验 JSON 大小。
8. System MCP/custom MCP 子进程增加 `NOTEWEAVE_MCP_PROCESS_TIMEOUT_SECONDS`，默认 3600 秒、允许范围 1 到 21600 秒；Compose、`.env.example` 和 Worker README 已同步。
9. provider callback token 增加密码学随机后缀；正式 ack DTO 增加长度约束并移除可变默认字典。
10. custom artifact registry 改为原子文件替换，损坏 JSON 会留下明确 warning；后台执行/ack 失败增加结构化日志。
11. `pytest` 从生产 dependencies 移至 `test` optional dependency；Artifact Worker 和 Docker 依赖增加兼容大版本上界。

## 8. 残余部署边界

- file runtime store 使用进程内锁和原子文件替换，正式 Compose 固定单个 Uvicorn 进程。不能把同一状态文件挂给多个 worker 进程或多个容器；横向扩展前应迁移到数据库/Redis claim。
- ack 响应丢失时可能重新执行一次 System MCP provider，但 callback、waiting resume 和 Java 终态现在具备幂等保护。要消除外部工具重复成本，需要 provider 自身支持持久化 job 查询/续接。
- 真实 B 站网络成功率、超长视频资源消耗、XeLaTeX/Whisper 容量和对象存储高可用仍需部署环境压测。
- 当前内部服务认证是共享 secret，不是 mTLS；custom MCP 仍只允许在默认关闭且受 token 保护的 internal/debug 面使用。
