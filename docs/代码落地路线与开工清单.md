## 4. 第一阶段实施顺序

建议按下面顺序推进，不要一开始同时铺太多链路。

1. 初始化工程骨架
2. 拉起 `docker compose` 的 `MySQL / Redis / Kafka / MinIO / Elasticsearch`
3. 落第一批 `Flyway migration`
4. 打通工作台、会话、资料上传、资料解析任务闭环
5. 打通问答 RAG 最小闭环
6. 打通 Note 模式最小闭环
7. 打通 Wiki 模式最小闭环
8. 打通右侧产物栏最小闭环
9. 打通 Deep Research 最小闭环
10. 最后接入 Memory Control Pack

原因很简单：

1. 问答 RAG 是所有链路的资料底座验证场
2. Note / Wiki 都建立在资料检索、引用和结构化返回稳定之后
3. Artifact 和 Research 都依赖任务系统、资料池和结果回写能力
4. Memory 最适合在基础链路稳定后接入，否则容易先设计过满

## 6. 第一批最小接口契约

真正建议开工前写清楚的，是下面这些接口和事件，而不是新的宏观图。

### 6.1 前端到 Java

1. 创建工作台
2. 上传资料
3. 创建会话
4. 发送聊天消息并指定模式
5. 启动 Deep Research
6. 启动 Artifact 生成
7. 查询任务进度
8. 将系统生成结果保存为资料

### 6.2 Java 到 Worker

1. 创建 `research task`
2. 创建 `artifact task`
3. 拉取工作台资料与任务输入
4. 回传阶段进度
5. 回传最终结果
6. 回传失败原因

### 6.3 异步事件

1. `source.uploaded`
2. `source.parsing`
3. `source.indexed`
4. `research.started`
5. `research.completed`
6. `artifact.started`
7. `artifact.completed`
8. `artifact.saved_as_source`

## 7. 第一阶段不要做的东西

为了避免过度设计，第一阶段明确不做这些：

1. 通用 Agent 平台
2. 可视化 Skill Graph 编辑器
3. 独立 `LLM Gateway`
4. 独立 `MCP Gateway`
5. 单独的向量数据库集群
6. 复杂审批流
7. 多人实时协作编辑
8. 全量多模态理解链路
9. 自动外网大规模爬取系统
10. 复杂的用户自定义 Agent 编排界面

## 8. 开工建议

最合理的开工方式不是继续补“系统还能怎么设计”，而是立刻进入下面这条路线：

1. 建工程目录
2. 补 `docker compose`
3. 冻结第一批表结构
4. 补第一批 API 契约
5. 先把工作台、资料上传、问答 RAG 跑通

只要这条主线跑通，后面的 Note、Wiki、Artifact、Research 和 Memory 才会真正落到代码而不是停留在文档层。
