## 1. 结论摘要

当前项目不是“整体假实现”。Transactional Outbox、Research task lease/fencing/CAS、checkpoint、原子 completion、引用所有权校验等核心机制具有真实代码路径和测试。主要风险集中在模块边界：上游已编译的数据没有进入 worker、降级产物仍以成功交付、幂等回执未绑定请求内容、局部恢复机制被描述成完整闭环。

截至审查冻结，共确认 16 项需要处理的问题：9 项运行时缺陷、4 项结构或产品语义缺陷、2 项安全/仓库卫生问题、1 项测试门禁缺口。其中 7 项直接影响简历亮点的真实性或可演示性。

## 3. 高置信问题清单

### NW-01 [HIGH] Research Intent 与 Research Memory 在 Agent 边界丢失

- 亮点影响：Deep Research、Context Engineering、Memory。
- 证据：`ResearchRunCommandService.java:68-85` 编译并保存 `research_intent_json`、`control_pack_json`；`ResearchAgentTaskCoordinatorService.java:187-193` 的 RunScope 查询不读取它们；`ResearchAgentTaskSnapshotCanonicalizer.java:35-59` 也未写入任务快照；`deep_cell_executor.py:274-281` 又临时构造空约束 ControlPack 和默认 ResearchIntent。
- 触发：用户设置 researchGoal、deliverableFormat、constraints、timeRange、depth，或工作区存在 RESEARCH Memory。
- 结果：详情与 usage log 显示“已编译”，实际 Search/Plan/Extract 不使用这些输入。
- 修复：任务快照升级，冻结携带 intent/control pack 及 digest；worker 严格反序列化，不再本地伪造。
- 批次：B1。状态：已修复并通过批次门禁。

### NW-02 [HIGH] 删除 Source 会遗留独立的 snapshot 原文件

- 亮点影响：资料底座、删除一致性、MinIO 数据治理。
- 证据：`UploadService.java:159-173` 把内容另存到 `source/.../snapshot/1/original/...`；`SourceService.java:102-122` 只将共享 `file_object.object_key` 放入删除事件；`SourceDeletionCleanupListener.java:50-69,179-191` 只为事件中的单个 key 建清理任务。
- 触发：删除上传资料或生成资料。
- 结果：数据库显示 DELETED、检索投影被清理，但 `source_snapshot.object_key` 对应对象永久残留。
- 修复：删除前读取所有 snapshot object key；共享 file object 仍按 ref_count 清理；为每个唯一对象建立可重试清理任务。
- 批次：B1。状态：已修复并通过批次门禁。

### NW-03 [HIGH/SECURITY] Memory 的高信任来源可由客户端伪造

- 亮点影响：Graduated Memory、长期个性化。
- 证据：`CreateMemorySignalRequest.java:7-18` 接受客户端 `sourceType/sourceId`；`MemorySignalService.java:40-72` 不验证 provenance；`MemoryCandidatePolicy.java:14-21,44-67` 给 USER_FEEDBACK 0.98 置信和 0.10 风险；READY candidate 会被 `MemoryPromotionService.java:28-38` 投影为 active。
- 触发：有 ANSWER_RUN 与 MEMORY_REVIEW 权限的 editor 提交任意文本并声明为 USER_FEEDBACK，再执行 promote。
- 结果：可污染共享 Memory，并影响后续 Chat/Artifact 控制包。
- 修复：公共接口不接受任意 sourceType；由服务端命令推导来源，sourceId 必须解析到当前工作区真实事件，保存 provenance digest，晋升时复验。
- 批次：B1。状态：已修复并通过批次门禁。

### NW-04 [HIGH] Artifact callback 幂等回执不绑定 callback 类型与 payload

- 亮点影响：幂等消费、可靠回调、最终一致性。
- 证据：`V024__add_worker_callback_idempotency.sql:1-11` 的唯一键仅为 `(task_id,idempotency_key)`，无 payload digest；`WorkerTaskCallbackService.java:176-213,323-336` 在副作用之后登记 COMPLETE 回执，并把任意唯一键冲突解释成当前类型的重复；worker 的 terminal key 只含 task/type。
- 触发：响应丢失后相同 key 携带不同结果重试，或不同 callback 类型误复用 key。
- 结果：服务端可能静默 ACK 已有终态，无法发现语义冲突；文档中的“同 key 不同 payload 冲突”不成立。
- 修复：事务起点 claim `(task,key,type,payload_digest)`；同 digest 返回原回执，不同类型或内容返回 409；回执保存处理状态和结果引用。
- 批次：B2。状态：已修复并通过批次门禁。

### NW-05 [HIGH/PRODUCT] Artifact 摘抄兜底仍以 COMPLETED 交付

- 亮点影响：Schema-First Artifact、Skill Graph、受控生成。
- 证据：Compose 默认 Artifact LLM 为空；`generation_runtime.py:29-44,73-88` 在无 LLM 或模型输出无效时进入 `SOURCE_EXTRACTIVE_FALLBACK`；`runner.py:239-253,345-351` 仍生成 `status=COMPLETED`，verifier 主要检查结构、短语与引用存在。
- 触发：标准 Compose 下带 source/direct input 的简历、报告、quiz 等任务。
- 结果：源片段轮转填充或通用题目可能被当成正式生成结果交付。
- 修复：将结果标记为 DEGRADED/EXTRACTIVE_PREVIEW；需要显式确认后才能成为正式版本；简历亮点类型默认 fail-closed，并补真实 provider 语义验收。
- 批次：B2。状态：已修复并通过批次门禁。

### NW-06 [HIGH/DEMO] 标准 Compose 不提供简历亮点的完整运行条件

- 亮点影响：QA Hybrid RAG、回答生成、Research、Artifact。
- 证据：`docker-compose.yml:179-224,292-298,336-339` 默认关闭 embedding/rerank/chat LLM，Research/Artifact LLM 为空。QA 检索会因 compose 开启的 MySQL fallback 降级为数据库扫描，而 `ChatAnswerGenerationAdapter.java:70-81` 因 LLM 与 template fallback 都关闭而返回 503。
- 触发：只按 README 执行标准 `docker compose --profile app up`，不另配 provider。
- 结果：服务可启动，但“BM25+Vector+RRF+Rerank+LLM 回答”不是默认可演示路径；Research/Artifact 也进入空结果或摘抄降级。
- 修复：增加显式 demo/provider 配置和启动 readiness；UI 在 provider 未就绪时禁用并解释对应能力；CI 增加纵向 smoke。
- 批次：B4。状态：已修复并通过批次门禁。新增 provider readiness 与 Compose 运行边界说明。

### NW-07 [HIGH] Redis 故障时本地 conversation 序列冒充全局游标

- 亮点影响：流式回答、断线重放、多实例可靠性。
- 证据：`RedisAnswerRealtimeBridge.java:97-124` 正常使用 Redis INCR；`ConversationEventMux.java:75-100,198-212` 在 bridge 失败后改用每个 JVM 自己的 `++channel.sequence`。
- 触发：同一 conversation 的请求落到多个 backend 实例，期间 Redis 短暂不可用。
- 结果：多个节点可产生相同序号；事件只在本机；Last-Event-ID 无法跨节点重放，Redis 恢复后序列仍可能冲突。
- 修复：Redis 不可用时 fail-closed 或切换到持久化 MySQL cursor/outbox；禁止 JVM 局部序号作为全局游标。
- 批次：B2。状态：已修复并通过批次门禁。

### NW-08 [HIGH] System MCP 成功结果在 callback 失败后只能靠重启恢复，并会重复执行 provider

- 亮点影响：MCP、等待/恢复、长任务可靠性。
- 证据：`system_mcp_executor.py:94-152` provider 成功后只重试三次 host ack；失败后线程退出，provider payload 未先持久化。`recover_system_mcp_acquisition_operations` 仅在 `main.py:119-122` 启动时调用，且 DISPATCHED_TO_PROVIDER 会重新执行 provider。
- 触发：provider 成功但 Java callback 短暂不可用。
- 结果：同进程中操作永久停留；重启后重复昂贵或有副作用的 provider 调用。
- 修复：先持久化 provider outcome，再独立重试 callback；恢复时只重发已缓存结果，不重新调用 provider。
- 批次：B2。状态：已修复并通过批次门禁。

### NW-09 [HIGH] Research quorum 的“独立来源域”实际只是 sourceId

- 亮点影响：受限反证、双候选 quorum、证据独立性。
- 证据：`ResearchAgentCompletionCommitter.java:596-606` 将 `EvidencePersisted::sourceId` 写入名为 `sourceDomains` 的字段，后续只判断列表是否相交。
- 触发：同一网站、同一发布者或同一内容镜像以不同 sourceId 进入两个候选。
- 结果：相关来源可被误判为独立证据，降低反证门槛。
- 修复：在证据快照中保存规范化 origin/domain 与内容 lineage digest；quorum 使用可信来源身份判断独立性。
- 批次：B3。状态：已修复并通过批次门禁。

### NW-10 [STRUCT/CLAIM] 多角色 Agent 中只有 DEEP_CELL 与受限 COUNTERFACTUAL 可达

- 结果：其余角色是声明与测试表面，没有生产命令路径。

### NW-11 [MEDIUM/SECURITY] 运行态 JSON 被 Git 跟踪且测试会改写

- 证据：仓库跟踪 `.artifact-worker-runtime-state.json`、`.artifact-worker-wait-queue.json`、`.artifact-worker-customizations.json`；配置默认使用当前工作目录的相对路径；测试导入 app 后会写入根目录文件。当前 runtime-state diff 超过 2600 行。

### NW-12 [MEDIUM/SECURITY] 登录接口没有速率限制或失败锁定

- 证据：`AuthController.java:24-26` 直接调用 `AuthService.login`；`AuthService.java:49-54` 只有 PBKDF2 和统一 401；identity filter 明确跳过 login/refresh。
- 触发：服务经反向代理或非 localhost 暴露。
- 结果：可持续在线猜解账号密码，并消耗高成本 PBKDF2 CPU。
- 修复：按 IP 与规范化账号双维度限速，失败指数退避，记录安全审计；避免账号枚举。
- 批次：B3。状态：已修复并通过批次门禁。

### NW-13 [MEDIUM] Artifact 文件持久化失败被吞掉

- 证据：`acquisition_runtime.py:71-91` 与 `capability_wait_queue.py:82-96` 在 `os.replace` 遇到 PermissionError 时只记录 warning，调用方继续成功。
- 触发：Windows 文件占用、权限变化、杀毒软件短时锁文件。
- 结果：内存状态与磁盘状态分叉，API 已接受的等待/回调状态在重启后消失。
- 修复：写入失败必须向调用方传播，或保留 pending-durable 状态并由后台重试；增加故障注入测试。
- 批次：B2。状态：已修复并通过批次门禁。

## 4. 已确认真实实现或明确边界

- DurableOutboxDispatcher 具有 CAS claim、数据库时钟 lease、attempt/backoff、dead letter 和事务 finalizer，不是空壳。
- Research checkpoint、task fencing token、atomic completion、candidate stable key、cell merge CAS 均有生产路径与专项测试。
- Deep Research 未配置 LLM 时不会伪造 evidence card，而是返回无支持候选；这是诚实失败，但标准部署的可用性不足。
- Artifact 自定义 MCP 注册只在 debug route 开启时可用，生产配置会禁止 debug；当前不按生产插件平台宣称。
- Artifact runtime 是编译期 DAG、运行期线性执行；现有文档已经按该边界描述，不再误报为运行时 DAG 调度器。
- Debug writeback 的 simulated receipt 只用于调试路径，真实用户写回走 Java ArtifactJobService；不列为生产假实现。
