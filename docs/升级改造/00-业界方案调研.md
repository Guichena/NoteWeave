# 业界方案调研

调研时间：2026-10。按五个改造模块整理业界的代表性做法，说明每种做法可以借鉴的点，以及对本项目改造设计的具体修订。修订内容已同步写入各模块文档的第 6 节。

## 一、Deep Research

### 1.1 代表方案

| 方案 | 核心做法 | 对本项目的启发 |
|---|---|---|
| **Table-as-Search**（阿里国际，ACL 2026 Findings） | 把信息检索建模为表格补全：主 Agent 由问题构造表结构（行是候选，列分为约束列和待收集信息列），表存在外部数据库。主循环每轮在两种动作中选一个：表中候选不足或候选不满足约束时执行 `ExpandRows`（由约束列生成多条检索策略，并行子 Agent 发现候选）；候选够了但有空单元格时执行 `PopulateCells`（按行把所有空信息列组成一条查询，并行检索）。用 `CheckSaturation` 加步数和时间上限判断结束。消融实验显示**规划模型的能力是瓶颈**：规划模型从 Qwen3-Max 换成 30B，各项指标下降 17 到 29 个点；换子 Agent 模型只下降 3 到 22 个点 | 项目的表格式状态就源自这篇论文，但目前缺少两样东西：由模型构造表结构，以及在两种动作之间做选择的主循环。论文本身也有不足：列在初始化后不能修改，单元格只有已填、待填、无需填三种状态，没有校验和冲突处理，这几点正是项目 Java 端已经做得比论文完整的地方 |
| **Anthropic 多 Agent 研究系统**（工程博客，2025-06） | 主 Agent 先把计划写入外部记忆，再并行派生 3 到 5 个子 Agent；派发给子 Agent 的任务必须写清目标、输出格式、建议的工具和来源、任务边界，否则会出现重复研究和遗漏；检索词**先宽后窄**，模型自己写的检索词往往过长过细，导致搜不到结果；投入按问题复杂度分级（简单事实 1 个 Agent、3 到 10 次工具调用，对比类 2 到 4 个子 Agent，复杂研究 10 个以上）；研究结束后由专门的引用 Agent 补引用；评测从约 20 条真实问题开始，用单次 LLM 评分（0 到 1 分加通过与否），评分维度为事实准确、引用准确、完整性、来源质量、工具效率；出错时从断点恢复，不从头重跑 | 单元格任务快照需要补充目标、列说明、任务边界（例如不要研究其他对比对象）；检索词生成要明确先宽后窄；规划阶段输出复杂度等级，据此分配预算；评测方式可以直接采用 |
| **LangChain open_deep_research** | 三个阶段：澄清需求 → 写研究简报 → Supervisor 把子课题委派给并行研究者，每个研究者的结果先压缩再交回，最后一次性写报告。摘要、研究、压缩、成文四类调用可以分别配置不同模型 | 研究简报是从对话到研究任务的一道显式转换，项目的 `ResearchBriefCompiler` 目前只是把上下文拼接起来，应改为由模型生成结构化的研究简报 |
| **Gemini / ChatGPT Deep Research** | 执行前先给出研究计划，用户可以修改后再开始；任务在后台异步执行。Gemini API 提供 `collaborative planning`，返回计划而不立即执行 | PLANNING 角色产出的表格可以先展示给用户确认（默认超时后自动开始），和现有的异步任务模型契合 |
| **STORM**（Stanford，NAACL 2024） | 直接让模型提问只会得到浅层问题。STORM 先从相似主题的文章中挖掘不同视角，再以每个视角模拟与专家的多轮问答，最后汇总成大纲 | 列（研究维度）的生成可以借鉴多视角提问：先生成若干视角（使用者、实现者、批评者等），每个视角各提问，再合并去重成列 |
| **SAFE**（Google DeepMind） | 把长回答拆成可独立理解的原子事实，过滤无关事实，再对每条事实做多步检索，判断是否被支持。与人工标注的一致率为 72%，分歧样本中 76% 判断正确，成本是人工的二十分之一 | 反证与证据校验以原子事实为单位，不以整段结论为单位 |
| **Chain-of-Verification**（Meta） | 先起草，再规划验证问题，然后**彼此隔离地**回答每个验证问题（回答时看不到草稿），最后修订。隔离回答的效果最好，因为模型会重复上下文中已有的错误 | 反证检索和判定时，不把待验证结论的原有证据放进同一个上下文，避免模型被原结论带偏 |
| **DRNOISE**（2026） | 在环境中植入一篇看起来正常但给出错误答案的文档，各 Deep Research Agent 的准确率下降 66 到 88 个百分点。主要失败模式是验证惰性：Agent 已经检索到真实记录，却在完成对照之前就采信了直接给出答案的文档。通用的验证提示只能部分缓解 | 说明反证不能只是一句提示词，需要强制流程：关键结论必须执行过反证检索，并记录找到或未找到反证 |
| **DeepVerifier** | 分解 Agent 找出可能出错的地方并提出追问，验证 Agent 执行，裁判 Agent 给出可执行的重试指令，多轮反馈 | 与项目的 Replan 审计思路一致，Replan 应输出具体的重试指令（换什么检索词、补哪个单元格） |

### 1.2 对模块一设计的修订

1. **主循环显式化（借鉴 Table-as-Search）**：Coordinator 每一轮根据表状态在 `EXPAND_ROWS`（下发 WIDE_DISCOVERY）和 `POPULATE_CELLS`（下发 DEEP_CELL）之间选择，结束条件为饱和判定加预算上限。不再固定为先做一轮深挖、再做一次宽搜索。
2. **规划使用最强模型**：PLANNING、WIDE_DISCOVERY 的规划调用通过 `llm_purpose_options` 配置为能力最强的模型，深挖抽取使用成本较低的模型。
3. **任务描述补全（借鉴 Anthropic）**：DEEP_CELL 快照增加 `objective`（要回答什么）、`column_specs`（列说明、答案格式）、`boundaries`（只研究当前实体，不要混入其他对比对象的证据）、`effort_tier`。
4. **检索词先宽后窄**：单元格检索词规划的提示词要求第一轮使用 2 到 6 个词的短查询，后续轮次根据结果收窄。
5. **研究简报由模型生成（借鉴 open_deep_research）**：`ResearchBriefCompiler` 改为调用模型生成结构化简报（目标、范围、时间范围、排除项、交付格式），对话上下文只作为生成简报的输入。
6. **多视角生成列（借鉴 STORM）**：PLANNING 先生成 3 到 5 个视角，每个视角给出想问的问题，再合并成列。
7. **计划确认（借鉴 Gemini）**：PLANNING 完成后进入 `PLAN_REVIEW` 状态，前端展示表格，用户可以增删行和列；超过配置时间（默认 0 秒，即不等待）自动开始。
8. **反证改为强制流程（借鉴 SAFE、CoVe、DRNOISE）**：高风险单元格和存在冲突的单元格，必须先把结论拆成原子事实，对每条事实做隔离的反证检索和判定，结果记为 `REFUTED / NOT_REFUTED / NO_COUNTER_EVIDENCE_FOUND`。报告中逐条写明反证结果，没有执行反证的结论不能进入正式结论。
9. **来源独立性**：调研中没有找到把来源独立性形式化的成熟方案。项目采用自定义做法：按注册域名去重，再对证据原文做 SimHash，相似度很高的转载内容合并为同一来源，最后用 noisy-OR 合并置信度。面试时需要说明这是项目自己的设计。
10. **评测（借鉴 Anthropic）**：先用约 20 条真实问题，以单次 LLM 评分为主（0 到 1 分加通过与否，五个维度），再人工抽查。

## 二、Memory 与上下文

### 2.1 代表方案

| 方案 | 核心做法 | 对本项目的启发 |
|---|---|---|
| **Mem0** | 两段式：抽取阶段从最近的对话中提取候选记忆；更新阶段先检索最相似的 S 条已有记忆，再让模型以工具调用的方式选择 ADD / UPDATE / DELETE / NOOP，所有操作写入历史表。图版本 Mem0ᵍ 在出现矛盾时把旧边标为失效，不做删除。有第三方报告指出，部分模型在这一步约有 25% 的输出 JSON 格式错误 | 比槽位精确匹配更通用：槽位用作结构化预过滤，最终操作由模型在相似记忆中判断。删除改为失效标记，保留版本链 |
| **Zep / Graphiti** | 双时间模型：`valid_at / invalid_at` 表示事实在现实中何时成立、何时失效，`created_at / expired_at` 表示系统何时得知、何时被替代。出现矛盾时设置旧边的 `invalid_at`，不删除；两条冲突时，现实中较早发生的那条失效。实体去重使用向量相似度加全文检索的混合方式 | 记忆版本需要区分用户偏好何时改变和系统何时记录，这样可以回答某次回答当时应用了哪条记忆，也便于效果归因 |
| **Letta / MemGPT** | 核心记忆常驻上下文且大小受限，归档记忆按需检索；记忆整理（合并、去重、处理矛盾）由空闲时运行的后台 Agent 完成，不占用对话延迟，因此可以使用更强的模型 | 与常驻类、按需类的划分一致。新增后台整理任务，定期合并近似重复的记忆、复查长期未被强化的记忆 |
| **Generative Agents**（Stanford） | 检索得分 = 新近度（指数衰减）+ 重要度（模型打分 1 到 10）+ 相关度（向量相似度），三项归一化后加权。参考实现中权重是手调的，作者也指出应该通过学习得到 | 记忆注入的价值函数加入新近度（距最近一次强化的时间衰减）；权重用评测集校准，不手调 |
| **LongMemEval**（ICLR 2025） | 评测五种记忆能力：信息抽取、跨会话推理、时间推理、知识更新、拒答。把记忆设计拆成索引、检索、读取三个阶段；有效的优化包括按会话拆分粒度、用事实扩展索引键、对查询做时间感知扩展 | 记忆评测集需要覆盖知识更新（偏好改变后旧偏好不再生效）和拒答（没有相关记忆时不乱用） |
| **对话话题切分研究**（TextTiling 系列、SuperDialseg 等） | 主流的无监督做法：先算相邻语句之间的语义相似度或连贯度，再用 TextTiling 的深度分数找边界；先对语句做指代消解改写，再计算相似度，效果更好；评测指标为 Pk 和 WindowDiff；零样本 LLM 切分在特定领域仍不如有监督模型 | 话题切分使用向量相似度加深度分数，替代单一阈值；复用模块三的查询改写结果（已经做过指代消解）作为切分输入；用 Pk 和 WindowDiff 评测 |

### 2.2 对模块二设计的修订

1. **冲突处理改为两段式（借鉴 Mem0）**：槽位精确匹配作为第一层，能直接判定的直接处理；其余情况检索最相似的 5 条生效记忆，让模型选择 `ADD / MERGE / SUPERSEDE / NOOP`。输出不合规时重试一次，仍不合规则进入人工复核。
2. **双时间字段（借鉴 Graphiti）**：`memory_runtime_revision` 增加 `valid_from`（用户何时表达）、`invalid_at`（被替代或撤销的时间）。替代时只设置 `invalid_at`，不删除。效果反馈按应用当时生效的版本归因。
3. **后台整理任务（借鉴 Letta）**：每天或每积累 N 条新信号时运行一次：合并近似重复的记忆、复查长期未被强化且效用下降的记忆、重新计算 Beta 后验。使用较强的模型，不占用对话延迟。
4. **注入价值函数加入新近度（借鉴 Generative Agents）**：价值 = 置信度 × 效用 × 相关度 × 新近度衰减，四项的指数权重用评测集校准。
5. **话题切分（借鉴 TextTiling 系列）**：以改写后的独立问题计算向量，在相邻消息之间计算相似度，用深度分数找边界；保留现有的显式切换和回到原话题的规则作为强信号。
6. **评测覆盖知识更新和拒答（借鉴 LongMemEval）**。

## 三、检索

### 3.1 代表方案

| 方案 | 核心做法 | 对本项目的启发 |
|---|---|---|
| **MTRAG 及 SemEval-2026 Task 8 参赛系统** | 多轮 RAG 的标准做法是把最后一轮改写成独立查询；改写提示要求模型先判断原问题是否已经独立，独立就原样返回，否则尽量少改，不添加新词。有参赛系统发现：**最后一轮原文与改写结果拼接后检索**，效果优于单独使用任何一个；用多种改写（最小改写、HyDE、关键词锚点等）分别检索，再做嵌套 RRF；对话越长，改写的累计误差越大 | S1 的改写设计采用这些细节：先判断是否独立；BM25 通道使用原文加改写的拼接；多改写结果做 RRF |
| **Anthropic Contextual Retrieval**（2024-09） | 在建索引前，让模型为每个片段生成 50 到 100 token 的上下文说明（这段属于哪份文档、讲什么），拼在片段前面再做向量化和 BM25。检索失败率：向量化加上下文后下降 35%，再加 BM25 下降 49%，再加 Rerank 下降 67%。借助提示词缓存，每百万文档 token 的成本约 1 美元 | 项目已有混合检索和 Rerank，缺少片段上下文增强。可在流水线的向量化阶段之前增加一步，属于索引侧的改动 |
| **HippoRAG**（NeurIPS 2024） | 以查询中的概念为种子，在知识图谱上运行个性化 PageRank，一步完成多跳检索；对连接度很高的节点降权（节点特异性）。比 IRCoT 等迭代检索便宜 10 到 30 倍、快 6 到 13 倍 | 与 Wiki 多跳扩展选用 PPR 的方案一致。补充节点特异性：被大量页面链接的枢纽页按度数降权，避免扩展结果总是落到几个大页面上 |
| **Microsoft GraphRAG / LightRAG** | GraphRAG 预先对图做社区划分并生成社区摘要，全局问题读社区摘要，局部问题读实体邻域。LightRAG 由模型从问题中抽取低层关键词（具体实体）和高层关键词（主题），分别检索实体和关系 | Wiki 页面本身就是模型写的主题摘要，相当于社区报告，不需要再建一层。查询改写的输出可以增加低层和高层两组关键词，分别用于精确匹配和主题匹配 |
| **Google Sufficient Context**（ICLR 2025） | 定义证据是否足以回答问题，用 LLM 评审，准确率 93%；在证据不足时模型更倾向于编造答案而不是拒答；把证据充分性与模型置信度组合起来决定是否回答，正确回答比例提高 2% 到 10% | 项目目前的 `QaEvidenceRelevancePolicy` 只做词项覆盖判断，且只在降级路径中使用。可以新增证据充分性判断，证据不足时明确告诉用户资料中没有足够信息 |
| **WeKnora**（腾讯） | BM25、向量、GraphRAG 混合召回，RRF 融合后 Rerank；支持 Wiki 模式和 ReAct Agent | 项目 QA 链路已参照它实现（策略档案名为 `qa-weknora-hybrid`），不需要额外借鉴 |

### 3.2 对模块三设计的修订

1. **改写细节（借鉴 MTRAG）**：改写输出增加 `is_standalone`，为真时直接使用原问题；BM25 查询使用最后一轮原文与改写结果的拼接；改写输出增加 `low_level_keywords`（实体）和 `high_level_keywords`（主题），分别对标题和正文字段加权。
2. **新增 S6：片段上下文增强（借鉴 Contextual Retrieval）**：在流水线的切片和向量化之间增加一步，为每个片段生成上下文说明，按资料分批调用并利用提示词缓存。上下文说明同时写入向量文本和 BM25 字段，原文保持不变用于展示和引用。增量复用缓存的键需要包含上下文说明的哈希。
3. **PPR 加节点特异性（借鉴 HippoRAG）**：扩展分数除以 `log(1 + 入度)`。
4. **新增 S7：证据充分性判断（借鉴 Sufficient Context）**：QA 生成前用 LLM 判断选出的证据是否足以回答，结合 Rerank 分数决定是否回答、部分回答或明确说明资料不足；判断结果写入回答记录，供评测统计拒答率和误拒率。
5. **评测增加 MTRAG 风格的多轮问题集**：问题分为可回答、不可回答、部分可回答三类，同时考察检索和拒答。

## 四、产物生成框架

### 4.1 代表方案

| 方案 | 核心做法 | 对本项目的启发 |
|---|---|---|
| **Instructor** | 用 Pydantic 定义输出结构，校验失败时把校验错误发回模型重新生成（reask），直到通过或达到重试上限；支持用 LLM 实现的语义校验器，失败时返回自然语言原因，作为下一次生成的修改依据 | 节点执行器的结构校验和重试直接采用这个模式，校验错误原文作为修复提示 |
| **DSPy Assertions** | 断言分两种：`Assert` 失败时回溯重试指定模块，持续失败则终止；`Suggest` 同样重试，但持续失败时只记录并继续执行。可以指定回溯到哪个模块。实验中约束满足率最多提升 164%，回答质量最多提升 37% | 输出契约中的规则分为硬性和建议两级，每条规则声明失败时回到哪个节点重做，不再统一只重写章节 |
| **ALCE**（Princeton，EMNLP 2023） | 用 NLI 模型评估引用：引用召回率（每个陈述是否被它引用的片段完整支持）和引用精确率（每个引用是否与陈述相关）；与人工判断相关系数超过 0.9；NLI 的弱点是难以识别部分支持 | 证据支撑校验同时计算召回率和精确率，前者对应无依据的陈述，后者对应凑数的引用 |
| **RAGAS Faithfulness** | 把回答拆成独立陈述，逐条判断能否从上下文推出；更细的标签分为支持、矛盾、不支持、非事实性、无法判断；可以用 Vectara 的 HHEM 小模型替代 LLM 判断，降低成本 | 章节校验以陈述为单位，标签采用更细的五类；大批量校验时可在 Worker 中先用 HHEM 初筛，只把不确定的部分交给 LLM |
| **STORM** | 先研究并生成大纲，再按大纲逐节写作，每节使用自己的参考资料 | 与按章节生成的方案一致 |
| **Anthropic 引用 Agent** | 正文写完后，由独立的步骤根据全部资料为每个论断定位引用 | 可作为备选：写作节点专注内容，引用节点负责定位片段，降低单次生成的负担 |
| **Anthropic Agent Skills** | 技能分三层按需加载：元数据（名称和描述，每个约 80 token）常驻；被选中后才加载完整说明；脚本和参考资料最后加载，脚本在外部执行，不占上下文 | 项目的 Skill 目录可以按同样的分层组织：目录只放元数据，提示词配方和参考资料按节点按需加载 |

### 4.2 对模块四设计的修订

1. **节点重试（借鉴 Instructor）**：`LLM_STEP` 校验失败时，把 Pydantic 的错误信息原文附在提示词中重试，最多 2 次。
2. **规则分级与回溯目标（借鉴 DSPy）**：`output_contract.rules` 每条规则声明 `level`（`ASSERT` / `SUGGEST`）和 `backtrack_to`（失败时回到的节点）。例如无依据数字回到 `impact_normalizer`，引用缺失回到引用节点，章节数量不足回到大纲节点。
3. **证据校验指标（借鉴 ALCE、RAGAS）**：以陈述为单位计算引用召回率和引用精确率，标签使用五类；HHEM 初筛作为可选配置，默认关闭。
4. **引用独立成节点（借鉴 Anthropic）**：`SECTIONED` 模式下，写作节点只负责内容，后面增加 `cite` 节点为每个陈述定位片段，定位不到的陈述交给修复节点。
5. **Skill 目录分层（借鉴 Agent Skills）**：目录接口只返回元数据，提示词配方、输出契约、规则插件在执行时按节点加载。

## 五、资料处理流水线

### 5.1 代表方案

| 方案 | 核心做法 | 对本项目的启发 |
|---|---|---|
| **Docling**（IBM，MIT 协议，LF AI 基金会） | 版面检测模型加 TableFormer 表格结构识别，扫描件回退到 EasyOCR 或 Tesseract；支持 PDF、DOCX、PPTX、XLSX、HTML；输出带出处信息（页码、坐标、元素类型）的文档结构。在 OpenDataLoader 评测的 12 个引擎中排第一（标题层级 0.824、表格 0.887、阅读顺序 0.898） | 一个组件即可覆盖多格式、版面、表格、OCR 四项需求，比 Tika、Tabula、双栏启发式、单独 OCR 组合起来更省事，也更可靠 |
| **Marker**（Datalab） | 基于 Surya 模型，输出整洁的 Markdown；厂商自测在 olmOCR-bench 上领先，速度为 2.9 页每秒 | 速度快，但评测由厂商自己运行，复杂表格的效果偏弱 |
| **MinerU**（上海人工智能实验室） | 中文、金融、科技文献效果好，公式识别强（UniMERNet），只支持 PDF，GPU 加速明显 | 如果资料以中文论文为主，值得和 Docling 在项目样例上对比 |
| **RAGFlow DeepDoc** | 每页运行 OCR、表格结构识别、版面识别三个模型，版面分为 10 类（正文、标题、图、图注、表、表注、页眉、页脚、参考文献、公式）；结构信息直接用于切片，使表格保留表头、图保留图注 | 解析输出的元素类型应传给切片器，表格和图注不跨片段拆开 |
| **两份评测的分歧** | olmOCR-bench（厂商运行）上 Docling 只有 50.3 分，OpenDataLoader 上 Docling 排第一 | 选型必须在项目自己的样例集上测，不能直接引用别人的排名 |
| **Kafka 长任务处理** | 优先调小 `max.poll.records`；`max.poll.interval.ms` 设为高于 P99 处理时间；处理确实很长时使用暂停分区加异步处理，手动提交位移，失败时 seek 回失败位置，处理逻辑保证幂等；使用静态组成员避免滚动重启时触发重平衡 | 与向量化分批的方案一致，补充静态组成员配置 |
| **tus 断点续传协议** | 用 HEAD 查询服务端已确认的偏移量，从该偏移继续 PATCH；偏移不一致返回 409；可选扩展包括校验和、过期、拼接；正在 IETF 标准化 | 项目的分片上传加查询已上传分片接口，功能上等价。保留现有接口，补充过期清理和校验和失败的错误码 |
| **LlamaIndex Ingestion Pipeline** | 缓存键 = 输入内容哈希 + 变换配置哈希；文档存储记录每个文档 ID 对应的内容哈希，内容未变则跳过，变化则更新，源已删除则删除 | 向量缓存的键必须包含切片器版本和上下文增强配置，否则切片规则调整后会误用旧向量 |

### 5.2 对模块五设计的修订

1. **解析方案改为 Docling 服务（替代 Tika + Tabula + 自写双栏检测 + 单独 OCR）**：在 Python 侧新增解析服务（可以放进 Artifact Worker 的系统 MCP，或者独立成 `parse-worker`），输入原件，输出带元素类型、页码、坐标的文档结构，Java 端转成 Markdown 和元素列表交给切片器。Java 端保留 PDFBox 和纯文本解析，作为解析服务不可用时的降级方案。
2. **选型评测**：在 `experiments/pipeline/` 准备 30 份样例（中文论文、英文双栏论文、扫描件、带表格的报告、PPT、Word），对比 Docling 和 MinerU 的标题层级、表格、阅读顺序、耗时，再确定默认引擎。
3. **切片器接收元素类型（借鉴 DeepDoc）**：表格、图注、公式作为不可拆分的块，表格保留表头，图注跟随图片位置。
4. **Kafka 配置**：增加静态组成员 `group.instance.id`，`max.poll.records=1`，`max.poll.interval.ms` 按 P99 设定。
5. **向量缓存键（借鉴 LlamaIndex）**：`(embedding_version, chunker_version, context_prompt_version, sha256(片段文本))`。
