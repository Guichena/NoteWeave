# 模块三：QA / Note / Wiki 检索改造设计

## 1. 现状结论

QA 主链路做得比较完整：向量和 BM25 双路召回 → 加权 RRF → 归属校验 → Rerank → 拼接相邻切片 → 按来源多样性和字符预算选证，召回不足时做查询扩展，Provider 不可用时直接失败。`retrieval/eval` 下已有标注、回放、质量门禁等评测基础设施。

问题集中在三处：送进检索的查询文本本身、Note 链路的分数融合、Wiki 链路的检索实现。

## 2. 缺陷清单

| 编号 | 缺陷 | 位置 |
|---|---|---|
| Q1 | 多轮对话时，送进向量化和 BM25 的查询是一段多行文本：当前问题 + 主题锚点 + 最近几轮的用户问题和助手摘要 + 前序摘要 + 用户约束。追问场景下真正的问题被大量上下文稀释，向量偏向历史话题，BM25 被历史词项干扰。三种模式共用这个查询 | `ConversationRetrievalContextAssembler.java:61`、`:110`，`ChatService.java:258` |

## 3. 改造方案

### S1 检索查询改写（解决 Q1、Q2、Q3）

1. 新增 `QueryRewriteService`，在有对话上下文时调用 LLM，输入当前问题、最近原文窗口、话题摘要，输出：
   ```json
   {
     "standalone_query": "PostgreSQL 的 GIN 索引支持哪些 JSONB 运算符",
     "keyword_query": "PostgreSQL GIN JSONB 运算符 jsonb_path_ops",
     "alternatives": ["jsonb_ops 和 jsonb_path_ops 的区别"],
     "question_type": "comparison",
     "must_terms": ["GIN", "JSONB"],
     "language": "zh"
   }
   ```
2. 各通道使用不同的查询：向量通道用 `standalone_query`，BM25 通道用 `keyword_query` 并对 `must_terms` 加权，召回不足时用 `alternatives` 做多查询召回，所有结果统一做 RRF。Rerank 使用 `standalone_query`。
3. 对话上下文只传给生成阶段，不再拼进检索查询。
4. 没有对话上下文的首轮问题跳过改写，直接使用原问题，不增加延迟。
5. 改写结果写进 `RetrievalPlan.filters`（已有 `retrieval_queries`、`must_terms`、`question_type` 等字段位），可回放、可审计。
6. 降级：LLM 不可用时，`standalone_query` 取当前问题原文，`keyword_query` 取当前问题加上话题锚点的关键词，不再拼接整段对话。
7. `QaQueryExpansionService` 的规则扩展只在改写不可用时使用。

### S2 公共 BM25F 组件（N1、N3、W2 的前置）

把 `KnowledgeWikiSearchEngine.bm25f` 抽成 `retrieval/lexical/Bm25fScorer`：输入字段定义（名称、权重、`b`）和文档集合，输出分数。切词规则沿用 `KnowledgeWikiSearchEngine.Query` 现有的实现并一起抽出（汉字二元切分加英文词项），Note、Wiki、记忆匹配共用这一套，避免各处各写一套切词。

### S3 Note 链路的分数融合（解决 N1、N2、N3、N4）

1. **资料召回（N2）**：五路信号各自产生排名，统一做加权 RRF：
   - 向量、ES 元数据、标签、笔记日志、关系扩展各为一路，权重写进策略档案（类似 `QaRetrievalStrategyProfile`），用评测集校准；
   - 窗口就绪度不参与打分，改为过滤条件：没有阅读窗口的资料不进入阅读阶段，只作为关系扩展的来源；
   - 融合后的前 40 条进入现有 Rerank。
2. **降级打分（N3）**：用 S2 的 BM25F 替代手调字段权重。
3. **阅读窗口（N1）**：在候选资料范围内，窗口级的 BM25 排名和向量排名做 RRF，再进入现有窗口 Rerank。主窗口、延续窗口、次要窗口的选择逻辑保留。
4. **加载范围（N4）**：候选集合只取各通道召回结果的并集，再按 ID 批量回填元数据；笔记与资料的关联按候选 ID 查询，不再全量加载。

### S4 Wiki 检索迁移到 ES 并引入向量（解决 W2）

1. 新建 `noteweave-wiki` 索引：`title`、`summary`、`content` 三个文本字段，`page_embedding` 向量字段，`citation_count`、`backlink_count`、`updated_at` 数值字段。Wiki 页面新建或改版时经 outbox 异步写入，复用资料检索投影的写入器和重建工具。
2. 查询：`multi_match`（title^3、summary^2、content）与向量 kNN 两路召回，RRF 融合，再加权威度加成（保留现有的 `log1p` 公式和上限），最后 Rerank。
3. 现有内存 BM25F 只在 ES 不可用时使用，且限制加载最近 500 页，并记录降级原因。
4. 链接计数改为在索引里维护，去掉每行 4 个关联子查询。

### S5 Wiki 多跳图扩展（解决 W1）

1. 以检索命中的页面为种子，在 `knowledge_item_link` 上做个性化 PageRank：重启概率 0.3，最多迭代 20 次或收敛，邻接按需分批加载，最多扩展 3 跳。
2. 种子的初始权重取检索的融合分数，扩展得到的页面分数为 PPR 分数。
3. 按 PPR 分数在节点数、边数、字符数三项预算内贪心选取扩展页面；每个扩展页面记录到达路径（种子 → 中间页 → 扩展页），回答时作为引用说明。
4. `graph_hops_used` 等指标改为真实统计值。

## 5. 评测

用 `retrieval/eval` 已有的标注和回放工具，分三组问题集：

- **首轮问题**：Recall@10、MRR、nDCG@10，确认改写不影响首轮效果；
- **多轮追问**：同样的指标，这是 S1 的主要收益；
- **Wiki 关联问题**（答案需要跨页面）：统计答案所需页面的覆盖率，衡量 S5 的效果。

同时记录每个阶段的 P50 / P95 延迟，改写带来的额外延迟需要在报告中写明。结果放进 `experiments/retrieval/`。

## 7. 实施记录

### 3A（2026-10-12 完成）

- 新增 `QueryRewriteService`。有对话上下文且模型可用时调用 `ChatLlmClient.streamChat`，校验 `is_standalone`、两个查询、`question_type`、`language` 和字符串数组；不合规时把错误附在提示里重试一次。首轮跳过模型，`method` 为 `RULE`，`degradation_reasons` 为空。模型关闭、调用失败或两次输出都不合规时，独立问题用当前问题原文，关键词查询用原文加话题锚点，原因码分别为 `QUERY_REWRITE_DISABLED`、`QUERY_REWRITE_LLM_UNAVAILABLE`、`QUERY_REWRITE_LLM_CALL_FAILED`、`QUERY_REWRITE_OUTPUT_INVALID`。
- `ChatService` 把 `AnswerContext.query()` 改为独立问题。`ConversationRetrievalContextAssembler` 仍然生成多行拼接文本，只写入改写输入和生成提示里的 `conversation_window`。
- QA、Note、Wiki 的 `plan` 都把改写结果复制进 `RetrievalPlan.filters`。向量和 Rerank 用独立问题，BM25 用关键词查询。`is_standalone` 为真时两路都用原文。召回不足时，模型改写只用 `alternatives` 做多查询并继续走原来的 RRF；规则改写仍用 `QaQueryExpansionService`。
- `must_terms`、`low_level_keywords`、`high_level_keywords` 做 should 加权，不做硬过滤。QA 的 Elasticsearch 分别提高 title/heading/content、title/heading、content。Note 元数据索引分别提高全部文本字段、title/tags、summary/section_descriptions。Wiki 仍是内存 BM25F，must 词乘 2，标题词再乘标题字段，正文词再乘正文字段；这些词不参与覆盖判定。Note 五路分数相加和 BM25F 公共组件留到 3B。
- 回答详情和证据接口从已保存的 `retrieval_plan_json` 读出 `retrieval_rewrite`，不新增表列，也不返回 `evidence_sufficiency`。
- `ScopedPassageSearch` 的实现是 `HybridScopedPassageSearch`，基于现有 QA 混合检索。调用方传入的 query 已是独立问句。Provider 不可用时返回 degraded。
- 配置 `noteweave.retrieval.query-rewrite.enabled` 默认打开。没有 Flyway 迁移。
- 与旧计划兼容：filters 里没有 `rewrite_method` 时，三个通道仍使用原来的单一查询。直接搜索 Wiki 时，旧的「当前问题：」「主题锚点：」前缀仍然能解析。Wiki 回答链路在关键词查询比独立问题多出话题锚点时，会把这两段拆回上述两行，覆盖判定继续按组取或；加权词本身仍不进入覆盖判定。
- 测试覆盖改写服务、计划字段、QA 分通道、范围检索降级和 Wiki 加权。没有用真实模型验证改写质量。
