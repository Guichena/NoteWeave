# 模块四：Schema 驱动的产物生成框架改造设计

## 1. 现状结论

框架层面做得比较完整：Skill 目录（输入 Schema、能力白名单、图定义）、执行计划编译（技能图拓扑排序、环检测）、能力解析与审批等待、异步 Provider 等待与恢复、产物版本与导出、MCP 接入音视频转写。视频学习链路有真实的 LLM 规划和基于素材包的校验。

但产物内容的生成过程名不副实：技能图节点是字符串模板，修复动作是用固定句子补数量，真正的内容来自一次 LLM 调用，校验不通过就直接失败。

## 2. 缺陷清单

| 编号 | 缺陷 | 位置 |
|---|---|---|
| A1 | 技能图节点（素材摘要、亮点抽取、影响归一化、要点写作）是字符串模板，例如 `推进 {phrase} 主链路设计，将 {summary} 组织为可复用运行时能力`。写死了定位句（Controlled Agentic Graph Harness、Capability Union Policy 等）和三条影响描述。这些节点的输出最终被一次 LLM 调用的结果覆盖，只留在 trace 里 | `skill_graph.py:98-250`、`:989` |
| A2 | 节点修复就是补齐数量：亮点不足 3 条时塞入固定句子，并把节点标成 `repaired` | `skill_graph.py:455-505` |
| A3 | 最终校验不通过直接抛错，没有修复重试；`repaired_checks` 始终为空列表 | `runner.py:246`、`:387` |
| A4 | 素材选择按顺序截断：每份资料最多 6000 字符，总计 24000 字符，取满为止，和用户要求、大纲章节都无关 | `generation_runtime.py:77` |
| A5 | 所有产物类型都是一次调用生成全部章节，学习指南、测验这类长产物容易超出输出长度或质量下降 | `generation_runtime.py:34` |
| A6 | 意图编译靠规则：看到校招、面试就判定受众为面试官，重点按逗号切分 | `intent_compiler.py:153`、`:206` |
| A7 | 证据覆盖只检查章节引用的资料标题是否存在，不检查内容是否支撑章节 | `runner.py:1157` |
| A8 | 校验器按类型手写（简历、测验、Wiki 各一个函数），所有 Skill 的 `output_schema_ref` 都是同一个 `artifact-content-v1`，目录里没有声明输出契约 | `verifier.py:301-656`、`artifact-skill-catalog-v2.json` |

## 3. 改造方案

### S1 技能图节点改为真实执行的类型化步骤（解决 A1、A2）

1. 目录里的每个图节点声明：`node_kind`（`LLM_STEP` / `RETRIEVE` / `VERIFY` / `REPAIR` / `TOOL`）、`prompt_recipe_id`、`input_schema`、`output_schema`。
2. 新增 `NodeExecutor` 接口，按 `node_kind` 分派：
   - `LLM_STEP`：按配方渲染提示词，调用 `complete_json`，用 pydantic 校验输出，不合规时带着校验错误重试一次；
   - `RETRIEVE`：见 S2；
   - `VERIFY` / `REPAIR`：见 S4。
3. 节点之间通过图状态传递，每个节点只能读取声明过的输入字段。
4. 以简历亮点为例，重写后的图：
   ```
   material_retrieve → fact_extractor → impact_normalizer → bullet_writer → verify → repair
   ```
   - `fact_extractor`：从检索到的片段中抽取事实，每条事实必须带片段 ID 和原文引用；
   - `impact_normalizer`：只保留原文中有依据的数字，没有数字的事实不允许编造指标；
   - `bullet_writer`：基于事实写要点，每条要点引用事实 ID。
5. 删除全部模板生成函数、写死的定位句和影响描述，删除按数量补齐的修复逻辑。

### S2 按大纲检索素材（解决 A4）

1. Java 新增内部接口 `POST /internal/worker/artifact-tasks/{taskId}/retrieve`，输入查询文本和条数，复用模块三改造后的混合检索，检索范围限定在任务快照的资料范围内，返回片段 ID、资料 ID、位置和内容。
2. Worker 的 `RETRIEVE` 节点按 `用户要求 + 大纲章节` 生成查询，每个章节单独检索，按片段去重后组成章节级素材包。
3. 预算按章节分配，不再按资料顺序截断。
4. 降级：接口不可用时，在本地对内容对象做 BM25 检索，并记录降级原因。

### S3 按章节生成（解决 A5）

1. 先生成大纲（章节标题、每章要点、引用的片段 ID），再按章节并发生成正文，每章只拿自己的素材包。
2. 最后一步做全文一致性检查（术语统一、章节之间不重复），只修改有问题的段落。
3. 短产物（简历亮点、摘要）保留单次生成，由目录里的 `generation_mode`（`SINGLE` / `SECTIONED`）配置。

### S4 校验与修复闭环（解决 A3、A7、A8）

1. **声明式输出契约**：目录里每个 Skill 增加 `output_contract`，示例：
   ```json
   {
     "sections": {"min": 3, "max": 8, "required_headings": ["一句话定位"]},
     "fields": {"bullets": {"type": "array", "min_items": 3, "max_items": 5}},
     "citation": {"density": "PER_SECTION", "ref_kind": "CHUNK"},
     "rules": ["no_fabricated_metrics", "quiz_answer_in_options"]
   }
   ```
   结构部分用 JSON Schema 校验；`rules` 是注册过的具名规则，现有简历、测验、Wiki 的专用检查改写成规则插件。新增产物类型时只需改目录。
2. **证据支撑校验**：引用改为片段 ID。每个章节先算章节文本和引用片段的词项覆盖，覆盖率低于阈值或含有数字、专有名词的句子，再调用 LLM 判断是否被片段支撑，输出 `SUPPORTED / PARTIAL / UNSUPPORTED`。LLM 不可用时记为 `NOT_RUN`，`citation.density` 为必需的 Skill 不允许通过。
3. **修复循环**：校验失败时，把失败项（哪个章节、哪条规则、哪句话不被支撑）交给 `REPAIR` 节点，只重写失败的章节，最多 2 轮。仍然失败时才判为失败，trace 记录每轮的失败项和修改内容。

### S5 意图编译改用 LLM（解决 A6）

调用 `artifact.compile_intent`，把用户要求编译成 `ExecutionSpec`（受众、重点、风格、约束、输出语言），用 pydantic 校验。LLM 不可用时退回现有规则，并在 trace 里记录。

## 4. 实施顺序

| 阶段 | 内容 |
|---|---|
| 4A | S4 的输出契约与规则插件、S5 意图编译 |
| 4B | S2 素材检索接口与 `RETRIEVE` 节点 |
| 4C | S1 节点执行器，简历亮点图重写，删除模板代码 |
| 4D | S4 的证据支撑校验与修复循环 |
| 4E | S3 按章节生成，学习指南、测验、Wiki 页面迁移到新图 |

4B 依赖模块三的混合检索；如果模块三还没做完，先接入现有的 QA 混合检索。

## 5. 评测

每种产物类型准备 10 个输入，统计：契约一次通过率、修复后通过率、句子级证据支撑率、无依据数字的出现次数、单次生成的耗时和 token 数。结果放进 `experiments/artifact/`。

## 6. 参考业界方案后的修订

依据见 [00-业界方案调研](00-业界方案调研.md) 第四部分。

| 修订 | 影响的方案 | 来源 |
|---|---|---|
| `LLM_STEP` 校验失败时把校验错误原文附在提示词中重试，最多 2 次 | S1 | Instructor |
| 契约规则声明 `level`（`ASSERT` / `SUGGEST`）和 `backtrack_to`（失败时回到的节点） | S4 | DSPy Assertions |
| 证据校验以陈述为单位，计算引用召回率和引用精确率，标签为支持、矛盾、不支持、非事实性、无法判断；HHEM 初筛作为可选配置 | S4 | ALCE、RAGAS |
| `SECTIONED` 模式增加独立的 `cite` 节点，写作节点只负责内容 | S3、S4 | Anthropic 引用 Agent |
| Skill 目录接口只返回元数据，提示词配方、契约、规则插件按节点加载 | S1 | Agent Skills |
