# 模块五：异步资料处理流水线改造设计

## 1. 现状结论

这是五个模块里最扎实的一个：解析、切片、向量化、索引拆成四个 Kafka 阶段，按快照阶段状态保证幂等；Outbox 有租约、指数退避加抖动、死信队列与手动重放；Kafka 消费端有 `DefaultErrorHandler` 加死信发布；分片上传有 MD5 校验、SHA-256 去重和引用计数；切片器已经是结构感知的；PDF 解析会去掉页眉页脚、合并断行；索引失败有定时重试。

问题集中在资料格式覆盖、大文件在单个阶段内的耗时、上传体验三方面。

## 2. 缺陷清单

| 编号 | 缺陷 | 位置 |
|---|---|---|
| P1 | 只支持 txt、md、json、csv、pdf 五种格式，docx、pptx、xlsx、html、epub 都会报不支持 | `SourceDocumentTextExtractor.java:38`、`:66` |
| P2 | 扫描版 PDF 没有文字层时直接失败，提示用户自己先做 OCR；部分页是扫描页的混合 PDF，这些页的内容会静默丢失 | `SourceDocumentTextExtractor.java:129` |
| P3 | PDF 用 `PDFTextStripper` 默认模式抽取，没有按位置排序，双栏论文的阅读顺序会错乱，表格被拆成散乱的文本行 | `SourceDocumentTextExtractor.java:121` |
| P4 | 向量化阶段在一次 Kafka 消费里完成整份资料的全部片段，没有批次级检查点。大文件可能超过默认 `max.poll.interval.ms`（300 秒），触发重平衡后整份重做，可能反复循环；资料改版时未变化的片段也会全部重新向量化 | `SourceRetrievalProjectionService.java:116`、`KafkaTaskConsumer.java:163` |
| P5 | 文本类资料用 `readAllBytes` 整个读入内存后再解码 | `SourceDocumentTextExtractor.java:90` |
| P6 | 上传缺少断点续传查询接口，页面刷新后前端无法知道哪些分片已上传；没有秒传，相同文件也要完整上传后才在合并阶段按哈希去重；合并时先把所有分片从 MinIO 读回本地再写回去 | `UploadController`、`UploadService.java:268` |
| P7 | 音视频转写在 Artifact Worker 进程内用守护线程执行，没有并发上限，同时上传多个视频会同时启动多个 faster-whisper 任务 | `source_transcription.py:92-122` |

## 3. 改造方案

### S1 多格式解析（解决 P1、P5）

1. 引入 Apache Tika（`tika-core` + `tika-parsers-standard`），新增 `TikaDocumentExtractor` 处理 docx、pptx、xlsx、html、epub、rtf 等格式；PDF 继续走现有的 PDFBox 链路（S2、S3 在此基础上增强）。
2. 结构保留：用 Tika 的 XHTML 输出，把标题（h1 到 h6）转成 Markdown 标题，表格转成 Markdown 表格，pptx 每页加 `## 第 N 页` 标题，xlsx 每个工作表转成 CSV 块。这样现有的结构感知切片器可以直接利用标题层级和表格。
3. 所有格式统一以流的方式读取，设置提取文本的上限（默认 2000 万字符），超过时截断并在资料状态里给出提示。文本类文件用流式解码，编码探测改为读取前 64KB。
4. 前端上传的格式白名单、`UploadSecurityPolicy` 的类型校验同步扩展。

### S2 OCR 兜底（解决 P2）

1. 按页判断：一页抽出的文字少于阈值（例如 20 个字符）且页面包含图片时，把这一页渲染成图片交给 OCR。
2. OCR 引擎放在 Artifact Worker 的系统 MCP 服务里（和转写同一个位置），新增 `ocr_pages` 工具，使用 RapidOCR（ONNX 运行，中英文效果较好，不需要 GPU）。
3. 解析阶段遇到需要 OCR 的页面时，进入 `OCR_PENDING` 子阶段，提交 OCR 任务，回调后合并文字，再进入切片阶段。流程和现有的音视频转写回调一致。
4. 每页记录文字来源（`TEXT_LAYER` / `OCR`）和 OCR 置信度，检索结果展示时可以标注来自 OCR。

### S3 版面感知的 PDF 抽取（解决 P3）

1. `PDFTextStripper` 开启 `setSortByPosition(true)`。
2. 双栏检测：统计每页文本块的横坐标分布，存在明显的中间空白带时按栏切分，先左栏后右栏。
3. 表格检测：引入 Tabula-java，检测到的表格区域单独抽成 Markdown 表格，从正文流中去掉对应区域，避免重复。
4. 用一组样例 PDF（单栏、双栏论文、带表格的报告、扫描件）做回归测试，比较抽取文本和人工标注的编辑距离。

### S4 向量化分批检查点与增量复用（解决 P4）

1. 把向量化阶段拆成多条消息：每批 64 个片段一条消息，主题仍为 `noteweave.source.embed`，消息体带批次号。每批完成后把结果写入派生存储 `embeddings-{version}/batch-{n}.bin`，并在 `source_embedding_batch` 表记录状态。
2. 所有批次完成后由最后一个完成的批次（数据库行锁判定）投递索引阶段。
3. 增量复用：按 `(embedding_version, sha256(片段文本))` 建立向量缓存表。同一工作区内，文本相同的片段直接复用已有向量，资料改版时只计算变化的片段。
4. 消费端配置 `max.poll.records=1`，并显式设置 `max.poll.interval.ms`，保证单条消息的处理时间有明确上界。

### S5 上传体验（解决 P6）

1. **断点续传**：新增 `GET /api/v2/uploads/{uploadId}`，返回已上传的分片序号列表；前端恢复上传时只补传缺失的分片。
2. **秒传**：创建上传时允许前端携带整个文件的 SHA-256（前端用 Web Worker 分块计算）。后端在 `file_object` 中命中相同哈希时直接引用已有对象并创建资料，跳过分片上传。后端仍在合并或复用时校验大小一致，防止伪造哈希。
3. **合并**：改用 MinIO 的 `composeObject` 在服务端拼接分片。拼接后的对象以流的方式读取一次计算 SHA-256，并与前端声明的哈希比对。

### S6 转写任务限流（解决 P7）

1. Worker 内用有界队列加固定大小线程池（默认 1，可配置）替代每任务一个守护线程。
2. 队列满时拒绝新任务，Java 端收到拒绝后保持 `TRANSCRIBING` 状态并按退避重试提交。
3. 任务状态持久化在现有的 `inputs/source-transcriptions/{snapshot_id}` 目录中，重启恢复逻辑保留，只是改为放入队列，不再直接起线程。

## 5. 评测

- **格式覆盖**：每种格式准备 5 个样例，检查标题层级和表格是否保留；
- **大文件**：用 128MB 文本和 500 页 PDF 测端到端耗时、峰值堆内存，以及中途杀掉消费者后的恢复耗时；
- **增量复用**：修改一份资料的 5% 内容后重新上传，统计重新向量化的片段比例；
- **PDF 抽取**：样例集上的字符级编辑距离，改造前后对比。

结果放进 `experiments/pipeline/`，简历中 128MB 单文件异步接入的描述以这里的实测数据为准。

### 5A 多格式解析、断点续传与秒传（2026-10-13）

- 新增独立 `workers/parse-worker`，固定 Docling 2.138.0。支持 PDF、DOCX、PPTX、XLSX、CSV、HTML、EPUB、DOC、RTF、ODT、Markdown 和 TXT；普通 JSON 沿用 Java 纯文本降级。旧 DOC、RTF 的本地转换依赖 LibreOffice，ODT 配置对应 SDK 依赖。关闭文档资源的本地与远程抓取，关闭外部插件和远程服务。
- 内部接口 `POST /internal/parse` 接收二进制文件流，绑定工作台、资料、快照、文件名、MIME 和真实 SHA-256。专用令牌缺失或不匹配时拒绝；上传上限 256 MiB，默认输出上限 2000 万字符、10 万元素，默认接纳一个文档。超时请求返回错误，后台实际转换结束后才释放槽位和临时文件。
- Java 默认优先调用 Docling，文件流发送与接收均有上限，拒绝重复 JSON 字段、多份 JSON、未知字段、身份及摘要不符和非法结构坐标。服务不可用时 PDFBox、纯文本真实降级并记录原因；Office 等没有解析器时失败。PDFBox 按位置排序，文本只探测前 64 KiB，再流式解码。保留旧字节入口与构造器兼容已有调用。
- 解析结果在同快照下保存 `parsed-document.json` 和兼容文本。提交及切片时重检最新快照资格，MIME 绑定快照文件对象并归一化。未知总页数为 0，仍可保留真实正整数页码；未提供页码、坐标、标题级别时保持空值。多定位原子元素保留首个真实位置并告警，不重复全文。
- 切片器接收类型化元素，表格、图注、公式完整独立成片；超出 Token 预算仍保存完整元素及阅读窗口，并标记超预算。`V144__source_chunk_structure_metadata.sql` 增加可空结构元数据，旧文本和转写路径保持兼容。
- 上传新增状态查询、格式列表和可选 `sha256`，`V143__upload_expected_sha256.sql` 保存声明摘要。状态返回已上传序号；已过期会话返回 404；完成接口幂等。秒传仅复用同工作台已存在且当前可读的资料，核对大小和对象存在性；未命中可读资料仍走正常上传。格式静态路径保留身份认证，仅排除上传 ID 权限路径匹配。
- MinIO 合规分片使用服务端合成，再流式读取一次核对大小、摘要和文件内容；旧非末分片不足 5 MiB 时流式合并兼容。永久原件使用服务端复制；数据库事务回滚时清理本次新建对象，保留共享对象。新文件对象使用独立 ID 路径，避免并发回滚误删。
- 新增 `noteweave.source-parser` 连接与预算配置，默认开启；Compose 新增解析服务，容器 8000、宿主 18103，模型缓存目录授予运行用户权限。测试配置关闭外部解析连接，专属 HTTP 测试使用本地模拟服务。
- 公式元素的 `text` 为空时读取 Docling 保存的真实 `orig`，避免 PDF 公式原文丢失；不推断或生成公式。自动化验证：Parse Worker 83、Artifact Worker 622、Research Worker 758、Frontend 320 项通过；Backend 全部 290 个测试类、1483 项中 1472 项通过、11 项沿用既有跳过条件，全部报告没有缺失、陈旧结果或失败。前端类型与界面契约检查通过，Compose 结构与服务地址核对通过。
- Backend 首轮出现两处测试断言或参数问题，已按真实行为修正；全量一个分组因本机 JVM 原生内存不足退出，另一个在用户继续消息到来时未完成，已独立重跑并核对完整 XML。未修改生产内存参数。真实文档质量、镜像构建、实际模型下载、完整服务栈和大文件性能评测按用户要求暂缓；本阶段 PDF OCR 关闭，按页来源标记在 5D 实现。

### 5B 分批向量化、增量复用与片段上下文（2026-10-13）

- 旧 EMBED 消息改作初始化入口，冻结资料、快照、当前任务、输入摘要和配置版本，每批最多 64 个片段。`V145__source_embedding_batches.sql` 保存批次状态、租约、真实上下文调用累计、派生对象和摘要，快照绑定当前向量任务及执行版本。模型请求在事务外执行，调用前及结果提交时重检资格；新任务或新快照不能被旧租约结果覆盖。
- 每批保存独立二进制结果，最后完成者在快照行锁下判定所有批次完成，投递一次 INDEX。新 manifest 保存身份、版本、连续范围与各批文件摘要；索引逐批读取有限大小的结果，校验完整范围、顺序、输入和有限向量数值。清单或文件损坏时明确失败，不再整份重新向量化。旧 NWE1 和构造器保留读取兼容。
- `V147__source_embedding_cache.sql` 按工作台、向量版本、切片版本、上下文提示词版本和原文 SHA-256 隔离，同时核对完整增强输入、实际经过 trim 与截断后发送的输入摘要、模型和维度。缓存损坏时重新计算，不跨工作台复用。切片时保存真实生效的 `chunker_version`，历史缺失或无效版本明确为未知，不用当前配置推测。
- `V146__source_chunk_context.sql` 保存独立上下文与成功缓存，原文、阅读窗口和引用内容不变。默认启用 `source.chunk.context`，一次批量生成最多 64 项，严格校验完整唯一片段标识、字段、类型、重复 JSON、输出长度；结构错误只纠错重试一次，每批累计最多两次调用。生成不可用或预算耗尽时保存空上下文及真实原因，不声称模型执行成功；租约失效异常直接终止。
- 上下文先独立提交，向量服务失败后可恢复，避免同输入再次生成。成功上下文缓存绑定完整输入、模型服务、提示词和输入输出预算；纠错提示也包含在字符上限内。章节和正文摘录按项有界截短并标记，不丢掉请求项后继续生成其说明。
- QA 索引保存 `context_text` 并通过 `copy_to=content` 参与既有 BM25；原文 `_source.content` 保留。既有工作台索引添加兼容映射，保持别的资料可检索；历史资料重新处理或重建时补齐上下文。同步上传、重建与兼容计算入口也使用 64 条批次；重建记录实际向量版本。提交后同步监听器暂停旧事务资源，确保投影、缓存和就绪状态真正持久化。
- Kafka 手工工厂显式配置 `max.poll.records=1`，稳定部署实例与固定 listener ID 组成独立静态成员。轮询和租约使用同一有限调用上界，默认轮询 1800000 ms、租约 7200 秒；请求预算大于配置值时同步提高有效值，溢出或超过租约上限时拒绝配置。P99、实际缓存复用率与大文件性能暂不评测，默认值不作为测量结果。
- 自动化验证：Backend 全部 297 个测试类、1550 项中 1539 项通过、11 项沿用既有跳过条件，报告无缺失、陈旧结果或失败；Parse Worker 83、Artifact Worker 622、Research Worker 758、Frontend 320 项通过，前端类型与界面契约检查通过。新增回归覆盖 64/65/129 个片段、租约和调用恢复、并发最后一次投递、完整输入缓存隔离、损坏清单、同步事务提交及重建、合法长模型名和 Kafka 成员身份。
- 全量发现独立 Kafka 配置没有应用属性对象，已允许其采用默认有限预算；完整应用仍按配置请求上界计算。真实模型、Kafka/MinIO/Elasticsearch 服务栈及质量、性能评测按用户要求暂缓。

### 5D 按页 OCR 来源与转写队列（2026-10-13）
