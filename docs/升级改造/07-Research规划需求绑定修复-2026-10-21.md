# Research 规划需求绑定修复记录

日期：2026-10-21。承接计划第 20 节的真实运行问题，本轮重点补齐规划链路的代码，未启动新的真实 research。

## 1. 已确认的代码问题

上一轮真实运行只保存了显式需求无法绑定维度这一错误，没有保存被拒绝的完整规划，因此不能断言当时具体触发了哪一种规范化情况。本轮通过确定输入复现并修复以下代码缺陷：

1. 去掉列名中的研究对象前缀并合并同名列后，`user_requirements.dimension` 仍引用旧列名。
2. 列名、对象名按 Unicode 和空格去重后，需求和必查要点仍可能引用被去掉的写法。
3. 最后一次补齐专家必查内容时，只保护已关联专家要点的列，可能替换用户明确需要的列；容量不足时还可能漏报未补齐的要点。
4. 超限修复会裁掉对象或列，存在通过缩小研究范围满足预算的情况；后端也保留同样的裁剪路径。
5. 规划失败反馈只包含概括性错误，第二次调用看不到被拒绝的候选方案，难以修复具体引用。
6. 确认阶段手动修改表格时，重新生成的简报会丢失显式需求定义、数量原文及规划完整性复核状态。

## 2. 代码改动

### 2.1 确定的名称映射

`planning_executor.py` 记录去重、规范化、去除对象前缀时实际发生的名称变化，并同步更新显式需求的维度及对象引用、必查要点的维度引用。只使用已确定的映射，不推测未知名称或同义词；未知维度及被移除的来源类列仍明确报错。

专家补列保留显式需求使用的列。空间足够时新增缺少的列；既不能新增也没有可替换列时返回具体缺项。显式需求模式下允许调整投入等级，但不再靠裁掉对象或列满足上限；没有显式需求的旧模式保留原来的截断兼容行为。

后端在显式需求模式下同样拒绝超出列数、对象数、单元格总数或投入等级的方案，保留原骨架与规划状态，不将超限方案悄悄变成更小的研究任务。

### 2.2 有效的模型修复反馈

维度绑定错误包含具体字段路径、失效列名和当前可用维度。第二次调用同时接收 `previous_output_rejected` 与 `candidate_plan_for_repair`，明确要求保留原问题、对象、数量，并使用最终列名修复引用。

原有结构规划的两次调用上限保留；新版本规划的完整性审计与有限修订仍受原有总预算约束，没有增加无限重试。模型输出无法修复时仍返回 `FALLBACK`，不能标为完整规划。

### 2.3 可归档的失败记录

新增可选的 `planning_diagnostics`：记录结构规划尝试的接受、拒绝或不可用状态、有限长度的校验原因、列名及需求引用编号。它只记录结构规划尝试，不代替模型调用成本统计。

诊断随角色结果保存，后端投影明确允许的字段，写入 `PLAN_DIAGNOSTICS` 记录，并由原计划接口 `/api/v2/workspaces/{workspaceId}/research-runs/{runId}/plan` 返回。查询继续受工作台与 Run 范围约束；旧结果返回空对象。前端补齐可选类型，评测脚本原有计划采集可以归档该字段。

不记录模型原始响应、引文或连接配置；不合规 JSON 日志只保留长度。诊断只用于定位，不参与事实资格或需求完成判断。

### 2.4 手动修改表格时保留明确要求

`ResearchPlanningService.revise` 在新模式下，从已保存的维度和对象标识恢复显式需求，再对修改后的表格重新验证。删除必需列或明确绑定的对象会返回具体错误；适用于全部对象的要求继续保护原对象，并可适用于新增对象。

保存需求定义时补齐已经验证的 `count_expression`，保留数量及其原文。旧数量规划缺少这一原文时要求重新规划，不能猜测或把数量要求丢掉。专家必查要点、原问题分句及完整性复核状态也会保留；未检查或未完成的状态不会因用户改表而升级。

这些改动只使用现有 JSON 字段与追踪表，没有新增数据库迁移，没有修改默认开关或 `.env`。
