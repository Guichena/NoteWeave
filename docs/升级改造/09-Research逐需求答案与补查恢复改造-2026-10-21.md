# Research 逐需求答案与补查恢复改造

日期：2026-10-21。承接计划第 22 节及真实复跑记录 08，落实用户要求完成的六项改造。

## 1. 新旧运行边界

新 Run 的特性快照增加 `requirement_answer_policy_version=1`，通过 `requirement_answer_policy_v1` 协商 Worker 能力。标记随需求契约、规划输入和成文输入冻结；已有 Run 不补写标记，不更新旧判定或历史成绩。原状态版本 2 至 5 的兼容路径继续保留，总开关仍默认关闭。

使用现有 JSON、需求、事实、血缘和补查记录，没有新增数据库迁移，没有修改 `.env`。

## 2. 已实现代码

### 2.1 固定需求完成条件

新增 `ResearchAnswerPolicy`，为每项需求冻结独立的 `answer_contract`，记录验收文本、数量、时间范围、必答属性及来源约束。问题原文继续用于追溯，成文核验只接收当前项的冻结条件，不再携带整段问题引文。规划提示同步约束：不能把用户未询问的安装、性能等专家补充内容加入显式必答项。

显式需求保持必答；确实存在显式定义时，派生项作为补充项单独计数，仍保留全部研究结果、缺项和核验状态。没有显式定义的回退规划继续保留研究项的必答属性。完成检查、报告覆盖、调度和前端展示使用对应计数，评测报告注明与旧规则的区别，不能按比例直接对比完成率。

### 2.2 时间适用性

首次引入、当前状态和标识对应关系分别冻结。PEP、RFC、JEP 等编号和标题对应关系可使用 `TIME_INVARIANT`，不能继承整个混合问题的当前状态要求。当前状态仍要求冻结截止日期、适用版本和生效依据；发布日期、版本元数据、未来阶段说明不能单独证明状态已生效。

来源语义检查同时接收各需求的时间意图，允许保留相关历史发现及稳定标识事实，但只有当前适用的事实才能回答当前状态。原有归档、日期引文、范围、截止日期及版本检查保留。

### 2.3 证据与事实的一对多关联

覆盖判定保留同一证据的全部事实关联，按需求所属对象与列选择，不再被后写入关联覆盖。合格和不合格支持混合时保留合格的部分观察，完整性保持未完成；范围外、未知引用继续拒绝。旧 Run 沿用原关联选择规则。

新模式在裁剪引用后，以及已有部分覆盖时，允许一次独立的剩余事实复核。输入只包含当前冻结验收条件、范围内事实和实际原文；最多六项、24000 字符，必答项优先。复核必须明确选择本项已有引用并判断全部条件是否满足；超时、缺项、重复、越界编号、格式异常或预算不足均保留部分覆盖。后端继续检查事实资格、数量、双路支持和时间范围，模型判断不能越过这些保护。

来源核验保持原有三次预留；总预算至少五次时，从前序抽取额度中额外保留一次复核。低预算场景先完成来源核验，复核只使用剩余额度。新增请求在生成完成回执和运行指标之前执行，实际 Provider 请求计入原任务消耗，没有新增总额度。

### 2.4 逐项答案及报告

新增 Worker `answer_policy.py`，先按冻结需求生成直接答案、事实编号和缺少的条件，再将答案组织为正文。新增内容继续经过独立逐句核验；最终答案记录从已核验语句重建，后端校验答案文本、事实、语句编号、状态和缺项与最终报告回执一致，草稿不能授予完成资格。

报告核验输入补齐冻结来源的 URL、标题及引文，避免只能看到事实编号而无法核对来源。已满足研究条件但表达不足时，先按 `EXPRESSION` 进行一次局部补写，并独立核验和复核，不重新搜索。补写、核验和报告共享原有最多 16 次成文授权上限；任务恢复继续计入之前已授权的调用，不增加无限重试。

### 2.5 明确核验原因与预算

新回执增加 `reason_code`，区分预算不足、模型不可用、超时、连接失败、返回格式错误、模型无法判断、答案不完整和已完成。后端检查原因与状态一致，前端显示对应中文说明。原始错误文本不写入回执。

成文优先为需求覆盖预留调用，先处理必答项，未核验项保留实际原因。评测工具保留策略版本、必答与补充项的独立计数，调用消耗和未知 token 不按零处理。

成文执行器会在零预算时不创建模型客户端，诊断优先记录 `BUDGET_EXHAUSTED`；正预算下确实没有客户端时记录 `MODEL_UNAVAILABLE`，避免把额度耗尽误报为配置缺失。

最终真实运行还暴露 SDK 连接异常被兼容客户端转为空返回、上层误报通用 Provider 错误的问题。客户端现在在实际调用记录中保留受限原因码，答案与报告核验穿过计量包装读取该码，区分 `PROVIDER_CONNECTION_ERROR`、`PROVIDER_TIMEOUT` 与成功传输后的 `INVALID_MODEL_OUTPUT`，不读取或保存错误正文。原有空返回及有限重试行为保持兼容。

### 2.6 补查分组与快照恢复

前一轮已修复按研究对象、计划修订号和对象集合版本分组合并补查。本轮进一步处理快照失效：后端在事务内重新锁定运行、任务与目标单元格，确认候选任务的冻结版本确实失效后，标记 `SNAPSHOT_STALE_REPLAN`、结束旧任务并释放占用与剩余额度，由协调器根据当前范围重新规划；不能仅凭 Worker 的失败码结束快照仍有效的任务。

成文补查按需求血缘累计次数，计划修订不重置上限；相同血缘及相同缺项不重复创建，仍受每项和全局限额约束。补查不再为非必答的专家补充项触发额外搜索。
