## 0. 一句话

**所有产物先生成同一种中间表示（每条事实陈述都绑定原文句子编号的结构化文档），再由确定性的渲染器转成报告、测验、幻灯片或音频；生成过程是一条固定的五段流水线（取材、规划、写作、核验、渲染），每种产物类型是一个 Skill 包。**

拆开是四条：

- **类型是 Skill**：每种产物是一个 Agent Skills 格式的 Skill 包，SKILL.md 写类型指令，type.yaml 写选项和参数；新增产物不写代码，不画图。
- **出处是结构**：Claim 的 `anchors` 是 Schema 必填字段，可点回原文由数据结构保证；核验只负责判断点回去的句子是否真的支撑这句话。
- **运行是账本**：Java 持有运行状态机和检查点账本，Python Worker 无状态执行，任何时刻崩溃都能从最近的检查点继续。
- **视频即素材**：视频解析通过我们部署的 MCP 服务接入，在取材阶段把字幕、转写和关键帧变成带时间戳的素材，视频产物与文档产物走同一条流水线；新增来源只需部署一个连接器并改配置。

## 1. 功能模型

1. 在工作台里选一种产物一键生成：报告（简报、学习指南、博客、FAQ、时间线、自定义）、测验、闪卡、思维导图、数据表、幻灯片、音频概览、视频概览、信息图。
2. 每次生成可以填一句自然语言要求；各类型另有少量有限选项（长度档位、难度、数量、语言、音频形式），用户只做选择，不写提示词。
3. 可以勾选部分资料作为范围，默认使用工作台全部资料。
4. 产物中每条事实陈述都可点击，跳到原文对应句子：文档高亮句子，PDF 定位到页内区间，音视频定位到时间点。
5. 每个版本附质量标签：抽检支撑率、删除的无出处陈述数、未核验条目，可展开查看具体句子。
6. 再生成（可带新要求）、版本对比、回滚；生成中能看到真实阶段进度，失败后可以从断点继续。
7. 导出 PDF、Markdown、PPTX、音频、视频、PNG；测验和闪卡支持在线练习。
8. 自定义产物类型：选输出形态，写一段类型指令，设默认选项；也可以把某次满意的要求另存为类型。保存后和内置类型一样一键生成。
9. 输入视频链接生成产物：例如粘贴 B 站链接并勾选分 P，生成学习幻灯片（PPTX，嵌入视频原关键帧）、课程讲义 PDF 或知识博客；产物中的陈述可以展开对应的转写原文和时间点。支持哪些视频平台由我们部署的连接器决定。
10. 产物版本可以保存为工作台资料，作为后续生成的素材。

## 2. 核心抽象

5 个核心对象，加 1 个扩展对象。

| 对象 | 一句话定义 | 去掉它会失去什么 |
|---|---|---|
| **ArtifactType** 产物类型 | 一个 Agent Skills 格式的 Skill 包，加载后成为不可变的类型版本：输出形态 kind、类型指令、用户可选项、阶段参数。内置类型和用户自定义类型是同一结构，区别只在归属 | 新增产物重新变成写代码、配图；自定义产物没有落点 |
| **Run** 生成运行 | 一次生成的冻结输入（类型版本、资料快照、要求、模型与提示词版本）加上状态机和阶段检查点 | 长任务无法恢复；结果无法追溯到确切输入；重复点击无法去重 |
| **EvidencePack** 素材包 | 本次运行冻结的原文片段集合，片段切成带编号的句子，并记录每句到原文的位置映射 | 引用没有封闭集合可校验，编造的引用无法被确定性发现；结果不可复现 |
| **Claim** 带出处的陈述 | 中间表示的最小文本单元：`text` + `anchors`（句子编号列表）+ `role`（事实或非事实） | 逐句出处失去数据载体；核验、指标、前端高亮没有统一单位 |
| **ArtifactVersion** 产物版本 | 通过核验的中间表示 + 素材包 + 质量报告 + 渲染文件，提交后不可变 | 再生成、对比、回滚、导出没有稳定对象；内容和文件无法分开处理 |
| **Connector** 解析连接器（扩展） | 由我们部署的一个 MCP 解析服务加一组链接规则，登记在 `connectors.yaml`，取材阶段按统一约定把视频等外部链接解析成素材 | 每接一个平台都要改流水线，平台差异会渗进 Java 和 Worker；解析调用无法统一限流、缓存和做契约检查 |

阶段（Stage）是代码里的一个接口，有 5 个实现，不对用户暴露，不算业务抽象。

### 2.1 中间表示的七种形态

kind 是中间表示 Schema 的分类。Schema 只有 7 份，按 kind 写，不再按类型各写一份。

| kind | 结构 | 覆盖的产物 |
|---|---|---|
| `DOC` | 章节 → 段落 / 列表 / 表格 → Claim | 简报、学习指南、博客、FAQ、时间线、自定义报告、Wiki 页、简历亮点、课程讲义 |
| `QUIZ` | 题目：题干、选项、正确项、解析 Claim、难度、知识点 | 测验 |
| `CARDS` | 卡片：正面、背面 Claim | 闪卡 |
| `TREE` | 节点：标签、Claim、子节点 | 思维导图 |
| `TABLE` | 列定义 + 行 → 单元格 Claim | 数据表 |
| `DECK` | 页：标题、要点 Claim、讲稿 Claim、版式提示 | 幻灯片、信息图（单页）、视频概览的画面 |
| `SCRIPT` | 段：说话人、Claim | 音频概览、视频概览的旁白 |

Claim 的 `role` 分 `FACT` 和 `NON_FACTUAL`。标题、过渡语、提问句、测验干扰项属于非事实文本，不要求出处。核验阶段限制非事实文本的比例，并随机抽查被标为非事实的句子，防止模型把事实标成非事实来逃避引用。

### 2.2 刻意删掉的抽象

| 现有抽象 | 处理 | 理由 |
|---|---|---|
| 技能图 Graph / Node / Edge | 删除 | 执行体是线性循环，类型之间拓扑没有差异（第 11 节问题 1、2） |
| Capability / Provider / Binding 三层 | 删除 | 14 个能力中 11 个只有一个提供方；剩下的提供方选择属于部署配置（问题 5） |
| Skill / Action / PromptRecipe / StyleProfile 分开注册 | 合并为一个 Skill 包 | 四者基本一一对应，分开注册只带来跨对象一致性校验代码；保留 Skill 这个名字，改用 Agent Skills 开放格式 |
| 意图编译 ExecutionSpec | 删除 | 把要求编译成 5 个字段再拼回提示词，会丢信息并多一次调用。要求原文直接进入提示词；只有影响取材的聚焦范围在取材阶段解析 |
| 能力审批队列、Provider 等待队列 | 删除 | 连接器由我们配置，启动时做契约检查；生成中不等待人工审批 |
| 用户自定义 MCP 注册（Worker 进程内字典和 `/debug/*` 接口） | 删除 | 改为我们维护的 `connectors.yaml`；用户自行接入暂缓（第 10 节） |
| Candidate 回执表 | 改为版本表上 `run_id` 的唯一约束 | 一次运行最多产出一个版本，唯一约束即可保证幂等 |
| 视频冻结入口、冻结知识计划、分 P 选择表 | 删除 | 视频在取材阶段解析为素材，规划和写作与文档类产物相同；分 P 由连接器预览工具声明的选项表达 |

## 3. 架构分层

```
┌──────────────────────── 交互层：前端 ────────────────────────┐
│ 类型面板 · 要求输入 · 运行进度(SSE) · 按 kind 渲染中间表示 · 锚点跳转原文 │
└──────────────────────────────┬──────────────────────────────┘
                     REST / SSE│
┌──────────────────────── 控制层：Java Host ───────────────────┐
│ ArtifactApi   TypeRegistry   RunLedger(状态机·检查点·租约)      │
│ VersionStore  FileStore      ConnectorRegistry(链接匹配)       │
│ ScopedRetrieval(复用检索模块)  Quota                            │
└───────┬──────────────────────────────────────▲──────────────┘
 outbox→Kafka run.dispatch          内部 API（带 lease_epoch）
┌───────▼──────────────── 执行层：Python Worker（无状态）───────┐
│ PipelineRunner: Gather → Plan → Draft → Check →(提交)→ Render  │
│ LlmClient  PromptStore  Checker  ToolGateway(MCP 客户端)  Renderers │
└────────────────────────────────────────────────────────────┘
 存储层：MySQL(账本) · MinIO(检查点与文件) · ES(片段检索) · Kafka(派发)
```

视频解析在取材阶段经 ToolGateway 调用我们部署的 MCP 服务，见第 6.3 节。

### 3.1 各层职责

| 层 | 职责 | 不做什么 |
|---|---|---|
| 交互层 | 类型面板、要求输入、进度展示、按 kind 渲染中间表示、锚点跳转原文 | 不读取运行内部状态和提示词 |
| 控制层 Java | 鉴权与工作台归属、类型注册表、Run 状态机、检查点账本、租约与围栏、outbox 派发、版本与文件、连接器配置与链接匹配、额度 | 不调用模型，不理解内容语义 |
| 执行层 Python | 五段流水线、模型调用、提示词渲染、Schema 校验、引用核验、MCP 客户端、渲染器 | 不直连数据库，不保存长期状态 |
| 存储层 | 账本、检查点和文件、片段检索、派发 | — |

### 3.2 Java 与 Python 怎么分

原则：**需要事务、归属和审计的状态归 Java；需要模型和内容处理生态的计算归 Python。**

- Java 不能只做回调接收器：运行状态、版本、额度都要求事务和权限检查，鉴权、工作台 ACL、outbox 已经在 Java；在 Python 再建一套，就会有两份真相。
- Python 不能只做无状态函数服务：MCP SDK、Pydantic、python-pptx、TTS、ffmpeg 都在 Python 生态；分段并发写作和调用预算也适合在一个进程内完成。
- Worker 在一个租约内跑完整条流水线，Java 不按阶段逐个派发。逐阶段派发每次运行要多 4 次 Kafka 往返，分段并发还要跨进程协调；它换来的更细恢复粒度，检查点已经提供了。代价是 Worker 崩溃时正在执行的那一段要重做，最多损失一个分段的模型调用。

### 3.3 为什么是这 5 个阶段

每个阶段的检查点和失败语义都不同，合并任意两个都会丢掉一种能力：

| 阶段 | 性质 | 合并会丢什么 |
|---|---|---|
| 取材 Gather | 外部 IO 为主（检索、工具），结果冻结为素材包 | 并入写作后，重试写作会重新检索，结果不可复现 |
| 规划 Plan | 一次全局模型调用 | 并入写作后无法分段并发，也无法控制覆盖度 |
| 写作 Draft | 按分段并发的模型调用 | — |
| 核验 Check | 确定性校验为主，加抽样判定 | 并入写作后，改核验规则必须重新生成 |
| 渲染 Render | 确定性转换或媒体合成，在版本提交之后 | 并入提交后，TTS 失败会让已经可读的内容无法交付 |

### 3.4 层间边界（硬规则）

1. Worker 只通过内部 API 读冻结输入、写检查点、提交版本；每次写入都带 `lease_epoch`，过期租约的写入一律拒绝。
2. Java 对 Worker 提交的中间表示只做结构校验：Schema 版本、大小上限、所有 `anchors` 都属于本次素材包。
3. 外部平台凭据只注入对应的连接器容器，Java 和 Worker 都不持有；日志脱敏。
4. 前端读取版本的中间表示和素材包投影（句子编号 → 资料、位置、原文），读不到提示词和模型原始输出。

## 4. 关键流程

```
用户点击学习指南，要求：讲得更基础些
│
├─ [Java] POST /api/v2/workspaces/{ws}/artifact-runs   Header: Idempotency-Key
│    校验工作台权限 → 解析类型的当前版本 → 冻结资料快照、工具绑定、模型配置、提示词包哈希
│    → 计算 input_hash → 同一事务写 artifact_run(QUEUED) 和 outbox(run.dispatch)
│
├─ [Kafka] run.dispatch
│
├─ [Worker] POST /internal/artifact-runs/{id}/lease → 拿到 lease_epoch 和冻结输入
│    读取检查点清单，已完成的阶段和分段直接跳过；之后每 20 秒心跳续约（租期 60 秒）
│
├─ ① 取材 GATHER ............................................ 检查点 gather
│    范围解析：要求 + 资料目录（标题树）→ 聚焦范围和 3–6 条查询（1 次小模型调用）
│    检索：在冻结快照内混合检索；COVERAGE 类型按资料结构分层抽样，保证各章都有素材
│    工具（可选）：有界工具循环，最多 3 轮、6 次调用，结果规整为片段
│    规整：去重 → 切句编号 P{n}.s{m} → 记录原文位置 → 按 token 预算截断 → 计算 pack_hash
│
├─ ② 规划 PLAN .............................................. 检查点 plan
│    模型输出骨架：分段（标题、要点、分配的句子编号、目标长度）+ 术语表
│    确定性校验：编号属于素材包、分段数在类型范围内、分段间要点不重复
│    短产物（思维导图、少量闪卡）使用 TRIVIAL 规划：整个素材包作为一个分段，不调用模型
│
├─ ③ 写作 DRAFT ............................................. 检查点 draft/{part_id}
│    各分段并发（每运行上限 4）：kind 写作模板 + 类型指令 + 要求 + 分段骨架 + 分段素材 + 术语表
│    → 输出该 kind 的中间表示片段，每条 FACT Claim 带 anchors
│    Schema 不合规时附校验错误重试 1 次
│
├─ ④ 核验 CHECK ............................................. 检查点 check
│    L1 格式：kind Schema + 类型规则（如测验只有一个正确项）
│    L2 引用闭合：FACT 必有 anchor；anchor 属于素材包；数字出现在被引句中
│    L3 语义支撑：按风险抽样，批量判定 SUPPORTED / PARTIAL / UNSUPPORTED / CONTRADICTED
│    修复：失败 Claim 按分段合并，局部重写 1 轮，只重检被改动的 Claim
│    仍失败：删除该 Claim 并记入质量报告；删除比例超过上限则整次运行失败
│
├─ [Java] POST /internal/artifact-runs/{id}/version
│    校验 epoch 和结构 → 写 artifact_version（run_id 唯一）与 artifact_version_source
│    → Run 置为 SUCCEEDED → SSE 通知前端：内容已可阅读
│
└─ ⑤ 渲染 RENDER（版本提交后异步执行）......................... 每个文件一行 artifact_file
     DOC → PDF；DECK → PPTX；SCRIPT → TTS 音频；DECK + SCRIPT → 视频
     失败只影响文件状态，可以单独重试，不重新生成内容
```

前端点击引用的路径：Claim 的 `P3.s4` → 版本素材包投影 → `source_snapshot_id` + 字符区间（文档）、页码 + 区间（PDF）或时间区间（音视频）→ 打开资料阅读器并高亮。

## 5. 数据模型

### 5.1 表

**artifact_type**：类型定义，内置与自定义共用

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `owner_user_id` | 为空表示系统内置；自定义类型归属用户，可在该用户的任意工作台使用（类型只含指令，不含资料） |
| `type_key`、`version` | 同一归属下 `(type_key, version)` 唯一；修改即生成新版本，旧版本供历史运行追溯 |
| `kind` | `DOC / QUIZ / CARDS / TREE / TABLE / DECK / SCRIPT` |
| `display_name`、`description` | 展示用 |
| `instruction` | 类型指令，填入 kind 模板的类型槽位；自定义类型上限 2000 字 |
| `options_json` | 用户可选项及默认值，如长度、难度、数量、音频形式 |
| `pipeline_json` | 阶段参数：`gather_mode`（FOCUSED / COVERAGE）、`plan_mode`（LLM / TRIVIAL）、分段数上下限、素材 token 预算、渲染器列表；自定义类型继承 kind 默认值，用户不可改 |
| `rules_json` | 类型规则，如必需章节标题 |
| `tool_policy` | `NONE / OPTIONAL / REQUIRED` |
| `status`、`content_hash`、`created_at` | — |

**artifact**：工作台里用户看到的一项产物，聚合多个版本

| 字段 | 说明 |
|---|---|
| `id`、`workspace_id`、`type_id`、`title` | — |
| `current_version_no` | 当前展示版本，回滚只改这个字段 |
| `status`、`created_by`、`created_at` | — |

**artifact_run**：一次生成，冻结输入 + 状态机 + 租约

| 字段 | 说明 |
|---|---|
| `id`、`artifact_id`、`workspace_id`、`user_id` | — |
| `type_id`、`type_version` | 冻结的类型版本 |
| `requirement`、`options_json` | 冻结的用户要求与选项（含视频链接与所选分 P） |
| `source_scope_json` | 冻结的资料快照 ID 列表 |
| `tool_binding_json` | 冻结的连接器 key、解析器版本与清单指纹 |
| `model_profile_json`、`prompt_bundle_hash` | 冻结的模型配置与提示词包版本 |
| `input_hash` | 以上冻结字段的哈希 |
| `idempotency_key` | `(workspace_id, idempotency_key)` 唯一 |
| `parent_version_id` | 再生成时指向来源版本 |
| `status`、`current_stage` | `QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED`；`current_stage` 记录所在阶段 |
| `attempt`、`lease_epoch`、`lease_owner`、`lease_expires_at` | 租约与围栏 |
| `budget_json`、`usage_json` | 预算上限；按阶段汇总的调用数、token、耗时、真实工具调用数 |
| `error_class`、`error_code`、`error_message` | 失败分类（第 8 节） |
| `created_at`、`started_at`、`finished_at` | — |

**artifact_run_checkpoint**：阶段产出，续跑和重放的依据

| 字段 | 说明 |
|---|---|
| `run_id`、`stage`、`part_key` | 唯一键；`part_key` 是写作分段 ID，其他阶段为空串 |
| `lease_epoch` | 写入时的租约代数 |
| `payload_ref`、`payload_hash`、`size_bytes` | MinIO 对象，包含该阶段输出及完整提示词与原始模型输出（保留 14 天） |
| `llm_calls`、`tokens_in`、`tokens_out`、`duration_ms` | 阶段级统计 |

**artifact_version**：不可变的产物版本

| 字段 | 说明 |
|---|---|
| `id`、`artifact_id`、`version_no` | — |
| `run_id` | 唯一，保证一次运行最多一个版本 |
| `ir_kind`、`ir_schema_version`、`ir_ref`、`ir_hash` | 中间表示 |
| `evidence_pack_ref`、`evidence_pack_hash` | 素材包，前端锚点跳转使用 |
| `quality_json` | 质量报告（第 7.3 节） |
| `content_status` | `READY / REDACTED`（资料撤销后屏蔽正文） |
| `created_at` | — |

**artifact_version_source**：`(version_id, source_id, source_snapshot_id)`。资料被删除或撤销时，用它找到受影响的版本；也用于展示引用了哪些资料。

**artifact_file**：`version_id`、`role`（PDF / PPTX / AUDIO / VIDEO / PNG）、`renderer`、`renderer_version`、`object_key`、`sha256`、`status`（PENDING / READY / FAILED）、`error_code`、`attempt`；`(version_id, role, renderer_version)` 唯一。

**tool_call_log**：`call_id`、`run_id`、`call_seq`、`connector_key`、`tool_name`、`args_hash`、`status`、`latency_ms`、`result_bytes`、`error_class`、`result_ref`。记录每次 MCP 调用，用于审计、熔断统计和前端展示真实调用数。

派发复用现有 `task_outbox`。

连接器登记在 `connectors.yaml`（第 6.3.4 节），由我们维护，不建表；视频解析缓存放在 MinIO，以连接器 key、视频 ID、分 P 和解析器版本的哈希作为对象键，也不建表。

### 5.2 中间表示与素材包

素材包（检查点 gather 的主体，也随版本保存）：

DOC 中间表示：

## 6. 扩展点

### 6.1 产物类型即 Skill 包

产物类型按 Agent Skills 开放规范封装，一个类型就是一个目录：

```
skills/study-guide/
├── SKILL.md                 # 必需：名称、描述、kind；正文是类型指令
├── assets/type.yaml         # 必需：用户可选项、阶段参数、类型规则、渲染器、可用连接器
└── references/examples.md   # 可选：优秀样例，写作阶段按需加载
skills/video-learning-deck/
├── SKILL.md
├── assets/type.yaml
└── assets/template.pptx     # 可选：PPTX 母版，渲染阶段使用
```

`SKILL.md`：

```markdown
---
name: study-guide
description: 把工作台资料整理成由浅入深的学习指南，包含学习目标、核心概念和复习路径。适合第一次系统学习一组资料。
metadata:
  kind: DOC
  version: "3"
---

面向第一次接触这些资料的读者，先给出学习目标，再按由浅入深的顺序讲核心概念，
最后给出复习路径。每个概念说明它解决什么问题。
```

`assets/type.yaml`：

```yaml
options:
  length: {choices: [SHORT, STANDARD, LONG], default: STANDARD}
  language: {choices: [zh-CN, en], default: zh-CN}
pipeline:
  gather_mode: COVERAGE
  plan_mode: LLM
  parts: {min: 3, max: 8}
  pack_token_budget: 40000
rules:
  required_headings: [学习目标, 核心概念, 复习路径]
renderers: [MARKDOWN, PDF]
connectors: []               # 视频类 Skill 填 [bilibili_video]
```

字段遵循规范：`name` 用小写字母和连字符，与目录名一致；`description` 不超过 1024 字；扩展信息放在 `metadata`。规范要求 `metadata` 的值是字符串，所以结构化配置单独放进 `assets/type.yaml`。

**按需加载（规范中的渐进式披露）**：

| 层级 | 内容 | 什么时候加载 |
|---|---|---|
| 元数据 | `name`、`description` | 类型面板展示；按资料推荐产物类型时，只把各 Skill 的元数据交给模型（NotebookLM 按资料推荐报告格式就是这种用法） |
| 正文 | 类型指令 | 生成时填入规划和写作模板的类型槽位 |
| 资源 | 样例、PPTX 母版 | 样例只在写作阶段加载，母版只在渲染阶段使用 |

**Skill 能改什么、不能改什么**：Skill 只描述产物写成什么样（指令、选项、样例、模板）；流程、出处规则和核验由流水线保证，Skill 改变不了。Skill 包里的 `scripts/` 目录不执行。

**为什么用 Skill 格式，不自定义一种格式**：

1. 这是开放规范，Claude Code、Codex 等工具都能读取，同一个 SKILL.md 可以拿到这些工具里直接复用；
2. 元数据、正文、资源分层加载是现成的设计，正好对应类型面板、生成、渲染三个时机，不必按类型把全部内容塞进上下文；
3. 自定义产物有了现成的格式，用户写一个 SKILL.md 即可。

代价：`metadata` 只能放字符串，结构化配置要多一个文件。

启动时 Java 扫描 `skills/` 目录，按内容哈希同步进 `artifact_type`，内容变化即新增版本。现有 9 个只差提示词的产物，各自就是一个只有 `SKILL.md` 和 `type.yaml` 的 Skill 包。

### 6.2 自定义产物（最小可用）

自定义产物保存为用户自己的 Skill 包，格式与内置类型相同。用户可以在表单里填写，也可以直接上传一个 SKILL.md，系统只读取名称、描述和正文，kind 和选项在表单里选择。用户可填写的内容只有：

| 项 | 说明 |
|---|---|
| 名称 | — |
| 输出形态 | 从 kind 中选一种（V2 开放 DOC、QUIZ、CARDS、TREE、TABLE、DECK） |
| 类型指令 | 一段自然语言，≤ 2000 字 |
| 默认选项 | 该 kind 的选项默认值 |
| 必需章节（可选，仅 DOC） | 标题列表，例如周报固定的本周进展、风险、下周计划 |
| 取材工具（V3） | 不使用 / 使用我们配置的取材工具 |

执行方式：自定义类型和内置类型走同一条流水线，类型指令填入 kind 模板的类型槽位。槽位前后有固定分隔，指令按纯文本插入（模板语法字符转义），出处规则写在指令槽位之后的系统部分，并且最终由 L2 确定性检查保证，指令里写不引用出处也不会生效。

另存为类型：某次生成的要求让用户满意时，可以一键另存为自定义类型，指令预填为该次要求。NotebookLM 的推荐报告允许查看对应提示词，这是同一个思路。

### 6.3 视频解析与 MCP（最小可用）

**定位**：与现有能力一致，用户输入视频链接，直接得到学习幻灯片、课程讲义 PDF、知识博客这类产物。视频解析（字幕、转写、关键帧、帧描述）由我们部署的 MCP 服务提供，在取材阶段调用，解析结果作为带时间戳的片段进入素材包，之后的规划、写作、核验与文档类产物完全相同。用户不登记自己的 MCP 服务，也不做 OAuth（第 10 节）。

#### 6.3.1 用户视角

1. 选择产物类型（视频学习幻灯片、课程讲义、知识博客等），粘贴 B 站链接，可以再填一句要求。
2. 系统调用预览工具，显示标题、时长和分 P 列表，用户勾选分 P。
3. 开始生成，进度依次显示解析视频、规划、写作、核验、渲染。
4. 得到 PPTX（嵌入视频原关键帧）或 PDF；产物中的事实陈述可以展开对应的转写原文和时间点。

#### 6.3.2 在流水线中的位置

```
取材 Gather
  ├ 工作台资料检索（已有）
  └ 请求带视频链接 → 按 connectors.yaml 匹配连接器
       → 查解析缓存（连接器 key + 视频 ID + 分 P + 解析器版本）
       → 未命中：经 ToolGateway 调用 fetch_video_source（MCP，Streamable HTTP），结果写入缓存
       → 转写分段切句编号，locator 记录分 P 与时间区间；关键帧作为图片片段，帧描述作为句子
  → 冻结素材包（视频片段与资料片段并列，引用方式相同）
规划 → 写作 → 核验：与文档类产物完全相同
渲染：DECK → PPTX，关键帧按页内要点引用的片段放入对应页；DOC → PDF
```

关键点是视频不再是一条特殊分支：它只是取材阶段多了一个素材来源。现有的冻结视频入口、视频素材表、冻结知识计划和分 P 选择表都可以删除（第 11 节问题 3）。

**解析缓存**：转写和关键帧分析耗时长，结果按连接器 key、视频 ID、分 P 和解析器版本存进 MinIO。对同一视频再生成或换一种产物类型时直接复用，解析器升级后版本号变化，自动重新解析。取材阶段完成后素材包写入检查点，Worker 中途崩溃续跑时也不会重新解析。

#### 6.3.3 连接器约定 `noteweave.source.v1`

每个连接器提供两个工具：

- **预览工具**：输入 `{"url": "..."}`，输出标题、时长、缩略图和 `options_schema`。`options_schema` 只允许扁平对象和字符串、数字、布尔、枚举字段（与 MCP elicitation 使用的受限 Schema 子集一致），前端据此渲染选择表单。B 站的分 P 就是一个多选枚举字段，系统不需要为分 P 专门写界面和建表。
- **解析工具**：输入 `{"url": "...", "options": {...}}`，`options` 来自预览阶段的选择；输出放在 `structuredContent` 中（MCP 2025-06-18 起支持结构化工具输出）。

视频返回带时间轴的分段和关键帧：

```json
{
  "schema": "noteweave.source.v1",
  "title": "Redis 缓存设计实战",
  "canonical_url": "https://www.bilibili.com/video/BV1xx411c7XX",
  "content": {
    "kind": "TIMED_TEXT",
    "media": {"duration_ms": 3612000, "video_id": "BV1xx411c7XX"},
    "segments": [
      {"part": 1, "start_ms": 12000, "end_ms": 18500, "text": "今天先讲缓存穿透的三种处理方式。"}
    ],
    "images": [
      {"part": 1, "at_ms": 60000, "resource": {"type": "resource_link", "uri": "…"},
       "caption": "幻灯片：缓存架构总览", "ocr_text": "…"}
    ],
    "transcript_origin": "SUBTITLE"
  },
  "metadata": {"author": "…", "language": "zh-CN"}
}
```

以后接文档类平台（如飞书）时返回 `{"kind": "DOCUMENT", "mime_type": "text/markdown", "text": "..."}`，走同一套取材逻辑。`transcript_origin` 区分官方字幕和 ASR 转写，产物中可以提示转写可能有误。

**为什么分预览和解析两步，而不用 MCP 的 elicitation**：elicitation 是服务端在一次调用过程中向用户提问，调用要一直保持打开，直到用户回答；解析在后台生成任务里执行，用户可能已经离开。预览发生在提交生成之前，用户一定在场，同步调用即可，超时 10 秒。

#### 6.3.4 配置：connectors.yaml

```yaml
connectors:
  - key: bilibili_video
    endpoint: http://bilibili-mcp:8080/mcp
    url_rules: [bilibili.com/video/, b23.tv/]
    preview_tool: get_video_info
    parse_tool: fetch_video_source
    parser_version: 3
    limits: {timeout_minutes: 30, max_text_mb: 5}
  - key: lark_doc
    endpoint: http://lark-adapter:8080/mcp
    url_rules: [feishu.cn/docx/, feishu.cn/wiki/]
    parse_tool: fetch_document
    enabled: false              # 配好飞书应用凭据后再打开
```

- 链接规则写成域名加路径前缀，不用正则，避免正则回溯攻击和难以审查的规则；按配置顺序匹配，取第一个。
- Java 用链接规则校验生成请求中的链接并调用预览，Worker 用地址发起解析。
- 外部平台凭据（例如飞书的 App ID 和 App Secret）只注入对应的适配服务容器，Java 和 Worker 都不持有。
- Worker 启动时对每个连接器执行一次 `tools/list`，确认工具存在、Schema 符合约定，不符合则停用并告警。
- 新增一种来源：写一个适配服务，在 Compose 里加一个容器，在配置里加一段。流水线、Java 和前端都不用改。

#### 6.3.5 为什么用 MCP 和独立的适配服务

**每个平台一个适配服务，不在配置里写参数映射**：第三方工具的参数各不相同，例如飞书文档工具要的是文档 ID，不接收链接。用配置描述链接中哪一段填到哪个参数，等于造一门小语言，出错也难排查。适配服务通常只有几十到几百行代码，有自己的测试，平台接口变化时也只改它。

**用 MCP，不用普通 HTTP 接口**：

1. 工具自带输入输出 Schema，预览选项表单和启动时的契约检查不需要为每个来源单独写代码。
2. 外部平台已经有官方 MCP 服务（例如飞书的 `@larksuiteoapi/lark-mcp`），适配服务可以直接作为它的客户端。
3. 同一个解析服务也能直接给 Claude、Cursor 等 MCP 客户端使用。
4. 视频解析依赖重（yt-dlp、ffmpeg、ASR 模型），独立容器部署，不污染 Worker 镜像，可以单独扩容。

代价是多了一层协议和每个连接器一个容器的运维成本。

#### 6.3.6 解析失败处置

用户明确给了视频链接，视频就是必需素材，解析失败时运行失败，不降级为只用工作台资料。

| 情况 | 处置 |
|---|---|
| 链接不匹配任何连接器 | 提交时直接提示暂不支持，不创建运行 |
| 连接器停用或不可达 | 提交时提示该来源暂不可用；运行中遇到则失败为 CONNECTOR_UNAVAILABLE，可以稍后重试 |
| 超时、5xx、连接中断 | 指数退避重试最多 2 次（解析只读，重试安全）；长时间解析靠进度通知延长空闲超时，总时长上限 30 分钟 |
| 工具返回 `isError` | 不重试，展示适配服务给出的错误信息（脱敏、截断），例如视频不存在、需要登录 |
| 平台凭据失效 | 适配服务返回约定错误码 CREDENTIAL_INVALID；运行失败，向运维告警 |
| 输出不符合约定 | 失败并告警。适配服务是我们自己写的，不符合约定属于程序缺陷，不做降级 |
| 超出大小上限 | 失败并说明上限；不静默截断 |

#### 6.3.7 内置 B 站服务的改造

现有 `bilibili_render_pdf_server.py` 有 8 个工具，通过 stdio 在 Artifact Worker 本机启动，只服务于产物的视频冻结分支。改造后：

- 部署为 Compose 里独立的 `bilibili-mcp` 容器，走 Streamable HTTP。
- 字幕获取、本地转写、关键帧截取、帧分析合并为解析工具 `fetch_video_source`，另加预览工具 `get_video_info`，按约定返回 TIMED_TEXT。
- `render_latex_pdf` 删除，PDF 由产物渲染器负责；现有的原帧 PPTX 渲染代码迁到 DECK 渲染器复用。

它也是 `noteweave.source.v1` 的参考实现，以后的连接器照着它写。

#### 6.3.8 外部平台示例：飞书文档（以后接入）

- 适配服务 `lark-adapter` 内部以 stdio 启动飞书官方的 `@larksuiteoapi/lark-mcp`（应用身份，App ID 加 App Secret），或直接调用飞书 OpenAPI 或 CLI；对外只暴露 `fetch_document(url)`，返回 DOCUMENT。
- 这里使用 stdio 没有问题：命令由我们固定在镜像里，与服务端执行用户提交的命令是两回事；stdio 只出现在适配服务容器内部。
- 不做 OAuth 的代价：只能以应用身份读取，用户需要先在飞书里把文档授权给这个应用。

由模型自主选择工具的取材循环（例如查内部知识库、工单系统）暂不实现，放在第 9 节 V3。

#### 6.3.9 安全边界

连接器都由我们部署，用户自带服务带来的风险（执行用户命令、用户凭据保管、工具描述被篡改）都不存在。仍需处理的是外部内容和用户输入的链接：

| 风险 | 措施 |
|---|---|
| 用户输入的链接指向内网 | 链接规则只匹配已配置的平台域名，其余链接直接拒绝 |
| 连接器访问内部服务 | 连接器容器放在单独的网络，只能访问外网和自身依赖，访问不到 MySQL、MinIO、Kafka 等内部服务 |
| 视频字幕或文档中的提示注入 | 解析结果只进入素材包的数据区，不进入指令区；生成内容仍须引用素材句子并经过核验 |
| 外部平台凭据泄露 | 只注入对应的适配服务容器，日志脱敏 |
| 资源耗尽 | 单次解析总时长 30 分钟、文本 5 MB、分段 2 万条、关键帧最多 200 张且单张 2 MB；连接器级熔断（连续 3 次失败后打开 5 分钟） |

### 6.4 新增 kind（工程师）

需要同时提供：kind Schema、规划与写作模板、L1 规则、渲染器、前端渲染组件。预期很少发生：7 种 kind 已覆盖 NotebookLM 的全部产物。

## 7. 质量与指标

### 7.1 三层核验

| 层 | 内容 | 方法 | 是否阻断 |
|---|---|---|---|
| L1 格式 | kind Schema；类型规则（必需章节、测验唯一正确项、卡片正面不含答案等） | 确定性 | 是，渲染依赖结构 |
| L2 引用闭合 | FACT 至少一个 anchor；anchor 属于素材包；Claim 中的数字、日期、百分比出现在被引句中（单位归一后比较） | 确定性 | 是，未通过的 Claim 进入修复，修复后仍失败则删除 |
| L3 语义支撑 | 被引句是否支撑该陈述 | 小模型批量判定 | 不阻断交付，失败 Claim 修复或删除，结果写入质量报告 |

可点回原文由 L2 保证；点回去是否真的支撑由 L3 衡量。两者分开，判定模型不可用时仍能交付可追溯的产物，同时如实标为未核验。这与项目约定一致：判定类调用不可用时记 `NOT_RUN`，不判为通过。

### 7.2 风险抽样

必判（全部进入 L3）：

- 含数字、日期、百分比、金额；
- 含比较、因果、否定、范围限定（比、导致、因此、不、并非、仅、所有等）；
- Claim 与被引句的词项覆盖率低于阈值 τ（初值 0.5，评测后校准）；
- anchor 超出规划阶段分配给该分段的范围；
- 修复后的 Claim。

随机抽样：其余 FACT Claim 的 10%，NON_FACTUAL 的 10%。随机样本用于在线估计未被抽中句子的支撑率，即风险规则的漏判情况。

判定输出只有 `claim_id`、`label`、`reason_code`（如 NUMBER_MISMATCH、SCOPE_MISMATCH、NOT_IN_SOURCE），不复制原文；按分段批量，每次最多 20 条。判定模型可以单独配置为较小的模型。

修复与删除的具体步骤见 7.2.1。

#### 7.2.1 局部修复

修复以 Claim 为单位，不重写整段或整章。

**哪些 Claim 会进入修复**：

- L2 确定性失败：FACT 没有 anchor、anchor 编号不在素材包里、Claim 中的数字没有出现在被引句中；
- L3 判定失败：UNSUPPORTED 或 CONTRADICTED。

PARTIAL 不修复，保留并在前端标为部分支撑；判定未执行的标为未核验，也不修复。

**步骤**：

1. 按分段分组：同一分段的失败 Claim 合并成一次模型调用，没有失败的分段不调用。
2. 修复输入：该分段当前的中间表示（只读上下文，让改写后的句子能和前后文衔接）；失败 Claim 列表，包括 ID、原文和原因代码（如 NUMBER_MISMATCH、ANCHOR_NOT_FOUND、NOT_IN_SOURCE）；它们原来引用的句子；该分段分配到的全部素材句子（带编号）。
3. 修复输出：每个失败 Claim 二选一，返回同 ID 的新 Claim（新文本加新 anchors），或者返回 DELETE，表示素材里找不到能支撑的说法。
4. 确定性合并：代码按 ID 只替换列表里的 Claim；模型返回了列表之外的 ID 一律忽略，其余 Claim 由代码原样保留，不依赖模型自觉不改。
5. 只重检被改动的 Claim：L1 检查分段结构，L2 检查新 anchors 和数字，L3 对每条改写后的 Claim 必判。
6. 仍失败的 Claim 删除；块为空则删除该块；类型规则要求的章节变空则运行失败；被删除的 FACT 占比超过 15%（初值）时运行失败。

只修 1 轮。第二轮的增量收益需要实测（附录 C）；如果修复前后通过率接近，可以取消修复，失败直接删除（7.5）。

**例子**：

| Claim | 失败原因 | 修复结果 |
|---|---|---|
| 引入二级缓存后命中率提升到 95%（引用 P3.s4，原文为 91%） | L2 数字不一致，L3 判为 CONTRADICTED | 改为提升到 91%，引用不变，重检通过 |
| 该方案已在生产环境稳定运行半年（引用 P5.s2，原文只说灰度上线） | L3 判为 UNSUPPORTED | 素材中找不到依据，返回 DELETE，该句删除并记入质量报告 |
| 布隆过滤器可以拦截不存在的 key（引用 P9.s1，素材包里没有这个编号） | L2 编号不存在 | 改为引用素材中确有此意的 P6.s3，重检通过 |

**为什么按 Claim 修，不按章节重写**：

- 已通过的句子保持不变，不会因为重写引入新的错误；
- 重检成本和失败数量成正比，章节重写要把整章重新判定一遍；
- 合并由代码按 ID 完成，模型改不到列表之外的内容。

**代价**：改写或删除之后，前后句的衔接可能变生硬，例如删掉的句子后面紧跟着一句以因此开头的话。修复时把整个分段作为只读上下文传入，可以缓解一部分，剩下的衔接问题本期接受。

与现有实现的区别：现有 4D 阶段的修复以章节为单位重写，最多 2 轮，每轮都重新做引用分配、一致性检查和全部陈述判定，这是耗时长的原因之一。

### 7.4 离线评测

- 数据集：12 个工作台（论文 PDF、网页文章、课程视频转写、会议录音转写、中英混合、长书章节）× V1 的类型 × 2 种要求（无特殊要求、聚焦某部分），约 150 次运行。放在 `experiments/artifact/`，与项目其他模块的评测约定一致。
- 引用质量：对全部 Claim 跑全量判定，计算引用召回率（被充分支撑的事实陈述 / 全部事实陈述）和引用精确率（有效支撑的引用对 / 全部引用对），沿用 04 文档 4D 阶段的定义。
- 判定器校准：人工标注 200 条 Claim，计算判定器与人工的一致率；一致率不达标时，L3 相关指标不能作为结论。
- 风险规则漏判率：全量判定发现的不支撑 Claim 中，在线未被必判规则选中的比例。
- 要求遵循：同一工作台有要求和无要求两份产物，用模型评审做两两比较，人工抽查。
- 类型专项：测验答案唯一性、难度分布；学习指南的资料覆盖度；闪卡正反面泄题率。
- 效率：各阶段耗时 P50/P95，每次运行 token 和成本。
- 回归门禁：提示词、类型指令或模型配置变更必须附评测子集的前后对比。

### 7.5 指标怎么定位设计问题

| 现象 | 指向的设计位置 | 处理方向 |
|---|---|---|
| 随机样本支撑率明显低于必判样本的修复后支撑率 | 风险规则漏判 | 增加风险特征或调整 τ，必要时提高随机比例 |
| 修复前不支撑率高，集中在某个 kind | 该 kind 的写作模板或锚点粒度 | 改模板并做评测对比；考虑更细的锚点 |
| anchor 越界比例高 | 规划分配给分段的素材不够 | 调整规划模板或分段素材预算 |
| 删除率高，但 L3 不支撑率低 | L2 失败为主（编号不存在、缺锚点），属于结构化输出问题 | 改用模型原生 JSON Schema 输出，或简化编号格式 |
| 引用都支撑，要求遵循得分低 | 要求没有影响取材范围或规划 | 检查范围解析输出与规划输入 |
| 学习指南只引用少数资料 | COVERAGE 抽样或规划分配不均 | 调整分层抽样或规划约束 |
| 修复后通过率与修复前接近 | 修复轮次无效 | 取消修复，失败直接删除，省一次调用 |
| 判定器与人工一致率低 | 判定模板或判定模型 | 先修判定器，期间 L3 指标不作结论 |
| 某阶段耗时占比异常 | 该阶段 | 看阶段级耗时、token、重试次数 |

### 7.6 耗时预算（估算，V1 实测校准）

以 5 个分段的标准长度学习指南为例：

| 阶段 | 模型调用 | 估算耗时 |
|---|---|---|
| 取材 | 1 次小模型（范围解析）+ 检索 | 5–15 秒 |
| 规划 | 1 次 | 10–20 秒 |
| 写作 | 5 次，并发 4 | 30–60 秒 |
| 核验 | 1–5 次小模型批量判定，修复 0–5 次 | 10–40 秒 |
| 渲染（PDF） | 无 | 5 秒以内 |

估算 P50 在 3 分钟以内，现状实测为 1251 秒。这是估算，V1 必须用阶段级统计实测。

## 8. 失败与恢复

### 8.1 失败分类与处置

| 类别 | 典型例子 | 处置 | 理由 |
|---|---|---|---|
| 瞬时故障 | 模型 429、5xx、超时；网络中断；MinIO 短暂不可用 | 单次调用指数退避加抖动，最多 3 次；429 遵守 Retry-After | 换个时间再试大概率成功；已完成部分有检查点，重试不重复 |
| 输出不合规 | JSON 解析失败、Schema 不符 | 附校验错误重试 1 次；仍失败则该分段失败，运行失败但可续跑 | 原样重试成功率低，带错误重试有效；无限重试只会消耗预算 |
| 引用不闭合 | anchor 不存在、FACT 缺 anchor | 局部修复 1 轮；仍失败删除该 Claim | 内容问题，局部处理即可 |
| 语义不支撑 | UNSUPPORTED、CONTRADICTED | 局部修复 1 轮；仍失败删除 | 同上 |
| 判定不可用 | 判定模型不可用、判定预算耗尽 | 标为 UNVERIFIED，版本照常交付并显示未核验 | L2 已保证可点回；缺失的语义核验如实展示，不判为通过 |
| 视频解析失败 | MCP 超时、5xx、熔断打开 | 重试 2 次后运行失败，细则见 6.3.6 | 用户明确给了视频链接，视频是必需素材，不能降级为只用工作台资料 |
| 平台凭据失效 | 连接器返回 CREDENTIAL_INVALID | 不重试；任务失败，向运维告警 | 重试不会改变凭据，需要人工更新配置 |
| 连接器契约不符 | 清单指纹变化或 Schema 不符合约定 | 停用该连接器并告警，等运维确认 | 上游升级可能改变工具行为，继续调用会产生不可预期的结果 |
| 素材不足 | 素材包为空或低于下限 | 立即失败，提示补充资料或放宽要求 | 确定性错误，重试结果相同 |
| 预算超限 | token、调用次数或总时长超限 | 失败 BUDGET_EXCEEDED；保留检查点，用户确认后可续跑 | 自动重试会继续花钱 |
| 模型拒答 | 内容策略拦截 | 失败，不重试 | 确定性 |
| 输入失效 | 运行中资料被删除、工作台权限被撤销 | 立即终止，丢弃中间结果，不提交版本 | 继续执行会处理已撤销的内容 |
| Worker 失联 | 进程崩溃、租约过期 | Java 重新派发，`lease_epoch + 1`，从检查点续跑；3 次后 WORKER_LOST | 检查点保证续跑不重复已完成的工作 |
| 渲染失败 | TTS 超时、PPTX 生成异常 | 文件级重试 3 次；仍失败则文件置 FAILED，可手动重试 | 内容和文件分离，版本内容不受影响 |
| 程序缺陷 | 未预期异常 | 失败 INTERNAL，不自动重试，告警 | 自动重试会重复触发同一缺陷 |

### 8.2 为什么不能一律重试

1. 确定性错误（素材不足、拒答、鉴权失败、程序缺陷）重试结果相同，只浪费 token 和时间。
2. 限流时所有任务一起重试会形成重试风暴，加重限流。
3. 内容类失败需要改变输入（附校验错误、局部重写），原样重试几乎没有意义。
4. 有副作用的调用重试可能重复执行。本方案只允许只读工具，正是为了让工具调用可以安全重试。
5. 输入失效时重试，会让已经撤销的内容继续被处理。

### 8.3 断点续跑

- **租约**：Worker 收到派发后申请租约，Java 用 CAS 把 `lease_epoch` 加一并返回；Worker 每 20 秒心跳，租期 60 秒。
- **围栏**：所有写入（检查点、版本、状态）都携带 `lease_epoch`，与当前值不一致时返回 409 STALE_LEASE，旧 Worker 收到后立即停止。
- **巡检**：Java 定时扫描租约过期且未终态的运行，`attempt + 1` 后重新派发。
- **续跑**：新 Worker 读取检查点清单，跳过已完成的阶段和写作分段，只重做缺失部分；L3 判定结果按 Claim 内容哈希缓存，未改动的 Claim 不重判；已记录的工具调用结果直接复用。
- **用户重试**：失败运行若属于可续跑类别（瞬时故障耗尽、预算超限、工具故障、输出不合规），用户点击重试即在同一运行上续跑；修改了要求则是再生成，创建新运行。

### 8.4 幂等清单

| 操作 | 幂等依据 | 冲突处理 |
|---|---|---|
| 创建运行 | `(workspace_id, idempotency_key)` 唯一 | 相同键返回已有运行；同键但 `input_hash` 不同返回 409 |
| 派发消费 | outbox 事件 ID；按运行状态判断 | 已终态的运行忽略消息 |
| 写检查点 | `(run_id, stage, part_key)` 唯一 + `payload_hash` | 相同哈希重复写返回成功；不同哈希返回 409 |
| 提交版本 | `artifact_version.run_id` 唯一 | 重复提交返回已有版本 |
| 渲染文件 | `(version_id, role, renderer_version)` 唯一 | 重复渲染写同一对象键 |
| 工具调用 | 只读；结果按 `(run_id, call_seq)` 记录 | 续跑复用已记录结果 |

### 8.5 可复现与可观测

可复现分三个层次，要分开说清楚：

- **可重放**：同一版本的中间表示重新渲染，结果一致。
- **可追溯**：每个 Claim → 句子 → 资料快照与位置；每次模型调用 → 提示词包哈希、模型配置、输入哈希、完整提示词与原始输出（检查点保留 14 天）。
- **重新生成不保证逐字一致**：模型本身有随机性。冻结的输入保证的是用相同条件重跑，素材包相同（快照固定、检索排序有确定的平局规则），差异只来自模型。

可观测：

- 链路：`run_id` 作为 trace 根，阶段 span 下挂模型调用 span（模型、purpose、token、耗时、重试次数）和工具调用 span，属性命名参照 OpenTelemetry GenAI 语义约定。
- 指标：按类型和 kind 的成功率、错误类别分布、阶段 P50/P95、每次运行 token 与成本、L3 抽检比例与支撑率、删除率、工具调用成功率和熔断次数。
- 运行详情页：阶段时间线、真实模型调用次数、真实工具调用列表（来自 `tool_call_log`）、质量报告。
- 调试：任意分段可以用检查点中的输入单独重放。

## 10. 明确不做的

1. **可编排流程**（用户自定义步骤、DAG、节点编辑器）。NotebookLM 的自定义入口只有一句要求和少量选项，用户没有编排步骤的需求；可编排意味着每个用户流程都要单独保证引用和质量，测试组合无法收敛；现有实现已经证明图在实际运行中退化成线性循环。重新考虑的条件：出现两种以上 kind 需要不同的阶段顺序。
2. **自定义输出结构**（用户自定义 Schema 或渲染器）。逐句出处依赖 Schema 中 Claim 的位置，用户自定义 Schema 无法保证这一点；渲染器是代码，不能对用户开放。7 种 kind 已覆盖 NotebookLM 的全部产物，个性化结构通过类型指令和必需章节表达。
3. **生成过程中的自主联网研究**。产物的承诺是每句话来自用户资料；开放联网会把来源扩大到不可控的范围，耗时也不可预测。需要联网研究时交给 Research 模块，研究报告保存为资料后再生成产物。

暂缓，有明确前提后再做：

- 用户自行接入 MCP 服务（含 OAuth）：原始需求中的用户接入自己的外部工具，本期不做。视频解析由我们的连接器覆盖；用户真正需要自带服务的是账号里的私有内容，主流服务要求 OAuth，实现和维护成本高；开放后还要处理用户凭据保管、执行用户命令、工具描述被篡改、按工作台授权等问题。流水线只认连接器约定，以后开放时增加登记界面、凭据保管和 OAuth 即可，取材流程不用改。重新考虑的条件：有明确的用户需要接入自己的服务。
- 带写操作的工具：会破坏重试安全，产物生成过程中只调用读取类工具。
- 全量在线语义核验：成本最高，离线评测已覆盖全量判定。
- 大纲交互编辑：NotebookLM 也没有，增加交互状态但收益不明确。
- 工作台之间共享产物或资料：违背工作台隔离的前提。
- 把链接导入为工作台资料（可以对视频直接提问、在多个产物间共用）：连接器约定已经兼容，需要时增加导入任务和资料侧存储即可。

## 附录 A：七个取舍

### A1 流程形态：固定流水线 + 运行状态机

**选择**：流程用固定的五段流水线；运行的生命周期用持久化状态机描述。这是两件事：流水线回答先做什么后做什么，状态机回答这次运行现在处于什么状态、能转到哪里。动态部分只有两处：写作阶段按规划结果展开分段并发，取材阶段内部的有界工具循环。

**为什么不选其他**：

- 可配置流水线：配置的使用者只有我们自己，改代码和改配置成本相近，配置还要额外写校验。
- DAG：现有实现证明节点之间没有真实分支和并行；DAG 带来调度、边语义、部分失败语义的成本，却不提供新能力。
- 状态机驱动流程：状态机适合由外部事件推动的生命周期（审批、等待回调），生成流程是内部的顺序计算，没有外部事件。
- Agent 自主循环：一键生成要求延迟和成本可预测、结果可复现、可评测，自主循环三者都难以保证。Agent 的决策能力用在真正需要判断的地方：取材时调用哪些工具、传什么参数，限定 3 轮 6 次。这与 Anthropic 的 Building effective agents 中的建议一致：可预测的任务优先用工作流，在需要灵活决策的环节嵌入 Agent。

**代价**：需要不同阶段顺序的新产物只能改代码；多角色辩论这类需要两次独立生成再合并的拓扑无法表达，辩论音频改为一次写作生成双方台词。

**改选条件**：两种以上 kind 需要不同的阶段顺序。

### A2 生成与引用：边写边引，用句子编号

**选择**：写作时每条事实 Claim 直接输出 anchors（句子编号），之后做确定性闭合校验，再按风险抽样做语义核验。

**为什么**：

- 模型写这句话时知道自己用了哪段材料；生成后再归因，要为每句话重新搜索证据，成本是句子数乘以候选片段数。现有实现的独立 cite 节点加逐引用复制原文的判定，就是 82% 输出 token 的来源。
- 编号让引用是否存在可以零成本确定性检查，前端也能直接高亮到句子。
- 用编号而不用引文：引文要求模型逐字复制，输出 token 多，空白和标点差异还会造成误判；编号只需几个 token。

**代价**：

- 模型可能引错编号（编号存在但不支撑），因此需要 L3。
- 句子粒度对长句、表格、图片不够精细：表格按行切句，图片以描述文本作为句子。
- 输入中每句加编号，输入 token 增加，估算约 5%。
- 写作时要同时管内容和引用，行文流畅度可能略受影响。

**改选条件**：V1 评测中，若边写边引的引用精确率比生成后归因低 10 个百分点以上，对精确率敏感的 kind 改为生成后归因。这是 V1 评测要回答的问题之一。

### A3 是否需要计划：需要，但按类型决定是否调用模型

**选择**：流水线固定有规划阶段。长文档、题量较多的测验和闪卡、幻灯片、音频脚本使用 LLM 规划；思维导图和少量闪卡使用 TRIVIAL 规划，不调用模型。

**收益**：

- 分段并发写作，总耗时取决于最慢的分段；
- 每段只拿自己的素材，上下文更小，引用更准；
- 覆盖度可控，测验的知识点不重复、难度有分布；
- 分段级检查点和局部修复；
- 规划输出的术语表和不重复的要点分配，替代了原来单独的全文一致性检查调用。

**代价**：多一次模型调用（约 10–20 秒）；规划出错会传导到所有分段；分段之间的衔接可能生硬。规划错误由确定性校验（编号、数量、要点不重复）挡住一部分，衔接问题 V1 接受。

**为什么短产物不规划**：思维导图需要全局结构，一次写完比先规划再拆分更自然；少量闪卡一次调用就能完成，规划只增加耗时。

**不暴露大纲编辑**：NotebookLM 也没有；会增加交互和状态，收益不明确。

### A4 质量校验做到什么程度

**选择**：L1 格式和 L2 引用闭合必须有，且阻断；L3 语义支撑必须执行，但抽样、不阻断交付（失败 Claim 修复或删除）；整体质量（可读性、要求遵循、覆盖度）只在离线评测中做。

**为什么**：

- L1 必须：渲染器依赖结构，格式错了无法展示。
- L2 必须：这是逐句出处这一硬要求的直接实现，确定性且几乎零成本。
- L3 抽样：全量判定是现状最大的成本；风险特征能把判定集中到最容易出错的句子；随机样本用于在线估计漏判。
- 整体质量放离线：在线没有对应的处置动作，算出来也只能展示。

**代价**：未被抽中的低风险句子仍可能不被支撑，只能靠随机样本估计比例，并在评测中校准规则；判定模型自身有误差，需要人工标注校准。

### A5 MCP 工具的位置：取材阶段的素材来源

**选择**：MCP 服务作为取材阶段的素材来源。生成请求带视频链接（以后也可以是飞书文档链接）时，取材阶段调用解析服务，结果冻结进素材包。解析服务都由我们部署和配置。工具不作为流水线的一等步骤。

**为什么放在取材阶段**：

- 与现有使用方式一致：用户给一个视频链接，直接拿到幻灯片或讲义，不需要先把视频加成资料再生成。
- 视频只是一种素材来源，规划、写作、核验不用区分来源，视频产物不再需要特殊分支。
- 复现和成本由两层保证：解析结果按视频缓存，同一视频再生成或换产物类型都不重复解析；素材包冻结在检查点里，续跑和追溯都基于同一份素材。

**为什么不作为一等步骤**：一等步骤意味着可以改流程拓扑，与 A1 冲突；工具输出格式不一，不规整就无法被引用。

**为什么由我们配置，不开放用户接入**：

- 视频解析要的是解析质量（字幕、转写、关键帧），一般用户不会为此自己部署服务。
- 用户真正需要自带服务的是账号里的私有内容，主流服务要求 OAuth，接入成本高。
- 只由我们配置时，用户凭据保管、执行用户命令、工具描述被篡改这些问题都不存在。
- 流水线只认连接器约定，以后要开放时增加登记界面、凭据保管和 OAuth 即可。

**代价**：

- 解析结果不出现在工作台资料列表里，用户不能直接对视频提问，缓存只在后台复用。
- 支持哪些平台取决于我们写了哪些适配服务。
- 飞书这类平台只能以应用身份读取，用户要先把文档授权给应用。

**改选条件**：用户需要对视频直接提问，或者希望一次解析供多个产物和对话共用时，增加导入为资料的入口；连接器约定和适配服务可以直接复用。

### A6 自定义产物：模板 + 指令

**选择**：用户选 kind，写一段类型指令，设默认选项，DOC 可以填必需章节，选择是否使用工具。

**为什么**：

- 只有一句指令不够：每次生成的一句要求已经存在，自定义类型的价值在于复用和选择输出形态。
- 不开放可编排步骤：见第 10 节第 1 条。
- 不开放阶段参数：用户不理解素材 token 预算这类参数，也不会去改，由 kind 默认值决定。
- 必需章节是唯一的结构化约束：周报、会议纪要这类类型确实需要固定的章节，用户会改它。

**代价**：更特殊的结构只能写进指令，靠模型遵守，校验只覆盖必需章节。

### A7 失败处理：按类别处置

**选择**：瞬时故障重试；输出不合规带错误重试一次；内容问题局部修复后删除；工具问题降级；确定性错误、权限和输入失效直接失败；预算超限停下等用户确认。完整分类见第 8.1 节。

**为什么不能一律重试**：见第 8.2 节。核心是三点：确定性错误重试结果相同；内容错误需要改变输入；重试的安全性依赖调用无副作用，所以工具限定为只读。

**代价**：分类本身需要维护，未知异常归入 INTERNAL 不自动重试，偶发的未知瞬时错误需要用户手动重试。
