# 12 产物生成框架改造规划

> 日期：2026-10-27。本文只规划简历第 4 条描述涉及的实现，是产物模块改造的实施依据。产物类型对标 NotebookLM，现有产物代码不作为约束，被替代的部分直接删除。

## 0. 目标描述

> 构建 Schema 驱动的产物生成框架：面向报告、测验、课程笔记等多类产物，以 SKILL.md 统一定义产物与输出契约，共享取材、规划、写作、校验、渲染五段流水线，新增产物只需一个 SKILL.md；采用 Java Host + Python Worker 分层承载任务编排、模型执行与版本管理，并通过 MCP 接入音视频转写与关键帧理解，以感知哈希去重画面、按时间轴对齐为图文文档，支持视频 PPT、PDF 讲义等产物生成。

## 1. 描述与实现对应

| 描述 | 实现 | 验收证据 |
|---|---|---|
| 面向报告、测验、课程笔记等多类产物 | 产物清单对标 NotebookLM，见第 2 节 | 清单内产物都能从前端生成 |
| Schema 驱动 | 每种产物形态一份 JSON Schema，同时用于约束模型结构化输出、校验、渲染器输入 | Schema 文件；模型输出不合规时被拒绝的测试 |
| 以 SKILL.md 统一定义产物与输出契约 | 一个产物一个目录，`SKILL.md` 头部声明名称、描述、产物形态、输出契约和选项，正文是生成指令 | 全部内置产物都由 SKILL.md 定义，代码里没有按产物写的分支 |
| 共享五段流水线 | 取材、规划、写作、校验、渲染五个阶段，所有产物共用；形态差异只体现在 Schema、提示词模板和渲染器 | 流水线代码不含产物名称判断 |
| 新增产物只需一个 SKILL.md | Java 与 Worker 读取同一个 `skills/` 目录，前端按钮来自 Skill 列表接口 | 演示：新增一个 SKILL.md，不改代码即可在前端出现并生成 |
| Java Host + Python Worker 分层承载任务编排、模型执行与版本管理 | Java 负责任务创建、派发、状态、版本与文件；Worker 负责流水线执行和模型调用 | 沿用现有任务和版本链路，新流水线接入后全链路测试通过 |
| 通过 MCP 接入音视频转写与关键帧理解 | 独立部署的音视频解析 MCP 服务，走 Streamable HTTP | 服务容器；B 站链接和上传的音视频都经它解析 |
| 以感知哈希去重画面 | 场景检测粗筛候选帧，再用感知哈希比较相邻帧，只对画面变化处做理解 | 解析结果记录去重前后的帧数 |
| 按时间轴对齐为图文文档 | 关键帧按时间点挂到对应的转写段，输出带时间戳的图文文档，进入资料库切片和索引 | 对话能检索到视频内容；资料详情能看到图文对齐结果 |
| 支持视频 PPT、PDF 讲义等产物生成 | 视频 PPT（DECK，嵌入原关键帧）和 PDF 讲义（DOC，插入关键帧）两个 Skill | 同一视频生成 PPT 和 PDF 讲义 |

## 3. 目标结构

```
资料接入
  B 站链接 / 上传的音视频 → 音视频解析 MCP 服务（转写 + 关键帧理解 + 感知哈希去重 + 时间轴对齐）
    → 图文文档（文字带时间戳，关键帧存 MinIO）→ 资料库（切片、索引）

产物生成
  前端产物按钮（来自 Skill 列表）→ Java Host 创建任务、派发
    → Python Worker：取材 → 规划 → 写作 → 校验 → 渲染
    → 结果回传 Java Host → 版本与文件
```

产物生成不直接调用 MCP。视频内容先作为资料入库，生成时和文档资料一样检索。原视频不入库，只保留解析出的文字和关键帧。

## 4. SKILL.md 与输出契约

### 4.1 目录

仓库根目录新增 `skills/`，Java 和 Worker 都读这一份，代替现在分散在三处的产物目录 JSON。每个产物一个目录，目录名即产物名，例如 `skills/study-guide/SKILL.md`、`skills/mind-map/SKILL.md`、`skills/video-deck/SKILL.md`。

### 4.2 SKILL.md 格式

```markdown
---
name: study-guide
description: 把工作台资料整理成由浅入深的学习指南，包含学习目标、核心概念和复习路径。
kind: DOC
version: 1
contract:
  sections: {min: 3, max: 8}
  required_headings: [学习目标, 核心概念, 复习路径]
options:
  length: {choices: [SHORT, STANDARD, LONG], default: STANDARD}
renderers: [MARKDOWN, PDF]
---

面向第一次接触这些资料的读者，先给出学习目标，再按由浅入深的顺序讲核心概念，
最后给出复习路径。每个概念说明它解决什么问题。
```

- `name` 与目录名一致，`description` 用于前端展示；这两个字段沿用 Agent Skills 的约定，其他工具也能识别。
- `kind` 指向一份产物形态 Schema；`contract` 是在 Schema 之上的契约规则；`options` 生成前端的选项表单；正文是生成指令。
- 加载时校验：名称与目录一致、`kind` 存在、`contract` 里的规则都已注册、选项格式正确。不合法的 Skill 启动时报错，不会静默跳过。
- 前端列表只读头部字段，生成时才加载正文。

### 4.3 产物形态 Schema

`schemas/` 下每种形态一份 JSON Schema：

| kind | 结构 | 里程碑 |
|---|---|---|
| `DOC` | 章节 → 段落、列表、插图 → 陈述 | M1 |
| `QUIZ` | 题目：题干、选项、答案、解析 | M1 |
| `CARDS` | 卡片：正面、背面 | M1 |
| `TREE` | 节点：标签、说明、子节点 | M1 |
| `TABLE` | 列定义、行 → 单元格 | M1 |
| `DECK` | 页：标题、要点、讲稿、配图 | M3 |
| `SCRIPT` | 段：说话人、台词 | M6 |

陈述、解析、卡片背面、节点说明、单元格这些事实性文本都带 `anchors`（引用的素材句子编号）。插图和配图引用素材中的关键帧 ID。

同一份 Schema 用在三处：写作时作为模型结构化输出的约束；校验时做结构检查；渲染器按它读取内容。

### 4.4 契约规则

契约规则是注册在代码里的具名检查，Skill 只能引用已注册的规则：

| 规则 | 作用 |
|---|---|
| `sections` | 章节数上下限 |
| `required_headings` | 必须出现的章节标题 |
| `quiz_single_answer` | 每道题有且只有一个正确答案，答案在选项中 |
| `card_no_leak` | 闪卡正面不包含背面的答案 |
| `tree_depth` | 思维导图层级与每层节点数上下限 |
| `table_columns` | 数据表列数上下限，单元格不为空 |
| `deck_bullets` | 每页要点数上下限 |
| `figure_required` | 指定章节或页面必须带配图 |

## 5. 五段流水线

流水线位于 Worker 新包 `app/pipeline/`，阶段顺序固定，所有产物共用。按产物形态区分的只有三样：Schema、提示词模板（`prompts/<kind>/<stage>.md`）和渲染器。

| 阶段 | 做什么 | 输出 |
|---|---|---|
| 取材 | 按用户要求和 Skill 指令生成查询，调用现有的范围检索接口；把命中片段切句并编号，视频片段保留时间戳和关联的关键帧 ID | 素材包 |
| 规划 | 一次模型调用，按形态生成骨架：DOC 是章节和要点，QUIZ 和 CARDS 是知识点分布，TREE 是一二级节点，TABLE 是列定义，DECK 是每页要点和选用的关键帧；再做确定性检查（编号存在、数量在契约范围内） | 骨架 |
| 写作 | 按章节、页面或知识点并发调用模型，输出受 Schema 约束；事实性文本带素材句子编号 | 内容 |
| 校验 | 依次做 Schema 检查、契约规则、引用检查（编号存在、数字与原句一致）；失败项合并成一次修复调用，按 ID 合并回去，修复后仍失败的删除 | 通过校验的内容 |
| 渲染 | 按形态调用渲染器，见下表 | 文件与展示数据 |

| kind | 渲染结果 |
|---|---|
| DOC | Markdown；带 PDF 渲染器的 Skill 另出 PDF |
| QUIZ、CARDS | 前端交互数据（作答、翻面），同时投影为 Markdown |
| TREE | 嵌套结构，前端思维导图组件直接使用 |
| TABLE | 表格数据，可导出 CSV |
| DECK | PPTX 和每页预览图 |

结果回传时，同时给出现有版本格式的投影，现有阅读页和导出在 M4 之前不用改。

## 6. Java Host 与 Python Worker 分工

| | Java Host | Python Worker |
|---|---|---|
| 任务编排 | 创建任务、outbox 派发、状态、取消、失败结束（沿用现有链路） | 消费任务，执行流水线 |
| 模型执行 | 不调用模型 | 模型调用、结构化输出、修复 |

| Skill | 读取 `skills/` 提供 `/api/v2/skills`，校验创建请求中的 Skill 与选项 | 读取 `skills/` 执行 |
| 资料接入 | 创建视频链接资料和解析任务，接收解析结果并交给现有切片和索引流程 | 调用音视频解析 MCP 服务 |

接口变化：

- `/api/v2/skills` 改为读取 `skills/` 目录，返回字段保持前端现有用法，另加 `kind`；
- 新增 `POST /api/v2/workspaces/{workspaceId}/sources/links/preview`，返回视频标题、时长和分 P 列表；
- 新增 `POST /api/v2/workspaces/{workspaceId}/sources/links`，提交 B 站链接和所选分 P；
- 新增内部接口 `GET /internal/worker/artifact-tasks/{taskId}/frames/{frameId}`，渲染时按任务资料范围读取关键帧图片；
- 产物完成载荷新增 `ir`、`evidence`、`pipeline_stats` 三个字段，写入现有 `result_payload_json`；
- `ArtifactCandidateVerificationPolicy` 增加新载荷的校验分支：Schema 版本正确，所有引用都在素材包内。

## 7. 音视频解析 MCP 服务

### 7.1 部署

现有 `bilibili_render_pdf_server.py` 由 Worker 通过 stdio 在本机启动。改为独立服务 `workers/media-mcp/`，单独容器部署，走 Streamable HTTP，地址写在配置中。容器包含 ffmpeg、ASR 模型和图片处理依赖，Worker 镜像不再携带这些依赖。

### 7.2 工具

| 工具 | 输入 | 输出 |
|---|---|---|
| `get_video_info` | B 站链接 | 标题、时长、分 P 列表 |
| `parse_video` | B 站链接、所选分 P | 图文文档 |
| `parse_media` | 上传的音视频文件引用 | 图文文档（音频只有文字部分） |

上传音视频现在调用的 `transcribe_local_audio` 改为调用 `parse_media`。

### 7.3 处理过程

1. **转写**：有官方字幕就用字幕，没有就用 ASR，沿用现有转写实现。
2. **关键帧**：先用 ffmpeg 场景检测粗筛候选帧；再计算感知哈希，与上一张保留帧的汉明距离小于阈值的视为同一画面，丢弃。阈值放在配置里。
3. **画面理解**：对保留的关键帧做 OCR 和画面描述，沿用现有帧观测实现。
4. 转写和关键帧两条线并行执行。
5. **时间轴对齐**：每个关键帧按时间点挂到所在的转写段，输出按时间排序的段落列表。

输出示例：

```json
{
  "title": "Redis 缓存设计实战",
  "source_url": "https://www.bilibili.com/video/BV1xx411c7XX",
  "segments": [
    {
      "part": 1, "start_ms": 12000, "end_ms": 18500,
      "text": "今天先讲缓存穿透的三种处理方式。",
      "frames": [{"frame_id": "f_003", "at_ms": 15000, "image_ref": "…",
                  "caption": "幻灯片：缓存穿透处理方式", "ocr_text": "布隆过滤器 / 缓存空值 / 接口校验"}]
    }
  ],
  "stats": {"candidate_frames": 412, "kept_frames": 58, "transcript_origin": "SUBTITLE"}
}
```

`stats` 记录去重前后的帧数和转写来源，作为感知哈希效果的证据。

### 7.4 入库

Java 收到图文文档后：关键帧图片存入 MinIO，文字和帧说明按段生成资料快照，切片时保留时间戳和帧 ID，之后走现有的切片、上下文增强和索引流程。原视频不保存，解析时下载的临时文件在解析结束后删除。

### 7.5 边界

- 链接只接受 B 站域名，其他链接直接拒绝；
- 单个视频的解析总时长、文字大小、关键帧数量都有上限，超出则失败并给出原因；
- 解析失败时资料显示失败原因，可以重试。
