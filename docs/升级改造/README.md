## 各模块最严重的问题

1. **Deep Research**：默认配置下研究表格固定为 1 行 4 列；发给搜索引擎的检索词可能是上万字符的上下文加 `::` 模板；深挖单元格里写死了 PostgreSQL / MySQL 的文档 URL 和查询提示词。
2. **Memory**：冲突检测只看正负极性；效果反馈接口没有调用方，效用分数从不更新；没有长期措辞的消息不会进入抽取。
3. **检索**：多轮对话时，送进向量化和 BM25 的查询是整段对话窗口拼成的多行文本；Wiki 每次查询从 MySQL 加载最多 5000 页全文在内存里打分。
4. **产物框架**：技能图节点是字符串模板，写死了定位句和影响描述；修复就是补数量；校验失败没有重试。
5. **流水线**：只支持五种格式；扫描件直接失败；大文件向量化可能超过 Kafka 消费超时后反复重做。

## 模块之间的依赖

- 模块四的素材检索（4B）依赖模块三的查询改写和混合检索（3A）；
- 模块二的记忆向量检索（S3、S4）和模块三的 Wiki 索引（S4）复用同一套 embedding 客户端和 ES 投影写入器；
- 模块三的 BM25F 公共组件（S2）同时被 Note 降级打分、Wiki 降级检索、记忆匹配使用；
- 模块一的 OCR、转写相关能力与模块五共用 Artifact Worker 的系统 MCP 服务。

## 通用约定

1. **LLM 降级**：生成和规划类调用（检索词、表格规划、查询改写、意图编译）在 LLM 不可用时退回规则，并记录降级原因；判定类调用（矛盾判断、证据支撑、反证判定、记忆冲突）在 LLM 不可用时记为 `NOT_RUN`，不允许判为通过。
2. **配置默认值**：新能力完成后默认打开，保留开关用于回退；`application.yml` 和 `docker-compose*.yml` 同步修改。
3. **新增 LLM 调用**：每个调用都有独立的 `purpose` 名称，输出用 pydantic 或 Jackson 做结构校验，不合规时带错误信息重试一次；调用次数计入现有预算。
4. **删除而不是保留**：被替代的模板代码、写死的数据直接删除，不保留为死代码；仍需要的规则只作为降级方案存在。
5. **测试**：每个阶段完成后运行 Worker（pytest）和 Backend（mvn test）全部测试；依赖具体产品或评测题的测试夹具改为通用夹具。
6. **评测**：每个模块完成后在 `experiments/<模块>/` 下提交评测脚本、数据集说明和结果文件。简历中的数字以这些结果为准。

## 推进方式

按 1A → 1F → 2A → … → 5D 顺序推进。每个阶段开始前确认该阶段涉及的具体文件和接口变化，完成后汇报测试结果，再进入下一阶段。
