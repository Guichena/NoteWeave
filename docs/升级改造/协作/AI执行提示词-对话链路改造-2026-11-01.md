## 每期的工作方式

1. 开始前读涉及的代码，确认设计里提到的类、字段、行号仍然成立。设计基于 `e2f72e39`，行号可能有偏移。
2. 发现设计与代码不符，或者有更简单、同样正确的做法时：
   - 可以调整，但要在第 15 节实施记录里写明差异和理由；
   - 涉及第 2 节原则或第 0 节设计要点的改变，先停下来问用户。
3. 数据库迁移从 V223 起按顺序编号，不修改已经执行过的迁移。
4. 新增的正文副本或展示文字，要在同一次修改里补上删除和脱敏路径。
5. 每期结束：
   - 按第 12 节的验收逐条检查；
   - 跑全量测试；
   - 在第 15 节追加实施记录（改动范围、与设计的差异、测试结果、未完成项）；
   - 提交并推送工作分支，然后向用户汇报。

## 测试

- **后端**：JDK 17，执行 `./mvnw -f backend/pom.xml test`。
  - 检索、会话、记忆相关的契约测试使用 `test-es` profile，需要一个不开鉴权的 Elasticsearch 8.15.3，默认地址 `127.0.0.1:19200`。可以这样启动：`docker run -d --name nw-test-es -p 127.0.0.1:19200:9200 -e discovery.type=single-node -e xpack.security.enabled=false docker.elastic.co/elasticsearch/elasticsearch:8.15.3`。
  - 19200 被占用时换端口，并设置 `NOTEWEAVE_ES_PORT`。
  - 已知与其他测试类同跑时偶发失败、单独跑能通过的用例：`JdbcActualUsageStoreTest`、`MemorySourceReadGateReadPathTest`、`WikiWorkspaceLockTest`。main 原样代码表现相同，不算回归，但要在记录里注明。
- **前端**：在 `frontend` 目录执行 `pnpm install --frozen-lockfile`、`pnpm test`、`pnpm build`、`pnpm ui:check`。
- **研究 Worker**：在 `workers/research-worker` 目录执行 `python -m pip install -e .` 和 `python -m pytest -q`；在仓库根目录执行 `python scripts/deepresearch/check_contract_vocabulary.py`。
- **CI**：与 `.github/workflows/ci.yml` 一致。推送前本地至少跑过后端、前端、研究 Worker 三项。
- **端到端**：`scripts/deepresearch/e2e_report_grounding.py` 需要真实模型和部署环境，没有环境就不跑，在记录里写明，由用户安排在测试服务器上验证。
