# Research 线改造计划

日期：2026-10-23。基线 `70631bd0`，集成分支 `codex/oth-20261023`（`d8ced2b5`）。本文件只覆盖 Deep Research Agent 相关任务，与《非 research 改造与设计审计》分开维护。

核实与修订见《核实与修订-2026-10-23.md》。本文件已按核实结果补齐 R-02 至 R-06 的前置与边界，未展开的细节以该文件为准。

## 一、结论

Research 是五项能力里实现最完整的一块。五十四张表、逐句核验、checkpoint 恢复都是真实现，不是空壳。本轮不改内部逻辑，只做八件事：命名纠正、可复跑回放、引用反例集、共享 outbox 边界确认、部署版本兼容记录、研究质量评审口径、恢复预算语义、多副本协调器约束。

与业界对照：架构与 Anthropic 的 orchestrator-worker 一致，引用闭包比他们更严；差距在部署期间的任务版本兼容、回放确定性、恢复后的预算语义。

## 三、与业界对照

| 维度 | 业界做法 | 我们的实现 | 判定 |
|---|---|---|---|
| 任务分解 | Anthropic 用 orchestrator-worker，主 Agent 规划后派生子 Agent 并行检索 | 角色工作流加 wave barrier 加任务协调器 | 对齐 |
| 计划持久化 | Anthropic 把计划写入 Memory，防止上下文超过 20 万 token 被截断后丢失 | 计划落库，checkpoint 保存 stage 与 decision | 对齐 |

| 质量评审 | LLM 评审加人工抽检，维度为事实准确性、引用准确性、完整性、来源质量、工具效率 | 有运行时指标，没有成体系的离线评审 | 落后 |

## 四、任务

### R-01 命名纠正

`ResearchVerifierGatedSummaryAssembler:107-113` 的判定是 `row_status != VERIFIED`，统计读模型里的受阻行数量，不参与校验。真正的校验在 `ResearchStatementSupportValidation` 与 verifier_decision、semantic_check 表里。

改名受阻行统计之类的描述性名称，不改行为。注意 guardrailed 计数另外排除了 CONFLICTED，改名时不要把这个语义连带改掉。工作量小。

### R-02 可复跑研究回放

目标：一条命令从固定资料与桩模型出发，走完规划、检索、证据、核验、报告，中途中断一次并从 checkpoint 恢复。

设计：

- 固定资料集放测试资源目录，桩模型按角色返回固定结果。
- 回放入口复用现有 coordinator 与 completion 路径，不绕过校验。
- 断言：最终报告通过逐句核验；恢复后 stage 与 decision 与中断前一致；恢复次数被正确记录；同一输入跑两次结果完全一致。

前置条件比原文估计的重。research 包内没有 `ChatLlmClient` 引用，模型调用都在 Python worker；conversation 与 memory 的脚本化桩不覆盖 research。worker 生产入口直接构造默认模型客户端，没有注入点，回放要么起一个假的 OpenAI 兼容服务，要么加参数。Java 侧已有 replay driver，但要求四个环境变量，材料由 Python 预生成；目前只有 extraction 有 fixture，规划、核验、成文都没有。Kafka 关闭后只有单任务 claim 接口，没有 list 或 next，需要直接驱动或补发现接口。外部检索走 MCP 搜索代理，固定资料回放需要假搜索服务。报告上传要求 `llm_calls` 与 permit 回执口径一致，假模型回放要满足这条。

依赖可关性：MySQL 必需，因为恢复用到行锁与 timestampadd；MinIO 可以换本地存储；窗口检索走 JdbcTemplate，不依赖 Elasticsearch。

工作量中到大，主要成本在编排与假服务，不在流程改造。

### R-03 引用审计的可复跑校验

目标：单独验证引用闭包。构造三类反例：引用范围外事实、遗漏联合证据、改写原事实文本。前两类应被拒绝；第三类在 FROZEN_FACT 下应被拒绝，在 SEMANTIC_ENTAILMENT 下按设计放行。

现有 `ResearchStatementSupportValidation` 已有这些判断，缺的是独立、可复跑的用例集。

失败关闭的边界要写准：第 87 行拦的是声称语义核验却计数为 0 的伪造记录，模型不可用不会阻断报告。worker 在模型不可用或预算用尽时会退回冻结事实，此时计数为 0 且 basis 是 FROZEN_FACT，不会触发该行。反例集仍应在桩模型下跑，避免模型抖动让用例不稳定。

改写原事实文本这一类反例，只在 basis 为 FROZEN_FACT 时才被第 86 行拒绝；如果标成 SEMANTIC_ENTAILMENT 且模型判 SUPPORTED，会被放行，这是设计意图，用例要按这个语义写。

工作量小。

### R-04 与共享 outbox 的边界确认

`TaskOutboxDispatcherService` 与 `DurableOutboxDispatcher` 是共享组件，非 research 线的 OTH-11 会改投递耗尽收尾。工作单要求不得改变 research outbox 行为。

范围要比原文更大：`DurableOutboxDispatcher.recordFailure` 同时处理 `task_outbox` 与 `research_agent_outbox`，三态改动会影响两条线。边界测试要覆盖两个存储的死信状态与收尾结果，不能只测 task_outbox。

任务：在 OTH-11 实施时补一组边界测试，确认两条 outbox 的收尾路径各自符合预期。工作量小，依赖 OTH-11。

### R-05 部署期间的任务版本兼容

现状：部署后运行中的研究任务可能读到新提示词或新角色配置，没有版本固定。

业界做法是 rainbow deploy 或任务级版本固定。这是产品与运维层面的决定，不是代码缺陷。建议先记录，暂不实现。

触发条件写清楚，满足任一再开工：同时运行多个副本；发布频率高于任务平均时长；出现运行中任务读到新提示词导致的复现问题。三者都不成立时，记录即可。

### R-06 研究质量评审口径

现状：有 runtime_metric 与 completion_metrics，但没有成体系的离线评审。

设计：按 Anthropic 的维度做 LLM 评审，事实准确性、引用准确性、完整性、来源质量、工具效率各 0 到 1 分，再加人工抽检。不写死通过率数字，只记录口径与样本。

样本与一致性要求：样本不少于 30 份报告，人工抽检比例不低于 20%，两名评审独立打分并报告一致性；评审固定模型版本与提示词版本，换版本要重新基线。

工作量中，需要模型调用授权。

### R-07 恢复后的预算语义

现状：预算耗尽后 resume 会新建 run，只复制问题、意图与来源，不复制预算与 reservation。预算上限来自新 run 的 discovery_loop limits，消耗按 run 聚合。也就是说，从 checkpoint 恢复等于重新发一份预算，存在重复消耗与成本失真。

任务：先定语义。要么把已消耗预算与 reservation 复制到新 run，要么在恢复时按剩余预算设上限；两种都要在报告里体现累计消耗。工作量小，需要产品确认口径。

验收：恢复后的 run 预算上限等于原上限减已消耗；报告里的累计消耗跨恢复单调不减。

### R-08 多副本协调器约束

现状：多副本时 coordinator 只靠 tick 内的 research_run 行锁串行化，而且锁在 tick 中段才拿到；规划下发与冲突裁决在锁外执行，没有 coordinator 租约。每个副本每秒扫描最多 25 个 run。幂等键能防重复建任务，但重复规划与锁等待会放大延迟。

任务：部署多副本时明确只跑一个 coordinator，或者补租约。前者写进部署文档即可，后者工作量中。

验收：两副本同时运行时，同一 run 不会出现两次规划下发；如果只跑单 coordinator，部署文档里有明确约束与检查项。
