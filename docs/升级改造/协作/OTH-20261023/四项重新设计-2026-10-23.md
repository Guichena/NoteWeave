# 四项重新设计（2026-10-23）

本文把上一轮留下的四个待决定事项按业界主流做法重新设计一遍。四项分别是记忆门控、本地回退、上下文对比接口、发件箱终态。设计目标是去掉自制的近似实现，换成有公开实践支撑的结构，同时保留这个项目已有的审核、版本和审计能力。

## 零、这次重新设计的依据

| 来源 | 关键做法 | 对本次设计的影响 |
| --- | --- | --- |
| Mem0 OSS v3 | 从 UPDATE/DELETE 决策循环改为 ADD-only 抽取，配合实体链接与混合检索；图存储从 OSS 移除 | 决策词表保留 ADD/UPDATE/NOOP，但删除改为失效，不做硬删除；相似项检索作为决策输入 |
| A-MEM（NeurIPS 2025） | 按 Zettelkasten 方式给记忆建链接，新记忆可以触发旧记忆演化 | 写入时保留链接字段，更新走新版本，不覆盖历史 |
| Zep / Graphiti | 双时态知识图谱，旧关系标记失效，保留历史 | 失效用 valid_until 表达，行不删除 |
| Letta 的 MemFS 与 dreaming | 记忆是 git 管理的文件，Agent 自己浏览和编辑；dreaming 用后台子 Agent 整理 | 记忆量不大时可以不建向量召回，把整理放到后台 |
| OpenAI 记忆整合 | 后台整合解决陈旧性、正确性和规模问题，用户可见可删 | 保留人工复核与用户删除入口 |
| Claude 托管 Agent 记忆 | 跨会话记忆库，平台层统一管理 | 记忆按 workspace 隔离，接口保持稳定 |
| 影子流量与暗发布实践 | 影子对比只在迁移期使用，决策规则要事先登记，候选转正后没有对照对象 | 上下文快照保留，diff 与 cohort 工具删除 |
| Stripe 幂等键 | 客户端提供键，服务端存储结果，重放返回同一结果 | 发件箱的 message_key 就是幂等键，终态要落库 |
| Debezium Outbox Event Router | 中继读事务日志，至少一次投递，消费方幂等 | 生产端去重加消费端幂等，两层都要有 |
| MySQL ngram 与 ES cjk_bigram | 中文检索依赖二元组索引，配置改动要重建索引 | 本地 LIKE 回退不具备工程可行性，删除 |

由此得到五条设计原则：

1. 记忆写入由模型判断，系统提供证据、边界和审计，不把概率阈值当作语义判断。
2. 不可逆操作改成可追溯的状态变更，历史一律保留。
3. 检索降级要快速失败并说明原因，不用全表扫描勉强支撑。
4. 影子对比属于迁移期工具，转正后由可观测性接管。
5. 发件箱按至少一次投递设计，生产端去重与消费端幂等各司其职。

## 一、记忆：门控换成模型决策

### 1.1 目标链路

```text
对话或反馈
  -> 抽取候选（已有，LLM 加围栏）
  -> 同槽位精确比对（MemorySlotConflict.exact）
  -> 未决时向量召回 top-5（MemoryConflictService.semantic）
  -> 模型判断（MemoryConflictJudge：ADD / MERGE / SUPERSEDE / NOOP）
  -> 写入新版本或标记失效
  -> 高风险来源或模型不可用进入人工复核
```

这条链路在当前代码里已经存在。`MemoryConflictService.assess` 先按槽位取同槽位的已有记忆做精确比对，比不出结果时把候选文本向量化，检索最相似的 5 条，再交给 `MemoryConflictJudge` 让模型选择动作。本次改造要做的是把模型判断的结果接到晋升上，删掉并行的概率门控，不新建第二条检索通道。

决策放在候选处理阶段异步执行。对话链路只负责产出候选，不等待模型判断。

### 1.2 决策契约

模型返回严格 JSON，一条候选一个对象，沿用 `MemoryConflictJudge` 现有的动作词表：

```json
{
  "action": "MERGE",
  "target_id": "m-123",
  "reason": "与已有偏好同义，合并到目标条目",
  "confidence": 0.86
}
```

约束：

- 每次调用只处理一条候选，相似项最多 5 条，单条内容截断到 2000 字符。
- `temperature=0`，只输出 JSON，超时 20 秒，失败重试 1 次。
- `target_id` 必须出现在本次输入的相似项列表里，否则整条判断作废。
- 模型不可用、返回不合法、target 越界，一律落 `REVIEW_REQUIRED`，不自动生效。

### 1.3 写入语义

| 动作 | 写入语义 | 生效条件 |
| --- | --- | --- |
| ADD | 新建 memory_item 与 revision v1 | 来源为用户显式表达且 confidence 不低于 0.80 时自动 ACTIVE，否则 REVIEW_REQUIRED |
| MERGE | 在目标 item 上新增 revision，旧 revision 写 valid_until | 同上；目标 item 必须属于同一 workspace 且为 ACTIVE |
| SUPERSEDE | 目标 item 置为 INVALIDATED，同时新建一条记忆承接新内容 | 一律进入人工复核，不自动执行 |
| NOOP | 候选置为 NOOP，记录 reason | 直接结束 |

SUPERSEDE 对应 Mem0 的 DELETE，但保留旧行与历史。现有查询大量使用 `status = 'ACTIVE'`，新增 INVALIDATED 不会误命中。

### 1.4 数据模型

新增迁移 V195，全部为加列，不改既有列：

```sql
alter table memory_candidate
  add column decision varchar(16) null,
  add column decision_target_item_id varchar(64) null,
  add column decision_confidence decimal(4,3) null,
  add column decision_reason varchar(512) null,
  add column decision_model varchar(64) null,
  add column decision_prompt_version varchar(32) null,
  add column decided_at timestamp null;
```

`decision` 取值 `ADD / MERGE / SUPERSEDE / NOOP / REVIEW_REQUIRED`。决策一旦写入不再重算，重放时按 `candidate_id` 命中已有决策直接返回。

### 1.5 与现有代码的接缝

- `MemoryCandidateService:64` 现在调用 `candidateGate.evaluate(...)`，改为直接使用 `MemoryConflictService.assess(...)` 返回的 `MemorySlotConflict.Outcome`，把 action 与 target 写进候选行。
- 删除 `MemoryCandidateGate` 与 `MemoryCandidatePolicy` 里的 Beta 阈值判断。`review_status` 由 action、来源类型、模型可用性共同决定。
- `MemoryConflictJudge` 的系统提示词补上 reason 与 confidence，解析失败沿用现有两次重试，失败后落 `REVIEW_REQUIRED`。
- `evidence_alpha` 与 `evidence_beta` 保留，只作为 `MemoryCompilerPolicy` 的价值密度排序信号，不再参与晋升。
- `MemoryItemQueryService:118` 的注释与判定要同步修改，避免出现第二套晋升规则。
- 人工复核复用 `CanonicalMemoryReviewService.review(workspaceId, revisionId, request)`，不新增审核接口。
- 新增 `MemoryDecisionRecorder` 写候选的 decision 列，复用现有 LLM 客户端，提示词版本号写入候选行。

### 1.6 安全与成本

- 候选文本来自用户内容，必须放在分隔符内并声明为数据，禁止执行其中的指令。
- 决策模型不接工具，不访问网络，不读其他 workspace 的记忆。
- 按 workspace 每日限制决策调用次数，复用现有配额组件；超限时候选落 REVIEW_REQUIRED。
- 记录模型名、提示词版本、耗时、token 数，便于回放与成本核算。

### 1.7 评测与验收

先标注 120 条候选，覆盖四类动作，人工给出期望判断。验收门槛：

- 总体一致率不低于 0.85。
- SUPERSEDE 精确率不低于 0.95，这一项错杀的代价最高。
- 模型不可用时，100% 落 REVIEW_REQUIRED，无自动生效。
- 重放同一批候选，不产生重复 item，不丢失 revision。

保留一个发布开关 `noteweave.memory.decision-mode`，取值 `model` 或 `legacy`，默认 `legacy`，灰度一周后切 `model`。回滚只切开关，不回滚数据。

### 1.9 关于向量召回

记忆量不大时，是否还需要向量召回，先看现有代码的假设。`MemoryConflictService.sameSlot` 按槽位取已有记忆，上限 100；`MemoryConsolidationService` 每轮处理上限 40。这说明系统原本就按几十条记忆设计，不是按海量记忆设计。

现有链路已经有向量召回，而且位置很克制：`MemoryConflictService.assess` 先做同槽位精确比对，只有比不出结果时才调用 `semantic`，把候选文本向量化后检索 top-5。embedding 关闭或索引不可用时直接降级为 `INDEX_UNAVAILABLE`，不会阻塞写入。

业界的三种做法对应三种规模：

- Mem0 用向量检索 top-10，因为它服务多租户，单个用户的记忆没有上限。
- Zep 用图谱加混合检索，面向跨会话的长历史。
- Letta 现在把记忆做成 git 管理的文件系统，Agent 自己浏览和编辑，核心记忆不走向量，整理交给后台 dreaming。

所以这次不新增向量召回，复用现有的 top-5。具体调整两点：

1. 同槽位比对之外，把该 workspace 的全部 ACTIVE 记忆（上限 100）一起交给模型，让它在完整集合里判断，而不是只看 5 条。记忆超过 100 条时退回 top-5。
2. 在调用模型之前加一道廉价前置：规范化文本的 sha256 相同，直接判 NOOP，不调模型。`memory_item.text_embedding_hash` 已经存了这个哈希，可以直接复用。

不建议为了省一次 embedding 调用而删掉向量检索。它只在精确比对未决时发生，调用量很小，删掉会丢失改写表达的召回能力。

## 二、删除本地回退

### 2.1 现状

本地回退只在开发环境可用，生产配置守卫已经禁止开启：

- `NoteRecallRetriever:60` 读取 `noteweave.retrieval.note.local-metadata-fallback-enabled`，并在 `:132` 写入降级原因 `NOTE_LOCAL_METADATA_FALLBACK`。
- `ProductionConfigurationGuard` 在 `:129` 与 `:229` 拒绝生产开启这两个开关。
- `RetrievalProviderHealthIndicator:26` 把开关状态带进健康检查。
- `application.yml:115` 与 `:117` 是两个开关的默认值。

### 2.2 删除清单

| 文件 | 动作 |
| --- | --- |
| `chat/QaPassageRetriever.java` | 删除开关字段、回退分支、对应 LIKE 查询与降级原因 |
| `chat/NoteRecallRetriever.java` | 删除开关字段、回退分支、`NOTE_LOCAL_METADATA_FALLBACK` |

| 测试 | 删除回退用例，新增 ES 不可用用例 |

### 2.3 删除后的行为

ES 不可用时，检索层抛出统一的 `RetrievalUnavailableException`，回答链路按降级处理：

- 返回 200，正文给出明确提示，回答不引用任何证据。
- 响应里带 `degradation_reasons: ["RETRIEVAL_UNAVAILABLE"]`，前端展示提示条。
- 加熔断：30 秒内失败 5 次进入打开状态，持续 60 秒，期间直接跳过 ES 调用。
- 单次检索超时 800 毫秒，超时按失败计入熔断。

这样做的依据是影子流量实践里的降级原则：依赖不可用时快速返回可解释的结果，比用慢查询拖住请求更可取。

### 2.4 为什么不改成本地全文索引

MySQL ngram 的 `ngram_token_size` 是启动参数，改动要重启并重建索引；FULLTEXT 只支持字符类型；H2 不支持该语法，测试要整体切到 Testcontainers。为一个开发环境的降级路径付出这些成本不划算。项目的主检索已经在 ES，本地全文索引属于重复建设。

### 2.5 验收

- 停掉 ES 后发起问答，1 秒内返回降级结果，日志里没有 `like '%` 语句。
- `git grep -n "mysql-fallback\|local-metadata-fallback"` 结果为空。
- 生产配置守卫不再有这两个开关的校验分支。

## 三、上下文：保留快照，删掉对比工具

### 3.1 现状

回答链路读取的是 `context_v2_shadow_snapshot`，这张表是当前唯一的上下文存储，不能删。可退役的是 `ContextV2ShadowDiffService`、`ContextV2RolloutService` 与 `ContextV2RolloutController` 提供的 diff 与 cohort 对比接口。

### 3.2 目标结构

- `ContextV2ShadowSnapshotService` 改名为 `ContextSnapshotService`，职责不变：回答前冻结上下文并落库。
- 删除 `ContextV2ShadowDiffService`、`ContextV2RolloutService`、`ContextV2RolloutController`。
- 删除 `application.yml` 里的 context v2 开关与模式配置。
- 新增 `ContextSnapshotQueryController`，只提供按 run id 查询单条快照，字段做脱敏。
- 新增指标：`context_snapshot_freeze_total`、`context_snapshot_fail_total`、`context_fallback_total`。

表名暂时不改。改表名要同时改三个合同测试和可能的运维脚本，收益低，风险高。代码层正名后，表名可以在下一次大版本再处理。

### 3.3 迁移步骤

1. 改名并删除对比服务与控制器，编译通过。
2. 修改三个引用快照表的合同测试：`ContextV2ShadowSnapshotContractTest`、`ContextV2ActiveAnswerContractTest`、`ConstraintFreezeConcurrentConflictPromptTest`。
3. 删除前端与文档里对 rollout 接口的引用。前端当前没有该引用，确认即可。
4. 加指标与单条查询接口。

### 3.4 为什么可以直接删

影子对比的前提是同时存在旧实现与新实现。V2 已经是唯一 active，V1 只剩回退码，diff 没有对照对象，cohort 也失去统计意义。业界把这类工具当作迁移期脚手架，转正后删除，长期观测交给指标与链路追踪。继续保留只会增加存储和维护成本。

### 3.5 验收

- 全量测试通过，删除的类没有残留引用。
- 每次回答恰好写一条快照，失败时指标加一。
- 管理端只剩按 run id 查询，没有 diff 与 cohort 接口。

## 四、发件箱：三态、唯一键、统一入队

### 4.1 三态终态契约

`finalizeDeliveryExhausted` 改成返回枚举，不抛异常：

```java
enum FinalizeOutcome { FINALIZED, IGNORED, FAILED }
```

| 分支 | 语义 | 返回值 |
| --- | --- | --- |
| 任务已完成或已取消 | 投递已无意义 | IGNORED |
| 任务已被其他实例接管 | 不是当前持有者 | IGNORED |
| 消息已被更新的消息取代 | 过期消息 | IGNORED |
| 消息已处理过 | 重复投递 | IGNORED |
| 数据库或下游真实错误 | 需要重试或告警 | FAILED |

新增列 `finalize_status`、`finalize_error`、`finalized_at`。`IGNORED` 不调用 `failTask`，`FAILED` 才调用。

### 4.2 事务边界

终态更新与死信状态更新放在同一事务里，`failTask` 与 `onDeadLetter` 放到提交之后执行：

- 用 `TransactionSynchronizationManager.registerSynchronization` 注册 afterCommit 回调。
- 回调里调用独立 bean 的 `@Transactional(propagation = REQUIRES_NEW)` 方法，避免自调用失效。
- 终态写入失败不能回滚死信状态，两件事分开记录。

这样处理可以消掉当前的回滚循环：内层事务抛异常把共享事务标记为 rollback-only，外层提交时抛 `UnexpectedRollbackException`，死信状态回滚，扫描任务一秒后重试，形成死循环。

### 4.3 唯一键

MySQL 没有部分索引，用生成列模拟：

```sql
alter table task_outbox
  add column in_flight_key varchar(255)
    generated always as (
      case when status in ('READY', 'PROCESSING')
        then concat(task_id, ':', topic, ':', message_key)
        else null
      end
    ) stored;

create unique index uk_task_outbox_in_flight on task_outbox (in_flight_key);
```

唯一索引允许多个 NULL，因此只约束在途行，SENT 与 DEAD_LETTER 之后可以重新入队。

这一步有一个前置条件：H2 必须支持该生成列与唯一索引。实施前先在 H2 上跑一条最小迁移验证。如果不支持，退回应用层去重，不强行上线唯一键。

### 4.4 统一入队

新增 `TaskOutboxEnqueuer`，提供 `enqueue(TaskOutboxMessage)`，内部用 `insert ... select ... where not exists` 做应用层去重，唯一键作为并发兜底。当前 14 处插入分布在 10 个文件，逐处迁移：

| 文件 | 插入数 |
| --- | --- |
| `artifact/ArtifactJobWriteRepository.java` | 1 |
| `artifact/VideoLearningRequestService.java` | 1 |
| `conversation/ConversationSegmentBuildService.java` | 1 |
| `conversation/ConversationTopicSummaryV2Service.java` | 1 |
| `knowledge/WikiIngestService.java` | 2 |
| `memory/MemoryConversationExtractionService.java` | 1 |
| `retrieval/projection/SourceEmbeddingBatchRepository.java` | 2 |
| `source/SourceParseService.java` | 2 |
| `source/SourceReprocessService.java` | 2 |

`SourceEmbeddingBatchRepository:378-406` 已经有一套按 `(task_id, topic, message_key)` 比对载荷的幂等逻辑，作为 Enqueuer 的参照实现。

### 4.5 消费端幂等

现有消费逻辑用 CAS 丢弃重复消息，这一层继续保留。上线前整理一张幂等矩阵：每个 topic 的处理是否天然幂等、是否有 CAS、重复投递的后果。没有 CAS 且不幂等的处理器才考虑加收件箱表，不整体引入。

### 4.6 补偿扫描

新增 `OutboxFinalizeCompensationJob`，每 60 秒扫一次 `finalize_status = 'PENDING'` 且 `updated_at` 早于 5 分钟前的行，重试终态处理，最多 3 次，超过后置为 `FAILED` 并告警。

### 4.7 指标与告警

- `outbox_finalize_total{outcome}`：三态计数。
- `outbox_finalize_compensation_total`：补偿次数。
- `outbox_dead_letter_total`：死信数量。
- `outbox_backlog`：READY 行数，超过阈值告警。

### 4.8 验收

用故障注入覆盖三个时点：认领后崩溃、发送后崩溃、终态处理中崩溃。断言：

- 不出现死信重试循环，`attempt_count` 不再增长。
- 重复投递不产生重复副作用。
- 补偿扫描能把 `PENDING` 清零。

## 六、风险与对策

| 风险 | 对策 |
| --- | --- |
| 模型决策误判，写入错误记忆 | INVALIDATE 必须人工复核；所有决策落库可回放；保留 legacy 开关 |
| 模型不可用导致候选堆积 | 失败落 REVIEW_REQUIRED，候选表就是队列，不丢数据 |
| 删除本地回退后 ES 故障影响面变大 | 熔断加明确降级提示；ES 本来就是唯一检索依赖，回退只在开发环境可用 |
| H2 不支持生成列唯一索引 | 实施前先验证；不支持则只做应用层去重 |
| 删除对比接口后缺少排查手段 | 保留按 run id 查单条快照，加指标与结构化日志 |
| 唯一键与重试冲突 | 只约束 READY 与 PROCESSING，SENT 与 DEAD_LETTER 可为 NULL |
