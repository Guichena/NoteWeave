# 三份文档的核实与修订

日期：2026-10-23。基线 `70631bd0`，集成分支 `codex/oth-20261023`（`a781155b`）。只读核实，不改代码。

核实对象：《Research 改造计划》《非 research 改造与设计审计》《非 research 线架构评估》。核实方式为逐条读代码，不依赖文档自述；所有数字都在 `a781155b` 上重新统计。

## 一、结论

三份文档的方向都成立，不需要推翻：不重写、按能力补接缝、先收敛资格判断再拆大类。但有十处事实性错误和十四处设计判断需要修正，其中五处会直接影响执行：

1. 资格 SQL 单一化的范围写错。33 处状态字面量里只有 26 处是同一段可读快照条件，分布在 chat 三个文件与 infra 一个适配器；source 与 answer 一处都没有。按原文范围施工会白改两个包，还会把状态迁移写入混进只读查询对象。
2. 记忆门控那节的证据句与代码相反。alpha、beta 有持久化、有更新链路，编译侧也在读后验。缺陷是晋升门控读固定先验，不是没有更新。
3. 响应 DTO 膨胀这个判断不成立。155 个 Response 里 153 个字段集合互不相同，完全重复只有一组。收敛成泛型包装的收益接近零，代价是接口契约变模糊。
4. 死信收尾的问题不是事务太长，而是收尾抛异常会让死信状态回滚，消息在租约过期后被反复领取，形成每秒一次的死循环。
5. 上下文那条并行路径的说法不成立。active 读取的就是 shadow 快照表，shadow 是当前存储，能退役的是对比接口，不是表。

### E4 的细节

`index_status = 'INDEXED'` 等值出现 33 处、8 个文件，这个原始计数是对的。但按语义拆开：

- 26 处是同一段当前可读快照条件，分布在 4 个文件：`chat/RetrievalHydrator` 11、`chat/NoteRecallRepository` 9、`infra/JdbcEvidenceOwnershipAdapter` 3、`chat/QaPassageRetriever` 3。写法一致：source 为 READY 且 INDEXED、快照 INDEXED、版本号等于最大的 INDEXED 版本，适配器再加 `projection_status = 'PROJECTED'`。
- 2 处语义不同：`artifact/ArtifactJobReadRepository` 的上游 revision 校验，没有 latest 版本子查询，也没有 projection 条件；同一文件另两处却接受 INDEXED 或 DISABLED。这是一处需要单独决策的不一致。
- 4 处是状态迁移写入：`SourceRetrievalProjectionFinalizer` 2、`RetrievalBackfillSourceFinalizer` 2。
- 1 处是覆盖率统计：`RetrievalBackfillService` 的 ready_source_count。

所以原文说的四个包不成立：source 包只有写迁移，没有读资格；answer 包只有端口与守卫，没有 SQL 条件。真正共享同一段条件的是 chat 三个文件加 infra 一个文件。

同一类重复还有更宽的范围：`projection_status = 'PROJECTED'` 读 7 处、写 2 处；`s.status = 'READY'` 26 处、16 个文件；latest 版本子查询 14 处、9 个文件，其中三处不带 index_status 过滤。这些不应该全部塞进一个查询对象，但要在收敛时统一命名与口径。

### E6 的细节

- 列已存在：`V161__memory_evidence_beta.sql` 增加 `evidence_alpha`、`evidence_beta`。
- 写入链路：`MemoryEvidenceService.assignPrior` 写先验，`observe` 按会话去重后累加 alpha 或 beta，`MemoryApplicationFeedbackService.addBeta` 与 `subtractBeta` 按反馈增减 beta。
- 读取链路：`MemoryCompilerService:305` 用存储的 alpha、beta 调 `MemoryCompilerPolicy.confidence`，直接影响回答编译。
- 门控链路：`MemorySignalService:66` 的 `confidence_score` 等于先验均值，`MemoryCandidateGate:31-34` 的方差也取自固定先验，两处都与存储后验无关。

准确的说法是：后验在编译侧真实生效，在晋升侧不生效。原文把两件事混成了一件。

还有一处隐藏的不一致：`MemoryEvidence.bandOf(sourceType, false)` 的第二个参数写死为 false，隐式对话反馈在门控里会被判成 EXPLICIT。它没有误通过，只是因为 `confidence_score` 存的是 0.5，被均值条件挡住了。一旦有人调整这个分数，隐式反馈就会直接满足两个条件。这一点要单独修。

### E9 的细节

- `ContextV2ShadowSnapshotService` 负责冻结并落库，`ContextV2ShadowDiffService` 只做单 run 引用差异与 cohort 汇总，`ConversationContextCompilerV2Service` 读消息、话题段、摘要、约束、记忆后调 planner。
- 回答链路读取的正是 `context_v2_shadow_snapshot`，冻结发生在编译回答之前。删表会直接打断 active。
- 配置里 `enabled`、`shadow`、`mode` 三个开关默认都是 true/true/ACTIVE，ACTIVE 下 shadowEnabled 仍为 true，所以每次回答都会写快照。这是 active 的存储写入，没有并行写两份。
- 真正的并行物是 diff 与 cohort 两个对比接口，以及 V1 回退码与完整性校验。

所以第三步要做的是给一张命名误导的表正名，再决定对比接口是否保留。原文的说法会让人以为可以直接下线，风险被低估。

### E10 的细节

- RRF 的 k 是 `QaRrfFusionService` 的方法参数，由 `QaRetrievalStrategyProfile` 的常量传入，没有配置项。准确说法是 k 由策略档位决定。

## 三、设计判断的修正

### D1 资格收敛的正确切法

不要做一个大查询对象。26 处共享的是同一段 join 与 where 片段，但 select 列表和驱动表各不相同，查询对象装不下，硬装就要加模式开关，等于把差异藏进参数。

建议：

1. 新增一个中立端口，方法按语义命名而不是按状态值命名，至少三个形状：当前可读快照、冻结快照、资料是否可读。实现放 infra。
2. 端口不能放 chat 或 answer，现有 `ArchitectureBoundaryTest` 已经禁止这两个包依赖 infra。
3. 只覆盖 26 处那一种形状，涉及 chat 三个文件与 infra 一个适配器。产物上游 revision 校验、research 的范围加载、knowledge 的可见性规则各自保留。
4. 产物那两处要先统一口径：`ArtifactJobReadRepository` 的 revision 校验要求 INDEXED，同文件另两处却接受 INDEXED 或 DISABLED。到底冻结快照能不能作为产物上游，需要先定，再谈复用。
5. 写迁移与覆盖率统计留在原处，只把状态字面量换成常量。
6. 加一条架构测试：除端口实现、4 个写入点与 1 处统计外，源码中不得出现 `index_status = 'INDEXED'`。ArchUnit 或一个读源码的单测都可以，成本很低。
7. 不做 SQL 视图。视图只能表达当前可读一种形状，表达不了冻结快照接受 DISABLED，还要新增迁移并保证 H2 与 MySQL 行为一致，收益只是少写 join 文本。

### D2 响应契约：放弃泛型包装

155 个 Response 里 154 个是 record，153 个字段集合互不相同；完全重复只有一组，仅差一个字段的三对。收敛成少数泛型包装只能消掉四处左右，却让 155 个接口丢掉显式字段名与编译期类型，OpenAPI 也会变模糊。

建议：删掉那一组完全重复的类，合并三对近似类，保留其余具体 record。原文第四步可以降级为一次小清理，不再作为独立阶段。

### D3 拆类：先 Video，再 Export，JobService 不拆

- `ArtifactVideoMaterialService` 确实混了 SQL、对象存储、校验、编排，还带 ImageIO 解码与帧文件补偿，最该先拆。建议拆出 BundleRepository、Validator、FrameFileStore、KnowledgePlanService，保留 facade。
- `ArtifactExportService` 次之，可拆 FileStore、ManifestValidator、VersionQuery。
- `ArtifactJobService` 896 行但全类没有 jdbc，只有仓储调用，是编排加读模型装配，属于长而不乱，不建议拆。

拆分的行为风险要写进任务：跨类搬迁后自调用会绕过 `@Transactional` 代理；帧文件先写存储再注册 afterCompletion 补偿的顺序不能变；digest 必须单实例，否则历史 bundle 的 content_digest 会漂移；错误码与状态码是对外契约。

### D4 死信收尾：先提交状态，再执行收尾

原诊断是慢操作拉长持锁时间，实际风险更大：`onDeadLetter` 在 `recordFailure` 的事务内，抛异常会让 DEAD_LETTER 更新回滚。此时 attempt_count 已经在 claim 时加到上限，普通候选查询因 attempt_count 小于上限不再选中它，只有 `deadLetterExpiredExhaustedTaskLeases` 在租约过期后再次改 DEAD_LETTER 并再次调用 `onDeadLetter`，再次回滚，形成每秒一次的死循环，attempt 不再增长，收尾永不提交。

还有一条更隐蔽的路径：内层 `@Transactional` 抛异常会把共享事务标成 rollback-only，外层提交时抛 UnexpectedRollbackException，整批投递受影响。触发条件是任务已处于 COMPLETED 或 CANCELLED 时 `failTask` 走 `handleNoTransition` 抛 transitionException。

建议：

1. 拆两段：短事务提交 DEAD_LETTER，事务外调用 `onDeadLetter`，结果写 `finalize_status` 与 `finalize_error`。
2. 补偿扫描改为扫 DEAD_LETTER 且 finalize_status 为空的记录，收尾本身保持幂等。
3. OTH-11 的三态同样要满足这条不变量：收尾失败不得回滚死信状态。FAILED 分支调 `failTask` 前先判任务终态，避免 transitionException 把外层事务标成 rollback-only。IGNORED 分支不调 `failTask`。

### D5 入队幂等：上提既有实现，不要新写一套

`SourceEmbeddingBatchRepository.enqueue` 已经实现了原文提议的逻辑：按 `(task_id, topic, message_key)` 查 READY 或 PROCESSING 的在途行，逐字段比较载荷，命中就返回。原文说没有业务唯一键、要新增组件，低估了现状。

建议把这段逻辑上提为共享入队组件，插入改成 `insert ... select ... where not exists` 单语句；加唯一索引前先清理历史重复行。

四个点的锁也不一致：上传到解析靠 `document_upload` 行锁，不是 source 或 snapshot 锁；解析、向量、索引三个点持 source 与 source_snapshot。跨路径仍有重复可能：重处理插 parse 消息与上传插 parse 消息同键不同 task_id，会同时存在两行在途消息；重处理插 embed 的键是 snapshotId，初始化插的是 snapshotId:batchNo。两条都靠消费侧 CAS 丢弃，不会重复切片，但会重复投递。这个结论要如实写进验收。

### D6 本地回退改 ngram 与测试库冲突

全部测试用 H2 `MODE=MySQL` 内存库，没有 Testcontainers。MySQL 的 `WITH PARSER ngram` 在 H2 上不可用，H2 的全文实现是另一套 API。选 ngram 就要么给这批用例引入 Testcontainers MySQL，要么接受测试与生产走不同路径。

建议选原文的第二个方案：按资料大小设上限，超过阈值直接返回不可用并给出原因。成本低，也不需要改测试基础设施。如果确实要 ngram，单独开一项，连同测试基础设施一起评估。

### D7 上下文前缀：已可判定，不是需要验证

聊天链路只发两条消息：systemPrompt 与 userPrompt。userPrompt 的顺序是用户问题、结合上文改写的问题、固定回答要求、最近对话上下文、资料片段、chat control；对话上下文内部又是当前问题、主题锚点、已冻结摘要、连续原文窗口、当前有效约束。

也就是说，userPrompt 开头就是本轮问题，后面每一段都会随轮次变化，原文窗口还是从末尾向前数的滑动窗口。可缓存的部分只有 systemPrompt 与固定模板段落。

建议：把固定说明与模板段落并入 systemPrompt，稳定内容放前、易变内容放后；按供应商能力设缓存断点。这条属于成本与延迟优化，不要混进重构阶段。

### D8 记忆门控：改措辞，不改行为

门控的两个输入都由来源类型推出，等价于来源白名单。这个行为本身可能是有意的：只有明确表达才自动晋升。真正的问题是代码用概率语言描述规则，评审追问时说不清。

建议分两步：

1. 第一步只改语义表达：门控改成显式来源策略，把 `prior.variance()` 的比较换成按来源等级的显式判定，并修掉 `bandOf(sourceType, false)` 写死 false 的问题。Beta 保留在证据服务与编译侧，那里是真的。只动门控一到两个文件，不改变任何晋升结果。
2. 第二步可选：门控在存在匹配记忆项时读该项的后验，新候选仍用先验。这会改变晋升行为，需要灰度。

第二步的边界要写清楚，否则会放开不该放开的来源：

- MODEL 不会因此自动晋升，因为效用 0.40 低于 0.60 门槛，最高只能到 0.45。这条担心可以排除。
- 真正风险在 INFERRED：隐式对话反馈与产物反馈效用 0.72，按后验判定时均值 0.7、方差 0.035 左右就能过线，约四五次跨会话支持就够。
- 建议阈值：均值不低于 0.80，alpha 加 beta 不少于 6，至少 3 个不同会话，方差仍按 0.04；MODEL 永不走后验。
- beta 需要时间窗或衰减，否则一次负面反馈会永久压低条目，现有逻辑只在撤销时减 beta。

原文说要把 alpha、beta 持久化，这一步已经完成，不需要新增迁移。

### D9 产物回流记忆缺一个入口，不只是缺映射

现状：`ArtifactMemoryRevisionGuard` 只做 `requireActive`，按 ARTIFACT_JOB_RUN 与 taskId 统计 usage 行，注入的 revision 不是当前 ACTIVE 就抛 409，不写任何记忆信号；`recordArtifactEdit` 没有生产调用方，只有测试在用；V193 收据注释明确编辑不进收据表。

更关键的是没有编辑入口：控制器只有创建、再生成、回滚、另存为资料、写回知识库，没有正文编辑接口。回滚不产生新 task，前后正文相同，即使接上回流也是零变化。

落地还缺三件：需要先新增编辑入口并传入修改前后的正文，版本只存 after，before 要从上一版本 payload 取；usage 行按 ARTIFACT_JOB_RUN 的 taskId 记录，编辑动作需要映射到该 run，可挂的位置是 `logPackUsage` 已经写入的那两处；V193 收据主键是 `(workspace_id, signal_kind, source_ref)`，用 `signal_kind=ARTIFACT_EDIT` 加 `source_ref=artifact-version:<versionId>` 可以做幂等，但现有 EDIT 逻辑靠 sameMagnitude 做替换，收据会把它变成每个版本只记一次，语义需要先确认。另外编辑差异截断在 800 字符，章节粒度会丢。

建议把这项从第四期移出，改成独立评估：先补编辑入口与正文数据，再谈候选映射。

### D10 分期调整

原文第一期把 token 度量与记忆门控放一起，两者风险不同。token 度量替换五处调用点，会改变预算判断与截断行为；门控改措辞不改变行为。建议拆开：先做门控措辞与资格收敛，再做 token 度量，并给 token 度量准备前后对比基线。

### D11 第三步要重新定义

原文写的是收敛到 V2 active、shadow 下线。按 E9 的核实，active 本来就存在 shadow 快照表里，真正可以退役的是 diff 与 cohort 两个对比接口，以及 V1 回退码。

建议改成三步：

1. 正名：把 `context_v2_shadow_snapshot` 及相关服务改成 active 语义的命名，避免后来人误删。
2. 补指标：freeze 成功率、V1 回退率、快照损坏率，连续观察一段时间。
3. 退役对比接口：确认网关日志连续 30 天无调用、前端无引用、合同测试迁移完成，再删 diff 服务与对比接口，保留失败回执与 fallback_code 至少一个发布周期。

删表本身不做，改名或迁表要单独评估。

### D12 Wiki 拆分的边界要改

原文写摄取、链接、索引三段拆开。实际链接写入不在 `WikiIngestService`，而在 `KnowledgeWikiMutationService.upsertWikiLinks`，由 `KnowledgeCommandService` 与 `KnowledgeVersionService` 调用；`WikiIngestService` 里是队列与任务、摄取、概念页清理与指纹、引用与正文、Wiki Index 重建。

建议按后五段拆，不要重复造一个链接模块。图谱与 PPR 的实现是真的，不需要改。

### D13 补一处三份文档都没列的风险

`MemoryIndexOutbox` 的扫描没有 claim 或 lease，直接选 PENDING 行再写向量，只有最后一次 update 带 `status = 'PENDING'` 守卫。多副本部署时两个实例会同时拿到同一批行，重复调用嵌入接口，最终状态不会错，但会产生重复的外部调用与费用。

`MemoryConsolidationService` 的 `synchronized` 只在单 JVM 内有效，游标是内存态，多副本下会重复调用模型判定。

这两处与 3.5 的定时任务互斥是同一类问题，但不在原文列出的 19 个任务里。建议在决定是否多副本部署时一并处理，单副本部署则只在文档里写明约束。

### D14 研究线有两处计划没覆盖的问题

1. 恢复后预算被清零。resume 新建 run 只复制问题、意图与来源，不复制预算与 reservation；预算上限来自新 run 的 discovery_loop limits，消耗按 run 聚合。从 checkpoint 恢复等于重新发一份预算，存在重复消耗与成本失真。建议先定语义：恢复时按剩余预算设上限，报告里体现累计消耗。
2. 多副本协调器没有租约。只靠 tick 内的 research_run 行锁串行化，而且锁在 tick 中段才拿到，规划下发与冲突裁决在锁外执行；每个副本每秒扫描最多 25 个 run。幂等键能防重复建任务，但重复规划与锁等待会放大延迟。建议部署时写死只跑一个 coordinator，或补租约。

另外 R-03 的失败关闭语义要写准：模型不可用不会阻断报告，worker 会退回冻结事实，计数为 0 且 basis 是 FROZEN_FACT；第 87 行拦的是声称语义核验却计数为 0 的伪造记录。
