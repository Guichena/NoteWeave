# 记忆系统重设计（2026-10-23）

这份文档把记忆部分单独拿出来，按最合理的做法重新设计，不受现有代码结构限制。目标有两个：一是回答向量召回到底该不该保留，二是给出一个可以作为简历重点讲述的记忆系统设计。

## 一、先回答：向量召回合理吗

合理，但只能作为多路召回中的一路，不能当成唯一通道。

调研里的证据比较一致：

- LongMemEval 的结论是纯向量检索在多会话推理和知识更新两类任务上很早就饱和，必须引入混合检索。
- GraphRAG-Bench 的消融显示，dense 加 BM25 的混合检索在多数基准上提升 3 到 7 分，多策略召回再提升 5 到 10 分，加 rerank 再提升 2 到 4 分。
- Mem0 用向量 top-10 是因为它服务多租户，单个用户的记忆没有上限；Letta 现在把记忆做成文件系统，Agent 自己浏览，核心记忆根本不走向量。

放到我们的场景里，结论分两层：

写时判断。记忆量按几十条设计，同槽位查询上限 100。这个规模下，精确匹配加全量给模型，比先向量召回再判断更准。向量只在同槽位比不出结果时用来找改写表达，top-5 足够。

读时注入。回答前要把最相关的记忆放进上下文，这时需要混合召回：BM25 加向量，再加时间与重要性，用 RRF 融合。纯向量会漏掉专有名词和精确短语，纯词法会漏掉改写表达。

所以向量通道保留，位置放在写时的兜底和读时的一路，不放在写时判断的主路径。

## 二、目标定位

调研里最新的综述把 Agent 记忆拆成三个轴：形态、功能、动态。动态轴又分形成、演化、检索三个阶段。这个视角比短期记忆与长期记忆的二分更准确，因为短期与长期只是同一套生命周期算子在时间上的不同调用方式。

我们的定位：

- 形态：token 级、可审计、可编辑。个人知识工作场景要求每条记忆都能追溯到来源，参数化与隐式记忆不适合。
- 功能：用户偏好、约束、事实、决策、否定知识。
- 动态：在线写入加后台整理，检索走混合召回。

与几个主流系统的差异：

| 系统 | 写入 | 冲突处理 | 有效性 | 溯源 | 否定知识 |
| --- | --- | --- | --- | --- | --- |
| Mem0 | 模型选 ADD/UPDATE/DELETE/NOOP | 覆盖或删除 | 无 | 弱 | 无 |
| Zep | 图谱抽取加失效 | 双时态标记失效 | 强 | 中 | 无 |
| Letta | Agent 自己编辑文件 | 覆盖 | 弱 | 文件历史 | 无 |
| 本设计 | 模型裁决五动作 | 矛盾保留为信号 | 双时态 | 强 | 有 |

综述明确指出，目前没有系统同时处理置信度、溯源链、条件作用域、否定知识和矛盾保留这五件事。这正是我们可以做出差异的地方。

## 三、五个差异化能力

### 3.1 证据锚定

每条记忆都带一条证据链，指向产生它的原始材料：对话消息、资料片段、产物版本、用户反馈。证据记录引用文本与权重，回答时可以顺着证据链回到原文。

这样做的直接好处是回答可解释。用户问为什么记得这件事，系统能给出具体出处，而不是只给一句模型推断。

### 3.2 双时态有效性

每条 revision 记录两个时间维度：

- 世界时间：这条事实从什么时候成立，到什么时候不再成立，字段是 `valid_from` 与 `valid_until`。
- 系统时间：系统什么时候记录、什么时候修改，字段是 `recorded_at`。

用户换了工作、改了偏好，旧记忆不删除，只把 `valid_until` 写成一个时间点。问历史问题时可以按世界时间取当时有效的版本，问现状时只取当前有效的版本。Zep 用双时态图谱做这件事，我们用版本表做，成本低很多。

### 3.3 校准置信

现有代码里已经有 `evidence_alpha` 与 `evidence_beta`，也在真实更新，只是晋升时没用。重设计把它们变成真正的校准置信：

- 先验按来源类型设定，用户显式表达用强先验，模型推断用弱先验。
- 每次独立证据加一，来源去重，同一会话不重复计数。
- 置信值参与读取排序与回答措辞，低置信记忆在回答里标注不确定。

置信不直接决定是否晋升。晋升由模型裁决，置信只作为裁决输入和展示信号。这样既保留了可解释性，也避免把概率阈值当成语义判断。

### 3.4 否定知识

用户说以后不要用某种格式、某类资料不可信，这类信息现在是负向信号，但没有一等公民的地位。重设计把否定知识做成独立类型：

- `polarity` 取 POSITIVE 或 NEGATIVE。
- 否定记忆与肯定记忆走同一套槽位与冲突判断。
- 回答时否定记忆作为约束注入，优先级高于普通偏好。

### 3.5 矛盾即信号

多数系统遇到矛盾就覆盖或删除。重设计保留双方，新增 `memory_conflict` 记录：

- `kind` 取 CONTRADICT、CONDITIONAL、DUPLICATE。
- 状态取 OPEN、RESOLVED、ACCEPTED。
- 解决方式有三种：时间上新的覆盖旧的、条件上双方各在自己的作用域成立、人工裁定。

矛盾保留下来之后，可以做两件事：回答时提示存在冲突，让用户确认；后台整理时统计冲突率，作为记忆质量的指标。

## 四、数据模型

在现有表基础上扩展，不推倒重来。

```text
memory_item            当前视图：作用域、槽位、极性、状态、置信、矛盾组
memory_revision        版本：valid_from、valid_until、recorded_at、文本、向量、哈希
memory_evidence        证据：来源类型、来源 id、引用文本、权重
memory_conflict        矛盾：左右条目、类型、状态、解决方式、检测者
memory_event           审计：追加写，记录每次动作
memory_candidate       候选：抽取结果、模型裁决、复核状态
```

关键列：

```sql
alter table memory_runtime_revision
  add column valid_from timestamp null,
  add column recorded_at timestamp not null default current_timestamp,
  add column condition_json json null;

alter table memory_item
  add column contradiction_group_id varchar(64) null,
  add column confidence_alpha decimal(8,3) not null default 1.0,
  add column confidence_beta decimal(8,3) not null default 1.0;

create table memory_conflict (
  id varchar(64) primary key,
  workspace_id varchar(64) not null,
  left_item_id varchar(64) not null,
  right_item_id varchar(64) not null,
  kind varchar(16) not null,
  status varchar(16) not null,
  resolution varchar(32) null,
  detected_by varchar(32) not null,
  created_at timestamp not null,
  resolved_at timestamp null
);
```

`condition_json` 存条件作用域，例如只在某个项目、某类任务下成立。这是综述里点名缺失的能力，实现成本不高。

## 五、写入链路

```text
抽取候选
  -> 规范化（去重、槽位补全、极性识别）
  -> 精确匹配（文本哈希、同槽位同值）
  -> 混合候选（同槽位 peers 上限 100、向量 top-5、BM25 top-5）
  -> 模型裁决（ADD / MERGE / SUPERSEDE / CONTRADICT / NOOP）
  -> 策略判定（自动生效或人工复核）
  -> 写事件、写 revision、写证据
```

裁决输出：

```json
{
  "action": "CONTRADICT",
  "target_id": "m-123",
  "reason": "新偏好与已有偏好在同一槽位上取值相反",
  "confidence": 0.81
}
```

动作语义：

| 动作 | 写入 | 生效 |
| --- | --- | --- |
| ADD | 新建条目与首版 revision | 用户显式表达且置信达标时自动生效 |
| MERGE | 目标条目新增 revision，旧版写 valid_until | 同上 |
| SUPERSEDE | 目标条目置为 INVALIDATED，新建条目承接 | 一律人工复核 |
| CONTRADICT | 双方保留，新建矛盾记录，条目标记 contested | 一律人工复核 |
| NOOP | 候选关闭 | 直接结束 |

幂等：候选 id 是幂等键，裁决结果落库后不再重算；同一批证据重放不会产生第二条记忆。

## 六、整理链路

整理放在后台，按 workspace 逐个执行，参考 LightMem 的两阶段思路：在线只做条目级写入，集群级合并与摘要放到空闲时间。

每轮做五件事：

1. 合并重复：同槽位、同值、文本相似度高的条目合并，保留最早的世界时间。
2. 摘要聚类：同一主题下条目过多时生成一条摘要记忆，原条目保留并链接到摘要。
3. 置信衰减：长时间没有被引用或强化的记忆，按半衰期降低 alpha，但不低于先验。
4. 矛盾巡检：同一槽位取值相反的条目生成矛盾记录，交给复核队列。
5. 失效清理：`valid_until` 已过且没有引用的条目转为 INVALIDATED，不删除。

护栏：单轮改动数量设上限，改动写审计事件，整理前后生成差异报告，任何删除都不执行。

## 七、读取链路

```text
问题改写
  -> 混合召回（BM25、向量、时间、重要性）
  -> RRF 融合
  -> rerank
  -> 预算裁剪
  -> 带 id、置信、有效时间的记忆块
  -> 回答并引用记忆 id
```

注入格式建议：

```text
[记忆 m-123 | 偏好 | 置信 0.86 | 2026-09 至今]
用户偏好简洁回答，不需要背景铺垫。
```

回答要求引用记忆 id，前端可以点击回到证据链。读取预算按 token 控制，默认 800 token，按分数截断。

## 八、评测

自建评测集，300 条，覆盖六类任务：

| 类型 | 例子 | 指标 |
| --- | --- | --- |
| 单跳 | 用户偏好什么格式 | recall@5、引用正确率 |
| 多跳 | 结合两条偏好推断 | recall@5、答案正确率 |
| 时间 | 上个月用户偏好什么 | 时间过滤准确率 |
| 更新 | 用户改了偏好后以哪个为准 | 更新精确率、陈旧率 |
| 矛盾 | 两条记忆冲突时怎么回答 | 冲突识别率 |
| 否定 | 用户明确不要什么 | 约束遵守率 |

基线四条：无记忆、全上下文、纯向量、Mem0 式写入。

指标：裁决一致率、更新精确率、陈旧率、召回率、引用正确率、token 成本、p95 延迟。

评测跑在固定夹具上，默认不调用付费模型；需要真实模型时单独开关。

## 九、实施阶段

| 阶段 | 内容 | 工作量 |
| --- | --- | --- |
| 一 | 证据表、双时态列、裁决五动作、评测集骨架 | 2 周 |
| 二 | 矛盾记录、否定知识、后台整理 | 2 周 |
| 三 | 混合召回、rerank、记忆感知回答与前端 | 1 周 |

第一阶段做完就能演示：写入有裁决，记忆有出处，回答能引用。第二阶段做出差异：矛盾保留、否定知识、后台整理。第三阶段补齐读取质量。

## 十、简历怎么写

可以按四条写，数字等做完评测再填：

- 设计并实现证据锚定、双时态的个人知识记忆层，支持偏好、约束、事实、否定知识四类记忆，每条记忆可追溯到原始对话或资料。
- 引入模型裁决写入，覆盖新增、合并、替换、矛盾、忽略五种动作，配合幂等键与审计事件，重放不产生重复记忆。
- 实现两阶段整理，在线条目级写入加后台集群级合并与衰减，降低上下文 token 占用并抑制陈旧记忆。
- 自建 300 条六类任务评测集，对比无记忆、全上下文、纯向量与 Mem0 式写入四种基线，量化召回率、更新精确率与陈旧率。

技术难点可以讲四件事：并发写入的幂等与顺序、双时态查询、矛盾检测的准确率、token 预算下的召回取舍。这四点都比单纯说用了向量库更能体现设计能力。
