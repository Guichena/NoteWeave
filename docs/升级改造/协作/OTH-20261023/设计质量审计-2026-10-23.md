# 设计质量审计：五项能力的真实实现与不合理设计

日期：2026-10-23。基线 `70631bd0`，审计对象为集成分支 `codex/oth-20261023`（`9a98fef3`）。只读审计，不改代码。

## 0. 结论

核心算法多数是真实现，不是空壳。真正不合理的地方集中在四处：度量口径、门控语义、本地降级实现、定时调度。这四处恰好都落在简历最容易被追问的位置上。

## 1. 已核实为真实现的部分

先把结论说清楚，避免把真实现当成假的去重写。

## 2. 不合理设计

### 2.1 Java 侧 token 度量是字符估算，没有供应商用量

`ContextTokenEstimator:15-29` 按中文每字 1 个 token、其余 4 个字符 1 个 token 估算。它被上下文预算、QA 证据预算、记忆编译、切片器共同使用（`ContextWindowPlannerV2:173-175`、`QaHybridRetriever:184`、`MemoryCompilerPolicy:139-144`、`DocumentChunker:774`）。

`HttpChatLlmClient` 不解析响应里的 `usage` 字段，全仓 Java 侧没有 `prompt_tokens` 或 `completion_tokens` 的读取。

后果：简历里输入 token 降低 34% 这类结论，如果按系统内数据统计，用的是字符估算，不同模型分词器差异可以达到两到三倍，数字站不住。对比之下，Python worker 的做法是正确的：`research-worker/app/llm_client.py:330-354` 记录真实用量，并且用 `tokens_reported` 标明这次是不是供应商上报的。

业界做法：用目标模型的真实分词器（OpenAI 兼容系可用 jtokkit 的 o200k 或 cl100k），或者直接读响应里的 `usage`，并像 worker 一样记录是否上报。

### 2.2 记忆门控的贝叶斯是装饰

`MemoryEvidence:59-65` 的先验是固定值：EXPLICIT 为 Beta(4,1)，INFERRED 为 Beta(1.5,1.5)，MODEL 为 Beta(1,2)。方差分别是 0.027、0.063、0.056。

`MemoryCandidateGate:31-41` 用 `prior.variance() <= maximumPosteriorVariance` 判断，而阈值默认 0.04（`MemoryCandidatePolicy:26`）。这三个先验里只有 EXPLICIT 的方差小于 0.04。也就是说，这个检查等价于只放行 EXPLICIT 来源，与贝叶斯更新无关，因为没有任何地方用反馈去更新 alpha 和 beta。

同一段代码里还有一处重复判断：`confidenceForSource` 返回先验均值，EXPLICIT 是 0.8、INFERRED 是 0.5、MODEL 是 0.33，再与 0.70 比较，得到的仍是同一个白名单。

其余数值同样是硬编码：来源效用 0.90、0.72、0.40，类别风险 0.28、0.18、0.14、0.12，相似度阈值 0.85 直接写在 `equivalentStatementSimilarity` 里。

后果：代码用概率语言描述，实际是规则表。评审追问先验怎么来的、反馈如何改变后验时，答不上来。

业界做法二选一：要么改成规则引擎的写法，按来源等级显式判定，删掉 Beta 与 posterior 的措辞；要么做真更新，把每个记忆条目的 alpha、beta 计数持久化，晋升与拒绝各更新一次，方差随证据量下降。

### 2.3 本地回退用 LIKE 做全表扫描

`NoteRecallRepository:398-418` 的本地回退预筛是 `lower(title) like ?`、`lower(content) like ?` 这类子串匹配，词项来自 `likePatterns`（`362`）。中文按二元组切分，一个查询会生成多个 LIKE 子句。

问题有三层：前缀通配导致无法使用索引；子串匹配会把无关词命中；二元组让子句数量随查询长度增长。资料达到 128 MB 时，这条路径不可用。

业界做法：用 MySQL FULLTEXT 的 ngram 解析器（`ngram_token_size=2`）建全文索引，或者在回退前按资料大小设上限，超过阈值直接返回不可用并给出明确原因。当前实现既不快也不准。

### 2.4 模型重排会静默丢弃候选

`FallbackRerankClient:29-30` 限制候选 40 条、每条 320 字。`llmRerank:80-96` 只对前 40 条打分，后面的候选既不参与排序也不报错，直接从结果里消失。

打分是 0 到 10 的整数，`parseScores:105-122` 归一到 0 到 1，只有 11 个取值。候选多时大量并列，排序退化为原顺序。

另外 `llm-fallback-enabled` 默认是 true（`46`），没有配置专用重排服务时，每次检索都会多一次模型调用，成本和延迟都落在主链路上。

业界做法：上游显式截断并记录被丢弃数量；用浮点分数或直接让模型输出排序序列；回退开关默认关闭，按环境显式打开。

### 2.5 十九个定时任务没有分布式互斥

全仓 19 处 `@Scheduled`，没有 ShedLock 或数据库层面的任务锁（全仓检索不到相关实现）。单副本部署时没问题，一旦扩容到两个后端实例，扫描、重建、晋升类任务会在每个实例上各跑一遍。

部分任务靠 CAS 保证幂等，例如研究协调器的推进；但不是所有任务都有这个保护，需要逐个确认。

业界做法：引入 ShedLock 的 JDBC provider，或者每个任务用 MySQL 的 `GET_LOCK` 包一层；如果确定长期单副本，就在部署文档里写死这个约束，不要留下隐含假设。

### 2.6 检索预算硬编码

`NoteReadingRetriever:85-93` 里每个资料固定 4 个窗口，候选上限 24，重排上限 8。这些数值散落在方法体里，没有进入策略配置。

后果：不同资料类型（论文、会议记录、视频转写）需要不同的窗口数和预算，现在只能改代码。

业界做法：把窗口数、候选数、重排数放进按资料类型区分的策略配置，与已有的 `NoteRetrievalStrategyProfile` 放在一起。

### 2.7 投递收尾在数据库事务内做业务收尾

`DurableOutboxDispatcher:413-425` 把死信状态更新和 `deadLetterHandler.onDeadLetter` 放在同一个事务里。业务收尾如果包含较慢的写操作，会拉长持有连接的时间。

这个设计本身是为了保证死信与业务收尾原子，方向没错，问题在于没有给收尾工作设边界。

业界做法：保持同事务，但给收尾逻辑设定明确的短事务边界，或者改成事务提交后通过事务同步回调触发，并对回调失败做补偿记录。

### 2.8 命名与语义不符

`ResearchVerifierGatedSummaryAssembler:107-113` 的判定是 `row_status != VERIFIED`，它统计的是读模型里的受阻行数量，不参与任何校验决策。真正的校验在 `ResearchStatementSupportValidation` 与 `research_verifier_decision`、`research_semantic_check` 表里。

这不是缺陷，但名字会让评审误以为这里是验证器。建议改名为受阻行统计之类的描述性名称。

## 3. 改造优先级

| 优先级 | 问题 | 影响 |
|---|---|---|
| 高 | 2.1 token 度量 | 直接影响简历数字的可信度 |
| 高 | 2.2 门控语义 | 评审最容易追问，且改动集中在三个类 |
| 中 | 2.3 本地回退 | 大文件场景不可用，但生产默认关闭 |
| 中 | 2.4 重排截断 | 候选多时排序质量下降，且成本不可控 |
| 中 | 2.5 定时任务互斥 | 扩容后才会暴露，当前单副本无影响 |
| 低 | 2.6 预算硬编码 | 影响可调性，不影响正确性 |
| 低 | 2.7 收尾事务边界 | 影响连接占用，不影响正确性 |
| 低 | 2.8 命名 | 只影响可读性 |
