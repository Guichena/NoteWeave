# 非 research 改造与设计审计

日期：2026-10-23。基线 `70631bd0`，集成分支 `codex/oth-20261023`（`d8ced2b5`）。本文件覆盖 QA、Note、Wiki、异步流水线、产物框架、Context 与 Memory，以及横切问题。Deep Research 相关内容见《Research 改造计划》，两份分开维护。

## 一、结论

四项能力在代码里都已落地，不需要从零建设。改造分三块：

1. 补两处模块接缝：产物编辑回流记忆、出队幂等。
2. 修七处设计不合理：token 度量、记忆门控语义、本地回退实现、重排截断、定时任务互斥、预算硬编码、收尾事务边界。
3. 留一套可复跑验收，替代全矩阵浏览器测试。

与业界对照的结果：检索栈基本对齐主流做法，差距集中在度量口径、门控语义、降级实现和调度这四处。

## 三、不合理设计与业界做法

### 3.1 Java 侧 token 度量是字符估算，没有供应商用量

现象：`ContextTokenEstimator:15-29` 按中文每字 1 个 token、其余 4 个字符 1 个 token 估算。它被上下文预算、QA 证据预算、记忆编译、切片器共同使用（`ContextWindowPlannerV2:173-175`、`QaHybridRetriever:184`、`MemoryCompilerPolicy:139-144`、`DocumentChunker:774`）。`HttpChatLlmClient` 不解析响应里的 `usage`，Java 侧没有读取 `prompt_tokens`。

为什么不对：不同模型的分词器对中文和代码的切分差异可以达到两到三倍。用它统计出来的 token 降幅，评审一问口径就站不住。

业界做法：用目标模型的分词器（OpenAI 系可用 [tiktoken](https://github.com/openai/tiktoken) 的对应编码，Java 可用 jtokkit），或者直接读响应里的 `usage` 字段。Python worker 已经做对了：`research-worker/app/llm_client.py:330-354` 记录真实用量，并用 `tokens_reported` 标明这次是否由供应商上报。

改造方向：Java 侧统一接一个 token 计数接口，优先用供应商 `usage`，缺失时用分词器，并在数据里记录来源。历史数据的口径要标注清楚，不要混算。

### 3.2 记忆门控的贝叶斯是装饰

现象：`MemoryEvidence:59-65` 的先验是固定值，EXPLICIT 为 Beta(4,1)，方差 0.027；INFERRED 为 Beta(1.5,1.5)，方差 0.063；MODEL 为 Beta(1,2)，方差 0.056。`MemoryCandidateGate:31-41` 用 `prior.variance() <= 0.04` 判断，三个先验里只有 EXPLICIT 通过。`MemoryCandidatePolicy:18` 的默认阈值 0.04 让这个检查等价于来源白名单。同一段逻辑里 `confidenceForSource` 再用先验均值与 0.70 比较，结果相同。来源效用 0.90、0.72、0.40，类别风险 0.28、0.18、0.14，相似度 0.85，全部硬编码。

为什么不对：代码用概率语言描述，实际是规则表，而且没有任何地方用反馈更新 alpha 和 beta。评审追问先验来源、后验如何变化时无法回答。

业界做法：Mem0 在抽取之后做一次模型决策，对相似记忆选择 ADD、UPDATE、DELETE 或 NOOP（[mem0ai/mem0](https://github.com/mem0ai/mem0)）。Zep 用双时态知识图谱，新事实写入时把旧事实标记为失效，保留历史（[Zep 论文](https://arxiv.org/abs/2501.13956)）。两者的共同点是：冲突由模型或时态规则处理，不靠固定阈值。

改造方向二选一：要么承认它是规则引擎，按来源等级显式判定，删掉 Beta 与 posterior 的措辞；要么做真更新，把每条记忆的 alpha、beta 计数持久化，晋升与拒绝各更新一次，方差随证据量下降。

### 3.3 本地回退用 LIKE 做全表扫描

现象：`NoteRecallRepository:398-418` 的本地回退预筛是 `lower(title) like ?`、`lower(content) like ?` 这类子串匹配，词项来自 `likePatterns`（`362`）。中文按二元组切分，一个查询生成多个 LIKE 子句。

为什么不对：前缀通配用不了索引；子串匹配会误命中；子句数量随查询长度增长。资料到 128 MB 时这条路径不可用。

业界做法：MySQL 提供 ngram 全文解析器，专门处理中日韩，默认二元组，建索引时用 `WITH PARSER ngram`，布尔模式支持短语查询（[MySQL ngram 文档](https://dev.mysql.com/doc/refman/8.0/en/fulltext-search-ngram.html)）。

改造方向：用 ngram 全文索引替代 LIKE；或者在回退前按资料大小设上限，超过阈值直接返回不可用并给出明确原因。

### 3.4 模型重排会静默丢弃候选

现象：`FallbackRerankClient:29-30` 限制候选 40 条、每条 320 字。`llmRerank:80-96` 只对前 40 条打分，后面的候选既不参与排序也不报错，直接从结果里消失。打分是 0 到 10 的整数，只有 11 个取值，候选多时大量并列，排序退化为原顺序。`llm-fallback-enabled` 默认 true（`46`），没配专用重排服务时每次检索都多一次模型调用。

为什么不对：静默丢弃让召回率随候选数量波动而无人察觉；整数打分让重排在大候选集上接近无效；默认开启让成本和延迟不可控。

业界做法：重排接口对单次文档数有上限，调用方需要分批并对超出部分显式处理，返回的分数是浮点相关度（[Cohere Rerank 文档](https://docs.cohere.com/v1/reference/rerank)）。

改造方向：上游显式截断并记录被丢弃数量；用浮点分数或让模型输出排序序列；回退开关默认关闭，按环境显式打开。

### 3.5 十九个定时任务没有分布式互斥

现象：全仓 19 处 `@Scheduled`，找不到 ShedLock 或数据库任务锁。单副本没问题，扩容到两个实例后扫描、重建、晋升类任务会各跑一遍。

为什么不对：部分任务靠 CAS 幂等，但不是全部；没有统一约束，扩容时是否安全取决于逐个任务的人工判断。

业界做法：ShedLock 用一张锁表加 `@SchedulerLock` 注解，保证同一任务同一时刻只在一个实例执行（[ShedLock](https://github.com/lukas-krecan/ShedLock)）。

改造方向：引入 ShedLock 的 JDBC provider，或者每个任务用 MySQL `GET_LOCK` 包一层；如果确定长期单副本，就在部署文档里写死这个约束。

### 3.6 检索预算硬编码

现象：`NoteReadingRetriever:85-93` 里每个资料固定 4 个窗口，候选上限 24，重排上限 8，散落在方法体里。

为什么不对：论文、会议记录、视频转写需要不同的窗口数和预算，现在只能改代码。

业界做法：检索参数按查询类型或资料类型配置化，这也是 Elasticsearch 把 `rank_window_size`、`size` 做成请求参数的原因。

改造方向：把窗口数、候选数、重排数放进按资料类型区分的策略配置，与已有的 `NoteRetrievalStrategyProfile` 放在一起。

### 3.7 投递收尾在数据库事务内做业务收尾

现象：`DurableOutboxDispatcher:413-425` 把死信状态更新和 `deadLetterHandler.onDeadLetter` 放在同一个事务里。

为什么不对：方向是为了死信与业务收尾原子，但没给收尾工作设边界，慢操作会拉长持有连接的时间。

业界做法：事务性发件箱模式要求状态更新与消息记录同事务，业务副作用放在提交之后，用补偿记录兜底（[transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)）。

改造方向：保持同事务，但给收尾逻辑设明确的短事务边界；或者改成提交后通过事务同步回调触发，并对回调失败做补偿记录。

## 五、改造设计

### 5.1 出队幂等收口（能力三）

现状：14 处直接插入 `task_outbox`，没有业务唯一键；单行投递 token 只保证至少一次投递。

设计：新增 `TaskOutboxEnqueuer`，在调用方事务内按 `(task_id, topic, message_key)` 查 READY 或 PROCESSING 的在途行；相同载荷返回既有行 id，不同载荷抛冲突，不存在则插入。只改造已经持有 source 或 snapshot 行锁的四个点：上传到解析、解析到切片、切片到向量、向量到索引。并发安全依赖既有行锁，不新增迁移。其余 10 处记为未覆盖。

验收：同键两个事务只产生一行；同键不同载荷被拒绝；SENT 与 DEAD_LETTER 之后允许重新入队。

### 5.2 产物编辑回流记忆（能力四与能力五的接缝）

现状：`ArtifactMemoryRevisionGuard` 只校验产物引用的记忆版本仍有效，产物编辑本身不产生记忆信号。

设计：产物版本保存或回滚时，把编辑差异映射为记忆候选，不直接晋升；`source_ref` 用产物版本 id，复用 V193 收据保证一次编辑只处理一次；是否晋升交给候选门控。

验收：编辑一次只产生一条候选；重复保存不重复；回滚产生反向候选；候选未晋升前不影响回答。

### 5.3 Note/Wiki 契约失败定性（能力二）

现状：11 个 `Phase3NoteWikiContractTest` 在基线就失败，断言期望回答里出现 `source-window-missing` 等标记，实际没有。标记本身仍在 `NoteRecallRetriever:422` 生成。

设计：先定性。若是渲染链路丢了标记，修 Note 答案装配与提示词渲染；若是测试固化了已废弃的文案，改断言并写明原因。不允许直接删断言。

验收：11 个用例转绿，或逐条给出原因与替代断言。

### 5.4 token 度量与记忆门控（新增）

设计见 3.1 与 3.2。范围：新增 token 计数接口与调用点替换、记忆策略语义调整、策略版本持久化。

验收：同一段文本用分词器与供应商 `usage` 的偏差在可接受范围内；门控决策在文档里能用一句话解释清楚，不再依赖 Beta 措辞。
