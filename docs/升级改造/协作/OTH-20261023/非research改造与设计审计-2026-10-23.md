# 非 research 改造与设计审计

日期：2026-10-23。基线 `70631bd0`，集成分支 `codex/oth-20261023`（`d8ced2b5`）。本文件覆盖 QA、Note、Wiki、异步流水线、产物框架、Context 与 Memory，以及横切问题。Deep Research 相关内容见《Research 改造计划》，两份分开维护。

核实与修订见《核实与修订-2026-10-23.md》。本文件已按核实结果修正 3.1 至 3.7、5.1 与 5.2，未展开的细节以该文件为准。

## 一、结论

四项能力在代码里都已落地，不需要从零建设。改造分三块：

1. 补两处模块接缝：产物编辑回流记忆、出队幂等。
2. 修七处设计不合理：token 度量、记忆门控语义、本地回退实现、重排截断、定时任务互斥、预算硬编码、收尾事务边界。
3. 留一套可复跑验收，替代全矩阵浏览器测试。

与业界对照的结果：检索栈基本对齐主流做法，差距集中在度量口径、门控语义、降级实现和调度这四处。

## 三、不合理设计与业界做法

### 3.1 Java 侧 token 度量是字符估算，没有供应商用量

现象：`ContextTokenEstimator:15-29` 按中文每字 1 个 token、其余 4 个字符 1 个 token 估算。它被上下文预算、QA 证据预算、记忆编译、切片器共同使用，共五处：`ContextWindowPlannerV2:175`、`QaHybridRetriever:184` 与 `218`、`MemoryCompilerPolicy:144`、`DocumentChunker:774`。`HttpChatLlmClient` 走流式请求，没有设置 `stream_options.include_usage`，也不解析响应里的 `usage`，Java 侧拿不到 `prompt_tokens`。

为什么不对：不同模型的分词器对中文和代码的切分差异可以达到两到三倍。用它统计出来的 token 降幅，评审一问口径就站不住。

业界做法：用目标模型的分词器（OpenAI 系可用 [tiktoken](https://github.com/openai/tiktoken) 的对应编码，Java 可用 jtokkit），或者直接读响应里的 `usage` 字段。Python worker 已经做对了：`research-worker/app/llm_client.py:330-354` 记录真实用量，并用 `tokens_reported` 标明这次是否由供应商上报。

改造方向：Java 侧统一接一个 token 计数接口，优先用供应商 `usage`，缺失时用分词器，并在数据里记录来源。历史数据的口径要标注清楚，不要混算。

### 3.2 记忆门控用概率语言描述规则表

现象：`MemoryEvidence:59-65` 的先验是固定值，EXPLICIT 为 Beta(4,1)，方差 0.027；INFERRED 为 Beta(1.5,1.5)，方差 0.063；MODEL 为 Beta(1,2)，方差 0.056。`MemoryCandidateGate:31-41` 用 `prior.variance() <= 0.04` 判断，三个先验里只有 EXPLICIT 通过。`MemoryCandidatePolicy:18` 的默认阈值 0.04 让这个检查等价于来源白名单。同一段逻辑里 `confidenceForSource` 再用先验均值与 0.70 比较，结果相同。来源效用 0.90、0.72、0.40，类别风险 0.28、0.18、0.14，相似度 0.85，全部硬编码。

为什么不对：代码用概率语言描述，实际是规则表，因为门控的两个输入都由来源类型推出。但要说清楚：alpha 与 beta 已经持久化（V161），`MemoryEvidenceService.observe` 按跨会话权重更新，`MemoryApplicationFeedbackService` 的 `addBeta` 与 `subtractBeta` 按反馈增减，`MemoryCompilerService` 用存储值计算置信度并参与编译。缺陷在晋升门控读不到这些后验。

另外 `MemoryEvidence.bandOf(sourceType, false)` 的第二个参数写死为 false，隐式对话反馈在门控里会被判成 EXPLICIT，只因 `confidence_score` 存的是 0.5 才没误通过。这一点要单独修。

业界做法：Mem0 在抽取之后做一次模型决策，对相似记忆选择 ADD、UPDATE、DELETE 或 NOOP（[mem0ai/mem0](https://github.com/mem0ai/mem0)）。Zep 用双时态知识图谱，新事实写入时把旧事实标记为失效，保留历史（[Zep 论文](https://arxiv.org/abs/2501.13956)）。两者的共同点是：冲突由模型或时态规则处理，不靠固定阈值。

改造方向分两步。第一步只改语义表达，门控改成显式来源策略，把 `prior.variance()` 的比较换成按来源等级的显式判定，并修掉 `bandOf` 写死 false 的问题，Beta 保留在证据与编译侧。第二步可选：门控在存在匹配记忆项时读该项后验，新候选仍用先验；需要灰度，阈值建议均值不低于 0.80、alpha 加 beta 不少于 6、至少 3 个不同会话、方差仍按 0.04，MODEL 永不走后验，beta 要加时间窗或衰减。持久化不需要新增迁移。

### 3.3 本地回退用 LIKE 做全表扫描

现象：`NoteRecallRepository:398-418` 的本地回退预筛是 `lower(title) like ?`、`lower(content) like ?` 这类子串匹配，词项来自 `likePatterns`（`362`）。中文按二元组切分，一个查询生成多个 LIKE 子句。

为什么不对：前缀通配用不了索引；子串匹配会误命中；子句数量随查询长度增长。资料到 128 MB 时这条路径不可用。

业界做法：MySQL 提供 ngram 全文解析器，专门处理中日韩，默认二元组，建索引时用 `WITH PARSER ngram`，布尔模式支持短语查询（[MySQL ngram 文档](https://dev.mysql.com/doc/refman/8.0/en/fulltext-search-ngram.html)）。

改造方向：用 ngram 全文索引替代 LIKE；或者在回退前按资料大小设上限，超过阈值直接返回不可用并给出明确原因。

约束：全部测试跑在 H2 `MODE=MySQL` 内存库上，没有 Testcontainers。MySQL 的 `WITH PARSER ngram` 在 H2 上没有对应语法，H2 的全文实现是另一套 API。选 ngram 就要给这批用例引入 Testcontainers MySQL，或者接受测试与生产走不同路径。建议选第二个方向，按大小设上限；如果确实要 ngram，单独开一项，连同测试基础设施一起评估。

### 3.4 模型重排会静默丢弃候选

现象：`FallbackRerankClient:29-30` 限制候选 40 条、每条 320 字。`llmRerank:80-96` 只对前 40 条打分，后面的候选既不参与排序也不报错，直接从结果里消失。打分只做 0 到 10 的截断，不校验整数，浮点也会被接受，候选多时大量并列，排序退化为原顺序。`llm-fallback-enabled` 默认 true（`46`），没配专用重排服务时每次检索都多一次模型调用。

为什么不对：静默丢弃让召回率随候选数量波动而无人察觉；打分区间窄让重排在大候选集上接近无效；默认开启让成本和延迟不可控。

业界做法：重排接口对单次文档数有上限，调用方需要分批并对超出部分显式处理，返回的分数是浮点相关度（[Cohere Rerank 文档](https://docs.cohere.com/v1/reference/rerank)）。

改造方向：上游显式截断并记录被丢弃数量；用浮点分数或让模型输出排序序列；回退开关默认关闭，按环境显式打开。

### 3.5 定时任务没有分布式互斥

现象：全仓 21 处 `@Scheduled`，分布在 19 个类，找不到 ShedLock 或数据库任务锁。单副本没问题，扩容到两个实例后扫描、重建、晋升类任务会各跑一遍。

为什么不对：部分任务靠 CAS 幂等，但不是全部；没有统一约束，扩容时是否安全取决于逐个任务的人工判断。

业界做法：ShedLock 用一张锁表加 `@SchedulerLock` 注解，保证同一任务同一时刻只在一个实例执行（[ShedLock](https://github.com/lukas-krecan/ShedLock)）。

改造方向：引入 ShedLock 的 JDBC provider，或者每个任务用 MySQL `GET_LOCK` 包一层；如果确定长期单副本，就在部署文档里写死这个约束。

### 3.6 检索预算硬编码

现象：`NoteReadingRetriever:97-103` 里每个资料固定 4 个窗口，候选上限 24，重排上限 8，散落在方法体里。没有按资料类型区分的策略类，`NoteRetrievalStrategyProfile` 是全局单档，按回答模式分档的是 `NoteAnswerModeStrategy` 这一层。

为什么不对：论文、会议记录、视频转写需要不同的窗口数和预算，现在只能改代码。

业界做法：检索参数按查询类型或资料类型配置化，这也是 Elasticsearch 把 `rank_window_size`、`size` 做成请求参数的原因。

改造方向：把窗口数、候选数、重排数放进按资料类型区分的策略配置，与已有的 `NoteRetrievalStrategyProfile` 放在一起。

### 3.7 投递收尾在数据库事务内做业务收尾

现象：`DurableOutboxDispatcher:413-425` 把死信状态更新和 `deadLetterHandler.onDeadLetter` 放在同一个事务里。

为什么不对：收尾抛异常会让死信状态更新一起回滚。claim 时 attempt_count 已经加到上限，普通候选查询不再选中它；租约过期后死信扫描再次改 DEAD_LETTER、再次调用收尾，再次回滚，形成每秒一次的死循环，收尾永不提交。内层 `@Transactional` 抛异常还会把共享事务标成 rollback-only，外层提交抛 UnexpectedRollbackException，影响整批投递。触发条件是任务已处于 COMPLETED 或 CANCELLED 时 `failTask` 走 `handleNoTransition` 抛 transitionException。

业界做法：死信是投递层事实，收尾属于消费侧补偿，两者不应同事务（[Dead Letter Channel](https://www.enterpriseintegrationpatterns.com/patterns/messaging/DeadLetterChannel.html)、[transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)）。

改造方向：拆两段。短事务先提交 DEAD_LETTER，事务外调用收尾，结果写 `finalize_status` 与 `finalize_error`；补偿扫描改为扫 DEAD_LETTER 且 finalize_status 为空的记录。OTH-11 的三态同样要满足这条不变量：收尾失败不得回滚死信状态。

## 五、改造设计

### 5.1 出队幂等收口（能力三）

现状：14 处直接插入 `task_outbox`。`SourceEmbeddingBatchRepository.enqueue` 已经实现按 `(task_id, topic, message_key)` 查 READY 或 PROCESSING 在途行并逐字段比较载荷，命中就返回，未命中才插入；其余 13 处没有这层逻辑。这段实现只覆盖 embed 主题，先查后插，没有唯一约束，并发事务仍可能各插一行。

设计：把这段比对逻辑上提为 `TaskOutboxEnqueuer`，插入改成 `insert ... select ... where not exists` 单语句，在调用方事务内使用。只改造四个插入点，它们都在事务内持行锁：上传到解析持 `document_upload` 行锁，解析到切片、切片到向量、向量到索引持 source 与 source_snapshot 锁。其余 10 处记为未覆盖。加唯一索引前要先清理历史重复行。

跨路径仍有重复可能：重处理插 parse 消息与上传插 parse 消息同键不同 task_id，会同时存在两行在途消息；重处理插 embed 的键是 snapshotId，初始化插的是 snapshotId:batchNo。两条都靠消费侧 CAS 丢弃，不会重复切片，但会重复投递。验收要如实写明这一点。

验收：同键两个事务只产生一行；同键不同载荷被拒绝；SENT 与 DEAD_LETTER 之后允许重新入队；跨路径重复投递被消费侧丢弃。

### 5.2 产物编辑回流记忆（能力四与能力五的接缝）

现状：`ArtifactMemoryRevisionGuard` 只做 `requireActive`，按 ARTIFACT_JOB_RUN 与 taskId 统计 usage 行，引用的 revision 不是当前 ACTIVE 就抛 409，不写记忆信号。`recordArtifactEdit` 没有生产调用方，只有测试在用。产物控制器只有创建、再生成、回滚、另存为资料、写回知识库，没有正文编辑入口。

设计：先补编辑入口并传入修改前后的正文；版本只存 after，before 要从上一版本 payload 取。编辑动作映射到 `logPackUsage` 已经写入的 ARTIFACT_JOB_RUN taskId，再生成版本时用该 taskId 记 usage。回滚不产生新 task，前后正文相同，不产生候选。V193 收据可以复用，用 `signal_kind=ARTIFACT_EDIT`、`source_ref=artifact-version:<versionId>` 做幂等，但现有 EDIT 逻辑靠 sameMagnitude 做替换，收据会把它变成每个版本只记一次，语义要先确认。另外编辑差异截断在 800 字符，章节粒度会丢。

验收：编辑一次只产生一条候选；重复保存不重复；回滚不产生候选；候选未晋升前不影响回答。

前置：没有编辑入口之前，这一项无法开工，建议从第四期移出，改成独立评估。

### 5.3 Note/Wiki 契约失败定性（能力二）

现状：11 个 `Phase3NoteWikiContractTest` 在基线就失败，断言期望回答里出现 `source-window-missing` 等标记，实际没有。标记本身仍在 `NoteRecallRetriever:422` 生成。

设计：先定性。若是渲染链路丢了标记，修 Note 答案装配与提示词渲染；若是测试固化了已废弃的文案，改断言并写明原因。不允许直接删断言。

验收：11 个用例转绿，或逐条给出原因与替代断言。

### 5.4 token 度量与记忆门控（新增）

设计见 3.1 与 3.2。两者风险不同，建议拆开排期：门控只改语义表达，不改变晋升结果；token 度量替换五处调用点，会改变预算判断与截断行为，需要前后对比基线。

范围：新增 token 计数接口与五处调用点替换、记忆门控语义调整、策略版本持久化。

验收：同一段文本用分词器与供应商 `usage` 的偏差在可接受范围内，并记录数据来源；门控决策在文档里能用一句话解释清楚。
