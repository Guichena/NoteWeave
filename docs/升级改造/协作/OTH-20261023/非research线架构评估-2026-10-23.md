# 非 research 线架构评估：重构还是修改

日期：2026-10-23。基线 `70631bd0`，集成分支 `codex/oth-20261023`（`8127b04d`）。只读评估，不改代码。

核实与修订见《核实与修订-2026-10-23.md》。本文件已按核实结果修正数字、范围与两处判断，未展开的细节以该文件为准。

## 一、结论

不建议重写。理由有三条：十万行主代码、七万行测试、行为已经过多轮验证；研究线占了近三成代码，是招牌能力；外部接口与数据库状态已经稳定。

架构方向本身是对的：模块化单体、端口与适配器、Java Host 掌控编排。问题不在架构选型，在实现纪律，集中在四处：

1. SQL 散落在服务里，同一语义重复实现。
2. 十一个上帝类，编排、校验、SQL、映射混在一起。
3. 平行路径，同一概念存在多套真相。
4. 响应 DTO 膨胀，每加一个端点就加一个类。

用绞杀者模式做四处结构性改造，每步保持行为不变，比推倒重来风险低得多。

### 2.5 语义重复

`index_status = 'INDEXED'` 这个状态字面量在 8 个文件里出现 33 次。按语义拆开：26 处是同一段当前可读快照条件，分布在 chat 三个文件与 infra 一个适配器；2 处是产物上游 revision 校验，语义不同，且同文件另两处接受 INDEXED 或 DISABLED；4 处是状态迁移写入；1 处是覆盖率统计。

所以真正重复的是那 26 处，涉及 chat 的检索水合、Note 召回、QA 片段三个入口，以及 infra 的证据归属适配器。这正是 OTH-12 的根因：改一处资格判断，另外三处不会跟着变。

同类问题还有最新快照版本、投影状态、资料就绪状态这些条件，都是各写各的。`projection_status = 'PROJECTED'` 读 7 处、写 2 处；`s.status = 'READY'` 26 处、16 个文件；latest 版本子查询 14 处、9 个文件，其中三处不带 index_status 过滤，口径已经不一致。

## 三、设计层面的四个问题

### 3.1 SQL 没有仓储边界

一千多处 jdbcTemplate 调用直接写在服务方法里，查询语义靠复制传播。后果有三个：

- 同一资格条件有二十六个副本，行为不一致时很难发现。
- 单元测试必须起数据库，纯逻辑测试写不出来。
- 换存储或加缓存时没有单一改动点。

这不是架构错误，是纪律缺失。端口与适配器在检索、向量、重排这些外部依赖上做得不错，但数据库访问没有同样的边界。

### 3.2 上帝类混合了四类职责

以 `MemoryApplicationFeedbackService` 为例，它同时做反馈判断、快照读取、锁内重读、写入与冲突处理。四类职责耦合在一个类里，任何一类变化都要改这个文件，测试也只能整体测。

业界做法是把编排留在应用服务，把判断、读取、写入拆成独立的协作者。这也是我们 OTH-02 改造时已经部分做过的事：判断移到事务外，写入放进短事务。但类没有拆。

### 3.3 平行路径

系统里存在几组并行实现：

- 上下文只有一套存储：回答链路读取的就是 `context_v2_shadow_snapshot`，shadow 是历史命名。真正的并行物是 diff 与 cohort 两个对比接口。
- 记忆的条目与槽位两套表达并存，是否都在生产路径上使用需要单独确认。
- 检索有 QA、Note、Wiki 三个入口，chat 三个文件各自实现同一段资格过滤，knowledge 另有自己的可见性规则。

平行路径本身是演进产物，不一定是错误。问题是它们共享同一批数据库状态，却没有共享同一套不变量。OTH-12 的问题就是其中一例。

### 3.4 响应 DTO 膨胀

155 个 Response 类，全部是 record，其中 153 个的字段集合互不相同，完全重复只有一组。真正的问题是数量多，不是重复多。

收敛成少数几个泛型包装只能消掉四处左右，却会让 155 个接口丢掉显式字段名与编译期类型，接口文档也会变模糊。建议只删掉那一组完全重复的类，合并三对近似类，保留其余具体 record。

## 四、业界对照

### 4.1 架构选型：模块化单体是对的

重写的常见理由是代码膨胀，但业界共识是先用单体把边界理清，再考虑拆分。Martin Fowler 的 [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html) 讲的就是这个顺序。我们的包结构已经是模块化单体的形状，缺的是模块之间的依赖纪律，不是换架构。

### 4.2 改造方式：绞杀者模式

Fowler 的 [StranglerFigApplication](https://martinfowler.com/bliki/StranglerFigApplication.html) 描述的正是这种情况：新实现一点点包住旧实现，旧路径逐步下线，全程可运行。适合 SQL 抽取、上帝类拆分、平行路径收敛这三类改造。

### 4.3 控制流：自己掌控是对的

[12-factor agents](https://github.com/humanlayer/12-factor-agents) 的第八条是掌控自己的控制流，不要把循环交给框架，否则暂停、恢复、人工介入都做不了。我们的 Java Host 掌控编排，方向正确。代价是代码量大，这个代价是合理的，不应为了减少代码量去引入一个把控制流藏起来的框架。

### 4.4 持久化执行：自建够用

Temporal 这类引擎提供持久化执行与确定性回放（[Temporal 文档](https://learn.temporal.io/tutorials/typescript/background-check/durable-execution/)），LangGraph 提供按 super-step 的 checkpoint（[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)）。我们用 outbox 加 lease 加 checkpoint 表自建，方向一致。以当前规模，引入引擎的收益不足以抵消改造成本，不做。

### 4.5 记忆：两阶段是主流

Mem0 的论文把记忆分成抽取与更新两阶段，更新阶段由模型对相似记忆选择 ADD、UPDATE、DELETE、NOOP（[Mem0 论文](https://ar5iv.labs.arxiv.org/html/2504.19413)）。Zep 用双时态知识图谱，把旧关系标记失效而不是物理删除（[Zep 论文](https://arxiv.org/abs/2501.13956)）。

我们的候选门控方向一致，但门控只读固定先验，等价于来源白名单；后验在证据服务与回答编译里是真实生效的，只是不影响晋升。这是设计问题，不是膨胀问题。

### 4.6 上下文：前缀稳定被反复强调

Anthropic 的上下文工程建议用 compaction、结构化笔记、子 Agent 三种手段（[Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。Manus 把 KV-cache 命中率列为生产环境最重要的指标，要求提示词前缀稳定、上下文只追加、工具用掩码而不是删除（[Manus 上下文工程](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）。

我们的上下文编译每轮重建，提示词前缀已确认不稳定：请求只有 systemPrompt 与 userPrompt 两条消息，userPrompt 开头就是本轮问题，后面是锚点、摘要、最近原文、约束与检索证据，都会随轮次变化。可缓存的部分只有系统提示词与固定模板段落。这一条建议单独排期做成本优化，不急着改。

## 六、重构还是修改：结论

重写不划算。四个结构性动作按顺序做：

1. 资格判断收敛。把当前可读快照这一段条件收进一个中立端口，实现放 infra，chat 三个入口与证据归属适配器共用。端口不能放 chat 或 answer，现有架构测试已禁止这两个包依赖 infra。这是收益最高、风险最低的一步，直接消除 OTH-12 那类改一处漏三处的问题。
2. 拆非研究线的上帝类。先拆视频素材，再拆产物导出，最后 Wiki 摄取；产物作业 896 行但没有直接 SQL，不拆。记忆反馈与检索投影在第一步顺带抽走持久化部分。
3. 给上下文表正名，退役对比接口。active 读取的就是 shadow 快照表，不能删表；能退役的是 diff 与 cohort 两个对比接口。这一步需要指标与调用日志支撑，风险高，放最后。
4. 响应类小清理。只删一组完全重复的类、合并三对近似类，不做泛型包装。

不做的事：微服务拆分、引入工作流引擎、引入通用框架、重写研究线。

## 七、顺序与验收

| 阶段 | 内容 | 风险 | 验收 |
|---|---|---|---|
| 0 | 资格对比测试 | 低 | 同一批快照状态下，新旧查询结果集完全相等 |
| A | 资格判断收敛到中立端口 | 低 | 26 处只剩一处实现，架构测试拦住回潮 |
| B | 拆视频素材、产物导出、Wiki 摄取 | 中 | 拆分前后用例一致，公开方法签名与错误码不变 |
| C | 上下文表正名、退役对比接口 | 高 | 指标连续观察，接口 30 天无调用，合同测试迁移完成 |
| D | 响应类小清理 | 低 | 接口字段不变，前端契约测试通过 |

每一步都是可独立上线的改动，失败可以回退，不需要整体冻结。

## 八、风险

- 拆上帝类容易引入行为变化，拆分前要先补特征测试，覆盖现有分支。跨类搬迁后自调用会绕过 `@Transactional` 代理，帧文件补偿与摘要必须保持单实例。
- 上下文表不能直接删，active 读取的就是它；退役对比接口前要确认无调用、无报表依赖。
- SQL 抽取如果只是机械搬移，收益有限。要按语义合并，而不是把同样的 SQL 换个地方放。测试库是 H2，收敛后的 SQL 必须两种库都能跑。
- 本地回退改 ngram 全文索引与 H2 测试库冲突，建议改为按资料大小设上限。
- 入队幂等在四个点成立，但跨路径仍可能产生同键在途消息，消费侧的 CAS 不能撤。
- 死信收尾不能与死信状态同事务，收尾失败不得回滚死信状态。
- 上下文前缀稳定性已确认不成立，可缓存的部分只有系统提示词，如果确实每轮重建，需要单独评估，不要混在重构里做。
