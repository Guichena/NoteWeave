# 非 research 线架构评估：重构还是修改

日期：2026-10-23。基线 `70631bd0`，集成分支 `codex/oth-20261023`（`8127b04d`）。只读评估，不改代码。

## 一、结论

不建议重写。理由有三条：十万行主代码、七万行测试、行为已经过多轮验证；研究线占了近三成代码，是招牌能力；外部接口与数据库状态已经稳定。

架构方向本身是对的：模块化单体、端口与适配器、Java Host 掌控编排。问题不在架构选型，在实现纪律，集中在四处：

1. SQL 散落在服务里，同一语义重复实现。
2. 十一个上帝类，编排、校验、SQL、映射混在一起。
3. 平行路径，同一概念存在多套真相。
4. 响应 DTO 膨胀，每加一个端点就加一个类。

用绞杀者模式做四处结构性改造，每步保持行为不变，比推倒重来风险低得多。

## 三、设计层面的四个问题

### 3.1 SQL 没有仓储边界

一千多处 jdbcTemplate 调用直接写在服务方法里，查询语义靠复制传播。后果有三个：

- 同一资格条件有三十三个副本，行为不一致时很难发现。
- 单元测试必须起数据库，纯逻辑测试写不出来。
- 换存储或加缓存时没有单一改动点。

这不是架构错误，是纪律缺失。端口与适配器在检索、向量、重排这些外部依赖上做得不错，但数据库访问没有同样的边界。

### 3.2 上帝类混合了四类职责

以 `MemoryApplicationFeedbackService` 为例，它同时做反馈判断、快照读取、锁内重读、写入与冲突处理。四类职责耦合在一个类里，任何一类变化都要改这个文件，测试也只能整体测。

业界做法是把编排留在应用服务，把判断、读取、写入拆成独立的协作者。这也是我们 OTH-02 改造时已经部分做过的事：判断移到事务外，写入放进短事务。但类没有拆。

### 3.3 平行路径

系统里存在几组并行实现：

- 上下文编译有 V2 shadow 与 V2 active 两套，shadow 仍在运行。
- 记忆有 memory_item 与 memory_slots 两套模型。
- 检索有 QA、Note、Wiki 三个入口，各自实现资格过滤。

平行路径本身是演进产物，不一定是错误。问题是它们共享同一批数据库状态，却没有共享同一套不变量。OTH-12 的问题就是其中一例。

### 3.4 响应 DTO 膨胀

155 个 Response 类，大部分是每个端点一个包装。好处是契约明确，坏处是重复字段与重复映射代码，改一个字段要动多个类。

## 四、业界对照

### 4.1 架构选型：模块化单体是对的

重写的常见理由是代码膨胀，但业界共识是先用单体把边界理清，再考虑拆分。Martin Fowler 的 [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html) 讲的就是这个顺序。我们的包结构已经是模块化单体的形状，缺的是模块之间的依赖纪律，不是换架构。

### 4.2 改造方式：绞杀者模式

Fowler 的 [StranglerFigApplication](https://martinfowler.com/bliki/StranglerFigApplication.html) 描述的正是这种情况：新实现一点点包住旧实现，旧路径逐步下线，全程可运行。适合 SQL 抽取、上帝类拆分、平行路径收敛这三类改造。

### 4.3 控制流：自己掌控是对的

[12-factor agents](https://github.com/humanlayer/12-factor-agents) 的第八条是掌控自己的控制流，不要把循环交给框架，否则暂停、恢复、人工介入都做不了。我们的 Java Host 掌控编排，方向正确。代价是代码量大，这个代价是合理的，不应为了减少代码量去引入一个把控制流藏起来的框架。

### 4.4 持久化执行：自建够用

Temporal 这类引擎提供持久化执行与确定性回放（[Temporal 文档](https://learn.temporal.io/tutorials/typescript/background-check/durable-execution/)），LangGraph 提供按 super-step 的 checkpoint（[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)）。我们用 outbox 加 lease 加 checkpoint 表自建，方向一致。以当前规模，引入引擎的收益不足以抵消改造成本，不做。

### 4.5 记忆：两阶段是主流

Mem0 的论文把记忆分成抽取与更新两阶段，更新阶段由模型对相似记忆选择 ADD、UPDATE、DELETE、NOOP（[Mem0 论文](https://ar5iv.labs.arxiv.org/html/2504.19413)）。Zep 用双时态知识图谱，把旧关系标记失效而不是物理删除（[Zep 论文](https://arxiv.org/abs/2501.13956)）。

我们的候选门控方向一致，但门控本身是固定阈值白名单，缺更新阶段的决策。这是设计问题，不是膨胀问题。

### 4.6 上下文：前缀稳定被反复强调

Anthropic 的上下文工程建议用 compaction、结构化笔记、子 Agent 三种手段（[Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。Manus 把 KV-cache 命中率列为生产环境最重要的指标，要求提示词前缀稳定、上下文只追加、工具用掩码而不是删除（[Manus 上下文工程](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）。

我们的上下文编译每次重建，前缀是否稳定需要验证。如果每轮都重排或重写历史，缓存命中率会很低，成本和延迟都会受影响。这一条建议单独验证，不急着改。

## 六、重构还是修改：结论

重写不划算。四个结构性动作按顺序做：

1. 资格 SQL 单一化。把快照资格、投影状态、工作区归属这几组条件收进查询对象，retrieval、chat、source、answer 四个包共用。这是收益最高、风险最低的一步，直接消除 OTH-12 那类改一处漏三处的问题。
2. 拆五个上帝类。记忆反馈、视频素材、产物导出、产物作业、Wiki 摄取，按职责拆成三个协作者，行为不变。
3. 收敛平行路径。上下文只保留 V2 active，记忆模型二选一，检索入口共享资格策略。这一步需要产品确认，因为 shadow 路径可能仍被使用。
4. 统一响应契约。把重复的 Response 收敛成少数几个泛型包装，减少映射代码。

不做的事：微服务拆分、引入工作流引擎、引入通用框架、重写研究线。

## 七、顺序与验收

| 阶段 | 内容 | 风险 | 验收 |
|---|---|---|---|
| A | 资格 SQL 单一化 | 低 | 行为不变，相关用例全绿，资格条件只剩一处 |
| B | 拆五个上帝类 | 中 | 每个类拆分前后用例一致，公开方法签名不变 |
| C | 收敛平行路径 | 高 | 需要产品确认；shadow 下线前先对比两边输出 |
| D | 统一响应契约 | 低 | 接口字段不变，前端契约测试通过 |

每一步都是可独立上线的改动，失败可以回退，不需要整体冻结。

## 八、风险

- 拆上帝类容易引入行为变化，拆分前要先补特征测试，覆盖现有分支。
- 收敛平行路径需要产品确认，shadow 路径可能仍被用于对比，贸然下线会丢观测能力。
- SQL 抽取如果只是机械搬移，收益有限。要按查询语义合并，而不是把同样的 SQL 换个地方放。
- 上下文前缀稳定性没有验证过，如果确实每轮重建，需要单独评估，不要混在重构里做。
