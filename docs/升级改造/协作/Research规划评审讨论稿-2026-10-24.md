1. v4 规划的大方向我基本同意：Java 管权限、预算、租约、提交和发布，Python 管研究策略，一个 run 只有一个调度权威，Judge 输出可执行的逐项结论并绑定版本，成本按每次尝试计量。

## 3. 影响完成率最大的五个问题

### 3.1 事实资格把未知当作不合格，官方原文被拒收

确认程度：代码确认，4 次真实运行复现（同一道题）。

- 代码：`ResearchSourceScopeChecks.java:45-50` 中，product 不是 MATCH、branch 不是 APPLICABLE、time 为 UNKNOWN 或 AFTER_CUTOFF 时都写入拒收原因，UNKNOWN 的拒收与时间模式无关。`ResearchRequirementCoverageService.java:167` 调用 `ResearchSourceScopePolicy.freeze(cell, entity, question, asOf)`，按整道题判断 temporal_mode，题目里出现目前二字，每个单元格都成了 CURRENT，包括从哪个版本开始提供这种历史性问题。
- 运行 `085744`：DEEP_CELL 抽到 9 条事实，合格 1 条；拒收原因 SOURCE_TIME_UNKNOWN 8 次、SOURCE_BRANCH_UNKNOWN 8 次、SOURCE_PRODUCT_UNKNOWN 8 次。被拒的是 docs.python.org 上的原文 Starting with the 3.13 release, CPython has support for a build of Python called free threading，报告正文写成未找到证据，交付状态 INSUFFICIENT_EVIDENCE。
- 同题另外三轮（`completion-v5`、两轮 `answer-policy-v1`）拒收原因同样以 SOURCE_TIME_UNKNOWN 和 SOURCE_TIME_HISTORICAL 为主，CURRENT 类需求停在 PENDING 或 PARTIAL。另一会话的验证记录（`06-Research完成度集中验证记录-2026-10-21.md`）中同题耗时 1541 秒、模型调用 124 次、搜索 28 次，系统需求覆盖 2/9，评分模型三次都判通过。第十二轮同题 90 秒、5/5 单元格通过。
- 影响面：数据集中只有这一题整题带目前，但产品、分支、时间三项的 UNKNOWN 拒收对所有题生效，官方文档页大多不标发布日期。我推断其他题也会受影响，这一点需要全量复测确认。
- 与规划的关系：规划 7.2 节要求 `canAnswerCurrent` 在缺少 scope 时返回未知、不能视为适用，方向是继续加严。在拿到误拒率数据之前，我反对再加严。
- 修法：资格检查分两级。引用逐字存在、来源身份、授权范围属于硬条件，不满足就拒收；时间、版本、产品适用性给出 APPLICABLE、UNKNOWN、MISMATCH 三档，只有 MISMATCH 拒收，UNKNOWN 进入报告说明（例如：文档未标注日期，以页面当前版本为准）。时间模式按单条需求判断。每个拒收原因都计数，评测报告列出被拒样例。

### 3.2 需求数量膨胀，重规划后需求身份断开

确认程度：单题运行确认。

- `085744` 中，一道两问的题规划了 4 条显式需求绑定，第 4 次尝试被判为逐条件核验未通过（同期 `research.planning.requirements` 出现 Connection error），规划结果标为 FALLBACK，退回到 DETERMINISTIC 骨架规划：实体名是 Subject，列名是哈希。随后两次 MARGINAL_GAIN_EXHAUSTED 重规划把 plan_revision 推到 3，需求 ID 随之重建（`predecessor_requirement_id` 指向旧 ID）。Worker 在 revision 1 报告 `req:c6e7…`、`req:8e0b…` 已完成，后端当前要求的是 `req:e885…`、`req:ffe2…`，`supporting_fact_ids` 为空，已找到的事实没有计入。
- 另外三轮在同一道两问题上拆出 6 到 9 条必需需求，多数被标为 CURRENT。每多一条必需需求，就多一个可能卡住完成状态的门槛。
- 与规划的关系：规划 R-N01 要求修订时保留 lineage 和事实，我同意，这条有直接证据支持。规划担心的是分母被删小，数据里出现的是分母变大和身份变化。
- 修法：需求 ID 由 lineage（实体加规范化需求文本）稳定生成，重规划只改执行分解；Worker 的观察结果按 lineage 归并；派生需求默认非必需；模型连接错误按基础设施失败重试，不触发骨架规划。

### 3.3 规划缺少领域内默认要讲的维度

确认程度：第十二轮时期多次运行确认。

- 10-20 两次 1.1.0 评分（`quality-20261020-082246`、`quality-20261020-090512`）中，9 道失败题有 5 道的单元格全部或几乎全部 VERIFIED，评分仍指出漏项：Nginx 配置变更是否需要重新加载进程；OTel 推送还是拉取、累计值与增量值的表示；Rust 迁移工具与生效版本；Kafka 重平衡或故障时对顺序的影响；Vite 生产构建使用的工具。这些点问题里没有明说，是回答这类问题时默认要覆盖的内容。
- 系统按自己规划的列判定完成，所以 run 是 COMPLETED_VERIFIED，用户拿到的仍是缺项回答。
- 我之前用提示规则补，`65bc6860` 把设计取舍做成逐条清单，导致 Vite、Kafka 回退；`b1e49247` 改成只作提示后部分恢复。提示补丁容易对评测集过拟合。
- 与规划的关系：规划允许调整 DERIVED 需求，这点合理；但它的 PlanJudge 主要检查少对象、少条件、数量和时间错误，没有覆盖这一类。
- 修法：规划时单独生成应覆盖要点，作为派生的非必需项，分配有限的研究预算但不阻塞完成；报告写完后由答案评审对照问题和应覆盖要点检查，缺事实就定向补查，已有事实就局部改写。

### 3.4 取证失败，基础设施错误被当成语义结果

确认程度：多次运行确认。

- PG17 增量备份题只完成 3/4，缺 `--incremental` 的命令与参数（官方版本页取不到或版本目录不匹配）。
- 覆盖率门槛题缺支持性实证，原因是 ACM、IEEE 出版商页面抓取失败。

- `085744` 规划阶段的模型 Connection error 导致退回骨架规划（见 3.2）。
- 与规划的关系：V4-02 语言路径过滤属实（`search_adapters.py:265-267、290`），但当前 20 题的官方来源都是中英文，它解释不了上述失败；V4-07 多副本限流属实，单 worker 下不是主要矛盾。
- 修法：搜索服务额度或网络失败时切换服务并退避重试，run 进入等待，最终计为执行失败，不写成证据不足；出版商页面失败时转查预印本和作者主页（`repair_queries.py` 已有提示，需要验证是否生效）；版本化文档按需求中的版本改写 URL；语言过滤改为排序，改动小，顺手做。

## 4. 对架构与选型的意见

### 4.1 赞同

- Java 持有权限、来源范围、租约与 fencing、预算账本、状态提交和发布，Python 持有研究策略。现在策略分散在两边：优先级、重规划触发、缺口策略、事实适用性判断在 Java，查询、抽取在 Python，同一类判断两边各有一份规则（版本目录就是例子）。一个 run 只有一个策略权威，我同意。
- Judge 输出逐项、可执行、绑定版本的结论；在线修复用的 Judge 与离线评测隔离。
- Lead 不能删除必需项、扩大来源授权或追加预算。

### 4.2 反对或需要调整

1. 语义适用性不应作为 Java 硬门槛。事实是否适用于某个时间、版本、产品，是语义判断，现在由 Java 规则直接拒收（3.1）。我建议 Java 只做可以确定的检查：身份、引用存在、授权、预算、版本号明确冲突；适用性由 Python 侧给出分级标签，以置信度进入完成判定。
2. 每一步都走 Lead 提案、Java 校验、再派发的往返，对单事实题只会增加延迟。建议 Python 领取一个 run 级研究任务，在授权预算内自行循环，Java 在提交事实和结束时校验；只有需要并行的子任务才经 Java 派发。
3. 质量修复不应排在基础设施之后。规划前三批的工作（压缩、语言、typed scope、checkpoint、预算继承、计量）都不直接解决 3.1 到 3.4。建议质量修复先做，基础设施并行或后置。
4. 每加一层判断就多一种误拒来源。规划没有要求各层报告误拒率。建议规定：每个门槛都要统计拒收原因和误拒样例，误拒率超过约定阈值不得启用。
5. PlanJudge 的检查范围要从少对象、少条件扩展到领域默认维度（3.3）。
6. 比较题已经按单元格并行派发 DEEP_CELL，多 Agent 并行的主要收益现在已经拿到了一部分。新增 Lead 的价值在于动态决定下一步补什么，这部分可以先在现有协调器里用缺口分类实现。只有第 6 节阶段 4 的原型在同预算下胜出，才值得引入 Lead。

### 4.3 OpenAI Agents SDK 与 pi

1. SDK 能替代的部分：单个角色内部的模型调用循环（调用工具、拿结果、决定下一步）、结构化输出解析和少量重试，大致对应 `llm_client.py` 的 JSON 调用与重试，以及 `loop_runtime.py` 中搜索、阅读、抽取循环的一部分。
2. NoteWeave 必须自己承担的部分：Kafka 投递、认领与心跳与 fencing、预算账本、证据归档与身份、事实资格、完成门槛、来源资格、报告发布、checkpoint。这一点我与规划看法一致。
3. 避免重复重试、重复历史和重复结算：SDK 的 `max_retries` 设为 0（现有 `llm_client.py:170` 已是如此），重试只由模型网关负责；不用 SDK Session 持久化历史，每次由业务上下文包生成输入；预算只在网关结算一次。
4. 取消、心跳失败、旧任务回包和部分输出：心跳沿用 `execution_control.py` 的独立线程；每次工具调用前检查取消与租约，失效时由工具网关抛出取消；提交时 Java 用 fencing token 拒收旧回包；已有结果按部分结果提交，status 与 stop_reason 分开。
5. pi：需要 Node 22 运行时，所有工具改成 RPC，usage 与取消协议重做。它的收益是更现代的 Agent 核心，而我们的问题不在 Agent 循环本身，跨语言迁移成本不值得，不选。
6. 我的建议是暂不引入 SDK。真正要回答的问题是：取证阶段由固定管线执行好，还是由模型自主调用工具循环执行好。这可以用现有 `llm_client` 加 DeepSeek 的 function calling 写一个约 200 行的工具循环原型来对照，不需要先处理 openai 2 到 3 的依赖冲突（`pyproject.toml` 现为 `openai>=2,<3`，SDK 要求 `>=3,<4`）。原型胜出后，再决定是否用 SDK 降低维护成本。

## 5. 最小纵向方案：需求、证据、报告、核验、恢复

范围：单实体事实题 1 道、两实体比较题 1 道。全部在现有角色协议内完成，不新增任务协议版本。

1. 需求：规划输出两类条目。显式需求来自原问题分句，带 question_quote，是必需项；应覆盖要点是领域默认维度，非必需。需求 ID 由 lineage 生成，重规划不变；时间模式逐条判断。
2. 证据：沿用 DEEP_CELL 的搜索、抓取、窗口、抽取。资格检查按 3.1 分为硬条件和分级适用性，只有硬条件失败或适用性为 MISMATCH 时拒收。
3. 报告：Writer 使用 evidence_quotes 配对写正文和逐项答案。
4. 核验：沿用 `statement_support` 的逐句支持核验；在 SYNTHESIS 角色内部新增答案评审，作用域是本次报告，因此不需要新协议。答案评审对显式需求和应覆盖要点逐项给出 PASS、FAIL、UNKNOWN 和修复类型（表达不足、缺事实、引用不支持）。表达不足在 Writer 内局部改写，最多两轮；缺事实交给现有 `ResearchReportFeedbackService` 派发定向 DEEP_CELL。
5. 恢复：在定向补查执行中途停掉 worker，恢复后检查需求 ID、已合格事实和报告版本保持不变，已完成的搜索不重复执行。checkpoint 闭包先只补需求与事实两类，这是 R-N04 的最小子集。

验收：固定检索录制下的无付费回放通过后，两道题各跑 3 次真实运行。看需求答案覆盖、引用支持、耗时、模型与搜索调用数、恢复前后差异。

### 9.5 当前剩余的主要失败原因

- 补查一轮：开补查的两轮平均通过 17 题、覆盖 91，关闭补查 15 题、覆盖 90，差距在波动范围内，开补查时每题模型调用多 4 到 15 次、耗时中位多 100 到 300 秒。fix19 同一镜像开补查 13/40、覆盖 85，关闭 15/40、覆盖 90，三组对照都没有稳定收益，最终关闭补查（`5751a1a3` 改为默认关闭）。
- 成文：逐题排查发现已核验的单元格常被逐句核对整段删掉，原因多是段落引用了别处单元格的证据编号。修复后离线重放 fix17 两轮的成文，漏写单元格从 98 个降到 10 个；fix18 缺失的 27 个要点只有 3 个答案已在成文输入里，fix17 每轮约 8.5 个。
- 剩余损失几乎都在检索与抽取：规划没要求的方面（例如 OpenTelemetry 的采集方式）、一侧答案只写在对方文档里的比较（Deployment 的顺序保证写在 StatefulSet 页面上）、单元格取到边缘事实。改检索词写法的两种规则离线重放都没有效果，未采用；同一题各研究对象的任务共享已抓到的网页可能有效，需要改后端派发，留待以后。
- fix19 加入以冒号结尾的引用扩到冒号后面的内容（`ea63d558`）与引用核对摘录放宽到 700 字符（`ba7f4dfe`）。合计少 3 题、3 个要点，留出集新增的失败多是检索没取到（Elasticsearch 2024 年新增的 AGPLv3、PostgreSQL 16 的 pg_stat_io），按波动处理。
- 抽取重放：把一次运行抓到的全部窗口交给同一版抽取提示，PostgreSQL 16、17，Python 3.13，git merge 等 5 个漏抽的要点 15 次里 13 次能抽到，提示不是瓶颈。漏抽的答案多在同一研究对象另一个任务抓到的网页里：后端每个任务最多 3 个单元格，一个对象的 4 到 5 列被拆成两个任务，各抓各的网页。fix20 把上限调到 6（完成协议的候选与证据上限同步放宽到 6 和 36），一个对象的各列共用网页。
- 比较题点名双方的检索词：两轮比较题原文中找不到的 23 个要点有 10 个能从对比文章回答，但来源多是第三方，题目要求官方文档时只能算线索，未采用。
- fix20 部署后 4 到 5 个单元格的任务全部提交失败：后端完成提交与 Worker 回执解析仍按每个任务 3 个单元格设限，单元测试只构造过不超过 3 个单元格的任务。`d5e6b161` 修复后以 fix21 重新评测。
- fix21 合计通过 17/40、要点覆盖 94，覆盖数是各轮最高，定为最终版本。40 题的深挖任务从 123 个减到 72 个，开发集耗时中位从 543 秒降到 391 秒。缺失的 26 个要点里成文损失 4 个、抽取损失 7 个、检索损失 15 个（fix19 为 5、9、15，另有 1 个只在线索里）。
- 要点覆盖提高后，要点齐全却因事实或引用不及格而未通过的题增加到 5 道（此前各轮 1 到 3 道），多是证据出处与研究对象对不上：结对编程一题把另一项研究的数据记在当前论文的单元格里，OIDC 一题把 OAuth 2.1 草案的原文标成 OIDC Core 的证据。下一步可以在抽取或核验时核对证据出处与研究对象是否一致。
