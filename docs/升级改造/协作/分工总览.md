## 3. 共享资源的约定

- **Flyway 迁移版本号**：B 使用 V140 到 V159，C 使用 V160 到 V179，避免合并时版本冲突。V133 到 V139 预留给 A 在集成时修补使用。
- **新增 HTTP 接口**：先写进 [接口约定](接口约定.md)，再实现。前端按约定并行开发，字段名以约定为准。
- **新增配置开关**：默认打开，保留开关用于回退；`application.yml` 和 `docker-compose.yml` 同步修改。
- **LLM 降级原则**：生成和规划类调用（检索词、表格规划、查询改写、意图编译）在模型不可用时退回规则，并记录降级原因；判定类调用（矛盾判断、证据支撑、反证判定、记忆冲突）在模型不可用时记为 `NOT_RUN`，不允许判为通过。
- **被替代的代码直接删除**：模板代码、写死的数据不保留；仍然需要的规则只作为降级方案存在。

## 4. 分支与合并

0. 基线已提交在 `feat/frontend-notebook-redesign`（包含 1A、1B 和这套协作文档），各分支都从基线拉出：B 用 `feat/upgrade-agents`，C 用 `feat/upgrade-retrieval-memory`，A 用 `feat/upgrade-frontend`，共享的集成分支是 `feat/upgrade-integration`。
1. 每完成一个阶段在自己的分支提交一次，提交信息使用简体中文，格式为 `feat(阶段号): 说明`，例如 `feat(1C): 定向反证与按原因改写的 Replan`。
2. 合并不依赖 A，由完成阶段的一方自己做：
   1. 先把 `feat/upgrade-integration` 合并进自己的分支，解决冲突；
   2. 跑 Worker、Backend、Frontend 三端全量测试，全部通过；
   3. 再把自己的分支合并进 `feat/upgrade-integration`，在进度看板交接记录里写明合并的提交。
3. 开始新阶段前，先把 `feat/upgrade-integration` 合并进自己的分支，拿到另外两条线已完成的工作。
4. 冲突落在别人归属的文件上时，保留对方的改动，只做让测试通过所需的最小调整，并在协调区说明。
5. 不改写已推送或已合入集成分支的历史，不使用强制推送。

## 5. 每个阶段的完成标准

1. 设计文档对应阶段的方案已实现；与设计不一致的地方写进该模块文档的实施记录，说明原因。
2. 新增或修改的行为都有测试；Worker、Backend 的全量测试通过，失败的旧测试要么修复，要么说明为什么旧断言已不成立。
3. 在 [进度看板](进度看板.md) 更新状态，写明新增的接口、配置、迁移脚本，以及还没验证的部分。
4. 在模块设计文档末尾的实施记录追加本阶段记录，格式参照 01 号文档的 1A、1B。

注意事项：
- 本机 `C:\Program Files\Java` 下只有 JDK 8，后端必须使用上面的 JDK 17 路径。
- 后端测试使用内嵌 H2，不需要 Docker。H2 读取 JSON 列时可能返回二次转义的字符串，解析时先 `readTree`，如果是文本节点再解析一层。
