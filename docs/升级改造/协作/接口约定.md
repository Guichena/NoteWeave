# 接口约定

后端与前端并行开发的依据。后端实现时字段名、取值必须与这里一致；需要调整时先改这份文档并在进度看板协调区说明。状态取值：`约定`（未实现）、`已实现`、`已联调`。

所有路径省略前缀 `/api/v2/workspaces/{workspaceId}`，响应都包在现有的 `ApiResponse` 信封里。

## 问答与检索（C 线实现，A 线前端）

### 3A 查询改写、3·S7 证据充分性

在现有回答记录（AnswerRun 详情、证据接口 `GET /answer-runs/{runId}/evidence` 的响应）中新增字段。`retrieval_rewrite` 状态：已实现，没有改写结果时省略该字段。`evidence_sufficiency` 状态：约定，留到 3·S7，当前响应不返回。

```json
{
  "retrieval_rewrite": {
    "is_standalone": false,
    "standalone_query": "string",
    "keyword_query": "string",
    "method": "LLM | RULE",
    "degradation_reasons": []
  },
  "evidence_sufficiency": "SUFFICIENT | PARTIAL | INSUFFICIENT | NOT_RUN"
}
```

`INSUFFICIENT` 时前端在回答上方提示资料中没有足够信息，`PARTIAL` 时提示只能回答一部分。

### 3D Wiki 多跳

Wiki 模式的证据项新增 `graph_path: ["种子页标题", "中间页标题", "扩展页标题"]`，只有通过图扩展得到的页面才有，状态：约定。

### 后端内部接口：供产物素材检索调用（C 线提供，B 线调用）

B 线 4B 的 `POST /internal/worker/artifact-tasks/{taskId}/retrieve` 不直接依赖 `QaHybridRetriever` 的内部细节，而是调用 C 线提供的服务。接口状态：已实现。实现类是 `com.noteweave.chat.HybridScopedPassageSearch`，放在 chat 包是为了避免 `retrieval.qa` 和 `QaHybridRetriever` 循环依赖。query 必须已经是独立自然语言。Provider 不可用时返回 `degraded`，不抛异常。

```java
package com.noteweave.retrieval.qa;

public interface ScopedPassageSearch {
    /** 在给定资料范围内检索片段；query 是一句独立的自然语言查询，不需要对话改写。 */
    Result search(String workspaceId, java.util.Set<String> sourceIds, String query, int limit);

    record Passage(String chunkId, String sourceId, String sourceSnapshotId, int chunkNo,
                   String title, String location, String content, double score) { }

    record Result(java.util.List<Passage> passages, boolean degraded, java.util.List<String> degradationReasons) { }
}
```

C 线在 3A 中先提供一个基于现有混合检索的实现；B 线开始 4B 时如果 3A 还没合并，可以先写一个临时实现放在 B 自己的目录里，3A 合并后删除。

## Memory（C 线实现，A 线前端）

### 2A 冲突检测

`GET /memory/review` 每个待确认项，以及 `GET /memory/items` 的每一项（记忆页实际读取的是这个接口）新增，状态：约定

```json
{
  "slot_key": "answer.language",
  "conflict": {
    "type": "SLOT_VALUE | POLARITY | SEMANTIC | NONE | CHECK_NOT_RUN",
    "conflicting_item_id": "string",
    "conflicting_text": "string"
  }
}
```

### 2B 证据累积评分

`GET /memory/items` 每项新增 `confidence: {alpha, beta, mean, variance}`、`reinforcement_count`、`last_reinforced_at`，状态：约定。

### 2C 与问题相关的注入

`GET /memory/control-pack/chat` 增加可选查询参数 `query`；`memory_references[]` 每项新增 `memory_class: ALWAYS_ON | ON_DEMAND`、`relevance`（0 到 1，常驻类可为空）、`selection_reason`、`display_text`，状态：约定。

- `selection_reason` 是可以直接展示给用户的简短中文说明，例如：适用于全部回答的常驻约束、与问题相关度较高。前端不再做代码到文字的映射。
- `display_text` 是记忆的当前文本，前端据此展示，不再按 ID 去记忆列表里查找。

回答证据接口 `GET /answer-runs/{runId}/evidence` 新增 `memory_references`，结构同上，记录这次回答实际编入的记忆，状态：约定。记忆页的预览与回答中的展示共用同一组件。

### 2D 效果反馈

| 接口 | 说明 | 状态 |
|---|---|---|
| `POST /answer-runs/{runId}/feedback`，请求体 `{rating: "POSITIVE" \| "NEGATIVE", reason?: string}` | 回答的点赞点踩，后端映射到本次注入的记忆。同一回答可以重复提交，以最后一次为准：前端点踩后会再提交一次带 `reason` 的请求。`reason` 目前取值为：内容不准确、没有回答问题、引用不支持结论、资料里有但没找到 | 约定 |
| 现有提交回答的请求体新增可选字段 `regenerated_from: answerRunId` | 前端重新生成时带上原回答 ID，后端记为 `RETRIED` | 约定 |

## 资料上传与解析（B 线实现，A 线前端）
