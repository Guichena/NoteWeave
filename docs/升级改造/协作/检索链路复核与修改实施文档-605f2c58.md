本文面向 NoteWeave 后端维护者，覆盖 QA、NOTE、WIKI 从查询改写、候选召回、排序、正文回填到回答生成、引用绑定和失效处理的修改。三种模式继续独立检索，公共层只负责工作台边界、最终证据契约、预算、引用和生命周期。

复核结论是：现有检索思路可以保留，但实现尚未完整兑现证据选择与引用约束。优先修复最终正文和排序被下游改变、WIKI 扩展结果被再次截断、页面依赖与实际编译材料不一致，以及输出引用缺少服务端校验。无需引入新的向量库、通用 Agent、全局知识图谱或另一套检索框架。

实施时以本文件的必改项为主。条件性问题写明触发前提；排序偏好与参数选择不直接视为算法错误。所有新增类、字段、状态和迁移名均为拟议接口，不表示它们已经存在于该提交。

## 1 现有实现与必须保留的边界

### 1.1 三种模式实际采用不同的证据单位

| 模式 | 现有主链路 | 最终证据单位与边界 |
|---|---|---|
| QA | 查询改写 → ES 向量与词法召回 → RRF → 重排 → 相邻块补全 → MMR 与预算 | 用户资料中的 source chunk；必须保留 source、snapshot、chunk 身份 |
| NOTE | 来源级多路召回 → 标签与共引关系扩展 → 来源排序与配额 → 阅读窗口补全 → 窗口规划和重排 | 当前有效资料的阅读窗口；日志和关联图提供找资料的线索 |
| WIKI | 正式知识页召回 → 页级重排 → Personalized PageRank 扩展 → 图预算 → 页面上下文 | 知识页的指定版本，并经页面引用回到资料快照和 chunk |

QA 当前生产 profile 是 V3。一次向量和词法召回各取 60，融合池上限 100，请求返回 top 40 重排结果，MMR 最多保留 20 条，内部 token 预算为 8,000，公共证据字符预算为 32,000。专用 provider 默认最多接收前 80 个候选，LLM 后备只处理前 40 个，两者评分输入不同。NOTE 返回窗口上限为 8，WIKI 计划中的种子候选上限为 5、图节点预算为 30。这些值是代码参数，不是效果结论。[S01] [S02] [S03]

公共执行顺序是 retriever 返回结果、按 Step.candidateLimit 截断、检查 scope 和 ownership，再由 EvidenceBudgeter.select 按 fusedScore 排序并执行最终预算。之后 ChatService 执行充分性判断和模式 compose，再保存草稿、引用、运行清单，最后启动生成。正是在这些边界之间，出现了排序、正文和身份被重新解释的问题。[S04] [S05]

### 1.2 已经成立的设计

- workspace 条件、当前快照检查和 source scope 并非缺失。QA、NOTE 有来源回填和有效性过滤，公共 ownership guard 还会复核身份。不能把后文的正文一致性问题概括成没有租户隔离。

- WIKI 没有正式页面时会明确返回资料不足，不会退回 QA 充当知识页回答。这一行为应保留。

- QA 已经实现 RRF、MMR、邻块去重和预算；NOTE 已经实现先选来源再读窗口；WIKI 已经实现 PPR 和图预算。修复不能把已有机制重新命名为新增算法。

- EvidenceBundleSnapshot.from 只持久化身份、分数等审计信息，不复制任意 retriever metadata。完整 NOTE 运行时快照进入 metadata，不等于整份日志正文已经落盘。

- 专用 rerank 服务关闭或抛出异常，并不必然没有重排。生产注入的 FallbackRerankClient 可尝试 LLM 后备；后备不可用或失败、或者返回结果在上层被拒绝时，可进入融合排序降级。当前 provider 返回空结果等路径未必会尝试 LLM。

以上保护分别由公共身份检查、各模式 compose、审计快照和重排客户端实现。[S06] [S07] [S08] [S09]

### 1.3 复核后需要收紧的旧结论

QA V3 常规中文和英文文本下，内部最多 20 条和 8,000 token 预算通常已经满足公共 32,000 字符预算。因此确定存在的问题是公共层重新按 RRF 分数排序，不能一概说公共层必定再次删除 MMR 成员。非常规字符计数或配置变化另行处理。

NOTE 的窗口重排通常仍决定前 8 条成员；后续 fusedScore 排序会覆盖其最终顺序，字符预算紧张时还可能改变留存优先级。应表述为重排结果被部分覆盖，不能说重排完全没有生效。

失效日志的标题和状态提示、未进入最终窗口的来源摘要，确实可能进入 NOTE 草稿。日志完整正文只确认进入运行时 NoteRetrievalSnapshot，未确认整份进入持久化 bundle snapshot。进入草稿的文本则会通过 initialContent 写入消息版本。

ES 的 content 保存原始 chunk 正文，context_text 是单独字段；增强上下文通过 copy_to 参与词法索引，但不会因此改写 _source.content。正文回填修复的目标是验证当前权威正文及其版本，而不是移除一个实际不存在的拼接字段。

## 2 问题分级与修改范围

P1 表示影响证据资格、归因、正文一致性或明确执行语义，必须优先处理。P2 表示影响召回、排序、容量或配置兼容，应在主契约确定后修复。这里不将任何问题标为已证实的跨工作台泄漏。

| 编号 | 级别 | 复核结论 |
|---|---|---|
| C01 | P1 | 最终正文、排序、评分来源没有统一契约，多个消费方重新裁剪或解释 |
| C02 | P1 | 充分性门控用数值猜评分来源，真实低分可能被当作没有分数 |
| C03 | P1 | PromptSpec.systemPrompt 未被实际生成调用消费；输出引用没有服务端白名单校验 |
| C04 | P1 | 删除与生成之间存在晚到正文和引用副本的清理缺口，需要补全运行级处理 |
| C05 | P2 | NONE 模式下 NOTE、WIKI 的 Prompt 版本与 none-v1 计划不一致 |
| Q01 | P1 | QA 拼接邻块正文后仍绑定主 chunk，出现引用归因错误 |
| Q02 | P1 | QA judge 看主块前 800 字，生成看带邻接块的正文前 900 字，证据视图不一致 |
| Q03 | P2 | 未返回真实重排分数的候选被补成人造分数，来源标记随后丢失 |
| Q04 | P2 | 查询改写回退时主题锚点只进入词法查询；扩展分支的局部排名被拼接位置替代 |
| N01 | P2 | 旧来源日志的零相关分可被 Math.max 提升为正分 |
| N02 | P1 | 正文回填不严格按已规划优先级消费预算，并可能输出空正文窗口 |
| N03 | P2 | 窗口重排顺序被公共 fusedScore 顺序覆盖 |
| N04 | P1 | 未选来源摘要和审计用失效日志标题仍可能进入回答草稿 |
| N05 | P2 | 稀疏候选池的最大窗口号被误当作原块真实末窗 |
| N06 | P2 | 中文二字词被下游长度条件全部拒绝；关系查询只处理前 200 个来源 |
| W01 | P1 | 5 个种子加扩展页返回后再 limit 5，通常丢弃全部扩展正文 |
| W02 | P1 | Wiki 编译使用 5 或 6 个 chunk，却只登记 3 或 4 个 citation |
| W03 | P1 | 页面资格检查丢失引用的 snapshot 身份，更新后的旧页可能继续当当前证据 |

| W07 | P2 | Wiki 预算按摘要计费，生成却读摘要和正文；任务未贯穿绑定 source snapshot |

每项的触发条件和修改位置见后文。旧 ES 与新 DB 正文不一致、生成期间来源被撤销，以及历史任务跨资料版本读取，均属于需要明确前提的条件性风险，不据此推断已经发生数据损坏。

## 3 先建立最终证据契约

### 3.1 只保留一份回答可用正文

修改 EvidenceBundle.Evidence 的使用约定：excerpt 表示经过资格校验和预算选择后、真正允许模型使用的正文。它不再同时表示全块内容、预览、带邻接块的临时文本或 Wiki 摘要。三个模式分别构造 excerpt，公共层不负责统一召回算法。

新增轻量的 EvidenceSliceRef，保存正文所属的窗口和切片范围。QA 和 NOTE 都必须保留既有 sourceId、sourceSnapshotId、passageId；NOTE 额外记录 sourceWindowId 和 windowNo；WIKI 继续以 knowledgeVersionId 定位。切片范围使用 Java UTF-16 半开区间，命名中明确单位，避免与 code point、字节和 token 混用。contentHash 对实际 excerpt 的 UTF-8 字节计算。

| 字段 | 语义 | 使用方 |
|---|---|---|
| excerpt | 允许生成和充分性判断使用的最终正文 | Judge、compose、manifest |
| selectionRank | 模式内最终选择顺序，从 1 开始 | 公共预算和引用编号 |
| sliceRef | window 身份、正文范围和正文摘要值 | 引用定位和审计 |
| scoreInfo | 真实评分值、来源、阶段、模型和评分正文摘要值 | 充分性判断和排序解释 |
| evidenceRole | QA_HIT、NOTE_WINDOW、WIKI_SEED 或 WIKI_EXPANDED | 模式内选择与图证据解释 |
| characterCost | 实际证据块渲染开销，不能继续只按 Wiki 摘要长度计费 | 统一预算 |

原有 rawScore、fusedScore 暂时保留作诊断，不能改名后冒充模型置信度。现有 double rerankScore 可在过渡期保留，但新判断只能读可空的 scoreInfo.value。新增值对象应放在 answer/strategy 附近，避免每条检索链各定义一套同义字段。[S10]

正文窗应在重排前生成，并在后续保持不变。首版可沿用现有模式长度约束，对普通段落取一个明确、可定位的连续窗口；长表格、代码块优先按行或结构边界选取包含命中词的片段。无法形成有意义的片段时跳过并保留原因，不能输出空证据。不要在 compose 中重新取另一段正文。

评分客户端可能仍有自己的输入上限。必须记录实际评分文本的 hash 和截断情况，不能把对前 320 字的评分解释成整份长窗口都已被模型看过。最终生成和充分性模型使用完整的最终 excerpt；排序只作为筛选信号。首版优先把后备 LLM 的正文优先预算写清楚，防止标题和 heading 占满评分输入。

### 3.2 最终顺序只能确定一次

EvidenceBudgeter.select 改为按 selectionRank 稳定遍历，不再全局按照 fusedScore 重排。QA 的 selectionRank 来自 MMR 选择顺序；NOTE 来自窗口重排或明确的降级顺序；WIKI 来自种子与扩展的模式内选择结果。公共层只执行去重、非空、资格和资源限制。

Step.candidateLimit 统一定义为 retriever 最多返回并由公共层接纳的总候选数，不再兼任 WIKI 的种子数。WIKI 单独解析 seedLimit。现有三个策略各使用自己的一个 Step，不需要发明跨模式分数归一化，也不需要把三个检索器合并。

预算耗尽时保持稳定顺序：如果某条证据容纳不下，可以继续尝试后续较短证据，但必须记录该条被预算排除；不得把它改成空字符串后作为零成本成员塞入。引用编号只在最终成员确定后分配。空结果交回对应模式的资料不足路径。

新成本合同同时计入有界的标题、标头和引用包装开销，MMR 的 token 预算也使用相同范围，或提前预留这些开销。最终编号可使用保守长度预留，不能为重新计算编号而改变选择顺序。第 1 节对旧 V3 通常不二次删成员的判断，不是对新包装成本合同的永久保证；新公共预算仍须正确处理超预算排除。

### 3.3 评分来源必须显式传递

拟议 ScoreInfo 至少包含 origin、stage、model、value、scoredTextHash。origin 区分 PROVIDER_MODEL、LLM_FALLBACK、FUSION_FALLBACK、GRAPH、NONE；stage 区分 SOURCE、PASSAGE、WINDOW、PAGE。不存在模型分数时 value 为 null，不能使用 0 表示未知。

QaRerankService 不再给未返回分数的候选制造接近最低已评分候选的数值。为它们保留独立的 fallbackRank，允许按融合顺序进入余量候选池，但不得参与模型分数门控。RerankResult.model 必须贯穿 QA、NOTE 和 WIKI 的适配层。当前 llm-listwise-v1 仅是后备评分方法标识，不能声称它是真实基础模型名称。[S11] [S09]

OpenAiCompatibleRerankClient.parse 必须在调用 asDouble 前检查分数字段存在且为数值，index 为整数、落在本次实际提交的文档范围且不重复，分数有限。缺失分数不能默认为 0。校验放在 provider 适配层，使非法成功响应能进入现有 LLM 后备；仅在最外层 QaRerankService 检查会错过该后备机会。不同供应商的值域须显式声明，不能无条件把全部模型限制成已经校准的 0 到 1 概率。[S23]

EvidenceSufficiencyJudge 删除 MODEL_SCORE_FLOOR 对来源的猜测、WIKI_SCORE_SCALE 的无条件除 100，以及按任意 degradationReason 后缀跳过全部评分的做法。真实的 0 和 0.01 都属于真实分数，不能因为较低而变成 ABSENT。NOTE 来源级重排失败也不能使成功的窗口级重排失去约束。[S12]

现有 0.15 和 0.35 阈值只能用于明确声明同一分数范围的模型契约；新 provider 或 LLM 后备不应仅因同为 0 到 1 就被当作已经校准。可以保留当前已知模型的策略，其他来源仅提供排序，充分性结论来自最终正文的判断。缺少重排分数本身不构成充分性的证据，但已经执行的正文 judge 仍可判为 SUFFICIENT；NOT_RUN 不得被解释为 SUFFICIENT。

### 3.4 元数据不得另带一份回答事实

NOTE 的 recallPlan、WIKI 的完整 context 列表属于检索过程信息。compose 必须从最终 evidence 重建可用正文和来源列表，不能从未经最终选择的快照里继续读摘要。检索 trace 保留候选 ID、分数、状态和失败原因；失效日志只留审计所需身份和原因，不给生成模型提供其标题或正文作为背景。

可以保留现有 SnapshotCodec 过渡，但必须在最终选择后重建为 selected-only 内容，并限制字段白名单。后续可直接让 compose 读取 EvidenceBundle，从而消除 metadata 中的正文副本。不要将整个 metadata Map 原样写入新的持久化字段。

### 3.5 资格校验覆盖权威身份和版本

候选排名前先进行成本可控的有效性过滤；最终正文回填时再验证完整身份。QA、NOTE 检查 workspace、source、snapshot、chunk/window、当前可用性和生成来源依赖资格；WIKI 检查 workspace、当前知识版本及该版本的全部来源依赖。

检索开始与模型调用之间可能经过多个网络调用。冻结草稿前和实际调用生成模型前，应针对最终少量证据再做一次当前资格检查。如果某条已选证据失效，不能只隐藏引用卡片、继续使用旧草稿正文；本次运行应终止或重新编译整份证据与提示。首版建议终止并给出资料已变化的明确原因，避免在同一运行内静默换资料。

模型调用前最近一次资格复核作为发送判定点，用于关闭已知的旧草稿继续生成路径；它与实际外部调用之间仍有并发间隔，不能声称一个本地检查提供跨系统原子撤销。完成写回前的运行状态检查处理删除后的晚到写入。两者用途不同，不能用一个 hash 或一次检索时检查替代。[S05] [S06] [S13]

## 4 QA 的具体修改

### 4.1 Q01 将邻块与主块的引用身份分开

QaHybridRetriever.trimmedEnrich 会在主块前后各补最多 300 字邻块文本；toChunk 仍使用主块身份，邻块 ID 仅在 matchReason 中出现。EvidenceCitationAssembler 则把拼接正文和主块 source_chunk_id 绑定，引用预览还可能主要来自上一块。该问题由代码路径直接成立。[S14] [S15]

首版采用最小修改：停止把邻接块正文注入主块 excerpt；主证据只包含其自身权威正文窗，MMR 和 token 预算也按该正文窗计算。邻接信息可以保留为诊断和后续候选线索。

若保留相邻块阅读能力，必须把邻块转成独立证据，携带自己的 chunkId、snapshotId、窗口和引用编号，并参与相同预算。不能仅补一个 previousChunkId 字段而仍把混合正文保存为主块引用。两种实现择一，本文件默认采用主块独立正文方案，以缩小首次修改范围。

### 4.2 Q02 统一 judge 和生成看到的内容

删除 EvidenceSufficiencyJudge.hitText 对字符串标记的补救解析，删除 judge 的每条前 800 字二次裁剪，以及 QaAnswerModeStrategy.compose 的前 900 字二次裁剪。改由正文窗口构造器一次产生已限长的 excerpt，预算、judge 和 compose 都消费该内容。引用卡片仍可显示 360 字预览，但预览必须是同一 excerpt 的子串，完整定位通过 manifest 中的 sliceRef 获取。[S12] [S16]

如果判断模型输入总预算小于生成预算，应提前在统一选择阶段缩小证据集合或正文窗，再冻结。不能让 judge 与生成各自截取不同内容，同时把判定结果称为针对最终答案证据的充分性判断。

移除旧字符串标记解析前，要转换所有会进入新 Judge 的 QA 生产者。HybridScopedPassageSearch 使用 QaHybridRetriever 的无 profile 重载，当前属于 V2 兼容路径；它不能继续输出旧的邻接拼接正文给新消费者。可以加显式旧版本适配，不必把所有无 profile 调用改为 CURRENT 而改变既有行为。

### 4.3 Q03 保留实际评分和降级来源

修改 QaRerankService.rerank 的未评分尾部处理，删除 minScored - epsilon 人造分数。修改 QaHybridRetriever.toChunk 及 QaPassageRetriever 的结果适配，继续传递 fallback 标志、实际模型和阶段。QaPassageEvidenceRetriever.toEvidence 将这些字段写入 scoreInfo，并保留 MMR 选择顺序。[S11] [S14] [S17]

对于请求 top 40 而融合池最多 100 的情况，其余候选可能没有返回真实分数；top 40 也不必对应融合数组的前 40 项。这属于正常接口情况，未评分项可以作为融合降级候选，但不应伪装成已被模型判为高分。全部重排失败时，已有 QA_RERANK_UNAVAILABLE 仍保留；诊断原因不能代替每条证据自己的评分来源。

### 4.4 Q04 修正查询改写回退和多分支融合

QueryRewriteService.rule 在追问回退时应使用已冻结的 topicAnchor 构造最小完整问题，保持关键词、向量和重排通道中的实体一致。只能使用当前会话冻结上下文中已有的实体；缺少可用锚点时保留原问句和降级原因，不让规则自行补概念。首轮无需模型改写的现有优化保留。[S18]

QaHybridRetriever 执行每个实际查询时统一封装 branchId 和 channel，并在收到该渠道结果后赋 localRank。规则扩展与 LLM 改写提供的 alternatives 两条入口都要覆盖，不能只改负责产生查询文本的 QaQueryExpansionService。QaRrfFusionService 使用各列表的局部排名累计贡献，不使用 mergeDistinct 后的拼接数组位置。扩展总权重先固定，再分给有效分支；增加改写数量不能自动增加这一路的总票数。重复文档仍保留其在多个列表中的贡献，最后按规范身份去重。[S19] [S20]

低召回扩展的触发数量应基于已通过当前版本与资格过滤的候选池。否则旧索引返回至少 3 个无效候选，就可能阻止扩展而最终得到空证据。首版继续保留数量触发策略，不额外引入查询规划 Agent。

### 4.5 校验 ES 命中与最终正文的关系

目前身份回填并不读取或校验 ES content 对应的权威正文。如果 ES 内容发生漂移而身份字段不变，最终可能使用索引正文。该问题需要索引与权威库不同步的前提，不能写成正常情况下必定发生。[S21] [S22]

正常新路径采用：有效性过滤、有上限的候选池从 source_chunk 回填原文、构造最终正文窗、重排、MMR、公共预算。优先采用权威回填，因为 NOTE 本来已有相近机制；具有可靠 hash 时也可验证索引正文后使用。只有兼容旧路径或异常漂移处理中，才需要对正文发生变化的有限池重新重排或丢弃旧评分，不能让正常路径普遍做两次重排。

### 4.6 QA 应保持的行为

继续允许向量或词法单通道明确降级；两路均不可用时明确失败。ES 关闭时不引入隐藏的全库 SQL RAG 兜底。must_terms 在当前改写契约中属于加权线索，不应未经产品语义变更直接改成硬过滤。生产词法召回来自 ES，不要把未处在该路径上的本地 Bm25fScorer 当成生产 QA 实现。

## 5 NOTE 的具体修改

### 5.1 先把资料版本贯穿召回和精读

ES NoteSourceHit 已携带 sourceSnapshotId，但 NoteRecallRetriever 只留下 sourceId，CandidateSource 也没有快照字段。当前版本回填能挡住旧窗口直接进入最终证据，却不能证明旧 ES 命中分数适用于新版本；多次窗口身份查询之间也可能发生版本切换。这是更新或索引滞后条件下的风险。[S24] [S25]

给真实取证 CandidateSource 增加 sourceSnapshotId，repository 回填实际 snapshot ID，所有 withX 方法保留它。精读入口接收 SourceSnapshotRef，身份和正文查询都限定该快照。ES 排名命中必须与当前 source 和 snapshot 一致；标签、日志这类源级线索可回填当前版本，但应标明其属于找资料的提示。

将 ReadingRetriever、ReadingPlanner、融合去重和 anchor 引用使用的内部 key 统一为 sourceId、sourceSnapshotId、chunkId、windowNo。保留外部 note-window:chunkUUID:windowNo 的证据 ID 兼容；source_window.id 继续用于 SQL 行定位，不能取代 chunkId。仅供关系预览的 CandidateSource 不得为凑字段伪造 snapshot，宜改用独立的轻量预览对象。

### 5.2 N01 正相关之后再降权

NoteJournalRetriever.sourceSignals 先计算相关性，再对 stale-source-updated 执行 Math.max(1, value / 2)。原分数为 0 时会变成 1；该正分还可能占用日志来源配额。修复只需先排除 value <= 0，再对正分做 freshness 折扣。保留正命中最小值可以作为取舍，但不能从零制造命中。[S26]

当前 stale-source-updated 表示引用来源更新，不等于日志随自然时间变老。当前查询取全部 NOTE，NoteJournalHit 也没有明确的日志类型和事件时间，因此本轮必改项只修来源版本折扣，不能宣称已经实现日志年龄衰减。年龄衰减作为另列的产品策略，必须先有可靠的 JOURNAL 类型和 eventAt；缺失时不得从标题猜日期，也不得让所有稳定知识笔记一律变旧。之后年龄系数才作用于已相关且可召回的日志提示，随年龄单调不增，明确时间范围先过滤；半衰期由业务约束确定。

### 5.3 N02 固定身份分配和正文装载顺序

RetrievalHydrator.fairAllocate 先按锚点优先级和来源轮询分配，随后又按来源顺序、chunkNo、windowNo 重排；hydrateWindowBodies 则直接按无 ORDER BY 的 SQL 返回顺序扣正文预算。6 个精读来源各最多 24 个身份，而正文默认最多装 96 个，预算不足在现有参数下就可能触发。[S21] [S27]

loadWindowIndex 接收有序 SemanticChunkAnchor，保留每个语义命中的名次和来源快照。先为每个来源保留高优先级锚点，再按现有配额轮询；返回前不重新排成文档位置顺序。正文 SQL 可以继续批量读取，但先构建 windowId 到 body 的映射，再按身份分配顺序消费保留字节和窗口数量预算。

两类顺序要分清：相关性和配额顺序决定谁获得正文预算；原文 chunk/window 顺序只用于判断真实邻接和展示上下文。语义身份预查询也不能在丢弃语义名次后只按文档位置截断，否则高相关但靠后的窗口会在重排前消失。

预算只限制保留正文时，不应宣传它也限制了 JDBC 已传输字节。维持现有分批查询的扫描边界，并将本次 usage 随 BodyLoadResult 返回，替代共享 lastWindowLoadUsage，防止不同请求的诊断数据相互覆盖。

### 5.4 空正文不得占用窗口角色和证据配额

NoteReadingRetriever 对未装载正文使用 getOrDefault(id, emptyString)，后续仍可能凭 heading 或 chunk 语义分获得主窗口角色。修改为只有实际装载且非空白的正文才能构造 ReadingWindow；兼容方法 hydrateNoteWindows 同步处理。超过预算或单窗大小的身份记录 omission reason，不变成零成本证据。

EvidenceBudgeter 增加非空正文检查作为最终防御，但不能只在最后过滤，否则 planner 和 top 8 名额已经被空对象消耗。该修复与前一节的顺序修复同时完成。[S27] [S04]

### 5.5 N03 保留窗口重排顺序和部分返回的真实状态

NoteReadingRetriever 返回按重排顺序排列的窗口，ReadingWindow.withRerankScore 保留旧 fusedScore；NoteEvidenceRetriever 再把该旧值交给公共预算器，导致最终顺序被覆盖。修改 toEvidence 使用已经确定的 selectionRank，旧分数仅用于诊断。[S27] [S28] [S29]

窗口重排要求前 8 却只返回 2 条时，当前实现直接只保留 2 条。新增 WindowRerankResult.partial 和每条 scoreInfo；在验证返回项后，按 planner 原有优先顺序补未评分候选至上限，显式标为未评分。不要给补齐候选制造接近高分项的分数，也不要让公共预算再次把它们排到已评分项前面。

源级重排失败、窗口级重排成功必须分别表达。最终充分性读取窗口 Evidence 的评分来源，不能因为 bundle 里有 NOTE_SOURCE_RERANK_UNAVAILABLE 就跳过全部分数约束。源级重排已有未评分尾部保留行为，不要误修成来源和窗口两层一律清空。

### 5.6 N04 让日志和关系图只参与合格召回

NoteAnswerModeStrategy.compose 从最终 Evidence 生成资料定位和摘录证据；移除 recallPlan 中未选来源的摘要和全部审计用失效日志标题。NoteJournalRetriever 先读取 Note 版本绑定的来源，再把来源引用交给 MaterialEligibilityPort，不能直接把 noteId 当 sourceId 评估。历史详情页是否可看另按 HISTORY_DISPLAY 处理，不能因为历史可看就继续影响当前回答。[S02] [S26]

本文件选择找资料的弱提示语义：所有绑定来源当前都具备 CURRENT_EVIDENCE 资格时，旧 Note 可按版本差异降权，用来定位当前资料；其旧摘要或正文不作为回答事实，最终窗口必须重新绑定当前 snapshot。任一来源当前不可用则整条 Note 不参与该召回信号。这里评估来源当前资格，不要求旧 Note 的绑定快照也等于当前；若改成严格快照相等，stale-source-updated 提示就会被直接排除，应同步删除无效的降权分支。WIKI 页面正文属于编译事实，仍必须执行严格绑定快照检查。

关系图共引查询同样限定可参与召回的 Note 集合。如果一个 Note 引用 A、B、C，而 C 已不可用，应按统一资格规则处理该 Note 的关系信号，不能让来源信号入口排除它、图入口却继续利用它。这里修的是召回资格一致性，不宣称 C 的原文已越过 source guard。

运行时诊断保留 noteId、versionId、原因和分数即可。MetadataEntry 的主链预览正文如果后续没有消费，应取消该次装载；这可以随 prompt 改造一起减少正文副本和无用读取，无需新增审计系统。

### 5.7 N05 用真实边界判断跨块续读

NoteReadingPlanner 从裁剪后的候选窗口计算 maxWindowByChunk，再据此判断跨 chunk continuation。若真实窗口为 0 至 8，候选只包含 0 至 2，窗口 2 会被误当末窗。该错误需要候选缺窗触发，但判断依据本身不正确。[S30]

WindowIdentity 增加从完整 source_window 集合取得的 lastWindowNo 或 windowCount。跨块续读要求同 source、同 snapshot、连续 chunkNo、真实末窗连接下一块 window 0；anchor 必须保存完整 NoteWindowKey，不能只保存 anchorWindowNo。

最小替代是对无法证明真实边界的情况只保留同 chunk 的 windowNo 加减 1，不做跨块 continuation。二者都比从有界池推测原文末尾正确。本文件建议在身份查询中同时取得真实边界，保留原有连续阅读能力。

### 5.8 N06 统一词项并补齐有界关系查询

LexicalTerms 为中文生成二字词，NoteRecallRetriever.addExpansionTerm 却拒绝不足三个汉字的词，纯中文标题和摘要无法贡献这条扩展通道。修复为接受当前分词器真正产生的中文二字词，并统一 NoteJournalRetriever 与 NoteRelationGraph 的归一化和停用词口径。标签保留完整标签，不需要全部切成二字词。[S24] [S26] [S31]

直接候选最多 200，再加最多 80 个关系候选，但 NoteRecallRepository 两个共引查询各只取前 200。应对完整的有界 loadedIds 分批查询，按 noteId 或 messageId 合并来源集合后，再统一建图。不能每批单独建图再合并分数，否则跨批共引仍会丢失。保留总量边界，不引入全工作台无界扫描或图数据库。[S25]

当前只从最近 31 条 Note 再做匹配，是有界扫描策略，会漏掉更早相关记录，但不能简单称算法错误。若产品要求回忆旧日志，可以在既有数据库查询中加入有界的关键词和日期候选入口，再沿用同一资格门禁；无需为这一点先增加新的长期记忆通道。

## 6 WIKI 的具体修改

### 6.1 W02 让编译材料与登记依赖完全一致

WikiIngestService 的来源页读取最多 5 个 chunk，正式引用只建立前 3 个；概念页可能给 WikiConceptWriter 和关键依据段提供 6 个 chunk，引用只建立前 4 个。若第五或第六个 chunk 提供了事实，该事实缺少正式 chunk 依赖；如果它来自另一资料，来源撤销检查还可能漏掉该资料。[S32] [S33]

新增仅在编译过程使用的 WikiCompilationEvidenceSet，冻结 sourceId、snapshotId、chunkId、正文和版本。模型输入、模板里的关键依据、知识版本 citation 注册都由同一集合产生。首版保留当前 5 和 6 的输入数量，登记全部有效输入依赖；若决定减少输入，必须同时缩小三个消费方，不能只截引用数组。

还要登记写入页面的 source.summary 和 relatedSources.summary 所属来源快照。只补齐 chunk 引用仍可能漏掉这些来源级文字。V213 已允许 citation.source_chunk_id 为空，可复用 citation 登记来源级依赖，不必新建命题图或新的血缘数据库。源码所需依据：编译输入里每一份事实文字，都能关联到本次冻结的来源身份。

KnowledgeQueryService 的页面 context 加载还会把 citationsForVersion 截到 5。必须将展示预览数量与完整依赖清单分开：UI 可预览前几条，知识版本资格、回答引用绑定和删除反查必须使用全部引用。ChatService.selectedWikiCitationIds 始终从最终版本对应的完整清单收集并按 ID 稳定去重，取消依赖两个列表顺序相等的快路径。

summaryFingerprint 和 conceptFingerprint 加入编译策略版本、完整来源快照身份和实际输入摘要值。新规则不能通过 reusableSummary 继续复用旧的不完整摘要。给新 knowledge_version 写 provenance_schema_version，旧自动版本为空时不宣称已经通过新完整性约束；旧自动页重编为新版本，人工页遵守编辑保护，不凭标题猜补遗漏来源。

依赖登记采用保守语义：凡提供给编译器且可能影响正文的资料，都登记为该版本依赖。正式依赖完整只保证来源可追踪，不等于证明每句话已经被该来源蕴含。WikiConceptWriter.accepted 当前没有引用标记也可以通过；可要求存在有效引用标记并校验其集合，但不能把这一格式校验宣称为事实核验。

### 6.2 W03 按来源与快照判断当前证据资格

KnowledgeCitationReadGate.versionSourceAvailability 只取 citation.source_id，再用 internalSource 评估，丢掉 citation.source_snapshot_id。MaterialEligibilityAssessor 只有收到绑定快照时才能识别 STALE_SNAPSHOT。故资料从 S1 更新为 S2、知识页仍停在 S1 时，最新知识页版本仍可能被当作当前证据。[S34] [S13]

首版不改全局 OriginRef.originKey，避免破坏按 sourceId 取结果的其他模块。读取版本全部 citation 的 sourceId、snapshotId；按 sourceId 去重后分批评估当前来源资格，再用共享纯函数比较每条绑定 snapshot 与 EligibilityDecision.snapshotId。CURRENT_EVIDENCE 和 REPUBLISH 要求来源资格通过且版本相同；缺 snapshot 按不可取证处理。HISTORY_DISPLAY 继续使用已有历史展示政策。

只把 internalSource 换成 internalSnapshot 并不够：现有 originKey 仍按 sourceId，批量传同一来源的多个快照会覆盖结果。按来源评估再逐绑定快照判断，能在不修改全局 key 的情况下解决这一点。

每批 assess 不得超过 MaterialEligibilityPort.MAX_ORIGINS_PER_ASSESS 的 200 条。先去重、分批、合并决定，再按每个知识版本求所有依赖均可用。未知资格、缺失依赖和解析失败不能默认为可用。[S35]

provenance_schema_version 是自动编译页的当前证据准入条件，不只是审计标签。自动页仅在完整性版本受支持、全部依赖合法且当前时进入 CURRENT_EVIDENCE 或 REPUBLISH。旧自动页即使已有少量 citations 全部通过，也不能自动视为完整。人工页面是否允许作为独立的无来源知识由明确的 origin 和产品政策决定；没有 citation 本身不能证明页面是人工创建。资料编译型 WIKI 回答不应因该兼容分支绕过资料溯源要求。

### 6.3 不把编辑保护状态改成资料失效状态

knowledge_item.status 的 ACTIVE 和 wiki_page_state 的 AUTO、MANUAL、NEEDS_REVIEW 有各自用途。findWikiItemIdBySource 和 findWikiItemIdByTitle 只找 ACTIVE；autoUpdatable 只允许 AUTO。把它们直接改成 STALE，会让 ingest 找不到原页或不再自动更新，甚至新建重复页。[S36]

保持页面编辑身份和 latest_version_id 的语义；证据资格按版本依赖独立计算。当前编辑版失效时不自动回退到更老的知识版本。AUTO 页可通过既有 ingest 产生新版本；MANUAL 或 NEEDS_REVIEW 页保留人工编辑保护，同时明确当前版本暂不可作为证据。

新版本发布时，正文、summary、全部 citation 关系、页面链接、latest_version_id 和索引 outbox 必须在既有版本发布事务中一致更新。不要先把旧页重新标为可用，再等待引用补齐。

WikiCompilationEvidenceSet 还需 inputHash 和 baseKnowledgeVersionId。文本在事务外生成；发布时按固定顺序锁定相关来源和页面，重新核对所有冻结来源的当前快照、资格和输入 hash，以及基础页面版本与编辑保护状态。任何条件变化都结束旧编译，不发布旧输入生成的正文。写入原子性与生成期间材料仍然有效是两个独立条件。

### 6.4 W04 将 Wiki Index 限定为导航材料

refreshWorkspaceIndexPage 复制 ACTIVE 页的 summary，但只给目录页登记最近 4 个工作台 chunk 的引用；这些 chunk 不能代表被复制摘要的来源。loadActiveWikiPages 也未按来源可读性筛选。仅完善普通概念页引用，无法解决这一条摘要复制路径。[S32]

采用最小方案：为系统生成的目录页设置明确的 NAVIGATION 用途，排除其作为检索种子和 PPR 证据节点的资格；目录正文不再复制页面摘要，也不再绑定任意最近 chunk 充当依据。导航只保留合格页面的标识和标题，以及不用于事实回答的工作台统计。

导航用途不要复用 AUTO、MANUAL、NEEDS_REVIEW。首版复用已有 knowledge_item.origin 列，新增明确的 SYSTEM_NAVIGATION 值；不能仅以用户可重名的标题 Wiki Index 判定。存量只对标题和系统生成标记共同确认的自动目录页赋该用途。已复制的摘要应从当前和可访问的历史目录正文、缓存中清除，保留纯导航版本。若将来确实需要目录参与回答，则须登记 pageVersion 依赖；本轮不引入该更大改造。

### 6.5 W05 先筛有效页面再计算有效排名

KnowledgeWikiSearchEngine 的词法路径先对 ACTIVE 页计算 BM25F、邻居传播和相对阈值，再由 KnowledgeQueryService 过滤不可读页。高分无效页可能抬高阈值，使有效页在资格过滤前就被淘汰。混合路径中，页正文也可能先进入 reranker 再被资格排除。[S37] [S38]

调整顺序为：有界召回身份、加载当前页身份与依赖、批量资格过滤、回填合格正文、重排与有效排名，再选种子。词法降级仍然限定有界页面集合，但该集合上的阈值和邻居信号只来自当前可取证页。过滤后候选不足可从同一通道继续有界补取，不能把不合格页重新放回，也不能改走 QA。

先完成来源资格分批和页面用途判断，再前移过滤。否则最近 500 页的词法降级或图端点聚合，可能一次提交超过 200 个来源，触发接口异常。

### 6.6 W01 将种子上限与总候选上限分开

WikiAnswerModeStrategy 把 Step.candidateLimit 设为 5；WikiEvidenceRetriever 用它选择 5 个种子，WikiGraphBudgeter 先放入全部种子再追加扩展。RetrievalOrchestrator 对返回列表又 limit 5。种子达到 5 个时，扩展正文全部被截掉，后续 maxEvidence 为 35 也无法恢复。[S03] [S39] [S40] [S04]

新增经过校验的 WikiRetrievalLimits：seedLimit 为 5，expandedCandidateLimit 为 30，Step.candidateLimit 为两者之和 35。seedLimit 从独立配置或 Step filters 的类型化解析结果读取。禁止只把旧 candidateLimit 从 5 改成 35，否则种子数量也会膨胀为 35。

WikiRetrievalQueryPort 和 KnowledgeQueryService 的种子返回数量也要显式接受 seedLimit，处理内部硬编码 limit 5。旧签名可委托 seedLimit 为 5，新调用不能被默认方法悄悄忽略。WikiAnswerModeStrategy.compose 按最终 bundle 的版本 ID 顺序恢复页面，不能继续只对原 snapshot 顺序做过滤。

最终证据数仍受正文预算约束，35 是候选上限，不是承诺每次向模型发送 35 页。种子保留自己的重排顺序，扩展页保留自己的 PPR 顺序；采用明确的组内顺序和分组预算，不用两种原始分数相互比较。首版可保持种子优先、合格扩展随后，记录 evidenceRole 和 selectionRank。

该项必须在 WIKI 正文预算和图工作量上限修复之后生效。否则原来的 limit 5 一撤销，就会放大被它掩盖的正文预算偏差。

### 6.7 W06 同时限制图探索和最终图证据

当前图预算在 expand 返回后才裁返回节点、边和字符，不能限制此前探索过多少邻居。高出度页面可能在 3 跳内访问远多于最终 30 个节点的图。保留 hops 限制，同时给 PPR 图构造传入累计 maxExploredNodes 和 maxExploredEdges；每层查询前计算剩余额度，达到上限停止扩展并记录 GRAPH_EXPLORATION_TRUNCATED。最终证据节点预算和探索工作量预算分开命名。[S40] [S41]

图查询、可读性检查和入度修正必须使用同一合格节点集合。不可用节点不提供正文，也不应通过未过滤的入度统计改变可用子图的惩罚项。保持确定的邻居读取顺序，使有限预算下不会仅由数据库行序决定被探索的边。

探索额度必须下沉到 AdjacencySource.linksTouching：接口接收剩余边数与分页游标，SQL 以稳定顺序和实际 limit 返回有界边，不能先一次载入整个高出度邻接再截内存列表。每批 frontier 最多 50 个 ID 不等于最多返回 50 条边。资格检查也受整次请求累计额度约束；扩展节点、边或正文预算任一为 0 时直接跳过图探索。

WIKI 的 RRF、BM25F、rerank 和 PPR 继续保留各自 double 值，不提前乘 100 取整后塞入同一个 score。只有最终页级真实模型评分进入 scoreInfo；PPR 只负责扩展组内排序，不进入充分性模型分数阈值。相应删除 Judge 中按知识页统一除 100 的逻辑。

PPR 的 seed 重启权重也必须读取明确的内部 seedWeight，首版可由种子排名转换成正权重。KnowledgePageHit.score 若为公开展示保留整数兼容，不再作为 PPR 输入。这样可避免展示取整或供应商评分量纲改变图随机游走的重启分布。有限探索子图上的 PPR 也不宣称与完整三跳图计算完全相同。

### 6.8 W07 预算按实际页面证据块计算

WikiEvidenceRetriever 当前在有 summary 时用 summary 作为 excerpt 和 cost，compose 却另外读取最多 300 字摘要、1,500 字正文和关系内容。当前 5 条截断会掩盖部分规模影响，但语义已不一致。修复为先构造最终 WikiPageEvidenceText，再让预算、Judge、compose、manifest 共享它。[S39] [S03]

页面正文内已有的 [[页面名]] 可能指向未选页面。进入回答提示前，将这些原文导航链接转成普通文本；只为最终选中的知识版本分配可引用标识。关系路径用于解释选中页面为何出现，不能让未选路径节点自动成为可引用证据。新增正文和链接包装都计入预算。

### 6.9 绑定任务源版本并拒绝旧投影排序复用

Wiki ingest 的排队入口校验 snapshot，但后续消费和 runSourceIngestNow 没有始终把该 snapshot 作为读取条件；部分 chunk 查询只限定来源。存在多代资料或旧任务重试时，就可能用一个任务身份读取另一代正文。将 snapshotId 作为任务载荷和执行上下文的必需字段，贯穿 ready intent、KafkaTaskConsumer、WikiIngestService 和 chunk 查询；任务快照已过期则结束旧任务，不把它改解释为重建最新资料。[S32] [S42]

统一执行命令还携带 taskId、workspaceId、sourceId、ingestPolicyVersion 和 deliveryGeneration。READY、手动重建、同步执行、补偿任务、撤销后逐源重编都使用同一命令；概念编译冻结所有参与来源的 source 到 snapshot 映射，不能只约束触发任务的主来源。发布前按第 6 3 节再核对全部参与来源。

Wiki ES hit 若未携带 page version，旧索引名次可能被应用到 DB 最新正文。为 WikiPageIndex.Hit 补 indexedVersionId 和 indexedGeneration，与 DB 的 latest_version_id 和 index_generation 核对。重命名等操作可以不改变 versionId，所以只检查版本还不完整。不一致项从当前请求剔除或对当前有限正文重新排序，并由现有 outbox 修复投影；不能沿用旧匹配结果冒充新版命中。

WikiIndexOutbox 当前的 pending 去重和 backfill 主要识别 item、operation 和 versionId。新增同版本资格变化投影时，要复用 index_generation 表示新的目标，旧在途任务不能吞掉更高代次的失效更新。来源资格变化应明确入队；不能指望同版本已存在 SENT 或 FAILED 记录的 backfill 自动恢复。沿用现有租约、CAS、外部版本和墓碑，DB 资格门禁继续覆盖异步投影传播窗口。[S43]

## 7 回答生成与引用必须消费同一份冻结结果

### 7.1 C03 把模式提示和引用集合带到真实模型调用

ChatService.buildAnswerDraft 验证 PromptSpec 后，只把 userPrompt 放入待生成草稿；ChatAnswerGenerationAdapter 再使用自己的固定 systemPrompt。模式策略提供的 systemPrompt 没有进入真实生成调用。这是提示契约被丢弃，并不能据此直接断言模型已经生成了错误答案。[S05] [S44]

新增轻量 GenerationContract，包含 schemaVersion、mode、promptVersion、systemPrompt、refusal、allowedEvidenceIds、citationBindings、evidenceBundleId 和 evidenceTextHashes。userPrompt 正文仍使用现有冻结草稿，不在这个 JSON 中再复制一份。AnswerGenerationMaterial 携带该契约；AnswerGenerationGateway 和 adapter 消费真实模式提示，公共通用规则按固定顺序拼接，不能覆盖模式约束。

契约在最终证据选择、充分性处理和 PromptSpec 验证之后生成。allowedEvidenceIds 取最终 PromptSpec.referencedEvidenceIds，并校验它是最终 bundle 的子集；refusal 时必须为空。完整已使用材料的审计依赖与允许在最终文本里引用的集合分别保存，不能因后端登记过材料就允许模型引用任意候选。

### 7.2 显式绑定引用身份

EvidenceCitationAssembler.persist 由返回数量改为返回 CitationAssemblyResult，其中包含 citationId、evidenceId、顺序和源身份。QA、NOTE 的一个 Evidence 绑定其真实 source chunk 和可选 window 定位；WIKI 的一个 page version 可绑定多个来源 citation，不能强行做一页一来源。

ChatService.bindExistingCitations 接收最终版本对应的完整引用 ID，去重后按稳定顺序绑定。提示拒答时不再为其绑定可引用页面标识。生成契约同时保存 evidenceId 到知识版本及其完整来源引用的映射，使引用展示和删除都可以按身份处理。

前端当前 buildCitationViews 先按标题、再按排名猜测引用对应的 manifest。对于同标题、多窗口或 WIKI 页证据对应多个源引用，这种关联不够严格。新回答应直接使用 CitationBinding；旧回答继续保留旧解析，但显示为旧协议，不能从标题推造不存在的精确版本关系。[S15] [S45]

### 7.3 复用已有证据角标而非再做一个引用组件

MarkdownSurface 已支持 [evidence:ID]、evidenceOrder 和 onEvidenceClick；MessageBubble 的聊天正文目前未接通这组属性。新契约回答使用该已有语法，服务端只允许本次 allowedEvidenceIds。MessageBubble 连接 manifest 中的顺序与身份，引用点击展示指定 Evidence；WIKI 展示 knowledgeVersionId，不按标题临时打开最新页作为当时证据。frontend AnswerEvidence 类型补齐后端已有的 sourceSnapshotId 和 knowledgeVersionId。[S46] [S47]

绑定还必须通过协议真正传到前端。AnswerEvidenceManifestResponse 增加 protocolVersion、allowedEvidenceIds 和 citationBindings；新协议在首个正文 delta 之前发送由冻结契约生成的 evidence.ready 元数据事件，包含白名单、证据顺序和绑定。新订阅、重连、已完成回放都先提供相同绑定，不能依赖 MessageBubble 在生成结束后才加载 manifest。前端 answers/api、model、store 解析并保存新事件；legacy citation.upsert 文本事件继续兼容，不把旧文本解析器偷偷改成对象解析。

MessageBubble 在新协议下显式传 compactCitations=true、evidenceOrder、onEvidenceClick，不再用旧 citations 数组自动激活任意数字角标。MarkdownSurface 在创建角标按钮前验证 ID 属于该运行的允许集合，未知或尚无绑定的 ID 不生成可点击按钮。细节面板可按需加载 manifest 正文，但渲染身份和顺序在流式开始时必须已知。[S57]

页面原文内的 [[未选页面]] 在证据文本构造时变为普通文本，不进入引用集合。可继续提供普通 Wiki 导航，但导航链接与回答的证据角标必须分开解释。模型看到过某个页面名称，不等于这页已被选中并验证。

### 7.4 输出检查必须位于流式发送之前

当前输入引用集合检查发生在生成前；adapter 只对最终非空文本进行校验，AnswerRunService.complete 也不验证模型写出的引用标识。模型可以输出不存在的编号或未选页面名，而运行仍完成。该缺口影响回答文字的引用约束，不表示模型能直接插入任意数据库 citation。[S44] [S48]

新增 CitationTokenValidator 或等价的窄解析器，在 tokenConsumer 和 BufferedAnswerDeltaEmitter 之间工作。解析器只对当前协议的引用标记作身份检查：标记可能跨多个 token，需要暂存未闭合部分；设定最大标记长度，防止无限等待。合法标记绑定到已冻结 Evidence；不认识、越界或引用已撤销证据时停止本次生成并返回明确错误，不能直接透传后再期待最终检查撤回已发送文本。

服务端和 MarkdownSurface 采用相同的有效引用位置规则：代码块、行内代码和转义字面量里的协议文本不生成引用，也不因未知 ID 直接终止。普通正文里的引用前缀到流结束仍未闭合时，返回 ANSWER_CITATION_INCOMPLETE，暂存部分不作为合法角标发送；完整检查沿用相同规则，不能另外生成一份修补后的不同正文。

冻结白名单只表达本次允许的身份，不感知后续撤销。生成器需接入运行级取消和撤销状态，并在 BufferedAnswerDeltaEmitter 实际 flush 到发送端之前检查；已经缓冲的内容也要受该检查约束。该机制阻止已知撤销后的后续发送和提交，不能撤回已经发送的字节，也不把本地检查描述为跨系统原子发送协议。

正文结束后再执行一次完整引用语法和集合检查，保证流式内容、最终返回字符串和持久化字符串一致。若客户端 stream 返回值与回调累计文本不同，应以经过同一校验器的规范文本为准，禁止将一份未校验的完整返回值另外写入数据库。

对新协议，不再将任意 [37] 或 [[标题]] 自动当作有效证据角标。旧格式的兼容渲染也应验证编号范围；未知标记展示为普通文本或无效引用，不能生成看似有效的来源按钮。引用白名单保障出处身份，不能证明每一句话都被对应资料语义支持；本轮不引入新的事实核验 Agent。

### 7.5 C04 补全删除和晚到写入处理

现有 ConversationMessageDeletionService 会清消息、覆盖摘要和约束，并调用快照脱敏；ChatAnswerGenerationAdapter.persistContent 也避免恢复已删 conversation_message。但是 message_revision、已持久化 citation.upsert 事件和回答 manifest 仍有独立正文副本，complete 的状态推进不等于这些副本已经清空。读接口用 CASE 隐藏正文也不等于物理抹除。[S49] [S50] [S48]

删除消息时，先通过 messageId、queryMessageId、assistantMessageId 和现有快照引用找到受影响 answer run，再使用一致的锁顺序处理 conversation 与 run。运行变为终态或增加拒绝写入的撤销标记，撤销当前 stream owner；随后清理该消息及其受影响运行的草稿、message_revision 正文、manifest excerpt、消息专属引用副本、含引用正文的事件和新增契约中的可显示文本，只留下身份、版本、原因和必要计数。

citation 可能被 WIKI 版本或其他消息共享。删除一条消息时先解除其 message_citation 绑定，只对不再被其他合法对象使用的消息专属 citation 清正文或删除；同时清理该运行自己的 manifest 和引用事件。不能为删除一条消息而全表清空仍被其他页面使用的主引用行。

共享引用的独占判断与新增绑定必须互斥。bindExistingCitations、知识版本引用注册和清理入口按同一顺序锁定相关 citation 行，再检查完整使用关系并决定是否清理。无法证明独占时只清运行专属副本，不因某个瞬间引用计数为零就清中央 citation；同时保持既有外键关系有效。

晚到生成写回应在同一收尾事务内检查 query 与 assistant 消息未删除、运行仍可提交、stream owner 有效、证据未被撤销，再写 conversation_message 和 message_revision 并推进 COMPLETED。当前先 persistContent 后 complete 的分离写回应收敛到一个有状态条件的完成入口。删除事务和完成事务沿同样锁序串行化，避免删除后又写回正文。流式发送也读取撤销结果，不能仅依靠每 45 秒续租才发现运行已失效。

来源删除还要处理派生 WIKI 证据。WIKI manifest 的 sourceId 为空，只有 knowledgeVersionId；RunReplayRedactionService.redactDeletedSource 只按 sourceId 清理，无法覆盖它们。通过 knowledge_version_citation 和 citation.source_id 先取得所有受影响知识版本，再按 knowledgeVersionId 清理 manifest、待生成草稿和相关缓存。不能先删掉依赖映射再查下游。[S50] [S32]

USER 来源删除继续按既有历史政策保留允许的历史审计，但不得参与当前召回；COMPLIANCE 删除按正文撤销要求清理相关知识版本 content、summary、缓存和引用副本。WikiPageVersionCache 需要按 workspace、item、version 精确失效，等待 TTL 到期不能表述为已经抹除缓存正文。缺失依赖的旧自动页无法靠一条 SQL 精确补回全部血缘，应保守退出当前证据后重编。[S51] [S52]

### 7.6 C05 保持 NONE 模式的版本一致

ChatService 为显式 NONE 创建 none-v1 计划和 bundle。NOTE 的 insufficientPrompt 和 WIKI 的无页面提示使用各自固定 PLAN_VERSION，公共 validator 在检查 refusal 前就会拒绝版本不一致。修改为所有 compose 分支从 bundle.retrievalPlanVersion 取版本，NOTE insufficientPrompt 显式接收该参数。不要放宽 validator，也不要借此增加无资料普通聊天回退。[S05] [S02] [S03] [S53]

## 8 表结构与接口修改

### 8.1 复用现有表并减少正文副本

本轮不增加独立检索库或通用血缘平台。answer_run_evidence_manifest 已有 rank_no、完整证据身份、excerpt、content_hash 和 character_cost；citation 已有 source、snapshot 和可空 chunk；knowledge_version_citation 已能表达一个页面版本依赖多条引用。应优先复用它们。[S54] [S55]

| 对象 | 拟增或调整字段 | 原则 |
|---|---|---|
| EvidenceBundle.Evidence | selectionRank、sliceRef、scoreInfo、evidenceRole | 运行时类型化传递，不再靠 free-form metadata 猜语义 |
| EvidenceBundleSnapshot | schemaVersion 升级并保存新排序和完整 ScoreInfo 含 truncated | 继续排除正文和任意 metadata |
| answer_run_evidence_manifest | source_window_id、window_no、slice_start_utf16、slice_end_utf16、score_origin、score_stage、score_model、model_score、scored_text_hash、evidence_role | 复用 rank_no、excerpt、content_hash；新增字段可空 |
| answer_run | generation_contract_json | 保存提示策略、白名单和绑定，不再复制 userPrompt 正文 |
| knowledge_version | provenance_schema_version | 新自动编译版本显式标记依赖完整性规则 |
| knowledge_item.origin | SYSTEM_NAVIGATION 新值 | 复用现有列，单独识别自动目录页 |
| WikiPageIndex.Hit | indexedVersionId、indexedGeneration | 对齐已有版本和索引代次 |

上述列的名称为建议。固定基线迁移到 V221，实际实现时使用下一未占用 Flyway 版本，不修改已经执行过的迁移。迁移负责结构扩展和可证明的元数据标记，不在迁移 SQL 中调用模型或伪造旧页依赖。

source_window_id 不建议新增强制外键，因为合规删除需要清 source_window，而可审计 manifest 仍需保留窗口 ID。该字段的合法性由写入时完整身份校验保证；删除后身份可保留，正文必须清掉。

slice_start_utf16 和 slice_end_utf16 对应明确的底层文本对象。QA 相对于 chunk.content，NOTE 相对于冻结 window.content；WIKI 多块摘要和正文拼装不应伪装成一个连续源切片，可以仅记录渲染正文 hash、versionId 和完整依赖，直到确有需要再扩展多段定位。

### 8.2 关键接口的拟议形状

以下代码说明字段合同，不是可以直接粘贴替换现有类的完整补丁。

```java

    ScoreOrigin origin, ScoreStage stage,
    String model, Double value,
    String scoredTextHash, boolean truncated
) {}
 
record EvidenceSliceRef(
    String sourceWindowId, Integer windowNo,
```

windowNo、slice 范围允许为空只用于不适用该定位方式的证据类型，不能让 NOTE 缺失 window 身份时默认为 0。ScoreInfo.value 为空表示无实际模型评分；0 是有效零分。模型标识未知时写 UNKNOWN 或方法标识，不编造模型版本。

### 8.3 固定执行顺序

1. 模式内召回与必要前置资格筛选。

2. 按权威身份回填正文并生成可定位窗口。

3. 模式内重排与选择，生成 selectionRank 和 scoreInfo。

4. 公共非空校验、当前身份复核和稳定预算。

5. 根据最终 Evidence 重建模式提示。

6. 充分性处理与 PromptSpec 契约校验。

7. 构建引用绑定与 GenerationContract。

8. 冻结材料及 manifest。

9. 调用模型前复核所选身份和运行状态。

10. 流式引用检查。

11. 同一收尾事务写正文、版本并完成运行。

上面的顺序是修改后的数据流。ChatService 现有充分性判断位于 compose 前，重构时可以继续先 judge 再 compose，只要双方使用完全相同的最终 excerpt，且 refusal 或 PARTIAL 处理之后才冻结 GenerationContract。关键约束是任何后续阶段不得重新添加未经最终选择的事实正文。

### 8.4 旧数据和缓存兼容

旧 EvidenceBundleSnapshot 按原 schemaVersion 读取，新字段缺失标为 LEGACY_UNKNOWN。不要根据旧分数大小反推 scoreOrigin，不把历史 excerpt 换成当前 DB 正文，也不重跑新版检索后改写旧回答的证据身份。

旧自动 Wiki 页的 provenance_schema_version 为空时，不能宣称其依赖完整。当前可用自动页由有身份的编译任务追加新版本；有人工编辑保护的页留在待处理状态。旧源快照不能直接被更新成当前快照来使门禁通过。

旧 ingest 载荷若有已知 snapshot 字段别名，可以显式映射；完全缺少冻结来源身份的旧任务应取消并创建新的有身份任务，或经过明确的受控转换，不能执行时默认补当前最新快照。新完整性门禁消费 provenance_schema_version，避免旧不完整页因部分依赖合法而继续取证。

新增 generation_contract_json 不存在的历史完成回答可按旧协议阅读；正在恢复执行的旧运行必须明确保留旧契约或重新创建新运行，不能拿新策略解释一份旧冻结草稿。新的输入或证据被删除时，新字段须与既有快照一起脱敏，不能只清旧列。

### 8.5 可选索引能力与资料状态

资料解析成功、资料可读、向量就绪、ES 投影就绪是不同状态。现有 ES 关闭路径可以维持资料可读；embedding 关闭而 ES 开启的写入组合仍可能进入要求向量的投影路径并被标失败。同步 finalizer 能观察到该问题，不能据此声称所有异步运行都一定同样失败。[S56]

SourceParseService、SourceRetrievalProjectionService、Coordinator、Finalizer 和 writer 应按启用能力创建投影任务：禁用可选投影记录 DISABLED 或 SKIPPED，资料本身仍为 READY；真实启用能力失败才记投影错误。需要支持 lexical-only 写入时，显式定义词法文档 schema 和 projection 状态，writer 不写不存在的向量字段。不要塞空向量以骗过原有合同。

该项保障资料链状态，不承诺 ES 关闭后 QA 和 NOTE 仍执行完整检索。检索不可用应明确返回当前能力边界，资料阅读接口继续可用。

## 9 建议实施顺序

### 9.1 必须先完成的共同修改

第一步确定最终 Evidence 的唯一正文、规范身份、selectionRank 和 scoreInfo，并同步修改审计 snapshot 和公共 Budgeter。否则 QA、NOTE 各自修好排序后，仍会在公共层被改回旧语义。

第二步修共享 provider 响应校验和充分性分数来源判断，并使最终资格检查复用当前来源政策。真实 0 分、未评分尾部、源级失败与窗口级成功必须能被区分。这个步骤是可信解释重排结果的前提。

第三步分别修 QA 的邻块归因与正文窗、NOTE 的快照身份和正文装载、WIKI 的编译依赖与精确快照门禁。这三条修改在共同契约确定后可以独立落地，不能互相改变证据单位。

### 9.2 WIKI 图扩展的前置依赖

WIKI 必须依次具备：完整编译依赖与导航页分离、受限批量资格检查、实际正文预算、图探索工作量上限、明确的种子和扩展顺序，然后才把总候选上限从 5 的误用恢复为 5 加 30。这些改动属于同一完整修复，不建议只提交一个上限数字。

compose 按最终版本顺序渲染、完整引用绑定进入 GenerationContract，也必须在扩大候选上限之前接通。可以分开提交内部改造，但新的候选数量行为最后生效。既有 4,000 扩展字符预算仍然有效，实际容纳页面少于 30 是正常结果。

### 9.3 生成和删除与新增持久化字段一起完成

GenerationContract、引用白名单、规范最终字符串和有状态完成入口必须与新增持久化字段一起接入。新增任何正文或显示文本副本的同一修改中，都要补上其删除路径；不能先存一份新快照，再把清理留到未来。

消息删除与源撤销需要同时处理正在准备、正在生成和已完成的运行。完整 WIKI 依赖是派生正文清理的前提，来源版本门禁是索引传播延迟期间的保护。三个边界缺一，不能宣称引用与删除闭环已经完成。

### 9.4 后续较小的召回修复

查询改写回退、多分支局部排名、中文词项、280 来源关系批处理、真实窗口边界和部分重排补齐，沿前述接口完成。N01 的零分降权和 C05 的 NONE 版本错误可以独立先修，改动很小且不依赖新的选择算法。

暂不纳入新的多 Agent 规划、跨模式统一检索器、全局命题图和覆盖率训练。这些不是解决本次实现错误的必要依赖。未来若加入维度覆盖选择或研究状态压缩，应建立在本轮完成的证据正文、身份和删除契约上。

## 11 修复后的产品行为与设计说明

QA 回答使用本次选中的资料原文窗口，每个窗口独立关联源快照和 chunk。相邻内容若参与回答，拥有自己的证据身份；相关性排序、充分性判断与引用定位可以解释到具体正文。

NOTE 先用标签、合格日志和局部关联图找到值得读的资料，再按当前快照读取连续窗口。候选线索不直接成为回答事实，来源不可用的日志只保留审计信息；中文词项和配额不再互相抵消。

WIKI 先读取正式编译页的当前有效版本，再沿有界概念图扩展。页面编译使用的材料与登记依赖一致，源更新后旧页停止作为当前证据，图扩展得到的有效页面能够进入最终选择。目录页用于导航，不用无关资料替复制摘要提供表面出处。

这三种模式共享 workspace 隔离、最终证据冻结和引用协议，但分别保留原文检索、资料级阅读和知识页检索的目标。对长对话，冻结上下文用于理解当前问题，长期偏好记忆用于控制表达；两者都不能代替本次资料证据。删除和撤销处理围绕这些实际存储副本与身份执行。

可用于实现完成后的功能描述：围绕资料问答、笔记整理和编译知识页设计三条独立检索链路，以版本化证据窗口统一排序、预算、充分性判断和引用；对来源更新和撤销执行精确资格检查，并保证图扩展与回答生成消费同一份冻结证据。只有相关修改完成后，才使用这段描述声明已经具备相应行为。
