# NoteWeave v2 后端模块与中间件落地设计

## 1. 目标

这份文档回答三个实现问题：

1. 后端代码按什么模块落地最合理
2. 核心亮点对应的中间件应该如何分工与落地
3. 核心亮点对应的 MySQL 表如何先落一版可用 DDL

范围明确控制在当前最重要的五条主线：

- `Deep Research`
- `Artifact Runtime`
- `RAG / Wiki / Note`
- `Graduated Memory`
- `文件上传 / Kafka / MinIO`

不追求一开始把所有能力做成平台，而是先把主链路打通。

## 2. 落地原则

### 2.1 模块化单体

后端推荐继续采用：

`Spring Boot API App + Spring Boot Worker + MySQL + Kafka + MinIO + Elasticsearch`

其中：

- `api-app` 负责接口、轻编排、状态查询、短链路同步处理
- `worker` 负责解析、索引、Deep Research、Artifact Job、Memory Promotion

### 2.2 一条主链路只保留一个主对象

避免一个功能落成多套相近对象：

- Deep Research 以 `research_run` 为主对象
- 产物生成以 `artifact_job` 为主对象
- 记忆晋升以 `memory_candidate` 为主对象

### 2.3 先把配置对象做成“注册表”，不做图形化平台

当前只需要：

- `production_action`
- `style_profile`
- `prompt_recipe`
- `skill_graph_template`
- `mcp_capability_binding`
- `capability_union_policy`

不需要先做可视化编排器。

## 3. 后端模块划分

推荐包结构：

```text
com.noteweave
  ├── common
  ├── auth
  ├── workspace
  ├── source
  ├── retrieval
  ├── knowledge
  ├── research
  ├── artifact
  ├── memory
  ├── task
  ├── capability
  └── observability
```

### 3.1 `source`

职责：

- 文件上传
- URL / 文本导入
- 原始文件落 MinIO
- 解析文本生成
- chunk 生成与索引
- SourceWindow 回源

核心类建议：

- `SourceApplicationService`
- `UploadSessionService`
- `SourceParserWorker`
- `ChunkIndexWorker`
- `SourceWindowQueryService`

### 3.2 `retrieval`

职责：

- Ask 检索
- Note / Wiki / Artifact 检索
- metadata 检索
- citation 回源

核心类建议：

- `HybridRetrievalService`
- `ArtifactRetrievalService`
- `MetadataSearchService`
- `CitationResolver`

### 3.3 `knowledge`

职责：

- Note / Wiki / Investigation Note 管理
- 版本管理
- 显式回写

核心类建议：

- `KnowledgeItemService`
- `KnowledgeVersionService`
- `WikiPublishService`

### 3.4 `research`

职责：

- `Research Run` 生命周期
- `Research Table` 状态
- `Stop Contract`
- `Branch / Checkpoint`
- 研究报告生成

核心类建议：

- `ResearchRunService`
- `ResearchHarnessService`
- `ResearchTableService`
- `ResearchVerifier`
- `ResearchTraceService`
- `ResearchReportService`

### 3.5 `artifact`

职责：

- `Artifact Job` 生命周期
- `Production Action` 解析
- `Style Profile` 加载
- `Skill Graph Template` 展开
- `Prompt Recipe` 运行
- `Artifact Version` 提交与回流

核心类建议：

- `ArtifactJobService`
- `ProductionActionResolver`
- `StyleProfileService`
- `SkillGraphPlanner`
- `PromptRecipeRunner`
- `ArtifactCommitService`

### 3.6 `memory`

职责：

- `Context Signal` 抽取
- `Memory Candidate` 生成
- 双门控校验
- `Memory Object` 晋升与回读

核心类建议：

- `ContextSignalExtractor`
- `MemoryCandidateService`
- `NoveltyGate`
- `TaskNeighborhoodValidator`
- `MemoryPromotionService`

### 3.7 `task`

职责：

- 统一异步任务调度
- 外盒投递
- 重试 / 取消 / 幂等

核心类建议：

- `TaskDispatcher`
- `TaskOutboxPublisher`
- `TaskWorkerExecutor`
- `TaskRetryPolicy`

### 3.8 `capability`

职责：

- MCP 能力注册
- capability binding 解析
- `Capability Union Policy` 门控
- 外部工具适配

核心类建议：

- `McpCapabilityRegistry`
- `CapabilityBindingService`
- `CapabilityUnionPolicyService`
- `ExternalToolGateway`

## 4. 核心运行链路

### 4.1 Deep Research

```text
POST /api/v2/research/runs
  -> ResearchRunService.createRun()
  -> TaskDispatcher.dispatch(RESEARCH_RUN)
  -> worker 执行 ResearchHarnessService
  -> 更新 research_row / research_cell / research_trace
  -> 生成 artifact + artifact_version
```

### 4.2 Artifact Runtime

```text
POST /api/v2/artifacts/jobs
  -> ArtifactJobService.createJob()
  -> ProductionActionResolver.resolve()
  -> StyleProfileService.load()
  -> TaskDispatcher.dispatch(ARTIFACT_JOB)
  -> worker 执行 SkillGraphPlanner + PromptRecipeRunner
  -> ArtifactCommitService.commit()
```

### 4.3 Graduated Memory

```text
Artifact confirmed / Research completed / Conversation summarized
  -> ContextSignalExtractor
  -> MemoryCandidateService.createCandidate()
  -> NoveltyGate
  -> TaskNeighborhoodValidator
  -> MemoryPromotionService.promote()
```

## 5. MySQL 设计范围

当前 DDL 只覆盖一版最小可用核心表：

- 工作区与资料
- Deep Research
- Artifact Runtime
- Graduated Memory
- Task / Outbox

不在这一版展开：

- 全量权限细节表
- 复杂评估表
- 可视化编排器配置表
- 多租户计费表

## 6. 中间件落地设计

这一节回答的不是“用哪些组件”，而是“每个组件在 NoteWeave v2 里到底承担什么职责，边界画到哪里”。

### 6.1 MySQL

定位：

- 业务真源
- 状态机真源
- 配置对象真源
- 审计对象真源

在 v2 中明确放 MySQL 的对象：

- Workspace / Topic Scope
- Source 元数据
- Conversation / Knowledge / Artifact
- Research Run / Research Table / Research Trace
- Production Action / Style Profile / Prompt Recipe / Skill Graph Template
- Context Signal / Memory Candidate / Memory Object
- Task / Outbox

不放 MySQL 的内容：

- 原始大文件正文
- 长篇解析文本正文
- 检索向量本体
- 高频流式 token 输出

### 6.2 Redis

定位：

- 短期运行态缓存
- 会话与幂等辅助层
- WebSocket / SSE 辅助状态层

推荐承接：

- 登录态缓存
- 短 TTL 的上下文缓存
- 幂等键
- Artifact Job / Research Run 的实时进度快照
- WebSocket resume token
- 热门检索结果短缓存

不建议承接：

- 长期知识对象
- Deep Research 主状态
- Memory 主状态

建议 key 规划：

```text
session:{sessionId}
idem:{taskType}:{idempotencyKey}
progress:research:{runId}
progress:artifact:{jobId}
ws:resume:{connectionId}
cache:retrieval:{workspaceId}:{hash}
```

### 6.3 Kafka

定位：

- 后台异步任务总线
- 长任务执行解耦层
- 事务外盒下游消费层

推荐 topic：

```text
source.parse
source.index
research.run
artifact.job
memory.promotion
embedding.backfill
task.dlq
```

推荐原则：

- Kafka 只传任务身份和轻量载荷
- 大快照仍回 MySQL / MinIO
- 不在 Kafka 中传大正文

当前不建议：

- 用 Kafka 直接承接前端流式响应
- 用 Kafka 存储长时间未消费的大型正文快照
- 把每一个细粒度 UI 事件都事件化

### 6.4 MinIO

定位：

- 原始文件对象存储
- 大文本快照存储
- 导出文件存储
- Research / Artifact 中间快照存储

推荐 bucket：

```text
raw-source
parsed-source
artifact-export
research-snapshot
artifact-snapshot
temp-upload
```

当前不建议：

- 把结构化元数据写进对象存储当主真源
- 把小型配置对象拆成单独文件存在 MinIO

### 6.5 Elasticsearch

定位：

- 统一检索层
- Ask / Wiki / Investigation / Artifact / Memory 共用检索底座

推荐索引：

```text
source_chunk_index
knowledge_note_index
knowledge_wiki_index
artifact_index
memory_index
source_metadata_index
```

关键边界：

- ES 是检索副本，不是业务真源
- 权限与状态仍回 MySQL 校验

当前不建议：

- 让 ES 承担权限判定
- 让 ES 直接作为 Wiki / Artifact 编辑回写的唯一读取源
- 为了“向量库名词更好看”再并行引入第二套向量底座

### 6.6 LLM Gateway

定位：

- 统一模型访问层
- Deep Research / Artifact Runtime / Memory 的模型复用层

推荐职责：

- 模型路由
- 参数模板
- 超时与重试
- 调用日志
- 成本统计

当前不建议：

- 在业务模块里直接散落各家 SDK 调用
- 让 Deep Research、Artifact Runtime、Memory 各自维护一套模型接入逻辑

### 6.7 MCP Gateway

定位：

- 外部能力接入层
- 不同 MCP Server 的统一能力面

推荐职责：

- server 注册
- capability 映射
- contract 归一化
- policy gate
- 超时、熔断、审计

当前不建议：

- 让业务层直接绑定 MCP 工具原名
- 用户一接入新 MCP 就默认全量开放给 Deep Research 和 Artifact Runtime

### 6.8 WebSocket / SSE

定位：

- 进度反馈层
- 流式输出层

推荐用途：

- Ask 的流式回答
- Deep Research 的阶段进度
- Artifact Job 的运行进度

当前不建议：

- 在 WebSocket 里保存长期任务主状态
- 把它当 Kafka 或数据库替代品

### 6.9 Observability Stack

定位：

- 运行可观测层

推荐最小集合：

- `Spring Actuator`
- `Micrometer`
- `Prometheus`
- `Grafana`
- 结构化日志

## 7. 中间件与主链路映射

### 7.1 Deep Research

```text
MySQL           保存 run / row / cell / trace
Kafka           驱动 research.run 异步执行
Redis           缓存进度快照
MinIO           保存 checkpoint / report snapshot
Elasticsearch   提供候选资料与原文检索
LLM Gateway     执行 plan / extract / verify / write
MCP Gateway     提供外部搜索、网页读取等能力
```

### 7.2 Artifact Runtime

```text
MySQL           保存 artifact_job / action / style / version
Kafka           驱动 artifact.job 异步执行
Redis           提供任务进度与短缓存
MinIO           保存 CCO snapshot / export file
Elasticsearch   检索输入资料、回流 artifact 检索
LLM Gateway     执行 recipe / verify / repair
MCP Gateway     提供视频、音频、网页等外部能力
```

### 7.3 Graduated Memory

```text
MySQL           保存 signal / candidate / object
Kafka           驱动 memory.promotion
Redis           可选缓存高频 memory read
Elasticsearch   提供 memory retrieval
LLM Gateway     执行 normalize / compare / abstract
```

## 8. 中间件实施顺序

### 8.1 第一层：必须先落

- MySQL
- MinIO
- Elasticsearch
- Kafka

### 8.2 第二层：体验增强

- Redis
- WebSocket / SSE
- LLM Gateway

### 8.3 第三层：能力扩展

- MCP Gateway
- Prometheus / Grafana
- 更细粒度的成本与策略控制

## 9. MySQL DDL 草案

说明：

- 默认 `MySQL 8.4`
- 字符集统一 `utf8mb4`
- 时间统一 `datetime(3)`
- JSON 字段只承接配置、快照和运行态，不作为主检索字段
- 对于 `artifact.latest_version_id`、`research_run.latest_artifact_id` 这类容易形成循环依赖的字段，首版可先保留普通列和应用层约束，不强上外键

### 9.1 工作区与资料

```sql
create table workspace (
  id bigint primary key auto_increment,
  workspace_key varchar(64) not null,
  name varchar(255) not null,

  updated_at datetime(3) not null default current_timestamp(3) on update current_timestamp(3),
  unique key uk_workspace_key (workspace_key)

create table topic_scope (
```

## 9. 设计取舍

当前这份设计有意做了三个收缩：

- 没把 `Skill Graph` 做成通用流程引擎，只保留模板化注册
- 没把 Memory 做成独立向量知识平台，只保留门控晋升主链路
- 没把 Deep Research 做成多智能体群聊系统，而是坚持 `Research Harness + Table-as-State`

这是为了保证亮点成立，同时实现成本可控。
