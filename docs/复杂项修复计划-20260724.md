## 执行批次

### 批次 A：生产身份与公开网络边界（P0）

范围：F-03、F-04、F-05、F-06、F-24、F-32。

完成标准：

1. 未配置内部 token 时，所有 `/internal/*` 控制面均拒绝非 loopback 请求；配置了 token 时必须按路由使用正确 dedicated token。
2. Compose 默认只暴露前端入口，数据库、Redis、Kafka、ES、MinIO 和 Worker 控制端口不对宿主公开；凭据不得使用可工作的弱默认值。
3. `NOTEWEAVE_ENVIRONMENT=production` 能触发生产配置校验，弱凭据、共享 token、HTTP Worker 地址和 fallback 开关均在启动阶段拒绝。
4. 运行态 JSON、callback token 和其他可恢复凭据不进入 Git 输入；新 checkout 不依赖旧进程状态。
5. 会话只保存不可逆 token hash，刷新令牌轮换具备唯一约束和 replay 拒绝，错误响应不泄露凭据。
6. 前端和公开 API 不返回 callback token 原文；追踪信息保留 request/operation 状态和脱敏摘要。

### 批次 B：跨服务边界与故障语义（P1）

范围：F-36、F-53、F-60、F-29、F-59、F-62。

完成标准：

1. Artifact LLM、MCP 和 callback 失败只返回可行动的错误码/摘要，不回显密钥、Authorization、内部路径或完整上游响应。
2. Bilibili MCP 的输入文件、输出目录和临时文件均限制在 sandbox 根目录内，拒绝路径穿越、符号链接逃逸和跨任务读写。
3. Worker callback 必须同时验证 token、task 存在、worker 类型/operation 归属和允许的状态迁移。
4. Redis/MinIO/Kafka 等关键依赖故障在生产环境 fail-closed 或明确 degraded，不得伪装成成功或永久处理中。
5. Compose、`application.yml`、`.env.example` 与消费者代码使用同一组重试/超时/实例变量。

### 批次 C：结构与性能债务（P2）

范围：F-11、F-12，以及 F-10 的深度性能部分。

已完成首轮：保持 API 与页面行为不变，`App.tsx` 已委托到 Chat/Wiki/Research/Memory/Shell 工作台，`ResearchRunService` 已委托到 command/query/artifact 服务，Research 列表使用批量 read model 装载 trace、checkpoint、evidence 和 wait context，避免按 run 的 N+1 查询。后续仅在性能证据明确时继续引入更轻量 projection。
