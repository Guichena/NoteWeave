## 1. 总体结论

当前提交**不建议直接作为生产发布基线**。

项目主干能力已经相当完整：Workspace 权限、异步任务、AnswerRun（QA/Note/Wiki）、Research Agent、Artifact Skill-first、Knowledge Wiki、Memory 审核都有大量实现与测试。但当前同时存在六类需要优先处理的问题：

1. **可直接导致功能不可用的活缺陷**：Research checkpoint 恢复仍走已退出正式部署的 legacy 消费链；默认 Compose 下任务会长期停在 `QUEUED`。
2. **生产安全与身份闭环不完整**：生产 guard 未接入 Compose 语义；前端无登录/token 注入；Artifact Worker 空 token fail-open；基础设施默认弱凭据并对宿主机公开。
3. **代码与当前产品界面不一致**：11 个 Research 高级面板完全失去运行时引用；会话历史、成员权限、checkpoint 恢复等后端能力前端未接线。
4. **结构性复杂度与重复状态机过高**：`App.tsx`、`ResearchRunService`、Artifact registry/runtime，以及 **4 套** Outbox 调度实现已超过单模块可安全维护边界。
5. **大量“看起来成功”的静默兜底**：ES→MySQL、Redis SSE 降级、Quota 本地回退、LLM template/fallback 固定文案、Skill 列表硬编码默认值，会掩盖真实故障并产生错误产品体验。
6. **二次补漏新发现的正确性/竞态缺陷**（更严重）：Wiki 失败写成 COMPLETED 却因回滚落不了库；前端 execution 轮询只触发一次；Artifact 同步 HTTP 跑整任务却与 5 分钟 lease 冲突；Answer stream lease 不续约；nginx 默认 1MB 拦截 128MB 上传契约。

## 4. 详细发现

### F-01 checkpoint 恢复使用无人消费的 legacy 链路

级别：高，发布阻断

证据：

- `backend/src/main/java/com/noteweave/research/ResearchRunController.java:69-75` 对外暴露恢复接口。
- `backend/src/main/java/com/noteweave/research/ResearchRunService.java:273-307` 创建恢复 run 时未写入 `agent_execution_mode`，使用迁移默认 `SEQUENTIAL_V1`，并写入 `noteweave.research.run`。
- `backend/src/main/resources/db/migration/V041__add_research_agent_execution_mode.sql:2` 默认值是 `SEQUENTIAL_V1`。
- `docker-compose.yml:246-285` 唯一正式 Research consumer 启动 `app.agent_kafka_consumer`，消费 `noteweave.research.agent.command`；没有服务启动 `app.kafka_consumer`。
- `backend/src/test/java/com/noteweave/Phase6ResearchArtifactContractTest.java:3484-3596` 测试人工调用 internal complete 完成恢复，未验证真实 Kafka 消费路径。

触发方式：对任意有 checkpoint 的 run 调用 `POST .../resume-from-checkpoint/{checkpointNo}`。

结果：新 run 返回 `QUEUED`，legacy outbox 可被发布，但默认 Compose 没有消费者执行它。

建议：恢复流程与 createRun 统一走 `INCREMENTAL_V1` bootstrap/coordinator；删除恢复接口对 `task_outbox/noteweave.research.run` 的写入，并新增 Compose 级真实链路测试。

### F-02 生产身份认证没有闭环

级别：高

证据：

- `backend/src/main/java/com/noteweave/security/ApiRequestIdentityFilter.java:38-67` 只接受数据库中已有的 bearer session token。
- 全仓库生产代码没有创建、刷新、撤销 `user_session` 的服务或认证 controller；写 session 的引用只存在测试。
- `frontend/src/shared/api/auth.ts:3-9` 只提供内存 token setter。
- `setAccessToken` 除定义与 re-export 外没有任何运行时调用者。
- `backend/src/main/java/com/noteweave/config/ProductionConfigurationGuard.java:53-54` 要求生产必须关闭 local-user fallback。

触发方式：设置 `NOTEWEAVE_LOCAL_USER_FALLBACK=false` 后打开前端。

结果：前端无法取得或设置有效 session；所有 `/api/v2/**` 返回 401。

建议：完成 login/refresh/logout/session 流程；前端建立唯一 auth owner。若只定位单用户本地应用，应删除伪多用户 session 模型并明确 loopback 边界。

### F-03 Artifact Worker 控制面在 token 为空时 fail-open

级别：高

证据：

- `workers/artifact-worker/app/config.py:8` 默认 `internal_auth_token=""`。
- `workers/artifact-worker/app/main.py:125-137` 只有 token 非空时才校验；空值时直接 `call_next`。
- 受影响路径包括 `/tasks/`、`/callbacks/`、`/internal/` 和启用后的 `/debug/`，以及 PDF 导出 `GET /tasks/{task_id}/exports/...`。
- Research/Artifact 双向 callback 在 token 空时也不发送鉴权头。

结果：任何能访问 18092 的客户端都能调用任务、回调、恢复和导出控制面。与 Java “无 token 仅 loopback”策略不一致。

建议：空 token 时 fail-closed，或只允许 loopback；Docker 端口绑定 `127.0.0.1` 或完全不发布。

### F-04 基础设施默认公开且使用弱凭据/无认证

级别：高

证据：

- MySQL：`root/root`、`noteweave/noteweave123`，`3306:3306`
- Redis：无密码，`6379:6379`
- Kafka：PLAINTEXT，`9092`
- MinIO：`minioadmin/minioadmin`，9000/9001
- Elasticsearch：关闭安全，`9200`
- Compose 展开后上述端口无 `127.0.0.1` 绑定；只有 Backend 显式 loopback
- Worker HTTP `18091/18092` 全网暴露，与 Backend 策略不一致

建议：开发 Compose 默认全部绑定 `127.0.0.1`；生产不发布基础设施端口；凭据必须从必填 secret 注入。

### F-05 ProductionConfigurationGuard 没有接入 Compose 环境语义

级别：高

证据：

- `ProductionConfigurationGuard` 仅 `@Profile("prod")`
- Compose 只设 `NOTEWEAVE_ENVIRONMENT`，没有 `SPRING_PROFILES_ACTIVE=prod`
- 展开后仍是 development、弱 internal token、弱 DB/MinIO、local-user fallback=true

结果：运维只设 `NOTEWEAVE_ENVIRONMENT=production` 时，guard 不会加载。

建议：guard 直接读取 `noteweave.environment`，或 Compose 联动 Spring profile；增加配置矩阵测试。

### F-06 仓库提交了可恢复的 Artifact 运行态与 callback token

级别：高

证据：

- 根目录 `.artifact-worker-runtime-state.json`、`.artifact-worker-wait-queue.json`、`.artifact-worker-customizations.json`
- 默认路径指向这些相对文件；import 时加载 store
- `.gitignore` 只忽略 `workers/**/.artifact-worker-*.json`，**不覆盖仓库根级**同名文件
- 文件含 operation、callback token、WAITING 任务完整 input

结果：干净 checkout 不是干净运行态；可能重试不属于当前运行的操作；泄露 token。

建议：删除并 gitignore 根级运行态；测试用临时目录；callback token 永不提交。

### F-07 Artifact fallback 会生成与用户资料无关的固定内容

级别：高

证据：

- Compose Artifact LLM key/base/model 默认为空
- `llm_client.py` 空 key/model 返回 `None`
- `generation_runtime.py` 采用 deterministic fallback 并继续生成
- `skill_graph.py` fallback 固定写入 Production Action / Skill Graph / Capability Union Policy 等本项目施工术语
- `runner.py` fallback 后再 repair 并正常渲染完成

结果：系统不是明确失败，而是注入无关内部术语，形成看似成功、事实无关的产物。

建议：删除领域固定文案；无 LLM 时只能从输入抽取/重排，否则 `BLOCKED/CONFIGURATION_REQUIRED`。

### F-08 11 个 Research 高级面板已经成为孤儿代码

级别：高

下列组件只在自身文件中出现，无 import / lazy import / 运行时调用：

- `ResearchProcessOverview.tsx`
- `ResearchRoundTimeline.tsx`
- `ResearchProcessStageLanes.tsx`
- `ResearchProcessTraceBrowser.tsx`
- `ResearchAuditOverview.tsx`
- `ResearchClosedLoopStatePanel.tsx`
- `ResearchCheckpointReplayPanel.tsx`（含「从此恢复」）
- `ResearchCheckpointSnapshotPanel.tsx`
- `ResearchCheckpointProvenancePanel.tsx`
- `ResearchCheckpointEvidenceReviewPanel.tsx`
- `ResearchCheckpointCurrentDiffPanel.tsx`

补充证据：

- `App.tsx` 只 lazy-load `ResearchReportPanel`；详情弹窗为简化版
- `researchApi.resumeFromCheckpoint` 仅有 API 与测试，无生产调用者
- `useResearchState` 的 checkpoint 选择 API 已实现，App 未解构使用
- Vite 构建无这些面板的独立 chunk

结果：约 1000 行组件与大量后端能力对用户不可达。

建议：属于产品则建 `ResearchDetailWorkbench` 并用组件/E2E 锁住入口；不属于则删除组件、API 与过期验收文档。

### F-09 Wiki 搜索会忽略 120 页以外的内容

级别：中高

证据：`KnowledgeWikiSearchEngine.java:55-74` 先 `order by updated_at desc limit 120`，再在内存按 query 打分。

结果：旧页面在打分前被截掉，是确定性召回错误。

建议：检索条件下推到 ES/MySQL 全文索引，或先按 query 过滤再 limit。

### F-10 Research 列表接口执行多层 N+1 组装

级别：中高

证据：`ResearchRunService` 列表路径对每个 run 调用 loadTraces、buildReportStructure、buildClosedLoopState、loadResumeCheckpointSummary、loadSavedReportSource、buildReportFileResponse 等。

结果：一次列表请求可能扩展为数百次 SQL/JSON/对象存储检查。

建议：轻量 summary projection；详情按单 run 加载；SQL 数量与响应体大小门禁。

### F-11 App.tsx 仍是前端巨型组合根

级别：结构

证据：`frontend/src/App.tsx` ~4601 行，~28 个 useState；Workspace / Conversation / Answer / Source / Knowledge / Research / Artifact / Memory 全堆一处；全局单一 `isBusy`/`status`。

影响：并发操作互相覆盖；功能抽出后易出现 F-08 式接线丢失。

建议：App 只保留路由与顶层 provider；分 ChatWorkspace、KnowledgeWorkbench、ResearchWorkbench、ArtifactStudio。

## 9. 二次补漏详细发现（F-41～F-62）

本节为同日第二轮针对竞态、事务、幂等、跨服务契约与前端状态机的补漏结果；不重复 F-01～F-40 已展开论述，除非新证据显著加强。

### F-41 Wiki 失败写成 COMPLETED，异常回滚后任务悬挂

级别：高

证据：`WikiIngestService.java:71-73, 100-102` 在 catch 中调用 `completeTask(..., "WIKI_INDEXED_FAILED"/"WIKI_RETRACTED_FAILED", ...)` 后 `throw ex`；方法 `@Transactional`，异常回滚包含这次 complete。

结果：失败任务既非 FAILED，也未真正 COMPLETED，可能长期 PENDING/RUNNING，Kafka 侧重试行为不可控。

建议：catch 中用 `failTask`/`REQUIRES_NEW` 独立事务落终态，或不要 throw 导致回滚终态写入。

### F-42 Source parse 不可处理时静默 ack

级别：高

证据：`KafkaTaskConsumer.java:52-56` 仅在 `isProcessable` 为真时 `startTask`+parse；否则直接 return，消息仍被成功消费。

结果：snapshot 非 PENDING、资料已删、重复消息等场景下 `SOURCE_PARSE` 任务永久 PENDING。

建议：不可处理时 `cancelTask`/`failTask` 并记录原因；幂等重复消息明确 ACK 语义。

### F-43 Answer stream lease 150s 不续约

级别：高

证据：`AnswerRunService.java:183-189` claim 写 `stream_lease_until = now+150s`；`AnswerGenerationOrchestrator` 生成全程无 renew。

结果：长回答/慢 LLM 超过约 150s 后第二连接可 claim；原 owner complete 的 CAS 失败，可能双流。

建议：生成中定期 renew lease；或 lease ≥ 最大生成超时且 complete 用 fencing token。

### F-44 Answer 取消与 complete 竞态

级别：高

证据：流内 `AnswerRunCancelledException` 只发 SSE terminal，不保证 `answerRunService.cancel` 落库；cancel API 与 `complete()` 对 GENERATING/FINALIZING 的 CAS 时序决定最终态。

结果：用户看到 cancelled，DB 可能 COMPLETED；或相反。

建议：单一状态机 owner；cancel 与 complete 共享 fencing；流内必须尝试落库 cancel。

### F-45 Research quorum cell binding 释放不一致

级别：高

证据：claim 时 quorum 绑定 owner 为 `quorum_group_key`；`expireLeases`/`submitExecution` 的 `releaseCellBindings` 仅用 `taskId`，匹配不到。

结果：cell 永久锁死，协调器无法再 claim；reaper 路径正常但 internal expire 不一致。

建议：释放与绑定使用同一 owner 键（quorum 用 groupKey）。

### F-46 Worker complete/fail 幂等与 CAS 不足

级别：高

证据：`WorkerTaskCallbackService` 空 idempotency key 不登记；`ArtifactJobService.completeFromWorker`/`markFailed` 与 `ResearchRunService.markFailed` 无充分 status CAS。

结果：重复 callback 可双版本、COMPLETED 被改 FAILED、产物/报告覆盖。

建议：强制 idempotency；终态 `where status in (...)` CAS；fail 不得覆盖 COMPLETED。

### F-47 Kafka 开 + ES 关 → source 永久 INDEXING

级别：高

证据：async parse 写 `PROCESSING/INDEXING`；READY 仅在 ES projector 路径收齐 PROJECTED 后设置。

结果：合法配置组合下资料永不 READY，QA/Note 永久 miss。

建议：ES 关闭时同步标记 INDEXED/READY 或拒绝 async 路径启动。

### F-48 前端 Execution 轮询只触发一次

级别：高

证据：`useExecutionRegistry.ts:71-79` 用 `setTimeout` 一次，依赖 `activeKey`；PENDING→RUNNING 后若 key 不变，不再调度。

结果：上传解析、Research、Wiki 等任务 UI 约 2.5s 后再拉一次即停，进度假死。

建议：poll 完成后若仍 active，链式 `setTimeout`；或 `setInterval` + 终态清理。

### F-49 waitFor 无超时锁死 isBusy

级别：高

证据：`answerRunStore.waitFor` 仅在终态 settle；`App.tsx` 在 conversation stream 连接时 `await waitFor`；全局 `isBusy` 禁用几乎全部按钮。

结果：漏 terminal 事件 / 重连跳过 cursor / 后端未写 stream 时 UI 永久 busy。

建议：waitFor 超时后 `getRun` reconcile；busy 按域拆分。

### F-50 Artifact outbox 同步 HTTP 与 5 分钟 lease 冲突

级别：高

证据：`HttpArtifactOutboxPublisher` `POST /tasks/{id}/run` 同步等待；Worker 同步跑完整流水线（MCP 默认可 3600s）；`ArtifactOutboxDispatcherService.STALE_CLAIM_AFTER = 5 minutes`。

结果：任务 >5 分钟后 lease 过期，scheduler 再次 claim 并再次 POST run → 重复执行/双写。

建议：fire-and-forget 或 Kafka 异步；readTimeout < lease；lease ≥ 任务上限或心跳续约。

### F-51 单线程 Scheduled + 同步 Artifact = 调度雪崩

级别：高

证据：仅 `@EnableScheduling`，默认单线程；Artifact/Research/Task/Coordinator 多 scheduler 共享；Artifact 同步阻塞会卡住 source outbox 与 agent command。

建议：`TaskScheduler` 多线程池隔离；禁止在 schedule 线程同步跑长任务。

### F-52 nginx body 1MB vs 后端 128MB

级别：高

证据：后端 `max-file-size: 128MB`；`frontend/nginx.conf` 无 `client_max_body_size`（默认 1m）。

结果：经 `localhost:3000` 上传 >1MB 413；直连 8081 成功 → 环境相关假故障。

建议：nginx `client_max_body_size 128m;` 与后端一致。

### F-53 Bilibili MCP 路径无 sandbox

级别：中高

证据：`bilibili_render_pdf_server.py` 对 `input_path`/`output_dir` 直接 `Path(...).resolve()` 读写；对比 export HTTP 有 `is_relative_to`。

结果：入参可控时可任意读文件 / 写任意目录（配合 custom MCP 可放大）。

建议：强制限制在 worker 工作目录；拒绝绝对路径与 `..`。

### F-54 Upload complete 并发双 source

级别：中

证据：`UploadService` complete 无 `for update`/status CAS；两请求同时见 UPLOADING 可双插 source。

建议：`SELECT ... FOR UPDATE` + `where status='UPLOADING'` CAS。

### F-55 ES 无 mapping，delete term 可能漏删

级别：中

证据：索引直接动态 mapping；`deleteBySourceId` 对 `source_id` 做 `term`。

结果：text 分析下清理不干净，脏 chunk 残留。

建议：启动 put mapping（id 类 keyword）；delete 用 keyword 字段。

### F-56 SSE 错误反转义 `\\n`

级别：中

证据：`sse.ts:27` `.replaceAll("\\n", "\n")` 非标准 SSE 行为。

结果：路径 `C:\new`、代码中的 `\n` 字面量被改写；JSON parse 失败后 silent skip。

建议：删除该 replace，仅 join 多行 `data:`。

### F-57 Answer reconcile 空 content 覆盖流式内容

级别：中

证据：`store.ts` `content: snapshot.content ?? current.content`；`""` 会覆盖已累积 delta。

建议：GENERATING 且 snapshot content 空时保留 current。

### F-58 跨服务超时严重不一致

级别：中

| 方向 | 超时 |
| --- | --- |
| Worker→Java | 30s |
| Java→Artifact Worker | **未配置，可无限挂起** |
| Artifact MCP | 3600s |
| Backend LLM | 60s |

与 F-50/F-51 叠加形成自激雪崩。

### F-59 MinIO bucket 双层软失败

级别：中

证据：`minio-init` 无 `set -e`；`MinioObjectStorage.ensureBuckets` catch 仅 warn。

结果：bucket 未创建仍 healthy，首次写才失败。

### F-60 Internal callback 无 task 归属

级别：中

证据：legacy ARTIFACT_JOB/RESEARCH_RUN callback 仅 shared token + taskId，无 worker_instance/workspace 绑定。

结果：持 token 的任意调用方可终结任意任务。

### F-61 Artifact 运行态文件脆弱

级别：中

证据：wait-queue/acquisition 启动 `json.loads` 无保护；多实例仅进程内 Lock；`os.replace` 失败后非原子 `write_text`。

结果：坏文件起不来；多副本 lost update / 双 resume。

### F-62 配置契约错位

级别：中

- `.env.example` 缺 heartbeat/drain/local-user-fallback/artifact base url 等

## 10. 已检查但未形成问题的高风险面

以下位置经过代码审阅，当前没有足够证据形成高置信问题：

- Workspace 资源权限：`WorkspaceAccessGuard` 对 workspace/member/resource ownership 做了数据库校验和 ACL cache version 约束。
- Java `/internal/*`：token 配置时使用常量时间比较；未配置时只允许 loopback，策略本身比 Artifact Worker 更安全。
- Artifact PDF **HTTP 下载**路径边界：task id、文件名和 resolved path 都有校验（问题在鉴权 fail-open；MCP 写路径见 F-53）。
- Research 外部抓取：存在 URL scheme、私网地址、重定向和响应大小保护；本次未发现可直接利用的 SSRF 绕过。
- Research agent complete（MA4G）：envelope digest + lease/fencing 相对完整（与 F-46 legacy fail 路径对比鲜明）。
- Research loop 预算/轮次终止：`max_rounds` / wall_clock / TERMINAL_DECISIONS 有测试覆盖。
- Segment summary promote：`for update` + version 校验合理。
- 前端 workspace 切换：`Latest*RequestGate` abort + isCurrent 防旧响应覆盖。
- ConversationStream cursor + Last-Event-ID 重连主路径可用（问题在 waitFor/reconcile 边角，见 F-49/F-57）。
- 生产代码几乎无 `TODO/FIXME` 标记；未完成工作主要体现在空 consumer、默认关 LLM、legacy 双轨、竞态与未接线 UI。
- 前端 XSS：主路径多为 text/`<pre>`，未见 `dangerouslySetInnerHTML`。
- CORS：backend 未配置宽松 CORS（相对安全）；依赖同源/网关。
- SQL 注入：业务 SQL 多为参数化；动态表名来自常量白名单。

### 14.4 「可接受兜底」vs「不可接受假成功」

| 可接受（需用户可见） | 不可接受（当前大量存在） |
| --- | --- |
| 返回 `degraded=true` + 原因列表，状态仍成功但 UI 标黄 | COMPLETED/200 且 UI 无任何降级提示 |
| CONFIGURATION_REQUIRED / BLOCKED 明确失败 | template / deterministic fallback 当正式交付 |
| 拒答 / insufficient | bestFallbackIndex / recency 硬捞无关证据 |
| 开发 profile 显式 demo 模式横幅 | 默认配置即假鉴权 / 假索引 / 假 LLM |
| 降级结果单独 artifact 类型（如 draft_template） | 与真生成共用 COMPLETED + 同一 UI |

### 14.5 针对「我们要求实现的功能」的违背清单

| 要求实现的能力 | 当前违背意愿的兜底 | 应改为 |
| --- | --- | --- |
| ES 检索型 QA | MySQL term + 假 INDEXED | ES 不可用 → 失败或显式 DEGRADED，禁止静默 MySQL 当正式 |
| 真 LLM 回答 | template-fallback + compose 模板 | 无 LLM → FAILED/CONFIGURATION_REQUIRED；UI 禁止流式假打字 |
| Skill-first 真生成 | DETERMINISTIC_FALLBACK + 领域 hardcode repair | 无 LLM → BLOCKED；repair 禁止注入项目文案；verifier 必须能 FAIL |
| 真网页 Deep Research | snippet-as-fetched 继续 verify | 无 snapshot → 证据等级降为 SNIPPET，禁止当 WEB_SNAPSHOT 进入强结论 |
| 资料索引就绪 | Kafka 关时 PROJECTED/INDEXED | 仅本地切片用 `LOCAL_ONLY` / `NOT_PROJECTED`，不得 READY-for-ES |
| 鉴权与多用户 | local-user 默认 | 默认 401；demo 模式必须显式开关 + UI 横幅 |
| Artifact 输出合同 | WARN 永不 FAIL | failed_checks → FAIL → job FAILED |
| Memory 审核闭环 | 双 API + legacy bridge | 单一 canonical；删 legacy 或只读兼容窗口 |
| 可靠异步任务 | 四套 outbox + 同步 HTTP 伪装 outbox | 统一 dispatcher + 异步 transport |

### 14.6 收敛原则（修复时强制）

1. **Fail loud, degrade loud**：任何 fallback 必须同时满足  
   - 状态字段可区分（`mode=TEMPLATE|DETERMINISTIC|MYSQL_FALLBACK|SNIPPET`）  
   - 用户可见（横幅/标签，不能只埋 trace）  
   - 指标可告警  
2. **禁止「成功态 + 假内容」**：template / deterministic / hardcode repair 不得写 COMPLETED。  
3. **一条业务能力一条主路径**：legacy/兼容层只读或限期删除。  
4. **Verifier 必须有 FAIL**：无 FAIL 的校验 = 假校验。  
5. **测试不得把假成功当合法成功**：例如 gate1 将 snippet fallback 当 pass case、Artifact 测试期望 fallback COMPLETED —— 这些测试在固化错误产品语义，需改写为「必须失败」或「必须标 DEGRADED」。
