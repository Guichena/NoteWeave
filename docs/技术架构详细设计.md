# NoteWeave v2 技术架构详细设计

## 1. 设计目标

这份文档承接 [系统架构设计](D:/java-projects/NoteWeave-v2/docs/系统架构设计.md) 的总纲，只回答“系统模块怎么分、模块之间怎么协作、哪些能力由 Java 主系统负责、哪些能力由 Python Worker 负责”。

它不重复展开具体技术版本、MySQL 表结构、Kafka topic、接口清单和索引策略。这些落地细节统一以 [技术栈与数据库设计](D:/java-projects/NoteWeave-v2/docs/技术栈与数据库设计.md) 以及对应专项文档为准。

## 2. 技术总图

当前阶段采用“前端工作台 + Java 业务主系统 + 资料/知识/任务底座”的轻量分层，并为后续 Python Worker 预留执行面：

```text
Client / UI
  -> Java REST + SSE API
  -> Domain Services
  -> MySQL / Task / Source Parse / Wiki Ingest
  -> 预留 Python Research Worker
  -> 预留 Python Artifact Worker
```

在实现分工上，进一步推荐采用：

```text
Client / UI
  -> frontend(App.tsx)
  -> Spring Boot Controllers
  -> Workspace / Upload / Source / Conversation / Chat / Knowledge / Task Services
  -> MySQL + Flyway
  -> 后续可替换 ES / Kafka / MinIO
  -> Python Research Worker
  -> Python Artifact Worker
```

其中：

- `Java` 负责研究工作台、三种聊天回答链路、业务真源、任务编排、状态管理和结果回写
- `Python Research Worker` 负责 `Deep Research` 的执行循环
- `Python Artifact Worker` 负责 `Artifact Runtime` 的执行循环

## 3. 模块分层

### 3.1 接口层

负责承接前端调用：

- 工作台与会话接口
- 资料上传、读取与删除接口
- 聊天发送与 SSE 流式返回接口
- Knowledge / Wiki 页面接口
- 任务状态与事件接口

当前实际 API 组：

```text
/api/v2/workspaces/*
/api/v2/uploads/*
/api/v2/conversations/*
/api/v2/chat/requests/*
/api/v2/messages/*
/api/v2/knowledge-items/*
/api/v2/tasks/*
```

### 3.2 应用编排层

负责把一个用户请求编排成多个领域动作。当前阶段没有再额外抽一层 Orchestrator，而是由 Controller 直连 Service 完成轻量编排。

当前主要编排落点：

- `WorkspaceController -> WorkspaceService`
- `UploadController -> UploadService -> SourceParseService`
- `ConversationController -> ConversationService`
- `ChatController -> ChatService -> RetrievalService / KnowledgeService`
- `KnowledgeController -> KnowledgeService / WikiIngestService`
- `SourceController -> SourceService`
- `TaskController -> TaskService`

这一层当前负责：

- 权限校验
- 上下文装配
- 调用领域服务
- 创建或触发任务
- 组织返回结果

### 3.3 核心域层

这是系统真正的业务中台。当前代码中已经存在或应继续沿用的服务包括：

- `WorkspaceService`
- `UploadService`
- `SourceParseService`
- `SourceService`
- `ConversationService`
- `ChatService`
- `RetrievalService`
- `KnowledgeService`
- `WikiIngestService`
- `TaskService`

### 3.4 能力层

能力层用于承接“智能能力”与“外部能力”。当前阶段已经有轻量实现，后续再扩成完整 Agent Runtime：

- `RetrievalService`
  承接 QA / NOTE 两条回答链路的检索逻辑
  其中 NOTE 已落地 `coverage-aware metadata rank + relation expansion + source window read plan`

- `KnowledgeService`
  承接 WIKI 链路的页面检索、排序、版本、关系读取，以及工作台总览 `wiki-index`、问题聚合、日志聚合与图谱治理信息输出
  同时承接 `wiki-graph` 的 `overview / ego / kinds` 图谱查询契约

- `WikiIngestService`
  承接 `wiki_enabled` 打开后的工作台级 Wiki 构建、回补、重建与 retract

- `后续扩展`
  `Python Research Worker`、`Python Artifact Worker`、Skill / MCP / Verifier 能力栈

### 3.5 基础设施层

当前最少包含：

- `MySQL + Flyway`
  核心业务对象、资料、知识、引用、任务、日志真源

- `source_chunk / source_window`
  当前阶段直接承担 QA / NOTE 的检索与原文窗口读取底座

- `task + task_outbox`
  当前阶段承担资料解析、Wiki ingest、Wiki retract 等异步任务链路

- `后续替换点`
  MinIO 承接对象存储、Kafka 承接异步解耦、Elasticsearch 承接更大规模检索

## 5. Deep Research Engine 详细设计

本节的主链路设计，与 [深度研究智能体编排升级设计](D:/java-projects/NoteWeave-v2/docs/深度研究智能体编排升级设计.md) 中补充的 `TAS-Informed Verification-Centric Research Harness`、`Table-as-State`、`Dual Verifier`、`Counterfactual Branching`、`Premature Commitment Guard`、`Stop Contract` 等升级思路一起阅读更完整。

在当前产品口径下，Deep Research 不是第四种模式，而是跨 `问答 / Note / Wiki` 的独立系统能力。

### 5.1 执行结构

```text
DeepResearchOrchestrator
  -> Planning Unit
  -> Wide Search Executor
  -> Source Reader
  -> Cell Extractor
  -> Cell Verifier
  -> Conflict Resolver
  -> Report Synthesizer
```

在升级口径下，这套结构更适合理解为 `Research Harness + Controlled Responsibility Split`：

- Harness 负责状态、预算、停止条件、恢复和分支
- 总 Research Agent 内部按规划、搜索、读取、抽取、验证、纠偏和合成等职责拆成若干功能模块

### 5.2 状态机

建议状态：

- CREATED
- PLANNING
- TABLE_READY
- WIDE_SEARCHING
- READING
- EXTRACTING
- VERIFYING
- RESOLVING
- WRITING
- COMPLETED
- PARTIAL_COMPLETED
- FAILED
- CANCELLED

### 5.3 Loop Engine

Loop Engine 负责决定下一步动作：

- 继续搜索
- 继续阅读
- 重新抽取
- 重新验证
- 处理冲突
- 进入写作
- 停止

输入：

- ResearchPlan
- ResearchTable
- VerificationResult
- Conflict 状态
- Budget 剩余量
- Stop Contract

输出：

- LoopDecision

### 5.4 研究对象

建议 Research Run 至少持久化以下对象：

- ResearchPlan
- ResearchTable
- ResearchRow
- ResearchCell
- SourceEvidence
- VerificationResult
- ConflictResolution
- FinalReport Snapshot

其中：

- `FinalReport Snapshot` 是必选对象，不是可选补充
- 研究报告完成后应入库为项目级正式资料
- 抓取网页、原文快照、检查点与过程证据优先保留为过程资产

如果后续正式引入 branchable harness，可补充：

- ResearchBranch
- ResearchExecutionCheckpoint
- ResearchHarnessPolicy

## 6. Artifact Runtime 详细设计

本节的主链路设计，与 [受控式异步产物生成Agent编排升级设计](D:/java-projects/NoteWeave-v2/docs/受控式异步产物生成Agent编排升级设计.md) 中补充的 `Schema-Gated Skill Graph Runtime`、`Style Profile`、`Capability Union Policy` 等升级思路一起阅读更完整。

### 6.1 主链路

```text
Validate Input
  -> Resolve Action
  -> Load Style Profile
  -> Resolve Workspace Source Scope
  -> Plan Source Acquisition
  -> Acquire Source Content
  -> Build CCO
  -> Compile Context
  -> Build Execution Plan
  -> Schema Gate
  -> Run Prompt Recipe
  -> Verify / Repair
  -> Commit Artifact
  -> Index Artifact
```

### 6.2 Action Resolver

根据以下信息选择 Production Action：

- 用户点击的按钮
- 当前研究工作台
- 当前资料池状态
- 用户配置偏好
- 当前 Style Profile

Production Action 与 Style Profile 属于生成任务要求，不属于产物生成的原材料。

### 6.3 Canonical Content Object

CCO 是 Artifact Runtime 的关键中间对象。

建议字段：

- kind
- title
- plainText
- segments
- sourceTrace
- metadata
- contentHash

### 6.4 Verify / Repair

建议至少检查：

- 内容是否为空
- 是否符合产物结构
- 是否包含必要章节
- 是否保留来源信息
- 是否出现明显长度异常

### 6.5 Artifact Commit

每次提交建议保存：

- 触发入口
- 使用的 Action
- 使用的 Style Profile
- 使用的 Skill / Prompt Recipe
- 使用的 资料列表
- 输入快照
- CCO 快照
- 校验结果
- 父版本

如果提交对象是 `Deep Research` 的最终研究报告，还应追加：

- project-level source mapping
- generated source metadata
- default retrieval enabled

### 6.6 Memory Signal Hook

Artifact Runtime 不是每次生成后都直接写 Memory，而是在用户反馈、产物修改或明确否定发生后发出 Memory Signal。

推荐链路：

```text
Commit Artifact Version
  -> User Feedback / Edit / Rejection
  -> Extract Memory Signal
  -> Build Memory Candidate
  -> Semantic Neighborhood Modeling
  -> Marginal Utility Scoring
  -> Staleness Guard
  -> Update Memory Ledger
```

这个设计让 Memory 只沉淀偏好、口径、禁用路径和交互策略，而不是复制产物正文或资料内容。

## 7. 任务邻域个性化记忆详细设计

### 7.1 三层对象

建议把记忆链路拆成三个正式对象：

- `Memory Signal`：来自用户反馈、项目口径变更、明确否定路径和产物修改的弱信号
- `Memory Candidate`：待评估的候选记忆
- `Memory Object`：通过任务邻域评估后进入个性化控制层的记忆对象

### 7.2 记忆类型

推荐先保留四类：

- `Preference Memory`：回答风格、表达深度、语言偏好
- `Decision Memory`：项目已确认口径和架构边界
- `Negative Memory`：用户明确否定过的方案、表达和结构
- `Interaction Memory`：协作节奏、先讨论还是先改文档、提交推送习惯

### 7.3 核心评估

候选记忆不直接写入，而是经过四类评估：

- `Semantic Neighborhood Modeling`
  判断它适用于哪些任务邻域，例如问答、Note、Wiki、产物生成、Deep Research、简历表达或技术设计。

- `Marginal Utility Scoring`
  判断它是否能跨任务减少重复纠错、保持项目口径一致或提升表达质量。

- `Negative Memory Check`
  判断它是否属于禁用路径，并在生成前转成 forbidden patterns。

- `Staleness Guard`
  判断它是否已被更新口径覆盖、是否需要降权或失效。

### 7.4 Task Neighborhood 建模

`Task Neighborhood` 可以利用 NoteWeave 现有对象建模，不需要新造复杂图系统：

- Topic Scope
- Source Type
- Production Action
- Artifact Type
- Query Intent
- User / Workspace Preference

只要两个任务在这些维度上足够接近，就可以认为它们处于相邻任务簇。

### 7.5 运行时编译

Memory 不应无脑拼接进上下文，而应由 `Task-Neighborhood Memory Compiler` 编译为 `Memory Control Pack`。

建议采用：

- `Chat Control Pack`：统一服务问答、Note、Wiki，只根据 answer_mode 做轻量差异化
- `Artifact Control Pack`：服务右侧产物生成，控制风格、结构、受众、格式、禁用路径和证据边界
- `Research Control Pack`：服务 Deep Research，控制研究偏好、报告结构、禁用表达和输出风格

这样可以避免 Memory 污染资料证据链，同时让系统在跨任务中保持一致的个性化行为。

## 8. Agent / Skill / MCP 落地方式

### 8.1 Agent

Agent 不应该是一个“无边界大脑”，而应该是受控节点执行器。

在系统中的角色：

- 决定下一步做什么
- 在允许范围内选择能力
- 给出结构化输出

输出形式必须结构化，例如：

- LoopDecision
- ActionSelection
- VerificationResult
- ConflictResolution

### 8.2 Skill

Skill 是一类任务能力的封装。

建议 Skill 至少声明：

- skill id
- skill version
- default prompt recipe
- output contract
- verifier policy
- required capabilities

示例：

- report_generation
- quiz_generation
- study_guide_generation
- faq_generation
- wiki_page_generation
- note_document_generation

### 8.3 MCP

MCP 负责外部能力接入。

建议系统内部不要直接依赖具体 MCP 工具名，而是抽象为标准能力：

- READ_WEB_PAGE
- SEARCH_WEB

这样可以把具体实现解耦在“内置能力层”与“用户自有 MCP 连接层”内部。

## 9. 可观测性边界

技术架构层只定义哪些链路必须可观测，不重复展开 trace 表结构和字段。

必须记录三类 Trace：

### 9.1 Research Trace

- 搜索 query
- 候选对象选择
- 访问过的 source
- 抽取到的 evidence
- cell 状态变化
- verifier 结果

### 9.2 Artifact Trace

- Action 选择结果
- 读取内容来源
- 使用的 Skill / Recipe
- CCO 摘要
- 校验与修复记录
- 最终提交版本

### 9.3 Memory Trace

- signal 来源
- candidate 抽取结果
- novelty 分数
- neighborhood validation 结果
- promote / reject 决策
- 注入命中记录

具体 trace 表、任务表、outbox 和索引策略统一放在 [技术栈与数据库设计](D:/java-projects/NoteWeave-v2/docs/技术栈与数据库设计.md) 中维护。

## 11. 总结

NoteWeave v2 的技术架构核心不是“把所有 AI 能力混在一起”，而是：

- 用清晰的聊天回答链路承接用户任务
- 用 Deep Research Engine 承接重型研究
- 用 Artifact Runtime 承接结构化产物生成
- 用 Task-Neighborhood Memory Compiler 承接跨任务个性化控制
- 用 Agent / Skill / MCP 做能力栈
- 用统一业务对象和证据链路把所有结果沉淀下来
