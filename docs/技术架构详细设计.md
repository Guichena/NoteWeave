# NoteWeave v2 技术架构详细设计

## 1. 设计目标

这份文档承接 [系统架构设计](D:/java-projects/NoteWeave-v2/docs/系统架构设计.md) 的总纲，进一步回答三个问题：

1. 后端模块如何拆分
2. Deep Research 与 Artifact Runtime 如何协作
3. Agent / Skill / MCP 在系统里如何落地

## 2. 技术总图

推荐采用“入口层 + 应用编排层 + 核心域层 + 能力层 + 基础设施层”的结构：

```text
Client / UI
  -> API Gateway / BFF
  -> Application Orchestrators
  -> Domain Services
  -> Capability Layer
  -> Storage / Index / Queue / Object Store
```

## 3. 模块分层

### 3.1 接口层

负责承接前端调用：

- 问答接口
- Wiki 接口
- 调查接口
- Deep Research 接口
- Artifact Job 接口
- Source 上传与读取接口

推荐 API 组：

```text
/api/v2/chat/*
/api/v2/wiki/*
/api/v2/investigation/*
/api/v2/research/*
/api/v2/artifacts/*
/api/v2/sources/*
```

### 3.2 应用编排层

负责把一个用户请求编排成多个领域动作。

建议的编排器：

- ChatOrchestrator
- WikiOrchestrator
- InvestigationOrchestrator
- DeepResearchOrchestrator
- ArtifactJobOrchestrator

这里不直接承载底层智能逻辑，而是负责：

- 权限校验
- 上下文装配
- 调用领域服务
- 创建任务
- 组织返回结果

### 3.3 核心域层

这是系统真正的业务中台，建议包含以下域服务：

- WorkspaceDomainService
- TopicScopeDomainService
- SourceDomainService
- KnowledgeDomainService
- CitationDomainService
- ResearchDomainService
- ArtifactDomainService
- RetrievalDomainService

### 3.4 能力层

能力层用于承接“智能能力”与“外部能力”：

- Agent Runtime
- Skill Registry
- MCP Capability Gateway
- Prompt Recipe Registry
- Verification Engine

### 3.5 基础设施层

建议最少包含：

- Object Storage：原始文件、快照、导出结果
- Relational DB：核心业务对象
- Search Index：chunks、notes、wiki、artifacts、metadata
- Queue / Job System：Research Run、Artifact Job
- Trace / Log Store：Research Trace、Artifact Trace

## 5. Deep Research Engine 详细设计

### 5.1 执行结构

```text
DeepResearchOrchestrator
  -> Plan Agent
  -> Wide Search Agent
  -> Source Reader Agent
  -> Cell Extraction Agent
  -> Cell Verifier Agent
  -> Conflict Resolver
  -> Report Writer Agent
```

### 5.2 状态机

建议状态：

- CREATED
- PLANNING
- TABLE_READY
- WIDE_SEARCHING
- READING
- EXTRACTING
- VERIFYING
- RESOLVING
- WRITING
- COMPLETED
- PARTIAL_COMPLETED
- FAILED
- CANCELLED

### 5.3 Loop Engine

Loop Engine 负责决定下一步动作：

- 继续搜索
- 继续阅读
- 重新抽取
- 重新验证
- 处理冲突
- 进入写作
- 停止

输入：

- ResearchPlan
- ResearchTable
- VerificationResult
- Conflict 状态
- Budget 剩余量

输出：

- LoopDecision

### 5.4 研究对象

建议 Research Run 至少持久化以下对象：

- ResearchPlan
- ResearchTable
- ResearchRow
- ResearchCell
- SourceEvidence
- VerificationResult
- ConflictResolution
- FinalReport Snapshot

## 6. Artifact Runtime 详细设计

### 6.1 主链路

```text
Validate Input
  -> Resolve Action
  -> Normalize Input
  -> Plan Content Acquisition
  -> Acquire Content
  -> Build CCO
  -> Compile Context
  -> Run Prompt Recipe
  -> Verify / Repair
  -> Commit Artifact
  -> Index Artifact
```

### 6.2 Action Resolver

根据以下信息选择 Production Action：

- 用户点击的按钮
- 当前上下文类型
- 当前资料类型
- 用户配置偏好

### 6.3 Canonical Content Object

CCO 是 Artifact Runtime 的关键中间对象。

建议字段：

- kind
- title
- plainText
- segments
- sourceTrace
- metadata
- contentHash

### 6.4 Verify / Repair

建议至少检查：

- 内容是否为空
- 是否符合产物结构
- 是否包含必要章节
- 是否保留来源信息
- 是否出现明显长度异常

### 6.5 Artifact Commit

每次提交建议保存：

- 触发上下文
- 使用的 Action
- 使用的 Skill / Prompt Recipe
- 使用的 Source 列表
- 输入快照
- CCO 快照
- 校验结果
- 父版本

## 7. Agent / Skill / MCP 落地方式

### 7.1 Agent

Agent 不应该是一个“无边界大脑”，而应该是受控节点执行器。

在系统中的角色：

- 决定下一步做什么
- 在允许范围内选择能力
- 给出结构化输出

输出形式必须结构化，例如：

- LoopDecision
- ActionSelection
- VerificationResult
- ConflictResolution

### 7.2 Skill

Skill 是一类任务能力的封装。

建议 Skill 至少声明：

- skill id
- skill version
- default prompt recipe
- output contract
- verifier policy
- required capabilities

示例：

- report_generation
- quiz_generation
- study_guide_generation
- faq_generation
- video_summary_generation

### 7.3 MCP

MCP 负责外部能力接入。

建议系统内部不要直接依赖具体 MCP 工具名，而是抽象为标准能力：

- READ_WEB_PAGE
- EXTRACT_TRANSCRIPT
- TRANSCRIBE_AUDIO
- SEARCH_WEB

这样可以把具体实现解耦在 MCP Gateway 内部。

## 9. 队列与异步执行

### 9.1 Deep Research

Research Run 必须异步执行，因为它天然是长任务。

建议支持：

- 创建任务
- 拉起执行
- 中断
- 重试
- 恢复
- 查看进度

### 9.2 Artifact Job

Artifact Job 也必须走异步，因为右侧按钮生成的内容可能：

- 需要读取多个 Source
- 需要调用 MCP 外部能力
- 需要校验与修复

建议统一走任务系统，而不是同步阻塞请求。

## 11. 可观测性设计

建议至少记录两类 Trace：

### 11.1 Research Trace

- 搜索 query
- 候选对象选择
- 访问过的 source
- 抽取到的 evidence
- cell 状态变化
- verifier 结果

### 11.2 Artifact Trace

- Action 选择结果
- 读取内容来源
- 使用的 Skill / Recipe
- CCO 摘要
- 校验与修复记录
- 最终提交版本

## 12. 演进路线

第一阶段优先把核心闭环跑通：

- 问答
- 调查
- Deep Research
- 右侧产物生成
- 回写沉淀

第二阶段再扩展：

- 更复杂的 Skill 市场
- 更细的 Claim / Entity 结构化层
- 更丰富的 MCP 能力生态
- 更完善的多用户协作与审批

## 13. 总结

NoteWeave v2 的技术架构核心不是“把所有 AI 能力混在一起”，而是：

- 用清晰的工作模式承接用户任务
- 用 Deep Research Engine 承接重型研究
- 用 Artifact Runtime 承接结构化产物生成
- 用 Agent / Skill / MCP 做能力栈
- 用统一领域模型和证据链路把所有结果沉淀下来
