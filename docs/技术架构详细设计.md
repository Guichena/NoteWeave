# NoteWeave v2 技术架构详细设计

## 1. 设计目标

这份文档承接 [系统架构设计](D:/java-projects/NoteWeave-v2/docs/系统架构设计.md) 的总纲，进一步回答三个问题：

1. 后端模块如何拆分
2. Deep Research 与 Artifact Runtime 如何协作
3. Agent / Skill / MCP 在系统里如何落地
4. Graduated Memory 如何以可实现方式接入

## 2. 技术总图

推荐采用“入口层 + 应用编排层 + 核心域层 + 能力层 + 基础设施层”的结构：

```text
Client / UI
  -> API Gateway / BFF
  -> Application Orchestrators
  -> Domain Services
  -> Capability Layer
  -> Storage / Index / Queue / Object Store
```

在实现分工上，进一步推荐采用：

```text
Client / UI
  -> Java API / BFF
  -> Java Domain Services
  -> MySQL / Redis / Kafka / MinIO / Elasticsearch
  -> Python Research Worker
  -> Python Artifact Worker
```

其中：

- `Java` 负责研究工作台、三种聊天回答链路、业务真源、任务编排、状态管理和结果回写
- `Python Research Worker` 负责 `Deep Research` 的执行循环
- `Python Artifact Worker` 负责 `Artifact Runtime` 的执行循环

## 3. 模块分层

### 3.1 接口层

负责承接前端调用：

- 问答接口
- Note 接口
- Wiki 接口
- Deep Research 接口
- Artifact Job 接口
- 资料上传与读取接口

推荐 API 组：

```text
/api/v2/chat/*
/api/v2/notes/*
/api/v2/wiki/*
/api/v2/research/*
/api/v2/artifacts/*
/api/v2/sources/*
```

### 3.2 应用编排层

负责把一个用户请求编排成多个领域动作。

建议的编排器：

- ChatOrchestrator
- NoteOrchestrator
- WikiOrchestrator
- DeepResearchOrchestrator
- ArtifactJobOrchestrator

这里不直接承载底层智能逻辑，而是负责：

- 权限校验
- 上下文装配
- 调用领域服务
- 创建任务
- 组织返回结果

### 3.3 核心域层

这是系统真正的业务中台，建议包含以下域服务：

- WorkspaceDomainService
- TopicScopeDomainService
- MaterialDomainService
- KnowledgeDomainService
- CitationDomainService
- ResearchDomainService
- ArtifactDomainService
- MemoryDomainService
- RetrievalDomainService

### 3.4 能力层

能力层用于承接“智能能力”与“外部能力”：

- Agent Runtime
- Style Profile Registry
- Skill Graph Registry
- MCP Capability Gateway
- Prompt Recipe Registry
- Verification Engine

### 3.5 基础设施层

建议最少包含：

- Object Storage：原始文件、快照、导出结果
- Relational DB：核心业务对象
- Search Index：chunks、notes、wiki、artifacts、metadata
- Queue / Job System：Research Run、Artifact Job
- Trace / Log Store：Research Trace、Artifact Trace

## 5. Deep Research Engine 详细设计

本节的主链路设计，与 [深度研究智能体编排升级设计](D:/java-projects/NoteWeave-v2/docs/深度研究智能体编排升级设计.md) 中补充的 `TAS-Informed Verification-Centric Research Harness`、`Table-as-State`、`Dual Verifier`、`Counterfactual Branching`、`Premature Commitment Guard`、`Stop Contract` 等升级思路一起阅读更完整。

在当前产品口径下，Deep Research 不是第四种模式，而是跨 `问答 / Note / Wiki` 的独立系统能力。

### 5.1 执行结构

```text
DeepResearchOrchestrator
  -> Planning Unit
  -> Wide Search Executor
  -> Material Reader
  -> Cell Extractor
  -> Cell Verifier
  -> Conflict Resolver
  -> Report Synthesizer
```

在升级口径下，这套结构更适合理解为 `Research Harness + Controlled Responsibility Split`：

- Harness 负责状态、预算、停止条件、恢复和分支
- 总 Research Agent 内部按规划、搜索、读取、抽取、验证、纠偏和合成等职责拆成若干功能模块

### 5.2 状态机

建议状态：

- CREATED
- PLANNING
- TABLE_READY
- WIDE_SEARCHING
- READING
- EXTRACTING
- VERIFYING
- RESOLVING
- WRITING
- COMPLETED
- PARTIAL_COMPLETED
- FAILED
- CANCELLED

### 5.3 Loop Engine

Loop Engine 负责决定下一步动作：

- 继续搜索
- 继续阅读
- 重新抽取
- 重新验证
- 处理冲突
- 进入写作
- 停止

输入：

- ResearchPlan
- ResearchTable
- VerificationResult
- Conflict 状态
- Budget 剩余量
- Stop Contract

输出：

- LoopDecision

### 5.4 研究对象

建议 Research Run 至少持久化以下对象：

- ResearchPlan
- ResearchTable
- ResearchRow
- ResearchCell
- MaterialEvidence
- VerificationResult
- ConflictResolution
- FinalReport Snapshot

其中：

- `FinalReport Snapshot` 是必选对象，不是可选补充
- 研究报告完成后应入库为项目级正式资料
- 抓取网页、原文快照、检查点与过程证据优先保留为过程资产

如果后续正式引入 branchable harness，可补充：

- ResearchBranch
- ResearchExecutionCheckpoint
- ResearchHarnessPolicy

## 6. Artifact Runtime 详细设计

本节的主链路设计，与 [受控式异步产物生成Agent编排升级设计](D:/java-projects/NoteWeave-v2/docs/受控式异步产物生成Agent编排升级设计.md) 中补充的 `Schema-Gated Skill Graph Runtime`、`Style Profile`、`Capability Union Policy` 等升级思路一起阅读更完整。

### 6.1 主链路

```text
Validate Input
  -> Resolve Action
  -> Load Style Profile
  -> Resolve Workspace Material Scope
  -> Plan Material Acquisition
  -> Acquire Material Content
  -> Build CCO
  -> Compile Context
  -> Build Execution Plan
  -> Schema Gate
  -> Run Prompt Recipe
  -> Verify / Repair
  -> Commit Artifact
  -> Index Artifact
```

### 6.2 Action Resolver

根据以下信息选择 Production Action：

- 用户点击的按钮
- 当前研究工作台
- 当前资料池状态
- 用户配置偏好
- 当前 Style Profile

Production Action 与 Style Profile 属于生成任务要求，不属于产物生成的原材料。

### 6.3 Canonical Content Object

CCO 是 Artifact Runtime 的关键中间对象。

建议字段：

- kind
- title
- plainText
- segments
- sourceTrace
- metadata
- contentHash

### 6.4 Verify / Repair

建议至少检查：

- 内容是否为空
- 是否符合产物结构
- 是否包含必要章节
- 是否保留来源信息
- 是否出现明显长度异常

### 6.5 Artifact Commit

每次提交建议保存：

- 触发入口
- 使用的 Action
- 使用的 Style Profile
- 使用的 Skill / Prompt Recipe
- 使用的 资料列表
- 输入快照
- CCO 快照
- 校验结果
- 父版本

如果提交对象是 `Deep Research` 的最终研究报告，还应追加：

- project-level source mapping
- generated source metadata
- default retrieval enabled

### 6.6 Memory Promotion Hook

Artifact Runtime 不是每次生成后都直接写长期记忆，而是在提交后发出记忆候选事件。

推荐链路：

```text
Commit Artifact Version
  -> Extract Memory Candidate
  -> Score Novelty
  -> Validate Task Neighborhood
  -> Promote or Reject
```

这个设计让长期记忆建立在产物质量与复用价值之上，而不是建立在一次性生成文本之上。

## 7. Graduated Memory 详细设计

### 7.1 三层对象

建议把记忆链路拆成三个正式对象：

- `Context Signal`：来自聊天记录、Research Trace、用户反馈的弱信号
- `Memory Candidate`：待判断的记忆候选
- `Memory Object`：通过门控后进入长期复用层的记忆对象

### 7.2 来源分级

推荐按来源做不同置信度处理：

- Conversation：偏好、表达方式、任务意图
- Research Trace：研究路径、方法选择、证据偏好
- Artifact Version：结构化结论、FAQ、模板、稳定摘要
- Note / Wiki：人工整理后的稳定知识

其中：

- Conversation / Research Trace 更适合形成 `Context Signals`
- Artifact / Wiki 更适合形成高质量 `Memory Candidate`
- 研究报告更适合作为正式资料与可检索成果，是否进一步晋升长期记忆仍需单独门控

### 7.3 Dual-Gate Promotion

长期记忆晋升建议使用双门控：

1. `Novelty Gate`
   判断候选内容相对现有记忆是否足够新，避免重复写入。
2. `Task Neighborhood Validation`
   判断候选内容是否能在相邻任务簇中复用，而不是只对单次任务有效。

只有同时通过两道门，内容才进入 `Memory Object`。

### 7.4 Task Neighborhood 建模

`Task Neighborhood` 可以利用 NoteWeave 现有对象建模，不需要新造复杂图系统：

- Topic Scope
- Material Type
- Production Action
- Artifact Type
- Query Intent
- User / Workspace Preference

只要两个任务在这些维度上足够接近，就可以认为它们处于相邻任务簇。

### 7.5 运行时注入

长期记忆不应无脑拼接进上下文。

建议采用：

- Ask 模式：只注入用户偏好、表达约束、近期稳定主题
- Artifact Runtime：优先注入模板、方法偏好、结构约束
- Deep Research：默认只读取轻量偏好信号，不直接注入大段历史记忆

这样可以避免 Research 被历史记忆污染，同时让产物生成真正受益于长期沉淀。

## 8. Agent / Skill / MCP 落地方式

### 8.1 Agent

Agent 不应该是一个“无边界大脑”，而应该是受控节点执行器。

在系统中的角色：

- 决定下一步做什么
- 在允许范围内选择能力
- 给出结构化输出

输出形式必须结构化，例如：

- LoopDecision
- ActionSelection
- VerificationResult
- ConflictResolution

### 8.2 Skill

Skill 是一类任务能力的封装。

建议 Skill 至少声明：

- skill id
- skill version
- default prompt recipe
- output contract
- verifier policy
- required capabilities

示例：

- report_generation
- quiz_generation
- study_guide_generation
- faq_generation
- video_summary_generation

### 8.3 MCP

MCP 负责外部能力接入。

建议系统内部不要直接依赖具体 MCP 工具名，而是抽象为标准能力：

- READ_WEB_PAGE
- EXTRACT_TRANSCRIPT
- TRANSCRIBE_AUDIO
- SEARCH_WEB

这样可以把具体实现解耦在“内置能力层”与“用户自有 MCP 连接层”内部。

## 10. 队列与异步执行

### 10.1 Deep Research

Research Run 必须异步执行，因为它天然是长任务。

建议支持：

- 创建任务
- 拉起执行
- 中断
- 重试
- 恢复
- 查看进度

### 10.2 Artifact Job

Artifact Job 也必须走异步，因为右侧按钮生成的内容可能：

- 需要读取多个资料
- 需要调用 MCP 外部能力
- 需要校验与修复

建议统一走任务系统，而不是同步阻塞请求。

### 10.3 Memory Promotion Job

Memory Promotion 也建议走异步任务，因为它涉及：

- 候选抽取
- 新颖性比较
- 邻域验证
- 写入或拒绝

这样可以把记忆管理从主交互链路中解耦出来。

## 12. 可观测性设计

建议至少记录三类 Trace：

### 12.1 Research Trace

- 搜索 query
- 候选对象选择
- 访问过的 source
- 抽取到的 evidence
- cell 状态变化
- verifier 结果

### 12.2 Artifact Trace

- Action 选择结果
- 读取内容来源
- 使用的 Skill / Recipe
- CCO 摘要
- 校验与修复记录
- 最终提交版本

### 12.3 Memory Trace

- signal 来源
- candidate 抽取结果
- novelty 分数
- neighborhood validation 结果
- promote / reject 决策
- 注入命中记录

## 13. 建设顺序建议

建议先保证下面这些主链路天然互通：

- 问答
- Note
- Deep Research
- 右侧产物生成
- 回写沉淀

在这套主链路稳定之后，再逐步补强：

- 更复杂的 Skill 市场
- 更细的 Claim / Entity 结构化层
- 更精细的 Memory 类型拆分
- 更丰富的 MCP 能力生态
- 更完善的多用户协作与审批

## 14. 总结

NoteWeave v2 的技术架构核心不是“把所有 AI 能力混在一起”，而是：

- 用清晰的聊天回答链路承接用户任务
- 用 Deep Research Engine 承接重型研究
- 用 Artifact Runtime 承接结构化产物生成
- 用 Graduated Memory 承接长期复用知识
- 用 Agent / Skill / MCP 做能力栈
- 用统一业务对象和证据链路把所有结果沉淀下来
