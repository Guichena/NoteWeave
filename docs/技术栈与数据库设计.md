## 2. 设计原则

### 2.1 先单体、后拆分

v2 目标架构推荐采用 `模块化单体 + 异步 Worker`，而不是一开始就拆成很多微服务。

原因：

- 当前核心复杂度在产品模型、异步任务、证据链和记忆晋升，而不在超大团队协作
- Deep Research、Artifact Runtime、Graduated Memory 之间耦合很强，过早拆服务只会增加事务和联调成本
- 旧版 NoteWeave 已经验证了 `Spring Boot + MySQL + Kafka + MinIO + Elasticsearch` 这一条线可落地

### 2.2 MySQL 只存业务真源

MySQL 负责：

- 用户、工作区、主题边界
- 会话、知识对象、产物对象
- 任务状态、审计记录、记忆晋升记录

MySQL 不负责：

- 原始大文件正文
- 大段解析文本
- 向量本体

这些内容分别放到对象存储和检索索引中，避免 MySQL 被当成大文件仓库。

### 2.3 Elasticsearch 足够承接目标检索层

推荐继续用 `Elasticsearch 8.x` 做：

- BM25
- dense vector
- hybrid retrieval
- metadata filter

当前不建议默认引入独立向量库，例如 `Milvus / Qdrant / Weaviate`。

原因：

- v2 的核心卖点不是“极致向量检索性能”，而是“证据闭环 + 研究流程 + 产物生成 + 记忆晋升”
- ES 已能覆盖 BM25 + vector + filter 的统一索引需求
- 双索引体系会显著增加运维、回填和一致性成本

### 2.4 Kafka 只做后台任务总线

Kafka 适合承接：

- 文件解析
- 切块和索引
- Deep Research 长任务
- Artifact Job
- Memory Promotion Job

不建议拿 Kafka 做前端会话流状态。

前端流式响应、断线续传、短期运行态更适合：

- WebSocket / SSE
- Redis

### 2.5 记忆层必须门控

`Graduated Memory` 不是“把聊天历史全存下来”。

技术实现上必须强制保留：

- `Context Signal`
- `Memory Candidate`
- `Memory Object`
- `Novelty Gate`
- `Task Neighborhood Validation`

这样后面无论产品怎么扩，长期记忆都不会失控。

### 2.6 先配置化，后平台化

虽然要支持 `Production Action + Prompt Recipe + Skill + MCP`，但不建议把它做成一个复杂的“可视化 Agent 平台”。

更合理的落地方式是：

- `Production Action` 用数据库种子或配置文件初始化
- `Prompt Recipe` 用版本化模板管理
- `Skill Binding` 和 `MCP Capability Binding` 先走静态声明
- 后台先不做复杂的图形化编排器

原因：

- 当前目标是把问答、Deep Research、右侧产物栏、Memory 闭环跑通
- 不是先做一个独立的 Agent 平台产品
- 平台化过早会把精力从核心体验转移到配置系统本身

### 2.7 技术设计服从亮点主线

这套技术设计不是为了堆满技术名词，而是为了稳定支撑几条最重要的产品主线：

1. `Deep Research`
2. `Artifact Runtime`
3. `RAG / Wiki / Note`
4. `Graduated Memory`
5. `文件上传 / Kafka / MinIO`

如果某项技术、某张表或某个模块不能明显支撑这些主线，就不应该优先进入当前设计。

## 3. 推荐技术栈

### 3.1 前端

推荐：

- `React 18`
- `TypeScript 5`
- `Vite 6`
- `TanStack Query`
- `Zustand`
- `Tailwind CSS`
- `Radix UI / shadcn 风格基础组件`

推荐原因：

- v2 是典型三栏工作台，包含多面板上下文、右侧产物栏、长任务状态、版本回看、异步进度和多种视图切换
- 相比旧版原生 JS 页面，这一版的交互复杂度已经更适合 `React + TypeScript`
- `TanStack Query` 适合管理查询、轮询、缓存和失效
- `Zustand` 足够承接当前工作区 UI 状态，不需要一开始上 Redux

不建议：

- 直接上 Next.js 全栈
- 引入过重的低代码前端框架
- 同时引入多套状态管理

### 3.2 后端

推荐：

- `Java 21 LTS`
- `Spring Boot 3.3.x`
- `Spring Web`
- `Spring WebSocket`
- `Spring Data JPA`
- `Spring Validation`
- `Spring Security`
- `Spring Kafka`
- `Spring Actuator`
- `Flyway`

说明：

- 旧版 NoteWeave 已经验证 `Spring Boot 3.3.x` 路线，迁移成本最低
- `Java 21` 是未来更合理的长期版本；若短期受旧镜像限制，也可以先落 `Java 17`
- 后端结构采用“接口层 + 编排层 + 领域服务层 + 能力层 + 基础设施层”

### 3.3 数据与中间件

推荐：

- `MySQL 8.4`
- `Redis 7.2`
- `Kafka 3.x（KRaft）`
- `MinIO`
- `Elasticsearch 8.x`

对应职责：

- `MySQL`
  核心业务真源

- `Redis`
  登录态、短期缓存、幂等键、WebSocket 运行态

- `Kafka`
  异步任务总线

- `MinIO`
  原始文件、快照、导出文件、解析大文本、研究/产物快照

- `Elasticsearch`
  chunk / note / wiki / artifact / memory 检索

### 3.4 模型与 AI 能力

推荐：

- `OpenAI-compatible LLM Gateway`
- `OpenAI-compatible Embedding Gateway`
- `Prompt Recipe Registry`
- `Skill Registry`
- `MCP Gateway`

原因：

- 保持模型供应商可替换
- 便于在 `Deep Research`、`Artifact Runtime`、`Graduated Memory` 三条链路之间复用
- 方便接 DeepSeek、OpenAI、阿里兼容网关、Gemini 代理层等实现

### 3.5 运维与测试

推荐：

- `Docker Compose` 作为本地环境
- `Testcontainers` 作为集成测试基座
- `Prometheus + Grafana` 作为后续观测增强方向

集成测试至少覆盖：

- MySQL
- Redis
- Kafka
- MinIO
- Elasticsearch

## 4. 当前架构不建议默认引入的东西

为了保证整体合理性，当前架构明确不建议默认引入以下技术：

- 微服务拆分
- 独立向量数据库
- 图数据库
- Flink / Spark 一类流计算框架
- Kubernetes 级多环境编排作为开发前提
- 全量事件溯源
- 分布式事务框架

这些东西不是永远不用，而是当前目标架构下并不构成优先收益。

- `auth`

推荐采用下面这套分层：

### 6.1 MySQL

保存：

### 6.2 MinIO

### 6.4 Redis

## 7. MySQL 设计总原则

### 7.1 命名规则

- 表名统一小写下划线
- 主键统一 `id BIGINT`
- 时间字段统一：
  `created_at`
  `updated_at`
- 可选软删除统一：
  `deleted_at`
  `deleted_by`

### 7.2 公共约束

- 字符集统一 `utf8mb4`
- 所有状态字段统一显式枚举字符串，不用隐式数字编码
- JSON 类字段只用于快照、运行时输入输出，不作为主检索字段
- 核心关系尽量使用关系表，不用 `citation_ids_json` 这种反模式

### 7.3 设计边界

以下对象必须独立建表，不能混在一张“万能内容表”里：

- `Conversation`
- `Knowledge Item`
- `Research Run`
- `Artifact`
- `Memory Object`

这是为了保证生命周期边界清晰。

### 7.4 主键与版本策略

为了保证实现简单稳定，推荐：

- MySQL 主键统一使用 `BIGINT AUTO_INCREMENT`
- 面向外部展示的对象可按需补 `public_id` / `biz_key`
- 版本对象统一使用 `(owner_id, version_no)` 约束，而不是把所有版本塞进一张通用版本表

这样更有利于：

- 降低 JPA / SQL 联调复杂度
- 保持分页、排序、批量写入行为稳定
- 避免把 ID 体系做成过重的分布式设计

## 11. 合理性检查结论

这套设计之所以相对合理，核心原因有五个：

1. `沿用旧版已验证基础设施`
   没有凭空换掉后端语言、主数据库、消息总线和对象存储。

2. `模块化单体优先`
   能覆盖当前复杂度，又不会把系统过早拆散。

3. `MySQL 真源、MinIO 大对象、ES 检索`
   数据职责分层清晰。

4. `Research / Artifact / Memory 生命周期明确分离`
   不会把“研究过程”“生成结果”“长期知识”混成一种对象。

5. `主动克制复杂度`
   明确不上微服务、向量库、图数据库、分布式事务这些高成本方案。

补充两条实现层面的合理性判断：

6. `先配置化，不先平台化`
   Action、Recipe、Skill、MCP 先服务业务闭环，而不是先做后台编排平台。

7. `主键与版本策略保持朴素`
   优先保证 SQL、迁移和对象关系稳定，不为了“高级感”引入过重 ID 设计。
