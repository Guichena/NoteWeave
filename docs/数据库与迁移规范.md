# NoteWeave v2 数据库与迁移规范

> 文档状态：DRAFT / 目标规范
>
> 权威等级：L4
>
> 最后核对日期：2026-07-12
>
> 当前实际结构以 `backend/src/main/resources/db/migration` 为 L0 事实源

## 1. 基本原则

- MySQL 是业务真源；
- Flyway 是唯一 schema 变更入口；
- 已发布 migration 不得修改；
- ES、Redis 和 Worker 本地状态不是业务真源；
- 大文件、报告和 checkpoint 存 MinIO；
- JSON 用于低频扩展和审计快照，不替代核心关系模型；
- 所有复杂状态更新使用合法状态条件和 version/CAS；
- 所有跨系统可靠投递使用 Outbox。

## 2. Migration 纪律

### 2.1 禁止事项

- 修改已经执行的 V001～V024；
- 手工改线上表后不补 migration；
- 为兼容 H2 修改历史 MySQL migration；
- 在应用启动时自动生成生产表；
- 一个 migration 同时进行不可回滚的大数据回填和破坏性删列。

### 2.2 Expand-and-Contract

```text
Expand：新增表/列/索引
Backfill：分批迁移数据
Dual Read：新读优先、旧读 fallback
Switch Write：只保留新写入者
Observe：指标和一致性校验
Contract：删除旧列/表/兼容代码
```

## 3. 目标核心模型

### 3.1 Answer

```text
answer_run
message_revision
answer_evidence_snapshot
```

普通 QA 只需要 AnswerRun。异步 Answer 通过可空 `execution_id` 关联长任务控制面。

### 3.2 Execution

```text
execution
execution_attempt
execution_event
```

Execution 只承接 Research、Artifact、Source、Rebuild、Export 和异步 Answer。

### 3.3 Reliable Delivery

```text
outbox_message
worker_callback_receipt
command_receipt（按需）
projection_checkpoint
```

不创建一个要求所有消费者写入的全局 `inbox_receipt`。

## 4. Outbox 表设计

建议字段：

```text
id
aggregate_type
aggregate_id
destination_type
destination
message_key
schema_version
payload_json / payload_locator
status
attempt_count
next_attempt_at
lease_owner
lease_until
last_error_code
last_error_message
created_at
sent_at
dead_lettered_at
version
```

核心索引：

```text
(status, next_attempt_at, created_at)
(destination, status, lease_until, created_at)
(aggregate_type, aggregate_id, created_at)
```

Claim 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 或条件 UPDATE/CAS。Dispatcher 不在长事务中执行网络请求。

## 5. 幂等数据设计

### 5.1 Worker Claim

`execution_attempt` 保存：

- attempt_no；
- worker_id；
- claimed_at；
- heartbeat_at；
- status；
- version。

只有 execution.active_attempt_id 对应的 attempt 可以提交结果。

### 5.2 Callback Receipt

```text
unique(attempt_id, idempotency_key)
```

保存 callback_type、result_status、result_ref，重复请求返回相同 Ack。

### 5.3 Projection Version

ES/Wiki 投影保存 aggregateVersion。只有新版本事件可以覆盖旧投影。

### 5.4 Command Receipt

只为不可自然幂等的外部业务命令创建：

```text
unique(consumer_name, command_id)
```

普通投影和缓存失效事件不写该表。

## 6. 状态与并发

所有复杂状态表至少包含：

```text
status
version
created_at
updated_at
```

更新示例：

```sql
update execution
set status = ?, version = version + 1, updated_at = current_timestamp
where id = ?
  and status in (?, ?)
  and version = ?;
```

affectedRows=0 表示重复、迟到或并发冲突，不能继续无条件写事件。

## 7. 线程池与数据库边界

- 事务不能跨线程传播；
- 在线线程只完成短事务；
- 线程池任务先读取必要快照，再在独立事务中提交；
- Outbox dispatcher claim 和 finalize 使用两个短事务；
- 线程池拒绝不能导致已提交业务命令丢失；
- maintenance 扫描使用分页和时间窗口，避免全表锁。

## 8. Redis 与数据库关系

### Redis 可以保存

- SSE Stream 的短期事件；
- 权限/Catalog/Projection 缓存；
- 限流计数；
- 短期协调 token；
- single-flight 标记。

### Redis 不可以作为唯一来源

- Execution 当前状态；
- Worker Attempt；
- Outbox 发送状态；
- Callback Receipt；
- Artifact/Research Version；
- Source READY 状态。

Redis key 丢失后，系统必须能够从 MySQL/MinIO 重建。

## 9. JSON 与对象存储

| 数据 | 存储位置 |
|---|---|
| 可查询状态、权限、版本 | MySQL 列/关系表 |
| 小型扩展配置 | MySQL JSON/longtext + schema_version |
| Research 大 checkpoint | MinIO + MySQL locator/hash |
| Artifact/Research 正文 | MinIO + 版本元数据，必要时 MySQL 保存小型展示副本 |
| 原文件 | MinIO source bucket |
| 导出 PDF | MinIO export bucket |

## 10. 索引规范

- 索引必须服务真实查询；
- list 接口优先 cursor `(created_at, id)`；
- Workspace 隔离字段通常位于组合索引前部；
- 状态扫描索引包含 status/nextAttempt/createdAt；
- 唯一约束优先承担幂等，不只依赖应用查询；
- 上线前使用 `EXPLAIN` 验证核心 Query；
- 禁止为所有 JSON 字段建立无依据索引。
