# NoteWeave v2 数据库迁移与建表顺序

## 1. 定位

这份文档不再讨论“系统该怎么设计”，只回答三个直接开工问题：

1. `Flyway migration` 应该按什么顺序创建
2. 第一批必须冻结哪些表，才能开始写代码
3. 哪些表现在就该建，哪些可以后补，避免一上来过度铺开

它承接：

- [技术栈与数据库设计](D:/java-projects/NoteWeave-v2/docs/技术栈与数据库设计.md)
- [代码落地路线与开工清单](D:/java-projects/NoteWeave-v2/docs/代码落地路线与开工清单.md)

## 2. 迁移总原则

### 2.1 只允许 Flyway 管库

正式开发阶段统一关闭自动 DDL：

- 不依赖 Hibernate 自动建表
- 不允许手工改线上结构
- 一切结构变更都通过 `Flyway migration` 进入仓库

### 2.2 先建真源，再建引用关系

迁移顺序必须遵守：

1. 先建用户、工作台、资料、任务这些真源表
2. 再建消息、引用、知识、研究、产物、记忆这些业务层对象
3. 最后再建 trace、seed、扩展绑定表

### 2.3 先保证主闭环，不先建全部增强表

第一阶段真正阻塞代码的，是这四段主闭环：

1. 工作台与成员
2. 资料上传、解析、切片、索引
3. 会话、消息、引用
4. 任务、outbox、Worker 调度

`skill_binding`、`mcp_capability_binding`、`research_branch` 这类增强表可以放后面，不作为第一批前置条件。

## 3. 推荐迁移文件顺序

下面这套顺序可以直接作为 `backend/src/main/resources/db/migration/` 的初始文件规划。

### 3.1 基础身份与工作台

`V001__create_user_and_workspace_tables.sql`

表：

- `users`
- `user_session`
- `workspace`
- `workspace_member`
- `topic_scope`

原因：

- 这是所有资料、会话、任务、知识对象的根依赖
- 不先冻结 `workspace` 边界，后面所有外键都会反复改

### 3.2 统一任务与事务外盒

`V002__create_task_and_outbox_tables.sql`

表：

- `task`
- `task_attempt`
- `task_event`
- `task_outbox`

原因：

- 文件解析、索引、Research、Artifact 都依赖这套任务骨架
- 如果没有 `task + outbox`，后面 Kafka 链路很容易各写一套

### 3.3 对象存储映射与资料主表

`V003__create_source_core_tables.sql`

表：

- `file_object`
- `source`
- `source_snapshot`
- `document_upload`
- `upload_chunk`

原因：

- 这是资料池的主干
- 文件上传、去重、版本快照都要先定下来

### 3.4 资料切片与原文回读

`V004__create_source_read_tables.sql`

表：

- `source_chunk`
- `source_window`

原因：

- 问答 RAG、Note、Wiki、Citation 都依赖稳定的 chunk 与窗口定位
- 这两张表必须在真正写检索前先冻结

### 3.5 会话与聊天消息

`V005__create_conversation_tables.sql`

表：

- `conversation`
- `conversation_scope`
- `conversation_message`
- `ui_context_snapshot`

原因：

- 三种聊天链路共用同一套会话模型
- `ui_context_snapshot` 也是 Deep Research 和 Artifact 任务触发时的上下文冻结点

### 3.6 统一引用对象

`V006__create_citation_tables.sql`

表：

- `citation`
- `message_citation`

原因：

- 第一阶段先把“消息引用资料”跑通就够了
- `knowledge_version_citation` 和 `artifact_version_citation` 可以放到对应对象落地时再建

### 3.7 Note / Wiki 知识对象

`V007__create_knowledge_tables.sql`

表：

- `knowledge_item`
- `knowledge_version`
- `knowledge_version_citation`

原因：

- Note 与 Wiki 共享知识对象主模型
- 这一步做完，三种聊天模式的数据承载就齐了

### 3.8 产物生成主表

`V008__create_artifact_tables.sql`

表：

- `artifact`
- `artifact_job`
- `artifact_version`
- `artifact_version_citation`

原因：

- 右侧产物栏至少需要“任务对象 + 版本对象 + 保存为资料”的闭环

### 3.9 产物动作与生成配置

`V009__create_artifact_config_tables.sql`

表：

- `production_action`
- `style_profile`
- `prompt_recipe`
- `skill_graph_template`

原因：

- 这些表是 Artifact Worker 的最小配置底座
- `skill_binding`、`mcp_capability_binding` 可后续再补

### 3.10 Deep Research 主对象

`V010__create_research_tables.sql`

表：

- `research_run`
- `research_row`
- `research_cell`
- `research_trace`

原因：

- 这一步冻结后，Research Worker 才能开始对接 Java 主系统

### 3.11 Memory 主对象

`V011__create_memory_tables.sql`

表：

- `memory_signal`
- `memory_candidate`
- `memory_object`
- `memory_usage_log`

原因：

- Memory 不应该抢在资料、聊天、Research、Artifact 前面落地
- 但也不该一直停留在概念层，所以在主闭环稳定后进入

### 3.12 检索与审计增强

`V012__create_trace_tables.sql`

表：

- `retrieval_trace`
- `llm_call_log`
- `artifact_trace`
- `memory_trace`

原因：

- 这些表重要，但不是主链路起步的硬前置

### 3.13 初始化种子数据

`V013__seed_builtin_actions_and_profiles.sql`

数据：

- 默认 `Production Action`
- 默认 `Style Profile`
- 默认 `Prompt Recipe`
- 默认 `Skill Graph Template`

原因：

- 没有这批种子，右侧产物栏虽然有表，但没法真正点击出内容

## 4. 第一批必须冻结的表

如果目标是尽快开始写代码，下面这批表必须先冻结：

1. `users`
2. `workspace`
3. `workspace_member`
4. `topic_scope`
5. `task`
6. `task_event`
7. `task_outbox`
8. `file_object`
9. `source`
10. `source_snapshot`
11. `document_upload`
12. `upload_chunk`
13. `source_chunk`
14. `source_window`
15. `conversation`
16. `conversation_message`
17. `ui_context_snapshot`
18. `citation`
19. `message_citation`

这批表一旦稳定，下面三件事就都能开干：

1. 工作台与资料上传
2. 问答 RAG 与引用返回
3. Kafka / Worker 异步任务骨架

## 5. 可以后补的表

为了避免一上来把数据库铺得过重，下面这些表建议在对应链路真正开始写时再补：

1. `knowledge_item`
2. `knowledge_version`
3. `artifact`
4. `artifact_version`
5. `artifact_job`
6. `research_run`
7. `research_row`
8. `research_cell`
9. `memory_signal`
10. `memory_candidate`
11. `memory_object`
12. `skill_binding`
13. `mcp_capability_binding`
14. `capability_union_policy`
15. `research_branch`
16. `research_execution_checkpoint`

这些不是不要，而是不必阻塞第一批代码。

## 6. 外键依赖顺序

为了避免迁移回滚和循环依赖，建议按下面依赖理解建表：

1. `users -> workspace -> workspace_member / topic_scope`
2. `workspace -> task`
3. `workspace -> file_object -> source -> source_snapshot`
4. `source_snapshot -> source_chunk / source_window`
5. `workspace -> conversation -> conversation_message`
6. `conversation_message + citation -> message_citation`
7. `workspace -> knowledge_item -> knowledge_version`
8. `workspace -> artifact -> artifact_job -> artifact_version`
9. `workspace -> research_run -> research_row / research_cell`
10. `workspace -> memory_signal -> memory_candidate -> memory_object`

注意：

- `citation` 自身应直接指向 `source / source_snapshot / source_chunk / source_window`
- 不要让 `citation` 反向依赖 `message_citation`
- `artifact_job`、`research_run` 与 `task` 是并行对象，不要混成同一张业务表

## 7. 首批索引与约束

第一批迁移里就应该带上的，不要拖到后面再补：

### 7.1 唯一约束

- `users.username`
- `users.email`
- `source_snapshot (source_id, version_no)`
- `upload_chunk (upload_id, chunk_index)`
- `conversation_message (conversation_id, message_seq)`

### 7.2 高频索引

- `workspace (owner_id, updated_at)`
- `source (workspace_id, status, updated_at)`
- `source (workspace_id, parse_status, index_status)`
- `source_chunk (source_snapshot_id, chunk_no)`
- `conversation (workspace_id, last_active_at)`
- `conversation_message (conversation_id, created_at)`
- `task (task_status, created_at)`
- `task_outbox (status, created_at)`

## 8. 开工建议

真正开始写数据库时，推荐顺序是：

1. 先落 `V001` 到 `V006`
2. 立刻打通工作台、上传、问答、引用闭环
3. 再落 `V007` 到 `V010`
4. 最后再接 `V011` 到 `V013`

也就是说，当前最需要的不是再讨论数据库还能怎么设计，而是先把第一段真实可跑的迁移写出来。
