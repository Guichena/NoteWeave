# NoteWeave v2 智能体工程落地设计

## 1. 目的

这份文档只围绕当前 NoteWeave v2 的智能体体系回答四个问题：

1. 当前应该落哪几个智能体能力
2. 这些能力需要哪些中间件与运行组件
3. 中间件内部应该如何设置，才能既够用又不过度设计
4. MySQL 需要哪些核心表，表之间如何关联

## 2. 当前智能体范围

当前系统只做三条主链路：

1. `Deep Research 智能体`
   负责开放式研究、证据绑定、验证闭环、反证分支与研究报告生成。

2. `受控式异步产物生成智能体`
   负责右侧产物栏的报告、FAQ、测验、学习指南、Wiki 草稿等异步生成任务。

3. `Graduated Memory 晋升链路`
   负责从聊天、研究与产物中抽取信号，把高质量内容晋升为长期记忆对象。

这里的“智能体”都不应该理解成多个自治子 Agent 在内部对话，而应理解为：

- 一个总 `Research Agent`
- 一个总 `Artifact Agent`
- 若干内部功能模块
- 一套共享能力底座

## 3. 总体落地形态

推荐采用：

`Java 主系统 + Python 智能体执行器 + 共享中间件`

最小部署结构：

```text
Web Client
  -> api-app
      -> MySQL
      -> Redis
      -> Kafka
      -> MinIO
      -> Elasticsearch
  -> python-research-worker
      -> Kafka
      -> MySQL
      -> Redis
      -> MinIO
      -> Elasticsearch
      -> OpenAI Python SDK / OpenAI-compatible API
  -> python-artifact-worker
      -> Kafka
      -> MySQL
      -> Redis
      -> MinIO
      -> Elasticsearch
      -> OpenAI Python SDK / OpenAI-compatible API
```

组件职责：

- `api-app`
  负责同步接口、会话接口、任务创建、上下文冻结、SSE / WebSocket 推送、结果回写。

- `python-research-worker`
  负责 `Deep Research` 执行。

- `python-artifact-worker`
  负责 `Artifact Job` 执行。

- `Java` 后台任务
  初期仍可负责文件解析、切块索引、Memory Promotion。

- `MySQL`
  保存任务真源、知识对象、研究状态、产物版本、记忆对象。

- `Kafka`
  只负责后台任务总线，不负责前端流式会话状态。

- `Redis`
  负责短期运行态、幂等键、进度快照、SSE / WebSocket resume。

- `MinIO`
  负责大对象与快照，包括原始文件、解析文本、研究快照、导出文件。

- `Elasticsearch`
  负责统一检索层，包括 chunk、note、wiki、artifact、memory。

- `Model Access Layer`
  `Java` 主系统只保留轻量配置与统一接入抽象；两个 Python 智能体执行器内部直接基于 `OpenAI Python SDK` 或兼容接口实现模型调用。

## 4. 智能体内部模块

### 4.1 Deep Research 智能体

总 `Research Agent` 内部建议拆成这些功能模块：

- `Research Planner`
  把问题重写成研究意图、研究表结构、停止契约和初始计划。

- `Wide Search Executor`
  负责宽搜索，先拉开候选来源空间。

- `Source Reader`
  负责网页、PDF、文档片段的定向读取。

- `Cell Extractor`
  负责把读取结果转换成候选字段值与候选证据。

- `Cell Verifier`
  负责字段级验证、引用级验证、冲突检测。

- `Conflict Resolver`
  负责局部修复、反证分支、路径纠偏。

- `Report Synthesizer`
  负责基于已验证状态合成研究报告。

- `Research State Ledger`
  负责保存 `run / branch / row / cell / trace / checkpoint`。

### 4.2 受控式异步产物生成智能体

总 `Artifact Agent` 内部建议拆成这些功能模块：

- `Action Resolver`
  根据按钮动作确定要生成什么。

- `Style Resolver`
  装配风格配置、语言偏好、长度偏好、格式要求。

- `Context Compiler`
  把问答上下文、检索结果、研究产物、已有 Note / Wiki 编成统一上下文对象。

- `Skill Graph Runtime`
  按模板决定调用哪些内置能力。

- `Capability Resolver`
  决定当前任务允许使用哪些内置 Skill 和哪些 MCP 能力。

- `Schema Gate`
  检查输入结构与输出结构是否满足契约。

- `Artifact Verifier`
  对最终输出做结构检查、引用检查、风格检查和修复。

- `Artifact Committer`
  负责版本写入、导出文件回存、结果回流检索层与记忆候选生成。

### 4.3 共享能力底座

两条主链路共用下面几类底座：

- `Prompt Recipe Registry`
- `Style Profile Registry`
- `Built-in Skill Registry`
- `MCP Capability Binding`
- `Citation / Evidence Layer`
- `Task / Outbox Runtime`
- `Trace / Audit Runtime`

## 5. 必要中间件与取舍

### 5.1 必须保留

- `MySQL`
- `Kafka`
- `Redis`
- `MinIO`
- `Elasticsearch`
- `SSE 或 WebSocket`
- `OpenAI SDK / OpenAI-compatible SDK`

### 5.2 当前不建议默认引入

- 独立 `LLM Gateway`
- 微服务拆分
- 独立向量数据库
- 图数据库
- Flink / Spark
- Kubernetes 作为本地开发前提

原因很简单：

- 当前系统的复杂度核心在长任务、证据闭环、产物编排和记忆晋升
- 不在海量服务治理
- 不在超高频消息计算
- 不在多套模型网关编排

## 6. 中间件详细设置

### 6.1 MySQL

推荐版本：

- `MySQL 8.4`

推荐设置：

- 字符集统一 `utf8mb4`
- 时间字段统一 `datetime(3)`
- 主键统一 `BIGINT AUTO_INCREMENT`
- JSON 字段只承接配置、快照、运行态，不作为主筛选条件
- 状态字段使用 `varchar(32)` 或 `varchar(64)`，不急着上数据库 enum

核心原则：

- MySQL 只存业务真源
- 大正文不进 MySQL
- 大快照不进 MySQL
- 向量本体不进 MySQL
- 长任务派发必须走 `task + task_outbox`

连接池建议：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 3000
      validation-timeout: 1000
      max-lifetime: 1800000
```

### 6.2 Kafka

推荐版本：

- `Kafka 3.x`
- `KRaft` 模式

推荐 Topic：

- `source.parse`
- `source.index`
- `research.run`
- `artifact.job`
- `memory.promotion`
- `task.retry`

推荐 Consumer Group：

- `nw-source-worker`
- `nw-research-worker`
- `nw-artifact-worker`
- `nw-memory-worker`

建议设置：

- Topic 只传任务身份和轻量载荷
- 大文本与大快照回 MySQL / MinIO
- 每类任务单独 consumer group
- 失败重试走 `task.retry` 或应用层重投
- 保留幂等键，避免重复执行

建议分区数：

- `source.parse`: `3`
- `source.index`: `3`
- `research.run`: `6`
- `artifact.job`: `6`
- `memory.promotion`: `3`

这里不建议为了“先进”把 Research 内部每一步都拆成 Kafka 微步骤。当前更合理的是：

- 一个 `Research Run` 对应一个后台任务
- 任务内部在 Worker 里跑受控循环
- 外部只同步关键状态和关键事件

### 6.3 Redis

推荐版本：

- `Redis 7.2`

当前用途：

- 任务进度快照
- SSE / WebSocket resume token
- 幂等键
- 短期会话上下文缓存
- 高频 Memory 读缓存

建议 Key 设计：

```text
nw:task:progress:{taskId}
nw:research:run:{runId}:progress
nw:artifact:job:{jobId}:progress
nw:sse:resume:{channelId}
nw:idempotency:{bizKey}
nw:memory:hot:{workspaceId}:{memoryType}
```

建议 TTL：

- 任务进度：`24h`
- resume token：`2h`
- 幂等键：`10min`
- 高频记忆缓存：`30min`

明确不做：

- 不把任务主状态只放 Redis
- 不把研究账本放 Redis
- 不把长期记忆真源放 Redis

### 6.4 MinIO

当前建议 Bucket：

- `nw-raw-source`
- `nw-source-parsed`
- `nw-research-snapshot`
- `nw-artifact-export`
- `nw-citation-snapshot`

建议对象 Key 结构：

```text
raw/{workspaceId}/{sourceId}/{yyyy}/{MM}/{dd}/{fileName}
parsed/{workspaceId}/{sourceId}/parsed.txt
research/{workspaceId}/{runId}/checkpoint/{checkpointNo}.json
research/{workspaceId}/{runId}/report/final.md
artifact/{workspaceId}/{artifactId}/version/{versionNo}.md
citation/{workspaceId}/{citationId}/snapshot.json
```

建议只在 MinIO 中保存：

- 原始文件
- 大段解析文本
- 研究 checkpoint
- 产物导出文件
- 引用快照

不建议把小型配置对象全部拆成独立 MinIO 文件。

### 6.5 Elasticsearch

推荐版本：

- `Elasticsearch 8.x`

建议索引：

- `nw-source-chunk`
- `nw-note`
- `nw-wiki`
- `nw-artifact`
- `nw-memory`

检索策略：

- `BM25 + dense vector + metadata filter`
- Deep Research 优先命中文档与来源片段
- Artifact Agent 优先命中上下文对象、研究产物与知识对象
- Memory 检索只做增强，不直接覆盖当前任务上下文

Mapping 原则：

- 长正文用 `text`
- 可筛选字段单独建 `keyword`
- 向量字段统一 embedding 维度
- 不在一个索引里混太多异构对象

### 6.6 SSE / WebSocket

当前建议：

- 任务进度优先用 `SSE`
- 需要更强交互时再补 `WebSocket`

SSE 事件类型建议：

- `task-created`
- `task-progress`
- `research-stage-changed`
- `artifact-stage-changed`
- `task-completed`
- `task-failed`

建议推送内容：

- 当前阶段
- 百分比区间
- 当前子目标
- 当前来源数量
- 当前分支数量
- 当前预算消耗

不要推送：

- 全量研究账本
- 大段正文
- 高频 token 级日志

### 6.7 模型接入层

当前建议直接基于 `OpenAI SDK` 或兼容接口实现一层轻量封装：

- `ChatModelClient`
- `EmbeddingClient`
- `ModelCallLogger`
- `PromptTemplateRenderer`

建议配置项：

```yaml
noteweave:
  ai:
    default-provider: openai-compatible
    chat-model: gpt-5
    embedding-model: text-embedding-3-large
    timeout-ms: 60000
    max-retries: 2
    temperature:
      research-plan: 0.2
      research-synthesis: 0.3
      artifact-generate: 0.6
      artifact-repair: 0.2
```

这里明确不单独做 `LLM Gateway` 服务。

## 7. 智能体任务链路

### 7.1 Deep Research

```text
POST /api/v2/research/runs
  -> 创建 research_run
  -> 创建 task(RESEARCH_RUN)
  -> 写 task_outbox
  -> outbox publisher 投递 research.run
  -> python-research-worker 消费
  -> 运行 Research Agent 内部功能模块
  -> 持续写 research_row / research_cell / research_trace
  -> 推送 Redis 进度快照
  -> SSE 持续反馈
  -> 生成报告并写 artifact / artifact_version
  -> 可选生成 memory_candidate
```

### 7.2 Artifact Job

```text
POST /api/v2/artifacts/jobs
  -> 创建 artifact_job
  -> 创建 task(ARTIFACT_JOB)
  -> 写 task_outbox
  -> outbox publisher 投递 artifact.job
  -> python-artifact-worker 消费
  -> 装配 Style / Prompt / Skill Graph / Capability Policy
  -> 运行 Artifact Agent
  -> 写 artifact / artifact_version
  -> 写 artifact_trace
  -> 可选生成 memory_candidate
```

### 7.3 Memory Promotion

```text
Artifact Confirmed / Wiki Confirmed / Note Confirmed
  -> 抽取 context_signal / memory_candidate
  -> 创建 task(MEMORY_PROMOTION)
  -> 写 task_outbox
  -> 投递 memory.promotion
  -> Java 后台任务执行 novelty gate + neighborhood validation
  -> 满足条件时写 memory_object
```

## 8. MySQL 表结构设计

## 8.1 设计原则

- 表结构优先服务 `Research / Artifact / Memory` 三条主链路
- 首版优先保留稳定关系与高频查询路径
- 大 JSON 只做运行时快照和配置承载
- 需要审计的长任务必须有 `trace` 或 `event` 表

## 10. 推荐索引与查询路径

必须优先保障这些查询路径：

- `research_run.workspace_id + run_status + created_at`
- `research_row.research_run_id + updated_at`
- `research_cell.research_row_id + column_key`
- `research_trace.research_run_id + created_at`
- `artifact_job.workspace_id + status + created_at`
- `artifact_version.artifact_id + version_no`
- `task.task_status + created_at`
- `task_outbox.publish_status + next_retry_at`
- `memory_candidate.workspace_id + status + created_at`
- `memory_object.workspace_id + memory_type + status`

不建议做的索引：

- 给 `content_markdown`、`canonical_content` 这类长文本建普通索引
- 给大 JSON 字段建复杂函数索引
- 为每个低区分度状态字段单独反复建索引

接口职责：

- Controller 只做请求接入与响应封装
- Orchestrator 负责启动任务与组装上下文
- Domain Service 负责领域规则
- Worker Handler 负责消费 Kafka 任务
- Runtime Module 负责执行具体智能体内部功能

## 12. 当前阶段最合理的实现顺序

1. 先打通 `task + task_outbox + Kafka + worker` 骨架
2. 再落 `Research Agent` 的 `run / row / cell / trace`
3. 再落 `Artifact Agent` 的 `job / artifact / version / action`
4. 再补 `Style Profile / Prompt Recipe / Skill Graph Template`
5. 再补 `Memory Candidate / Memory Object`
6. 最后补 `用户自定义 MCP 连接` 与更完整观测

## 13. 设计结论

当前最合理的智能体工程方案不是做一个很重的 Agent 平台，而是：

- 用一个总 `Research Agent` 承接深度研究
- 用一个总 `Artifact Agent` 承接异步产物生成
- 用 `Graduated Memory` 承接长期沉淀
- 用 `task + outbox + Kafka + worker` 承接长任务
- 用 `MySQL + MinIO + Elasticsearch + Redis` 承接状态、快照、检索与短期运行态

这样既能把几个亮点真正落进工程里，也不会为了“看起来高级”而把系统做得过重。
