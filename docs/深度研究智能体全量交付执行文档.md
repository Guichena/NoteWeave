## 2. 一句话总目标

`NoteWeave Deep Research = Research Harness + Closed-Loop Research + Table-as-State + Dual Verifier + 反证分支 + Formal Research Report + Workbench Delivery`

最终交付的不是一个“能回答复杂问题”的普通问答器，而是一个面向复杂开放式研究任务、能研究、能读取、能验证、能纠偏、能成文、能展示、能回流资料池的正式 `Deep Research` 系统。

## 3. 产品边界冻结

### 3.1 独立功能定位

`Deep Research` 是工作台中的独立功能，不是：

- `Ask` 升级模式
- `Note` 升级模式
- `Wiki` 升级模式
- 从聊天、页面、资料上下文里隐式升级出来的研究模式

### 3.2 唯一任务入口

研究任务只来自用户显式输入，和上下文无关。

用户可以显式提供：

- `research_goal`
- `source_scope`
- `constraints`
- `depth / profile`
- 是否启用外部搜索
- 报告偏好

### 3.3 与工作台的关系

工作台只做三件事：

- 承载 `run / detail / history / checkpoint / artifact`
- 展示研究报告、来源、检索过程与审计层
- 接收研究完成后的报告回流，让成果重新进入资料池

工作台不负责：

- 基于现有聊天上下文自动发起研究
- 把页面内容自动拼成研究输入
- 把 `Deep Research` 退化成普通问答

### 3.4 展示面冻结

主界面只强调三类内容：

- 最终结论
- 正式报告
- 来源列表

详情弹窗固定两层：

1. `process`：搜索、抓取、读取、证据命中、来源链路
2. `audit`：`Dual Verifier`、`反证分支`、`checkpoint / resume`

明确不做：

- 过程回放播放器
- 主界面堆大量 verifier 原始字段
- 难展示、难讲解、对简历亮点帮助不大的重型多 agent 平台复杂度

## 5. 这次交付真正要打出来的亮点

这次 `Deep Research` 最值得讲的，不是“会搜网页”，而是把复杂开放式研究任务中的三个核心问题压住：

1. 状态易漂移
2. 路径易跑偏
3. 结果难验证

对应的系统答案必须稳定落在五个关键词上：

- `Research Harness`
- `Closed-Loop Research`
- `Table-as-State`
- `Dual Verifier`
- `反证分支`

也就是说，最终对外讲解时，系统必须能证明：

- 研究不是一次性长文本生成，而是受控闭环
- 状态不是靠 prompt 和记忆硬撑，而是 `Table-as-State`
- 研究路径不是一路瞎跑，而是 verifier 驱动收敛
- 有冲突时不是简单平均，而是走 `反证分支`
- 最终报告不是“模型说了算”，而是来源驱动、验证驱动

## 6. 参考项目吸收策略

重点参考：

- `reference/Marco-DeepResearch/Marco-DeepResearch-Family/Table-as-Search`
- `reference/Marco-DeepResearch/Marco-DeepResearch-Family/DeepWideSearch`
- `reference/MiroFlow`

总原则只有一句话：吸收长处，不复制复杂度。

| 参考项目 | 已吸收的重点 | 还保留为条件增强的重点 | 明确不照搬什么 |
| --- | --- | --- | --- |
| `Table-as-Search` | `Table-as-State`、row/cell/evidence、状态推进从 prompt 迁到表结构 | 如果最终验收暴露状态分层不够清晰，再补更细粒度状态映射 | 不做重型多 agent 编队 |
| `DeepWideSearch` | `wide -> deep` 路径、真实样例 gate、覆盖意识、查询族思路 | 如果真实样例暴露搜索覆盖不足，再补 query family budgets | 不把项目重心改成 benchmark 工程 |
| `MiroFlow` | `search / fetch / read` 编排、fallback、trace、展示层可讲性 | 如果最终验收暴露抓取/读取偏轻，再补 transport / retry / content-type 级增强 | 不做通用 agent 平台和过厚工具宇宙 |

当前阶段的结论是：

- 长处已经吸收进主链与工件
- 剩余部分只作为条件增强，不再默认继续加复杂度

这三包已经从“默认主线”降级为“条件触发项”，只有最终验收或真实 demo 暴露问题才执行。

#### `H1` 工具栈硬化

触发条件：

- 外部搜索覆盖浅
- `fetch` 对正文抓取不稳定
- `read` 证据锚定不够强
- fallback 虽存在但解释力不够

补强重点：

- `search family / query effectiveness`
- `fetch content type / failure code / transport fallback`
- `read window / evidence linkage / source anchoring`

#### `H2` verifier / 反证分支硬化

触发条件：

- verifier 过松或过严
- `反证分支` 有流程但无纠偏价值
- 冲突证据处理在报告层表达不充分

补强重点：

- `Dual Verifier`
- `counterfactual_summary`
- `verifier-gated synthesis`
- unresolved / guardrailed rows 的报告表达

#### `H3` checkpoint / resume 硬化

触发条件：

- checkpoint 与当前 run 关系讲不清
- resume 后净推进不可判断
- 资料回流与恢复链路同源性不够强

补强重点：

- checkpoint summary / diff / lineage
- resume 前后净推进展示
- artifact / writeback / source_scope reuse 同源关系
