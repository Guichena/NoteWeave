# NoteWeave v2 深度研究智能体工程落地设计

## 1. 目的

这份文档只针对 `Deep Research 智能体` 的内部实现展开，不讨论右侧产物生成智能体，也不展开整套 Memory 体系。

它重点回答六个问题：

1. `Research Agent` 内部到底有哪些功能模块
2. 这些模块之间如何协作
3. 长任务如何运行、恢复、暂停与终止
4. 这条链路需要哪些中间件
5. 这些中间件在 `Research Agent` 里分别承担什么职责
6. MySQL 需要哪些核心表与关系

## 2. 设计定位

`Research Agent` 的实现口径应明确为：

- 一个总 `Research Agent`
- 一套 `Research Harness`
- 若干内部功能模块

在工程上，它更适合作为：

- `Java` 主系统调度的独立 `Python Research Worker`

不是多个自治子 Agent 在内部长期对话。

这条链路的核心目标是：

- 把开放式研究问题变成可执行长任务
- 把研究过程沉淀为可计算状态
- 把证据、字段、冲突、分支与结论绑定起来
- 把研究结果做成可验证、可恢复、可审计的产物

一句话概括就是：

`用 Verification-Centric Research Harness 驱动单主 Research Agent，在 Table-as-State 上组织 Search、Read、Extract、Verify、Repair 的闭环研究流程。`

在当前产品口径下，Deep Research 不是第四种模式，而是跨 `问答 / Note / Wiki` 的独立系统能力。

Research 链路的产出需要明确分两层：

- `研究过程资产`
  搜索结果、网页快照、抓取文本、证据片段、检查点与运行轨迹，默认只服务当前 `Research Run`，不直接进入主检索链路。

- `确认后资料成果`
  最终研究报告、被引用的关键网页快照、被用户确认纳入的来源等高价值内容，可以进入项目级共享资料池，像用户上传文件一样参与检索、引用和后续产物生成。

## 3. 研究智能体内部结构

## 3.1 总体结构

```text
DeepResearchOrchestrator
  -> Research Planner
  -> Research State Ledger
  -> Research Loop Runtime
      -> Wide Search Executor
      -> Material Reader
      -> Evidence Extractor
      -> Cell Candidate Builder
      -> Local Verifier
      -> Conflict Resolver
  -> Global Verifier
  -> Report Synthesizer
  -> Progress Publisher
```

## 3.2 模块职责

### `DeepResearchOrchestrator`

职责：

- 创建 `Research Run`
- 冻结上下文快照
- 装配预算策略与停止契约
- 启动后台任务
- 控制最终收口

### `Research Planner`

职责：

- 重写研究问题
- 识别研究对象
- 生成研究表结构
- 生成初始搜索计划
- 生成 `Stop Contract`

输入：

- 用户问题
- 当前 `Topic Scope`
- 已选资料
- 当前上下文快照

输出：

- `ResearchIntent`
- `ResearchPlan`
- `ResearchSchema`
- `StopContract`

### `Research State Ledger`

职责：

- 保存 `run / branch / row / cell / evidence / trace / checkpoint`
- 保存预算使用情况
- 保存验证结果与冲突结果
- 作为所有功能模块共享的唯一状态账本

它是这套设计里最关键的底座，`Table-as-State` 就落在这里。

### `Wide Search Executor`

职责：

- 基于 Research Run 的资料快照生成查询束
- 同时保留直接查询、资料定向查询、覆盖缺口检查和反证证据检查
- 对标题、摘要、原文窗口样本文本做轻量字段覆盖评分
- 记录命中字段、覆盖度、搜索角度和检索理由
- 避免过早锁死到某一个来源
- 通过 `SearchAdapter` 把工作台资料检索与外部搜索能力解耦
- 无外部搜索 key 时只使用工作台资料，有外部搜索 key 时叠加外部搜索候选

输出对象：

- `Material Candidate`
- `Search Finding`
- `matched_fields`
- `coverage_score`
- `search_angle`
- `provider`
- `adapter`
- `url`

当前第一阶段工程实现已经落地：

- `WorkspaceSearchAdapter`
- `ExternalSearchAdapter`
- `CompositeSearchAdapter`
- `build_default_search_adapter`
- `run_research_search`

配置入口：

- `NOTEWEAVE_RESEARCH_SEARCH_API_KEY`
- `NOTEWEAVE_RESEARCH_SEARCH_PROVIDER`
- `NOTEWEAVE_RESEARCH_SEARCH_BASE_URL`
- 兼容 `SERPER_API_KEY / SERPER_BASE_URL`
- 兼容 `SEARCH_API_KEY / SEARCH_API_BASE`

设计边界：

- Search 阶段只负责发现候选来源和归一化命中。
- 真实网页正文读取、快照保存和失败降级放在 `Material Reader / ReadAdapter` 阶段。
- 外部搜索命中必须继续经过读取、抽取和验证，不能直接作为报告事实。

### `Material Reader`

职责：

- 读取网页
- 读取 PDF / 文档
- 读取已索引原文窗口
- 对目标字段做定向片段回读

输出对象：

- `Evidence Fragment`

### `Evidence Extractor`

职责：

- 从片段中抽取候选事实
- 抽取可回溯引用
- 识别支持性与冲突性证据

输出对象：

- `MaterialEvidence`
- `Claim Candidate`

### `Cell Candidate Builder`

职责：

- 把候选事实写入 `row / cell`
- 形成字段级候选值
- 记录证据数量、置信度与当前子目标

输出对象：

- `ResearchCell`
- `ResearchCellEvidence`

### `Local Verifier`

职责：

- 检查当前字段值是否被证据支持
- 检查字段值是否与原文一致
- 检查来源质量是否足够
- 检查是否存在冲突证据
- 决定字段继续搜索、继续阅读、局部修复还是临时通过

### `Conflict Resolver`

职责：

- 处理局部失败
- 触发反证分支
- 对高价值冲突做局部重跑
- 决定是继续主线、挂起主线还是切换分支

### `Global Verifier`

职责：

- 检查全局覆盖率
- 检查关键结论是否仍有未解冲突
- 检查预算是否还值得继续消耗
- 检查是否满足停止契约

### `Report Synthesizer`

职责：

- 只基于已验证字段和已绑定证据生成研究报告
- 输出结构化研究结论
- 输出冲突摘要

这里必须遵守 `Verifier-Gated Synthesis`。

### `Progress Publisher`

`Report Synthesizer` 除了生成最终文本，还必须保证：

- 每个 `Research Run` 最终都产出一份研究报告
- 研究报告默认具备项目级归属
- 研究报告提交并确认后，由 `Java` 主系统纳入工作台资料池
- 该资料在检索层与用户上传文件共用同一套召回与引用规则，但保留 `generated_by = research_agent` 的来源标记

职责：

- 发布阶段变化
- 发布预算变化
- 发布当前子目标
- 发布当前分支状态
- 发布最终完成或失败事件

## 6. Loop Engine 详细执行

## 6.1 单次循环输入

- 当前 `ResearchPlan`
- 当前 `ResearchTable`
- 当前 `Branch`
- 当前预算剩余量
- 当前 `VerificationResult`
- 当前 `ConflictResolution`
- 当前 `StopContract`

## 6.2 单次循环输出

- `LoopDecision`

建议决策类型：

- `SEARCH_MORE`
- `READ_MORE`
- `EXTRACT_AGAIN`
- `VERIFY_CELL`
- `OPEN_BRANCH`
- `MERGE_BRANCH`
- `SYNTHESIZE_REPORT`
- `STOP_RUN`

## 6.3 执行顺序

```text
1. Planner 生成初始计划
2. 初始化 run / row / cell
3. Wide Search 拉开候选来源
4. Material Reader 读取工作台窗口或外部 URL 快照
5. Evidence Extractor 生成证据对象
6. Cell Candidate Builder 写入 cell
7. Local Verifier 校验字段
8. Conflict Resolver 做局部修复或开分支
9. Global Verifier 判断是否收敛
10. Report Synthesizer 输出结果
```

## 6.4 何时开分支

只有以下情况才值得开分支：

- 某个关键字段反复验证失败
- 某个高价值结论出现强冲突证据
- 当前主线明显过度依赖单一来源
- 同一个解释路径连续主导多个 loop

这意味着分支不是默认动作，而是高成本纠偏动作。

## 6.5 何时停止

建议由 `Stop Contract` 统一控制：

- 关键字段覆盖率达标
- 高价值字段最小证据数达标
- 剩余冲突低于阈值
- 预算剩余量低于阈值
- 连续多轮新增价值过低

## 7. Research Agent 所需中间件

`Research Agent` 只需要下面这些中间件：

- `MySQL`
- `Kafka`
- `Redis`
- `MinIO`
- `Elasticsearch`
- `SSE`
- `OpenAI SDK / OpenAI-compatible SDK`

这里不需要：

- 独立 `LLM Gateway`
- 微服务网关体系
- 多级任务编排平台

## 8. 中间件在 Research Agent 里的详细职责

## 8.1 MySQL

`Research Agent` 中 MySQL 负责：

- `research_run`
- `research_branch`
- `research_row`
- `research_cell`
- `source_evidence`
- `research_cell_evidence`
- `research_trace`
- `research_execution_checkpoint`
- `task`
- `task_outbox`
- `task_event`

设计原则：

- MySQL 存状态真源
- MySQL 不存大正文
- MySQL 不存长篇研究快照全文
- 复杂快照对象走 MinIO

推荐设置：

- `utf8mb4`
- `datetime(3)`
- `BIGINT AUTO_INCREMENT`
- 高频筛选字段单独索引
- JSON 只用于配置、快照摘要和运行态

## 8.2 Kafka

`Research Agent` 中 Kafka 只负责异步任务派发。

建议 Topic：

- `noteweave.research.run`
- `task.retry`

建议 Consumer Group：

- `noteweave-research-worker`

建议做法：

- 一个 `Research Run` 对应一个任务消息
- Worker 内部运行完整 loop
- 不把 `search / read / verify` 再拆成多级 Kafka 子任务

推荐消息载荷：

```json
{
  "task_id": "task-r-1",
  "target_type": "RESEARCH_RUN",
  "target_id": "run-1",
  "workspace_id": "workspace-1"
}
```

## 8.3 Redis

`Research Agent` 中 Redis 只存短期运行态：

- 进度快照
- 当前阶段
- 当前子目标
- 当前预算消耗
- SSE resume token

推荐 Key：

```text
nw:research:run:{runId}:progress
nw:research:run:{runId}:stage
nw:research:run:{runId}:budget
nw:sse:resume:{channelId}
```

推荐 TTL：

- 运行进度：`24h`
- resume token：`2h`

明确不做：

- 不把研究账本只放 Redis
- 不把 `row / cell / evidence` 真源放 Redis

## 8.4 MinIO

这里要明确一条资产分层规则：

- MinIO 中保存的网页快照、checkpoint 与过程证据属于 `研究过程资产`
- MinIO 中保存的最终研究报告属于 `确认后资料成果`
- 最终研究报告落盘后，需要继续由 `Java` 主系统完成资料映射、索引写入与资料池纳入

`Research Agent` 中 MinIO 负责保存：

- 大段网页快照
- PDF 解析文本
- checkpoint 完整快照
- 最终研究报告文件

建议 Bucket：

- `nw-research-snapshot`
- `nw-source-parsed`
- `nw-citation-snapshot`

建议对象 Key：

```text
research/{workspaceId}/{runId}/checkpoint/{checkpointNo}.json
research/{workspaceId}/{runId}/report/final.md
parsed/{workspaceId}/{sourceId}/parsed.txt
citation/{workspaceId}/{citationId}/snapshot.json
```

## 8.5 Elasticsearch

对 Research 链路，Elasticsearch 需要明确分两层：

- `过程资产查询`
  仅用于当前 `Research Run` 内部复核、回看与证据追踪。

- `正式资料查询`
  包括用户上传文件、研究报告和已被纳入的关键来源，可由 `问答 / Note / Wiki / Artifact` 共享召回。

`Research Agent` 中 Elasticsearch 负责：

- 候选来源检索
- Material Window 检索
- 关键词 + 向量混合检索
- metadata filter

建议索引：

- `nw-source-chunk`
- `nw-note`
- `nw-wiki`

Research 初期主要依赖：

- `nw-source-chunk`
- 必要时回查 `note / wiki`

## 8.6 SSE

`Research Agent` 的长任务反馈优先用 `SSE`。

建议事件类型：

- `research-created`
- `research-stage-changed`
- `research-progress`
- `research-branch-opened`
- `research-conflict-detected`
- `research-completed`
- `research-failed`

建议推送字段：

- `runId`
- `taskId`
- `stage`
- `message`
- `progressPercent`
- `activeRowCount`
- `verifiedCellCount`
- `branchCount`
- `budgetUsed`
- `budgetLimit`

## 8.7 模型接入层

`Research Agent` 的模型调用建议在 `Python Research Worker` 内直接使用 `OpenAI Python SDK` 或兼容接口做轻量封装：

- `ResearchModelClient`
- `SearchQueryRewriter`
- `StructuredExtractor`
- `VerifierPromptRunner`

建议配置：

```yaml
noteweave:
  research:
    model:
      planner: gpt-5
      extractor: gpt-5
      verifier: gpt-5
      timeout-ms: 60000
      max-retries: 2
      temperature:
        planner: 0.2
        extractor: 0.2
        verifier: 0.1
        synthesizer: 0.3
```

## 9. API 与任务链路

## 9.1 创建任务

当前入口：

`POST /api/v2/workspaces/{workspaceId}/research-runs`

请求体至少包含：

- `question`
- `profile`

同步阶段完成：

- 创建 `research_run`
- 初始化 `task`
- 写入 `task_outbox`
- 返回 `research_run_id`、`task_id`

## 9.2 查询详情

当前接口：

- `GET /api/v2/workspaces/{workspaceId}/research-runs/{researchRunId}`

## 9.3 任务主链路

```text
POST /workspaces/{workspaceId}/research-runs
  -> Java create research_run
  -> Java create task(RESEARCH_RUN)
  -> Java insert task_outbox
  -> Kafka publisher sends noteweave.research.run
  -> Python Research Worker consumes Kafka message
  -> planner builds plan and schema
  -> initialize row / cell patch
  -> loop search -> read -> extract -> verify -> repair
  -> emit checkpoint / progress / trace events
  -> Java persist state and publish SSE
  -> global verify
  -> synthesize final report
  -> Java update run completed
```

## 12. 代码结构建议

建议包结构：

```text
research
  ├─ application
  │   ├─ DeepResearchOrchestrator
  │   ├─ ResearchQueryService
  │   └─ ResearchProgressService
  ├─ domain
  │   ├─ model
  │   ├─ service
  │   └─ policy
  ├─ runtime
  │   ├─ planner
  │   ├─ search
  │   ├─ read
  │   ├─ extract
  │   ├─ verify
  │   ├─ repair
  │   └─ synthesize
  ├─ infrastructure
  │   ├─ persistence
  │   ├─ kafka
  │   ├─ redis
  │   ├─ storage
  │   ├─ searchindex
  │   └─ llm
  └─ web
```

职责划分：

- `application`
  启动任务、组装上下文、对外暴露服务

- `domain`
  保存领域规则、状态流转、停止契约、验证规则

- `runtime`
  承载真正的研究循环与各功能模块

- `infrastructure`
  对接 MySQL、Kafka、Redis、MinIO、ES、模型接口

## 13. 第一阶段最小可用实现

第一阶段最小可用版本先落稳定任务链路，不直接铺开重型研究表：

1. `research_run`
2. `research_trace`
3. `task + task_outbox`
4. `Research Worker Input Contract`
5. `Planner`
6. `Query Bundle`
7. `SearchAdapter`
8. `ResearchHarness Trace`
9. `Table-as-State Ledger`
10. `Local Verifier`
11. `Global Verifier`
12. `Report Writer`
13. `progress / complete / fail` 回调
14. `SSE` 长任务进度读取

`research_row`、`research_cell`、`research_branch`、`source_evidence`、`research_cell_evidence` 和 checkpoint 表作为增强阶段再落地。当前先把这些对象放在 Python Worker 的 `state_ledger`、`local_verifier`、`global_verifier` 和 `trace_summary` 中返回，由 `research_run` 与 `research_trace` 承接结果和审计信息。

## 14. 设计结论

当前最合理的 `Research Agent` 落地方式不是做成复杂多智能体网络，而是：

- 一个总 `Research Agent`
- 一个强状态账本
- 一个受控循环执行器
- 一个局部验证加全局验证的双层验证体系
- 一套由 `Java` 主系统调度、由 `Python Research Worker` 执行的 `task + outbox + worker` 长任务链路

这套做法既能保住你前面设计里的亮点，也能直接支撑后续真正落代码。
