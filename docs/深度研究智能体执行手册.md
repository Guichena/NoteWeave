# 深度研究智能体执行手册

> **最终边界说明（2026-07-12）**：本手册中的 Table-as-State 精确绑定、独立 Global Verifier、有界顺序反证 executor、运行中 checkpoint/resume 和 verifier-gated synthesis 已闭合。当前不是并行多 Agent runtime；执行与验收以 `ResearchAgent-Capability-Coverage.md` 为准。

## 1. 目的

这份手册不是新的架构蓝图，而是 `NoteWeave v2` 当前 `Deep Research / Research Agent` 的统一执行口径。

它回答三类问题：

1. 研究任务在系统里到底按什么顺序执行。
2. `search / read / extract / verify / branch / report` 各层分别做什么。
3. 当前实现应如何吸收 `Table-as-Search`、`DeepWideSearch`、`MiroFlow` 的长处，而不把系统做成失控的重型多 Agent 网络。

---

## 2. 基本定位

`Deep Research` 是工作台内独立的重型研究入口，不是问答、Note、Wiki 的派生模式。

研究任务只能由用户显式输入创建，允许用户显式附带：

- `question`
- `research_goal`
- `deliverable_format`
- `constraints`
- `time_range`
- `depth`
- `source_scope`

系统最终要产出两层内容：

- `研究过程资产`
  搜索命中、网页快照、读取窗口、证据片段、checkpoint、trace。
- `正式研究成果`
  `report_structure` 和 `final_report_markdown`，以及后续确认写回资料池的研究报告。

## 3. 参考项目吸收原则

### 3.1 Table-as-Search

吸收重点：

- 把长视野搜索形式化为“表格补全”
- 显式状态跟踪，而不是靠 prompt 临时记忆
- 宽搜索和深搜索职责分离
- 搜索、访问、状态更新都应可恢复、可追踪

落到 NoteWeave 的对应原则：

- `ResearchStateLedger` 是唯一研究状态账本
- 搜索阶段要输出结构化 hit，而不是只返回文本
- 外部网页读取必须进入状态表和验证链路

### 3.2 DeepWideSearch

吸收重点：

- 真实研究任务经常同时要求“广度”和“深度”
- 产物更接近表格化调研结果，而不是单点答案
- 宽搜和深挖失衡会直接导致覆盖缺口
- 工具调用成本和失败重试要计入执行策略

落到 NoteWeave 的对应原则：

- search 不只回答单个事实，而要覆盖候选来源与候选对象
- read 不只打开第一页，而要服务字段补全与冲突复核
- stop contract、budget、retry 不能缺席

### 3.3 MiroFlow

吸收重点：

- 工具层要模块化
- search/read/reasoning/browser 应显式分层
- retry、fallback、并发稳健性是研究框架的一部分
- 研究框架要支持可复现 trace

落到 NoteWeave 的对应原则：

- `search_adapters.py` 和 `read_adapters.py` 应持续向内部 tool layer 演进
- transport、adapter、runtime 要清晰分层
- 外部工具失败时必须能降级，而不是直接中断研究

## 5. 标准执行顺序

### 5.1 创建 Research Run

入口职责：

- 接收用户显式输入
- 冻结 `ResearchIntent`
- 装配 `Control Pack`
- 创建 run 与 task

关键原则：

- 不从问答上下文隐式继承任务
- 不把 Memory 当证据
- 不把工作台状态自动视作研究目标

### 5.2 Planner

目标：

- 重写问题
- 生成 `query_set`
- 生成 `stop_contract`
- 生成 `required_finding_contract`

当前执行要求：

- query 至少覆盖 `direct`
- 若有 `source_scope`，增加 `source_scoped`
- 必须允许 `coverage_gap`
- 必须预留 `counterfactual evidence check`

### 5.3 Search Layer

目标：

- 发现候选来源
- 形成结构化 `ResearchSearchHit`
- 为后续读取提供 URL、provider、matched_fields、coverage_score

当前实现口径：

- `WorkspaceSearchAdapter`
- `ExternalSearchAdapter`
- `CompositeSearchAdapter`

当前强化方向：

- 多 provider 链式配置
- provider 级 retry/backoff
- 分页扩展
- hit 去重合并

执行要求：

- 外部搜索命中不能直接写报告
- search 输出必须进入 read/extract/verifier
- counterfactual hit 要能被 recovery 优先调度

### 5.4 Read Layer

目标：

- 把命中来源变成 `ResearchReadWindow`
- 为证据抽取提供可消费正文

当前实现口径：

- `WorkspaceReadAdapter`
- `UrlReadAdapter`
- `CompositeReadAdapter`
- `JinaUrlSnapshotTransport`
- `HttpUrlSnapshotTransport`
- `CompositeUrlSnapshotTransport`

执行要求：

- 工作台资料优先走已解析窗口
- 外部网页优先走正文抓取，再回退到 snippet
- 读取结果要记录：
  - `snapshot_status`
  - `snapshot_key`
  - `retention_reason`
  - `read_focus`

重要约束：

- 二进制内容不直接当正文
- URL reader 失败不等于 run 失败
- fallback 也必须保留可解释来源线索

### 5.5 Evidence Extractor

目标：

- 从 `ResearchReadWindow` 抽取 `ResearchEvidenceCard`
- 绑定 `window_id`
- 标记支持/冲突关系

执行要求：

- 不能从未读取窗口凭空生成证据
- evidence 必须可回溯到 source 和 window
- 空抽取应触发 recovery，而不是静默跳过

### 5.6 Table-as-State 更新

目标：

- 把命中、证据、字段补全、验证结果沉淀到 ledger

状态对象至少包括：

- `ResearchStateRow`
- `ResearchStateCell`
- `ResearchStateBranch`
- `ResearchVerifierDecision`
- `ResearchStateLedger`

执行要求：

- ledger 是唯一共享状态
- verifier、branch、report 都只读 ledger，不绕过 ledger 自己造状态

### 5.7 Local Verifier

目标：

- 判断当前 search/read/extract 是否足够形成下一步研究推进
- 生成 `intent_completion_contract`
- 生成 `research_intent_alignment`

应重点检查：

- 有没有 hit
- 有没有 read window
- 有没有 evidence card
- 有没有必需字段缺口
- 有没有显式冲突或缺少反证

### 5.8 Recovery / Counterfactual Branch

目标：

- 在主路径不足时决定是：
  - `READ_MORE`
  - `COUNTERFACTUAL_RECHECK`
  - `WRITE_WITH_GUARDRAILS`
  - `SYNTHESIZE_REPORT`

触发原则：

- 冲突明显时优先 `COUNTERFACTUAL_RECHECK`
- 覆盖不足时优先 `READ_MORE`
- 达到轮次上限但不能完全放行时允许 `WRITE_WITH_GUARDRAILS`

预算约束：

- 分支必须有限
- 每轮 read/search 都受 budget 控制
- 不能无限反证、无限重读

### 5.9 Global Verifier

目标：

- 决定是否允许报告合成

标准出口：

- `READY_TO_WRITE`
- `WRITE_WITH_GUARDRAILS`

关键原则：

- 最终报告不能从自由生成直接产出
- 必须从 verifier 通过或 guarded 的状态合成

### 5.10 Report Synthesizer

最终双产物契约：

- `report_structure`
- `final_report_markdown`

推荐语义：

- `report_structure` 给前端直接展示
- `final_report_markdown` 给写回资料池和导出使用

当前结果层应优先强调：

- 调研成果
- 来源基础
- 来源支撑结论
- agent 能力亮点

过程轨迹、检索回放和审计材料继续放在详情层。

### 5.11 Writeback

研究报告在明确保存后可回流资料池。

执行要求：

- `generated_by = research_agent`
- `generated_ref_id = research_run_id`
- 报告可再次进入后续 research 的 `source_scope`

## 6. 当前内部 tool 层口径

当前代码已经开始把 adapter/transport 之上的能力正式收束为 [research_tools.py](/D:/java-projects/NoteWeave-v2/workers/research-worker/app/research_tools.py)；虽然底层仍由 adapter/transport 承担实际 I/O，但执行手册统一把对外语义理解为内部 research tools：

- `search_web`
  - workspace search
  - external provider chain
- `visit_webpage`
  - jina reader
  - http fetch fallback
- `read_workspace_source`
  - 已解析资料窗口
- `extract_evidence`
  - 从 read window 到 evidence card
- `verify_local`
- `verify_global`
- `open_counterfactual_branch`
- `synthesize_report`

本轮新增约束：

- `loop_runtime.py` 应优先通过 `ResearchToolbox` 驱动单轮闭环，而不是直接散调底层函数。
- 每轮都应沉淀 `tool_traces`，至少覆盖工具名、状态、输入摘要、输出摘要和 recovery mode。
- `tool_traces` 进入 worker result/checkpoint，作为后续过程展示与审计的真源之一。

这层语义现在已经不只是文档口径，而是 agent 内核里的正式工程对象。

## 7. 三类典型执行模式

### 7.1 单点事实型研究

适用：

- 明确问题
- 来源数量有限
- 更重视结论准确性

策略：

- `direct query` 为主
- 少量 `counterfactual query`
- read 预算较小
- verifier 更快收口

### 7.2 深宽结合型研究

适用：

- 市场调研
- 厂商搜集
- 竞品情报
- 候选对象 + 多属性补全

策略：

- `source_scoped + coverage_gap + direct` 并行
- 先拉宽候选对象，再深挖字段
- Table-as-State 必须作为主骨架

这是最接近 `Table-as-Search + DeepWideSearch` 的任务形态。

### 7.3 冲突纠偏型研究

适用：

- 来源互相矛盾
- 路径可能跑偏
- 重要结论需要反证

策略：

- Local verifier 明确标注 conflict
- 优先触发 `COUNTERFACTUAL_RECHECK`
- 对 targeted source / targeted query 做受控重查

## 9. 执行红线

以下规则不能被破坏：

- 不把外部搜索 snippet 直接当最终事实
- 不绕过 ledger 直接写报告
- 不让 verifier 变成纯展示字段
- 不让反证分支无限展开
- 不把 Deep Research 做成自由放养式群聊多 Agent 系统

---

## 10. 一句话执行定义

`NoteWeave 的 Deep Research 应按“单主 Agent + Verification-Centric Research Harness”执行：以 Table-as-State 管理研究状态，以 Search/Read/Extract/Verify/Repair 受控闭环推进任务，以 Dual Verifier 和反证分支抑制路径漂移，并最终产出 report_structure 与 final_report_markdown 两类正式研究成果。`
