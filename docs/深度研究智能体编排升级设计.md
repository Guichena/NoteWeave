# 深度研究智能体编排升级设计

## 1. 文档定位

这份文档是 NoteWeave v2 针对 `Deep Research 智能体` 的专项设计文档。

它重点回答五个问题：

1. 这个智能体的最终定位到底是什么
2. 它应该具备哪些核心功能
3. 它在系统里应该采用怎样的详细架构
4. 它的研究循环、状态、验证与停止机制如何协同
5. 怎样在保留新颖性的同时避免工程设计做重

这份文档不展开：

- MySQL DDL 细节
- Kafka topic 细节
- Controller / Service / Repository 代码组织
- 前端页面交互稿

这些内容分别放在具体落地文档中处理。

## 2. 设计目标与边界

### 2.1 设计目标

我们希望 Deep Research 智能体具备以下能力：

- 能把开放式问题组织成结构化研究任务
- 能在多轮 Search / Read / Extract / Verify 中稳定推进
- 能在证据不足、证据冲突、来源不稳时做出可解释决策
- 能避免过早锁死到单一路径或单一来源
- 能沉淀研究状态、研究轨迹和最终研究产物
- 能以长任务方式运行，但仍保持可恢复、可审计、可停止

### 2.2 明确不做的事

这版设计明确不走以下路线：

- 不做自由放养式多 Agent 群聊系统
- 不做通用 Agent 平台化编排中心
- 不做所有节点都多模型共识的高成本结构
- 不把所有工具、所有 MCP、所有策略一次性塞给模型
- 不把研究任务做成无限循环直到模型“感觉差不多”

我们的方向是：

`单主研究智能体 + 内部功能拆分 + 强状态账本 + 强验证机制 + 受控分支恢复`

## 3. 总体定位

NoteWeave 的 Deep Research 智能体，最终更适合被定义为：

`Verification-Centric Research Harness`

如果要再压缩成一句更完整的架构描述，可以写成：

`TAS-Informed Verification-Centric Research Harness`

它的核心不是“会自己一直搜索的聊天 Agent”，而是：

- 以结构化研究状态承载任务进展
- 以验证驱动研究循环推进
- 以反证分支抑制过早承诺
- 以停止契约控制长任务收敛

如果要展开成一条更完整的内部架构口径，则是：

`Table-as-State + Interaction-Scaled Research Loop + Dual Verifier + Counterfactual Branching + Verifier-Gated Synthesis`

如果按“问题 - 方法 - 效果”的方式概括，这个智能体可以进一步描述为：

面向复杂开放式研究任务中状态易漂移、路径易跑偏、结果难验证的问题，提出验证驱动的 `Research Harness`，将研究、读取、验证与修正组织为受控的 `Closed-Loop Research`；系统以 `Table-as-State` 管理研究状态，以 `Dual Verifier` 控制验证闭环，并通过反证分支进行路径纠偏。

## 4. 功能设计

这一节回答“这个智能体到底要做什么”。

### 4.1 任务进入与研究启动

智能体应支持从以下上下文发起研究任务：

- 用户直接输入开放式研究问题
- 在问答上下文中把复杂问题升级为 Deep Research
- 在 Note 或 Wiki 上下文中对一个主题发起深度研究
- 基于一组已选 资料 发起定向研究

启动阶段需要完成：

- 任务重写与澄清
- 研究目标归一化
- 研究对象识别
- 研究深度与预算档位确认
- 是否允许外部检索确认

输出对象：

- `ResearchIntent`
- `ResearchPlan`
- `ResearchSchema`
- `StopContract`

### 4.2 研究计划构建

智能体应先形成一份相对完整的研究计划，而不是直接无计划循环。

计划至少应包含：

- 研究目标
- 研究对象或候选对象集合
- 关键字段与字段优先级
- 搜索策略
- 阅读策略
- 证据要求
- 停止契约
- 预算约束

计划输出后，系统创建研究表与运行时状态账本。

### 4.3 候选发现与宽搜索

对于开放问题，智能体应先进行 `Wide Search`，而不是马上围绕单一路径深挖。

这一阶段的目标：

- 扩展候选对象集合
- 建立来源多样性
- 获取初始高质量来源池
- 发现潜在冲突路径

这一阶段不追求立刻写出最终结论，而追求把后续研究空间铺开。

### 4.4 目标导向阅读

Deep Research 不是泛读，而是围绕当前字段、当前子目标、当前冲突点做定向阅读。

阅读阶段应支持：

- 网页阅读
- PDF / 文档阅读
- 结构化元数据读取
- 局部段落回读
- 同一来源多段证据绑定

阅读的输出不直接等于结论，而是转换为：

- `Evidence Candidate`
- `Claim Candidate`
- `Cell Candidate`

### 4.5 字段补全与证据绑定

研究任务需要被压成结构化字段补全过程。

每个 row / cell 的核心动作包括：

- 生成候选值
- 绑定支持证据
- 绑定来源等级
- 生成置信度初值
- 判断是否需要补充证据

这一步的目标不是“写得好看”，而是“让研究状态可计算、可验证、可分支”。

### 4.6 局部验证与冲突检测

每个关键字段在进入稳定状态前，都必须经过局部验证。

局部验证至少回答：

- 当前字段值是否被证据支持
- 当前字段值是否与原文一致
- 当前来源质量是否足够
- 当前字段是否存在冲突证据
- 当前字段是否需要继续搜索或阅读

如果局部验证失败，不应直接结束整次研究，而应进入局部修复或局部分支。

### 4.7 反证分支与局部修复

当系统发现以下情况时，应触发 `Counterfactual Branching` 或 `Conflict-Scoped Recovery`：

- 某条解释路径连续主导多个 loop
- 某个来源被过度依赖
- 关键字段出现高价值冲突
- 同一字段多次修复仍无法收敛

此时系统可以：

- 开启反向搜索分支
- 为冲突字段创建替代解释分支
- 重跑某个 row / cell 的局部研究路径
- 把原主路径保留为 mainline，不直接覆盖

### 4.8 全局收敛判断

研究任务不能依赖主观“差不多完成了”的判断。

系统应通过全局验证判断：

- 关键字段覆盖率是否达标
- 关键结论是否仍有未解冲突
- 高价值对象是否达到最小证据要求
- 当前研究是否还值得继续消耗预算
- 当前是否只能部分完成而不适合继续深挖

### 4.9 研究产物生成

Deep Research 智能体的默认输出应控制在研究产物范围内，而不是泛化为所有内容生成器。

推荐输出包括：

- `Research Report`
- `Structured Finding Table`
- `Evidence Digest`
- `Conflict Summary`

其中最终报告应采用：

`Verifier-Gated Synthesis`

也就是报告只能从已验证字段、已验证证据和已记录冲突中合成，而不是重新自由发挥。

### 4.10 进度反馈与可恢复运行

作为长任务系统，Deep Research 还应具备：

- 进度展示
- 当前阶段展示
- 当前分支展示
- 当前预算消耗展示
- 暂停 / 继续能力
- checkpoint 恢复能力
- 失败后局部恢复能力

这部分不是附属能力，而是研究型长任务体验成立的基础。

## 5. 详细架构设计

这一节回答“这个智能体在系统里应该怎么搭”。

### 5.1 架构总图

```text
DeepResearchOrchestrator
  -> Research Planner
  -> Research State Ledger
  -> Research Loop Runtime
      -> Search Adapter
      -> Read Adapter
      -> Extractor
      -> Local Verifier
      -> Branch / Repair Controller
  -> Global Verifier
  -> Research Synthesizer
  -> Artifact / Note / Wiki Writeback Adapter
```

### 5.2 模块分层

推荐拆成六层：

1. `入口编排层`
   承接用户发起、装配上下文、创建 Research Run。

2. `计划层`
   负责生成研究目标、研究表结构、研究计划和停止契约。

3. `循环运行时层`
   负责推进 Search、Read、Extract、Verify、Revise 的受控循环。

4. `验证控制层`
   负责局部验证、全局验证、冲突检测、分支决策和停止决策。

5. `状态账本层`
   负责保存研究表、研究轨迹、分支、checkpoint、budget 和 verifier 决策。

6. `结果合成层`
   负责把已验证状态转成研究报告和结构化结论。

### 5.3 核心模块职责

#### 5.3.1 DeepResearchOrchestrator

职责：

- 创建 `ResearchRun`
- 收集当前上下文
- 调用 Planner 初始化研究状态
- 推动 Loop Runtime 运行
- 决定何时进入结果合成阶段

它是总控，但不直接承载所有智能逻辑。

#### 5.3.2 Research Planner

职责：

- 任务重写与澄清
- 研究目标规范化
- 研究对象识别
- 生成 `ResearchSchema`
- 生成 `ResearchPlan`
- 生成 `StopContract`

Planner 的输出决定了后续研究空间与预算分配。

#### 5.3.3 Research Loop Runtime

职责：

- 决定下一步动作
- 调用搜索、阅读、抽取、验证能力
- 把每一步结果写回状态账本
- 触发局部修复或反证分支

它不是一个自由 Agent，而是一个受控循环执行器。

#### 5.3.4 Search / Read Adapters

职责：

- 对接搜索能力
- 对接网页读取与文档读取能力
- 做内容归一化
- 输出统一的 `Evidence Candidate`

当前工具脊柱建议保持轻量且完整：

- 搜索
- 网页 / 文档读取
- 结构化抽取
- 可选代码执行

#### 5.3.5 Local Verifier

职责：

- 字段级验证
- 证据级验证
- 引用级验证
- 来源质量判断
- 冲突检测

它解决的是“这个局部结论靠不靠谱”。

#### 5.3.6 Branch / Repair Controller

职责：

- 判断当前问题是局部可修复还是需要开分支
- 控制分支数量与分支预算
- 决定主路径 / 支路径关系

它是 `Counterfactual Branching` 和 `Conflict-Scoped Recovery` 的控制枢纽。

#### 5.3.7 Global Verifier

职责：

- 判断研究是否收敛
- 判断是否满足停止契约
- 判断是否应转入部分完成
- 判断最终报告是否可生成

它解决的是“整个研究 run 是否值得继续”。

#### 5.3.8 Research Synthesizer

职责：

- 根据已验证状态合成研究报告
- 根据冲突记录生成冲突摘要
- 根据结构化结果生成研究表输出

它应遵守 `Verifier-Gated Synthesis`：

- 不允许绕过 verifier 自由写结论
- 不允许高价值结论脱离 Research Table 独立生成

### 5.4 详细协作链路

```text
用户发起 Deep Research
  -> Orchestrator 收集上下文
  -> Planner 生成 ResearchPlan / ResearchSchema / StopContract
  -> State Ledger 初始化 ResearchRun / Table / Budget / Branch
  -> Loop Runtime 执行 Wide Search
  -> 写入候选对象与来源池
  -> Loop Runtime 执行 Goal-Conditioned Reading
  -> 写入 Evidence Candidate / Claim Candidate / Cell Candidate
  -> Local Verifier 判定字段状态
  -> Branch / Repair Controller 决定 Local Repair 或 Counterfactual Branch
  -> Global Verifier 判断研究是否继续
  -> 满足条件后进入 Research Synthesizer
  -> 输出 Report / Table / Evidence Digest
  -> 写回 Artifact 或进一步回流系统
```

## 6. 运行时状态与对象模型

这一节回答“运行时到底保存什么状态”。

### 6.1 Research Run 状态机

推荐状态：

- `CREATED`
- `PLANNING`
- `TABLE_READY`
- `DISCOVERING`
- `READING`
- `EXTRACTING`
- `VERIFYING`
- `REPAIRING`
- `BRANCHING`
- `SYNTHESIZING`
- `COMPLETED`
- `PARTIAL_COMPLETED`
- `FAILED`
- `CANCELLED`

### 6.2 Cell 状态机

关键字段建议采用更细的状态：

- `EMPTY`
- `DISCOVERED`
- `CANDIDATE_READY`
- `EVIDENCE_BOUND`
- `VERIFIED`
- `CONFLICTED`
- `NEEDS_REPAIR`
- `FROZEN`

其中：

- `VERIFIED` 表示当前字段可以进入稳定结果层
- `CONFLICTED` 表示存在高价值冲突，需要分支或复核
- `FROZEN` 表示当前字段在本轮预算下不再继续消耗资源

### 6.3 Branch 状态机

建议支持：

- `MAINLINE`
- `ACTIVE_BRANCH`
- `RESOLVED_BRANCH`
- `REJECTED_BRANCH`
- `MERGED_BRANCH`

### 6.4 预算模型

预算不应只有 token，还应包括：

- 搜索预算
- 阅读预算
- 分支预算
- 重试预算
- 总循环轮数预算

这样系统才能在工程上真正控制研究复杂度。

### 6.5 状态账本内容

`Research State Ledger` 至少保存：

- `ResearchRun`
- `ResearchPlan`
- `ResearchTable`
- `ResearchRow`
- `ResearchCellState`
- `EvidenceRef`
- `ResearchBranch`
- `ResearchCheckpoint`
- `VerifierDecision`
- `LoopDecision`
- `BudgetSnapshot`

### 6.6 Adaptive Evidence Horizon

`Adaptive Evidence Horizon` 是对上下文装配的约束策略。

每轮不应把全部历史上下文都拼给模型，而应只保留：

- 当前子目标
- 当前 row / cell 候选
- 最近有效来源
- 当前关键冲突
- 最近一轮 verifier 反馈
- 必要的上轮分支摘要

这使得系统既能保持上下文相关性，又不至于因为历史膨胀而失控。

## 7. 核心机制设计

这一节回答“为什么这套架构能成立”。

### 7.1 Table-as-State

`Table-as-State` 是这套架构的状态基石。

Research Table 不是为了展示最终表格，而是为了：

- 承载任务结构
- 承载研究进展
- 承载证据绑定
- 承载 verifier 反馈
- 承载 branch 与 retry 信息

它让 Research Agent 从“prompt 驱动”转成“状态驱动”。

### 7.2 Full-Horizon Plan + Lazy Replanning

智能体应先建立一版完整研究计划，然后在必要时才重规划。

只有在以下情况触发重规划：

- 关键字段长期无法填充
- 候选对象集合发生明显变化
- 高价值冲突长期无法消解
- 用户切换研究深度或预算档位

这可以降低无谓的全局重想成本。

### 7.3 Interaction-Scaled Research Loop

循环的价值不在于跑得多，而在于每一轮都能让状态前进。

每一轮 loop 至少要带来以下变化之一：

- 新候选对象被发现
- 新证据被绑定
- 某个字段从候选走向验证
- 某个冲突被显式识别
- 某个主路径被修正或分支化

没有状态变化的 loop 应被限制。

### 7.4 Dual Verifier

这套系统采用双层验证：

- `Local Verifier`
  负责字段、证据、引用级验证

- `Global Verifier`
  负责进度、收敛、完成度验证

这使得系统既能处理局部正确性，也能处理整体研究效率。

### 7.5 Counterfactual Branching

这套机制的关键不是“多开分支”，而是“只在必要时开反证分支”。

触发条件可以包括：

- 单一路径连续主导多个 loop
- 单一来源高频支撑关键结论
- 关键字段出现高价值冲突
- verifier 判定当前路径偏置信号过强

它的目标是抑制研究任务中最常见的过早承诺问题。

### 7.6 Premature Commitment Guard

这不是一个独立大模块，而更像运行时保护规则集。

核心规则：

1. 候选发现阶段保持来源多样性
2. 关键字段优先要求跨来源证据
3. 单一路径主导过久时触发反向检索
4. 报告写作前检查是否存在高频单一路径引用

### 7.7 Feedback Fidelity Gate

工具返回的信息并不天然可信，系统应至少区分：

- `PRIMARY_SOURCE`
- `SECONDARY_SOURCE`
- `WEAK_SOURCE`

它会影响：

- verifier 门槛
- 字段可写入性
- 报告引用优先级
- 是否需要额外复核

### 7.8 Evidence-Gated Progress

研究推进不由 token 数决定，而由验证状态决定。

每轮 loop 输出建议压成：

- `ADVANCE`
- `REPAIR`
- `BRANCH`
- `PARTIAL`
- `STOP`

这使得研究循环从自由生成转成状态门控。

### 7.9 Stop Contract

`Stop Contract` 应在任务开始时就明确：

- 完成条件
- 部分完成条件
- 放弃条件
- 人工接管条件

例如：

- 关键列覆盖率达到阈值
- 核心结论最少证据数达标
- 关键冲突全部解决或显式挂起
- 分支预算消耗到上限
- 重试次数到上限

### 7.10 Verifier-Gated Synthesis

这是最终结果层最值得强调的新机制之一。

它要求：

- 报告只从已验证字段合成
- 冲突必须在报告中显式呈现，而不能被模型自动抹平
- 未验证字段不能直接进入最终核心结论

这会让 Deep Research 的结果更像研究产物，而不是润色过的自由文本。

## 8. 关键对象设计

这里不展开数据库 DDL，只定义运行时最关键对象。

### 8.1 ResearchPlan

建议至少包含：

- `task_id`
- `research_goal`
- `target_entities`
- `research_schema`
- `search_budget`
- `read_budget`
- `branch_budget`
- `stop_contract`
- `risk_profile`

### 8.2 ResearchCellState

建议至少包含：

- `row_id`
- `column_key`
- `candidate_value`
- `status`
- `confidence`
- `evidence_refs`
- `source_quality`
- `branch_id`
- `last_verifier_result`
- `repair_count`

### 8.3 ResearchBranch

建议至少包含：

- `branch_id`
- `parent_branch_id`
- `branch_reason`
- `hypothesis_summary`
- `target_scope`
- `status`
- `created_from_checkpoint`

### 8.4 ResearchCheckpoint

建议至少包含：

- `run_id`
- `checkpoint_no`
- `table_snapshot_ref`
- `trace_snapshot_ref`
- `active_branch_id`
- `budget_snapshot`
- `created_at`

### 8.5 VerifierDecision

建议至少包含：

- `decision_scope`
- `decision_type`
- `reason_code`
- `evidence_summary`
- `repair_action`
- `requires_manual_review`

### 8.6 LoopDecision

建议至少包含：

- `step_no`
- `decision_type`
- `target_scope`
- `branch_action`
- `budget_to_consume`
- `why_this_step`

## 9. 推荐执行流程

```text
用户发起 Deep Research
  -> Task Clarification
  -> Build ResearchIntent
  -> Build ResearchPlan / ResearchSchema / StopContract
  -> Initialize Research Table as State
  -> Wide Search and Candidate Discovery
  -> Goal-Conditioned Reading
  -> Fill High-Priority Cells
  -> Local Verifier
  -> Conflict-Scoped Recovery or Counterfactual Branch
  -> Progress Update to State Ledger
  -> Global Verifier
  -> Stop Contract Check
  -> Verifier-Gated Synthesis
  -> Write Back to Artifact / Note / Wiki
```

其中最关键的控制节点有六个：

- `ResearchPlan`
- `Local Verifier`
- `Conflict-Scoped Recovery`
- `Counterfactual Branch`
- `Global Verifier`
- `Stop Contract`

## 10. 工程上如何保持不做重

### 10.1 不做真正自治的多 Agent 网络

这套架构可以按规划、执行、验证、纠偏、合成几个职责做内部功能拆分，但实现上更建议：

- 一个主 orchestrator
- 多个受控能力模块
- 少量结构化中间对象

而不是多个 Agent 彼此长期对话。

### 10.2 工具集保持轻量完整

Research Agent 初期最小工具集就够了：

- 搜索
- 网页 / 文档读取
- 结构化抽取
- 可选代码执行

不需要一开始挂满所有 MCP。

### 10.3 共识机制只放高风险节点

只有这些节点值得考虑高成本复核：

- 初始研究计划
- 高价值冲突结论
- 最终研究报告中的核心结论

普通搜索、普通阅读、普通字段抽取没必要上共识。

### 10.4 分支必须受预算约束

`Counterfactual Branching` 很强，但不能无限开。

建议至少限制：

- 每个 run 的最大分支数
- 每个关键字段的最大反证分支数
- 分支触发必须有明确 reason code
- 每个分支的阅读预算上限

### 10.5 报告生成不能反客为主

Deep Research 的重点是研究执行，不是无边界内容生成。

因此：

- 研究报告是默认研究产物
- 报告应从验证状态中合成
- 其他泛化产物生成优先交给 Artifact Runtime

## 11. 与 NoteWeave 其他能力的关系

Deep Research 在产品上是独立重型入口，它的职责边界应明确为：

- 负责开放问题的研究执行
- 负责研究状态、研究轨迹、研究报告
- 负责为后续产物生成提供高质量证据底座

它不是：

- 所有产物生成任务的统一入口
- 通用 Skill Graph 编排平台
- 长期记忆的直接写入器

它与其他能力的关系更适合理解为：

- 对 Ask / Note / Wiki 提供研究升级入口
- 对 Artifact Runtime 提供高质量研究输入
- 对 Memory 机制提供研究偏好、报告修改和用户反馈等 Memory Signal

Deep Research 运行时可以读取 `Research Control Pack`，但只把它用于研究偏好、报告结构、禁用表达和交互策略，不把 Memory 当作研究结论或 verifier 的事实依据。

## 12. 关键架构抓手总结

如果只保留最能代表这套 Research Agent 架构的几个抓手，我建议优先看这四个：

1. `Table-as-State`
   把研究表从展示层升级为研究智能体的状态账本。

2. `Dual Verifier`
   把验证从结果补锅升级为局部验证和全局验证双层机制。

3. `Counterfactual Branching`
   当主路径过强时自动发起反证探索，抑制过早承诺。

4. `Verifier-Gated Synthesis`
   最终研究报告只能从已验证状态合成，而不是自由生成。

如果还要补一个控制层概括词，再补：

- `Evidence-Gated Progress`

## 13. 一句话定位

`NoteWeave 的 Deep Research 智能体不是一个自由放养式多 Agent 群聊系统，而是一个 Verification-Centric Research Harness：系统以 Table-as-State 承载研究执行状态，以 Interaction-Scaled Research Loop 推动 Search、Read、Extract、Verify 的受控研究循环；规划、搜索、读取、验证、纠偏与合成都属于总 Research Agent 的内部功能模块，并通过 Dual Verifier、反证分支、Stop Contract、Evidence-Gated Progress 与 Verifier-Gated Synthesis 保证长任务能够可控收敛并输出可信研究产物。`

## 14. 参考方向

这版设计重点吸收的是以下几类思想，而不是照搬某个框架：

- MiroThinker / MiroFlow 的 `interactive scaling`、`tool-augmented research`、`workflow robustness`
- 长任务 Agent 的 `harness engineering`
- Deep Research 场景下的 `execution-state memory`
- 面向研究型任务的 `verifiable progress`
- 面向偏置抑制的 `premature commitment diagnostics`

核心原则仍然是：

`吸收理念，不照搬重框架。`
