# 深度研究智能体编排升级设计

## 1. 目的

这份文档在 [改造计划/深度研究智能体功能与架构设计.md](D:/java-projects/NoteWeave-v2/改造计划/深度研究智能体功能与架构设计.md) 的基础上，吸收 2026 年关于 long-running agents、workflow optimization、research loop 和 harness engineering 的最新设计思想，给出更适合 NoteWeave 的升级方案。

目标不是把 Deep Research 变成一个“更复杂的多 Agent 群聊系统”，而是把它升级成一个：

- 有显式研究状态
- 有可恢复执行轨迹
- 有证据反馈门控
- 有高风险决策保护
- 有清晰停止条件

的 `Research Harness`。

## 2. 先给结论

NoteWeave 的 Deep Research 智能体，不建议只讲成：

`Table-as-Search + Loop Engineering`

更适合升级为：

`Table-as-State + Loop Engineering + Durable Research Harness`

如果要再进一步压成一句更“新”的说法，我建议用：

`Evidence-Gated Branchable Research Harness`

它的意思是：

- `Table-as-State`
  研究表不是展示层，而是运行时状态层

- `Loop Engineering`
  Search、Read、Extract、Verify、Revise 是受控闭环，不是自由循环

- `Durable Research Harness`
  任务能 checkpoint、恢复、分支、审计

- `Evidence-Gated`
  研究进展不是靠模型“感觉差不多了”，而是靠证据和验证状态推进

- `Branchable`
  当出现低置信或冲突时，不是覆盖旧路径，而是允许分支探索

## 3. 2026 最值得吸收的设计思想

### 3.1 Harness 比模型本身更决定上限

2026 的一个很强结论是：对于长任务 agent，决定效果的经常不是单个模型，而是外层 harness。

这意味着 Deep Research 的关键不只是：

- 用哪个模型
- prompt 怎么写

而是：

- 状态怎么外置
- loop 怎么停
- 验证如何驱动下一步
- 错误路径如何隔离
- 是否支持恢复与分支

对 NoteWeave 的意义是：

Deep Research 不该只被定义成“多 Agent 架构”，而应该被定义成：

`Research Harness + Structured Agent Roles`

### 3.2 Full-Horizon Planning + Lazy Replanning

2026 关于 data-centric agents 的一个重要发现是：

不是所有任务都适合每一步都重新想一次。

对于结构明确、证据导向的研究任务，更合理的默认策略往往是：

- 先生成一个较完整的研究计划
- 执行时按计划推进
- 只有在证据不足、冲突出现、候选集变化明显时才触发重规划

也就是：

`Full-Horizon Plan + Lazy Replanning`

对 NoteWeave 的升级建议：

- `Plan Agent` 先输出 ResearchPlan、ResearchSchema、Search Budget、Stop Contract
- `Loop Engine` 默认尊重已有 plan
- 不是每次 search / read 后都重新规划全局
- 只在以下情况触发重规划：
  - 关键列长期无法填充
  - 候选对象集合发生明显扩张或收缩
  - 高价值冲突无法消解
  - profile / budget 发生切换

这样 Deep Research 会更像“研究执行”，而不是“每一步都从头 brainstorm”。

### 3.3 Premature Commitment Guard

2026 一个很值得吸收的失败模式研究是：

`Premature Commitment`

也就是 agent 过早相信某一条解释路径，然后后续所有搜索、阅读、验证都在替它自我证明。

对 Deep Research 这类任务，这个风险非常真实：

- 太早相信某个项目“最像答案”
- 太早相信某个来源“最权威”
- 太早把一个低证据结论写进表格
- 太早把某种架构解释当成事实

因此建议引入：

`Premature Commitment Guard`

具体可以落成四条规则：

1. 候选发现阶段保留多样性，不让单域名或单类来源垄断
2. 关键 cell 在进入 VERIFIED 前，优先要求跨来源证据
3. 当某个解释路径连续主导多个 loop 时，触发一次反向搜索
4. 报告生成前检查是否存在“高频引用单一路径”的结论

这会让系统更像研究者，而不是更像辩手。

### 3.4 Memory 不是知识记忆，而是执行状态管理

2026 一个非常强的新思想是：

对长任务 agent 来说，memory 的关键用途不只是“记住知识”，而是“维护执行状态”。

对 Deep Research 尤其适用。

因此建议把当前设计里的 `Research Table + Research Trace` 进一步理解成：

`Research Execution State`

推荐显式拆成三层：

- `Active Table State`
  当前 row / cell 状态、证据、置信度

- `Subgoal Summary`
  已完成子任务的折叠总结

- `Trace Branch`
  当探索失败、冲突未解或路径切换时，保留分支轨迹

也就是说，Deep Research 的“记忆”更像：

`execution-state ledger`

而不是普通对话记忆。

### 3.5 Trajectory Branching

2026 在 runtime 设计里，一个很有价值的思路是：

`trajectory branching`

对 Deep Research 来说非常适合。

当前研究系统常见的问题是：

- 新证据推翻旧判断时，只能覆盖旧值
- 无法保留“曾经为什么这么判断”
- 报告写作前难以回顾不同研究路径

如果引入 branchable execution：

- 某个 cell 遇到冲突时可以开新分支
- 某个 row 的研究路径可以从特定 checkpoint 重跑
- FAST 模式下的粗略路径可分叉成 HIGH_CONFIDENCE 的精查路径

这会让 Deep Research 不只是“循环”，而是“可分支的循环式研究”。

### 3.6 Verifiable Reward Closes the Loop

2026 一个很实战的结论来自 AI Co-Scientist 方向：

真正能把研究 loop 跑起来的，不是“更多 agent”，而是**可验证反馈**。

对 NoteWeave 来说，Deep Research 的可验证反馈不一定是单一数值 reward，但可以是：

- cell 是否 VERIFIED
- 是否满足最小 evidence count
- 是否仍有 CONFLICT
- 关键列覆盖率是否达标
- 最终报告是否引用了未经验证的 cell

因此建议把 Deep Research 的 loop 推进条件明确成：

`Evidence-Gated Progress`

也就是：

- 没有证据，不算完成
- 证据冲突，不算完成
- 报告能否写，不由 token 数决定，而由验证状态决定

### 3.7 Consensus Only Where It Pays

2026 一个很成熟的观点是：

多模型共识很贵，不该到处用。

对 Deep Research 来说，最合理的方式不是所有节点都多模型投票，而是只把共识保留给高风险节点：

- ResearchPlan 是否合理
- 高价值结论是否成立
- Keep / Revert 某条研究解释路径
- 最终报告中的关键结论是否能发布

也就是：

`High-Stakes Consensus`

普通节点：

- 搜索 query 生成
- 网页读取
- 初次字段抽取
- trace 摘要

这些没必要上共识。

### 3.8 Feedback Fidelity Gate

2026 另一个重要提醒是：

tool feedback 不是天然可靠的。

对 Deep Research 来说，问题体现在：

- 网页抓取内容不完整
- OCR / PDF 解析错位
- README 过期
- 二手博客把一手结论转述错了

因此建议引入：

`Feedback Fidelity Gate`

至少区分：

- `PRIMARY_SOURCE`
  官网、论文、代码仓库、原始文档

- `SECONDARY_SOURCE`
  博客、媒体稿、解读文

- `WEAK_SOURCE`
  聚合摘要、低质量转载、来源不清内容

这样 verifier 不只是判断“有没有证据”，还判断“证据质量是什么级别”。

## 4. 对现有 Deep Research 设计的升级方式

### 4.1 从 Table-as-Search 升级到 Table-as-State

原设计已经很接近正确方向了，但建议再明确一点：

Research Table 不是“研究结果展示表”，而是：

`Deep Research 的外部执行状态层`

它至少应该承载：

- row / cell 状态
- evidence count
- confidence
- branch id
- retry count
- last verifier result
- active subgoal

这样你面试时可以直接说：

`我不是把表格当 UI，而是把表格当 agent state ledger。`

### 4.2 从循环执行升级到 Stop Contract 驱动

Loop Engineering 很容易被理解成“反复循环直到差不多”。

更好的 2026 表达是：

`Loop + Stop Contract`

建议每个 Research Run 初始化时就写清：

- 完成条件
- 部分完成条件
- 放弃条件
- 升级人工确认条件

例如：

- 关键列覆盖率 >= 80%
- 核心对象至少 2 条 primary evidence
- 关键结论没有 unresolved conflict
- 单 cell 重试不超过 N 次
- 预算耗尽时进入 PARTIAL_COMPLETED 而不是继续硬跑

### 4.3 从全局重试升级到局部修复与分支

建议把当前 `Retry` 机制升级成两类动作：

- `Local Repair`
  针对单个 row / cell 重试

- `Branch Exploration`
  针对解释路径、候选集或冲突结论开分支

这样更符合研究任务本身的形态。

### 4.4 从普通 Trace 升级到 Branchable Research Trace

Research Trace 不只是日志。

建议升级成：

- `Mainline Trace`
  当前主研究路径

- `Branch Trace`
  冲突、替代解释、补充搜索路径

- `Decision Trace`
  为什么继续、为什么停止、为什么标低置信

这样未来如果要做可视化，会非常强。

### 4.5 从单级 verifier 升级到双层验证

建议 verifier 分两层：

1. `Cell Verifier`
   判断当前字段值是否被证据支持

2. `Progress Verifier`
   判断当前 loop 是否值得继续

前者关注内容真假，后者关注研究是否还在有效推进。

## 5. NoteWeave 版本的推荐对象模型

关键字段建议包括：

- `planning_horizon`
- `replan_policy`

## 6. 推荐执行流程

```text
用户发起 Deep Research
  -> Clarify / Rewrite Research Prompt
  -> Build Full-Horizon ResearchPlan
  -> Initialize Research Harness Policy
  -> Create Research Table as State
  -> Wide Search
  -> Cell Completion Loops
  -> Cell Verification
  -> Premature Commitment Guard Check
  -> Local Repair or Branch Exploration
  -> Progress Verifier
  -> High-Stakes Consensus (if needed)
  -> Report Writing
  -> Evidence Gate for Final Report
  -> Commit Artifact / Note / Wiki Draft
```

最关键的升级节点有五个：

- `Full-Horizon Plan + Lazy Replanning`
- `Premature Commitment Guard`
- `Branch Exploration`
- `Progress Verifier`
- `Evidence Gate`

## 7. 哪些点最值得写进项目亮点

如果只挑最能打的几个点，不建议把所有概念都写进去。

Deep Research 这条线最值得强调的是：

1. `Table-as-State`
   表格不仅承载结果，也承载执行状态

2. `Loop Engineering with Stop Contract`
   不是无限循环，而是有反馈和停止条件的研究闭环

3. `Evidence-Gated Progress`
   研究推进由验证状态驱动，而不是由模型主观完成感驱动

4. `Premature Commitment Guard`
   防止 agent 过早锁死到单一路径

5. `Durable / Branchable Research Harness`
   支持 checkpoint、恢复和分支探索

## 8. 对 NoteWeave 最合适的一句话定位

`NoteWeave 的 Deep Research 智能体不采用自由放养式多 Agent 群聊，而采用 Evidence-Gated Branchable Research Harness：系统以 Table-as-State 承载研究执行状态，以 Loop Engineering 驱动 Search、Read、Extract、Verify、Revise 受控闭环，以 Stop Contract 和 Progress Verifier 控制停止条件，并通过 Premature Commitment Guard、Branch Exploration 与 Durable Checkpointing 提升长程研究任务的可靠性与可恢复性。`
