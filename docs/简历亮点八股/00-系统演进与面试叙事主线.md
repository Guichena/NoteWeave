# NoteWeave 从 0 到 1：系统演进与面试叙事主线

> 使用边界：本文是面试叙事，不是逐日项目史。`[当前实现]`、`[目标设计]`、`[已测-模拟]`、`[行业参考]` 与 `[生产待验证]` 的定义以 [docs 阅读导航](../README.md)为准；完整演化判据见 [系统设计演化与技术取舍](../系统设计演化与技术取舍.md)。

## 1. 先说明这条时间线的口径

这篇文档按工程问题的因果关系组织项目，不把它冒充成逐日开发历史。面试时讲的是：如果从一个最小可用的知识助手开始，哪些问题会依次暴露，为什么现有方案无法继续支撑，系统因此引入了什么机制。仓库中的迁移脚本、服务、状态机和测试只能证明当前方案边界，具体日期、个人贡献与协作经历由候选人使用自己的记录确认，本文不推断。

整条主线只有一句话：NoteWeave 最初要解决“资料很多，但很难持续整理、检索和产出”的问题，后来逐步发现，生成质量不仅取决于模型，还取决于资料是否可靠进入系统、检索是否匹配场景、长任务是否可恢复、证据是否可验证、上下文和记忆是否会污染事实。

## 2. 从一个最小原型讲起

### V0：同步聊天原型先证明需求

最小方案可以只有一个 Web 接口：用户上传文件，后端读取文本，把最近几轮消息和相关片段拼进 Prompt，再调用模型返回答案。它的优点是开发快、链路短、容易验证用户是否真的需要“围绕自己的资料提问和产出”。

这个方案很快会遇到六类问题：大文件解析占住请求线程；文件、业务状态和检索索引无法原子更新；一套 TopK 检索同时服务问答、深读和 Wiki 时效果不稳定；Research 或 PDF 生成需要几分钟甚至更久，进程崩溃后无法恢复；最近 N 条消息会丢主题，直接自动记忆又会放大模型错误；最终答案有引用，也不代表引用真的支持结论。

这些问题决定了后续演进顺序。先建立可靠资料底座，再做场景化检索；任务变长后，引入受控 Agent 执行框架；开放式研究需要比普通产物生成更强的状态和验证模型；最后把会话压缩、长期 Memory 与事实 Evidence 分开治理。

## 3. 六个阶段如何连续演进

| 阶段 | 当时可工作的方案 | 新暴露的问题 | 引入的核心设计 | 主要代价 |
|---|---|---|---|---|
| V0 同步原型 | 单体接口、同步解析、最近 N 条消息 | 请求阻塞、失败难恢复、数据不可审计 | 先保留最短链路验证需求 | 不适合长任务和多存储 |
| V1 资料底座 | MySQL 记录资料，文件存本地或对象存储 | DB 成功与消息发送无法原子提交，重复消费难避免 | MinIO、Transactional Outbox、Kafka、幂等状态机、ES 可重建投影 | 最终一致，需要补偿和观测 |
| V2 场景化 RAG | 一套 Chunk TopK 加 Prompt | QA、Note、Wiki 对“相关”的定义不同 | 三条 Retrieval Plan，共享 Evidence 契约；BM25、向量、RRF、Rerank、受限图读取 | 策略和评测成本增加 |
| V3 产物 Agent | 一个 Prompt 一次生成 | 长任务超时，工具和能力容易越权，失败后全量重做 | Skill、Schema、ExecutionSpec、编译期 DAG、MCP Policy、Verifier/Repair、Waiting/Resume | 灵活性受约束，框架复杂度上升 |
| V4 Deep Research | 自由 ReAct 循环 | 研究漂移、过早收敛、冲突覆盖、引用不支持结论 | Research Intent、Table-as-State、Cell CAS、候选仲裁、双层 Verifier、Checkpoint | 状态对象和验证成本更高 |
| V5 Context 与 Memory | 最近 N 条、自由摘要、自动写记忆 | 上下文断裂、摘要覆盖历史、记忆污染事实、重放不一致 | Message Ledger、Segment、Summary Revision、RunInputSnapshot、Memory Promotion、Evidence Isolation | 存储、隐私与版本治理更复杂 |

### 面试时不要把中间件当作起点

不要说“项目用了 Kafka、Redis、Elasticsearch、MinIO，所以架构很完整”。更有说服力的讲法是：同步解析拖慢接口，因此把命令异步化；DB 和 Kafka 无法共享事务，因此增加 Outbox；资料召回既有精确词也有语义表达，因此组合 BM25 与向量；不同检索分数不可直接比较，因此用 RRF；昂贵任务既要限制到达速率，也要限制同时运行数，因此用 Redis 令牌桶和并发租约。

技术名称应该出现在问题之后。每引入一个组件，都要能回答“不用它会怎样”和“用了它付出什么”。

## 4. V1：资料底座为什么从同步调用演进到事件驱动

### 4.1 文件为什么不直接放 MySQL

候选方案有三种。文件系统实现简单，但多实例共享、备份和对象版本管理麻烦；MySQL BLOB 可以跟业务记录放在一起，但大对象会放大日志、备份和主从复制压力；MinIO 提供 S3 语义、不可变对象和 Hash 校验，更适合原文件及派生文件。当前方案让 MySQL 保存身份、状态和引用，MinIO 保存大对象。

取舍是业务状态和文件不再处于同一个本地事务。系统必须明确 MySQL 是业务真源，并通过补偿处理对象已写但事务失败、数据库成功但后续解析失败等情况。

### 4.2 为什么不是数据库提交后直接发 Kafka

“先提交 DB，再发 Kafka”会在进程崩溃时丢消息；“先发 Kafka，再提交 DB”会让消费者看见尚不存在的业务对象；XA 或分布式事务会提高部署和故障处理复杂度，而且 Kafka、MinIO、ES 仍不能自然组成一个全局事务。

当前方案在同一个 MySQL 事务中写业务记录和 Outbox。Dispatcher 通过 Lease、CAS 和 Claim Token 领取记录，再投递 Kafka。它选择消息至少送达一次，不承诺端到端 Exactly-once，重复由消费端幂等键、唯一约束和终态状态机吸收。

### 4.3 为什么还需要 Elasticsearch

MySQL 适合事务、约束和精确查询，不适合承担全文相关性、向量检索和索引版本切换。Elasticsearch 只保存可重建投影，文档必须带 Workspace、Source、Snapshot 和 Index Version。这样 ES 故障影响检索能力，但不会成为资料事实的唯一来源。

代价是投影存在延迟，系统必须区分“ES 被配置关闭”“ES 暂时故障”“资料尚未投影完成”，并提供重建、回填和质量门禁。

## 5. V2：为什么一条通用 RAG 最终拆成三条链路

### 5.1 通用 Chunk TopK 的优点和上限

一条 Hybrid Search 链路复用度高，参数少，适合早期验证。但 QA 关心能否找到直接回答问题的片段；Note 关心先选中哪份资料，再围绕锚点阅读连续原文；Wiki 关心页面身份、版本、关系和来源回链。只换 Prompt 无法改变候选对象、排序特征和证据预算。

当前方案共享 Scope、Provider、Evidence Bundle、Citation 和 Trace，但保留 QA、Note、Wiki 三种 Retrieval Plan。它不是复制三套基础设施，而是在统一契约上允许不同策略。

### 5.2 为什么 QA 使用 BM25、向量、RRF 和 Rerank

BM25 对专有名词、数字和代码符号稳定，向量召回覆盖同义表达和自然语言改写。直接相加两路原始分数需要持续校准，Learning to Rank 又需要足够训练数据。RRF 只使用名次，能低成本融合异构召回；当前通过通用 `RerankClient` 只精排融合后的有限候选，把远程计算成本放在更小集合上。Cross-Encoder 是可选 Provider 的常见实现原理，不是仓库协议锁定的模型结构。

代价是 RRF 忽略原始分差，Rerank 增加延迟和 Provider 依赖。因此系统保留 RRF 原顺序作为降级结果，并把 Strategy Tuple 固化进快照，保证一次运行可复现。

### 5.3 为什么排完 TopK 还要做 Evidence Selection

排序优化的是单个候选相关性，Prompt 需要的是一个证据集合。相邻 Chunk 可能来自同一段资料，如果直接取前 K 个，会挤掉其他来源并浪费 Token。Evidence Selection 还要处理来源覆盖、重复片段、直接支持度和预算，必要时在证据不足时拒答。

## 6. V3：为什么产物生成从一次 Prompt 演进为受控 Agent

### 6.1 自由 Agent 和固定 Workflow 各自擅长什么

自由 Agent 能动态选择工具，适合路径未知的探索任务，但结果和权限边界不稳定；固定 Workflow 易观测、易恢复，却难处理不同产物和可选能力。当前方案选择中间路线：Skill 描述目标、Schema 和能力边界，Compiler 生成冻结的 ExecutionSpec，Graph 在编译期完成环检测和拓扑排序，运行期按拓扑序线性执行。

当前运行时以编译期 DAG 和受控节点序列为主，重点是确定性、可审计和恢复；当独立 I/O 节点占主要耗时、等待分支或任务并发明显增加时，再引入 Ready Queue、条件边和节点级并发。

### 6.2 为什么引入 MCP，并把能力收在系统边界内

MCP 提供统一工具发现和调用协议，减少每个 Skill 自己适配外部能力的成本。当前采用系统注册、能力交集、输入 Schema、内部认证和调用审计，把工具副作用收在 Host 与 Worker 的边界内。这样 Skill 可以复用工具协议，又不会让一次用户请求直接获得超出 Workspace 和任务范围的网络、文件或写回能力。

### 6.3 为什么 Verifier 和 Repair 不能省

模型自我反思仍依赖同一份上下文和生成偏差。Verifier 把确定性检查与语义检查分开：Schema、必填章节、Hash、文件大小可以由程序判断，内容覆盖和风格再交给模型。Repair 接收结构化失败项，只重做相关节点；最终输出还要通过全局契约，避免局部修复破坏其他部分。

## 7. V4：为什么 Deep Research 需要独立于普通 Agent 的状态模型

### 7.1 ReAct 能启动探索，但不适合直接作为长期真源

ReAct 的优势是简单、灵活，适合短路径、低风险、失败可接受的探索。开放式研究通常要比较多个实体和字段，持续几十个步骤。只保存对话轨迹会出现目标漂移、重复搜索、来源冲突被最后一次写入覆盖，以及恢复后无法判断哪些结论已经验证。

当前方案把 Research Intent 作为稳定目标，把 Plan 作为可变策略，把 Row、Cell、Evidence 作为结构化状态。每个 Cell 有版本、候选、来源和验证状态，Worker 不能直接覆盖 Canonical 值。

### 7.2 为什么采用候选仲裁而不是 Last Write Wins

Last Write Wins 实现简单，但新结果不等于正确结果；多数投票容易被同一站点的重复转载伪造；Authority-first 适合存在明确权威源的字段，但无法覆盖所有开放问题。当前合并门要求来源身份可审计，并对候选做独立性和支持度判断。冲突无法消解时返回 `VERIFIED_VALUE_CONFLICT`，保留原值，不虚构自动纠正状态。

### 7.3 为什么同时需要 Local 和 Global Verifier

Local Verifier 判断一个 Cell 的候选是否有直接证据、是否存在冲突；Global Verifier 判断整张表是否满足 Intent、关键字段是否缺失、引用是否覆盖报告。局部正确不代表整体任务完成，整体看起来完整也不代表每个结论有证据。

### 7.4 为什么使用 Checkpoint，而不是完整 Event Sourcing

只存最终结果无法恢复，完整事件溯源能重建任意中间状态，但事件 Schema、回放兼容和存储成本更高。当前方案保存结构化 Checkpoint、任务审计和完成回执，大对象放 MinIO，并校验大小和 SHA-256。它获得可恢复性和幂等重放，但不承诺从所有历史事件重建全部状态。

## 8. V5：为什么 Context 和 Memory 必须独立设计

### 8.1 最近 N 条为什么不够

最近 N 条实现最简单，也能保证尾部连续，但主题切换后会带入无关内容，长主题又可能被窗口截断。系统因此保留单调 Message Sequence，用 Segment 表示稳定主题，用版本化 Summary 压缩历史，同时保留连续 Raw Tail。

摘要异步生成时冻结 Segment Version。Promotion 发现版本已变化，就把旧摘要标为 Stale，而不是覆盖新消息。这样摘要生成失败或落后时，可以回退到有界原文，而不会静默丢掉中段历史。

### 8.2 为什么不让模型自动写长期 Memory

自动写入快，但一次幻觉、Prompt Injection 或过时偏好会持续影响后续任务；全部人工确认最安全，却会制造过多审核负担。当前方案让 Answer、Research、Artifact 只提交 Observation 或 Candidate，由 Java Memory Runtime 做类型、Scope、敏感性、重复和冲突门控，再进入审核或受限自动晋升。

### 8.3 为什么 Memory 不能参加 Evidence Rerank

Memory 表示偏好、约束和历史观察，Evidence 表示可引用的资料事实。如果 Memory 进入 Source Recall 或 Citation 排序，模型之前生成的内容可能反过来证明自己，形成闭环污染。两者可以同时进入 Context Compiler，但使用独立预算、标签和信任域。

### 8.4 为什么冻结 RunInputSnapshot

任务开始后，消息、摘要、Memory 和资料都可能变化。如果重试时重新编译上下文，同一个 Run 会得到不同输入。Snapshot 固化 Message Ref、Summary Revision、Memory Revision、Evidence Ref、策略版本和 Hash。隐私删除发生后，系统返回降级回放或不可回放，不用新内容伪装历史输入。

## 9. 从用户功能继续下钻的演进地图

五条技术主线最终要落回用户功能。面试官如果从页面或接口发问，可以先定位到下面这张表，再进入对应详细文档。

| 用户功能 | 最早可行方案 | 随规模暴露的问题 | 当前实现方向 | 面试时主动讲的代价 |
|---|---|---|---|---|
| Workspace 与权限 | 请求带 User ID，查询时加 Workspace ID | 客户端身份可伪造，成员状态变化后旧权限继续生效 | 服务端身份过滤、Workspace Membership、ACL Version、对象归属二次校验 | 每条链路都要传递和校验身份，测试面增大 |
| 资料上传 | 单请求上传到本地盘 | 大文件占线程，多实例文件不共享，失败难恢复 | 分片约束、内容真实性校验、MinIO 对象、MySQL Snapshot、异步 Task | 用户先看到 Pending，需要进度和失败状态 |
| 解析与切块 | 上传请求内直接解析 | 格式耗时不稳，重复请求生成重复 Chunk | Outbox、Kafka Worker、Snapshot + Chunk No 幂等、失败终态 | 存在队列与最终一致性窗口 |
| QA 问答 | BM25 TopK 加 Prompt | 同义表达漏召回，同源 Chunk 挤满上下文 | Scope Filter、BM25 + Vector、RRF、Rerank、Evidence Selection | 延迟和 Provider 成本上升 |
| Note 深读 | 全库 Chunk 排序 | 命中片段却丢失资料和章节语境 | Source Recall、Anchor、Reading Window、两阶段 Rerank | 链路比 QA 多一层，参数要单独评测 |
| Wiki 组织 | 把生成页面当普通文档检索 | 页面版本和来源关系丢失，生成内容可能自证 | 当前版本、文本种子、受限关系读取、Source Backlink | 不是完整 GraphRAG，关系信号能力有限 |
| 流式回答 | HTTP 等待完整文本 | 长回答首字延迟高，断线后只能重跑 | SSE、单调 Event Sequence、Replay-prime-before-live、Redis Realtime Bridge | 需要游标过期、合并和重连语义 |
| 连续对话 | 最近 N 条消息 | 主题切换和长会话导致关键约束丢失 | Message Ledger、Segment、Summary Revision、Raw Tail | 摘要版本和 Stale 治理复杂 |
| 产物生成 | 一次 Prompt 返回 Markdown | 多步骤工具失败后全量重做，输出结构不稳 | Skill、Schema、ExecutionSpec、编译期 DAG、Verifier/Repair | 牺牲自由度，运行时当前不做节点并行 |
| 外部能力 | 每个工具写专用 Client | 工具发现、Schema 和 Trace 重复 | 受信任系统 MCP、Capability Intersection、调用审计 | 不开放任意插件，自定义调试能力需要强边界 |
| Deep Research | ReAct 搜索后直接写报告 | 目标漂移、字段缺证、来源冲突、长任务中断 | Intent、Table-as-State、候选仲裁、双层 Verifier、Checkpoint | 模型调用和状态管理成本高 |
| 长期 Memory | 自动保存模型总结 | 幻觉、注入和过期信息持续污染后续任务 | Candidate、风险门控、Review、Revision、Outcome Feedback | 记忆进入上下文有延迟，用户可能需要审核 |
| 任务重试 | 失败后重新读取当前上下文 | 同一个 Run 重试时输入变化，结果不可解释 | RunInputSnapshot、策略版本、内容 Hash | 引用对象删除后只能降级重放 |
| 删除与隐私 | 数据行加 Deleted 标志 | 摘要、缓存、快照和外部对象仍泄露派生内容 | 派生摘要 Stale/清空、缓存失效、Cleanup Task、Replay 降级 | 历史结果可能无法完整回放 |

### 9.1 Workspace 与权限怎么讲

最早把 `workspace_id` 当查询条件即可验证多空间功能，但客户端传来的用户身份不能成为信任根，ES 索引脏数据也可能绕过单层过滤。当前由服务端身份过滤器确定 Actor，业务层校验 Membership 与对象归属，检索在 ES 下推 Scope 后仍用 MySQL Hydration 二次确认。它增加了重复校验，却把“排序正确”和“绝不越权”分成两个目标。

### 9.2 上传、解析和可检索状态怎么讲

上传成功只表示对象和业务任务已经可靠创建，不表示内容已经可检索。解析固定 Snapshot，切块使用稳定位置身份，投影完成后才把版本标为 Ready。这样状态更多，但可以准确告诉用户是上传失败、解析失败、索引延迟还是检索服务故障。

### 9.3 QA、Note、Wiki 怎么讲

三个入口共享 Conversation、Scope、Evidence 和 Citation，但相关性目标不同。QA 从多资料中找直接支持，Note 围绕少数资料保留连续原文，Wiki 读取版本化知识页并尽量回到原资料。拆链路的判断标准不是页面名称，而是候选单位、排序目标和证据组织是否相同。

### 9.4 流式回答与断线恢复怎么讲

SSE 比 WebSocket 更适合当前单向 Token 和状态事件推送，代理与前端消费也更简单。服务器为事件分配连续序号，重连时先补历史再接 Live，边界事件需要去重和合并。Redis Bridge 不可用时不能返回空流冒充任务结束，要明确失败或回源，因为“暂时取不到事件”和“确实没有事件”语义不同。

### 9.5 Research 与普通 Artifact 为什么分开

两者共享长任务、Outbox、Worker、配额、对象存储和幂等完成，但状态粒度不同。Artifact 的目标和图通常在执行前已知，核心是受控生成与输出验证；Research 的路径和证据缺口动态变化，需要 Cell、候选仲裁、Gap、Wave 和全局完成契约。复用基础设施，不强行复用领域状态机。

### 9.6 删除为什么是跨模块功能

删除一条消息或资料不仅影响一张表，还会影响摘要、Memory Candidate、RunInputSnapshot、引用、ES 投影、MinIO 对象和回放能力。系统以“停止在线可见和召回”为第一目标，外部副作用通过持久 Cleanup 收敛，保留的 Tombstone 只用于最小审计。强行保证删除后历史运行仍可完整重放，会与隐私语义冲突。

## 11. 所有功能点都用同一个决策模板

1. 用户在什么场景遇到了什么问题。
2. 最小方案是什么，它为什么一开始合理。

8. 主动给出当前边界，以及什么条件出现时会换方案。

## 12. 一次完整面试如何分层讲

### 30 秒版本

NoteWeave 是一个围绕个人和团队资料持续整理、检索、研究和产出的知识工作台。我没有把它做成单次聊天，而是先用 MySQL、MinIO、Outbox、Kafka 和 Elasticsearch 建立可恢复的资料底座，再按 QA、Note、Wiki 拆分检索策略；长产物使用受控 Skill Graph、MCP、配额租约和 Verifier/Repair；开放式研究进一步用 Table-as-State、候选仲裁和双层验证；长会话则通过版本化摘要、不可变输入快照和门控 Memory 保持连续，同时把 Memory 与事实 Evidence 隔离。

### 3 分钟版本

先讲业务起点，再沿着三条因果链展开。第一条是资料如何可靠进入系统：文件进 MinIO，业务状态进 MySQL，Outbox 解决 DB 与 Kafka 双写，ES 只做可重建投影。第二条是模型如何得到正确输入：QA 用混合召回，Note 先选资料再扩原文窗口，Wiki 读取版本化页面和来源回链，三条链路最后统一为 Evidence Bundle。第三条是长任务如何可控：普通产物用 Skill、Schema、ExecutionSpec 和 Verifier，Deep Research 用字段化状态、Cell CAS、候选仲裁和 Checkpoint。最后补充 Context 与 Memory，说明系统冻结每次 Run 的真实输入，并禁止 Memory 进入 Citation 和 Evidence Rerank。

### 继续深挖时的顺序

面试官偏后端，就展开 Outbox、Kafka、幂等、CAS、Lease 和多存储一致性；偏搜索，就展开 BM25、向量、RRF、Rerank、Evidence Selection 和评测；偏 Agent，就展开 Skill Compiler、Capability Policy、Waiting/Resume、Table-as-State 和 Verifier；偏系统设计，就展开真源、投影、版本、故障矩阵、可观测性和容量；偏大模型应用，就展开 Context Compiler、Snapshot、Memory Promotion、Citation Support 和防污染边界。

## 13. 面试中最重要的真实性边界

- 不把内部 Gold Set 说成公开 Benchmark，也不把 6 条手工 fixture 的 100% 说成在线融合链路准确率。
- 不把编译期 DAG 说成运行时并行图调度。当前运行期按拓扑序线性执行。
- 不把工具协议的复用能力讲成任意能力开放。当前面试主线只需说明系统注册、权限交集和受控写回。
- 不把 Kafka 的投递语义说成业务端到端 Exactly-once。系统采用 At-least-once 加业务幂等。
- 不把 Elasticsearch 说成事实真源。它是可以从 MySQL 和 MinIO 重建的查询投影。
- 不把 Memory 说成资料证据。它只能影响表达、偏好和约束，不能自证事实。
- 不虚构线上用户量、QPS、准确率和压测结论。没有真实数据时，就说明验证使用了哪些契约测试、集成测试、故障注入和确定性样例。

这个项目真正解决的不是“让模型多调用几个工具”，而是把资料、检索、上下文和长任务都变成有身份、有版本、有状态、有证据、可恢复的工程对象，并且对每一次技术选择说明收益、代价和适用边界。

### 15.1 Workspace 隔离的 4 至 5 分钟串讲

**背景。** Workspace 不是 Controller 里的一个查询参数，而是资料、权限、运行、知识和成本的共同隔离边界。最简单的实现只在 URL 里传 `workspaceId`，Controller 查一次成员关系，随后 Service、缓存、Kafka 和搜索都信任这个值。单体同步阶段看起来足够，但任务一旦异步化，就会出现 Repository 漏过滤、缓存只按对象 ID 命中、Worker 信任 Payload、搜索返回旧权限文档等 Bad Case。

**错误判断。** 最初容易认为“入口鉴权通过，内部服务就可信”，或者依赖前端不展示其他 Workspace。问题在于权限会变化，消息会重试，Checkpoint 会恢复，缓存和投影又有延迟。一次入口校验无法证明几分钟后的 Worker 仍有权读取或写回，也无法阻止旧 Callback 携带过期 Scope。

**方案。** `[当前实现]` Workspace 已进入主要 API、业务表、ACL Cache 和契约测试。`[目标设计]` 使用纵深校验：API 从认证上下文取得 Actor；Service 验证 Membership 和动作；SQL 用 Workspace 与对象 ID 联合定位；缓存 Key 加 Workspace 与 ACL Epoch；Kafka 和 Callback 只携带业务身份，控制面重新读取真源；Elasticsearch 命中回 MySQL 检查当前 Head 与 ACL；MinIO 的对象 Key 本身不授予下载权；Trace 可以记录受控 Scope，但 Metrics 不使用高基数 Workspace ID。

**并发、撤权和故障。** ACL 正缓存降低数据库压力，却会延迟撤权；负缓存避免穿透，却会延迟新授权。因此不能只把 TTL 调得很短，而是引入权限变更事件、主动失效、ACL Epoch 和读时校验。策略服务或权限真源不可用时，高风险写操作 Fail Closed，只读链路可以在明确不泄露的前提下给出错误或降级。旧 Worker 即使仍在执行，最终写回还要通过 Lease、Fencing、Workspace 和目标版本条件。

**参数、验证与边界。** ACL Cache 当前默认 TTL 300 秒、负缓存 30 秒、Jitter 60 秒，这是配置事实，不是撤权传播 SLO。验证要覆盖跨 Workspace 对象 ID、相同文本 Cache 碰撞、索引旧文档、重复 Callback、权限变更乱序和策略服务故障，硬门槛是 Scope Violation 为 0。`[生产待验证]` 仍包括真实租户规模、权限变更频率、缓存命中和区域化合规。只有数据驻留、热点隔离或客户独立密钥要求明确时，才从共享 Schema 演进到分库、独立索引或独立对象桶。

## 16. 技术栈选型的面试级长回答

这一节用于回答“为什么采用这套技术栈，而不是调研到的其他方案”。回答时不要先背组件名称，而要先说明系统的约束：NoteWeave 同时有短请求、资料异步处理、可恢复的 Research 和 Artifact 长任务，还要满足 Workspace 隔离、证据可追溯、任务可重试和前端断线恢复。由此可以得到一个很重要的分工原则：Java 主服务负责可信的控制面，MySQL 负责业务状态和约束，Outbox 保存跨进程投递意图，Kafka 统一承载资料、Research 和 Artifact 的持久命令流；Artifact 的版本化最小命令还携带 Delivery Token，把 Broker 投递与 Host 的 Lease、Fencing、Callback 仲裁衔接起来。Python Worker 负责模型和工具生态，MinIO 保存大对象，Elasticsearch 只是可重建的检索投影，Redis 只承担低延迟协调，浏览器通过 React、TypeScript 和 SSE 获得结果。这个顺序比“我们用了多少中间件”更重要，因为每个组件都对应一个明确的不变量，替换组件时也不会把领域语义一起替换掉。

### 16.1 Java 17、Spring Boot 3.3.5、Spring JDBC 和 MySQL 8.4

面试时我会把 Java 主服务称为控制面，而不是简单的后端接口层。浏览器提交请求后，主服务首先确定当前 Actor、Workspace 和资源归属，然后在一个明确的事务里写入用户可见的业务状态，例如 `Source`、`AnswerRun`、`ResearchRun`、`ArtifactJob`、版本和事件。Spring Boot 3.3.5 提供 HTTP、配置、验证、Actuator 和 Kafka 集成，Java 17 的类型系统、记录类、异常边界和成熟的线程模型适合承载这些状态机。数据访问使用 Spring JDBC 而不是让 ORM 隐藏 SQL，因为项目大量使用条件更新、受影响行数判断、批量插入、JSON 快照、唯一键和按 Workspace 的复合过滤。比如一次租约续期不能只把对象读出来再保存，而要在 `where task_id = ? and lease_epoch = ? and fencing_token = ?` 的条件下更新，返回零行时必须解释为旧 Owner、版本冲突或任务不存在。JDBC 让这种 SQL 和事务边界显式可见，代价是 RowMapper、分页和参数维护工作更多，但它更适合当前以状态机和并发仲裁为核心的控制面。

MySQL 8.4 被选作业务真源，是因为 Workspace、成员、任务、版本、Evidence、Outbox 和回调收据之间存在大量关系约束、唯一键和事务边界。MongoDB 或把 JSON 文档作为主模型可以更快地改变字段，但很难自然表达“同一个 Workspace 内同一个业务幂等键只能成功一次”“旧版本不能覆盖新版本”“当前租约 Owner 才能推进状态”这类约束。PostgreSQL 当然也能满足这些要求，并且在 JSON、扩展和部分高级查询上有优势；当前没有采用它，不是因为它不够好，而是因为本项目的核心收益来自关系约束、JDBC 直写和可预测的迁移，而不是数据库扩展能力。Flyway 从空库按版本执行迁移，禁止修改已执行文件，保证代码、表结构和测试可以一起演进；这也比 JPA 自动建表更可控，因为自动建表无法替代大表索引、兼容发布、回填和锁等待设计。面试官如果追问为什么不用 JPA，我会回答：简单 CRUD 可以用 JPA，但本项目的关键路径需要看到 SQL 的条件更新和行数语义，所以选择 JDBC，把自动化程度换成对一致性和故障语义的掌控。

### 16.2 Kafka、Transactional Outbox 和 At-least-once

资料解析、检索投影、Wiki ingest、Research 命令和 Artifact 派发都不适合占用浏览器的同步 HTTP 请求。业务状态和 Outbox 先在 MySQL 本地事务提交，再由 Dispatcher 向 Kafka 发布。普通事件的重复由业务唯一键、版本检查和条件更新吸收。Artifact 的旧实现通过单条拉取、Delivery Token、Callback Receipt 和 70 分钟 Lease 约束读取与回写；推荐设计不再让 Consumer 占着 Offset 执行小时级任务，而是在 MySQL 幂等登记 Durable Execution 后提交 Offset，随后由 Scheduler、Execution Lease 和 Fencing 管理。Broker ACK、Execution Registration、Offset Commit 和业务终态是不同提交点，整条链路仍是 At-least-once。外部副作用完成但 Receipt 尚未确认时，仍需 Operation 幂等和 Unknown Outcome 对账。

RabbitMQ 在工作队列、路由和低延迟确认上很有优势，Redis Streams 也能较快搭出消费组。当前没有采用它们作为主投递骨干，主要考虑的是项目已经需要分区消费、命令保留、失败重试、DLQ 查询和按 offset 观察延迟，Kafka 的模型与这些需求更吻合；同时 Redis 已经承担令牌桶、并发租约和实时桥接，如果再把它当可靠任务主队列，故障时会把缓存、限流和任务恢复耦合在一起。Transactional Outbox 也不是免费方案，它会带来数据库轮询、投递延迟和清理问题，所以每类 Outbox 都有 Claim、Lease、Attempt、Dead Letter 和 Redrive 规则。面试中需要主动说明：我们没有使用 XA 或跨数据库分布式事务，因为它会把 MySQL、Broker 和 Worker 绑在一个昂贵的提交协议里；当前更愿意接受短暂的最终一致窗口，再用可恢复的本地状态和幂等边界把窗口收敛。若未来队列年龄、任务等待分支或补偿复杂度持续超过现有状态机的维护能力，再重新评估额外编排层；目前 Java 状态机、Outbox 和 Worker 契约足以覆盖真实范围。

### 16.3 Python 3.12 Worker 与 Java 控制面的跨语言边界

Python Worker 的价值不在于“Python 更适合写服务”，而在于 Research 和 Artifact 的执行面会频繁接触模型 SDK、网页读取、解析库、搜索工具和 MCP 生态。把这些依赖全部塞进 Java，会让主服务的发布周期、类路径和故障面被外部工具牵制；把全部业务迁到 Python，又会让用户 API、权限、事务和迁移失去统一的控制点。因此当前采用 Java 创建 Run、Task 或 Job，冻结输入快照并分发命令，Python 只领取任务、执行步骤、保存 checkpoint，再通过受内部认证保护的 HTTP callback 回写结果。Worker 不直接写 MySQL 业务表，回调必须携带 task、attempt、owner、fencing 或版本信息以及幂等 callback key，Java 再用状态机和受影响行数判断是否接受。这条边界把“模型调用失败”和“业务状态被越权修改”分开处理，也允许以后替换 Python 运行时而不改变浏览器契约。

全 Java 的优点是类型和部署统一，调试链路短；但当前 AI 工具和数据处理生态在 Python 中迭代更快，且长任务本身不应阻塞 Spring 请求线程。全 Python 或引入额外图编排框架也有优点，例如图执行和重试抽象更丰富，但它们会把 Workspace ACL、MySQL 事务、版本写回和产品 API 再复制一份，形成两个控制面。当前项目已经有明确的 `ResearchRun`、`ArtifactJob`、`Task`、Outbox、Lease 和 callback 表，继续使用现有控制面更容易保持状态、权限和回放一致。只有当任务数量、平均执行时长、等待分支和补偿逻辑增长到现有状态机难以维护时，才根据运行数据评估新的编排实现，而不是因为框架更流行就提前替换。

### 16.4 MySQL、MinIO 和 Elasticsearch 的三层数据分工

资料链路刻意把“业务元数据”“大对象内容”和“检索索引”分开。上传记录、Source 生命周期、Snapshot、Chunk 身份、版本、ACL 和解析状态进入 MySQL；原始文件、固定快照和 Artifact 文件进入 MinIO 的 S3 兼容对象存储；切片后的 BM25、向量、过滤字段和检索版本进入可重建的 Elasticsearch 投影。用户上传成功只表示对象和业务任务已经可靠建立，不等于已经解析或可检索。解析器基于固定 Snapshot 产生稳定的 `chunk_no`、digest 和来源身份，投影构建成功后才把检索版本收口为 Ready。删除时先停止在线可见和召回，再由 Cleanup Task 清理对象和索引，这承认三套存储之间存在最终一致窗口，但每个窗口都有状态和补偿入口。

把文件直接存 MySQL BLOB 会简化事务，却会放大数据库备份、连接和大字段读写压力；把文件放本地磁盘则无法支持多实例和容器重建。MinIO 在本地提供可重复的 S3 语义，未来可以切换云 S3，而不把业务层绑定到某家云厂商。检索方面，Elasticsearch 同时提供 BM25、过滤、向量和聚合，适合 QA、Note 和 Wiki 共用一套带版本的投影；Qdrant、Weaviate 等向量数据库在纯语义召回上很有优势，但当前系统不能丢掉关键词、Workspace 过滤、来源版本和可解释的分数。GraphRAG 适合关系密集的知识网络，当前 Wiki 只把链接和受限图关系作为辅助信号，事实仍回到版本化 Source，因此没有先引入图数据库。Elasticsearch 也可以关闭，关闭时只能返回明确的 fallback 或错误，不能把空列表伪装成正常召回。

### 16.5 React 19、TypeScript、Vite 与 SSE 的交付链路

前端采用 React 19、TypeScript 和 Vite 5，定位是一个围绕 Workspace、会话、资料、研究运行和产物版本的工作台，而不是需要服务端渲染的内容站点。TypeScript 的价值是把 `/api/v2` 的请求、响应、状态和事件名称固化在编译期，减少 Java DTO、前端状态和 Worker 回调字段各自漂移；Vite 提供较轻的开发和构建链路，适合当前单页工作台与 Playwright、Vitest 的快速反馈。前端发起聊天或长任务后，先拿到稳定的 Run 或 Task 身份，再用查询接口读取快照，用 SSE 接收增量事件。SSE 是单向服务端推送，正好对应回答 Token、状态变化、进度和完成事件，不需要为当前场景引入双向 WebSocket 协议。

这里最关键的不是“页面能看到流式文字”，而是交付可靠性。事件先写入 `answer_event` 或任务事件表，服务端为每条事件分配单调序号；浏览器断线后带 `after` 或 `Last-Event-ID`，服务器先回放游标之后的历史，再接入 Live，终态还会根据数据库状态补发快照和 Evidence Manifest。SSE 连接本身不是队列，内存 Channel、Redis Bridge 或浏览器连接都不能当事实源。WebSocket 可以支持双向实时协作，长远可能适合多人编辑或交互式 Agent 控制，但当前引入它会增加连接状态、代理、心跳和消息路由复杂度，而用户主要是从服务器接收事件。因此选择 SSE 是以当前交互方向和可恢复语义为依据，不是断言 WebSocket 技术落后。

### 16.6 Redis 7.2 的边界：低延迟协调，而不是业务真源

Redis 在 NoteWeave 中承担的是需要低延迟和 TTL 的协调工作，例如 Workspace 与 Actor 维度的速率令牌桶、工作负载并发租约、短期 ACL 或编译缓存，以及多实例 SSE 的实时桥接。对令牌桶和租约，Lua 或原子命令把检查、扣减和过期放在一个 Redis 操作中，避免多个 Java 实例先读后写；对缓存和实时桥接，失效或断线后可以回源 MySQL 的状态和事件。这个边界必须反复强调，因为如果把 Redis 里的键当成任务真源，重启、淘汰或网络分区就会直接改变业务结论。MySQL 记录 Run、Task、版本和 Evidence，Kafka 记录待执行命令，Redis 只加速和协调它们。

我们没有用 JVM `ConcurrentHashMap` 代替 Redis，因为本地 Map 只覆盖单实例，无法做跨进程配额和租约；也没有把所有状态放 Redis 再定期落 MySQL，因为那会把持久化、备份和权限审计变成异步猜测。代价是 Redis 故障时高风险任务可能选择 Fail-closed，用户会看到明确的“暂时不可调度”，而不是每个实例各算一份限额。Mem0、Zep、Letta 这类 Memory 产品提供了很好的记忆搜索、版本和上下文层次思想，但当前 Memory 需要与 Workspace、Review、Revision、Outcome 和删除语义一起进入项目数据库，所以采用自己的候选、审核和编译模型，避免把关键用户数据藏在外部运行时。调研到的实现可以作为未来独立 Memory Provider 的参考，不能替代当前的事实源和权限边界。

### 16.7 LLM、Embedding、Rerank、MCP 和安全边界

模型相关能力全部通过 Provider 或 Adapter 接入，LLM 负责回答或长任务生成，Embedding 和 Rerank 负责检索增强，具体提供方、开关、超时和错误映射来自配置。这样做的原因是模型供应商会变化，网络错误、限流、空响应和格式损坏也必须有明确语义；如果把某一个厂商 SDK 直接散落在 Controller 和 Worker 中，替换模型会同时改动业务状态机、测试和 UI。当前环境默认可以关闭这些 Provider，`NoOp` 或空结果只能表达“能力未启用”或“没有可用结果”，不能写成模型已经回答成功。面试时应主动区分机制验证和模型质量验证：本地测试证明的是超时、降级、Evidence、重试和回放，不能推出公网模型的准确率或生产容量。

MCP 在项目中是受信任系统 Skill 的能力协议，用来统一工具发现、输入 Schema、调用审计和结果回传。当前重点是能力交集、内部认证、Workspace 范围和受控写回，浏览器使用用户会话或 Bearer Token，Worker 使用独立内部 token，并且还要通过 Task、Lease 和 Fencing 检查。把鉴权只放在前端、只放在 Worker 或只放在工具协议层都不够，控制面必须在每个跨租户读写和每个跨进程回调处再次仲裁。

### 16.8 Docker Compose、测试和可观测性的真实边界

Docker Compose 把 MySQL、Redis、Kafka、MinIO、Elasticsearch、Java Backend、React Frontend 和两个 Worker 放在同一套本地联调拓扑中，目标是让上传、异步解析、检索、SSE、Research 和 Artifact 可以被端到端验证。它主要服务于开发、演示和集成验证，不能替代面向目标规模的容量测试。测试也按边界分层：Java 单元测试验证状态机、DAO 条件更新和错误映射，集成测试验证 MySQL、Kafka、Redis 和对象存储协作，Worker 测试验证 Schema、checkpoint 和 callback，前端用类型检查、Vitest、Playwright 验证 API 和 SSE 交互；Actuator、worker metrics、Outbox/DLQ 查询和运行时 inspector 则用来解释“卡在哪里”。

这套技术栈的核心取舍可以收束为一句话：我们没有追求组件最多或框架最先进，而是让每种故障都有归属，让每个结果都有来源，让每个长任务都有恢复点。Java 加 MySQL 的控制面、Kafka 加 Outbox 的投递面、Python Worker 的执行面、MinIO 加 Elasticsearch 的资料面，以及 React 加 SSE 的交付面，已经形成了较小而完整的闭环。只有当数据量、并发、任务时长、Provider 限额或运行约束发生变化时，才根据监控和压测结果讨论替换组件或拆分服务。

### 16.9 业界参照如何转化为当前选择

调研资料的作用是提供问题的通用解法，不是把明星项目的拓扑原样搬进来。Kafka 与 Debezium Outbox 帮助确定事件投递边界，长任务框架帮助理解 Checkpoint、Waiting 和 Retry，RAG 项目帮助拆分 Ingestion、召回、Rerank 和 Evidence，Memory 项目帮助理解 Scope、版本、更新与删除，MCP 项目帮助明确 Schema、授权和审计。NoteWeave 把这些知识翻译成自己的对象和边界：Outbox、Task、RunInputSnapshot、Evidence、Memory Candidate、Skill Graph、Callback Receipt 和 Workspace ACL。面试主回答先讲这些已经实现的对象，只有面试官进一步追问规模或任务复杂度时，再展开替代方案的切换判据。

**建议的收尾方式**：如果面试官只给我四到五分钟，我会沿着“浏览器请求进入 Java 控制面，状态落 MySQL，Outbox 投递 Kafka，Python Worker 执行并回调，资料对象放 MinIO，检索投影进 Elasticsearch，结果用 SSE 可恢复交付”讲一遍，再挑一个取舍深入。最后明确三件事：MySQL 是业务真源，Kafka、Redis、SSE 和 Elasticsearch 都不是事实源；当前采用 At-least-once 加业务幂等，不声称端到端 Exactly-once；Provider 是否启用不改变核心状态机、权限和回放边界。

## 17. 全项目 4 到 5 分钟标准回答

NoteWeave 最初是给学校资料场景做的知识助手。学生和教师手里有 PDF、讲义、笔记和课程网页，但资料分散，普通聊天只能临时问一次，回答很难追溯，也不能继续整理成 Note、Wiki、研究报告或讲义产物。最早的方案就是同步上传、取最近几轮消息、检索几个片段，再调用模型。这能快速验证需求，但很快遇到六个问题：大文件阻塞请求；MySQL、文件和索引之间会部分成功；一套 TopK 无法同时服务问答、深读和知识组织；Research 和 Artifact 长任务中断后无法恢复；长会话会超窗；模型生成的引用也不一定真的支持结论。

第一步是把资料做成可靠底座。MySQL 保存 Workspace、Source、Snapshot、Chunk 身份、状态和权限，MinIO 保存原文件与派生大对象，Elasticsearch 只做可重建检索投影。业务记录和 Outbox 在同一个 MySQL 事务提交，Dispatcher 再把解析、投影和其他命令投到 Kafka。整条链路选择 At-least-once，重复由业务幂等键、唯一约束、状态前置条件和 Receipt 吸收，不说端到端 Exactly-once。这样数据库提交后进程退出，命令仍在 Outbox；ES 丢失可以重建，也不会反向覆盖 Source 真源。

第二步是把 RAG 按用户任务拆开。QA 要找能直接回答问题的 Passage，组合 BM25 和向量召回，用 RRF 融合不同分数空间，再对有限候选 Rerank 和 Evidence Selection；Note 先确定资料与锚点，再扩连续 Reading Window；Wiki 读取版本化页面、来源回链和受限关系。三条链路共享 Scope、Evidence、Citation 和 Trace，不共享同一个 TopK 策略。这样不是复制三套系统，而是在同一证据契约上允许不同的“相关性”定义。当前向量和 Rerank Provider 可以关闭，未启用时不能把降级结果说成完整 Hybrid 已验证。

第三步是受控 Agent 与 Artifact。一次 Prompt 适合简单 Markdown，但 PDF、PPT 或多步骤产物需要工具、文件、校验和修复。Skill 描述目标、Schema 和 Capability，Compiler 生成冻结 ExecutionSpec 和 DAG，运行时按当前实现的拓扑序执行；MCP 只暴露系统注册并经过 Workspace、Task 和 Capability 交集的能力。Verifier 先做 Schema、必填章节、Hash、文件等确定性检查，再做语义检查；Repair 只重做失败部分。这里选择受控 Workflow 而不是完全自由 Agent，是用一部分灵活性换可恢复、可审计和权限边界。

Research Agent 是项目最重点的演进。普通 ReAct 可以边想边搜，但长研究容易漂移、重复搜索、被单一来源带偏，并在恢复后不知道哪些结论已经确认。系统把 Research Intent 冻结，把问题拆成 Row/Cell 的 Table-as-State；Worker 只能提交带 Evidence 的 Candidate，不能直接覆盖 Canonical 值；Cell 通过版本和 CAS 仲裁并发，来源按 Lineage 判断独立性，Local Verifier 检查 Claim 与 Evidence，Global Verifier 检查整张研究表的覆盖、冲突和 Citation。长任务用 Lease、Fencing、Checkpoint、预算和 Completion Receipt 恢复，旧 Worker 晚到不能覆盖新 Owner。动态探索可以提出新方向，但是否进入主研究计划由控制面接受，不让模型自己改变完成标准。

第四步是 Conversation、Context 和 Memory。用户一次发送先形成幂等 Turn，AnswerRun 按 PREPARING、RETRIEVING、GENERATING、FINALIZING 和终态推进，Input Snapshot 冻结消息、摘要、Memory、Evidence 和策略。AnswerEvent 持久化单调序号，Redis 和 SSE 只负责实时交付；断线后通过 `Last-Event-ID` 从 MySQL 回放，再用 Snapshot 校正。长会话把稳定历史切成 Segment，Summary Revision 先校验再 Promotion。Memory 只接收 Candidate，按 Scope、风险和冲突审核成 Revision；它可以影响偏好和约束，但不能进入 Evidence Rerank 或作为 Citation，避免模型生成内容反过来自证。

横切治理围绕 Workspace 和运行身份展开。用户 Token 只证明身份，Service 还要检查 Permission；只传资源 ID 的接口先反查真实 Workspace，检索 Evidence 进入 Prompt 前再做 Ownership Guard。成员变化提升 ACL Version，让旧缓存自然失效。长任务入口有速率与在途 Quota，真正 Provider 调用还有 Permit 和 Budget；通用 Task 负责用户可见状态，Research Domain Task 单独负责 Lease Epoch 和 Fencing。前端 Event 只做增量，Snapshot 才是权威状态，多标签页 Subscriber 不会创建多个 Generation Owner。

验证上分四类。内部 Gold 测 QA Recall/nDCG/Citation、Research Cell/Verified Claim、Artifact First-pass/Repair；故障注入测重复、晚到、Lease、Checkpoint 和结果未知；容量压测绑定硬件、Provider 和流量模型；真实业务才看 Workspace 激活、采纳和节省时间。论文和产品只提供指标结构，例如 BEIR 的检索指标、ALCE/DeepResearchBench 的 Citation、LiveDRBench 的 Claim、GPT Researcher 的来源数、耗时和单次成本，不能把外部成绩或内部演练数字直接写成 NoteWeave 线上结果。

当前源码能证明的是 Java/MySQL 控制面、MinIO/ES 资料分工、Outbox/Kafka 投递、Python Worker 回调、场景化检索契约、Research/Artifact 状态、Context/Memory、SSE 回放、权限和部分指标。完整 OpenTelemetry、正式生产 SLO、真实学校用户量、公开 Benchmark 同协议分数、长期成本和跨可用区容灾仍待验证。这个项目的核心不是堆中间件，而是把资料、证据、运行和记忆都变成有身份、有版本、有状态、能恢复的对象，并明确每个方案什么时候值得、失败时怎样收敛、规模变大后先扩哪一层。

## 18. 重点知识点：怎样证明这不是为了面试堆出来的过度设计

### 3 分钟回答

判断过度设计不能看组件数量，而要看每个机制是否对应一个已经出现或明确可复现的失败窗口。同步聊天阶段不需要 Kafka、Lease 和复杂 Memory，只要一个接口就能验证需求；资料解析超过请求时限后才需要异步 Task；MySQL 提交与 Kafka 发送出现双写窗口后才需要 Outbox；Worker 任务跨分钟并可能重试后，Lease 和 Fencing 才有价值；只有长期研究出现多字段、冲突和恢复要求时，Table-as-State 才比 ReAct 轨迹更合适。

每个组件都能替换，但业务不变量不能丢。Kafka 可以换成数据库队列或 RabbitMQ，仍要保留至少一次输入下的幂等与死信；Elasticsearch 可以换搜索引擎，仍是可重建投影；Redis 可以暂时关闭，任务和事件仍在 MySQL；Python Worker 可以换运行时，Java 控制面仍仲裁权限、版本和终态。这说明系统不是把中间件当领域模型。

我还会主动承认当前有些能力是目标设计。完整多 Agent 并行、公平队列、OpenTelemetry、正式 SLO、签名 Release Manifest 和跨区域容灾都不能因为文档画出来就说已上线。当前默认 Provider 也可能关闭，测试主要证明状态、契约和恢复，不证明真实模型质量。把实现、固定演练、目标设计和生产待验证分开，反而能说明我知道架构复杂度应该由数据和故障驱动。

如果要继续简化，我会从不保护当前不变量的层开始。任务很短且没有外部副作用时，可以不用完整 Lease/Fencing；单实例低流量可以用数据库 Dispatcher，不必独立 Kafka；Memory 没有真实复用价值时，只保留 Context Snapshot；Wiki 关系不足时不引入图数据库。反过来，当 Queue Age、重复副作用、撤权窗口、恢复耗时或质量 Bad Case 持续出现，再增加对应机制。这个切换判据比“用了大厂技术栈”更能回答工程判断。

### 二阶追问：为什么一开始不直接用成熟 Agent 框架

成熟框架能快速表达工具和图执行，但 NoteWeave 已有 Workspace 权限、MySQL 状态、Source Snapshot、Artifact Version 和 Research Cell。如果框架 Checkpoint 与业务表都决定终态，会出现双真源。当前只复用工具和执行思想，把业务推进留在控制面；任务分支和补偿复杂度超过现有状态机后再评估编排层。

### 二阶追问：单体为什么还要 Kafka 和 Worker

服务是否单体与工作是否需要跨请求持久化是两回事。分钟级解析、Research 和渲染不应占住 HTTP 线程，Python 生态也适合独立执行。早期可以用数据库任务队列简化，Kafka 的价值要由多消费者、保留重放、积压观察和独立扩缩容证明，不是单体必须标配。
