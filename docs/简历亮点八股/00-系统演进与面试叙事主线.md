# NoteWeave 从 0 到 1：系统演进与面试叙事主线

## 1. 先说明这条时间线的口径

这篇文档按工程问题的因果关系组织项目，不把它冒充成逐日 Git 提交历史。面试时讲的是：如果从一个最小可用的知识助手开始，哪些问题会依次暴露，为什么现有方案无法继续支撑，系统因此引入了什么机制。仓库中的迁移脚本、服务、状态机和测试可以证明最终方案，具体开发日期则以 Git 历史为准。

整条主线只有一句话：NoteWeave 最初要解决“资料很多，但很难持续整理、检索和产出”的问题，后来逐步发现，生成质量不仅取决于模型，还取决于资料是否可靠进入系统、检索是否匹配场景、长任务是否可恢复、证据是否可验证、上下文和记忆是否会污染事实。

## 2. 从一个最小原型讲起

### V0：同步聊天原型先证明需求

最小方案可以只有一个 Web 接口：用户上传文件，后端读取文本，把最近几轮消息和相关片段拼进 Prompt，再调用模型返回答案。它的优点是开发快、链路短、容易验证用户是否真的需要“围绕自己的资料提问和产出”。

这个方案很快会遇到六类问题：大文件解析占住请求线程；文件、业务状态和检索索引无法原子更新；一套 TopK 检索同时服务问答、深读和 Wiki 时效果不稳定；Research 或 PDF 生成需要几分钟甚至更久，进程崩溃后无法恢复；最近 N 条消息会丢主题，直接自动记忆又会放大模型错误；最终答案有引用，也不代表引用真的支持结论。

这些问题决定了后续演进顺序。先建立可靠资料底座，再做场景化检索；任务变长后，引入受控 Agent 执行框架；开放式研究需要比普通产物生成更强的状态和验证模型；最后把会话压缩、长期 Memory 与事实 Evidence 分开治理。

## 3. 六个阶段如何连续演进

| 阶段 | 当时可工作的方案 | 新暴露的问题 | 引入的核心设计 | 主要代价 |
|---|---|---|---|---|
| V0 同步原型 | 单体接口、同步解析、最近 N 条消息 | 请求阻塞、失败难恢复、数据不可审计 | 先保留最短链路验证需求 | 不适合长任务和多存储 |
| V1 资料底座 | MySQL 记录资料，文件存本地或对象存储 | DB 成功与消息发送无法原子提交，重复消费难避免 | MinIO、Transactional Outbox、Kafka、幂等状态机、ES 可重建投影 | 最终一致，需要补偿和观测 |
| V2 场景化 RAG | 一套 Chunk TopK 加 Prompt | QA、Note、Wiki 对“相关”的定义不同 | 三条 Retrieval Plan，共享 Evidence 契约；BM25、向量、RRF、Rerank、受限图读取 | 策略和评测成本增加 |
| V3 产物 Agent | 一个 Prompt 一次生成 | 长任务超时，工具和能力容易越权，失败后全量重做 | Skill、Schema、ExecutionSpec、编译期 DAG、MCP Policy、Verifier/Repair、Waiting/Resume | 灵活性受约束，框架复杂度上升 |
| V4 Deep Research | 自由 ReAct 循环 | 研究漂移、过早收敛、冲突覆盖、引用不支持结论 | Research Intent、Table-as-State、Cell CAS、候选仲裁、双层 Verifier、Checkpoint | 状态对象和验证成本更高 |
| V5 Context 与 Memory | 最近 N 条、自由摘要、自动写记忆 | 上下文断裂、摘要覆盖历史、记忆污染事实、重放不一致 | Message Ledger、Segment、Summary Revision、RunInputSnapshot、Memory Promotion、Evidence Isolation | 存储、隐私与版本治理更复杂 |

### 面试时不要把中间件当作起点

不要说“项目用了 Kafka、Redis、Elasticsearch、MinIO，所以架构很完整”。更有说服力的讲法是：同步解析拖慢接口，因此把命令异步化；DB 和 Kafka 无法共享事务，因此增加 Outbox；资料召回既有精确词也有语义表达，因此组合 BM25 与向量；不同检索分数不可直接比较，因此用 RRF；昂贵任务既要限制到达速率，也要限制同时运行数，因此用 Redis 令牌桶和并发租约。

技术名称应该出现在问题之后。每引入一个组件，都要能回答“不用它会怎样”和“用了它付出什么”。

## 4. V1：资料底座为什么从同步调用演进到事件驱动

### 4.1 文件为什么不直接放 MySQL

候选方案有三种。文件系统实现简单，但多实例共享、备份和对象版本管理麻烦；MySQL BLOB 可以跟业务记录放在一起，但大对象会放大日志、备份和主从复制压力；MinIO 提供 S3 语义、不可变对象和 Hash 校验，更适合原文件及派生文件。当前方案让 MySQL 保存身份、状态和引用，MinIO 保存大对象。

取舍是业务状态和文件不再处于同一个本地事务。系统必须明确 MySQL 是业务真源，并通过补偿处理对象已写但事务失败、数据库成功但后续解析失败等情况。

### 4.2 为什么不是数据库提交后直接发 Kafka

“先提交 DB，再发 Kafka”会在进程崩溃时丢消息；“先发 Kafka，再提交 DB”会让消费者看见尚不存在的业务对象；XA 或分布式事务会提高部署和故障处理复杂度，而且 Kafka、MinIO、ES 仍不能自然组成一个全局事务。

当前方案在同一个 MySQL 事务中写业务记录和 Outbox。Dispatcher 通过 Lease、CAS 和 Claim Token 领取记录，再投递 Kafka。它选择消息至少送达一次，不承诺端到端 Exactly-once，重复由消费端幂等键、唯一约束和终态状态机吸收。

### 4.3 为什么还需要 Elasticsearch

MySQL 适合事务、约束和精确查询，不适合承担全文相关性、向量检索和索引版本切换。Elasticsearch 只保存可重建投影，文档必须带 Workspace、Source、Snapshot 和 Index Version。这样 ES 故障影响检索能力，但不会成为资料事实的唯一来源。

代价是投影存在延迟，系统必须区分“ES 被配置关闭”“ES 暂时故障”“资料尚未投影完成”，并提供重建、回填和质量门禁。

## 5. V2：为什么一条通用 RAG 最终拆成三条链路

### 5.1 通用 Chunk TopK 的优点和上限

一条 Hybrid Search 链路复用度高，参数少，适合早期验证。但 QA 关心能否找到直接回答问题的片段；Note 关心先选中哪份资料，再围绕锚点阅读连续原文；Wiki 关心页面身份、版本、关系和来源回链。只换 Prompt 无法改变候选对象、排序特征和证据预算。

当前方案共享 Scope、Provider、Evidence Bundle、Citation 和 Trace，但保留 QA、Note、Wiki 三种 Retrieval Plan。它不是复制三套基础设施，而是在统一契约上允许不同策略。

### 5.2 为什么 QA 使用 BM25、向量、RRF 和 Rerank

BM25 对专有名词、数字和代码符号稳定，向量召回覆盖同义表达和自然语言改写。直接相加两路原始分数需要持续校准，Learning to Rank 又需要足够训练数据。RRF 只使用名次，能低成本融合异构召回；Cross-Encoder Rerank 只处理融合后的有限候选，把更高计算成本放在更小集合上。

代价是 RRF 忽略原始分差，Rerank 增加延迟和 Provider 依赖。因此系统保留 RRF 原顺序作为降级结果，并把 Strategy Tuple 固化进快照，保证一次运行可复现。

### 5.3 为什么排完 TopK 还要做 Evidence Selection

排序优化的是单个候选相关性，Prompt 需要的是一个证据集合。相邻 Chunk 可能来自同一段资料，如果直接取前 K 个，会挤掉其他来源并浪费 Token。Evidence Selection 还要处理来源覆盖、重复片段、直接支持度和预算，必要时在证据不足时拒答。

## 6. V3：为什么产物生成从一次 Prompt 演进为受控 Agent

### 6.1 自由 Agent 和固定 Workflow 各自擅长什么

自由 Agent 能动态选择工具，适合路径未知的探索任务，但结果和权限边界不稳定；固定 Workflow 易观测、易恢复，却难处理不同产物和可选能力。当前方案选择中间路线：Skill 描述目标、Schema 和能力边界，Compiler 生成冻结的 ExecutionSpec，Graph 在编译期完成环检测和拓扑排序，运行期按拓扑序线性执行。

这不是完整的通用工作流引擎。当前没有运行时 Ready Queue、条件边和节点级并发。选择它是因为现阶段更看重确定性、可审计和恢复，暂时不为未出现的复杂调度需求支付成本。

### 6.2 为什么引入 MCP，但不做开放插件市场

MCP 提供统一工具发现和调用协议，减少每个 Skill 自己适配外部能力的成本。生产只启用受信任的系统 MCP。仓库中的自定义 MCP 注册是默认关闭的内部调试能力，尚无签名、白名单、进程沙箱和网络出口隔离，不能把它描述成用户可自由安装的生产插件平台。

### 6.3 为什么 Verifier 和 Repair 不能省

模型自我反思仍依赖同一份上下文和生成偏差。Verifier 把确定性检查与语义检查分开：Schema、必填章节、Hash、文件大小可以由程序判断，内容覆盖和风格再交给模型。Repair 接收结构化失败项，只重做相关节点；最终输出还要通过全局契约，避免局部修复破坏其他部分。

## 7. V4：为什么 Deep Research 需要独立于普通 Agent 的状态模型

### 7.1 ReAct 能启动探索，但不适合直接作为长期真源

ReAct 的优势是简单、灵活，适合短路径、低风险、失败可接受的探索。开放式研究通常要比较多个实体和字段，持续几十个步骤。只保存对话轨迹会出现目标漂移、重复搜索、来源冲突被最后一次写入覆盖，以及恢复后无法判断哪些结论已经验证。

当前方案把 Research Intent 作为稳定目标，把 Plan 作为可变策略，把 Row、Cell、Evidence 作为结构化状态。每个 Cell 有版本、候选、来源和验证状态，Worker 不能直接覆盖 Canonical 值。

### 7.2 为什么采用候选仲裁而不是 Last Write Wins

Last Write Wins 实现简单，但新结果不等于正确结果；多数投票容易被同一站点的重复转载伪造；Authority-first 适合存在明确权威源的字段，但无法覆盖所有开放问题。当前合并门要求来源身份可审计，并对候选做独立性和支持度判断。冲突无法消解时返回 `VERIFIED_VALUE_CONFLICT`，保留原值，不虚构自动纠正状态。

### 7.3 为什么同时需要 Local 和 Global Verifier

Local Verifier 判断一个 Cell 的候选是否有直接证据、是否存在冲突；Global Verifier 判断整张表是否满足 Intent、关键字段是否缺失、引用是否覆盖报告。局部正确不代表整体任务完成，整体看起来完整也不代表每个结论有证据。

### 7.4 为什么使用 Checkpoint，而不是完整 Event Sourcing

只存最终结果无法恢复，完整事件溯源能重建任意中间状态，但事件 Schema、回放兼容和存储成本更高。当前方案保存结构化 Checkpoint、任务审计和完成回执，大对象放 MinIO，并校验大小和 SHA-256。它获得可恢复性和幂等重放，但不承诺从所有历史事件重建全部状态。

## 8. V5：为什么 Context 和 Memory 必须独立设计

### 8.1 最近 N 条为什么不够

最近 N 条实现最简单，也能保证尾部连续，但主题切换后会带入无关内容，长主题又可能被窗口截断。系统因此保留单调 Message Sequence，用 Segment 表示稳定主题，用版本化 Summary 压缩历史，同时保留连续 Raw Tail。

摘要异步生成时冻结 Segment Version。Promotion 发现版本已变化，就把旧摘要标为 Stale，而不是覆盖新消息。这样摘要生成失败或落后时，可以回退到有界原文，而不会静默丢掉中段历史。

### 8.2 为什么不让模型自动写长期 Memory

自动写入快，但一次幻觉、Prompt Injection 或过时偏好会持续影响后续任务；全部人工确认最安全，却会制造过多审核负担。当前方案让 Answer、Research、Artifact 只提交 Observation 或 Candidate，由 Java Memory Runtime 做类型、Scope、敏感性、重复和冲突门控，再进入审核或受限自动晋升。

### 8.3 为什么 Memory 不能参加 Evidence Rerank

Memory 表示偏好、约束和历史观察，Evidence 表示可引用的资料事实。如果 Memory 进入 Source Recall 或 Citation 排序，模型之前生成的内容可能反过来证明自己，形成闭环污染。两者可以同时进入 Context Compiler，但使用独立预算、标签和信任域。

### 8.4 为什么冻结 RunInputSnapshot

任务开始后，消息、摘要、Memory 和资料都可能变化。如果重试时重新编译上下文，同一个 Run 会得到不同输入。Snapshot 固化 Message Ref、Summary Revision、Memory Revision、Evidence Ref、策略版本和 Hash。隐私删除发生后，系统返回降级回放或不可回放，不用新内容伪装历史输入。

## 9. 从用户功能继续下钻的演进地图

五条技术主线最终要落回用户功能。面试官如果从页面或接口发问，可以先定位到下面这张表，再进入对应详细文档。

| 用户功能 | 最早可行方案 | 随规模暴露的问题 | 当前实现方向 | 面试时主动讲的代价 |
|---|---|---|---|---|
| Workspace 与权限 | 请求带 User ID，查询时加 Workspace ID | 客户端身份可伪造，成员状态变化后旧权限继续生效 | 服务端身份过滤、Workspace Membership、ACL Version、对象归属二次校验 | 每条链路都要传递和校验身份，测试面增大 |
| 资料上传 | 单请求上传到本地盘 | 大文件占线程，多实例文件不共享，失败难恢复 | 分片约束、内容真实性校验、MinIO 对象、MySQL Snapshot、异步 Task | 用户先看到 Pending，需要进度和失败状态 |
| 解析与切块 | 上传请求内直接解析 | 格式耗时不稳，重复请求生成重复 Chunk | Outbox、Kafka Worker、Snapshot + Chunk No 幂等、失败终态 | 存在队列与最终一致性窗口 |
| QA 问答 | BM25 TopK 加 Prompt | 同义表达漏召回，同源 Chunk 挤满上下文 | Scope Filter、BM25 + Vector、RRF、Rerank、Evidence Selection | 延迟和 Provider 成本上升 |
| Note 深读 | 全库 Chunk 排序 | 命中片段却丢失资料和章节语境 | Source Recall、Anchor、Reading Window、两阶段 Rerank | 链路比 QA 多一层，参数要单独评测 |
| Wiki 组织 | 把生成页面当普通文档检索 | 页面版本和来源关系丢失，生成内容可能自证 | 当前版本、文本种子、受限关系读取、Source Backlink | 不是完整 GraphRAG，关系信号能力有限 |
| 流式回答 | HTTP 等待完整文本 | 长回答首字延迟高，断线后只能重跑 | SSE、单调 Event Sequence、Replay-prime-before-live、Redis Realtime Bridge | 需要游标过期、合并和重连语义 |
| 连续对话 | 最近 N 条消息 | 主题切换和长会话导致关键约束丢失 | Message Ledger、Segment、Summary Revision、Raw Tail | 摘要版本和 Stale 治理复杂 |
| 产物生成 | 一次 Prompt 返回 Markdown | 多步骤工具失败后全量重做，输出结构不稳 | Skill、Schema、ExecutionSpec、编译期 DAG、Verifier/Repair | 牺牲自由度，运行时当前不做节点并行 |
| 外部能力 | 每个工具写专用 Client | 工具发现、Schema 和 Trace 重复 | 受信任系统 MCP、Capability Intersection、调用审计 | 不开放任意插件，自定义调试能力需要强边界 |
| Deep Research | ReAct 搜索后直接写报告 | 目标漂移、字段缺证、来源冲突、长任务中断 | Intent、Table-as-State、候选仲裁、双层 Verifier、Checkpoint | 模型调用和状态管理成本高 |
| 长期 Memory | 自动保存模型总结 | 幻觉、注入和过期信息持续污染后续任务 | Candidate、风险门控、Review、Revision、Outcome Feedback | 记忆进入上下文有延迟，用户可能需要审核 |
| 任务重试 | 失败后重新读取当前上下文 | 同一个 Run 重试时输入变化，结果不可解释 | RunInputSnapshot、策略版本、内容 Hash | 引用对象删除后只能降级重放 |
| 删除与隐私 | 数据行加 Deleted 标志 | 摘要、缓存、快照和外部对象仍泄露派生内容 | 派生摘要 Stale/清空、缓存失效、Cleanup Task、Replay 降级 | 历史结果可能无法完整回放 |

### 9.1 Workspace 与权限怎么讲

最早把 `workspace_id` 当查询条件即可验证多空间功能，但客户端传来的用户身份不能成为信任根，ES 索引脏数据也可能绕过单层过滤。当前由服务端身份过滤器确定 Actor，业务层校验 Membership 与对象归属，检索在 ES 下推 Scope 后仍用 MySQL Hydration 二次确认。它增加了重复校验，却把“排序正确”和“绝不越权”分成两个目标。

### 9.2 上传、解析和可检索状态怎么讲

上传成功只表示对象和业务任务已经可靠创建，不表示内容已经可检索。解析固定 Snapshot，切块使用稳定位置身份，投影完成后才把版本标为 Ready。这样状态更多，但可以准确告诉用户是上传失败、解析失败、索引延迟还是检索服务故障。

### 9.3 QA、Note、Wiki 怎么讲

三个入口共享 Conversation、Scope、Evidence 和 Citation，但相关性目标不同。QA 从多资料中找直接支持，Note 围绕少数资料保留连续原文，Wiki 读取版本化知识页并尽量回到原资料。拆链路的判断标准不是页面名称，而是候选单位、排序目标和证据组织是否相同。

### 9.4 流式回答与断线恢复怎么讲

SSE 比 WebSocket 更适合当前单向 Token 和状态事件推送，代理与前端消费也更简单。服务器为事件分配连续序号，重连时先补历史再接 Live，边界事件需要去重和合并。Redis Bridge 不可用时不能返回空流冒充任务结束，要明确失败或回源，因为“暂时取不到事件”和“确实没有事件”语义不同。

### 9.5 Research 与普通 Artifact 为什么分开

两者共享长任务、Outbox、Worker、配额、对象存储和幂等完成，但状态粒度不同。Artifact 的目标和图通常在执行前已知，核心是受控生成与输出验证；Research 的路径和证据缺口动态变化，需要 Cell、候选仲裁、Gap、Wave 和全局完成契约。复用基础设施，不强行复用领域状态机。

### 9.6 删除为什么是跨模块功能

删除一条消息或资料不仅影响一张表，还会影响摘要、Memory Candidate、RunInputSnapshot、引用、ES 投影、MinIO 对象和回放能力。系统以“停止在线可见和召回”为第一目标，外部副作用通过持久 Cleanup 收敛，保留的 Tombstone 只用于最小审计。强行保证删除后历史运行仍可完整重放，会与隐私语义冲突。

## 10. 中间件选择的面试对照表

| 组件或机制 | 它解决的具体问题 | 当时可选方案 | 为什么选择当前方案 | 必须主动说出的代价 |
|---|---|---|---|---|
| MySQL | 业务状态、事务、唯一约束、状态机 | PostgreSQL、文档库 | 团队和项目栈匹配，关系约束适合任务与版本模型 | 横向扩展不是当前重点 |
| Flyway | 版本已演进到 V090 的迁移顺序和可重复建库 | 手工 SQL、ORM 自动建表 | 迁移可审计，测试可从空库验证 | 迁移兼容需要纪律 |
| MinIO | 原文件、快照和产物大对象 | 本地盘、DB BLOB、公有云 S3 | 本地可部署并兼容 S3 语义 | 与 DB 最终一致，需要补偿 |
| Kafka | 解析、投影和 Agent 命令分发 | 同步 RPC、Redis Stream、RabbitMQ | Consumer Group、分区和重放适合异步流水线 | 运维复杂，仍需业务幂等 |
| Transactional Outbox | DB 状态和消息产生的一致性 | 双写、XA、CDC | 不引入分布式事务，失败可恢复 | Polling 扫描 DB，存在投递延迟 |
| Elasticsearch | 全文、向量和可重建检索投影 | MySQL LIKE、独立向量库 | 一套引擎承载 BM25、过滤和向量检索 | 索引版本和重建成本 |
| Redis | 低延迟令牌桶、并发租约、编译缓存、实时桥接 | JVM Map、DB 行锁 | Lua 可原子更新，TTL 支持租约回收 | 故障时昂贵任务 Fail Closed，可用性下降 |
| SSE | 回答和任务事件流式推送 | WebSocket、轮询 | 单向服务端推送足够，协议和代理配置简单 | 双向交互能力有限，需要重连和重放语义 |
| Java Host | 权限、事务、状态机和业务 API | 全 Python 服务 | Spring 事务和类型契约适合业务真源 | 跨语言协议增加维护成本 |
| Python Worker | LLM、检索工具和产物生态 | 全 Java 实现 | AI 工具生态和迭代速度更好 | 需要内部鉴权、Schema、幂等回调 |
| MCP | Skill 调用外部能力的统一接口 | 每个工具写 HTTP Adapter | 工具发现、参数协议和 Trace 统一 | 生产安全边界尚不支持开放插件 |

## 11. 所有功能点都用同一个决策模板

面对任何功能追问，都可以按下面八步组织，不需要从类名开始背：

1. 用户在什么场景遇到了什么问题。
2. 最小方案是什么，它为什么一开始合理。
3. 数据量、时延、正确性或安全边界变化后，最小方案在哪里失效。
4. 至少比较两个候选方案，并承认它们各自的优点。
5. 说明当前约束下的选择依据，不说“某技术更先进”。
6. 讲清数据结构、状态机或算法，不只报中间件名称。
7. 说明失败场景、观测指标和验证方法。
8. 主动给出当前边界，以及什么条件出现时会换方案。

一个可直接套用的回答骨架：

> 最开始我用的是 A，因为它能最快验证 X。任务变成 Y 以后，A 在 Z 场景会失败。我们比较过 B 和 C，B 的优势是……，C 的优势是……。当前项目更受 P 约束，所以选择了 C。实现上最关键的是 D 状态机和 E 不变量。它换来了 F，但代价是 G。我们用 H 测试和 I 指标验证；如果未来出现 J，我会演进到 B 或另一套方案。

## 12. 一次完整面试如何分层讲

### 30 秒版本

NoteWeave 是一个围绕个人和团队资料持续整理、检索、研究和产出的知识工作台。我没有把它做成单次聊天，而是先用 MySQL、MinIO、Outbox、Kafka 和 Elasticsearch 建立可恢复的资料底座，再按 QA、Note、Wiki 拆分检索策略；长产物使用受控 Skill Graph、MCP、配额租约和 Verifier/Repair；开放式研究进一步用 Table-as-State、候选仲裁和双层验证；长会话则通过版本化摘要、不可变输入快照和门控 Memory 保持连续，同时把 Memory 与事实 Evidence 隔离。

### 3 分钟版本

先讲业务起点，再沿着三条因果链展开。第一条是资料如何可靠进入系统：文件进 MinIO，业务状态进 MySQL，Outbox 解决 DB 与 Kafka 双写，ES 只做可重建投影。第二条是模型如何得到正确输入：QA 用混合召回，Note 先选资料再扩原文窗口，Wiki 读取版本化页面和来源回链，三条链路最后统一为 Evidence Bundle。第三条是长任务如何可控：普通产物用 Skill、Schema、ExecutionSpec 和 Verifier，Deep Research 用字段化状态、Cell CAS、候选仲裁和 Checkpoint。最后补充 Context 与 Memory，说明系统冻结每次 Run 的真实输入，并禁止 Memory 进入 Citation 和 Evidence Rerank。

### 继续深挖时的顺序

面试官偏后端，就展开 Outbox、Kafka、幂等、CAS、Lease 和多存储一致性；偏搜索，就展开 BM25、向量、RRF、Rerank、Evidence Selection 和评测；偏 Agent，就展开 Skill Compiler、Capability Policy、Waiting/Resume、Table-as-State 和 Verifier；偏系统设计，就展开真源、投影、版本、故障矩阵、可观测性和容量；偏大模型应用，就展开 Context Compiler、Snapshot、Memory Promotion、Citation Support 和防污染边界。

## 13. 面试中最重要的真实性边界

- 不把内部 Gold Set 说成公开 Benchmark，也不把 6 条手工 fixture 的 100% 说成在线融合链路准确率。
- 不把编译期 DAG 说成运行时并行图调度。当前运行期按拓扑序线性执行。
- 不把内部调试自定义 MCP 说成生产插件市场。它尚无完整沙箱、签名和白名单。
- 不把 Kafka 的投递语义说成业务端到端 Exactly-once。系统采用 At-least-once 加业务幂等。
- 不把 Elasticsearch 说成事实真源。它是可以从 MySQL 和 MinIO 重建的查询投影。
- 不把 Memory 说成资料证据。它只能影响表达、偏好和约束，不能自证事实。
- 不虚构线上用户量、QPS、准确率和压测结论。没有真实数据时，就说明验证使用了哪些契约测试、集成测试、故障注入和确定性样例。

## 14. 用一句话收住整个项目

这个项目真正解决的不是“让模型多调用几个工具”，而是把资料、检索、上下文和长任务都变成有身份、有版本、有状态、有证据、可恢复的工程对象，并且对每一次技术选择说明收益、代价和适用边界。

## 15. 叙事阶段与源码验收点

讲演进故事时，每个阶段至少落到一个可检查的生产入口，避免把 V0 到当前版本讲成抽象架构史。

| 叙事阶段 | 用户功能 | 当前生产入口 | 可以继续追问的实现证据 |
|---|---|---|---|
| 同步聊天原型 | 用户发送消息并获得回答 | `ConversationTurnModule`、`AnswerRunService` | 消息序列、Answer Run 状态迁移、SSE 事件 |
| 资料异步化 | 上传后后台解析并变为可检索 | `UploadService`、`SourceParseService`、`DurableOutboxDispatcher` | 本地事务加 Outbox、重复消费、DLT 与 READY 收口 |
| 场景化 RAG | QA、Note、Wiki 使用不同检索方式 | `QaHybridRetriever`、`NoteRetrievalService`、`WikiEvidenceRetriever` | Passage、Source、Page 三种召回单位和不同 Evidence Budget |
| 长任务 Agent | 创建 Research 或 Artifact 后异步执行与恢复 | `ResearchAgentTaskService`、`ArtifactJobService`、`WorkerTaskCallbackService` | Lease Epoch、Fencing Token、Checkpoint、受控回调 |
| Context 与 Memory | 长对话压缩、运行快照、长期偏好治理 | `RunInputSnapshotService`、`SegmentSummaryPromotionService`、`MemoryCompilerService` | Snapshot 稳定性、Revision、Scope、风险晋升与删除 |
| 生产约束 | 配置错误时拒绝启动，依赖故障时有限降级 | `ProductionConfigurationGuard`、`WorkloadQuotaService`、`RetrievalReleaseGateService` | Fail-closed、发布门禁、默认关闭 Provider 和未验证的 HA 边界 |

这些入口证明当前实现，不证明线上规模。没有真实用户量、生产 SLO、成本账单和灾备演练时，结果只能描述为仓库实现、集成测试或本地运行证据。
