## 0. 脑图主干

```text
资料接入
├─ MySQL：业务真源和状态机
├─ MinIO：原文件与不可变快照
├─ Kafka：解析、索引等异步任务
├─ Elasticsearch：可重建检索投影
└─ 可靠性：Outbox + 幂等 + 重试 + DLQ + 补偿
```

## 0.1 从 0 讲起的演进版主回答

最开始上传接口同步完成保存、解析、切块和索引。它的优点是链路短、结果立即一致，适合小文件原型。文件变大、Embedding 和 ES 写入变慢以后，请求线程长时间占用，任一步失败都只能整条重试，用户也分不清资料已经保存还是完全失败。

第一步是把解析与索引拆到 Worker，但这又带来 DB 与 Kafka 双写：先提交 DB 再发消息可能丢任务，先发消息再提交 DB 可能让 Consumer 看到不存在的业务对象。我们比较过 XA、Kafka Transaction、CDC 和 Polling Outbox。XA 与跨存储边界不匹配，Kafka Transaction 不能覆盖任意 MySQL 和 MinIO，CDC 吞吐和延迟更好但平台治理成本高。当前规模选择同事务 Outbox 加 Polling Dispatcher，未来扫描成为瓶颈再切 CDC。

Outbox 只能保证命令不会静默丢失，Kafka 仍是 At-least-once。Consumer 因此使用稳定幂等键、唯一约束和状态机，Dispatcher 使用 Lease、CAS 和 Claim Token，防止旧 Owner 在租约过期后确认新任务。MySQL 是业务真源，MinIO 保存不可变大对象，ES 是可重建投影；跨存储通过失败终态、Post-commit Cleanup、补偿和对账最终收敛。

这个方案牺牲了即时可检索和强事务，增加了 Outbox 扫描、重试、死信和观测成本，换来接口解耦、故障可恢复和水平扩展。面试里我不会说端到端 Exactly-once，而会说明重复在哪些边界出现、由哪个幂等机制吸收。

## 1. 30 秒回答

资料链路跨 MySQL、MinIO、Kafka 和 Elasticsearch，我没有用同步接口串行调用，而是把上传、解析和索引拆成事件驱动流水线。MySQL 保存业务状态，MinIO 保存原文件和快照，Kafka 解耦解析与索引，Elasticsearch 作为可重建投影。数据库事务里同时写业务数据和 Transactional Outbox，再由 Dispatcher 可靠投递；消费端通过稳定幂等键、状态机、退避重试和死信重驱保证至少一次消息下的正确处理。当前支持 128 MB 单文件接入，接口无需同步等待解析完成。

## 2. 核心追问

### 为什么不在上传接口里同步解析？

解析耗时受文件大小、格式和外部模型影响，会拉长请求、占用 Web 线程，也无法平滑重试。上传接口只完成文件固化和任务创建，解析、切片、向量化、索引通过异步任务推进，用户读取明确的处理中、完成或失败状态。

### DB 写成功但 Kafka 发送失败怎么办？

业务数据和 Outbox 在同一 MySQL 事务提交。Dispatcher 后续扫描 READY 记录并发送 Kafka，发送失败按退避策略重试，超过上限进入 Dead Letter。这样不存在业务已提交但消息永久丢失的窗口。

### Kafka 发成功但 Outbox 状态没更新怎么办？

消息可能重复投递，所以消费端必须幂等。Outbox 恢复后再次发送相同 Message ID，Consumer 根据 Task ID、Snapshot ID、Projection Version 等稳定键识别重复，返回已有结果或跳过。

### 为什么不用 Kafka Exactly Once？

Kafka EOS 主要覆盖 Kafka 内部读写事务，无法自动覆盖 MySQL、MinIO 和 Elasticsearch。跨系统仍需要业务幂等和补偿，因此采用 At-least-once Delivery 加 Idempotent Consumer 更符合边界。

### MySQL、MinIO、ES 谁是真源？

业务状态以 MySQL 为真源，原始二进制和不可变文件以 MinIO 对象为真源，Elasticsearch 是可重建检索投影。不能笼统说只有一个真源，要按数据类型定义权威归属。

## 3. 高可靠、高可用、高并发如何区分

### 高可靠

重点是不丢任务、不重复产生副作用、失败后能恢复，对应 Outbox、幂等、重试、DLQ、补偿和状态审计。

### 高可用

重点是单实例故障时系统还能继续，对应无状态 Host 多实例、Dispatcher Lease/CAS、Kafka Consumer Group、Worker 接管和可重建投影。

### 高并发

重点是吞吐和资源控制，对应请求快速落库、异步削峰、批量 Claim、Kafka 分区、Consumer 并行度和下游限流。没有压测数据时不声称具体 QPS。

## 4. 幂等设计

### 幂等键怎么选？

不要用随机请求时间。上传分片使用 Upload ID + Chunk Index，解析使用 Snapshot ID + Parser Version，索引投影使用 Snapshot ID + Index Version，消息使用 Outbox/Command ID。

### 幂等是不是查一下有没有就行？

并发下“先查再写”仍会重复，需要数据库唯一约束、CAS 或条件更新。外部副作用还要保存结果锚点，使重复请求能够返回原结果。

## 5. 重试、死信和补偿

### 什么错误应该重试？

网络超时、临时 Provider 失败、下游过载等可恢复错误；格式不支持、权限失败、Schema 不兼容等永久错误不应盲目重试。重试需要指数退避、抖动和上限。

### DLQ 有什么用？

DLQ 隔离持续失败消息，避免阻塞正常消费。进入 DLQ 后保留原消息、尝试次数、最后错误和业务身份，修复原因后通过 Redrive 回到 READY，而不是人工拼一条新消息。

### 补偿和重试有什么区别？

重试是重复同一步；补偿是根据全局状态修复缺失结果，例如文件已存在但解析任务未创建、MySQL 显示完成但 ES 投影缺失。补偿扫描必须幂等。

### 为什么不能只说“系统重试三次”？

NoteWeave 至少有三个不同失败域，重试对象和完成条件并不相同：

| 失败域 | 当前链路 | 它保护什么 | 结束条件 |
|---|---|---|---|
| Host 投递 | MySQL Outbox 到 Kafka | 业务状态已提交后，投递意图不能静默丢失 | Broker ACK；失败最多 5 个 Outbox Attempt 后 Dead Letter |
| Broker 消费 | Kafka 到 Java、Research Worker 或 Artifact Worker 的业务处理 | Broker 已有消息，但业务处理或回调确认可能短暂失败 | Java Consumer 有限重试后进入 `.DLT`；Artifact Worker 在协议确认后手动提交 Offset，无效命令先持久化到专用 DLQ |
| Worker 回写 | Artifact Worker 到 Java Callback | Worker 已经执行，业务终态尚未由 Host 仲裁 | Progress/Heartbeat 续租；Complete/Fail 以幂等键和 Delivery 所有权提交并确认 Outbox |

这三层不能机械相乘成“最多调用多少次”。当前 Artifact 在 Broker ACK 后仍保持 70 分钟 Delivery Lease，Worker 完成 Callback 后才提交 Offset，这是迁移前协议。推荐方案在 Consumer 幂等登记 Durable Execution 后提交 Offset，随后由 Scheduler、Active Permit、Execution Lease 和 Fencing 管理长任务。两种方案都必须限制端到端 Retry Budget，包括昂贵副作用是否已经发生、剩余 Deadline、当前 Owner 和错误是否可恢复；新方案额外避免慢任务阻塞 Kafka 分区。

## 6. 顺序与并发

### 如何保证同一资料的事件顺序？

Kafka Message Key 使用稳定业务 ID，让同一资料进入同一分区；消费端仍通过状态机和版本检查防止旧事件覆盖新状态。仅依赖 Kafka 顺序不够，因为重试和跨 Topic 仍可能改变到达顺序。

### Consumer 越多越好吗？

有效并行度受分区数和下游容量限制。Consumer 多于分区不会提高吞吐，下游 ES、MinIO、数据库连接池或 Embedding Provider 可能先成为瓶颈，需要压测后调节批次和并发。

## 7. 故障场景

- MinIO 上传成功、DB 提交失败：对象暂时孤儿化，由生命周期或补偿任务清理，不能把未提交对象暴露为资料。
- 解析完成、索引失败：Snapshot 保持解析完成但投影未就绪，索引任务重试或重建。
- Dispatcher 宕机：Lease 到期后其他实例重新 Claim。
- Consumer 处理成功、Offset 未提交：消息重放，幂等键阻止重复副作用。
- ES 索引损坏：从 MySQL 元数据和 MinIO 快照重新投影。

## 8. 为什么选 Polling Outbox

当前规模下 Polling Outbox 易实现、可观测、无需引入 Kafka Connect 与 Debezium。Dispatcher 使用批量 Claim、数据库 Lease 和合理轮询降低开销。只有 Outbox 吞吐成为实测瓶颈时，才考虑 CDC Outbox。

## 9. 可观测性

关注 Ready/Retry/Dead Letter 数量、最老 Ready 消息年龄、投递与消费延迟、重复消费次数、解析失败率、Projection Lag、Redrive 成功率、MinIO 和 ES 错误率。只看 Kafka Lag 不能判断业务是否一致。

## 10. 一句话收尾

这条链路的核心不是“用了 Kafka”，而是明确每类数据的真源，并用 Outbox、幂等状态机和补偿把跨存储的失败窗口变成可观察、可恢复的最终一致过程。

## 11. 功能背后的中间件八股串讲

### 11.1 Kafka 为什么吞吐高

结合资料解析功能回答：Kafka 将同一 Partition 的消息顺序追加到日志，顺序写比随机写更适合磁盘；Producer 可以批量发送并压缩；Broker 使用 Page Cache，数据传输可以利用零拷贝路径；Partition 又提供横向并行度。项目选择 Kafka，不只是为了“异步”，还因为解析、索引和 Research Command 都是可分区、可积压、可重放的任务流。

### 11.2 Partition、Consumer Group 与并发度

一个 Partition 在同一 Consumer Group 内同一时刻只由一个 Consumer 消费，所以有效消费并行度上限约等于 Partition 数。增加 Worker 而不增加 Partition 不会提高并行度。Partition 太多又会增加 Broker 文件句柄、元数据和 Rebalance 成本。

项目使用稳定业务 ID 作为 Key，使同一 Snapshot 的事件落到同一 Partition，获得分区内顺序。不同 Snapshot 可以并行处理。即便如此，Consumer 仍要校验 Version，因为跨 Topic、重试和补偿不能依赖全局顺序。

### 11.3 Producer 的 acks 和幂等

`acks=0` 延迟低但可能丢消息，`acks=1` 只等 Leader，Leader 未同步就故障仍可能丢，`acks=all` 等待 ISR 条件，可靠性更高。Kafka 幂等 Producer 能避免网络重试造成同一 Producer Session 内的重复，但不能替代跨 MySQL 和业务副作用的幂等。

项目真正的业务边界是：MySQL Outbox 保证消息意图产生，Kafka Producer 配置保证 Broker 可靠接收，Consumer 幂等保证重复消息不产生重复业务结果。

### 11.4 Offset 什么时候提交

先提交 Offset 再处理，Consumer 崩溃会丢业务；处理完再提交，崩溃可能重复处理。项目选择后者，也就是 At-least-once。正确顺序是业务结果持久化成功后再确认消费，重复由唯一键和状态机吸收。

### 11.5 Rebalance 为什么危险

Consumer 加入、离开或订阅变化会触发 Partition 重新分配。长耗时解析如果阻塞 Poll，可能被认为失活，任务尚未完成就发生 Rebalance。解决方向包括把长任务和 Poll 解耦、合理设置 Poll/Session 参数、暂停 Partition、使用任务表和 Lease 承接长执行。不能靠无限调大超时掩盖问题。

### 11.6 Transactional Outbox 的原子性来自哪里

Outbox 不是 Kafka 事务。它利用 MySQL 本地事务保证“业务状态和待发送消息”同时提交或同时回滚。真正发送发生在事务之后，所以会重复但不会漏。其核心取舍是把无法实现的跨系统原子提交，转换成数据库内原子记录加异步重试。

### 11.7 Polling Outbox 如何避免多实例重复 Claim

Dispatcher 不能先 Select 再无条件 Update。应该使用条件更新、`SELECT ... FOR UPDATE SKIP LOCKED` 或 Lease/CAS。项目的共享 Dispatcher 用 Lease Owner、Lease Until 和条件更新领取记录。即使极端情况下重复发送，Consumer 幂等仍是最后防线。

### 11.8 指数退避为什么要加 Jitter

固定间隔会让大量失败消息同时重试，形成惊群。常见退避：

```text
delay = min(max_delay, base × 2^attempt) + random(0, jitter)
```

指数部分给下游恢复时间，Jitter 打散重试。永久错误不应进入长重试，否则只会积压和浪费资源。

### 11.9 幂等、去重和 Exactly-once 的区别

去重是识别重复输入，幂等是重复执行结果不变，Exactly-once 是端到端可观察副作用只发生一次。项目采用稳定 Message ID 去重、唯一约束和状态机实现幂等，不声称跨 MySQL、MinIO、ES 的严格 Exactly-once。

### 11.10 最终一致性的一致性窗口

用户上传完成后，MySQL 已有 Source，但 ES 可能尚未投影。这段时间就是一致性窗口。系统必须暴露 `PENDING/PARSING/INDEXING/READY/FAILED`，让用户知道资料何时可检索。最终一致不等于“迟早会好”，还需要重试上限、DLQ、补偿和对账证明系统能收敛。

### 11.11 Redis/Kafka/MySQL 在这里分别解决什么

MySQL 负责真源、事务和状态约束；Kafka 负责异步分发、削峰和可重放；Redis 在另一个亮点里负责短周期配额和并发租约。不能用 Redis List 替代可靠业务真源，也不能用 Kafka 消息状态替代 MySQL 任务状态。

## 12. 源码级可靠性追问

### 面试官问：Outbox 有行锁和 Lease，为什么还需要 Claim Token？

Lease 过期后新 Dispatcher 可以接管，但旧 Dispatcher 可能在暂停恢复后继续发送确认。项目要求 ACK 同时匹配 Outbox ID、Owner 和本次 Claim Token，旧投递不能确认新 Claim。这是 Fencing 思想在消息发布确认上的落点。

只写 `where id=?` 会出现 ABA 类问题：记录看起来还是同一个 ID，但执行权已经换了一代。

### 面试官问：Consumer 遇到错误是不是都不提交 Offset？

不是。消息不可解析或缺失关键身份时不能按成功 ACK；业务目标已删除、缺失等永久错误要先落 Failed/Cancelled 终态，再确认消息；已经完成的重复消息直接幂等确认。三类错误分别对应传输失败、业务失败和重复输入。

任务开始后还会复查 Source 状态，并发删除发生后转 Cancelled，避免旧任务继续投影。

### 面试官问：Redis 缓存挂了为什么不能返回空列表？

空列表是合法业务结果，Redis 异常是基础设施降级，两者语义不同。资料目录缓存带 Catalog Version 和 Schema Version，不匹配或 Redis 故障时回退 MySQL。变更通过提升 Catalog Version 生成新 Key，旧快照自然过期，避免复杂的逐 Key 精确删除。

这里可以引出 Cache Aside、Versioned Cache Key、TTL Jitter 和缓存一致性。缓存可以丢，业务真源不能被缓存异常替代。

### 面试官问：为什么删除外部文件必须 Post-commit？

如果数据库事务尚未提交就删除 MinIO 或 ES，事务回滚后数据库仍引用已消失资源。项目只在删除事务提交后发布 Cleanup Event，再异步清理外部投影和无人引用对象。清理失败进入重试任务，在线查询先依据数据库状态屏蔽已删除资料。

这属于事务后事件和补偿设计，不是跨 MySQL、MinIO、ES 的分布式事务。

### 面试官问：上传时只限制扩展名够吗？

不够。项目同时检查扩展名、MIME、处理类型和实际 UTF-8 文本，拒绝伪装成 Markdown 的二进制或编码载荷。对象 Key 和下载路径还做包含校验，避免 Bucket Escape 与 Path Traversal。

### 面试官问：ES 关闭和 ES 故障为什么要区分？

显式关闭是可预期配置，解析完成后可以标记 Local-only Parsed；运行中故障是降级事件，必须向上暴露，不能返回空命中。同步失败、消费耗尽和 DLQ 最终走统一 Terminal Finalizer，保证 Task、Snapshot 和 Projection 状态一起收口。

## 13. 4 到 5 分钟标准主回答

资料底座负责把用户上传的文件变成可以被 QA、Note、Wiki 和 Research 使用的资料。它横跨上传接口、MySQL、MinIO、Kafka、解析 Worker 和 Elasticsearch。最容易出问题的地方不是文件能不能解析，而是一次操作跨越多个不能参加同一事务的系统：数据库可能成功、消息可能失败，对象已经存在、索引还没完成，或者删除事务回滚、外部文件却提前被清理。

我的第一层设计是明确数据所有权。MySQL 保存 Source、Snapshot、Task、Outbox 和 Projection 状态，是业务状态真源；MinIO 保存原文件和不可变内容快照，是大对象真源；Elasticsearch 只是可以重建的检索投影。接口返回的 PENDING、PARSING、INDEXING、READY、FAILED 和 CANCELLED 都来自业务状态，而不是临时判断某个中间件是否有数据。

上传接口只做必要工作：验证 Workspace 权限、扩展名、MIME 和 UTF-8 文本，计算稳定身份，把对象写入受控 Key，然后在 MySQL 事务中创建 Source、Snapshot、Parse Task 和 Outbox。接口不等待解析和索引，所以大文件不会长期占用 HTTP 线程。

数据库和 Kafka 之间使用 Transactional Outbox。业务状态与 Outbox 行在同一个 MySQL 事务提交，Dispatcher 再异步 Claim READY 记录并发布 Kafka。这样数据库提交成功但 Kafka 暂时不可用时，消息仍在 Outbox 中重试。Kafka 已发送但 Dispatcher 在更新状态前崩溃时，消息可能重复，但不会永久丢失。

多实例 Dispatcher 用短事务 Claim。领取时记录 Owner、Lease 和 Claim Token，发布确认必须同时匹配这三个身份。旧实例发生 Stop-the-world GC 或网络暂停，Lease 过期后由新实例接管；旧实例恢复时，它持有的旧 Token 不能确认新 Claim。这比只用 `select for update skip locked` 更完整，因为数据库锁只覆盖 Claim 事务，不能覆盖外部 Kafka 调用。

Kafka 采用 At-least-once 消费，Consumer 必须幂等。消息先校验结构和业务身份，再按 Task 状态决定是否执行。已完成任务收到重复消息直接 ACK；资料已删除或目标不存在时落业务 Cancelled/Failed 终态；消息本身不可解析时不能伪装成成功。处理完成后再提交 Offset，避免业务尚未落库就丢失消息。

重试也分类型。网络超时、Provider 限流和暂时不可用采用指数退避加 Jitter；格式不支持、权限错误和目标已删除属于永久错误，直接进入终态；超过上限进入 Dead Letter，保留原业务身份和失败分类。Redrive 复用原 Outbox ID 和幂等键，不复制成一条身份全新的消息。

Elasticsearch 投影使用稳定 Document ID 和版本化索引。新 Snapshot 解析完成后写 Chunk，数量校验通过才标记 Projection Ready。删除资料先提交数据库状态，再通过 Post-commit Cleanup 清理 ES 和无人引用对象。即使外部清理暂时失败，在线检索也根据 MySQL 当前状态做归属校验，不会继续采用已删除资料。

高并发来自接口异步化、Kafka Partition、Consumer Group 和批量投影；高可靠来自 Outbox、幂等、重试、死信和对账；高可用来自多实例 Dispatcher、Worker 水平扩容和可恢复状态。它们不是同一个概念。系统没有承诺跨 MySQL、MinIO 和 ES 的强一致事务，而是通过明确状态、一致性窗口和补偿让系统最终收敛。

这套方案的代价是状态机、Outbox 表、对账任务和可观测性都更复杂。文件很小、解析极快、失败可以人工重试时，同步处理更简单；当前项目需要后续多条 AI 链路共享资料，也需要删除、重建和失败恢复，所以事件驱动方案更合适。

## 14. 长回答后的 Trade-off 追问

### 追问：为什么选 Polling Outbox，不用 CDC？

Polling Outbox 只依赖数据库表和定时调度，容易控制 Claim、优先级和 Redrive，适合当前规模。缺点是轮询增加数据库查询，并存在一个 Poll Interval 的延迟。CDC 读取 Binlog，延迟低、对业务查询压力小，但需要 Debezium 等额外基础设施，还要处理 Schema 演进和运维。当前项目优先降低部署复杂度，因此使用 Polling。

### 追问：为什么不用 Kafka Transaction 同时提交数据库？

Kafka Transaction 可以保证 Kafka 内部多个写入和 Offset 的原子性，不能把普通 MySQL 业务事务自动加入同一个原子提交。XA 或两阶段提交会增加协调、阻塞和故障恢复复杂度。Outbox 接受重复投递，用本地事务保证业务与发送意图不分离，更适合跨存储链路。

### 追问：为什么不把文件直接存 MySQL？

小文本可以存数据库，但大文件会放大 Buffer Pool、备份、复制和事务日志压力。MinIO 更适合流式上传、大对象和生命周期管理。代价是数据库与对象存储之间没有原子事务，因此要用不可变 Key、Hash、状态引用和孤儿对象清理。

### 追问：Exactly-once 能不能彻底解决重复？

端到端链路包含数据库、Kafka、Worker、MinIO 和 ES，单个中间件的 Exactly-once 不能覆盖全部副作用。项目采用 At-least-once Delivery 加业务幂等，目标是“重复输入不会产生重复业务结果”，而不是声称网络和所有存储只执行一次。

## 15. 面试官八维度母题长回答

### 15.1 业务抽象：为什么核心对象不是“文件”，而是 Source、Snapshot、Task 和 Projection？

如果把这个模块只抽象成文件上传，后续解析、切片、Embedding、索引、删除和重建都会挤进一个 File 状态里，最终既说不清用户上传的逻辑资料，也说不清某次解析产物。我的拆分依据是身份、生命周期和可变性。Source 表示 Workspace 中用户可见的逻辑资料，负责标题、归属、删除和当前版本指针；Snapshot 表示某一时刻不可变的内容版本，绑定对象 Key、内容 Hash 和解析版本；Task 表示一次可以失败、重试、接管的过程；Projection 表示从 Snapshot 派生、允许重建的检索视图。这样“资料还存在但新版本正在索引”“旧版本可读但新投影失败”“用户删除逻辑资料但外部对象尚待清理”都能被准确表达。

这套抽象直接决定接口语义。上传成功只表示 Source、Snapshot 和后续处理意图已经可靠建立，不表示资料已经可检索；查询状态读 MySQL 中的业务状态，不通过探测 Kafka 或 ES 临时拼出结论。PENDING、PARSING、INDEXING、READY、FAILED 和 CANCELLED 是对用户可解释的生命周期，底层某次消息重复或者 Worker 换实例不会改变业务身份。新版本也不会原地覆盖旧 Snapshot，而是创建新 Snapshot，只有投影满足完整性条件后才推进 Source 的可用指针，避免读者看到半成品。

面试官继续追问为什么不做一张大表，我会回答：一张表在原型期更快，但会把逻辑身份、内容版本、执行尝试和派生结果的基数混在一起，重试可能错误地创建新资料，删除也无法判断该清理哪个对象。当前拆分的代价是表和状态更多，需要跨对象不变量与对账任务；收益是每层都有稳定幂等键和责任边界。若未来只有小文本、无版本、无异步解析，退回同步单表更经济。这里的业务抽象不是为了套 DDD 名词，而是为了让失败恢复、版本切换和用户承诺有可落地的语义。

### 15.2 数据与一致性：跨 MySQL、Kafka、MinIO 和 ES 如何收敛？

我不会说这条链路实现了分布式强一致。它实际采用的是“局部原子性、全局最终收敛”。MySQL 对 Source、Snapshot、Task、Outbox 和投影状态提供本地事务；MinIO 保存不可变大对象；ES 保存可重建投影。上传时先将对象写到受控且不可变的 Key，再在一个 MySQL 事务里建立 Snapshot、Task 和 Outbox。若对象成功而数据库回滚，会留下不可见的孤儿对象，由生命周期或对账任务清理；若数据库提交成功，发送意图一定存在于 Outbox，Kafka 暂时不可用只会扩大延迟，不会让任务静默消失。

Dispatcher 对 READY 行做短事务 Claim，记录 Owner、Lease 和 Claim Token，外部发布不占数据库锁。发布成功但 ACK 前崩溃时可能再次发送，所以 Consumer 按 Snapshot ID、Task Type、Parser Version 或 Projection Version 组成稳定幂等身份，并用唯一约束、条件更新和终态检查吸收重复。业务结果持久化之后才确认消费。ES 使用稳定 Document ID 和版本条件，旧事件即使晚到也不能覆盖新 Snapshot。索引数量和版本校验通过后，Projection 才能 Ready。删除则先提交 MySQL 中的不可见状态，再触发 Post-commit Cleanup，在线读取仍做 Source 归属和状态校验。

三层追问的关键是承认窗口。Outbox 解决的是“业务已提交但消息意图丢失”，不解决 Kafka 重复；幂等解决重复副作用，不保证物理调用只发生一次；补偿与对账解决跨存储长期漂移，不把暂时不一致伪装成原子事务。XA 能缩小部分提交窗口，但会把异构系统耦合进协调协议，MinIO 和 ES 也未必适配。Kafka Transaction 主要覆盖 Kafka 内部读写，不能自动纳入普通 MySQL 事务。因此当前方案选择可观察的最终一致，代价是状态机、死信和修复工具，边界是必须用最大消息年龄、投影滞后和对账差异证明它确实会收敛。

### 15.3 并发与容量：Kafka 分区数、Worker 并发和下游容量怎么一起算？

容量设计不能只说“Kafka 吞吐高”。我会先拆成入口速率、在途量、服务时间和下游配额。上传接口异步化只缩短 HTTP 占用，并没有消灭工作量。按 Little 定律，在途任务约等于到达速率乘平均处理时长；如果每分钟进入 120 个任务、平均解析 2 分钟，就会稳定存在约 240 个在途任务，Worker 和下游没有同等服务能力时，积压一定增长。首先要测不同文件大小和格式的解析时长分布，再确定 Consumer 并发、批量大小、连接池和资源限额。

Kafka 的同一 Consumer Group 内，一个 Partition 同时只交给一个 Consumer，所以有效并行上限先受 Partition 数约束；但分区不是越多越好，过多会增加 Broker 元数据、文件句柄和 Rebalance 成本。同一 Snapshot 用稳定 Key 保持分区内顺序，不同 Snapshot 才并行。Consumer 并发还要受 MySQL 连接池、MinIO 带宽、ES Bulk Queue、Embedding Provider 限流和进程内存约束。若 Hikari 最大连接数是 20，就不能把几十个 Worker 线程都设计成同时持有数据库连接并期待线性增长。

背压应在队列年龄和下游饱和前触发。入口可以限制单文件 128 MB、Workspace 并发和批量数量；Worker 对外部 Provider 使用超时、有限重试和熔断式暂停；ES 写入按批量和错误率调节，不让无限本地队列掩盖积压。重点指标是最老 READY 年龄、Kafka Lag、任务处理时长的 P95/P99、各阶段吞吐和下游拒绝率。当前配置值只是起始假设，不是容量证明。真正的容量结论必须来自分层压测，并注明文件分布、机器配置、分区数、下游配额和可接受积压恢复时间。

### 15.4 安全：上传一份资料会穿过哪些信任边界？

第一层是租户与对象权限。请求进入时必须验证登录身份、Workspace Membership、资源归属和所需权限，不能只相信前端传来的 Workspace ID。后续异步消息也携带稳定业务身份，Worker 处理前重新读取当前 Source 状态，防止用户在排队期间撤权或删除资料。ES 命中不能直接返回，还要回到当前 Workspace 和 Source 可见性做归属校验，因为检索投影可能有一致性延迟。

第二层是内容与存储边界。只检查扩展名不够，还要检查 MIME、允许的处理类型、实际编码和内容大小，拒绝伪装成 Markdown 的二进制或异常载荷。对象 Key 由服务端生成并做规范化，下载和清理路径验证 Bucket 与前缀，避免 Path Traversal、Bucket Escape 和越权引用。解析器面对不可信内容时要有超时、大小和资源限制，文档中的指令只是数据，不能提升为系统指令或长期 Memory。

第三层是服务间身份。Java Host、Worker 和内部回调使用面向 Audience 的独立 Token，比较采用常量时间；生产配置不能继续使用默认弱密钥、明文外部链路或共享万能 Token。第四层是派生数据生命周期。删除不是只删一行，需要让在线读取立即不可见，再异步清理 MinIO、ES、缓存和派生 Chunk，并保留最少的 Tombstone 或审计身份。当前边界是应用层控制，并不等于已经拥有恶意文件沙箱、DLP、病毒扫描和完整密钥轮换平台。若业务允许 Office、PDF 或外部解析器，应把隔离解析、扫描、资源配额和供应链安全列为正式演进项。

项目入口可以具体到 `UploadSecurityPolicy` 和 `UploadService`：前者约束文件类型、大小与上传声明，后者只有在分片与完成条件满足后才创建 Source 和解析任务。解析、投影和删除阶段继续携带 Workspace、Source 与 Snapshot 身份，`SourceDeletionCleanupListener` 把外部清理变成持久任务。测试使用 `UploadSecurityPolicyTest` 和 `SourceDeletionCleanupListenerTest` 覆盖入口拒绝、重复清理与失败终态。这样回答安全题时，能从一次上传的实际方法一直讲到删除收敛，而不是只罗列 MIME、SSRF 和 ACL。

### 15.5 可观测性：资料搜不到时，如何定位卡在哪一段？

我会从同一个业务身份出发，而不是分别翻四套中间件日志。上传时生成 Source ID、Snapshot ID、Task ID 和 Outbox ID，结构化日志和指标保留这些关联字段；消息侧再带 Message ID、Attempt、Partition 和 Consumer Group。诊断顺序是先查 MySQL 中业务状态与版本，再看 Outbox 是否产生、是否被 Claim、是否发布，随后看 Kafka 消费、解析结果、投影版本和在线可见性。这样可以区分“发送意图没产生”“消息积压”“解析永久失败”“ES 写入失败”“投影已好但 ACL 拦截”等不同问题。

指标需要覆盖流量、延迟、错误和饱和度。Outbox 看 READY、RETRY、DEAD 数量和最老消息年龄；Kafka 看 Lag、消费速率、Rebalance 和重复消费；解析看格式分布、处理耗时、失败分类和重试放大率；投影看 Projection Lag、文档数差异、Bulk 拒绝和重建进度；依赖看连接池使用率、MinIO 与 ES 错误率。只报警 Kafka Lag 不够，因为 Consumer 可能已经消费但投影不完整，反过来短时 Lag 也可能在正常恢复预算内。

面试官问 SLO 时，我会先给定义方式而不捏造数字。例如“上传请求持久化成功率”“从上传提交到可检索的 P95 时间”“删除提交到所有在线读取不可见的时间”“死信在值班预算内被处置的比例”。告警应结合错误预算和持续窗口，避免一次抖动就通知。一次事故的证据链应能回答首个失败时间、受影响 Workspace、失败阶段、重试是否有效、积压多久清空。当前已有 Micrometer 和结构化状态，已经能按 Outbox、Source、Projection 和 Cleanup 阶段定位问题；任务规模增长后，再按跨进程关联需求细化观测链路。

### 15.6 成本：事件驱动为什么不是“加了 Kafka 就更便宜”？

事件驱动主要购买的是解耦、削峰、重放和恢复能力，不天然降低成本。成本至少包括对象存储的原文件与多版本 Snapshot、Kafka 的副本与保留、MySQL 的 Outbox 和状态历史、ES 的索引与副本、Embedding 调用、失败重试，以及运维这些组件的人力。尤其要防重试放大：一次下游故障若让解析、Embedding 和索引整条重做，模型与计算成本会按尝试次数增长，所以稳定的阶段结果、错误分类和局部重试既是可靠性设计，也是成本控制。

控制策略应对应成本来源。不可变 Snapshot 可以按引用和保留策略清理，Kafka 保留期服务于可重放窗口而不是无限增长，Outbox 已完成记录归档，ES Mapping 和副本数按查询与恢复目标选择。解析结果和 Embedding 可用内容 Hash 加模型版本去重，索引失败只重投影，不重复解析。永久错误尽早进入终态，避免指数退避只是更慢地浪费资源。Redrive 前先确认根因已修复，并限制批次，防止恢复动作再次打爆下游。

方案比较也要纳入团队成本。低流量、小文件、允许人工重试时，同步处理或数据库任务表可能比 Kafka 更便宜；当任务需要多消费者、峰谷明显、要求重放和独立扩展时，Kafka 的固定运维成本才更值得。当前 Docker Compose 主要用于组件联调，面试中我会用“单位成功 Snapshot 的存储、消息、解析和索引成本”做核算口径，再根据真实队列年龄和资源消耗决定是否调整部署形态。

当前代码中的成本控制点包括 `DocumentChunker` 固定 Chunk 策略、Embedding Batch 32、`DurableOutboxDispatcher` 最多 5 次 Attempt，以及 `SourceRetrievalProjectionService` 在维度或数量不匹配时直接失败。失败不会无界调用 Provider，但仓库还没有按 Source 记录对象存储、Embedding、ES 写放大与人工 Redrive 的统一账单。因此可以解释成本模型和保护机制，不能声称已经得到生产单位成本。

### 15.7 测试证据：如何证明故障窗口真的被覆盖，而不只是画了架构图？

证据要按不变量和失败窗口组织。对 Outbox，核心不变量是业务提交后一定存在发送意图，测试要覆盖事务回滚、发布前崩溃、发布成功但 ACK 前崩溃、Lease 过期后旧 Owner 恢复、重复 Claim 和 Claim Token 不匹配。对 Consumer，要覆盖处理成功但 Offset 未提交后的重放、相同消息重复、旧版本晚到、永久错误与可重试错误分流。对投影，要覆盖部分 Bulk 成功、数量不一致、ES 暂时不可用、索引重建和删除并发。

测试层次不能混用。单元测试验证状态机、退避和幂等键；数据库集成测试用真实 MySQL 验证唯一约束、条件更新与锁行为；消息契约测试验证 Schema 与兼容性；基础设施集成测试用 Kafka、Redis、MinIO 和 ES 验证边界；端到端测试证明上传最终可检索以及删除后不可见。故障注入在精确时点终止进程或模拟超时，再检查恢复后没有静默丢失、没有重复业务副作用、状态最终收敛。对账测试则故意制造 MySQL 与 ES 差异，验证能够发现并修复。

证据也有边界。内部 Fixture 通过只能证明这些样本和故障点，不等于线上所有格式、峰值容量和数据分布都被覆盖；一次成功压测也不等于长期稳定。面试时应能给出测试名称、注入位置、预期不变量和实际观察，而不是只说“我们做过单测”。尚未执行过的测试不能表述为本轮已验证，缺少真实容量或恢复时长数据时，应把它列为后续验证项。

仓库中的对应证据可以直接点名：`DurableOutboxDispatcherTest` 验证 Claim、续租、确认和耗尽 Dead Letter；`KafkaRetrievalProjectionFailureRecoveryTest` 验证投影消费失败后的恢复；`SourceRetrievalProjectionServiceCompensationTest` 验证 ES 写入后业务 Finalize 失败时取消 Current；`RetrievalLiveElasticsearchIntegrationTest` 验证真实 ES Mapping 与 Alias。四类测试分别守住消息所有权、失败恢复、跨存储补偿和索引行为，不能用其中一种替代其余三种。

### 15.8 演进边界：什么时候从 Polling Outbox 升级到其他传输方式？

演进不应由“技术更新”触发，而应由可测瓶颈触发。Polling Outbox 的优点是实现透明、Claim 与 Redrive 可控、部署依赖少；当最老 READY 年龄持续超预算、轮询查询占数据库明显比例、即使批量与索引优化后仍无法满足延迟，才评估 Debezium 或其他 CDC。CDC 降低轮询压力并缩短发布延迟，但引入 Binlog 权限、Connector 运维、Schema 演进、Offset 保存和重放治理，Consumer 幂等仍然不能删除。

同理，当前 Docker Compose 适合本地和集成环境。若规模、故障域或恢复目标发生变化，应先从 MySQL 真源、Kafka 命令、MinIO 对象和 ES 可重建投影分别计算恢复窗口，再决定备份、复制、服务扩展和流量切换方式。重点不是先指定某个部署工具，而是保证恢复后的重复事件、版本对账和权限边界仍然成立。

业务演进也有边界。新增文件类型需要解析器隔离和资源模型；新增 Projection 应从同一 Snapshot 派生，并有自己的版本与重建路径；Schema 变化要采用兼容读写和分阶段迁移；大规模重建要与在线流量隔离优先级。我的判断原则是保留 MySQL 业务真源、不可变 Snapshot、稳定幂等身份和可重建投影这几个长期不变量，替换传输实现。这样系统可以在轮询负载、投影延迟或数据增长达到阈值时演进，而不需要推翻用户可见状态和恢复协议。

当前是否需要改变投递方式，可以用 `OperationalMetricsBinder` 的 `noteweave.outbox.oldest_ready_age_seconds`、Outbox 状态数量和数据库轮询负载判断；是否需要调整检索部署，则用 Projection Lag、重建时间和 Alias 切换风险判断。仓库已实现 `RetrievalBackfillService.rebuildWorkspace()` 与 `RetrievalIndexManager.switchAliases()`，所以索引演进有落点。面试中先讲当前闭环，再用这些指标说明什么变化会触发下一步优化。

## 当前链路核对

上传接口是创建 Upload、写 Chunk、Complete 三步，资料域使用 `file_object`、`document_upload`、`upload_chunk`、`source`、`source_snapshot`、`source_chunk` 和 `source_cleanup_task`。解析、投影、对象清理均可异步重试，SSE 或 Kafka 不是唯一事实源。仓库 MySQL 迁移文件当前到 `V104`，具体环境版本仍以 Flyway History 为准。

## 17. 面试版上下游链路与技术取舍长回答

资料底座解决的是“上传成功以后，怎样最终变成可引用、可检索、可删除的资料”，不是单纯把文件保存下来。用户先创建上传会话，分块写入对象存储并在 MySQL 记录上传状态，Complete 阶段校验块数量、大小、Digest 和 Workspace 归属。之后 Java 在同一事务里创建 Source、Snapshot、解析 Task 和 Outbox，HTTP 请求到这里就结束，不假设解析已经完成。Dispatcher 领取 Outbox 后把命令发到 Kafka，Consumer 再读取固定 Snapshot，生成 Chunk、Window 和检索 Projection，最终由 Finalizer 把版本推进到 Ready。浏览器看到的是 Pending、Parsing、Indexing 或 Failed 等真实状态，而不是一个过早的成功标记。

这条链路采用 MySQL、MinIO、Kafka 和 Elasticsearch 的分工，是因为每个系统保存的东西不同。MySQL 负责身份、状态、唯一键和事务；MinIO 负责原文件、快照和产物大对象；Kafka 负责跨进程命令；Elasticsearch 负责可重建查询投影。文件直接存 BLOB 会放大数据库备份和连接压力，本地磁盘又不适合多实例；同步调用解析会占住请求线程，失败后很难恢复；ES 也不能成为业务真源，因为索引可以删除、重建或切换版本。当前接受多存储之间的最终一致窗口，但用状态、Digest、Projection Version 和 Cleanup Task 把窗口显式化。

可靠性依赖 At-least-once 加业务幂等。Outbox 可能重复发送，Kafka Consumer 可能重复消费，Worker 可能在写入 ES 后、Finalize 前崩溃，回调也可能因为网络丢响应而被重试。因此 Claim 使用 Attempt 和 Lease Owner，消费以 Source、Snapshot、Chunk No 或业务幂等键去重，Finalize 使用当前版本和状态条件更新，DLQ 保存永久失败原因，Redrive 必须重新检查版本和权限。这里没有用 XA 或全局 Exactly-once，因为跨 MySQL、Kafka、MinIO 和 ES 的统一提交成本高，且不能替代业务副作用幂等；本项目更关心重复不会造成第二个业务结果，暂时延迟可以被观察和补偿。

面试官追问为什么不用 CDC、RabbitMQ 或 Redis Streams 时，可以承认它们的优点。CDC 能减少轮询并接近数据库日志，RabbitMQ 更适合简单工作队列，Redis Streams 搭建消费组较快；当前选 Polling Outbox，是因为系统需要明确的 Claim、Lease、Attempt、DLQ、回放和本地开发可复现，而且 Redis 已经承担配额、租约和实时桥接，不希望它同时成为任务真源。规模扩大后可以把 Outbox Dispatcher 替换为 CDC 发送器，但必须保留本地事务、稳定幂等键、Projection 可重建和失败终态。

这套设计的验证重点不是“Kafka 能不能发消息”，而是提交后崩溃、已发送未确认、重复消费、旧 Projection 晚到、对象删除失败、ES 写成功但 Finalize 失败等故障窗口。当前测试和指标能够证明状态收口、补偿和显式失败语义；如果数据量和消息积压继续增长，再用实际队列、锁等待和恢复耗时决定下一步容量优化。
