# 面试官八维度审计与横切系统设计

## 1. 这份文档解决什么

前五组材料按 Deep Research、RAG、资料底座、Agent 框架、Context 与 Memory 组织，纵向机制已经较完整。面试官还会横向判断：业务问题是否真实，数据边界是否说得清，并发和容量是否算过，安全是否覆盖信任边界，故障能否定位，成本是否受控，测试证据是否可信，方案能否继续演进。

后面的八个回答按正常技术面试语速设计。每个回答先给结论，再讲当前实现、替代方案、取舍、验证和边界。没有线上证据的部分明确标为“设计目标”或“下一阶段”，不把 Docker Compose、默认参数和本地测试包装成生产成绩。

涉及具体线程池、连接池、配额、缓存、超时、重试、Lease 与 Worker 并发时，以[项目真实配置参数与容量口径](15-项目真实配置参数与容量口径.md)为准。默认设置用于解释资源边界，不能代替容量测试。

## 3. 业务抽象：如何证明系统不是技术拼盘

### 面试官问：这个项目的核心业务抽象是什么，为什么需要这么多模块？

可以先把系统压缩成三个业务动作：资料进入系统，系统基于资料完成回答或产出，用户在长期使用中继续修正和积累知识。中间件和 Agent 机制都服务这三个动作。资料进入系统对应 Source、Snapshot、Chunk 与 Projection；一次回答或长任务对应 Conversation、Run、Task、Evidence 与 Artifact Version；长期连续性对应 Segment、Summary Revision 和 Memory Revision。

这几个对象没有直接合成一张大表，因为它们的身份和生命周期不同。Source 是用户资料的稳定身份，Snapshot 表示某次不可变内容；Conversation Message 是原始交互记录，RunInputSnapshot 表示某次执行实际看到的输入；Artifact Job 表示持续需求，Artifact Version 表示一次不可变产出。把稳定身份和版本分开后，更新、重试、回放与删除才能有明确语义。

业务不变量比页面功能更重要。第一，任何 Evidence 都必须回到当前 Workspace 内可访问的 Snapshot 或受控外部快照。第二，旧 Worker、旧计划和重复消息不能覆盖新状态。第三，Elasticsearch、Redis 与生成结果都不是业务事实真源。第四，Memory 可以改变表达和约束，不能改变资料事实。第五，终态一旦提交，只能幂等返回，不能被晚到消息逆转。

替代方案是按 Controller 或页面拆模块，开发初期更快，但同一个 Task、Source 和权限规则会散落在多个功能中。另一个方向是先建立非常抽象的通用工作流和知识图谱，扩展性看起来更强，却会在需求尚未稳定时增加大量配置和治理。当前选择先围绕 Source、Run、Task、Version、Evidence 这些稳定对象建立深模块，再让 QA、Note、Wiki、Research 和 Artifact 使用它们。

衡量业务价值也要分层。功能层看资料从上传到 Ready 的时间、回答首字延迟、引用覆盖、长任务完成率和用户是否保存产物；质量层看检索 Recall、Citation Support、拒答正确性、Memory 误召回；工程层看积压、重试、死信、租约丢失和恢复时间。当前项目没有真实线上用户规模，因此这些是应记录的指标和已有测试证据，不是已经达到的生产 KPI。

## 4. 数据与一致性：如何讲清真源、事务和版本

### 面试官问：系统横跨 MySQL、Kafka、MinIO、Redis 和 Elasticsearch，怎么保证数据一致？

先定义每种数据的 Owner。MySQL 保存 Workspace 权限、业务状态机、稳定身份、版本指针、任务和 Outbox，是业务真源；MinIO 保存原文件、Checkpoint 和产物等大对象，身份和 Hash 仍由 MySQL 记录；Kafka 负责命令与事件分发，不保存最终业务状态；Elasticsearch 是可重建查询投影；Redis 保存短期配额、租约、缓存和实时事件桥接，故障后不能改变事实。

本地原子性只覆盖一个 MySQL 事务。创建 Source、Task 和 Outbox 可以一起提交，Dispatcher 再发送 Kafka。发送与确认不是原子操作，所以允许重复，不允许消息静默丢失。Consumer 通过稳定业务键、唯一约束、From Status 条件更新、版本和 Fencing Token 吸收重复与旧结果。文件或 ES 副作用无法参加本地事务，系统通过不可变对象、结果锚点、失败终态、Cleanup Task、补偿和对账收敛。

长耗时模型调用和网络 I/O 不放在数据库事务中。贯穿几分钟持有悲观锁会占用连接、扩大死锁与故障恢复成本。系统只在 Claim、版本晋升、合并和终态提交这些短临界区使用行锁或条件更新，执行阶段使用 Lease 与业务版本。冲突概率低且可以检测的路径偏向乐观 CAS；同一 Wiki Item 追加新版本等短而高冲突的路径，可以用行锁串行。

隔离级别不能替代业务并发控制。即使数据库使用可重复读，同一个外部调用仍可能被两个 Worker 执行；即使串行化隔离能避免部分写冲突，也无法锁住 Kafka、MinIO 和模型 Provider。版本、幂等键与 Fencing 解决的是跨事务、跨进程、跨存储的旧结果问题。

索引设计围绕访问路径和门禁设计，而不是给每列建索引。Session Token Hash 需要唯一索引，用户会话查询需要 `user_id + status + expires_at`；Outbox 需要按状态和下次重试时间扫描；稳定业务键需要唯一约束；投影、任务和版本查询需要以 Workspace 与父对象开头的组合索引。索引会增加写放大，所以每个索引都应对应查询、唯一性或 Claim 路径。当前 Flyway 迁移已演进到 V090，能证明 Schema 版本化，但生产大表在线迁移、回填节流和回滚演练仍是后续工作。

## 5. 并发与容量：如何从公式落到线程池和背压

### 面试官问：系统能支撑多少并发，瓶颈在哪里，如何做容量规划？

没有压测数据时不能报一个系统 QPS。可以先画出四层容量：入口接受速率、队列积压、Worker 在途任务、下游 Provider 与存储吞吐。短请求和长任务也要分开。上传登记、状态查询和权限校验受 Web 线程、Hikari 连接池和数据库延迟影响；Research、Artifact、Embedding 和 Rerank 受任务耗时、Provider Rate Limit、Kafka 分区和 Worker 数影响。

Little's Law 可以给第一版并发估算：平均在途量 `L = λW`。如果昂贵任务平均 30 秒完成，稳定到达率每秒 0.1 条，平均在途约 3 条；并发上限设为 4 只是一个保护起点，还要结合 P95 耗时、失败重试、Provider 限额和安全余量。对资料解析，如果单 Consumer 平均 2 秒处理一条、峰值每秒 20 条，目标利用率 0.7，理论并行槽接近 58，但文件大小、数据库连接、MinIO 和 ES 批量能力会改变结果。

系统从入口就做背压。Redis 令牌桶按 Workspace、Actor 和 Workload 控制到达速率，并发租约按 Workspace 与 Workload 限制长任务在途数。Kafka 提供缓冲，但积压不是免费容量，必须看 Consumer Lag 与 Oldest Ready Age。线程池使用有界队列和 AbortPolicy，让过载显式失败；阻塞型 SSE Connection 与 Redis XREAD Bridge 使用独立线程池和零队列，避免少量阻塞任务饿死普通 Answer I/O。数据库 Hikari 默认最大连接数 20，也意味着不能把所有线程池最大值简单相加后同时访问数据库。

扩容顺序取决于观测结果。CPU 和 Worker 执行饱和时增加 Consumer 实例，但实例数超过 Kafka Partition 不再提高并行度；Rerank 占主要延迟时先减少融合候选或批处理，不一定加机器；数据库锁等待与连接池耗尽时，继续加 Worker 反而恶化；Provider 429 增长时应降低入口速率或等待，而不是快速重试。

容量答案最后要给边界。当前默认桶容量、并发 4、线程池大小和 128 MB 上传上限都是保护配置，不是生产极限。完整结论需要固定数据集、文件大小分布、真实 Provider、端到端压测和故障恢复压测，至少报告稳定吞吐、P50/P95/P99、错误率、积压恢复斜率和资源利用率。

## 6. 安全：如何覆盖四个信任边界

### 面试官问：这个 AI 系统的安全模型是什么，除了防 Prompt Injection 还做了什么？

安全可以按外部用户、内部服务、工具执行和数据内容四个边界回答。外部用户登录后拿到随机生成的 Access Token 与 Refresh Token，数据库只保存 SHA-256 Hash，不保存可直接使用的明文 Token。Refresh 使用条件更新完成轮换，同一 Refresh Token 重放时更新行数不再是 1，系统返回 `REFRESH_TOKEN_REPLAYED`；登出会撤销 Session 并清空两个 Hash。密码由 PasswordHasher 管理，具体算法和参数应以当前实现为准，不能泛称“军工级加密”。

身份认证后还要做授权。请求身份由服务端 Filter 解析，客户端不能通过 Header 随意指定用户。WorkspaceAccessGuard 读取 Workspace 状态与 ACL Version，再校验 Active Membership 和 Role Permission。ACL 缓存 Key 带 Workspace、User 和 ACL Version，成员或角色变化后提升版本，旧缓存自然失效；Denied 使用更短 TTL，降低新授权被负缓存阻塞的时间。访问知识页、消息、Task、Conversation 和 Upload 时会先反查资源所属 Workspace，避免只校验路径里的 Workspace ID。

内部服务不能复用用户 Token。`/internal/*` 使用独立 Audience Token，Research 与 Artifact 路径可以配置不同凭据，并使用常量时间比较；开发环境未配置时只允许 Loopback。ProductionConfigurationGuard 会拒绝默认 Secret、本地用户回退、MySQL QA 回退、Quota 本地回退和模板 LLM 回退，并要求内部 Token 分离、Worker HTTPS、Kafka SSL 或 SASL_SSL，以及 Redis、ES、MinIO 的生产凭据与加密传输。

工具边界由 Capability Intersection、Trusted Permit、Schema 与运行环境共同控制。外部抓取要防 SSRF、Loopback、DNS Rebinding、跨端口重定向和凭据跨重定向，内容按不可信输入处理。生产只启用受信任系统 MCP；调试自定义 MCP 能启动子进程，但没有完整签名、白名单、进程沙箱和网络出口隔离，因此默认关闭且生产禁止开启。

数据内容还涉及多租户泄漏、日志泄密和长期污染。ES 查询先下推 Workspace Scope，Hydration 再用 MySQL 归属二次校验；Trace 保存 ID、Hash、计数和受控摘要，不保存密钥和不必要全文；错误持久化前经过 SensitiveErrorMessageSanitizer；Memory 不进入 Evidence Rerank，外部文本不能直接晋升为系统规则。当前仍缺独立 Secret Manager、密钥轮换平台、完善的进程沙箱和正式威胁建模演练，这些要主动说明。

## 7. 可观测性：如何从请求定位到业务不变量

### 面试官问：任务失败或变慢时，你如何在多服务链路中定位？

日志、指标、Trace 和审计解决的问题不同。日志记录离散事件和错误上下文，指标回答问题发生了多少次、持续多久，Trace 串起一次 Run 的阶段和候选变化，审计记录谁在什么版本上做了哪次权限或状态决定。只说“加日志”无法回答积压趋势、P95 延迟和旧 Owner 覆盖是否发生。

请求进入 Java Host 后生成 Request ID，并把 Workspace ID 放入 MDC。异步 Answer I/O 使用 TaskDecorator 传播 MDC，避免换线程后日志失去关联。业务对象还要携带 Conversation ID、Run ID、Task ID、Delivery ID、Version 和 Node 或 Cell Identity。跨 Kafka 与 Python Worker 时，不依赖 ThreadLocal，而是把稳定身份写入版本化 Envelope 和 Trace。

定位顺序从用户症状开始。资料迟迟不可检索，先看 Projection Lag、Oldest Ready Age 和 Consumer Lag，再分辨 Outbox 未发送、Consumer 未处理、ES 写入失败还是状态终态化失败；回答慢，先看 Retrieval Trace 各 Step、Embedding/Rerank Provider 延迟、Evidence 数量和 LLM 首字时间；Research 卡住，查看当前 Wave、Lease、Checkpoint、Gap、重试和 Stop Decision；Artifact 失败，查看 Node Trace、Capability Resolution、Verifier 与 Repair Count。

告警要对应动作。Outbox Ready 数增长但最老年龄不增长，可能只是流量波动；Oldest Ready Age 持续超阈值才需要查 Dispatcher。Consumer Lag 增长同时 Provider 429 上升，应降低并发或入口速率；Dead Letter 增长要按错误类别判断是否 Redrive，永久 Schema 错误不能盲目重放。ACL Denied、Scope Violation、Internal Auth Failure 和敏感错误清洗命中属于安全告警，不能和普通 4xx 混在一起。

SLO 目前没有线上基线，文档只能给设计方法。可以定义资料上传接受成功率、上传到 Ready 的 P95、QA 首字和完成延迟、Citation Support、长任务成功率、断线重放成功率与删除收敛时间。每个 SLI 都要明确分母、排除项和降级是否算成功。仓库已有 Micrometer、Actuator Health、模块 Trace 和业务 Metrics，但没有完整 OpenTelemetry 跨服务链路与生产告警平台，不能宣称已经建成全链路 APM。

## 8. 成本：如何把 Token 和工程资源放在同一张账上

### 面试官问：Agent 和 RAG 调用很多模型，怎么控制成本，又怎么避免为了省钱牺牲质量？

成本至少分五类：生成与验证 Token、Embedding 和 Rerank 调用、外部搜索与抓取、计算和存储、人工审核。只统计主模型 Token 会漏掉 Verifier、Repair、重试、无效候选和长期快照。一次 Run 的成本应该按阶段记录输入 Token、输出 Token、Provider、模型版本、调用次数、失败重试和缓存命中，并关联到 Run、Task、Cell 或 Node。

RAG 的成本控制从漏斗开始。Scope 和词法过滤先减少无效候选，BM25 与 Vector 召回后用 RRF 合并，Cross-Encoder 只处理有限集合，Evidence Selection 再控制送入 LLM 的字符数。Rerank 全库质量理论上更高，却会把计算成本和延迟放大到不可接受。Embedding 可以批量执行，索引版本避免模型变更后混用旧向量；查询缓存只有在权限、策略和版本都进入 Key 时才安全。

Research 的主要浪费来自重复搜索、过早写作后返工和无限 Replan。Intent、Gap Priority、Adaptive Evidence Horizon、Stop Contract、循环上限和 Budget Checkpoint 限制搜索范围；Local Verifier 尽早阻止低质量候选进入全局写作；Checkpoint 让崩溃恢复不必从头调用 Provider。代价是 Verifier 本身也收费，因此低风险字段可以先跑确定性规则，高影响字段才使用更强验证。

Artifact 用冻结 ExecutionSpec 避免 Waiting 恢复后重新规划，局部 Repair 只重做失败节点，不全量生成。Context Compiler 通过 Summary、Raw Tail 和 Memory Pack 分区预算，减少每次携带全部历史；缓存编译结果降低重复计算，但失效错误可能带来语义风险，不能为了命中率忽略版本。

模型路由不能只按价格。候选模型必须满足上下文长度、结构化输出、Tool Calling、数据政策、延迟和质量门槛，再在合格集合里比较成本。当前代码存在预算、Token Ledger、Provider Health 和候选控制，但没有完整的价格表、真实账单对账和单位任务毛成本报表。因此面试中应讲成本模型和已有控制点，不报未经记录的“节省百分比”。

## 9. 测试证据：如何证明不是只写了很多 Mock

### 面试官问：你怎么证明这些一致性、恢复和 Agent 质量机制真的有效？

先把证据分成四层。第一层是纯函数和算法单测，例如 RRF、Canonicalization、Token Bucket、Stop Policy、Chunk Window 和 Memory Rank；它证明输入输出规则。第二层是状态机与契约测试，例如终态不能逆转、旧 Epoch 拒绝、回调幂等、Scope 隔离和 Memory 不进入 Retrieval；它证明业务不变量。第三层是真实中间件集成或故障注入，例如 Redis Lua 原子性、MySQL 行锁矩阵、Kafka 重复投递、ES Mapping 和 MinIO 对象行为；它证明不是只在 Mock 中成立。第四层是质量评测，例如 Gold Set、Shadow Replay、Citation Support 和 Verifier Precision/Recall；它证明模型行为，不等同于线上业务结果。

故障测试要覆盖时间窗口，而不只是异常类型。Outbox 要测发送成功后状态更新失败，Consumer 要测业务提交后 Offset 未提交，Lease 要测过期后旧 Owner 晚到，Summary 要测构建期间新消息到达，Completion 要测数据库提交后 HTTP 响应丢失，删除要测事务回滚与外部 Cleanup。很多分布式 Bug 只在“某一步成功、下一步失败”时出现。

架构测试也有价值。ArchUnit 或包依赖契约可以防止 Memory 代码进入 Retrieval、Worker 绕过 Host 写业务表、旧 Route 或 Legacy Bridge 被重新引用。配置组合测试要验证生产模式拒绝弱 Secret、危险 Fallback 和调试路由。Flyway 从空库迁移验证只能证明新建路径，升级真实大库还需要迁移时间、锁范围和回滚演练。

质量数字要说明数据来源。当前 RAG 的 6 条内部样本和 33.3% 至 100% 固定结果是手工回归 fixture，不是在线融合链路实测；Gold Set 是内部 Harness，不是公开 Benchmark；测试文件很多也不等于覆盖率足够。更强证据需要扩大人工 Reviewed 样本，保留失败 Case，按查询类型分桶，报告置信区间，并在真实 Provider 和隔离环境中持续重放。

回答测试题时，最好把“需求、不变量、测试、观测”串起来。比如需求是旧 Worker 不能覆盖新结果，不变量是 Epoch 与 Version 必须匹配，测试制造租约过期和晚到回调，运行指标记录 Fencing Reject。这样测试不是罗列框架，而是证明设计目标。

## 10. 演进边界：何时升级架构，何时保持简单

### 面试官问：如果用户量扩大十倍，你会怎么演进，当前方案哪些地方会先出问题？

演进顺序要由指标触发。Outbox 扫描占用数据库 I/O、Oldest Ready Age 在 Dispatcher 扩容后仍上升时，Polling 才需要迁移到 CDC；Kafka Consumer 已达到 Partition 上限且单分区处理饱和时，再增加 Partition，并评估顺序与 Rebalance 成本；MySQL 连接和热点行成为瓶颈时，先优化访问路径、批量和索引，再考虑读写分离或按 Workspace 分片。

Artifact Skill Graph 当前是编译期 DAG、运行期线性节点序列。只有 Trace 显示多个独立 I/O 节点占主要时间，并且状态合并规则稳定时，才引入 Ready Queue、条件边和节点级并发；如果需要人工审批、长时间定时器、跨天补偿和大量可视化编排，再评估 Temporal、Camunda 或成熟工作流引擎。LangGraph 更适合模型状态图和动态推理，但业务权限、Outbox、文件终态和多租户配额仍要由 Host 管理。

部署层当前主要是 Docker Compose 与健康检查，适合本地和单机集成验证。要进入生产高可用，需要补 Kubernetes 或等价编排、Readiness 与 Liveness 区分、Pod Disruption、滚动升级、优雅 Drain、Secret Manager、网络策略、持久卷或托管存储、多可用区数据库和 Kafka。Research Worker 已有 Heartbeat、Lease 与 Drain Grace 的配置基础，但这不等于完成了集群级故障演练。

灾备要明确 RPO 与 RTO。MySQL 是业务真源，应有定期备份、Binlog 或托管 PITR；MinIO 需要版本、复制或对象备份；ES 可以从 MySQL 和 MinIO 重建，因此备份优先级低于重建脚本和时间预算；Redis 主要保存可恢复的短期状态，但实时事件窗口与租约丢失会影响恢复体验；Kafka 保留期要覆盖可接受的停机窗口。当前仓库没有证明生产备份恢复演练，所以只能给出设计，不声称已有 RPO/RTO。

功能演进也要保持边界。短对话不需要 Segment 与 Memory，一次性任务不需要 RunInputSnapshot，单一固定产物不需要 Skill Compiler，三五步探索可以直接用 ReAct，小规模数据可以继续 Polling Outbox。架构升级的标准是现有方案已经出现可观测失败，而不是新技术更流行。

## 11. 面试官连续三层追问的统一答法

第一层通常问“为什么选它”，回答业务问题、候选方案和选择依据；第二层问“怎么实现”，回答数据结构、状态机、线程或中间件机制；第三层问“怎么证明”，回答失败窗口、测试、指标和未完成边界。任何回答如果只能说到第二层，面试官会怀疑它来自方案文档而不是工程实践。

可以用下面的句式收敛，但不要逐字背：

> 这个选择先解决的是 X。最小方案 A 在 Y 条件下会失败，我们比较过 B 和 C。当前约束更适合 C，实现上由 D 不变量和 E 状态机保证。它付出的代价是 F。测试里制造 G 窗口，运行时看 H 指标。现在还没有 I 的生产证据，所以当 J 指标出现时才继续演进。

## 12. 当前不能夸大的能力

- 没有真实线上 SLO、用户规模、QPS、P99、成本节省率和公开 Benchmark 成绩。
- Docker Compose、Healthcheck 和 Restart Policy 不等于 Kubernetes 多副本高可用。
- Micrometer、模块 Trace 和 Actuator 不等于完整 OpenTelemetry 与生产告警平台。
- 版本迁移到 V090 不等于做过生产大表在线迁移和回滚演练。
- ProductionConfigurationGuard 能拒绝危险配置，不等于完成 Secret Manager、密钥轮换和零信任网络。
- 编译期 DAG 不等于运行期 Ready Queue、条件边和节点并行。
- 调试自定义 MCP 不等于安全的用户插件平台。
- 内部 Gold Set 与固定回归 fixture 不等于线上质量统计。
