# NoteWeave 全项目指标体系与面试计算手册

## 1. 文档定位与事实边界

指标用于回答四类问题：用户是否得到结果，系统是否稳定，资源是否够用，方案改动是否真的改善质量。NoteWeave 同时包含资料接入、场景化 RAG、Deep Research、Artifact Agent、Context/Memory 和实时流式链路，单看 QPS、错误率或模型准确率都不够。

本文负责“测什么、怎样计算”，线程池、连接池、TTL、Timeout、Retry、Lease 和 Worker 并发的当前真实值统一查阅[项目真实配置参数与容量口径](15-项目真实配置参数与容量口径.md)。配置值是保护策略，指标和固定工作负载才产生容量证据。

本文把指标分成三种成熟度，面试时必须区分：

| 标记 | 含义 | 可以怎样描述 |
|---|---|---|
| 已埋点 | 源码中已经通过 Micrometer 或业务 Counter/Timer 记录 | “当前代码已采集” |
| 可计算 | 数据库状态、Trace、快照或日志中已有原始字段，可以离线聚合 | “可以按该口径计算，仍需接 Dashboard” |
| 建议补充 | 面试和生产治理需要，但当前仓库没有完整采集闭环 | “上线前会补，不说已经实现” |

当前 Actuator 暴露 `health`、`info` 和 `metrics`，代码存在 Micrometer Counter、Gauge、Timer 与 DistributionSummary。仓库没有完整 Prometheus/Grafana 配置、统一 OpenTelemetry 跨服务 Trace、线上 SLO 基线和生产告警闭环。Docker Compose 的健康检查也不能证明生产高可用。内部 Gold、Shadow 和 Fixture 是确定性评测证据，不代表线上准确率或公开 Benchmark 成绩。

## 2. 指标类型与计算基础

### 2.1 Counter、Gauge、Histogram 和 Timer

**Counter** 只增不减，适合请求、成功、失败、重试和拒绝次数。观察窗口内的增量为：

```text
delta = counter(t2) - counter(t1)
rate = delta / (t2 - t1)
```

进程重启会让 Counter 归零，查询端应用 `rate()` 或 `increase()` 一类窗口函数处理，不直接比较两个实例的绝对值。

**Gauge** 表示当前值，可以上升或下降，适合队列深度、活跃连接、连接池使用量和最老消息年龄。Gauge 的瞬时值可能抖动，告警通常要求持续多个窗口。

**Histogram/DistributionSummary** 记录值的分布，适合 Payload 字节数、候选数量和 Token 数。均值会掩盖长尾，应同时看分位数和 Bucket。

**Timer** 是带次数的延迟分布，可以得到 Count、Total Time、Mean、P50、P95、P99。平均延迟为：

```text
mean_latency = sum(all latency) / request_count
```

P95 表示 95% 的样本不超过该值，不表示最慢 5% 的平均值。不同实例的分位数不能直接做算术平均，应该合并 Histogram Bucket 后重新计算。

### 2.2 Rate、Ratio 与 Percentage

Rate 带时间单位，比如每秒请求数；Ratio 是两个数量之比；Percentage 是 Ratio 乘 100%。面试中最常见的错误是分母不清楚。

```text
success_rate = successful_terminal_runs / accepted_runs
error_rate = failed_requests / total_requests
retry_rate = retry_attempts / first_attempts
cache_hit_rate = cache_hits / cache_lookup_attempts
```

`accepted_runs` 是否包含用户取消、限流拒绝和仍在运行的任务必须提前定义。长任务按“本窗口创建、本窗口终态”计算会产生时间偏差，更稳的做法是按 Cohort 追踪某批已接受任务的最终结果。

### 2.3 平均数、分位数和加权聚合

宏平均先算每个 Case 的指标再平均，每个 Case 权重相同；微平均先合并所有样本的分子分母，大 Case 权重更高。

```text
macro_metric = sum(metric_per_case) / case_count
micro_precision = sum(true_positive) / sum(predicted_positive)
```

检索评测常用 Macro，避免候选多的 Query 主导结果。线上流量与成本分析常用按请求量加权的 Micro。报告指标时要同时给样本数、时间窗口、版本、数据分布和排除项。

### 2.4 标签基数

Micrometer Tag 应使用状态、模式、阶段、错误分类、Topic 这类有限集合。`user_id`、`workspace_id`、`run_id`、URL 和原始错误消息会造成高基数，增加时序库内存与查询成本。这些身份应放日志或 Trace，通过 Correlation ID 定位。项目中的 `mode`、`result`、`phase`、`topic`、`workload` 和受控 `error_code` 适合作为 Tag，但仍要限制错误码与 Topic 的集合。

## 3. 业务与用户体验指标

### 3.1 北极星指标与护栏指标

NoteWeave 的北极星指标可以定义为“每周产生至少一个可验证有效结果的活跃 Workspace 数”。有效结果按业务类型拆开：资料达到 READY、QA 生成带有效证据的回答、Research 通过完成契约、Artifact 通过最终校验并保存。它比注册用户数或模型调用次数更接近用户价值。

北极星指标不能单独优化，需要护栏：失败率、P95 完成时间、Citation Support、单位成功结果成本、安全拒绝与删除收敛时间。否则系统可能通过降低校验门槛或无限增加模型调用来提高完成量。

### 3.2 激活、留存与任务完成

```text
activation_rate = activated_new_workspaces / new_workspaces
task_completion_rate = successful_terminal_tasks / accepted_tasks
time_to_first_value = first_valid_result_at - workspace_created_at
D7_retention = users_active_on_day_7 / users_activated_on_day_0
```

激活事件应选择“首次资料 READY 并完成一次有效回答”这类价值事件，不用登录或点击按钮代替。任务完成率按 Answer、Research、Artifact 和 Source Pipeline 分组，用户取消单列，不能全部算系统失败。

### 3.3 漏斗与降级

资料漏斗可以统计 `UPLOAD_ACCEPTED -> PARSED -> INDEXED -> READY`，回答漏斗统计 `RUN_CREATED -> RETRIEVAL_DONE -> FIRST_TOKEN -> COMPLETED`，Artifact 统计 `COMPILED -> RUNNING -> VERIFIED -> SAVED`。阶段转化率为：

```text
stage_conversion = reached_next_stage / entered_current_stage
```

降级成功率需要独立观察：

```text
degraded_success_rate = successful_degraded_runs / degraded_runs
```

降级成功不等于完整成功。回答没有 Rerank、Memory Cache 回源、ES 显式关闭等情况都应在结果和指标中保留 Degradation Reason。

## 4. 延迟、吞吐、并发与容量

### 4.1 延迟拆分

端到端延迟应按用户等待拆分：

```text
T_total = T_queue + T_prepare + T_retrieval + T_provider + T_verify + T_writeback
```

流式回答还要区分：

```text
TTFT = first_token_at - request_accepted_at
TPOT = (last_token_at - first_token_at) / output_token_count
completion_latency = terminal_at - request_accepted_at
```

资料可检索延迟为 `projection_ready_at - upload_committed_at`，Research/Artifact 长任务更适合报告 P50、P95、P99 和最大年龄，不用同步接口的毫秒级标准套用。

### 4.2 QPS、TPS 与吞吐

```text
QPS = requests / seconds
TPS = committed_business_transactions / seconds
document_throughput = ready_snapshots / minute
token_throughput = generated_tokens / second
```

QPS 必须注明接口和请求组合。上传 10 QPS、QA 10 QPS 和 Research 10 QPS 的成本完全不同。异步接口的接收 QPS 不等于后台完成吞吐，稳定运行要求长期完成速率不低于到达速率。

### 4.3 Little 定律

```text
L = lambda * W
```

`L` 是平均在途任务数，`lambda` 是平均到达率，`W` 是平均停留时间。每分钟进入 30 个 Research，平均 4 分钟完成，则平均约有 120 个在途任务。若并发上限只有 20，排队时间会持续增长，除非实际到达率下降或服务时间缩短。

Little 定律要求系统处于相对稳定状态，不适合直接套在持续增长的积压上。容量规划还要看 P95 服务时间、突发系数和下游限额。

### 4.4 利用率、饱和度与排队

```text
utilization = busy_capacity / total_capacity
thread_pool_saturation = active_threads / maximum_threads
db_pool_utilization = active_connections / maximum_connections
quota_utilization = active_leases / concurrency_limit
```

利用率长期接近 100% 时，排队延迟会非线性增长。建议同时观察队列长度、拒绝数、最老任务年龄和下游 429。项目配置中的 Hikari 最大连接数 20、线程池大小、Worker 并发和 Redis Lease 上限只是保护参数，未经压测不能换算成生产 QPS。

### 4.5 积压与清空时间

```text
backlog_growth_rate = arrival_rate - completion_rate
drain_rate = completion_rate - arrival_rate
estimated_drain_time = backlog / drain_rate
```

只有 `completion_rate > arrival_rate` 时才存在有限清空时间。比如积压 600 个任务，恢复后每分钟完成 50 个、新增 20 个，净清空速率为 30 个/分钟，预计 20 分钟清空。Kafka Lag、Outbox READY 数和 Waiting Task 都可用此方法估算恢复时间。

## 5. 可用性、可靠性与 SLO

### 5.1 可用性

```text
availability = successful_eligible_requests / eligible_requests
time_availability = available_time / total_time
```

按请求计算更贴近用户，按时间计算适合基础设施。限流、无权限、无效参数通常从服务可用性分母排除，但规则必须固定。返回 200 但结果为空或进入错误降级不能算完整成功。

### 5.2 SLI、SLO、SLA 与错误预算

SLI 是测量值，SLO 是内部目标，SLA 是对外承诺。若月度可用性 SLO 为 99.9%，30 天错误预算约为：

```text
error_budget = 30 * 24 * 60 * (1 - 0.999) = 43.2 minutes
```

请求型错误预算为：

```text
allowed_bad_events = eligible_events * (1 - target)
budget_burn_rate = observed_bad_ratio / allowed_bad_ratio
```

99.9% 目标允许 0.1% 错误，若过去一小时错误率为 1%，Burn Rate 为 10。多窗口告警可以同时看短窗口快速燃烧与长窗口持续燃烧，减少瞬时抖动误报。

### 5.3 MTTR、MTBF、RTO 与 RPO

```text
MTTR = sum(recovery_duration) / incident_count
MTBF = total_operating_time / failure_count
```

RTO 是故障后允许多久恢复，RPO 是最多允许丢多少时间范围的数据。Outbox 和任务状态可减少消息意图丢失，不自动给出数据库、Kafka、MinIO 和 ES 的 RPO。备份恢复演练才能证明 RTO/RPO，Docker restart policy 不能替代。

## 6. 事件驱动资料底座指标

### 6.1 Outbox 核心指标

项目已埋点：

| 指标 | 类型 | 作用 |
|---|---|---|
| `noteweave.outbox.messages{status}` | Gauge | READY、CLAIMED、SENT、RETRY、DEAD 等状态数量 |
| `noteweave.outbox.oldest_ready_age_seconds` | Gauge | 最老 READY 消息等待时间，比总数更能反映饥饿 |
| `noteweave.outbox.dispatch.success{topic}` | Counter | 发布并成功确认 Claim 的次数 |
| `noteweave.outbox.dispatch.retry{topic}` | Counter | 进入重试的次数 |
| `noteweave.outbox.dispatch.dead_letter{topic}` | Counter | 进入死信的次数 |
| `noteweave.kafka.consumer.retry{topic}` | Counter | Kafka Consumer 重试次数 |
| `noteweave.kafka.consumer.dlt{topic}` | Counter | 投递 DLT 次数 |
| `noteweave.kafka.consumer.dlt_publish_failure{topic}` | Counter | DLT 发布本身失败 |

推荐派生：

```text
dispatch_success_rate = dispatch_success / dispatch_attempts
retry_amplification = total_delivery_attempts / unique_outbox_messages
dead_letter_rate = dead_lettered_messages / dispatched_unique_messages
oldest_ready_age = now - min(available_at for READY messages)
```

Outbox 数量低但最老年龄高，可能是特定 Topic 饥饿或毒消息；数量高但年龄低，可能只是正常突发。两者必须一起看。

### 6.2 Kafka 指标

```text
consumer_lag = log_end_offset - committed_offset
lag_time_estimate = consumer_lag / recent_consume_rate
duplicate_delivery_rate = duplicate_messages_absorbed / consumed_messages
rebalance_rate = rebalance_count / time_window
```

Lag 是消息条数，不直接等于时间或业务不一致。消息处理时长差异大时，应同时看最老业务事件年龄和 Projection Lag。Consumer 多于 Partition 不会继续提高同组并行度。

### 6.3 Source、Snapshot 与 Projection

项目已埋点 `noteweave.source.messages{status}`、`noteweave.source.projection_chunks{status}`，可从业务表计算：

```text
ready_rate = ready_snapshots / accepted_snapshots
projection_lag = projection_ready_at - snapshot_committed_at
orphan_rate = unreferenced_objects / uploaded_objects
reconciliation_mismatch_rate = mismatched_projections / checked_projections
rebuild_throughput = rebuilt_chunks / minute
```

删除收敛时间从数据库删除提交开始，到在线查询不可见、缓存失效、ES/MinIO 派生清理完成为止。在线不可见与物理清理应分别设 SLI。

## 7. 缓存指标

项目统一使用 `noteweave.cache.requests{cache,result}`，覆盖 `source_catalog`、`wiki_page_version`、`memory_compiled_pack` 等缓存；ACL 使用 `noteweave.security.acl.cache{result}`。常见 Result 包括 Hit、Miss、Disabled、Error、Schema Mismatch 或 Fallback，具体以代码中的有限集合为准。

```text
hit_rate = hit / (hit + miss)
effective_hit_rate = valid_hit / lookup_attempts
fallback_rate = fallback / lookup_attempts
load_penalty = mean(db_load_latency_after_miss)
```

高命中率不一定代表收益大，应计算节省时间：

```text
saved_latency = hits * (mean_origin_latency - mean_cache_latency)
```

还应观察缓存穿透、击穿和雪崩：不存在 Key 的回源率、热点 Key 并发构建数、单位时间集中失效数。TTL 与 Jitter 是策略参数，不能当作缓存质量指标。

## 8. 场景化 RAG 指标

### 8.1 在线检索过程指标

项目已埋点：

| 指标 | 含义 |
|---|---|
| `noteweave.retrieval.step.latency{mode,step,result}` | 各检索阶段延迟 |
| `noteweave.retrieval.step.candidates{mode,step}` | 每阶段候选数量分布 |
| `noteweave.retrieval.bundle.selected_evidence{mode}` | 最终证据条目数 |
| `noteweave.retrieval.bundle.selected_characters{mode}` | 最终证据字符预算 |
| `noteweave.retrieval.bundle.degraded{mode,reason}` | 检索降级次数 |
| `noteweave.retrieval.scope_violation{mode,stage}` | Scope/归属校验拦截 |

候选漏斗可以计算：

```text
filter_survival_rate = candidates_after_filter / candidates_before_filter
rerank_retention = candidates_after_rerank / candidates_before_rerank
evidence_selection_rate = selected_evidence / final_candidates
budget_utilization = selected_characters / character_budget
```

`graph_characters_used` 是图关系渲染的 Token-safe Proxy，不是 tokenizer 精确 Token，也不包含 Wiki 正文、Summary 和 Citation 文本。

### 8.2 Recall@K、Precision@K 与 Hit@K

设 Gold 相关集合为 `G`，Top K 检索结果为 `R_K`：

```text
Recall@K = |G intersect R_K| / |G|
Precision@K = |G intersect R_K| / K
Hit@K = 1 if |G intersect R_K| > 0 else 0
```

Gold 有 3 个相关 Passage，Top 5 找到其中 2 个，则 Recall@5 为 `2/3`，Precision@5 为 `2/5`，Hit@5 为 1。QA 常关注 Hit/Recall，证据预算紧时也要看 Precision。

### 8.3 MRR

MRR 关注第一个相关结果出现多早：

```text
RR(q) = 1 / rank_of_first_relevant_result
MRR = sum(RR(q)) / query_count
```

三个 Query 的首个相关排名为 1、2、4，MRR 为 `(1 + 1/2 + 1/4) / 3 = 0.5833`。MRR 不关心第二个及后续相关结果，适合“找到一个就够”的问题，不适合完整证据覆盖。

### 8.4 DCG 与 NDCG@K

NDCG 支持多级相关性，越相关且排名越靠前，贡献越大：

```text
DCG@K = sum((2^rel_i - 1) / log2(i + 1)), i = 1..K
NDCG@K = DCG@K / IDCG@K
```

`IDCG` 是同一批结果按理想相关性排序的 DCG。NDCG 范围通常为 0 到 1。二值相关时也能使用，但多级标注更能反映强相关与弱相关的排序质量。

### 8.5 MAP 与 Rerank Lift

```text
AP(q) = average(Precision@i for every relevant result at rank i)
MAP = average(AP(q))
metric_lift = metric_new - metric_baseline
relative_lift = (metric_new - metric_baseline) / metric_baseline
```

Rerank Lift 应同时报告 Recall/NDCG 变化、P95 延迟增量和单位请求成本增量。只报相对提升会在基线很小时制造夸张效果，面试中优先给绝对 Delta。

### 8.6 Citation 与答案质量

```text
citation_precision = supported_citations / all_citations
citation_recall = cited_supported_claims / claims_requiring_evidence
citation_support_rate = claims_supported_by_valid_evidence / verifiable_claims
answer_correctness = correct_answer_units / evaluated_answer_units
faithfulness = claims_entailed_by_context / claims_about_context
```

Citation 存在不代表支持结论，还要检查引用是否真的蕴含 Claim、身份是否属于当前 Snapshot、是否过期。Correctness 需要 Gold Answer 或人工标注，Faithfulness 只判断是否忠于给定 Context，不保证 Context 本身正确。

### 8.7 当前评测边界

仓库的 Retrieval Gold/Shadow 支持 `macroRecallAtK`、`macroMrr`、`macroNdcgAtK` 和 Delta Gate。内部 6 条消融 Fixture 与确定性 BM25 Replay 只能证明样本和契约，不应表述为线上 Hybrid/Rerank 准确率。正式结论需要版本化 Gold、盲审、样本分层、置信区间和 Shadow/线上实验。

## 9. Deep Research 指标

### 9.1 研究状态覆盖

```text
cell_completion_rate = terminal_cells / planned_cells
verified_cell_rate = verified_cells / required_cells
evidence_coverage = cells_with_acceptable_evidence / required_cells
conflict_rate = conflicted_cells / evidence_bearing_cells
conflict_resolution_rate = resolved_conflicts / detected_conflicts
```

Cell 数量不能单独代表研究质量。拆得更细会机械抬高数量，必须绑定同一 Research Schema、执行模式和 Required Cell 集合。

### 9.2 来源质量与多样性

```text
source_acceptance_rate = accepted_sources / fetched_sources
source_diversity = unique_source_domains / accepted_sources
primary_source_ratio = accepted_primary_sources / accepted_sources
evidence_reuse_rate = citations_reusing_same_source / all_citations
```

Domain 数只是一种粗粒度多样性，多个镜像站可能来自同一原始材料。更严格的计算应按 Source Family、Publisher 和内容 Hash 去重。

### 9.3 Verifier 指标

```text
precision = TP / (TP + FP)
recall = TP / (TP + FN)
F1 = 2 * precision * recall / (precision + recall)
false_positive_rate = FP / (FP + TN)
false_negative_rate = FN / (FN + TP)
```

Verifier Precision 低会反复打回正确结果，增加成本；Recall 低会放过错误结果。严重事实错误更关注 Recall，自动阻塞发布时也必须控制 Precision。阈值要按错误严重度分层，不应把格式错误和错误事实混在同一个 F1 中。

### 9.4 闭环与恢复

```text
loop_rounds_per_run = total_loop_rounds / runs
useful_branch_rate = branches_contributing_final_evidence / branches_created
stop_correctness = correctly_stopped_or_continued_cases / evaluated_stop_cases
recovery_success_rate = resumed_runs_reaching_terminal / resumed_runs
replay_rate = idempotent_replays / completion_submissions
completion_conflict_rate = completion_conflicts / completion_submissions
rollback_rate = completion_rollbacks / completion_transactions
```

项目已埋点 `research.agent.completion.latency`、Payload Bytes、Candidate Cells、Commit、Replay、Conflict、Rollback，以及按 Dimension 记录的 Budget Released。它们证明完成边界可观测，不等于端到端 Research 质量已具备线上 SLO。

### 9.5 Research 成本效率

```text
cost_per_verified_cell = total_run_cost / verified_cells
cost_per_accepted_source = total_fetch_and_model_cost / accepted_sources
verification_yield = newly_verified_cells / additional_loop_cost
marginal_gain_per_round = quality_delta / incremental_cost
```

最后一轮只增加 0.5% Coverage 却消耗大量 Token，说明 Stop Contract 应收紧。QUICK 与 DEEP 模式的预算和质量目标不同，不能把两者混合平均。

## 10. Agent 执行框架与 Artifact 指标

### 10.1 编译与运行

```text
compile_success_rate = valid_execution_specs / compile_requests
run_success_rate = successful_runs / accepted_runs
node_first_pass_rate = nodes_passed_without_repair / executed_nodes
node_retry_rate = retried_node_attempts / initial_node_attempts
waiting_rate = runs_entering_waiting / accepted_runs
waiting_age = now - waiting_since
```

编译失败是请求在执行前被 Schema、Graph 或 Capability 校验拦住；运行失败是合法 Spec 执行后失败。两者混在一起会误判 Provider 稳定性。

### 10.2 工具、Provider 与 Capability

```text
provider_success_rate = successful_provider_calls / provider_calls
provider_fallback_rate = runs_using_non_primary_provider / provider_routed_runs
tool_success_rate = successful_tool_calls / tool_calls
capability_denial_rate = denied_capability_requests / capability_requests
approval_wait_time = approval_resolved_at - approval_requested_at
```

Provider 成功率按用途、模型和错误分类分组，不能用动态 URL 或 Request ID 做 Tag。Fallback 成功仍需验证是否满足相同输出契约与能力边界。

### 10.3 Verifier、Repair 与写回

```text
first_pass_yield = outputs_passing_final_contract_first_time / generated_outputs
repair_rate = outputs_requiring_repair / generated_outputs
repair_success_rate = repaired_outputs_passing_contract / repair_attempts
repair_amplification = total_generation_attempts / successful_outputs
writeback_conflict_rate = version_conflicts / writeback_attempts
```

局部 Repair 的价值要同时看通过率、正确区域变化率和 Token 节省。修复率很高可能说明 Verifier 有价值，也可能说明首轮 Prompt 或模型选择有问题。

### 10.4 当前埋点

Artifact Outbox 已有 `noteweave.artifact.outbox.dispatched`、`failed`、`dead_lettered` 和 `redriven`。任务状态非法迁移有 `noteweave.task.invalid_transition{from,to}`。建议补充 Spec 编译延迟、Node Attempt 延迟、Waiting 数与年龄、Provider/Tool 调用结果、Repair 和写回冲突的正式 Micrometer 指标。

## 11. Context 与 Memory 指标

### 11.1 Token 与压缩

```text
compression_ratio = summary_tokens / source_tokens
token_saving_ratio = (raw_context_tokens - compiled_context_tokens) / raw_context_tokens
budget_utilization = selected_tokens / maximum_tokens
truncation_rate = runs_with_truncation / compiled_runs
```

Compression Ratio 越低不代表越好，压缩过度会丢数字、否定和例外。应与关键约束保留率一起看：

```text
constraint_retention = retained_gold_constraints / gold_constraints
```

### 11.2 Summary 并发与新鲜度

```text
stale_summary_rate = stale_builds / completed_summary_builds
promotion_success_rate = promoted_revisions / ready_revisions
summary_freshness_lag = promoted_at - source_head_at
duplicate_build_rate = redundant_builds / summary_builds
```

Stale Rate 突然升高可能是用户消息频率增加、Worker 变慢或触发阈值过于积极。不能简单追求 0，因为并发会话中主动阻断晚到版本本来就是正确行为。

### 11.3 Memory 质量与治理

```text
candidate_acceptance_rate = promoted_candidates / reviewed_candidates
memory_precision = useful_recalled_memories / recalled_memories
memory_recall = recalled_relevant_memories / all_relevant_memories
conflict_rate = candidates_conflicting_with_active / candidates
negative_feedback_rate = negative_outcomes / applied_memories
deletion_propagation_time = last_derived_removal_at - delete_committed_at
```

Memory Precision 低会污染 Prompt，通常比 Recall 低更危险。Gold Relevant Memory 很难构造，应使用人工标注会话、显式用户纠正和 Outcome Feedback 组合评估。Utility 是排序信号，不是准确率。

### 11.4 Replay Fidelity

```text
snapshot_replay_fidelity = matching_replay_inputs / replay_attempts
manifest_completeness = present_required_manifest_fields / required_manifest_fields
```

模型输出含随机性时，不要求文本逐字一致。可比较 Spec、History Head、Summary Revision、Memory Revision、Evidence Identity、Provider 参数和关键结构约束。隐私删除后 Replay Degraded 属于预期边界，应从普通失败中区分。

### 11.5 当前埋点

项目已记录 `noteweave.memory.compiler.db.load{phase,result}` Timer，并通过统一缓存 Counter 记录 `memory_compiled_pack` 的结果。建议补 Token Budget 分布、截断、Summary Stale/Promotion、Candidate 状态、Outcome 和删除传播指标。

## 12. 实时流式与 SSE 指标

项目已埋点 Answer/Conversation 两套事件指标，包括 Active Subscribers、Published、Replayed、Cursor Expired、Replay Trimmed、Delta Coalesced、Subscriber Overflow、Dispatch Rejected、Bridge Unavailable，以及 Redis Publish/Read/Error/Duplicate/Cancel。

```text
replay_success_rate = successful_replay_connections / replay_requests
cursor_expiry_rate = expired_cursor_requests / replay_requests
subscriber_overflow_rate = overflowed_subscribers / subscriber_sessions
delta_coalescing_ratio = coalesced_deltas / published_deltas
bridge_error_rate = bridge_errors / bridge_operations
```

Delta Coalescing 降低调度压力，但可能增加单次可见延迟；Overflow 表示慢消费者或队列过小；Replay Trimmed 只说明缓冲区淘汰发生，需结合 Cursor Expired 才知道用户是否受影响。活跃连接数要与 SSE Connection Pool、Dispatch Pool 和 Redis Bridge 饱和度一起看。

## 13. 配额、公平性与背压指标

项目已埋点：

| 指标 | 主要 Tag | 作用 |
|---|---|---|
| `noteweave.quota.decisions` | control、workload、result、backend | 速率或并发控制的决策分布 |
| `noteweave.quota.rejections` | control、workload、backend | 被拒绝的工作量 |
| `noteweave.quota.lease.recovered` | workload、backend | 清理并恢复的过期租约 |

```text
quota_rejection_rate = rejected_decisions / quota_decisions
lease_recovery_rate = recovered_expired_leases / acquired_leases
workspace_fairness = min(workspace_success_share / workspace_demand_share)
```

公平性也可用 Jain 指数衡量各租户得到的吞吐：

```text
Jain = (sum(x_i))^2 / (n * sum(x_i^2))
```

范围为 `1/n` 到 1，越接近 1 越均匀。但不同 Workspace 套餐和权重不同时，应先把吞吐除以各自权重，不应追求绝对平均。

## 14. 安全指标

项目已埋点 ACL Cache、ACL DB Load 和 `noteweave.security.access.denied{reason,resource}`，并有 Scope Violation、内部认证与生产配置 Guard 的可审计路径。

```text
authentication_failure_rate = failed_authentication / authentication_attempts
authorization_denial_rate = denied_authorization / authorization_checks
scope_violation_rate = blocked_cross_scope_candidates / checked_candidates
token_replay_detection_rate = replayed_refresh_tokens / refresh_attempts
mean_time_to_revoke = enforcement_at - revocation_committed_at
```

Denied 增加可能是攻击，也可能是前端 Bug、权限变更或缓存版本问题，要按受控 Reason 分类。安全指标不应包含原始 Token、用户输入、URL 或敏感对象 Key。误报率与漏报率需要人工确认样本，不能从拒绝次数直接推导。

## 15. 数据库、Redis、Kafka、MinIO 与 ES 基础设施指标

### 15.1 MySQL/Hikari

关注 Active、Idle、Pending Connections，获取连接耗时、查询 P95、慢查询、锁等待、死锁、事务回滚、Buffer Pool 命中、复制延迟和磁盘使用。派生公式：

```text
pool_utilization = active / max
connection_wait_rate = pending_requests / db_requests
transaction_rollback_rate = rollbacks / transactions
```

### 15.2 Redis

关注命令延迟、错误、连接使用、内存、Eviction、Keyspace Hit/Miss、Lua 耗时、主从延迟和持久化状态。缓存命中率、配额拒绝率与 Redis 健康必须分开，Redis 正常也可能因为策略产生拒绝。

### 15.3 Kafka

关注 Producer Error/Retry、Request Latency、Under Replicated Partitions、ISR Shrink、Consumer Lag、Rebalance、Fetch Rate 和磁盘。业务 Outbox 成功不能替代 Broker 可靠性指标。

### 15.4 MinIO

关注 Put/Get/Delete 延迟与错误、吞吐、对象数、存储容量、磁盘故障和孤儿对象。对象上传成功但数据库回滚产生的孤儿应通过业务对账计算，不会自然出现在普通存储错误率中。

### 15.5 Elasticsearch

关注 Search/Index P95、Bulk Reject、Refresh/Merge、JVM Heap、GC、Thread Pool Queue、Shard 状态、磁盘水位和索引文档数。Projection 正确性还要用 MySQL Snapshot 与 ES Document 的版本和数量对账，Cluster Green 不等于业务投影完整。

## 16. LLM 与成本指标

### 16.1 Token 与调用成本

Research Worker 已记录每次调用的 Input Tokens、Output Tokens、Attempts、Latency、Purpose、Provider/Model 和 Estimated Cost，并能汇总 Usage。费用公式为：

```text
llm_cost = input_tokens / billing_unit * input_price
         + output_tokens / billing_unit * output_price
```

如果价格按百万 Token，`billing_unit = 1,000,000`。缓存 Token、Reasoning Token 或工具费用需要按 Provider 账单规则单列，不能全部套同一单价。

### 16.2 单位经济性

```text
cost_per_successful_answer = total_answer_cost / successful_answers
cost_per_ready_snapshot = pipeline_cost / ready_snapshots
cost_per_verified_research = research_cost / verified_research_runs
cost_per_saved_artifact = artifact_cost / saved_verified_artifacts
```

总成本应包括模型、Embedding、Rerank、搜索/抓取、存储、消息、计算、重试和人工 Review。模型账单低不代表单位成功结果便宜，Repair 与失败重试可能放大成本。

### 16.3 重试与边际收益

```text
retry_cost_ratio = cost_of_retry_attempts / total_cost
repair_cost_ratio = repair_cost / generation_cost
cost_efficiency = accepted_quality_units / total_cost
marginal_quality_per_cost = quality_delta / incremental_cost
```

质量单位必须固定，比如 Verified Cell、通过 Contract 的 Artifact 或 Gold Query 的 NDCG，不能用不可比较的主观总分。

## 17. 测试、发布与演进证据指标

```text
test_pass_rate = passed_tests / executed_tests
flaky_rate = tests_with_inconsistent_outcome / executed_tests
defect_escape_rate = production_defects / total_detected_defects
change_failure_rate = failed_deployments / deployments
deployment_frequency = deployments / time_window
lead_time_for_change = production_at - change_committed_at
```

覆盖率包括 Line、Branch 和 Mutation Coverage，但高覆盖率不能证明状态机与故障窗口正确。NoteWeave 更应统计关键不变量覆盖：Outbox 发布前后崩溃、旧 Lease Owner 晚到、重复 Callback、Summary Stale Promotion、Scope 隔离、删除传播和缓存故障降级是否都有测试。

发布门禁建议把功能、质量、容量和恢复分开：契约与集成测试通过；Gold/Shadow 指标不回退；P95 与成本在预算内；备份/重建或故障注入满足 RTO；安全配置 Guard 通过。当前仓库测试可以证明具体 Fixture 与失败窗口，不能替代生产演练。

## 19. Dashboard 与告警组合

### 19.1 总览页

总览只放用户结果和系统风险：成功结果数、端到端 P95、失败率、降级率、单位成功成本、最老积压年龄、Security Denial 异常变化和 SLO Burn Rate。不要把 JVM、Kafka、ES 的几十个图都堆在首页。

### 19.2 链路页

资料链路看 Upload、Outbox、Kafka、Parse、Projection、READY 与删除；回答链路看 Run、Retrieval、TTFT、Provider、Stream 和 Terminal；Agent 链路看 Compile、Queue、Node、Waiting、Verifier、Repair 和 Writeback；Context 页看 Token Budget、Summary、Memory、Cache 和 Replay。

### 19.3 告警原则

告警优先使用症状和持续时间：用户成功率下降、P95 超预算、最老 READY 年龄持续增长、DLQ 新增、Subscriber Overflow、Waiting Age 超限。CPU 高但用户无影响可以先记录，不能让原因型告警淹没症状型告警。每条告警应附带 Runbook：确认哪个身份、查哪张状态表、看哪个依赖、如何限流/暂停 Redrive、怎样验证恢复。

## 20. 面试计算题与完整回答

### 20.1 为什么平均延迟 200 ms，用户仍然觉得慢？

平均值会被大量快请求拉低。假设 95 个请求 100 ms、5 个请求 2.1 s，平均约 200 ms，但最慢 5% 用户明显受影响。应报告 P50、P95、P99，并按接口、Workspace 负载和 Provider 分组。流式场景还要区分 TTFT 与完整完成时间。

### 20.2 100 QPS、平均耗时 2 秒，需要多少并发？

按 Little 定律，平均在途约 `100 * 2 = 200`。这只是平均值，还要给 P95 耗时、突发系数、连接池和下游配额留余量。若只有 50 个并发槽，稳定吞吐无法达到 100 QPS，队列会增长。

### 20.3 Kafka Lag 为 10 万，多久能恢复？

不能只用 Lag 回答。若 Consumer 每秒处理 300 条，新消息每秒进入 100 条，净清空速率为 200 条/秒，约 500 秒清空。若两者相等，永远清不完。消息处理成本差异大时，还要看最老事件年龄和业务 Projection Lag。

### 20.4 命中率从 80% 提高到 90%，收益是多少？

需要 Origin 与 Cache 延迟。每秒 1000 次查询，Origin 20 ms、Cache 1 ms，命中率提升 10 个百分点，每秒减少 100 次 Origin，粗略节省 1900 ms 的累计等待和相应数据库负载。若缓存结果经常 Stale 或构建昂贵，还要减去错误与失效成本。

### 20.5 Recall@5 为 100%，RAG 就好吗？

不能。相关证据可能都进了 Top 5，但顺序差、无关候选多、证据被 Budget 截掉、Citation 未引用，或者生成不忠于证据。还要看 Precision/NDCG、Evidence Selection、Citation Support、Faithfulness、延迟与成本。

### 20.6 Repair Rate 高说明 Verifier 很强吗？

不一定。高 Repair Rate 可能说明 Verifier 找到了问题，也可能说明首轮生成质量差、Contract 过严或误报多。需要同时看 First Pass Yield、Verifier Precision/Recall、Repair Success、总 Token 放大和正确区域是否被改坏。

### 20.7 99.9% 可用性每月能坏多久？

30 天约 43.2 分钟。对请求型 SLO 更适合用坏事件数量计算。还要说明哪些请求 Eligible，计划维护是否排除，降级结果是否算 Good Event。

### 20.8 为什么配置了 20 个数据库连接，不能说支持多少 QPS？

QPS 取决于每个请求持有连接的时间、查询数量、事务长度、慢查询、锁竞争和其他共享任务。若平均每个请求占连接 50 ms，理论上限约 `20 / 0.05 = 400 QPS`，但这是忽略网络、事务冲突、后台任务和长尾的理想值。实际容量必须压测并保留饱和余量。

## 21. 面试中回答指标题的固定结构

一个指标至少讲六件事：它回答什么业务问题；分子和分母是什么；统计窗口与聚合方式；数据从哪里采集；指标变坏可能有哪些原因；它不能证明什么。涉及方案比较时再补基线、Delta、成本和显著性。

推荐口径：

```text
1. 先定义用户结果或系统不变量
2. 给公式、单位、窗口和维度
3. 说明项目中的采集点与现有成熟度
4. 给一个带数字的计算例子
5. 解释异常时如何下钻到下一层指标
6. 主动说明误区、Trade-off 和未完成边界
```

不要孤立报“QPS 多少”“准确率多少”。完整的容量结论至少包含负载模型、输入分布、机器与依赖配置、P95/P99、错误率、持续时间和成本；完整的 AI 质量结论至少包含 Dataset Version、样本量、标注规则、Baseline、绝对 Delta、失败切片和是否经过线上验证。
