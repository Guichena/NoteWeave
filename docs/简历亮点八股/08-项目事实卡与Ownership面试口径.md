# 项目事实卡与 Ownership 面试口径

> 本文是所有面试包装的事实闸门。架构方案可以依据源码组织成理想叙事，但团队规模、本人职责、开发时间、学校真实用户、事故、流量、成本和业务收益只能填写本人可证明的信息。故障故事的证据规则见[真实缺陷排查](09-真实缺陷排查与复盘案例.md)，百分比和样本数的证据规则见[数字生成手册](29-业务指标埋点与简历数字生成手册.md)。

> 使用边界：这份事实卡只允许填写本人可证明的信息。仓库事实标 `[当前实现]`，固定回放与故障注入标 `[已测-模拟]`，生产补全标 `[目标设计]`，真实用户、流量、成本和业务结果在没有证据时统一标 `[生产待验证]`。

## 1. 为什么需要事实卡

架构讲得越完整，面试官越会检查真实性。技术方案可以从源码确认，开发周期、团队规模、个人职责、真实流量和业务结果只能由候选人本人确认。没有事实依据的字段宁可留空，也不能根据代码量推断。

事实分为四档：

| 类型 | 定义 | 面试表达 |
|---|---|---|
| 真实运行数据 | 来自真实用户、日志、监控或账单 | 可以报告时间窗口、样本和数值 |
| 测试证据 | 来自自动测试、Fixture、故障注入或隔离环境 | 明确说是测试结果 |
| 配置上限 | 文件大小、连接池、配额、TTL 等参数 | 只能说系统限制，不能说实际容量 |
| 设计与估算 | Little 定律、容量模型、生产演进方案 | 明确说是设计或估算 |

### 2.2 学校原型与面试改造怎样划边界

学校原型解决的是课程资料分散、站内搜索弱、通用模型回答没有课程来源的问题。与这个目标直接相关的是 Workspace、ACL、Source、不可变 Snapshot、异步解析、QA/Note/Wiki、Citation、SSE 和删除传播。它们能组成一条完整的课程资料生命周期：教师维护资料，学生只在授权课程范围内检索，回答绑定原始证据，资料更新或撤回后旧投影失效。

Deep Research、Artifact、Memory 风险分层、跨 Provider 恢复和完整发布门禁可以解释为后续工程化改造。它们扩展了课程调研、实验报告或学习产物场景，也明显超出一个校内 MVP 的必要范围。面试时主动承认这部分包含工程研究和能力展示目的，能够回答“为什么个人项目这么复杂”，也能避免把所有复杂度都包装成学校的刚性需求。

当前权限模型还有一个需要主动说明的真实缺口：`WorkspaceRole` 中 `OWNER` 拥有全部权限，`EDITOR` 可以写资料、运行回答、维护知识和执行任务，`VIEWER` 只有 `WORKSPACE_READ`。如果学生需要直接提问，不能简单把学生映射为当前 `VIEWER`，应新增只允许 `WORKSPACE_READ + ANSWER_RUN` 的 `LEARNER` 角色，或者把问答权限做成独立可配置能力。直接扩大 `VIEWER` 会改变已有只读语义，也可能让原本只需查看结果的成员产生 Provider 成本。

### 2.3 AI 协作边界怎样回答

`[本人已确认]` 这个项目只有一名人类开发者。AI 编程工具参与过代码草稿、测试样例、资料检索、方案比较、文档整理和审查提示，但没有独立的需求所有权、生产权限或结果责任。需求是否成立、方案是否采用、代码是否合并、测试是否足够、文档中的数字能否对外使用，都由本人判断并承担最终责任。

面试中可以说“个人独立负责并使用 AI 辅助开发”，不说“所有代码逐行手写”，也不把 AI 描述成另一个负责某模块的队友。面试官继续追问时，用下面四层证据回答：

1. **输入**：我给 AI 的业务约束、失败窗口、接口契约和验收条件是什么。
2. **判断**：AI 给过哪些候选方案，我为什么采用、修改或拒绝其中一个。
3. **验证**：我怎样用源码审查、定向测试、故障注入、静态检查或运行结果确认它符合项目不变量。
4. **责任**：生成内容有错误时，由我定位、修正并更新测试和文档，不能把错误归因于工具。

一段可直接使用的回答是：

> 这是我一个人负责的项目，开发过程中用了 AI 编程工具辅助生成草稿、查资料和做代码审查。架构边界、业务不变量、方案取舍、测试设计和最终验收由我负责。AI 给出的实现我不会直接当成正确答案，例如 Research Agent 的停止策略、Lease/Fencing 和完成协议，我都要回到状态机、失败窗口和定向测试逐项确认。所以我说的独立负责，指没有其他人类开发者，并且我对最终结果负责，不等于每一行代码都由我手工输入。

这段口径仍不能替代具体 Ownership 证据。至少准备一个 AI 草稿存在问题、本人通过审查或测试发现并修正的真实提交；如果暂时不能从 Git 或记录中定位，就把它作为面试前补证项，不临场编造。

## 3. 当前仓库能够证明的事实

NoteWeave v2 是 Java Host 加 Python Worker 的知识工作系统。Java 侧负责 Workspace 权限、MySQL 业务状态、Outbox、配额、回调和写回，Research/Artifact Worker 负责模型、搜索、内容处理和工具执行。核心存储与中间件包括 MySQL、Redis、Kafka、MinIO 和 Elasticsearch。

仓库能够证明五条技术主线：场景化 RAG、验证驱动 Deep Research、事件驱动资料底座、受约束 Agent 执行框架、Context/Memory 治理。代码审查记录还确认了同事务 Outbox、Claim Fencing、Redis Lua 配额、RRF、批量 Ownership 校验、不可变输入快照、Summary Promotion 和有界事件重放等实现。

测试证据必须带时间边界。2026-07-31 的历史审查快照曾记录一组 Backend、Frontend 和两个 Worker 的数量，但它不是当前命令输出，也不能代表线上可靠性。面试时应重新运行对应命令，报告版本、环境、Skipped 和失败重试情况。

仓库没有证明真实线上用户量、QPS、线上准确率或统一生产 SLO。内部 6 条 RAG Fixture 也不是在线融合检索准确率；这些指标应在规模和运行约束明确后用压测与线上数据补齐。

### 4.1 学校场景的完整演练回答

> 下文是一份学校场景演练答案。项目来源、唯一人类开发者和本人负责全项目已经确认；目标用户映射、试用范围和理想指标仍是 `[演练假设-待本人确认]`，补出原始数据后才能写进简历。

NoteWeave 最初是我为学校场景做的课程资料服务。教师和助教把课件、实验说明和参考资料放进课程 Workspace，学生在授权范围内提问，系统返回带原文引用的回答，也能按 Note 或 Wiki 方式深读和组织知识。当前 v2 的重构从 2026 年 5 月开始，项目由我独立负责，并使用 AI 编程工具辅助开发。我负责领域拆分、Java 控制面、Python Worker、前端、资料异步化、检索策略、长任务恢复、测试和评测体系，所有生成内容都由我审查和验收。

初版把上传、解析、检索和生成放在比较直接的同步流程中，适合先验证功能。资料变大、课程并发集中在考试周以后，同步请求会被解析和模型调用占住；MySQL、对象存储和索引之间也没有一个跨系统事务，失败后可能出现数据库有记录但资料不可检索，或者对象和索引没有清理干净。我把 MySQL 定为业务真源，用 MinIO 保存原文件，用 Transactional Outbox 和 Kafka 传递解析、索引和长任务命令，Elasticsearch 只保存可重建投影。Consumer 按 Snapshot Version 幂等处理，任务通过 Lease、Attempt 和 Fencing 防止旧 Worker 晚到覆盖新状态。

检索没有只做一条通用 RAG。QA 面向快速问答，使用关键词和向量 Hybrid、RRF、可选 Rerank 与最终 Ownership 校验；Note 面向围绕指定资料的连续阅读；Wiki 面向稳定页面、版本和关系。后续为了课程调研和面试展示，我又补了可恢复的 Deep Research、受约束 Artifact Skill，以及 Context/Memory 的版本和审核机制。我会明确说明这些是 v2 的工程化扩展，不会把它们全部说成学校 MVP 的必要功能。

理想演练数据中，可以把结果回答成“在 8 个课程 Workspace、216 名受邀用户的 30 天试用口径下，174 人完成激活，激活率 80.6%；2,934 个已接受任务中有 2,846 个通过业务完成条件，成功率 97.0%；320 条分层 QA Gold 上，Hybrid 相比 BM25 的 Recall@5 从 0.742 提升到 0.869，Citation Support 为 91.8%，Scope Violation 为 0；小于 10 MB 的资料从 Accepted 到 Projection Ready 的 P95 为 18.6 秒”。这些数字当前只用于演练，真实简历必须换成带 Manifest、日志和标注记录的结果。

我最有代表性的复盘是 Outbox 最后一次 Claim 后进程退出。早期实现有 Lease 和重试，但 Attempts 耗尽后没有扫描器把过期的 `PROCESSING` 任务推进到 Dead Letter，任务可能永久卡住。我补了过期耗尽扫描、Attempt CAS 和旧 Owner Fencing，并用 Claim 后退出、多扫描器竞争和重复回调测试验证只发生一次终态迁移。这个案例比单纯说“用了 Kafka”更能代表我对失败窗口和系统不变量的理解。

## 5. “你具体负责了什么”如何回答

回答必须包含动作、边界和证据。不要说“负责整个后端”，应说：

```text
我负责的决策：为什么拆这个边界，比较过哪些方案
我写的核心模块：类、状态机、协议或测试
不属于本人实现的部分：框架默认能力、第三方中间件和 AI 工具本身
我推动的验证：哪类测试、审查或基准
我承担的结果：修复了什么失败窗口，留下什么边界
```

可用回答模板：我主要负责 `[模块]`。我做的不只是接入 `[中间件]`，而是定义 `[业务不变量]`，实现 `[关键机制]`，并通过 `[测试证据]` 验证。`[不属于本人或未完成部分]` 不在我的责任范围，我在文档中把它标成演进方向。

## 7. 大厂面试官常见真实性追问

### 7.1 这是个人项目，为什么做得像大型系统？

先承认项目性质，再解释设计来源。个人项目可以研究复杂边界，但不能包装成服务百万用户。回答重点是哪些问题通过失败测试真实复现，哪些能力只是为演进保留。复杂度没有真实需求支撑时，也要承认某些模块偏工程研究性质。

### 7.2 为什么没有线上数据？

没有就直接说没有。随后给出当前证据层级：契约测试、真实基础设施集成测试、故障注入、隔离 MySQL/Flyway 验证和内部 Fixture。再说明若上线会先补哪些 SLI、压测和灰度门禁。诚实边界比编一个 QPS 更重要。

### 7.3 你做错过什么决策？

从真实审查记录选择一项。比如把 Polling Outbox 的重试与 Lease 设计完整后，仍遗漏了“最后一次 Claim 后进程崩溃”的窗口；修复时增加过期 Lease 兜底扫描、Attempt CAS 和终态测试。回答要落到为什么第一次没考虑到，以及如何改变后续设计方法。

### 7.4 哪些说法最容易被追问戳破？

- 说“有统一意图识别”，却只能指出 QA Rewrite、Research Intent 或 Artifact Skill 中的一处。
- 说“Replan 能减少成本”，却没有 Plan Diff、失效范围、重复动作和单位成功成本。
- 说“系统支持高并发”，却只有线程池和连接池默认值，没有工作负载、窗口与压测 Manifest。
- 说“定位到根因”，却只能给出同时发生的指标，没有排除过程、反证和修复后重放。
- 说“我独立负责”，却不能说明本人做过的决策、失败判断、关键测试和未完成边界。

遇到这些追问时不要扩大叙述。回到当前仓库能证明的对象、状态、配置和测试，再把缺少的统一合同、生产数据或个人事实明确标成待验证或待填写。

### 8.1 学校场景的产品判断

**用户和核心任务**，教师或助教负责维护课程资料和知识结构，学生负责查找依据、理解指定材料和完成调研。管理员关注成员、课程隔离、资料撤回和成本。北极星指标不是登录人数，而是每周产生至少一个可验证有效结果的活跃课程 Workspace。

**为什么不只用网盘或通用大模型**，网盘能保存文件，但难以回答“这条结论来自哪一页、当前课程使用的是哪个版本”；通用大模型能生成答案，却无法天然保证只使用当前课程资料，也无法在教师撤回资料后同步撤销引用。NoteWeave 的差异点是 Workspace Scope、不可变 Source Snapshot、Evidence Manifest、版本化投影和删除传播。

**学校 MVP 应保留什么**，第一阶段只保留课程 Workspace、教师上传、异步解析、学生带引用 QA、资料状态、权限和删除。Note/Wiki 可以作为第二阶段的深读与知识组织，Deep Research 用于课程调研或毕业设计资料综述。Artifact 和复杂 Memory 治理不是校内 MVP 的前置条件，时间不足时优先关闭，而不是牺牲权限、引用和删除正确性。

**采用阻力**，教师需要整理和更新资料，扫描 PDF 可能需要 OCR，学生会把“回答流畅”误解为“回答正确”，学校还会关心试卷、未公开课件和学生数据的保留。产品上要展示引用和资料版本，支持问题反馈与教师纠错；工程上要按课程隔离、记录撤权和删除传播，并把低证据问题明确拒答。

**如何判断值得继续做**，先看课程激活率、Time to First Value、有效回答采纳率、教师纠错率和每个成功结果成本。若教师维护成本没有下降，或者大量回答仍需要人工重写，继续增加 Agent 能力不会解决核心问题，应先改资料接入、引用可读性和纠错闭环。

## 9. 项目介绍类常见八股

### 9.1 请用三分钟介绍项目

三分钟回答不能把组件名单当主线。前四十秒说明用户和核心任务：NoteWeave 面向需要管理资料、检索知识并执行长任务的知识工作场景。接下来一分钟讲 V0 为什么失效，同步上传、检索和生成在文件变大、任务变长后产生请求阻塞、跨存储不一致、失败无法恢复和上下文污染。再用一分钟讲三个关键选择：MySQL 保存业务真源与任务状态，Outbox/Kafka 把跨系统工作异步化；检索按 QA、Note、Wiki 拆策略并保留可重建投影；Agent 使用不可变 ExecutionSpec、Lease/Fencing 和受控 Capability 执行。最后二十秒说证据与边界，指出当前有契约、集成、故障窗口和质量 Fixture；如果面试官继续追问规模，再补充队列、连接池、索引和 Provider 的容量口径。

面试官继续追问时，先让他选择感兴趣的链路，不需要一次说完五个亮点。若追问“你做了什么”，只讲本人确认过的模块、设计决策和测试；若追问“系统多大”，给真实代码、测试或数据规模，未知就说明尚未做生产压测。项目介绍的目标是建立问题与决策的因果关系，不是证明组件越多越好。

介绍中还要主动给出一个 Trade-off。比如采用异步化后，上传接口更快且任务可恢复，但用户必须理解 PROCESSING 到 READY 的窗口，系统也增加 Outbox、Consumer、DLQ 和对账。采用不可变 Snapshot 后可以稳定回放，却要承担存储和删除降级成本。面试官若追问“最初为什么不直接这么做”，可以说明 V0 的目标是验证用户链路，只有当任务时长、跨存储和多租户约束出现后才值得引入复杂度。若继续追问演进，就从队列年龄、锁等待、索引延迟、任务时长和恢复窗口等可观测信号回答。

### 9.2 为什么选这些中间件，有没有过度设计

回答每个中间件时都用“它承载哪个已经存在的业务语义”。MySQL 承载 Source、Snapshot、Job、ACL 等真源状态，因为这些对象需要事务、唯一约束和条件更新。Kafka 承载可重放的异步事件流，解决解析、索引和派生工作不应阻塞上传请求的问题。Redis 承载短期配额、并发租约、缓存和多实例实时桥接，它丢失后允许降级或重建，因此不作为业务真源。Elasticsearch 保存可重建检索投影，MinIO 保存大对象正文。中间件不负责自动解决一致性，Outbox、幂等、版本和对账仍由业务协议定义。

判断是否过度设计要回到失效条件。若只是单机 Demo，同步调用和数据库轮询更简单；当任务持续数分钟、需要崩溃恢复、检索与写入解耦、多租户限制 Provider 成本时，持久状态机和异步调度才有价值。当前 Docker Compose 用于开发与演示，面试官问“为什么不用某某新技术”时，比较当前约束、团队成本、故障模式和规模触发条件，不用先进性作理由。

可以再逐个说未选方案。Redis Stream 能减少一个中间件，但当前 Kafka 更适合资料事件的保留与多 Consumer；直接用 ES 作真源能减少 Hydration，却难以承载事务、Ownership 和可审计状态；自由 Agent 灵活，却让长任务恢复、权限和成本边界不稳定。未选方案并非错误，在流量、团队或产品目标变化后可能重新评估。技术选型的验证证据应包括故障注入、吞吐与长尾、运维复杂度和数据恢复，而不是“大家都在用”。

如果面试官要求删掉一个组件，可以优先讨论早期用 MySQL Outbox Polling 直接驱动 Worker，暂缓 Kafka；当 Consumer 数量、保留重放和积压吞吐成为瓶颈后再迁移。这个回答能证明架构允许分阶段演进，而不是所有组件缺一不可。

### 9.3 项目最难的点是什么

“难”要落到一个可复现的工程矛盾。可选择跨存储一致性：上传同时涉及对象存储、MySQL、Kafka 和 ES，无法用一个本地事务覆盖，任何外部 I/O 前后崩溃都会留下不同状态。解决方式是划分真源与投影，事务内提交业务状态和 Outbox，事务外投递，Consumer 幂等，Projection 带版本，对失败任务提供 Retry、DLQ、对账与重建。代价是用户会看到从上传完成到可检索之间的最终一致窗口，系统也要维护更多状态和监控。

也可以选择长任务恢复或 Context 一致性，但一场面试只选本人最熟的一项。完整答案要包含最初误判、失败窗口、最终不变量、测试证据和规模边界。只说“技术难度高”“并发量大”不能支撑追问。若项目没有真实高并发，难点可以是正确性和可恢复性，不需要编造流量。

以长任务为例，难点不是把任务丢给 Worker，而是处理 Claim 后崩溃、Heartbeat 暂停、旧 Worker 晚回调、Provider 已成功但 ACK 丢失和恢复后输入漂移。系统通过持久 Job/Attempt、冻结 ExecutionSpec、Lease/Epoch、Waiting/Resume 和幂等 Receipt 建立不变量，代价是状态机与清理工作增加。验证要卡住每个关键 I/O 前后制造崩溃，断言最多一个新 Owner 可确认结果，同时允许重复执行被安全吸收。这样回答能从业务困难一直落到底层并发控制。

第三层追问通常是“规模继续扩大后怎么做”。可以回答先观察队列年龄、调度公平性、Provider 中断时长、工具副作用和恢复窗口，再针对瓶颈增加隔离、配额、补偿和演练。这样既能说明当前协议的边界，也能自然引出演进触发条件。

### 9.4 如何证明这是你的设计

可验证的 Ownership 来自四类证据：能解释为何选这个抽象；能画出状态变化与失败窗口；能指出代码、迁移和测试的具体位置；能说出方案不理想的地方以及下一步触发条件。只会说组件作用，可能只是阅读过项目；能解释旧 Owner 为什么会晚到、为什么 Token 必须参与条件更新、测试如何卡在 Claim 后崩溃，才接近真实参与。

回答时也要明确协作边界。这个项目没有其他人类开发者，但 AI 辅助生成和开源组件能力仍要单独说明。个人价值体现在需求拆解、架构选择、验收标准、故障测试和代码评审，不需要声称每行代码都手写。三层追问最终会落到具体状态、日志和取舍。

准备时给每个亮点做一张 Ownership 表：问题怎样发现，AI 或外部资料提供过哪些候选，自己为什么做出当前选择，审查过哪些核心类或迁移，怎样设计测试并完成验收。面试官问到第三方框架或中间件内部能力时，先说明它不属于本人实现，再讲项目在其上增加的业务协议。能够指出一次自己的设计判断怎样被测试或审查推翻，以及之后怎样修改，比泛泛声称“负责整体架构”更可信。

证据还应能双向定位。口述 Token Rotation 时能指向数据库 Hash、条件更新和 Replay 错误；口述 Outbox 时能指出状态索引、Claim Token 和故障测试；口述 RAG 时能说明当前 Fixture 样本与线上评测的差距。若只能从代码名复述功能，却说不出决策背景与反例，Ownership 仍然薄弱。

面试前可让同伴随机挑一个状态字段，连续问“谁写、何时写、重复写怎样、失败后谁恢复、如何证明”。项目自有模块应能回答到 SQL 条件、错误码和测试窗口；框架、中间件与 AI 工具能力则讲清使用边界和项目增加的契约。不要背提交数量，提交量无法证明设计判断或业务责任。

### 9.5 项目取得了什么结果

结果分业务结果和工程结果。业务结果需要真实用户、任务完成率、检索质量或节省时间的数据，没有就不能虚构。工程结果可以陈述当前命令实际输出的测试文件和用例数量，但必须保留测试日期、环境、Skipped 和“测试通过不等于生产效果”的边界；旧审查稿中的固定数量不作为当前口径。

更好的后续证据是建立固定工作负载：上传到 READY 的延迟、Agent 成功率、恢复率、RAG Gold Set、TTFT、单位成功 Run 成本和故障注入结果。面试官问收益时，如果目前仍是个人或演示项目，可以直接说“当前主要证明工程可行性，没有线上业务收益数据”，再说明如果上线会怎样设计指标。真实而完整的验证计划，比编造提升百分比更可靠。

结果还要说明分母与对照组。任务成功率是否排除用户取消，RAG 准确率样本来自哪里，P95 在什么机器和数据规模下测得，都决定数字能否比较。没有业务基线时，可以报告能力边界，例如重复回调不会产生第二次终态、旧 Snapshot 不能覆盖新 Projection、100 个检索 Hit 的 Ownership 查询保持常数级，但不要把机制测试换算成用户提升。

面试官可能问“如果再给一个月做什么”。优先补真实度最高的缺口：固定容量工作负载、跨版本发布演练、备份恢复、在线 Shadow 指标和安全边界，而不是再接一个中间件。回答应给触发条件和验收标准，例如只有 Gold Set 与 Shadow 表明向量召回在质量收益上覆盖成本，才考虑独立向量库。

## 11. Ownership 回答的源码证据规则

Ownership 不能通过“我用了哪些技术”证明。每个声称由本人完成的亮点，面试前应准备一组可以现场展开的证据：一个业务入口、两个关键类、一个失败窗口、一个测试类和一个规模边界。比如讲 Outbox，可以从 `DurableOutboxDispatcher.claim()` 展开 Attempt CAS 和 Lease Owner，再说明最后一次 Claim 崩溃为何需要过期耗尽扫描；讲 RAG，可以从 `SourceRetrievalProjectionService.projectSnapshot()` 展开双 Projection 和维度校验，再说明首次启用必须 Rebuild；讲 Memory，可以从 `MemoryCompilerService` 展开 Scope 与 Token Budget，再说明 Memory 不进入 Evidence Rerank。

这组源码证据只能证明候选人理解仓库，不能单独证明实际开发过程。本人已经确认负责范围与 AI 协作边界；投入时间、生成代码的具体审查记录和结果数据仍要用个人记录、提交与测试补证。

## 当前事实卡

项目入口可从 `backend/src/main/java/com/noteweave` 的 Controller、Service、DAO 和 Flyway 迁移追溯，前端入口可从 `frontend/src/App.tsx`、`AuthGate.tsx` 和 `features/*` 追溯。Research 与 Artifact 的执行面分别在 `workers/research-worker`、`workers/artifact-worker`。本人已经确认对全项目负责，面试口径仍要指出可展示的 commit、测试和故障窗口，不能只用“仓库里有代码”代替过程说明。

## 12. 项目真实性与 Ownership 的 4 到 5 分钟完整回答

项目介绍不能从“我用了 Java、Kafka、RAG 和 Agent”开始，因为技术名称无法证明做过什么。更可靠的讲法是沿一条可追溯链路说明业务入口、决策、实现、验证和边界。例如资料上传这个亮点，可以先说用户需要把文件变成可检索资料，再说明为什么从同步解析改成 MinIO、MySQL、Outbox、Kafka 和 Projection；随后落到 `UploadService`、`SourceParseService`、`DurableOutboxDispatcher` 和 `SourceRetrievalProjectionFinalizer`，解释每个类在链路中的责任；最后给出重复提交、ES 写后 Finalize 失败、对象删除失败等故障测试，并说明容量结论仍需结合目标规模验证。

Ownership 要区分三种事实。仓库事实说明代码和测试实际存在；本人已经确认需求、设计、实现审查、测试和文档由自己负责，AI 提供辅助；结果事实仍要有真实指标、时间窗口和环境证据。面试前每个亮点至少准备一个用户入口、两个关键类、一次候选方案取舍、一个失败窗口和一个测试类，不能用“AI 生成后能运行”替代设计与验收过程。

回答技术取舍时，也要避免把调研结果包装成个人经历。可以说“我比较过 RabbitMQ 和 Kafka，当前需求需要分区、保留和 DLQ，所以选择 Kafka”，但不能说“我在生产把 RabbitMQ 切换成 Kafka”而没有发布、监控或回滚证据。对于其他方案，只在面试官追问具体规模或编排复杂度时说明它们的适用边界。对于没有真实数据的结果，使用“仓库测试证明了幂等和恢复机制”“当前只能给出容量计算方法”，不要填入虚构的 QPS、准确率、节省比例或线上用户数。

面试官追问“你遇到过什么问题”时，真实故障和场景推演必须分开。Outbox 回调可能永久卡在 `PROCESSING`、对象与 ES 清理可能不收敛、Windows MCP 输出可能编码失败、Maven 全量测试可能因 JVM 映射失败，这些可以按真实仓库证据讲；CPU 飙高、队列积压、连接池耗尽和 Provider 长时间超时则应标注为排障题或设计推演。这样回答会少一些夸张的故事，但能把事实、判断和假设边界分清，面试官继续追问时也能回到源码、测试和配置。

## 13. 主战故障案例卡：Outbox Claim 后进程退出

这是最适合用来证明 Ownership 的案例，因为它同时涉及业务语义、数据库条件更新、消息至少一次、租约恢复和测试证据。下面的回答可以直接作为母稿，但“我负责的代码”“实际命令”和“观察结果”必须由本人确认后替换。

### 13.1 90 秒回答

问题不是 Kafka 会不会重复，而是 Dispatcher 已经把 Outbox Claim 成 `PROCESSING`，随后进程在发送前或发送后退出，任务可能永久卡住，也可能被错误地再次确认。早期设计只覆盖了主动发送失败，没有把“最后一次 Claim 后进程退出”当成独立失败窗口。

我把它拆成四个状态事实：Outbox 行保存状态、Attempt、Lease Owner、Lease Until 和 Delivery Token；发送是否成功由外部 Broker 的结果决定，不能假设本地状态和网络响应原子完成；恢复器只接管已过期 Lease，旧 Owner 晚到时必须因为 Owner、Attempt 或状态不匹配而被拒绝；重复消息由 Delivery ID 和业务幂等键吸收。修复后增加过期扫描、Attempt CAS 和终态检查，并测试 Claim 后退出、发送成功确认丢失、重复回调和旧 Owner 晚到四个窗口。

### 13.2 四到五分钟回答

第一步先讲失败窗口。事务把业务状态和 Outbox 一起提交，只能保证“命令意图已经被记录”，不能保证 Dispatcher 已经把命令发送并把状态改成最终结果。Dispatcher Claim 时会把行从 `READY` 改为 `PROCESSING`，写入本次 Attempt、Lease Owner 和过期时间。此时如果进程退出，数据库里看起来像正在处理，但外部系统可能还没有收到命令；如果命令已经发送而响应在网络中丢失，下一次扫描又可能重复发送。这里不能追求跨数据库和 Broker 的全局原子提交，正确目标是命令不静默丢失、重复发送不产生第二个业务结果。

第二步讲修复不变量。恢复器只允许处理 `PROCESSING` 且 `lease_until` 已过期的行，并在接管时递增 Attempt 或 Lease Epoch。原 Owner 即使恢复后继续发送，也必须携带旧的 Owner 和 Attempt，条件更新影响行数为零时被解释为 Fencing 拒绝，而不是普通数据库异常。发送确认、回调收据和终态提交都要带稳定 Delivery ID；如果同一 Delivery 已经完成，接口返回已有结果；如果业务终态已经写入，重复请求只能幂等返回，不能再次写入对象、版本或事件。

第三步讲测试如何证明设计。测试一在 Claim 成功后立即终止进程，等待 Lease 过期，验证另一 Dispatcher 能接管并最终完成；测试二让 Broker 接收成功但让本地确认失败，验证重试不会创建第二个 Source、Version 或 Artifact；测试三让旧 Owner 在接管后晚到，验证条件更新影响行数为零且新 Owner 的结果不被覆盖；测试四重复提交同一个 Callback，验证 Receipt、终态和外部副作用都保持单份。每个测试都要记录输入状态、注入点、预期状态、实际状态和使用的命令。

第四步讲代价和边界。Lease 太短会把慢 Worker 误判为死亡，Lease 太长会延迟故障接管；Attempt 和 Receipt 增加了表字段、索引和清理成本；至少一次投递意味着消费者必须长期保持幂等。这个方案解决的是业务状态恢复，不等于任意外部副作用都可以回滚，所以对象删除、邮件发送或其他不可逆动作仍要单独设计 Preview、幂等键和补偿语义。
