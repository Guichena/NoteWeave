# 项目事实卡与 Ownership 面试口径

## 1. 为什么需要事实卡

架构讲得越完整，面试官越会检查真实性。技术方案可以从源码确认，开发周期、团队规模、个人职责、真实流量和业务结果只能由候选人本人确认。没有事实依据的字段宁可留空，也不能根据代码量推断。

事实分为四档：

| 类型 | 定义 | 面试表达 |
|---|---|---|
| 真实运行数据 | 来自真实用户、日志、监控或账单 | 可以报告时间窗口、样本和数值 |
| 测试证据 | 来自自动测试、Fixture、故障注入或隔离环境 | 明确说是测试结果 |
| 配置上限 | 文件大小、连接池、配额、TTL 等参数 | 只能说系统限制，不能说实际容量 |
| 设计与估算 | Little 定律、容量模型、生产演进方案 | 明确说是设计或估算 |

## 3. 当前仓库能够证明的事实

NoteWeave v2 是 Java Host 加 Python Worker 的知识工作系统。Java 侧负责 Workspace 权限、MySQL 业务状态、Outbox、配额、回调和写回，Research/Artifact Worker 负责模型、搜索、内容处理和工具执行。核心存储与中间件包括 MySQL、Redis、Kafka、MinIO 和 Elasticsearch。

仓库能够证明五条技术主线：场景化 RAG、验证驱动 Deep Research、事件驱动资料底座、受约束 Agent 执行框架、Context/Memory 治理。代码审查记录还确认了同事务 Outbox、Claim Fencing、Redis Lua 配额、RRF、批量 Ownership 校验、不可变输入快照、Summary Promotion 和有界事件重放等实现。

测试证据必须带时间边界。2026-07-31 的审查记录显示：Backend 755 个测试，0 Failure、0 Error、11 Skipped；Frontend 43 个文件、142 个测试并成功 Build；Artifact Worker 222 个测试；Research Worker 368 个测试。面试时要说“该次审查环境中的结果”，不能把测试数量表述为线上可靠性。

仓库没有证明真实线上用户量、QPS、线上准确率、生产 SLO、跨可用区容灾、完整 OpenTelemetry 或 Kubernetes 集群高可用。内部 6 条 RAG Fixture 也不是在线融合检索准确率。

我在 `[时间范围]` 做了 NoteWeave v2，这是一个面向 `[目标用户或使用场景]` 的知识工作系统。我的主要职责是 `[本人负责模块]`，团队分工是 `[团队与协作边界]`。最初版本把上传、检索和生成放在同步链路里，功能能跑，但文件变大、任务变长以后出现请求阻塞、跨存储不一致、Agent 难恢复和上下文污染。

## 5. “你具体负责了什么”如何回答

回答必须包含动作、边界和证据。不要说“负责整个后端”，应说：

```text
我负责的决策：为什么拆这个边界，比较过哪些方案
我写的核心模块：类、状态机、协议或测试
我没有负责的部分：框架默认能力、第三方中间件、他人模块
我推动的验证：哪类测试、审查或基准
我承担的结果：修复了什么失败窗口，留下什么边界
```

可用回答模板：我主要负责 `[模块]`。我做的不只是接入 `[中间件]`，而是定义 `[业务不变量]`，实现 `[关键机制]`，并通过 `[测试证据]` 验证。`[不属于本人或未完成部分]` 不在我的责任范围，我在文档中把它标成演进方向。

## 6. 五个亮点的 Ownership 证据表

| 亮点 | 需要本人确认的责任 | 可指向的工程证据 |
|---|---|---|
| Deep Research | 是否设计 Cell、Verifier、Checkpoint 与完成协议 | Worker、Research Java 包、契约测试 |
| RAG | 是否负责三策略、RRF、Rerank、Gold/Shadow | Retrieval Strategy 与 Eval 测试 |
| 资料底座 | 是否负责 Outbox、Consumer、Projection、Cleanup | Dispatcher、Migration、故障测试 |
| Agent 框架 | 是否负责 Skill Compiler、Quota、MCP、Writeback | Artifact Worker、Quota Service、跨服务契约 |
| Context/Memory | 是否负责 Snapshot、Summary、Memory Promotion | Conversation/Memory Service 与测试 |

“源码存在”只能证明项目实现，不能自动证明个人贡献。最终表述要与 Git 历史、实际协作过程一致。

## 7. 大厂面试官常见真实性追问

### 7.1 这是个人项目，为什么做得像大型系统？

先承认项目性质，再解释设计来源。个人项目可以研究复杂边界，但不能包装成服务百万用户。回答重点是哪些问题通过失败测试真实复现，哪些能力只是为演进保留。复杂度没有真实需求支撑时，也要承认某些模块偏工程研究性质。

### 7.2 为什么没有线上数据？

没有就直接说没有。随后给出当前证据层级：契约测试、真实基础设施集成测试、故障注入、隔离 MySQL/Flyway 验证和内部 Fixture。再说明若上线会先补哪些 SLI、压测和灰度门禁。诚实边界比编一个 QPS 更重要。

### 7.3 你做错过什么决策？

从真实审查记录选择一项。比如把 Polling Outbox 的重试与 Lease 设计完整后，仍遗漏了“最后一次 Claim 后进程崩溃”的窗口；修复时增加过期 Lease 兜底扫描、Attempt CAS 和终态测试。回答要落到为什么第一次没考虑到，以及如何改变后续设计方法。

## 9. 项目介绍类常见八股

### 9.1 请用三分钟介绍项目

三分钟回答不能把组件名单当主线。前四十秒说明用户和核心任务：NoteWeave 面向需要管理资料、检索知识并执行长任务的知识工作场景。接下来一分钟讲 V0 为什么失效，同步上传、检索和生成在文件变大、任务变长后产生请求阻塞、跨存储不一致、失败无法恢复和上下文污染。再用一分钟讲三个关键选择：MySQL 保存业务真源与任务状态，Outbox/Kafka 把跨系统工作异步化；检索按 QA、Note、Wiki 拆策略并保留可重建投影；Agent 使用不可变 ExecutionSpec、Lease/Fencing 和受控 Capability 执行。最后二十秒说证据与边界，指出当前有契约、集成、故障窗口和质量 Fixture，但没有可声称的生产百万流量或集群高可用数据。

面试官继续追问时，先让他选择感兴趣的链路，不需要一次说完五个亮点。若追问“你做了什么”，只讲本人确认过的模块、设计决策和测试；若追问“系统多大”，给真实代码、测试或数据规模，未知就说明尚未做生产压测。项目介绍的目标是建立问题与决策的因果关系，不是证明组件越多越好。

介绍中还要主动给出一个 Trade-off。比如采用异步化后，上传接口更快且任务可恢复，但用户必须理解 PROCESSING 到 READY 的窗口，系统也增加 Outbox、Consumer、DLQ 和对账。采用不可变 Snapshot 后可以稳定回放，却要承担存储和删除降级成本。面试官若追问“最初为什么不直接这么做”，可以说明 V0 的目标是验证用户链路，当任务时长、跨存储和多租户约束出现后才值得引入复杂度。最后用一句话给出演进边界，例如当前没有生产集群证据，上线前仍需容量、灾备和安全演练。

### 9.2 为什么选这些中间件，有没有过度设计

回答每个中间件时都用“它承载哪个已经存在的业务语义”。MySQL 承载 Source、Snapshot、Job、ACL 等真源状态，因为这些对象需要事务、唯一约束和条件更新。Kafka 承载可重放的异步事件流，解决解析、索引和派生工作不应阻塞上传请求的问题。Redis 承载短期配额、并发租约、缓存和多实例实时桥接，它丢失后允许降级或重建，因此不作为业务真源。Elasticsearch 保存可重建检索投影，MinIO 保存大对象正文。中间件不负责自动解决一致性，Outbox、幂等、版本和对账仍由业务协议定义。

判断是否过度设计要回到失效条件。若只是单机 Demo，同步调用和数据库轮询更简单；当任务持续数分钟、需要崩溃恢复、检索与写入解耦、多租户限制 Provider 成本时，持久状态机和异步调度才有价值。当前 Docker Compose 是开发与演示部署，不把它包装成生产集群。面试官问“为什么不用某某新技术”时，比较当前约束、团队成本、故障模式和迁移触发条件，不用先进性作理由。

可以再逐个说未选方案。Redis Stream 能减少一个中间件，但当前 Kafka 更适合资料事件的保留与多 Consumer；直接用 ES 作真源能减少 Hydration，却难以承载事务、Ownership 和可审计状态；自由 Agent 灵活，却让长任务恢复、权限和成本边界不稳定。未选方案并非错误，在流量、团队或产品目标变化后可能重新评估。技术选型的验证证据应包括故障注入、吞吐与长尾、运维复杂度和数据恢复，而不是“大家都在用”。

如果面试官要求删掉一个组件，可以优先讨论早期用 MySQL Outbox Polling 直接驱动 Worker，暂缓 Kafka；当 Consumer 数量、保留重放和积压吞吐成为瓶颈后再迁移。这个回答能证明架构允许分阶段演进，而不是所有组件缺一不可。

### 9.3 项目最难的点是什么

“难”要落到一个可复现的工程矛盾。可选择跨存储一致性：上传同时涉及对象存储、MySQL、Kafka 和 ES，无法用一个本地事务覆盖，任何外部 I/O 前后崩溃都会留下不同状态。解决方式是划分真源与投影，事务内提交业务状态和 Outbox，事务外投递，Consumer 幂等，Projection 带版本，对失败任务提供 Retry、DLQ、对账与重建。代价是用户会看到从上传完成到可检索之间的最终一致窗口，系统也要维护更多状态和监控。

也可以选择长任务恢复或 Context 一致性，但一场面试只选本人最熟的一项。完整答案要包含最初误判、失败窗口、最终不变量、测试证据和未解决边界。只说“技术难度高”“并发量大”不能支撑追问。若项目没有真实高并发，难点可以是正确性和可恢复性，不需要编造流量。

以长任务为例，难点不是把任务丢给 Worker，而是处理 Claim 后崩溃、Heartbeat 暂停、旧 Worker 晚回调、Provider 已成功但 ACK 丢失和恢复后输入漂移。系统通过持久 Job/Attempt、冻结 ExecutionSpec、Lease/Epoch、Waiting/Resume 和幂等 Receipt 建立不变量，代价是状态机与清理工作增加。验证要卡住每个关键 I/O 前后制造崩溃，断言最多一个新 Owner 可确认结果，同时允许重复执行被安全吸收。这样回答能从业务困难一直落到底层并发控制。

第三层追问通常是“现在还有什么没解决”。可以回答跨区域 Fencing、生产级调度公平性、长时间 Provider 中断和不可逆工具副作用仍需要更强演练与治理。主动给出边界能避免把一个经过测试的单机协议夸大成全球调度平台，也能自然引出演进触发条件。

### 9.4 如何证明这是你的设计

可验证的 Ownership 来自四类证据：能解释为何选这个抽象；能画出状态变化与失败窗口；能指出代码、迁移和测试的具体位置；能说出方案不理想的地方以及下一步触发条件。只会说组件作用，可能只是阅读过项目；能解释旧 Owner 为什么会晚到、为什么 Token 必须参与条件更新、测试如何卡在 Claim 后崩溃，才接近真实参与。

回答时也要明确协作边界。AI 辅助生成、开源组件能力、他人负责模块都应如实说明。候选人的价值可以体现在需求拆解、架构选择、验收标准、故障测试和代码评审，不要求声称每行代码都手写。真实性比夸大 Ownership 更重要，因为三层追问最终会落到具体状态、日志和取舍。

准备时给每个亮点做一张 Ownership 表：问题是谁发现的，方案是谁提出的，自己写了哪些核心类或迁移，测试是谁设计的，最终由谁验收。面试官问某个实现细节时，若它不在本人范围，应先说明边界，再讲自己理解的接口 Contract，不抢占他人贡献。能够指出一次自己做错的设计、如何被测试或审查推翻，以及之后怎样修改，比泛泛声称“负责整体架构”更可信。

证据还应能双向定位。口述 Token Rotation 时能指向数据库 Hash、条件更新和 Replay 错误；口述 Outbox 时能指出状态索引、Claim Token 和故障测试；口述 RAG 时能说明当前 Fixture 样本与线上评测的差距。若只能从代码名复述功能，却说不出决策背景与反例，Ownership 仍然薄弱。

面试前可让同伴随机挑一个状态字段，连续问“谁写、何时写、重复写怎样、失败后谁恢复、如何证明”。本人负责的模块应能回答到 SQL 条件、错误码和测试窗口，不负责的模块则讲清 Contract 和协作边界。不要背提交数量，提交量无法证明设计判断或业务责任。

### 9.5 项目取得了什么结果

结果分业务结果和工程结果。业务结果需要真实用户、任务完成率、检索质量或节省时间的数据，没有就不能虚构。工程结果可以陈述已有证据，例如审查时 Backend 755 个测试、Artifact Worker 222 个测试、Research Worker 368 个测试，以及前端 43 个测试文件、142 个测试，但必须保留测试日期、环境、Skipped 和“测试通过不等于生产效果”的边界。

更好的后续证据是建立固定工作负载：上传到 READY 的延迟、Agent 成功率、恢复率、RAG Gold Set、TTFT、单位成功 Run 成本和故障注入结果。面试官问收益时，如果目前仍是个人或演示项目，可以直接说“当前主要证明工程可行性，没有线上业务收益数据”，再说明如果上线会怎样设计指标。真实而完整的验证计划，比编造提升百分比更可靠。

结果还要说明分母与对照组。任务成功率是否排除用户取消，RAG 准确率样本来自哪里，P95 在什么机器和数据规模下测得，都决定数字能否比较。没有业务基线时，可以报告能力边界，例如重复回调不会产生第二次终态、旧 Snapshot 不能覆盖新 Projection、100 个检索 Hit 的 Ownership 查询保持常数级，但不要把机制测试换算成用户提升。

面试官可能问“如果再给一个月做什么”。优先补真实度最高的缺口：固定容量工作负载、跨版本发布演练、备份恢复、在线 Shadow 指标和安全边界，而不是再接一个中间件。回答应给触发条件和验收标准，例如只有 Gold Set 与 Shadow 表明向量召回在质量收益上覆盖成本，才考虑独立向量库。

## 10. 可以直接确认的项目参数事实

面试介绍中可以使用下面这些数字，但要称为“当前默认配置”或“本地 Compose 设置”，不能称为生产容量：Backend Hikari 最大连接 20、最小空闲 4；Answer I/O 线程池 `4/16/64`；SSE Connection `4/32/0`；分布式配额 Rate Capacity 20、每分钟补 20、Workspace/Workload 并发 4、Lease 300 秒；Research Agent 默认执行并发 1、Fetch 并发 4、任务 Lease 60 秒、Heartbeat 15 秒；Outbox 每秒扫描、Batch 50、普通 Lease 1 分钟、最多 5 次；Access Token 15 分钟、Refresh Token 30 天。

这些设置体现的设计判断是有界资源、快速失败、短事务和可恢复任务。它们不能证明 400 QPS、32 个稳定 SSE 用户或每分钟完成 20 个 Agent 任务。完整参数、源码位置和容量口径统一查阅[项目真实配置参数与容量口径](15-项目真实配置参数与容量口径.md)。
- 配置上限不说成压测吞吐。
- Docker Compose 不说成生产集群。
- Fixture 不说成线上准确率。
- 设计方案和现有实现分别标注。
- 至少准备一个做对、一个做错、一个推动取舍的真实案例。

## 11. Ownership 回答的源码证据规则

Ownership 不能通过“我用了哪些技术”证明。每个声称由本人完成的亮点，面试前应准备一组可以现场展开的证据：一个业务入口、两个关键生产类、一个失败窗口、一个测试类和一个仍未解决的边界。比如讲 Outbox，可以从 `DurableOutboxDispatcher.claim()` 展开 Attempt CAS 和 Lease Owner，再说明最后一次 Claim 崩溃为何需要过期耗尽扫描；讲 RAG，可以从 `SourceRetrievalProjectionService.projectSnapshot()` 展开双 Projection 和维度校验，再说明首次启用必须 Rebuild；讲 Memory，可以从 `MemoryCompilerService` 展开 Scope 与 Token Budget，再说明 Memory 不进入 Evidence Rerank。

这组源码证据只能证明候选人理解仓库，不能自动证明本人独立实现。本人负责范围、决策参与程度、投入时间、协作对象和结果数据仍必须由候选人如实填写，文档不代写个人经历。
