# 真实缺陷排查与复盘案例

> 权威契约：Outbox、Lease、Fencing、Callback、Unknown Outcome 和恢复对账见 [API 与事件契约](../API与事件契约-v2.md)。案例证据只来自仓库审查、测试或故障模拟，统一视为 `[当前实现]` 或 `[已测-模拟]`，不能改写成生产事故。

## 1. 使用边界

以下案例来自仓库审查、测试和修复记录。它们属于开发或审查阶段发现的真实工程缺陷，不是线上生产事故。面试时可以说“代码审查和故障测试发现”，不能说“线上告警发现”或虚构用户影响。

每个案例按现象、风险、排查、根因、修复、验证和反思展开，可以支持 4 到 5 分钟回答。

## 2. 案例一：Outbox 回调租约任务可能永久卡在 PROCESSING

### 2.1 背景与现象

Outbox Dispatcher Claim 一条任务后，会设置 Lease Owner、Lease Until、Attempt Count 和 Delivery Token，再调用外部 Worker。正常路径收到回调后进入完成状态，失败路径进入重试或死信。早期实现只处理主动回调失败，没有完整覆盖“已经 Claim，随后进程崩溃，直到重试次数耗尽”的恢复窗口。

表面现象是任务一直处于 `PROCESSING`，没有新的回调，也没有进入 DLQ。普通 Happy Path、回调异常测试和发布失败测试都可能通过，因为缺陷只发生在 Lease 已领取、最后一次执行又丢失回调的组合窗口。

### 2.2 排查过程

排查先画状态机，不从日志猜。对每个非终态询问：谁能推进它，推进条件是什么，Owner 永久消失后是否还有扫描器接管。检查后发现，重试入口依赖正常失败处理，而过期 Lease 扫描没有对“Attempts 已耗尽”的记录做终态化。任务既不能重新执行，也不会自动进入 Dead Letter。

这个问题说明“有 Lease”和“可恢复”不是同一件事。Lease 只让所有权过期，系统还需要一个确定的接管与终态规则。

### 2.3 修复

Dispatcher 增加耗尽且 Lease 过期记录的扫描。扫描通过条件更新匹配 ID、状态、Attempt、Lease Owner 或 Claim Token，只有当前代际仍然成立时才进入 Dead Letter。旧 Dispatcher 晚到不能确认新 Claim，多个扫描器并发也只有一个能完成状态迁移。

修复没有简单把状态重置为 READY，因为 Attempts 已耗尽的毒任务继续执行只会增加副作用和下游压力。进入 Dead Letter 后保留原业务身份、错误和尝试信息，由受控 Redrive 恢复。

### 2.4 验证与反思

回归测试覆盖最后一次 Claim 后崩溃、Lease 过期、多扫描器竞争和重复扫描，断言任务只终态化一次。后续审查还补了 Attempt CAS，防止旧 Claim 对新代际执行状态更新。

反思是异步状态机不能只枚举显式异常，还要枚举每次外部 I/O 前后进程消失的窗口。以后设计长任务时，应为每个非终态写出“Owner 永久消失后谁负责推进”。

## 3. 案例二：外部对象和 ES 清理失败只记日志，删除无法收敛

### 3.1 背景与风险

资料删除先提交 MySQL 状态，再在事务提交后清理 MinIO 对象和 Elasticsearch 投影。Post-commit 是正确方向，因为事务提交前删除外部资源会在数据库回滚后留下悬空引用。早期实现的问题是，外部清理失败只记录日志，没有持久任务、重试身份和死信状态。

用户侧资料已经不可见，但派生对象可能长期残留。它不一定造成在线越权，因为读取仍由 MySQL 状态拦截，却会造成存储泄漏、合规风险和无法证明删除收敛。

### 3.2 根因

设计把 Cleanup 当成“事务后的附加动作”，没有把它当成有生命周期的业务任务。日志只能帮助人工发现，不能承担可靠队列职责。进程崩溃、网络超时和应用重启都可能让动作永久消失。

### 3.3 修复

新增持久化 `source_cleanup_task`，删除事务内写入清理意图，事务提交后由调度器执行。任务使用数据库时间筛选，领取时记录 Owner、Lease、Attempt 和 Fencing 信息；失败有界重试，第五次执行后仍失败进入 Dead Letter。对象 Key 使用 SHA-256 生成稳定幂等身份，避免 utf8mb4 长 Key 超出 InnoDB 唯一索引长度。

修复过程中又发现两个二阶窗口：JVM 时间与数据库时间混用会让 Lease 判断漂移；第五次 Claim 后进程崩溃可能触发第六次执行。最终通过统一数据库时间、Attempt CAS 和过期耗尽扫描收口。

### 3.4 验证与面试重点

测试覆盖重复清理、外部暂时失败、最后一次 Claim 崩溃、过期 Lease 竞争和 Dead Letter。Flyway V090 在隔离 MySQL 8.4.9 从空库应用，并验证 Check 与两类 Unique 约束。共享数据库仍等待正式部署迁移，这个边界要如实说明。

该案例可以回答“重试和补偿有什么区别”。重试重复同一清理动作，补偿体系还要持久记录意图、识别孤儿、处理终态并支持对账。

## 4. 案例三：Windows 本地编码导致 MCP 子进程输出解码失败

### 4.1 现象

Artifact Worker 的测试在部分 Windows 环境出现 2 个失败，而同一逻辑在 UTF-8 环境正常。失败集中在 Custom MCP 子进程输出包含非 ASCII 字符时，异常发生在读取标准输出，不在业务 Schema 校验。

### 4.2 排查

先比较失败用例的输入、命令退出码和原始字节。子进程本身执行成功，问题发生在 Python 按本机默认编码解码输出。Windows 中文环境可能使用 GBK，而工具输出按 UTF-8 写入，同一字节流因此在不同机器得到不同结果。

### 4.3 修复与验证

`custom_mcp_executor.py` 显式指定 UTF-8，并为不可解码内容提供受控容错，不再依赖 Locale。历史测试记录曾覆盖该路径；当前通过数量应以重新执行的 worker 测试输出为准。

这个案例的重点不是编码知识点本身，而是排查方法：先区分进程执行失败、协议失败和传输解码失败；再比较环境变量与原始字节。跨语言系统必须显式约定字符集、时间、数字与 JSON Canonicalization，不能依赖机器默认值。

## 5. 案例四：完整 Maven 测试因 JVM 内存映射失败

### 5.1 现象与误区

全量 `mvn test` 曾反复崩溃，错误不是某个断言失败，而是 JVM `hs_err_pid` 日志显示 G1 Virtual Space `mmap` 失败。机器约 15 GB 内存，测试并行、Fork JVM、容器和其他进程共同占用地址空间与物理内存。

如果只看 Maven 最后的非零退出码，容易误判为业务测试不稳定。正确分类应先判断 Assertion Failure、Java OOM、Native Allocation Failure、进程被系统终止还是基础设施不可用。

### 5.2 修复思路

通过限制 Surefire `-Xmx`、Fork 数和复用策略降低峰值内存，再分模块运行定位高占用测试。最终审查记录中 Backend 全套 755 个测试完成，0 Failure、0 Error、11 Skipped。

### 5.3 反思

测试能否执行也是交付系统的一部分。单测数量多但 CI 经常 OOM，不能称为可靠证据。测试容量需要记录 JVM、Fork、容器依赖和机器配置，资源问题与代码缺陷要分别归因。

## 6. 复盘回答的三层追问

面试官第一层问“发生了什么”，回答现象与影响；第二层问“怎么定位”，回答假设、证据和排除过程；第三层问“为什么以后不会再发生”，回答不变量、自动测试、监控和仍存在的边界。

禁止只说“加了重试”“加了判空”“调大内存”。完整修复应说明为什么原设计漏掉该窗口，以及新机制可能带来的副作用。

## 7. 常见故障八股：CPU 突然升到 100% 怎么排查

先确认范围和时间，是单实例、整组实例还是同一宿主机，CPU 是 User、System、I/O Wait 还是被容器限额 Throttle。应用 QPS、发布、定时任务和依赖延迟是否同时变化，决定优先怀疑流量、代码回归、GC 或下游阻塞。Java 进程可连续采集线程 CPU 与线程 Dump，把高 CPU 线程的 Native ID 转为十六进制后对应到栈；再用 JFR、Async-profiler 或火焰图确认热点方法。只看一次 Dump 容易把瞬时采样当成根因，至少比较多个时间点。

常见模式包括死循环、无界重试、JSON/正则等计算热点、锁自旋、高分配速率触发频繁 GC，以及线程过多产生调度开销。若 CPU 高但吞吐没有增加，结合队列、拒绝、GC Pause 和下游 429 判断是否为重试放大。修复可以是关闭入口、限流、回滚、降低并发或修正算法，但每个动作都要有恢复验证。NoteWeave 的 Provider/MCP 重试必须受总 Deadline、最大次数和错误分类约束，否则依赖故障时会把一个请求放大成多次 CPU、网络和 Token 消耗。

还要区分 CPU 饱和与被配额限制。容器只获得半个核心时，进程指标可能很快到 100%，宿主机却很空；大量平台线程也可能改变观察方式。止损后应保留发布版本、火焰图、线程样本和流量切片，使用相同输入做前后对比。若热点来自合法业务增长，修复方向可能是算法优化、缓存、任务拆分与扩容；若来自异常重试，扩容只会让更多请求冲击下游。面试官继续追问“为什么告警晚了”，可以说明 CPU 原因型告警要与用户成功率、队列年龄和 SLO Burn Rate 联动。

## 8. 常见故障八股：OOM 与内存持续上涨怎么区分

先看错误类型。`Java heap space` 通常表示 Heap 无法分配；`GC overhead limit exceeded` 表示大量时间用于 GC 但回收很少；`Direct buffer memory` 指堆外直接内存；`unable to create native thread` 可能是线程数、进程限制或 Native 内存不足；容器被 OOMKilled 还可能没有 Java OOM 日志。任务管理器中的进程 RSS 包含 Heap、Metaspace、Code Cache、线程栈、Direct Buffer 和 Native 库，不能只用 `-Xmx` 推断总内存。

排查先保存 GC Log、Heap Dump、Native Memory Tracking 和容器事件。Heap Dump 看 Dominator Tree、Retained Size 和到 GC Root 的引用链，区分缓存容量过大、ThreadLocal 残留、队列积压、监听器未解绑与真实泄漏。若对象数量随业务负载上升并在任务完成后下降，可能只是工作集；持续跨多次 Full GC 增长才更像泄漏。NoteWeave 的 SSE Subscriber Queue、Replay Buffer、批量文档解析和任务上下文都必须有界，慢消费者不能让内存随连接时间无限增加。修复后要用相同工作负载重放并观察 Old Gen 基线，不以“调大 Xmx 后暂时不报错”作为关闭条件。

生产环境抓 Heap Dump 可能短暂停顿并生成很大的文件，磁盘空间和隐私要提前评估。无法立即抓 Dump 时，可先看类直方图、分代占用、分配速率与线程数，并在隔离实例复现。内存优化也要防止把问题转移到别处，例如缩小队列会增加拒绝，改为 Direct Buffer 会把压力移出 Heap，频繁 Full GC 会牺牲长尾。最终验证至少包括稳定负载下的内存平台期、峰值流量后的回落、取消任务后的对象释放和 OOM 时的自动保护。

## 9. 常见故障八股：线程死锁与线程池耗尽

Java 内置锁死锁可在 Thread Dump 中看到线程互相等待的锁和持有关系，`jstack` 可能直接报告 Found one Java-level deadlock。数据库锁、分布式锁和 Future 相互等待未必被 JVM 自动识别，需要结合调用链、超时和外部状态。预防手段包括固定加锁顺序、缩小临界区、避免持锁做 I/O、使用可超时的 TryLock，以及减少嵌套锁。锁超时只能解除等待，不能保证业务状态仍正确。

线程池耗尽更常见。所有 Worker 都阻塞在下游，队列不断积压，接口表现为超时但 CPU 不高。排查要看 Active、Queue、Oldest Age、Rejected、每类线程栈和下游延迟。CompletableFuture 在同一小线程池中提交子任务并同步 `join`，也会出现线程饥饿。NoteWeave 将 Answer I/O、SSE Dispatch、Connection 和 Redis Bridge 隔离，并使用有界或零队列与 AbortPolicy，使过载显式化。隔离会增加线程和配置成本，池之间仍可能在数据库或 Provider 处重新汇合，因此还要检查共享资源。

死锁修复后应写出资源获取顺序，并用并发测试稳定复现；线程池耗尽则要对阻塞调用设置超时，传播取消，并验证队列满时返回什么。CallerRunsPolicy 会把压力推回提交线程，可能拖慢入口或调度器；Discard 类策略会静默丢任务；AbortPolicy 会显式失败，但上层必须转换为可理解的过载状态。面试官问“核心线程数怎么配”时，应区分 CPU 密集与 I/O 等待，并以服务时间、目标并发、下游限额和压测决定，不能机械使用 CPU 核数公式。

## 10. 常见故障八股：接口 P99 突然恶化

平均值正常而 P99 恶化，表示少量请求进入了不同路径。先按版本、接口、Workspace、请求大小、缓存结果、Provider、错误重试和实例切片，找到慢请求集中在哪类 Cohort。随后把端到端时间拆成入口排队、连接池等待、SQL、锁等待、缓存、检索、模型 TTFT、工具调用和流式发送。Trace 只记录跨度还不够，异步 Job、Kafka Event 和回调需要传播 RunId、TaskId、Attempt 和版本才能串联。

常见原因包括缓存同时失效、数据库执行计划因数据分布变化而改变、连接池少量请求排队、GC Pause、下游长尾、DNS/TLS 建连、重试以及大请求序列化。处理时先保护用户路径，例如限流、降级 Rerank、暂停后台回填或切换 Provider，再定位根因。NoteWeave 的 RAG 应分别观察 Retrieval、Hydration、Rerank 和 Generation，Agent 应看 Queue、Node、Waiting 和 Repair。接口返回 200 但生成质量为空，不能算作性能恢复。

P99 对样本量敏感。每分钟只有几十个请求时，单窗口 P99 波动很大，应结合更长窗口、直方图 Bucket 和慢请求明细；客户端、网关与服务端的延迟口径也可能不同。排查时比较 P50、P95、P99 与 Max，判断是整体变慢还是尾部出现新路径。优化完成后除了延迟，还要检查错误率、结果质量和单位成本，避免通过关闭校验或减少证据把数字做快。SLO 应围绕用户完成链路定义，而不是只测 Controller 方法耗时。

恢复后至少跨一个完整业务峰值继续观察，防止短窗口误判。

## 11. 常见故障八股：Kafka Lag 持续增长

Lag 是生产位点与消费位点的差值，先判断生产速率是否突增、消费速率是否下降、是否只有部分 Partition 落后。单个 Partition 热点可能来自 Key 分布不均，所有 Partition 同时变慢更可能是下游数据库、ES、外部服务或 Consumer 实例问题。还要看 Rebalance、消费错误、Retry Topic、DLQ、批次大小、处理时长和 Commit 行为。只加 Consumer 数量不能突破 Partition 数，也不能解决共享数据库已经饱和。

恢复时间可按 `backlog / (completion_rate - arrival_rate)` 粗估，前提是完成速率大于到达率。若积压任务包含永久坏消息，无限重试会阻塞或持续消耗，应分类进入 DLQ 并保留人工 Redrive。NoteWeave 的解析与投影事件需要业务幂等和 Snapshot Version，重复消费不能生成旧投影覆盖新状态。处理完成但 Offset 未提交会重复，Offset 已提交但业务状态未落库会丢失，因此消费完成定义必须围绕业务提交边界说明。

积压期间还要保护恢复过程。直接把并发拉满可能让 MySQL、ES 或对象存储再次过载，形成恢复抖动。可暂停非关键 Producer、按租户或事件类型限速 Redrive，并优先处理影响在线可见性的任务。验证恢复不能只看 Lag 回到零，还要检查 DLT、业务状态数量、Snapshot 与 Projection 版本对账以及最老任务年龄。若保留期小于恢复时间，旧消息可能在消费前被删除，因此容量规划要把峰值积压与 Retention 一起计算。

## 12. 常见故障八股：Redis 延迟、热点 Key 与缓存雪崩

Redis 单线程执行命令的主路径意味着一个慢命令、大 Key 删除、Lua 长脚本或网络输出阻塞会影响其他请求。排查要看命令 P99、Slowlog、CPU、内存、Eviction、连接数、网络带宽、主从复制和持久化 Fork。热点 Key 会让单个分片承受集中流量，大 Key 会放大序列化、网络和删除成本。`KEYS`、大范围集合操作和无界 Lua 都应避免出现在在线路径。

缓存穿透是大量查询不存在 Key，击穿是热点 Key 失效后并发回源，雪崩是大量 Key 同时失效或缓存整体不可用。可使用负缓存、TTL Jitter、单飞构建、逻辑过期、限流和降级，但每种方案都有陈旧窗口或额外复杂度。NoteWeave 的 ACL 缓存带版本，失效时仍需回到 MySQL 校验；Redis 配额故障的策略要按工作负载选择 Fail Closed 或受限降级，不能统一返回成功。修复后除命中率外，还要验证回源量、错误返回、数据新鲜度和数据库是否被二次压垮。

如果 Redis 发生主从切换，客户端重连、DNS 或拓扑刷新也会贡献长尾；异步复制可能丢失最近写入的缓存、租约或配额状态。不同用途的影响不相同：缓存丢失主要产生回源，配额丢失可能短时放大请求，实时事件窗口丢失会让 Cursor Expired，业务真源不应因此损坏。面试官问是否应该 Fail Open 时，要按安全性、成本和用户影响分别回答，并给出最大降级速率与恢复后的状态校验。

止损动作也要区分用途。缓存实例异常时可临时旁路并限制数据库回源；配额实例异常时，高成本 Agent 请求更适合 Fail Closed 或采用很小的本地应急额度；实时桥接异常时保留持久终态并让客户端稍后查询。恢复后不能只重启客户端连接，还要检查热 Key、旧租约、Replay Window 和数据库负载是否回到基线，并补充对应 Runbook。

## 13. 故障题的标准证据链

三分钟回答可以按“症状、影响、切片、候选原因、证据与反证、止损、已验证根因、修复、重放”展开。症状是用户或指标看到什么；相关性只说明两个信号同时变化；候选原因必须能被指标、日志、Trace、Dump 或数据库状态证伪；只有改变该原因后原故障能稳定消失，并且相邻解释被排除，才能称为已验证根因。证据不足时保留“高概率候选”或“待验证”，不能为了故事完整强行收口。

每次诊断记录至少包含结论等级、观察时间窗、受影响对象、支持证据、反证、未解释现象和下一步验证。比如 Provider 429 与 Queue Age 同时上升只能建立相关性，还要通过降低入口并发、观察 429 与净清空速率是否恢复，排除 Hikari Pending、Poison Message 和 Worker CPU 饱和，才能判断主要限制资源。AI 可以归一化告警、聚合证据、检索 Runbook 和生成验证清单，但不能把模型猜测升级为根因，也不能自动执行危险 SQL、修改生产数据或关闭关键告警。

面试官常追问“为什么监控没发现”“为什么测试没覆盖”“是否会复发”。回答应说明原告警看了什么错误信号，新的 SLI 与阈值如何定义，测试怎样在关键 I/O 前后制造崩溃，以及 Runbook 如何判定恢复。禁止用重启服务作为根因，也不要在没有 Dump、日志和时间线时断言某个组件泄漏或死锁。

### 13.1 已测模拟：Rerank 响应畸形与部分返回

这个案例属于 `[已测-模拟]`，不是生产事故。`QaRerankServiceTest` 和 `NoteSourceRerankServiceTest` 使用受控 Provider 分别返回空结果、越界 `documentIndex`、重复下标、非有限分数和部分合法结果。排查重点不是“模型为什么答错”，而是把 Provider 当成不可信协议边界，先验证响应身份、范围、唯一性和数值，再允许它改变候选顺序。

空结果或任一畸形项会让整批 Rerank 退回原有 RRF 或资料级顺序，并产生 `QA_RERANK_UNAVAILABLE` 或 `NOTE_SOURCE_RERANK_UNAVAILABLE`。合法的部分返回不会丢掉其余候选，已返回项在前，遗漏项按原顺序补后。该测试证明降级顺序确定、异常下标不会错误索引候选；它没有证明真实 Provider 的质量、P99 或错误率。

这个回放还暴露出一个当前缺口：QA 部分返回只在补回候选上设置 `fallbackScore=true`，聚合 `RerankOutcome.degraded` 仍是 `false`。因此监控若只看聚合降级率，会漏掉“Provider 长期只返回少量候选”的质量退化。目标补强应增加部分响应计数、返回比例和聚合降级原因，再用固定候选回放验证告警，不应把当前实现描述成已经闭环。

### 13.2 已修复设计缺陷：Artifact 进程内启动与 202 未知结果

`[历史设计，已移除]` 最小反例是：Host 用 Delivery D1 调用 Worker，Worker 已把 Task 放入 FastAPI `BackgroundTasks`，但 202 在返回途中丢失。Host 把本次派发记为失败，后续可能用 D2 重投；Worker 进程内若仍在执行，原执行的 Callback 仍携带 D1。Host 的 Delivery Ownership 会拒绝 D1，这证明 Fencing 在工作，却不证明任务可以顺利完成，也不证明 Worker 重启后不会再次执行。这个问题不是 FastAPI 的缺陷，而是把进程内后台任务误用为持久长任务执行引擎。

`[当前实现]` 已移除 `/tasks/{task_id}/run` 和 `BackgroundTasks` 启动入口，改为 MySQL Outbox 加 Kafka。命令携带 D1，Worker 在昂贵执行前用 D1 读取冻结输入；如果 Outbox Lease 已由 D2 接管，Java 返回 409，Consumer 把 D1 识别为旧重放并提交 Offset。Callback 传输未确认时不提交 Offset，无效命令也必须先写入 Artifact DLQ 才提交。现有单测证明 Broker 发布命令携带 Token、自动提交关闭、单条拉取、旧 Token 跳过、Callback 未确认不提交和 DLQ 先于提交；它仍不是生产事故证据，也不能证明所有外部工具副作用天然幂等，后续混沌验收仍应覆盖 Worker Kill、Callback 断网和外部 Operation 对账。

## 14. 用项目真实参数回答故障题

线程池耗尽时，先按池定位。Answer I/O 是 Core 4、Max 16、Queue 64；SSE Dispatch 是 `2/8/128`；SSE Connection 是 `4/32/0`；Redis Bridge 是 `2/16/0`；Artifact Dispatch 是 `1/1/0`。它们都使用 AbortPolicy。看到 Answer Queue 接近 64 且 Rejected 增加，要继续看 LLM 60 秒超时、Hikari Pending 和 Provider 429；SSE Connection 被拒绝则不应误判成模型执行池不足。

Kafka 积压时，项目 Consumer 关闭 Auto Commit、按 Record Ack，失败后约 1 秒和 2 秒加 Jitter 重试，再进入 `.DLT`。Outbox 每 1 秒 Tick、每批最多 50、普通 Lease 1 分钟、最多 5 次，单次 Kafka Publish 最多等待 10 秒。理论上一轮能 Claim 50 条，不表示每秒能完成 50 条，最坏发布等待会让单线程 Dispatcher 很慢。恢复时应限制 Redrive，观察最老 READY 年龄和下游容量。

Redis 故障时，客户端 Connect Timeout 500 ms、Command Timeout 750 ms。ACL 正缓存 300 秒、负缓存 30 秒、Jitter 60 秒；配额 Lease 300 秒，Local Fallback 默认关闭且生产禁止。Redis 慢 750 ms 后失败的用户表现，要按缓存回源、配额拒绝和 SSE Bridge 分别分析。完整参数表见[项目真实配置参数与容量口径](15-项目真实配置参数与容量口径.md)。

## 16. 故障复盘题的 4 到 5 分钟完整回答

遇到故障时，我不会先猜某个中间件坏了，而是先定义用户看到的错误终态，再沿请求、状态、队列、依赖和回放逐层缩小范围。以“资料删除后仍能被检索”为例，用户症状可能是在线召回仍命中，也可能是历史回答引用仍可见。第一步查 MySQL 中 Source、Snapshot 和删除意图的状态，第二步看 Cleanup Task 是否创建、Claim、Retry 或进入 Dead Letter，第三步检查 MinIO 对象和 Elasticsearch Projection 是否仍有当前版本，第四步确认缓存、SSE 回放和 Evidence Manifest 是否需要脱敏。这样可以区分“删除没有提交”“异步清理没有推进”“索引旧版本仍可见”和“历史回放策略不符合隐私要求”，而不是只重启 Worker。

第二层是判断故障发生在控制面还是执行面。Outbox 可能在数据库提交后、发送前崩溃，也可能已发送但 ACK 丢失；此时要看 Outbox 状态、Attempt、Lease Owner、Kafka Offset、Consumer 业务状态和 Callback Receipt。旧 Worker 可能在租约过期后晚到，条件更新的影响行数为零应解释为 Fencing 拒绝，而不是把它当成数据库异常。Kafka Lag 上升时还要区分生产者突然增大、Consumer 处理变慢、Provider 429、数据库锁等待和 Poison Message，继续加 Consumer 可能会放大下游压力。Redis 延迟上升时要区分缓存回源、配额 Fail-closed、实时 Bridge 降级和热点 Key，不能把所有 Redis 错误都改成无限重试。

第三层是给出证据和修复边界。真实仓库案例可以讲 Outbox 最后一次 Claim 后卡住、对象和 ES 清理只记日志、Windows MCP 输出解码失败、Maven 测试因 JVM 内存映射失败；每个案例都应说明触发条件、观测信号、最小修复、回归测试和仍未证明的部分。CPU 100%、OOM、死锁、P99 恶化等章节是通用排障方法，除非有日志和时间窗口，否则要说成场景推演。修复也不能只说“加重试”，永久错误要进入失败终态或 DLQ，短暂错误才做有界退避；对象清理、索引回填和回调都要有持久任务，否则进程重启后会丢失补偿意图。

面试收尾时可以把故障治理提升为架构原则：系统应该把失败转成可查询状态，把重试限制在明确的业务幂等边界，把每次恢复绑定到版本、Owner 和证据，而不是用日志掩盖不确定性。当前仓库的测试能够证明若干故障窗口和错误分类，不能证明没有任何线上故障，也不能从本地测试推导真实 MTTR、SLO 或生产容量。这个边界要主动说出来，反而能说明复盘不是编故事，而是在管理证据。


## 17. 案例优先级与面试使用方式

## 18. 核心事件一：Outbox 最后一次 Claim 后卡死

### 18.1 4 到 5 分钟主回答

我排查过一个异步任务可能永久停在 `PROCESSING` 的缺陷。任务进入 Outbox 后，Dispatcher 通过条件更新 Claim，写入 `Lease Owner`、`Lease Until`、`Attempt Count` 和 `Delivery Token`，然后调用外部 Worker。正常失败会按照次数重试，最终进入 Dead Letter。问题出在最后一次 Claim 之后，Dispatcher 或 Worker 在回调前退出，数据库里已经把 Attempt 加到了上限，Lease 过期以后，普通候选查询又明确排除了耗尽任务。于是这条记录既不能被下一轮正常重试选中，也没有扫描器把它推进到终态，表面上就是一直 `PROCESSING`。

我没有先看某一条错误日志，而是把状态机列出来，逐个问每个状态由谁推进、推进条件是什么、Owner 永久消失后谁接管。沿着这条链看，根因不是 Lease 时长太短，也不是 Kafka 没有消费，而是“Attempt 耗尽”和“Lease 过期”两个条件组合后没有对应的状态迁移。Lease 只能表示这一代 Owner 已经失效，不能自动决定任务该重试还是失败。

修复时没有把任务简单重置成 `READY`。如果它已经达到最大尝试次数，强行重试可能再次调用下游，重复写入或继续消耗配额，毒任务也会被无限放大。现在由过期耗尽扫描器使用条件更新，把仍然满足 `id`、当前状态、当前 Attempt 和 Lease 已过期条件的记录迁移到 `DEAD_LETTER`。旧 Dispatcher 晚到时，更新影响行数为零，表示它的代际已经被 Fencing 拒绝；多个扫描器同时发现同一条记录，也只会有一个成功完成终态化。之后如果人工确认问题已经解除，再通过受控 Redrive 创建新一代尝试，而不是修改旧记录掩盖历史。

验证覆盖了最后一次 Claim 后进程退出、Lease 到期、多扫描器竞争、重复扫描以及旧代际晚到回调。核心不变量有三个：耗尽且过期的任务最终可查询地进入 `DEAD_LETTER`；旧代际不能修改新代际；同一条业务任务不会因为恢复扫描被重复终态化。这个缺陷来自仓库审查和故障模拟，不能说成线上告警发现，也不能据此声称真实 DLQ 率或 MTTR。

### 18.2 面试官可能追问

- **为什么 Lease 过期后不能直接重试？** 过期只能证明原 Owner 的时间窗口失效，不能证明外部 Worker 没有执行成功。直接重试可能形成重复副作用，所以要先看幂等边界、Callback Receipt 或业务结果，再决定重试、未知或死信。
- **为什么 Dead Letter Handler 要和状态迁移放在同一事务？** 如果先做业务死信记录再更新 Outbox，进程崩溃会留下无法解释的两套状态；同一事务至少保证数据库内的业务终态和补偿记录一起提交。外部通知仍可能失败，所以外部动作还要有自己的 Outbox 或对账。
- **扫描器执行到一半失败会不会漏任务？** 会出现暂时未处理，但不会永久丢失，只要扫描条件可重复执行、状态迁移是条件更新、下一轮仍能看到过期记录。这里追求的是可重复收敛，不是一次扫描完成。
- **怎么证明修复没有变成无限 DLQ 堆积？** 需要同时看 Dead Letter 数量、Redrive 成功率、按错误类型分桶的失败分布和恢复后再次耗尽比例。当前仓库只证明状态窗口和竞争行为，生产容量与长期堆积仍待验证。

## 19. 核心事件二：删除已提交，但外部清理永不收敛

### 19.1 4 到 5 分钟主回答

资料删除同时影响 MySQL 真源、MinIO 对象和 Elasticsearch 投影。删除事务内先把 Source 标成不可见并写入清理意图，事务提交后再删除对象和索引，这是为了避免数据库回滚后外部资源已经被删掉。早期实现把事务后的清理当成一次附加调用，失败只记日志。应用重启、网络超时或进程在提交后退出时，日志可能存在，但没有一条持久任务保证下一次还会继续清理。

这个问题有两个容易混在一起的定义。用户不可见是 Delete Visibility Lag 的终点，MinIO 和 Elasticsearch 物理清理完成是 Cleanup Completion Lag 的终点。前者可以由 MySQL 状态和 ACL 在读路径上立即拦截，后者需要异步补偿收敛。若只看接口返回 `200`，就会把“用户现在搜不到”和“所有派生副本都已删除”误当成同一个事实。

修复是把清理意图在删除事务内写入 `source_cleanup_task`，提交后由调度器领取。任务记录稳定的 Source 身份、对象 Key、投影版本、Owner、Lease 和 Attempt，失败进行有界重试，第五次仍失败进入 Dead Letter。对象 Key 用 SHA-256 形成稳定幂等身份，清理重复执行时可以把对象不存在视为幂等成功，索引删除则按 Source 和版本条件删除，避免误删新版本。Lease 判断统一使用数据库时间，Attempt 采用 CAS，过期且耗尽的任务由扫描器推进终态。

我会把验证拆成四条链：删除事务回滚时不能产生清理任务；提交成功后一定能查到清理任务；重复执行不会扩大删除范围；外部依赖持续失败时最终进入可查询的 Dead Letter。面试中还要主动说明边界，当前实现能证明“删除意图持久化”和“失败有终态”，不能证明对象存储、搜索集群和备份系统已经完成正式合规审计。历史回答里的 Evidence Manifest、SSE 回放和缓存也要有自己的隐私策略，物理对象删掉并不自动等于历史输出已经被撤回。

### 19.2 面试官可能追问

- **用户不可见但对象还在，算不算删除成功？** 要按产品承诺拆成两个 SLO。在线访问应在主事务提交后立即拒绝，物理清理需要单独的完成延迟和 Dead Letter 监控，不能用一个布尔值掩盖差异。
- **为什么日志不能承担补偿队列？** 日志没有稳定的业务身份、领取状态、重试次数和幂等约束，也无法保证日志写入和删除事务同时提交。它适合审计和诊断，不适合做唯一的恢复真源。
- **清理任务自己卡住怎么办？** 清理任务和 Outbox 一样需要 Lease、过期接管、Attempt 上限和终态扫描。补偿队列也必须被当成业务状态机，不能假设“补偿一定成功”。
- **如何避免清理旧版本时误删新版本？** 删除动作带 Source、Snapshot 或 Projection Version 条件，外部执行使用稳定 Key 和版本校验。条件不匹配时返回“已被新版本接管”或“无需删除”，不能把它当成通用成功。

## 20. 核心事件三：Artifact `202` 与结果未知

### 20.1 4 到 5 分钟主回答

Artifact 生成曾经有进程内启动 Worker 的历史设计。Host 调用执行接口后收到 `202`，只能说明 HTTP 层接受了请求，不能证明 Worker 已经可靠接单，更不能证明 PDF、Markdown 或对象存储已经生成成功。Host 在响应丢失时可能重投，原 Worker 可能已经开始执行，第二个 Worker 又可能重复调用外部工具，形成结果未知和副作用重复的风险。

现在的设计把长任务改为 MySQL Outbox 加 Kafka。命令带 `delivery_token`，Worker 在昂贵执行前读取冻结的输入快照，旧 Token 直接返回 `409` 并停止。Worker 回调携带内部认证、Delivery Token、幂等键和 Payload Digest，Host 用 `worker_callback_receipt` 记录已经接收的回调。Callback 未确认时，消费者不提交 Offset；无效命令先写 Artifact DLQ 再提交 Offset，避免 Poison Message 阻塞整条分区。

这里要把几种身份分开。Delivery Token 保护某一代投递的所有权，Callback 幂等键防止同一回调重复落库，Operation ID 绑定一次业务操作，Provider Receipt 证明外部工具是否已经接受或完成。Fencing 只能阻止旧 Worker 更新 Host 状态，不能撤销旧 Worker 在外部系统已经产生的副作用。因此，外部副作用还需要 Provider 幂等键、可查询 Receipt 或人工对账，不能把“旧回调被拒绝”说成 Exactly-once。

验证重点是发送前退出、发送后 ACK 丢失、Callback 重复、旧 Token 晚到、文件写入成功但回调失败、Provider 已执行但 Receipt 不可查。当前仓库已经移除进程内启动入口并具备 Outbox、Token 和 Receipt 设计；Provider 级别的真正 Exactly-once 和跨系统对账属于生产待验证边界。

### 20.2 面试官可能追问

- **为什么 `202` 不代表成功？** HTTP 状态只描述当前连接上的接收结果，任务是否入队、是否被 Worker Claim、是否完成文件 Contract 都是后续状态。
- **Callback 丢失时为什么不马上重跑？** 因为未知结果既可能是 Worker 未执行，也可能是已执行但响应丢失。应先按 Operation ID、Provider Receipt、对象 Key 和回调收据查询，再决定重试或人工对账。
- **Kafka 至少一次和 Receipt 能不能推出 Exactly-once？** 不能。它们只能减少 Host 内部重复处理，外部邮件、文件转换、第三方 API 等副作用仍可能已经发生。
- **旧 Worker 被拒绝后已经写出的文件怎么办？** 文件写入要使用 Operation ID 派生的幂等 Key，并由异步对账扫描“存在文件但没有有效 ArtifactVersion”的孤儿；无法安全判断归属时进入人工处理，不自动删除可能属于新代际的文件。

## 21. 核心事件四：Rerank 协议防御与降级指标盲区

### 21.1 3 到 4 分钟主回答

Rerank Provider 返回的 `documentIndex` 和分数不能直接信任。固定模拟覆盖了空结果、越界下标、重复下标、非有限分数和部分合法返回。越界下标直接索引候选会造成异常，重复下标会让同一文档占据多个名次，`NaN` 或无穷分数会污染排序。更隐蔽的是 Provider 只返回部分合法结果时，系统看起来没有报错，但未返回的候选到底排在后面还是被悄悄丢弃，会改变召回语义。

当前策略是：空结果或任一结构性畸形项，整批回退到原 RRF 或 Source 顺序；部分合法返回时，先放已返回项，再按原顺序补回遗漏候选。Provider 下标只允许映射到本批候选范围内，不能由外部响应直接访问集合。这样优先保护结果完整性和可解释性，代价是某个合法部分可能被放弃，排序质量会下降但不至于返回错误文档。

面试官如果继续问指标，我会补充一个已识别的缺口：部分返回时，聚合 `RerankOutcome.degraded` 可能仍为 `false`，只看聚合降级率会漏掉长期的部分返回。因此需要单独记录 `Partial Response Count`、`Returned Ratio`、结构性错误类型和回退原因，并按 Provider、模型版本、候选数量和超时桶切片。当前结论来自固定模拟，不声称真实 Provider 的质量、P99 或稳定性。

### 21.2 面试官可能追问

- **为什么畸形一项要整批回退，不能只丢掉坏项？** 因为坏项可能意味着序号映射、协议版本或 Provider 输出整体不可信，局部修补会让结果变得不可解释。只有明确属于可安全忽略的未知字段，才适合局部容错。
- **部分返回为什么不直接算失败？** 已返回项可能有有效排序信息，全部回退会丢掉可用信号。补回遗漏项并打上降级原因，可以在完整性和质量之间取平衡。
- **如何证明回退策略没有伤害业务？** 用同一 Gold Set 做配对实验，比较原始 RRF、完整 Rerank 和部分返回回退三组的 Recall@K、Citation Support、首条证据命中率和延迟，另外报告部分返回样本数。
- **如果 Provider 长期部分返回，先修代码还是换模型？** 先确认协议、超时和候选规模，再看返回比例与业务收益。若代码能正确降级但 Provider 质量不稳定，换模型或缩小候选批次可能比继续堆重试更合理。

## 22. 故障复盘二阶追问

### 如何区分真实缺陷、已测模拟和通用场景题

真实缺陷必须有仓库代码、测试、迁移或审查记录作为证据；已测模拟必须说明触发脚本或测试覆盖了哪一个窗口；通用场景题只讲排查方法，不能加具体发生时间、用户数、恢复时长或线上告警。面试中可以用四个标签：`[当前实现]`、`[已测-模拟]`、`[历史设计，已移除]`、`[生产待验证]`。

### 如何证明修复没有把问题藏起来

先写修复前的不变量缺口，再写修复后的可观测状态。例如 Outbox 修复后，不能只说“不会卡死”，要证明耗尽且过期记录能进入 `DEAD_LETTER`，旧代际更新会被拒绝，扫描重复执行不会产生第二次业务终态。删除补偿也不能只看对象数量，要同时看任务创建率、完成延迟、Dead Letter 数和孤儿对象对账结果。

### 一次故障测试通过，为什么仍不能说系统可靠

测试只覆盖指定前置条件和时间窗口。可靠性还受到数据规模、并发竞争、依赖行为、发布过程和恢复操作影响。更准确的回答是：“这个测试证明了该状态窗口可以收敛，不能推出所有运行时场景都不会复发；生产还要补 SLO、告警、容量和对账证据。”

### 为什么故障排查不能从重启服务开始

重启可能暂时清理进程状态，却会丢失现场，掩盖 Lease、Attempt、Offset、Callback Receipt 和数据库锁等待等证据。先冻结时间窗口和关联 ID，保存状态快照，再做止损。只有确认重启不会删除必要证据，且服务已经影响用户时，才把重启作为受控恢复动作。
