# 发布、迁移、灰度与回滚专项

> 阅读说明：第 1 到 10 节保留为发布题速查，第 11 到 14 节是常见八股长回答，第 15 节补充覆盖数据库、事件、Worker、索引、灰度与回滚的 3 到 5 分钟母题。

> 权威边界：Release Bundle、兼容、灾备和回滚契约见 [API 与事件契约](../API与事件契约-v2.md)，质量与 Burn Rate 门禁见 [评测报告](../测试与评测/NoteWeave-评测指标报告.md)。未做过的生产发布和恢复演练标 `[生产待验证]`。

## 1. 发布题的核心

发布不是把新镜像启动起来。面试官关注新旧版本同时存在时是否兼容、数据写坏后能否回退、后台任务是否重复、索引切换是否丢数据。NoteWeave 横跨 Java、Python、MySQL、Kafka、Redis、MinIO 和 Elasticsearch，需要把代码发布与数据演进分开设计。

## 2. 数据库 Expand/Contract

直接重命名或删除列会让旧实例失败。更稳的迁移分三步：

1. Expand：增加 Nullable 列、新表或兼容索引，旧代码仍可运行。
2. Migrate：新代码兼容读旧字段并写新字段，后台回填并对账。
3. Contract：所有实例切换并观察稳定后，停止旧写入，最后删除旧结构。

增加 Non-null 列时，可以先 Nullable 或提供安全默认值，回填后再加约束。大表 DDL 要评估锁和重建成本。Flyway Migration 一旦进入共享环境，不应修改已发布脚本，应新增版本向前修复。

历史审查曾在隔离 MySQL 8.4.9 验证部分迁移，但不能据此推断任何共享持久卷或生产环境版本。当前仓库最高迁移文件为 V104，环境实际版本必须读取 Flyway History。

## 3. 事件 Schema 演进

Producer 和 Consumer 不会同时升级。新增可选字段通常向后兼容，删除、改名、改变语义或把可选改必填会破坏旧 Consumer。Envelope 应保留 Schema Version、Event ID、Occurred At 和业务身份。

Consumer 采用 Tolerant Reader，但不能静默忽略安全关键字段。新 Consumer 先兼容旧/新版本，随后升级 Producer，确认旧消息保留期已过后再删除旧解析路径。DLQ 与 Redrive 必须保留原 Schema Version，不能人工拼成身份全新的消息。

## 4. Java 与 Python 跨服务升级

先发布能读取新旧 Contract 的接收方，再发布产生新字段的发送方。Java Host 与 Worker 回调使用版本、幂等键和 Worker Type 校验。若新 Worker 回调字段旧 Host 不认识，先扩 Host；若 Host 开始要求新字段，必须确认所有 Worker 已升级。

长任务在发布期间仍可能运行。ExecutionSpec、Input Snapshot 和回调协议需要版本化，旧任务继续按旧 Spec 完成，不能被新 Catalog 重新编译。滚动升级前还要支持 Drain：停止领取新任务，继续 Heartbeat 和完成已有任务，超过预算再安全退出。

## 5. Elasticsearch 双写、回填与 Alias

修改 Mapping 不能总在原索引原地完成。常用流程：创建新版本索引；从 MySQL/MinIO 真源回填；新写入对旧/新索引双写或通过变更日志追平；比较文档数、版本、抽样查询和 Gold 指标；原子切换 Read Alias；保留旧索引一段时间用于回滚。

双写不等于强一致，必须记录每个 Projection Version 的状态并对账。回滚 Alias 只能恢复读路径，如果新代码已经写入旧版本无法解析的数据，还需要兼容写或反向迁移。

## 6. Feature Flag、Shadow 与灰度

Feature Flag 用于隔离功能发布与代码部署。Flag 应有 Owner、默认值、Scope、过期时间和审计，不应永久堆积。安全边界和数据库约束不能只靠前端 Flag。

RAG 新策略先做离线 Replay，再以 Shadow 模式计算候选但不影响用户结果，比较 Recall/NDCG、P95 和成本；随后按 Workspace 或稳定 Hash 小流量灰度。灰度观察成功率、延迟、成本、降级与错误切片，达到门禁才扩大。

Agent/MCP 灰度还要限制副作用。只读 Shadow 可以真实执行，写工具不能在 Shadow 中产生实际写入，应使用 Preview 或隔离目标。

## 7. 回滚分类

代码回滚适用于新代码问题且数据仍兼容；配置回滚适用于阈值、Provider 或策略；流量回滚把请求切回旧版本；数据回滚需要备份、反向迁移或补偿，风险最高；索引回滚切 Alias，但要处理追平差异。

回滚前要问：新版本是否写入旧版本无法理解的数据，是否产生不可逆外部副作用，是否启动新后台任务，旧 Worker 是否还能接收消息。无法安全回滚时采用 Forward Fix，并先关闭入口或功能 Flag 控制爆炸半径。

## 8. 发布门禁

发布前至少检查：契约与集成测试、Flyway 从空库和升级路径、旧新版本兼容、Gold/Shadow 不回退、P95 与成本预算、生产配置 Guard、备份可用、回滚命令和负责人。发布后观察 Cohort，而不是只看实例存活。

健康检查分 Liveness 与 Readiness。Liveness 失败表示进程需要重启，Readiness 失败表示暂不接流量。把下游短暂故障放进 Liveness 可能造成所有实例重启风暴。

## 9. 恢复与数据重建

MySQL 保存业务状态，对象存储保存原始内容，Kafka 保存可重放命令，ES 可以从真源重建，Redis 保存短期状态。随着数据量和停机影响增长，应分别测量备份、回填、对账、连接恢复和租约接管耗时。

恢复目标只有演练才能证明。演练报告应记录故障范围、恢复步骤、耗时、数据差异、重复消息和对账结果。Docker Compose Healthcheck 与 Restart Policy 只能证明当前联调环境的启动与自恢复行为。

## 10. 五分钟发布题回答

回答顺序：先说明新旧版本会并存；数据库采用 Expand/Contract；跨服务 Contract 先升级接收方；长任务绑定旧 Spec 并 Drain；检索索引用回填、双写、对账和 Alias；新策略先 Shadow 再灰度；回滚前检查数据与副作用兼容；最后说明监控、门禁和恢复演练的证据边界。

## 11. 常见八股：滚动发布、蓝绿发布与金丝雀发布

滚动发布逐批替换实例，资源额外开销较小，但发布期间新旧版本会同时服务请求，接口、事件、数据库和缓存必须兼容。蓝绿发布维护两套完整环境，通过流量切换上线，回切快但资源成本高，状态同步和长连接迁移仍需处理。金丝雀发布把少量用户或 Workspace 导入新版本，以真实流量观察后逐步扩大，能降低爆炸半径，但要求稳定分流、版本标识、Cohort 指标和明确停止条件。

NoteWeave 的长任务不能只按 HTTP 请求所在实例理解。Job 可能在旧 Worker 上运行数小时，发布后新代码已经开始接收回调。ExecutionSpec、事件 Schema、Checkpoint 和 Callback 必须具备版本，旧 Worker 要 Drain 而不是立即终止。SSE 长连接也可能跨发布断开，客户端需要 Cursor 重连和有界 Replay。当前 Docker Compose 环境主要用于联调；若任务规模和发布频率增长，再把流量分组、实例替换和连接迁移纳入发布验证。

选择发布方式要看状态、成本和回滚能力。无状态短请求适合滚动；数据库不兼容改动不能靠蓝绿消除；模型或检索策略更适合 Shadow 加金丝雀；存在不可逆写入时，即便流量能秒切也无法真正回滚。发布成功条件应是用户 SLI、任务 Cohort、数据对账和成本均在预算内，不是新实例全部 Ready。

常见追问是“灰度 5% 怎么选”。随机请求分流会让同一用户在新旧版本间跳转，缓存、会话和长任务难以解释，通常按稳定 Hash 的 User、Workspace 或租户 Cohort 分组。5% 也未必有足够样本发现低频错误，应根据基线失败率和最小可检测差异计算观察时间。扩大前要检查错误切片，而不是只看总体平均值；一个大租户或特定文件类型的回归可能被总量掩盖。

## 12. 常见八股：配置、Feature Flag 与密钥如何发布

配置也有版本和兼容性。修改线程池、超时、重试、Provider 路由或检索 TopK 可能比代码变更影响更大，应经过评审、灰度、审计和回滚。动态配置需要明确读取频率、缓存、默认值、校验和失败策略；错误配置不能让所有实例同时重载并进入不可恢复状态。对相互依赖的字段应做整体校验，避免只更新一半形成无效组合。

Feature Flag 用来把代码部署与功能开放分开，但它会增加状态组合。每个 Flag 需要 Owner、Scope、默认值、过期时间、审计和删除计划。安全授权、数据库约束和幂等不能依赖 Flag，因为旧客户端、内部调用或配置错误可能绕过它。模型、RAG 与 Agent 写工具的灰度范围不同，Shadow 中的写操作必须 Preview 或写入隔离环境。

密钥通过 Secret 管理和注入，不进入 Git、镜像或普通日志。轮换要支持新旧密钥短期并存，先让验证方接受新密钥，再切换签发方，最后撤销旧密钥。NoteWeave 的 ProductionConfigurationGuard 会拒绝弱默认密钥、危险回退和不安全协议，但启动 Guard 只是最后一道门禁，还需要最小权限、轮换、审计和泄漏响应。

配置回滚也要保留语义兼容。把超时从 30 秒缩到 5 秒可能让旧长任务大面积进入 Waiting，把并发上限调高可能迅速打满 Provider TPM。动态配置平台应记录发布人、旧值、新值、Scope、时间和关联变更，关键参数使用两人评审或门禁。无法解析新配置时，服务应拒绝启动还是保留最后已知好版本，要按安全与可用性选择，不能静默采用危险默认值。

## 13. 常见八股：接口和消息如何做到向前、向后兼容

向后兼容通常指新服务仍能处理旧客户端或旧消息，向前兼容指旧服务遇到新数据时能够忽略未知字段或显式拒绝，而不是错误解释。JSON 新增可选字段通常较安全，删除字段、改变含义、收紧枚举和复用旧字段风险很高。事件 Schema 必须有版本，Consumer 应按自己理解的版本处理，Producer 不能假设所有 Consumer 同时升级。

数据库、缓存和消息要一起考虑。新代码写入旧代码无法解析的枚举后，代码回滚会失败；缓存 Value Schema 改变时，Key 应带版本或读取方支持双格式；Kafka Consumer Group 中新旧实例并存时，事件必须满足共同可读范围。长任务冻结 ExecutionSpec 可以避免运行中语义漂移，但恢复路径仍要保留对应版本的解释器或迁移器。

兼容性测试应同时启动 N 与 N+1 版本，覆盖旧写新读、新写旧读、重复消息、未知字段和回滚。Contract Test 证明协议样例兼容，不能替代真实数据库升级和跨版本端到端测试。面试官问“为什么不用停机发布”时，可以说明停机虽简化兼容，却损害可用性且无法处理外部回调和长任务，只有业务允许明确维护窗口时才可能是更低成本选择。

枚举演进是高频陷阱。新 Producer 发出 `WAITING_CAPABILITY`，旧 Consumer 若把未知值映射为默认成功，会破坏状态机；更安全的是保留 Unknown 分支、进入隔离队列或拒绝处理并告警。字段含义也不能原地改变，即便 JSON Schema 仍能解析。协议版本需要写清语义、废弃周期和 Consumer 升级门禁，指标按版本切片，才能知道旧流量何时真正消失。

## 14. 常见八股：发布失败后为什么不一定能回滚

代码是可逆的，数据和副作用未必可逆。新版本若删除列、改变加密格式、写入旧版本不认识的状态、发送外部通知或执行工具写回，切回旧镜像不能恢复原语义。回滚前必须知道写入了哪些数据、是否有旧版本兼容读、后台任务是否仍在运行，以及外部动作能否补偿。无法逆转的场景先关闭入口、冻结新任务并 Forward Fix，避免旧版本继续错误处理新数据。

数据回滚也不能简单恢复整库备份，否则会覆盖发布后产生的合法新数据。更常见的是补偿脚本、按事件反向迁移、修复 Projection 或将受影响对象隔离后重算。脚本需要幂等、Dry Run、影响行数门禁、速率限制和审计。ES Alias 回切只影响读流量，双写期间的差异仍要对账；Kafka 回退 Offset 会带来重复消费，Consumer 必须幂等。

面试回答要把回滚演练和恢复证据分开。演练应记录决定回滚的指标、操作时间、数据差异、长任务处理和用户影响。当前项目没有生产回滚演练证据，只能说明设计和隔离环境迁移测试。这样的边界不会削弱回答，反而说明候选人知道发布不是“镜像换回去”这么简单。

决定回滚的时间本身也要预算。检测时间、人工确认时间、执行时间和数据恢复时间共同构成用户影响窗口。自动回滚适合信号明确、操作可逆的无状态版本，错误率轻微波动或业务质量下降可能需要人工判断。每次发布应预先指定 Decision Owner、阈值和最晚决策点，避免故障时多方讨论却无人有权暂停扩容或关闭入口。

## 15. 发布工程母题长回答

### 15.1 数据库、事件和跨语言 Worker 如何兼容升级

滚动发布期间新旧版本会共存，因此数据库迁移先 Expand 后 Contract。先增加新列、新表或新枚举，使旧代码继续工作；发布能够读新旧格式的新代码；后台按可暂停、可重试的小批次回填；切换新写入并对账；确认旧版本、旧任务和旧数据都消失后，再删除旧结构。新增非空无默认字段、直接重命名或原地改变字段含义，会让旧实例和回滚失败。

事件 Schema 采用相同原则。新增可选字段通常较安全，未知枚举要进入 Unknown 或隔离，不能映射成默认成功。Producer 与 Consumer 不同时升级时，先升级接收方使其理解新旧，再切 Producer。每条事件带 SchemaVersion、EventId、AggregateId 与业务 Version。Contract Test 覆盖旧写新读、新写旧读、未知字段和重复消息，但还要启动 N/N+1 版本做端到端验证。

Java Host 与 Python Worker 的任务可持续很久，升级不能杀掉旧 Worker 就算完成。提交时冻结 ExecutionSpec、输入 Snapshot 与协议版本，旧 Worker 先停止 Claim 新任务并 Drain，在途任务继续 Heartbeat 或保存 Checkpoint。新 Host 仍需接受旧版本 Callback，并用 Token/Epoch 防止旧 Owner 晚到。无法长期维护旧解释器时，需要迁移任务或明确终止策略。

迁移脚本可执行不等于大表上线安全。完整证据包括空库创建、上一版本升级、跨版本兼容、数据校验、DDL 锁与耗时、回填速度、长任务 Drain 和回滚演练；仓库最高版本号 V104 也不替代这些证据。

### 15.2 ES 索引、模型策略和 Feature Flag 怎样灰度

Elasticsearch Mapping 不能总在原索引原地修改。常用流程是创建版本化新索引，从 MySQL/MinIO 真源回填，新写入通过双写或变更日志追平，比较文档数、业务 Version、抽样查询与 Gold 指标，再原子切换 Read Alias。旧索引保留一段时间用于读回滚。双写不能保证强一致，需要 Projection 状态、失败重试和对账；Alias 回切也不能修复新写入的兼容问题。

RAG、模型和 Agent 策略先离线 Replay，再 Shadow。Shadow 计算结果但不影响用户，比较 Recall、NDCG、Citation、P95、Token 与单位成功成本；写工具不能在 Shadow 产生真实副作用，只能 Preview 或写隔离目标。进入金丝雀后按稳定 Workspace/User Hash 分组，避免同一用户在版本间跳转。总体指标之外，还要按文件类型、语言、租户和失败原因切片。

Feature Flag 将代码部署与功能开放分离，每个 Flag 需要 Owner、Scope、默认值、过期时间、审计和删除计划。Flag 不能代替权限与数据库约束。扩大灰度前定义样本量、观察时间、质量、成本和停止阈值，出现异常先关闭入口或回切流量，再决定回滚代码还是 Forward Fix。灰度能力应结合目标流量和发布频率验证，不能由本地 Compose 直接推导。

灰度结束后要删除旧策略和 Flag，长期双路径会让测试组合指数增加。模型质量指标存在随机波动，应固定输入快照、Provider 版本和评测集，并同时看失败案例。若新策略只提升平均质量却让高价值租户成本翻倍，需要按业务权重重新判断，而不是机械通过总分门禁。

### 15.3 回滚、发布门禁和恢复怎样形成闭环

回滚分代码、配置、流量、索引和数据。代码回滚要求新数据仍能被旧代码理解；配置回滚要求旧值语义仍有效；流量切回不能撤销外部通知或写工具副作用；Alias 回切只修复读路径；数据回滚风险最高，整库恢复会覆盖发布后的合法数据，通常需要补偿脚本、反向迁移或按对象修复。无法安全回滚时先关闭入口、冻结后台任务并 Forward Fix。

发布门禁覆盖单元、契约、集成和迁移测试，生产配置 Guard、备份可用性、容量与成本预算、回滚命令、Decision Owner 和观察窗口。Liveness 只回答进程是否需重启，Readiness 回答是否能接新流量，把短暂下游故障放进 Liveness 可能制造重启风暴。发布后看用户 SLI、任务 Cohort、最老积压、数据对账和单位成本，不以 Pod 或进程全部存活作为成功。

恢复按每个真源定义。MySQL 保存业务状态，对象存储保存原始内容，Kafka 保存可重放命令，ES 保存可重建投影，Redis 保存短期配额、租约和 Replay 状态。随着数据量和停机影响增加，需要分别测量回填、对账、连接恢复和状态重建耗时，不能只给一个笼统恢复数字。

演练记录检测、决策、执行和数据恢复各阶段耗时，验证重复消息、长任务、用户连接与最终对账。NoteWeave 当前已有隔离迁移和测试证据；当规模或恢复窗口提出明确要求时，再按这些指标补充演练。五分钟回答最后主动说清当前实现、测试证据和容量假设的边界。

一次完整演练还应验证监控和人工操作能否工作：告警是否在预算内触发，Runbook 是否指向正确状态表，恢复脚本是否支持 Dry Run、限速和幂等，恢复后用户是否能重新获取终态。备份文件存在不代表可恢复，只有在隔离环境完成还原、应用启动和数据抽样校验后才算证据。

## 16. 发布题中的项目真实设置

当前 Compose 是开发与演示拓扑：MySQL 8.4、Redis 7.2、Kafka、MinIO、Elasticsearch 与 Backend/Worker 容器。服务有 Healthcheck 和 Restart Policy，Research Consumer 使用 `on-failure:5`。发布题应围绕当前的版本兼容、Drain、回滚和对账回答；当流量、任务时长或发布频率增长，再补充目标部署形态的验证。

Research Worker Drain Grace 为 30 秒、Poll Timeout 500 ms；Task Lease 60 秒、Heartbeat 15 秒。当前 Artifact MCP Process Timeout 为 3600 秒、旧 Outbox Lease 为 70 分钟，发布时必须处理长消费会话。推荐迁移后，Kafka Consumer 只登记 Durable Execution，Drain 重点变成停止 Scheduler Claim、等待有界 Grace、保存 Checkpoint，再由 Execution Lease/Epoch 接管旧 Owner，不再等待 Kafka Poll 一小时。

Research Rollout Guard 的代码默认窗口 15 分钟、最小样本 10、Terminal/Delivery Failure 上限各 20%、Rejected Merge 上限 30%，但 Compose 默认把 Guard 关闭。面试时应说“实现了门禁参数，当前演示环境没有默认启用”。最小样本 10 也不能代表生产统计显著性。

Production Guard 的真实门禁包括：不同 Audience 内部 Token 必须独立，Redis/ES/Kafka 密钥不能是弱值，Worker、MinIO 和 ES 使用 HTTPS，Kafka 使用 SSL 或 SASL_SSL，并禁止 Local User、QA MySQL、Quota Local 与 LLM Template 回退。完整来源见[项目真实配置参数与容量口径](15-项目真实配置参数与容量口径.md)。

## 18. 发布题的上下游 4 到 5 分钟完整回答

发布不是把新镜像替换旧镜像，而是同时改变 Java 代码、MySQL Schema、Kafka Payload、Python Worker、ES Projection、配置和前端契约。一个安全发布先识别哪些对象会被旧版本读取，哪些消息会在队列中滞留，哪些任务会跨版本运行，再按兼容顺序推进。数据库采用 Expand/Contract，先增加可空或带默认值的字段，让旧代码也能工作；应用和 Worker 先发布兼容读写，再做回填、索引和策略切换；确认所有消费者都能理解新语义后，最后才删除旧字段或收紧约束。Flyway 只负责按序执行迁移，不替代应用兼容和数据回滚设计。

事件和跨语言协议需要向前、向后兼容。Producer 新增字段时，旧 Consumer 应能忽略或使用安全默认值；新 Consumer 读取旧消息时，必须区分缺失、空值和未知版本，永久不兼容的消息进入明确终态或 DLT。Research 和 Artifact 的任务输入绑定 Input Snapshot、Contract Version 或 Spec Hash，旧任务继续使用旧输入，不能在 Worker 重启后自动读取新字段。Callback 也要校验 Task、Attempt、Delivery Token 和 Version，避免新 Worker 的回调误推进旧 Job。前端 API 类型和 SSE 事件名称同步更新，但老浏览器重连仍要能识别终态和游标。

检索不能原地覆盖 ES Index。新的 Chunk 策略、Embedding 维度或 Mapping 创建新 Generation，构建开始时冻结 Catalog Watermark，先回填固定基线，再用 Change Log 追平期间的上传、更新和删除。计数、版本、Workspace 归属、质量 Receipt 和增量水位全部通过后，才按环境、索引族或租户桶切换 Alias；失败继续读旧 Generation，切换后保留回切窗口。Shadow 和 Feature Flag 让新 RAG 策略先旁路产生候选，不影响在线结果，Release Gate 未通过时拒绝扩大。研究执行模式和 Provider 也要由 Rollout Guard 控制，窗口内的失败率、拒绝率、成本和质量都应能回到同一个 Run。

回滚要先区分代码、配置、数据和外部副作用。代码可以切回旧镜像，配置可以恢复旧 Provider 或 Feature Flag，数据库破坏性变化通常不能简单回滚，只能用补偿迁移和 Forward Fix，已发送的 Kafka 命令、已写的 MinIO 对象和已生成的 Artifact 版本也不能假装消失。长任务发布时停止新派发，给在途 Worker 留出 Grace，超时由 Lease 和 Fencing 接管；不要只依赖容器收到 SIGTERM。当前仓库有配置 Guard、Flyway、Alias、Rollout 和 Lease 测试，面试中按当前保护、验证门禁和目标规模分别回答。

## 19. 一次完整发布事件：考试周前灰度 Research 新策略

这是 `[演练假设]`，用于回答发布过程和决策，不是生产事故或真实学校上线记录。

### 变更内容

准备上线新的 Research Intent Matrix、严格 Evidence Validation 和增量 Checkpoint Hydration，同时升级部分 Research 表结构与 Worker Callback 字段。风险不只在模型效果：旧 Run 可能仍按旧 Task Snapshot 执行，新 Worker 可能回调旧 Host，新增字段可能让旧 Consumer 解析失败，策略还可能扩大 Search/Read/Token 成本。

### 发布前拆分

先把一个大变更拆成四个可独立停止的步骤：

1. Schema Expand：新增表、可空字段和索引，旧 Host 不读取也不受影响。
2. 兼容代码：Host 能读取旧/新 Schema，Worker Callback 新增字段保持可选并带版本。
3. 数据与策略准备：回填需要的数据，冻结 Gold、Prompt、Provider、预算和 Feature Flag 组合。
4. 功能开放：Shadow 只计算候选，再按稳定 Workspace Cohort 灰度，最后才考虑 Contract。

Flyway 文件一旦进入共享环境不修改原脚本，发现问题新增向前修复 Migration。大表索引或回填不与实例启动强绑定，使用有界批次、游标、影响行数和对账，避免一个实例迁移超时把所有副本卡在 Readiness 之前。

### 跨版本执行

Research Run 创建时保存 Feature Flag Snapshot，已开始的 Run 不读取发布后的动态 Flag。Task Snapshot 还固定 Execution Mode、Schema、角色、预算和 Fencing 信息。发布 Worker 时先停止领取新任务，已有任务继续 Heartbeat、写 Checkpoint 或完成；新 Host 保留旧 Callback 解释路径。旧 Worker 晚到的 Completion 仍要经过 Owner、Epoch、Fencing 和 Run 状态，不能因为协议兼容就无条件接收。

### Shadow 与灰度

Shadow Cohort 使用相同学校 Gold 与 Source Snapshot，比较 Required WorkItem Completion、Citation Support、Rejected Merge、Terminal Failure、Delivery Failure、P95 和单位成功成本；比较型 Cohort 再单独比较 Matrix Cell Coverage。写工具、副作用和 Memory Promotion 在 Shadow 中关闭或写隔离目标。通过离线门禁后，按 Workspace 稳定 Hash 选择灰度，避免同一课程新旧策略来回跳；高价值课程和内部演练 Workspace 可先进入观察组。

当前 Research Rollout Guard 有 15 分钟窗口、最小样本 10、Terminal/Delivery Failure 上限 20%、Rejected Merge 上限 30% 等配置入口，但最小样本 10 只适合保护性门槛，不代表统计结论，Compose 是否启用也要按实际配置说明。灰度还要看质量、成本和关键切片，不能只满足失败率。

### 止损与恢复

如果失败集中在新策略，先关闭对应 Feature Flag，停止新增 Cohort，不立刻回滚 Schema，因为 Expand 结构对旧代码兼容。正在运行的 Run 继续使用冻结 Snapshot，除非存在安全或不可逆副作用才取消。若问题来自新 Worker Callback，暂停新命令、保留旧 Worker 或回切 Worker 镜像；若新数据已经使用旧代码不认识的语义，优先 Forward Fix，不盲目回滚 Host。

恢复判定不以实例 Ready 为准。要确认新 Cohort 不再扩大、旧策略完成率恢复、Queue Age 开始下降、DLT 和 Rejected Merge 没有继续增长、已开始 Run 的终态可解释、Schema 对账无差异。观察窗口结束后才清理 Flag 和旧解析路径，Contract 删除更晚进行。

### 当前事实边界

`[当前实现]` 可以讲 Research Feature Flag Snapshot、Rollout Guard、版本化任务与回调、Lease/Fencing、Flyway 和配置门禁。`[目标设计]` 是把发布批次、Cohort、质量 Receipt、代码/Schema/Worker 版本和回滚动作统一进签名 Release Manifest。`[生产待验证]` 包括真实考试周流量、统计显著性、完整 Drain 时长、跨可用区发布和恢复数据。

## 20. 重点知识点：数据库 Expand、Migrate、Contract

### 3 分钟回答

滚动发布时新旧应用会同时访问同一个数据库，因此数据库迁移的第一要求不是“SQL 能执行”，而是共同可读写。Expand 先增加旧代码看不见也不会失败的结构，例如 Nullable 列、新表、兼容索引或新枚举旁路字段；Migrate 发布能同时理解新旧格式的代码，必要时双写并用后台任务回填；Contract 只有在旧实例、旧 Worker、旧消息、旧 Snapshot 和旧数据全部退出后，才停止旧写并删除旧结构。

增加 Non-null 字段不能直接要求所有历史行立刻满足。先允许空值或给安全默认，代码写入新值，回填按主键/时间游标分小批执行，每批记录扫描范围、更新行数和校验摘要。回填必须可暂停、可重试、幂等，并控制数据库 CPU、锁等待、复制延迟和 Hikari Pending。完成后先加读门禁和一致性校验，再收紧约束。

字段重命名通常用“新增新列、兼容读、双写、回填、切读、停旧写、删除旧列”，而不是一次 Rename。枚举语义变化更危险，旧代码可能把未知状态当成功；应保留 Unknown/Rejected 路径或引入新字段。Flyway 保证 Migration 顺序和一次性执行，不保证在线 DDL 无锁，也不提供业务级回滚。已发布脚本不修改，错误通过新 Migration 向前修复。

是否可以回滚取决于新版本写了什么。若只 Expand，代码回切通常安全；若已写入旧版本无法解析的新状态，切回镜像会扩大错误，需要保留兼容 Reader 或 Forward Fix。Contract 是不可逆风险最高的阶段，应晚于完整观察窗口和备份还原演练。仓库迁移编号和空库成功都不能替代上一生产版本升级、数据分布、DDL 耗时和回滚路径验证。

### 二阶追问：双写期间两列不一致怎么办

先定义哪个字段是真源和切换阶段。写路径在同一事务更新两列，后台对账按主键找差异；读取先旧后新或新后旧要有明确优先级，并记录 fallback。不能用“最后写入时间较新”猜语义。差异修复完成、旧写入归零后再切读。

### 二阶追问：为什么不在启动时自动完成全部回填

回填时间和锁影响随数据量增长，绑定启动会让所有新实例同时争抢数据库，也会延长 Readiness。Schema Expand 可以由迁移完成，数据回填用单独的有 Lease Job 执行，并暴露进度、速率、失败和暂停控制。

## 21. 重点知识点：Feature Flag、Shadow、Canary 和 Rollback

### 3 分钟回答

代码部署回答“新逻辑是否已经存在”，Feature Flag 回答“哪些请求可以使用”。二者分离后可以先部署兼容代码，再逐步开放功能，但也引入了组合状态。Flag 必须有 Owner、Scope、默认值、创建原因、到期时间和删除计划；安全授权、数据库约束和幂等不依赖 Flag，否则一次配置错误就会绕过硬边界。

Shadow 不改变用户结果，适合检索、规划和只读工具的新策略对比。它必须冻结同一输入，保存 Baseline/Treatment、Cohort 和成本；写工具、外部通知、Artifact 发布和 Memory Promotion 只能 Preview 或进入隔离目标。Canary 才让一小部分真实 Workspace 使用新结果，按稳定 Hash 分流，避免同一用户在版本间漂移。灰度比例由最小样本、错误基线、最小可检测差异和风险决定，不机械使用 5%。

扩大前同时看用户 SLI、错误、延迟、成本、降级和关键切片。Research 还要看 Required WorkItem Completion、Citation、Rejected Merge、Lease Lost 和 Provider 预算，比较型任务补 Matrix Cell Coverage；RAG 看 Recall、Citation、Refusal 和 Scope Violation；Artifact 看 First-pass/Repair 和文件可用性。安全不变量是零容忍，平均质量提升不能抵消一次跨 Workspace 泄露。

Rollback 不是一个按钮。Flag 关闭只阻止新请求，已经创建的 Run 仍使用冻结 Feature Flag Snapshot；代码回滚要求新数据兼容；Alias 回切只恢复检索读路径；外部副作用需要补偿；数据库 Contract 可能只能 Forward Fix。发布前要定义停止阈值、Decision Owner、最晚决策点和每种回滚动作，事故时才能先控制爆炸半径，再处理数据。

### 二阶追问：Feature Flag 为什么要保存到 Run Snapshot

长任务可能跨越发布窗口。若每个步骤动态读取当前 Flag，同一个 Run 前半段用旧策略、后半段用新策略，恢复也无法复现。Snapshot 让运行语义稳定；安全紧急开关可以取消 Run 或在副作用提交前重新校验，但不能静默改变中间算法。

### 二阶追问：Shadow 通过为什么还要 Canary

Shadow 看不到用户交互、真实缓存、并发争用、Provider 限额和副作用链路，且常使用固定数据。Canary 验证真实环境，但限制影响范围。两者回答不同问题，离线 Gold、Shadow、Canary 和全量开放不能互相替代。

## 22. 发布与回滚的二阶追问

### 新版本已经写入新枚举，如何紧急回滚

先确认旧版本是否有 Unknown 分支。能安全读取时回切代码，并关闭新写入；不能读取时不要把流量交给旧版本，先用 Flag 关闭入口或发布兼容 Reader 的 Forward Fix。受影响记录按版本隔离和对账，不能批量改成某个旧状态掩盖语义。

### Kafka 中还有旧版本消息，什么时候能删旧 Consumer 解析器

不仅看 Broker Retention，还要看 DLT、重放库、Checkpoint 和暂停的长任务。旧 Schema 消息可能在 Redrive 时重新出现。只有保留期结束、DLT 清空或完成迁移、旧 Producer 归零并有版本指标证明后，才删除；无法解析的历史消息要有明确归档或终态策略。

### Alias 切换成功但 MySQL 显示失败，发布到底算什么状态

这是结果未知，不先宣告失败。读取 ES Alias 实际指向、候选 Generation 和 Release Manifest：已指向目标则幂等补写数据库；仍是旧版本才可重试；QA/Note Alias 分裂则回切完整上一 Manifest。当前项目还缺统一 Manifest 与 Reconciler，因此只能把它作为目标闭环，不能说已经自动处理。

### 自动回滚什么时候会害人

指标抖动、样本过少或新版本已产生不可逆写入时，自动回切可能反复震荡或让旧代码读取新数据。自动回滚适合信号明确、版本兼容、动作幂等的无状态或纯读策略；数据迁移、外部通知和长任务通常先自动停扩、人工判断后处理。

### 发布期间旧 Worker 的 Lease 过期，新 Worker 能否直接接管

只有新 Worker 理解旧 Task Snapshot 和 Callback Contract 才能接管。Claim 产生新 Epoch/Fencing Token，旧 Worker 即使恢复也不能提交。若新镜像已删除旧解释器，应该先 Drain 或显式迁移任务，而不是依赖 Lease 强行接管。

### 怎样证明备份真的能恢复

备份成功只证明文件被写出。要在隔离环境还原 MySQL 与对象引用，运行 Flyway/应用兼容检查，抽样校验 Workspace、Source、Run、Outbox 和文件 Hash，再测到 Readiness 与核心用户旅程的耗时。RTO/RPO 只能来自这样的演练，不能从备份频率直接宣称。

### 前端与后端不同步发布怎么办

API 新增字段保持可选，旧字段在浏览器版本存活窗口内不能立刻删除；SSE 新事件类型要让旧客户端忽略未知事件并最终通过 Snapshot 收敛。破坏性改动使用 API/事件版本或兼容适配层，并监控旧客户端占比。仅在同一静态站点强制刷新且没有离线客户端时，兼容窗口才可能缩短。
