# 行为面试与现场系统设计题

> 使用边界：演化候选方案可参考 [系统设计演化与技术取舍](../系统设计演化与技术取舍.md)，但 Situation、个人 Action、协作和 Result 必须由候选人本人证据确认。设计题可以讲 `[目标设计]`，不得包装成 `[当前实现]` 或生产经历。

## 1. 行为面试不能虚构

本文件提供问题结构，不替候选人编团队经历。所有 Situation、Action 和 Result 必须来自真实开发、审查、协作或学习过程。个人项目也能回答 Ownership，但要明确没有跨团队和真实生产用户时的边界。

## 2. STAR 的工程化写法

Situation 用两三句话说明业务、约束和风险；Task 说明本人承担的决策，不写“团队需要”；Action 重点写如何判断、比较和推进，不把团队成果全部归为个人；Result 给证据与边界；最后补 Reflection，说明后来改变了什么方法。

```text
S：当时出现了什么具体约束
T：我需要对哪个结果负责
A：我收集了什么证据，比较了什么，做了什么
R：测试、指标、交付或风险发生了什么变化
Reflection：第一次哪里想错，以后如何避免
```

## 3. 必备八个行为案例

### 3.1 最大技术挑战

可选真实材料：跨存储删除、Outbox 最后一次 Claim 崩溃、Research 原子完成、Context Snapshot 一致性。重点解释为何普通重试不够，以及如何枚举失败窗口。

### 3.2 做错的技术决策

选择一个审查后修复的问题。比如早期 Cleanup 只在 Post-commit Listener 中执行，方向上避免了事务回滚问题，却遗漏了进程崩溃后清理意图丢失。回答应承认第一次设计的不完整，不把它包装成计划内演进。

### 3.3 在时间不足时如何取舍

可以使用“编译期 DAG、运行时线性执行”。线性执行限制并行度，却保持状态与恢复简单。说明当时为什么不实现 Ready Queue，未来由什么指标触发升级。

### 3.4 如何处理不同意见

必须填写真实人物与意见，没有团队争议就使用技术方案评审，不假装跨团队冲突。回答应包含双方方案的优点、决定标准、如何做小实验，以及被否决一方如何继续参与。

### 3.5 如何保证质量

不要只报测试数量。说明先定义不变量，再写故障窗口测试，之后做代码与文档对照审查。可以使用 RAG Fixture 口径被纠正为手工回归基线的案例，体现发现证据不足后主动收敛说法。

### 3.6 如何推动复杂任务

按边界拆分：MySQL 真源、Outbox 发送意图、Consumer 幂等、Projection 重建、监控与对账。说明每一步如何定义完成条件，避免只说“拆成小任务”。

### 3.7 一次失败经历

测试 OOM、编码失败或审查发现的安全边界都可以，但要说明本人实际做过的排查。没有参与修复的案例不能说成个人行动。

### 3.8 最有影响力的结果

个人项目不使用虚构用户量。可以报告工程结果，例如修复某个永久卡死窗口、完成真实 MySQL Migration 验证、让测试套件在固定环境通过。业务影响没有证据时明确说尚未上线验证。

### 3.9 学校场景的八个完整演练母稿

> `[演练假设-待本人确认]` 这些故事以真实代码、测试和缺陷为技术骨架，学校使用范围、个人行动、协作对象、时长和业务结果是理想模拟答案。面试前必须按本人实际经历删改。没有发生过的线上故障只能说成代码审查或故障测试发现。

#### 故事一：最大技术挑战，资料为什么不能继续同步处理

**Situation**，学校原型需要让教师上传课件，学生随后在课程 Workspace 中提问。初版把上传、解析、切片和索引串在一条请求链路里，小文件演示正常，但大课件、多个课程集中更新时，请求等待时间变长，某一步失败后也很难判断资料是否已经可检索。

**Task**，我负责把“上传成功”拆成持久接收和可检索两个业务承诺，并保证 MySQL、对象存储、Kafka 与 ES 之间没有全局事务时，命令不会静默丢失，重复执行也不会生成第二个业务结果。

**Action**，我把 MySQL 设为 Source、Snapshot、Task 和 Outbox 的真源，原文件进入对象存储，事务内同时提交业务状态与 Outbox。Dispatcher 用 Claim、Attempt 和 Lease 领取，Kafka Consumer 按业务身份和 Snapshot Version 幂等，ES 只保存可重建投影。Projection Ready 由 Finalize 条件更新确认，旧 Snapshot 晚到只能影响零行。删除则先让 MySQL 状态不可见，再持久化 Cleanup Task 收敛外部副本。

**Result**，仓库测试已经覆盖重复投递、ES 写后 Finalize 失败、旧版本晚到和删除重试。理想演练结果可以补充为 1,036 个主流文件中 99.4% 在 Deadline 内达到正确 READY，P95 为 18.6 秒。该数字没有实测前，只报告测试覆盖和计算口径。

**Reflection**，我后来设计异步流程时会先列每次跨系统 I/O 前后进程退出的窗口，再决定重试、幂等、补偿和对账，不再只画 Happy Path。

#### 故事二：做错的技术决策，把清理当成事务后的附加动作

**Situation**，我最初把 MinIO 和 ES 清理放在事务提交后的 Listener 中。这样避免数据库回滚时外部对象已经被删除，但外部调用失败后只记日志，进程退出会让清理意图永久丢失。

**Task**，我需要让资料删除既能立即阻止在线读取，又能最终清理所有派生内容，并证明最后一次重试后进程退出也不会留下永久 `PROCESSING`。

**Action**，我承认原设计只解决了事务顺序，没有解决可靠交付。修复时新增持久化 `source_cleanup_task`，删除事务内写清理意图，调度器通过 Owner、Lease、Attempt 和 Fencing 领取。失败有界重试，耗尽后进入 Dead Letter；统一使用数据库时间判断 Lease，并用 SHA-256 生成稳定对象幂等身份，避免长 Key 唯一索引问题。

**Result**，测试覆盖重复清理、外部临时失败、最后一次 Claim 后退出、多个扫描器竞争和 Dead Letter；Flyway V090 在隔离 MySQL 8.4.9 从空库应用并验证约束。这里能声称的是设计缺陷被审查和测试关闭，不能说发生过线上数据泄露。

**Reflection**，日志只能帮助诊断，不能承担可靠队列。凡是业务要求“最终必须完成”的动作，都要有持久身份、生命周期、终态和对账入口。

#### 故事三：时间不足时的取舍，运行期先线性执行 Skill Graph

**Situation**，后续为了课程调研和产物生成，我需要支持 Skill 依赖、验证和修复，但开发窗口有限。完整 DAG 调度器还需要 READY/RUNNING 状态、条件边、并行写合并和节点级恢复。

**Task**，我需要在可审计、可重放和交付时间之间做取舍，避免为了并行度引入当前场景用不到的状态复杂度。

**Action**，我保留编译期 DAG，用 Kahn 拓扑排序检查未知节点、重复 ID 和环；运行期把合法图固化为顺序 `node_sequence`，按序执行并在每个节点后验证或修复。网络 Fetch 可以受限并发，但业务节点不并行提交状态。文档明确记录当前没有 Ready Queue、条件边和节点级并行。

**Result**，当前执行路径的依赖顺序和失败位置更容易确定，能够用同一 ExecutionSpec 回放；代价是独立节点不能并行缩短总时长。升级触发条件设为 P95 长任务时长、可并行节点占比和 Provider 预算证明并行收益大于状态复杂度。

**Reflection**，取舍题需要说清楚暂时不做什么、失去什么，以及什么证据会改变决定，不能把未完成包装成刻意设计。

#### 故事四：如何处理不同意见，早期是否需要 Kafka

**Situation**，在学校规模下，直接用 MySQL Polling Outbox 驱动 Worker 更简单；另一种方案是引入 Kafka，获得分区、多 Consumer、保留重放和独立积压观测。这个分歧可以来自技术评审，不需要编造团队冲突。

**Task**，我需要避免把“大厂常用”当选择理由，给出当前规模下可验证的判定标准。

**Action**，我把问题拆成命令是否需要多类 Consumer、事件保留多久、是否需要按 Workspace 或 Snapshot 保序、数据库轮询压力、故障恢复和部署成本。结论是业务状态与发送意图仍由 MySQL Outbox 保证，Kafka 只负责跨进程异步传输；早期也可以先让 Poller 直接调用 Worker。当资料解析、索引、Research 和 Artifact 形成多个独立消费者并需要重放时，再启用 Kafka。

**Result**，当前代码保留 Outbox 作为可靠性核心，没有把 Kafka Transaction 误当成 MySQL 与 Broker 的全局事务。演练时可以说最终选择 Kafka 是为了多 Consumer 和可重放，但必须承认对单机学校 Demo 有运维成本。

**Reflection**，我会先比较业务语义和失败窗口，再比较组件；未选方案在规模变化后仍可能成为更好的方案。

#### 故事五：如何保证质量，主动推翻“100% 准确率”口径

**Situation**，早期 RAG Fixture 在 3 到 6 个固定样本上出现过 100% 结果。这个数字适合做回归，却容易被误写成线上 Hybrid 检索准确率。

**Task**，我需要让评测既能阻止越权和质量退化，也不会用小样本制造虚假的项目收益。

**Action**，我把评测对象固定为 Case、Dataset、Strategy、Provider/Model、Index/Snapshot、Prompt/Schema、Judge/Rubric 和 Gate Policy。质量层报告 Recall、MRR、nDCG、Citation Support 和拒答；安全层把 Scope Violation、危险工具和失效 Snapshot 设为硬门禁；Observation 保留 Bundle、Trace 和失败分类。发现当前只有 4 Case/3 Case 后，我把它降级为 L0 机制回放，并设计 320 条课程分层 Gold 的理想采集方案。

**Result**，当前能证明 Quality Gate 会拒绝固定退化 Fixture，不能证明线上准确率。理想演练答案可以使用 Hybrid Recall@5 从 0.742 到 0.869，但取得真实标注和 Manifest 前不写入简历。

**Reflection**，测试通过和业务有效是两层证据。遇到漂亮数字时先检查分母、样本分布、对照和置信区间，再决定能否宣传。

#### 故事六：如何推动复杂任务，把 v2 改造拆成可验收边界

**Situation**，从学校资料原型改造成当前 v2 时，资料、问答、Research、Artifact、Memory 和前端会互相依赖。如果按页面或组件并行堆功能，很容易出现 Worker 直接写业务表、检索结果绕过 Ownership 或旧接口重新成为真源。

**Task**，我负责把改造拆成可以独立验收的协议和不变量，并控制迁移期间新旧路径的边界。

**Action**，我先稳定 Workspace、Source、Snapshot、Task 和 Outbox，再建立 Java Host 与 Python Worker 的内部 Contract；随后分开 QA、Note、Wiki 的 Retrieval Plan，最后增加 Research、Artifact 和 Memory。每一阶段都要求业务入口、状态真源、失败窗口、测试和退出条件，使用 Flyway 演进 Schema，并通过 Architecture Boundary Test 防止 Worker 写表和 Memory 反向依赖 Retrieval。

**Result**，当前仓库形成 Java 控制面加两个 Python Worker 的清晰边界，核心状态和内部契约都有迁移或测试落点。项目仍是本地 Compose 和演示基线，没有跨团队发布节奏时，不把这个故事说成组织推动。

**Reflection**，复杂任务的推动结果不只是“按时完成”，还包括后续接手者能判断事实源、失败责任和验证入口。

#### 故事七：一次失败经历，环境问题被误判成业务测试失败

**Situation**，完整 Maven 测试曾反复非零退出，最初容易把它归因于测试不稳定。`hs_err_pid` 实际显示 G1 Virtual Space `mmap` 失败，测试 Fork、容器和其他进程共同占用机器内存。

**Task**，我需要先恢复可重复的测试环境，再判断业务断言是否真的失败。

**Action**，我先区分 Assertion Failure、Java Heap OOM、Native Allocation Failure 和进程被系统终止；随后限制 Surefire `-Xmx`、Fork 数和复用策略，分模块运行定位峰值来源，并记录机器、JVM 和容器依赖。类似地，Artifact Worker 在 Windows 的非 ASCII 输出失败通过比较原始字节和 Locale，最终在子进程读取处显式指定 UTF-8。

**Result**，历史审查记录中 Backend 全套 755 个测试完成，0 Failure、0 Error、11 Skipped。这个数字带时间边界，不替代当前重新执行，也不证明生产效果。

**Reflection**，交付证据依赖可运行的测试基础设施。环境失败和代码失败必须分开归因，修复后还要留下相同环境可复现的命令。

#### 故事八：最有影响力的结果，建立可验证的学校知识闭环

**Situation**，学校服务最容易把成功定义成上传量或问答次数，但这些数字不能说明学生是否拿到可信结果，也不能说明教师是否减少重复维护。

**Task**，我需要把项目结果从调用量改成有效结果，同时给质量、成本和安全设置护栏。

**Action**，我定义激活为首次资料 READY 后完成一次有效回答，采纳要求回答在观察窗内未被重跑且被收藏、引用或标记有帮助。QA 同时看 Recall、nDCG、Citation Support、拒答和 Scope；资料链路看 Projection Ready 和删除收敛；Research 看 Field Coverage、Checkpoint Recovery 与单位成功成本。

**Result**，理想演练数据为 216 名受邀用户中 174 人激活，2,934 个已接受任务中 2,846 个成功，2,124 个有效结果被采纳。它展示了完整计算方式，但当前没有生产日志时只能说“这是计划中的理想验收口径”。真实工程影响仍用 Outbox、投影、Fencing 和测试结果回答。

**Reflection**，面试中的影响力由可验证的用户结果和本人决策共同支撑，组件数量、代码行数和调用次数都不能替代它。

## 4. 高频主管面追问

- 为什么做这个项目，用户是谁？
- 哪一部分最能代表你的能力？
- 哪一部分设计过度了？
- 如果只给两周，会砍掉什么？
- 哪个决定是你独立做的？
- 你如何证明方案比旧版好？
- 遇到不会的问题如何推进？

- 如果重做一次，第一周会改什么？

每题准备 2 分钟版本与 5 分钟追问版本。

## 5. 现场系统设计统一流程

### 5.1 需求澄清

确认用户、核心动作、读写比例、延迟、可用性、一致性、多租户、安全、保留期和成本。没有确认“上传成功是持久化还是可检索”，后续设计会在错误目标上优化。

### 5.2 容量估算

估算 DAU、峰值 QPS、对象大小、Token、保存年限和增长。用 Little 定律计算在途，用副本与索引放大计算存储。数字可以是假设，但公式、单位和假设必须公开。

### 5.3 API 与数据模型

定义同步响应、异步 Job、幂等键、分页、错误码和状态查询。数据模型说明主键、唯一约束、版本、索引和真源。不要一开始画几十个服务。

### 5.4 核心链路与失败

先画最重要的写链路和读链路，再枚举每次跨系统 I/O 前后崩溃。说明重试、幂等、补偿、顺序、背压和降级。

### 5.5 安全、观测与演进

补多租户 Scope、内部认证、输入安全、删除语义；定义 SLI、Dashboard 和告警；最后讲什么规模或指标触发分库、CDC、向量库或图执行器。

## 6. 现场题一：设计多租户知识库与 RAG

### 6.1 需求

支持 Workspace 上传资料、异步解析、关键词/向量检索、带引用回答、删除和权限变更。上传接收 P95 与可检索时间分开定义，检索必须 Fail Closed 防跨租户泄漏。

### 6.2 设计主线

MySQL 保存 Source/Snapshot/ACL，Object Storage 保存原文件，Kafka 传输解析与索引命令，ES/向量库保存可重建 Projection。上传写对象后在本地事务创建业务状态与 Outbox。Consumer 幂等，索引按 Snapshot Version 切换。查询前下推 Scope，命中后批量回 MySQL 校验 Ownership。

### 6.3 深追问

容量问 Partition、Embedding 配额与索引大小；一致性问上传到可检索窗口；安全问脏索引与撤权；质量问 Recall/NDCG/Citation；演进问何时拆独立向量库。

## 7. 现场题二：设计长任务 Agent 平台

### 7.1 需求

支持报告、研究和工具任务，运行几分钟到几小时，可暂停恢复、多租户限流、Provider 故障切换、受控写回。

### 7.2 设计主线

提交时冻结 ExecutionSpec 与 Input Snapshot，MySQL 保存 Job/Attempt/Checkpoint，Outbox 派发，Worker 使用 Lease/Epoch/Fencing。Redis 令牌桶控制到达速率，并发租约限制在途。只有具备持久等待与唤醒契约的能力在 Provider 不可用时进入 Waiting，并在恢复时复用原 Spec；Research 的 429 当前走有界重试和失败分类。工具能力取系统、Skill、Workspace、审批和运行环境交集，写回由 Host 最终授权。

### 7.3 深追问

为什么不自由 Agent，为什么令牌桶不能替代并发租约，旧 Worker 晚回调怎么办，Provider 成功但 ACK 丢失怎么办，如何控制 Token 与 Repair 成本。

## 8. 现场题三：设计断线重连的流式回答

### 8.1 需求与模型

客户端建立 SSE，服务生成 Delta 和 Terminal Event。每个 Run 或 Conversation 有单调 Sequence，服务保留有界 Replay Window。客户端带 Cursor 重连，只读取之后事件。

### 8.2 正确顺序

连接时先 Prime Replay，再订阅 Live，避免终态先到导致历史 Delta 丢失。多实例通过 Redis Stream/Bridge 传播，进程内 Mux 负责 Subscriber Queue。慢消费者队列满时合并 Delta 或断开，不能无限占内存。

### 8.3 边界

Cursor 早于保留窗口时显式返回 Expired，引导客户端查询最终结果。断线重连不能重新启动生成，Terminal 与历史结果以持久业务状态为准。

## 9. 现场题四：设计文档删除与合规清理

删除先在 MySQL 提交不可见状态，使在线查询立即 Fail Closed；事务内写 Cleanup Task；事务后删除 ES、MinIO、缓存和派生内容。任务有幂等键、Lease、Attempt、DLQ 和对账。Run Snapshot 与 Summary 若引用删除正文，只保留允许的 Tombstone/Hash，Replay 降级。

追问重点是隐私删除与可回放冲突、清理时延、无法删除外部副作用时如何补偿，以及如何证明全部派生已清理。

## 10. 系统设计表达禁区

- 未估算容量就直接分库分表。
- 把 Kafka 当成一致性方案。
- 把 Redis 当业务真源。
- 只说微服务、扩展性和最终一致，不给失败窗口。
- 只报部署组件名称，不说明队列、任务和数据规模。

## 11. 行为面试常见八股

### 11.1 你遇到过最大的失败是什么

选择一个本人确认过、确实改变了后续设计的问题。可以使用 Cleanup 只在 Post-commit Listener 执行的案例：当时已经意识到不能在事务提交前删除外部对象，却漏掉提交后进程崩溃会让清理意图永久丢失。回答先讲当时约束和错误假设，再讲如何通过审查或故障窗口测试发现，随后说明把清理意图持久化为可 Claim、Retry、DLQ 和对账的任务。最后承认新增状态表和运维成本，以及还需通过更大数据量和更长任务时长验证清理窗口。

失败题不适合把结果包装成“最终非常成功”。面试官看的是是否承担责任、如何修正判断和怎样防止同类问题。若案例来自开发或代码审查，要明确不是线上事故；若问题主要由他人发现，也应如实说明自己的参与。三层追问会问为什么第一次没想到、监控为什么没发现、现在还可能从哪里失败，答案需要落到设计检查表、故障注入和状态对账。

STAR 的 Result 不只写“问题解决了”。可说新增 Cleanup Task 状态机、幂等键、Lease、Attempt、DLQ 与对账，并补充提交后进程退出的故障测试。反思部分说明第一次设计只覆盖事务回滚，没有把进程崩溃当成独立失败窗口。若面试官追问优先级，可以解释在线不可见先于物理清理，先阻止继续读取，再异步完成外部删除。数据量或对象大小增长后，清理时延需要重新测量。

回答前把真实时间、影响范围、自己当时的角色和谁发现问题填入事实卡。若没有量化用户影响，可以报告受影响的测试场景或状态数量，不换算为生产事故。失败题最终要让面试官听到判断方式发生了什么变化，例如之后所有跨系统操作都按 I/O 前后枚举崩溃窗口，并把清理意图是否持久化纳入设计评审。

### 11.2 你和同事意见不一致怎么办

不要只说“充分沟通”。先复述双方目标和约束，再把争议转为可验证的问题。比如对方希望直接使用自由 ReAct Agent 以提高灵活性，你担心长任务不可恢复和工具越权。可以共同定义样例集、成功率、Token 成本、恢复场景和 Capability 边界，做最小实验比较自由执行与编译后 ExecutionSpec。若数据仍不充分，由明确的决策 Owner 按当前风险做选择，并记录回看时间。

面试官会追问“最后听谁的”“你是否反对过正确方案”。回答应说明决策机制，不要塑造自己永远正确。一个成熟案例应包含自己被说服或折中调整的部分，例如保留受控动态 Repair，而不是完全静态工作流。项目没有真实团队争议证据时，不能虚构同事和会议，可以把这段作为回答方法，并在事实卡中替换为本人经历。

三分钟回答可以按五段组织：共同目标、分歧假设、验证指标、决策过程、回看结果。争论自由 Agent 与编译工作流时，指标可选任务完成率、恢复一致性、越权率、Token 成本和未知工具处理。实验不必证明一方全面优胜，也可能得到分层方案：稳定主路径由 ExecutionSpec 驱动，局部失败允许有界 Repair。若最终采用对方方案，应说明自己学到什么和之后如何支持执行，避免把“被说服”描述成失去影响力。

补充真实细节时，要交代分歧发生在哪个决策点、各自依据什么数据、决策由谁承担以及多久后回看。若时间不足无法实验，可采用可逆方案、Feature Flag 和明确回看日期。面试官关注的是你如何在信息不全时推进，而不是是否能用一次会议让所有人同意。

复盘时还要说明决策结果是否按约定回看，以及自己是否主动修正立场。

### 11.3 如何推动一个跨团队项目

跨团队推动先统一交付 Contract 和完成定义。对于 Java Host 与 Python Worker，可把任务协议、幂等键、错误分类、版本、回调认证和超时写成契约，用 Fixture 和 Contract Test 让两侧独立验证。里程碑按可验收能力切分，例如能提交并查询、能处理重复回调、能在崩溃后恢复，而不是按“后端完成百分比”汇报。风险清单需要 Owner、截止时间、升级路径和降级方案。

行为面试会继续问某一方延期怎么办。回答可以是先判断是否阻断关键路径，是否能用 Mock、旧版本协议或关闭功能降低耦合；对外明确新范围与风险，不在最后一天才暴露。当前 NoteWeave 是代码事实材料，真实团队规模和推动经历仍需本人填写。没有跨团队经验时，可以讲跨语言模块协作的工程方法，但不能把工具进程拟人成真实团队。

推动过程需要可见的风险台账。比如协议版本未定、回调认证缺失、Windows 编码差异和 Worker Drain 都应有 Owner 与验收证据。每周状态不汇报“完成 80%”，而报告哪些 Contract 已通过、哪些失败窗口仍未覆盖以及谁被阻塞。发生延期时先保住最小闭环，允许提交、执行、回调和恢复，再把次要能力放到后续版本。面试官问如何影响没有汇报关系的人时，重点是共同目标、清晰接口、低成本验证和及时升级风险。

跨团队题还会问如何处理接口变更。可回答先维护版本化 Schema 和兼容窗口，让两边用固定 Fixture 做 Consumer-driven Contract Test；破坏性变更先升级接收方，再切发送方，最后删除旧格式。真实案例中需要替换团队名称、节奏和结果，不能用 Java/Python 模块关系冒充组织协作。

### 11.4 为什么离职、为什么选择我们、未来规划

这些问题必须基于本人事实，文档不能代写具体公司和经历。回答结构可以保持一致：离开原因聚焦希望解决的问题与成长方向，不泄露前公司机密，也不把责任全部推给他人；选择公司要结合真实业务、岗位职责和自己的能力证据；未来规划说明想深化的能力以及如何为岗位创造结果，避免只报职位名称。

技术候选人可以把 NoteWeave 作为能力证据：做过长任务、RAG、事件驱动和一致性设计，因此希望继续负责复杂后端或 Agent 平台，但需要根据目标岗位删减。面试官会检查动机是否和岗位匹配、是否稳定、是否理解业务。任何薪资、公司、时间和个人原因都由本人确认，不能从仓库推断。

“为什么我们”至少要连接三个事实：公司的真实业务阶段、岗位要解决的问题、自己的可验证能力。不能只复述招聘页面，也不能把所有公司都回答成“技术氛围好”。未来规划可以分一年和三年，一年内补齐业务理解并交付某类结果，三年内在复杂系统、Agent 平台或技术 Ownership 上承担更完整责任。若被追问管理还是技术，应表达当前选择及依据，同时保留根据团队需求演进的空间。

离职原因保持正向且具体，例如希望从功能交付走向复杂系统 Ownership，但必须与本人事实一致。涉及组织、薪资或冲突时可以诚实说明，不泄露机密，不贬低前同事。回答长度由真实经历支撑，文档只能提供结构，不能替换事实槽位。

常见连续追问包括“为什么现在离开”“如果新岗位也有相同问题怎么办”“你还面哪些方向”。回答要保持前后一致，并说明自己做过哪些内部改善尝试，避免让离职看起来是遇到困难就退出。未来规划应能被岗位工作验证，例如一年内独立负责可靠任务链路，而不是抽象地说成为架构师。

## 12. 现场系统设计常见八股追问

### 12.1 如何估算 QPS、存储和带宽

先声明假设。若系统有 10 万 DAU，每人每天 20 次读取，则日请求 200 万，平均 QPS 约 `2,000,000 / 86,400 = 23`。若峰均比取 10，峰值约 230 QPS。这个数字只用于起步，还要拆读写、突发、后台任务和重试。存储按每日新增对象数乘平均大小，再乘保留天数、副本、索引和元数据放大；带宽按请求大小乘峰值速率，并区分入口、内部复制和出口。

Agent 系统还要估算 Token 和在途任务。每分钟到达 20 个任务、平均执行 3 分钟，按 Little 定律平均在途约 60 个；Provider RPM、TPM 与并发三种配额分别约束请求到达、Token 速率和同时执行数。面试数字可以是假设，但单位、公式和峰值系数必须公开。不能拿 Hikari 20 连接或 Worker 并发 1 直接反推生产容量。

继续估算存储时，把原文件、解析文本、Embedding、倒排索引、副本、Snapshot 历史和日志分别计算。若每天新增 10 万份 1 MB 文件，只算原文就是约 100 GB/天，再乘保留期和副本；索引放大要用样本测量，不能拍脑袋固定三倍。带宽还包括用户上传、Worker 拉取、Kafka 事件和跨可用区复制。最后用瓶颈表说明数据库连接、Kafka Partition、Embedding TPM、ES 写入与对象存储带宽分别如何压测和扩展。

估算后要做合理性校验。峰值 QPS 是否与 DAU 和使用时段一致，Token 预算是否超过 Provider TPM，三年存储是否包含删除与归档，跨区带宽是否形成主要成本。给出低、中、高三档假设比单点数字更稳，并说明容量达到 60% 到 70% 时如何触发扩容或限流。这里的百分比是设计示例，不是当前生产阈值。

### 12.2 一致性和可用性怎么选

不要用一句“采用最终一致”结束。先按数据分类：权限撤销、Refresh Token Rotation、幂等 Receipt 和任务终态需要强条件更新或读主；ES 检索投影、缓存和统计允许最终一致，但必须带版本、过期与对账；用户上传成功到可检索存在状态窗口，应通过 PROCESSING/READY 显式表达。网络分区时，具体操作可以选择拒绝写入、受限降级或返回旧数据，不存在整套系统统一选择 CP 或 AP 的简单答案。

面试官可能追问 CAP、BASE 和 PACELC。CAP 讨论发生网络分区时一致性与可用性的取舍，PACELC 进一步提醒没有分区时也有延迟与一致性的权衡。回答要回到某个读写操作、复制协议和失败语义。NoteWeave 的 MySQL 本地事务与外部投影最终一致是分层选择，不代表数据库本身没有强一致语义。

可以用上传链路完整回答：对象与 MySQL 状态提交后返回 PROCESSING，Outbox 失败会重试，Kafka 重复由 Consumer 幂等吸收，ES 只接受不旧于当前 Snapshot 的版本。撤权发生时，在线查询先 Fail Closed，缓存版本失效，旧 ES 命中还要回 MySQL 验证 Ownership。分区期间检索可降级或返回旧投影，但授权无法确认时不放行。恢复后通过状态表、最老任务年龄和版本对账证明收敛。

若面试官要求更强的一致性，可以比较同步写 ES、数据库与检索同库、分布式事务或读时校验。同步外部写会拉长事务并降低可用性，ES 不适合作为权限真源，2PC 也未必被所有参与者支持。当前选择用状态可见性和版本收敛换取可恢复性，用户会承担短暂不可检索窗口，这个代价需要产品状态明确表达。

### 12.3 如何设计限流、熔断、降级和重试

限流控制进入系统的速率或并发，可用固定窗口、滑动窗口、漏桶、令牌桶和并发信号量。令牌桶允许一定突发，漏桶输出更平滑，并发租约限制在途工作量，三者解决的问题不同。熔断在依赖持续失败时快速拒绝，避免每个请求都等待超时；降级提供更便宜或功能较少的路径；重试只适用于可恢复且幂等的失败，并受次数、退避、Jitter 和总 Deadline 限制。

NoteWeave 用 Redis 令牌桶限制 Workspace、Actor、Workload 到达速率，用并发租约限制 Workspace、Workload 在途任务。Provider 不健康时先按能力契约处理：已有合法候选且能力边界相同才切换，具备持久等待契约才进入 Waiting，否则按当前路径做有界重试或失败。RAG 可在 Rerank 不可用时退化为融合召回，但 Query Embedding 不可用时生产 QA Hybrid 当前明确失败；安全校验和 Ownership 不能降级为放行。继续追问要说明 Redis 故障策略、Retry Storm、半开探测、预算传播和降级质量指标。

四种机制的顺序通常是入口限流、依赖调用前隔离与熔断、失败后按分类重试、能力不足时降级。熔断窗口太短会因偶发错误频繁开关，太长会延迟恢复；半开状态只放少量探测。重试预算要在调用链传播，避免网关、Host 和 Worker 各重试三次形成二十七次请求。验证要注入 429、超时、连接拒绝和慢响应，检查用户错误、下游调用次数、Waiting Age 与恢复速率。

容量恢复时还要防止惊群。依赖刚恢复，如果所有 Waiting Task 同时重试，会再次击穿，可按租户公平排队并用指数退避与 Jitter 逐步放量。熔断指标要按 Provider 和错误类型切分，认证失败不能靠熔断后重试解决。降级结果必须有标识并单独统计质量，不能把少证据回答当作完整成功。

### 12.4 如何设计幂等

幂等表示同一个业务操作执行多次，最终效果与执行一次一致。接口可以接受由客户端生成的 Idempotency Key，并与 Actor、Workspace、Operation Scope 组成唯一约束；服务保存请求摘要、状态和结果。相同 Key 与相同 Payload 返回原结果，相同 Key 与不同 Payload 返回冲突。消息消费可用业务唯一键、Inbox 表、状态机条件更新或版本号去重。只在 Redis `SETNX` 一个短 TTL Key，过期后仍可能重复，也无法原子绑定数据库结果。

NoteWeave 的 Callback、Outbox Consumer、Cleanup Task 和受控 Writeback 都需要不同层次的幂等。Provider 已完成但响应丢失时，重试可能产生第二次外部副作用，因此还要使用 Provider 支持的请求键、查询原 Receipt 或由 Host 统一提交。幂等记录保存多久取决于业务重放窗口和成本；永久保存会膨胀，过早清理会重新开放重复窗口。

接口幂等还要定义并发等待语义。第一个请求仍在 PROCESSING 时，第二个相同请求可以返回 202 与状态地址，或短暂等待原结果，不能同时执行。失败记录是否允许重试要区分永久输入错误与临时依赖错误。消息幂等可通过唯一 Inbox、业务状态条件和版本门禁组合，Redis 锁只能减少并发，不能替代最终数据库约束。

测试同时发送几十个相同 Key 请求，覆盖相同与不同 Payload、处理进程在提交前后崩溃、Receipt 返回丢失和幂等记录过期。指标记录 Duplicate、Conflict、In-progress、Replay 与外部副作用次数，证明“重复请求没有重复结果”而不是只证明接口都返回 200。

## 13. 如何把八股自然放进项目回答

现场回答不要把 HashMap、MVCC、Kafka 和 CAP 连续背一遍。先讲业务对象与失败窗口，面试官问到底层时再下钻。例如讲 Outbox 时可进入 MySQL 两阶段日志提交、行锁、联合索引、Kafka 至少一次和消费幂等；讲 SSE 时可进入 TCP、HTTP 长连接、线程池、背压与 Redis Stream；讲 Agent Lease 时可进入 CAS、Fencing、GC Pause 和分布式锁；讲 RAG 时可进入倒排索引、TopK、缓存和一致性投影。

每次下钻后都要回到设计选择。标准结构是“概念是什么，底层怎样工作，项目哪里使用，失败时怎样表现，替代方案有什么代价，如何验证”。八股的价值是解释项目机制，不是用术语覆盖事实缺口。个人职责、生产数据和真实事故仍以事实卡为准。

## 14. 系统设计估算如何使用项目真实参数

设计题可以把当前配置作为起算样例，但必须先说它不是压测结论。单 Backend Hikari 上限 20；Answer I/O 为 `4/16/64`；SSE Connection 为 `4/32/0`；Quota Rate Capacity 20、每分钟补 20、单 Workspace/Workload 并发 4；Research Agent 默认执行并发 1、Fetch 并发 4；Outbox Batch 50、Tick 1 秒；Embedding Batch 32；Rerank Batch 80。

例如估算 Agent 在途时，业务到达率为每分钟 20、平均执行 3 分钟，Little 定律得到 60 个在途任务，但当前单 Research Worker 执行并发 1、Quota 单 Workspace 并发 4，显然需要排队、更多 Worker 或更小到达率。能否横向扩 Worker 还受 Kafka Partition、Provider TPM、数据库连接和任务 Claim 竞争约束。

估算 SSE 时，当前 Connection Max 32、进程内 Replay 512、Subscriber Queue 64、Redis Stream Max Length 512/TTL 600 秒、Follow Timeout 125 秒。它只能说明默认有界策略，不能声称支持 32 个生产长连接。压测必须覆盖连接保持、事件速率、慢消费者、断线重连和 Redis Bridge 故障。

估算存储时，单文件上限 128 MB、Chunk Size 900/Overlap 120、Embedding 1024 维只是最坏输入和当前模型参数。真实容量要使用文件大小分布、文本提取比例、Chunk 数、索引放大、副本和保留期。完整配置表见[项目真实配置参数与容量口径](15-项目真实配置参数与容量口径.md)。

## 项目现场题的事实锚点

现场设计可以从已有边界展开：Workspace ACL 是租户边界，MySQL 是业务真源，outbox/receipt 负责至少一次投递，SSE 用持久化事件恢复，Research/Artifact 用 lease/fencing 防止旧 worker 覆盖新状态，Memory 通过 review/revision 控制晋升。WorkloadQuota 的并发租约按 Workspace + Workload 隔离，Research Tool Permit 另按 Provider、Workspace、Run + Role 限流。题目若把并发、数据量、任务时长或协作范围提高到新的量级，再根据新增约束设计扩展，并明确哪些是当前能力、哪些是题设新增条件。

| 根因 | 不是“权重没调好”，而是把可权衡 SLO 与不可妥协的不变量放进同一目标函数。Scope Filter 还是 Candidate 生成后的附加指标，没有成为发布前置条件。 |

| 参数 | 当前固定 Policy：Macro Recall/MRR/nDCG 与兼容字段 Citation Precision/Coverage 至少 0.9，兼容字段 Refusal Accuracy 为 1，质量 Delta 至少 -0.05，Overlap 至少 0.75，Top1 Changed Ratio 至多 0.25，Scope Violation 为 0，P95 至多 1000 微秒。对外讲解将 Coverage 称为 Citation Completeness，将 Refusal Accuracy 称为 Refusal Recall；目标门禁再补 Refusal Precision、Answer Coverage 和 Selective Accuracy。 |

| 复盘 | 以后新增性能优化时，先写它不能破坏的业务不变量，再写优化目标。发生安全 Bad Case 后，将去敏样本固化到 Safety Regression，而不是只修当前代码。 |

### 16.2 故事 B：消融没有 Lift，是否应该删除 Rerank

> 类型：`[已测-模拟]` 数据判断故事。适合回答“做错的技术决策”“如何用数据做取舍”。

| 叙事节点 | 母稿内容 |
|---|---|
| 背景 | Rerank 增加 Provider 调用、延迟、成本和失败路径。若它没有质量收益，删除它是合理的复杂度收敛候选。 |
| 初版判断 | QA 消融中 Hybrid RRF、Hybrid RRF + Rerank、Full Pipeline 都是 1.0，于是形成“Rerank Lift 为 0，可以直接删除”的初步结论。 |
| 异常 | `[已测-模拟]` 数据集只有 3 个 QA Case。Keyword Only 为 0.3333，Vector Only 为 0.6667，Hybrid RRF 已达到 1.0，后续阶段没有剩余错误可供 Rerank 改善，指标出现天花板效应。 |
| 错误判断 | 把“当前样本没有观察到收益”说成“该机制没有收益”。这忽略了样本量、Query 难度、排名位置、延迟分布和降级路径。 |

| 根因 | 评测集只适合 Smoke/Contract，不适合识别 Rerank 的边际贡献。Gold 构造集中在“能否召回”，没有构造“都召回了但顺序错误”的 Case。 |
| 取舍 | 暂不依据这 3 Case 删除 Rerank，也不默认保留。先建立 Hard Query Set，记录 Rerank Lift、Top1 Changed、MRR/nDCG Delta、P95、成本和超时降级，再按切片选择 Always On、条件触发或关闭。 |

| 复盘 | 消融实验不是组件投票。每个阶段都要有能触发其设计价值的 Case，并提前写清“什么证据会让我删除、保留或条件启用它”。 |

这个故事的高分点不是维护 Rerank，而是承认当前证据不足以支持删除或保留。面试官继续问成本时，回答需要测 Provider 账单、Batch 利用率、Timeout 和 P95/P99；当前仓库参数只能作为实验设置，不能替代结果。

### 16.3 故事 C：评测可复现与隐私保护发生冲突

> 类型：`[已测-模拟]` 安全与可审计故事。适合回答“如何处理敏感数据”“怎样让结果可复现”。

| 叙事节点 | 母稿内容 |
|---|---|
| 背景 | Retrieval Snapshot 若原样保存 Query、路径、正文、Source/Citation ID，最容易复盘 Bad Case，却也会把租户内容复制进评测产物和 CI 留存。 |
| 初版判断 | 为保证可复现，直接归档完整输入和排名结果。这个做法调试方便，但扩大了敏感数据的副本、访问面和删除传播范围。 |
| 异常 | 评测产物需要长期比较 Ranking 是否稳定，同时又不能让 Receipt 变成内容仓库。只删 Query 会破坏同一身份的配对比较，只做普通 Hash 又可能被字典反查。 |
| 错误判断 | 把“可复现”等同于“必须保留原文”，或反过来只保留一个总分。前者带来隐私风险，后者无法证明输入 Artifact 是否相同、排名是否变化。 |
| 证据 | `[已测-模拟]` Sanitizer Fixture 覆盖 4 条 Path、16 个值：同 Salt 得到稳定身份，不同 Salt 得到不同身份；脱敏后 Recall 1.0、兼容字段 Citation Coverage 1.0、Scope Violation 0。该 Coverage 只证明 Citation Completeness 未下降，不证明 Citation Accuracy 或 Claim-Evidence Coverage 为 1.0。Receipt 测试共验证聚合证据结构和排名签名。 |
| 根因 | 内容调试证据、比较身份和发布证明混在一个 Artifact 中，没有按最小披露原则分层。 |
| 取舍 | 原始 Snapshot 放入受控、短保留期的评测环境；导出的 Dataset 使用版本化稳定脱敏；长期 Receipt 只保留 Byte Size、SHA-256、安全版本、Policy Profile、聚合质量/延迟和 Ranking Signature。 |
| 参数 | Receipt Schema 为 `retrieval-evaluation-evidence-receipt-v1`，明确不保存路径、Query、正文和 Case/Evidence/Source/Citation ID。Salt 必须按环境受控和轮换，不能提交到仓库或日志。 |
| 灰度 | 先对副本运行脱敏，比较脱敏前后 Case Count、排名和聚合指标；不一致立即停止导出。生产接入前还要补访问审计、保留期、撤销传播和密钥管理验证。 |

| 副作用 | 脱敏后定位正文问题更慢；Salt 丢失会失去跨 Run 身份关联，泄露则增加枚举风险；聚合 Receipt 无法回答单 Case 为什么失败。因此原始证据和长期 Receipt 需要不同权限与保留策略。 |
| 复盘 | 评测系统也属于资料生命周期的一部分。设计新指标时同步回答采集什么、谁能看、保留多久、如何撤销以及最少需要证明什么。 |

本人若没有处理真实敏感数据的经历，可以把 Result 说成“完成了固定 Fixture 下的脱敏与 Receipt 契约验证”，不能说“通过了合规审计”或“避免了某次生产泄露”。

## 17. 行为题与现场设计题的 4 到 5 分钟完整回答

行为题和系统设计题虽然形式不同，但都要讲清“问题为什么出现、做了什么选择、承担什么代价、如何证明结果”。行为题不能用源码替代个人经历，应该从真实的冲突、限制或失败开始，说明自己负责的范围、协作对象、具体动作和结果，再补一个没有解决的边界。系统设计题则先确认用户、规模、延迟、正确性和合规要求，再画出 Workspace、业务真源、异步任务、检索或交付链路，最后才选数据库和中间件。两类题都不能只说“我用了 Kafka”或“我很有责任心”。

现场设计多租户 RAG 时，可以沿资料生命周期回答：上传对象与 MySQL 元数据分开，Source Snapshot 固定内容，解析和投影异步化，ES 查询前置 Workspace Scope，MySQL 再做 Ownership Hydration，Evidence Manifest 固化引用，SSE 按事件游标恢复。面试官追问缓存、旧 Projection 晚到和删除后的索引清理时，分别回答 Cache Key 带 Scope 和 Version、条件更新与版本门禁、持久 Cleanup Task 与回放脱敏；若题目提高并发或数据规模，再补充分片、复制和恢复策略。

设计长任务 Agent 时，先把用户请求变成 Job、Run、Task 和 Input Snapshot，Java 控制面负责权限、状态和幂等，Worker 执行 Skill Graph，Lease、Heartbeat、Fencing 防止旧 Owner，Checkpoint 和 Waiting 支持恢复，Verifier 与 Repair 控制输出质量，写回必须回到 Host。面试官问为什么不让模型直接调用任意工具，可以说明 Capability Intersection、内部 Token、Schema 校验和副作用审批；如果等待、补偿和人工批准复杂到一定程度，再评估是否需要额外编排层，当前领域状态仍由 MySQL 和 Worker 契约承载。

行为题的技术细节也要有证据等级。可以复述仓库中 Outbox 卡住、对象清理不收敛或跨平台编码失败等真实缺陷，但时间、影响用户数、修复耗时和团队冲突必须来自本人记录；没有这些信息，就把内容标成个人项目中的设计复盘。结果没有线上指标时，使用“测试证明重复回调不会产生第二个版本”“故障注入证明旧 Lease 无法写回”，不要说“稳定性提升了百分之多少”。这种回答节奏能同时展示工程判断、沟通边界和技术深度，也避免为了迎合 STAR 模板虚构故事。

## 18. 学校场景的现场系统设计补充

### 18.1 设计课程资料知识服务

**需求澄清**，用户分课程管理员、教师或助教、学生。教师上传和更新课件，学生只能访问已加入课程的资料并做带引用问答；资料撤回后必须立即停止在线读取，物理派生允许在明确 Deadline 内清理。需要确认课程数量、成员数、文件类型、考试周峰值、是否包含试卷或未公开答案、回答延迟和学校数据保留要求。

**领域映射**，当前 `Workspace` 可以承载课程边界，`Source` 和不可变 `Snapshot` 表示一份课程资料及版本，`QA/Note/Wiki` 分别承载问答、围绕指定资料深读和稳定知识页。教师可映射 `EDITOR`，课程管理员映射 `OWNER`。当前 `VIEWER` 只有读取权限，学生若需要提问，应新增 `LEARNER`，只授予 `WORKSPACE_READ` 和 `ANSWER_RUN`；不能为了省一个角色直接给所有学生资料写权限。

**写链路**，上传先校验成员与 `SOURCE_WRITE`，对象进入 MinIO，MySQL 事务提交 Upload、Source、Snapshot 和 Outbox。解析和投影异步执行，Consumer 按 Snapshot Version 幂等，Projection Ready 后才进入可检索集合。教师更新资料时创建新 Snapshot，不原地覆盖旧内容；查询只读取当前可见版本，历史 AnswerRun 通过 Evidence Manifest 记录当时引用身份。

**读链路**，学生提问先校验 `LEARNER` 的 Answer 权限，冻结 Workspace、资料范围和策略版本；ES 按 Workspace Scope 召回，命中后回 MySQL 批量做 Ownership Hydration，再选择 Evidence、生成回答并持久化事件。SSE 断开后按 Cursor 回放，不能重新启动一次模型生成。

**正确性与安全**，MySQL 是权限和业务状态真源，ES 与缓存只能做候选。撤权时提高 ACL Version，让旧缓存失效；删除先提交不可见状态，再用 Cleanup Task 清理 MinIO、ES、Wiki、Memory 编译结果和历史回放中的敏感正文。试卷、答案和个人数据应使用独立 Scope 与审计，默认拒绝跨课程检索。

**指标**，业务看课程激活、有效回答采纳和教师纠错；资料看 Projection Ready P95/P99 和删除收敛；QA 看 Recall、nDCG、Citation Support、拒答和 Scope Violation；容量看考试周 Queue Age、Hikari Pending、Kafka Lag、Provider 429、SSE Overflow 和单位成功成本。

### 18.2 考试周突发流量怎样扩展

考试周的流量模型不能只说“QPS 很高”。静态页面、资料列表和 QA 生成要分开估算。假设峰值有 30 个 HTTP 请求每秒，其中真正触发模型回答的是 2 个每秒，演练完成 P95 为 6.8 秒，Little 定律得到约 `2 x 6.8 = 13.6` 个回答在途。当前 Answer I/O 最大线程 16、Hikari 最大连接 20，只能作为保护参数；检索、模型和数据库共享资源后仍需混合压测。

第一步做入口隔离。资料读取、QA、Research 和 Artifact 使用不同 Workload 配额，考试周优先保证课程 QA，限制长 Research 和批量回填。第二步让应用实例横向扩展，但 SSE 事件与任务状态必须持久化，Redis Bridge 只传输实时事件，断线结果从 MySQL 回源。第三步检查 Kafka Partition、ES 查询、数据库连接和 Provider TPM 的最小瓶颈，Consumer 数不能超过有效 Partition 并行度。

当前单实例 SSE Connection 最大线程为 32。若峰值需要 100 条同时流式连接，不能声称调大一个配置即可解决，应压测线程、Redis Stream、Subscriber Queue 和慢客户端，再决定多实例分担或改用更适合大量连接的事件交付模型。过载时返回明确限流或排队状态，不能让线程池和连接池无限等待。

### 18.3 教师更新资料后，旧回答怎样处理

教师正常更新课件时创建新 Source Snapshot，旧 Snapshot 保留历史身份但退出当前检索范围。新的解析和投影达到 READY 后，通过版本门禁切换可见版本；旧 Projection 晚到不能覆盖新状态。正在执行的 AnswerRun 或 Research Run 继续使用提交时冻结的 Input Snapshot，保证回放一致，不能执行一半切到新课件。隐私删除、成员撤权和安全封禁不属于普通更新，它们推进输入有效性 Epoch，在途 Run 必须停止新的外部调用并在最终提交前取消或转入 `INPUT_REVOKED`。

已经生成的历史回答不应悄悄改写。Evidence Manifest 保存当时的 Snapshot 和 Citation，界面可以标记“引用资料已有新版本”，由用户重新运行得到新回答。若旧资料因错误或合规原因撤回，历史回放只保留允许的 Tombstone、Hash 和版本身份，正文和引用预览按删除策略降级。

这个设计体现了两种正确性：新查询看到当前课程事实，历史运行能够解释当时为什么得到那个结果。直接让所有历史回答跟随 Latest Pointer 会破坏可审计性。

### 18.4 学期结束后的归档与删除

课程结课后先区分归档、成员撤权和物理删除。归档课程可以变成只读，保留 Source Snapshot、Wiki Version 和历史回答；学生离课后撤销成员关系并提高 ACL Version。达到学校保留期后再提交删除事实，在线读取立即 Fail Closed，Cleanup Task 异步清理对象、索引、缓存和派生结果。

RTO 和 RPO 要按数据层分开。MySQL 保存课程、成员、资料状态和任务账本，需要备份与恢复演练；MinIO 保存原文件，需要版本或备份策略；ES、缓存和编译结果可以从真源重建，恢复目标主要是重建吞吐和可检索时间。Kafka 保留时间不能替代业务备份，DLQ 也不能替代资料归档。

## 19. 围绕学校背景的连续追问

| 面试官追问 | 回答主线 | 项目知识点 |
|---|---|---|
| 为什么用 Workspace，不直接建 Course 表？ | Workspace 是当前通用隔离边界，课程只是一个业务类型；若需要学期、院系、选课同步和课程复制，再增加 Course 聚合并引用 Workspace | 领域建模、通用边界与业务特化 |
| 学生为什么不能直接用 VIEWER？ | 当前 VIEWER 只有读权限，问答会产生 Provider 成本和新业务状态，应增加 LEARNER 或独立授予 ANSWER_RUN | RBAC、最小权限、成本权限 |
| 教师上传成功后学生为什么还搜不到？ | Accepted 只表示对象和业务意图持久化，Projection Ready 才表示可检索；前端展示状态并允许失败重试 | 最终一致、异步 UX、状态机 |
| 同一个问题很多学生重复问怎么办？ | 可以缓存检索计划或经版本化的安全结果，但 Key 必须包含 Workspace、ACL/Source Version、策略和模型；个性化 Context 不能误共享 | 缓存键、版本、租户隔离 |
| 如何避免模型泄露其他课程内容？ | ES 前置 Scope，MySQL Ownership 二次校验，Evidence Manifest 再固化；权限服务异常时 Fail Closed | 多租户安全、纵深防御 |
| 为什么不能保证 Exactly-once？ | MySQL、Kafka、MinIO、ES 和 Provider 没有统一事务，采用至少一次、幂等、Fencing、Receipt 和对账保证业务效果 | 分布式事务、未知结果 |
| 课程资料突然更新，正在生成的回答怎么办？ | Run 使用冻结 Snapshot 完成，后续新 Run 使用新版本，历史回答提示资料已更新 | Snapshot Isolation、可重放 |
| 如何判断 RAG 真的有用？ | 固定课程 Gold，对比 BM25、Hybrid、Rerank 的 Recall/nDCG、Citation Support、拒答、延迟和成本，再接用户采纳 | 离线评测、在线价值、消融 |
| 学校规模不大，为什么需要 Kafka？ | MVP 可以 Polling Outbox 直接驱动 Worker；多 Consumer、保留重放和独立积压出现后再启用 Kafka | 演进式架构、过度设计判断 |
| 如果只保留三项功能？ | Workspace/ACL、资料异步接入、带引用 QA；Note/Wiki 后置，Research/Artifact/Memory 关闭 | MVP、风险优先级、产品判断 |

学校背景的价值是给架构约束一个真实来源，不是把所有功能都解释成学校刚需。回答时先说课程资料、权限、引用和考试周负载，再进入 Outbox、RAG、Lease 或 SSE；Deep Research、Artifact 和 Memory 属于后续扩展时，要主动说明它们解决的新增场景和复杂度。
