# 大厂常见基础八股与项目映射

## 1. 阅读方法

这篇补齐跨模块的基础题。每道题按三分钟主回答准备：先说明概念解决什么问题，再讲核心机制，然后落到 NoteWeave 的对象、失败窗口和 Trade-off，最后留下可以继续下钻的入口。面试官只问定义时，用前两三句回答；连续追问时，再展开实现、替代方案和验证方法。

基础八股不能替代项目事实。文中提到的复制、发布和容量治理方案，只有在数据量、并发或运行约束达到相应量级时才需要展开。当前系统的源码事实、测试证据和运行边界仍以项目事实卡、详细设计和指标手册为准。

## 2. 操作系统：进程、线程与上下文切换

进程是资源分配和隔离的基本单位，拥有独立虚拟地址空间、文件描述符和安全上下文；同一进程内的线程共享堆、代码和打开的文件，每个线程有自己的栈、寄存器和程序计数器。线程间共享数据成本低，但一个线程破坏内存可能影响整个进程。进程隔离更强，通信需要管道、Socket、共享内存或其他 IPC，并承担序列化和调度成本。

上下文切换时，系统保存当前任务寄存器和调度状态，恢复另一个任务，还会影响 CPU Cache 与 TLB。线程数量远大于可运行核心、频繁锁竞争或大量短任务，会增加调度开销。I/O 阻塞线程并不持续占 CPU，但会占用线程栈、调度实体和应用线程池名额。判断线程是否过多要看 Runnable 数、阻塞点、切换速率、CPU 利用率和吞吐，不能只看一个固定阈值。

NoteWeave 的 Java Host 与 Python Worker 使用进程边界，适合隔离语言依赖和崩溃故障，但需要版本化协议、认证、超时和跨进程 Trace。Java 进程内部又把 Answer I/O、SSE Dispatch、Connection 和 Redis Bridge 分开，防止一种阻塞占满所有线程。面试官追问“进程还是线程”时，应从隔离、共享状态、故障域、通信量和部署方式选择，而不是把进程一定说成更安全或线程一定说成更快。

线程与协程也常被比较。协程或虚拟线程能降低大量阻塞任务的调度和栈成本，但不会增加 CPU 核心，也不会解除数据库连接、Provider 并发和内存限制。验证方案应包含吞吐、P99、上下文切换、线程数和依赖饱和度。若共享可变状态设计错误，换成更轻量的执行单元只会让竞态更容易出现。

## 3. 操作系统：虚拟内存、页缓存与缺页

每个进程看到连续虚拟地址空间，操作系统通过页表把虚拟页映射到物理页。虚拟内存提供隔离、按需分配和共享映射。访问尚未映射的页会产生缺页异常，若数据已在内存只是补页表，称为 Minor Fault；若需要从磁盘读取，Major Fault 延迟高得多。TLB 缓存近期页表映射，随机访问大工作集可能造成 TLB 和 CPU Cache Miss。

文件 I/O 通常经过 Page Cache。应用读取文件后，即便 Java Heap 不大，操作系统也可能用空闲内存缓存文件页，因此“机器内存已用很多”不一定是泄漏。反过来，容器内存上限可能同时计算 Heap、Direct Buffer、线程栈和部分文件缓存，`-Xmx` 接近 Limit 会给 Native 区域留下不足。`mmap` 把文件映射进地址空间，减少显式拷贝但仍受地址空间、页缓存和刷新语义约束。

NoteWeave 处理上传文件、MinIO 流和模型响应时，应优先流式处理并限制单批大小，避免一次把整个对象读进 Heap。测试中出现的 G1 Native `mmap` 失败说明 JVM、Fork、容器依赖与系统内存共同决定可运行容量。排查内存问题要同时看 Heap Dump、Native Memory、RSS、Page Fault 和容器事件，不能只依据 GC 指标。

面试官还会问 Swap。Swap 能缓解物理内存瞬时不足，却可能让需要低延迟的 Java 进程出现严重抖动，容器环境也常有不同限制。零拷贝则是减少用户态与内核态之间的数据复制和上下文切换，`sendfile` 适合文件到 Socket 的传输，但加密、内容变换和应用层解析可能打断路径。是否优化要用 CPU、带宽和延迟证据判断。

## 4. 操作系统：阻塞 I/O、非阻塞 I/O 与 I/O 多路复用

阻塞 I/O 在数据未准备好时挂起调用线程，编程模型简单，但大量连接通常需要大量线程。非阻塞 I/O 立即返回是否就绪，应用若不断轮询会浪费 CPU。I/O 多路复用通过 `select`、`poll`、`epoll` 或 `kqueue` 等机制，让一个线程等待多个文件描述符的就绪事件，再处理真正可读写的连接。它减少等待线程数量，不会让业务处理、序列化或数据库查询自动变快。

Level-triggered 模式只要描述符仍就绪就会继续通知，较容易编程；Edge-triggered 只在状态变化时通知，处理时通常要一直读到 EAGAIN，否则可能漏掉后续数据。Reactor 把事件分发给 Handler，Proactor 强调异步操作完成通知。Java NIO、Netty 和响应式框架在这些模型上提供抽象，但业务代码若调用阻塞数据库或模型 SDK，仍需隔离到合适的执行器。

NoteWeave 的 SSE 是长连接，连接线程、事件 Dispatch 和后台生成任务是不同资源。连接数很高并不等于模型并发很高。Subscriber Queue 必须有界，慢客户端需要合并 Delta 或断开，不能让多路复用掩盖应用层背压。面试官问“为什么不用一个线程处理所有连接”时，要说明事件循环适合短小非阻塞处理，CPU 重任务和阻塞 I/O 仍需移出 Event Loop。

多路复用的验证重点是 Event Loop 是否被阻塞。可以观察单次 Handler 时间、待处理任务、连接数、写缓冲区水位和慢消费者。若在 Event Loop 中执行 JSON 大对象处理或同步数据库查询，其他连接会一起延迟。线程池卸载也要有界，否则问题只是从 Event Loop 转移到无界队列。

## 5. 网络：TCP 如何保证可靠传输

TCP 提供有序、可靠的字节流。发送方为字节编号，接收方通过 ACK 确认，丢包后按超时或重复 ACK 触发重传；校验和检测传输错误，接收窗口实现流量控制，拥塞窗口根据网络反馈调整发送速率。TCP 不保留应用消息边界，一次 `write` 可能被拆分，多次 `write` 也可能合并，应用协议需要长度字段、分隔符或固定结构解决粘包拆包。

三次握手让双方确认收发能力并交换初始序列号。四次挥手来自全双工方向分别关闭，主动关闭方进入 TIME_WAIT，用于让延迟报文过期并能重传最后 ACK。大量短连接会增加握手、TLS 和 TIME_WAIT 成本，连接池与 Keep-alive 可以复用连接，但池过大又会占文件描述符和下游连接。TCP Keepalive、HTTP Keep-alive 与应用心跳是不同层次。

可靠传输只保证字节到达对端协议栈，不保证对方业务事务提交。Provider 已执行但响应丢失时，客户端看到超时，重试可能产生重复副作用。NoteWeave 的 Callback 和 Writeback 需要幂等键、Receipt 或状态查询，不能用“TCP 可靠”推导业务 Exactly-once。继续追问可进入滑动窗口、拥塞控制、半连接队列、RST、Nagle 与 Head-of-line Blocking。

抓包排查时，重传不一定是服务端 Bug，也可能来自链路丢包、接收方处理不及时或抓包位置。应用 Read Timeout 也不等于 TCP 超时，它可能发生在连接仍健康但业务迟迟不返回。面试回答可用“连接建立、请求送达、业务提交、响应送达”四个边界枚举故障，说明每一层需要不同的超时、重试和幂等证据。

## 6. 网络：HTTP/1.1、HTTP/2、HTTP/3 与 HTTPS

HTTP/1.1 支持持久连接和请求流水线，但实践中一个连接上的前序响应会阻塞后续响应，浏览器通常建立多个连接。HTTP/2 把请求拆成带 StreamId 的二进制帧，在一个 TCP 连接上多路复用，并提供 Header Compression；单个流的应用阻塞减少了，但 TCP 丢包仍会让整个连接等待缺失字节。HTTP/3 基于 QUIC 与 UDP，把可靠性和拥塞控制放到用户态，每个 Stream 独立处理丢包，并能减少连接恢复成本，但部署、网络设备兼容和可观测性更复杂。

HTTPS 在 HTTP 下使用 TLS。握手协商协议与密码套件，服务端提供证书链，客户端验证受信 CA、有效期和 Hostname，再通过非对称算法协商密钥，后续数据主要使用高效对称加密。关闭证书验证会让加密失去身份保证。双向 TLS 还验证客户端证书，适合部分服务间身份场景，但证书签发、轮换和撤销需要治理。

NoteWeave 的 SSE 基于 HTTP 长连接，服务端发送事件，客户端断线后用 Cursor 恢复；它不同于双向 WebSocket。内部服务 Token 提供应用身份，不能替代 TLS 的传输与服务端身份验证。面试时比较 SSE、WebSocket 和轮询，应从通信方向、代理兼容、重连、事件顺序和资源占用出发。

HTTP 状态码也属于高频题。幂等读取使用 GET，创建可用 POST，完整替换偏向 PUT，部分更新用 PATCH，但最终仍由接口契约定义。429 表示限流并可携带重试提示，503 表示服务暂不可用，504 常来自网关等待上游超时。返回 200 再在 Body 中写失败，会破坏网关、监控和客户端重试语义。流式响应一旦发送 Header，后续错误只能通过事件协议表达。

## 7. 网络：DNS、负载均衡与超时预算

DNS 把域名解析为记录，递归解析结果会在本地、系统和中间 Resolver 按 TTL 缓存。TTL 短能更快切流量，却增加解析压力；TTL 长降低压力但故障切换更慢。DNS 成功不代表目标健康，客户端也可能长期缓存旧地址。SSRF 防护若只验证域名字符串，会被重定向、IPv6 表示、DNS Rebinding 或解析到内网地址绕过，连接时仍需校验最终地址与协议。

负载均衡可在四层按 IP/端口转发，也可在七层理解 HTTP Host、Path 和 Header。常见算法有轮询、加权、最少连接、一致性哈希。最少连接不等于最少负载，长连接和任务实际开销可能不同；一致性哈希减少节点变化时的 Key 迁移，但节点热点和虚拟节点数仍需治理。健康检查要区分进程存活与是否能接新流量。

超时至少包括 DNS、Connect、TLS、连接池获取、Read、Write、单次尝试和总 Deadline。外层 Deadline 必须覆盖内层全部尝试，取消信号应向下传播。NoteWeave 的 Provider 与 Worker 重试若各自不知道总预算，会形成叠乘。面试官追问“超时设多少”时，应基于用户 SLO、依赖 P99、重试次数和失败代价计算，再用线上分布调整，不能回答固定三秒适用于所有依赖。

负载均衡还要处理长连接和状态。SSE 建立后通常固定在一个实例，实例退出需要先摘流再 Drain，断开后依靠 Cursor 重连。服务端重试如果切换实例，幂等状态必须在共享真源中，不能只存在本机内存。验证超时预算时要故意注入 DNS 慢、连接拒绝、首字节慢和中途断流，确认错误分类与重试次数符合预期。

## 8. Redis：数据结构与典型使用场景

String 可保存文本、二进制、计数和位图，常用于缓存、计数器与令牌；Hash 适合小型对象字段；List 是双端链表语义，可做简单队列但缺少完善消费确认；Set 适合去重和集合运算；Sorted Set 通过分值排序，适合排行榜、延迟队列和时间窗口；Stream 提供带 ID 的追加日志、Consumer Group、Pending 与确认，适合有界事件流。HyperLogLog 用较小空间估算基数但有误差，Bitmap 适合稠密整数状态，Geo 基于有序集合提供地理查询。

选择结构要看访问命令、元素规模、原子性和过期方式。一个 Hash 的字段不能各自独立 TTL；大 List、Set 或 Hash 会形成 Big Key，删除和网络传输可能阻塞。Lua 能把多步读改写为服务器内原子执行，但脚本执行期间会阻塞主线程，应限制复杂度和 Key 数。Pipeline 减少网络往返，不提供事务隔离；MULTI/EXEC 保证命令批次顺序执行，但不提供关系数据库式回滚。

NoteWeave 用 Redis Lua 承载 Workspace、Actor、Workload 令牌桶和 Workspace、Workload 并发租约，并用于部分缓存与实时桥接。它与 MySQL Outbox Lease 的持久任务抢占不同。面试官问“Redis 为什么快”时，可讲内存访问、高效结构、事件循环和减少锁竞争，同时说明网络、慢命令、大 Key、持久化与复制仍会造成长尾。

过期策略也常被问。Redis 会结合惰性删除和定期采样删除，过期 Key 不保证在 TTL 到点时立即从内存清除。内存达到上限后按配置执行 Noeviction、LRU、LFU 或随机淘汰，选择范围可能是全部 Key 或带 TTL 的 Key。配额和锁等正确性状态不应与可随意淘汰的缓存混在同一策略中，至少要分实例、命名空间或容量保护。

## 9. Redis：持久化、复制、Sentinel 与 Cluster

RDB 在某个时间点生成快照，文件紧凑且恢复快，但两次快照之间的数据可能丢失，Fork 和 Copy-on-write 会增加内存与 I/O 压力。AOF 记录写命令，按策略刷盘，数据窗口更小但文件和重写成本更高。混合持久化可结合 RDB 基线与增量 AOF。任何策略都要结合磁盘故障、主从复制和恢复演练，Redis 开启持久化不等于业务数据绝对不丢。

主从复制通常异步，主库确认写入时从库可能尚未收到。Sentinel 负责监控、选主和通知客户端，故障切换期间可能有短暂不可用或丢失未复制写。Redis Cluster 将 16384 个 Slot 分布到多个主节点，客户端根据重定向访问；多 Key 原子操作通常要求 Key 位于同一 Slot，可通过 Hash Tag 控制，但热点租户也可能集中到一个分片。扩容迁移和故障切换需要客户端正确处理 MOVED、ASK 与拓扑更新。

NoteWeave 当前使用 Redis 保存配额、租约和实时窗口。若并发或连接规模增长，需要重新评估 Lua Key 的分布、租约语义、事件窗口和客户端重试；缓存允许丢失后回源，限流状态丢失可能短时放大流量，实时 Replay 丢失会影响断线体验，不同数据需要不同恢复目标。

复制读取还会产生陈旧。Replica 适合可接受旧值的只读查询，不适合刚撤权后的安全判断。面试官追问数据恢复时，应分别说明服务恢复时间、已确认写的数据窗口和业务降级，而不是只报一个节点数。

## 10. Redis：缓存穿透、击穿、雪崩与一致性

Cache-aside 的读流程是先查缓存，Miss 后读数据库并回填；写流程常见做法是先更新数据库再删除缓存。先删缓存再写数据库，会让并发读把旧值重新写回。即使先写库再删缓存，删除失败仍会产生陈旧，可通过重试任务、Outbox、版本化 Key 或短 TTL 收敛。双写数据库与缓存不能天然原子，追求强一致时应减少缓存范围或让读取验证版本。

穿透针对不存在数据，可用参数校验、负缓存或 Bloom Filter；击穿针对热点 Key 突然失效，可用单飞构建、互斥锁、逻辑过期与后台刷新；雪崩是大量 Key 同时失效或缓存整体故障，可用 TTL Jitter、多级缓存、限流与降级。Bloom Filter 有假阳性且删除困难，只能判断“可能存在”或“一定不存在”，不能当权限依据。

NoteWeave 的 ACL 缓存以 `acl_version` 保证权限变化可使旧条目失效，并设置正负 TTL 与 Jitter。资源命中后仍要进行 Workspace、Membership 与 Ownership 校验，不能因缓存命中省略安全边界。Memory Pack 和 Catalog 缓存要把 Scope、Revision、Schema 或 Fingerprint 纳入 Key，命中率不能以跨版本或跨租户污染为代价。

缓存一致性测试应构造并发窗口：读线程 Miss 后暂停，写线程更新数据库并失效缓存，再让旧读线程尝试回填，确认版本门禁会拒绝旧值。Redis 故障时检查回源是否受限，恢复后检查旧 Key 是否还能污染。指标至少包括 Hit/Miss、回源量、构建耗时、Fallback、版本不匹配和数据新鲜度，单看命中率会掩盖错误缓存。

## 11. Redis：分布式锁为什么比 SETNX 复杂

基础实现用 `SET key token NX PX ttl` 原子加锁，释放时通过 Lua 比较 Token 后删除，防止客户端 A 删除已过期并被客户端 B 获得的新锁。仍然存在持有者暂停超过 TTL 的问题：A 的锁过期，B 获得锁，A 恢复后继续写。自动续期可以减少过期，却不能在进程长暂停、网络分区或续期线程故障时保证互斥。

需要保护持久资源时，应使用单调 Fencing Token。每次获得租约拿到更大的 Epoch，下游写入只接受不小于当前版本的请求，旧持有者即使恢复也无法覆盖新结果。若下游不支持条件写，分布式锁只能降低并发概率，不能形成完整正确性证明。Redlock 等算法的适用性也取决于故障模型、时钟和业务是否能接受偶发双持有者，不能只背节点多数。

NoteWeave 的 Worker Lease、Outbox Claim 和 Callback 使用 Token、Epoch 或数据库条件更新抵挡晚到写；Redis 并发租约用于资源治理，不应作为业务状态唯一保护。面试继续追问时，要区分互斥、选主、租约、幂等和 Fencing，它们解决的失败窗口不同。

锁还要定义等待、续期和失败语义。拿不到锁是立即失败、排队还是稍后重试，会影响公平性和用户延迟；持有者取消或崩溃后，业务任务是否能由新 Owner 恢复，需要持久状态支持。测试应暂停旧 Owner 直到 TTL 过期，让新 Owner 完成写入，再恢复旧 Owner，断言下游条件拒绝旧 Epoch。这比只测两线程不能同时进入临界区更接近分布式故障。

若业务只需要防止重复提交，幂等键通常比全局锁更简单；若需要限制在途数量，Semaphore 或租约计数更合适；若要选出唯一调度者，还要考虑 Leader 故障与 Fencing。面试官常用“锁过期但任务没完成”追问，回答重点应是下游拒绝旧写，而不是无限续期。

## 12. Kafka：Topic、Partition、Replica 与 Consumer Group

Kafka Topic 被拆成多个 Partition，每个 Partition 是有序追加日志。顺序只在 Partition 内成立，Producer 使用 Key 决定分区，可以让同一业务对象进入同一 Partition。Partition 数影响并行度、文件与元数据开销，也影响未来扩容时 Key 到 Partition 的映射。副本中 Leader 处理读写，Follower 拉取日志，ISR 表示与 Leader 保持足够同步的副本集合。

Consumer Group 中一个 Partition 同时只分配给组内一个 Consumer，因此增加 Consumer 超过 Partition 数不会增加并行度。不同 Group 各自维护 Offset，可独立消费同一 Topic。Rebalance 会重新分配 Partition，处理中的消息、长耗时任务和 Offset 提交需要协调，否则可能暂停、重复或失去所有权。Cooperative Rebalance 可以减少一次性撤销范围，但业务仍要处理重复。

NoteWeave 的资料解析和投影可以按 Source 或 Snapshot 身份分区，使同一对象事件保持局部顺序。跨 Source 不需要全局顺序，强求单 Partition 会限制吞吐。Consumer 收到旧 Snapshot 事件时应通过版本门禁拒绝覆盖新投影，Kafka 中的到达顺序不能替代业务版本。

Partition 扩容后，默认分区算法可能让同一个 Key 映射到不同 Partition，新旧消息跨分区时不再有原顺序。需要严格对象顺序的系统应在扩容窗口停止相应 Producer、使用稳定路由层，或让 Consumer 依赖业务版本仲裁。副本数提高容灾但增加网络与磁盘写放大，Partition 过多还会增加 Leader 选举、文件句柄和恢复时间。

## 13. Kafka：可靠性、Offset 与 Exactly-once 边界

Producer 的 `acks=all` 要求 Leader 等待 ISR 中所需副本确认，配合合理的最小 ISR 可以提高持久性；幂等 Producer 通过 ProducerId 和序列号减少重试导致的日志重复。事务 Producer 可以原子写多个 Kafka Partition，并让 `read_committed` Consumer 隐藏未提交记录。它仍不能自动把 MySQL 业务事务、MinIO 写入和外部 API 合并成一个 Exactly-once 事务。

At-most-once 通常先提交 Offset 再处理，失败时可能丢；At-least-once 先处理再提交，崩溃时可能重复；所谓 Exactly-once 需要限定范围，在 Kafka 内部状态与输出 Topic 可借助事务实现，跨外部系统仍需幂等、Inbox/Outbox、版本或对账。自动提交 Offset 容易让提交时机与业务完成脱节，手动提交也要清楚批次中部分成功如何处理。

NoteWeave 的 Consumer 完成条件应是业务状态或投影版本已经持久化，而不是方法没有抛异常。处理成功但 Offset 未提交会重复，唯一约束和状态机应吸收；永久 Schema、权限或数据错误进入 DLT，临时依赖错误退避重试。面试官问“Kafka 会不会丢消息”时，要分 Producer、Broker、Consumer 和业务处理四段说明配置、失败窗口与证据。

验证可靠性要主动 Kill Producer、Broker 和 Consumer。分别卡在发送前、Broker 确认后客户端收 Ack 前、业务提交后 Offset 提交前，检查是否丢失、重复和乱序。消息中的 EventId、AggregateId、Version、TraceId 与 SchemaVersion 要有稳定含义。Kafka 指标健康也不证明投影正确，仍需从 MySQL 真源对账文档数量和 Snapshot Version。

## 14. Kafka：积压、顺序、重复和消息队列选型

积压出现时先比较生产速率与完成速率，再按 Partition 看热点、Rebalance、失败重试和下游瓶颈。恢复净速率等于完成速率减到达速率，只有为正才能清空。盲目增加 Consumer 可能受 Partition 数、数据库连接、ES Bulk Queue 或外部配额限制。长任务不宜一直占 Kafka Poll 线程，可以先持久化 Task 再由有界 Worker 执行，同时保证 Offset 与任务创建的完成语义。

严格全局顺序代价很高，通常只需要按业务 Key 有序。失败消息若持续阻塞同一 Partition，可暂停该 Key、转入 Retry Topic 或持久任务队列，但跨 Topic 重试会改变相对顺序。重复是正常故障语义，消费逻辑必须以业务 ID、版本和状态条件判断，不以日志中“只看到一次”为证据。

Kafka 适合高吞吐、可重放事件流；RabbitMQ 偏向灵活路由、低延迟工作队列和成熟确认；Redis Stream 适合已有 Redis 且规模、保留与隔离要求可控的事件流；数据库 Outbox Polling 组件少、事务边界清晰，但吞吐和保留能力有限。NoteWeave 同时用 MySQL Outbox 与 Kafka，是因为前者保证发布意图与业务状态同事务，后者负责异步传输和消费扩展，两者职责不同。

选型还要看消息大小、保留期、顺序范围、延迟、运维能力和消费者数量。大文件不应直接放入消息，通常只传 Object Key、Hash 和版本，避免 Broker 网络与磁盘被巨型 Payload 占满。DLQ 也不是垃圾桶，每条死信要保留原因、原事件、Attempt 与安全的 Redrive 工具，修复 Consumer 后按速率重新执行并对账。

## 15. 分布式理论：CAP、BASE 与一致性模型

CAP 的前提是发生网络分区，此时系统无法同时保证所有请求都成功响应和所有节点都返回最新一致结果。选择一致性可能拒绝或阻塞部分请求，选择可用性可能返回旧值或接受冲突写。它不是说正常状态只能在一致性与可用性中二选一，也不能给整个复杂系统统一贴 CP 或 AP 标签。PACELC 进一步描述无分区时，一致性复制也常与延迟存在权衡。

线性一致让操作看起来按某个全局实时顺序发生；顺序一致保留各客户端程序顺序但不要求实时；因果一致保证有因果关系的操作顺序；最终一致只承诺停止更新后副本逐渐收敛。读己之写、单调读和会话一致性是更贴近产品体验的保证。BASE 强调基本可用、软状态和最终一致，是设计取向，不是某个中间件自动提供的协议。

NoteWeave 对 Refresh Token Rotation、ACL 撤权和任务状态 CAS 依赖数据库强条件；对 ES Projection、缓存和派生内容接受版本化最终一致。上传接口应区分对象已持久化、解析中和可检索 READY，不能把中间状态伪装成强一致。回答一致性题时，应指定对象、操作、复制范围、分区行为和用户可见语义。

一致性保证越强，通常需要更多节点协调和更高延迟，但“最终一致”也不是低成本默认项，它需要冲突处理、版本、补偿、用户状态和对账。面试官给出网络分区场景时，应逐个回答读、写、撤权和恢复行为。例如 ACL 无法确认时 Fail Closed，旧检索投影可以返回但命中后必须回真源校验，统计页可暂时展示旧值并标明刷新时间。

验证一致性要构造并发和分区，而不是只跑正常链路。暂停 Outbox、乱序投递 Snapshot、让旧缓存晚回填、在撤权时查询相似资源，检查版本与权限不变量。指标看 Projection Lag、Stale Reject、对账差异和删除收敛时间。系统恢复后“最终”必须有可证明的收敛条件，不能把永久不一致也归为最终一致。

## 16. 分布式事务：2PC、TCC、Saga 与 Outbox

两阶段提交由协调者先让参与者 Prepare，全部成功后再 Commit。它能提供较强原子性，但参与者需支持协议，协调者与锁持有会影响可用性和吞吐，故障恢复复杂。TCC 把业务操作拆成 Try、Confirm、Cancel，需要为每个参与方设计冻结资源和幂等补偿，侵入性高。Saga 把长事务拆成一串本地事务，失败后执行语义补偿，适合长流程，但隔离较弱，补偿也未必能完全撤销外部影响。

Transactional Outbox 在同一个本地事务中写业务状态和消息意图，Dispatcher 再投递到 Broker。它避免“数据库提交但消息没发”的丢失窗口，代价是可能重复、存在发布延迟，并需要 Claim、重试、DLQ、归档和监控。Consumer 仍需幂等，Outbox 不能保证外部副作用 Exactly-once。CDC 可从数据库日志捕获 Outbox 变更，减少轮询压力，但增加连接器和运维边界。

NoteWeave 的 MySQL、MinIO、Kafka 和 ES 不共享分布式事务，因此选择真源、Outbox、版本化 Projection 与 Cleanup Task。删除先让数据库状态不可见，再异步清理派生；无法撤销的外部写回需要 Preview、审批、Receipt 或补偿。面试时要主动枚举每次跨系统 I/O 前后崩溃会留下什么状态。

补偿不是数据库回滚。已发出的邮件无法收回，只能发送纠正通知；已经调用外部工具写入的数据可能需要反向操作或人工处理。Saga 因此要保存每一步输入、结果、幂等键和补偿状态，并允许补偿本身失败后重试。选择 2PC、TCC、Saga 或 Outbox，取决于参与者能力、隔离要求、流程时长和可补偿性，不以组件流行度决定。

## 17. 分布式基础：一致性哈希、雪花 ID 与时钟问题

一致性哈希把节点与 Key 映射到环上，节点变化时只迁移相邻范围；虚拟节点改善负载均匀性。它适合客户端分片或缓存路由，但不能自动处理热点 Key、数据复制、故障转移和容量差异。Rendezvous Hashing 也能在节点变化时减少迁移，计算与实现特性不同。选择算法要结合节点规模、权重和重平衡成本。

雪花 ID 通常把时间戳、机器标识和序列号组合成 64 位趋势递增 ID。优点是不依赖数据库单点且大致有序，问题包括时钟回拨、机器 ID 冲突、同毫秒序列耗尽和时间信息泄露。数据库自增简单且索引局部性好，但跨库协调困难；UUID 易生成但随机 UUID 可能造成 B+Tree 页分裂，UUIDv7 等时间有序方案能改善写入局部性。ID 方案需要说明唯一范围和排序语义，趋势递增不等于严格事件顺序。

分布式系统不能依赖普通墙上时钟判断绝对先后。NTP 调整、暂停和网络延迟会让时间戳相同或倒退。NoteWeave 的任务 Ownership 使用数据库版本、Epoch、Token 和 Sequence，而不是只比较 `updated_at`；SSE Cursor 和 Snapshot Version 也需要单调业务序号。时间仍可用于 TTL、告警和审计，但正确性条件要考虑时钟误差或使用数据库原子序列。

时钟还影响租约。客户端本地判断 Lease 是否过期，若节点时钟偏差过大可能提前或延后接管，更稳的方案是以同一个数据库或协调服务时间为准，并留出安全余量。ID 中暴露时间与机器信息可能带来业务量推断和安全风险。验证要模拟时钟回拨、同毫秒高并发和节点标识冲突，而不只测生成一百万个 ID 没重复。

## 18. Spring Web：一次请求如何到达业务代码

Servlet 容器接收 HTTP 请求后，把它交给 Filter Chain。Filter 适合认证、Trace、编码和通用安全头；DispatcherServlet 根据 HandlerMapping 找到 Controller，通过 HandlerAdapter 解析参数和执行方法；拦截器可在 Controller 前后做应用级检查；Controller 调用应用服务，异常由 ExceptionResolver 或 `@ControllerAdvice` 转为稳定错误响应。AOP 位于 Bean 方法调用层，适合事务和指标。这些扩展点处于不同生命周期，不能互相随意替代。

Filter 能覆盖静态资源或未命中 Controller 的请求，Interceptor 更容易获得 Handler 元数据，AOP 只能拦截经过 Spring 代理的 Bean 调用。认证通常放在安全 Filter Chain，Workspace 资源级授权仍应在应用服务或 Guard 中根据真实资源归属执行。只在 Controller 注解上检查角色，无法表达“这个 Passage 属于哪个 Workspace”。

NoteWeave 的 InternalServiceAuthFilter 验证面向不同 Audience 的内部 Token，并使用常量时间比较；WorkspaceAccessGuard 再检查 Workspace 状态、ACL Version、Membership、Role 和 Resource Ownership。异常响应要避免泄露资源是否存在，日志也不能记录原始 Token。继续追问可进入参数校验、序列化、线程模型、事务代理、自调用和全局异常处理。

一次请求还可能跨异步边界。Controller 返回 Accepted 后，后台 Job 的身份、Scope 和输入必须冻结或重新校验，不能依赖原请求线程中的 SecurityContext。参数校验负责格式和局部约束，业务校验负责状态与权限，两者错误码不同。全局异常处理不能吞掉事务异常后仍返回成功，也不能把内部堆栈直接暴露给调用方。

## 19. 安全：Session、JWT、OAuth 2.0 与权限模型

Session 模式由服务端保存会话状态，客户端持有随机 SessionId。优点是撤销和服务端控制直接，代价是需要共享存储或粘性路由。JWT 自包含声明并用签名防篡改，服务端验证时可少一次会话查询，但已签发 Token 在过期前不易撤销，Payload 只是 Base64Url 编码并不保密。短期 Access Token 配合可轮换 Refresh Token，可以减少长期凭据暴露窗口；Refresh Replay 需要服务端状态检测，不能只靠 JWT 自包含。

OAuth 2.0 是授权框架，OIDC 在其上增加身份层。Authorization Code 加 PKCE 适合浏览器和移动端，Client Credentials 适合受信服务身份。Access Token 的 Audience、Scope、Issuer 和过期时间都要验证，不能把给服务 A 的 Token 拿到服务 B 使用。RBAC 按角色赋权，ABAC 结合用户、资源和环境属性，ReBAC 关注关系图；实际系统常组合使用。

NoteWeave 当前 Access/Refresh Token 使用随机值，数据库保存 SHA-256 Hash，Refresh Rotation 通过条件更新检测重放，Logout 撤销并清理 Hash。Workspace 权限不只看角色，还校验成员状态与资源归属。内部服务 Token 按 Audience 区分。面试时要说明认证解决“你是谁”，授权解决“你能做什么”，资源归属解决“你能否操作这个具体对象”。

Token 存储位置也会被追问。浏览器 LocalStorage 易受 XSS 读取，HttpOnly Cookie 降低脚本窃取风险但要处理 CSRF；SameSite、Secure、Domain 与 Path 需要配合。密码应使用带 Salt 的慢哈希，如 Argon2、scrypt 或 bcrypt，随机访问 Token 可保存快速密码学 Hash 以便查找。日志、Trace 和指标标签都不能记录原始凭据。

## 20. 安全：SQL 注入、XSS、CSRF、SSRF 与重放攻击

SQL 注入来自把不可信输入拼入 SQL 结构，参数化查询能隔离数据与语句，但动态表名、排序字段和拼接条件仍需白名单。XSS 是不可信内容在浏览器中被当作脚本执行，防护依赖按输出上下文编码、CSP、避免危险 DOM API 和正确 Cookie 属性。CSRF 利用浏览器自动携带 Cookie 发起用户未授权请求，可用 SameSite Cookie、CSRF Token、Origin 校验和避免把状态修改设计成 GET。

SSRF 诱导服务端访问攻击者指定地址，可能触达内网、云元数据或本机管理接口。防护要限制协议、端口和目标网络，重新验证重定向与 DNS 最终解析，设置响应大小、超时和出站网络策略。Prompt Injection 与 SSRF 可以组合，外部网页中的恶意文字诱导 Agent 调用 Fetch 或写工具，因此内容可信度和工具权限必须分开。

重放攻击重复发送合法请求或凭据。Nonce、时间窗口、幂等键、请求签名和一次性 Refresh Rotation 分别覆盖不同场景。NoteWeave 的 Research Fetch 有明确的出站检查，其他调用也要沿 Provider、Workspace 和副作用边界分别配置。安全回答要主动说明信任边界和验证路径。

安全测试要用攻击输入和越权矩阵验证。准备两个 Workspace、相似资源 ID、撤权前后的缓存、重定向到内网的 URL、重复 Refresh Token 和未知 MCP Capability，确认系统 Fail Closed 且不泄露对象存在性。依赖扫描和静态规则只能发现部分问题，运行时最小权限、网络隔离、审计和密钥轮换仍需单独证明。

## 21. 微服务：服务发现、负载均衡、熔断和链路追踪

服务发现分客户端发现和服务端发现。客户端从 Registry 获得实例并自行负载均衡，控制灵活但每种客户端都要维护逻辑；服务端发现由网关或代理选择实例，客户端简单但代理成为关键基础设施。注册表中的实例存在 TTL 和传播延迟，Readiness、主动摘流和连接排空决定发布期间是否把请求送到未准备或即将退出的实例。

微服务把部署和故障域分开，也引入网络失败、协议版本、分布式追踪、数据归属和发布编排。拆分依据应是业务边界、团队 Ownership、扩缩容和故障隔离，不按 Controller 数量拆。共享数据库会让服务通过表结构耦合，完全独立数据库又带来跨域一致性问题，需要事件、API 和对账。单体在规模较小时更容易保持事务与调试简单。

NoteWeave 的 Java Host、Artifact Worker 和 Research Worker 已有跨进程协议。Trace 需要把 HTTP、Outbox、Kafka、Worker 与 Callback 通过稳定业务 ID 串联，MDC 只解决进程内日志上下文。熔断、限流和重试必须围绕 Provider、MCP 与 Worker 的不同失败语义配置，不能用统一注解覆盖所有依赖；当调用量或任务时长增长时，再按瓶颈细化隔离与容量。

是否拆服务应看独立扩缩容、发布频率、数据 Ownership 和故障隔离收益是否超过网络与运维成本。Research Worker 的语言运行时和长任务资源特征与 Java Host 不同，进程边界有明确理由；同一个业务事务内的几张表若硬拆服务，会把简单本地事务变成跨服务协议。面试官问“单体如何演进”时，可先做模块化边界、独立接口和测试，再在真实压力出现时拆部署。

## 25. 基础八股如何串成一个项目回答

如果面试官连续问操作系统、网络、Redis、Kafka、事务和安全，我会把它们挂回同一条请求链路。浏览器发起请求后，Spring Web 在线程池中完成身份过滤和参数校验，JDBC 事务把业务状态与 Outbox 写入 MySQL，Kafka Consumer 把命令交给 Worker，Redis 负责配额和短期协调，SSE 把持久化事件交回浏览器。操作系统层解释线程、阻塞 I/O、虚拟内存和页缓存如何影响延迟，网络层解释 DNS、TCP、TLS、HTTP 超时和重连，数据层解释索引、MVCC、Outbox 和幂等，安全层解释 Session、Audience Token、ACL、SSRF 和重放保护。这样每个八股都有业务落点，不会变成彼此孤立的定义。

Redis 题要先区分缓存、租约和事实状态。项目用 Lua 原子实现 Workspace/Workload 令牌桶和并发 Lease，使用 TTL 回收短期状态，ACL Cache 和编译缓存失效后可以回源 MySQL；但任务、版本、Evidence 和事件仍在 MySQL。Redis Cluster、Sentinel、AOF 和 RDB 适合不同的可用性与恢复目标，不能因为使用 Redis 就自动得到分布式锁正确性。Kafka 题要讲 Topic、Partition、Consumer Group、Offset、Rebalance 和 Ack 如何对应 Outbox、命令、重试和 DLT，明确 At-least-once 加业务幂等，不把 broker 的投递保证说成端到端 Exactly-once。

网络和安全也要进入失败语义。Connect Timeout、Read Timeout、Provider Timeout、Lease Heartbeat 和 SSE Emitter Timeout 组成不同预算，DNS 解析到私网、跨端口重定向或携带凭证都会形成 SSRF 风险；Bearer Session 只证明用户身份，Workspace Membership 才决定资源权限，内部 Worker Token 还要匹配 Audience、Task 和 Fencing。WebSocket 可以支持双向通信，当前回答事件以服务端单向推送为主，所以选择 SSE，并用 Last-Event-ID 恢复；如果未来出现多人协作或交互式控制，再评估双向协议。

分布式理论题也要从项目的真实边界回答。CAP 不是“永远只能三选二”的口号，关键是发生网络分区时业务愿意牺牲什么；资料索引可以暂时落后，权限和业务状态不能被陈旧投影绕过；Saga 和 Outbox 能解决跨系统最终一致，不能凭空提供全局回滚。当前的 Flyway、MySQL、Redis、Kafka、MinIO、ES 和两个 Python Worker 形成的是可恢复的模块化系统。面试中最后要把一个基础原理落到源码方法、真实参数、故障测试和规模触发条件上，才能说明真正理解了它。

### 二阶回答示例：Redis Lua 原子执行，为什么配额仍可能不准

Lua 只保证脚本在单个 Redis 实例上串行执行，解决令牌补充、扣减和租约写入之间的竞态。它不能保证 Redis 与 MySQL Task 创建原子提交，也不能阻止已获得租约的 Worker 在 Redis Lease 过期后继续执行。NoteWeave 在 Acquire 成功但数据库失败时补偿 Release，任务终态重复释放使用幂等身份，旧执行者还要由数据库 Fencing 拒绝提交。Redis 故障时生产 Fail Closed 是为了防止每个实例各自计算一份额度，代价是昂贵任务暂时不可接纳。真正的正确性来自 Redis 原子控制、数据库状态机和恢复对账组合。
