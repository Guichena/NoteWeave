# NoteWeave 项目真实配置参数与容量口径

> 本文只回答“当前代码和 Compose 配了什么、为什么这样保护”，不回答“系统实测能扛多少”。QPS、并发、尾延迟、恢复斜率和单位成本统一从[容量规划、性能压测与成本治理](42-容量规划-性能压测与成本治理一体化面试手册.md)的工作负载与 Manifest 产生；故障阈值和 SLO 动作见[可观测性与 SLO](41-可观测性-SLO与故障定位一体化面试手册.md)。

> 参数核对日期：2026-08-06。核对范围包括 Backend `application.yml` 与配置类、根目录 Docker Compose、Research Worker 和 Artifact Worker。环境变量可覆盖默认值，后续配置变更需要同步复核本手册。

> 证据边界：本手册中的代码默认值、Compose 覆盖和校验约束属于 `[当前实现]`；只有绑定 Manifest 的回放、压测或故障注入结果才标 `[已测-模拟]`；生产容量、SLO、成本和最优参数均属 `[生产待验证]`。公共调参原则见 [API 与事件契约](../API与事件契约-v2.md)。

## 1. 参数分成四种证据

面试中提到一个数字前，先判断它属于哪一类。

| 类型 | 含义 | 可以怎么说 | 不能怎么说 |
|---|---|---|---|
| 代码默认值 | 未提供环境变量时使用的值 | 当前默认配置是 20 个连接 | 系统实测可支撑某个 QPS |
| Compose 覆盖值 | 当前本地 App Profile 的运行设置 | Compose 中 Research 并发默认为 1 | 生产环境也固定为 1 |
| 校验约束 | 代码强制的上下界或关系 | Heartbeat 必须小于 Lease 的三分之一 | 这个比例已经经过生产验证 |
| 测试或压测结果 | 固定环境和工作负载下测得 | 在某环境、某数据下得到 P95 | 脱离环境推广为生产容量 |

当前文档能可靠确认前三类。仓库没有足够证据证明真实线上 QPS、用户规模或跨环境容量。所有默认值都支持环境变量覆盖，参数变更后应重新压测并更新本手册。

## 2. 当前部署边界

本地 App Profile 使用 Docker Compose。MySQL 为 8.4，Redis 为 7.2 且开启 AOF，Kafka 使用单节点 KRaft，MinIO、Elasticsearch、Backend、Frontend、Research Worker 和 Artifact Worker 也由 Compose 编排。基础设施端口默认只绑定 `127.0.0.1`。

Kafka 与 Redis 的 Compose 配置用于本地联调和故障语义验证；健康检查和 `restart` 策略用于本地恢复。生产配置 Guard 要求 Kafka 使用 SSL 或 SASL_SSL，MinIO、ES 和 Artifact Worker 使用 HTTPS，并要求不同 Audience 的内部 Token 与强密钥。若目标流量或数据量增长，应按实际瓶颈重新校准中间件容量。

真实来源：[docker-compose.yml](../../docker-compose.yml)、[ProductionConfigurationGuard.java](../../backend/src/main/java/com/noteweave/config/ProductionConfigurationGuard.java)。

## 3. MySQL 与上传限制

| 设置 | 当前默认值 | 工程作用 |
|---|---:|---|
| Hikari Maximum Pool Size | 20 | 限制单 Backend 实例同时占用的数据库连接 |
| Hikari Minimum Idle | 4 | 保留少量空闲连接，减少突发建连 |
| Connection Timeout | 30 秒 | 获取连接最长等待时间 |
| Validation Timeout | 5 秒 | 连接有效性检查预算 |
| Max Lifetime | 30 分钟 | 在基础设施主动断连前轮换连接，具体仍需匹配数据库环境 |
| 单文件上传上限 | 128 MB | Spring Multipart 文件与请求上限均为 128 MB |
| 文档 Chunk Size | 900 | 当前切块字符预算 |
| Chunk Overlap | 120 | 相邻块保留的重叠字符 |

20 个连接是保护参数，不等于 20 QPS 或 20 个用户。若平均每个请求持有一个连接 50 ms，理想吞吐粗估为 `20 / 0.05 = 400 QPS`，但真实请求可能多次取连接，后台 Outbox、Cleanup 和 Research 也共享连接，还会受到慢 SQL、锁、磁盘和长事务影响。连接池容量要用在线请求与后台任务混合压测验证。

上传允许 128 MB，不表示系统已证明 128 MB 文件能在目标延迟内完成解析、Embedding 和索引。文件处理应流式化，并测量对象存储、Worker 内存、解析时间、Chunk 数、Embedding 批次和从上传到 READY 的整体时间。

真实来源：[application.yml](../../backend/src/main/resources/application.yml)。

## 4. Java 执行器的当前设置

| 执行器 | Core | Max | Queue | Shutdown | 主要用途 |
|---|---:|---:|---:|---|---|
| Answer I/O | 4 | 16 | 64 | 等待最多 20 秒 | 模型或回答生成 I/O |
| SSE Dispatch | 2 | 8 | 128 | 等待最多 10 秒 | 向 Subscriber 派发事件 |
| SSE Connection | 4 | 32 | 0 | 不等待 | 长连接跟随，60 秒 KeepAlive，核心线程可超时 |
| Redis Answer Bridge | 2 | 16 | 0 | 不等待 | 阻塞式 XREAD Pump |
| Scheduling | 4，代码最少 2 | 4 | 调度器内部 | 等待最多 30 秒 | 定时任务 |
| Artifact Dispatch | 1 | 1 | 0 | 等待最多 30 秒 | Artifact Outbox 派发 |
| Answer Event Scheduler | 2 | 2 | 调度器内部 | `shutdown` | Delta 批处理 |
| Answer Lease Scheduler | 4 | 4 | 调度器内部 | `shutdown` | Answer Stream Lease 续租 |

前四个 ThreadPoolTaskExecutor 都使用 AbortPolicy，过载会显式拒绝。SSE Connection 与 Redis Bridge 使用零队列，使线程数先扩到 Max，不让阻塞连接藏在队列里。Answer I/O 会传播并在 finally 中恢复 MDC；其他 Executor 是否需要业务身份传播，要按调用路径分别判断。

这些池不能分别独立估算容量。32 条 SSE Connection 线程不代表 32 个模型调用，16 个 Answer I/O 线程也可能同时争用 20 个数据库连接或同一个 Provider 配额。压测至少同时观察 Active、Queue、Rejected、数据库 Pending、Provider 429、SSE Overflow 和端到端 P99。

真实来源：[RealtimeExecutorConfig.java](../../backend/src/main/java/com/noteweave/config/RealtimeExecutorConfig.java)、[SchedulingConfiguration.java](../../backend/src/main/java/com/noteweave/config/SchedulingConfiguration.java)。

## 5. Redis、配额与缓存

### 5.1 Redis 客户端与本地部署

| 设置 | 当前值 |
|---|---:|
| Connect Timeout | 500 ms |
| Command Timeout | 750 ms |
| Compose 持久化 | AOF 开启 |
| Compose 认证 | `requirepass` |
| 当前拓扑 | 单 Redis 实例 |

500/750 ms 表示控制平面希望快速识别 Redis 不可用，避免配额、缓存或实时桥接长时间占住线程。Redis 单实例加 AOF 不等于高可用，也不能保证最近写入绝不丢失。缓存、配额租约与 SSE Replay 对 Redis 丢失的影响不同，必须分别定义降级。

### 5.2 Workload 配额

| 设置 | 分布式 Redis 路径 | 本地回退路径 |
|---|---:|---:|
| Rate Capacity | 20 | 5 |
| Refill | 20/分钟 | 5/分钟 |
| Concurrency Limit | 4 | 1 |
| Lease | 300 秒 | 同一 Lease |
| Local Fallback | 默认关闭 | 生产 Guard 强制关闭 |

Rate Key 按 Workspace、Actor、Workload 约束到达速率；Concurrency Key 按 Workspace、Workload 约束在途任务。令牌桶容量 20 允许短时突发，补充速率约每 3 秒 1 个 Token。并发 4 与 Rate 20/分钟不是同一限制。Lease 300 秒需要运行方续租，不能把 4 个并发槽理解成系统总 Worker 数。

项目还有两层容易与入口配额混淆的限制。Java Research 执行面在发放受信任 Tool Permit 时，通过 `ResearchAgentRateLimitService` 同时扣 Provider、Workspace、Run + Role 三个 Redis Bucket，默认 Capacity/Refill 为 `10/10 每分钟`；Redis 不可用时默认 Fail Closed。Research Worker 的 Fetch Adapter 另有进程内 `4 请求/秒` 固定间隔限速和 Fetch 并发 4。三者分别保护任务入口、跨 Worker 的 Research Tool Provider、单 Worker 的网络 Fetch，Key、单位和错误码都不同，不能在面试中合并成“Redis 限流 20”。

| 层次 | 当前入口或实现 | 默认值 | 失败语义 |
|---|---|---:|---|
| 昂贵任务入口 | `WorkloadQuotaService` | Rate `20/20 每分钟`，并发 4，Lease 300 秒 | `WORKLOAD_RATE_LIMITED`、`WORKLOAD_CONCURRENCY_LIMITED` 或 Redis 不可用 |
| Research Tool Permit | `ResearchAgentRateLimitService` | Provider、Workspace、Run + Role 三桶共同使用 `10/10 每分钟` | `RESEARCH_AGENT_RATE_LIMITED`，Redis 不可用默认拒绝 |
| Worker Fetch | `FixedIntervalRateLimiter` 与 Fetch Semaphore | 4 请求/秒，并发 4 | 本进程等待并按 Fetch 错误策略有限重试，不形成全局配额 |

### 5.3 缓存 TTL

| Cache | TTL | Jitter 或负缓存 |
|---|---:|---:|
| ACL Positive | 300 秒 | Jitter 60 秒 |
| ACL Negative | 30 秒 | Jitter 60 秒应用于缓存策略 |
| Source Catalog | 120 秒 | Jitter 30 秒 |
| Wiki Page Version | 600 秒 | Jitter 120 秒 |
| Memory Compiled Pack | 180 秒 | Jitter 30 秒 |

ACL 缓存还带 `acl_version`，权限变化不依赖等待 300 秒自然过期。负缓存只保留 30 秒，降低不存在资源长期陈旧的风险。Jitter 用于分散失效时间，不是数据新鲜度指标。命中率提高必须同时检查回源、版本不匹配、撤权和跨 Scope 隔离。

真实来源：[application.yml](../../backend/src/main/resources/application.yml)、[WorkloadQuotaService.java](../../backend/src/main/java/com/noteweave/quota/WorkloadQuotaService.java)。

## 6. Embedding、Rerank 与 LLM

| 能力 | 默认是否启用 | 批次或输入 | Timeout | Attempts |
|---|---|---|---:|---:|
| Embedding Query | 否 | 1024 维，最多 12000 字符 | 10 秒 | 最多 3 次 |
| Embedding Document | 否 | Batch 32 | 60 秒 | 最多 3 次 |
| Rerank | 否 | Batch 80，每文档最多 1800 字符 | 20 秒 | 最多 3 次 |
| Backend LLM | 否 | 模型由环境变量指定 | 60 秒 | 客户端路径另行控制 |
| Research LLM | 需要配置 | 输入最多 120000 字符，安全余量 8000 | 60 秒 | 最多 3 次，总调用上限 64 |
| Artifact LLM | 需要配置 | 模型由环境变量指定 | 60 秒 | 按 Worker 调用路径处理 |

Compose 默认也关闭 Backend Elasticsearch、Embedding、Rerank 与 LLM。QA MySQL Fallback 和 Note Local Metadata Fallback 在 `application.yml` 默认关闭，但本地 Compose App Profile 默认打开；Production Guard 禁止生产启用这些弱回退。面试时必须区分“代码实现了可配置链路”“`application.yml` 代码默认值”和“当前 Compose 默认实际调用模型/回退”。

Attempts 不能直接乘 Timeout 当作总 Deadline，因为调用可能提前失败并退避，也可能多个层次各自重试。更安全的口径是明确单次预算、最大次数和调用链总预算，再用故障注入确认最坏时间。Research 总调用上限 64 是成本熔断保护，不代表一次任务正常会调用 64 次。

### 6.1 QA 检索漏斗与参数联动

| 阶段 | 当前值 | 保护对象 | 过大或过小的失败模式 |
|---|---:|---|---|
| Vector Recall | 60 | 语义召回覆盖 | 太小漏同义证据；太大增加 ES、Hydration 和精排压力 |
| Keyword Recall | 60 | 精确词和术语覆盖 | 太小漏错误码与版本号；太大引入 Fuzzy 噪声 |
| kNN `numCandidates` | 300 | ANN 搜索宽度，公式为 `max(5×60, 100)` | 太小损失近邻召回；太大增加 ES CPU 与长尾 |
| Fusion Ceiling | 100 | 两路去重后的候选上界 | 太小可能在精排前丢证据；太大放大后置校验成本 |
| RRF | `k=60`，Vector/Keyword `0.7/0.3` | 避免直接相加异构原始分数 | 权重偏斜会压制另一类错误模式；`k` 太小会过度放大头部名次 |
| Low Recall Expansion | Primary Fusion 少于 3 条时触发，最多 5 个变体 | 只修复低召回 Query | 门槛太高会让正常查询也放大 Provider 调用，太低会漏掉需要扩展的查询 |
| Rerank Input/Output | Client Batch 80，Top N 40 | 限制远程精排输入与返回量 | 输入过大增加超时与重试成本；输出过小可能在 Selection 前丢证据 |
| Final Evidence | 最多 6 条、8000 字符 | Prompt 噪声、引用身份与上下文成本 | 太小证据不足；太大增加重复来源、Token 与引用错误 |

当前 Vector 与 Keyword Threshold 都是 0，不代表所有候选都可信，而是把绝对阈值校准推迟到排序、Ownership 和 Evidence Policy。参数变更应固定 Snapshot、Query 分桶和 Evidence Budget，先画 Recall、Fusion、Rerank、Ownership、Selection 漏斗，再同时比较 Recall@K、nDCG、Citation Support、拒答、P95/P99、Provider 429 与单位请求成本。没有该对照时，只能说当前默认值，不说“经过调优”。

Rerank 还存在一个参数与协议耦合：策略允许 Fusion 100、Rerank Top N 40，但客户端 Batch 80，所以只有融合顺序前 80 条会进入单次 Provider 请求。Provider 返回空、越界下标、重复下标或非有限分数时整批退回原顺序；只返回部分合法下标时会补回遗漏候选，但 QA 聚合降级当前不会置位。这是已由单测覆盖的失败语义和一个待补的观测缺口，不是生产质量结论。

真实来源：[application.yml](../../backend/src/main/resources/application.yml)、[Research Settings](../../workers/research-worker/app/config.py)、[Artifact Settings](../../workers/artifact-worker/app/config.py)。

## 7. Kafka 与 Outbox

### 7.1 Kafka 客户端

| 设置 | 当前值 |
|---|---|
| Producer Acks | `all` |
| Publish Wait | 最多 10 秒 |
| Consumer Auto Commit | 关闭 |
| Ack Mode | Record |
| Offset Reset | earliest |
| Consumer Retry | 原始投递后最多 2 次重试 |
| Retry Delay | 约 1 秒、2 秒，各加最多 20% Jitter |
| 失败终态 | 发布到源 Topic 的 `.DLT` |
| Compose Broker | 单节点 KRaft，SASL_PLAINTEXT |

`acks=all` 配合 Record Ack 与关闭 Auto Commit，让 Offset 更接近单条业务完成，但 Consumer 仍可能在业务提交后、Offset 提交前崩溃，因此必须幂等。当前自动创建的 Java DLT Topic 采用小规模默认值，吞吐、保留时间或恢复窗口增长时，应重新配置 Partition、保留和消费容量。

### 7.2 Outbox

| 设置 | 当前值 |
|---|---:|
| Dispatch Tick | 1000 ms |
| 单次 Candidate Batch | 50 |
| 普通 Lease | 1 分钟 |
| Artifact Callback Lease | 70 分钟 |
| Artifact 控制面 HTTP Connect / Read | 3 秒 / 30 秒 |
| Artifact 命令 Topic | `noteweave.artifact.job` |
| Artifact Consumer | Auto Commit Off、Max Poll Records 1、Max Poll Interval 4200 秒 |
| Max Attempts | 5 |
| 单次 Kafka Publish Wait | 10 秒 |
| Retry Backoff | 指数增长，60 秒封顶，最多约 20% Jitter |
| Research Command Dispatch 调度器 | 1000 ms，Batch 25 |

普通 Outbox Lease 覆盖短 Kafka 发布。当前 Artifact 在 Broker ACK 后保留 70 分钟 Delivery Lease，Consumer 单条拉取并用 4200 秒 Max Poll 覆盖最长工具执行；这些是旧协议的真实配置，不是推荐架构。它会将 Kafka 消费会话与小时级执行权绑定，分区吞吐和 Rebalance 都受最慢任务影响。推荐迁移为：Consumer 按 Command ID 在 MySQL 幂等登记 Durable Execution，提交事务后提交 Offset；Scheduler 再使用 Active Permit、Execution Lease、Epoch 和 Fencing 管理 Worker。Connect 3 秒、Read 30 秒继续只约束 HTTP 控制面。旧 Delivery Sweep 和 409 Fencing 在迁移期保留，直到所有 Callback 都绑定 Durable Execution。Batch、Tick 和分区数都不能单独推出完成吞吐。

### 7.3 三个重试域不能混成一个参数

Outbox Attempt 处理 Host 到 Broker 的发布失败；Kafka Consumer 重放处理 Broker 已持久化但 Artifact 协议尚未确认的失败；Artifact Callback 的幂等键和 Lease 处理 Worker 已执行但 Host 尚未接受进度或终态的失败。这三个机制保护的提交点不同，也可能放大彼此。调参前要先画出当前工作负载实际经过哪些边界，不能把 `Outbox 5 × Consumer 重放 × Provider 3` 当成一个准确的最大调用次数。

Artifact 的关键 Bad Case 已从“HTTP 202 丢失”变为“外部副作用完成后、Callback 和 Offset 均未确认时 Worker 崩溃”。Kafka 会重放该命令；读取冻结输入时的 Delivery Token Fencing 能拦截已失效的旧 Delivery，Callback 幂等能阻止双终态，但在当前 Delivery 仍有效时，外部工具是否重复仍取决于稳定 Operation Identity、Provider 幂等键和结果查询。调优重点不是延长 HTTP Read Timeout，而是故障注入下的副作用对账、Unknown Outcome 年龄和可恢复错误分类。

真实来源：[KafkaConfig.java](../../backend/src/main/java/com/noteweave/infra/KafkaConfig.java)、[OutboxDispatchPolicy.java](../../backend/src/main/java/com/noteweave/infra/outbox/OutboxDispatchPolicy.java)、[TaskOutboxDispatcherService.java](../../backend/src/main/java/com/noteweave/infra/TaskOutboxDispatcherService.java)、[KafkaArtifactOutboxPublisher.java](../../backend/src/main/java/com/noteweave/worker/KafkaArtifactOutboxPublisher.java)、[Artifact Kafka Consumer](../../workers/artifact-worker/app/artifact_kafka_consumer.py)、[Artifact Worker main.py](../../workers/artifact-worker/app/main.py)。

## 8. Research Worker 的 Lease、并发和成本保护

| 设置 | 当前默认或 Compose 值 |
|---|---:|
| Execution Mode | `INCREMENTAL_V1` |
| Agent Max Concurrency | 1 |
| Bundle Max Cells | 3 |
| Fetch Max Concurrency | 4 |
| Fetch Timeout | 20 秒 |
| Fetch Retries | 3 |
| Fetch Rate | 4 请求/秒 |
| Task Lease | 60 秒 |
| Heartbeat Interval | 默认由 Lease/4 得到，Compose 明确为 15 秒 |
| Heartbeat Failure Budget | 默认 Interval 的 2 倍，Compose 为 30 秒 |

| Completion Attempts | 3 |
| Kafka Consume Attempts | 3 |

| Drain Poll | 500 ms |

校验器要求 Heartbeat Interval 小于 Lease 的三分之一，Failure Budget 加一个 Interval 后仍小于 Lease，Heartbeat Request Timeout 小于 Interval。当前 `60/15/30/5` 满足：15 小于 20，30 加 15 小于 60，5 小于 15。这个关系给续租失败留出停止工作的安全窗口。

Agent Max Concurrency 为 1，表示默认运行路径有意保持有界顺序执行；Fetch Concurrency 为 4，只并发网络取证，不代表四个 Agent 分支并行提交状态。面试时不能把编译期 DAG 描述成运行时大规模并行 Ready Queue。提高 Agent 并发前要测 Provider TPM、任务状态竞争、数据库连接、合并正确性和单位成功成本。

## 9. SSE、Replay 与 Answer Lease

| 设置 | 当前值 |
|---|---:|
| 进程内 Replay Capacity | 512 个事件，代码最少 32 |
| Subscriber Queue | 64 个事件，代码最少 8 |
| Redis Stream Max Length | 512 |
| Redis Stream TTL | 600 秒，代码最少 60 秒 |
| Follow Timeout | 125 秒 |
| Answer Stream Lease | 150 秒 |
| Lease Renewal | 每 45 秒 |
| Delta Batch | 最多 512 字符或 30 ms |

Subscriber Queue 满时，如果队尾与新事件都是 `answer.delta`，系统先合并 Delta；无法合并则记录 Overflow 并关闭慢 Subscriber。Replay Capacity 512 是事件条数，不是字符数或秒数；Delta 经过 512 字符/30 ms 合并后，实际可回放文本量取决于输出节奏。Redis Stream 600 秒 TTL 提供多实例短期桥接，最终回答和业务终态仍由 MySQL 保存。

Answer Lease 150 秒、每 45 秒续租，正常情况下有三次以上续租机会。续租失败会把本地 Lease 标记无效，旧生成者不能继续确认终态。125 秒 Follow Timeout 是单次跟随连接预算，不代表模型任务总时长。SSE 容量要分别压测连接数、事件速率、慢消费者和断线重连。

真实来源：[SessionEventMux.java](../../backend/src/main/java/com/noteweave/answer/SessionEventMux.java)、[RedisAnswerRealtimeBridge.java](../../backend/src/main/java/com/noteweave/infra/RedisAnswerRealtimeBridge.java)、[AnswerRunService.java](../../backend/src/main/java/com/noteweave/answer/AnswerRunService.java)、[BufferedAnswerDeltaEmitter.java](../../backend/src/main/java/com/noteweave/answer/BufferedAnswerDeltaEmitter.java)。

## 11. Rollout Guard 的当前门槛

Backend 代码默认启用 Research Rollout Guard，窗口 15 分钟，最小任务样本 10，Terminal Failure 与 Delivery Failure 上限均为 20%，Rejected Merge 上限为 30%。但 Compose App Profile 把 Guard 默认覆盖为关闭。因此可以说“代码实现了默认门槛，当前 Compose 演示环境没有默认开启”，不能说当前部署已经由这些指标自动拦截发布。

## 12. 面试中如何解释这些数字

一个参数至少讲四件事：约束对象、失败时表现、相邻参数关系、调优证据。以 Answer I/O 的 `4/16/64` 为例，4 个 Core 承担常态 I/O，突发时最多扩到 16，之后最多排队 64，队列继续增长时 AbortPolicy 显式拒绝。它与 Hikari 20、LLM 60 秒和配额并发 4 共同作用，不能单独推出 QPS。调优要同时看 Active、Queue、Rejected、TTFT、数据库 Pending 和 Provider 429。

以 Research `Lease 60/Heartbeat 15/Failure Budget 30/Request Timeout 5` 为例，参数关系保证续租失败后有时间停止 Provider 工作，旧 Worker 晚到再由 Fencing 拒绝。若把 Lease 缩短到 20 秒而不调整 Heartbeat 和网络 P99，正常抖动会频繁接管；若把 Lease 拉长到 10 分钟，崩溃恢复变慢。调优依据是 Heartbeat 延迟分布、GC/进程暂停、网络故障和可接受恢复时间。

以缓存 ACL `300/30/60` 为例，正缓存 5 分钟降低数据库读，负缓存 30 秒缩短不存在对象的陈旧窗口，60 秒 Jitter 分散失效，`acl_version` 保证撤权不等自然过期。面试中应主动说 TTL 是性能策略，版本与真源校验才是安全正确性。

## 13. 参数变更的验证清单

- 调线程池时，同时压测队列、拒绝、数据库连接、Provider 配额和关闭行为。
- 调 Hikari 时，观察 MySQL CPU、锁等待、事务时间和后台任务，不只看 Pending。
- 调 Redis Timeout 时，注入连接拒绝、慢命令和主从切换，验证 Fail Open/Closed 策略。
- 调缓存 TTL 时，测试撤权、旧值晚回填、批量失效和数据库回源峰值。
- 调 Kafka Retry 或 Outbox Batch 时，测试重复、DLT、下游过载和积压恢复。
- 调 Lease/Heartbeat 时，暂停进程、制造网络超时和旧 Owner 晚到，验证 Fencing。
- 调 Embedding/Rerank Batch 时，比较吞吐、P99、内存、Provider 限额和检索质量。
- 调 SSE Buffer 时，覆盖慢消费者、Cursor Expired、Delta 合并和 Redis 故障。
- 调 Token 生命周期时，验证 Rotation、Replay、Logout、撤销和日志脱敏。

配置审查的最终问题不是“这个数字看起来合不合理”，而是“它保护哪个资源，超过后系统怎样失败，指标能否提前看到，改动后用什么证据验收”。

## 15. 参数与容量题的 4 到 5 分钟完整回答

面试时我会先把参数分成四类：代码默认值、部署覆盖值、正确性保护阈值和经过负载验证的容量结论。比如 Hikari 最大连接数 20、SSE Replay 512、Subscriber Queue 64、Research Lease 60 秒、Heartbeat 15 秒、Embedding Batch 32、Rerank Batch 80，这些数字说明系统如何保护资源、多久回收租约、批量如何切分和断线能回放多长窗口，但都不能单独推出 QPS、在线连接数或 P99。只有绑定机器、Provider、数据分布、持续时间、成功率和成本的压测结果，才可以称为容量结论。

参数要沿上下游解释。上传 multipart 128 MB 影响对象存储、请求线程和解析批次；Chunk Size/Overlap 900/120 影响 Chunk 数、Embedding 成本、召回粒度和 Note Window；Hikari 20 约束并发 SQL，线程池大于连接池时只会增加等待；Kafka Outbox Tick 1 秒、Batch 50 和 Lease 1 分钟决定调度延迟与恢复窗口，不是每秒必然发送 50 条；Research Command Dispatch 另有 Tick 1 秒、Batch 25；SSE Emitter 120 秒、Follow 单次等待 125 秒、Replay 512 和 Subscriber 64 决定慢消费者和重连策略，不能用事件条数代替连接容量；Research Worker 并发 1、Fetch 4 只说明当前执行保护，不等于四个分支同时修改状态。

调参时要看耦合关系。提高 Worker 并发会增加 Kafka 消费、MySQL Claim、Provider 请求、MinIO 读取和 Callback 压力；提高 Embedding Batch 可能提高吞吐，却会增加单次请求大小、失败重试成本和内存；增大 SSE Replay 能延长恢复窗口，也会增大每个 Run 的内存与 Redis Stream 保留；缩短 Lease 能更快接管故障，但网络抖动和 GC 停顿会带来误判。参数必须配套观测 Oldest Ready Age、Queue Size、Hikari Pending、Provider 429、Lease Lost、SSE Overflow、Replay Cursor Expired 和错误率，不能只看平均延迟。

容量计算可以作为面试中的估算起点。用 `L = λW` 估算在途请求，用并发上限和平均服务时间估算下游压力，再把重试、反证、断线重放和慢消费者作为放大项。假设一个 Research Run 平均五分钟，入口每分钟两条，平均在途约十条；如果每条同时四个 Fetch，外部请求并发可能接近四十，还没有计入重试和其他用户。真正的瓶颈可能是 Provider、连接池或数据库锁，而不是 Worker 数量。生产扩容要先确认最老任务年龄、Provider 429、数据库锁等待和队列积压的变化，再决定提高并发、收紧限流或拒绝新任务。将长期不可用任务持久化 Waiting 是目标设计，不是当前所有 Provider 路径的统一行为。

参数回答最后要主动说边界。Compose 默认关闭 LLM、Embedding、Rerank、Elasticsearch 或 MinIO 时，只能验证基础设施和显式降级；H2 通过不能证明 MySQL 锁行为；线程池默认值也不能直接推出目标环境吞吐。参数表的价值是让保护逻辑可复现、让变更有依据，不能把配置数字包装成没有数据支撑的性能承诺。

## 16. 端到端容量算例：从工作负载推导最小瓶颈

下面是面试设计算例，不是当前线上结果。它的作用是展示容量推导顺序，实际回答时要把入口速率、文件分布、Provider 限额和机器资源替换成已经确认的数据。

### 16.1 先定义三类负载

假设一个中等工作日有三类请求：资料上传每小时 120 个文件，平均每个文件 2 MB；QA 平均每秒 0.2 个请求，P95 端到端耗时 8 秒；Research 每分钟进入 2 个 Run，平均运行 5 分钟，每个 Run 同时发起 4 个 Fetch。上传、QA 和 Research 不能共用一个“总 QPS”，因为它们的服务时间、下游依赖和失败语义不同。

上传侧每小时 120 个文件，平均到达率约 `0.033/s`。如果每个文件解析、切片和投影平均占用 6 秒，那么平均在途解析任务约为 `L = 0.033 × 6 = 0.2` 个；峰值按 5 倍计算约为 1 个到 2 个任务。这个结果说明当前默认 Worker 并发 1 在低峰验证中够用，但不能据此推导高峰吞吐。真正需要观察的是单文件大小分布、Chunk 数、Embedding 批次、ES 写入耗时和失败重试。

QA 入口平均 `0.2/s`，P95 8 秒时平均在途量约为 `L = 0.2 × 8 = 1.6`。如果 Provider 等待占据主要时间，线程池和连接池会比 CPU 更早成为瓶颈。Hikari 最大连接 20 并不意味着可以安全地启动 20 个并发回答，因为检索、归属 Hydration、缓存回源和写事件都会占用连接。面试时应继续问每个请求平均持有连接多久、是否有慢 SQL、Hikari Pending 是否上升，再决定调整并发还是优化 SQL。

Research 每分钟 2 个 Run，平均 5 分钟完成，平均在途量约为 `2 × 5 = 10` 个。每个 Run 同时 4 个 Fetch，外部请求并发起点约为 40；如果平均每次失败重试 20%，外部压力接近 `40 × 1.2 = 48`。因此 Research 的第一瓶颈很可能是 Provider 限额或 Fetch 队列，而不是 Java Web 线程。此时应先用 Workspace/Workload 入口配额、Research Tool Permit 和 Worker Fetch 限速分层保护，观察 Provider 429、Oldest Ready Age、Task Lease Lost 和失败终态；若需要跨长时间窗口自动恢复，再补持久 Waiting 状态、截止时间和唤醒策略。

### 16.2 把资源约束串起来

容量推导要把四层资源连起来：入口速率决定任务产生速度，Kafka 和 Outbox 吸收短期波动，Worker 并发决定在途执行数，下游 Provider、MySQL、Redis、MinIO 和 ES 决定实际服务时间。只要一层利用率接近饱和，继续扩大上游线程池就会把等待转移到连接池、队列或 Provider。

可以把某类工作负载的准入初值写成：

```text
admission_limit = min(
  executor_service_capacity,
  database_connection_budget / connections_held_per_task,
  provider_concurrency_or_rate_budget,
  worker_and_callback_capacity,
  cost_budget / expected_cost_per_inflight_task
) - safety_reserve
```

这只是结构化估算，不是当前系统已经实现的统一算法。`WorkloadQuotaService` 当前能证明 Workspace + Actor + Workload 速率控制和 Workspace + Workload 并发 Lease，各执行器也有独立上限；跨线程池、Hikari、Provider、队列年龄和成本的统一 Admission Controller 仍是目标设计。同步 QA 超预算时优先快速拒绝或显式降级，异步 Research/Artifact 才允许持久排队，并限制最老年龄、Workspace 份额和 Deadline。

限流策略先用 Count-only 记录决策和原因，再在受控 Workspace 执行。触发阈值与恢复阈值分开，要求连续窗口、最短降级时间和半开探测，避免 Provider 一次成功就恢复全部并发。容量实验必须同时观察入口拒绝、Queue Oldest Age、Executor Rejected、Hikari Pending、Provider 429、单位成功成本和质量门禁。

可以用下面的判断顺序回答扩容问题：

1. `Oldest Ready Age` 上升，先确认 Outbox Dispatcher 是否被锁等待或发送错误阻塞。
2. Kafka Lag 上升且 Worker CPU 低，检查 Provider 延迟、429、连接池等待和 Poison Message，不要立即加 Consumer。
3. Worker CPU 高而下游延迟稳定，才考虑增加执行并发，并检查 Kafka Partition 是否足够。
4. Hikari Pending、数据库锁等待和事务耗时同时上升，优先优化批量、索引和短事务，继续加 Worker 会放大争用。
5. SSE Queue 满、Replay Cursor 过期或 Redis Bridge 延迟上升，先限制慢消费者和事件窗口，再判断是否需要改变连接模型。

### 16.3 面试官追问“十倍流量怎么办”

十倍流量不能直接回答“把实例数乘十”。我会先把上传、QA、Research 和 Artifact 分开重算，找出最先达到 70% 到 80% 利用率的资源；然后确认是否能通过批量、缓存、限流、降级和任务分级把需求压回当前边界。如果瓶颈是 Kafka 分区，扩消费者没有意义；如果瓶颈是 Provider 429，扩 Worker 只会增加失败；如果瓶颈是 MySQL 锁等待，应先降低写竞争和缩短事务；如果瓶颈是索引投影延迟，应该隔离回填和在线查询。每次改变参数都要重新观察队列年龄、P95、错误率、资源利用率和恢复斜率，而不是只看平均 QPS。

### 16.4 容量算例的验收输出

一次可复现的容量验证至少应留下：工作负载生成方式、文件大小和查询类型分布、Provider 与模型版本、机器规格、并发阶梯、P50/P95/P99、错误与降级比例、Oldest Ready Age、Hikari Pending、Kafka Lag、Redis 延迟、ES 投影延迟和恢复到稳定水位的时间。没有这些字段时，只能称为设计估算，不能称为压测结论。
