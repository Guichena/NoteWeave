# NoteWeave 项目真实配置参数与容量口径

> 参数审计日期：2026-08-03。审计范围包括 Backend `application.yml` 与配置类、根目录 Docker Compose、Research Worker 和 Artifact Worker。环境变量可覆盖默认值，后续配置变更需要同步复核本手册。

## 1. 参数分成四种证据

面试中提到一个数字前，先判断它属于哪一类。

| 类型 | 含义 | 可以怎么说 | 不能怎么说 |
|---|---|---|---|
| 代码默认值 | 未提供环境变量时使用的值 | 当前默认配置是 20 个连接 | 系统实测可支撑某个 QPS |
| Compose 覆盖值 | 当前本地 App Profile 的运行设置 | Compose 中 Research 并发默认为 1 | 生产环境也固定为 1 |
| 校验约束 | 代码强制的上下界或关系 | Heartbeat 必须小于 Lease 的三分之一 | 这个比例已经经过生产验证 |
| 测试或压测结果 | 固定环境和工作负载下测得 | 在某环境、某数据下得到 P95 | 脱离环境推广为生产容量 |

当前文档能可靠确认前三类。仓库没有足够证据证明生产 QPS、百万用户、高可用 RTO/RPO 或跨区域容量。所有默认值都支持环境变量覆盖，参数变更后应重新压测并更新本手册。

## 2. 当前部署边界

本地 App Profile 使用 Docker Compose。MySQL 为 8.4，Redis 为 7.2 且开启 AOF，Kafka 使用单节点 KRaft，MinIO、Elasticsearch、Backend、Frontend、Research Worker 和 Artifact Worker 也由 Compose 编排。基础设施端口默认只绑定 `127.0.0.1`。

Kafka 单节点只有一个 Broker/Controller，Compose 中使用 SASL_PLAINTEXT；Redis 是单实例；健康检查和 `restart` 策略用于本地恢复。这些设置不能称为生产高可用、跨节点副本、滚动发布或灾备。生产配置 Guard 要求 Kafka 使用 SSL 或 SASL_SSL，MinIO、ES 和 Artifact Worker 使用 HTTPS，并要求不同 Audience 的内部 Token 与强密钥。

真实来源：[docker-compose.yml](../../docker-compose.yml)、[ProductionConfigurationGuard.java](../../backend/src/main/java/com/noteweave/config/ProductionConfigurationGuard.java)。

## 3. MySQL 与上传限制

| 设置 | 当前默认值 | 工程作用 |
|---|---:|---|
| Hikari Maximum Pool Size | 20 | 限制单 Backend 实例同时占用的数据库连接 |
| Hikari Minimum Idle | 4 | 保留少量空闲连接，减少突发建连 |
| Connection Timeout | 30 秒 | 获取连接最长等待时间 |
| Validation Timeout | 5 秒 | 连接有效性检查预算 |
| Max Lifetime | 30 分钟 | 在基础设施主动断连前轮换连接，具体仍需匹配数据库环境 |
| 单文件上传上限 | 128 MB | Spring Multipart 文件与请求上限均为 128 MB |
| 文档 Chunk Size | 900 | 当前切块字符预算 |
| Chunk Overlap | 120 | 相邻块保留的重叠字符 |

20 个连接是保护参数，不等于 20 QPS 或 20 个用户。若平均每个请求持有一个连接 50 ms，理想吞吐粗估为 `20 / 0.05 = 400 QPS`，但真实请求可能多次取连接，后台 Outbox、Cleanup 和 Research 也共享连接，还会受到慢 SQL、锁、磁盘和长事务影响。连接池容量要用在线请求与后台任务混合压测验证。

上传允许 128 MB，不表示系统已证明 128 MB 文件能在目标延迟内完成解析、Embedding 和索引。文件处理应流式化，并测量对象存储、Worker 内存、解析时间、Chunk 数、Embedding 批次和从上传到 READY 的整体时间。

真实来源：[application.yml](../../backend/src/main/resources/application.yml)。

## 4. Java 执行器的当前设置

| 执行器 | Core | Max | Queue | Shutdown | 主要用途 |
|---|---:|---:|---:|---|---|
| Answer I/O | 4 | 16 | 64 | 等待最多 20 秒 | 模型或回答生成 I/O |
| SSE Dispatch | 2 | 8 | 128 | 等待最多 10 秒 | 向 Subscriber 派发事件 |
| SSE Connection | 4 | 32 | 0 | 不等待 | 长连接跟随，60 秒 KeepAlive，核心线程可超时 |
| Redis Answer Bridge | 2 | 16 | 0 | 不等待 | 阻塞式 XREAD Pump |
| Scheduling | 4，代码最少 2 | 4 | 调度器内部 | 等待最多 30 秒 | 定时任务 |
| Artifact Dispatch | 1 | 1 | 0 | 等待最多 30 秒 | Artifact Outbox 派发 |
| Answer Event Scheduler | 2 | 2 | 调度器内部 | `shutdown` | Delta 批处理 |
| Answer Lease Scheduler | 4 | 4 | 调度器内部 | `shutdown` | Answer Stream Lease 续租 |

前四个 ThreadPoolTaskExecutor 都使用 AbortPolicy，过载会显式拒绝。SSE Connection 与 Redis Bridge 使用零队列，使线程数先扩到 Max，不让阻塞连接藏在队列里。Answer I/O 会传播并在 finally 中恢复 MDC；其他 Executor 是否需要业务身份传播，要按调用路径分别判断。

这些池不能分别独立估算容量。32 条 SSE Connection 线程不代表 32 个模型调用，16 个 Answer I/O 线程也可能同时争用 20 个数据库连接或同一个 Provider 配额。压测至少同时观察 Active、Queue、Rejected、数据库 Pending、Provider 429、SSE Overflow 和端到端 P99。

真实来源：[RealtimeExecutorConfig.java](../../backend/src/main/java/com/noteweave/config/RealtimeExecutorConfig.java)、[SchedulingConfiguration.java](../../backend/src/main/java/com/noteweave/config/SchedulingConfiguration.java)。

## 5. Redis、配额与缓存

### 5.1 Redis 客户端与本地部署

| 设置 | 当前值 |
|---|---:|
| Connect Timeout | 500 ms |
| Command Timeout | 750 ms |
| Compose 持久化 | AOF 开启 |
| Compose 认证 | `requirepass` |
| 当前拓扑 | 单 Redis 实例 |

500/750 ms 表示控制平面希望快速识别 Redis 不可用，避免配额、缓存或实时桥接长时间占住线程。Redis 单实例加 AOF 不等于高可用，也不能保证最近写入绝不丢失。缓存、配额租约与 SSE Replay 对 Redis 丢失的影响不同，必须分别定义降级。

### 5.2 Workload 配额

| 设置 | 分布式 Redis 路径 | 本地回退路径 |
|---|---:|---:|
| Rate Capacity | 20 | 5 |
| Refill | 20/分钟 | 5/分钟 |
| Concurrency Limit | 4 | 1 |
| Lease | 300 秒 | 同一 Lease |
| Local Fallback | 默认关闭 | 生产 Guard 强制关闭 |

Rate Key 按 Workspace、Actor、Workload 约束到达速率；Concurrency Key 按 Workspace、Workload 约束在途任务。令牌桶容量 20 允许短时突发，补充速率约每 3 秒 1 个 Token。并发 4 与 Rate 20/分钟不是同一限制。Lease 300 秒需要运行方续租，不能把 4 个并发槽理解成系统总 Worker 数。

### 5.3 缓存 TTL

| Cache | TTL | Jitter 或负缓存 |
|---|---:|---:|
| ACL Positive | 300 秒 | Jitter 60 秒 |
| ACL Negative | 30 秒 | Jitter 60 秒应用于缓存策略 |
| Source Catalog | 120 秒 | Jitter 30 秒 |
| Wiki Page Version | 600 秒 | Jitter 120 秒 |
| Memory Compiled Pack | 180 秒 | Jitter 30 秒 |

ACL 缓存还带 `acl_version`，权限变化不依赖等待 300 秒自然过期。负缓存只保留 30 秒，降低不存在资源长期陈旧的风险。Jitter 用于分散失效时间，不是数据新鲜度指标。命中率提高必须同时检查回源、版本不匹配、撤权和跨 Scope 隔离。

真实来源：[application.yml](../../backend/src/main/resources/application.yml)、[WorkloadQuotaService.java](../../backend/src/main/java/com/noteweave/quota/WorkloadQuotaService.java)。

## 6. Embedding、Rerank 与 LLM

| 能力 | 默认是否启用 | 批次或输入 | Timeout | Attempts |
|---|---|---|---:|---:|
| Embedding Query | 否 | 1024 维，最多 12000 字符 | 10 秒 | 最多 3 次 |
| Embedding Document | 否 | Batch 32 | 60 秒 | 最多 3 次 |
| Rerank | 否 | Batch 80，每文档最多 1800 字符 | 20 秒 | 最多 3 次 |
| Backend LLM | 否 | 模型由环境变量指定 | 60 秒 | 客户端路径另行控制 |
| Research LLM | 需要配置 | 输入最多 120000 字符，安全余量 8000 | 60 秒 | 最多 3 次，总调用上限 64 |
| Artifact LLM | 需要配置 | 模型由环境变量指定 | 60 秒 | 按 Worker 调用路径处理 |

Compose 默认也关闭 Backend Embedding、Rerank 与 LLM。QA MySQL Fallback 在 `application.yml` 默认关闭，但本地 Compose App Profile 默认打开；Production Guard 禁止生产启用这个回退。面试时必须区分“实现了可配置链路”和“当前 Compose 默认实际调用模型”。

Attempts 不能直接乘 Timeout 当作总 Deadline，因为调用可能提前失败并退避，也可能多个层次各自重试。更安全的口径是明确单次预算、最大次数和调用链总预算，再用故障注入确认最坏时间。Research 总调用上限 64 是成本熔断保护，不代表一次任务正常会调用 64 次。

真实来源：[application.yml](../../backend/src/main/resources/application.yml)、[Research Settings](../../workers/research-worker/app/config.py)、[Artifact Settings](../../workers/artifact-worker/app/config.py)。

## 7. Kafka 与 Outbox

### 7.1 Kafka 客户端

| 设置 | 当前值 |
|---|---|
| Producer Acks | `all` |
| Publish Wait | 最多 10 秒 |
| Consumer Auto Commit | 关闭 |
| Ack Mode | Record |
| Offset Reset | earliest |
| Consumer Retry | 原始投递后最多 2 次重试 |
| Retry Delay | 约 1 秒、2 秒，各加最多 20% Jitter |
| 失败终态 | 发布到源 Topic 的 `.DLT` |
| Compose Broker | 单节点 KRaft，SASL_PLAINTEXT |

`acks=all` 在当前单 Broker Compose 中不提供多副本容灾。Record Ack 与关闭 Auto Commit 让 Offset 更接近单条业务完成，但 Consumer 仍可能在业务提交后、Offset 提交前崩溃，因此必须幂等。当前自动创建的 Java DLT Topic 是 1 Partition、1 Replica，也只适合本地环境。

### 7.2 Outbox

| 设置 | 当前值 |
|---|---:|
| Dispatch Tick | 1000 ms |
| 单次 Candidate Batch | 50 |
| 普通 Lease | 1 分钟 |
| Artifact Callback Lease | 70 分钟 |
| Max Attempts | 5 |
| 单次 Kafka Publish Wait | 10 秒 |
| Retry Backoff | 指数增长，60 秒封顶，最多约 20% Jitter |
| Research Command Dispatch | 1000 ms，Batch 25 |

普通 Lease 覆盖短 Kafka 发布，Artifact 70 分钟 Lease 覆盖 Worker 最长一小时执行，并依靠进度 Callback 续租。最后一次 Callback Lease 到期后有专门 Sweep 转入 Dead Letter，避免永久卡在 PROCESSING。Batch 50、Tick 1 秒只能给出理论候选扫描上限，真实完成速率仍受 Kafka 10 秒等待、数据库、任务类型和失败重试约束。

真实来源：[KafkaConfig.java](../../backend/src/main/java/com/noteweave/infra/KafkaConfig.java)、[OutboxDispatchPolicy.java](../../backend/src/main/java/com/noteweave/infra/outbox/OutboxDispatchPolicy.java)、[TaskOutboxDispatcherService.java](../../backend/src/main/java/com/noteweave/infra/TaskOutboxDispatcherService.java)。

## 8. Research Worker 的 Lease、并发和成本保护

| 设置 | 当前默认或 Compose 值 |
|---|---:|
| Execution Mode | `INCREMENTAL_V1` |
| Agent Max Concurrency | 1 |
| Bundle Max Cells | 3 |
| Fetch Max Concurrency | 4 |
| Fetch Timeout | 20 秒 |
| Fetch Retries | 3 |
| Fetch Rate | 4 请求/秒 |
| Task Lease | 60 秒 |
| Heartbeat Interval | 默认由 Lease/4 得到，Compose 明确为 15 秒 |
| Heartbeat Failure Budget | 默认 Interval 的 2 倍，Compose 为 30 秒 |
| Heartbeat Request Timeout | `min(5 秒, Interval/2)`，Compose 为 5 秒 |
| Completion Attempts | 3 |
| Kafka Consume Attempts | 3 |
| Drain Grace | 30 秒 |
| Drain Poll | 500 ms |

校验器要求 Heartbeat Interval 小于 Lease 的三分之一，Failure Budget 加一个 Interval 后仍小于 Lease，Heartbeat Request Timeout 小于 Interval。当前 `60/15/30/5` 满足：15 小于 20，30 加 15 小于 60，5 小于 15。这个关系给续租失败留出停止工作的安全窗口。

Agent Max Concurrency 为 1，表示默认运行路径有意保持有界顺序执行；Fetch Concurrency 为 4，只并发网络取证，不代表四个 Agent 分支并行提交状态。面试时不能把编译期 DAG 描述成运行时大规模并行 Ready Queue。提高 Agent 并发前要测 Provider TPM、任务状态竞争、数据库连接、合并正确性和单位成功成本。

真实来源：[Research Settings](../../workers/research-worker/app/config.py)、[agent_kafka_consumer.py](../../workers/research-worker/app/agent_kafka_consumer.py)、[docker-compose.yml](../../docker-compose.yml)。

## 9. SSE、Replay 与 Answer Lease

| 设置 | 当前值 |
|---|---:|
| 进程内 Replay Capacity | 512 个事件，代码最少 32 |
| Subscriber Queue | 64 个事件，代码最少 8 |
| Redis Stream Max Length | 512 |
| Redis Stream TTL | 600 秒，代码最少 60 秒 |
| Follow Timeout | 125 秒 |
| Answer Stream Lease | 150 秒 |
| Lease Renewal | 每 45 秒 |
| Delta Batch | 最多 512 字符或 30 ms |

Subscriber Queue 满时，如果队尾与新事件都是 `answer.delta`，系统先合并 Delta；无法合并则记录 Overflow 并关闭慢 Subscriber。Replay Capacity 512 是事件条数，不是字符数或秒数；Delta 经过 512 字符/30 ms 合并后，实际可回放文本量取决于输出节奏。Redis Stream 600 秒 TTL 提供多实例短期桥接，最终回答和业务终态仍由 MySQL 保存。

Answer Lease 150 秒、每 45 秒续租，正常情况下有三次以上续租机会。续租失败会把本地 Lease 标记无效，旧生成者不能继续确认终态。125 秒 Follow Timeout 是单次跟随连接预算，不代表模型任务总时长。SSE 容量要分别压测连接数、事件速率、慢消费者和断线重连。

真实来源：[SessionEventMux.java](../../backend/src/main/java/com/noteweave/answer/SessionEventMux.java)、[RedisAnswerRealtimeBridge.java](../../backend/src/main/java/com/noteweave/infra/RedisAnswerRealtimeBridge.java)、[AnswerRunService.java](../../backend/src/main/java/com/noteweave/answer/AnswerRunService.java)、[BufferedAnswerDeltaEmitter.java](../../backend/src/main/java/com/noteweave/answer/BufferedAnswerDeltaEmitter.java)。

## 11. Rollout Guard 的当前门槛

Backend 代码默认启用 Research Rollout Guard，窗口 15 分钟，最小任务样本 10，Terminal Failure 与 Delivery Failure 上限均为 20%，Rejected Merge 上限为 30%。但 Compose App Profile 把 Guard 默认覆盖为关闭。因此可以说“代码实现了默认门槛，当前 Compose 演示环境没有默认开启”，不能说当前部署已经由这些指标自动拦截发布。

最小样本 10 很小，只适合早期保护和确定性回归，不足以发现低频失败。真正生产灰度要按基线错误率、最小可检测差异和业务切片计算样本量，并同时观察延迟、成本与安全拒绝。

## 12. 面试中如何解释这些数字

一个参数至少讲四件事：约束对象、失败时表现、相邻参数关系、调优证据。以 Answer I/O 的 `4/16/64` 为例，4 个 Core 承担常态 I/O，突发时最多扩到 16，之后最多排队 64，队列继续增长时 AbortPolicy 显式拒绝。它与 Hikari 20、LLM 60 秒和配额并发 4 共同作用，不能单独推出 QPS。调优要同时看 Active、Queue、Rejected、TTFT、数据库 Pending 和 Provider 429。

以 Research `Lease 60/Heartbeat 15/Failure Budget 30/Request Timeout 5` 为例，参数关系保证续租失败后有时间停止 Provider 工作，旧 Worker 晚到再由 Fencing 拒绝。若把 Lease 缩短到 20 秒而不调整 Heartbeat 和网络 P99，正常抖动会频繁接管；若把 Lease 拉长到 10 分钟，崩溃恢复变慢。调优依据是 Heartbeat 延迟分布、GC/进程暂停、网络故障和可接受恢复时间。

以缓存 ACL `300/30/60` 为例，正缓存 5 分钟降低数据库读，负缓存 30 秒缩短不存在对象的陈旧窗口，60 秒 Jitter 分散失效，`acl_version` 保证撤权不等自然过期。面试中应主动说 TTL 是性能策略，版本与真源校验才是安全正确性。

## 13. 参数变更的验证清单

- 调线程池时，同时压测队列、拒绝、数据库连接、Provider 配额和关闭行为。
- 调 Hikari 时，观察 MySQL CPU、锁等待、事务时间和后台任务，不只看 Pending。
- 调 Redis Timeout 时，注入连接拒绝、慢命令和主从切换，验证 Fail Open/Closed 策略。
- 调缓存 TTL 时，测试撤权、旧值晚回填、批量失效和数据库回源峰值。
- 调 Kafka Retry 或 Outbox Batch 时，测试重复、DLT、下游过载和积压恢复。
- 调 Lease/Heartbeat 时，暂停进程、制造网络超时和旧 Owner 晚到，验证 Fencing。
- 调 Embedding/Rerank Batch 时，比较吞吐、P99、内存、Provider 限额和检索质量。
- 调 SSE Buffer 时，覆盖慢消费者、Cursor Expired、Delta 合并和 Redis 故障。
- 调 Token 生命周期时，验证 Rotation、Replay、Logout、撤销和日志脱敏。

配置审查的最终问题不是“这个数字看起来合不合理”，而是“它保护哪个资源，超过后系统怎样失败，指标能否提前看到，改动后用什么证据验收”。

## 14. 参数对应的生产消费点

环境变量只有被生产代码读取并影响控制流，才算有效设置。下面列出面试最常用参数的消费位置。

| 参数组 | 配置消费类或方法 | 参数怎样影响运行 | 失败表现 |
|---|---|---|---|
| Hikari | Spring Datasource 与全部 `JdbcTemplate` Service | Max 20 限制同时借出的连接，Connection Timeout 30 秒限制等待 | Pending 上升后请求或后台任务获取连接超时 |
| Answer/SSE Executor | `RealtimeExecutorConfig` 各 Bean 方法 | Core、Max、Queue 决定创建、排队和扩容顺序，统一使用 `AbortPolicy` | 队列与线程均满时显式拒绝；Connection 与 Bridge 为零队列 |
| Redis Timeout | `RedisConfig` | Connect 500 ms、Command 750 ms 限制缓存、配额与 Bridge 等待 | 缓存可按领域回源，配额生产 Fail-closed，Bridge 记录降级 |
| Quota | `WorkloadQuotaService.requireRate()/acquireLease()/renewLease()` | Token Bucket 与 Sorted Set Lease 由 Redis Lua 原子更新 | 返回 429、Lease Lost 或 Redis 不可用错误 |
