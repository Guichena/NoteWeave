# 业务指标埋点与简历数字生成手册

> 本文是全项目数字口径的权威入口。默认讲第 15 节的 4 到 5 分钟回答，论文与产品对照看第 16 节，数字真实性和 Benchmark 可比性分别看第 17、18 节。其他功能文档出现的理想百分比与样本数都服从本文标签和 Manifest 规则。

> 定位：[全项目指标体系](07-全项目指标体系与面试计算手册.md)回答“应该看什么”，本文回答“数字怎样真正生产出来”。目标是让简历上的每个百分比都能追溯到 SQL、Gold Set、实验 Manifest 和失败样本，而不是凭印象写一个看起来漂亮的数。

## 1. 数字的四种来源必须分开

| 类型 | 数据来源 | 能说明什么 | 不能混成什么 |
| --- | --- | --- | --- |
| 业务结果 | 用户事件、采纳和行为窗口 | 是否为用户创造价值 | 不能用 Fixture 冒充 |
| 离线质量 | 冻结 Gold Set、策略和评分脚本 | 特定任务分布下的质量 | 不能推出线上留存 |
| 故障演练 | 可控宕机、重复、延迟和脏数据注入 | 不变量与恢复能力 | 不能当日常成功率 |
| 容量压测 | 固定硬件、数据规模、并发模型 | 给定环境的吞吐和尾延迟 | 不能由线程池配置推算 |

面试官最反感的不是数字小，而是分母和场景说不清。每个数字至少要回答：谁产生、何时产生、分子分母、排除项、样本数、版本和失败样本。

## 2. 一条数字的生产链

```text
业务问题
  -> 指标定义
  -> 事件或表字段
  -> 数据清洗与切片
  -> Baseline / Treatment
  -> 评分脚本
  -> 置信区间与失败样本
  -> Experiment Manifest
  -> 简历句子
  -> 面试追问材料
```

任何一步缺失，数字只能降级为演练假设。

## 3. 指标 Manifest 模板

每次实验保存一份 Markdown 或 JSON Manifest：

```yaml
experiment_id: rag-qa-2026-08-01
claim: Hybrid + RRF + Rerank improves evidence recall over BM25
commit: <git-sha>
dataset: qa-gold-v3
dataset_size: 160
snapshot_cutoff: 2026-07-31T00:00:00Z
workspace_fixture: school-course-fixture-v2
baseline:
  retrieval: bm25
treatment:
  retrieval: hybrid
  fusion: weighted-rrf-v2
  reranker: provider-model-version
constants:
  top_k: 10
  chunk_policy: chunk-v4
  permission_policy: workspace-acl-v2
metrics:
  - recall_at_10
  - ndcg_at_10
  - citation_support
  - p95_latency_ms
  - cost_per_success
exclusions:
  - corrupted fixture source
scoring_script: scripts/eval/qa_eval.ps1
reviewer: self-review + frozen judge version
result_artifact: reports/qa-gold-v3-result.json
limitations:
  - single-domain school material
  - not production traffic
```

Manifest 的作用不是形式化，而是防止两个月后忘记当时更换过 Chunk、模型或 Gold 标签。

## 4. 总体业务指标从哪里来

### 4.1 Workspace 激活

推荐定义：新建 Workspace 在 7 天内至少有一个 READY Source，并完成一次通过业务校验的 Answer、Research 或 Artifact。

```sql
with first_value as (
  select w.id as workspace_id,
         min(case when s.status = 'READY' then s.updated_at end) as first_source_ready_at,
         min(case when ar.status = 'SUCCEEDED' then ar.finished_at end) as first_answer_at
  from workspace w
  left join source s on s.workspace_id = w.id
  left join answer_run ar on ar.workspace_id = w.id
  where w.created_at >= :cohort_start and w.created_at < :cohort_end
  group by w.id
)
select avg(case when first_source_ready_at is not null
                      and first_answer_at is not null then 1.0 else 0.0 end) as activation_rate
from first_value;
```

当前还缺少统一的 Validator Passed 和 Research/Artifact First Value Event，因此上线前应补 `business_value_event(workspace_id, actor_id, capability, run_id, event_type, occurred_at)`，否则只能用终态做代理。

### 4.2 Time to First Value

`首个业务有效事件时间 - Workspace.created_at`，报告 P50/P95。不要从登录时间算，也不要把 Source Ready 当成最终价值。学校场景可以分别报告“首次资料可检索”和“首次有效答案”。

### 4.3 采纳率与人工节省

需要显式事件：`RESULT_ACCEPTED`、`RESULT_REGENERATED`、`RESULT_EDITED`、`RESULT_SAVED_AS_SOURCE`。建议把用户主动保存为 Source、显式导出或确认写回作为强采纳，“点赞”作为弱采纳；自动保存、系统重试、强制课程流程和演示账号不进入分子。采纳率要冻结观察窗口与撤销窗口，例如完成后 24 小时内主动采纳，且随后 24 小时没有删除、撤销或立即重跑；分母只包含界面与权限上确实存在采纳机会的完成结果。人工节省通过同任务人工 Baseline 的中位时长减系统辅助时长计算，不能让用户凭感觉估百分比。

## 5. Source 数据卡

### 5.1 当前可直接计算

资料处理成功率：

```sql
select count(*) as accepted,
       sum(case when status = 'READY' then 1 else 0 end) as ready,
       sum(case when status = 'READY' then 1 else 0 end) / count(*) as ready_rate
from source
where created_at >= :start and created_at < :end;
```

端到端近似耗时：

```sql
select id, workspace_id, source_type,
       timestampdiff(microsecond, created_at, updated_at) / 1000.0 as ready_latency_ms
from source
where status = 'READY'
  and created_at >= :start and created_at < :end;
```

`updated_at` 只能作为近似 ReadyAt，因为后续元数据编辑也会改变它。要形成可信 P95，应补 `source_state_transition` 或单独 `ready_at`。

### 5.2 应补埋点

| Event | 字段 | 用途 |
| --- | --- | --- |
| `UPLOAD_ACCEPTED` | upload、workspace、bytes、mime | 起点和文件分桶 |
| `PARSE_COMPLETED` | source、snapshot、page/chunk、duration | 拆解析耗时 |
| `INDEX_COMPLETED` | snapshot、projection、duration | 拆索引耗时 |
| `SOURCE_READY` | source、snapshot、attempts | 精确 ReadyAt |
| `SOURCE_FAILED` | stage、errorCode、retryable | 失败归因 |
| `SOURCE_DELETED_VISIBLE` | source、committedAt | 在线删除延迟 |
| `SOURCE_PURGED` | source、store、completedAt | 物理清理延迟 |

### 5.3 面试主指标

- `Projection Ready P95/P99`
- `Deadline 内收敛率`
- `解析结构保真`
- `重复投递写放大`
- `删除在线不可见延迟`

## 6. QA Gold Set 与 SQL

### 6.1 Gold Case 至少包含

```text
case_id
workspace_fixture
query
query_type: exact / semantic / multi-hop / unanswerable / conflict / forbidden
allowed_snapshot_ids
gold_evidence_spans
reference_answer
atomic_claims
expected_abstention
```

### 6.2 运行数据

`answer_run` 提供模式、状态、Model、开始、首 Token 和完成时间；`message_revision` 提供 Token 与 Prompt Version；`answer_run_evidence_manifest` 提供冻结证据；`answer_event` 验证流完整性。

```sql
select ar.mode,
       count(*) as runs,
       avg(ar.status = 'SUCCEEDED') as success_rate,
       avg(timestampdiff(microsecond, ar.started_at, ar.first_token_at) / 1000.0) as avg_ttft_ms,
       avg(timestampdiff(microsecond, ar.started_at, ar.finished_at) / 1000.0) as avg_total_ms,
       avg(mr.input_tokens) as avg_input_tokens,
       avg(mr.output_tokens) as avg_output_tokens
from answer_run ar
left join message_revision mr on mr.answer_run_id = ar.id
where ar.created_at >= :start and ar.created_at < :end
group by ar.mode;
```

分位数建议在指标系统或导出后计算，不要用平均值冒充 P95。

### 6.3 必报组合

```text
Recall@10 / nDCG@10
  + Citation Support / Scope Violation
  + P95 / Cost per Successful Answer
```

一个质量主结果配安全和成本护栏，才像真实工程决策。

## 7. Research Gold Set

### 7.1 Case 结构

每个任务应冻结研究 Goal、WorkItem 类型及其必填集合、允许来源、冲突事实、关键 Claim、最低独立来源数、预算和交付格式。比较型任务把方案与评价维度标成 `MATRIX_CELL`；开放调查、时间线和来源审计分别使用自己的类型化验收条件。不要只准备参考报告，否则无法判断“写得不一样但仍正确”的结果。

### 7.2 当前表可计算的运行指标

```sql
select rr.id,
       rr.status,
       count(distinct rat.id) as task_count,
       sum(rat.attempt_count) as total_attempts,
       sum(case when rat.status = 'SUCCEEDED' then 1 else 0 end) as successful_tasks,
       timestampdiff(microsecond, rr.created_at, rr.updated_at) / 1000.0 as elapsed_ms
from research_run rr
left join research_agent_task rat on rat.research_run_id = rr.id
where rr.created_at >= :start and rr.created_at < :end
group by rr.id, rr.status, rr.created_at, rr.updated_at;
```

`updated_at` 同样只是近似终态时间，正式数据应读取 Stage 或明确 TerminalAt。

### 7.3 最值得做的五个 Research 数字

1. Required WorkItem Completion。
2. Citation Support 与 Citation Completeness。
3. Conflict Discovery Recall。
4. Checkpoint Resume Reuse Rate。
5. Verified Claim per 1K Tokens。

`Required WorkItem Completion = 通过类型化验收的必填 WorkItem / 必填 WorkItem`，它是全 Research 主覆盖指标。比较型子集再报告 `Matrix Cell Coverage = 通过 Cell 验收的必填 Cell / 必填 Cell`。两者都要按任务类型和难度做宏平均，不能用更多、更细的 WorkItem 抬高分数。Research 的优势不应只宣传“报告更长”，而应宣传覆盖、证据、恢复和单位有效产出。

### 7.4 故障注入矩阵

| 注入点 | 预期不变量 | 统计结果 |
| --- | --- | --- |
| Claim 后 Worker 退出 | Lease 到期后可重新领取 | Recovery Success、恢复耗时 |
| Provider 成功后 Completion 前退出 | 不重复业务合并，外部调用可能重复 | Merge Duplicate=0、额外调用数 |
| Completion 响应丢失 | 重试返回相同 Receipt | Duplicate Completion Convergence |
| 旧 Worker 晚到 | Fencing 拒绝 | Stale Owner Accepted 必须为 0 |
| Checkpoint 内容截断 | 哈希校验拒绝 Hydrate | Corrupt Snapshot Accepted 必须为 0 |
| Cell 版本冲突 | 不做 Last Write Wins | Conflict Preserved Rate |

## 8. Artifact 数字

当前可从 `artifact_job`、`artifact_job_run`、`artifact_version`、`artifact_file` 和 `worker_callback_receipt` 计算旧 Job 状态、运行状态、版本生成、已创建文件状态、重复回调和修复次数，但不能直接得到严格 File Ready Rate。ArtifactJob 是长期用户意图，再生成和回滚会产生多个 ArtifactRun，因此 Job 状态比例不能作为生成成功率。现有 `artifact_file` 又只覆盖已经创建的文件；某个必需格式连第一轮物化都没开始时没有行，直接对 `af.status` 求平均会把失败从分母排除。Run 再与多条 File 直接 Join，也会让多文件运行重复加权。

推荐的严格接纳完成率先在 ArtifactRun 粒度单独聚合，并使用已经经过统一观察截止点的创建 Cohort。取消、失败和超期未完成留在分母中并另按状态输出；若只查询最近创建的 Run，仍在运行的长任务会造成右删失偏差。下面是迁移后的目标查询形态，当前 `artifact_job_run` 若仍混合生成请求与 ExecutionAttempt，应先完成身份拆分，不能直接把结果写进简历。

```sql
select aj.action_key,
       count(*) as runs,
       sum(ar.status = 'SUCCEEDED') / nullif(count(*), 0) as accepted_completion_rate
from artifact_run ar
join artifact_job aj on aj.id = ar.artifact_job_id
where ar.accepted_at >= :cohort_start
  and ar.accepted_at < :cohort_end
  -- cohort_end 必须早于统一 observation_deadline 至少一个最长业务期限
group by aj.action_key;
```

严格文件口径需要在内容 Contract 通过时就冻结 Delivery Contract，并为每个必需格式创建 `PENDING` Manifest 行。随后以这些义务为分母，而不是以实际生成出的文件为分母。目标查询形态如下，`required` 和 `object_readable` 属于推荐补充字段：

```sql
select aj.action_key,
       count(*) as required_files,
       sum(af.status = 'READY' and af.object_readable = true)
         / nullif(count(*), 0) as file_ready_rate
from artifact_file af
join artifact_version av on av.id = af.artifact_version_id
join artifact_job aj on aj.id = av.artifact_job_id
where af.required = true
  and av.content_contract_status = 'PASS'
  and av.created_at >= :start and av.created_at < :end
group by aj.action_key;
```

真正可宣传的组合：Validator First-pass Yield、Repair 后通过率、Save/Export Success、P95 和单位成功成本。必须按产物类型分桶，PDF、Markdown、PPT 的验证难度不能混在一个平均值里。

## 10. 面试官会怎样追每个数字

### “Recall 提升 8.1 个百分点，样本怎么来的”

回答数据来源、Query 分桶、Gold Span 标注、Snapshot 截止时间和配对实验。若只会说“自己造了 160 道题”，可信度不够。应解释其中多少来自历史资料问法、多少 Hard Negative、多少不可回答和越权用例。

### “为什么 Citation Support 不是模型自评”

先将答案拆为原子 Claim，再判断 Evidence 是否蕴含 Claim。LLM Judge 只做初筛，抽样由冻结 Rubric 人工校准，报告一致率和争议处理。生成模型不能不经校准地自评自证。

### “30/30 恢复是否等于 100% 可用”

不是。它只证明给定注入点和版本下 30 次演练都满足不变量。30/30 的 Wilson 95% 下界仍约为 88.6%，而且未覆盖机房故障和真实 Provider 行为。

### “人工节省 60% 怎么算”

同一类任务先由用户独立完成，再使用系统辅助完成，记录有效工作时长，中位数差除以 Baseline 中位数。要控制熟练度和任务难度，不能让同一个人第二遍做同一道题产生学习效应。

### “为什么 P95 不是平均值”

交互体验由慢请求决定，平均值会掩盖长尾。P95 仍需按文件大小、模型、Query 类型和冷暖缓存切片，否则总体 P95 也会误导。

## 11. 统计最低要求

| 要求 | 最低口径 |
| --- | --- |
| 比例 | 同时报分子、分母和 Wilson 95% CI |
| 策略对比 | 同一 Case 配对，报告绝对百分点差 |
| 排名指标 | 报逐 Case 结果并做配对 Bootstrap |
| 延迟 | P50、P95、P99，注明超时和失败是否进入分母 |
| 成本 | 包含失败、重试、搜索、Rerank 和人工复核 |
| 多次试验 | 冻结调参集与最终测试集，避免在测试集上反复挑参数 |
| LLM Judge | 冻结模型、Prompt、Rubric，并用人工样本校准 |

## 12. 强口径、保守口径和禁止口径

### 强口径

有 Manifest、结果文件和失败样本时，报数据集、样本数、Baseline、绝对提升和护栏代价。

### 保守口径

只有源码和小 Fixture 时，说“建立了可复现评测和门禁，并在 N 个固定 Case 上通过”，主动说明样本不足以证明泛化收益。

### 禁止口径

- 用 4/4 写“准确率 100%”。
- 用线程池 20 推导“支持 20 并发”。
- 用内部 Gold 与 BEIR、GAIA、BrowseComp 分数直接横比。
- 删除失败、超时和拒答案例后再计算成功率。
- 只报相对提升，不报 Baseline 和绝对差。
- 把演练假设讲成学校实际部署数据。

## 13. 第一批补数执行顺序

1. **Source Ready**：补精确 Stage 时间，按格式和大小跑 100 份文件矩阵。
2. **QA Gold v1**：从 4 Case 扩到至少 100 条，优先补能区分 BM25、Hybrid 和 Rerank 的 Hard Query。
3. **Research Gold v1**：先做 30 到 40 条类型化任务，覆盖比较、开放调查、时间线和来源审计，重点标 Required 集合、冲突和最低独立来源。
4. **故障恢复**：固定 6 个注入点，每点至少重复 20 到 30 次，保存不变量结果。
5. **Artifact Validator**：按产物类型各准备正例、可修复和不可修复 Case。
6. **业务事件**：真实试用开始后再采激活、采纳和时间节省，不用离线质量替代。

## 14. 面试前随身卡

每个简历数字只背八项：

```text
业务问题
指标公式
样本来源
Baseline
结果与绝对 Delta
质量/安全/成本护栏
三个 Bad Case
不能推出什么
```

能回答这八项，数字才是项目证据；只能背一个百分比，数字反而会成为面试风险。

## 15. 4 到 5 分钟指标与实验回答

NoteWeave 最初是学校资料服务，最容易写进简历的数字是上传了多少文件、生成了多少字或调用了多少来源，但这些只能证明系统做了工作，不能证明用户得到有效产出。我把数字分成业务结果、离线质量、故障演练和容量压测四类，先确定每类能回答什么，再决定能不能宣传。

业务结果看 Workspace 激活、首次资料可检索、Time to First Value、有效结果采纳和人工工作时间。这里“任务完成”不等于“用户得到价值”。例如 Research 进入 SUCCEEDED，但报告没有被保存、导出或继续编辑，只能算技术终态；保存为 Source、接受 Artifact Version 或完成带引用回答才是更强的采纳信号。人工节省要用同类任务的人工 Baseline 与系统辅助组比较，控制任务难度和学习效应，不能让用户凭感觉填一个百分比。

离线质量按功能建不同 Gold。QA Case 冻结 Query、Source Snapshot、Gold Evidence、不可回答条件和越权干扰，分别计算 Recall@K、nDCG、Citation Support、Faithfulness 和 P95；Research Gold 冻结 WorkItem 类型、必填集合、最低独立来源、冲突事实和交付约束，计算 Required WorkItem Completion、Verified Claim、Citation Support、Conflict Discovery 和单位 Token 产出，比较型子集再计算 Matrix Cell Coverage；Artifact 按 Skill 和文件类型统计 First-pass Yield、Repair Yield、File Ready、采纳和单位成功成本。不能用一个“准确率”把召回、生成、引用和业务接受混在一起。

故障演练回答的是不变量。Worker Claim 后退出，系统能否在 Lease 到期后接管；旧 Worker 晚到，Fencing 是否拒绝；Completion 响应丢失，重试能否返回同一 Receipt；Checkpoint 损坏，哈希是否阻止 Hydrate。30/30 只能说在固定版本、环境和注入点上零失败，不能写成 100% 可用。容量压测同样必须绑定硬件、数据规模、Provider 模式、流量模型、持续时间和质量护栏，不能从线程池或连接池默认值反推 QPS。

每次实验用 Manifest 冻结 Commit、Dataset、Snapshot、Chunk、Index、Model、Prompt、Tool Bundle、Judge、预算、随机种子和评分脚本。Baseline 与 Treatment 跑同一批 Case，报告绝对百分点差，不只报相对提升；比例给分子、分母和 Wilson 区间，排序指标做配对 Bootstrap，延迟包含超时与失败并报 P50/P95/P99。结果文件还要保留切片和 Bad Case，否则面试官问“哪类题变差”时无法解释。

外部论文和产品主要给我指标结构，不给项目背书。BEIR 常用 nDCG@10、Recall@K 和 MRR 比较检索；GAIA、BrowseComp 偏工具使用和难事实定位；DeepResearchBench、ALCE、LiveDRBench 更关注报告、Claim 和 Citation；STORM 公开的是其 FreshWiki 协议下的组织性和覆盖变化；GPT Researcher README 常用来源数、报告长度、耗时和单次成本宣传；向量数据库常用 Recall、QPS 和 Latency。NoteWeave 可以沿用这些维度，但只有在相同 Benchmark、检索快照、模型、工具权限、预算和 Judge 下复现，才谈横向分数。内部学校 Gold 更适合证明功能取舍，不能宣称达到某论文或厂商水平。

最终简历只选一到两个主结果，并主动带护栏。例如 RAG 报 Recall@10 的绝对提升，同时报 nDCG、Citation Support 和 P95 代价；Research 报 Required WorkItem Completion，同时报 Citation Support、恢复和单位成功成本，只有比较型任务才补 Matrix Cell Coverage；Artifact 报 First-pass Yield 和 Repair Yield，同时报未修复样本。当前文档中的 160 条 QA、60 条 Research 和具体百分比都标为演练假设，只有生成对应 Manifest、原始结果和失败样本后才能换成强口径。现阶段可说已经建立指标契约、固定小规模回放和补数方案，不能把理想数据卡讲成学校真实线上成绩。

## 16. 论文、公司和类似产品都在宣传什么

| 对象 | 常见公开数字 | 它真正测量什么 | NoteWeave 可对齐的口径 | 不能直接比较的原因 |
| --- | --- | --- | --- | --- |
| BEIR 等检索 Benchmark | nDCG@10、Recall@K、MRR | 固定语料下的检索排序 | QA/Note/Wiki 分场景 Recall、nDCG、P95 | 语料、Query、模型和过滤条件不同 |
| 向量库/搜索产品 | Recall、QPS、Latency、资源成本 | 指定硬件和索引参数的性能质量平衡 | 固定硬件下的 Retrieval Recall/P95/QPS | Shard、维度、索引和数据分布不同 |
| Rerank Provider | nDCG/MRR Lift、多语言、吞吐 | 相对某 Baseline 的排序改善 | BM25/Hybrid 后的配对 Rerank Lift 与成本 | Candidate Set 和模型版本不同 |
| GAIA/BrowseComp | 任务正确率、难事实定位 | 工具使用、浏览和短答案核验 | Research 工具能力的外部补充测试 | 不覆盖长报告、Citation 和恢复 |
| DeepResearchBench/ALCE | 报告质量、Citation Accuracy/Completeness | 长文研究与引用 | Research Cell、Claim、Citation 分层评测 | 任务域和 Judge 协议不同 |
| LiveDRBench | Claim Precision/Recall/F1 | 高 Fan-out Claim 发现 | Verified Claim P/R/F1 与来源覆盖 | 不代表最终文风、学校权限和 SLO |
| STORM | 组织性、主题覆盖、用户采用度 | 多视角预写作与大纲 | Matrix/Perspective Discovery 消融 | 论文结果不能迁移到内部 Gold |
| GPT Researcher 等产品 | 来源数、报告长度、耗时、单次成本 | 输出规模、等待和价格 | 独立来源、Supported Claim、P95、Cost/Run | 产品自报、模型和搜索 Provider 不同 |
| Agent/Artifact 产品 | 任务成功、格式通过、修复、导出 | 产物能否交付 | First-pass Yield、Repair Yield、Accepted Version | Skill 和验证规则不一致 |

行业宣传通常偏向三类容易理解的数字：更多来源、更快生成、更低单次价格。项目面试要再补一层有效性。来源数按独立 Lineage 去重，并报告有多少 Claim 被支持；报告长度配 Citation Completeness 和冗余率；单次价格改为每个 Successful Run、Verified Claim 或 Accepted Artifact 的成本。数字仍然好懂，但不容易被追问击穿。

## 17. 重点知识点：怎样证明一个简历数字不是编的

### 3 分钟回答

一个可信数字不是从结果表开始，而是从业务问题开始。假设要证明 Hybrid + RRF 改善资料问答，我先定义它应该影响 Evidence Recall 和排序，而不是直接承诺用户留存。然后冻结学校课程资料 Snapshot 和分层 Query，Gold 标注正确 Evidence、不可回答条件和越权干扰；Baseline 与 Treatment 使用同一 Case、同一模型、同一 Top K 和同一权限策略，只改变检索方案。

实验结果保存逐 Case 命中、排序、延迟、Token 和失败原因。Recall@10 从 84.4% 到 92.5% 应表述为绝对提升 8.1 个百分点；同时报告样本量、Wilson 或 Bootstrap 区间、nDCG、Citation Support 和 P95。若延迟增加 660 ms，就把它作为代价写出来。只展示整体平均会掩盖多跳、不可回答或长文档 Case 的退化，所以还要按 Query 类型、文件大小、语言和冷暖缓存切片。

这些信息由 Manifest 绑定到 Commit、Dataset、Snapshot、Chunk、Index、Model、Prompt、Judge、预算、脚本和结果文件哈希。面试时不需要展示完整报告，但必须能说出三个 Bad Case：哪些题没有改善，为什么失败，是 Gold 标注问题、召回问题、Rerank 问题还是生成问题。数字经过这条链路才能从“理想包装”升级为可复现证据。

如果目前只有源码和小 Fixture，使用保守口径：“建立了分层 Gold、指标契约与固定回放，当前样本用于保护机制，完整收益待扩大数据后验证。”这比把 4/4 写成 100% 更可信。包装可以选择更有亮点的指标和故事，但不能改分母、删除失败样本或把演练值改成线上实测。

### 二阶追问：Manifest 能防止造假吗

它不能阻止故意造假，但能让版本、数据、参数和结果互相校验，降低无意选择性报告。更强做法是结果文件内容寻址、脚本自动生成摘要、保留失败样本，并由另一人复核 Gold 与随机样本。

### 二阶追问：为什么一定报绝对提升

从 1% 到 2% 可以说相对提升 100%，但业务上只增加 1 个百分点。绝对差让 Baseline 清晰；必要时同时报相对变化，但不能只选看起来更大的写法。

## 18. 重点知识点：为什么内部 Gold 不能和公开 Benchmark 直接横比

### 3 分钟回答

指标名称相同不代表实验相同。两个系统都报 Recall@10，但一个使用公开 Web、一个使用课程私有资料，一个允许实时搜索、一个冻结 Snapshot，Query 难度、相关性标注、过滤条件、Embedding、索引参数和 K 都不同，分数没有可比性。Research 的差异更大：BrowseComp 主要是难事实短答案，DeepResearchBench 看长报告和 Citation，LiveDRBench 看 Claim 发现，不能合成一个“行业 Research 分数”。

真正横比至少固定 Benchmark Version、题目切片、Source Snapshot、模型、Prompt、工具权限、最大调用数、时间预算、费用预算、Judge 和评分脚本。Live Web 还受时间、地区和搜索结果变化影响，应区分 Frozen/Retro Search 与 Live Search。厂商 README 的来源数、耗时和成本是产品方在特定配置下的自报，只能作为宣传维度参考。

内部学校 Gold 的价值是贴近项目业务：它可以标注课程 Workspace 权限、资料版本、类型化必填 WorkItem、比较型 Cell、冲突事实、可拒答条件和 Artifact 格式。这些恰好是公开 Benchmark 不覆盖的。面试中可以说“参考 BEIR 的检索指标、ALCE 的 Citation 评价、LiveDRBench 的 Claim P/R/F1，并在学校场景建立内部 Gold”，不能说“内部 92% 高于某 Benchmark 的 70%，所以达到业界领先”。

更完整的证据分三层：内部 Gold 证明功能取舍；公开 Benchmark 同协议复现证明外部可比能力；真实用户数据证明采纳、节省时间与 SLO。三层可以互相补充，不能互相替代。

### 二阶追问：模型或搜索结果更新后历史分数还有效吗

只对原 Manifest 有效。模型、Index、Prompt、Provider 或 Source Snapshot 变化都要生成新实验身份。历史结果保留用于回归，不覆盖旧报告；Live Search 需要保存可合法保存的检索轨迹或至少记录时间与来源 Manifest。

### 二阶追问：能否只跑公开 Benchmark，不做内部 Gold

不能。公开 Benchmark 不知道 Workspace ACL、资料版本、学校任务结构和 Artifact 契约。它适合展示通用能力和外部可比性，内部 Gold 才能验证产品是否解决自己的问题。

## 19. 评测与数字的二阶追问

### Gold Set 是谁标的，如何控制主观性

先把答案拆成 Gold Evidence、原子 Claim、必填字段和允许拒答条件。高风险 Case 双人独立标注，记录分歧与裁决；普通 Case 抽样复核。不能让同一个生成模型同时产出答案、生成 Gold 和担任最终 Judge。

### LLM Judge 与人工不一致怎么办

先在人工校准集上计算 Judge 对 Supported/Unsupported 的 Precision、Recall 和混淆矩阵，检查分歧集中在哪类 Claim。Judge 适合批量初筛时就保留人工抽查；发布门禁优先使用可确定验证的 Schema、Citation Span、单位、日期和权限不变量。升级 Judge 后重新校准，不能把新旧分数直接拼接。

### 为什么“报告使用了 20 个来源”不一定是亮点

多个 URL 可能来自同一上游转载，来源多也可能只有少量与 Claim 相关。按 Source Lineage 去重，报告独立来源数、有效 Citation 数、Supported Claim、来源集中度和冗余成本。来源更多只在覆盖提升且质量、延迟和成本护栏可接受时有价值。

### 用户采纳率为什么可能误导

默认保存、教师强制要求或无法找到拒绝按钮都会抬高采纳率。区分显式接受、保存为 Source、导出、继续编辑和默认保留，并观察后续修改与删除窗口。采纳说明用户行为，不自动说明事实正确。

### 样本数达到多少才够

没有统一数字。比例指标按预期差异和置信区间宽度做功效分析；稀有安全事件使用对抗用例和零容忍门禁；复杂 Research 可以先用 30 到 50 个高信息 Case 做配对消融，再逐步扩大。样本选择和分层比追求一个整齐数量更重要。

### 指标提升但用户投诉变多，信哪个

先检查离线分布是否覆盖真实 Query、指标是否允许错误降级、延迟和拒答是否进入护栏。离线 Recall 提升可能伴随无关 Evidence、回答变长或 P99 恶化。用户投诉是分布偏移或漏指标的证据，不应被离线总分压掉；补线上失败样本回 Gold，但保持训练集与最终测试集分离。
