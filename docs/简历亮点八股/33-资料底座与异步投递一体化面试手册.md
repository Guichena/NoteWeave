# 资料底座与异步投递一体化面试手册

> 这篇把事件驱动资料底座的架构、演进、Outbox、Kafka、Claim、版本投影、故障案例和指标合并在一个入口。它是 QA、Note、Wiki、Research 和 Artifact 的共同基础。

## 1. 主回答

资料上传不是一个接口把文件存进 MinIO 就结束了。用户真正需要的是：文件可解析、Source Snapshot 可追溯、Chunk/Window 可重建、检索投影最终收敛、删除和权限变化能传播，而且解析失败不能卡住整个请求线程。

项目采用 MySQL 业务真源、MinIO 对象存储、Kafka 异步命令和 Elasticsearch 可重建投影。事务内提交 Source 或 Snapshot 以及 Outbox，Dispatcher 领取后投递解析、索引和清理任务。每个阶段有明确业务状态，Worker 回调带幂等键，旧 Dispatcher 和重复消息不能把已完成 Source 改回错误状态。

## 2. 从同步上传到可重建资料底座

| 阶段 | 方案 | 问题 | 当前设计 |
| --- | --- | --- | --- |
| V0 | 请求线程同步解析和索引 | 大文件阻塞，超时后结果未知 | 上传与处理拆开 |
| V1 | MySQL 写完后直接发 Kafka | DB 成功、消息失败导致任务丢失 | Transactional Outbox |
| V2 | 一个 processing 布尔值 | 解析、索引、清理状态互相覆盖 | 阶段状态和终态语义 |
| V3 | 投影写成功就算完成 | 业务真源和投影版本可能错位 | Snapshot、版本和质量回执 |
| V4 | 失败任务直接重试 | 重复处理、旧 Worker 晚到 | Claim Token、Lease、Fencing、幂等 |
| V5 | 删除只删对象 | 搜索、缓存、派生产物残留 | 可见删除和物理清理分离 |

## 3. 核心数据模型

```text
FileObject
  -> DocumentUpload
  -> Source
       -> SourceSnapshot(version, sha256, parse/index status)
            -> SourceChunk
                 -> SourceWindow
            -> Retrieval Projection
  -> Outbox / Task / Callback Receipt
```

| 对象 | 作用 |
| --- | --- |
| FileObject | Workspace 内按 SHA 去重的原始对象 |
| DocumentUpload | 分片上传和接收状态 |
| Source | 用户可见资料逻辑对象 |
| SourceSnapshot | 不可变版本、解析和索引状态 |
| Chunk/Window | 可重建的文本投影和连续阅读窗口 |
| Outbox | 事务提交后的可靠异步命令 |
| Task/Lease | 处理阶段的领取、续租和重试 |
| Callback Receipt | Worker 回调幂等和结果绑定 |

MySQL 保存业务状态和版本，MinIO 保存对象，Elasticsearch、向量索引、Redis 和缓存都属于投影。投影损坏时应该从 Source Snapshot 重建，不能反向覆盖业务真源。

## 4. 正常链路

1. 上传接口校验 Workspace、大小、Mime、分片和对象摘要。
2. 文件完成后创建或复用 FileObject，生成 Source 和初始 Snapshot。
3. 事务同时写业务状态和 Outbox，不在事务里等待解析或索引。
4. Dispatcher 领取 Outbox，按阶段投递 Kafka Task。
5. Worker 解析文本、Markdown、JSON、CSV 和文本型 PDF，生成 Chunk/Window。
6. Projection Worker 更新全文或向量投影，并返回版本和质量信息。
7. Host 通过条件更新推进业务终态，发布 Source Ready 事件。
8. QA、Note、Wiki 和 Research 只读取当前 Workspace 允许的 Snapshot。

## 5. 为什么 Outbox、Kafka 和 DB 状态要分工

Outbox 解决“业务提交成功但消息没发出去”，Kafka 解决异步缓冲、重试和消费者解耦，业务状态解决用户查询和恢复。它们不提供跨 MySQL、MinIO、Elasticsearch 的分布式强事务，所以系统采用最终一致，并用对账、补偿和重建把不一致窗口变得可见。

Dispatcher Claim 后宕机，Lease 到期可重领；旧实例恢复后用 Fencing 或条件更新被拒绝。消息重复是正常输入，消费者必须按业务幂等键和 Snapshot Version 收敛。

这里的“消费后完成业务再提交 Offset”适用于解析、投影等有界步骤。Artifact 一类分钟到小时级命令不能照搬：Consumer 只校验并按 Command ID 幂等登记 Durable Execution，登记事务提交后即可提交 Offset，Scheduler 再用 Execution Lease 和 Fencing 管理长任务。否则最慢外部调用会决定分区进度，并迫使系统依赖超长 `max.poll.interval`。

## 6. 失败与恢复矩阵

| 失败点 | 正确结果 | 不能做什么 |
| --- | --- | --- |
| DB 已提交，进程在发消息前退出 | Outbox 扫描后补发 | 不能依赖内存队列 |
| Kafka 投递超时 | 允许重试，记录 delivery attempt | 不能直接判定业务失败 |
| Worker 解析成功，回调响应丢失 | 重复回调返回同一 Receipt | 不能重复创建 Snapshot |
| 索引写成功，Finalize 失败 | 投影待对账或补偿 | 不能静默宣称 Ready |
| 新版本处理时旧版本回调 | 条件更新拒绝旧版本 | 不能 Last Write Wins |
| 删除提交但投影未清理 | 在线读取先不可见，清理任务继续 | 不能只删 MinIO |
| 解析能力不支持 DOCX/OCR | 明确失败或能力等待 | 不能宣称所有格式都支持 |

## 7. 删除、权限和版本传播

删除分为两个时间点：业务上立即不可见，物理对象和派生投影异步清理。权限变化、Source 撤销或 Snapshot 过期时，检索查询先按当前 ACL 和版本过滤，后台再清理 ES、向量、缓存、Wiki 关系和派生产物。

这样牺牲了物理清理的即时性，换来用户语义和系统恢复之间的可控边界。高风险读路径在权限服务不可用时关闭访问，不能用缓存旧权限放行。

## 8. 当前解析能力边界

当前能作为已验证能力讲的是文本、Markdown、JSON、CSV 和文本型 PDF。DOCX、HTML、OCR 和复杂扫描件应作为目标扩展或生产待验证能力。面试中可以讲解析器接口、能力路由和失败语义，但不要把设计接口说成已经完成的解析效果。

## 9. 指标

| 指标 | 计算 | 业务意义 |
| --- | --- | --- |
| Upload Accepted Rate | 接收成功上传 / 上传尝试 | 接收面稳定性 |
| Projection Ready P95 | ReadyAt - UploadAcceptedAt | 用户等待时间 |
| Deadline Convergence | 截止时间内正确 Ready / 接受 Snapshot | 最终一致收敛 |
| Outbox Delivery Amplification | Delivery Attempt / 唯一 Outbox 消息 | 重试放大和毒消息 |
| Callback Duplicate Convergence | 重复回调后的业务增量 | 幂等正确性 |
| Projection Rebuild Success | 重建后通过质量门禁的 Snapshot / 重建 Snapshot | 投影可重建性 |
| Delete Visibility Lag | 在线不可见时间 - 删除提交时间 | 用户删除语义 |
| Cleanup Completion Lag | 物理清理完成时间 - 删除提交时间 | 资源回收和合规 |

## 10. 学校场景演练

考试周前，教师批量上传历年试卷和课程讲义。上传接口只负责分片和对象摘要，用户可以先看到处理中状态；Outbox 将解析和索引任务异步投递。一个 PDF 解析失败时，其他资料继续完成，失败文件进入可重试状态。教师删除过期试卷后，QA 立即不再召回，后台再清理对象和索引。

该故事可以用于讲业务价值：上传请求不再被大文件处理拖住，失败隔离到单个 Snapshot，后续 Research 和 Artifact 读取同一不可变资料版本。没有真实监控前，不要补报“考试周处理了多少文件”。

## 11. 面试官连续追问

### 为什么不直接用 Kafka 作为真源

Kafka 适合事件流和重放，不适合直接承载 Workspace 资源归属、当前状态和复杂查询。MySQL 负责业务真源，Kafka 负责异步传递，Snapshot 负责内容版本。

### Outbox 也会重复，怎么保证不重复处理

Outbox 至少一次投递，消费者按业务对象、阶段和版本做幂等。唯一键、条件更新和回执共同保证重复消息不重复创建业务结果。

### ES 与 MySQL 如何强一致

不做强一致承诺。MySQL 提交后通过 Outbox 最终驱动投影，用户查询看到的是带版本和状态的投影。关键链路支持对账、补偿和从 Snapshot 重建。

### 旧 Dispatcher 晚到怎么办

领取时记录 Lease、Owner 和版本，提交时条件带 Claim Token 或 Fencing Token。旧实例即使网络恢复，也只能得到过期或版本冲突结果。

### 为什么删除不直接同步清理所有地方

跨 MySQL、MinIO、ES、缓存和派生产物同步清理容易把用户请求拖成长事务，也会在部分失败时更难恢复。先改变用户可见语义，再异步清理，代价是需要清理任务、审计和延迟指标。

## 12. 简历表达

> 设计来源驱动的异步资料底座，采用不可变 Source Snapshot、Transactional Outbox、Kafka 投递、阶段状态和可重建检索投影；通过 Claim/Lease/Fencing、Worker Callback Receipt 和版本条件更新处理重复消息、旧 Worker 晚到、索引失败和删除传播。

## 13. 4 分钟标准主回答

资料底座的业务终点不是文件上传成功，而是资料能被检索、引用、版本化和删除。同步解析和索引会让大文件占住请求线程，数据库写完后直接发 Kafka 又存在进程退出导致消息丢失。因此上传只负责接收和创建 Source/Snapshot，事务内同时写 Outbox，Dispatcher 再异步投递解析和索引任务。

MySQL 保存 Source、Snapshot、Task 和业务状态，MinIO 保存对象，Elasticsearch 和向量索引都是可重建 Projection。Worker 回调带幂等键和 Snapshot Version，重复消息由唯一约束和条件更新吸收；Claim 后实例退出，Lease 到期重新领取；旧 Worker 晚到则由 Fencing 或版本门禁拒绝。Projection 写成功不等于业务 READY，解析、切片、索引和质量回执全部收敛后才进入用户终态。

删除先提交用户不可见事实，查询层立即按当前状态和 ACL 拒绝，后台再清理对象、全文索引、向量、缓存和派生关系。这样不需要跨 MySQL、MinIO 和 ES 的强事务，但必须有清理任务、对账和残留指标。当前已验证解析能力是文本、Markdown、JSON、CSV 和文本型 PDF，OCR、DOCX 和复杂扫描件不能当作现有能力。

这条链路最重要的指标是 Projection Ready P95、Deadline Convergence、Outbox Lag、重复投递放大、Rebuild Success 和 Delete Visibility Lag。业务上它为 QA、Note、Wiki、Research 和 Artifact 提供同一不可变资料版本。

## 17. 指标公式、行业参照与学校业务价值

资料底座的业务成功不是 Kafka 发出消息，也不是 Worker 返回 `200`，而是某个不可变 Snapshot 在截止时间内变成可检索、可引用、权限正确且可删除的版本。指标要按接收、投递、投影、读取和删除五段计算。

| 链路 | 指标 | 公式 | 不能误解成什么 |
| --- | --- | --- | --- |
| 接收 | Upload Accepted Rate | `创建 Source 与 Snapshot 成功的上传 / 合法上传尝试` | 不代表解析和索引已完成 |
| 投递 | Outbox Oldest Ready Age | `当前时间 - 最老 READY 消息创建时间` | 比消息条数更能反映是否卡住 |
| 投递 | Delivery Amplification | `总投递 Attempt / 唯一业务消息` | 大于 1 不一定是错误，至少一次允许重复 |
| 投影 | Projection Ready P95 | `ReadyAt - UploadAcceptedAt` 的 P95 | 必须注明文件类型、大小和负载 |
| 收敛 | Deadline Convergence | `截止时间内 READY 且版本正确的 Snapshot / 接受 Snapshot` | 不能只看最终有无成功 |
| 重建 | Rebuild Success | `通过结构和质量门禁的重建 Snapshot / 发起重建 Snapshot` | Alias 切换成功不等于质量通过 |
| 删除 | Delete Visibility Lag | `所有在线读取拒绝时间 - 删除提交时间` | 不代表外部对象已物理删除 |
| 删除 | Cleanup Completion Lag | `对象、索引和派生清理完成时间 - 删除提交时间` | 不包括未接入对账的备份系统 |

Deadline Convergence 比“最终成功率”更适合学校场景。教师在上课前十分钟上传材料，课后两小时才索引成功对业务没有意义。统计时要按文本、PDF、CSV、文件大小、页数和考试周负载分桶，同时报告 Dead Letter 和 Degraded Snapshot，不能把超时后成功的任务从分母删除。

`[行业参考]` Transactional Outbox 与 CDC 产品常宣传低延迟传递、至少一次和连接器覆盖，对象存储宣传耐久性与吞吐，搜索和向量产品宣传索引吞吐、Refresh Latency、Recall、QPS 与 P95。资料解析产品还会强调格式覆盖率。NoteWeave 应借鉴这些维度，但真正承重的是“从上传到可用”的端到端截止时间、版本正确率、权限隔离和可重建性，不能拿单组件峰值代替业务链路。外部依据见[资料底座演进取舍](../research/资料底座演进取舍外部依据.md)。

### 面试官问“为什么不用 CDC 直接替代 Outbox”

CDC 能可靠捕获数据库变更，但业务消费者仍需要知道事件类型、聚合身份、Schema Version、幂等键和重放语义。直接读取任意业务表变更会把内部表结构泄漏成事件合同。当前规模用事务内显式 Outbox 更容易审查；当写入吞吐、轮询压力和多下游订阅成为主要问题时，可以用 CDC 传输 Outbox 表，领域事件合同仍然保留。

### 面试官问“怎么证明投影真的可重建”

从冻结的 Source Snapshot 和策略版本创建新 Projection Build，不读取旧索引结果。构建后做文档数、Source/Snapshot 覆盖、重复 Chunk、Scope、向量维度、抽样 Recall 和 Citation 回链门禁，再使用带版本的 Alias Promotion。比较新旧 Projection 的 Query 结果和 Degradation，切换结果未知时先读回 Alias，不盲目重试。只有这些步骤完成，才能说“投影可重建”，备份恢复和跨区域灾备仍需单独演练。

`[演练假设]` 可以准备一张学校数据卡：`N=500` 个混合文件，Deadline Convergence `97.6%`，Projection Ready P95 `42 s`，重复投递放大 `1.08`，重建门禁通过率 `99.2%`，删除在线不可见 P95 `1.4 s`，外部清理完成 P95 `73 s`。这些数字必须绑定硬件、文件分布、并发、Provider 和 Manifest，没有真实回放时只用于解释计算方式。

### 二阶追问：投影已 READY，但用户为什么仍可能搜不到

READY 可能只代表某个 Snapshot 的索引阶段完成。查询还会受到当前 Source 状态、Workspace ACL、Catalog Version、Alias、Query Filter、Embedding Provider 和 Evidence Selection 影响。排查顺序是先确认 MySQL 当前 Snapshot，再看 Catalog 与 Alias，随后看查询过滤和候选，不能只查 Elasticsearch 文档是否存在。
