# 重点知识点三分钟深挖库

> 这篇解决一个准备误区：功能主线讲满 3 分钟，不代表面试官继续追问某个机制时还能讲清楚。下面只收录高频且能体现工程判断的知识点，每节都按“问题、原理、项目实现、替代方案、失败窗口、八股映射”组织，目标是每个重点点位都能独立讲 3 分钟左右。普通 DTO、简单 CRUD 和非核心配置只做速查，不强行扩写。

## 1. 重点等级和训练方式

| 等级 | 内容 | 准备要求 |
| --- | --- | --- |
| L1 核心机制 | Research 状态、RAG 融合、Outbox、Lease/Fencing、SSE、权限和评测 | 每个点独立 3 分钟，至少承接三层追问 |
| L2 重要实现 | DTO、表字段、Controller、缓存 Key、Worker 回调 | 能讲 60 到 90 秒，能指向源码 |
| L3 速查知识 | 普通 CRUD、简单映射、非关键配置 | 记住用途和边界，不占主回答时间 |

L1 的固定口述顺序：先说业务失败，再说原理，再落到 NoteWeave 对象和代码，接着比较替代方案，最后讲一个反例和一个八股追问。面试官打断时停在当前层，不要把整段背完。

## 2. Table-as-State 与 Cell CAS

### 3 分钟标准回答

开放式研究最难的问题不是让模型调用更多工具，而是判断研究是否覆盖完整。对话轨迹只能说明做过哪些动作，不能直接回答“课程比较的维护成本维度是否已经有证据”。所以 Research 用 Matrix 表达实体和维度，用 Cell 表示最小可验收单元。Cell 保存当前版本、覆盖状态、Claim、Evidence 引用和验证结果，研究进度可以按字段统计。

Cell 更新使用 Expected Version 条件更新。Worker 先基于版本 3 生成 Candidate，提交时 Host 只有在数据库仍是版本 3 时才合并为版本 4。两个 Worker 并发更新同一个 Cell，后到者不会覆盖先到者，而是进入冲突或重新计算。这样选择的是乐观并发控制，避免整个研究被长事务和悲观锁绑住。

它的代价是冲突处理复杂，Candidate、Merge 和拒绝原因都要持久化；简单问答不需要 Matrix。与 Todo List 相比，Table-as-State 多了规划成本，却带来 Coverage、Gap、Verifier 和 Resume 的共同语言。与事件溯源相比，Cell 当前状态查询更简单，历史变化用 Trace、Candidate 和版本保留，不把所有业务读取都变成事件重放。

### 延伸追问

1. **为什么不用悲观锁**：研究任务包含网络调用，不能把数据库锁持有到模型返回；乐观锁让外部调用在事务外完成，提交时再竞争。
2. **冲突后一定重试吗**：不一定。若两个候选证据互补，可以进入合并审查；若来源互斥，则应保留冲突并降级结论。
3. **Cell Version 和 Source Version 有什么区别**：Cell Version 是研究状态并发版本，Source Version 是资料内容版本。前者保护写入竞争，后者保护证据对应的内容不漂移。

### 对应八股

MySQL 乐观锁、CAS、MVCC、唯一约束、事务边界、事件溯源、DDD 聚合根、读写分离。

## 3. Candidate 仲裁与 Evidence Qualification

### 3 分钟标准回答

Worker 返回的结果不能直接视为事实。模型可能引用了不在 Workspace 范围内的资料，引用定位可能为空，也可能只是把同一篇转载文章提交了多次。Research 因此把 Candidate 和 Evidence 分开。Evidence 先记录来源身份、Snapshot、定位、摘要和资格状态，Candidate 再引用这些 Evidence 并提出对 Cell 的更新。

Host 的确定性门禁先检查 Workspace、Source Scope、Snapshot、定位格式、Claim Schema、重复引用和 Candidate 的 Base Version。通过后再进行 Local Verifier 和 Global Verifier。Local Verifier 判断单个 Cell 的 Claim 是否被 Evidence 支持，Global Verifier 判断 Matrix 覆盖、跨 Cell 冲突、来源独立性和报告结构。验证失败会产生明确 Reason Code，进入 Repair、冲突审查或拒答。

这种设计没有承诺消灭幻觉，它解决的是错误可见性和结果可追溯性。直接让模型自评成本更低，但验证标准会漂移；只用规则又无法处理语义蕴含。项目采用规则、局部语义验证和全局结构验证三层组合，并把 Gold Set、人工抽样和 Judge 版本纳入评测。这样面试官继续问“凭什么相信 Verifier”时，可以回答 Verifier 也要校准，不是第二个模型说通过就算通过。

### 延伸追问

1. **来源独立性怎样判断**：按 Source Lineage、域名、版本和转载关系聚类，十条转载不能算十个独立来源。
2. **部分支持如何计分**：先把报告拆成原子 Claim，支持、部分支持和不支持分别统计，不能只看引用链接存在。
3. **验证器误杀怎么办**：保留 WARN 和人工复核通道，记录 False Positive，不能把所有不确定结果都静默拒绝。

### 对应八股

数据血缘、Schema 校验、规则引擎、Precision/Recall、LLM Judge 校准、数据质量、幂等和可审计性。

## 4. Checkpoint Hydration 与长任务恢复

### 3 分钟标准回答

长任务失败后最简单的做法是重新提问，但这会重复搜索、重复付费，而且无法证明哪些步骤已经生效。Research Checkpoint 保存的是结构化账本，不是最后一段报告文本。它包括 Wave、Round、Plan Revision、Entity Set Version、预算视图，以及 Task、Candidate、Merge 的高水位、Canonical JSON、内容大小和摘要哈希。

恢复时保持用户的 ResearchRun 身份不变，从指定 Checkpoint 创建新的 ExecutionAttempt，推进 Epoch 和 Fencing Token。Hydrator 恢复已经确认的 WorkItem、Evidence、计划和预算锚点，只重新调度高水位之后的工作。Run 负责用户意图和最终采用，Attempt 负责恢复次数、故障和执行成本；用户改变目标或主动 Fork 时才创建新 Run。若 Checkpoint 哈希或版本不匹配，恢复应拒绝，而不是用部分内容继续跑。

Checkpoint 与日志的区别是，日志记录过程，Checkpoint 记录经过事务确认的业务切面。事件溯源可以提供更细的历史，但恢复和查询成本更高。项目选择结构化快照加高水位，因为 Research 需要快速读取当前状态，同时保留必要的审计信息。当前 Completion 级回执已经落地，所有外部 Search、Read、Model 调用的 Operation Receipt 仍是更强的目标设计。

### 延伸追问

1. **快照写成功后进程退出怎么办**：恢复从 Checkpoint 继续，未被确认的 Task 按状态和高水位重新调度，不能假设外部调用成功。
2. **为什么不从最后一条日志继续**：日志可能跨事务、乱序或缺少外部副作用确认，不能直接作为业务恢复点。
3. **快照太大怎么办**：保存摘要、引用和增量高水位，大对象继续由 Source Snapshot 或对象存储持有。

### 对应八股

Snapshot、Event Sourcing、WAL、事务一致性、快照压缩、增量备份、RPO/RTO、Exactly Once 语义边界。

## 5. Lease、Fencing 与业务效果收敛

### 3 分钟标准回答

分布式任务里“我曾经领取过”不等于“我现在还有提交资格”。Worker Claim 后获得 Lease、Lease Epoch 和单调 Fencing Token。Heartbeat 只能由当前 Worker、当前 Epoch 和 Token 续租。Lease 过期后，新的 Worker 可以领取任务并得到更大的 Token。旧 Worker 如果网络恢复，仍可能拿着旧结果晚到，Host 在提交时校验 Token 和状态条件，拒绝旧 Owner。

幂等键保护的是同一个业务动作不能重复产生结果，Fencing 保护提交者身份已经失效时不能写入。两者不能互相替代。Kafka 和 HTTP 仍可能 At Least Once，项目不承诺端到端 Exactly Once，而是通过唯一约束、条件更新、Callback Receipt 和状态机，让业务最终只出现一个有效结果。

Lease 时间不能随意设大。太短会让正常任务频繁丢租约，太长会延迟故障恢复；应根据 Heartbeat 周期、网络 P99、Worker 处理时间和恢复目标推导。长任务不应只靠无限续租，还要有最大执行时间和取消语义。面试官问锁过期后任务还在写怎么办时，答案必须落到 Fencing，而不是说“重新加锁”。

### 延伸追问

1. **为什么不用 Redis 分布式锁**：Redis 适合短期协调，持久任务状态和提交资格仍需 MySQL 或业务真源确认。
2. **旧 Worker 读到新数据怎么办**：Task Snapshot 冻结输入，提交阶段再校验版本和 Token，避免旧上下文覆盖新状态。
3. **取消和完成竞争怎么办**：用数据库条件迁移仲裁终态，先成功更新者获胜，后到者读取既有结果。

### 对应八股

分布式锁、Lease、Fencing Token、CAS、CAP、At Least Once、幂等、脑裂、时钟漂移和故障检测。

## 6. Hybrid Search、RRF 与 Rerank

### 3 分钟标准回答

QA 同时面对精确术语和自然语言表达。BM25 对课程编号、错误码、专有名词有效，向量检索对同义表达有效。直接把 BM25 分数和向量相似度相加是不稳的，因为分数分布和量纲不同。项目先保留两路候选，再用 Weighted RRF 按排名融合：`RRF(d) = Σ w_i / (k + rank_i(d))`。

RRF 的优点是减少分数校准，缺点是丢失分数间隔信息，因此可以在融合候选上再用 Cross Encoder 或外部 Reranker。Rerank 只判断单条候选与 Query 的相关性，不能解决证据集合重复、子问题覆盖和来源独立性，所以后面还要做 Evidence Selection。完整链路的目标不是选出五条最高分，而是用有限 Token 组成足够支撑答案的证据集合。

参数必须和资源链一起解释。TopK 越大，Recall 可能上升，但 Rerank 调用、内存、Token 和 P95 也上升；Rerank 候选数越大，精度和成本同时增加。正式实验要固定 Chunk Policy、Index Version、Embedding、Reranker、Prompt 和 Gold，报告 Recall、nDCG、Citation Support、P95 和单位成本。当前小 Fixture 只能证明计算器和失败语义。

### 延伸追问

1. **RRF 的 `k` 怎么选**：在开发集上网格搜索，锁定后在测试集只运行一次，观察不同 Query 类型的配对 Delta。
2. **Rerank Provider 超时怎么办**：回退到融合候选，记录降级模式，提高高风险拒答阈值或直接拒答。
3. **为什么不用 Learning to Rank**：数据量和标注成本不足时，RRF 更稳、更容易解释；当有长期点击和人工标签后再评估 LTR。

### 对应八股

BM25、TF-IDF、倒排索引、HNSW、双塔与 Cross Encoder、RRF、Learning to Rank、TopK、尾延迟和缓存。

## 7. Evidence Selection 与 Reading Window

### 3 分钟标准回答

排序完成后直接取 TopK 仍然会出现两个问题：候选可能来自同一段重复内容，或者每条都相关但没有覆盖用户问题的不同子部分。Evidence Selection 是集合级决策，要同时考虑相关性、去重、子问题覆盖、来源独立性、引用资格和 Token Budget。它保护的是“这一组证据能不能共同支撑答案”，不是单条候选分数。

Note 的 Reading Window 是同一个思想在长文场景中的变体。系统先找 Source，再定位 Anchor，然后按标题层级、相邻 Chunk、段落边界和最大字符数扩展。固定前后各取三个 Chunk 简单，但遇到章节切换、表格和代码块就会把无关内容带进上下文。Window 太小会丢前提，太大则增加成本和生成噪声。

QA 的 Selection 偏向覆盖和多样性，Note 的 Window 偏向连续性，Wiki 的图读取偏向关系预算。三者共享证据快照和权限校验，不共享同一个选择器。评测上要分别看 QA 的 Citation Support、Note 的 Window Coverage 和 Wiki 的 Supporting Evidence，不能用 Recall 一个指标代表全部场景。

### 延伸追问

1. **MMR 能不能替代 Selection**：MMR 主要控制相似性和多样性，不能天然知道子问题覆盖、来源资格和引用闭环。
2. **Window 如何防 Token 爆炸**：设置字符、Token、章节跳变和最大窗口数预算，超出时按结构边界截断并记录原因。
3. **证据冲突怎么办**：保留冲突来源和版本，不让 Selection 静默去掉其中一条，交给拒答或 Conflict Verifier。

### 对应八股

集合优化、MMR、Submodular Coverage、Token Budget、分页、缓存、文本切分和上下文窗口。

## 8. Workspace Scope 与归属校验

### 3 分钟标准回答

多租户检索最危险的错误不是召回少一条，而是把另一个 Workspace 的资料返回给用户。项目在查询阶段带 Workspace、Source Scope 和 Snapshot 过滤，结果返回后再由 EvidenceOwnershipGuard 和 EvidenceScopeGuard 做归属、版本和资源存在性检查。双重校验是为了防止索引配置或关联查询出现错误，客户端传入的 `workspaceId` 不能作为资源归属证明。

删除或撤权时，MySQL 先提交用户可见状态，投影和缓存异步失效。权限服务不可用时，高风险读取应 Fail Closed；普通统计可以展示带时间的旧值，但不能把旧 ACL 用于 Evidence 和写回。Memory、Research 和 Artifact 的结果写回也必须重新校验 Workspace 和资源版本。

这部分和普通 RBAC 不同。RBAC 只回答角色是否拥有 Permission，归属校验还要回答“这个 Message、Task、Source 或 Citation 属于哪个 Workspace”。因此 Repository 条件、Service Guard、投影过滤和审计指标要一起设计。安全指标不是“授权成功率”，而是 Cross-Workspace Leakage 必须为 0、撤权传播延迟可观测。

### 延伸追问

1. **为什么 Controller 不能只信路径 Workspace**：IDOR 攻击可以把资源 ID 和路径拼接成跨租户请求。
2. **缓存旧 ACL 多久可以接受**：高风险动作不能依赖 TTL，使用 ACL Version 使成员变更立即切换缓存 Key。
3. **返回 403 还是 404**：按资源枚举风险决定外部错误，内部保留拒绝原因和审计记录。

### 对应八股

RBAC、ABAC、IDOR、缓存失效、Fail Closed、数据脱敏、审计、最小权限和多租户隔离。

## 9. Transactional Outbox 与可重建 Projection

### 3 分钟标准回答

资料状态写入 MySQL 后还要触发解析、索引、缓存失效和派生写回。直接在事务提交后发 Kafka 会出现 DB 成功但进程在发消息前退出，任务永远丢失。Transactional Outbox 在同一事务里写业务状态和待投递消息，Dispatcher 之后按 Lease 领取并投递。Kafka 负责异步解耦和重试，MySQL 仍保存用户查询所需的业务状态。

Elasticsearch 和向量库属于 Projection，不是真源。Projection 可以延迟、失败或重建，用户读取时要知道当前版本和 Ready 状态。消费者按对象、阶段和 Snapshot Version 做幂等，旧 Worker 晚到用条件更新拒绝。删除时先让用户不可见，再异步清理对象和投影，最后通过对账确认收敛。

Outbox 不能带来跨存储强一致，项目采用最终一致加补偿、对账和重建。面试官问 Kafka 会不会丢消息时，要拆 Producer、Broker、Consumer 和业务处理四段回答，不能只背 ACK 配置。面试官问为什么不直接用 Kafka 做真源时，要说明 Kafka 不适合承载 Workspace 资源归属和复杂当前状态查询。

### 延伸追问

1. **Outbox 消息重复怎么办**：唯一业务键、状态条件和 Callback Receipt 吸收重复，不依赖“只投递一次”。
2. **Projection Ready 如何定义**：解析、切片、索引和质量校验都达到业务终态，不能只看 ES 写入成功。
3. **删除和重建冲突怎么办**：使用 Snapshot/Deletion Version，旧版本重建不能把已删除数据重新发布。

### 对应八股

Transactional Outbox、Kafka ACK、Consumer Offset、DLQ、最终一致、补偿事务、CDC、幂等和数据对账。

## 10. Skill Compiler、Capability Resolution 与 MCP

### 3 分钟标准回答

自由 Agent 的问题不是模型不会调用工具，而是工具能力、输入格式和副作用边界没有稳定合同。Skill 把产物目标、输入、输出、工具、Verifier 和版本写成定义，Skill Compiler 再把用户要求、Source Scope、Control Pack、Provider 和格式能力编译成 ExecutionSpec。Worker 消费的是稳定中间表示，不需要在运行中重新猜用户意图。

MCP 可以统一工具协议，但不自动授予权限。Capability Resolution 要同时取 Skill 允许的能力、Workspace 策略、当前 Provider 健康、Task 类型和安全策略的交集，最终把工具 Schema、参数约束、Scope 和副作用等级写入 ExecutionSpec。这样即使模型要求调用一个工具，也可能因为当前 Job 没有 Capability、参数不符合 Schema 或需要审批而被拒绝。

与直接维护几十个 Adapter 相比，协议统一后接入成本下降；代价是需要维护 Schema Version、兼容性、能力白名单和回调审计。与 LangGraph 等框架相比，项目保留自己的 Host 状态真源，是因为 Artifact 写回、Workspace 权限和配额属于业务域。小任务可以走固定 Skill，复杂任务才使用动态编译。

### 延伸追问

1. **Skill 和 Prompt Template 的区别**：Skill 还包含输入输出 Schema、工具能力、Verifier、版本和失败语义。
2. **能力解析失败怎么办**：具备持久等待合同的能力进入 Waiting，否则明确拒绝，不能让模型静默调用未授权工具。
3. **MCP 工具如何防 SSRF 和数据外泄**：参数 Schema、URL 白名单、网络隔离、Scope 绑定和写回 Guard 要组合使用。

### 对应八股

编译器中间表示、DAG、拓扑排序、Schema Evolution、MCP、Tool Calling、最小权限和 SSRF。

## 11. Quota、Waiting/Resume 与 Repair

### 3 分钟标准回答

Agent 任务有两类资源问题：短时间突发会打满 Provider，长任务又会长期占用 Worker。项目用 Redis Lua 实现 Workspace、Actor、Workload 维度的令牌桶，同时用并发租约限制在途任务。令牌桶保护一段时间内的调用量，并发租约保护同时运行的数量；只做其中一个都会留下另一类风险。

任务遇到 Provider 暂时不可用、用户需要补资料或外部能力未准备好时，先检查该能力是否已有持久 Wait Receipt、恢复条件和唤醒入口。只有合同齐全才进入 Waiting，并保存 Wait Reason 与已编译 ExecutionSpec；否则按当前错误策略有限重试或明确失败。条件满足后 Resume 不重新解释整条用户请求。Verifier 发现章节或字段失败时触发局部 Repair，只重新生成失败节点；最终仍要做全局 Contract 检查，避免局部修好后整体不一致。

Redis 只负责短期协调，Task、Outbox、Job 和 Version 仍在 MySQL 中持久化。令牌桶成功后到 Job 创建之间存在崩溃窗口，所以生产化需要预留记录、补偿释放或把准入和任务状态绑定。Provider 超时也不能直接标记失败，可能进入 UNKNOWN，等待回执、重试或人工处理。

### 延伸追问

1. **令牌桶参数如何推导**：根据 Provider QPS、成本预算、Worker 并发、用户 SLO 和重试放大计算，再用 P95/P99 校准。
2. **Repair 为什么不全量重跑**：减少成本和不稳定性，但结构性失败或上游事实变化时必须升级全量。
3. **Waiting 和 Retry 区别**：Retry 是同一动作的再次尝试，Waiting 是等待外部条件，不应占用活跃并发租约。

### 对应八股

令牌桶、漏桶、滑动窗口、Semaphore、Lease、Redis Lua、背压、重试退避和状态机。

## 12. Artifact Version/File 与质量验证

### 3 分钟标准回答

产物生成不能只看 Markdown 文本是否返回。ArtifactJob 表示长期用户意图，ArtifactRun 表示一次不可变的生成、再生成或追加式回滚请求，ExecutionAttempt 表示 Worker 接管和基础设施恢复代际，ArtifactVersion 表示逻辑内容，ArtifactFile 表示 PDF、Markdown 等具体交付文件。逻辑版本通过内容 Contract，不代表 PDF 导出或对象存储已经 READY，所以状态必须区分 PASS、WARN、FAIL 和 UNKNOWN。

内容 Contract 检查章节、字段、引用、题目答案、来源覆盖和结构要求；文件 Contract 检查 Mime、大小、SHA-256、对象存在、格式可读性和危险内容。Worker 只返回候选结果，Host 保存 Version、File 和写回关系。回调使用 Task 和幂等键唯一约束，文件生成超时先标记未知或可恢复，不能因为 HTTP 连接失败就重复创建版本。

质量指标应按产物类型分桶，包括 First-pass Yield、Repair Yield、File Ready Rate、Citation Completeness、Claim-Evidence Coverage、P95 和 Cost per Accepted Artifact。生成式模型的文本质量和文件交付质量是两条链。内容 Contract 通过后先保存不可见的 `DELIVERY_PENDING` Version，并创建全部必需文件的 Manifest；PDF 失败时内容版本可以保留并重试 DeliveryAttempt，但不能把 Version 提升为用户可见的 `READY`，失败的必需文件也必须留在 File Ready Rate 分母。

### 延伸追问

1. **为什么用 Markdown 作为中间表示**：结构可验证、易 diff、便于多格式导出；代价是复杂版式和视觉语义需要额外能力。
2. **WARN 能不能交付**：必须有用户可理解的降级说明和风险边界，高风险缺陷不能用 WARN 掩盖。
3. **回滚会不会覆盖用户修改**：创建新版本或 Proposal，并校验当前 Head Version，不能无条件覆盖。

### 对应八股

版本控制、内容寻址、SHA-256、对象存储一致性、状态机、Schema Validation、幂等回调和文件格式。

## 13. Turn、AnswerRun 与 SSE Replay

### 3 分钟标准回答

用户点击发送和模型执行不是同一个对象。TurnSubmission 用 `(actor, conversation, clientRequestId)` 唯一约束一次语义提交，准备阶段创建 Query Message、Assistant Placeholder、RunInputSnapshot 和 AnswerRun。AnswerRun 代表一次不可变的语义回答运行，可以取消、失败或完成；用户再生成和模型切换创建新 AnswerRun，基础设施恢复在同一 Run 下追加 AnswerExecutionAttempt。AnswerEvent 记录单个 Run 的增量、证据和终态，ConversationEventMux 再把多个业务事件投影到会话流。

SSE 只负责传输，MySQL 的 AnswerEvent 才是恢复真源。客户端带 `Last-Event-ID` 重连时，服务端先回放持久事件，再接入 Redis 实时桥，并以 Seq 去重。数据库提交后 Redis 发布前宕机，订阅者可能暂时收不到实时通知，但重连可以补齐。生成 Owner 与 SSE Subscriber 分离，浏览器断开不等于用户取消任务。

长会话使用 Segment Summary Revision，摘要先构建再 Promotion，失败时保留上一版。用户删除消息后，未来 Run 不再编译该内容，历史 Run 用 Replay Redaction 处理。这样幂等、断线、取消、删除和上下文压缩都有独立状态，不能把所有问题塞进 Message 表。

### 延伸追问

1. **SSE 为什么不是 WebSocket**：当前主要是服务端单向流，SSE 的 HTTP 兼容和自动重连更合适，双向高频协作再考虑 WebSocket。
2. **事件会不会重复**：允许重复传输，客户端和业务按 Run Seq 去重，最终以 Snapshot 校正。
3. **取消和完成竞争怎么办**：数据库条件状态迁移仲裁终态，晚到事件不能改回终态。

### 对应八股

HTTP 长连接、SSE、TCP 重连、背压、幂等、消息顺序、Redis Pub/Sub、事务提交与事件发布。

## 14. Auth、Refresh Rotation 与 ACL Version

### 3 分钟标准回答

认证只证明用户是谁，Workspace 鉴权才证明他能访问什么。项目使用随机 Access/Refresh Token，数据库只保存 Token Hash。Refresh 时以旧 Refresh Hash 做条件更新，两个并发刷新只有一个成功，另一个返回 Replay。登录和注册有独立限流和安全事件，密码哈希与高熵 Token 哈希采用不同策略。

Workspace 角色映射到细粒度 Permission，OWNER 拥有全部权限，EDITOR 可以写资料、回答和知识，VIEWER 只读。WorkspaceAccessGuard 先检查 Workspace 状态，再查 Membership、ACL Version 和 Role，资源接口还要从 Message、Task、Upload 或 Knowledge Item 反查真实 Workspace，不能信任 URL 中的 workspaceId。检索结果进入 Prompt 前再做 Ownership Guard，防止投影配置错误导致跨租户 Evidence。

ACL Cache 的 Key 包含 Workspace、User 和 aclVersion。成员变化在事务中提升版本，旧权限缓存不会再命中。数据库或缓存异常时，高风险读取 Fail Closed。当前能力适合应用内多租户权限，SSO、MFA、mTLS 和 Token Family 撤销属于生产身份平台增强，不能把它们说成已经完成。

### 延伸追问

1. **为什么不用 JWT**：当前需要即时注销、轮换和权限变更，数据库 Session 更容易控制；拆服务后再评估短期 JWT。
2. **为什么 SHA-256 可以存 Token**：Token 是高熵随机值，不能枚举；人类密码仍需慢哈希。
3. **403 还是 404**：按资源枚举风险决定外部错误，内部保存审计原因。

### 对应八股

认证与授权、RBAC/ABAC、IDOR、密码学哈希、Token Rotation、缓存失效、Fail Closed 和最小权限。

## 15. Gold Set、指标和实验可信度

### 3 分钟标准回答

业务指标、离线质量、故障演练和容量压测必须分开。QA Gold 保存 Query、允许 Snapshot、Gold Evidence、原子 Claim、参考答案和预期拒答；Research Gold 保存必填 Cell、最低独立来源、冲突事实和交付格式；Artifact Gold 保存产物结构、引用、文件和可修复错误。每次实验用 Manifest 冻结 Dataset、Index、Chunk、Model、Prompt、Judge、预算和脚本。

质量结果报告分子、分母、样本数、切片、失败样本和置信区间。Recall@K 说明证据有没有被召回，Citation Support 说明证据是否支持 Claim，Faithfulness 说明生成是否超出上下文，业务采纳率才说明用户是否真的接受结果。4/4 命中只能说明固定 Fixture 通过，不能写成系统准确率 100%。

面试官问“比业界好吗”时，先比较任务定义、Dataset、Snapshot、模型、预算和评分脚本是否一致。BEIR、GAIA、BrowseComp、LongMemEval 等公开 Benchmark 可以借鉴指标设计，不能把内部小样本和它们的分数直接横比。工程上最有价值的主结果通常是质量指标加安全、延迟或成本护栏。

### 延伸追问

1. **为什么用配对实验**：同一 Query 在 Baseline 和 Treatment 下对比，减少样本难度差异。
2. **LLM Judge 可信吗**：冻结模型和 Rubric，用人工校准集评估一致性，不能自评自证。
3. **为什么同时报 P95 和质量**：Rerank、长上下文和验证都会增加尾延迟，业务选择必须看到代价。

### 对应八股

实验设计、置信区间、Bootstrap、A/B、数据泄漏、分层采样、SLO、P95/P99、成本核算和可观测性。

## 17. 简单知识点的处理方式

普通查询 DTO、简单列表接口、没有并发和状态含义的字段映射，只保留三个信息：入口、输入输出、当前边界。不要为了凑长度把每个 Controller 都扩成 3 分钟。面试时间有限，重点应放在能改变正确性、成本、恢复、安全或质量结论的机制上。


## 18. 故障状态机、Unknown Outcome 与补偿收敛

### 3 分钟标准回答

异步系统的故障不能只按“成功、失败”二分。Outbox 任务可能在 Claim 后进程退出，Artifact 可能收到 `202` 但不知道 Worker 是否执行，删除可能已经让用户不可见但外部对象还没清理。面试回答先区分控制面状态和执行面结果，再说明谁负责推进、何时过期、怎样防止旧代际覆盖新代际。

项目里用 Lease 和 Attempt 管理一次投递，用 Delivery Token 或 Fencing 防止旧 Owner 晚到，用条件更新保证状态迁移只作用于当前代际。Attempt 耗尽且 Lease 过期的任务不能直接重置为 READY，而应进入可查询的 Dead Letter，再由受控 Redrive 创建新一代。Artifact Callback 还需要幂等键、Payload Digest 和 Receipt，但这些只能保证 Host 内部不重复落库，不能替外部工具撤销已经发生的副作用。

删除链路把清理意图写进与业务删除同一事务，事务提交后由持久任务执行 MinIO 和 Elasticsearch 清理。用户不可见和物理清理完成分开计时，分别监控 Visibility Lag 与 Completion Lag。验证时关注状态能否重复收敛、旧代际是否被拒绝、失败是否进入终态，而不是只看一次接口返回或日志。

### 延伸追问

1. **Lease 过期后为什么不直接重试**：过期只说明 Owner 失效，不能证明外部执行没有发生，必须结合幂等键、Receipt 或对账再决定动作。
2. **At-least-once 为什么不是 Exactly-once**：消息和 Host 状态可以去重，外部邮件、文件转换和第三方 API 的副作用仍可能重复。
3. **删除成功如何定义**：在线访问拒绝和外部资源物理清理是两个可观测终点，应分别设置 SLO。
4. **补偿任务会不会自己卡住**：补偿任务仍需 Lease、Attempt、过期接管和 Dead Letter，它也是状态机。

### 对应八股

Transactional Outbox、Lease、Fencing、CAS、At-least-once、幂等、Unknown Outcome、DLQ、补偿事务、最终一致性、对账和合规删除。
