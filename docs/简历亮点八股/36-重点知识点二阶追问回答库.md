# 重点知识点二阶追问回答库

> 本文承接[重点知识点三分钟深挖库](35-重点知识点三分钟深挖库.md)。第一层问题回答“是什么和为什么”，本文处理面试官继续问的“为什么不用另一个方案、极端情况下怎样失败、规模变化后怎样演进、参数怎样推导、如何证明效果”。每个回答都可以独立展开，不要求一次全部说完。

## 1. Research 状态建模的二阶追问

### 为什么不用一张 JSON 保存整个研究状态

一张 JSON 的优点是原型快，模型输出也容易直接落库，但它会把并发、索引和审计问题推迟到读取时。两个 Worker 修改不同 WorkItem，也需要覆盖整份 JSON；任何一个旧版本写入都可能丢掉另一个 Worker 的更新。按 Typed WorkItem、Candidate、Evidence 和 Merge 拆表后，可以对单个 WorkItem 做 Expected Version 条件更新，对 Task、Evidence 和状态建立索引，也能按类型统计 Coverage 和冲突原因。Matrix Cell 是比较型 WorkItem，不是所有研究任务的唯一模型。

项目没有把所有小字段都过度拆表。Research Brief、部分策略和冻结配置仍适合 JSON，因为它们在 Run 创建后基本不可变，不参与高频并发写。判断标准是字段是否需要独立约束、索引、生命周期和并发仲裁。面试官继续问 JSON 列性能时，可以讲 MySQL JSON 查询、虚拟列和索引，但当前核心不变量不能只靠应用层解析整份 JSON 保护。

### 为什么不用事件溯源完整重建 ResearchRun

事件溯源能保留完整历史，适合审计和重放，但代价是读模型、Schema 演进、事件幂等和快照维护都更复杂。Research 的主查询是“当前计划有哪些 WorkItem 未完成、当前预算多少、哪些 Task 可 Claim”，比较型任务再查询 Matrix 覆盖。用关系表和当前状态读取更直接。项目保留 Trace、Candidate、Merge 和 Checkpoint 来解释历史，不要求所有读取都从事件重放。

当监管或科学研究场景要求完整决策可验证时，可以进一步把关键 Merge、Verifier Decision 和外部 Operation Receipt 做成不可变事件，再建立当前状态 Projection。迁移前提是确实需要跨版本回放，并且团队能承担事件 Schema 兼容和 Projection 重建成本。

### 比较型任务的 Matrix Cell 非常多时怎么办

Cell 数量取决于实体数、维度数和规划修订，不能让 Planner 无界展开。系统需要设置 Matrix 行列预算、每轮新增 Cell 上限、最小信息增益和总 Token/时间预算。Claim 查询按 Run、状态、优先级和 Lease 过期建立组合索引，读取 Matrix 时采用分页或摘要，而不是一次把所有 Evidence 加载进内存。

规模继续增大后，调度可以按 Entity 或 Branch 分区，Checkpoint 保存高水位和摘要，冷 Evidence 放对象存储或归档表。分片会增加跨分区冲突和全局验证成本，所以只有比较型 Run 的 Cell 数、Task 数和锁等待达到明确阈值后才值得引入。开放调查、时间线和来源审计按各自 WorkItem 预算控制，不能硬转成 Matrix 才扩容。

## 2. Candidate、Verifier 和证据的二阶追问

### 两个 Candidate 为什么不一定比一个可靠

两个 Candidate 只有在来源和错误模式相对独立时才增加信息。如果两个 Worker 使用同一模型、同一 Query、同一转载来源，它们可能稳定地产生相同错误。项目因此把“候选数量”与“来源独立性”分开，按 Source Lineage、域名、Snapshot 和引用关系判断是否真正提供了新证据。

合并策略也不能简单多数投票。权威来源与多个低质量转载冲突时，数量不代表可信度。当前更合理的是先做确定性资格校验，再按来源权威、时间、直接性、冲突类型和 Cell 要求进入 Quorum 或 Review。评测要构造同源重复、过期权威和少数正确来源等反例，验证仲裁不会只数票。

### Verifier 也是模型，如何避免自评自证

Verifier 的输入、Prompt、模型版本和 Rubric 必须冻结，生成模型和验证模型最好在关键任务上分离。先把报告拆成原子 Claim，再用确定性规则检查来源、定位和 Schema，语义 Verifier 只判断规则无法判断的蕴含与冲突。人工校准集要包含支持、部分支持、反驳、无关和来源过期几类 Case，统计 Precision、Recall 和争议样本。

Verifier 分数不能直接当最终事实正确率。它是发布门禁和诊断信号，False Positive 会误杀有效结果，False Negative 会放过错误。生产策略可以按风险分层：低风险 WARN 允许交付并提示，高风险结论需要多来源或人工复核。面试时应主动承认 Judge 漂移和同模型偏差。

### Citation Support 很高，为什么答案仍可能错

Faithfulness 只说明答案没有超出给定 Evidence，Evidence 本身可能过期、错误或不完整。Citation Support 还可能因为 Claim 拆得过粗而虚高，比如一整段结论只绑定一个大段引用。项目需要同时检查 Source Quality、Snapshot Freshness、Claim Atomicity、Conflict Discovery 和最终 Correctness。

因此指标不能合成一个“可信度分数”就结束。检索 Recall 说明证据有没有机会被看到，Citation Support 说明引用是否支持，Correctness 说明结论是否符合 Gold 或人工判断，业务采纳说明结果是否有用。不同层次的失败需要不同修复手段。

## 3. Checkpoint、Receipt 和恢复的二阶追问

### 外部模型调用成功，但 Operation Receipt 没写入就宕机怎么办

这是典型 Unknown Outcome。Host 不知道 Provider 是否已经计费或生成结果，直接重试可能重复成本，不重试又可能永远卡住。最强方案是 Provider 支持幂等键，Host 在调用前写 Operation Intent，调用后写 Receipt，恢复时先按幂等键查询 Provider 或结果缓存。

当前实现更强的是 Completion 级业务收敛，所有外部 Operation Receipt 尚未完全覆盖。因此面试时不能承诺调用层 Exactly Once。可以说明系统保证重复 Completion 不重复合并，而外部调用重复窗口通过预算、缓存、超时和未来的 Operation Receipt 缩小。这个边界比直接说“幂等就行”更准确。

### Checkpoint 保存频率怎样确定

频率越高，恢复时重算越少，但数据库写入、序列化和存储成本越高。可以用期望损失估算：`Checkpoint Cost + Failure Probability × Recompute Cost`。研究任务的自然边界是重要 WorkItem 完成、Plan Revision、预算阈值和高成本外部步骤之后；只有启用了真实 Fan-out 时才使用 Wave/Barrier 完成点，不必按固定秒数机械保存。

正式调优需要观测任务时长分布、失败率、单步成本、Checkpoint 大小和 Hydration P95。若任务只有几十秒，频繁 Checkpoint 不划算；若一次外部搜索或模型调用成本很高，应在可确认的业务边界尽快落快照。

### Hydration 过程中发现 Snapshot 已被删除怎么办

恢复不能绕过当前权限和删除语义。Checkpoint 证明同一个 ResearchRun 过去看过什么，但新的 ExecutionAttempt 是否还能继续读取，要重新检查 Workspace、Source 状态和当前政策。若资料被删除或撤权，可以标记 Resume Blocked、要求用户重新选择范围，或者只恢复不依赖该 Source 的 WorkItem。只有用户改变目标、资料范围或主动 Fork 时才创建新 Run。

旧 Run 的审计仍保留引用标识，Replay 层按 Redaction 展示。这样区分了“历史发生过”和“现在仍允许使用”。若强行使用旧快照恢复，会违反用户删除和权限撤销预期。

## 4. Lease、Fencing 和任务调度的二阶追问

### Lease 秒数和 Heartbeat 周期如何推导

Lease 至少覆盖正常 Heartbeat 抖动和短时 GC/网络停顿，通常让 Heartbeat 周期显著小于 Lease，例如保留两到三次续租机会。具体值要从 Worker 单步 P99、网络 P99、JVM 或 Python 停顿、数据库延迟和恢复目标推导，不能只背默认值。

Lease 太短会产生误抢占，两个 Worker 同时计算同一任务；太长会延迟故障恢复。Fencing 能阻止旧结果提交，但不能消除重复计算成本，所以还要观测 Lease Expiry Rate、False Takeover、Late Completion 和额外 Provider 调用。参数调整必须同时看正确性和成本。

### Fencing Token 存在哪里，为什么要单调递增

Token 必须由业务真源或能原子递增的协调服务生成，并与 Task 当前 Owner、Epoch 和 Lease 一起校验。单调递增让下游只需记住已接受的最大 Token，任何更小 Token 都是旧 Owner。随机 Token 只能判断是否相等，无法表达所有权的新旧顺序。

如果跨多个下游写入，需要每个有副作用的下游都接受 Fencing 或由 Host 统一提交。只有调度器检查 Token，而 Worker 还能直接写对象存储和业务表，旧 Owner 仍可能留下副作用。所以项目把最终业务写回集中在 Host。

### 队列积压时如何保证公平

只按创建时间会让一个大 Workspace 占满 Worker，只按优先级又可能饿死低优先级任务。可以按 Workspace 配额、Workload 类型、任务优先级和 Age 组合调度，再用 Redis 并发租约限制单租户在途数量。Research、Artifact 和普通 QA 的时长和成本不同，不应共用一个简单 FIFO。

公平策略必须避免无限复杂。当前规模下先用显式优先级、Workspace 限额和超时，只有出现稳定积压和租户争抢后再引入 Weighted Fair Queue。验证指标包括 Queue Age P95、Starvation Count、Workspace Share 和 Deadline Miss。

## 5. RAG 检索算法的二阶追问

### BM25、向量和 Rerank 的参数如何联动

BM25 TopK 和 Vector TopK 决定候选池，RRF 的 `k` 和权重决定头部平滑程度，Rerank TopN 决定昂贵模型看到多少候选，Evidence Budget 决定最终进入 Prompt 的数量。候选池太小会丢 Recall，太大会提高 Rerank P95 和成本；最终证据太多还会造成 Lost in the Middle。

调参应该固定 Gold 和其他变量，先保证召回，再调融合与 Rerank，最后调 Evidence Selection 和 Prompt Budget。按 Query 类型切片，因为精确术语和语义问法需要不同通道。上线时同时监控 Recall 代理、降级率、Rerank P95、Token 和拒答率，不能只盯一个 nDCG。

### 为什么不用分数归一化后加权求和

归一化可以工作，但不同 Query、索引版本和模型下的分数分布会变化，Min-Max 还容易受异常值影响。RRF 用排名降低校准需求，适合数据量不大、需要可解释基线的阶段。它的缺点是丢失分数间隔，比如第一名远高于第二名和只高一点会被同样处理。

有稳定标注数据后，可以使用学习到的融合或 LTR，把 BM25、向量、来源、时间和结构特征共同输入模型。迁移条件是离线和线上收益覆盖训练、特征一致性和监控成本，而不是因为 LTR 理论上更高级。

### 强模型加长上下文会不会淘汰 RAG

长上下文降低了切片和召回的部分压力，但资料规模、权限、版本、成本、引用和更新仍存在。把所有资料发给模型无法证明用户是否有权读取，也会重复传输大量无关 Token。RAG 仍承担范围选择、证据快照、引用和可回放职责。

对于单份中等长度资料，长上下文可能比复杂检索更简单，Note 可以选择整篇或大 Window；对于多 Workspace、大资料库和频繁更新场景，检索仍有价值。项目应根据文档长度、Query 类型和成本路由，而不是把一种方案绝对化。

## 6. Chunk、Window 和图扩展的二阶追问

### Chunk 大小如何确定

Chunk 太小会切断定义与论证，太大则降低召回精度并增加 Rerank 和 Prompt 成本。应按标题、段落、列表、代码块和表格边界切分，再用 Token 上限保护。Overlap 能缓解边界断裂，但也会增加重复候选和索引规模。

评测时按文档类型和长度分桶，观察 Recall、Gold Span Coverage、重复率、索引大小和 P95。Chunk Policy 属于版本化策略，改变后需要重建 Projection，并让旧 AnswerRun 继续引用原 Snapshot 和旧策略。

### Reading Window 为什么不直接取整篇 Source

整篇输入在短资料上简单有效，但长 PDF 会造成高 Token、Lost in the Middle 和无关章节干扰。Reading Window 先定位 Anchor，再沿结构扩展，可以在连续性和预算之间平衡。系统还要处理 Anchor 位于表格、代码块或章节边界的情况，不能机械取前后 N 个 Chunk。

如果 Source 小于阈值或用户明确要求全文总结，可以走整篇模式；如果资料很长，按章节或多 Window 读取。选择应写入 Plan，方便评测和回放。

### Wiki 图扩展如何避免指数增长

每一跳都限制最大节点、最大边、关系类型和 Workspace，优先显式链接和来源回链，再结合文本相关性排序。访问过的节点去重，低置信边不继续扩展。两跳不是固定真理，应该由 Gold、图密度和 Token Budget 决定。

图扩展失败时可以回退到页面文本检索，不能把图不可用等同于整个 Wiki 不可用。评测除答案外还要看 Link Precision、Supporting Evidence 和 Version Consistency。

## 7. Outbox、Kafka 和 Projection 的二阶追问

### Outbox 表会不会成为瓶颈

Outbox 的写入与业务事务同库，会增加写放大和索引维护。Dispatcher 查询必须使用状态、Topic、LeaseUntil 和 CreatedAt 的组合索引，批量 Claim 后短事务更新，避免扫描和长锁。历史消息按保留策略归档或分区，不能无限留在热表。

当吞吐远超单库能力，可以用 CDC 读取数据库日志，减少轮询压力，但 CDC 仍需要事件 Schema、幂等消费者和运维系统。当前项目规模优先 Outbox Polling，因为实现和故障解释更直接。迁移依据应是 Outbox Lag、DB CPU、锁等待和批量吞吐，而不是架构时髦程度。

### Kafka 消费成功但 Offset 没提交怎么办

短投影消息会再次投递，所以业务处理必须幂等。消费者完成的定义是业务状态或 Projection Version 已经持久化，不是方法没有抛异常。重复到达时读取已有终态或唯一键冲突，返回相同语义结果，再提交 Offset。

Artifact 小时级命令采用另一提交边界：Consumer 先按 `command_id` 在 MySQL 幂等登记 Durable Execution，事务提交后即可提交 Offset，Scheduler 再领取 Execution。登记后宕机不会丢任务，Offset 提交前宕机会重放并命中同一唯一键。Kafka 事务不能自动覆盖 MySQL、MinIO 和 ES，两条路径都依赖 At Least Once 加业务收敛；区别是慢外部调用不能占着 Consumer Session。

### Projection 与真源不一致如何对账

对账按 Workspace、Source Snapshot 和 Projection Version 比较，检查缺失、旧版本、多余文档和删除残留。发现差异后从 Source Snapshot 重建，而不是让 ES 结果回写 MySQL。重建任务也带版本和删除水位，避免旧重建覆盖新版本或复活已删数据。

对账频率由风险和成本决定。高风险权限和删除可做实时 Guard 加异步清理，普通排名投影可以周期抽样。指标包括 Projection Lag、Mismatch Rate、Rebuild Success 和 Delete Residue。

## 8. Agent、MCP 和 Artifact 的二阶追问

### Skill Graph 如何处理循环依赖

编译时将 Skill 节点和依赖构成 DAG，使用拓扑排序检查循环。静态循环直接拒绝并返回具体节点路径。动态 Repair 不修改已经完成节点的依赖方向，而是创建受限修复任务，并设置最大轮次和总预算，防止模型用循环掩盖无法完成。

某些业务确实需要迭代，比如生成、验证、修复。它不应建成无界图环，而应建成状态机中的有界 Loop，Stop Contract 包含最大轮次、边际收益和预算。这样既保留迭代，又能证明终止。

### MCP Server 不健康时如何降级

Capability Resolution 在编译或执行前检查 Provider 健康。如果能力是可选的，可以选择降级 Skill 或省略非关键输出，并将 Degradation 写入 Trace；如果能力是产物 Contract 的必需项，具备持久等待合同才进入 Waiting，否则明确失败，不能生成看似完整但缺关键能力的结果。

健康检查不能只看 TCP 可连，还要看 Schema Version、认证、调用 P95 和错误率。熔断后恢复采用半开探测，避免所有任务同时冲击恢复中的 Provider。任务级 Deadline 仍要覆盖连接、读取和重试。

### Artifact 文件落库成功但对象存储失败怎么办

先区分逻辑 Version 和 File。对象上传成功后再把 File 标记 READY，数据库只有元数据但对象不存在时保持 PENDING、FAILED 或 UNKNOWN，并由修复任务对账。对象已上传但数据库提交失败时，可以通过确定性 Object Key、Digest 和 Pending Manifest 发现孤儿并补登记或清理。

不能用跨 MySQL 和对象存储的强事务假设。采用幂等 Object Key、Checksum、状态机、补偿和对账。用户下载前再次检查 File Status 和对象存在，避免返回损坏链接。

## 9. Conversation、SSE 和 Context 的二阶追问

### TurnSubmission 在准备一半时失败怎么办

Turn Ledger 记录 Preparation JSON、Attempt、Error 和 Recovery Lease。唯一 Client Request 已经占位后，重复 HTTP 请求不会再创建第二条用户消息。Recovery Scanner 只领取超时且未完成的 Submission，继续创建缺失的 Message、Input Snapshot 或 AnswerRun。

每一步都要幂等，不能假设事务覆盖全部外部准备。若请求 Payload 与同一个 Client Request ID 的旧 Hash 不同，应拒绝冲突，避免客户端错误地复用幂等键。

### SSE 回放和 Redis 实时订阅之间会不会丢事件

危险窗口是数据库历史追平后、Redis 订阅建立前。可以先订阅再回放，然后按 Seq 去重；或者回放后订阅，再二次读取高水位。客户端以 Last-Event-ID 和 Run Seq 去重，最终用 AnswerRun Snapshot 校正完整状态。

Redis 不是真源。发布失败只影响实时延迟，持久 AnswerEvent 仍可补齐。多标签页产生多个 Subscriber，不应触发多个 Generation Owner。

### Segment Summary 丢失关键约束怎么办

Summary Revision 在 Promotion 前用 Gold 约束、实体、未完成任务和时间事实做完整性检查。新摘要失败时保留上一版 READY，不能覆盖。RunInputSnapshot 还可以保留关键消息引用，摘要只是压缩层，不是删除原始历史的理由。

评测要按会话长度、语言、更新和否定约束分桶，看 Retention、Compression、Temporal 和 Abstention。发现摘要系统性丢失某类约束时，先改 Segment 边界和 Rubric，不只是换更大模型。

## 10. Memory 和删除语义的二阶追问

### Memory 撤销如何传播到已经编译的 Control Pack

新 Run 编译时读取当前 Revision 和 Revoke Watermark，过滤已撤销或被替代内容。已经开始的 Run 使用冻结 Input Snapshot，不在执行中悄悄变化；高风险撤销可以取消相关 Run 或在写回前重新校验。缓存 Key 包含 Memory Version 或 Watermark，版本变化后旧缓存不再命中。

完整依赖传播需要记录哪些 Summary、Control Pack、Artifact 和 Run 使用了哪条 Revision。当前项目的完整 Revoke Watermark 和依赖图仍是目标设计，所以面试时要说明已实现边界和继续补全路径。

### 用户偏好和事实为什么不能用同一套 Memory 规则

偏好允许模糊和覆盖，例如“回答简洁一些”；事实需要来源、时间和冲突处理，例如“课程截止日期”。任务状态有更短 TTL，安全规则则可能只能由管理员修改。统一相似度召回会把不同风险内容混在一起。

因此 Candidate 先分类，再按类型走审核、版本、过期和编译策略。评测也分 Update、Temporal、Preference、Abstention 和 Pollution，不能只报 Memory Hit Rate。

### 删除后为什么不直接物理删全部历史

业务读取需要立即不可见，派生摘要、索引和 Control Pack 需要失效，审计或法规保留可能有不同期限。跨多个存储同步物理删除容易部分失败，所以先提交删除事实和 Redaction，再异步清理并对账。

用户侧不能继续看到被删内容，内部也不能让旧 Memory 进入新 Run。是否保留加密审计标识、何时物理清理，要由隐私政策决定，不能只从技术方便出发。

## 11. 认证和权限的二阶追问

### Refresh Token 被盗后只做 Rotation 够吗

并发条件更新能检测旧 Token 重放，但更强方案需要 Token Family。发现旧 Refresh 再次使用时，撤销整个 Family、记录设备和 Security Event，并通知用户重新登录。否则攻击者和正常用户可能轮流刷新，系统只拒绝后到的一方。

Token Family 增加状态和误报处理，当前实现主要覆盖单 Session Rotation 和 Replay 拒绝。面试时可以把 Family 撤销作为生产身份平台增强，不说成现有事实。

### ACL Version 更新和成员修改必须同一事务吗

必须保证成员状态和 aclVersion 对外原子可见。若先改成员后改版本，短窗口内旧缓存仍可能放行；若先改版本后成员未成功，缓存又会基于错误状态重建。放在同一 MySQL 事务中，提交后新请求读取新版本并重新查 Membership。

缓存只存计算结果，不是真源。DB 不可用时高风险权限检查 Fail Closed，不能因为缓存还有旧 OWNER 就继续写。

### Internal API 如何防止普通用户 Token 调用

路径分区不等于安全。Internal API 使用独立 Audience 或内部 Token、网络策略和最小 Capability，Worker 请求绑定 Task、Workspace 和 Payload Digest。外部用户 Access Token 即使有效，也不能通过内部认证 Filter。

生产环境还可加 mTLS、短期服务凭证和密钥轮换。本地 Compose 只证明接口分区和认证逻辑，不能描述成完整零信任网络。

## 12. 指标和统计的二阶追问

### 为什么 30/30 故障恢复仍不能说 100% 可靠

30 次全部通过的点估计是 100%，但它只覆盖指定注入点、版本和环境。Wilson 95% 下界仍低于 100%，更没有覆盖机房、磁盘、真实 Provider 和长时间压力。正确表述是“在 30 次受控演练中零失败”，并列出注入位置和不变量。

可靠性还要看恢复耗时、重复成本、数据一致性和未覆盖窗口。样本增加后按故障类型分层，不能把不同风险混成一个成功率。

### 业务节省时间怎样避免自我报告偏差

同类任务随机分配人工 Baseline 和系统辅助组，记录有效工作时间、修订次数和结果质量。避免同一个人先手工再做相同题产生学习效应，可以交叉任务或使用不同但等难的 Case。报告中位数、分布和质量门槛，不只问用户“感觉节省多少”。

如果当前没有真实用户实验，就保留测量设计，不填写百分比。离线 Gold 的质量提升不能替代业务时间节省。

### LLM Judge 和人工标注不一致怎么办

先定义原子 Claim 和 Rubric，随机抽样双人标注，计算一致率并讨论争议 Case。Judge 在校准集上测 Precision、Recall 或相关性，确定适合做批量初筛还是只能辅助。模型、Prompt 和温度要冻结，升级后重新校准。

最终报告同时给自动评测和人工抽样，不把 Judge 分数当绝对真相。高风险发布门禁优先使用确定性规则和人工复核。

## 13. 系统设计综合二阶追问

### 如果不用 Kafka，系统怎样简化

早期可以让 MySQL Outbox Dispatcher 直接调用 Worker 或使用数据库任务队列，减少 Broker 运维。只要保留任务状态、幂等、Lease 和回执，业务语义不变。当消费者增多、需要保留重放、积压吞吐和独立扩缩容时再引入 Kafka。

这个回答说明中间件是实现手段，不是架构核心。真正核心的是业务真源、至少一次输入下的收敛和失败恢复。

### 如果流量扩大十倍，先扩哪里

先按资源链测量：API 线程和连接池、MySQL 锁等待与慢 SQL、Outbox Lag、Kafka Consumer Lag、Worker 并发、Provider P95、ES 查询和 SSE 连接。不同瓶颈使用不同扩展手段，不能先拍脑袋分库分表。

Research 和 Artifact 是长任务，通常先做 Workspace 公平调度、Worker 水平扩展和 Provider 配额；QA 是交互请求，优先保护 TTFT、检索 P95 和连接池。数据库达到写入和索引瓶颈后再考虑分区、归档或读写拆分。

### 如何判断当前架构是不是过度设计

把机制对应到失效条件。任务只持续几秒、单用户、无写回时，不需要完整 Lease/Fencing 和多级审批；任务跨分钟、会重试、涉及多 Workspace 和外部副作用时，持久状态机开始有价值。每个组件应有可观察触发条件，例如 Outbox Lag、重复回调、锁等待、恢复成本和权限风险。

如果删掉某机制不会破坏当前不变量，可以简化；如果只是还没有生产数据，则把它标成目标设计，不把设计存在当成已经产生收益。面试官通常更认可这种边界判断，而不是坚持所有组件都不可替代。

## 15. 使用方法

第一轮随机抽一个一级主题，完整讲 3 分钟。第二轮从该主题任选一个二阶问题，再讲业务条件、原理、项目对象、失败窗口和替代方案。第三轮把回答落到 Java、MySQL、Redis、Kafka、HTTP、检索算法或安全八股，并指出当前证据和生产边界。能连续完成三轮，才算真正掌握这个知识点。


## 16. 故障复盘与证据边界

### Outbox 最后一次 Claim 后为什么会永久卡住

普通重试查询通常只选择 `attempt_count < MAX_ATTEMPTS` 的候选。最后一次 Claim 已经把 Attempt 加到上限，Owner 又在回调前退出，Lease 过期后这条记录同时满足“没有活跃 Owner”和“不能进入普通重试”，如果没有耗尽扫描器，就会停在 `PROCESSING`。修复需要一个独立的过期耗尽迁移，使用 ID、状态、Attempt 和 Lease 条件做 CAS，旧 Dispatcher 的晚到更新必须被 Fencing 拒绝。

### 为什么删除后日志不能代替清理任务

日志没有业务状态、重试身份、Owner、Lease 和幂等约束，也不能保证和删除事务同提交。删除事务内写入 `source_cleanup_task` 后，即使进程在提交后退出，下一轮调度仍能看见意图。对象和索引清理要把“当前状态不可见”和“物理资源已清理”拆成两个延迟指标，不能用接口返回值代替清理完成证据。

### Artifact Callback Receipt 能否证明外部 Exactly-once

不能。Receipt 只能证明 Host 已收到或处理某个回调，Delivery Token 只能阻止旧代际更新当前任务。Worker 可能已经调用 Provider，但 Host 在回调前崩溃，重投会再次触发副作用。需要 Provider 幂等键、可查询 Receipt、Operation ID 和对账任务，无法判断时进入 Unknown Outcome 或人工处理。

### Rerank 部分返回为什么要单独计数

只看 `degraded` 聚合字段，可能把部分合法返回当成普通成功。应记录返回条数与候选条数的比例、部分返回次数、结构性错误类型、回退原因和 Provider 版本，再将其与 Recall@K、Citation Support、P95 和成本配对分析。固定模拟只能证明防御策略，不能外推线上 Provider 质量。

### 面试中怎样守住事实边界

把内容标成 `[当前实现]`、`[已测-模拟]`、`[历史设计，已移除]`、`[演练假设]` 和 `[生产待验证]`。仓库测试能证明状态窗口、错误分类和不变量，不能凭空给出线上事故时间、影响用户数、MTTR、SLO 或合规审计结果。被要求给数字时，优先给分子、分母、样本范围和实验 Manifest。
