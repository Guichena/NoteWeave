# 全项目面试文档审查矩阵

> 审查目标不是让每个文件一样长，而是让重要机制有足够深度，简单实现不浪费准备时间。全目录按主背、重点深挖和速查三档使用。

## 0. 先确定权威顺序

[面试推荐架构与规模化演进裁决](43-面试推荐架构与规模化演进裁决.md)是推荐设计的最高层裁决。它回答“如果不受当前历史包袱限制，面试时应选择什么方案”。出现冲突时按下面的顺序处理：

1. 当前能力、真实参数和已经发生的行为以源码、配置和 `[当前实现]` 事实卡为准。
2. 字段含义、幂等键、状态迁移和跨服务提交条件以契约文档为准。
3. 面试中的推荐设计、规模化方案和迁移终点以 `43` 为准。
4. 演进、案例和题库用于解释为什么改变，不能覆盖前三层。

回答可以采用比源码更好的方案，但要说出当前差异、迁移步骤、触发升级的规模条件和代价。推荐设计不能写成已经上线，旧配置也不能反过来限制面试方案。

全目录共同遵守八条不变量：

| 不变量 | 统一要求 | 主要防止的问题 |
| --- | --- | --- |
| Run 与 Attempt 分离 | 用户意图属于稳定 Run，基础设施恢复和 Worker 接管只新增 Attempt | 把故障恢复算成新业务请求，采纳率和成本分母失真 |
| Typed WorkItem | Research 共享运行合同，Matrix 只服务比较型任务，不统一不同类型的验收语义 | 所有研究被二维表限制，开放问题和时间线难表达 |
| Kafka 快速接纳 | Consumer 先幂等登记 Durable Execution，再提交 Offset；长任务由 Scheduler 和 Lease 执行 | 慢外部调用阻塞分区，依赖超长 Poll 保活 |
| Host 唯一 Version ID | Host 在 ArtifactRun 上持久化 `reserved_version_id`；`RESERVED` 只是预留身份，不创建空 Version。内容通过后用同一 ID 创建 `DELIVERY_PENDING` Version，只有 `READY` 可见和可写回 | 两套业务版本库、空预留污染指标、文件与审批身份不一致，或半成品提前暴露 |
| Artifact 交付提交点 | 内容 Contract 通过后先创建不可见的 DELIVERY_PENDING Version，并冻结全部必需文件 Manifest；DeliveryAttempt 再物化文件，全部必需文件 READY 后才晋升 Version | 文件失败前没有分母、交付失败被隐藏，或对象存储半成品被误当成业务版本 |
| Admission 与 Active 分离 | WAITING 保留 MySQL Admission Reservation，释放 Redis Active Permit，恢复时重新竞争 | 等待任务占执行槽，或 Redis TTL 把已接纳业务事实静默抹掉 |
| Lease 与 Fencing 分责 | Admission Reservation 表示持久接纳，Active Permit 表示稀缺资源占用，Budget Reservation 表示额度授权；只有拥有业务提交权的 Domain Execution Lease 使用单调 Epoch/Fencing 拒绝旧 Owner 写回 | 所有令牌强绑为同一代次导致无意义失效，或没有业务 Fencing 让旧 Worker 覆盖新结果 |
| Explicit 与 Derived Memory 分流 | 用户明确偏好可按窄 Scope 生效并撤销，模型推断必须审核；RAG Evidence 使用独立事实预算，不能被 Memory 或历史 Summary 挤掉 | 把保存、导出、重试误判成真实偏好，或让偏好污染事实证据 |
| Generation 与 Watermark | 回填冻结 Catalog Watermark；每次 Source 变更只写一条 Change Log，同一发布域内保持单调顺序，新 Generation 消费同一日志；发布由单写协调器串行化，并用 expected old 条件动作与 Reconciler 收敛 | 活跃 Workspace 反复全量重建，全局顺序热点，重复事件应用，或并发发布相互覆盖 |
| Domain Event 与 Stream Projection | 领域事实只写一次，会话流通过 `source_event_id` 投影 | 两份事件事实漂移，重连后重复或缺失 |

## 4. C 档速查范围

以下内容不单独凑 3 分钟：普通 Create/List/Get DTO，只有参数校验的 Controller，简单 Repository 映射，不影响状态和安全的字段，未参与资源链推导的配置默认值，以及没有失败窗口的前端展示逻辑。

速查回答只保留三项：入口在哪里，输入输出是什么，当前边界是什么。面试官继续追问并发、事务、权限或性能时，再切换到 B 档对应知识点。

## 7. 验收标准

随机抽一个 A 档功能，能讲 4 分钟并主动给出 Trade-off。再随机抽一个 B 档机制，能讲原理、项目对象、替代方案和失败窗口。最后随机抽一个二阶问题，能继续落到 Java、MySQL、Redis、Kafka、网络、安全或统计，并明确当前实现、固定演练和生产待验证边界。完成三轮后，该功能才算准备完成。

## 10. 详细架构附件的权威顺序

`01` 到 `05` 五份详细架构已经统一增加阅读顺序和冲突处理规则。面试主回答以 `30` 到 `34` 一体化手册为入口，详细架构只承担算法、状态与机制深挖；字段和跨服务语义以契约文档及当前源码为准；理想设计和生产事实通过标签区分。

| 附件 | 重点校准的高风险口径 |
| --- | --- |
| Research 详细架构 | Checkpoint、Canonical Merge 和多角色设计不能越过当前契约与并发开关 |
| RAG 详细架构 | `3 + 3` 手工基线不是在线准确率，受限图读取不是完整 GraphRAG |
| 资料底座详细架构 | At-least-once 加业务幂等不等于跨存储 Exactly-once |
| Agent 详细架构 | 编译期 DAG 不等于并行运行时，Waiting 与 MCP 安全只能按已接入路径声称 |
| Context 与 Memory 详细架构 | 已有 Revision 与隔离不等于完整撤销传播和物理删除 |

这组附件篇幅已经足够，不再追加重复的 4 分钟主回答。后续优化重点是删除与新入口重复但口径较旧的段落，以及给真实源码变化建立一次性校准记录。

## 11. 五份题库统一为打断式训练

`01` 到 `05` 的“面试题与参考回答”已经统一三档入口。A 档只使用 `30` 到 `34` 的 4 分钟功能主回答；B 档只展开会改变状态、安全、质量或成本的关键机制；C 档保留组件职责、概念区分、DTO 和普通参数等 30 到 90 秒速查。题库末尾的八维长回答仍可作为换角度训练，不再与一体化手册争夺默认入口。

这条规则解决两个面试问题：简单题不会因为硬凑时长显得背稿，重点题也不会只停在一句定义。面试官继续追问时，回答从 C 档术语切到 B 档机制，再落到项目反例、源码边界和验证证据，不必重新背一遍完整系统演进。

## 12. 基础八股专项的重点路由

Java、MySQL 和分布式基础专项已经补出明确的 B 档知识点索引。Java 重点保留 JMM/CAS/Fencing、线程池与背压、JVM/GC/Lease、事务/Outbox、Timeout/Unknown Outcome 和 SSRF；MySQL 重点保留联合索引、MVCC 与锁、唯一约束与状态机、事务与 Outbox、连接池与长事务、DDL 兼容；Redis/Kafka 重点保留 Lua 配额、权限缓存、至少一次、结果未知、版本化最终一致和重试放大。

其余集合、语法、组件定义和普通配置仍属于 C 档，不因专项文档篇幅较长就要求全部讲三分钟。重点机制的验收标准是能够回答“底层原理、项目反例、实现边界、故障窗口、验证证据”五项，并继续承受至少一轮二阶追问。

## 13. 演进、案例与契约附件不再争夺主入口

`16` 到 `24` 已统一补充职责说明。`30` 到 `34` 负责默认 4 分钟功能主回答；演进专项只讲触发问题、候选、外部依据、选择和代价；案例专项只讲学校事件、消融、指标与 Ownership；契约专项只讲字段、状态、不变量和失败窗口。Artifact 还额外区分通用执行框架与产物业务，避免把 Quota、Kafka、文件质量和用户采纳混成一个层次。

面试准备时，同一功能只背一份主回答。面试官问“为什么”时进入演进附件，问“数字和你做了什么”时进入案例附件，问“并发和失败窗口”时进入契约附件。这样保留深度，又不会让多份长文产生互相矛盾的版本。

## 15. 横切专项的第二组独立深挖

`38` 到 `40` 已各增加一组可独立讲三分钟的重点机制：Task 治理增加多租户公平调度与过载保护，前端工作台增加跨刷新幂等和过期请求闭环，检索发布增加 Alias 结果未知与 Manifest 对账。它们分别补上了原文中只能靠零散追问拼接的调度、客户端一致性和跨存储发布问题。

三组新增内容都主动区分当前与目标。当前 Workspace 并发 Lease 不等于完整 DRR；当前 Request Gate 和服务端幂等不等于跨刷新提交账本；当前多 Alias 更新不等于具备统一 Release Manifest 与 Reconciler。面试时可以讲完整演进方案，但必须在回答末尾明确现有证据停在哪一层。

## 16. 横切附件的最终权威分工

`06` 只做八维横向审计，不作为新功能背诵；`07` 定义测什么，`29` 定义数字怎样生产，`41` 定义运行 SLO 与告警，`42` 定义容量压测和成本；`43` 裁决推荐架构；`08` 是个人事实与 Ownership 闸门；`15` 是配置基线，不提供容量结论。总索引和 README 应覆盖全部 50 份面试 Markdown，不允许出现孤立入口。

这套分工使配置、指标、实验和生产事实不再互相替代。默认值不能冒充压测，固定回放不能冒充线上质量，目标设计不能冒充当前能力，架构叙事也不能替候选人证明个人经历。

## 17. Research 默认入口的重点机制已就地闭环

完成度审计发现 Research 默认入口原先只有 4 分钟主回答，没有显式三分钟机制段。现已在 `30` 中补齐 Table-as-State 与候选仲裁、Checkpoint 与结果未知、Verifier 与引用可信度三组独立回答，每组包含项目反例、方案比较、代价、验证边界和二阶追问。Research 作为项目重点，不再要求面试时临时跳转多个附件才能继续下钻。

## 19. 本轮跨文档一致性审计结论

本轮检查重点是同一概念在不同入口中的状态、参数、指标和事实标签是否被混写。已统一以下规则：
