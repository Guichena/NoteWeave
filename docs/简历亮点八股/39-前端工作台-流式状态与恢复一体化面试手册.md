# 前端工作台、流式状态与恢复一体化面试手册

> 定位：这篇回答前端为什么不是把接口数据塞进几个 `useState`，以及会话、Research、Artifact 和 Task 同时运行时，怎样处理流式增量、权威快照、过期请求、重连、多 Run 和 Workspace 切换。它对应 React 状态管理、HTTP/SSE、并发竞态、AbortController、不可变更新和前端可观测性。

## 1. 60 秒主回答

NoteWeave 的工作台同时展示会话回答、任务进度、Research Checkpoint、Artifact 版本和资料状态。难点不在页面数量，而在数据到达顺序：SSE 增量可能早于发送接口返回，旧 Run 的详情可能晚于新 Run，请求在切换 Workspace 后仍可能完成，浏览器断线后还要从游标恢复。

我的处理方式是按资源拆 Store，并建立统一优先级：MySQL 查询得到的 Snapshot 是完整状态，领域 Event 是一次写入的恢复事实，Conversation SSE 是带 `source_event_id` 的订阅投影，乐观状态只改善交互，派生 View Model 不反向写服务器。`AnswerRunStore` 以 Run ID 保存多条并发回答，用 Event ID 和 Run Sequence 去重，终态后拒绝晚到 Delta；`ReconnectingSseClient` 持有 `Last-Event-ID` 并指数退避；Execution Registry 在 SSE 断开时才启用 HTTP 轮询；Research 与 Artifact 使用按通道的 Request Gate 和 AbortController，保证过期响应不能覆盖当前选择。

## 2. 前端有四类状态，优先级不同

```text
Server Snapshot
  -> 资源完整状态和终态真源

SSE Event
  -> 低延迟增量，允许重复和重放

Optimistic State
  -> 用户提交后的即时反馈，可回滚

Derived View Model
  -> 当前选择、格式化、过滤、对比，不写回真源
```

| 状态 | 项目例子 | 能否覆盖其他状态 |
| --- | --- | --- |
| Server Snapshot | AnswerRun、Task、Research Detail、Artifact Version | 可以校正增量和乐观状态 |
| SSE Stream Entry | 由领域 Event 投影的 `answer.delta`、`answer.completed`、`task.progress` | 只能按序推进，不能反向决定业务终态 |
| Optimistic State | 立即追加用户消息、Loading 标记 | 请求失败必须回滚，不能作为刷新后的事实 |
| Derived State | 当前 Checkpoint 对比、历史版本列表、状态文案 | 应从稳定状态计算，不独立复制业务事实 |

前端的核心不变量是：旧异步结果不能写进新 Workspace、新 Run 或新版本；重复事件不能重复追加；终态不能被晚到增量改回运行中；任何断线都能通过 Snapshot 恢复。

## 3. 为什么不用一个全局 Store

项目当前使用领域 Reducer、Hook 和小型 Store，而不是把所有状态放进一个全局对象。会话回答按 `answerRunId` 和 Run Sequence 收敛，Task 按 `taskId` 观察，Research 还需要 Run、Checkpoint 和 Comparison 三组选择，Artifact 需要 Job、Version、History Selection 与 Writeback Receipt。它们的身份和过期规则不同。

一个全局 Reducer 容易出现两类错误：Workspace 切换时漏清某块状态，某个领域为了复用 Action 被迫理解其他领域字段。当前 `useExecutionRegistry`、`useResearchState`、`useArtifactState` 分别拥有清理、请求取消和版本选择，工作台 Controller 只编排用户动作。

这不意味着拒绝 Redux、Zustand 或 React Query。若跨页面共享、缓存失效和服务端状态种类继续增长，可以引入查询缓存管理 Snapshot，把 SSE Reducer 保留为增量层；不应让通用缓存库隐式决定 Run Sequence、终态优先级和 Checkpoint 对比语义。

## 4. 会话流如何处理多 Run

`AnswerRunStore` 使用 `Map<runId, AnswerRunState>`，一个 Conversation 可以同时存在多个 AnswerRun。重新生成不会覆盖旧 Run，SSE Envelope 显式携带 `run_id`、`run_sequence` 和数据。

事件处理顺序是：

1. `conversation.snapshot` 直接走完整快照校正。
2. 其他事件先按全局 Event ID 去重。
3. 解析 Run ID 与 Run Sequence，没有归属的事件丢弃。
4. Sequence 小于等于该 Run 当前水位时忽略。
5. Reducer 处理 Delta、Snapshot、Citation 和终态。
6. 当前 Run 已终结时，晚到 Delta、Citation 或失败事件都不再修改。

Store 的 Event ID 集合有 2048 的默认容量，防止长会话无限增长。真正的长期顺序依赖 Run Sequence 和服务端游标，不依赖浏览器永远记住所有事件 ID。

### SSE 比发送接口更早返回怎么办

会话订阅在页面进入时就建立。用户发送后，SSE 可能已经创建对应 Run 状态，POST 响应稍后才返回 `answer_run_id`。Controller 读取 Store 中已缓冲内容，再创建 Assistant Message，因此不会丢失首批 Delta。反过来，SSE 尚未连接时，Controller 使用单 Run 流作为回退，结束后仍请求 AnswerRun Snapshot 校正。

## 5. 重连、游标和快照校正

`ReconnectingSseClient` 自己维护 Cursor。收到有 ID 的事件后推进 Cursor；连接异常时从 250 毫秒开始退避，最大 5 秒；重连请求带 `Last-Event-ID`。Abort 用于页面卸载和资源切换，AbortError 不显示为业务错误。

连接成功只表示 HTTP 流建立，不表示状态已经追平。会话工作台收到 `conversation.snapshot` 后才将 `connected` 设为真。这样发送动作不会因为一个刚建立但尚未回放完成的连接，错误地等待不存在的终态事件。

`AnswerRunStore.reconcileRun` 使用查询快照校正内容、状态和错误，同时保留已经收到的 Citation，以及服务端快照暂时为空时的流式内容。Snapshot 是数据库查询真源，但也要考虑读副本延迟或终态聚合尚未完成，不能用空字符串擦掉用户已经看到的内容。

## 6. Task Observer 为什么同时有 SSE 和轮询

Execution Registry 观察多个 Task，每个 Task 一个 `ExecutionObserver`。SSE 正常时，事件只负责触发 Snapshot Refresh；SSE 断开时才启动 2.5 秒默认轮询。两条通道不会长期并行抢写，因此没有两个同等级真源。

Registry 还有三层去重：同一 Task 的并发 `load` 复用 Promise；每个 Task 只有一个 AbortController；Task Event 按 ID 合并并按创建时间和 ID 排序。任务进入终态后 Observer 停止，最后一次 Snapshot 标记是否做过终态复查。

这种设计增加了一次查询，但把 Task Row、Wait Context 和 Event History 的完整状态放在同一响应中。若未来 Task 事件量很大，可以让 SSE Reducer 直接更新稳定字段，并降低 Snapshot Refresh 频率；当前规模下优先保证收敛容易验证。

## 7. 过期请求怎样被阻止

Research 和 Artifact 都会出现“用户先选 A，马上改选 B，A 的慢响应最后回来”。只看请求完成时间无法判断哪个结果有效。

`LatestResearchRequestGate` 和 `LatestArtifactRequestGate` 按通道保存 AbortController。新请求开始时取消同通道旧请求，并返回一个 Lease：

```text
isCurrent = not aborted
            and request.workspaceId == currentWorkspaceId
            and controller is still the channel owner
```

只有 `isCurrent()` 为真才 Dispatch。Workspace 变化时取消全部通道并重建领域状态。Research 将 History、Run、Checkpoint 和 Comparison 分成独立通道，选择新 Run 时取消旧 Run、Checkpoint 和 Comparison；Artifact 将 Job 列表和 History Detail 分开，浏览历史不会阻塞 Job 刷新。

Abort 只用于节省浏览器与服务端资源，正确性来自 `isCurrent` 二次检查。网络栈可能无法真正取消已经到达服务器的请求，或第三方 Promise 不支持 Abort；仅调用 `abort()` 仍可能让旧结果进入回调。

## 8. 乐观更新、幂等和当前缺口

发送消息时前端先追加用户消息，POST 失败后按最近匹配项回滚。成功后追加带 `answerRunId` 的 Assistant Placeholder，再由 Store 按 Run 更新。这样用户不必等待创建 Run 后才看到自己的输入。

服务端 Turn 合同支持 `client_request_id` 幂等，但当前 `useChatSessionController` 使用 `${mode}-${Date.now()}` 生成 ID。它能区分当前点击，不能在页面刷新、手工重试或多个标签页之间稳定复用同一次语义提交。面试时应主动说明：服务端幂等 Ledger 已有，前端跨刷新幂等仍需补齐。

目标实现是点击时生成 `crypto.randomUUID()`，连同 Payload Hash 和本地草稿身份保存到 `sessionStorage` 或 IndexedDB；在请求结果未知时继续复用同一 ID 查询或重试，明确新建语义 Turn 后才换 ID。不能只把 `Date.now()` 换成 UUID，若每次重试仍生成新 UUID，幂等问题没有解决。

当前回滚也按角色和文本寻找最近消息。同一文本连续发送时存在误删风险。更完整的做法是乐观 Message 使用本地 `clientMessageId`，POST 返回后与服务端 Message ID 绑定，失败按身份删除。

## 9. Research 和 Artifact 的历史状态

Research State 同时保存 Run List、当前 Run、选中的 Checkpoint、比较 Checkpoint 和恢复来源 Checkpoint。切换 Run 时先清空旧详情和对比，避免页面在新请求等待期间把旧 Run 内容标成新 Run。请求返回时以 Detail 中真实 `research_run_id` 再次确定当前身份。

Artifact State 保存最新 Version 与用户选中的历史 Version，两者不是一个对象。浏览旧版本不能改写当前 Head；Rollback 返回新权威 Version 后，Reducer 才同时更新最新和当前选择。写回 Source 与写回类型按 Version Key 记录，避免旧 Version 的回执显示到新版本。

这两块都使用 `revision` 触发派生视图刷新，但 Revision 只是前端呈现版本，不是服务器乐观锁。真正的 Artifact Version No、Research Checkpoint No 和 Head Version 仍由后端契约仲裁。

## 10. 浏览器内存、背压和渲染性能

流式 Delta 每个 Token 都触发 React 更新会造成大量渲染。当前事件可以是文本块而非逐 Token，Store 又将状态按 Run 隔离。规模继续增长时，可以在浏览器用 `requestAnimationFrame` 或 30 到 50 毫秒窗口聚合 Delta，再更新消息；终态、错误和 Citation 不应被长时间批处理。

事件历史不能无限保存在组件树。Answer Event ID 使用有界集合，Task History API 有数量上限，Research 时间线应做分页或窗口化。长 Markdown 渲染可以按稳定段落增量解析，避免每个 Delta 重新解析全文；历史版本和 Checkpoint Diff 可按需加载。

SSE 每域连接数、代理缓冲和后台标签页节流也要考虑。当前 Conversation 使用一条聚合流，Task 按活跃任务建立 Observer。若同时跟踪大量任务，应改为 Workspace 级 Task Mux 或服务端聚合流，避免浏览器建立数十条连接。

## 11. 学校场景演练

学生在同一个工作台里提交课程问答，同时查看一个 Research Run 和上一版讲义 Artifact：

1. Conversation SSE 已建立并完成 Snapshot 追平。
2. 学生提交问题，前端先显示用户消息，后端创建 Run。
3. 第一段回答先从 SSE 到达，Store 按 Run ID 缓冲；POST 返回后 Assistant Placeholder 直接使用缓冲内容。
4. 网络断开，Client 保留 Cursor 并退避；Task Observer 启用 HTTP 轮询。
5. 学生切换到另一个 Research Run，旧详情请求被 Abort，`isCurrent` 再阻止晚到响应。
6. SSE 重连带 Last Event ID，重复事件按 Event ID 和 Run Sequence 收敛，最终请求 AnswerRun Snapshot。
7. 学生浏览 Artifact v2 时，后台最新 v3 刷新不会覆盖历史选择；执行回滚后以后端返回的新 Version 更新 Head。

## 12. 指标和计算方式

| 指标 | 公式或采集点 | 意义 |
| --- | --- | --- |
| Stream Connect Latency | 开始订阅到收到 Conversation Snapshot | 页面何时真正追平 |
| Reconnect Recovery P95 | 断线发现到 Snapshot 恢复完成 | 网络抖动后的可用性 |
| Duplicate Event Rate | 被 Event ID 或 Sequence 拒绝的事件 / 收到事件 | 重放和多路投递程度 |
| Sequence Gap Rate | 检测到 Run Sequence 缺口的 Run / 活跃 Run | 是否需要主动补快照 |
| Snapshot Correction Rate | Snapshot 与本地状态不一致次数 / Reconcile 次数 | 增量层漂移程度 |
| Stale Response Reject Count | `isCurrent=false` 的完成请求数 | 用户快速切换带来的竞态 |
| Optimistic Rollback Rate | 提交失败并回滚次数 / 提交次数 | 入口可靠性和错误体验 |
| Client Idempotency Reuse | 结果未知后复用原 ID 的重试 / 结果未知重试 | 前端幂等是否真正闭环 |
| Active SSE Connections | 按页面、Workspace、流类型计数 | 浏览器与网关连接压力 |
| Render Batch Size | 每次 UI Commit 聚合的字符或事件数 | 流畅度与显示延迟取舍 |
| Terminal Reconcile Mismatch | 终态 Snapshot 与流终态不一致次数 | 流协议或读模型问题 |

前端性能不能只报 Lighthouse。该工作台更应看发送到首段可见的 TTFT、长回答期间主线程 Long Task、重连恢复、旧响应拒绝和状态收敛。

## 13. 4 到 5 分钟标准主回答

NoteWeave 前端的主要复杂度来自长生命周期资源和异步顺序。会话回答、Task、Research Checkpoint 和 Artifact Version 的数据通过 POST、查询和 SSE 以不同顺序到达。一个回答的第一段 Token 可能早于发送接口返回，用户切换 Run 后旧请求可能最后完成，网络重连还会重复回放事件。如果直接把最后返回的数据写进 `useState`，页面很容易被旧响应覆盖，或者把重复 Delta 追加两遍。

我先规定四类状态的优先级。服务器 Snapshot 是完整状态真源，领域 Event 决定业务过程，Conversation SSE Entry 只负责低延迟订阅投影，乐观状态只改善交互，View Model 只做展示派生。AnswerRunStore 用 Map 保存一个 Conversation 下多个 Run，每个事件必须有 Run ID 和单调 Run Sequence；`source_event_id` 与全局 Event ID 做短期去重，Run Sequence 防止旧事件回退，终态后拒绝晚到修改。

会话进入时先建立聚合 SSE。Reconnecting Client 收到事件后推进 Cursor，断线采用有上限的指数退避，重连请求带 Last-Event-ID。HTTP 连接建立并不代表已追平，只有收到 Conversation Snapshot 才把连接标成 Ready。发送接口和 SSE 存在竞争时，Store 先按 Run ID 缓冲事件，POST 返回后 Placeholder 直接读取缓存；SSE 不可用时使用单 Run 流回退，结束后仍查询 AnswerRun Snapshot 校正。空的查询快照不会擦掉已经展示的流式内容，避免短暂读延迟造成闪回。

Task 使用另一套 Execution Registry。每个活跃 Task 有一个 Observer，SSE 正常时只在事件到达后刷新 Snapshot，断线时才启动轮询，所以不是两个真源同时抢写。同一 Task 的并发加载会复用 Promise，Event 按 ID 合并，终态后停止 Observer。Research 与 Artifact 不适合用同一套顺序规则，它们使用按通道 Request Gate。新 Run、Checkpoint 或历史 Version 请求开始时取消同通道旧请求，响应回来后还要检查 Controller 仍是当前通道 Owner、Workspace 仍匹配，才能 Dispatch。Abort 节省资源，`isCurrent` 才保证正确性。

乐观发送先显示用户消息，失败再回滚。这里我会主动承认一个当前边界：服务端 Turn 支持 clientRequestId 幂等，但前端现在用 Mode 加时间戳，只能覆盖单次点击，刷新后重试不会复用原语义 ID。下一步会在点击时创建 UUID 和本地 Message Identity，在结果未知期间持久化并复用，直到查到已有 Turn 或用户明确开始新提交。当前按文本回滚也应改成按本地 Message ID 删除。

性能方面，Conversation 用一条聚合流减少连接，Event ID 集合有界，Task History 有上限。长回答规模增长后再按动画帧或短时间窗批量提交 Delta，并对历史列表做分页和虚拟化。验证时不只做组件截图，还测试重复 Event、乱序 Sequence、终态后晚到 Delta、Last-Event-ID 重连、Workspace 切换取消和 Snapshot 校正。指标看 TTFT、Reconnect Recovery、Stale Response Reject、Snapshot Correction 和主线程 Long Task。

当前实现能证明多 Run Store、游标重连、终态保护、断线轮询、Request Gate 和对应测试；跨刷新幂等、本地草稿身份持久化、Sequence Gap 主动补偿、大量 Task 的 Workspace 级聚合流和生产浏览器性能仍需继续补全。

## 14. 重点知识点：增量事件与权威快照怎样收敛

### 3 分钟回答

事件流和快照解决不同问题。事件流告诉前端刚发生了什么，延迟低、数据小，但可能重复、乱序、断线和缺口；快照告诉前端某个时点的完整业务状态，恢复简单，但频繁查询成本高，也可能受到读副本延迟影响。可靠前端通常让事件负责推进体验，让快照负责恢复和校正。

NoteWeave 的事件至少有两级身份：Conversation Event ID 用于连接游标，Run Sequence 用于单个回答内排序。重连时 Last-Event-ID 让服务端从持久记录续播，浏览器先按 Event ID 去重，再拒绝不大于 Run 水位的事件。终态是吸收态，晚到 Delta 不能修改。收到 Conversation Snapshot 或主动查询 AnswerRun 时，再把完整内容、状态和错误合入 Store。

快照也不能无条件覆盖。流式内容已经到达，而查询快照因聚合延迟暂时为空时，直接覆盖会让页面文字消失；旧请求返回的新鲜快照，对当前 Workspace 而言仍然是过期数据。因此 Reconcile 需要资源身份、请求所有权和字段级规则。服务端终态通常高于本地运行态，空内容不应擦除非空内容，Citation 可以保留已去重的增量，真正冲突则记录 Correction 指标并重新拉取。

若检测到 Sequence 从 7 跳到 10，不能简单接受 10 后继续。可以暂停该 Run 的增量显示，请求 `afterSequence=7` 的事件补齐，或直接拉 Snapshot 并把水位更新到服务端高水位。具体选择看事件是否承载不可从快照恢复的过程信息。NoteWeave 的用户可见最终内容能从 Snapshot 恢复，过程审计则需要服务端事件历史。

## 15. 二阶追问

### 为什么不用原生 EventSource

原生 EventSource 自动重连方便，但自定义认证 Header、统一 API Client、精确 Abort 和测试 Fetch 流时限制较多。当前 Client 用 Fetch 读取 SSE，可以显式发送 Last-Event-ID 和认证信息。代价是要自己解析 Chunk、退避和连接状态。若认证改成 Cookie 且浏览器兼容优先，原生 EventSource 仍是合理选择。

### Event ID 有界集合淘汰后，旧重复事件会不会再次生效

会话级短期去重集合不是唯一保护。单 Run 还有单调 Sequence，已终结 Run 还有吸收态，重复旧事件即使 Event ID 被淘汰也会因 Sequence 不增长被拒绝。若某类事件没有 Run Sequence，就必须依赖稳定游标、业务幂等键或 Snapshot，不应只依赖 2048 个内存 ID。

### 两个标签页同时发送同一问题怎么办

相同文本不等于同一语义提交，默认应创建两个 Turn。只有它们共享同一个持久 clientRequestId 时才收敛为一个。跨标签页可以用 BroadcastChannel 协调 Draft Identity，但也要允许用户明确重复提问。服务端唯一约束是最终仲裁，前端协调只是减少误操作。

### AbortController 能保证服务端取消吗

不能。Abort 通常终止浏览器等待和连接，服务端可能已经收到请求并继续执行。前端正确性依赖 `isCurrent`，业务取消需要独立的 Cancel API、服务端状态迁移和向 Worker/Provider 传播。页面卸载只取消订阅，不应隐式取消长任务。

### React StrictMode 会不会建立两条 SSE

开发环境 Effect 可能执行挂载、清理、再挂载。Client 的 `start/stop` 必须幂等，Cleanup 要 Abort 旧连接并清状态。服务端订阅本身是只读，多建连接不能触发多次生成。测试应统计活动 Client 和 Cleanup，生产环境还要观察每会话连接数。

### 为什么 Snapshot 空内容要保留本地内容，会不会掩盖真实删除

该规则只适用于 AnswerRun 生成与终态聚合窗口，不能作为通用删除语义。真正删除应有显式 Tombstone、Revision 或 Redaction Event。若服务端明确返回 `content_redacted=true` 或更高 Revision 的空内容，前端必须清除。没有版本和删除标志时，空字符串无法区分尚未聚合与有意清空。

### Sequence Gap 怎样自动修复

Store 记录 expected Sequence。发现大于 expected+1 时标记 Run 为 `RECOVERING`，暂停继续拼接，调用事件历史或 AnswerRun Snapshot。恢复响应携带高水位，成功后原子替换内容和水位，再处理缓存中更高 Sequence；超时则保留可见内容并显示恢复状态。当前 Store 只拒绝旧序列，主动 Gap Recovery 属于目标增强。

### 流式回答很长时怎样避免卡顿

将 Delta 先追加到非 React Buffer，每 30 到 50 毫秒或每个动画帧合并一次；Markdown 只重新解析未稳定尾部，已完成段落缓存 AST；Citation 和终态立即刷新；历史消息使用虚拟列表。批处理窗口增加少量显示延迟，需要用主线程 Long Task、每秒 Commit 次数和字符可见延迟一起调。

## 20. 重点知识点：跨刷新幂等和过期请求怎样闭环

### 3 分钟回答

前端生成一个 UUID 还不等于幂等。用户点击发送后，POST 可能已经到达服务端，但浏览器在响应前刷新；如果 UUID 只存在组件内存，刷新后会生成新 ID，服务端只能把它当成新 Turn。完整方案需要持久提交账本，按 Workspace、Conversation 和本地 Draft Identity 保存 `clientRequestId`、Payload Hash、创建时间、发送状态和服务端 Receipt。

发送前先把 Payload 的稳定序列化 Hash 与 ID 写入本地账本，再显示乐观消息。结果明确成功后绑定 Turn、Message 和 Run；明确失败且服务端保证未受理时可以结束记录；网络超时或页面退出属于 UNKNOWN，重试必须复用原 ID 和相同 Payload。若用户修改问题或资料范围，Hash 改变，应创建新 ID，不能拿旧幂等键提交不同语义。服务端唯一约束负责最终仲裁，前端账本只保证刷新后仍知道该查询还是重试。

多标签页需要区分意外重复与用户有意重复。BroadcastChannel 可以广播正在发送的 Draft Identity 和 Receipt，减少双击或两个标签页恢复同一草稿；但两个标签页独立输入同一句问题，默认仍是两个 Turn。任何跨标签协调都不能代替服务端 `(actor, conversation, clientRequestId)` 唯一约束与 Request Hash 冲突检测。

过期读请求是另一类问题。AbortController 只能停止浏览器等待，服务器可能继续执行，Abort 也可能晚于响应。每个 Workspace/Run/Version 通道使用递增 Generation 或 Controller Identity，响应回来后同时校验当前 Workspace、目标 ID、Generation 和期望 Version。只有全部匹配才能写 Store。状态更新还要遵守终态吸收和 Snapshot 优先级，旧详情即使内容合法，也不能覆盖用户刚切换的新 Run。

验证要覆盖刷新前 POST 已到达但响应丢失、刷新前 POST 尚未发送、两个标签页复用同一 ID 但 Payload 不同、切换 Workspace 后旧请求晚到、Abort 与响应同时完成。指标看 Client Idempotency Reuse、Duplicate Turn、Unknown Submission Recovery、Stale Response Reject 和 Optimistic Rollback。当前跨刷新提交账本与 BroadcastChannel 仍是 `[目标设计]`，面试中只能把现有 Request Gate 和服务端幂等作为 `[当前实现]`。

### 二阶追问：本地存储被清理后还能保证幂等吗

不能保证客户端继续复用原 ID。服务端可以通过短期查询接口、最近未决 Submission 或用户确认减少重复，但无法仅凭相同文本判断是否同一语义动作。产品可以在结果未知时提示用户恢复最近提交，不应悄悄把相同问题永久去重。

### 二阶追问：为什么不用请求内容 Hash 直接当幂等键

同一问题允许用户有意重复生成，内容 Hash 会错误合并；不同上下文、资料范围和策略下相同文本也不是同一请求。随机 Client Request ID 表示用户动作，Payload Hash 只用于检测同一 ID 被复用为不同内容，两者职责不同。
