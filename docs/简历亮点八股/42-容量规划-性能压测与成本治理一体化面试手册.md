# 容量规划、性能压测与成本治理一体化面试手册

> 定位：这篇回答“系统能扛多少、瓶颈在哪里、十倍流量怎么办、怎样压测、怎样控制模型成本”。主回答 4 到 5 分钟；工作负载建模、排队与资源链、压测方法、成本治理分别准备 3 分钟；二阶追问可独立展开。默认配置只证明保护意图，不能当作生产容量结论。

## 1. 先给面试官的 60 秒回答

我不会给 NoteWeave 报一个脱离场景的统一 QPS，因为上传解析、同步 QA、Research 和 Artifact 的资源模型完全不同。QA 是低延迟、读密集、Provider 驱动；Research 是分钟级、Fan-out、多次 Search/Read/LLM；Artifact 是长任务、CPU/内存/对象存储和模型混合；上传还会形成解析与索引回填突发。

容量规划先用到达率、服务时间和 Little's Law 估算在途量，再把每类任务映射到线程池、Hikari、Kafka 分区、Worker、Provider Permit、ES、对象存储和 SSE。真正容量是这些约束的最小值，不是 Java 线程数。压测采用固定数据和 Provider Stub 建基线，再做真实 Provider 小流量校准，观察 P50/P95/P99、吞吐、错误、降级、Queue Age、恢复斜率和单位有效产出成本。十倍流量时先减少重复工作与不必要 Fan-out，再分池、背压和水平扩容，最后才是增大线程与连接；如果瓶颈是 Provider 429，扩 Worker 只会更贵更慢。

## 2. 四类工作负载必须分开

| 负载 | 用户期望 | 主要资源 | 关键容量指标 | 典型风险 |
| --- | --- | --- | --- | --- |
| 上传/解析/投影 | 尽快可检索 | 网络、对象存储、解析 CPU/内存、Kafka、Embedding、ES | 文件/分钟、MB/秒、Projection Freshness | 大文件内存峰值、回填挤占在线检索 |
| 同步 QA | 秒级首个有效结果 | Servlet/Answer IO、Hikari、ES、Embedding、Rerank、LLM、SSE | QPS、P95/P99、首结果时间、Grounded Success | Provider 尾延迟、线程或连接等待 |
| Research | 分钟级可信报告 | Coordinator、Kafka、Worker、Search/Read/LLM、预算、Checkpoint | Run/小时、Queue Age、Verified Claim/小时 | Fan-out 放大、Provider 429、长尾与 Lease |
| Artifact | 分钟级可下载产物 | Worker CPU/内存、LLM、渲染器、对象存储、Callback | Accepted Artifact/小时、文件大小、Repair Rate | 大对象、渲染并发、回调结果未知 |

“系统支持 100 QPS”如果不说明是哪条路径、请求大小、质量要求、Provider 是否 Mock、持续多久和错误阈值，基本没有意义。面试回答至少给出 Workload、环境、数据集、并发模型、持续时间和验收条件。

## 3. 容量推导的基本模型

### Little's Law

稳定系统中：

```text
L = lambda * W
```

`L` 是平均在途数量，`lambda` 是平均到达率，`W` 是平均停留时间。若 `[演练假设]` Research 每分钟到达 2 个，平均端到端 3 分钟，则平均约 6 个在途 Run。它不是容量承诺，因为长尾、突发、失败重试和多 WorkItem Fan-out 会扩大分布。

### 利用率和排队

```text
Utilization rho = arrival_rate / service_capacity
Headroom = 1 - rho
```

当利用率接近 1，平均吞吐看似很高，但排队和 P99 会非线性恶化。线上交互路径不能以 100% 利用率为目标。具体安全水位由服务时间方差、突发程度和恢复要求决定，不从教科书拍一个固定百分比。

### 并行任务的放大

Research Run 不是一次 Provider 调用：

```text
Provider calls per Run
  = sum(work_item_count_by_type * calls_per_work_item_type)
  + candidate_calls
  + verification_calls
  + synthesis_calls
  + retry_calls
```

`MATRIX_CELL`、`CLAIM_INVESTIGATION`、`OPEN_QUESTION`、`TIMELINE_EVENT` 和 `SOURCE_AUDIT` 的调用画像不同，容量估算按 WorkItem 类型分桶。比较型 Run 拆成多个 Matrix Cell 并行后，用户延迟可能下降，但瞬时并发、Token 和 Search 成本会上升。平均调用数必须和 P95 调用数一起看，避免少数复杂问题吃完配额。

### 最小瓶颈

```text
Effective Capacity = min(
  admission_limit,
  executor_capacity,
  db_capacity,
  kafka_partition_capacity,
  worker_capacity,
  provider_capacity,
  storage_capacity
)
```

某一层扩容后，瓶颈会转移。20 个 Hikari 连接、16 个 Answer IO 最大线程和 4 个 Workspace 并发上限不能相加，也不能直接推出 QPS。

## 4. NoteWeave 当前参数怎样正确解释

`[当前实现]` 默认参数反映本地/保护性配置：Hikari 最大连接数 20、最小空闲 4、连接等待 30 秒；Answer IO 核心 4、最大 16、队列 64；调度池 4；Workload Quota 默认每 Workspace/Workload 并发 4、Lease 300 秒；LLM 超时 60 秒；Embedding 查询超时 10 秒、批处理 60 秒；Rerank 超时 20 秒；上传最大请求 128 MB。

这些数字不能直接用于简历宣传，原因包括：

1. 默认值可能只是开发环境起步值，没有持续压测证据。
2. 一个 QA 可能持有线程但不持有数据库连接，也可能错误地在事务内等待 Provider，资源占用方式不同。
3. Provider 默认可能未启用或使用本地 Stub，延迟和限流与生产不同。
4. Workspace 并发 4 是治理上限，不是 Worker 能稳定处理 4 个复杂 Run 的证明。
5. 128 MB 是接纳上限，不代表应用能同时解析多个 128 MB 文件。

正确说法是“当前有这些保护边界，我会通过负载模型和压测 Manifest 推导生产值”。

## 5. 一条 QA 请求的资源链

```text
HTTP request
  -> Controller / validation
  -> Hikari: Workspace ACL、Conversation、Snapshot
  -> ES / retrieval
  -> optional Embedding
  -> optional Rerank
  -> LLM
  -> Answer Event persistence
  -> SSE delivery
```

端到端延迟可以拆为：

```text
Ttotal = Tqueue + Tdb + Tretrieval + Tembed + Trerank + Tllm + Tpersist + Tstream
```

不能把各组件 P95 直接相加当端到端 P95，因为慢请求不一定是同一批样本。需要 Trace 或请求级时间戳计算真实端到端分布。优化时按 Critical Path，而不是按所有阶段耗时总和排序。

线程池与 Hikari 的关系也不能一比一。网络调用应在 Answer IO 等有界执行器中，数据库事务尽量短；若线程在持有连接时等待 60 秒 LLM，20 个连接很快耗尽。即使线程池有 16 个线程，也可能因为连接、Provider Permit 或 SSE 写入压力只得到更低有效并发。

## 6. Research 和 Artifact 的资源链

### Research

```text
Run Admission
  -> ResearchRun + ExecutionAttempt
  -> Coordinator 生成 Typed WorkItem
  -> Outbox/Kafka
  -> Worker Claim + Lease
  -> Provider Permit
  -> Search/Read/LLM
  -> Candidate/Verifier/Checkpoint
  -> Completion Commit
```

Research 的瓶颈经常不是单次调用时长，而是 Fan-out 和长尾。控制变量包括各类 WorkItem 数量、Candidate 数、WorkItem 与 Fetch 并发、Provider Permit、预算、超时、重试和 Checkpoint 频率。默认只让独立 I/O 有界并发，达到独立性、预算和 Provider 水位条件后才启用 Wave/Barrier。并行度继续提升会因 429、合并冲突、数据库提交和上下文膨胀而降低单位成功吞吐。

### Artifact

```text
Kafka Command
  -> Consumer 校验并幂等登记 Durable Execution
  -> Commit Offset
  -> Scheduler Claim + Execution Lease
  -> Content Worker / Provider
  -> Candidate + Content Contract Validation
  -> Host DELIVERY_PENDING Version + Frozen Required-file Manifest + Candidate Receipt
  -> DeliveryAttempt / Renderer
  -> Staging File + Contract Validation
  -> Required Files READY + Delivery Receipt
  -> Version READY
```

Kafka Consumer 只承担毫秒到秒级的持久接纳，不能在 Poll 生命周期里执行 PDF、PPT、转写或模型长调用。合法命令登记 Durable Execution 后提交 Offset；永久 Schema 或身份错误持久化 `command_rejection` 并进入 DLT 后提交；数据库不可用和事务结果未知不提交。Kafka Lag 反映接纳链路是否落后；Durable Execution Queue Age、Active Permit 和各 Resource Class 利用率才反映小时级执行容量。Offset 提交后的可靠性来自 MySQL 中的 Execution、幂等 `command_id`、Scheduler 和 Reconciler，不来自超长 `max.poll.interval`。

Artifact 还要考虑不同 Skill 的资源画像。纯 Markdown 生成主要受 LLM 和对象存储影响；PDF、PPT 或媒体处理会增加 CPU、内存、临时磁盘和渲染器并发。不能为所有 Skill 共用同一 Worker 并发值。应该给 Skill 或 Resource Class 标注 `cpu_weight`、`memory_weight`、`provider_weight` 和最大输出大小，再由调度器分池或加权接纳。内容 Contract 通过后就冻结 `DELIVERY_PENDING` Version 和全部必需文件清单，文件尚未开始、失败或取消都继续留在 File Ready Rate 分母中，避免通过延迟创建 Manifest 美化交付容量。

## 7. Timeout、Retry、Lease、线程池和连接池怎样联动

超时不是越短越好，重试也不是越多越可靠：

```text
Worst-case occupied time
  ~= attempts * request_timeout
   + sum(backoff)
```

若 LLM 超时 60 秒、重试 3 次且线程一直阻塞，单请求最坏占用可能超过 180 秒；线程池队列 64 会把失败转成更长等待。需要区分连接超时、读取超时、端到端 Deadline 和用户 Deadline，并把剩余时间向下游传播。下游剩余时间不足时不再发起新重试。

Domain Execution Lease 要覆盖正常 Heartbeat 间隔、允许漏报数、调度抖动和最大暂停，但不能被外部超时无限拖长。Worker 等待 Provider 时仍要 Heartbeat，提交时继续检查 Fencing。MySQL Admission Reservation 限制 Workspace 已接纳的未终结任务，Redis Active Permit 限制真正占用 Worker 或 Provider 的任务，Domain Execution Lease 负责提交权。WAITING 保留 Reservation，释放 Active Permit，恢复时重新竞争执行槽。三者不能合并成一个并发数字。

数据库连接只在执行 SQL/事务时持有，不能跨 Provider 调用。线程池拒绝策略要和入口背压一致：交互请求可以快速失败或降级；已经持久化的任务不能因内存队列满而静默丢弃，应保留在持久队列等待 Worker。

## 8. 压测方法：先证明模型，再追峰值

### 第一阶段：单组件基线

分别测 MySQL 关键查询、ES 检索、Embedding、Rerank、LLM Stub、对象存储和渲染器。目的是获得服务时间分布和资源曲线，不声称端到端能力。

### 第二阶段：固定端到端回放

使用版本化数据集、固定 Query、固定 Source 大小和确定性 Provider Stub，验证应用自身的排队、线程、连接、Kafka、状态机和恢复。Stub 延迟要包含常态、长尾、429、超时和畸形响应，不能全部立即成功。

### 第三阶段：真实 Provider 校准

小流量调用真实 Provider，记录区域、模型版本、时间段、配额和成本。它用于校准外部延迟和限流，不进行无界峰值压测，也不能把供应商偶然低延迟当长期保证。

### 第四阶段：混合工作负载

按学校场景组合 QA、上传、Research 和 Artifact，验证资源隔离。只压单一 QA 得到的峰值不能回答考试周同时上传和生成讲义时是否稳定。

### 阶梯并发和恢复

每个并发档位保持足够长，使 Queue Age、GC、连接和缓存进入稳态。到达模型至少覆盖恒定速率、突发和慢增长。压到错误率急升后必须观察降载恢复：

```text
Drain Rate = completion_rate - arrival_rate
Estimated Drain Time = backlog / Drain Rate
```

若降载后 Queue Age 不下降，说明存在死锁、毒任务、下游长期不足或恢复逻辑缺失，峰值 QPS 再高也没有意义。

## 9. 压测验收指标

| 维度 | 必看指标 | 不能只看什么 |
| --- | --- | --- |
| 用户延迟 | P50/P95/P99、首结果、端到端完成时间 | 平均值 |
| 吞吐 | Accepted、Completed、Valid Output/秒 | HTTP 请求数 |
| 正确性 | Grounded Answer、Verified Claim、Accepted Artifact | 200 比例 |
| 饱和度 | Executor Active/Queue、Hikari Pending、Kafka Lag、Durable Execution Queue Age、Active Permit、Provider Permit | CPU |
| 可靠性 | Retry、DLT、Lease Lost、Stale Completion、Unknown Outcome | 最终失败数 |
| 降级 | Degraded Rate、拒答率、Fallback 类型 | 总成功率 |
| 恢复 | Oldest Queue Age、Drain Rate、恢复到 SLO 的时间 | 压测停止时间 |
| 成本 | Token、Search、Embedding、Rerank、Storage、单位有效产出 | 单请求 Token |

压测 Manifest 至少保存 Git Commit、配置摘要、环境规格、数据集版本、Provider 模式、流量模型、预热、持续时间、指标查询、失败样本和原始报告哈希。没有 Manifest 的“提升 40%”难以复现。

## 10. 成本不能只看 Token

### 成本构成

```text
Total Cost
  = LLM input/output token cost
  + Embedding cost
  + Rerank cost
  + Search/Read provider cost
  + Object storage and transfer
  + Compute and database cost
  + retry and repair waste
```

Research 的 Search 和 Read 可能按请求计费，Artifact 的大文件会有存储和传输，重复 Embedding 会浪费批处理资源。只报 Token 会错过一半以上的治理对象。

### 单位有效产出

```text
Cost per Grounded Answer = QA 总成本 / 通过依据门禁的回答数
Cost per Verified Claim = Research 总成本 / 通过 Verifier 的 Claim 数
Cost per Successful Run = Research 总成本 / 有效终态 Run 数
Cost per Accepted Artifact = Artifact 总成本 / 观察窗口内有明确用户接受动作、且达到 READY 并可下载的 Version 数
```

单位“成功 HTTP 请求”的成本没有业务意义。一个便宜但无依据的回答、一个生成后无法打开的 PDF，都不应进入有效产出分母。

### 边际收益

候选数从 2 增加到 4，质量可能只提升 1%，成本却接近翻倍。应做配对实验：同一 Gold Case 比较 Quality Lift、Latency Delta 和 Cost Delta，得到：

```text
Marginal Efficiency = quality_gain / incremental_cost
```

达到收益拐点后停止扩大 Fan-out，复杂 Query 再由分类器分配更高预算。

## 11. 十倍流量的判断顺序

1. 明确哪类 Workload 十倍，是到达率、数据量、租户数还是单任务复杂度十倍。
2. 用生产分布或固定回放重算 `lambda`、服务时间和在途量，而不是整体乘十。
3. 消除重复调用、无效 Retry、重复 Embedding、N+1 查询和过度 Fan-out。
4. 隔离交互 QA、Research、Artifact 和回填任务，建立独立队列、Permit 和资源池。
5. 在入口做背压和公平调度，防止单 Workspace 形成无限积压。
6. 根据瓶颈扩对应层：加分区、Worker、ES Shard、Provider 配额或数据库能力。
7. 做故障与降载恢复演练，验证十倍负载撤掉后能否清空积压。

垂直扩大线程池通常排在后面。线程增加只在 CPU、连接、Provider 和内存仍有余量时提高吞吐，否则只增加排队位置和上下文切换。

## 12. 四种瓶颈的不同方案

### Provider 429

缩小 Provider Permit，按 `Retry-After` 与带抖动退避，减少 Candidate/Fan-out，启用替代 Provider 或明确 Waiting。不能加 Worker 硬冲；重试也要进入预算。

### Kafka Lag 增长

先判断到达率是否高于持久接纳速率、分区是否热点、幂等登记是否被数据库拖慢、是否有毒消息。Consumer 不执行慢外部调用，只校验命令、幂等登记 Durable Execution，然后提交 Offset。若 Kafka Lag 低但 Execution Queue Age 上升，瓶颈在 Scheduler、Worker、Provider 或 Resource Class，扩 Consumer 没有帮助。只有接纳链路本身饱和且 Key 顺序允许时才增加分区和 Consumer。

### MySQL 锁等待或 Hikari Pending

查慢 SQL、索引、锁顺序、事务范围和连接持有时间。Provider 调用不能放事务里。确认 MySQL 有余量后才扩连接池；否则更大的池会放大锁竞争。

### ES 重建或 Embedding 回填

回填与在线检索分队列、限速和资源池，使用 Generation 物理索引和按环境、索引族或租户桶管理的 Alias。构建开始时冻结 Catalog Watermark，期间的上传、更新和删除进入 Change Log；全量回填结束后先 Catch-up 到发布水位，再检查覆盖、语义质量和租户隔离，最后 Promote。回填吞吐不能以牺牲在线 P99 为代价，也不能因为活跃 Workspace 新增一条资料就从头重建。

## 13. 重点知识点一：为什么默认配置推不出 QPS

### 3 分钟回答

QPS 本质上由服务时间、资源占用和并发上限共同决定。线程数只告诉我最多有多少线程同时工作，不告诉我每个请求占用多久，也不告诉我是否等待数据库连接、Provider Permit 或网络。相同 16 个线程，如果请求平均 100 毫秒且不阻塞，理论吞吐和请求平均 10 秒时相差两个数量级。

NoteWeave 的路径差异更大。同步 QA 可能有一次检索和一次 LLM；Research 会展开多种 WorkItem、Candidate、Verifier 和 Synthesis，其中比较型任务才使用 Matrix Cell；Artifact 的 PDF Skill 可能使用渲染器和大对象存储。Hikari 最大 20 只能说明连接池保护边界，前提是数据库事务短；若代码持有连接等待 LLM，20 个连接很快耗尽。Workspace 并发 4 只是租户治理，也不代表全局稳定并发。

所以容量结论必须包含工作负载、请求大小、Provider 模式、质量门禁、持续时间和错误阈值。我先用 Little's Law 估在途量，再用阶梯压测找到第一个饱和点，同时观察完成吞吐而不是接纳吞吐。最终把 Commit、配置、数据集、环境和报告哈希写入 Manifest。默认配置可以用于解释设计意图，但不能写成“支持 X QPS”。

### 二阶追问：理论上可以用 `threads / latency` 算吗

可以做粗略上界，但只适合单一、稳定、线程全程占用且没有其他瓶颈的模型。真实系统有队列、异步 IO、连接池、外部配额和长尾，必须用压测校准，并给安全余量。

### 二阶追问：为什么完成吞吐比请求吞吐重要

接口可能快速返回 202，把工作留在队列。接纳 QPS 很高但完成速率低，只会增加 Queue Age。异步系统容量以长期完成吞吐和积压稳定为主。

## 14. 重点知识点二：排队、长尾和背压

### 3 分钟回答

当到达率接近服务能力时，系统不是线性变慢，而是排队快速增长。平均服务时间看似稳定，用户 P99 却会因为队列、重试和共享资源竞争恶化。长任务分布通常重尾，少数复杂 Research 会长期占用 Permit，因此只看均值会低估并发需求。

背压的目标是让过载可控地暴露，而不是把所有请求接收后在内存中等待。NoteWeave 的长任务先持久化 Task，再由 Quota 限制 Workspace 在途量；Provider Permit 约束真正外部调用；WAITING 表达依赖暂不可用。交互 QA、Research、Artifact 和索引回填应分池，避免长任务队头阻塞短请求。

队列不是免费容量。队列越大，失败发现越晚，用户等待越长，任务执行时输入可能已经过时。入口拒绝要给明确 Retry-After；已接纳任务则必须通过状态和事件可恢复。扩容判断看 Queue Age、完成速率、利用率和错误率，不能因为 CPU 低就继续接纳，系统可能被 Provider 或连接池限制。

### 二阶追问：队列容量应该怎么定

从最大可接受等待时间和稳定完成吞吐反推：`queue_limit <= completion_rate * max_wait_time`，再用突发模型和任务大小校准。还要限制单 Workspace 份额，避免一个租户吃满全局队列。

### 二阶追问：优先级队列能解决长短任务冲突吗

只能部分解决。严格优先级会饿死低优先任务；单一 FIFO 有队头阻塞。更适合按 Workload 分池，再在 Workspace 间做加权公平或 Deficit Round Robin，并保留总资源护栏。

## 15. 重点知识点三：怎样设计可信压测

### 3 分钟回答

可信压测先固定实验对象。每次记录代码 Commit、配置、机器、数据集、Provider、缓存状态、预热、持续时间和到达模型。只给一个并发数和平均 QPS 无法复现。NoteWeave 还要固定 Source 大小、Query 类型、Research WorkItem 类型与数量分布、Artifact Skill，因为这些直接决定调用放大和内存占用。比较型数据集还要单独记录 Matrix 行列规模。

第二是逐层测。单组件基线用于定位服务时间，固定 Stub 的端到端回放用于测应用自身，真实 Provider 小流量用于校准外部延迟，最后才是混合负载。Stub 不能全是零延迟成功响应，要注入 P95/P99、429、超时、重复回调和结果未知，否则测试不到 Lease、Retry、Receipt 和背压。

第三是验收不只看峰值。达到目标吞吐时，P95/P99、错误、降级、Grounded/Verified/Accepted 质量和单位成本都要在阈值内。压测结束后观察 Queue Age 清空和系统回到 SLO 的时间。最终报告保留原始直方图和失败样本，避免只展示最好的一分钟。

### 二阶追问：闭环压测和开放模型有什么区别

闭环模型中虚拟用户等上一个请求完成再发下一个，系统变慢时到达率自动下降，容易掩盖排队；开放模型按独立到达率发请求，更接近突发用户流量。两者都可用，但容量和过载测试应包含开放模型。

### 二阶追问：缓存预热后压测是否作弊

不是，但必须分开报告冷启动和稳态。考试周或发布后可能遇到冷缓存，长期运行看稳态。只报热缓存最好结果会高估上线能力。

## 16. 重点知识点四：成本治理为什么与质量一起看

### 3 分钟回答

Agent 成本不是单次 LLM Token，而是 Search、Read、Embedding、Rerank、模型、存储、计算以及 Retry/Repair 的总和。降低调用次数如果让 Verified Claim 或 Accepted Artifact 大幅下降，不叫优化；提高质量如果靠无界 Fan-out，也不能持续。

我会把成本分摊到有效业务产出：QA 用通过证据门禁的回答，Research 用 Verified Claim 或 Successful Run，Artifact 用校验通过且可下载的 Version。再对 Candidate 数、Rerank、Verifier、模型档位和 Context 长度做配对实验，计算增量质量除以增量成本。达到边际收益拐点后，不再对所有请求扩大预算，而是用 Query Complexity 或 Risk Tier 分层。

预算还要和运行治理联动。Run 开始 Reserve 上限，每次可信 Provider 调用计入 Usage，终态 Settle，未使用额度 Release；Retry、Repair 和重复回调必须避免重复计费。成本异常时先判断输入增长、重试风暴、模型切换还是 Fan-out 参数变化，再决定降级，不能只给用户硬截断导致产物无效。

### 二阶追问：缓存会不会让成本指标失真

会，因此同时报逻辑请求成本与实际付费成本，并记录 Cache Hit。不同实验必须使用一致的缓存策略，或分冷/热两组。缓存节省也要扣除存储、失效和错误命中风险。

### 二阶追问：怎样防止预算账本重复扣费

每次外部操作使用稳定 Operation ID 和 Receipt，Reserve/Settle 条件更新，重复回调返回已有结算。结果未知先查询 Receipt 或 Provider 状态，不立即创建新 Operation。

## 19. 常见二阶追问

### CPU 只有 30%，为什么不能继续加流量

系统可能等待 Provider、数据库连接、Kafka 分区或对象存储，CPU 不是唯一饱和资源。看 Queue Age、线程状态、Hikari Pending、Permit、网络和依赖延迟。低 CPU 加 Worker 可能只放大外部限流。

### P95 达标但 P99 很差，是否可以上线

取决于请求量、用户旅程和最坏损失。Research 少量长尾可能占用大量 Permit 并拖慢所有任务；安全和数据损坏不能用 P95 掩盖。分析 P99 的类型、可降级性和错误预算，再决定门禁。

### Kafka 多加分区就能线性扩容吗

不能。Key 顺序、热点 Key、Consumer 外部依赖、数据库写入和 Rebalance 都会限制扩展；分区增加也有 Broker 与运维成本。先确认 Consumer 可并行且下游有余量。

### 为什么不使用无界虚拟线程解决阻塞

虚拟线程降低线程栈和调度成本，但不会增加数据库连接、Provider 配额和内存。无界并发会更快耗尽下游。即使用虚拟线程，也需要 Semaphore/Permit、Deadline 和背压。

### 连接池应该和线程池一样大吗

不必。只有访问数据库的短阶段需要连接，线程可能执行网络和序列化。按数据库并发、事务时间和 MySQL 能力独立推导，观察 Pending 和持有时长校准。

### 压测时 Provider 产生真实费用怎么办

大规模用契约一致的 Stub 和录制分布，真实 Provider 只做受预算保护的小流量校准，明确禁止对第三方做未授权压力测试。成本本身也是压测停止条件。

## 23. 4 到 5 分钟标准主回答

面试中如果问 NoteWeave 能扛多少，我不会直接报统一 QPS，因为这个系统有四种完全不同的负载。上传解析受文件大小、CPU、内存、对象存储、Embedding 和 ES 回填影响；同步 QA 关心秒级首结果，受连接池、检索、Rerank、LLM 和 SSE 影响；Research 是分钟级 Fan-out，会展开不同类型的 WorkItem、Candidate、Verifier 和 Synthesis；Artifact 又会因 Markdown、PDF、PPT 等 Skill 有不同的模型、CPU、内存和文件成本。

我的第一步是建模。对每类 Workload 记录到达率、服务时间和分布，用 Little's Law `L=lambda*W` 估平均在途量，再把请求映射到 Answer IO、Hikari、Kafka 分区、Worker、Provider Permit、ES 和对象存储。有效容量取所有约束的最小值。比如当前 Hikari 最大 20、Answer IO 最大 16、队列 64、Workspace 长任务并发 4，这些只能说明保护边界，不能相加或直接推出 QPS。若线程在事务里等待 60 秒 LLM，连接池会先耗尽；若 Provider 429，CPU 再空也没有容量。

第二步是控制排队和放大。Research 按 WorkItem 类型统计调用画像，Run 调用量是各类 WorkItem、候选、验证、合成和重试之和。默认只并发独立 Fetch，工作单元确实独立且 Provider 与预算有余量时才开启 Wave。入口使用 MySQL Admission Reservation 控制 Workspace 未终结任务数，Redis Active Permit 控制真实 Worker 或 Provider 占用，Budget 控制总消费；WAITING 保留 Reservation 但释放 Active Permit，恢复时重新竞争。当前 Research 的 429 仍按有限重试和失败分类处理，完整 Waiting/Resume 属于 `[目标设计]`。交互 QA、Research、Artifact 和索引回填分池，超时、重试、Execution Lease 和 Deadline 联动，数据库连接不跨 Provider 调用持有。

Artifact 的消息接纳与长任务执行分开。Kafka Consumer 校验命令并幂等登记 Durable Execution 后就提交 Offset，Scheduler 再领取执行；因此 Kafka Lag 衡量接纳，Execution Queue Age 和 Resource Class 衡量执行。检索回填也不直接重建后切 Alias，而是冻结 Catalog Watermark，用 Change Log 追平增量，再对 Generation 做 Release Gate。

第三步是压测。我先测 MySQL、ES、Provider 和渲染器基线，再用版本化资料、Query 和 Provider Stub 做端到端回放。Stub 不只返回成功，还模拟长尾、429、超时、重复回调和结果未知。之后用真实 Provider 做受预算保护的小流量校准，最后混合 QA、上传、Research 和 Artifact 做阶梯并发。验收不仅看峰值 QPS，还看 P50/P95/P99、有效完成吞吐、Queue Age、Hikari Pending、Kafka Lag、Execution Queue Age、Lease Lost、降级率、Grounded Answer、Verified Claim、Accepted Artifact 和降载后的恢复斜率。

第四步是成本。总成本包含模型 Token、Embedding、Rerank、Search/Read、对象存储、计算以及 Retry/Repair 浪费。我不会算每个 HTTP 200 的成本，而是算每个 Grounded Answer、Verified Claim、Successful Run 和 Accepted Artifact。对 Candidate 数、模型档位、Verifier 和 Context 长度做配对实验，比较质量增量与成本增量，到边际收益拐点后只给复杂或高风险 Query 更高预算。

十倍流量时先明确是哪种负载或单任务复杂度增长，然后去掉重复 Embedding、无效 Retry、N+1 和过度 Fan-out，隔离资源池并建立背压与公平调度，再按真实瓶颈扩 Kafka、Worker、Provider 配额、ES 或数据库。Provider 429 时加 Worker 只会更慢；MySQL 锁等待时加连接会放大竞争；ES 回填则应限速并与在线检索隔离。所有可宣传数字都必须绑定 Commit、配置、环境、数据集、Provider 模式、流量模型和报告哈希。当前代码能证明参数入口、治理机制和部分指标，真实全校规模、生产 QPS、长期成本和十倍容量仍需要正式压测与生产数据验证。
