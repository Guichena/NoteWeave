# 面试推荐架构与规模化演进裁决

> 本文回答一个问题：如果不受当前源码历史包袱限制，NoteWeave 在面试中应该选择什么设计。源码事实仍按原文档标记；本文给出推荐设计、简化路径、升级条件和迁移代价。出现冲突时，面试方案以本文为准，真实实现能力仍以代码和事实标签为准。

## 1. 总体原则：按任务风险选择架构，不让所有请求走最重链路

系统提供三档执行剖面：

| 剖面 | 适用任务 | 主要机制 | 不启用什么 |
|---|---|---|---|
| Lite | 短问答、单资料摘要、低风险草稿 | 冻结输入、一次生成、确定性格式检查、结果版本 | Matrix、双候选、全局语义 Judge、Checkpoint |
| Structured | 多资料比较、讲义、题集、可恢复长任务 | Typed WorkItem、Evidence、局部验证、Task Lease、阶段 Checkpoint | 默认多 Agent、所有字段双候选、强人工审核 |
| High Assurance | 对外报告、高风险事实、需要审计或写回的任务 | 独立来源、风险分级验证、异构 Judge 或人工抽检、预算、完整 Manifest | 无界探索、自动发布、未确认外部副作用重试 |

选择剖面的输入包括任务持续时间、事实风险、来源范围、是否产生外部副作用、是否要求恢复和是否需要人工发布。复杂机制必须由一个可观察问题触发，不能因为系统已经实现就默认开启。

面试主线应先讲 Structured，再说明 Lite 如何降级、High Assurance 如何增强。这样既能展示深度，也不会让学校项目显得从第一天就堆满基础设施。

## 2. Research：统一 ResearchPlan，不把所有问题压成 Matrix

### 2.1 推荐领域模型

```text
ResearchRun                 用户的一次稳定研究意图
  -> ExecutionAttempt       一次执行代际或恢复尝试
  -> ResearchPlan           版本化计划
       -> WorkItem[]         可验收工作单元
  -> Evidence[]             归档且带来源身份的证据
  -> Claim[]                由证据支持或反驳的原子结论
  -> ReportVersion          最终交付版本
```

`WorkItem` 使用带类型的联合模型：

| WorkItem 类型 | 适用任务 | 验收方式 |
|---|---|---|
| `MATRIX_CELL` | 多方案、多维度比较 | 字段覆盖、来源支持、冲突状态 |
| `CLAIM_INVESTIGATION` | 验证一个事实或因果判断 | 支持、反驳、不充分 |
| `OPEN_QUESTION` | 探索尚未确定的子问题 | 发现结果、后续分支、停止理由 |
| `TIMELINE_EVENT` | 事件演进和时间线 | 时间、主体、来源和顺序一致性 |
| `SOURCE_AUDIT` | 法规、官方文档、关键来源核验 | 身份、版本、时效和直接性 |

Matrix 仍是比较型任务的优秀 Planner，但不再是所有 Research 的领域真源。Planner 先根据任务类型选择模板，再生成 WorkItem。计划修订通过 `plan_revision` 和 WorkItem Diff 表达，不靠向矩阵无限加行列。

共享的 WorkItem Envelope 只保存 `work_item_id`、类型、依赖、风险级别、预算授权、状态和类型化载荷引用。每一种类型由自己的 Contract Adapter 解析载荷、判断完成条件并生成可解释 Receipt；不允许在共享表里堆一个任意 JSON，再让所有调用方自行猜测字段。这里的 Seam 是稳定运行合同，Adapter 承担真实且不同的验收语义。

`OPEN_QUESTION` 必须在创建时绑定停止合同：最大墙钟时间、最大成本或 Token 预算、最大分支数、连续低收益窗口、完成验收和允许的终态。新增合格 Evidence 连续两个探索批次低于阈值，或任一硬预算耗尽后，Planner 只能把 WorkItem 收敛为 `COMPLETED`、`ABSTAINED` 或 `INSUFFICIENT`，并记录触发规则、未解问题和停止理由，不能继续无界 Replan。`COMPLETED` 仍需满足类型化验收，不能只因为时间用完就算完成。

### 2.2 Run 与 Attempt 必须分开

基础设施恢复、Worker 接管和 Checkpoint 续跑只创建新的 `ExecutionAttempt`，继续属于同一个 `ResearchRun`。Attempt 保存 Epoch、Owner、Lease、Checkpoint、Provider 配置、本代新增消费和执行统计；Run 持有总预算，恢复不能通过新增 Attempt 重置额度。

以下情况才创建新 Run：用户改变研究目标、资料范围或交付要求；用户明确重新运行并希望保留两个独立结果；从旧结果创建分支研究。这样用户采用、取消、成本和成功率都以稳定 Run 统计，执行故障则按 Attempt 统计。

### 2.3 并发从依赖图产生，不从角色数量产生

默认调度器按 WorkItem 依赖和风险顺序执行，Search/Fetch 等 I/O 可以有界并发。只有满足以下条件才开启 WorkItem 并发：工作单元没有依赖；Provider Permit 有余量；预算允许；来源策略不会产生重复搜索；合并拒绝率低于门槛。

`Wave/Barrier` 只在真实 Fan-out/Fan-in 出现时启用。单 Agent 并发为 1 时使用阶段游标和依赖计数，不维护空转 Barrier。角色只是执行配置，例如调查、反证和来源审计，不是用多个聊天人格模拟组织结构。

### 2.4 验证按风险分级

```text
L0 确定性门禁
  身份、权限、Snapshot、数字、单位、时间、引用定位

L1 单次语义验证
  Claim 与 Evidence 的支持、反驳和不充分判断

L2 独立复核
  异构模型、独立来源、盲审或人工抽检
```

Local 和 Global 表示验证责任，不强制等于两次模型调用。低风险字段可能只用 L0；普通研究使用 L0 加有争议 Claim 的 L1；高风险结论才进入 L2。生成模型不能在没有独立校准的情况下给自己最终背书。无法稳定判断时返回 `ABSTAIN/INSUFFICIENT`，不靠增加反思轮次制造确定感。

## 3. Artifact：传输、执行和交付使用三个独立提交点

### 3.1 Kafka Consumer 不执行小时级任务

> 事实边界：本节是推荐架构，不是当前 Artifact Consumer 的实现描述。当前 Python Consumer 在提交 Offset 前直接调用 Artifact Executor，并通过较大的 `max_poll_interval` 覆盖长任务和 MCP 超时。面试时必须先承认这个当前限制，再说明为什么把“快速登记 Durable Execution + Scheduler 执行”作为下一步演进，不能把推荐方案说成已经上线。

推荐链路：

```text
Kafka Command
  -> Consumer 校验 Schema 和 Command ID
  -> MySQL 幂等登记 Durable Execution
  -> Commit Offset
  -> Scheduler 领取 Execution
  -> Worker Lease + Heartbeat
  -> Candidate Callback
  -> Host Commit
```

Consumer 只做毫秒到秒级的持久接纳，不占着 Offset 等待 PDF、转写或模型执行。命令重复由 `command_id` 唯一约束吸收。小时级任务的业务提交权由 Domain Execution Lease、Epoch 和 Fencing 管理，不由 Kafka Consumer Session 管理；Admission Reservation、Active Permit 和 Budget Reservation 分别只表达持久接纳、瞬时资源占用和预算授权，不共享这个 Fencing 代次。

快速提交 Offset 不等于捕获所有异常后 ACK。可解析且合法的命令先登记 Durable Execution；永久 Schema、身份或版本错误先写入带消息位置、摘要和原因的 `command_rejection`，再投递 DLT 或进入人工 Redrive，最后提交 Offset；数据库不可用、事务结果未知等临时错误不提交 Offset。原始 Payload 可能含敏感输入，拒绝记录默认保存 Digest 和受控摘要，不复制完整内容。这样毒消息不会永久堵住分区，临时故障也不会被静默吞掉。

这样一个慢任务不会阻塞同分区后续命令，Consumer 可以正常 Rebalance，任务超时也不需要把 `max.poll.interval` 调到一小时。代价是需要 Scheduler 和 Execution Reconciler，但项目已经拥有持久 Task，因此这比让 Kafka 同时承担队列和执行租约更清晰。

### 3.2 Host 预分配唯一 Version ID

```text
ArtifactJob              用户意图
  -> ArtifactRun         一次生成、再生成或追加式回滚请求
  -> ExecutionAttempt    基础设施执行、恢复或接管代际
  -> ReservedVersionId   Host 预分配的交付身份
  -> Worker Candidate    内容、引用、文件候选和 Trace
  -> ArtifactVersion     Host 验证后提交
  -> ArtifactFile[]      绑定同一个业务 Version ID
```

用户改变要求、参数或资料范围并发起再生成时创建新 `ArtifactRun` 和新 Version ID；Worker 重启、租约接管、Checkpoint 恢复或相同输入的基础设施重试只创建新 `ExecutionAttempt`，继续绑定原 Run 和 Version ID。Worker 可以保存临时执行记录，但不能创建另一套业务 Version ID。所有文件、审批、写回、Receipt 和 API 都绑定 Host 的 `artifact_version_id`。调试仓储使用 `attempt_id`，不能伪装成业务版本库。

预分配只保留身份，不代表产物已经交付。ArtifactRun 持久化唯一 `reserved_version_id` 和 Reservation 状态；该 ID 初始处于内部 `RESERVED` 阶段，此时还没有 `artifact_version` 业务行，也不进入用户版本列表。内容 Contract 通过后，Host 才在同一事务用该 ID 建立 Version 并冻结全部必需文件 Manifest，进入不可下载、不可写回的 `DELIVERY_PENDING`；所有必需文件达到 `READY` 后，Version 才原子提升为用户可见的 `READY`。首轮内容前取消只终结 Run 和 Reservation，不创建空 Version；交付开始后文件重试耗尽进入 `DELIVERY_FAILED`，显式重试可带同一 Version ID 回到 `DELIVERY_PENDING`，取消或超过保留期则把 Version 置为 `ABANDONED`。已经 `READY` 的 Version 不再接受取消或状态倒退，用户只能归档、删除或追加式回滚；已经执行的外部写回使用 Receipt 和显式补偿 Proposal 处理。每次文件物化使用新的 `delivery_attempt_id` 和 Staging Key，保留错误、Checksum、对象 Receipt 和时间线；重试只能重物化同一不可变内容，若内容变化必须创建新 ArtifactRun 与 Version ID。ID 不回收、不复用，只有 `READY` 能下载、采纳或写回。

指标资格由实际到达的阶段决定，不能仅凭最终状态删分母。所有已接纳 Run 都进入固定 Cohort 的严格接纳完成率，取消、失败和超期未完成分别单列；已经完成首轮生成并接受内容 Contract 判定的 Candidate 进入 First-pass Yield；内容 Contract 通过后，系统立即冻结 Delivery Contract，其中声明的全部必需文件进入 File Ready Rate 分母，即使物化尚未开始，或最终进入 `DELIVERY_FAILED`、`ABANDONED`，也不能从分母移除；只有 `READY` Version 进入采纳率的合格分母。这样既不会让空预留 ID 污染内容质量，也不会通过不创建失败文件记录抬高成功率。

### 3.3 先验证，再产生可执行副作用

推荐提交顺序：

```text
冻结输入
  -> 生成结构化 Candidate
  -> 内容 Contract
  -> Host 提交不可见 DELIVERY_PENDING Version
  -> 创建全部必需文件的 PENDING Manifest
  -> 在隔离区导出必需格式
  -> 文件 Contract
  -> 晋升对象并更新文件 Manifest
  -> 所有必需文件 READY 后提升 Version 为 READY
  -> 创建发布或写回 Proposal
  -> 审批与 Expected Revision 校验
  -> 执行写回
```

内容 Contract 通过后，Host 先把不可变内容提交为不可见的 `DELIVERY_PENDING` Version，并一次性创建全部必需格式的 `PENDING` Manifest。随后每个 DeliveryAttempt 使用独立 Staging Key 导出和验证文件；对象晋升、Checksum 与可读性复核完成后，对应文件才标记 `READY`。所有必需文件都 `READY` 后，Version 才提升为 `READY`。这样导出在第一步失败时仍有稳定交付义务、失败记录和重试身份。失败 Staging 文件由 TTL 或清理任务回收。写回预览可以提前生成，可执行写回请求必须绑定 `READY` Version，不能只等待 Version 行创建。外部目标写入带 Idempotency Key 和 Expected Revision，结果未知时先查询 Receipt，不直接重放。

## 4. Memory：显式偏好和模型推断采用不同信任路径

推荐分成三层：

| 层 | 内容 | 写入路径 | 默认生命周期 |
|---|---|---|---|
| Session Context | 当前会话约束、Raw Tail、Summary | 会话状态机 | 会话或 Segment |
| Explicit Memory | 用户明确要求记住的偏好和规则 | 窄 Scope 校验后立即生效，可撤销 | 跨会话 |
| Derived Memory | 模型从行为或对话中推断的偏好 | Candidate、风险评估、Review、Promotion | 审核后跨会话 |

显式 Memory 只有在内容涉及高风险事实、跨 Workspace 传播或敏感信息时才要求人工审核。普通的“这个课程以后都用三级标题”可以在当前 User/Workspace Scope 直接创建 Active Revision，同时提供撤销入口和审计事件。

保存、导出、重试和编辑只能作为弱 Outcome Signal。它们可以调整排序先验或进入离线复核，不能单独证明某条 Memory 正确，也不应自动 Promotion、Revoke 或覆盖显式规则。明确的用户纠正和撤销拥有更高优先级。

## 5. Task 与 Quota：接纳身份和执行槽分开

```text
Admission Reservation
  在 MySQL 中记录一个 Workspace 已经接纳多少未终结长任务

Active Permit
  控制当前真正占用 Worker/Provider 的任务数

Budget Reservation
  控制一次 Run 最多消费多少资源

Domain Execution Lease
  控制哪个 Worker 拥有提交资格
```

任务进入 WAITING 时保留 Admission Reservation，释放 Active Permit；恢复时重新竞争 Active Permit。这样 Provider 配置缺失的任务不会占住实际执行槽，租户也不能无限堆积等待任务。Reservation 只有在 Task 终态、取消或显式等待到期事务提交时关闭，Redis TTL 不能改变已接纳业务事实。

四种对象只有可识别、幂等关闭和可观测是共同要求。Admission Reservation 跟随持久 Task，不靠 TTL 自动消失；Active Permit 可以过期回收；Budget Reservation 使用预留、消费、结算和释放账本；只有拥有业务提交权的 Domain Execution Lease 需要单调 `lease_epoch`、`fencing_token`、Owner 和 Heartbeat。给 Quota Permit 增加一个下游不校验的 Fencing Token，只会混淆资源占用与业务写权限。

通用 Task 负责用户状态，Domain Execution 负责执行权。两套状态机不直接暴露给每个调用方，而是收进一个 `RunLifecycle` 深模块：

```text
accept(admissionRequest) -> TaskRef
observe(taskRef) -> TaskSnapshot
requestCancel(cancelRequest) -> CancellationDecision
recordDomainDecision(taskRef, completionDecisionRef) -> TaskTransitionReceipt
```

Research 与 Artifact 是这个 Seam 上的两个真实 Adapter，分别解释领域完成合同、取消传播和结果引用。`completionDecisionRef` 只引用领域已经持久化的裁决，稳定字段包括领域对象身份、Expected Task Version、Disposition、Result Ref、Source Event ID 和 Receipt ID，不携带 Evidence、文件或任意业务 JSON。`RunLifecycle` 内部负责 Task/Domain 映射、Admission Reservation、持久事件、终态仲裁和 Reconciler。完成合同已经满足且不存在仍可产生必需副作用的 Execution 时，模块才推进 Task 终态；Task 取消后，Adapter 不得创建新副作用。前端、Controller 和通用 Task 查询只依赖这一小组 Interface，不需要理解 Cell、Wave、Artifact File 或 Fencing 字段。

## 6. 检索投影：Generation 发布，不为每个 Workspace 建长期 Alias

推荐使用共享或租户分桶的物理索引：

```text
qa-chunk-g{generation}
note-source-g{generation}

文档字段包含 workspace_id、source_id、snapshot_id、schema_version
查询必须下推 workspace_id 和授权范围
```

Alias 按环境、索引族或租户桶管理，不按每个 Workspace 无限增长。`ReleaseManifest` 保存 QA 与 Note 使用的 Generation、Schema、Embedding、Catalog Watermark 和兼容关系。只有两类投影必须保持同代语义时才原子成组发布；一类退化不应无条件拖垮另一类。

全量回填使用稳定 Catalog Watermark，构建期间的上传、更新和删除各写入一条 Change Log。事件只要求在同一发布域内有单调顺序，例如索引族或租户桶，不要求全系统无关 Workspace 共享一个总序列。每条事件携带稳定 `change_id`、Source、Snapshot、操作类型和顺序；Generation 以 `(generation, change_id)` 幂等应用，删除使用 Tombstone，重复投递不能复活旧 Snapshot。新 Generation 只消费同一条 Change Log，不为每个 Generation 复制写入变更事件。Backfill 完成后按 Watermark 追平增量，再做短窗口校验和 Alias 切换。这样活跃 Workspace 不会因为任意一次上传而从头重建，也不会用全局热点换取不需要的跨域顺序。

```text
PREPARE -> CATCH_UP -> EVALUATE -> PROMOTE -> OBSERVE
```

结构覆盖、语义质量 Receipt 和安全不变量必须在 PROMOTE 前形成强制门禁。Alias 已切但数据库结果未知时，Reconciler 读取真实 Alias 指向并按 Operation ID 收敛，不能盲目重复切换。

## 7. SSE：一个事实事件，多种订阅投影

每次状态变化只由拥有该不变量的聚合写一条权威领域事件：Task 拥有接纳、取消请求和用户可见状态，Research/Artifact/AnswerRun 拥有各自结果与执行事实。若 Task 终态由领域完成驱动，Task 投影必须引用原 `source_event_id`，不能再创造一条语义独立的“领域已完成”事实。Conversation 或 Workspace 流同样只是异步投影。

“一次事实事件”不等于“一张万能事件表”或“所有领域共用同一个 Payload”。共享 Event Envelope 只包含 `event_id`、聚合身份、聚合内序号、事件类型、Schema Version、时间和 Payload Digest；Research、Artifact、AnswerRun 与 Source 使用各自版本化 Payload 和权限规则。Projector 通过 Adapter 生成订阅投影，未知 Schema 进入隔离和告警，不能按空字段继续消费。

```text
Domain Event Log
  -> Outbox/Projector
  -> ConversationStreamEntry(source_event_id, cursor, view_payload)
  -> Redis 实时通知
  -> SSE
```

`source_event_id` 和投影唯一约束防止同一领域事件被重复物化。Run Sequence 负责聚合内顺序，Conversation Cursor 只负责订阅位置，不要求跨 Run 全局业务排序。

实时桥采用确定的无缺口握手：先建立通知订阅并记录高水位，再回放数据库到该水位，最后消费订阅期间缓存的新事件；或者使用支持游标的日志流直接追平。不能只写“再次检查或先订阅再回放”而不确定实现算法。客户端仍以 Snapshot 校正完整状态，Delta 按字符块或短时间窗持久化，避免逐 Token 写数据库。

## 8. Outbox、Kafka 和工作流框架的升级条件

学校早期版本可以使用 MySQL Task Queue 或 Polling Outbox，适合单集群、任务量低、消费者少的场景。出现以下需求后再引入 Kafka：多类独立消费者；需要保留和重放；积压需要独立扩容；需要按分区观察延迟；数据库轮询成为明确瓶颈。

继续使用自研状态机的条件是流程短于小时级、Timer 和人工 Signal 少、状态转换稳定、团队能够维护对账。出现跨天 Timer、大量人工暂停、补偿分支持续增加、Workflow Versioning 成为发布负担，或者 Durable Execution 故障处理已经主导工作流代码时，再评估 Temporal。动态图编排和 Agent 节点生态成为主要变化点时，再评估 LangGraph。框架替换调度与恢复，不替代 Workspace ACL、Evidence、Artifact Version 和领域真源。

## 9. 迁移优先级：先修语义，再优化成本，最后处理规模

| 优先级 | 改造 | 为什么先做 | 迁移与回滚 |
|---|---|---|---|
| P0 | Run/Attempt 分离、Host 唯一 Version ID、写回顺序、领域事件单真源、RunLifecycle interface | 这些问题会污染业务身份、审计和外部副作用，流量很小也会发生 | 先双写兼容字段和映射，由 Lifecycle Adapter 包住旧状态机；读路径切到新 interface，回滚只切读，不删除旧记录 |
| P0 | Kafka 快速登记 Durable Execution | 长任务绑定 Consumer Session 会阻塞分区并放大 Rebalance，当前 70 分钟协议已经暴露结构性风险 | 新旧 Consumer 按 Schema Version 分流，登记表与旧 Delivery Token 并存；确认无旧任务后下线长 Poll |
| P1 | Explicit/Derived Memory 分流、Admission Reservation/Active Permit 分离 | 直接改善用户控制感、等待槽利用率和错误归因 | 先 Shadow 记录新决策，比较 Review、撤销和 Permit 指标；策略开关可退回旧门控 |
| P1 | Typed WorkItem 与分级 Verifier | 降低 Matrix 对开放问题的限制，并把验证成本放到有风险的 Claim | 先将现有 Cell 映射为 `MATRIX_CELL`，保持旧 API；新类型逐个灰度，不一次迁移全部 Planner |
| P2 | Generation、Watermark、Change Log Catch-up 与分桶 Alias | 解决高频更新下的重复全量构建和 Cluster State 膨胀 | Source 变更只写一条 Change Log；新 Generation 消费同一日志并 Shadow 对账后切 Alias；旧 Generation 保留回切窗口 |

升级条件不使用拍脑袋的固定用户数，而看可观测信号。Matrix 无法表达的任务比例、同 Run 锁冲突和无效 Cell 比例上升时引入更多 WorkItem 类型；双模型验证的成本增量长期高于质量收益时改为风险分级；Kafka 分区被 P95/P99 长任务占住、Rebalance 频繁或 Lag 与执行时长强相关时迁移 Durable Execution；Catalog Drift Abort、回填窗口和 Alias/Shard 数量持续增长时迁移 Generation Catch-up。跨天 Timer、人工 Signal 和补偿分支成为主要故障来源后，再考虑 Temporal，不因为“长任务”三个字就先换框架。

## 10. 面试中的五分钟推荐回答

NoteWeave 最初服务学校课程资料，低风险问答和摘要并不需要复杂 Agent。系统先把请求分成 Lite、Structured 和 High Assurance 三档，只有多资料、长时间、需要恢复或需要写回的任务才进入受治理执行。

Research 使用稳定 ResearchRun 和多个 ExecutionAttempt。Planner 不再把所有问题都压成二维 Matrix，而是生成带类型的 WorkItem。方案比较使用 Matrix Cell，开放调查使用 Claim 和 Question，时间型任务使用 Timeline Event。默认单任务调度并允许 Fetch I/O 有界并发，只有工作单元真正独立、Provider 和预算有余量时才启用 Wave 与并行 Worker。验证从确定性门禁开始，普通争议 Claim 才调用语义 Judge，高风险结论再使用异构模型、独立来源或人工抽检。

Artifact 把消息传输、长任务执行和结果交付分开。Kafka Consumer 只把命令幂等登记为 Durable Execution 后提交 Offset，小时级任务由 Scheduler、Execution Lease 和 Fencing 管理。Host 在运行开始时预留唯一 Version ID，该 ID 处于不可见的 `RESERVED` 阶段；Worker 只返回 Candidate。内容 Contract 通过后，Host 就创建不可见的 `DELIVERY_PENDING` Version，并冻结全部必需文件的 `PENDING` Manifest；DeliveryAttempt 随后物化和校验文件，所有必需文件变为 `READY` 后再提升 Version 为 `READY`，最后创建带 Expected Revision 的写回 Proposal。失败的交付进入可重试的 `DELIVERY_FAILED`，取消或超过保留期后进入 `ABANDONED`，ID 永不复用。File Ready Rate 的分母是内容通过时冻结的全部必需文件，尚未启动、失败或取消的文件都不能被排除。

Memory 也按信任来源分层。当前会话内容只进入 Context，用户明确要求记住的低风险偏好可以立即按窄 Scope 生效并支持撤销，模型推断的偏好必须走 Candidate 和 Review。用户保存或重试只能作为弱反馈，不能自动证明某条记忆正确。

资源治理把 Admission Reservation、Active Permit、Budget 和 Domain Execution Lease 分开。WAITING 任务保留持久接纳身份但释放执行槽。检索投影按 Generation 和 Catalog Watermark 构建，回填期间通过 Change Log 追平增量，避免每次上传都让全量构建作废。SSE 只保存一份领域事实，Conversation 流是带 `source_event_id` 的订阅投影。

这套设计的重点不是机制数量，而是每个机制都有触发条件和退出条件。低风险任务可以退回一次生成，高风险任务可以增加独立验证；流量、任务时长和人工流程没有达到阈值时，不提前引入 Kafka、Wave Barrier 或工作流平台。

## 11. 二阶追问

### 为什么稳定 Run 加 Attempt 比恢复创建新 Run 更好

Run 表示用户意图，Attempt 表示基础设施执行。恢复、Worker 接管和 Provider 重试不会改变用户目标，所以只推进 Attempt Epoch。这样取消和采用针对稳定 Run，成本与故障可以按 Attempt 拆分。用户改变输入或主动 Fork 时才创建新 Run，避免把基础设施失败伪装成多次业务请求。

### Consumer 提前提交 Offset，进程随后宕机怎么办

提交 Offset 前必须先在 MySQL 幂等登记 Durable Execution。进程在数据库提交后、Offset 提交前退出，消息会重放并命中同一个 Command ID；Offset 已提交后退出，Scheduler 仍能从 MySQL 找到未执行任务。可靠性来自持久 Task，不来自长时间占住 Offset。

### 为什么不统一成一个万能 WorkItem

统一身份、状态和调度合同，不统一验收语义。Matrix Cell 的完成条件是字段覆盖，Timeline Event 需要时间与顺序，Source Audit 需要版本和权威性。用带类型联合模型可以共享运行时，又不会把业务差异藏进一个任意 JSON。

### 显式 Memory 立即生效会不会被 Prompt Injection 利用

只有经过可信用户动作、窄 Scope、长度和敏感内容检查的显式指令可以走快路径。网页、工具输出和模型建议不能伪装成用户指令。高风险事实、权限政策和跨 Workspace 规则仍必须审核。立即生效不等于无条件写入。

### 共享索引怎样保证多租户安全

`workspace_id` 是查询强制过滤条件，但不能只依赖调用方传参。检索服务从认证上下文构造 Scope Filter，命中后再回业务真源校验 Source/Snapshot Ownership。共享索引减少 Alias 和 Shard 数量，代价是必须把租户过滤、缓存 Key 和 Inspector 权限做成不可绕过的基础能力。

## 12. 本轮设计审查记录：哪些方案看似高级，实际不够合理

下面不是源码功能清单，而是面试推荐架构的裁决记录。回答时先讲问题和约束，再讲为什么选择当前方案；不要把表中的目标设计说成已经全量上线。

| 被否决或需要收缩的设计 | 主要问题 | 推荐设计 | 体现的能力 |
| --- | --- | --- | --- |
| 用 Redis Admission Lease 代表任务已被系统接纳 | TTL 到期会让仍在 WAITING 的持久任务从配额事实中消失；Redis 故障会改变业务真相 | MySQL Admission Reservation 与 Task 同事务，Redis Active Permit 只表达瞬时占用 | 区分业务事实、资源协调和故障恢复 |
| 所有 Lease 共用一套 Fencing Token | Admission、预算和执行权生命周期不同；下游不校验的 Token 没有安全意义 | 只有 Domain Execution Lease 使用 Owner、Epoch、Fencing；其他 Reservation/Permit 各自幂等关闭 | 从不变量而不是名词复用出发 |
| 通用 Task 同时承载 Research Cell、Artifact 文件和 Worker Claim | 状态枚举不断膨胀，前端被迫理解领域内部状态，取消与终态规则散落 | `RunLifecycle` 深模块加 Research/Artifact Adapter；通用 Task 只做用户投影 | 设计小 Interface、把复杂度藏进模块 |
| Artifact JobRun 同时表示用户再生成和 Worker 重试 | 用户意图、执行故障、成本和交付版本无法准确归因 | Job 表示长期意图，ArtifactRun 表示一次不可变请求，ExecutionAttempt 表示执行代际，Version 表示交付结果 | 身份建模、审计和指标归因 |
| Worker 与 Host 各创建一个 Version ID | 文件、审批、回调和业务读取出现双重身份，补偿和回放难以闭合 | Host 预留唯一 Version ID；Worker 只写 Attempt 与 Candidate | 单一业务真源和提交权设计 |
| 回滚时把 Current Pointer 倒拨到旧 Version | 版本时间、已发布引用和写回审计倒退，并发 Head 更新难以仲裁 | 创建 `ROLLBACK` ArtifactRun，追加带 `restored_from_version_id` 的新 Version，Expected Head CAS 后推进 Head | 单调版本历史和并发控制 |
| 文件成功后才创建 Artifact Version 或 Manifest | 导出第一步失败时没有稳定责任对象，失败样本可以从分母消失 | 内容通过后先创建不可见 `DELIVERY_PENDING` Version 和完整 `PENDING` Manifest，再进行 DeliveryAttempt | 交付合同、可恢复性和防指标美化 |
| 所有 Research 都建成二维 Matrix | 开放调查、时间线和来源审计被迫伪装成 Cell，验收语义模糊 | 小型 WorkItem Envelope 加类型化 Contract Adapter；Matrix 只服务比较型任务 | 抽象边界和领域建模 |
| 一个任意 JSON WorkItem 或万能事件 Payload | 表面统一，实质把 Schema 判断扩散给所有调用方，升级无法门禁 | 公共 Envelope 只保存身份、顺序、版本和摘要；领域 Payload 独立版本化 | Schema 演进和深模块意识 |
| Artifact 回调把正文、计划、验证、审批、写回和 Trace 混进一个结果 JSON | Host 难以区分业务真源与 Worker 回显，Schema 漂移扩散，敏感 Trace 可能进入用户版本 | 强类型 ArtifactCandidate Envelope，只携带身份、Digest 和 Content/Validator/Citation/Trace Receipt 引用；Host 验证后投影业务 Version | 深模块、最小信任面和数据最小化 |
| 每个 Workspace 一个长期 ES Alias | Workspace 墾长会放大 Cluster State、Shard 和运维成本 | 环境或租户桶级 Generation，查询强制 Workspace Scope，Change Log 追平 Watermark | 多租户隔离与规模成本权衡 |
| 用户保存或重试就自动晋升 Memory | 行为信号可能表示格式偏好、误触或失败重试，不能证明事实正确 | Explicit Memory 与 Derived Memory 分流，弱行为只进入排序或审核候选 | 信任边界和反馈偏差 |
| 不可变 Input Snapshot 无条件执行到底 | 运行期间发生删除、撤权或安全封禁时，稳定输入会变成继续泄露的通道 | 内容引用保持冻结，另用 Scope/Revocation Epoch 控制工具调用与最终提交资格 | 区分可复现性与持续授权 |
| 编译时 Capability Set 被当作整段长任务的永久授权 | 审批过期、成员撤权、策略收紧或参数替换后仍可能执行副作用 | 编译能力只作上限；每次高风险调用重新与当前 ACL、Policy、Approval、Epoch 求交集，参数 Digest 改变必须新 Proposal | 防 TOCTOU、最小权限和可审计审批 |
| 所有 Claim 都双模型验证 | 成本和延迟线性增加，同源模型错误仍可能一致 | L0 确定性门禁、L1 风险 Claim 语义验证、L2 高风险独立复核 | 风险分级而非堆模型 |
| 因为是长任务就立即上 Kafka、Temporal 或多 Agent | 引入运维、版本迁移和调试成本，但小规模学校场景未必获得收益 | 先用持久 Task/Outbox 和明确状态机，达到 Lag、跨天 Timer、人工 Signal 或动态编排阈值再升级 | 架构适配规模，而不是技术名词堆砌 |

### 12.1 当前实现、推荐设计和生产能力必须分开

面试中的可信顺序是：先说明 `[当前实现]` 能从代码、迁移或测试证明什么；再指出真实限制；然后给出 `[目标设计]`、迁移步骤、灰度门禁和回滚路径；最后把没有真实 Provider、用户或压测证据的成绩标为 `[生产待验证]`。目标设计可以比源码更优，但不能用“我们线上已经”开头，也不能把理想数据卡改写成真实业务收益。

最能体现 Ownership 的说法不是“这些表和类都是我写的”，而是“我识别了哪个业务不变量，比较了哪些失败窗口，为什么拒绝了更简单或更复杂的方案，如何验证迁移没有改变用户可见语义”。项目由本人和 AI 工具共同完成时，还要明确 AI 负责草稿、检索或对照，人负责约束定义、方案采用、代码审查、证据核验和最终结果。

## 13. 高概率二阶追问

### Admission Reservation 的配额行会不会成为数据库热点

学校规模下可以按 Workspace 锁单行计数，因为事务短、写入频率低，语义最容易证明。若单个大租户的接纳 QPS 让锁等待成为 P95 主因，再按 Workload 分片、使用限量 Reservation Bucket 或单写者队列。不能一开始改成 Redis 近似计数，因为那会把准确接纳边界换成难解释的漂移。扩展时仍以 Reservation 明细为审计真源，计数投影可以重建和对账。

### Task 和 Admission Reservation 同事务，Redis Active Permit 怎么避免双写

接纳事务只提交 Task、Reservation 和 Outbox，不申请 Redis Permit。Scheduler 收到持久事实后再竞争 Active Permit；拿到 Permit 但尚未提交领域 Claim 就崩溃，由短 TTL 回收，拿到 Claim 后则由 Domain Execution Lease 判断谁能提交。释放失败不会改变 Task 终态，只产生 Permit Recovery Metric。这样 Redis 只影响何时执行，不影响任务是否存在和结果是否合法。

### 为什么内容通过后就创建 DELIVERY_PENDING，不等文件成功再建 Version

因为内容 Contract 已经形成一个不可变交付义务。先建 Version 与 Manifest，文件第一步失败也有稳定 Version ID、必需文件分母、错误 Receipt 和重试入口；如果文件成功后才建记录，最早失败的样本无法审计，File Ready Rate 也会天然偏高。`DELIVERY_PENDING` 不对用户开放下载或写回，因此不会把半成品伪装成可用版本。

### 一份领域事件怎样支持 Conversation、Workspace 和审计三种视图

领域聚合只提交一次事实事件和 Outbox。不同 Projector 读取同一个 `event_id`，按各自权限、游标和 Payload Schema 生成视图，并用 `(projection_type, source_event_id)` 唯一约束吸收重复。读取端需要跨聚合排序时使用投影 Cursor，不反过来要求所有领域共享全局业务序列。Projector 可重放，领域事实不可由投影回写。

### RunLifecycle 会不会变成另一个万能服务

它只拥有四类稳定责任：Task 与领域对象映射、接纳 Reservation、取消与终态仲裁、事件和对账；不解析 Research Evidence，也不校验 Artifact 文件。领域完成合同通过 Adapter 提供，新增第三个业务类型前要证明它真的需要相同生命周期。如果 Interface 开始出现 `if research`、`if artifact` 字段或任意 Payload，说明 Seam 选错，应把语义退回领域模块。

### 为什么推荐方案不直接照源码讲

源码展示的是在时间和场景约束下形成的当前实现，系统设计题考察的是能否识别约束变化后的更优边界。可靠回答要同时给出当前路径、结构性风险、推荐终态和迁移顺序。只背源码会显得缺少判断，只讲理想架构又无法证明 Ownership；两者之间的差距和演进依据才是项目最有价值的面试内容。
