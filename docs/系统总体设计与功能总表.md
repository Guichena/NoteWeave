# NoteWeave v2 系统总体设计与功能总表

## 1. 目的

这份文档是 NoteWeave v2 的整体设计母文档，用来先锁定三件事：

1. 系统最终长什么样
2. 系统最终拥有哪些功能
3. 功能、亮点、执行链路之间如何衔接

它不展开数据库、接口、Topic、Key、类结构等实现细节，只负责把整体产品形态和系统边界一次讲清楚。

## 2. 一句话总定位

`NoteWeave v2 是一个参考 NotebookLM 产品形态的研究工作台：每个工作台承接一组资料、多次聊天、Wiki 页面、结构化笔记、生成产物和研究任务；用户在同一个聊天界面中选择问答、Note、Wiki 三种回答链路，Deep Research 与右侧产物栏作为独立任务能力存在，其确认后的成果可以像用户上传文件一样回流到当前工作台。`

## 3. 最终产品结构

系统最终不是“四五个割裂页面”的拼装，而是一个以 `研究工作台` 为基本单位的统一产品结构：

- `一个基本单位`
  `研究工作台`

- `三种聊天回答链路`
  `问答`、`Note`、`Wiki`

- `两个独立系统能力`
  `Deep Research`、`右侧产物栏`

- `一个共享资料底座`
  `共享项目级资料池`

- `一套长期沉淀机制`
  `Graduated Memory + Task-Neighborhood Memory Compiler`

- `一套受控扩展能力栈`
  `Agent / Skill / MCP`

这里有一个必须统一的产品判断：

- `研究工作台` 是产品基本单位，承接资料池、多次聊天、Wiki、Note、Artifact、Research Run
- `问答 / Note / Wiki` 不是三个割裂页面，而是同一聊天界面背后的三种回答链路
- 三条链路在聊天区统一采用 `主回答正文 + 证据卡片` 交互，引用、候选资料、原文窗口和摘录证据默认折叠为可点击卡片
- 每个聊天会话拥有自己的上下文、模式选择和运行记录；资料边界默认继承当前研究工作台
- `Deep Research` 不是第四种聊天模式，而是独立重型任务能力
- `右侧产物栏` 不是附属按钮区，而是跨聊天链路的统一产物生成入口
- `共享项目级资料池` 不是某个模式私有资料区，而是整套工作台共用的资料真源

## 4. 顶层界面形态

推荐固定为 NotebookLM 风格的三栏工作台：

```text
左侧：项目资料与导航
中间：统一聊天区
右侧：产物栏与结果区
```

其中：

- 左侧负责 `资料选择 / 范围切换 / 对象导航`
- 中间负责 `多次聊天 / 模式选择 / 引用展示 / 任务发起`
- 右侧负责 `产物动作触发 / 任务进度查看 / 结果回写`

当用户没有显式切换回答链路时，默认落在 `问答` 链路。Wiki 工作台、资料阅读页和 Deep Research 结果页可以作为辅助页面存在，但聊天时不自动跳转。

## 5. 系统功能总表

### 5.1 产品层功能

#### 问答链路

- 围绕当前资料池做低延迟问答
- 支持引用资料、笔记、Wiki 页面和产物
- 支持从当前问答一键发起 `Deep Research`
- 支持从右侧产物栏一键生成报告、FAQ、测验等结果
- 支持把高价值回答保存为结构化笔记

#### Note 链路

- 在同一聊天界面中进入“边回答、边整理、边沉淀”的回答逻辑
- 实现重点直接参考 `Marginalia-style Structured Reading Funnel`
- 先通过资料标题、摘要、标签、历史笔记、结构化元数据和关系信号定位候选资料
- 候选资料召回采用 `coverage-aware metadata rank`，显式考虑 `title / summary / tags / metadata / sample_text` 字段权重与 `query_coverage`
- 历史 Note 会经过 `Journal Freshness Guard`，来源更新后自动降权，来源失效后只作为审计线索保留
- 再通过 `candidate triage + verify batch` 把真正要验证的资料窗口收束出来
- 最后读取原文窗口，抽取可引用摘录并生成带引用回答
- 对外只强调“正常聊天回答 + 依据卡片”：回答正文留在聊天区，额外解释通过 `资料定位 / 深读窗口 / 摘录证据` 卡片展开
- 结构化笔记是回答后的可选沉淀，不是 Note 链路的主职责
- 适合深读资料、做解释对比，并把高价值回答沉淀成有来源、有摘录、有结构的笔记

#### Wiki 链路

- 在同一聊天界面中优先走 `WebKonra / WeKnora` 式全量 Wiki 检索逻辑
- 优先读取 Wiki 页面、页面链接、索引和来源回链
- 回答阶段不只读单页，而是会对命中的多页面网络做综合结论、页面关系和来源回链编排
- 回答中只保留简要依据和 `进入 Wiki 工作台` 按钮
- 用户主动点击后进入默认 Wiki 工作台浏览、编辑和维护页面
- Wiki 页面网络的主更新路径由 `wiki_enabled + wiki ingest / retract` 驱动，人工修补页只作为辅助修正入口
- 当前自动构建的最小正式页面集已经固定为 `资料页 + 概念页 + Wiki Index`
- 页面正文会做轻量 `Auto Link` 互链回写，`rebuild-links` 也会刷新老页面的正文互链与关系边
- 这里的 Wiki 能力是为研究工作台聊天服务的轻量知识网络，不演化成独立企业 Wiki / CMS 平台
- 默认 Wiki 工作台先展示工作台总览，再进入页面阅读；总览优先展示构建状态、最近资料变化、最近更新和页面类型分布
- 最近 Wiki 任务、维护提醒、问题过滤、日志和手动补页能力保留在 Wiki 工作台的辅助维护区，不再从聊天页直接暴露修补入口
- Wiki 工作台会显式展示 `待处理任务 / 自动补缺 / 人工确认` 三类运行态提示，辅助判断当前工作台的构建与维护状态
- 维护提醒可直接跳转相关页面，页面视图会继续展示问题建议、最近变更和图谱关系
- Wiki 图谱支持 `overview / ego` 两种视角、按页面类型过滤，以及从图谱搜索直接跳到页面或子图
- Wiki 治理会区分 `可自动修复` 与 `需人工确认` 两类问题，Auto Fix 只处理低风险问题
- 适合基于稳定知识网络回答，而不是自动把聊天变成 Wiki 页面

#### Deep Research

- 作为顶栏或上下文中的独立按钮存在
- 可从当前聊天、选中资料、Wiki 工作台上下文或资料多选上下文发起
- 是显式长任务，不与普通对话混在一起
- 必须最终产出一份 `研究报告`
- 研究报告经用户确认后可进入当前研究工作台，供后续聊天、Wiki、Note 和产物生成继续使用

#### 右侧产物栏

- 面向当前研究工作台资料池展示可直接触发的产物动作
- 默认内置 `报告 / FAQ / 测验 / 学习指南 / Wiki 页面 / 结构化笔记`
- 支持用户新增自定义产物形式
- 支持先产出 `Markdown`，再导出 `MD / PDF`
- 结果可保留为 Artifact，也可回写到主链路

### 5.2 资料层功能

#### 共享项目级资料池

- 统一承接用户上传文件
- 承接 URL、文本和后续扩展导入
- 承接被确认纳入的研究结果与关键来源
- 作为三种聊天回答链路、Deep Research 和右侧产物生成的统一检索底座

#### 资料对象统一

系统内需要明确区分以下对象：

- `资料`
  用户上传或系统确认纳入的工作台资料对象

- `Artifact`
  由右侧产物栏或研究能力生成的产物对象

- `Note`
  面向个人整理与阶段沉淀的工作对象

- `Wiki`
  面向长期维护的稳定知识对象

#### Research 结果分层

Deep Research 的产物需要拆成两层：

- `研究过程资产`
  包括搜索结果、网页快照、抓取文本、证据片段、checkpoint、trace；默认只服务当前研究任务，不直接进入主检索链路

- `确认后资料成果`
  包括最终研究报告、被引用的关键网页快照、被确认纳入的来源；可以进入共享项目级资料池

这层划分很重要，因为系统不能把研究过程噪声和正式知识对象混在一起。

### 5.3 执行层功能

#### Deep Research 执行链路

Deep Research 智能体的核心能力是：

- 把开放式问题转成显式 `Research Run`
- 在 `Research Table` 上维护外部执行状态
- 按 `Search -> Read -> Extract -> Verify -> Revise` 受控循环推进
- 在证据不足、来源冲突、路径过强时做修复、回退或分支探索
- 最终产出可引用、可回写、可沉淀的研究报告

当前建议把它对外概括为：

- `验证驱动的 Deep Research 智能体`
- 详细架构关键词使用 `Verification-Centric Research Harness`

#### 右侧产物执行链路

右侧产物栏背后不是一组 Prompt，而是一套统一产物执行系统：

- 通过 `Production Action` 抽象不同产物类型
- 通过 `Style Profile` 承接风格、结构、受众和篇幅配置
- 通过 `Skill Graph` 组织生成所需技能子链路
- 通过 `Schema-Gated Skill Graph Runtime` 保证执行受控
- 必要时调用内置能力或用户自有 MCP

### 5.4 回写与沉淀层功能

#### 统一回写链路

系统必须支持以下显式回写动作：

- `问答 -> Note`
- `Deep Research -> 研究报告`
- `研究报告 -> 工作台资料`
- `研究报告 -> 结构化笔记 / Wiki 页面`
- `右侧产物 -> Artifact`
- `右侧产物 -> 结构化笔记`
- `右侧产物 -> Wiki 页面`
- `研究报告 / 高价值产物 -> 工作台资料`

这里强调两点：

- 回写必须显式确认，不做静默注入
- 只有进入正式对象层的内容，才有资格参与长期沉淀

#### 任务邻域个性化记忆

Memory 不作为事实来源，也不参与资料检索排序。

它是跨会话、跨链路、跨任务的个性化控制层：

- 用户反馈、项目口径、表达偏好和禁用路径可以形成 `Memory Signal`
- 候选记忆通过 `Semantic Neighborhood Modeling` 与 `Marginal Utility Scoring` 判断是否具备跨任务复用价值
- `Negative Memory` 用于记录用户明确否定过的方案和表达
- `Staleness Guard` 用于防止旧口径污染新设计
- `Memory Compiler` 按任务邻域把记忆编译为三类 `Memory Control Pack`：面向统一聊天页的 `Chat Control Pack`、面向右侧产物生成的 `Artifact Control Pack`、面向 Deep Research 的 `Research Control Pack`

这意味着：

- 资料池、原文窗口和 Wiki 页面仍然是事实来源
- Memory 不作为 Citation，也不替代检索证据
- Memory 主要服务问答、Note、Wiki、产物生成和 Deep Research 的个性化表达与行为一致性

### 5.5 基础设施层功能

当前只保留支撑核心亮点成立所必需的基础设施：

- `文件上传`
- `对象存储（MinIO）`
- `异步任务链路（Kafka）`
- `解析与切片`
- `检索索引`
- `任务状态与进度反馈`
- `引用、证据、版本与审计记录`

资料基础设施的专项落地见 [资料基础设施详细设计](D:/java-projects/NoteWeave-v2/docs/资料基础设施详细设计.md)。这份文档负责把文件上传、MinIO 对象存储、Kafka 异步处理、解析切片、索引准备和系统生成成果资料化串成同一条实现链路。

不额外引入当前并非刚需的平台层，比如独立 `LLM Gateway` 或通用 `MCP Gateway`。

## 6. 当前阶段已落地范围

截至当前阶段，Java 主系统已经把 Phase 1 ~ 3 的主干做成可运行原型：

- `研究工作台`
  已支持创建工作台、默认会话、资料上传、资料删除和任务状态读取

- `问答链路`
  已支持工作台范围内的轻量 QA 检索、引用写入和 SSE 返回

- `Note 链路`
  已支持“正常聊天回答 + 资料定位 / 深读窗口 / 摘录证据”依据卡片结构，并支持回答保存为 Note
  其中候选资料层已支持 `query_coverage / coverage_terms / matched_fields` 的可解释输出
  前端展示已收敛为聊天主回答配合 `资料定位 / 深读窗口 / 摘录证据` 卡片，`来源引用` 作为附属折叠卡片，不再把内部步骤平铺给用户

- `Wiki 链路`
  已支持页面创建、追加版本、页面搜索、页面详情、版本历史、版本详情、出链、反链、来源回链，以及 `显式链接 / 自动互链 / 混合互链` 三类关系边

- `工作台级 Wiki 构建`
  已支持 `wiki_enabled` 开关、开启回补、资料上传触发 `WIKI_INGEST`、资料删除触发 `WIKI_RETRACT`、手动重建、重建链接、Auto Fix、日志、问题列表和动态构建建议

- `前端工作台`
  已支持同一聊天框下切换 `问答 / Note / Wiki`，以及进入默认 Wiki 工作台查看总览、页面、版本、治理问题、图谱和关系

因此，当前文档中的 Note / Wiki 口径已经不再只是“后续方案”，而是和现有代码实现保持同步的现行方案。

## 7. 右侧产物栏的正式定义

右侧产物栏需要明确成一个“可扩展的产物生成系统”，而不是固定六个按钮。

正式定义如下：

- 面向用户表现为一组可点击的产物动作
- 面向系统表现为一组可扩展的 `Production Action`
- 每个 Action 可绑定自己的结构 schema、风格选项、skill 组合和输出模板
- 平台内置一批高频 Action
- 用户可以增加新的产物形式，而不是只能使用预置按钮

当前建议内置的产物类型：

- 报告
- FAQ
- 测验
- 学习指南
- Wiki 页面
- 结构化笔记

产物生成的输入边界：

- 原材料：当前研究工作台资料池、已保存为资料的系统产物，以及对应解析文本、索引片段、标题、摘要、标签、元数据和引用信息
- 生成要求：产物类型、篇幅、语气、结构、受众、引用密度和输出格式
- 运行能力：内置 Skill、内置 MCP、用户自定义 MCP、Prompt Recipe、输出 schema、证据约束和局部修复策略

用户新增的产物形式也应遵守统一约束：

- 必须声明输出 schema
- 必须声明允许使用的 skill / capability 范围
- 必须声明默认输出格式和回写选项

## 8. Deep Research 的正式定义

Deep Research 也需要被正式定义为一个独立能力，而不是“更强一点的问答”。

它的系统定位是：

- 面向复杂开放式问题的重型研究能力
- 以显式 run、显式 budget、显式 trace、显式 verification 为核心
- 研究过程允许失败、修复、回退与分支
- 最终必须收敛为一份正式研究报告

它的产品约束是：

- 可以从当前聊天、选中资料、Wiki 工作台上下文或资料多选上下文发起
- 不默认把中间过程塞回主会话
- 报告是正式产物，也是后续主链路可消费资料

## 9. 功能与亮点分离

为了后续汇报和实现不打架，需要把“系统具备什么”与“系统怎么讲”分开。

### 9.1 功能口径

功能口径回答的是：

- 系统到底有什么模式
- 有哪些独立能力
- 资料怎么流转
- 产物怎么生成
- 结果怎么回写
- 长期知识怎么沉淀

### 9.2 亮点口径

亮点口径回答的是：

- Deep Research 为什么比普通搜索式问答更强
- 右侧产物栏为什么不是一堆 Prompt 模板
- 共享资料池和任务邻域个性化记忆为什么能形成长期复用价值

当前建议对外只稳定突出三个主亮点：

1. `验证驱动的 Deep Research 智能体`
2. `可扩展的右侧产物生成系统`
3. `共享项目级资料池与门控式知识沉淀`

更高密度的简历写法，统一放在 [项目亮点与简历草案](D:/java-projects/NoteWeave-v2/docs/项目亮点与简历草案.md)。

## 10. 工程实现总分工

当前推荐的工程分工是：

- `Java 主系统`
  承接研究工作台、三种聊天链路、业务真源、对象管理、回写链路、权限与任务编排

- `Python Research Worker`
  承接 Deep Research 的研究循环、验证闭环、报告合成与运行恢复

- `Python Artifact Worker`
  承接右侧产物栏背后的 Skill 编排、结构生成、格式导出与结果产出

这个拆分的核心理由是：

- 聊天链路、资料真源和对象生命周期强依赖业务系统，适合继续放在 Java
- 两条智能执行链路相对独立，更适合放在 Python 中快速迭代

## 11. 当前冻结的总口径

后续所有设计文档都应默认服从以下总口径：

- 一个基本单位：`研究工作台`
- 三种聊天回答链路：`问答 / Note / Wiki`
- 两个独立能力：`Deep Research / 右侧产物栏`
- 一个共享底座：`共享项目级资料池`
- 一套门控式任务邻域记忆机制：`Graduated Memory + Task-Neighborhood Memory Compiler`
- 一个实现分工：`Java 主系统 + Python Research Worker + Python Artifact Worker`
