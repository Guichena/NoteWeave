# NoteWeave v2 系统架构设计

## 1. 定位

NoteWeave v2 是一套围绕“单一用户工作区”构建的统一知识工作台。

基于三份上游设计文档，v2 的最终架构口径应统一为：

- 3 个用户可见工作模式：`问答`、`Full Wiki`、`资料调查`
- 1 个全局独立功能入口：`Deep Research`
- 1 个轻量知识沉淀层：`Note`
- 1 个右侧产物动作栏：`Artifact Actions Rail`
- 1 个受控异步执行平面：`Artifact Runtime`
- 1 套门控式长期记忆机制：`Graduated Memory`
- 1 套能力扩展栈：`Agent / Skill / MCP`

这里最重要的区别是：

- `问答`、`Full Wiki`、`资料调查` 是用户直接感知的主要工作模式
- `Deep Research` 是全局可触发的独立重型功能入口，可以从任意模式发起
- `Artifact Actions Rail` 是类似 NotebookLM 的右侧产物按钮区，用来快速生成报告、测验、学习指南等产物
- `Artifact Runtime` 不是顶层页面，而是支撑右侧按钮与其他生成任务的受控执行平面
- `Graduated Memory` 不是一个单独页面，而是贯穿会话、研究与产物的门控式记忆晋升机制
- `Note` 不是完整产品世界，而是 Ask / 调查 / Deep Research / Artifact 输出后的轻量沉淀层

## 2. 总体架构结论

v2 应采用“模式层 + 引擎层 + 共享底座层”的三层结构：

```text
NoteWeave v2
  ├── 用户可见模式层
  │     ├── 问答模式
  │     ├── Full Wiki 模式
  │     └── 资料调查模式
  ├── 全局功能入口层
  │     ├── Deep Research 按钮
  │     └── Artifact Actions Rail
  ├── 执行引擎层
   │     ├── Deep Research Engine
   │     └── Artifact Runtime
  └── 共享底座层
        ├── Workspace / Topic Scope
        ├── Source / Parsing / Retrieval
        ├── Evidence / Citation / Version
        ├── Note / Wiki / Investigation Note
        ├── Context Signal / Memory Promotion
        ├── Async Task / Budget / Trace
        └── Permission / Observability
```

这意味着 v2 不再按“Chat 产品”“Wiki 产品”“研究产品”分裂成多个业务世界，而是在一个工作区内让不同任务使用不同模式，并通过全局按钮入口调起重型能力，同时共享同一套资料、证据、版本和回写链路。

## 2.1 产品形态

前端产品形态建议明确参考 NotebookLM 一类知识工作产品：

- 左侧：资料列表 / 主题范围 / 导航
- 中间：主阅读区或对话区
- 右侧：产物动作栏与结果区

核心原则是：

- 用户始终围绕“当前资料上下文”工作
- 对话不是唯一主入口，资料阅读和产物生成同样是一等能力
- 右侧按钮栏可以直接对当前上下文发起产物生成，而不要求用户手写 Prompt

可抽象为：

```text
Source Context / Reading Context / Chat Context
  -> 右侧 Artifact Action Button
  -> 创建 Artifact Job
  -> Artifact Runtime 执行
  -> 结果回写为 Artifact / Note Draft / Wiki Draft / Quiz
```

## 3. 架构北极星

整套系统应满足以下六个特性：

1. `模式清晰`
   用户先选择自己要做的是问答、维护 Wiki，还是调查资料，而不是先暴露底层检索算法。

2. `证据优先`
   Source、原文片段、Citation、Artifact Version、Research Trace 必须贯穿整个链路。

3. `长任务隔离`
   深度研究与重型生成不能污染普通问答体验，也不能阻塞轻量交互。

4. `知识生命周期分离`
   Conversation、Note、Wiki、Investigation Note、Artifact、Research Run 之间必须有关联，但不能混为同一种对象。

5. `统一回写`
   Ask、调查、Deep Research、右侧按钮产物生成的结果，最终都应该能以显式确认的方式回写为 Note、Wiki 草稿、调查结论或 Artifact。

6. `可审计`
   复杂任务必须具备预算、状态、证据、重试与恢复能力，而不是一次性黑盒输出。

7. `门控记忆`
   聊天记录、Research Trace 与已确认 Artifact 都可以提供记忆信号，但只有通过门控验证的内容才能晋升为长期 Memory。

## 4. 用户可见模式层

### 4.1 问答模式

用途：

- 日常提问
- 文档 / Note / Wiki 检索问答
- 快速理解单个概念或局部资料

特点：

- 低延迟
- 基于当前会话连续性
- 允许引用 Notes、Wiki、Artifacts 与 Sources
- 不默认进入多阶段深度研究
- 右侧可直接出现产物按钮，如报告、测验、学习指南、FAQ

输出去向：

- Conversation
- 可手动保存为 Note
- 可引用已有 Wiki / Artifact / Source

### 4.2 Full Wiki 模式

用途：

- 维护长期稳定知识
- 组织主题页、概念页、总览页、关系页
- 进行覆盖度检查、反向链接和关系修复

特点：

- 比 Note 更严格的生命周期
- 内容面向长期维护，而非一次性结论
- 以页面网络而不是扁平笔记为核心

输出去向：

- Wiki Page
- Wiki Version
- Citation-backed stable knowledge

### 4.3 资料调查模式

用途：

- 围绕一个主题系统地找资料、读资料、比较资料
- 在资料层而不是 chunk 层工作
- 形成可复查的调查结论和 Investigation Note

模式原则：

- 先定位资料，再阅读原文窗口，最后形成结论
- 强调 `SourceCard -> SourceWindow -> Investigation Note`
- 支持从内部资料开始，逐步扩展到受控的外部获取

当调查任务变成开放式、多步骤、需要反复验证的研究流程时，用户可以显式点击 `Deep Research` 按钮创建 Research Run。

## 5. 全局功能入口与产物按钮

### 5.1 Deep Research 按钮

Deep Research 应作为一个独立功能入口存在，而不是埋在某个模式内部。

推荐交互：

- 在顶栏、工具栏或上下文菜单中提供 `深度研究` 按钮
- 用户可以从问答、Wiki、调查任一上下文发起
- 点击后创建 `Research Run`
- 研究结果默认写入 `Artifact`
- 用户再决定把结果流入问答、Wiki 或调查

这更符合你的目标产品形态：

- 3 个模式负责日常工作
- Deep Research 负责重型研究任务
- 其结果回流到 3 个模式中继续消费

### 5.2 右侧产物动作栏

右侧区域应是 v2 很重要的产品形态特征。

它不是“更多功能”抽屉，而是围绕当前上下文提供可直接点击的产物按钮。

推荐默认按钮：

- 报告
- 测验
- 学习指南
- FAQ
- 时间线总结
- Wiki 草稿

这些按钮的本质不是直接拼 Prompt，而是触发对应的 `Production Action`。

### 5.3 按钮触发逻辑

```text
用户位于当前上下文
  -> 点击右侧按钮（例如“生成测验”）
  -> 解析当前上下文范围
  -> 选择对应 Production Action
  -> 创建 Artifact Job
  -> Artifact Runtime 执行
  -> 生成 Artifact Version
  -> 用户确认是否回写
```

当前上下文可以来自：

- 当前聊天会话
- 当前阅读资料
- 当前调查主题
- 当前 Wiki 页面
- 当前选中的多个 Sources

## 6. 支撑层而非顶层模式

### 6.1 Note 层

Note 是轻量沉淀层，不是与 Ask / Wiki / 调查并列的完整产品模式。

它的职责是：

- 保存阶段性理解
- 承接 Ask 结果
- 承接调查过程中的中间结论
- 承接 Artifact 的人工筛选回写

因此 Note 更像“统一工作台里的个人沉淀容器”，而不是另一套独立业务世界。

### 6.2 Artifact 层

Artifact 是生成型结果层，不默认等同于稳定知识。

典型产物包括：

- 研究报告
- 对比总结
- 学习指南
- FAQ
- 测验
- Wiki 草稿
- 课程笔记
- 会议纪要

Artifact 的特点是：

- 带版本
- 带来源
- 可比较
- 可再次生成
- 可选择性回流检索

### 6.3 Graduated Memory 层

长期记忆不应等同于“聊天历史自动累积”，也不应等同于“只有产物才能写入”。

更合理的产品口径是参考 ChatGPT / Gemini 一类产品的多来源上下文思路，但收紧为更可控的知识工作台版本：

- `Conversation` 和 `Deep Research Trace` 先提供可衰减的 `Context Signals`
- `Artifact Version` 和人工确认后的 `Note / Wiki` 提供更稳定的 `Artifact Memory`
- 只有同时通过 `Novelty Gate` 与 `Task Neighborhood Validation` 的内容，才晋升为跨任务可复用的 `Promoted Memory`

这样做的好处是：

- 不浪费聊天和研究过程里的高价值偏好与方法信号
- 不把未验证对话直接固化为长期知识
- 让右侧产物生成、Wiki 沉淀和后续问答共享同一套高质量记忆底座

推荐把这套机制命名为 `Graduated Memory`，强调“不同来源、不同置信度、分阶段晋升”。

## 7. 执行引擎层

### 7.1 Deep Research Engine

Deep Research Engine 是全局可触发的独立长任务引擎。

它可以由以下上下文触发：

- 问答中的复杂问题
- 资料调查中的开放式主题
- Wiki 页面扩展研究
- 用户手动指定的一组 Sources

它负责把开放式研究任务拆成显式循环：

```text
Plan
  -> Search
  -> Read
  -> Extract
  -> Verify
  -> Revise
  -> Stop / Continue
```

核心职责：

- 生成研究计划
- 构建与维护 Research Table
- 执行 Wide Search 候选发现
- 执行目标导向阅读
- 完成 cell 级抽取与验证
- 处理证据不足与来源冲突
- 产出最终研究报告或结构化调查结论

它应采用受控 loop，而不是无限自主 Agent：

- 外部状态：`Research Table`
- 反馈信号：`Evidence / Verifier / Conflict / Confidence`
- 约束条件：`Budget / Retry / Stop Condition`
- 审计记录：`Research Trace`

Research 结果的推荐流向：

- 回到问答继续追问
- 生成 Wiki 草稿
- 生成 Investigation Note
- 保留为 Artifact 报告
- 提炼为 Note

Deep Research 本身不是长期记忆容器。

它更适合作为：

- 高价值 `Context Signals` 的来源
- 后续产物生成的证据底座
- 记忆候选发现的上游过程

### 7.2 Artifact Runtime

Artifact Runtime 是统一产物生成主链路。

它负责：

- 解析输入
- 识别 Production Action
- 获取并归一化内容
- 组织上下文
- 运行 Prompt Recipe
- 调用对应 Skill / MCP 能力
- 校验与修复输出
- 提交 Artifact Version

Artifact Runtime 的设计原则不是“自由放养 Agent”，而是“固定主链路 + 局部智能节点”：

```text
Validate Input
  -> Resolve Action
  -> Normalize Input
  -> Acquire Content
  -> Build Canonical Content
  -> Compile Context
  -> Run Prompt Recipe
  -> Verify / Repair
  -> Commit Artifact
  -> Index Artifact
```

在 NoteWeave 中，Artifact Runtime 还是 `Graduated Memory` 的核心入口之一：

- 被确认的 `Artifact Version` 可以形成稳定记忆候选
- 产物中的结构、方法模板、FAQ 形式和结论摘要，比原始对话更适合作为长期复用单元
- 但是否真正晋升为长期 Memory，仍要经过门控验证，而不是默认自动写入

它既服务于独立产物生成，也服务于：

- 右侧按钮栏的快速产物生成
- 资料调查后的报告生成
- Wiki 草稿输出
- 学习资料结构化整理
- 音视频输入的总结与纪要

## 8. Agent / Skill / MCP 能力栈

这一层必须明确写进系统设计，否则右侧产物按钮会退化成普通 Prompt 模板。

### 8.1 Agent

Agent 负责局部智能决策与受控编排。

适用场景：

- Deep Research loop 中的规划、搜索、验证、修订
- Artifact Runtime 中的 Action Resolver、Content Planner、Verifier / Repair

原则：

- Agent 不直接拥有无限工具权限
- Agent 只能在系统允许的动作边界内决策
- Agent 的输出必须可追踪、可审计

### 8.2 Skill

Skill 负责沉淀成可复用的任务能力模板。

适用场景：

- 报告生成 Skill
- 测验生成 Skill
- 学习指南 Skill
- 视频总结 Skill
- FAQ Skill

Skill 可以理解为：

- 面向某类产物的结构化能力包
- 内含 Prompt Recipe、输出结构、校验规则、可选能力依赖

### 8.3 MCP

MCP 负责接入外部工具与内容能力。

适用场景：

- 网页读取
- 视频字幕提取
- 音频转写
- 外部搜索
- 第三方资料服务

MCP 在系统中的角色不是替代业务逻辑，而是提供标准化能力接口。

### 8.4 三者协作关系

```text
右侧按钮 / Deep Research 按钮
  -> 选择 Production Action
  -> Agent 做局部决策
  -> Skill 提供任务模板与结构
  -> MCP 提供外部工具与数据能力
  -> Artifact Runtime / Deep Research Engine 执行
```

## 9. 共享底座层

三种模式与两个引擎共享同一套底座能力：

### 9.1 工作区与主题边界

- Workspace 作为顶层边界
- Topic / Research Scope 作为主题性组织边界
- 统一权限、归属与可见性

### 9.2 资料输入与解析

- 文件导入
- URL 导入
- 文本导入
- 原始文件快照
- 解析文本
- 文档切块
- 原文定位信息

### 9.3 检索与原文回读

- Ask 模式所需的文档检索与 Note 检索
- Wiki 页面检索与链接读取
- 资料调查模式所需的 metadata 检索、SourceCard 候选发现、SourceWindow 原文回读

### 9.4 证据、引用与版本

- Citation
- Evidence Span
- Source Snapshot
- Knowledge Version
- Artifact Version
- Report / Investigation Trace linkage

### 9.5 异步任务与观测

- Research Run
- Artifact Job
- 状态流转
- 预算控制
- 重试
- 中断恢复
- Trace / 日志 / 进度展示

### 9.6 Graduated Memory

- 会话信号抽取
- Research Trace 信号抽取
- Artifact / Note / Wiki 记忆候选抽取
- `Novelty Gate`
- `Task Neighborhood Validation`
- 记忆晋升记录
- 记忆回读与注入

### 9.7 UI 上下文解析

- 当前聊天上下文
- 当前阅读上下文
- 当前调查主题上下文
- 当前 Wiki 页面上下文
- 当前多资料选中上下文

这层能力专门服务于右侧按钮栏和 Deep Research 按钮的“当前上下文感知”。

## 10. 关键业务流

### 10.1 Ask 到 Note

```text
用户提问
  -> 问答模式检索与回答
  -> 用户确认保存
  -> 生成 Note
```

### 10.2 右侧按钮生成产物

```text
用户在阅读 / 对话 / 调查中工作
  -> 点击右侧按钮（如“生成报告”或“生成测验”）
  -> 创建 Artifact Job
  -> Artifact Runtime 运行 Production Action
  -> 得到 Artifact Version
  -> 用户确认是否回写或加入检索
```

### 10.3 资料调查到深度研究

```text
用户发起调查主题
  -> 发现 SourceCard
  -> 打开 SourceWindow
  -> 形成 Investigation Note
  -> 如任务升级，则点击 Deep Research 按钮启动 Research Run
  -> 生成研究报告 Artifact
```

### 10.4 Deep Research 回流三种模式

```text
Deep Research 完成
  -> 回到问答继续追问
  -> 保存为 Wiki 草稿
  -> 保存为调查结论
  -> 保存为 Note / Artifact
```

### 10.5 产物回写

```text
Artifact Version
  -> 用户审阅
  -> 回写为 Note / Wiki 草稿 / Investigation Note / 保留为 Artifact
```

### 10.6 记忆晋升

```text
Conversation / Research Trace / Artifact Version
  -> 抽取 Context Signals / Memory Candidate
  -> 通过 Novelty Gate
  -> 通过 Task Neighborhood Validation
  -> 写入 Promoted Memory
  -> 在后续问答 / 产物生成中按需注入
```

这三条链路共同构成：

`资料输入 -> 证据使用 -> 结果生成 -> 人工确认 -> 知识沉淀`

如果把长期记忆也纳入，则可以扩展为：

`资料输入 -> 证据使用 -> 结果生成 -> 人工确认 -> 门控晋升 -> 长期复用`

## 11. 前端导航建议

前端应该体现“3 个工作模式 + 全局功能入口 + 右侧产物栏”，推荐采用：

1. `问答`
2. `笔记`
3. `Wiki`
4. `调查`
5. `产物`

其中：

- `问答`、`Wiki`、`调查` 是主要工作模式
- `笔记` 和 `产物` 是沉淀与管理界面
- `Deep Research` 作为顶栏或上下文全局按钮
- `Artifact Actions Rail` 作为右侧固定区域

## 12. 第一轮非目标

第一轮架构锁定不默认包含以下内容：

- 企业级多租户协作模型
- 默认的大规模外部网页自动抓取
- 无门控的全局自治记忆写回
- 实时多人协同编辑
- 完整 Claim / Entity / Knowledge Graph 推理层
- 无限制自主 Agent 编排

## 13. 架构总结

NoteWeave v2 不应被定义为“一个大而全的 Agent 平台”，而应被定义为：

`一个参考 NotebookLM 产品形态、以三种工作模式为日常入口、以 Deep Research 按钮和右侧产物按钮栏为重型能力入口、以 Graduated Memory 为长期复用机制、以 Agent / Skill / MCP 为扩展栈、以 Evidence / Citation / Version 为共享底座的统一知识工作台。`
