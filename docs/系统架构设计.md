# NoteWeave v2 系统架构设计

## 1. 定位

NoteWeave v2 是一套围绕“研究工作台”构建的统一知识工作台。

基于三份上游设计文档，v2 的最终架构口径应统一为：

- 1 个基本产品单位：`研究工作台`
- 3 个聊天回答链路：`问答`、`Note`、`Wiki`
- 1 个全局独立功能入口：`Deep Research`
- 1 个右侧产物栏：`Artifact Actions Rail`
- 1 个受控异步执行平面：`Artifact Runtime`
- 1 套门控式长期记忆机制：`Graduated Memory`
- 1 套能力扩展栈：`Agent / Skill / MCP`

这里最重要的区别是：

- `研究工作台` 是资料、聊天、Wiki、Note、Artifact、Research Run 的统一容器
- `问答`、`Note`、`Wiki` 是同一聊天界面背后的三种回答链路，不是三套割裂页面
- 每个聊天会话拥有自己的上下文、回答链路和运行记录；资料边界默认继承当前研究工作台
- `Deep Research` 是全局可触发的独立重型功能入口，可以从当前聊天、选中资料或 Wiki 工作台上下文发起
- `Artifact Actions Rail` 是类似 NotebookLM 的右侧产物栏，用来快速生成报告、测验、学习指南等产物
- `Artifact Runtime` 不是顶层页面，而是支撑右侧按钮与其他生成任务的受控执行平面
- `Graduated Memory` 不是一个单独页面，而是贯穿会话、研究与产物的门控式记忆晋升机制
- 三种回答链路共享同一套项目级资料池，差异主要在检索对象、推理路径、输出结构和回写建议
- 右侧产物栏本质上是一套可扩展的 `Production Action` 系统，而不是固定几个按钮

## 2. 总体架构结论

v2 应采用“研究工作台 + 聊天链路层 + 引擎层 + 共享底座层”的分层结构：

```text
NoteWeave v2
  ├── 研究工作台
  │     ├── 资料池
  │     ├── 多个聊天会话
  │     ├── Wiki / Note / Artifact
  │     └── Research Run
  ├── 聊天回答链路层
  │     ├── 问答链路
  │     ├── Note 链路
  │     └── Wiki 链路
  ├── 全局功能入口层
  │     ├── Deep Research 按钮
  │     └── 右侧产物栏
  ├── 执行引擎层
   │     ├── Deep Research Engine
   │     └── Artifact Runtime
  └── 共享底座层
        ├── Research Workspace / Topic Scope
        ├── Shared Material Pool / Parsing / Retrieval
        ├── Evidence / Citation / Version
        ├── Conversation / Note / Wiki / Artifact
        ├── Context Signal / Memory Promotion
        ├── Async Task / Budget / Trace
        └── Permission / Observability
```

这意味着 v2 不再按“Chat 产品”“Wiki 产品”“研究产品”分裂成多个业务世界，而是在一个研究工作台内让不同聊天选择不同回答链路，并通过全局按钮入口调起重型能力，同时共享同一套资料、证据、版本和回写链路。

## 2.2 实现分工

在工程实现上，当前推荐采用：

- `Java 主系统`
  承接研究工作台、三种聊天链路、业务真源、任务编排、权限控制、前后端接口与最终结果回写。

- `Python Research Worker`
  承接 `Deep Research` 的研究循环、搜索、读取、验证、纠偏与研究报告合成。

- `Python Artifact Worker`
  承接右侧产物栏背后的 `Artifact Agent` 执行，包括 skill 编排、MCP 调度、结构校验、局部修复与产物生成。

这样拆分的原因是：

- `问答`、`Note`、`Wiki` 三种聊天链路与研究工作台、资料、知识对象和回写链路强耦合，更适合继续放在 `Java` 主系统中
- `Deep Research` 与 `Artifact Agent` 的执行流程相对独立，且主要通过任务创建、运行事件和结果回写与主系统发生关系，更适合作为独立 `Python` 执行器实现

## 2.1 产品形态

前端产品形态建议明确参考 NotebookLM 一类知识工作产品：

- 左侧：资料列表 / 主题范围 / 导航
- 中间：统一聊天区
- 右侧：产物动作栏与结果区

核心原则是：

- 用户始终围绕“当前资料上下文”工作
- 对话是日常主入口，资料阅读、Wiki 工作台和产物生成作为辅助入口服务同一个研究工作台
- 右侧产物栏可以直接对当前上下文发起产物生成，而不要求用户手写 Prompt

可抽象为：

```text
Material Context / Reading Context / Chat Context
  -> 右侧 Artifact Action Button
  -> 创建 Artifact Job
  -> Artifact Runtime 执行
  -> 结果回写为 Artifact / Note Draft / Wiki Draft / Quiz
```

## 3. 架构北极星

整套系统应满足以下八个特性：

1. `模式清晰`
   用户在同一个聊天界面里选择本次回答走问答、Note，还是 Wiki 链路，而不是先暴露底层检索算法。

2. `证据优先`
   资料、原文片段、Citation、Artifact Version、Research Trace 必须贯穿整个链路。

3. `长任务隔离`
   深度研究与重型生成不能污染普通问答体验，也不能阻塞轻量交互。

4. `知识生命周期分离`
   Conversation、Note、Wiki、Artifact、Research Run 之间必须有关联，但不能混为同一种对象。

5. `统一回写`
   Ask、Deep Research、右侧产物栏生成的结果，最终都应该能以显式确认的方式保存为结构化笔记、沉淀为 Wiki 页面或保留为 Artifact。

6. `可审计`
   复杂任务必须具备预算、状态、证据、重试与恢复能力，而不是一次性黑盒输出。

7. `门控记忆`
   聊天记录、Research Trace 与已确认 Artifact 都可以提供记忆信号，但只有通过门控验证的内容才能晋升为长期记忆。

8. `资料池统一`
   用户上传文件、导入网页与被确认的系统生成资料应进入同一套项目级资料池，再由问答、Note、Wiki 共享检索与引用。

## 4. 用户可见模式层

### 4.1 问答链路

用途：

- 日常提问
- 围绕当前资料池做检索增强问答
- 快速理解单个概念或局部资料

特点：

- 低延迟
- 基于当前会话连续性
- 允许引用笔记、Wiki 页面、产物与工作台资料
- 不默认进入多阶段深度研究
- 右侧可直接出现产物按钮，如报告、测验、学习指南、FAQ
- 当用户未显式选择回答链路时，默认落在问答链路

输出去向：

- Conversation
- 可手动保存为结构化笔记
- 可引用已有 Wiki 页面、产物与工作台资料

### 4.2 Note 链路

用途：

- 在统一聊天界面中回答问题，同时整理资料和沉淀笔记
- 结合 NotebookLM 式 `Workspace-bounded RAG` 和 Marginalia 的结构化检索漏斗
- 将一次问答转化为有来源、有摘录、有结构的笔记

特点：

- 与问答共享同一套资料池与引用体系
- 先通过标题、摘要、标签、历史笔记和资料关系缩小候选资料
- 再读取原文窗口，保留页码、段落、时间戳或 quote locator
- 最后抽取摘录卡片并生成结构化笔记
- 比 Wiki 更灵活，但仍保留来源、引用和编辑链路

输出去向：

- 结构化笔记
- 笔记版本
- 可继续参与后续问答、整理和知识页生成

### 4.3 Wiki 链路

用途：

- 维护长期稳定知识
- 组织主题页、概念页、总览页、关系页
- 进行覆盖度检查、反向链接和关系修复

特点：

- 比 Note 更严格的生命周期
- 内容面向长期维护，而非一次性结论
- 以页面网络而不是扁平笔记为核心

输出去向：

- Wiki Page
- Wiki Version
- Citation-backed stable knowledge

## 5. 全局功能入口与产物按钮

### 5.1 Deep Research 按钮

Deep Research 应作为一个独立功能入口存在，而不是埋在某个模式内部。

推荐交互：

- 在顶栏、工具栏或上下文菜单中提供 `深度研究` 按钮
- 用户可以从问答、Note、Wiki 任一上下文发起
- 点击后创建 `Research Run`
- Research 过程默认保存“过程资产”，正式产出必须包含一份研究报告
- 研究报告默认作为项目级正式成果进入共享资料池
- 用户再决定把研究报告继续流入问答、Note 或 Wiki

这更符合你的目标产品形态：

- 3 个模式负责日常工作
- Deep Research 负责重型研究任务
- 其结果回流到 3 个模式中继续消费

### 5.2 右侧产物栏

右侧区域应是 v2 很重要的产品形态特征。

它不是“更多功能”抽屉，而是围绕当前上下文提供可直接点击的产物按钮。

推荐默认按钮：

- 报告
- 测验
- 学习指南
- FAQ
- 时间线总结
- Wiki 页面
- 结构化笔记

这些按钮的本质不是直接拼 Prompt，而是触发对应的 `Production Action`。

### 5.3 按钮触发逻辑

```text
用户位于当前上下文
  -> 点击右侧按钮（例如“生成测验”）
  -> 解析当前上下文范围
  -> 选择对应 Production Action
  -> 创建 Artifact Job
  -> Artifact Runtime 执行
  -> 生成 Artifact Version
  -> 用户确认是否回写
```

当前上下文可以来自：

- 当前聊天会话
- 当前结构化笔记
- 当前阅读资料
- 当前 Wiki 页面
- 当前选中的多个资料

## 6. 支撑层而非顶层模式

### 6.1 Artifact 层

Artifact 是生成型结果层，不默认等同于稳定知识。

典型产物包括：

- 研究报告
- 对比总结
- 学习指南
- FAQ
- 测验
- Wiki 页面
- 课程笔记
- 会议纪要

Artifact 的特点是：

- 带版本
- 带来源
- 可比较
- 可再次生成
- 可选择性回流检索
- 其中 `Deep Research` 的研究报告属于必须产出的正式成果型 Artifact

Research 结果在资料层要明确分两层：

- `研究过程资产`
  搜索结果、网页快照、抓取文本、证据片段、检查点与运行轨迹，默认服务于当前 Research Run，不直接进入主检索链路。

- `确认后资料成果`
  研究报告、被引用的关键网页快照、被用户确认纳入的来源与其他高价值成果，可以进入项目级共享资料池，像用户上传文件一样参与检索与引用。

### 6.2 Graduated Memory 层

长期记忆不应等同于“聊天历史自动累积”，也不应等同于“只有产物才能写入”。

更合理的产品口径是参考 ChatGPT / Gemini 一类产品的多来源上下文思路，但收紧为更可控的知识工作台版本：

- `Conversation` 和 `Deep Research Trace` 先提供可衰减的 `Context Signals`
- `Artifact Version` 和人工确认后的 `Note / Wiki` 优先形成高质量 `Memory Candidates`
- 只有同时通过 `Novelty Gate` 与 `Task Neighborhood Validation` 的内容，才晋升为跨任务可复用的 `Memory Object`

这样做的好处是：

- 不浪费聊天和研究过程里的高价值偏好与方法信号
- 不把未验证对话直接固化为长期知识
- 让右侧产物生成、Wiki 沉淀和后续问答共享同一套高质量记忆底座

推荐把这套机制命名为 `Graduated Memory`，强调“不同来源、不同置信度、分阶段晋升”。

## 7. 执行引擎层

### 7.1 Deep Research Engine

Deep Research Engine 是全局可触发的独立长任务引擎。

在当前升级口径下，它可以进一步理解为一个 `TAS-Informed Verification-Centric Research Harness`：以 `Research Table` 承载外部执行状态，以 `Interaction-Scaled Research Loop` 驱动 Search、Read、Extract、Verify、Revise 的受控闭环，并通过 `Dual Verifier`、`Counterfactual Branching`、budget 和 `Stop Contract` 决定任务推进、局部修复或分支探索。

它可以由以下上下文触发：

- 问答中的复杂问题
- Note 中需要进一步论证或扩展的草稿
- Wiki 页面扩展研究
- 用户指定的一组资料

它负责把开放式研究任务拆成显式循环：

```text
Plan
  -> Search
  -> Read
  -> Extract
  -> Verify
  -> Revise
  -> Stop / Continue
```

核心职责：

- 生成研究计划
- 构建与维护 Research Table
- 执行 Wide Search 候选发现
- 执行目标导向阅读
- 完成 cell 级抽取与验证
- 处理证据不足与来源冲突
- 产出最终研究报告或结构化研究结论

推荐进一步强调三个设计点：

- `Table-as-State`
  `Research Table` 不只是展示结果，而是研究执行状态层

- `Evidence-Gated Progress`
  研究推进由 evidence 和 verification 状态驱动

- `Branchable Recovery`
  低置信或冲突路径支持局部修复与分支探索，而不是整任务重跑

它应采用受控 loop，而不是无限自主 Agent：

- 外部状态：`Research Table`
- 反馈信号：`Evidence / Verifier / Conflict / Confidence`
- 约束条件：`Budget / Retry / Stop Condition`
- 审计记录：`Research Trace`

Research 结果的推荐流向：

- 必产出一份研究报告
- 研究报告默认进入项目级共享资料池
- 回到问答继续追问
- 生成结构化笔记供二次加工
- 用户确认后沉淀为 Wiki 页面
- 保留为 Artifact 报告并持续参与检索

Deep Research 本身不是长期记忆容器。

它更适合作为：

- 高价值 `Context Signals` 的来源
- 后续产物生成的证据底座
- 记忆候选发现的上游过程

### 7.2 Artifact Runtime

Artifact Runtime 是统一产物生成主链路。

它负责：

- 解析输入
- 识别 Production Action
- 识别或加载 Style Profile
- 获取并归一化内容
- 组织上下文
- 形成执行计划并通过 schema gate
- 运行 Prompt Recipe / Skill Graph
- 调用对应 Skill / MCP 能力
- 校验与修复输出
- 提交 Artifact Version

Artifact Runtime 的设计原则不是“自由放养 Agent”，而是“固定主链路 + 局部智能节点”：

```text
Validate Input
  -> Resolve Action
  -> Load Style Profile
  -> Normalize Input
  -> Acquire Content
  -> Build Canonical Content
  -> Compile Context
  -> Build Execution Plan
  -> Schema Gate
  -> Run Prompt Recipe / Skill Graph
  -> Verify / Repair
  -> Commit Artifact
  -> Index Artifact
```

在 NoteWeave 中，Artifact Runtime 还是 `Graduated Memory` 的核心入口之一：

- 被确认的 `Artifact Version` 可以形成稳定记忆候选
- 产物中的结构、方法模板、FAQ 形式和结论摘要，比原始对话更适合作为长期复用单元
- 但是否真正晋升为长期记忆，仍要经过门控验证，而不是默认自动写入

它既服务于独立产物生成，也服务于：

- 右侧产物栏的快速产物生成
- Deep Research 后的报告生成与二次加工
- Wiki 页面输出
- 学习资料结构化整理
- 音视频输入的总结与纪要

## 8. Agent / Skill / MCP 能力栈

这一层必须明确写进系统设计，否则右侧产物栏按钮会退化成普通 Prompt 模板。

### 8.1 Agent

Agent 负责局部智能决策与受控编排。

适用场景：

- Deep Research loop 中的规划、搜索、验证、修订
- Artifact Runtime 中的 Action Resolver、Content Planner、Verifier / Repair

原则：

- Agent 不直接拥有无限工具权限
- Agent 只能在系统允许的动作边界内决策
- Agent 的输出必须可追踪、可审计

### 8.2 Skill

Skill 负责沉淀成可复用的任务能力模板。

适用场景：

- 报告生成 Skill
- 测验生成 Skill
- 学习指南 Skill
- 视频总结 Skill
- FAQ Skill

Skill 可以理解为：

- 面向某类产物的结构化能力包
- 内含 Prompt Recipe、输出结构、校验规则、可选能力依赖

在升级口径下，多个 Skill 更适合按 `Skill Graph` 组织，而不是简单平铺列表。

### 8.3 MCP

MCP 负责接入外部工具与内容能力。

适用场景：

- 网页读取
- 视频字幕提取
- 音频转写
- 外部搜索
- 第三方资料服务

MCP 在系统中的角色不是替代业务逻辑，而是提供标准化能力接口。

### 8.4 三者协作关系

```text
右侧产物栏 / Deep Research 按钮
  -> 选择 Production Action
  -> Agent 做局部决策
  -> Skill 提供任务模板与结构
  -> MCP 提供外部工具与数据能力
  -> Artifact Runtime / Deep Research Engine 执行
```

## 9. 共享底座层

三种聊天回答链路与两个引擎共享同一套底座能力：

### 9.1 工作区与主题边界

- Workspace 作为顶层边界
- Topic / Research Scope 作为主题性组织边界
- 统一权限、归属与可见性

### 9.2 资料输入与解析

- 文件导入
- URL 导入
- 文本导入
- Deep Research 研究报告入库
- 被确认网页快照入库
- 原始文件快照
- 解析文本
- 文档切块
- 原文定位信息

### 9.3 检索与原文回读

- Ask 模式所需的文档检索与 Note 检索
- Wiki 页面检索与链接读取
- Deep Research 报告与系统生成正式资料的统一检索
- 过程资产与正式资料的分层读取

### 9.4 证据、引用与版本

- Citation
- Evidence Span
- Material Snapshot
- Knowledge Version
- Artifact Version
- Report / Research Trace linkage

### 9.5 异步任务与观测

- Research Run
- Artifact Job
- 状态流转
- 预算控制
- 重试
- 中断恢复
- Trace / 日志 / 进度展示

### 9.6 Graduated Memory

- 会话信号抽取
- Research Trace 信号抽取
- Artifact / Note / Wiki 记忆候选抽取
- `Novelty Gate`
- `Task Neighborhood Validation`
- 记忆晋升记录
- 记忆回读与注入

### 9.7 UI 上下文解析

- 当前聊天上下文
- 当前阅读上下文
- 当前结构化笔记上下文
- 当前 Wiki 页面上下文
- 当前多资料选中上下文

这层能力专门服务于右侧产物栏和 Deep Research 按钮的“当前上下文感知”。

## 10. 关键业务流

### 10.1 Ask 到 Note

```text
用户提问
  -> 问答链路检索与回答
  -> 用户确认保存
  -> 生成结构化笔记
```

### 10.2 右侧按钮生成产物

```text
用户在阅读 / 对话 / Note / Wiki 中工作
  -> 点击右侧按钮（如“生成报告”或“生成测验”）
  -> 创建 Artifact Job
  -> Artifact Runtime 运行 Production Action
  -> 得到 Artifact Version
  -> 用户确认是否回写或加入检索
```

### 10.3 Deep Research 主链路

```text
用户从当前聊天、选中资料或 Wiki 工作台上下文发起 Deep Research
  -> 创建 Research Run
  -> 保存研究过程资产
  -> 生成研究报告 Artifact
  -> 研究报告进入项目级共享资料池
  -> 可继续生成结构化笔记或 Wiki 页面
```

### 10.4 Deep Research 回流研究工作台

```text
Deep Research 完成
  -> 回到问答继续追问
  -> 保存为结构化笔记
  -> 沉淀为 Wiki 页面
  -> 保留为 Artifact
```

### 10.5 产物回写

```text
Artifact Version
  -> 用户审阅
  -> 保存为结构化笔记 / 沉淀为 Wiki 页面 / 保留为 Artifact
```

### 10.6 记忆晋升

```text
Conversation / Research Trace / Artifact Version
  -> 抽取 Context Signals / Memory Candidate
  -> 通过 Novelty Gate
  -> 通过 Task Neighborhood Validation
  -> 写入 Memory Object
  -> 在后续问答 / 产物生成中按需注入
```

这三条链路共同构成：

`资料输入 -> 证据使用 -> 结果生成 -> 人工确认 -> 知识沉淀`

如果把长期记忆也纳入，则可以扩展为：

`资料输入 -> 证据使用 -> 结果生成 -> 人工确认 -> 门控晋升 -> 长期复用`

## 11. 前端导航建议

前端应该体现“研究工作台 + 统一聊天区 + 全局功能入口 + 右侧产物栏”，推荐采用：

1. `问答`
2. `Note`
3. `Wiki`
4. `产物`

其中：

- `问答`、`Note`、`Wiki` 是同一聊天区背后的三种回答链路
- `产物` 是沉淀与管理界面
- `Deep Research` 作为顶栏或上下文全局按钮
- `Artifact Actions Rail` 作为右侧固定区域

## 12. 第一轮非目标

第一轮架构锁定不默认包含以下内容：

- 企业级多租户协作模型
- 默认的大规模外部网页自动抓取
- 无门控的全局自治记忆写回
- 实时多人协同编辑
- 完整 Claim / Entity / Knowledge Graph 推理层
- 无限制自主 Agent 编排

## 13. 架构总结

NoteWeave v2 不应被定义为“一个大而全的 Agent 平台”，而应被定义为：

`一个参考 NotebookLM 产品形态、以研究工作台为基本单位、以统一聊天区承接问答 / Note / Wiki 三种回答链路、以 Deep Research 按钮和右侧产物栏为独立系统能力、以共享项目级资料池为资料底座、以 Graduated Memory 为长期复用机制、以 Agent / Skill / MCP 为扩展栈、以 Evidence / Citation / Version 为可信闭环的统一知识工作台。`
