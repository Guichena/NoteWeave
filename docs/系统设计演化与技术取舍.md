# NoteWeave v2 系统设计演化与技术取舍

> 本文只回答“为什么从简单方案演化到当前边界，以及何时值得继续迁移”。最终结构、状态和契约分别以 [系统架构设计](./系统架构设计.md)、[API 与事件契约](./API与事件契约-v2.md) 和各领域专题为准，本文不复制完整实现表格。

## 1. 证据、方法与项目定位

NoteWeave 是来源驱动的研究与知识工作台，统一主线为 Source 版本化、检索投影、QA/Note/Wiki、Deep Research、Artifact、Memory 候选与审核、后续运行上下文和用户反馈治理。演化路线根据当前代码、迁移、配置、测试可证明边界，以及可复现 Bad Case 推导，不使用 Git 历史虚构“真实事故”。

本文使用五类证据：

- `[当前实现]`：可由当前源码、迁移、配置或测试直接证明。
- `[目标设计]`：为生产完整性补充，不能描述成已上线。
- `[已测-模拟]`：固定数据回放、Mock、故障注入或模拟压测结果。
- `[行业参考]`：公开官方文档、标准、论文或主仓库的设计。
- `[生产待验证]`：需要真实用户、Provider、数据规模或持续时间窗验证。

每条演化都按 V0、Bad Case、错误判断、修复、新问题、目标边界和迁移触发条件展开。初版不是“错误代码”，而是在规模、风险和认知有限时成本最低的方案；只有 Bad Case 已经出现或复杂度收益可量化时，才引入更重的组件。

## 2. 总体架构：从功能 Demo 到来源驱动工作台

### V0：同步请求中的若干 AI 功能

最小方案是上传资料后，在一个 HTTP 请求里完成解析、检索、模型调用并返回答案。Note、Wiki、Research、Artifact 和 Memory 可以分别用 Controller 加 Prompt 快速验证交互。

**Bad Case。** 长任务占住请求线程；刷新页面后进度丢失；同一 Source 在不同功能里被重复解析；模型回复、文件和记忆缺少共同版本关系；某个模块声称成功却无法证明使用了哪个资料版本。

**错误判断。** 只增加 Agent 或更强模型不能解决真源、隔离、恢复和版本问题。把所有能力塞进统一 Agent 还会让状态、权限和副作用边界更模糊。

### 修复：Source 真源、投影和控制面/执行面

`[当前实现]` 系统已经分为 Java 控制面、Python Research/Artifact Worker、MySQL、Kafka、Redis、Elasticsearch 和 MinIO，并以 Workspace、Source Snapshot、Run/Task、Artifact Version 与 Memory Revision 等对象承载业务关系。迁移基线已到 `V104`。

`[目标设计]` MySQL 只保存业务真相与推进权，MinIO 保存不可变载荷，Elasticsearch、向量、缓存和 Memory 编译结果都是可重建投影。控制面负责权限、状态、预算、版本和最终提交，执行面只持有短期 Lease 和最小能力。

**新问题。** 分布式组件增加 Outbox、乱序、重复、未知结果、投影延迟、跨组件恢复和可观测性成本，因此必须有公共可靠性契约，而不是每个 Agent 各写一套重试。

**迁移触发。** 当前边界不自动等于微服务越多越好。只有团队边界、独立扩缩容、故障隔离或部署频率收益超过契约与运维成本时，才拆分更多服务。

## 3. 用户输入：从直接驱动能力到强类型执行合同

### V0：原始文本直接选择 Prompt、工具或产物

最短路径是把用户输入直接交给 QA Prompt、Research Planner 或 Artifact Action。它能快速跑通单功能 Demo，但“第二个”“按刚才的要求”“做成报告再导出 PDF”同时包含指代、约束继承和多项交付，单个字符串无法说明系统究竟理解了什么。

**Bad Case。** Rewrite 丢掉否定或 Source 限制；模型猜错指代后扩大检索范围；Research 通过 Replan 偷偷降低原始交付标准；Artifact 在缺少 URL 或目标版本时直接执行；一个多意图请求共用状态，失败后无法单独恢复或取消。

**当前边界。** `[当前实现]` QA 有版本化 Conversation Rewrite 和确定性低召回 Expansion，Research 有结构化 Intent、Matrix 与 Plan Digest，Artifact 以显式 `skill_key` 和 Schema 做确定性校验。三个局部合同尚未合并成统一 Intent Router，文档不能把目标设计包装成现状。

### 修复：保留原文，按能力编译强类型输入

`[目标设计]` 入口冻结 Original Input、规范化结果、实体/别名、显式约束、未决指代、缺失字段、澄清原因和策略版本。共享结果只提出能力候选，不拥有授权和执行权。QA 编译 Retrieval Query Set，Research 编译不可被 Replan 降低的 Intent，Artifact 编译 Skill 候选与 Missing Slots；服务端再按 Workspace、对象状态、Schema、预算和审批复核。

**新问题。** 澄清过多会增加交互成本，澄清不足会误执行。置信度若未用冻结数据集校准，只是模型语气。评测必须把槽位完整、指代、澄清 Precision/Recall 和错误路由拆开，不能用最终生成成功率代替理解质量。

**迁移触发。** 当前显式产品入口和 `answer_mode/skill_key` 已能覆盖多数功能。只有跨入口自然语言请求、多意图组合与歧义样本形成稳定分布，并且错误路由成为可测问题时，才值得增加共享 Understanding Snapshot 和路由服务。

## 4. Workspace：从查询参数到纵深隔离

### V0：请求携带 `workspaceId`

最初只在 URL 或请求体中传 Workspace，再由 Service 查询对象。这能支持基本多空间功能，但容易把 Workspace 当成普通过滤条件。

**Bad Case。** Repository 漏过滤导致越权；缓存只按对象 ID 命中其他 Workspace；Kafka 消费者信任 Payload；搜索结果和对象存储 Key 缺少 Scope；Trace 把用户内容或高基数 Workspace ID 当标签。

**错误判断。** 只在 Controller 做一次鉴权不能覆盖异步 Worker、缓存、索引、Callback 和写回。依赖前端隐藏入口也不是权限控制。

### 修复：每层重复验证

`[当前实现]` Workspace 进入主要 API、数据库对象和测试契约，ACL Cache 具有正负 TTL 与 Jitter 配置。

`[目标设计]` API 从认证上下文获得 Actor；Service 验证 Membership 与动作；SQL 以 Workspace 和对象 ID 联合定位；缓存 Key 含 Workspace 与 ACL Epoch；Kafka/Callback 重新读取主服务真源；搜索结果读时回表；MinIO Key 不授予权限；Telemetry 只保留受控低基数 Scope。

**新问题。** 权限变化传播可能比读取更慢；正缓存延迟撤权，负缓存延迟授权。解决方式是 ACL Epoch、主动失效、读时校验和高风险操作 Fail Closed，而不是无限缩短 TTL。

**迁移触发。** 单库共享 Schema 先满足当前规模。只有租户合规、数据驻留、热点隔离或大客户独立密钥要求明确时，再评估分库、独立索引或独立对象桶；代价是跨 Workspace 治理、迁移和运维显著增加。

## 5. Source 与资料基础设施：从文件上传到不可变版本

### V0：文件即资料

同步上传后直接解析文本并写向量，简单且反馈快。

**Bad Case。** 大文件超时；对象已写但数据库失败形成孤儿；覆盖上传后旧引用失真；解析、Chunk 和索引版本无法对账；删除文件但向量、缓存、Wiki、Memory 和 Artifact 仍残留。

**错误判断。** 仅增加重试会重复解析和写索引；仅依赖对象名无法判断业务版本；只删除当前索引不处理派生关系会留下脏数据。

### 修复：Upload、Snapshot、Projection 与 Tombstone

`[当前实现]` Source、Source Snapshot、Chunk、上传分段、清理任务和检索投影已经有数据与事件边界。上传上限与 Chunk 参数见 [资料基础设施详细设计](./资料基础设施详细设计.md)。

`[目标设计]` 上传和业务提交分离；Source 是稳定逻辑对象，Snapshot 不可变；解析、Chunk、Embedding、全文与向量索引携带 Source Version 和 Projection Version。更新创建新 Snapshot，不原地改旧引用。删除或 ACL 变化写 Tombstone，经 Outbox 传播到索引、缓存、评测副本、Wiki 回链、Memory 与 Artifact 依赖。

**新问题。** 投影延迟、乱序事件、重建耗时和删除传播成为核心运维指标。消费者用版本栅栏拒绝旧事件，Read Path 回表验证当前权限与版本。

**迁移触发。** 当前按固定 Chunk 参数起步。只有真实文档类型显示召回质量、索引成本或上下文连贯性存在系统差异时，才引入按格式分段、语义切片或层级索引。完整设计见 [资料基础设施详细设计](./资料基础设施详细设计.md)。

## 6. QA RAG：从纯向量 Top K 到可拒答证据选择

### V0：Embedding Top K 后生成

纯向量召回实现快，适合语义相近查询。

**Bad Case。** 专有名词、编号和精确短语漏召回；相似文本挤占候选；相邻 Chunk 断裂；模型在证据不足时仍输出流畅答案；引用存在但不支持具体 Claim。

**错误判断。** 盲目增大 Top K 会增加噪声、Token 和延迟；只换更大模型不能补回未召回证据；有引用不等于引用准确。

### 修复：多路召回、融合、重排与选择性回答

`[当前实现]` QA 已具备多路召回、RRF、有限 Rerank 与 Evidence Selection。可回放参数见 [问答 RAG 链路设计](./问答RAG链路设计.md)，不是最优值证明。

`[目标设计]` 关键词和向量并行召回，按 RRF 融合，重排后做 Workspace/版本/ACL 过滤，再选择能够覆盖 Claim 的 Evidence。证据不足、冲突未解决或权限不可验证时拒答或明确不确定性。

**新问题。** 混合检索增加索引一致性、候选预算和评测复杂度。必须同时看 Recall@K、nDCG、引用准确率、Claim-Evidence Coverage、Faithfulness、Refusal Recall/Precision、Answer Coverage 与 Selective Accuracy，避免通过扩大拒答范围换取表面正确率。

**迁移触发。** 仅当实体关系、多跳问题在固定金标集上持续失败，且普通混合检索无法改善时，再试点 GraphRAG；它增加图构建、更新、权限裁剪和解释成本。完整设计见 [问答 RAG 链路设计](./问答RAG链路设计.md)。

## 7. Note：从回答生成到可审阅草稿

### V0：复用 QA Prompt 输出长文

复用 QA 能快速得到笔记，但答案式 Top K 只覆盖离散证据，缺乏连续阅读语境；直接写回还会覆盖用户编辑。

**Bad Case。** 标题命中但正文关系断裂；引用 Chunk 上下文不足；模型加入评价性措辞；重试生成不同内容；用户已修改目标 Note 时旧草稿仍写回。

### 修复：Anchor、阅读窗口、Draft Revision 与条件写回

`[当前实现]` Note 使用独立于 QA 的检索预算。参数见 [Note 链路设计](./Note链路设计.md)，只表示当前配置事实。

`[目标设计]` 先召回 Anchor，再展开同 Snapshot 的连续阅读窗口，做去重、覆盖与预算选择；生成中性 Draft Revision，用户审核后用目标 Head 版本条件写回。Prompt Injection 内容留在不可信证据区，模型无法授予写权限。

**新问题。** 窗口过大会稀释相关性，过小会断上下文；条件写回会产生可见冲突。参数通过窗口覆盖、人工修改率、引用质量和 Token 成本共同选择，冲突进入比较/合并而不是覆盖。

**迁移触发。** 只有跨 Source 长文、章节规划和多轮编辑成为主工作流时，才引入更重的文档规划器与协同编辑模型。完整设计见 [Note 链路设计](./Note链路设计.md)。

## 8. Wiki：从可编辑页面到版本化知识投影

### V0：一张页面表保存最新正文

CRUD 简单，但无法解释哪次修改改变了事实，反链和搜索也容易与正文不同步。

**Bad Case。** 页面覆盖后历史丢失；重命名形成断链；Source 更新但 Wiki 仍显示旧结论；搜索索引返回已撤权或旧版本页面；自动修复修改过多内容。

### 修复：不可变 Page Version、Current Head 与治理状态

`[当前实现]` Wiki 已有页面、版本、链接、来源回链和检索相关接口与数据结构。

`[目标设计]` Page Version 不可变，Current Head 是受版本条件保护的指针；Link、Backlink、Graph 和 Search 都是投影。Source 版本变化生成 Stale Dependency 或 Governance Issue，自动修复只生成 Proposal 或新 Version，经审核后切 Head。搜索命中读时回 MySQL 验证 Head 与 ACL。

**新问题。** 大规模反链重建、重命名和依赖传播会产生写放大。只有图查询、治理队列或跨页影响分析形成稳定需求时才增加专门图存储，且图仍是投影。

完整设计见 [Wiki 模式设计](./Wiki模式设计.md)。

## 9. Deep Research：从单 Prompt 到可恢复证据生产线

### V0：一次 ReAct 循环完成搜索和成文

它适合 Demo，但模型容易重复搜索、过早成文、引用搜索摘要、忽略来源冲突，进程中断后无法知道哪些外部调用已发生。

**错误判断。** 增加最大步骤或并行 Agent 会放大重复调用和合并冲突；Checkpoint 记录“走到哪一步”不等于外部搜索和抓取可安全重放。

### 修复：Stage、Ledger、Barrier、Receipt 与 Typed Claim

`[当前实现]` `V097-V104` 已加入 Evidence Validation、Intent Matrix、Run Stage、Checkpoint Hydration、Role Result、Discovery Proposal、Feature Flag Snapshot 和 Completion Replay Observation。Research Worker 与主服务通过 Task、Lease、Fencing 和 Completion 契约协作。

`[目标设计]` Research 按规划、发现、获取、抽取、验证、冲突处理、综合与 Artifact 提交分阶段；Canonical Ledger 保存 Evidence 和 Candidate，Stage Barrier 只在支持条件满足后推进。搜索、网页、模型和工具调用都有 Operation Receipt。数字、单位、日期和比较类 Claim 先做确定性 Typed Validation，再进入语义验证。

**新问题。** 更严格的门禁会降低表面完成率并增加 `NO_SUPPORTED_CANDIDATE`。这是正确失败，不应通过放松引用门槛换取“成功”。需要同时评估完成率、证据充分率、冲突发现、恢复率、成本和尾延迟。

`[已测-模拟]` 历史验收与 `NO_SUPPORTED_CANDIDATE` 失败屏障见 [质量、测试与发布门禁](./测试与评测/NoteWeave-评测指标报告.md)。该结果证明失败门禁生效，不证明 Research 已具备生产质量。

**迁移触发。** 等跨日等待、动态 Signal、历史兼容和人工干预分支让自建状态机维护成本明显升高时，再评估 Temporal 或 LangGraph 持久化。完整设计见 [Deep Research 架构文档](./DeepResearch-ResearchAgent架构文档.md)。

## 10. Artifact：从生成文件到 Skill-first 交付

### V0：Action + Prompt 直接输出文件

Bad Case 包括格式漂移、整篇重跑、任意 Tool 扩权、Worker 成功但 Callback 丢失、对象已写但 Version 未提交，以及旧 Source 被盲写回。

### 修复：Catalog、Graph、Receipt、Validator 与 Version

`[当前实现]` 系统已有 Skill-first 目录、输入快照、Graph、Verifier/Repair、等待恢复、Callback 幂等、Artifact Version、比较、回滚、导出与写回接口。

`[目标设计]` Skill 注册包含签名、Schema、风险、Provider 允许列表、预算和发布证据；模型只建议 Skill 与工具意图。每个外部节点保存 Operation Receipt，Verifier 通过后才能提交 Version/File Manifest；审批绑定精确输入摘要和目标，写回使用目标版本条件。

**新问题。** Skill Metadata 可能被投毒，发布组件组合可能爆炸，长 Provider 会产生未知结果。通过受签名 Catalog、Release Bundle、等待态、结果对账和按 Skill 灰度控制。

**迁移触发。** 只有等待、Timer、Signal 与历史分支超过现有 Task/Checkpoint 可验证范围时才引入 Durable Workflow；只有产物可自然分区且合并确定时才并行多 Agent。完整设计见 [Artifact Skill 执行架构](./Artifact-Skill执行架构.md)。

## 11. Memory：从历史拼接到受控上下文编译

### V0：聊天历史或自动摘要回填 Prompt

Bad Case 是 Token 膨胀、一次错误长期污染、临时偏好被永久化、跨 Workspace 泄漏和无法撤销。换成向量检索只解决“找得到”，不解决“该不该记”。

### 修复：Signal、Candidate、Review、Revision、Control Pack 与 Outcome

`[当前实现]` 系统已有两代 Memory 模型，`V080/V082` 建立并切换到 canonical runtime，HTTP 能力覆盖 Signal、Promotion、Review、Revision、Control Pack、Revoke、Outcome 和 Inspector。

`[目标设计]` 原始交互只形成 Signal，Extractor 只能提出 Candidate；策略和人工/规则审核决定 Version；Compiler 按 Run Type、ACL、有效期和 Token 预算生成确定性 Control Pack。Outcome 只产生新 Candidate。Revoke 主动传播到缓存、索引和评测副本，并由读时 Watermark 拒绝残留。

**新问题。** 自动批准、长期漂移和撤销传播都需要持续观测。先 Shadow Recall，再只读提示，最后才允许极低风险自动批准。

**迁移触发。** 只有时间关系和多跳查询在固定评测中证明平面 Item 不足时才引入知识图谱投影；向量或图始终不取代治理真源。完整设计见 [Memory 机制详细设计](./Memory机制详细设计.md)。

## 12. 公共可靠性：从“重试即可”到结果可判定

### V0：HTTP 成功、Kafka ACK 或异常重试

常见错误是把 Outbox 事务提交当作消息已发布，把 Kafka ACK 当作业务完成，把 Callback 200 当作 Artifact 已提交，或把网络超时当成 Provider 一定失败。

**Bad Case。** Dispatcher 发布后崩溃产生重复；Worker 执行成功但 Callback 丢失；Lease 到期后旧 Worker 继续写；Provider 已扣费但客户端超时；Checkpoint 恢复重复调用外部工具；跨组件恢复后出现缺失、重复和未知状态。

### 修复：分层保证与对账

`[当前实现]` Task、Outbox、Callback Receipt、Lease、Heartbeat、Fencing、Checkpoint 与 Worker 契约已存在于主要长任务链路。

`[目标设计]` Outbox 保证业务事务内记录“需要发布”；Kafka ACK 只确认 Broker 接收或消费位点；Callback Receipt 证明某个 Payload 被控制面接收；业务终态必须由真源状态机、版本条件和副作用 Receipt 共同决定。结果未知先查询或等待，不立即重试非幂等调用。

OpenTelemetry 的 Producer、Publish、Receive、Process Span 与 Span Link 用于诊断异步因果；全量 Metrics 计算 SLO。Collector 队列、重试和 WAL 只保护遥测，不替代业务消息保证。

**新问题。** 更强对账增加存储与运维成本，因此只对不可逆、高成本或用户可见副作用保存完整 Receipt。低风险只读调用可以在明确幂等前提下重试。

**迁移触发。** 当未知结果、跨日等待、Timer 和人工 Signal 成为主要任务形态，且自建状态机缺陷率与维护成本持续超过引入工作流平台的成本时再迁移。公共契约见 [API 与事件契约](./API与事件契约-v2.md)。

## 13. 发布、可观测、安全与灾备演化

### 发布

从单独升级模型，演化为 Release Bundle：Model、Prompt、Schema、Validator、Retrieval/Index、Skill/Graph、Policy 和 Feature Flag 一起版本化。固定回放通过后按 Workspace/能力灰度，错误预算 Burn Rate 超阈值时暂停发布、降级或回滚。进行中的 Run 固定创建时 Bundle，避免中途语义变化。

### 可观测

从日志字符串演化为状态指标、低基数 Metrics、结构化事件和采样 Trace。Head Sampling 保留基线，Tail Sampling 提升错误与长尾保留率；Workspace ID、Source ID 和 Prompt 不进入 Metric Label。Trace 用于定位，SLO 必须由全量 Metrics 计算。

### 安全

从 API 登录校验演化为对象级 ACL、运行时最小授权、审批绑定、SSRF 防护、供应链审计与删除传播。RAG 和模型微调不能消除 Prompt Injection。策略服务故障时，高风险写操作 Fail Closed。

### 灾备

从单组件备份演化为跨组件恢复顺序：先恢复身份、Workspace 与 MySQL 真源，再恢复对象载荷，随后恢复 Kafka/Outbox 推进，最后重建 Elasticsearch、缓存和 Memory 投影。RTO/RPO 按能力定义，恢复后用业务 ID、Version、Digest 与 Receipt 对账缺失、重复和未知状态。备份存在不等于可恢复，必须做恢复演练。

## 14. 规模变化后的迁移判据

| 变化信号 | 先做什么 | 何时引入更重方案 |
|---|---|---|
| 单库锁等待或热点上升 | 索引、短事务、批处理、归档和读写路径治理 | 明确租户隔离或分片收益后再分库 |
| 检索规模增长 | Bulk、Refresh、Shard、候选预算和冷热索引调优 | 单集群隔离与恢复目标无法满足时拆集群 |
| 长任务跨日等待增多 | 完善 Receipt、Timer、Signal 与对账 | 历史分支难以验证时引入 Durable Workflow |
| Artifact Skill 数量增长 | Catalog 签名、兼容矩阵和 Bundle 收敛 | 独立团队和发布频率需要时拆 Skill 平台 |
| Memory 冲突与时间关系增长 | 有效期、冲突类型和投影优化 | 图查询质量收益明确时增加图投影 |
| 跨地域与合规要求 | 数据分级、驻留、备份恢复和密钥边界 | 合同或法规要求明确时做区域化控制面 |
