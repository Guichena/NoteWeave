# NoteWeave v2 资料基础设施详细设计

## 1. 定位

资料基础设施是研究工作台的底层资料底座，负责把用户上传文件、URL 导入、文本导入和系统确认后的生成成果，统一转成可解析、可检索、可引用、可回放的 `Source` 对象。

它不是一个单独的产品模式，而是支撑三种聊天回答链路、Deep Research、右侧产物生成和 Wiki / Note 沉淀的基础能力。

正式口径：

`资料基础设施以 MySQL 记录业务真源，以 MinIO 保存原始文件和快照，以 Kafka 解耦解析、切片、索引和后处理任务，以 Elasticsearch 支撑资料检索，以统一 Source / Snapshot / Chunk 模型保证系统生成内容和用户上传文件拥有一致的后续消费方式。`

## 2. 设计目标

这部分设计只解决五个核心问题：

1. 文件怎么稳定上传
2. 原始内容怎么保存和追溯
3. 解析、切片、索引怎么异步解耦
4. 系统生成成果怎么像用户上传文件一样进入资料池
5. 聊天、Note、Wiki、Deep Research、Artifact Runtime 怎么消费同一套资料底座

不额外建设通用文件网关、独立文档中台或复杂数据湖。

## 3. 核心对象

### 3.1 Source

`Source` 是工作台内的统一资料对象。

它只表达“这份资料已经进入当前研究工作台，并可以被后续链路消费”。

典型来源：

- 用户上传文件
- URL 导入
- 用户粘贴文本
- Deep Research 确认后的研究报告
- 右侧产物栏确认保存为资料的 Artifact

关键字段：

- `id`
- `workspace_id`
- `topic_scope_id`
- `source_type`
- `title`
- `origin_type`
- `origin_ref`
- `mime_type`
- `status`
- `parse_status`
- `index_status`
- `created_by`
- `created_at`
- `updated_at`

### 3.2 Source Snapshot

`Source Snapshot` 是资料的版本快照。

它解决两个问题：

- 同一份资料更新后，历史引用仍然能回到当时版本
- Deep Research 和 Artifact 生成时可以冻结本次使用的资料版本

关键字段：

- `id`
- `source_id`
- `version_no`
- `file_object_id`
- `object_key`
- `content_hash`
- `parser_version`
- `snapshot_status`
- `created_at`

### 3.3 File Object

`File Object` 是 MinIO 对象引用。

它只保存对象存储信息和去重信息，不承载业务语义。

关键字段：

- `id`
- `workspace_id`
- `bucket_name`
- `object_key`
- `content_hash`
- `size_bytes`
- `content_type`
- `ref_count`
- `status`

### 3.4 Source Chunk

`Source Chunk` 是检索和引用的最小文本单元。

它必须能回到：

- 所属 `Source`
- 所属 `Source Snapshot`
- 原文位置
- MinIO 中的解析文本或原始文件

关键字段：

- `id`
- `source_id`
- `source_snapshot_id`
- `chunk_no`
- `content`
- `page_no`
- `section_path`
- `char_start`
- `char_end`
- `token_count`
- `metadata_json`

## 4. 文件上传链路

### 4.1 创建上传事务

用户在研究工作台上传文件时，Java 主系统先创建 `document_upload`。

创建时确定：

- 所属 `workspace_id`
- 所属 `topic_scope_id`
- 文件名
- 文件大小
- MIME 类型
- 分片大小
- 分片数量
- 过期时间

上传事务状态：

- `INIT`
- `UPLOADING`
- `MERGING`
- `MERGED`
- `FAILED`
- `EXPIRED`

### 4.2 分片上传

前端按分片上传到后端，后端校验分片大小与 MD5 后写入 MinIO 临时路径。

推荐对象路径：

```text
workspace/{workspace_id}/upload_tmp/{upload_id}/{chunk_index}
```

每个分片写入 `upload_chunk`：

- `upload_id`
- `chunk_index`
- `chunk_md5`
- `size_bytes`
- `object_key`

### 4.3 合并与去重

全部分片上传完成后，Java 主系统进入 `MERGING`。

合并步骤：

1. 校验分片数量和顺序
2. 合并为最终对象
3. 计算全文 hash
4. 查询是否已有相同 `content_hash`
5. 生成或复用 `file_object`
6. 创建 `source`
7. 创建 `source_snapshot`
8. 写入解析任务 outbox

推荐最终对象路径：

```text
workspace/{workspace_id}/source/{source_id}/snapshot/{version_no}/original/{file_hash}.{ext}
```

## 5. MinIO 存储规范

### 5.1 Bucket 建议

保持 bucket 数量少，优先用 object key 区分业务类型。

建议：

- `noteweave-source`
- `noteweave-derived`
- `noteweave-export`

### 5.2 Object Key 分类

原始文件：

```text
workspace/{workspace_id}/source/{source_id}/snapshot/{version_no}/original/{file_name}
```

解析正文：

```text
workspace/{workspace_id}/source/{source_id}/snapshot/{version_no}/parsed/content.md
```

解析结构：

```text
workspace/{workspace_id}/source/{source_id}/snapshot/{version_no}/parsed/structure.json
```

Deep Research 快照：

```text
workspace/{workspace_id}/research/{research_run_id}/snapshot/{checkpoint_id}.json
```

Artifact 导出文件：

```text
workspace/{workspace_id}/artifact/{artifact_id}/version/{version_no}/export/{format}/{file_name}
```

## 6. Kafka 异步处理链路

### 6.1 事务外盒

所有需要异步执行的资料任务都先写入 MySQL `task` 和 `task_outbox`，再由 outbox publisher 投递到 Kafka。

不从业务事务里直接发送 Kafka 消息。

这样可以保证：

- Source 已创建，解析任务才会被投递
- 投递失败可以补偿
- 消费重复时可以幂等处理

### 6.2 Topic 建议

资料解析：

```text
noteweave.source.parse
```

资料切片：

```text
noteweave.source.chunk
```

检索索引：

```text
noteweave.source.index
```

系统生成成果资料化：

```text
noteweave.generated.ingest
```

导出文件生成：

```text
noteweave.artifact.export
```

### 6.3 任务状态

资料处理任务统一走 `task` 状态机：

- `PENDING`
- `RUNNING`
- `RETRYING`
- `SUCCEEDED`
- `FAILED`
- `CANCELLED`

Source 本身只保留聚合状态：

- `parse_status`
- `index_status`
- `status`

这样前端可以快速展示资料是否可用，而后端仍能保留完整任务轨迹。

## 7. 解析、切片与索引

### 7.1 解析

解析任务负责把不同格式资料转成统一中间结果。

输入：

- `source_id`
- `source_snapshot_id`
- MinIO 原始文件路径
- MIME 类型

输出：

- 解析正文
- 文档结构
- 标题和摘要
- 页码、章节、表格、图片占位等结构元数据

解析产物写入 MinIO，解析状态写回 MySQL。

### 7.2 切片

切片任务从解析正文和结构元数据生成 `source_chunk`。

切片原则：

- 保留章节路径
- 保留页码或原文位置
- 控制 chunk token 长度
- 支持相邻窗口回读
- 为引用回跳保存稳定位置

### 7.3 索引

索引任务把 `source_chunk` 写入 Elasticsearch。

基础索引字段：

- `workspace_id`
- `source_id`
- `source_snapshot_id`
- `chunk_id`
- `title`
- `summary`
- `content`
- `section_path`
- `tags`
- `metadata`
- `created_at`

向量索引可以作为增强能力存在，但当前设计不强依赖独立向量数据库。

## 8. 系统生成成果如何进入资料池

Deep Research 最终研究报告、右侧产物栏生成的报告、FAQ、学习指南、Wiki 页面草稿和 Note 文档，默认先是 `Artifact` 或对应业务对象。

只有用户明确点击“保存为资料”后，系统才创建新的 `Source`：

1. 读取生成成果的当前版本
2. 渲染为 Markdown 中间文件
3. 写入 MinIO
4. 创建 `Source`
5. 创建 `Source Snapshot`
6. 进入解析、切片、索引链路

这样系统生成内容和用户上传文件在后续检索中处于同一层级。

## 9. 与五条核心能力的关系

### 9.1 问答 RAG

问答 RAG 默认读取当前工作台已完成解析和索引的 `Source Chunk`。

它关注低延迟和引用回跳。

### 9.2 Note 链路

Note 链路先用标题、摘要、标签、结构化元数据和历史笔记定位候选 `Source`，再打开原文窗口读取片段。

它依赖资料基础设施提供稳定的资料级元数据和原文窗口。

### 9.3 Wiki 链路

Wiki 链路优先读取已有 Wiki 页面网络，同时通过来源回链回到 `Source Snapshot` 和 `Source Chunk`。

它依赖资料基础设施保证 Wiki 页面背后的引用仍然可追溯。

### 9.4 Deep Research

Deep Research 过程资产默认不直接进入主检索链路。

最终研究报告和被用户确认纳入的关键来源，才进入 `Source` 体系。

### 9.5 右侧产物生成

Artifact Runtime 默认以当前工作台资料池和已保存为资料的系统产物为原材料。

它不直接读取未确认的研究过程资产，也不默认把聊天上下文当作资料来源。

## 10. 接口草案

创建上传：

```http
POST /api/workspaces/{workspaceId}/uploads
```

上传分片：

```http
PUT /api/uploads/{uploadId}/chunks/{chunkIndex}
```

完成上传：

```http
POST /api/uploads/{uploadId}/complete
```

查询资料处理状态：

```http
GET /api/sources/{sourceId}/processing-status
```

系统成果保存为资料：

```http
POST /api/artifacts/{artifactId}/versions/{versionNo}/save-as-source
```

## 12. 面试讲法

这部分可以概括为：

`我没有把文件上传简单做成文件表，而是把它设计成工作台级资料基础设施：MySQL 保存 Source / Snapshot / Chunk 真源，MinIO 保存原始文件、解析正文和导出快照，Kafka 通过事务外盒驱动解析、切片、索引和生成成果资料化，最终让用户上传文件、研究报告和确认后的系统产物都进入同一套可检索、可引用、可回放的资料底座。`

## 13. 最终口径

资料基础设施是简历亮点里的工程底座，核心价值不在“用了 Kafka 和 MinIO”，而在于把文件上传、对象存储、异步解析、索引准备、版本快照和系统生成成果资料化串成同一条可落地链路。
