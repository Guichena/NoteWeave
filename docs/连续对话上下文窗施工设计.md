# NoteWeave v2 连续对话上下文窗施工设计

## 1. 目标

当前 `QA / Note / Wiki` 三条链路都已经支持“上一轮追问增强”，但这还不等于真实的连续对话理解。

现在的实现本质上只会把：

- 当前问题
- 上一轮用户问题
- 上一轮回答摘要

拼进检索 query。

这对“继续展开”“它的第二点呢”这类一跳追问已经有帮助，但还不能稳定承接：

- 连续 3 到 5 轮围绕同一主题的深聊
- 中间出现一次轻度改写、压缩、分点、对比后的继续追问
- QA / Note / Wiki 三条链路在同一会话里持续围绕同一主题推进

因此，本次施工目标是把当前“单轮追问增强”升级为：

`主题感知滚动上下文窗`

英文口径：

`Topic-Aware Rolling Context Window`

一句话定义：

`系统不再只拼接上一轮，而是围绕当前问题动态编译最近连续相关的多轮对话、前序主题摘要和主题锚点，再把这份上下文包注入 QA / Note / Wiki 三条检索链路。`

## 2. 设计原则

### 2.1 不做无限聊天记录拼接

不能把整段历史对话直接塞进检索 query。

原因：

- token 成本线性上升
- 检索 query 噪声越来越大
- 长上下文会削弱真正关键主题的权重
- 三条链路都会被历史闲聊污染

### 2.2 滑动窗口只是工作记忆，不是全部记忆

本方案不是“最近 N 条消息”的普通窗口，而是：

- 最近连续相关轮次作为 `工作记忆窗`
- 更早但同主题的轮次压成 `前序主题摘要`
- 从多轮问题中抽出 `主题锚点`

### 2.3 三条链路共享一套上下文编译器

`QA / Note / Wiki` 的差异应该体现在检索方式，而不是各自维护一套聊天上下文逻辑。

因此：

- 上下文编译发生在 `ChatService`
- 编译结果统一注入三条链路
- 各链路只决定如何使用这份上下文包

## 3. 方法口径

本次实现采用一个轻量但可讲亮点的方法：

### 3.1 Topic-Aware Rolling Context Window

由三部分组成：

1. `Rolling Working Window`
2. `Topic Anchor`
3. `Topic Summary`

### 3.2 Dual-Speed Context Gate

为了让方案更稳，同时避免过度设计，引入一个轻量门控概念：

- `短速度视角`
  最近几轮对话里，用户当前显式在追问什么
- `长速度视角`
  这段连续对话整体稳定围绕什么主题

当短速度问题和长速度主题一致时，继续沿用当前主题窗。

当短速度问题明显切走时，认为发生了 `topic drift`，重新截断工作记忆窗并重建主题摘要。

工程上不引入额外模型，只用启发式规则实现这套门控。

## 4. 上下文结构

本次在代码里引入的上下文对象应至少表达下面这些信息：

```text
ConversationContext
  - retrievalQuestion
  - contextApplied
  - windowTurnCount
  - topicAnchor
  - topicSummary
  - workingTurns
```

解释：

- `retrievalQuestion`
  最终送入检索层的上下文增强 query
- `contextApplied`
  本轮是否判定为连续追问场景
- `windowTurnCount`
  当前纳入了多少轮连续相关对话
- `topicAnchor`
  当前连续对话最稳定的主题锚点
- `topicSummary`
  工作窗之外、更早历史的主题压缩摘要
- `workingTurns`
  真正纳入窗口的轮次列表

## 5. 编译流程

### 5.1 步骤 1：判定是否需要上下文增强

触发条件：

- 问题非常短
- 出现追问词
- 出现代词指代
- 出现“第二点 / 前者 / 后者 / 这个 / 它 / 继续 / 展开 / 补充”这类延续信号

如果不是连续追问类问题：

- 直接按当前问题检索
- 不进入上下文编译

### 5.2 步骤 2：回收最近历史并按轮次重组

不再只取最近一条用户消息和最近一条助手消息，而是：

- 回收最近 `10 ~ 12` 条消息
- 按 `USER -> ASSISTANT` 重组成对话轮次

轮次结构：

```text
ConversationTurn
  - userQuestion
  - assistantAnswerSummary
  - messageSeq
```

### 5.3 步骤 3：构建工作记忆窗

从最近轮次开始向前回看，最多吸收最近 `3` 轮相关对话。

吸收规则：

- 第一轮一定吸收
- 如果更早轮次与当前追问存在明显主题连续性，则继续吸收
- 如果出现明显话题边界，则停止向前扩展

工作窗不是“固定 3 轮”，而是“最多 3 轮相关轮次”。

### 5.4 步骤 4：识别主题边界

本次不引入模型判边界，只做轻量启发式：

- 如果当前问题主要由追问词组成，默认仍沿用当前主题
- 如果当前问题和最近主题存在显著关键词重叠，认为同主题
- 如果当前问题出现新的显式对象，而与最近主题几乎无重叠，认为切换主题

例如：

- `继续展开它`
  同主题
- `那第二点为什么重要`
  同主题
- `换成 Wiki 说说`
  大概率切主题
- `我们再看上传链路`
  大概率切主题

### 5.5 步骤 5：提炼主题锚点

主题锚点不是知识图谱实体，也不是长期 Memory，只是本段连续对话的稳定中心。

轻量实现：

- 从当前问题与工作窗中的用户问题里
- 过滤“继续 / 展开 / 这个 / 它 / 第二点 / 刚才”这类追问词
- 选出最能代表主题的一条高信息量问题短语

示例：

- `Note 和 Wiki 两种检索方式有什么区别？`
- `AnchorAlpha 的资料定位`
- `Alpha策略 的关联页面`

### 5.6 步骤 6：生成前序主题摘要

如果同一主题连续对话超过工作窗容量：

- 工作窗之外但仍属于同主题的更早轮次
- 被压缩成一段短摘要

摘要规则：

- 只保留用户问题主旨
- 辅以助手回答的关键信息
- 不保留 markdown 标题、长证据块、卡片细节

目标是让模型知道：

- 之前已经围绕什么讨论过
- 这轮追问是在什么背景上继续推进

### 5.7 步骤 7：编译最终 retrievalQuestion

最终 query 结构统一为：

```text
当前问题：...
主题锚点：...
连续对话窗口：
- 用户：...
  助手摘要：...
- 用户：...
  助手摘要：...
前序主题摘要：...
```

这样三条链路拿到的是“为检索服务的上下文包”，而不是杂乱聊天原文。

## 6. 与三条检索链路的结合方式

### 6.1 QA 链路

`QA` 依旧是最快的一条链路。

它使用上下文包的方式：

- 用 `retrievalQuestion` 召回 chunk
- 在回答正文中提示已结合连续对话窗口
- 在证据选择区暴露：
  - 连续对话窗口轮数
  - 主题锚点
  - 前序主题摘要是否生效

适合承接：

- 连续追问
- 分点展开
- 比较后继续深问

### 6.2 Note 链路

`Note` 不是简单复用 QA query，而是把上下文包喂给“资料级候选定位”。

影响点：

- `findNoteRecallPlan`
- `readEntriesMetadataForNote`
- `openSourceWindowsForNote`

好处：

- 连续多轮整理时，不会把每轮都当成孤立资料检索
- 可以稳定围绕同一批候选资料和原文窗口持续深读

### 6.3 Wiki 链路

`Wiki` 主要依赖页面网络而不是 chunk。

上下文包对它的作用是：

- 连续多轮问同一主题时，优先保持同一组页面网络
- 避免“它 / 那一页 / 这个关系”这种追问回退成泛搜

影响点：

- `findRelevantWikiPageContexts`

## 7. 工程范围控制

这次只做“轻量可上线版”，不做下面这些：

- 不新增数据库表
- 不引入 Redis 会话摘要缓存
- 不引入外部 topic classifier
- 不把这套上下文窗升级为长期 Memory
- 不做跨会话上下文继承

这次只解决：

`单会话内部的连续多轮对话理解`

## 9. 函数级施工清单

这一节用于直接指导后续 AI 编码，不再只讲概念，而是明确到函数、输入输出和改造顺序。

### 9.1 现行落点

本次连续对话上下文窗施工统一收口在：

- `backend/src/main/java/com/noteweave/chat/ChatService.java`

原因：

- 三条链路共享聊天上下文编译器
- 当前上下文增强逻辑就在 `ChatService`
- 这次不引入新表、不引入新中间件、不拆新服务

### 9.2 需要维护的核心对象

#### `ConversationHistoryMessage`

用途：

- 承接数据库里最近消息的轻量读取结果

字段：

- `messageSeq`
- `role`
- `content`

#### `ConversationTurn`

用途：

- 把零散消息重组成“用户一问 + 助手一答”的轮次

字段：

- `userQuestion`
- `assistantAnswerSummary`
- `messageSeq`

#### `ConversationContext`

用途：

- 作为三条链路共享的上下文编译结果

字段：

- `currentQuestion`
- `retrievalQuestion`
- `contextApplied`
- `windowTurnCount`
- `topicAnchor`
- `topicSummary`
- `workingTurns`

### 9.3 函数职责与契约

#### `buildConversationContext(conversationId, currentUserMessageId, currentQuestion)`

职责：

- 整个连续对话上下文窗的主入口

输入：

- 当前会话 id
- 当前用户消息 id
- 当前问题正文

输出：

- 一个完整的 `ConversationContext`

约束：

- 如果当前问题不是连续追问场景，必须返回 `contextApplied=false`
- 不能把整段历史消息原文直接拼进 `retrievalQuestion`
- 必须保证 `retrievalQuestion` 是“可供检索的上下文包”，不是调试日志

#### `buildConversationTurns(history)`

职责：

- 把最近消息重组为轮次

输入：

- 最近 N 条 `ConversationHistoryMessage`

输出：

- 按时间正序排列的 `ConversationTurn` 列表

约束：

- 只保留可形成 `USER -> ASSISTANT` 的完整轮次
- 助手回答必须先做 `stripMarkdownForContext`

#### `buildWorkingTurns(currentQuestion, turns)`

职责：

- 从最近轮次里截取最多 3 轮连续相关对话

输入：

- 当前问题
- 最近轮次列表

输出：

- 真正纳入工作窗的轮次列表

约束：

- 第一轮必须吸收
- 只要检测到明显话题边界，就停止继续向前扩展
- 返回结果必须保持时间正序

#### `belongsToCurrentTopic(currentQuestion, currentAnchorCandidate, candidateQuestion, workingTurns)`

职责：

- 判断一个更早轮次是否仍属于当前主题

输入：

- 当前问题
- 当前问题归一化后的候选锚点
- 待吸收轮次的问题
- 已经在工作窗里的轮次

输出：

- `true / false`

约束：

- 追问型短问题优先沿用当前主题
- 显式新对象问题要允许切断旧主题

#### `buildTopicAnchor(currentQuestion, workingTurns)`

职责：

- 从当前问题和工作窗轮次中提取最稳定主题锚点

输出要求：

- 尽量是“高信息量的主题短语”
- 不能退化成“继续展开它 / 第二点为什么重要”这类追问壳子

#### `buildTopicSummary(topicAnchor, workingTurns, allTurns)`

职责：

- 当同主题轮次超过工作窗容量时，对更早轮次做轻量压缩

输出要求：

- 优先保留用户问题主旨
- 辅以一句助手回答摘要
- 长度可控、可直接拼进 `retrievalQuestion`

#### `shareTopicTerms(left, right)`

职责：

- 做轻量主题重叠判断

约束：

- 不依赖外部模型
- 优先使用归一化短语包含关系
- 其次使用主题词交集

#### `normalizeTopicPhrase(question)`

职责：

- 去掉追问壳子，保留主题主体

约束：

- 要去掉“继续 / 展开 / 第二点 / 它 / 这个”等噪声追问词
- 不能把真正的主题对象一起删掉

### 9.4 三条链路接入点

#### QA

接入函数：

- `buildQaAnswer`

必须做到：

- 检索用 `context.retrievalQuestion()`
- 问题分类用 `context.currentQuestion()`
- 证据区输出 `连续对话窗口 / 主题锚点 / 前序主题摘要`

#### Note

接入函数：

- `buildNoteAnswer`
- `buildNoteSynthesis`

必须做到：

- `findNoteRecallPlan`
- `readEntriesMetadataForNote`
- `openSourceWindowsForNote`

这三个入口都使用 `context.retrievalQuestion()`

同时回答文案里要体现：

- 不是孤立查询
- 已纳入连续对话窗口
- 当前主题锚点是什么

#### Wiki

接入函数：

- `buildWikiAnswer`

必须做到：

- `findRelevantWikiPageContexts` 使用 `context.retrievalQuestion()`
- 回答区和上下文区体现页面网络是围绕同一主题连续追问命中的

### 9.5 不需要新增的工程对象

这次明确不做：

- 新 Spring Service
- 新 Repository
- 新 SQL migration
- 新 Redis key 设计
- 新 Kafka topic
- 新配置文件

这样可以保证施工范围稳定在：

- `ChatService`
- 现有契约测试
- 少量设计文档同步

## 10. TDD 施工矩阵

### 10.1 主干场景

| 场景 | 期望 |
|---|---|
| QA 连续三轮追问 | 命中最近连续对话窗口，不回到孤立检索 |
| Note 连续三轮追问 | 候选资料与原文窗口仍围绕原主题 |
| Wiki 连续三轮追问 | 页面网络仍围绕原页面组和页面关系 |

### 10.2 边界场景

| 场景 | 期望 |
|---|---|
| 连续 4 到 5 轮同主题对话 | 超出工作窗的更早轮次进入 `前序主题摘要` |
| 中途切到新主题 | 旧主题窗口被截断，不应污染新检索 |
| 当前问题很短，如“继续讲” | 允许强依赖上下文 |
| 当前问题是完整新问句 | 不应错误继承旧窗口 |
| 助手历史回答很长 | 进入工作窗前先做 markdown 剥离和摘要裁剪 |

### 10.3 测试文件落点

- `backend/src/test/java/com/noteweave/Phase3NoteWikiContractTest.java`

建议分工：

## 12. 对外讲法

最终可以这样讲：

`我们没有把长聊天记录简单拼进 prompt，而是设计了一个 Topic-Aware Rolling Context Window。系统把连续多轮对话分成工作记忆窗、主题锚点和前序主题摘要三层，再通过 Dual-Speed Context Gate 识别话题是否仍连续，并把编译后的上下文统一注入 QA、Note、Wiki 三条检索链路，从而降低长对话里的语义漂移和检索失焦。`
