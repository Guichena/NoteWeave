# NoteWeave v2 TDD与迁移总则

## 1. 核心原则

### 1.1 迁移优先

只要旧版 NoteWeave 的现有能力满足下面条件，就优先迁移而不是重写：

1. 业务语义仍然成立
2. 代码边界还能收敛到 v2 模型
3. 测试后风险可控

优先迁移：

1. 用户与权限基础设施
2. 文件上传、解析、切片、索引链路
3. 旧版 Wiki 的版本、引用、存储与检索能力
4. 审计、日志、导出、任务执行基础设施

不优先迁移：

1. 与旧版 `team / personal` 产品边界耦合的接口与页面
2. 没有清晰边界、几乎无法测试的“万能 service”
3. 与 v2 三链路模型明显冲突的旧领域对象

### 1.2 TDD 优先

每次开发都按下面顺序执行：

1. 先定义本次只覆盖哪个子阶段
2. 先写失败测试
3. 再写最小实现
4. 测试通过后再整理结构
5. 最后更新文档和提交

### 1.3 小闭环优先

每轮 AI 开发不要跨多个大能力，只做一个小闭环。

正确例子：

1. 只完成“创建上传事务”
2. 只完成“完成上传并创建 source”
3. 只完成“QA 模式返回 citation”

错误例子：

1. 一轮同时做上传、问答、Wiki、Artifact
2. 先把所有实体和 controller 壳子铺满，再回头补逻辑

## 2. 统一测试分层

### 2.1 后端

1. 单元测试
2. Repository / SQL 集成测试
3. Controller / 契约测试
4. 异步任务集成测试

### 2.2 前端

1. 组件测试
2. 页面流程测试

### 2.3 Worker

1. 输入输出契约测试
2. 阶段状态测试
3. 失败恢复测试

## 3. AI 开发模板

后续每轮开发都推荐按下面格式执行：

1. 读取对应阶段文档
2. 选择一个子阶段
3. 列出可迁移代码清单
4. 先写测试
5. 跑测试确认失败
6. 补最小实现
7. 跑测试直到通过
8. 小范围重构
9. 更新文档或 README
10. 提交并推送

## 4. 提交规范

建议提交信息带上阶段标识：

1. `phase1: bootstrap backend and flyway`
2. `phase2: implement source upload completion`
3. `phase3: add note mode answer flow`
4. `phase4: add artifact job runner`
5. `phase5: implement research run completion`

## 5. 完成定义

一个子阶段完成，至少满足：

1. 对应测试全部通过
2. 没有引入新的断链文档
3. 没有破坏上一子阶段闭环
4. 代码和文档能说明“这一步具体完成了什么”
