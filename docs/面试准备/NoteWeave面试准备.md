## 0. 人设、时间与简历定稿

**人设：** Java 后端 + AI 工程落地。主服务做鉴权、状态、版本提交和写回；模型与 Worker 只产出候选。不是「会调 API 的人」。

**时间：** 简历写 2026.01–2026.05。v2 仓库连续建设从 2026-05 起。开口先划校园 Agent 交付和个人改造，细节以 [项目事实卡](../简历亮点八股/08-项目事实卡与Ownership面试口径.md) 本人填写为准。

**口述节奏：**

```text
30 秒：下面这段开场
2 分钟：1.0 架构口述（细节表在 1.2～1.4，不要照表念）
每条 4 到 5 分钟：第 2～6 章（净讲约 3 分钟；再把该条缺的机制讲透就满）
选型：第 1.4 节；条内对照在总文档各章
继续追问：该章缩小版设计 / 应考故事 / 八股 30–34
```

**30 秒开场：** 校园资料如果只接大模型，没有课程来源、长任务失败不可解释、聊天摘要还会污染后续事实。NoteWeave 是来源驱动的资料研究工作台：Java 主服务管鉴权、版本和提交，Python Worker 按冻结输入做检索、研究和生成。核心方法不是「接了大模型」，而是把资料钉在 Snapshot 上，把长任务收成可验证、可恢复的状态。

### 简历正文（锁定）

**NoteWeave｜AI 资料研究工作台**

**2026.01 – 2026.05**

**核心技术：** `SpringBoot` `MySQL` `Redis` `Kafka` `Elasticsearch` `Skill Graph` `MCP`

**项目描述：** 面向校园资料研究与知识沉淀构建来源驱动工作台，覆盖多类型资料接入、QA/Note/Wiki 分场景知识链路、Deep Research、Skill 产物生成与长期记忆；Java 控制面持有权限与提交权，Python Agent Runtime 按冻结输入执行检索、研究与生成长任务。

**核心职责与贡献：**

1. **设计验证驱动的 Deep Research Agent：** 针对开放研究易漂移、中断不可恢复、引用不支撑结论的问题，采用 `Verification-Centric Research`，以 `Table-as-State` 将问题收成有界矩阵，统一组织实体、字段、Evidence 与结论。主服务保存权威状态，Worker 只提交候选；通过 Plan/Replan、Local/Global Verifier 和受限反证形成纠偏闭环，并配合逐轮 Checkpoint、Lease/Fencing 与引用审计。研究完成以证据门禁为准，证据不足明确失败。

2. **构建任务感知的 QA / Note / Wiki 知识链路：** 针对问答、深读、知识沉淀对「相关」定义不同、一套向量 TopK 效果不稳的问题，三条链路共享 Source 版本、Workspace ACL 与 Evidence 契约，按场景拆检索单元和写回语义。QA 融合 BM25、Vector 与 Weighted RRF，再经 Rerank 和 Evidence Selection 给出可拒答带引用回答；Note 先做资料级召回，再按 Reading Window 连续精读并审阅写回；Wiki 以不可变 Page Version 维护当前页，链接、反链和来源回链作为可重建投影。检索命中读时回库校验权限与当前版本；Scope Violation 作为硬门槛。

3. **搭建高可靠的事件驱动资料底座：** 针对大文件同步解析占住请求、业务库与搜索索引无法原子更新的问题，基于 MySQL、MinIO、Kafka 与 Elasticsearch 将原文件、业务状态和检索投影分离。解析、切片、Embedding 与索引写入走异步任务；同一数据库事务写入业务变更与 Transactional Outbox，消费端凭幂等键、版本栅栏、退避重试和死信重驱保证最终一致。删除先提交否定事实再扇出，投影可从真源重建。

4. **构建工程化 Agent 执行框架：** 针对一次 Prompt 生成结构漂移、工具越权、失败后全量重做的问题，将报告、测验、学习指南抽象为 `Skill Catalog`，以 Schema 驱动的 `Skill Graph` 编译获取、生成、校验与修复路径。Java Host 冻结输入并独占版本提交，Python Worker 只返回 Candidate，经 Verifier 后由 Host 落版本。通过内置 MCP 接入白名单资料与工具；结合 Redis 令牌桶、并发租约与任务状态持久化，实现 Workspace 级限流、资源隔离和故障恢复。

5. **设计面向长任务的 Context Engineering 与 Memory 体系：** 针对长对话全量回放导致 Token 膨胀、自动写记忆污染后续事实的问题，采用 Topic-aware Window 与增量摘要，只重算受新增消息影响的片段，并在任务启动时冻结可见资料与记忆版本。通过候选提取、门控晋升和版本化管理沉淀长期 Memory，将短期会话、用户记忆与资料证据分层隔离，避免偏好进入引用和事实链。

## 1. 整体架构

### 1.0 两分钟架构口述

先鉴权进入 Workspace。资料上传后原件进 MinIO，MySQL 保存 Source 身份和不可变 Snapshot，解析、切片、索引经 Outbox 异步投递；用户查库里的状态，不去探 ES。索引就绪后走 QA、Note、Wiki，或拉起 Deep Research、Artifact。主服务提交版本，Worker 只回候选；检索命中必须回库核权限和当前版本。断线按 MySQL 事件序号回放。Memory 只进后续约束，不进引用。当前没有覆盖全部能力的统一 Intent Router，入口按 `answer_mode` 或 `skill_key` 选链路。

五条贡献落在这条链的不同段：资料底座保证上传成功不等于能搜；QA / Note / Wiki 共享版本和权限，但检索单元和写回不同；Research 把开放问题收成有界矩阵，Artifact 用 Skill Graph 出可版本化产物；Context 冻结当次输入，Memory 只进约束不进引用。

选型要匹配约束。同步 HTTP 适合秒级演示；我们有大文件和可恢复长任务，所以上传和处理拆开。ES 适合词法、过滤和检索；事实、版本、删除仍在 MySQL，命中回库。Kafka 适合传异步意图和削峰，不适合当当前 Head。Redis 适合配额和短协调，不当业务真源。配额不可用生产 Fail Closed；缓存和 SSE 桥回源 MySQL，禁止把空结果当成「没权限 / 没记忆 / 没事件」。口播「至少一次 + 消费幂等」，不宣称 exactly-once。

### 1.1 要解决什么

校园资料分散、通用模型没有课程来源、长任务失败不可解释。生成质量不绑在模型上，而绑在：资料可追溯、检索匹配任务、长任务可恢复、结论可校验、记忆不污染证据。

notes 口径：AI 项目要从业务目标倒推，补三类细节——数据从哪来、系统怎么跑、效果怎么评。本项目数据来自 Workspace 内 Source 版本；运行上 Java 提交、Worker 执行；评测按任务分层，不用一个「准确率」。

### 1.2 一次请求怎么走

```text
Workspace 鉴权
  → 资料：上传 → 解析 / 切片 → 检索索引（异步）
  → 交互：QA / Note / Wiki
  或 长任务：Deep Research / Artifact
  → 断线按 MySQL 事件回放
  → Memory 只进入后续上下文，不进入引用
```

| 简历条 | 落在哪一段 |
| --- | --- |
| 3 资料底座 | 上传到索引就绪 |
| 2 QA / Note / Wiki | 交互检索与写回 |
| 1 Deep Research、4 Artifact | 长任务执行与提交 |
| 5 Context / Memory | 输入冻结、断线回放、记忆隔离 |

`[当前实现]` 还没有覆盖全部能力的统一 Intent Router。QA 有改写与扩展，Research 有结构化 Intent，Artifact 靠显式 `skill_key` 与 Schema；Note / Wiki 由入口和 `answer_mode` 选择链路。不能声称已经做完跨能力多意图拆分。

被要求画整系统时，按「缩小版系统设计」讲：约束 → 几块组件 → 主链路逐步 → 两三个机制怎么落地 → 失败挂在哪。五条各自的缩小版在 `01`～`05` 第 1 节。

### 1.3 主服务、Worker、存储怎么分工

| 组件 | 职责 | 边界 |
| --- | --- | --- |
| Java 主服务 | 鉴权、任务状态、版本提交、写回 | 模型输出只当候选 |
| Python Worker | 按任务开始时冻结的输入做检索、研究、生成 | 回调候选，主服务校验后落库 |
| MySQL | 资料版本、任务状态、删除意图 | 检索命中不能改这里的事实 |
| MinIO | 原文件 | 不是业务版本 |
| Elasticsearch / 缓存 | 检索与加速，可重建 | 命中必须回库核权限和当前版本 |
| Kafka | 解析和索引的异步投递 | 与业务写入同一本地事务走 Outbox；消费幂等；最终一致，不宣称 exactly-once |
| Redis | 配额、短期协调、流式桥接 | 不当业务真源。配额挂了 Fail Closed；缓存/SSE 回源，空≠没有 |

### 1.4 各方案特点，以及当前系统更适合什么

面试官问「为什么用 Kafka / 为什么不用 LangGraph」时，先对齐**问题约束**和**方案特点**，再落到当前更贴哪一类。不要一上来否定对方提到的技术。条内更细对照在 `01`～`05`。

当前工作台的硬约束就四条：资料要回到某一版原文；检索要过 Workspace 权限；长任务要可恢复；模型输出不能直接当事实。谁更贴这四条，就用谁。

**控制面怎么拆**

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 同步 HTTP 一条做完 | 路径短、演示快、无异步 | 秒级、失败可重点、无版本 | 我们有大 PDF 和可恢复 Run → 上传与处理拆开 |
| 一个通用 Agent | 一条对话轨迹打全部能力 | 单用户、ACL 松、结果不写回资料 | 问答/精读/研究/产物状态不同 → 共享 Source，按任务拆链路 |
| Worker 直写业务表 | 少一次回调，延迟低 | 单机、执行面可信、无重复投递 | 多 Worker、要对象级鉴权 → Java 提交，Worker 交候选 |
| LangGraph 作真源 | 图、循环、Checkpointer 熟 | Worker 内编排、单次运行恢复 | 要 Evidence/ACL/提交 → 真源在 Java；图可作执行辅助 |
| Temporal 作真源 | 跨天 Timer、Wait/Signal、工作流 UI | 人工审批、跨天等待是主路径 | 现在主路径是有界研究/产物 → 自建 Run/Attempt；跨天等待变主路径再评估 |
| Dify / Coze | 节点编排快，降搭建成本 | 内部 demo、流程稳定的运营工具 | 要对象授权和 Version 提交 → 平台不进权威路径 |

**中间件各自管什么**

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| ES 当检索面 | 词法熟、过滤熟、可混合向量 | 「搜得到」 | 课号/专名 + ACL → ES 检索，命中回 MySQL 才是权限结论 |
| 专用向量库 | ANN 规模、向量运维强 | 语义问法为主、专名少、过滤简单 | 校园专名密 → 先 ES 词法+向量；向量 P95 成主瓶颈再拆向量面 |
| Kafka 传命令 | 可重放、削峰、解耦消费 | 异步意图、积压可观测 | 当前 Head/归属仍要查库 → MySQL 真源，Kafka 传意图 |
| 本地消息表 / Outbox | 和业务同一事务 | 「意图不能丢」 | 先发消息会看到不存在的 Source → 同行写 Outbox |
| CDC | 少改业务代码，变更搬得全 | 表很多、要跟多种下游 | 现在表少、要 Tombstone 语义 → Outbox 更直接；轮询成为负担再评估 CDC |
| Redis | 快、适合短协调和配额 | 窗口计数、租约、SSE 桥 | 版本/删除不能靠 TTL → 状态在 MySQL；配额 Lua，不可用 Fail Closed |
| MinIO / S3 | 存大对象、多实例一致 | 原件字节 | 文件不进 MySQL BLOB；云上换 S3 语义不变 |

**语言、锁、一致性**

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 全栈 Python 或全栈 Java | 少跨语言协议 | 团队单一、生态够用 | Java 事务/ACL 熟，Python RAG/PDF/MCP 熟 → 控制面 Java、执行面 Python |
| 事件溯源作唯一真源 | 任意时刻可重放 | 审计重放是主查询 | Head/ACL/当前页要好查 → 当前状态在 MySQL，Outbox 留意图 |
| Saga | 多写库补偿 | 多个服务都有写权 | 权威写几乎只在 MySQL，投影可重建 → Outbox 足够 |
| Redis SET NX | 互斥快 | 临界区极短、丢了可重做 | 租约过期后旧持有者仍可能回调 → Lease 管领取，Fencing 管写回 |
| ZK / etcd 选主 | 进程级强一致租约 | 多活控制面谁当主 | 业务版本用 MySQL CAS；选主以后再评估，不替代 Cell/Version 条件更新 |

### 1.5 贯穿五条的设计思想

不要背成口号，被问「你的架构原则是什么」时按失败窗口讲：

| 思想 | 挡什么 | 落在对象上 |
| --- | --- | --- |
| 真源与投影分离 | 搜索、缓存、图谱把旧权限写成事实 | MySQL Source/Head；ES/反链/缓存可重建 |
| 控制面与执行面分离 | Worker 越权、重复回调、旧进程晚到 | Java 提交；Worker 只交 Candidate |
| 输入冻结、输出门禁 | 重试输入漂移；「写完」当成功 | Snapshot / Control Pack；证据或 Schema 不过不提升版本 |
| 至少一次 + 消费幂等 + 未知结果先对账 | 丢消息、重复副作用、超时当失败 | Outbox、Receipt、Fencing；不口播 exactly-once |
| 权限每层重复校验，高风险 Fail Closed | 只在 Controller 鉴权，缓存/索引/回调绕过 | 读时回库；权限挂了关掉高风险读 |
| 完成率服从正确失败 | 放宽引用、无限 Repair、用 Job 当成功率分母 | `NO_SUPPORTED_CANDIDATE`、拒答、READY 才可下载 |
| 深模块、小接口 | 三套 Controller 复制检索/重试 | 公共契约一份；QA/Note/Wiki 只换 Adapter |

Redis 挂了不能一套话：配额/工具许可生产 Fail Closed；ACL 与 Pack 缓存回源 MySQL，空结果不能当成「没权限/没记忆」；SSE Stream 回源事件表，空不能当成「没事件」。

领域词（Workspace、Source、Snapshot、Projection、Tombstone、Run、Lease、Fencing）见 [CONTEXT.md](../../CONTEXT.md)，开口用这些词，少用「账本」。

## 2. Deep Research

### 口述（4～5 分钟）

**简历原句：** 验证驱动；Table-as-State；主服务权威状态、Worker 只交候选；Plan/Replan、Verifier、Checkpoint、Lease/Fencing；完成看证据门禁。

**口述主回答（按停顿切，约 4～5 分钟）。**

校园调研不是「再写一篇长文」。用户要的是：这门课和那门课在学时、实验、考核上差在哪，每句话能回到哪份大纲的哪个版本。如果做成一次 Prompt 出报告，超时后既不知道搜过什么，也无法证明引用是原文。自由 ReAct 把状态放在对话里，进程一断，外部搜索可能已经扣费，重跑又重复调用。

所以我把开放问题收成有界矩阵：行是实体，列是必须有证据的字段，单元格保存候选、证据和验证状态。Planner 只定义要验证的格子，不写答案。默认最多 80 格，超限直接 `PLAN_BOUNDED`，不能为了跑完偷偷少问几列。这就是简历里的 Table-as-State。

执行上外层是 Plan，内层才允许单个格子做有限 Search/Read/Extract。Java 保存 Run、矩阵、证据、预算、阶段；Python Worker 拿冻结的 Task Snapshot 干活，只交 Candidate。格子的执行权是 MySQL 上的 Task Lease，大约 60 秒、心跳 15 秒，管的是「谁在跑这一格」，不要和产物入口的 300 秒在途租约混成一个「Agent Lease」。提交时核对任务、Lease 代数、Fencing Token、快照摘要和单元格期望版本，过了才写进权威状态。Replan 只能补 GAP 或冲突格，不能把「必须引用课程大纲」改成「随便写一篇」来换完成率。

外部搜索另有 Redis Hash 工具许可桶，按 Provider / Workspace / Role，大约 10/10 每分钟，Lua 里补令牌再扣。这不是入口那套 20/分钟。Redis 挂了工具许可 Fail Closed，不能当成无限额度。

质量不靠多个 Agent 投票。Local Verifier 只接受绑在同一实体+字段上的证据；Global 从当前事实重算覆盖，不抄 Local 的结论。数字、单位、年份先走类型化校验。冲突保留，不 Last-Write-Wins。综合只产草稿，主服务按合同校验 Claim 和 Evidence 后才提升产物。证据不足就明确失败，例如无 LLM 的确定性回放会停在 `NO_SUPPORTED_CANDIDATE`，这是门禁生效，不是功能没做完。

纠偏不是无限自我反思。高影响结论只有一个来源、出现明确冲突、或候选高置信但覆盖低时，进入**受限反证**：生成有限个反向检索目标（否定证据、替代解释、不同来源），顺序执行，查询族和次数封顶。结果回写原格的支持/冲突集合，再交给 Verifier。这不是并行 Tree Search，也不是每个格子都跑一套对抗搜索。预算和必填格就是停止条件，用完了不能靠「再想一轮」续命。

恢复不是把旧聊天再喂一遍。Checkpoint 水合的是计划版本、格子、证据、预算和高水位，只给缺口建新任务；已成功的搜索靠回执复用。租约到期后旧 Worker 晚到，栅栏直接拒写。超时是未知结果：先对账再决定重试，不把超时直接当失败重放。

**选型（特点 → 当前更适合）。** 校园调研的约束是：范围看得见、引用能回到某一版大纲、中断能续、模型不能直接改结论。LangGraph 的特点是图和循环恢复，更适合 Worker 内部编排。Temporal 的特点是跨天 Timer 和人工信号，更适合审批等待是主路径的工作流。多 Agent 投票的特点是角色分工，更适合没有单一权威来源的开放讨论。当前更贴「有界格子 + 单一提交权」：Java 持有 Run/格子/证据，Python 只交候选；图编排变重可以搭在 Worker，真源不搬家。评测分覆盖、Citation Support、冲突发现、恢复，不用一个总分。

**最困难（联调）：** 旧 Worker 晚到把新格子盖掉。租约只让别人能领，写回必须带代数。见本章应考故事 A。

### 怎么讲（notes）

来自 `18` Plan/Replan、`06` Plan/Executor、`07` Agent 难点：

- Plan 不是步骤清单。要能回答：目标、边界、信息够不够、约束、可用工具、Checkpoint、失败怎么恢复。
- 外层 Plan 管目标、阶段、检查点；内层才对单格做有限 Search/Read/Extract。不要把整次研究做成自由 ReAct。
- Replan = 当前目标 + 已有状态 + 新观察 + 偏差判断 + 修正策略。目标一般不改；改的是路径、工具、步骤。
- Checkpoint 是 Plan 必须确定的内容，不是可选日志。恢复看的是格子和证据，不是旧聊天。
- 不要把「我做了 Planner」当主卖点。面试能被追问的是：有界、可恢复、引用支撑结论、证据不足能正确失败。
- LangGraph / Temporal / Dify 降的是编排成本，不自动给你 Workspace、Evidence、提交权。

人设收口：Java 保存权威状态，Worker 只交候选。生成质量绑在证据门禁，不绑在模型文采。

### 缩小版系统设计

**约束。** 开放调研要能回答：覆盖了哪些实体和字段、每句引用哪一版资料、中断后从哪续、证据不够能不能明确失败。

#### 1.1 架构

```text
用户 / Conversation
        │  CreateResearchRun（question, goal, scope, depth…）
        ▼
┌───────────────────────────────────────┐
│ Java Host（权威状态、提交权）            │
│  Run / Intent / Plan / Cell            │
│  Task Lease+Fencing / Evidence         │
│  Budget / Checkpoint / Completion      │
└────────────┬──────────────▲───────────┘
             │ Kafka 命令    │ Candidate
             │ Task Snapshot │ Evidence + Receipt
             ▼              │
┌───────────────────────────────────────┐
│ Python Worker（执行面，无业务写权）      │
│  按冻结 Snapshot：Search/Read/Extract   │
│  只交 Candidate，不改 Cell 当前值        │
└───────────────────────────────────────┘
持久化：MySQL 真源；MinIO 原文；检索投影只读
```

Host 厚、Worker 薄：非确定性（模型、搜索）留在执行面；权限、版本、预算、门禁留在有事务的 Host。

#### 1.2 端到端怎么跑

1. **创建。** Host 校验 Workspace 和 Source Scope，冻结 Intent、资料范围和当时策略。用户改目标或范围只能开新 Run，不能在旧 Run 里重规划偷换语义。
2. **规划。** Planner 把比较型问题编成矩阵：行=实体，列=必须有证据的字段。默认最多约 1–20 行、2–8 列、80 Cell；超限 `PLAN_BOUNDED`。Planner **只定义要验证的格子，不写答案**。
3. **外层 Plan。** 冻结必填格、预算、停止条件、Checkpoint 边界。这是 GCCSC 里的 Goal/Constraint/Checkpoint。
4. **领任务。** Host 为缺口格建 Task，写入不可变 Task Snapshot（目标格、期望版本、Provider、范围、预算、Schema）。Worker Claim 后拿到租约和 Fencing Token。
5. **内层执行。** 单格允许有限 Search/Read/Extract。结果打成 Candidate：带 `baseCellVersion`、Evidence 引用（来源身份、Snapshot、定位）。Worker 不更新 Cell 当前值。
6. **提交。** Host 核：任务仍属于该 Owner、Lease 代数、Fencing Token、快照摘要、单元格期望版本、证据在 Scope 内。条件更新成功才写入权威状态。冲突不 Last-Write-Wins。
7. **校验。** Local 只接受绑在同一实体+字段上的证据；数字/单位/日期先走 L0 规则。Global 从当前事实**重算**覆盖，不抄 Local 结论。冲突保留。
8. **反证（有界）。** 高影响且单源、或明确冲突时，生成有限个反向检索目标，顺序执行，结果回写原格。
9. **Checkpoint。** 阶段边界把计划版本、格子、证据、预算、高水位做成可水合摘要（含哈希）。恢复在同一 Run 下新 Attempt，只给 GAP/STALE 建任务。
10. **完成。** 综合只产草稿。主服务按单元格合同核 Claim↔Evidence 后才提升报告。必填未覆盖或无支撑 → `NO_SUPPORTED_CANDIDATE`，这是门禁，不是没做完。

#### 1.3 状态存在哪、谁写谁读

| 数据 | 在哪 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| Run / Intent / Plan / Cell | MySQL | 仅 Host | Host；Worker 只读 Snapshot 副本 |
| Task Snapshot | MySQL，领取时冻结 | Host | Worker |
| Evidence / Candidate | MySQL（提交后） | Host 校验后落 | Verifier、报告 |
| 原件 | MinIO | 上传链路 | Worker 按 Snapshot 读 |
| 检索命中 | ES 投影 | 资料底座 | Worker 检索后必须能回到 Snapshot |
| Checkpoint | MySQL | Host | 恢复 Hydration |

#### 1.4 三个机制具体怎么落地

**有界矩阵。** 不是把对话存成状态。每个 Cell 有：候选值、证据列表、验证状态、版本。覆盖率 = 通过验收的必填格 / 必填格。超 80 格拒绝规划，不能少问几列换完成率。

**Lease + Fencing + 回执。** Claim 时发租约（谁在跑）。写回必须带代数/Token，条件更新失败即拒（旧 Worker 晚到）。Completion 带幂等键，重复回调收敛到同一业务结果。三件套保护三个窗口，不要合成一句「做了幂等」。

**恢复。** 读最近有效 Checkpoint，校验摘要未截断，推进 Attempt，重放高水位之后的缺口任务。已成功的外部搜索靠回执复用，不把聊天再喂一遍。超时先对账再重试。

`[当前实现]` 比较型走 Matrix。`[目标设计]` Typed WorkItem（开放调查/时间线）。开口用 Table-as-State；被问「所有问题都塞表吗」再讲适配层。

#### 1.5 中间件落到哪种结构（可考到这一层，不到函数名）

| 中间件 | 用它的哪一点 | 落到什么结构 | 为什么是这个 | 不用它当什么 |
| --- | --- | --- | --- | --- |
| MySQL | 事务、条件更新、唯一约束 | Run/Plan/Cell/Task 行；Lease Owner + Until + Epoch；Fencing Token；Checkpoint 摘要哈希；Completion 幂等键 Unique | 格子当前值只能被「对上代数」的提交改掉 | 不当聊天记录；不当搜索引擎 |
| Kafka | 可重放命令、削峰 | Research 命令 Topic；Key 用 Run/Task 稳定 ID，同任务进同一分区 | 派发与执行解耦；Worker 崩了命令还在 | 不当 Cell 真源；Offset 已交 ≠ 格子已更新 |
| Redis | Lua 原子、TTL | **Hash 令牌桶**（tokens + 上次补充时间）按 Provider / Workspace / Run+Role，默认 10/10 每分钟。入口那套 **Hash + ZSet 租约**（约 20/min、并发 4、Lease 300s）是另一层，不要合成「Redis 限流 20」 | 工具调用会打满外部搜索；INCR 不够「按时间补令牌」。Lua 避免多 Host 同时读到 1 再一起放行 | Redis 挂了工具许可 **Fail Closed**；配额丢失不能当成「无限额度」 |
| Elasticsearch | 词法 + 向量检索 | 只给 Worker 找候选段落 | 搜得到 | 命中必须能回到 Source Snapshot；ES 不能改 Cell |
| MinIO | 大对象 | 按 Snapshot 读原文 | Worker 精读连续章节 | 不当版本号 |

Task Lease 当前量级：约 60s，Heartbeat 15s。过短会误杀慢搜索，过长会拖接管。这是保护参数，不是吞吐。`[当前实现]` Completion 级回执已有；Search/Read/Model 的 Operation Receipt 仍是生产化边界——超时先对账，不能承诺外部搜索绝不重复扣费。

### 应考故事（联调/审查，不要说成线上事故）

口径同 [09](../简历亮点八股/09-真实缺陷排查与复盘案例.md)。开口「研究长任务联调里最难的是旧执行者晚到」，不要报节省了多少 Token。

**被问「实习最困难」优先讲故事 A**（旧 Worker 覆盖新格子），对方问超时再讲故事 B。

#### 故事 A：租约到期后，旧 Worker 把新格子写回去了

**现象。** 同一格先出现正确候选，过一会儿又变回一份更旧、引用也对不上的值。Run 没失败，只是结论「抖」了一下。

**定位。** 先画所有权，不先怪模型。MySQL 里该 Task 的 Lease Until 已过，新 Owner 已经 Claim 成功、Epoch +1。随后旧 Worker 的回调才到，如果只验 Task ID 不验代数，条件更新会成功，新结果被盖掉。Kafka 上可能还有旧命令重放，Offset 看起来正常。

**根因。** 租约只回答「过期后能不能再领」。不回答「旧持有者晚到的成功回调能不能写」。心跳断了、GC、网络分区都会制造这个窗口。Redis 工具桶管的是调用速率，拦不住写回。

**修复思想。** 写回必须带 Fencing Token / Epoch，`UPDATE … WHERE epoch=? AND owner=?` 影响行数为 0 就是拒写，不是数据库异常。重复 Completion 靠幂等键收敛到同一行。两个 Worker 基于同一 `baseCellVersion` 算出不同值：冲突保留，不 Last-Write-Wins。

**验证。** 旧 Owner 晚到、重复回调、同格并发提交。不变量：最多一个新 Owner 能确认；拒写要计数，不当数据丢失。

**可追问。** 为什么不用 Redis SET NX 当这把锁？NX 能互斥领取，没有单调代数，租约过期后旧客户端仍可能 SET 成功。业务栅栏放在 MySQL 条件更新上。Lease 60s / Heartbeat 15s 是保护值：再短会误杀慢 Read，再长会拖接管。

#### 故事 B：搜索已经扣费，Host 超时当失败又放了一遍

**现象。** 一次研究外部搜索次数明显多于格子数。有的格证据重复。Worker 日志显示同一查询做了两次。

**定位。** 拆三截：Host 派发、Worker 已执行、回调是否到达。常见窗口：HTTP/Kafka 超时，Host 当失败；Worker 其实已经搜完。早期若没有 Completion 幂等，第二次派发会再搜一遍。更糟的是把超时当失败后换 Owner，又不拒旧写——故事 A 叠上来。

**根因。** 超时是**未知结果**，不是失败。Kafka 至少一次会重放命令；外部搜索没有回执时，系统无法证明「没做过」。`[当前实现]` 有 Completion 级回执；全部 Search/Read/Model 的 Operation Receipt 仍是边界，所以不能说端到端不重复扣费。

**修复思想。** 超时先查回执/格子版本，再决定重试还是等待。重放命令必须带同一 Delivery Token，Worker 发现 Token 已被新代际接管就停（语义上 409）。已成功的搜索在 Checkpoint 高水位里，恢复只补缺口。入口 Redis Hash 桶限制到达率，降低「失败就狂着重放」把 Provider 打满。

**验证。** 派发成功但回调丢失；命令重放；旧 Token 跳过。Host 侧业务行不因重放翻倍。对外搜索重复仍可能发生——主动讲这个缺口。

**可追问 Redis。** 工具许可是三层桶（Provider / Workspace / Run+Role），10/10 每分钟，和入口 20/min、并发 4 不是同一个 Key。面试不要说成「Redis 限流 20」。Lua 原子是为了补令牌和扣减不被切开；脚本不能太长，否则堵 Redis 单线程。

### 对照：各方案特点，当前更适合什么

硬约束：范围看得见、引用回到某一版资料、中断能续、模型不能直接改结论。先讲对方提到的技术擅长什么，再落到当前更贴哪一类。

**口述。** ReAct 灵活，适合下一步不确定的短探索。固定 workflow 可重复，适合格式稳定的产物。LangGraph 图恢复熟，适合 Worker 内编排。Temporal Timer/Signal 熟，适合跨天等待是主路径。多 Agent 投票适合没有单一权威来源的讨论。校园调研更贴「外层有界 Plan + 内层有限探索 + Host 提交」：格子在 Java，候选在 Python。

#### 9.1 控制结构

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 纯 ReAct / TAO | 走一步看一步，灵活 | 短探索、停止条件不敏感 | 整次研究要覆盖和预算 → 只放在**内层单格** |
| 固定 workflow | 步骤可重复，SLO 好写 | 交付格式极稳、几乎无缺口 | Artifact 可以偏 Graph；Research 外层要能补 GAP |
| 计划写死的 Plan-Execute | 目标比 ReAct 稳 | 执行中不会出现新缺口 | 开放研究有冲突 → Plan 冻结目标，Replan 只补缺口 |
| 多 Agent 投票 | 角色分工，看起来专业 | 没有单一权威来源的讨论 | 课程大纲是权威来源 → Local/Global 是验证责任，不是投票 |
| LangGraph 作真源 | 图、循环、Checkpointer | Worker 内编排、单次运行恢复 | 要格子/Evidence/提交 → 真源在 Java，图可搭在 Worker |
| Temporal 作真源 | 跨天 Timer、Wait、工作流 UI | 人工审批、跨天等待是主路径 | 现在主路径有界 → 自建 Run/Attempt；跨天等待变主路径再评估 |
| 一次长 Prompt | 路径最短 | 演示、无版本、无恢复 | 正式研究要矩阵和门禁 |

#### 9.2 状态与恢复

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 对话当状态 | 实现快 | 短聊、无外部副作用 | 要看见覆盖了哪几格 → 格子/证据/预算在 MySQL |
| Worker 直写 | 少一次 RPC | 单机、执行面可信 | 重复回调和旧 Lease → Host 校验后写 |
| 恢复建子孙 Run | 用户侧像「又跑了一次」 | 每次都是新问题 | 中断续跑要同一 Run → Attempt + Checkpoint |
| 聊天重放当 Checkpoint | 不用水合设计 | 无付费搜索、无已验证格 | 要复用搜索回执 → 水合计划/格子/高水位 |
| 并行 Tree Search | 覆盖面大 | 预算充足、取消简单 | 费用和 429 敏感 → 有界顺序反证；高影响格再评估并行 |

#### 9.3 矩阵、校验、反证

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 固定四格表 | 单个问题结构稳 | 单对象问答 | 多课比较 → 行=实体、列=字段，最多 80 格 |
| 矩阵当唯一抽象 | 比较型清楚 | 只有比较任务 | `[当前实现]` 比较走 Matrix；开放调查/时间线用 Typed WorkItem |
| 无上限拆任务 | 看起来更深 | 成本不敏感 | 校园预算有限 → `PLAN_BOUNDED` |
| 有链接即引用成立 | 实现省事 | 不核对数字/方向 | 学时、年份会反 → L0 规则 + Local 绑定 + Global 重算 |
| 模型给自己打分 | 少一个组件 | 低风险草稿 | 冲突会被写圆 → 不确定就 ABSTAIN；Judge 要校准集 |
| 无限自我反思 | 偶尔能圆回来 | 不怕烧 Token | 停止条件是预算和必填格 → 有界反证，用尽明确失败 |

收口：编排框架降的是**编排成本**；当前更需要 **Intent 稳定、格子可恢复、引用支撑结论**。框架可以放在执行面，真源不搬家。

---

### 机制深挖（失败窗口与落地）

#### 有界矩阵（Table-as-State）

**失败窗口。** 开放问题只存在 Prompt 里：超时后不知道覆盖了什么，也无法比较「这门课和那门课差在哪」。固定四格（答案/证据/限制/含义）对多实体比较又太僵。无上限拆任务则成本和停止条件失控。

**设计。** 把研究意图编译成矩阵：行是实体，列是必须有证据的字段，单元格保存候选、证据、版本和验证状态。Planner 只定义要验证的单元，不写事实答案。超限 `PLAN_BOUNDED`，不能静默裁掉必填格换完成率。

**notes 方法。** Plan 先回答「目标是否明确、信息是否完整、约束是什么」。信息不够先记缺口，不直接执行。矩阵就是把 Goal/Constraint 变成可检查的格子，而不是生成一篇大纲。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 对话当状态 | 崩溃后覆盖不可见 | 不换 |
| 固定四格表 | 比较、时间线表达不开 | 不换 |
| 无上限自由拆任务 | 成本与停止条件失控 | 不换 |
| 矩阵当唯一抽象 | 时间线/开放调查被硬塞进格子 | 目标 Typed WorkItem 落地后，矩阵只保留给比较型 |

**失败怎么收。** 超界拒绝规划，返回可观测原因。不能为了跑完偷偷少问几列。

---
#### 主服务状态 vs Worker 候选

**失败窗口。** Worker 直写「当前结论」：重复回调、旧进程晚到、越权范围都会写成事实。聊天消息当唯一状态，会和 AnswerRun 的检索-生成状态搅在一起。

**设计。** Java 保存 Run、矩阵、证据、预算、阶段。Worker 按不可变 Task Snapshot 执行，只提交 Candidate / Evidence / 综合草稿。提交时校验任务、Lease 代数、Fencing Token、快照摘要、单元格期望版本和证据范围，通过后才写入权威状态。

**notes 方法。** Agent 价值在工具可靠和失败处理，不在「Python 也能写库」。把非确定性留在执行面，把权限、版本、审计留在 Host。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| Worker 直写业务表 | 无法做对象级鉴权和版本条件 | 不换 |
| 聊天消息当唯一状态 | 恢复语义不够 | 不换 |
| 双写 Java 状态 + 图数据库状态 | 两个权威源 | 不换 |
| LangGraph Checkpointer 当业务真源 | 恢复图状态 ≠ 恢复 Evidence 与提交 | 图恢复可作执行辅助，权威状态仍在 Host |

**失败怎么收。**

| 失败点 | 正确结果 | 不能做什么 |
| --- | --- | --- |
| 校验失败 | 拒绝写入，留审计 | 把 HTTP 200 当研究完成 |
| 重复 Completion | 同一业务结果 | 再插一条结论 |
| Worker 超时 | 未知结果：先查回执 | 当失败后换人重跑且不拒旧写 |

---
#### Plan / Replan

**失败窗口。** 走一步看一步会漏字段、重复搜索、把原问题做成别的题。计划写死成 workflow，执行中的缺口和冲突没有入口。Replan 若能改交付标准，模型会用「范围缩小」换完成率。

**设计。** 外层 Plan 冻结目标、范围、预算和必填单元。内层单个单元格允许有限 Search/Read/Extract，结果仍是候选。Replan 只针对 GAP / 冲突 / 过期单元补任务，**不能降低**原始 Intent（例如把「必须引用课程大纲」改成「随便写一篇」）。用户改目标、资料范围或交付标准 → 新 ResearchRun，不是在旧 Run 里重规划偷换语义。

**notes 方法。** Plan 用 GCCSC 检查，缺一项就不是计划：

| 项 | 在本项目里对应什么 |
| --- | --- |
| Goal | 冻结的 Intent / 交付标准 |
| Context | Source Scope、已有格子和证据 |
| Constraint | 预算、最多 80 格、必须引用的资料范围 |
| Step | 外层必填格，内层有限 Search/Read/Extract |
| Checkpoint | 计划版本、格子、证据、预算、高水位 |

Replan 粒度先选当前步骤 / 阶段 / 局部，最后才全局重来。根因先看：目标错、上下文错、约束错、步骤错、工具错；不要让模型空口「重新想一遍」。基础设施恢复只建 Attempt，不算 Replan。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 纯 ReAct | 停止条件漂、状态在对话里 | 只允许内层单格有限探索 |
| 纯固定 workflow | 开放研究步数事先列不全 | Artifact 类格式稳定任务可以偏 workflow |
| Replan 可改交付标准 | 用缩范围换完成率 | 只有显式降级机制，且要用户可见 |
| 一上来多 Agent 分工 | 协调和合并成本高于收益 | 验证责任清晰、合并契约先写完再评估 |
| 基础设施恢复也 Replan | 把崩溃当成「计划错了」 | 恢复只建 Attempt，不改 Plan |

**失败怎么收。** 信息不够先记缺口，不编造单元格值。Replan 次数是信号：越多说明原 Plan 越差，但不能把「少 Replan」当成唯一质量指标。

---
#### Local / Global Verifier

**失败窗口。** 搜到文本 ≠ 支持该格结论。数字、单位、年份、比较方向可能词面能对上但事实反了。两个校验器互相抄结论，双层就是摆设。多数票会丢掉权威来源和时间范围。

**设计。** Local：只接受绑定到同一 `entity + column` 的证据，冲突-only 证据不能被模型判成支持。Global：从当前事实重算覆盖、对齐和分数，不复制 Local 结论。类型化校验先挡数字/单位/日期，再进语义。不一致则 Repair 或阻断成文。Local/Global 是验证责任，不强制等于两次模型调用。

分层（追问用，不要全塞进 4 分钟）：L0 规则（范围、Snapshot、定位、数字单位）；L1 只对有语义争议的格子做支持/反驳/不充分；L2 高风险才异构复核或人工抽检。不确定允许 `ABSTAIN/INSUFFICIENT`。生成模型不能无约束给自己最终背书。

**notes 方法。** 效果怎么评要分层：覆盖、Citation Support、冲突发现。不要用「多 Agent 投票」假装严谨。Judge 需要校准集。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 只靠模型自检 | 会把冲突写圆 | 不换 |
| 多数票 / 多 Agent 投票 | 权威来源和时间范围丢失 | 不换 |
| 两个 Verifier 共享同一段结论 | 失去独立性 | 不换 |
| 词面重合当引用成立 | 比较方向和单位仍可能错 | 不换 |

**失败怎么收。** 验证失败不进入无条件综合；冲突保留，不 Last-Write-Wins。无可用候选进入 `NO_SUPPORTED_CANDIDATE`，属于正确失败。

---
#### 1 受限反证（简历原词，追问必答）

**失败窗口。** 高影响结论只有一个来源、资料互相打架、候选过早收敛、多轮搜索高度同质。若此时让模型「再想想」，会把冲突写圆，并无限烧预算。并行开一棵反证树则分支爆炸，取消和合并都难。

**设计。** 只对高影响或冲突格生成有限个 Recovery Target：否定证据、替代解释、不同来源。顺序执行，限制查询族、阅读窗口和尝试次数。结果回写原格的支持/冲突集合，再交给 Verifier 决定接受、保留争议或失败。这是有界顺序反证，不是并行 Tree Search，也不是每个格子都跑对抗搜索。

`[当前实现]` Canonical Merge 对已 `VERIFIED` 值冲突 Fail Closed：返回 `VERIFIED_VALUE_CONFLICT`，保留原 Cell，不自动改成 `CONFLICTED`，也没有完整的 `CORRECTED` 状态机。冲突靠后续轮次生成可验证候选，或在报告里保留限制条件。不要说成已经会自动拆口径。

**和其他做法比。**

| 方案 | 特点 |
| --- | --- |
| 无限自我反思 | 成本失控，冲突被写圆 |
| 全量并行反证树 | 费用、429、重复阅读、难以取消 |
| 每个 Cell 都对抗搜索 | 已验证格浪费预算 |

**失败怎么收。** 预算或轮次用尽仍缺证 → `INSUFFICIENT` / 明确失败，列出缺口，不把不确定性藏进流畅长文。`No Hit` 不能写成「事实不存在」。

---
#### Checkpoint 恢复

**失败窗口。** 从「旧上下文再跑一遍」会重复付费搜索，也会把已验证单元格打回重做。Checkpoint 记录「走到哪一步」不等于外部调用可安全重放。

**设计。** Checkpoint 保存计划版本、单元格、证据、阶段、预算和高水位。恢复时在同一 ResearchRun 下推进执行代际，Hydrate 前一有效 Checkpoint，只为 GAP / STALE / Repair 建新任务。已完成的搜索/模型调用靠外部回执复用。`[当前实现]` 有 Completion 级回执和 Checkpoint Hydration；全部 Search/Read/Model 的 Operation Receipt 仍是生产化边界，不能承诺调用成本绝对不重复。

**notes 方法。** Checkpoint 要含：当前阶段目标、阶段产出、验收标准、能否进入下一阶段、失败如何恢复、关键 evidence。恢复成功 = 对上同一 Canonical 状态，不是「又写出一篇报告」。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 把聊天记录当 Checkpoint | 外部副作用说不清 | 不换 |
| 每次恢复新建子孙 Run 当推荐路径 | 已完成工作被高估为「也能恢复」 | 子孙 Run 只当迁移兼容 |
| LangGraph Checkpointer 当业务恢复 | 恢复图状态 ≠ 恢复 Evidence 与提交 | 图恢复可辅助执行，不能替代 Host 状态 |
| 超时当失败、换人重跑且不拒旧写 | 重复副作用 | 不换 |

**失败怎么收。** 截断或摘要对不上则拒绝水合。用户改目标才新 Run。不要把 Descendant Run 讲成终态。

---
#### Lease / Fencing

**失败窗口。** 租约到期后旧 Worker 仍可能回调。没有栅栏，晚到的成功会覆盖新 Owner。Lease、Fencing、幂等键保护的窗口不同，不要合成一句「做了幂等」。

**设计。** 执行权用租约绑定 Owner 与代数；写回带 Fencing Token。条件更新失败则拒绝。与资料/Artifact 共用「租约 + 栅栏」模式，但 Research 有自己的任务表和矩阵状态，不共用一张任务业务枚举。

三件套（追问必答）：

| 机制 | 保护的窗口 |
| --- | --- |
| Lease | 任务可以被重新领取 |
| Fencing | 旧 Worker 晚到也不能提交 |
| 幂等键 / Completion Receipt | 重复回调业务结果收敛 |

**和其他做法比。**

| 方案 | 特点 |
| --- | --- |
| 只靠心跳、不校验写回代数 | 网络分区后双写 |
| 超时当失败、换人重跑且不拒旧写 | 重复副作用 |
| 所有能力一张任务表 | 矩阵/证据状态塞不进去 |

**失败怎么收。** 旧写回拒绝并计数；不把拒绝当数据丢失。

---
#### 证据门禁与正确失败

**失败窗口。** 「模型写完」就算成功，门禁会被生成长度绕过。证据不足时硬写长文，引用会漂。用更多 Agent / 更多步抬完成率，成本上升覆盖不一定升。

**设计。** 综合只产 Candidate；主服务按单元格合同校验 Claim 与 Evidence 后才提升为产物。必填未覆盖、冲突未关闭、引用未绑定版本 → 明确失败。`NO_SUPPORTED_CANDIDATE` 在无可用候选时进入失败屏障，属于正确失败。

**notes 方法。** 完成率虚高是 AI 项目最常见的包装。正确失败要可观测，评测分层，不用一个总分。

**和其他做法比。**

| 方案 | 特点 |
| --- | --- |
| 生成成功即 Run 成功 | 完成率虚高 |
| 放宽引用换成功率 | 与验证驱动相反 |
| 用更多 Agent / 更多步抬完成率 | 成本上升，覆盖不一定升 |

**失败怎么收。** 失败原因可观测；确定性回放无 LLM 时允许停在该屏障，不解释成「Research 没做完」。

### 10. 校园演练（被要求举例时）

比较三种课程资料助手：检索质量、教师维护成本、引用追溯、考试周容量。Host 冻结课程资料范围，Planner 生成 `3 × 4` 共 12 个必填格。Worker 只发现/阅读/抽取；两个 Worker 同格更新时旧版本进冲突。阶段结束 Checkpoint，模拟 Worker 退出后同一 Run 恢复。Verifier 查覆盖、Claim 支持、来源独立性和冲突。Finalizer 出比较表；用户看 Evidence Manifest 或写回 Source。这是固定演练故事，不要补报用户数和节省时间。

---

### 11. 评测口径

| 指标 | 衡量什么 | 不要怎么报 |
| --- | --- | --- |
| 必填格覆盖 | 范围是否跑完 | 不要和文采混成总分 |
| Citation Support | 已给引用是否真支撑 | 不要用「有链接」代替 |
| 冲突发现 | 矛盾资料是否被写圆 | 不要 Last-Write-Wins 后假装一致 |
| 恢复复用 | 中断后少重算多少有效步 | 不要把「又生成一篇」当恢复成功 |
| 重复回调收敛 | 业务行是否还在涨 | 不要说 exactly-once |

评测分层：必填覆盖、Citation Support、冲突发现、恢复复用。不报一个总分，不上 Fixture 百分比。

---

### 边界

比较型走 Matrix；开放调查和时间线按 Typed WorkItem 适配。恢复在同一 Run 下推进 Attempt。超时先对账。Temporal 要等跨天 Timer、人工暂停多到自建状态机养不动再评估。

## 3. QA / Note / Wiki

### 口述（4～5 分钟）

**简历原句：** 「相关」按任务定义；三条链路共享版本、ACL、Evidence；QA 混合召回；Note 窗口精读；Wiki 页面版本与回链；命中回库；Scope 硬门槛。

**口述主回答。**

这条不是「又做了一套向量 RAG」。校园里同一份资料要服务三种事：考试周问「实验几学分」要短证据；写笔记要读连续章节；知识页要稳定标题和来源回链。一套 Chunk TopK 会让专名漏掉、论证被切碎、改页面后旧引用失真。所以三条链路只共享 Source Snapshot、Workspace 权限和 Evidence 契约，「相关」和写回按任务拆。

用户原问题和检索表达必须分开。上一轮问过「操作系统」，这轮说「那门课实验几学分」，检索 query 要带上课名；生成仍以原问题为回答目标，改写不能放宽 Scope。`[当前实现]` 多轮改写有版本，低召回最多扩 5 个确定性变体，原问题不会被 Expansion 覆盖。没有实体别名表和跨能力 Intent，不能说成完整 NLU。指代会改答案对象或资料范围时要澄清，不能猜。答案正确也不能反推改写正确，Rerank 可能偶然补救。

QA 先 Workspace、版本、可见性过滤，再 BM25 和向量各召回 60。两路分数不可比，不能归一化相加，用 Weighted RRF：`weight / (k + rank)`，K=60，向量/词法 0.7/0.3，融合最多 100，再对前 40 做 Rerank。这些是可回放配置，不是最优证明。ES 命中只是候选：回 MySQL Hydrate 权限、Snapshot、Wiki Head，不通过就丢弃。最终 Evidence 最多 6 条、8000 字，第一轮每个 Source 一条，避免同一讲义相邻段占满 Prompt。生成只引用 Manifest 里的 Evidence ID。证据不足就拒答，不写空引用成功。Rerank 超时或畸形时退回 RRF 顺序并打 Degraded，不装成「没有证据」。AnswerRun 是 PREPARING → RETRIEVING → GENERATING → FINALIZING，没有单独的 VALIDATING 状态。ACL 在 Redis 里是 String，Key 带 `acl_version`，正缓存大约 300 秒；命中后仍要回 MySQL，缓存空了回源，不能当成没权限。

Note 若复用 QA TopK，定义往往在命中前一段。所以先资料级召回（Top K 8），再在 Snapshot 里扩连续 Reading Window（候选 24、精排 8），出中性草稿，用户确认后按目标版本条件写回 Source。生成成功不自动入库，也不进 Memory。`[当前实现]` 草稿版本合同还不完整，面试主动讲。

Wiki 不能一张表覆盖更新。页面身份稳定，每次发布追加 Version，Head 用期望版本 CAS。链接存稳定 ID，反链和图谱可重建。来源撤销进治理态。目标是自动修复只出提案；`[当前实现]` Auto-fix 仍可能直接建缺页，面试主动讲。检索命中一律回 MySQL 核权限和当前 Head，ES 命中不是权限结论。

越权进有效结果必须是 0，不能和 Recall 加权。Embedding/Rerank 关掉要打 Degraded，发布门禁另要求无降级。仓库小 Fixture 只证明路径和门禁，不是线上准确率。当前没有覆盖全部能力的统一 Intent Router，Note / Wiki 靠入口和 `answer_mode`。

**选型（特点 → 当前更适合）。** 这条约束是：课号要搜到、同义也要搜到、命中还得过权限和当前版本。专用向量库的特点是 ANN 和向量运维，更适合语义问法为主、专名少的语料。BM25 的特点是精确词可解释，更适合通知和课号。分数相加实现短，更适合两路已经校准到同一量纲。GraphRAG 的特点是关系扩展，更适合图已经是真源的产品。当前更贴校园资料：ES 做词法+过滤+向量，RRF 按名次融合；Wiki 用受限显式链接，页面真源仍是 Version。向量 P95 成主瓶颈再拆向量面；关系查询成主流量再加强图，仍不取代 QA/Note。

**最困难（联调）：** 邻课讲义进了有效证据。ES filter 不是鉴权，命中后必须回库。见本章应考故事 A。

### 怎么讲（notes）

来自 `19` RAG/Prompt、`06` 检索评估、`07` 上下文与指代：

- 检索不是一个 index 打天下。专名、课号、错误码走词法；同义问法走向量；两路分数不可比，用 RRF 按名次融合，再 rerank。
- Query 往往要先改写：口语、省略、代词、多意图不能直接打索引。改写是「帮检索」，不是让模型先答题。
- 召回追求「不要漏」，重排追求「更准」，Selection 追求「能撑结论且不占满 Prompt」。三步不要合成「搜一下」。
- 切片不是越小越好：切断步骤/定义，命中也答不完整。Note 要连续窗口，正是这个原因。
- 效果怎么评：Recall@K、Citation Support、Faithfulness、拒答，不用一个「RAG 准确率」。仓库 6 条 Fixture 只证明路径。
- Prompt 优化要有方法：结构化约束 + 错误样本迭代，并要求只引用 Manifest 里的 Evidence ID。

人设收口：三条链路共享 Source 版本、Workspace ACL、Evidence 契约；「相关」和写回按任务拆。不是再做一套向量库。

### 缩小版系统设计

**约束。** 同一份课程资料要服务三种事：短证据问答、连续精读、带版本的知识页。命中必须过权限和当前版本；生成只能引用选中的 Evidence。

#### 1.1 架构

```text
Turn（冻结输入）
  → AnswerMode：QA / Note / Wiki（入口或 answer_mode，不是统一 Intent Router）
  → RetrievalPlan（查询、范围、版本、通道、预算）
  → RetrievalOrchestrator
        plan → retrieve → revalidate → explain
        Adapter：QA Passage | Note Window | Wiki Page/Link
  → 召回（ES 词法 / 向量）→ Hydrate MySQL（ACL / Snapshot / Head）
  → EvidenceBundle → PromptSpec → AnswerRun
        PREPARING → RETRIEVING → GENERATING → FINALIZING
  → Citation 或拒答；SSE 按事件序号回放
```

公共模块只暴露小接口，三种定位是同一 Seam 上的 Adapter。没有单独的 `VALIDATING` 状态：校验在 Hydrate、Selection、生成约束里。

#### 1.2 三条链路分别怎么跑

**QA（短证据）。** 原问题与检索表达分开：改写版本只影响检索，生成仍对 Original Query。先 Workspace/版本/可见性过滤，BM25 与向量各召回 60。RRF：`Σ w_i/(k+rank_i)`，K=60，向量/词法 0.7/0.3，融合最多 100。对前 40 Rerank。Selection：最多约 6 条、8000 字，第一轮每 Source 一条。生成只引 Manifest 里的 Evidence ID；不足则拒答。

**Note（连续精读）。** 先资料级召回 Top K≈8，锁定 Source Snapshot，以命中为 Anchor，按标题层级和相邻位置扩 Reading Window（候选约 24，精排 8）。出中性草稿，用户确认后按目标版本 CAS 写回 Source。生成成功不自动入库，也不进 Memory。

**Wiki（页面版本）。** Knowledge Item 身份稳定；发布追加不可变 Page Version；Head 用期望版本 CAS。链接存稳定 ID；反链/图/搜索是投影。读时回库核 Head 和 ACL。来源撤销进治理态。目标是自动修复只出提案；`[当前实现]` Auto-fix 仍可能直接建缺页。

#### 1.3 状态存在哪、谁写谁读

| 数据 | 在哪 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| Turn / AnswerRun / Plan / Bundle | MySQL | Java | Replay、生成 |
| Chunk / Window 索引 | ES（投影） | 资料底座 | 召回；命中必须 Hydrate |
| Source Snapshot / Wiki Head | MySQL | 上传/Wiki 发布 | Hydrate、写回 CAS |
| 原件 | MinIO | 上传 | Note 扩窗口时读连续正文 |

#### 1.4 三个机制具体怎么落地

**RRF。** 两路分数不可比，不用 min-max 相加。只用名次：两路都靠前的文档融合后更靠前。权重和 K 是可回放配置，不是最优证明。向量关掉走词法并打 `Degraded`。

**读时回库。** ES 命中只是候选。Hydrate 查 Workspace、可见性、Snapshot、Wiki Head，不通过丢弃。这是安全路径，不是性能可选项。

**Scope=0。** 越权进有效结果必须为 0，不和 Recall 加权。Gold 要有跨课、已删、旧版负例。

`[当前实现]` QA 有多轮改写版本和最多 5 个确定性 Expansion；没有完整 NLU。Note 草稿版本合同不完整。Wiki 有限关系读取不是 GraphRAG。

#### 1.5 中间件落到哪种结构（可考到这一层，不到函数名）

| 中间件 | 用它的哪一点 | 落到什么结构 | 为什么是这个 | 不用它当什么 |
| --- | --- | --- | --- | --- |
| Elasticsearch | 倒排（BM25）+ 可选 knn | 两路各召回约 60；文档带 Workspace/Snapshot；查询侧 filter 只是初筛 | 课号走倒排，同义走向量。倒排的特点是精确词、可解释；knn 的特点是近邻，不表达权限 | filter 里的 `workspace_id` **不是**鉴权结论 |
| MySQL | 事务、当前 Head、ACL | Hydrate：命中后回表核可见性、Snapshot、Wiki Head | ES 会滞后；权限和版本的真源在库 | 不当全文检索主引擎 |
| Redis **String** | GET/SET+EX、版本进 Key | ACL 正缓存 300s / 负 30s / Jitter 60s；Wiki 页缓存 600s。Key 含 `acl_version` 或对象版本 | 读路径热、ACL 行小，String 够用。负缓存短，避免「不存在」长期假阴 | 缓存命中后 **仍要**回表看 Item/Head；Redis 故障回源，不把空当成无权限 |
| MinIO | 原文字节 | Note 扩 Reading Window 时按 Snapshot 读连续正文 | 窗口要的是相邻段落，不是另一份 TopK Chunk | 不当检索索引 |

Rerank 是对融合后前约 40 条的远程打分，不是 Redis 结构。超时或响应畸形时**退回 RRF 顺序**，并打 Degraded，不装成「没有证据」。

### 应考故事（联调/审查，不要说成线上事故）

口径同 [09](../简历亮点八股/09-真实缺陷排查与复盘案例.md)。开口「检索联调里最难的是搜到了但不该给」，Fixture 百分比不上简历。

**被问「实习最困难」优先讲故事 A**（跨课泄漏），对方问回答挤满重复段再讲故事 B。

#### 故事 A：邻课讲义进了有效证据

**现象。** 问「这门课实验几学分」，引用里出现另一门课的大纲。平均召回还不错，所以只看总分会漏掉。

**定位。** 分三层。① ES 查询带了 `workspace_id` filter，仍可能因投影滞后、旧别名、或关联错误打到邻课文档。② Redis ACL String 若 Key 不带 `acl_version`，撤权后 300s 内仍放行。③ 若生成直接信 ES 命中、不做 Hydrate，就越权进 Prompt。反证：MySQL 里该 Source 对当前成员不可见——说明检索面和真源不一致。

**根因。** 把「搜得到」当成「能给用户」。ES filter 是性能初筛；权限和当前版本在 MySQL。均值 Recall 会掩盖偶发越权。

**修复思想。** 召回之后 Hydrate：Workspace、可见性、Snapshot、Wiki Head，不通过丢弃。发布门禁 Scope Violation=0，不和 Recall 加权。Gold 必须有跨课、已删、旧版负例。ACL 缓存 Key 带版本，高风险读在权限服务不可用时关掉。

**验证。** 固定负例回放：越权进 EvidenceBundle 的条数为 0。只证明门禁对这批输入成立，不是线上 Hybrid 准确率。

**可追问 ES。** 倒排擅长课号；knn 擅长「撤课/退选」同义。两路分数不可比所以 RRF 用名次。不能为了召回把 filter 拿掉。Wiki 页缓存 600s 命中后仍回表看 Head，否则改页面后旧反链会回来。

#### 故事 B：同一讲义相邻三段占满 Prompt，结论却撑不住

**现象。** 引用很多，看起来很「有依据」，但定义在命中前一段，答案把实验学时写错。Rerank 偶发超时后，有时变成「没证据」拒答，有时又突然流畅作答。

**定位。** 融合后的前 K 是同一 Source 相邻 Chunk。若整包进 Prompt，多样来源被挤掉。Rerank 畸形/超时时，若把空列表当成「没有证据」，会过度拒答；若忽略错误继续当精排成功，会用脏顺序生成。

**根因。** 相关 ≠ 能撑 Claim。Rerank 是远程打分，失败是能力降级，不是检索真空。Note 若复用 QA TopK，定义更容易落在窗口外。

**修复思想。** Selection：最多约 6 条/8000 字，第一轮每 Source 一条。生成只引 Manifest ID。Rerank 失败保留 RRF 顺序并打 Degraded，发布另要求无降级。Note 走 Source→Anchor→连续 Window。拒答看证据充分性，不把拒答算成召回失败。

**验证。** 相邻重复占满的 Case 被 Selection 打散；Rerank 超时路径有 Degraded 标记。不把小 Fixture 说成 Rerank 提升。

**可追问。** 为什么不把 Rerank 结果放 Redis？相关性依赖 Query+文档+模型版本，缓存 Key 必须含这些，收益有限；当前热路径是 ACL/Wiki 缓存，不是精排缓存。

### 机制深挖（失败窗口与落地）

#### 「相关」按任务拆开

**失败窗口。** 问答要能撑结论的片段；深读要连续原文；知识页要当前版本和来源关系。同一套 Chunk TopK：专名漏掉、论证被切碎、改页面后旧引用失真。

**设计。** 只共享 Source Snapshot、Workspace ACL、Evidence 契约。QA 的候选单位是 Passage；Note 先 Source 再 Window；Wiki 先 Page Version 再有限关系。写回也不同：QA 不入库，Note 审阅后条件写 Source，Wiki 追加 Version。

公共编排可以收成一组小接口：`plan` → `retrieve` → `revalidate` → `explain`。三种定位是同一 Seam 上的 Adapter，不能为了「统一 RAG」抹平目标函数。

**notes 方法。** notes 说「不是只用一个 index」：这里对应的是三种检索单元和三种写回语义，不是三套互不相通的资料库。资料真源仍是同一 Snapshot，避免重复解析和权限分叉。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 统一向量 TopK | 三条链路互相伤害 | 不换 |
| 三条链路各建资料库 | 重复解析、权限不一致 | 不换 |
| 让模型直接读全部资料 | 成本、权限、引用无法证明 | 资料永远很少且无版本需求时才可能 |
| 一上来完整 GraphRAG | 社区摘要贵，且不能替代原文版本 | Wiki 只做受限关系读取 |

**失败怎么收。** 优化 QA 召回不得擅自改 Note 窗口语义。评测指标也不能合成一个「RAG 准确率」。

---
#### Query 改写 + BM25 + Vector + Weighted RRF

**失败窗口。** 用户问「实验几学分」，资料写的是课号和「学分学时」；只向量会漏专名，只 BM25 会漏同义。两路分数直接加会漂。原问题带代词或上一轮实体，不改写会检索成另一件事。

**设计。** 先 Workspace / 版本 / 可见性过滤，再关键词与向量各召回，用 RRF 按名次融合：

```text
RRF(d) = Σ w_i / (k + rank_i(d))
```

`[当前实现]` 两路各 60、融合上限 100、RRF K=60、向量/词法权重 0.7/0.3。这些是可回放配置，不是最优证明。

原问题与检索表达分开。`qa-conversation-rewrite-v1` 保存多轮改写版本；低召回路径最多生成 5 个确定性查询变体，去重并去掉问句前缀。**Original Query 永不被 Expansion 覆盖**；Normalized Query 只影响候选检索。生成仍以原问题和显式约束为回答目标，不得引用计划外证据。

指代（「它」「那门课」「第二个」）若只影响搜索措辞，可在原 Scope 内并行受限变体；若会改 Workspace、Source、答案对象或写回目标，必须先澄清。实体只能来自当前冻结的 Conversation Snapshot，不能从其他 Workspace 或未授权 Memory 猜。没有统一实体别名表和跨能力 Intent Decision，不能说成完整 NLU。

**notes 方法。** 「LLM 不是直接回答，而是先把自然语言转成适合检索的 query」。校园例子：上一轮「操作系统」，这轮「那门课实验几学分」——检索必须带课名，但不能把 Scope 扩到邻课。答案正确不能反推改写正确，Rerank 可能偶然补救；要沿 Query Variant → Candidate → Evidence → Claim 分层定位。选 ES 是因为词法、过滤、生态成熟，不是因为「不会向量库」。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 只上向量库 | 课号、专名漏召回 | 不换 |
| 分数 min-max 后相加 | 量纲不同，校准成本高 | 有稳定校准集再评估学习排序 |
| 一上来学排序 | 标签不够时不稳定 | 有稳定标注再试 |
| 不改写直接打索引 | 口语、省略、多意图漏检 | 短、专名密集的题可跳过改写 |
| 把改写当完整 NLU | 无别名表、无跨能力 Intent | 不换；澄清只在会改对象/范围时 |

**失败怎么收。** 向量关闭则显式降级到允许的词法路径，并打标 `Degraded`，不装成 Hybrid 成功。发布门禁另要求无降级。

#### Rerank、Evidence Selection、拒答

**失败窗口。** 融合后的前 K 仍可能是同一讲义相邻段，或相关但撑不住 Claim。有引用不等于引用支持结论。证据不足时流畅作答更糟。Rerank 整包进 Prompt 会把 Token 和噪声一起抬上去。

**设计。** 只对有限候选 Rerank（当前 Top N 40 量级）。Selection 先保来源多样，再填预算：最多约 6 条、8000 字；第一轮每个 Source 一条，避免同一讲义占满。生成只使用选中 Evidence，Citation 引用稳定 ID。证据不足、冲突、权限不可验证 → 拒答，不写空成功。

**notes 方法。** 结构化 Prompt：只基于给定资料、不足就说不足、输出结论+依据。错误样本迭代针对幻觉、漏条件、空引用。评估同时看漏拒和过度拒答。

**和其他做法比。**

| 方案 | 特点 |
| --- | --- |
| Rerank 结果整包进 Prompt | Token 和重复来源失控 |
| 用「多引用」当质量 | 相邻段重复引用不增加支持 |
| 把拒答算成召回失败 | 会逼系统编空引用 |
| 小 Fixture 上宣传 Rerank +100% | 6 条消融不是线上 Lift |

**失败怎么收。** Scope 外片段不得当 Gold。拒答应由证据充分性、覆盖、引用资格和冲突状态共同决定，不是「没搜到」一种。

#### Reading Window 与 Note 写回

**失败窗口。** 用 QA 的 Chunk TopK 做笔记，定义和限定条件常落在命中前后。聊天语气直接存成资料，无法审阅。生成成功自动入库，会把草稿写进 Source 和 Memory。

**设计。** Source Recall（当前 Top K 8 量级）→ Anchor → 连续 Window（候选约 24，精排 8）。按标题层级、相邻位置、字符上限和章节边界扩展。生成中性草稿，用户确认后按目标版本条件写回 Source。模型生成成功不自动入库，也不进 Memory。

**notes 方法。** 切片太大带噪声，太小切断步骤。Note 的窗口就是「按语义边界保留连续论证」，不是把全库最相关 Chunk 拼起来。

**和其他做法比。**

| 方案 | 特点 |
| --- | --- |
| 聊天一键保存 | 语气和未审内容进资料池 |
| Note 复用 QA 策略 | 丢掉定义所在的前后文 |
| 写回 Last-Write-Wins | 覆盖他人修改 |

**失败怎么收。** 窗口未就绪、资料已删、版本冲突各自有状态；冲突保留双方。`[当前实现]` 前端可编辑草稿；独立 Draft Revision、Reject、Expected Version 完整合同仍是下一阶段，面试主动讲。

#### Page Version、反链、来源回链

**失败窗口。** 原地改页面会丢掉历史和引用。只解析 Markdown 链接，标题一变就断链。混合新正文与旧关系会形成不存在的知识状态。一上来 GraphRAG，构图误差会当成关系事实。

**设计。** Knowledge Item 是稳定身份；每次发布追加不可变 Version；Head 用期望版本条件推进。Link 存稳定目标 ID；Backlink、图、搜索是可重建视图。Source 撤销让页面进入过期/治理，而不是改旧正文。目标是自动修复只出提案；`[当前实现]` Auto-fix 仍可能直接建缺页。读取限制跳数、节点数、边数、关系类型和 Workspace。

**notes 方法。** 元数据过滤先于相似度。Wiki 的「相关」是关系可解释，不是向量近。

**和其他做法比。**

| 方案 | 特点 |
| --- | --- |
| 单表覆盖更新 | 历史和引用失真 |
| 图数据库当页面真源 | 无版本、无 CAS Head |
| 一上来完整 GraphRAG | 贵，且不能替代原文版本 |
| 文本相似度直接当边 | 概念关系不可审计 |

**失败怎么收。** 旧索引命中若 Head 已变或无权限，读时拒绝。不能把受限图读取宣传成 GraphRAG。`[当前实现]` Auto-fix 仍可能直接建缺页，目标态是高风险 Proposal。

#### 读时回库

**失败窗口。** 索引、缓存可能滞后于权限和当前版本。若 ES 命中直接进 Prompt，会出现跨课、已删、旧版。

**设计。** 召回之后 Hydrate MySQL：Workspace、Source 可见性、Snapshot、Wiki Head。不通过则丢弃该候选。这是安全路径，不是性能优化可选项。Scope Guard 与 Ownership Guard 是二次校验，不是「ES 里带了 workspace_id 就够」。

**和其他做法比。** 把 `workspace_id` 只当 ES filter；信任缓存 TTL 当撤权。

**失败怎么收。** 高风险读在权限服务不可用时关闭访问，不 Fail Open。

#### Scope Violation 硬门槛

**失败窗口。** 平均召回上升时，可能夹带邻课或已删资料。均值会掩盖越权。

**设计。** 越权进入有效结果的样本必须为 0，不能和 Recall 加权。Gold 里要有跨课、已删、旧版负例。发布门禁：Scope 失败直接停，不靠总分回升放行。

**和其他做法比。** 「整体准确率还行就上线」；用拒答范围换安全分。

**失败怎么收。** 发现即停用策略/索引切换，修完全量回放再恢复。仓库 Fixture 上 Scope=0 只证明门禁对固定输入成立。

## 4. 资料底座

### 口述（4～5 分钟）

**简历原句：** 原文件、业务状态、检索索引分离；异步解析；Transactional Outbox；幂等、栅栏、死信；删除先否定事实。

**口述主回答。**

资料链路要保证两件事：回答引用的是某一版原文，而不是「现在磁盘上那份」；上传接口成功不等于已经能搜。如果在一个 HTTP 里读文件、切片、写 ES，大 PDF 占线程，搜索抖动还会拖垮上传。文件塞进 MySQL BLOB 会放大 binlog 和备份。所以拆三层：MySQL 管 Source 身份、不可变 Snapshot、解析/投影状态、删除意图；MinIO 管原件；Elasticsearch 只是可重建索引。引用钉在 Snapshot 上。切片默认 900/120，这是配置基线，要用同一 Parser 和固定评测集比 Recall 和窗口连续性，不能当最优。

一致性不能靠「写完库再发 Kafka」。进程若在发送前死，意图丢了；若先发消息再提交，消费者会看到还不存在的 Source。MySQL、Kafka、MinIO、ES 也做不成一个全局事务。做法是同一本地事务写业务行和 Outbox。可靠投递要拆三截：意图已落库、Broker 已收到、业务 Ready。Outbox 只保证第一截。Dispatcher Claim 后发送；Claim 后宕机则租约到期可重领，旧实例用栅栏拒发。发送成功未标 SENT 会重发，所以消费端必须按 Source + Snapshot + 投影类型 + 目标版本幂等。旧 Snapshot 的任务晚到，版本栅栏拒写，防止新别名被旧索引盖掉。

Kafka ACK 只说明 Broker 接到记录，Consumer 提交 Offset 只说明不再正常重读，都不能当业务 Ready。用户查询读 MySQL 状态：解析中、投影中、Ready、失败。Outbox、Kafka Lag、业务状态要对账：Lag 低但一直「投影中」，问题在 Worker 或回执，不在 Broker。一个 PDF 解析失败隔离到该 Snapshot，其他资料继续。毒消息有限重试进 DLQ，重驱是显式动作，死信不是「已经最终一致」。解析和投影是有界步骤，可以做完再交 Offset；Artifact 小时级任务只登记 Durable Execution 就交 Offset，两套消费模型不要混着讲。

删除更不能先清对象。对象删了库回滚，原文找不回。事务里先提交 Tombstone/不可见，再扇出索引、缓存、Wiki 回链、Memory。在线不可见和物理清理分开。Catalog/ACL 在 Redis 是 String，Key 带版本，正缓存大约 300 秒、负缓存 30 秒；Wiki 页缓存大约 600 秒。TTL 不承担撤权，读路径比 MySQL 版本。Redis 缓存挂了回源 MySQL，空不能当成「没这份资料」；权限服务挂了，高风险读才关掉。

索引丢了按 Snapshot 重建，质量回执后切别名，旧索引留窗口。128 MB 是接纳上限，不是吞吐。当前已验证格式是文本、Markdown、JSON、CSV、文本型 PDF，DOCX/OCR 不能说成已完成。没有观测窗口就不要报 Ready P95。

**选型（特点 → 当前更适合）。** 资料链路的约束是：引用钉某一版原文，上传成功不等于能搜，删除必须先不可见。XA 的特点是跨资源提交，更适合同构短事务。Kafka 日志的特点是重放和削峰，更适合当事件流，不是当当前 Head。CDC 的特点是少改业务代码，更适合表很多、要搬全量变更。SET NX 的特点是互斥快，更适合临界区极短、丢了可重做。当前更贴「一个权威库 + 可重建投影」：意图和业务同行落库，对象进 MinIO，索引可重建，写回用条件更新当栅栏。表多到轮询 Outbox 成为负担再评估 CDC。

**最困难（联调）：** Claim 之后进程没了，任务停在处理中。有租约不等于可恢复。见本章应考故事 A。

### 怎么讲（notes）

来自 `01` 一致性 / 高可靠、`10` Kafka、`06`「数据从哪来」：

- AI 项目要能说清数据从哪来：这里是 Workspace 内 Source 的不可变 Snapshot，不是「现在磁盘上那份」。
- MySQL 与 ES 不同步强一致。库提交后异步索引，失败重试、死信、补偿、重建。
- 先提交库再发消息会丢意图；先发消息再提交库，消费者会看到还不存在的对象。所以同一本地事务写业务行和 Outbox。
- 口播「至少一次投递 + 消费幂等」，不要说 exactly-once。Kafka ACK 只说明 Broker 接到记录。
- 问题排查四段：现象（搜不到 / 搜到已删）、定位（看 MySQL 状态不是探 ES）、原因（投递丢失 / 乱序 / 投影滞后）、解决（Outbox、栅栏、Tombstone）。
- 长任务不要占着 Kafka Offset 执行。解析/投影是有界步骤；Artifact 小时级命令只登记 Durable Execution 就交 Offset。

人设收口：原文件、业务状态、检索投影分离。上传接口成功 ≠ 已经能搜。删除先否定事实。

### 缩小版系统设计

**约束。** 引用钉某一版原文；上传成功不等于能搜；删除先不可见；索引丢了能从真源重建。

#### 1.1 架构

```text
客户端分片上传
  → Java：校验 Workspace / 大小 / Mime / SHA（接纳上限 128MB）
  → MinIO：FileObject（按 SHA 去重）
  → 同一 MySQL 事务：Source + Snapshot + 解析任务 + Outbox
  → Dispatcher Claim Outbox ──Kafka──► Parser Worker
                                      Chunk / Window（基线 900/120）
                               Kafka──► Projection Worker
                                      全文 / 向量 + 质量回执
  → Host 条件更新 Snapshot → Ready（用户查库，不探 ES）
  → QA / Note / Wiki / Research 只读允许的 Snapshot
```

三层：MySQL 管身份、版本、阶段状态、删除意图；MinIO 管字节；ES/缓存是可重建投影。

#### 1.2 端到端怎么跑

1. **接纳。** 分片校验完整性后，创建或复用 FileObject。这一步成功只表示对象到了，不是可检索。
2. **提交意图。** 同一事务写 Source、不可变 Snapshot、解析任务、Outbox。事务提交 = 「需要解析/索引」已持久。不在请求线程里切片或 Embedding。
3. **投递。** Dispatcher Claim Outbox 后发 Kafka。Claim 后宕机：租约到期可重领，旧实例用栅栏拒发。发送成功未标 SENT 会重发 → 消费必须幂等。
4. **解析。** Worker 按 Snapshot 读原件，写 Chunk/Window。当前已验证：文本、Markdown、JSON、CSV、文本型 PDF。失败隔离到该 Snapshot，其他文件继续。
5. **投影。** 建全文/向量索引，带 Source+Snapshot+投影版本。质量回执后 Host 条件更新 Ready。部分成功不标完整 Ready。
6. **查询。** 用户看 MySQL：解析中 / 投影中 / Ready / 失败。Kafka ACK 和 Consumer Offset 都不是业务 Ready。
7. **删除。** 事务先写 Tombstone/不可见，再 Outbox 扇出索引、缓存、Wiki 回链、Memory。在线不可见与物理清理分开。
8. **重建。** 新索引按 Snapshot+投影版本构建，回执后切别名，旧索引留窗口；旧 Worker 写不进新别名。

#### 1.3 状态存在哪、谁写谁读

| 数据 | 在哪 | 谁写 | 不变量 |
| --- | --- | --- | --- |
| Source / Snapshot / 阶段状态 | MySQL | Host | 引用钉 Snapshot，不覆盖更新 |
| 原件字节 | MinIO | 上传 | 不是业务版本 |
| Chunk / 向量索引 | ES | Projection Worker | 可从 Snapshot 重建 |
| Outbox | MySQL | 与业务同行 | 意图已落库 ≠ Broker 已收到 ≠ Ready |
| Tombstone | MySQL | 删除事务 | 先于对象清理 |

幂等键：Source + Snapshot + 投影类型 + 目标版本。只接受不旧于当前目标的事件。

#### 1.4 三个机制具体怎么落地

**Outbox 三截。** ①意图已落库 ②Broker 已收到（ACK）③业务完成（MySQL Ready）。对账看这三张表：Lag 低但一直投影中，问题在 Worker/回执，不在 Broker。

**有界步骤 vs 长任务。** 解析/投影做完再交 Offset。Artifact 小时级只登记 Durable Execution 就交 Offset。同用 Kafka，消费模型按任务长度选。

**删除。** 先否定事实再扇出。缓存 600s TTL 不承担撤权；读路径比 ACL/版本。权限挂了，高风险读关掉。

#### 1.5 中间件落到哪种结构（可考到这一层，不到函数名）

| 中间件 | 用它的哪一点 | 落到什么结构 | 为什么是这个 | 不用它当什么 |
| --- | --- | --- | --- | --- |
| MySQL InnoDB | 事务、条件更新、唯一约束 | 业务行 + Outbox 行同一事务；幂等键 Unique(Source, Snapshot, 投影类型, 目标版本)；写回 `UPDATE … WHERE epoch/owner=?` | 需要「意图和状态一起提交」和栅栏拒旧写 | 不当文件库 |
| Kafka | 至少一次投递、可重放、削峰 | 解析/投影命令 Topic；消费组；Offset 只表示不再正常重读 | 有界步骤可做完再交 Offset；积压可看 Lag | 不当当前 Head；ACK ≠ Ready |
| MinIO | 大对象、内容寻址 | Object Key 用内容 SHA-256，不按文件名 | 去重、多实例路径一致；utf8 长路径不塞 InnoDB 唯一索引 | 不当权限系统 |
| Elasticsearch | 词法 + 过滤 + 可切别名 | 文档带 Snapshot/Workspace；别名指当前投影版本 | 搜得快；重建时新索引回执后切别名 | 不当资料事实 |
| Redis | 快、TTL、可带版本进 Key | **String**：ACL/Catalog 缓存，Value 是小型 JSON；Key 含 `workspace + acl_version`（或对象版本）。正缓存 TTL 300s + Jitter 60s，负缓存 30s | GET/SET+EX 够用，不需要集合运算。版本进 Key，撤权不用干等 300s。Jitter 防同一时刻打穿 MySQL | TTL 不当撤权；Redis 挂了高风险读 Fail Closed，不把空缓存当成「无权限」 |

长任务入口的配额也在 Redis，但属于条 4：Lua 里同时改 **Hash 令牌桶**（tokens + 上次补充时间）和 **Sorted Set 租约**（member=任务，score=过期时间），保证「扣令牌 + 占并发槽」原子。资料底座自己不靠这套配额做正确性。

连接超时刻意短（约 Connect 500ms / Command 750ms）：控制面要快发现 Redis 不可用，避免缓存或配额把请求线程挂死。单实例 + AOF 只是本地联调，不宣称 Redis 高可用。

#### 故事 A：Claim 之后进程没了，任务停在处理中

**现象。** 上传后一直「解析中」。Kafka Lag 不高，也没有进死信。Happy Path 和「回调报错」的测试都是绿的。

**定位。** 不先翻日志猜。画出非终态：谁能推进、Owner 没了以后谁接手。发现 Dispatcher 已经 Claim（有 Owner、有过期时间、有投递代数），随后进程退出，回调没回来。重试入口只接「显式失败」，**Lease 过期扫描不管 Attempts 已经用尽**的行。于是既不能再领，也不会进死信——卡死。

**根因。** 「有租约」≠「可恢复」。租约只让所有权过期；还要规定 Owner 永久消失后如何终态化。Kafka Offset 已经往后走了也没用，因为业务行还在 PROCESSING。

**修复思想。** 增加「耗尽且租约过期」的扫描：用条件更新匹配 ID、状态、Attempt、Owner/Token，只有当前代际仍成立才进死信。不把毒任务直接打回 READY 重跑（会放大副作用）。死信保留业务身份，重驱是显式动作。时间用数据库时间，不用 JVM 时钟，避免租约判断漂移。

**验证。** 最后一次 Claim 后杀进程、租约过期、两个扫描器并发——只能终态化一次。旧 Claim 不能改新代际。

**可追问中间件。** MySQL 条件更新当栅栏；Kafka 此时只说明命令可能发过；真正卡住的是库里的阶段状态。这就是「三截对账」：Outbox SENT、Lag、MySQL 阶段必须对上。

#### 故事 B：老师删了过期试卷，问答还能搜到

**现象。** 管理端已经删除，问答偶发仍引用那份试卷。过一会儿又好了。

**定位。** 先查 MySQL：Source 已不可见。再查 ES：文档还在。再查缓存：Catalog/ACL 的 String 还是旧值。说明在线可见性已经收了，**投影和缓存还没跟上**。早期清理是事务提交后直接调 MinIO/ES，失败只打日志，没有持久清理任务。

**根因。** 把清理当成「事务后附加动作」，日志当队列。进程一崩，扇出永久消失。TTL（Wiki 页 600s、Catalog 120s）被误当成撤权。读路径若信 ES 命中，就会把已删资料送进 Prompt。

**修复思想。** 删除事务里先写 Tombstone/不可见 + 持久清理意图，提交后再扇出。清理任务同样有 Owner、租约、Attempt、死信。在线读一律 Hydrate MySQL，ES 命中不是权限结论。缓存 Key 带 `acl_version`，撤权主动失效；TTL 只限制漏失效的最长窗口。对象 Key 用 SHA-256，避免长路径撑爆 InnoDB 唯一索引。

**验证。** 删完立刻问跨课/已删负例，有效结果必须是 0。外部清理失败可重试，但不得把可见性改回去。

**可追问 Redis。** ACL 用 String + EX，正 300s / 负 30s / Jitter 60s。为什么不用 Hash？一次只读写一个 Workspace 的一小份 ACL，Hash 没有额外收益。为什么版本进 Key？改权限等于换 Key，旧 String 自然不再被打中，不必依赖 EXPIRE 当正确性。

### 对照：各方案特点，当前更适合什么

硬约束：引用钉某一版原文，上传成功不等于能搜，删除先不可见。Kafka 讲场景，不背名词。

**口述。** 同步解析适合秒级小文件。BLOB 适合极少大对象。XA 适合短、同构事务。CDC 适合表很多、要搬全量变更。RabbitMQ 适合短任务路由。Kafka 日志适合重放和削峰。当前更贴「一个权威库 + 可重建投影」：库存身份和 Snapshot，对象进 MinIO，ES 可重建，意图走 Outbox。

#### 10.1 三层分工

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 请求里同步解析+索引 | 上传完就能搜的体感 | 秒级小文件、失败可重点 | 大 PDF 和可恢复 → 上传与处理拆开，查 MySQL 状态 |
| MySQL BLOB | 少一个对象存储 | 极少、很小的附件 | 讲义 PDF 会放大 binlog → MinIO 存字节 |
| 本地盘 / NAS | 起步快 | 单机 | 多实例 → S3 API（MinIO，云上换 S3 语义不变） |
| ES 当资料事实 | 搜到就能当原文 | 检索即事实、无版本 | 要 Snapshot 和删除语义 → ES 是投影 |
| 覆盖同一 Snapshot | 实现短 | 不在乎旧引用 | 旧回答要可解释 → 新内容新 Snapshot |
| 一个 `processing` 布尔 | 字段少 | 单阶段任务 | 解析/索引/清理会互相覆盖 → 分阶段终态 |

#### 10.2 意图怎么送到处理面

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 先提交库再发消息（无 Outbox） | 少一张表 | 丢意图可接受 | 意图不能丢 → 同行写 Outbox |
| 先发 Kafka 再提交库 | 实现少一行 | 消费者能容忍脏读 | 会看到不存在的 Source → Outbox 后发 |
| XA 跨 MySQL+Kafka+ES | 听起来强一致 | 短、同构、两阶段可运维 | ES 不适合两阶段 → 最终一致 + 幂等 + 对账 |
| CDC 换 Outbox | 少改业务代码，搬表全 | 表很多、多种下游 | 现在表少、要 Tombstone → Outbox；轮询成为负担再评估 CDC |
| Kafka 当业务真源 | 日志可重放 | 事件流分析、当前状态不常查 | Head/归属要查库 → MySQL 真源，Kafka 传命令 |
| RabbitMQ | 路由灵活、短任务熟 | RPC 回调、短消息 | 解析/索引要重放和削峰 → 日志型 Kafka |
| Broker exactly-once 跨库 | 话术好看 | 单系统内 | 跨 MySQL 与 ES 仍会重复 → 至少一次 + 消费幂等 |

解析/投影是**有界步骤**，可做完再交 Offset。Artifact 小时级只登记 Durable Execution 就交 Offset。同用 Kafka，消费模型按任务长度选。

#### 10.3 删除、重建、对账

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 先删对象再提交库 | 磁盘立刻腾出 | 允许原文丢失 | 库回滚要找得回 → 先 Tombstone 再清理 |
| TTL 当撤权 | 实现零 | 短暂缓存 | 已删课不能被搜到 → 读路径比版本 |
| 原地覆盖索引当发布 | 切流量快 | 不怕半成品 | Ready 要质量回执 → 新索引切别名，旧索引留窗口 |
| 只看 Kafka Lag | 监控好接 | 消费进度即业务进度 | Lag 低仍可能投影中 → Outbox / Lag / MySQL 三截对账 |

收口：中间件各管一截。可靠投递拆成「意图已落库 / Broker 已收到 / 业务已完成」。

### 机制深挖（失败窗口与落地）

#### 库 / 对象 / 索引分离

**失败窗口。** 文件、状态、检索挤在一处：大对象拖垮备份；搜索故障拖垮上传；覆盖正文让旧回答失真。文件塞进 MySQL BLOB 会放大 binlog。

**设计。** 引用钉在 Snapshot 上。切片默认 900/120，这是配置基线，要用同一 Parser 和固定评测集比 Recall 和窗口连续性，不能当最优。128 MB 是接纳上限，不是吞吐。

**notes 方法。** 「数据从哪来、系统怎么跑」：来源是对象存储里的原件 + 库里的版本；跑法是异步阶段状态，而不是一个 HTTP 做完。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| MySQL BLOB | 备份和 binlog 被文件放大 | 不换 |
| 本地盘当对象库 | 无多实例、无校验 | 不换 |
| ES 当资料事实 | 无事务、版本、删除语义 | 不换；只加强索引 |
| 覆盖更新同一 Snapshot | 旧回答失真 | 不换 |
| 一个 HTTP 里解析+索引 | 占线程、库和索引无法一起提交 | 长任务永不走这条 |

**失败怎么收。** 对象在、库记录无 → 孤儿清理。库记录在、对象无 → 标记缺失，不装成可下载。

---
#### 异步解析与索引

**失败窗口。** 上传请求里同步解析、切片、Embedding 会占线程、超时；HTTP 成功也无法表示索引完成。一个 `processing` 布尔会让解析、索引、清理互相覆盖。

**设计。** 分块上传校验完整性后，事务创建 Snapshot + 解析任务 + Outbox。解析写 Chunk / Window；投影构建索引，质量回执后才 Ready。用户查的是 MySQL 业务状态：解析中、投影中、Ready、失败。当前已验证格式：文本、Markdown、JSON、CSV、文本型 PDF。DOCX / OCR 不能说成已完成能力。

**和其他做法比。** 同步链路；用「ES 里有文档」当 Ready；解析失败却返回上传成功可检索。

**失败怎么收。** 解析失败、投影降级、部分分片成功都不能标完整 Ready。一个 PDF 失败，其他资料继续；失败隔离到单个 Snapshot。

---
#### Transactional Outbox

**失败窗口。** 先提交库再发 Kafka：崩溃丢投递。先发 Kafka 再提交库：消费者看到不存在的 Source。跨 MySQL/Kafka/MinIO/ES 没有可用的全局事务。

**设计。** 同一 MySQL 事务写业务行和 Outbox。Dispatcher 领取后发 Kafka。Outbox 保证「需要投递」已持久，不保证 Broker 已收到，更不保证业务完成。发送成功未标 SENT 会重发，所以消费端必须幂等。

**notes 方法。** 可靠投递讲三截：意图已落库、Broker 已收到、业务已完成。面试里把这三截拆开，比说「Kafka 保证可靠」更像做过。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 本地消息表都没有的双写 | 必丢或必脏读 | 不换 |
| 立刻上 CDC | 仍要幂等和 Schema 治理 | 当前规模 Outbox 更直接；CDC 换掉轮询搬运时再评估 |
| XA | 运维和失败窗口更难 | 不换 |
| Kafka 当业务真源 | 不适合归属、当前状态、复杂查询 | 不换 |

**失败怎么收。**

| 失败点 | 正确结果 | 不能做什么 |
| --- | --- | --- |
| DB 已提交，发消息前退出 | Outbox 扫描补发 | 依赖内存队列 |
| Kafka 投递超时 | 允许重试，记 attempt | 直接判定业务失败 |
| 发送成功未标 SENT | 重发 + 消费幂等 | 说成 exactly-once |
| Dispatcher Claim 后宕机 | 租约到期重领；旧实例栅栏拒发 | 当成消息已丢失 |
| Lag 低但业务一直投影中 | 对账 Worker / 回执，不先怪 Broker | 只看 Kafka 监控下结论 |

**对账三截（追问「怎么知道一致了」）。** Outbox 未 SENT、Kafka Lag、MySQL 阶段状态是三张表，对不上就按窗口修，不要合成一个「消息可靠」。Lag 低只说明分区读得快；Ready 只看业务条件更新是否成功。

---
#### 幂等与版本栅栏

**失败窗口。** 至少一次投递会重复、乱序。旧 Snapshot 的索引任务晚到，会盖住新别名。

**设计。** 幂等键：Source + Snapshot + 投影类型 + 目标版本。只接受不旧于当前目标的事件。重复返回已处理回执。旧 Dispatcher 恢复后用 Fencing / 条件更新拒绝。

**和其他做法比。** 靠 Kafka exactly-once 神话跨 MySQL 和 ES；Last-Write-Wins 无版本。

**失败怎么收。** 旧事件拒绝写入当前别名；不把拒绝当丢数据。Worker 解析成功但回调丢失：重复回调返回同一 Receipt，不新建 Snapshot。

---
#### 死信与重驱

**失败窗口。** 毒消息占分区；无限重试放大成本和延迟。死信若没有重驱，只是把失败藏进队列。

**设计。** 有限重试后进入 DLQ，业务进入可诊断终态。重驱是显式操作，带幂等。DLQ 是隔离和取证，不是自动修成功。未知结果先对账。

**和其他做法比。** 失败直接丢；无限重试；把 DLQ 积压当「最终一致已完成」。

**失败怎么收。** 重试放大倍数要观测（Delivery Attempt / 唯一 Outbox）。死信不是「已经最终一致」。

---
#### 删除先否定事实

**失败窗口。** 先删对象或索引、库回滚，文件找不回。只过期缓存，撤权窗口内仍能搜到。

**设计。** 事务内提交 Tombstone / 不可见，再 Outbox 扇出索引、缓存、Wiki 回链、Memory、评测副本。在线不可见与物理清理分开。缓存 600 秒 TTL 不承担撤权；读路径比 ACL / Source 版本。

**和其他做法比。** 先删 MinIO 再提交库；只删当前 ES 文档不管派生；TTL 当撤权。

**失败怎么收。** 权限服务不可用时高风险读关闭。物理清理失败可重试，不得恢复可见性。删除提交但投影未清理：在线已不可见，清理任务继续。

---
#### 投影重建

**失败窗口。** 索引损坏、换模型、换切片参数时，若业务资料跟着没，用户资料会丢。重建无版本栅栏，旧 build 会切回当前。无回执切流量会把半成品当 Ready。

**设计。** 新索引按 Snapshot + 投影版本构建，质量回执后切别名，旧索引留窗口。重建推进到目标版本，旧 Worker 写不进新别名。投影损坏从 Snapshot 重建，不能反向覆盖业务真源。

**和其他做法比。** 原地覆盖同一索引当发布；无回执切流量。

**失败怎么收。** 重建中查询仍走旧别名或明确未就绪。索引写成功但 Finalize 失败：投影待对账，不能静默 Ready。

### 12. 评测口径

| 指标 | 意义 | 不要怎么报 |
| --- | --- | --- |
| Upload Accepted Rate | 接收面 | 不要把接纳当 Ready |
| Projection Ready P95 | 用户等待 | 没有观测窗口不报 |
| Outbox Delivery Amplification | 重试放大 / 毒消息 | 不要说投递次数低就是可靠 |
| Callback Duplicate Convergence | 幂等 | 不要说 exactly-once |
| Delete Visibility Lag | 用户删除语义 | 不要和物理清理混成一个 SLO |

### 边界

接口成功 ≠ 可检索。Chunk 900/120 是配置基线。128 MB 只是接纳上限。Compose 关 ES 时的本地回退不是生产默认。CDC 能换掉轮询搬运，但幂等和 Schema 演进还在。

## 5. Artifact / Skill / MCP

### 口述（4～5 分钟）

**简历原句：** Skill Catalog + Schema 的 Skill Graph；Host 提交版本；Worker 出 Candidate；Verifier；MCP 白名单；令牌桶与并发租约。

**口述主回答。**

产物生成的坏味道是「一个 Prompt 出文件」。章节漂移、失败整篇重跑、模型调用不该用的工具、Worker 已经写了对象但版本没落库、超时当失败再放一遍导致重复副作用。所以先把报告、测验、学习指南收进 Skill Catalog：稳定 skill_key、输入输出 Schema、风险和允许的能力。未知 Skill 或缺必填 Fail Closed，不靠模型置信度硬跑。

执行不是运行时让模型随便选边。编译期把获取、生成、校验、修复、等待收成 Skill Graph：节点、依赖、超时、预算在编译期固化，环和未知节点直接拒绝，进行中的任务不原地换图。按拓扑执行，节点后做 Verifier，只修失败节点，有次数上限。MCP 在这里只是白名单内的调用协议：注册表、域名、风险等级，执行前重新鉴权。工具描述里的「忽略审批」当不可信输入丢掉。用户自定义生产 MCP 和 Debug 注册在生产必须关掉。

Kafka 在这条链路只负责接纳：Consumer 按 Command ID 在 MySQL 幂等登记 Durable Execution，事务提交后立刻交 Offset。小时级跑图的权利在 Execution Lease，不靠占着分区 Poll。否则一个讲义 PDF 会把同一分区上的解析任务卡住。

提交权在 Java Host。任务开始冻结 Input Snapshot，同一事务写 Job、Task、Outbox。Host 创建 Run 时预分配 Version ID，Worker 的候选和文件都引用它，避免回调乱序出现两套版本；ID 处于内部 RESERVED 时用户还看不见。Worker 只回 Candidate。Host 校验内部身份、幂等键、Lease、Fencing Token、Payload Digest 后才落 Version。这样生成成功、回调成功、版本提交是三件事。内容合同通过后先不可见 `DELIVERY_PENDING`，文件齐了才 READY。Kafka 接到命令不等于产物交付；Callback 200 也不等于用户可下载。超时先查回执再决定重试，这就是未知结果，不能当失败重放。未接入等待合同的 Provider 429 只做有限重试，不能包装成自动 Resume。

配额落在 Redis 里是两套结构，不要和 SSE 的 Stream、Research 的 10/10 工具桶混成「限流 20」。入口是 Hash 令牌桶（tokens + 上次补充时间），Workspace+Actor+Workload，大约 20/分钟，Lua 里按时间补再扣。在途是 Sorted Set，member 是任务 Token，score 是过期时间，Workspace+Workload 大约并发 4、Lease 300 秒——管的是这个 Workspace 同时占着几个长任务，不是格子上那 60 秒 Task Lease。生产 Redis 不可用 Fail Closed。这些是保护参数，不是压测 QPS。

**选型（特点 → 当前更适合）。** 产物的约束是：结构不能漂、工具不能越权、失败不能整篇重来、超时不能当失败重放。Dify 的特点是搭流程快，更适合内部演示。运行时改边的特点是适应资料差异，更适合探索性 Agent。开放 MCP 的特点是生态大，更适合本地个人助手。只限 QPS 的特点是保护入口，更适合短请求。当前更贴「格式稳定的多租户产物」：Catalog 收口能力，编译期 Graph，Host 预分配 Version ID，速率和在途两套配额。跨天等人补资料成为主路径再评估 Temporal。Job 是长期意图，不能当成功率分母。文件型 Worker 库不适配多实例，也要主动讲。

**最困难（联调）：** 回调超时后再跑，MinIO 里两份 PDF。超时是未知结果，Fencing 收不回已写对象。见本章应考故事 A。

### 怎么讲（notes）

来自 `06`/`07` Agent 价值、`18` Plan 与工具边界：

- Agent 价值在意图边界、工具可靠、失败处理和评估，不在配 workflow。不要把 Dify / LangGraph / MCP 平台当掌握了 Agent。
- 这些平台降搭建成本，不自动给对象授权、配额和提交权。那些仍要工程设计。
- 格式稳定的产物（讲义、测验）外层可以偏编译好的 Graph；不要运行时让模型随便改边。
- 工具在测试阶段可以观察 Plan 需要什么；线上强制白名单。工具描述里的「忽略审批」是供应链输入，不是策略。
- 超时是未知结果：先查回执再决定重试，不能当失败重放。
- 评估不要用 Job 当成功率分母。Job 是长期意图；一次生成是 Run/Attempt。

人设收口：Skill Catalog + Schema 的 Skill Graph；Java Host 独占版本提交；Worker 只回 Candidate。

### 缩小版系统设计

**约束。** 讲义/测验结构不能漂；工具不能越权；失败不能整篇重来；超时不能当失败重放；用户只能看到文件齐了的版本。

#### 1.1 架构

```text
显式 skill_key + 输入
  → Java Host
       Catalog/Schema 准入（未知或缺必填 Fail Closed）
       冻结 Input Snapshot
       预分配 artifact_version_id（内部 RESERVED）
       编译 Skill Graph（获取/生成/校验/修复/等待）
       同一事务：Job / Run / Task / Outbox
  → Kafka：只按 Command ID 幂等登记 Durable Execution，立刻交 Offset
  → Scheduler：令牌桶 + 在途租约 + Execution Lease
  → Python Worker：按固化图执行，只回 Candidate（引用预分配 Version ID）
  → Host 回调：身份 / 幂等键 / Lease / Fencing / Digest
  → Verifier → 内容合同通过 → DELIVERY_PENDING（用户不可见）
  → 文件 Contract 齐 → READY（可下载/写回）
```

Kafka 在这条链路只负责**接纳**。小时级 Owner/Heartbeat/Timeout 在 Execution Lease，不靠超长 `max.poll.interval`。

#### 1.2 端到端怎么跑

1. **准入。** 稳定 `skill_key` 命中 Catalog：IO Schema、风险、允许能力。模型猜测不能覆盖显式 key。缺 URL/语言/写回目标 → 澄清或拒绝。
2. **冻结与占坑。** 输入快照冻结 Source Scope、Skill 版本、Control Pack。Host 预分配 Version ID，Worker 的候选和文件都引用它，避免回调乱序出两套版本。此时用户看不见。
3. **编译图。** 获取、生成、校验、修复、等待收成有向图：节点、依赖、超时、预算。环和未知节点编译期拒绝。进行中的任务不原地换图。
4. **接纳。** 事务落 Job/Run/Outbox。Consumer 登记 Durable Execution 后交 Offset。DB 提交、Offset 未交而退出：重放同一 Command ID 返回已有 Execution。
5. **调度。** 入口令牌桶 Workspace+Actor+Workload，约 20/分钟；在途租约约并发 4、Lease 300s。Redis Lua 原子更新；不可用生产 Fail Closed。
6. **执行。** Worker 按拓扑跑节点。节点后 Verifier；只修失败节点，有次数上限。缺资料且已有 Wait Receipt 才进 Waiting 并放租约。
7. **回调。** Host 核内部身份、幂等键、Lease、Fencing、Payload Digest。超时是未知结果：先查 Receipt 再决定是否重试。
8. **交付。** 内容合同过 → 不可见 `DELIVERY_PENDING` + 必需文件 PENDING Manifest。Staging 导出、文件合同过，全部 READY 后 Version 才用户可见。写回另走带 Expected Version 的 Proposal。

#### 1.3 状态存在哪、谁写谁读

| 数据 | 在哪 | 谁写 | 不变量 |
| --- | --- | --- | --- |
| Job / Run / Attempt / Version | MySQL | 仅 Host | Job ≠ 一次生成；只有 READY 可下载 |
| DurableExecution | MySQL | Consumer 幂等登记 | Offset 已交仍能领到 |
| 文件字节 | MinIO Staging → 正式 Key | Host 在文件合同后晋升 | Markdown 通过 ≠ PDF READY |
| CallbackReceipt | MySQL | Host | 重复回调同一语义 |
| 配额 | Redis | Lua | 不当业务真源 |

#### 1.4 三个机制具体怎么落地

**三阶段成功。** 生成成功=有合法 Candidate；回调成功=Host 收到绑定 Digest 的 Receipt；版本提交成功=校验后落 Version/文件。Kafka 有命令、Callback 200，都还不是用户可下载。

**预分配 ID。** RESERVED → DELIVERY_PENDING → READY。首轮内容前取消不创建空 Version。已 READY 不能倒退成取消。ID 不回收。

**未知结果。** 网络超时不能证明 Worker 没做完。先查回执；旧栅栏写回拒绝。未接入等待合同的 Provider 429 只做有限重试，不能包装成自动 Resume。

`[当前实现]` `artifact_job_run` 仍混请求与尝试；PDF/写回可能早于最终 Verifier——面试主动讲。

#### 1.5 中间件落到哪种结构（可考到这一层，不到函数名）

| 中间件 | 用它的哪一点 | 落到什么结构 | 为什么是这个 | 不用它当什么 |
| --- | --- | --- | --- | --- |
| Redis **Hash** | 字段级读写、Lua 原子 | 令牌桶：`tokens`、`last_refill`。Key ≈ Workspace+Actor+Workload。容量/补充约 20/分钟 | 要「按时间补令牌再判断再扣减」。多 Host 先 GET 再 SET 会同时放行。Lua 在 Redis 里连续执行，中间不插别的命令 | Lua 不是分布式事务；脚本太长会堵单线程 |
| Redis **Sorted Set** | 按 score 排序、按范围删 | 在途租约：member=任务/Token，score=过期时间。同一 Workload 上限约 4，Lease 300s | 领取时 ZADD；续租改 score；回收用 ZREMRANGEBYSCORE 清过期。比扫 Hash 全部 field 合适 | 不是分布式锁；Release 必须对上自己的 Token，防误放别人的槽 |
| Kafka | 命令保留、消费组 | 产物命令 Topic。Consumer **登记 Durable Execution 后交 Offset** | 小时级任务不能占着分区 Poll。登记事务提交、Offset 未交而退出：重放同一 Command ID 返回已有记录 | Offset 已交 ≠ 文件 READY；ACK ≠ 用户可下载 |
| MySQL | 事务、唯一约束、条件更新 | Job/Run/预分配 Version ID/CallbackReceipt；写回 `WHERE fencing=?` | 版本身份和回执必须可查 | 不当对象存储 |
| MinIO | 大对象、可换 Key | 先写 Staging Key，文件合同过再晋升正式对象 | 半成品不进用户下载路径 | 本地磁盘文件库当版本（多实例对不上） |

三套 Redis 不要混：入口 Hash+ZSet（20/min、并发 4）、Research 工具桶（10/10）、SSE Stream（条 5）。生产 Redis 不可用：昂贵任务 **Fail Closed**。Connect 500ms / Command 750ms，快发现挂掉，避免配额检查把线程拖死。

### 应考故事（联调/审查，不要说成线上事故）

口径同 [09](../简历亮点八股/09-真实缺陷排查与复盘案例.md)。开口「产物联调最难的是超时到底做没做完」。`artifact_job_run` 仍混请求和尝试，主动讲。

**被问「实习最困难」优先讲故事 A**（超时重放重复文件），对方问 Kafka 卡分区再讲故事 B。

#### 故事 A：回调超时，再点一次，MinIO 里两份 PDF

**现象。** 用户看到生成失败，重试后下载到内容几乎一样的两个版本；对象存储多了一份。Host 日志里第一次回调晚到被拒或被当成另一次成功。

**定位。** 拆三阶段：Worker 是否已生成文件、回调是否到达、Version 是否提交。典型窗口：Worker 写完对象，回调在路上超时，Host 当失败又派发。早期 Worker 自建 Version ID，两次回调就是两套身份。Kafka 至少一次会把同一命令再送一次。

**根因。** 超时是未知结果。Fencing 只能阻止旧 Worker **改 Host 状态**，不能把已经写到 MinIO 的对象收回来。没有预分配 ID 和文件 Staging，副作用会先于版本出现。

**修复思想。** Host 创建 Run 时预分配 Version ID，Worker 的候选和文件都引用它。内容合同过了先 `DELIVERY_PENDING`（用户不可见），Staging 导出，文件合同过再晋升 READY。超时先查 Receipt：已有 Digest 则幂等返回，不新派。旧 Token 写回条件更新行数为 0。Job 不当成功率分母——这次是同一 Job 下的第二次 Attempt。

**验证。** 回调丢失、重复回调、旧栅栏晚到。用户可见版本不翻倍。`[当前实现]` PDF/写回可能仍早于最终 Verifier——这是已知缺口，目标是校验先于可执行副作用。

**可追问 Redis。** 重试会打入口令牌桶。Hash 桶空了应 429，而不是换一条「不占配额」的路径硬跑。Lua 扣了令牌之后若 MySQL 创建任务失败，要靠租约过期回收槽位，所以 ZSet score 必须是过期时间。

#### 故事 B：一个讲义生成把 Kafka 分区卡住，别的课上传也停了

**现象。** 产物任务跑了很久，同一分区上的解析/其他命令 Lag 往上走。看起来像 Kafka 挂了，Broker 其实健康。

**定位。** Consumer 若「占着 Offset 执行到 PDF 完成再提交」，Poll 间隔被最慢任务决定。再调大 `max.poll.interval` 只是把 Rebalance 延后。解析链路（条 3）是有界步骤，本来可以做完再交 Offset；产物是小时级，混用同一消费模型就会互相拖死。

**根因。** 把 Kafka 当执行器。Kafka 的特点是日志、重放、消费组，擅长**接纳和缓冲**，不擅长持有一小时执行权。

**修复思想。** Consumer 校验 Command ID，MySQL 幂等登记 Durable Execution，事务提交后立刻交 Offset。Scheduler 用 Execution Lease（续租、超时、Fencing）管长跑。分区进度不再等于最慢 PDF。无效命令先落 DLQ 再交 Offset，避免毒消息堵分区。

**验证。** 登记后杀 Consumer：Offset 已交，Scheduler 仍能从 MySQL 领到未执行记录。重复命令返回同一 Execution。不要把 Compose 联调成功率当成分区隔离已在生产验证。

**可追问。** Redis 并发 ZSet 限制同一 Workspace 同时 4 个长任务，保护的是 Provider 和线程，不是 Kafka 分区。分区卡死和配额打满是两个现象，不要用加 Consumer 台数解决下游已经慢的问题。

### 对照：各方案特点，当前更适合什么

硬约束：结构不漂、工具不越权、失败能局部修、超时先对账。平台降搭建成本，不自动给授权和提交权。

### 机制深挖（失败窗口与落地）

#### Skill Catalog

**失败窗口。** 每种产物写一套 Action+Prompt，扩展要改主流程。模型自选任意工具会越权。缺 URL、语言、写回目标时硬跑，副作用不可逆。

**设计。** 报告、测验、学习指南注册为 Skill：稳定 `skill_key`、输入输出 Schema、风险、修复策略、允许的能力。未知 Skill 或缺必填 Fail Closed。显式 `skill_key` 优先于模型猜测。

**notes 方法。** 意图边界先于规划。这里用 Catalog 收口「能做什么」，而不是让模型从开放工具列表里猜。线上工具强制白名单，和 notes「测试观察 / 线上限制」一致。

**和其他做法比。** 万能 Prompt；用户任意注册生产 Action；用自然语言置信度覆盖 Schema 失败。

**失败怎么收。** 缺必填要澄清或拒绝，不带着空参数执行。Skill 数量「11」不当质量指标。

---
#### Skill Graph + Schema

**失败窗口。** 获取、生成、校验、修复、等待挤在一次调用里，失败只能全量重做。运行时任意改边，权限和预算无法编译期收口。

**设计。** 编译期把 Skill 收成图：节点、依赖、超时、预算、等待点。按固化顺序执行，节点后验证与修复。Schema 约束输入输出，结构漂移进 Repair 或失败，不直接当版本。图变了要新版本，不原地替换进行中的任务。

**notes 方法。** 外层 Plan（这里是编译好的 Graph）管阶段和检查点；内层节点才允许有限模型决策。不要把「自主多 Agent」当当前宣称。

**和其他做法比。**

| 方案 | 特点 | 何时更贴另一类 |
| --- | --- | --- |
| 一次 Prompt 出文件 | 章节漂移、失败整篇重跑 | 不换 |
| 运行时任意改边的多 Agent | 权限和预算无法收口 | 当前不宣称通用动态调度 |
| 把 MCP Tool 列表当 Graph | 列表没有依赖、超时、校验 | 不换 |
| 固定纯 workflow | 资料差异无法局部决策 | Graph 骨架 + 节点内有限决策 |

**失败怎么收。** 环、未知节点、重复 ID 在编译期拒绝。

---
#### Host 提交 vs Worker 候选

**失败窗口。** Worker 自己建版本：回调乱序会出现两套 Version；对象已写、库未提交则用户看到半成品。Worker 文件库当业务版本，多实例对不上。

**设计。** Java Host 冻结 Input Snapshot，事务内 Job/Task/Outbox，创建 Run 时预分配唯一 `artifact_version_id`。Worker 所有 Candidate、文件、Trace 都引用它，只回 Candidate。Host 校验回调身份、幂等键、Lease、栅栏、Payload Digest 后才落版本。用户改要求 → 新 Run；Worker 重启/租约接管 → 新 Attempt，仍绑原 Run 和 Version ID。

预分配 ID 生命周期（追问「会不会两个版本」）：

| 阶段 | 用户能看见吗 | 含义 |
| --- | --- | --- |
| RESERVED | 否 | 只有内部 ID，没有业务 Version |
| DELIVERY_PENDING | 否 | 内容合同已过，文件未齐 |
| READY | 是 | 可下载、采纳、写回 |
| DELIVERY_FAILED / ABANDONED | 否 | 交付链失败或超期；ID 不回收 |
| 已 READY 后取消 | 不允许倒退 | 只能归档、删除或追加式回滚 |

**和其他做法比。** Worker 文件库当业务版本；回调 200 当 Version 已提交；用 Kafka offset 当执行成功。

**失败怎么收。** 首轮内容前取消只终结 Run 和 Reservation，不创建空 Version。`[当前实现]` `artifact_job_run` 仍混请求与尝试；Worker 与 Host Version ID 未完全统一——面试主动讲，不当成已完成目标设计。

---
#### Verifier 与局部 Repair

**失败窗口。** 模型一次通过结构、引用、安全校验不现实。整篇重跑贵，且可能改掉已经对的部分。PDF/写回若早于最终 Verifier，失败产物已经外溢。

**设计。** 内容 Contract 查章节、字段、引用、题目答案；文件 Contract 查 Mime、Digest、大小、对象存在。PASS / WARN / FAIL / UNKNOWN 不能混成一个成功布尔。只修失败节点，有次数上限。目标：内容契约通过后先不可见交付中版本，文件齐了再生效。Repair 高可能是生成差，也可能是校验严，要和成本一起看。

**notes 方法。** Checkpoint 之后才进下一阶段。内容通过是检查点，文件 READY 是检查点，写回是另一条带审批的副作用，不要连成一次「成功」。

**和其他做法比。** 无限 Repair 换通过率；跳过校验直接 PDF/写回。

**失败怎么收。** 预算耗尽则失败，保留候选与原因，不标成功。`[当前实现]` PDF/写回可能早于最终 Verifier——已知缺口。

---
#### MCP 白名单

**失败窗口。** 任意 MCP Server 等于任意代码和网络。工具描述里的「忽略审批」若当策略，等于把供应链输入写成系统规则。模型填任意 URL 抓取会出网。

**设计。** 只调用注册表内能力、允许域名、风险等级。执行前重新鉴权。冻结的 Capability Set 只定义本 Run 上限，运行期间只能收紧。描述中的指令不当系统策略。内置 MCP 扩展资料和工具，不是开放插件市场。用户自定义生产 MCP 和 Debug 注册在生产必须关掉。

**notes 方法。** 「了解平台机制和限制才加分」。MCP 在这里是调用协议，不是插件市场，也不是授权系统。

**和其他做法比。** 用户自定义生产 MCP；用 MCP 规范代替 Workspace 授权；模型填任意 URL 抓取。

**失败怎么收。** 私网、凭据转发、未注册能力一律拒绝。副作用参数变化必须新的 OperationIntent 和 Approval，不能复用旧审批。`[目标设计]` 高风险工具调用前把编译能力与当前 ACL、Policy、未过期 Approval 再求交集。

---
#### 令牌桶与并发租约

**失败窗口。** 到达过快打满 Provider；同一 Workspace 占满在途会挤掉问答。只限 QPS 不限在途，长任务会堆积；只限并发，短时仍能打满 Provider。多实例各用本地计数会超卖。

**设计。** 两套配额，不要合成一个「Agent 并发」：

| 机制 | 键 | 量级 | 保护什么 |
| --- | --- | --- | --- |
| 入口令牌桶 | Workspace + Actor + Workload | 约 20/分钟 | 时间窗口内突发 |
| 在途租约 | Workspace + Workload | 约并发 4、Lease 300s | 同时占用的长任务 |
| Research 工具许可桶 | Provider / Workspace / Role | 独立 | 不能和入口配额混用 |

Redis Lua 做原子更新；Redis 只负责短期协调，Task/Outbox/业务状态仍以 MySQL 为真源。生产 Redis 不可用 Fail Closed。参数是保护值，不是压测 QPS。

**和其他做法比。** 只限 QPS 不限在途；多实例各用本地计数；用线程池大小当配额。

**失败怎么收。** 超限明确拒绝或有界排队。不能把 20/min、并发 4 写成压测吞吐。

---
#### 三阶段成功与未知结果

**失败窗口。** 把「模型返回了」「Worker 回调了」「用户能下载」混成一个成功，超时重试会重复副作用，指标会美化。HTTP 超时当失败重放，可能重复写文件。

**设计。** 拆开：生成成功（候选）、回调成功（主服务收到合法 Receipt）、版本提交成功（校验后落 Version/文件）。超时属于未知结果：先查回执再决定重试。内容通过后先 `DELIVERY_PENDING`，必需文件 READY 后才用户可见。首轮内容前取消只终结 Run 和 Reservation，不创建空 Version。已经 READY 的 Version 不允许倒退为取消。

Kafka 在这条链路只负责接纳：Consumer 校验 Command ID 和 Schema，MySQL 幂等登记后交 Offset。小时级 Owner/Heartbeat/Timeout/Fencing 在 Execution Lease，不靠超长 `max.poll.interval`。

**和其他做法比。** HTTP 超时当失败重放；文件还没有就对用户暴露版本；用 Job 当成功率分母。

**失败怎么收。** 回调丢失由 Worker 重发 + 对账；旧栅栏写回拒绝。Waiting 只有能力已实现持久 Wait Receipt 时才能进；未接入等待合同的 Provider 429 仍按有限重试，不能包装成自动 Resume。

## 6. Context / Memory

### 口述（4～5 分钟）

**简历原句：** Topic-aware Window 与增量摘要；任务启动冻结输入；候选-审核-版本；会话、记忆、资料证据分域；记忆不进引用。

**口述主回答。**

长任务有两个坑。一是上下文：最近 N 条会丢掉当前主题开头的约束，全量回放又把 Token 和噪声一起抬上去；压缩若每次重写全文，历史会被改掉且无法定位。二是记忆：把聊天摘要自动写进去，模型误判和网页里的指令会进后续研究，还没法单条撤销。检索命中只说明找得到，不说明该记住、谁能读、有没有过期。

当次问答或研究在 Turn 提交时冻结输入：消息、摘要版本、Memory 版本、Source 范围、策略元组。中途资料更新不影响当次 Run；要新上下文就 Regenerate，不要把 Replay 和重跑做成一个按钮。SSE 按 MySQL 事件序号回放。这里有两套计时器，不要和产物 300 秒在途租约混：Emitter 大约 120 秒只是连接寿命，Answer Lease 大约 150 秒管生成提交权。实时桥是 Redis Stream（有 ID、可跨实例 XREAD，MAXLEN 大约 512、键 TTL 600 秒），不是入口那套 Hash 配额。终态在 MySQL；Stream 挂了回源事件表，空不能当成「没有事件」。

会话按主题切 Segment。Topic-aware Window 按当前步骤组上下文：检索阶段侧重问题和范围，生成阶段侧重 Evidence 和格式。指代消解发生在会话窗口里——「那门课」要能回到上一轮实体——但不靠把聊天写进长期记忆来补。增量摘要只重算受新消息影响的片段，先当 BUILDING 修订，完整性检查后再晋升 READY；失败保留旧 READY，未晋升的不进冻结输入。这比滑动窗口多一步「丢了哪条约束能看出来」。Compiler 的顺序是：先权限，再过滤已撤销，再按任务类型选 Memory，最后和 Evidence 合并，Evidence 有独立事实预算，摘要不能把证据挤掉。

Memory 和 Evidence 分信任域。交互只出 Signal，抽取只出 Candidate。用户明确说「记住：讲义用中文术语」且范围窄、无敏感字段，才走可撤销的显式记忆；模型从闲聊推断的偏好仍是 Candidate，自动批准默认关。审核通过才不可变 Version。编译按 QA / Research / Artifact 的范围和 Token 预算生成 Control Pack，Evidence 有独立事实预算，摘要和记忆不能把当前任务所需证据挤掉。网页、附件、工具输出默认不能写长期记忆。记忆可以进后续 Prompt 的约束区，**不能**进 Evidence Manifest，也不能当 Citation。否则模型用自己写过的话自证。

撤销是事务更新 Head 再出事件，主动失效缓存和检索副本，读路径再校验。Memory Pack 在 Redis 是 String，Key 带 Revision 指纹，TTL 大约 180 秒加 Jitter；这是编译加速，不是记忆过期。Redis 挂了回源编译，禁止返回空 Pack 冒充「用户没有记忆」。完整撤销水印和提交前 Epoch 校验仍是 `[目标设计]`，开口不要说成已经拦住所有在途 Run。

**选型（特点 → 当前更适合）。** 这条约束是：当次输入可复现，长期记忆不污染证据。滑动窗口的特点是简单可靠，更适合短会话。全量重摘要的特点是长度一定下降，更适合不怕改写历史的闲聊。向量库当记忆的特点是「找得到」，更适合没有权限和冲突的个人笔记。LangGraph Checkpoint 的特点是单次运行恢复，更适合图内状态，不是跨 Run 治理。当前更贴「冻结当次输入 + 审核后的版本化记忆」：窗口跟步骤走，摘要先修订再晋升，记忆进约束不进引用。自动批准默认关。长期污染没有生产窗口就不要报百分比。

**最困难（联调）：** 删了含学生姓名的消息，新问答里还在。TTL 不是撤销；摘要和 Pack 缓存都是派生数据。见本章应考故事 A。

### 怎么讲（notes）

来自 `07` 上下文难点、`06` 上下文/记忆工程、`16` 指代与关键事实、`01`「上下文不是越多越好」：

- 上下文窗口不是「能放多少 Token」。窗口内容跟 Agent 当前状态有关：检索阶段侧重问题和范围，生成阶段侧重 Evidence 和格式。
- 压缩之后细节丢失，是上下文工程最难被追问的点。只做滑动窗口会丢掉早期约束；每次全量重摘要会改写未变历史。
- 分层：滑动窗口 → 增量摘要 → 关键事实字段 → 长期 Memory。丢了哪条约束要能看出来，不能靠把窗口再加大一倍。
- 记忆、画像、RAG 事实必须分信任域。检索命中只说明找得到，不说明该记住、谁能读、有没有过期。
- 指代消解在会话里做：上一轮实体不能丢。但「用户说过」不能当资料引用。
- LangGraph Checkpoint 解决单次运行恢复，不是跨运行的记忆治理。向量库不能当记忆事实：相似度不表达权限和冲突。

人设收口：任务启动冻结输入；Topic-aware Window + 增量摘要；候选-审核-版本；记忆不进引用。

### 缩小版系统设计

**约束。** 当次运行输入可复现、可审计；窗口跟当前步骤走；压缩丢了哪条约束能看出来；长期记忆不进引用。

#### 1.1 架构

```text
Conversation
  → Topic Segment（按主题切，不是纯时间切尾）
  → Turn 提交
       冻结 RunInputSnapshot：
         消息 / 摘要版本 / Memory 版本 / Source 范围 / 策略元组
  → Context Compiler（确定性，按顺序）
       1. Workspace 权限
       2. 过滤已撤销 / 过期 Revision
       3. 按任务类型选 Memory（QA / Research / Artifact 预算不同）
       4. 与消息、摘要、Evidence 合并
       Evidence 有独立事实预算，Summary/Memory 不能把证据挤掉
  → AnswerRun / ResearchRun / ArtifactRun
  → SSE：按 MySQL 事件序号回放（断线 ≠ 业务失败）
```

两套计时器：Emitter ≈120s 是连接寿命；Answer Lease ≈150s 管生成提交权。终态在 MySQL，不在连接里。

#### 1.2 端到端怎么跑

1. **切主题。** 会话按主题成 Segment。公共上下文（权限、长期偏好）和意图专属上下文分开；换主题时旧任务上下文归档。
2. **组窗口。** Topic-aware Window 跟当前步骤走：检索阶段侧重问题和范围；生成阶段侧重 Evidence 和格式。指代（「那门课」）在窗口里解，实体来自冻结的 Conversation Snapshot。
3. **冻结。** Turn 提交后这份 Snapshot 不再随中途资料更新而变。要新上下文开 Regenerate（新 Run），不要和 Replay 做成一个按钮。
4. **增量摘要。** 只重算受新消息影响的片段。先 BUILDING，完整性检查后晋升 READY；失败保留旧 READY。未晋升的不进冻结输入。
5. **记忆写入。** 交互只出 Signal；抽取只出 Candidate。用户明确「记住」且窄 Scope、无敏感字段，可走可撤销显式记忆；模型推断默认审核。通过后不可变 Version，追加不覆盖。自动批准默认关。网页/工具输出默认不能写长期记忆。
6. **记忆读取。** Compiler 生成 Control Pack，放在约束/偏好区。可引用 ID 只来自 Evidence Manifest。
7. **撤销。** 事务更新 Head 并出事件，失效缓存和检索副本；读路径再校验。TTL≈180s 是性能配置，不是撤销 SLO。新 Run 不再编译被删内容；历史 Run Replay 做 Redaction。
8. **回放。** SSE 按事件序号。断线重连从游标继续，不是业务失败。

#### 1.3 状态存在哪、谁写谁读

| 数据 | 在哪 | 谁写 | 不变量 |
| --- | --- | --- | --- |
| Conversation / Turn / Snapshot | MySQL | Java 在 Turn 提交时 | 运行中新消息不改已开始的 Run |
| Segment Summary Revision | MySQL | 摘要任务晋升后 | BUILDING 不进冻结输入 |
| Memory Signal/Candidate/Version | MySQL | 抽取只写 Candidate；审核写 Version | 记忆不得进 Evidence Manifest |
| Control Pack | 随 Run 冻结 | Compiler | 不是隐式全局 Prompt |
| SSE 事件 | MySQL 序号 | 运行过程 | Emitter 不是真源 |

#### 1.4 三个机制具体怎么落地

**冻结 vs 撤权。** 普通偏好更新不改在途 Run。隐私删除、撤权、高风险记忆撤销是 Hard Revocation：`[目标设计]` 提交前比 `input_validity_epoch`，已推进则受控取消，禁止写回和新的外呼。

**压缩丢细节。** 不靠把窗口加大一倍。关键事实字段单独存（课名、必须引用大纲）；原始对话可回溯；不确定向用户确认。

**信任域。** 会话 ≠ 记忆 ≠ 资料证据。检索命中只说明找得到。记忆进引用链视为评测失败。

#### 1.5 中间件落到哪种结构（可考到这一层，不到函数名）

| 中间件 | 用它的哪一点 | 落到什么结构 | 为什么是这个 | 不用它当什么 |
| --- | --- | --- | --- | --- |
| MySQL | 事务、条件更新、单调序号 | Turn/Snapshot/Summary Revision/Memory Version；事件表按 Run 内 seq 递增 | 当次输入和终态必须可回放 | 不当实时推送通道 |
| Redis **String** | GET/SET + EX、Key 可带指纹 | Memory Pack 缓存。Key ≈ `scope + 目标 + 策略版本 + Revision 指纹`；Value 只存引用和受控文本，**不存 Evidence**。TTL 180s + Jitter 30s | 编译结果可重建，缓存只加速。指纹进 Key，晋升/撤销后旧 Key 自然打不中 | Redis 挂了必须回源编译，**禁止返回空 Pack 冒充「没有记忆」** |
| Redis **Stream** | 有 ID、可跨实例追、可截断 | SSE 实时桥：XADD 追加，XREAD 拉；MAXLEN 约 512 条；键 TTL 600s | 多实例生成，浏览器要低延迟。Stream ID 能对上 MySQL seq 做去重。Pub/Sub 没有积压，断线就丢，不适合当桥 | Stream **不是**终态。600s 只是桥的寿命；权威事件在 MySQL。Cursor 早于窗口要拒绝，不能装成从零续 |
| Redis **Hash + Sorted Set**（配额，条 4 共用） | Lua 单线程原子 | Hash：令牌桶（剩余 tokens、上次补充时间）。ZSet：在途租约，score=过期时间，member=任务 | INCR 不够：要同时「按时间补令牌」和「占/释放并发槽」。Lua 避免先扣桶后占槽中间崩溃。ZSet 按过期时间扫租约，比扫 Hash 全部 field 合适 | 配额失败生产 Fail Closed；本地内存计数会超卖 |
| Redis 短超时 | 快失败 | Connect ≈500ms，Command ≈750ms | 实时桥和缓存不能把 Java 线程挂死 | 单实例 AOF ≠ 高可用 |

为什么 Pack 不用 Hash？一次编译读写的是整份 Pack，按指纹整体替换，String 更直接。为什么 SSE 不用 List？List 也能队列，但没有 Stream 那种消费 ID 和跨实例 XREAD 语义，截断和 TTL 也不如 Stream 直观。

业务上的「记忆过期」用 Version 的 Valid Until / Stale / Deleted，**不用 Redis EXPIRE 表达**。键级 TTL 删的是缓存，不是「这条事实从哪天起失效但审计还要留着」。

### 应考故事（联调/审查，不要说成线上事故）

口径同 [09](../简历亮点八股/09-真实缺陷排查与复盘案例.md)。开口「长会话联调里最难的是压缩和删除」，不要把 LongMemEval 分数当项目成绩。

**被问「实习最困难」优先讲故事 A**（删了还出现），对方问流式再讲故事 B。

#### 故事 A：删掉含学生姓名的消息，新问答里还在

**现象。** 用户删了一条带姓名的消息。刷新后再问，回答里仍出现该姓名；有时过几分钟才消失。

**定位。** 分三层看，不要只看 UI。① MySQL 消息已删或已标删除。② 覆盖这段的 Summary Revision 还是旧 READY，Compiler 仍把它编进新 Snapshot。③ Redis String 上的 Pack 缓存 Key 没带新指纹，180s 内打中旧 Pack。历史 Run 的 Replay 若原样吐 Snapshot 正文，还会再泄露一次。

**根因。** 把「删除」当成改一行或等 TTL。摘要是派生数据，消息删了摘要不会自动过期。缓存 TTL 是性能，不是撤销 SLO。冻结 Snapshot 解释「当时看见了什么」，但不能让新 Run 继续编译已删内容。

**修复思想。** 删除事务更新当前 Head，相关 Summary 标 STALE/DELETED 并触发重建。Pack Key 带 Revision 指纹，晋升/撤销后旧 String 自然失效，同时发失效事件。新 Run 的 Compiler 过滤已撤销。历史 Run Replay 做 Redaction：留身份和 Hash，不留正文。读路径再校验，不信缓存。

**验证。** 删除 Case：新 QA/Research 不再出现该文本；Replay 降级且无正文；Stale Read 视为硬门槛。完整水印传播仍有目标设计成分，面试分开讲。

**可追问 Redis。** 为什么空 Pack 危险？Redis 故障时若返回空，系统会当成「用户没有记忆」，约束丢失，比慢更糟——所以回源编译或明确降级。为什么 Jitter 30s？避免同一时刻大量 Pack 失效打穿 Compiler。

#### 故事 B：刷新页面漏了一截字，终态却显示成功

**现象。** 生成到一半刷新。有时少一段 delta，但最后变成「已完成」。Redis 看起来也没挂。

**定位。** 两套计时器先分开：Emitter ~120s 是连接寿命，Answer Lease ~150s 是生成权。终态在 MySQL 事件表。缺口出在 **先回放再订 Redis Stream** 的缝：回放到 seq=100，订 Stream 之前正好 XADD 了 101，实时通知已过，回放又没拿到。

**根因。** 把 Redis Stream 当过「不会丢的实时通道」。Stream 的特点是跨实例、带 ID、可截断（MAXLEN~512，TTL 600s），适合做桥，不是真源。Pub/Sub 更不合适：无积压，断线即丢。

**修复思想。** 以 MySQL 单调 seq 为准。要么先订 Stream 再回放、把订期间的事件按 seq 去重；要么回放后再读一次库的高水位补缝。Cursor 早于有界窗口就拒绝「从零续」，让客户端拉 Snapshot。检测到缺口停止盲目拼接 delta。Redis 读失败不能当成「没有事件」。

**验证。** 故障窗：库提交后、Stream 发布前杀进程；回放与 Live 切换时插入新事件；同一 delta 重复到达。成功标准是终态和正文都收敛，不是「推送一次成功」。

**可追问。** 为什么 MAXLEN 512 不是 512 字？是条数。慢消费者队列满时同类 delta 可合并，合并不了就 Overflow 关掉，避免内存被拖死。配额那套 Hash+ZSet+Lua 保护的是「能不能开新的长任务」，和这条 SSE 桥不是同一个 Redis 用法。

### 对照：各方案特点，当前更适合什么

硬约束：当次输入可复现，长期记忆不污染证据，撤销后新 Run 看不到。

**口述。** 滑动窗口简单可靠，适合短会话。全量重摘要长度一定下降，适合不怕改写历史的闲聊。向量库当记忆擅长「找得到」，适合没有权限冲突的个人笔记。LangGraph Checkpoint 擅长单次运行恢复。当前更贴「冻结当次输入 + 审核后的版本化记忆」：窗口跟步骤走，摘要先修订再晋升，记忆进约束不进引用。

#### 9.1 当次上下文

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 全量回放 | 实现零 | 极短会话 | Token 和已删内容会涨 → Snapshot + Topic-aware Window |
| 固定最近 N 条 | 简单可靠 | 无早期约束的闲聊 | 主题开头的「必须引大纲」会丢 → 按主题切，窗口跟步骤走 |
| 每轮全量重摘要 | 长度一定下降 | 不怕改写未变历史 | 细节丢失要能定位 → 增量摘要，失败保留旧 READY |
| 每步读最新 | 看起来永远新鲜 | 不需要审计当时看见了什么 | 重试要同输入 → Turn 提交时冻结，要新上下文就 Regenerate |
| Replay/Regenerate 一个按钮 | UI 少 | 用户不分「看当时」和「再跑」 | 两套动作 |
| 终态只在 Emitter | 少写库 | 不断线、连接即任务 | 120s 连接寿命 ≠ 业务 → 终态在 MySQL，SSE 按序号回放 |
| LangGraph Checkpoint 当记忆 | 单次运行能续 | 图内状态恢复 | 跨 Run 的撤销和引用隔离 → Checkpoint 只管当次执行 |

#### 9.2 长期记忆放哪

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 摘要自动进系统 Prompt | 用户感觉记得我 | 个人助手、可容忍误记 | 会污染后续研究 → Signal → Candidate → 审核 → Version |
| 向量库三用（检索/记忆/权限） | 一个组件 | 无 ACL、无冲突 | 相似度不管该不该记 → 分信任域 |
| Mem0 类自动记忆层 | 接入快 | 个人产品 | 缺 Workspace ACL 和 Hard Revocation → 可参考抽取，权威走审核版本 |
| 「用户说过」当 Citation | 检索空洞能补上 | 不要求资料可追溯 | 会自证 → 可引用 ID 只来自 Evidence Manifest |
| Tool/网页自动写记忆 | 信息全 | 工具输出可信 | 供应链指令会进来 → 默认不能写 |
| 短 TTL 当撤销 | 快 | 短暂缓存 | 180s 内仍可能编进 Run → 事务更新 Head + 事件失效 |
| Last-Write-Wins | 实现短 | 单写者 | 并发审核会互相覆盖 → 新事实追加 Version |

#### 9.3 编译与安全

| 方案 | 特点 | 更适合什么问题 | 当前更贴哪边 |
| --- | --- | --- | --- |
| 记忆和 Evidence 抢同一预算 | 实现省 | 证据不重要 | 摘要会挤掉当前任务证据 → Evidence 独立事实预算 |
| 冻结后无视撤权 | 重试极稳 | 无隐私/权限变化 | 敏感结果不能发出去 → 普通偏好不改在途 Run；Hard Revocation 受控取消 |
| 自动批准默认开 | 记忆更「智能」 | 低风险、可逆 | 污染不可逆 → 默认关；有采纳窗口再谈放开低风险类 |

收口：滑动窗口、摘要、关键事实、长期 Memory 是四层。Checkpoint 恢复当次运行；跨运行治理是版本化 Memory。

### 机制深挖（失败窗口与落地）

#### 任务启动时冻结输入

**失败窗口。** 生成中途资料更新、权限收回、摘要晋升，若每次重读「最新」，同一次任务重试会得到不同输入，也无法审计当时看见了什么。把 Replay 和 Regenerate 做成一个按钮，用户无法区分「看当时」和「用新上下文再跑」。

**设计。** Turn 提交后冻结：消息、摘要版本、Memory 版本、Source 范围、检索策略。当次结果只解释这份快照。Regenerate 开新 Run。SSE 按库中事件序号回放，断线不是业务失败。

普通偏好更新和新 Summary 不改变在途 Run。隐私删除、成员撤权、Source 封禁、高风险 Memory 撤销属于 Hard Revocation。`[目标设计]` Snapshot 带 `input_validity_epoch`，高风险工具和最终提交前再比当前 Epoch；已推进则受控取消，禁止发布、写回和新的外部调用。已发给 Provider 的内容无法追回，只能停后续动作并记影响范围。

**notes 方法。** 「系统怎么跑」要能复现输入。冻结是为了重试和审计，不是为了无视后续安全事实。

**和其他做法比。** 每步读最新正文；终态只存在 Emitter 里；Replay 和 Regenerate 同一个按钮。

**失败怎么收。** 高风险提交前应再校验权限世代；失效则受控取消，不能用「已经冻结」继续发敏感结果。完整撤销世代校验仍有目标设计成分，面试分开讲。

---
#### Topic-aware Window

**失败窗口。** 固定最近 N 条会丢掉当前主题开头的约束（例如「必须引用本课大纲」），也会把无关闲聊塞进窗口。全部历史丢进 RAG，Token 和噪声一起涨，还可能把已删内容带回去。

**设计。** 会话按主题切 Segment。窗口优先保留与当前任务相关的片段，而不是纯时间切尾。检索阶段侧重问题和范围；生成阶段侧重 Evidence 和格式。公共上下文（权限、长期偏好）和意图专属上下文分开；主题切换时旧任务上下文归档。

指代消解也在这层做：上一轮实体「操作系统」必须能解「那门课」。关键事实字段单独保留，不依赖摘要还记不记得课名。解出来的实体只用于当前会话检索和约束，**不能**因此写成长期 Memory，更不能当 Citation。实体只能来自冻结的 Conversation Snapshot。

**notes 方法。** 「需要放入窗口的东西都跟 Agent 当前状态有关」。notes 里「省略主语还去搜市场占有率」的失败，对应这里就是检索 query 丢掉课名。窗口过大稀释相关，过小断约束，要用任务完成质量和 Token 一起看。

**和其他做法比。** 一律最近 N 条；把全部历史丢进 RAG；用加大窗口掩盖摘要丢细节。

**失败怎么收。** 主题切分错了会丢约束或串题；要能指出当前窗口里有哪些强制约束，而不是只报 Token 用量。

---
#### 增量摘要

**失败窗口。** 每次全量重摘要贵，且可能改写未变历史，造成「压缩后细节丢失」且无法定位。摘要失败若直接覆盖，后续 Run 会建立在坏压缩上。摘要直接当 Memory，临时上下文会污染长期事实。

**设计。** 只重算受新消息影响的片段；摘要先当 Revision（BUILDING），完整性检查后再晋升 READY。未晋升的摘要不进冻结输入。新摘要失败时，旧 READY 继续提供上下文。细节丢失用关键事实字段补，不靠把窗口再加大一倍。压缩比例只表示省了多少 Token，不能直接代表信息质量。

**notes 方法。** 压缩补救：关键事实单独存、原始对话可回溯、不确定就向用户确认。这正是 notes 说的「最顶尖难度」。

**和其他做法比。** 每轮把全文压成一段；摘要不经校验直接当事实；所有摘要都当 Memory。

**失败怎么收。** 校验失败保留旧摘要版本。相关消息删除后，Summary 标 STALE 或 DELETED 并触发重建。

---
#### 候选 → 审核 → 版本

**失败窗口。** 自动把聊天写进记忆：误判、网页指令、临时偏好会污染后续任务，且无法单条撤销。向量相似度当「该记住」，会把偶发提及写成长期事实。

**设计。** 原始交互只形成 Signal。抽取器只出 Candidate。策略检查敏感字段、冲突、来源、范围。推荐分层：用户明确要求记住的低风险偏好，经窄 Scope 和敏感检查后可直接 Active Revision 并支持撤销；模型推断的偏好才走 Candidate / Review / Promotion。通过后不可变 Version，新事实追加版本，不覆盖。自动批准默认关闭。

**notes 方法。** 记忆工程不是「把对话丢进 ES」。要回答：该不该记、谁能读、冲突怎么办、怎么撤销。

**和其他做法比。** 聊天摘要直接进系统 Prompt；Last-Write-Wins 改记忆；向量相似度当「该记住」。

**失败怎么收。** 跨 Workspace 文本碰撞不能串数据。并发审核不能互相覆盖。网页、附件、工具输出默认不能写长期 Memory。

---
#### 信任域：会话 / 记忆 / 资料证据

**失败窗口。** 把记忆当引用，模型会用自己写过的话自证。Research 结论被生成过也不等于长期事实。一层向量库既当检索又当记忆又当权限，越权和污染无法分开修。

**设计。** Evidence 来自 Source Snapshot，可引用。Memory 是审核过的约束或对 Evidence 的版本化引用，按任务类型编译进上下文，**不得**进入 Rerank 特征或 Citation。编译顺序：先 Workspace 权限，再过滤已撤销/过期，再按风险和任务类型选 Memory，最后与消息、摘要、Evidence 合并。用户偏好进表达/结构控制；长期事实需要来源和时间；任务状态有过期。

**notes 方法。** 「记忆 + 用户画像 + RAG 事实要分开」。画像/偏好不是证据。指代消解用会话关键事实，引用仍必须回到 Source 版本。

**和其他做法比。** 一层向量库三用；Tool Output 自动记；「用户说过就当资料」。

**失败怎么收。** 发现记忆进了引用链视为评测失败，不是「召回更好」。无 Manifest ID 的引用视为无效。用记忆补检索空洞还挂引用，直接判失败。

---
#### 记忆不进引用链

与上节同一硬约束，单独可被追问：Citation 必须能回到 Source 版本。

**设计。** 生成器的可引用 ID 只来自 Evidence Manifest。Memory Pack 放在约束/偏好区。Context Compiler 为 RAG Evidence 保留独立事实预算，历史 Summary 和 Memory 不能把当前任务所需证据挤掉。

**失败怎么收。** 无 Manifest ID 的引用无效。评测把「记忆进引用」设为硬门槛，不能和 Recall 加权。

---
#### 撤销主动失效

**失败窗口。** 只改一行状态或等缓存 180 秒，索引和编译结果里仍可能读到已撤记忆。删向量点但不记否定事实，重建会把旧记忆召回。历史 Run 的 Snapshot 不能直接改写，但 Replay 若原样吐出已删内容，隐私失败。

**设计。** 事务更新当前 Head 并出事件，失效缓存、全文/向量副本。读路径校验，不依赖 TTL。TTL/Jitter（默认约 180 秒）是性能配置，不是撤销 SLO。删除后的新 Run 不应再编译被删内容；历史 Run 通过 Replay Redaction 处理，相关 Summary 标 STALE。物理删除、审计保留、派生失效是不同生命周期。

**和其他做法比。** 短 TTL 当正确性；删向量点但不记否定事实；改 UI 当作已删除。

**失败怎么收。** 扇出失败要对账；高风险读 Fail Closed。Stale Read Rate 目标按评测门禁收，没有生产窗口就不要报百分比。完整 Revoke Watermark 和依赖传播仍是目标设计。

### 10. 校园演练（被要求举例时）

教师明确说「记住：这门课讲义优先中文术语」。系统验证来自可信用户动作、窄 Scope、无敏感内容，直接创建可撤销 Active Revision。模型从闲聊推断「可能喜欢中文」仍只是 Candidate。「下学期规则会变」不能自动晋升长期事实。

用户删除含学生姓名的消息后，新 QA / Research 不再看到它；历史 Run Replay 做 Redaction。用户纠正事实后新 Revision 生效，旧版本可追溯。不要把 LongMemEval 论文分数写成项目成绩。

### 11. 评测口径

| 指标 | 意义 | 不要怎么报 |
| --- | --- | --- |
| Summary Retention | 摘要是否保住 Gold 约束 | 不要只报压缩比 |
| Memory Pollution Rate | 不该进当前 Run 的记忆 | 没有窗口不报百分比 |
| Stale Read Rate | 已撤销仍被编译 | 硬门槛，不和采纳率加权 |
| Correct Abstention | 记忆不足时是否克制 | 不要把乱答当召回更好 |
| Hard-revocation Commit Violation | 撤销后仍写回/外呼 | 目标 0；Snapshot 稳定性不能压过权限 |

长期污染、采纳、Token 收益属生产待验证。
