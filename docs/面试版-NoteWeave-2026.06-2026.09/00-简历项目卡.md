# NoteWeave 简历项目卡

## 项目名称与技术栈

**NoteWeave｜AI 资料研究工作台**  
**时间：** `2026.06 - 2026.09`（学校原型更早；v2 工程化重构集中在 2026.05 - 2026.08）

**核心技术：** `Spring Boot`、`MySQL`、`Redis`、`Kafka`、`Elasticsearch`、`MinIO`、`Python`、`MCP`、`RAG`、`Harness Engineering`

## 30 秒开场

我做的是一个面向个人资料研究和长期知识沉淀的 AI 工作台。它不只是把文档丢给大模型，而是把资料接入、问答、精读、知识沉淀、Deep Research 和结构化产物生成拆成不同链路。Java 主服务负责权限、任务状态、版本和最终写回，Python 负责检索、模型调用和 Agent 长任务。整个系统的核心设计是把资料和结论都变成可追溯、可校验、可恢复的状态。

## 项目描述

面向个人资料研究与长期知识沉淀场景构建 AI 工作台，覆盖资料接入、QA / Note / Wiki、Deep Research、结构化内容生成及长期 Memory，并采用 Java + Python 协同承载业务流程与 Agent 长任务。

**个人 Ownership 口径：** 核心负责 Java 控制面、任务/版本模型、RAG、Research 状态与 Host/Worker 契约；Python Worker、前端、Prompt 和第三方 Provider 按具体实现或验收范围说明，不把目标架构或第三方能力说成已经全部生产化。

## 简历正文建议稿

1. **设计验证驱动、可恢复的 Deep Research Agent：** 针对开放研究易漂移、证据不足和长任务中断的问题，将研究过程抽象为 `Table-as-State`，显式维护研究对象、待验证字段、Evidence 与结论，通过 Plan / Replan、Verifier 和受限反证持续纠偏；结合 Checkpoint 与引用审计支持任务断点恢复和结论逐项回溯。建立固定研究问题集，围绕有效研究单元完成率、引用支撑率、冲突发现率和恢复成功率做基线对比，具体数值以评测 Manifest 为准。

2. **构建任务感知的 QA / Note / Wiki 知识链路：** 针对问答、资料精读和长期知识沉淀对相关性与上下文组织方式的不同需求拆分三条链路：QA 采用 `BM25 + Vector + RRF + Rerank`，Note 采用资料级召回与连续原文窗口，Wiki 通过页面关系与来源回链组织长期知识。建立统一评测集，分别观察 Recall、Evidence 支撑、任务通过、越界引用和来源回链，不用单一准确率掩盖不同任务的失败。

3. **搭建异步资料处理流水线：** 针对大文件同步解析阻塞请求、资料处理链路耗时较长的问题，将解析、切片、向量化和索引构建拆分为 Kafka 异步任务，并通过任务幂等与失败恢复保障长链路可靠执行，支持 `128 MB` 单文件异步接入，避免大文件处理占用业务请求链路。

4. **构建 Schema 驱动的产物生成框架：** 面向报告、测验、课程笔记等多类型内容生成场景，统一抽象产物定义、执行流程与输出契约，减少新增产物时重复的 Prompt 与流程开发；采用 **Java Host + Python Worker** 分层承载任务编排、模型执行与版本管理，并通过受控 MCP 能力接入音视频转写与内容理解。当前重点证明 Schema、Repair、文件 Manifest 和写回意图协议，真实外部写回仍按目标架构和模拟回放口径回答。

5. **设计 Context 与长期 Memory 机制：** 针对长会话全量回放导致 Token 膨胀、自动记忆容易污染后续事实的问题，采用 `Topic-aware Window + 增量摘要` 压缩长会话上下文，通过候选提取与门控晋升沉淀长期 Memory，并将用户偏好与资料 Evidence 分层隔离。通过固定约束保留集比较输入 Token、关键约束保留率、事实回读一致率和误晋升率，具体数值以评测 Manifest 为准。

## 简历数字填写规则

`128 MB` 只能作为上传配置上限或固定回放输入，不等同于吞吐、并发或生产容量。百分比必须补充评测集版本、分母、基线方案、统计区间和失败样本。没有原始数据时不填写提升百分比，改为描述已建立的评测、回放和故障注入方法。
