# 系统总架构与面试主线

## 1. 系统全景回答

NoteWeave 的核心问题不是“怎么调用模型”，而是资料研究任务具有三个工程特征：资料会更新，长任务会中断，模型输出不能直接当事实。因此系统分成控制面和执行面。Java Spring Boot 主服务负责 Workspace 权限、资料版本、任务状态、配额和最终提交；Python Worker 负责解析、检索、模型调用、工具调用和长任务执行。MySQL 保存业务真源，MinIO 保存原文件，Elasticsearch 保存可重建检索投影，Kafka 负责异步解耦，Redis 负责短期协调、限流和租约。

资料上传后先写入 MinIO 和 MySQL 的 Source / Snapshot，再通过事务内 Outbox 投递解析任务。Worker 完成解析、切片、向量化和索引构建后，只回传处理结果和候选状态。QA、Note、Wiki 共享资料版本和权限，但不共享同一个检索目标。Research 和 Artifact 都是长任务，运行输入需要冻结，Worker 不能越过 Host 直接写入业务版本。最终结果必须经过引用、Schema 或权限门禁，才变成用户可见版本。

## 2. 总体部署与数据分工

```text
                    ┌──────────────┐
                    │ Web / API    │
                    └──────┬───────┘
                           │
                  ┌────────▼────────┐
                  │ Java Host       │
                  │ ACL / State     │
                  │ Version / Commit│
                  └──┬────┬────┬────┘
                     │    │    │
        ┌────────────┘    │    └──────────────┐
        ▼                 ▼                   ▼
   MySQL 真源        Kafka + Outbox       Redis 协调
   状态/版本/权限     异步命令/重试          Quota/Lease/SSE
        │                 │                   │
        │                 ▼                   │
        │          Python Worker              │
        │          Parse/RAG/Agent/MCP        │
        │                 │                   │
        └───────┬─────────┴──────────┬────────┘
                ▼                    ▼
             MinIO              Elasticsearch
             原文件             检索投影，可重建
```

| 组件 | 权威职责 | 不负责什么 |
| --- | --- | --- |
| MySQL | Source、Snapshot、Task、Run、Version、ACL | 不承担全文和向量检索 |
| MinIO | 原始 PDF、音视频和生成文件 | 不保存业务状态 |
| Elasticsearch | BM25、过滤、向量和检索投影 | 不作为权限或版本真源 |
| Kafka | 解析、切片、Embedding、索引和长任务异步投递 | 不作为当前业务状态 |
| Redis | 令牌桶、并发租约、短期缓存和流式桥接 | 不作为事实账本 |
| Java Host | 事务、鉴权、状态推进、版本提交 | 不承载模型推理 |
| Python Worker | 检索、模型、MCP、解析和候选生成 | 不直接写权威业务表 |

## 3. 一条请求如何贯穿系统

1. 请求进入 Workspace，先解析用户、Workspace、能力和资料范围。
2. 如果是资料接入，原件写 MinIO，MySQL 写 Source 和不可变 Snapshot，并在同一事务写 Outbox。
3. Kafka 投递解析任务，Worker 以 `source_id + snapshot_id + stage` 做幂等处理。
4. 交互请求根据 `answer_mode` 选择 QA、Note 或 Wiki；长任务根据 `skill_key` 或 Research 类型进入对应 Runtime。
5. Worker 使用任务启动时冻结的输入执行，输出 Candidate、Evidence、Artifact 或 Progress。
6. Host 校验 Workspace、版本、租约、Schema、引用和状态后提交；不满足门禁则拒答、重试或进入可解释失败。

## 4. 贯穿五条亮点的设计原则

| 原则 | 解决的问题 | 项目落点 |
| --- | --- | --- |
| 真源与投影分离 | 索引、缓存和页面不能反向篡改事实 | MySQL 与 ES / Cache |
| 控制面与执行面分离 | Worker 晚到、重复回调、模型越权 | Java 提交，Python 交候选 |
| 输入冻结、输出门禁 | 重试时上下文漂移，生成成功但不可用 | Snapshot、Control Pack、Verifier |
| 至少一次 + 幂等 | Kafka、HTTP、Provider 重试产生重复副作用 | Idempotency Key、Receipt、CAS |
| 正确失败优先 | 用低质量答案换完成率 | 拒答、`NO_SUPPORTED_CANDIDATE`、失败可解释 |

## 5. 技术选型的约束与代价

Kafka、MySQL、ES、Java／Python 分工和受控 Runtime 各自处理不同的失败窗口。异步化增加最终一致和幂等成本，业务真源增加投影回查，跨语言拆分增加协议维护；只有对应的资料规模、任务时长或权限约束出现时，这些代价才值得承担。

| 选择 | 当前理由 | 明确代价 | 什么时候换方案 |
| --- | --- | --- | --- |
| Kafka 异步处理 | 大文件、长链路、需要削峰和重放 | 最终一致、乱序、重复消费 | 任务需要跨天等待和人工信号时评估工作流引擎 |
| MySQL 做真源 | 版本、权限和事务查询明确 | 检索要回库校验，写扩展性有限 | 事件审计成为主查询时再评估事件溯源 |
| ES 做混合检索 | 专名、过滤、BM25 和向量可统一 | 索引重建和版本治理复杂 | 语义规模和向量 P95 成主瓶颈时拆向量库 |
| Java Host + Python Worker | Java 事务治理稳定，Python AI 生态成熟 | 跨语言协议和部署复杂 | 团队语言统一或边界稳定时可合并 |
| 自建受控 Runtime | 需要 ACL、候选提交和细粒度恢复 | 状态机与运维成本更高 | 跨天 Timer、人工审批成为主路径时迁移 Temporal 等工作流引擎 |

## 6. 规模化追问的回答边界

当前没有足够的线上数据支撑 QPS、真实用户量或生产 SLO。容量估算以文件大小、处理阶段、并发上限和 Provider 延迟为输入，并逐阶段测稳态吞吐；线程数还受连接池、Kafka 分区、对象存储带宽和 Provider 配额限制，不能直接换算为 QPS。
