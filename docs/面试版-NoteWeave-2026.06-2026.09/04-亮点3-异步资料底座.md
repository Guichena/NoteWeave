# 亮点 3：高可靠异步资料处理底座

## 1. 简历亮点对应的面试回答

资料接入不能把解析、切片、Embedding 和索引全部放在一次 HTTP 请求里。大文件会占用请求线程，任一阶段失败都会让用户不知道资料到底处于什么状态，业务库和搜索索引也无法原子更新。我把原文件、业务状态和检索投影拆开：MinIO 保存字节，MySQL 保存 Source / Snapshot 和处理状态，Kafka 承载异步任务，Elasticsearch 保存可重建投影。通过 Transactional Outbox、任务幂等、版本栅栏、退避重试和死信重驱，把“最终一致”变成可观察、可恢复的过程。

## 2. 领域对象和状态机

```text
Source                 资料身份，不随文件覆盖
└─ Snapshot             一次不可变内容版本
   ├─ ObjectRef         MinIO 对象和校验和
   ├─ ParseStatus       PENDING / RUNNING / READY / FAILED
   ├─ ChunkSetVersion   切片版本
   └─ IndexGeneration   对应的 ES 投影代次
```

处理状态建议分成业务状态和投影状态，不用一个 `processed=true` 混在一起：

```text
UPLOADED → PARSING → CHUNKED → EMBEDDING → INDEXING → READY
             ↘ FAILED  ↘ RETRY_WAIT  ↘ DEAD_LETTER
```

`READY` 只表示当前 Snapshot 的必需投影已达到可检索门槛；文件上传成功不等于已经可以搜索。每个状态变更带 `snapshot_id + generation + version`，旧任务不能覆盖新版本。

## 3. 正常接入流程

1. API 创建 Upload Session，校验 Workspace、大小、类型和幂等键。
2. 客户端或服务端把原文件写入 MinIO，记录对象校验和。
3. MySQL 事务写入 Source、Snapshot、初始状态和 Outbox Event。
4. Dispatcher 发布 `SOURCE_SNAPSHOT_CREATED`，Kafka Consumer 按阶段领取任务。
5. Parser 从 MinIO 读取固定 Snapshot，输出结构化文本和页码、章节等定位信息。
6. Chunker 生成带 `snapshot_id + chunk_version` 的切片；Embedding 阶段批量生成向量。
7. Indexer 将切片、词法字段、向量和权限元数据写入 ES 投影。
8. 只有所有必需阶段的 Receipt 都成功，Host 才将 Snapshot 标记为 `READY`。

大文件 `128 MB` 的关键不是“把同步接口超时调大”，而是客户端上传和处理链路解耦。HTTP 只负责创建上传意图和返回状态查询地址，耗时操作全部进入任务状态机。

## 4. Transactional Outbox 解决什么问题

如果先提交 MySQL 再直接发 Kafka，进程可能在两者之间崩溃，数据库已经显示有新资料，但下游永远收不到解析命令。如果先发 Kafka 再提交 MySQL，Consumer 可能读到不存在的 Snapshot。Outbox 把业务变更和待投递事件写入同一本地事务：

```text
BEGIN
  insert snapshot
  insert outbox(event_id, aggregate_id, event_type, payload, ready_at)
COMMIT
```

Dispatcher 以 `event_id` 领取事件并发布 Kafka，成功后标记 SENT。发布失败会退避重试，超过阈值进入 Dead Letter；重驱前先检查当前 Snapshot 版本和幂等状态。

Outbox 不能保证 exactly-once。它保证“业务提交成功后事件最终可投递”，Kafka 和 Consumer 仍是至少一次，因此下游必须幂等。

## 5. 幂等、乱序和版本栅栏

每个处理阶段使用稳定幂等键，例如：

```text
parse:{snapshot_id}:{parser_version}
chunk:{snapshot_id}:{chunker_version}
embedding:{chunk_set_version}:{embedding_model_version}
index:{snapshot_id}:{index_generation}
```

Consumer 处理时先登记任务执行记录，重复消息命中已完成 Receipt 就直接确认，不重复生成切片或向量。写 ES 时携带 `snapshot_id + generation`，查询和回写都校验当前 Head；旧版本晚到只能写入旧代次或被拒绝，不能把新索引覆盖掉。

删除采用“先否定事实，再扇出投影”：MySQL 先写 Tombstone 或 `deleted_at`，查询立即按真源过滤；随后异步删除 ES、缓存和关系投影。即使删除任务延迟，也不会因为旧索引命中而重新暴露资料。

## 6. 失败恢复矩阵

| 故障 | 状态处理 | 恢复动作 |
| --- | --- | --- |
| Parser 超时 | `RETRY_WAIT`，保留尝试次数 | 退避重试，超过阈值进死信 |
| Embedding Provider 429 | 任务未完成，不标记失败 | 按 Provider 配额和 Retry-After 延迟 |
| Kafka 重复消息 | 命中幂等键 | 返回已处理 Receipt，不能重复副作用 |
| Worker 处理中宕机 | Lease 过期 | Scheduler 重新领取，旧 Token 无法写回 |
| ES 写入成功但回调丢失 | 结果未知 | 对账索引代次，补写 Receipt，不盲目重建 |
| 新 Snapshot 完成、旧删除消息晚到 | 版本栅栏拒绝 | 只处理匹配 generation 的删除或重建 |

## 7. 关键 Trade-off

- **MinIO + MySQL，而不是把文件放 BLOB：** 大对象和事务元数据分离，数据库备份压力小；代价是需要处理对象上传成功但数据库提交失败的孤儿文件，靠 Upload Session 清理。
- **Kafka + Outbox，而不是同步链路：** 支持削峰、重放和多阶段解耦；代价是最终一致、乱序和消费幂等复杂。
- **ES 作为投影，而不是事实库：** 检索快且可重建；代价是索引延迟和重建发布流程。
- **版本栅栏，而不是最后写入获胜：** 防止旧任务覆盖新资料；代价是需要在每个阶段携带版本号并处理过期任务。
- **死信重驱，而不是无限重试：** 让毒消息与暂时性故障分开；代价是需要人工或运维入口审查死信原因。

## 8. 面试官高频追问

**问：Kafka Lag 为零，为什么资料还是搜不到？**  
Lag 只说明消息被消费，不代表索引写入成功或 Snapshot 已通过 READY 门禁。要沿 `snapshot_id` 检查 Parser、Embedding、Indexer Receipt、ES generation 和最终状态。

**问：为什么不直接用 CDC？**  
CDC 适合表很多、下游要完整捕获变更的场景；当前资料链路的事件语义是“某个 Snapshot 的某个阶段需要处理”，Outbox 更容易携带版本、删除和重建信息。表数量和下游类型显著增加后再评估 CDC。

**问：如何证明 128 MB 不是把请求线程卡住？**  
上传接口只创建 Session 和对象引用，解析任务在 Kafka Consumer 中执行；通过请求耗时、Worker 处理耗时、Outbox Oldest Ready、Kafka Lag 和 Snapshot 状态转移观察，压测时还要注入 Worker 重启和 ES 故障。
