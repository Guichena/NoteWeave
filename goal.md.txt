你要把“面试准备”目录里的文档改造成一套能帮助候选人应对大厂项目面试的材料。

文档最终要帮助候选人做到：

四、大厂面试官风格要求

你在改造文档时，必须模拟真实大厂面试官的追问方式。

大厂面试官一般不会只问：

- 你用了哪个函数？
- 这个接口叫什么？
- 这个类在哪个文件？
- 这个方法参数是什么？
- 某个 SQL 怎么写？
- 某一行代码是什么意思？

这些不是文档重点。

大厂项目面试更关注：

1. 你为什么做这个项目。
2. 这个项目解决了什么真实问题。
3. 系统整体是怎么设计的。
4. 核心链路是什么。
5. 你做过哪些技术取舍。

8. 当前方案有什么问题。
9. 出现问题你怎么排查。
10. 如果数据量、用户量、文档量变大，你怎么优化。
11. 哪个设计最能体现你的思考。
12. 如果面试官质疑项目只是“套 RAG”，你怎么回应。

所以文档里的面试问题和回答，要尽量采用这种追问风格：

第一层：你这个项目解决什么问题？

第二层：为什么这个问题不能用更简单的方式解决？

第三层：你当前采用了什么方案？

第九层：如果让你继续优化，你会怎么演进？

五、架构设计要求

文档里要补充 NoteWeave 的系统架构设计，但不要写成死板的架构八股。

要围绕项目真实链路讲：

1. NoteWeave 的整体架构

必须讲清：

- 前端工作台负责什么。
- Spring Boot 后端负责什么。
- MySQL 存什么。
- MinIO 存什么。
- Redis 用在什么地方。
- Kafka / Task / Worker 解决什么问题。
- Elasticsearch 在 RAG 检索中承担什么角色。
- LLM 在生成链路中承担什么角色。
- Citation / Evidence 如何保证可追溯。
- Wiki 如何作为长期知识层重新进入检索链路。

2. 架构设计不是只画图

文档必须讲清楚：

- 为什么这么拆。
- 每一层解决什么问题。
- 如果不这么拆会有什么问题。
- 当前架构适合什么规模。
- 当前架构哪里还不够生产化。
- 未来可以怎么演进。

3. 架构表达要有面试感

比如不能只写：

“系统使用 MySQL、Redis、Kafka、Elasticsearch、MinIO。”

要写成：

“我在架构上没有把所有逻辑都堆在同步接口里。业务状态放在 MySQL，原始文件放在 MinIO，长耗时的解析、Chunk、Embedding 和索引通过 Task / Outbox / Kafka / Worker 异步执行，检索侧使用 Elasticsearch 承担 BM25 和向量召回。这样设计的原因是：文档处理天然耗时且容易失败，如果放在上传接口里同步做，会导致接口超时、失败难恢复、用户体验差。异步任务链路虽然复杂一些，但能带来状态追踪、重试、幂等和后续运维能力。”

六、出现问题时的排查要求

文档必须专门补充“出现问题怎么办”。

大厂面试官很喜欢从项目设计继续追问：

- 如果 RAG 回答不准怎么办？
- 如果检索不到结果怎么办？
- 如果回答引用错了怎么办？
- 如果上传后迟迟不能检索怎么办？
- 如果向量检索失败怎么办？
- 如果 Wiki 发布了但检索不到怎么办？
- 如果用户看到了不该看的资料怎么办？
- 如果 Kafka 消息重复消费怎么办？
- 如果 Worker 执行失败怎么办？
- 如果 ES 索引版本不一致怎么办？
- 如果 LLM 生成了幻觉怎么办？

文档里每个核心链路都要补充：

1. 可能出现的问题。
2. 可能原因。
3. 如何定位。
4. 当前项目已有的支撑手段。
5. 当前还缺什么。
6. 后续如何优化。
7. 面试时如何回答。

例如 RAG 回答不准，要能写出：

可能原因：

- 文档没有成功索引。
- 用户问题没有召回到正确 Chunk。
- Chunk 切分过细导致上下文不足。
- Chunk 切分过粗导致噪声太多。
- BM25 对语义相似问题召回不足。
- 向量召回偏移。
- RRF 融合权重不合适。
- Evidence Context 太长或太短。
- Prompt 约束不足。
- LLM 自身幻觉。

排查方式：

- 查看 Document 状态和 indexStatus。
- 查看 Chunk 是否生成。
- 查看 ES 检索结果。
- 查看 RetrievalTrace。
- 查看不同 retriever 的召回结果。
- 查看 RRF 融合后的排序。
- 查看最终进入 Prompt 的 Evidence。
- 查看 LLMCallLog。
- 用 RAG Eval 做回归验证。

面试表达：

“我不会一上来就说换模型，因为 RAG 效果差可能发生在检索、切片、排序、Prompt 或生成任何一环。我会先看文档是否成功入索引，再看召回结果和 RetrievalTrace，然后看 Evidence 是否足够支撑答案，最后才考虑模型和 Prompt。”

七、方案取舍与选择要求

文档必须重点体现“方案取舍”。

每个重要技术点都不能只写“用了什么”，必须写：

1. 有哪些可选方案。
2. 每个方案的优点。
3. 每个方案的缺点。
4. 为什么当前阶段选这个方案。
5. 为什么没有选择更复杂的方案。
6. 未来什么时候需要升级。

必须重点补充这些方案对比：

1. grep vs MySQL LIKE vs Elasticsearch BM25

grep：
- 适合作为本地调试和 baseline。
- 实现简单。
- 不适合大规模知识库。
- 不支持复杂相关性排序和权限过滤。

MySQL LIKE：
- 适合非常早期 MVP。
- 可以少引入一个中间件。
- 但长文本检索性能和排序能力弱。
- 不适合作为 RAG 主检索方案。

Elasticsearch BM25：
- 适合关键词、术语、专有名词、技术文档。
- 支持倒排索引、相关性排序、字段过滤。
- 更适合作为 NoteWeave 团队知识库的基础召回方案。
- 缺点是引入额外中间件和索引维护成本。

2. BM25 vs 向量检索

BM25：
- 精确词匹配能力强。
- 可解释性好。
- 适合技术文档和专有名词。
- 对同义表达、语义相似问题不够好。

向量检索：
- 适合语义相似。
- 能处理用户问题和原文表达不一致的情况。
- 需要 embedding 模型、向量维度、索引版本管理。
- 成本和复杂度更高。
- 失败时要能降级到 BM25。

3. 单路检索 vs Hybrid Retrieval

单路 BM25：
- 简单稳定。
- 但召回可能不全。

单路向量：
- 语义能力强。
- 但对专有名词、编号、配置项不一定稳定。

Hybrid Retrieval：
- BM25 和 Vector 互补。
- 更适合真实 RAG。
- 需要融合排序和调试能力。

4. 原始 score 加权 vs Weighted RRF vs Rerank

原始 score 加权：
- 实现直观。
- 但不同检索器 score 分布不一致，难以直接比较。

Weighted RRF：
- 基于 rank 融合。
- 工程稳定。
- 易于解释。
- 适合 BM25、Vector、Wiki 多路召回融合。

Rerank：
- 排序效果可能更好。
- 但成本更高、延迟更高、复杂度更高。
- 当前如果未实现，必须明确写“当前暂未实现”。
- 面试中要说明：当前阶段先用 RRF 平衡效果和复杂度，后续在高价值场景引入 rerank。

5. 同步处理 vs 异步处理

同步处理：
- 实现简单。
- 链路短。
- 但大文件解析、Embedding、索引会导致接口超时。
- 失败后难恢复。

异步处理：
- 上传接口快速返回。
- 后台处理长耗时任务。
- 支持状态追踪、重试、幂等、失败排查。
- 工程复杂度更高。

NoteWeave 选择异步，是因为文档处理和索引构建天然耗时，适合 Task / Outbox / Kafka / Worker。

6. Artifact 自动进入 Wiki vs 人工确认后进入 Wiki

自动进入：
- 流程简单。
- 用户操作少。
- 但模型生成内容可能有偏差，会污染长期知识库。

人工确认后进入：
- 多一步操作。
- 但保证长期知识质量。
- 体现可信 AI 和知识治理意识。

NoteWeave 当前选择人工确认后进入 Wiki。

- 文档是否讲清 NoteWeave 为什么不是普通笔记应用。
- 是否讲清 RAG、Wiki、Artifact、Citation 的关系。
- 是否能回答“这项目有什么亮点”。
- 是否能回答“这不就是套 RAG 吗”。

第 2 轮：整体架构设计

重点检查：

- 文档是否讲清前端、后端、MySQL、Redis、MinIO、Kafka、Elasticsearch、LLM 的职责。
- 是否讲清为什么这么拆。
- 是否讲清当前架构的优缺点。
- 是否讲清后续如何演进。

第 3 轮：为什么不用 grep / LIKE

重点检查：

- 文档是否讲清 grep、LIKE、BM25 的区别。
- 是否能体现“不是盲目上 ES，而是有方案取舍”。
- 是否能回答“为什么不用更简单的方案”。

第 4 轮：BM25、向量检索与 Hybrid Retrieval

重点检查：

- 文档是否讲清 BM25 和向量检索分别适合什么。
- 是否讲清为什么两者互补。
- 是否讲清向量失败时如何降级。
- 是否能回答“只用 BM25 或只用向量有什么问题”。

第 5 轮：Weighted RRF、Rerank 与排序融合

重点检查：

- 文档是否讲清为什么不同检索器 score 不能直接相加。
- 是否讲清 Weighted RRF 的直觉和公式。
- 是否讲清为什么当前阶段先用 RRF。
- 是否讲清 rerank 为什么暂未实现、什么时候适合引入。

第 6 轮：文档上传、解析、Chunk、索引链路

重点检查：

- 文档是否讲清上传到可检索的完整链路。
- 是否讲清同步处理和异步处理的取舍。
- 是否讲清 Task / Outbox / Kafka / Worker。
- 是否讲清如果上传后检索不到，如何排查。

第 7 轮：Chunk 与 Evidence Context

重点检查：

- 文档是否讲清为什么要 Chunk。
- 是否讲清不同 Chunk 策略的优缺点。
- 是否讲清相邻 Chunk 合并和同文档限流。
- 是否讲清如果答案缺上下文，如何定位是否是 Chunk 问题。

第 8 轮：Citation / Evidence 回溯

重点检查：

- 文档是否讲清为什么 RAG 必须有 Citation。
- 是否讲清 Citation 为什么结构化存储。
- 是否讲清引用漂移、快照、sourceVersion。
- 是否讲清如果引用错了怎么排查。

第 9 轮：Wiki 与 Artifact 知识沉淀

重点检查：

- 文档是否讲清 Wiki 和 Document 的区别。
- 是否讲清 Artifact 为什么不能自动进入 Wiki。
- 是否讲清人工确认的价值。
- 是否讲清 WikiRetriever 为什么可以更高权重。
- 是否讲清 Wiki 发布后检索不到怎么排查。

第 10 轮：权限隔离、安全与越权检索

重点检查：

- 文档是否讲清 Space 权限模型。
- 是否讲清检索阶段必须做权限过滤。
- 是否讲清为什么不能先全局召回再过滤。
- 是否讲清 Citation 返回前二次校验。
- 是否讲清如果发生越权，应该如何定位。

第 11 轮：RAG 评测、问题排查与项目优势表达

重点检查：

- 文档是否讲清 RAG 效果差如何排查。
- 是否讲清 RetrievalTrace、LLMCallLog、RAG Eval。
- 是否能体现工程排障能力。
- 是否能自然表达项目亮点和个人优势。

第 12 轮及以后：继续查漏补缺

继续围绕以下方向检查文档是否能回答：

- query rewrite 是否需要。
- rerank 什么时候引入。
- Memory 和 RAG 的边界。
- Wiki 和 Graph 的关系。
- 向量维度变化怎么处理。
- ES index alias 怎么演进。
- Prompt 注入风险。
- 删除文档后索引怎么清理。
- Citation 漂移怎么避免。
- 多租户索引隔离怎么做。
- 成本和延迟如何控制。
- 生产环境如何扩展。
- 简历上如何写得有亮点但不夸大。

十六、最终质量标准

最终文档要让候选人能自然说出类似下面的回答：

“NoteWeave 不是简单套一个 RAG，而是围绕知识从资料进入系统、被检索引用、生成成果、再沉淀为长期知识这个闭环来设计的。比如检索这里，我对比过 grep、LIKE、BM25、向量检索、Hybrid Retrieval 和 Rerank。grep 和 LIKE 适合早期 baseline 或调试，但不适合作为团队知识库的核心检索；BM25 适合关键词、术语和技术文档；向量检索适合语义相似；所以当前选择 BM25 + Vector，再用 Weighted RRF 融合。这个选择不是为了堆技术，而是在效果、复杂度、可解释性和工程落地之间做平衡。

如果 RAG 回答不准，我不会第一反应就换模型，而是会先看文档有没有成功索引，再看 Chunk 是否合理、BM25 和向量分别召回了什么、RRF 融合后 Evidence 是否足够、Prompt 是否约束清楚，最后再看模型问题。这个项目里我想体现的是 RAG 工程链路里的检索质量、证据可信、权限隔离、问题排查和可演进设计。”

你的文档升级目标，就是让用户能达到这种面试表达效果。
