# 分块与入库

## 总体思路

WeKnora 的分块不是固定长度硬切，而是结合标题层级、段落结构、启发式标记和上下文 breadcrumb 做自适应切分。这样做的原因很简单：企业文档不是纯文本，章节、列表、代码块、表格、图片说明都承载着不同语义。

## 为什么不用纯固定 chunk size

固定切块实现简单，但会把标题、上下文和论证链切散。对于面试资料、技术方案、规范文档，这种切散会直接伤害召回质量。WeKnora 选择保留结构信息，是为了让 chunk 本身带着“它来自哪里”的语义。

## 设计 tradeoff

- **更大 chunk**：上下文更完整，但召回粒度差。
- **更小 chunk**：更容易命中，但信息碎片化。
- **带 breadcrumb**：增加 embedding 负担，但显著改善语义定位。
- **先切后修**：实现简单；**先修后切**：质量更高但工程更重。

## 入库流程

1. 解析原文，原文可能来自上传文件、同步数据或 Wiki 草稿。
2. 按结构生成 chunk。
3. 为 chunk 补 breadcrumb 和元数据。
4. 写入 chunk 存储和向量索引。
5. 记录来源、页码、章节、图片引用、上传路径和解析状态等证据字段。

## 对 Noteweave 的可复用点

- 面试复盘文档很适合结构感知切分。
- 概念卡、项目卡、决策记录也应该带 breadcrumb。
- 先做分块预览，再做批量入库，能少踩很多坑。
- 如果原始资料来自图片、PDF 或聊天附件，先确保它们已经通过对象存储和解析链路稳定下来，再谈分块。

## 面试追问

### 1. 为什么标题层级比固定 token 更重要？

因为标题层级决定了文档的语义边界。固定 token 只是在切长度，不理解“这段是在定义、这段是在举例、这段是在下结论”。对于技术文档和复盘文档，丢掉标题层级就等于丢掉逻辑结构。

### 2. breadcrumb 会不会让 chunk 变长、变脏？

会增加一点长度，但这是可接受的 tradeoff。breadcrumb 的作用不是堆字数，而是给 chunk 提供上位语境。面试官如果追问，可以直接说：在企业知识里，语境往往比原始片段还重要。

### 3. 什么场景下不适合过度切分？

定义性文档、长表格、配置说明、流程图说明都不适合切太碎。过度切分会让检索命中后上下文不完整，模型只能猜。对这类内容，宁可稍大一点 chunk，也要保留完整论证链。

### 4. 为什么先做分块预览很重要？

因为分块策略一旦错了，后面所有索引、召回和答案都会跟着错。预览能让你在入库前看到切片边界、标题是否保留、图片是否丢失、上下文是否完整，比事后调检索参数高效得多。
