# 召回与排序

## 总体思路

WeKnora 的检索是 Hybrid：关键词召回负责“精确命中”，向量召回负责“语义命中”，权限过滤负责“能不能看”，排序融合负责“把最该看的排前面”。

## 为什么要做多后端抽象

这是 WeKnora 很值得学的地方。它不是绑定某个向量库，而是把检索能力抽象成统一接口，这样才能同时支持本地部署、私有云、不同厂商和不同成本模型。

## 关键 tradeoff

- **BM25 + 向量**：比单一向量稳定，但实现复杂度更高。
- **多后端统一接口**：迁移容易，但要维护适配层。
- **高召回**：答案更全；**高精度**：结果更干净。
- **检索前过滤**：更安全；**检索后过滤**：实现更简单但容易泄露候选上下文。

## 排序策略的设计理由

WeKnora 的思路不是“找最多”，而是“找最有证据价值的”。这也是为什么它把关键词、语义和权限一起考虑，而不是把 embedding 当唯一答案来源。

## 对 Noteweave 的建议

Noteweave 也应该保留统一检索接口。哪怕早期只接一个后端，也要把：

- 数据过滤
- 关键词召回
- 向量召回
- 融合排序
- 证据字段
这些职责拆开。

## 面试追问

### 1. 为什么 BM25 还没过时？

因为很多企业问题本质上是关键词问题，不是纯语义问题。比如错误码、配置项、表名、类名、文档标题，这些都更依赖词项匹配。BM25 对这类问题很稳，和向量结合后能补足彼此短板。

### 2. 多后端统一接口的最大收益是什么？

不是“写起来酷”，而是迁移成本低。企业知识系统会遇到成本变化、供应商变化、私有化要求变化。统一接口能把上层业务和后端存储解耦，避免每换一个后端就重写业务逻辑。

### 3. 为什么权限过滤不能放在检索之后？

因为检索之后再过滤，候选内容已经进入上下文了，等于先看再说不能看，这在敏感知识场景里不安全。过滤应该在检索阶段就参与范围裁剪。

### 4. 如果检索结果很多，怎么判断是召回问题还是排序问题？

先看召回范围是否覆盖了正确证据，再看前几条排序是否把正确答案压下去了。召回缺失说明索引、chunk 或过滤有问题；召回有但排不上去，才是排序或融合策略的问题。
