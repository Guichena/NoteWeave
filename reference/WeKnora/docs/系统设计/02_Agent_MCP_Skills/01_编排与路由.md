# 编排与路由

## 总体思路

WeKnora 的 Agent 编排核心在于：把“用户想干什么”变成“系统该走哪条链路”。这比直接问模型答案更重要。

## 关键模块

- `internal/application/service/agent_service.go`
  - `CreateAgentEngine()`
  - `resolveKBAndDocInfos()`
  - `ValidateConfig()`
  - `getKnowledgeBaseInfos()`
  - `getSelectedDocumentInfos()`
- `internal/application/service/chat_pipeline/chat_pipeline.go`
  - `EventManager`
  - `Register()`
  - `Trigger()`
- `internal/handler/custom_agent.go`
  - `CreateAgent()`
  - `UpdateAgent()`
  - `CopyAgent()`

## 路由为什么重要

如果所有请求都走同一个提示词，系统很快会出现边界混乱：检索范围不清、工具调用失控、输出风格混杂、权限范围被稀释。WeKnora 通过显式路由把这些问题前置处理。

## tradeoff

- **强路由**：更可控，但配置成本高。
- **弱路由**：更灵活，但容易把错问题送到错链路。
- **按 KB 路由**：更清晰，但跨库问题需要额外处理。

## 对 Noteweave 的建议

把用户任务分成几类：

1. 找资料
2. 研究整理
3. 生成草稿
4. 复盘总结
5. 结构化沉淀

每类任务都应该有自己的路由与上下文模板。

## 面试追问

### 1. 路由为什么要放在 Agent 前面？

因为路由决定后面整条链路怎么走。先路由再执行，才能控制检索范围、工具选择和输出格式。如果把所有请求都交给模型自由发挥，系统会越来越像一个不可预测的黑盒。

### 2. 路由是规则好还是模型好？

不是二选一。明确、高频、稳定的路径适合规则；模糊、开放、长尾的问题适合语义相似度或小模型兜底。WeKnora 的思路是组合式路由，而不是单一策略。

### 3. 如何处理跨 KB 问题？

跨 KB 问题要么先做项目识别再聚合范围，要么在路由层就显式允许跨库查询，但要保留结果出处。不能让模型自己“顺手搜全库”，那样权限和证据都会失控。

### 4. 为什么事件编排重要？

因为 Agent 不是单次函数调用，而是一串状态变化。事件化之后，才能把检索、工具调用、生成、失败和恢复都放到统一的可观测链路里。
