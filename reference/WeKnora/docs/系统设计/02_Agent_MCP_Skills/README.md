# Agent / MCP / Skills

这一部分讲 WeKnora 如何把模型能力、工具调用和任务边界放在一起管理。核心不是“让模型自己想”，而是“让模型在可控边界内做多步推理”。

## 为什么要拆这层

WeKnora 不是只有 RAG。复杂任务往往需要：

- 先判断意图
- 再决定要不要检索
- 再决定检索范围
- 再决定是否调用外部工具
- 再决定是否生成 Wiki 或草稿

这就是 Agent 层存在的原因。

## 关键 tradeoff

- **纯 RAG**：简单，但复杂任务能力不足。
- **完全自治 Agent**：灵活，但风险高、难审计。
- **Skill-based Agent**：更稳，但前期要设计技能边界。

## 对 Noteweave 的启发

Noteweave 的研究、复盘、写作、摘要、面试准备都适合做成“可配置 Agent + 可复用 Skills”，而不是每次都临时拼提示词。

## 面试追问

### 1. 为什么 Agent 不直接做成一个大 Prompt？

因为大 Prompt 只能表达“会说什么”，很难表达“什么时候检索、检索什么、用什么工具、失败时怎么退回”。拆成路由、技能和工具之后，链路才可控、可测、可审计。Agent 的价值不只是生成文本，而是把思考和行动交替起来：先判断、再行动、再观察结果、再继续推理。

### 2. 为什么 Skills 比模板更适合长期维护？

模板是文本拼接，Skills 是能力单元。面试官如果追问“知识如何复用”，你可以回答：Skills 能版本化、按需加载、配脚本和资源，适合重复执行的任务；模板只能解决一次性表达。

### 3. MCP 为什么值得保留？

因为它把外部工具标准化了。对 Noteweave 这种想长期接网页抓取、网盘、代码仓库、PDF 服务的项目来说，协议层标准化会大幅降低后续扩展成本。工具协议统一后，Agent 层只需要理解“有哪些工具、参数是什么、结果怎么读”，不用为每个服务写一套特殊逻辑。

### 4. 如果工具调用失败，系统怎么办？

分层兜底：意图回退、检索回退、工具回退、生成回退。一个成熟系统不应该因为某个工具失败就整体崩掉，而应该返回可解释的降级结果。
