# Wiki 知识编织

## 总体思路

WeKnora 的 Wiki 不是把文档简单转成网页，而是把原始文档编织成可链接、可维护、可检索、可修复的知识网络。
这里的“原始文档”通常不是纯手写 Markdown，而是来自上传文件、同步资料、RAG 结果和 Agent 生成草稿的混合输入。Wiki 层负责把这些碎片沉淀成稳定页面，并用 MySQL + 任务表维护它们的生命周期。

## 链路

1. 资料进入知识库
2. Agent 或规则抽取摘要、概念和关系
3. 生成 Wiki 页面
4. 建立页面间链接和图谱
5. 定期 lint、修复、重建链接

页面写入不是一次性动作，而是“创建 / 更新 / 反链修复 / 索引重建 / 问题记录”这一整条链。这个链条里，MySQL 负责持久化，队列表负责异步编排，关系图负责导航。

## 设计 tradeoff

- **自动生成**：效率高，但容易有噪声。
- **人工维护**：质量高，但成本高。
- **自动生成 + 人工修正**：最符合企业知识资产生命周期。
- **同步写页面**：简单，但容易阻塞；**任务化修复**：更稳，但要处理队列与重试。

## 对 Noteweave 的启发

Noteweave 的价值不只是保存笔记，而是把零散内容组织成主题页、项目页、概念页和关系页。
如果 Noteweave 想做成面试可讲的项目，就不能只保留“笔记列表”，还要有页面、链接、重命名、反链修复、索引页和问题列表这些长期维护能力。
如果素材来自上传文件或截图，先看 [文件上传与对象存储](../11_文件上传与对象存储/README.md)；如果页面重建、修复和同步依赖后台编排，再看 [Redis / MQ / MySQL 任务编排](../12_Redis_MQ_MySQL任务编排/README.md)。

## 面试追问

### 1. Wiki 和知识图谱的关系是什么？

Wiki 负责内容组织和阅读路径，图谱负责关系表达和结构发现。前者适合让人看懂，后者适合让系统推理。成熟的知识系统通常不会只保留一个层：页面承载“可读知识”，图谱承载“对象关系”，二者共同构成可维护知识网络。

### 2. 为什么要支持 auto-fix？

因为知识页会随着资料增长而失真。自动修复不是锦上添花，而是长期维护机制。面试官如果追问“维护成本怎么控制”，auto-fix 就是一个很好的回答点。

### 3. 为什么不是所有内容都直接转成页面？

因为不是所有片段都值得成为知识页。WeKnora 的思路是把高价值、可复用、关系明确的内容沉淀成页面，低价值重复片段留在检索层即可。知识图谱和 Wiki 的目标不是“把所有东西都结构化”，而是让跨文档、跨概念、跨主题的知识更容易被发现和复用。

### 4. 图谱如果抽错了怎么办？

不把图谱当唯一真相。先保留证据链，再允许人工修正，再通过 lint 和 re-build 慢慢修复。图谱应该是可修正的知识层，而不是一次性抽取结果。

### 5. Wiki 为什么不能只靠前端拼 Markdown？

因为真正的 Wiki 需要版本、来源、反链、重命名、问题记录和重建机制。前端拼出来的 Markdown 只能展示内容，不能维护知识关系；一旦页面被引用、被重命名、被修复，后端必须有完整的持久化和队列能力来兜住这些变化。
