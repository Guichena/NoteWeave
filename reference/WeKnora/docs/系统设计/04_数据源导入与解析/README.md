# 数据源导入与解析

## 总体思路

WeKnora 的知识入口不只来自手工上传，也来自外部平台同步。为了支撑多来源知识，系统把“连接器、同步、解析、清洗、入库”拆成独立层。

## 关键 tradeoff

- **手工导入**：简单，但扩展性有限。
- **自动同步**：体验好，但需要游标、凭证和冲突策略。
- **本地解析**：可控；**远端解析**：省资源但依赖外部服务。

## 对 Noteweave 的启发

Noteweave 如果要做长期知识工作台，导入链路必须先于智能链路稳定，否则上层所有总结和编织都会建立在脏数据上。
如果输入里大量是上传文件、截图和附件，先看 [文件上传与对象存储](../11_文件上传与对象存储/README.md)；如果后面要做批量同步、重试和后台修复，再看 [Redis / MQ / MySQL 任务编排](../12_Redis_MQ_MySQL任务编排/README.md)。

## 面试追问

### 1. 为什么要把导入和解析分开？

因为导入解决“从哪来”，解析解决“变成什么”。外部平台接入、文件格式处理、图片提取和正文结构识别是不同问题，混在一起会让系统越来越难维护。

### 2. 为什么同步必须可暂停、可恢复？

因为企业数据源常常很大、权限经常变、API 也会波动。可暂停和可恢复意味着同步链路不是一次性任务，而是可运维流程。同步系统要像消息流一样处理状态：谁处理了、是否确认、失败后能不能重试、是否会重复入库，这些比“能不能拉一次数据”更重要。

### 3. 解析引擎为什么要可插拔？

因为本地、云端、gRPC、HTTP 都有各自的成本和部署条件。可插拔让系统在不同环境下仍能保持同一个上层接口。
