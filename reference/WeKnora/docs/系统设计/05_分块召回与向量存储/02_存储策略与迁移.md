# 存储策略与迁移

## 总体思路

WeKnora 不仅要把索引存起来，还要知道“存多少、迁到哪、如何复制、如何估算代价”。这使得检索后端不只是运行时依赖，也是可运维资产。

## 关键能力

- `EstimateStorageSize()`
- `CopyIndices()`
- `DeleteByChunkIDList()`
- `DeleteByKnowledgeIDList()`
- `BatchUpdateChunkEnabledStatus()`

不同实现里，这些能力分别出现在 ES、SQLite、Milvus、Qdrant、Weaviate、Doris、Tencent VectorDB 等后端。

## 为什么值得学

这类能力解决的是工程真实问题：知识库会增长、后端会替换、索引会重建、数据会迁移。没有这些能力，系统很快只能停留在 demo。

## tradeoff

- **复制索引**：快，但需要保证 ID 映射正确。
- **重建索引**：更稳，但成本高。
- **容量估算**：增加一层复杂度，但能避免资源爆掉。

## 面试追问

### 1. 为什么不直接重建所有索引？

因为重建成本高、耗时长，而且会影响可用性。复制索引能在很多场景下减少重复计算，尤其是多知识库迁移和环境切换。

### 2. 为什么要估算空间？

因为知识系统的成本会随着文档规模和向量维度快速增长。面试官如果问“怎么避免资源打爆”，容量估算就是非常直接的回答。

### 3. 删除和更新为什么是索引层职责？

因为索引本身就是数据资产的一部分，不是单纯查询缓存。删除和更新如果只靠业务层补丁，很容易和检索后端状态不一致。
