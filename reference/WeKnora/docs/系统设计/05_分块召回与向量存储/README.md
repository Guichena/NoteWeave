# 分块召回与向量存储

## 总体思路

这一模块关注的是“索引怎么存、存到哪里、如何迁移、如何估算成本、如何把 chunk 变成真正可检索的数据结构”。它是 RAG 的底座，但又比 RAG 更偏基础设施。

## 关键设计

WeKnora 不把向量库当成单一依赖，而是把它抽象成统一的检索引擎接口。这样一来，系统既能支持本地轻量部署，也能支持企业级私有云和多厂商存储后端。

## tradeoff

- **单一后端**：实现快，但迁移难。
- **统一抽象**：扩展强，但适配层多。
- **向量专用**：效率高，但全文检索和过滤要补。
- **Hybrid Store**：更全，但更复杂。

## 对 Noteweave 的建议

Noteweave 如果想长期演进，底层索引必须支持可插拔，不然一旦用户数据增大或部署环境变化，整个产品都要重构。

## 面试追问

### 1. 为什么底层索引一定要抽象？

因为检索引擎往往比业务层更容易变。今天用一个后端，明天换另一个；如果不抽象，业务代码会被后端细节绑死。

### 2. 为什么向量库不是越强越好？

因为强不等于适合。企业知识里关键词过滤、成本、延迟、权限和迁移同样重要。向量库只是底座，不是产品本身。

### 3. 面试官如果问你“以后怎么迁移”，怎么答？

答：通过统一接口、索引复制和容量估算来迁移，而不是把迁移当一次性脚本。系统设计要承认后端会变化，所以要先设计演进路径。
