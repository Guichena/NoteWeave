# 会话与流式输出

## 总体思路

WeKnora 把一次问答当成会话的一部分，而不是孤立请求。这样才能支持连续对话、中断、恢复、置顶、清空和多轮上下文继承。

## tradeoff

- **短请求**：实现简单，但体验断裂。
- **长会话**：体验好，但要管理状态和上下文。
- **流式输出**：实时感更强，但控制链路更复杂。

## 对 Noteweave 的建议

研究和写作场景特别依赖“继续写”“补充一段”“回到上一个主题”。因此会话设计要先于功能设计。
如果会话里还要接图片、附件或语音上传，那就要继续看 [文件上传与对象存储](../11_文件上传与对象存储/README.md)，因为会话只是承接入口，真正的解析和回流在上传模块里完成。

## 面试追问

### 1. 为什么会话比一次性请求更重要？

因为真实工作流是连续的。研究、复盘、写作和排障都不是“一问一答”，而是会多轮修正、补上下文、切换主题。会话承载的是任务连续性。

### 2. 为什么流式输出要和中断恢复一起设计？

因为只有流式没有恢复，体验会断；只有恢复没有流式，体验又慢。两个能力一起做，才是可用的交互链路。会话流本质上要处理“事件持续产生、用户可能中断、系统需要记录进度”的问题，所以它需要状态、确认和恢复机制，而不是简单把 token 往前端推。

### 3. 如果用户切换话题怎么办？

会话层要允许状态切换、置顶和清空。不要把上一轮上下文默认塞给下一轮，否则模型会把话题混在一起。
