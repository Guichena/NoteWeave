# 权限 / RBAC / 共享

## 总体思路

WeKnora 的权限设计不是单纯的“登录后能不能看”，而是围绕租户、组织、知识库、chunk、agent 和共享资源建立完整的访问边界。它真正要解决的不是身份认证，而是“某个主体在某个上下文里能否访问某个资源、以什么方式访问、访问后要留下什么痕迹”。

## 关键模块

- `internal/middleware/rbac.go`
- `internal/middleware/kb_access.go`
- `internal/application/repository/kbshare.go`
- `internal/application/repository/agent_share.go`
- `internal/handler/rbac_lookups.go`
- `docs/wiki/安全认证/RBAC说明.md`
- `docs/wiki/安全认证/共享空间说明.md`

## 关键实现

- `RequireRole(min, cfg)`：做租户角色门禁，适合“这个操作至少要 Contributor / Admin”这类判断。
- `RequireOwnershipOrRole(min, lookup, cfg)`：先看角色，再看资源所有权，适合知识库、Agent 这类“本人可改、管理员也可改”的场景。
- `KBAccessFromContext()`、`KBIDFromParam()`、`KBIDFromKnowledgeIDParam()`、`KBIDFromChunkIDParam()`：把路由参数翻译成资源访问上下文。
- `resolveKBAccessOnce()`、`resolveSharedAgentAccess()`：把共享关系和资源归属合并成一次可判定的访问结果。
- `kbshare.go`、`agent_share.go`：把“共享关系”从业务对象里拆出来，避免权限逻辑散落在各个 handler。
- `ErrResourceNotFound`：刻意区分“资源不存在”与“权限不足”，避免把 404 伪装成 403。

## 为什么这样设计

知识平台的共享不是复制一份文档，而是把资源以受控方式开放给其他主体。这样才能兼顾协作和边界。

更细一点说，权限体系要同时满足三个目标：

1. 资源边界要清楚，不能跨租户串读。
2. 协作要足够灵活，不能把每次共享都做成复制。
3. 失败语义要准确，404、403、503 不能混在一起，否则排障和审计都会被误导。

## tradeoff

- **强隔离**：安全，但共享成本高。
- **弱隔离**：协作方便，但容易越权。
- **资源级共享**：最符合企业知识协作的真实需求。
- **显式共享表**：比隐式继承复杂一点，但便于撤销、审计和追踪。
- **资源所有权 + 角色双判定**：比纯 RBAC 重一点，但更贴近真实协作。

## 常见失败模式

- 只做角色判断，不做资源判断，最后把别人的 KB、chunk 或 Agent 也放行了。
- 把“资源不存在”直接当成 403，导致前端误判成权限问题。
- 共享关系写进业务对象后，后续撤销和审计都很难做。
- 只看 RBAC 不看审计，最后出了问题却说不清谁改了什么。

## 面试追问

### 1. 为什么 RBAC 还不够？

因为 RBAC 只能表达角色，不能表达资源边界。知识系统里“谁能看哪份知识、哪类 chunk、哪个 agent”都很细，所以还需要资源级权限和共享关系。身份认证只解决“你是谁”，授权还要继续回答“你能访问哪个资源、能做什么动作”。

### 2. 为什么共享必须可撤销？

因为知识是会更新的，协作关系也会变化。共享如果不可撤销，系统就很难维护边界和版本一致性。

### 3. 为什么审计日志是权限系统的一部分？

因为权限不是只关心“放不放行”，还关心“谁做了什么”。在企业知识平台里，审计是权限闭环的重要组成。

### 4. 为什么要把 404 和 403 分开？

因为它们回答的是两个完全不同的问题。404 是“资源是否存在”，403 是“你有没有资格访问这个资源”。如果把两者混成一个结果，调用方就无法区分是路由写错了、资源被删了，还是权限不够。

### 5. 为什么共享关系要单独建表？

因为共享关系本身就是一种生命周期对象，它需要新增、撤销、查看和审计。把它单独建模以后，后续无论是临时共享、跨租户授权，还是按资源粒度追踪访问历史，都能保持一致的处理方式。
