# 存储解析与后端适配

## 总体思路

WeKnora 把解析引擎、向量库、对象存储、Web Search 都做成可配置后端。这样同一套上层逻辑可以跑在不同部署环境里。这里的关键不是“能连上”，而是“换后端后上层语义不变、错误语义不乱、迁移语义可控”。

## 关键模块

- `internal/infrastructure/docparser/engine_registry.go`
- `internal/infrastructure/web_search/registry.go`
- `internal/handler/vectorstore.go`
- `internal/handler/web_search_provider.go`
- `docs/wiki/集成扩展/集成向量数据库.md`
- `docs/wiki/集成扩展/添加网络搜索引擎.md`

## 关键实现

- `vectorStoreService.CreateStore()` / `UpdateStore()` / `DeleteStore()`：负责向量库生命周期。
- `ResolveStoreView()` / `BatchResolveStoreView()` / `EnvDefaultStoreView()`：把“环境默认值”和“租户视图”分开处理。
- `registerInRegistry()` / `validateConnectionConfig()` / `SaveDetectedVersion()`：负责把配置接到运行时注册表，并记录后端版本。
- `NewTencentVectorDBRetrieveEngineRepository()`：把后端实现封装成统一的检索仓库。
- `EstimateStorageSize()` / `CopyIndices()` / `Retrieve()` / `VectorRetrieve()` / `KeywordsRetrieve()`：分别覆盖容量评估、索引迁移和两种召回路径。
- `BatchUpdateChunkEnabledStatus()` / `BatchUpdateChunkTagID()`：支持索引批量维护和元数据回写。

## tradeoff

- **统一抽象**：易扩展。
- **多适配器**：实现成本更高。
- **配置驱动**：运维灵活，但要做好默认值和校验。
- **先注册再使用**：比直接 new 对象多一层，但更适合插件化后端。
- **显式连接校验**：前置成本高一点，但减少运行时故障。

## 常见失败模式

- 后端类型切换了，但旧索引没有复制或重建。
- 只维护连接配置，不维护版本信息，迁移后无法判断兼容性。
- 默认视图与租户视图混在一起，导致一个环境配置影响多个租户。
- 后端抽象层只覆盖写入，不覆盖检索和删除，最后链路不完整。

## 面试追问

### 1. 为什么后端适配不能散落在业务逻辑里？

因为那样一旦换后端，业务逻辑就会被污染。适配层的职责就是把变化隔离掉。

### 2. 为什么 Web Search 也要做成 provider？

因为搜索源本身也会变化。标准化 provider 能让系统随时替换不同搜索服务，而不改 Agent 层。

### 3. 为什么解析器和存储引擎要用相似的设计方式？

因为它们本质上都在做“后端能力抽象”。一个负责把源文件变成可读内容，一个负责把可检索内容落到不同存储里，抽象方式应保持一致。

### 4. 为什么要记录后端版本？

因为迁移不是只看“能不能连上”，还要看“数据格式是否兼容”。版本信息能帮助系统判断旧索引是不是还能复用，还是必须重建。

### 5. 为什么要先估算容量再迁移？

因为迁移本质上是资源重新分配。如果不先估算规模，迁移过程可能把存储、网络和索引重建时间都拖爆，最后影响线上可用性。
