# 模型配置与多后端适配

## 总体思路

WeKnora 的一个重要设计是把模型、解析器、存储、检索都做成可配置可替换。系统不假设某一家模型服务或某一个后端永远可用。

## 关键实现

- `internal/handler/initialization.go`：统一承接 KB 初始化、模型校验、下载和多模态测试。
- `UpdateKBConfig()` / `InitializeByKB()`：把模型配置和知识库生命周期绑定。
- `CheckOllamaStatus()` / `CheckOllamaModels()` / `DownloadOllamaModel()` / `GetDownloadProgress()`：处理本地模型可用性与下载任务。
- `CheckRemoteModel()` / `TestEmbeddingModel()` / `CheckRerankModel()` / `CheckASRModel()` / `TestMultimodalFunction()`：把模型能力验证前置到配置阶段。
- `internal/application/service/vectorstore.go` + `internal/handler/vectorstore.go`：管理向量库实例、视图、测试和注册。
- `internal/infrastructure/docparser/engine_registry.go`、`internal/infrastructure/web_search/registry.go`：把解析器和搜索源都做成注册式后端。

## 设计原则

1. **配置必须可验证**：不能只写配置，不校验可用性。
2. **能力必须可分型**：chat、embedding、rerank、ASR、VLM 各有职责。
3. **后端必须可替换**：本地、云端、私有化、混合部署都要能落。
4. **失败必须可诊断**：连接错误、下载失败、能力不足要区分开。

## tradeoff

- **内置默认值**：易用，但灵活性差。
- **显式配置**：更灵活，但配置成本更高。
- **多后端抽象**：演进能力强，但需要更多适配层。
- **初始化即测试**：前期步骤更多，但能减少“装好了却不能用”的故障。
- **模型按能力拆分**：配置更细，但排障和替换更清楚。

## 常见失败模式

- 只保存配置，不验证连通性，导致知识库初始化后才发现模型不可用。
- 把不同模型能力塞进一类配置，后续无法单独替换。
- 下载任务没有状态机，前端只能看到卡住。
- 后端切换时不做版本记录，迁移后很难判断旧索引是否还能兼容。

## 面试追问

### 1. 为什么模型配置要和 KB 初始化放在一起？

因为知识库能不能工作，依赖模型是否可用。把模型测试和 KB 初始化绑定，能减少“库建好了但不能问”的情况。

### 2. 为什么要支持 embedding、rerank、chat、ASR 等多种模型类型？

因为它们承担的是不同职责。混在一个配置里，后面排障和调优会很混乱。

### 3. 为什么要保留多后端适配？

因为企业部署环境变化大。今天是本地，明天是私有云，后天可能换厂商。可替换是架构的生存能力。

### 4. 为什么初始化要先校验再落库？

因为配置错误是高频故障源。先校验能把“写错参数”尽早暴露出来，避免把错误配置带进后续的检索、问答和同步链路。

### 5. 为什么模型能力要按类型拆开而不是统一成一个大配置？

因为不同能力的失败语义不同。chat 失败、embedding 失败、rerank 失败、ASR 失败，排查路径完全不一样。拆开以后，系统才知道该去看哪一层、该给用户什么反馈。
