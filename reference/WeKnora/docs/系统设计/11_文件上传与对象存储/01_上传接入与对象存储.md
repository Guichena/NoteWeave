# 上传接入与对象存储

## 总体思路

WeKnora 的上传链路先做安全校验，再做存储选择，最后才生成可访问 URL。这里最重要的是把“上传动作”和“访问动作”解耦：用户上传的是原始数据，系统返回的是经过租户命名和后端适配后的稳定资源标识。

## 关键实现

- `FileService` 接口：`CheckConnectivity()`、`SaveFile()`、`SaveBytes()`、`GetFile()`、`GetFileURL()`、`DeleteFile()`
- `NewFileServiceFromStorageConfig()`：按租户 storage 配置选择后端
- `saveImageAttachments()`：图片上传入口，限制数量和大小
- `resolveImageFileService()`：按租户动态选择图片存储后端
- `parseQARequest()`：处理聊天请求中的图片和附件入口

## 为什么这样设计

对象存储不是可选项，而是知识系统的原件仓库。图片、附件、文档切片和多模态中间产物都需要一个统一的落点，这样后续的解析、索引和回放才有依据。

### 关键细节

- `SaveBytes()` 适合聊天图片、OCR 中间产物、解析缓存和临时文件。
- `SaveFile()` 适合浏览器上传的原始文件。
- `GetFileURL()` 负责把内部存储路径转成可访问地址。
- `DeleteFile()` 负责清理无效或过期资源。
- `CheckConnectivity()` 让系统在初始化时先发现存储问题，而不是等到用户上传时才爆。

## 存储后端选择

`NewFileServiceFromStorageConfig()` 会先看租户级配置，再看默认 provider，最后决定用 local、MinIO、COS、TOS、S3、OBS、OSS 或 KS3。

这个设计的意义是：

1. 开发环境可以本地落盘。
2. 生产环境可以切对象存储。
3. 不同租户可以用不同后端。
4. 上层业务不用关心具体协议。

## tradeoff

- **本地盘**：最轻，但不适合多实例。
- **对象存储**：更稳，但要处理签名和可访问性。
- **租户独立后端**：最灵活，但运维复杂度更高。
- **统一 file service**：上层更干净，但适配器更多。

## 常见失败模式

- 用客户端上传的 URL 直接去抓图，导致 SSRF。
- 文件名没做安全化，出现路径穿越。
- 忽略 `CheckConnectivity()`，等到高峰期才发现存储不可用。
- 只有保存没有删除，垃圾文件越堆越多。

## 面试追问

### 1. 为什么 `FileService` 要抽成接口？

因为文件后端会变。接口能把存储差异收口，上层只关心保存、读取、删除和 URL 生成。

### 2. 为什么图片上传要限制数量和大小？

因为图片会直接进入后续多模态模型链路。没有限制，上传接口会被当成低成本攻击入口，也会把模型上下文和对象存储成本打穿。

### 3. 为什么要给每个租户单独命名空间？

因为租户是最基本的边界。路径里带租户语义，才能在下载、审计、清理和迁移时维持边界一致。

### 4. 为什么不能把存储 provider 的选择写死？

因为企业环境差异很大。写死会让本地开发、私有化部署和多云部署都很难维护。

### 5. 为什么服务端必须重新生成文件名？

因为原始文件名不可控，可能重复、可能非法、可能带路径符号。重新生成能统一命名、避免冲突，也方便后续清理。
