# 附件解析与多模态回流

## 总体思路

文件上传只是第一步。WeKnora 更关键的做法，是把附件解析成可以进入检索和 Wiki 的文本证据：文本附件要抽正文，音频要做 ASR，图片和文档里的嵌入图片要重新保存并重写链接，最后再把这些内容回流成 chunk 或知识页。

## 关键实现

- `AttachmentProcessor.ProcessAttachment()`：附件处理主入口
- `processTextFile()`：逐行读取文本，支持截断
- `processAudioFile()`：基于 ASR 做音频转写
- `processWithDocParser()`：处理简单格式
- `processWithDocumentReader()`：处理复杂格式
- `ImageResolver.ResolveAndStore()`：解析并重写文档中的图片引用
- `ImageMultimodalService.Handle()`：图片 OCR / caption / 子 chunk 回流
- `indexChunks()`、`checkAndFinalizeAllImages()`：把多模态结果推进检索链路

## 解析策略

1. 纯文本先走快速行读，避免不必要的重型解析。
2. 音频只在配置了 ASR 时转写，否则保留占位信息。
3. 简单格式交给轻量 reader，复杂格式交给 DocumentReader。
4. 文档中的图片、HTML data URI、相对路径图片统一转存。
5. 多模态输出生成子 chunk，再进入索引。

## 为什么这样设计

附件不是“附属信息”，而是知识本体的一部分。很多面试材料、项目复盘、流程文档和截图，真正有价值的部分就在附件里。WeKnora 把附件解析成可搜索文本，是为了让上传动作直接变成知识沉淀动作。

### 关键细节

- `ProcessAttachment()` 会先校验文件名和类型，再保存文件，再抽取内容。
- 文本文件会按行读取并在必要时截断，避免超长附件把上下文撑爆。
- 图片会通过 `ImageResolver` 重写到对象存储，避免原始引用失效。
- `ImageMultimodalService` 会为 OCR 和 caption 生成子 chunk，保证多模态结果可检索。

## tradeoff

- **只存原文件**：实现简单，但不利于检索。
- **边传边解析**：体验好，但主链路更重。
- **先存后解析**：更稳，但链路更长。
- **文本优先**：成本低，但会损失图片和版面信息。
- **全量多模态**：信息最全，但成本和延迟更高。

## 常见失败模式

- 不做文件类型校验，导致任意二进制都进来。
- 不做大小限制，附件把接口和模型上下文一起拖慢。
- 图片引用不重写，后续原始链接失效后页面就断了。
- OCR / caption 有结果但不入库，最后等于白做。

## 面试追问

### 1. 为什么附件处理不能只做存储？

因为知识系统需要的是可检索内容，不是冰冷文件。没有解析，附件就只是占空间的二进制；有了解析，它才变成可搜索、可总结、可编织的知识素材。

### 2. 为什么音频要走 ASR？

因为很多资料是口述、录音或会议纪要。音频不转写，知识就被锁在媒体里，后面的 RAG 和 Wiki 都用不上。

### 3. 为什么图片要单独生成子 chunk？

因为图片里的文本和语义经常和正文不同步。把 OCR 和 caption 变成子 chunk，检索时才能单独命中图像信息。

### 4. 为什么要在解析时重写图片引用？

因为原文里的图片可能是临时 URL、远程链接或者相对路径。重写到对象存储以后，知识页和 chunk 才有稳定的依赖。

### 5. 为什么解析失败时不能直接丢弃附件？

因为失败本身也是状态。保留原始文件和错误信息，后续才能重放、重试和排障。
