# 文件上传与对象存储

## 总体思路

WeKnora 把文件上传看成知识系统的前置入口，而不是单独的附件功能。图片、PDF、音频、Markdown、网页剪藏和聊天中的 base64 片段，最终都要落到一个稳定的存储后端，再被解析、切分、索引、编织成知识。

这条链路的关键不是“能不能传上去”，而是“上传后能不能被稳定复用、能不能被解析、能不能被追溯、能不能跨 RAG 和 Wiki 复用”。

## 关键实现

- `internal/types/interfaces/file.go`：`FileService` 的统一接口。
- `internal/application/service/file/factory.go`：按租户配置构建不同存储后端。
- `internal/handler/session/qa.go`：QA 请求里的图片和附件入口。
- `internal/handler/session/image_upload.go`：图片上传、限额、租户存储选择。
- `internal/handler/session/attachment_processor.go`：附件保存、解析和内容抽取。
- `internal/infrastructure/docparser/image_resolver.go`：把文档中的嵌入图片保存到统一存储。
- `internal/application/service/image_multimodal.go`：图片 OCR / caption / 子 chunk 回流。

## 设计原则

1. **对象存储是事实源**：上传后的文件必须有稳定 URL 和可回收路径。
2. **租户隔离前置**：文件路径、命名和下载权限都要带租户语义。
3. **解析与上传解耦**：先保存，再解析；失败时原件不能丢。
4. **上传结果可复用**：同一份素材应该能服务聊天、RAG、Wiki 和多模态任务。

## tradeoff

- **本地存储**：部署简单，但跨实例共享弱。
- **对象存储**：更适合生产，但要处理签名、权限和成本。
- **同步解析**：用户等待时间短，但会拖慢主请求。
- **异步回流**：主链路更稳，但状态管理更复杂。

## 常见失败模式

- 上传后直接把客户端 URL 当成可信 URL，留下 SSRF 风险。
- 只保存原文件，不保存可追溯 URL，后续解析和回放都做不起来。
- 图片和附件的大小、格式、数量不设限，最后把模型上下文拖爆。
- 不区分临时文件和正式文件，清理和回收很难做。

## 面试追问

### 1. 为什么文件上传要放进系统设计，而不是产品细节？

因为它决定了知识素材是否能被稳定保存、复用和追溯。对于 RAG 和 Wiki 来说，上传入口其实就是知识入口。

### 2. 为什么不能直接把上传内容塞进数据库？

数据库适合保存结构化状态，不适合承接大文件和高频下载。对象存储更适合保存原件，数据库只保留索引、元信息和状态。

### 3. 为什么文件上传必须支持多后端？

因为私有化、云化、本地开发、单机 demo 的约束完全不同。文件服务抽象能把这些差异收口，上层不需要知道底层是 local、MinIO 还是云厂商对象存储。

### 4. 为什么图片上传要由服务端补 URL？

因为客户端给的 URL 不能信。服务端生成 URL，才能统一路径命名、权限控制和审计。

### 5. 为什么上传和解析要分开？

上传解决“先存住”，解析解决“再理解”。只做上传，知识还没进入可检索状态；只做解析，没有稳定原件，后续重建和审计都会出问题。
