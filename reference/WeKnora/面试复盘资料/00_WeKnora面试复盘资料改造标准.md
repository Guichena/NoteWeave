# WeKnora 面试复盘资料回答风格与 QA 改造标准

这份标准只解决一件事：把 `面试复盘资料` 写成可以直接拿去讲的面试回答，而不是资料索引、知识点清单或源码目录。

后续所有文档都要围绕“面试官问什么、我第一句话怎么答、怎么结合 WeKnora 展开、最后怎么自然复述”来写。目录、源码锚点、边界提醒可以出现在回答里，但不能喧宾夺主。

---

## 1. 总原则：先像人一样回答，再展开技术

每个问题都按下面顺序组织：

1. **先判断面试官真正想考什么。**
2. **第一句话先给结论，不要绕。**
3. **再用 WeKnora 的真实链路承接。**
4. **然后解释技术原理、取舍和边界。**
5. **最后给一段可直接复述的自然语言答案。**

最重要的一句话：

> 先答结论，再讲链路；先讲项目，再讲八股；先讲事实，再讲演进；最后一定落成一段能说出口的话。

不合格写法：

- “WeKnora 用了 RAG、Agent、Wiki、Redis、Postgres、向量库。”
- “上传后解析、切块、Embedding、入库。”
- “Redis 很快，因为基于内存。”
- “向量库就是 TopK 检索。”

合格写法：

> 我不会把 WeKnora 讲成一个简单的 Chatbot，它的核心是把企业分散文档变成可检索、可问答、可沉淀、可治理的知识资产。离线侧，文档上传后会经过存储、解析、分块、Embedding 和索引构建；在线侧，问题会经过权限过滤、混合召回、rerank、上下文拼装和大模型生成。RAG 解决即时问答，Agent 解决多步工具任务，Wiki 解决长期知识组织，所以这个项目的复杂度主要在知识进入、知识被查、知识被沉淀和知识被管住这四件事上。

---

## 2. 标准 QA 格式

普通面试文档统一使用这个格式：

```md
### Q1：问题

#### 面试官为什么问

说明这个问题背后考察什么能力，不要复述题目。

#### 先给结论

用 1 到 3 句话直接回答。这里要像面试开口第一句，而不是列提纲。

#### 回答思路

列出回答顺序，通常是 3 到 5 点。它是给自己看的提纲。

#### 结合我的项目怎么答

落到 WeKnora 的链路、组件和业务场景。这里要讲“怎么流转、为什么这样拆、失败时怎么办”。

#### 技术原理 / 链路设计讲解

解释背后的原理、取舍和工程价值。八股知识要放到项目场景里讲。

#### 技术栈特点与选型理由

可选。只有当问题涉及组件选型、替代方案或中间件时才写。

#### 可直接复述的面试回答

必须是一段完整自然语言，尽量 150 到 300 字。不要只列点，不要写成论文。

#### 常见追问

列 2 到 4 个面试官可能继续问的问题。

#### 常见坑

提醒哪些话不能说满，哪些表述容易显得不懂。
```

如果是八股加强版，可以用更轻的格式：

```md
## N. 八股知识点：主题

### N.1 是什么

### N.2 为什么 / 原理

### N.3 和 WeKnora 怎么结合

### N.4 常见追问

### N.5 可直接复述的面试回答

### N.6 常见坑
```

## 3. “可直接复述的面试回答”写法

这一段是整篇资料最重要的部分。它要像面试现场自然说出来的话。

### 好答案必须包含四层

1. **结论句**：先回答这个问题是什么。
2. **项目句**：落到 WeKnora 的哪条链路。
3. **原理句**：说明为什么这么做。
4. **边界句**：说明不能说满或需要演进的地方。

模板：

> 这个问题我会先从 `{结论}` 讲起。在 WeKnora 里，`{项目链路}`。这样设计的原因是 `{技术原因和工程价值}`。但这里不能简单说成 `{容易说满的话}`，因为 `{边界/风险}`，所以更准确的表达是 `{稳妥结论}`。

示例：

> 文档入库我不会把它理解成一个上传接口，而是一条异步数据管道。在 WeKnora 里，上传成功只表示原文件和元数据被系统接收，真正可问答还要经过 docreader 解析、chunk 分块、Embedding、向量/关键词索引构建以及状态更新。这样拆是因为解析和模型调用都可能很慢，也可能失败，如果同步阻塞上传接口，用户体验和系统稳定性都会变差。但这里不能说成强一致事务，因为 DB、对象存储、向量库和模型调用跨了多个系统，更准确的说法是通过状态机、幂等处理和失败补偿做到最终一致。

## 4. 回答风格要求

### 要像面试回答，不要像课堂笔记

推荐表达：

- “我会先把它拆成两条链路来看。”
- “这个问题表面在问组件，实际在问异步任务的可靠性。”
- “在 WeKnora 里，这个点落在文档入库和 Wiki ingest 两类任务上。”
- “这里我不会说它完全强一致，只能说通过幂等和补偿降低脏数据风险。”

避免表达：

- “定义如下。”
- “优点有一二三四五。”
- “源码位置包括……”
- “该组件提供了若干能力。”

### 每个回答都要有主语

不要只写名词，要写谁对谁做了什么。

差：

> Redis、Asynq、docreader、向量库、Postgres。

好：

> API 层只负责接收文件和记录状态，真正耗时的解析、分块和向量化交给 Asynq worker；worker 调 docreader 拿到解析结果后，再写 chunk 和索引。

### 八股必须回到项目

差：

> Redis 使用单线程和 I/O 多路复用，所以性能高。

好：

> Redis 的低延迟适合放在 WeKnora 的任务队列、短期流式事件和分布式锁场景里。但文档、chunk、权限这些长期事实源不能放 Redis，因为它不适合复杂查询和长期一致性管理。

## 5. WeKnora 各主题回答主线

### 项目介绍

回答主线：

> 企业知识分散 -> 文档入库 -> RAG 问答 -> Agent 工具任务 -> Wiki 沉淀 -> 多租户治理。

不要只背 RAG、Agent、Wiki 名词，要说它们分别解决什么场景。

### 文档入库

回答主线：

> 上传成功不等于可问答；入库是异步数据管道；核心是解析、分块、Embedding、索引、状态和补偿。

重点回答状态流转、幂等、失败恢复和一致性边界。

### 在线 RAG

回答主线：

> query -> 权限范围 -> 混合召回 -> rerank -> 上下文拼装 -> LLM 流式回答。

不要把 RAG 说成 TopK，要讲 chunk、召回、排序、上下文和评测。

### Agent / MCP

回答主线：

> RAG 解决明确问答，Agent 解决多步任务；MCP 接入外部工具，但必须有权限、审批、超时和结果归纳。

不要说 Agent 自动万能，要讲工具不可信和人工审核边界。

### Wiki

回答主线：

> RAG 是查询时增强，Wiki 是入库后沉淀；重点是页面生成、链接、图谱、引用、批处理和一致性。

不要把 Wiki 说成摘要功能。

### 中间件

回答主线：

> 按负载选组件：Postgres 管事实源，对象存储管大文件，Redis/Asynq 管后台任务，docreader 管解析，向量库管召回，Langfuse 管质量观测。

不要把中间件堆砌当成亮点，要说每个组件解决什么问题以及引入什么成本。

## 6. 现有资料改造要求

本目录现有资料按下面方向改：

1. 删除每篇开头额外的“本篇定位 / 当前仓库事实锚点 / 面试表达边界”资料说明。
2. 统一 QA 小标题：
   - `详细回答`、`结合项目的详细回答` 统一改成 `结合我的项目怎么答`。
   - `面试中可以直接说出口的版本` 统一改成 `可直接复述的面试回答`。
   - `回答中的常见坑` 统一改成 `常见坑`。
3. 每个 Q 的主体优先保留这几个部分：`面试官为什么问`、`回答思路`、`结合我的项目怎么答`、`技术原理 / 链路设计讲解`、`可直接复述的面试回答`、`常见追问`、`常见坑`。
4. 八股加强版可以保留“是什么 / 原理 / 项目结合 / 可直接复述”的结构，但必须每个知识点都落回 WeKnora。
5. “可直接复述的面试回答”必须是完整段落，不能只列项目符号。
