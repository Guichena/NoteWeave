## 3. 问答与讲解

### Q1：请你介绍一下 WeKnora 这个项目

#### 面试官为什么问

这是开场问题，但不是让你念 README。面试官想看你能否把项目讲成“业务目标 -> 技术方案 -> 核心链路 -> 你的贡献 -> 结果”的结构。

#### 先给结论

WeKnora 是一个面向企业文档理解和知识问答的 RAG/Agent 框架。

#### 回答思路

1. 先讲业务场景：企业文档分散，搜索不到、问答不准、知识难维护。
2. 再讲核心能力：文档入库、RAG 问答、Agent 多步推理、Wiki 自动沉淀、IM/多端接入。
3. 然后讲架构：Go 应用服务、Python 文档解析服务、异步任务队列、向量/关键词检索、LLM/Rerank/Embedding 模型、对象存储。
4. 最后讲你的职责和量化结果。这里需要你补充真实指标。

#### 结合我的项目怎么答

可以说：WeKnora 是一个企业级知识管理和智能问答框架。用户可以把 PDF、Word、图片、Excel、网页、第三方知识源等内容导入系统，系统会进行文档解析、分块、Embedding、索引构建，然后在问答时通过混合检索、重排和大模型生成答案。项目还提供 Agent 模式，支持 MCP 工具、web search 和多轮推理；Wiki 模式则会把原始文档进一步沉淀成结构化 Markdown 页面和知识图谱。

从仓库看，项目不是单一问答 Demo，而是包含完整工程闭环：`internal/application/service` 承载业务服务，`internal/application/service/chat_pipeline` 负责问答流水线，`docreader` 是 Python 文档解析服务，`router/task.go` 里通过 Asynq 注册异步任务，`internal/application/service/retriever` 抽象多种检索引擎，`frontend` 是 Vue 3 + Vite 前端，`docker-compose.yml` 支持 app、frontend、docreader、Redis、Postgres、向量库、Neo4j 等部署。

#### 技术原理 / 链路设计讲解

项目的基本闭环是：

```text
用户上传文档
-> 后端校验文件类型、配额、重复文件、存储配置
-> 保存原文件到对象存储或本地存储
-> 写入 knowledge 记录，状态为 pending/disabled
-> 投递 document:process 异步任务
-> docreader 解析文档
-> chunker 分块，必要时生成 parent-child chunk
-> 调用 embedding 模型向量化
-> 写入 DB chunk 表和向量/关键词索引
-> 问答时执行 query understand、混合检索、Graph 检索、rerank、merge、LLM 流式生成
```

这个链路体现了 RAG 系统的关键工程点：离线入库和在线问答分离；解析、分块、向量化是离线重计算任务；在线链路要压缩延迟，重点做召回、排序、上下文构造和流式返回。

#### 技术栈特点与选型理由

- Go + Gin：适合构建高并发 API 服务，部署简单，性能稳定。
- Python docreader：文档解析生态更丰富，适合处理 PDF、Office、图片 OCR、网页抽取。
- Asynq + Redis：适合异步文档处理、摘要、问题生成、Wiki 入库等耗时任务。
- Postgres/SQLite + GORM：承载业务元数据和轻量部署。
- 多向量库适配：支持 pgvector、Elasticsearch、Qdrant、Milvus、Weaviate、Doris、Tencent VectorDB 等，降低厂商锁定。
- Langfuse/OpenTelemetry：用于追踪 LLM、Embedding、Rerank、异步任务等调用链。

#### 可直接复述的面试回答

WeKnora 是一个面向企业文档理解和知识问答的 RAG/Agent 框架。它解决的问题不是简单聊天，而是把企业里分散的 PDF、Word、网页、飞书、Notion、语雀等知识源沉淀成可检索、可问答、可推理的知识资产。整体链路上，用户上传文档后，后端会做文件校验、去重、存储和异步入库，docreader 负责解析文档，chunker 负责分块，随后调用 Embedding 模型写入向量和关键词索引。在线问答时，系统会做 query 理解、混合检索、图谱检索、rerank、上下文拼装，再用大模型流式生成答案。项目还支持 Agent 通过 MCP、web search 和内置工具处理复杂任务，Wiki 模式会把文档沉淀成结构化知识页面。我的理解是，这个项目的核心价值在于把大模型能力工程化地嵌入企业知识管理，而不是做一个简单模型调用壳。

### Q2：为什么这个项目需要 RAG、Agent 和 Wiki 三种形态？

#### 面试官为什么问

面试官想看你是否理解产品功能背后的技术边界。很多候选人会把 RAG、Agent、知识图谱、Wiki 混在一起讲，实际这些能力适合的场景不同。

#### 先给结论

这三个能力解决的是不同层次的问题。RAG 解决的是“我有一个明确问题，去知识库里找依据并回答”；Agent 解决的是“这个问题可能需要多步推理、搜索、调用工具，甚至先查 A 再查 B”；Wiki 解决的是“原始文档太散，应该沉淀成结构化、可维护、可链接的知识体系”。

#### 回答思路

1. RAG 适合短链路问答：问题明确，答案来自已有知识。
2. Agent 适合多步任务：需要规划、工具调用、web search、跨知识源综合。
3. Wiki 适合知识沉淀：把非结构化文档变成可维护的结构化页面。
4. 三者不是替代关系，而是从“查询”到“推理”再到“沉淀”的递进。

#### 结合我的项目怎么答

项目中普通知识问答走 `session_knowledge_qa.go` 里的 chat pipeline；Agent 模式则会引入自定义 Agent、MCP 服务、工具调用和多轮推理；Wiki 入库在 `wiki_ingest.go` 中独立成异步任务，使用 pending ops、批处理、Redis 锁和 dead-letter 来保障规模化处理。

#### 技术原理 / 链路设计讲解

RAG 的核心是检索增强生成：先召回，再生成。它的优势是可控、成本低、延迟相对可控；缺点是无法自动拆解复杂任务，也不会主动维护知识结构。

Agent 的核心是“推理循环 + 工具调用”：模型根据任务决定下一步调用知识库、web search、MCP 工具或其他工具，再根据观察结果继续推理。它适合复杂任务，但成本、延迟和稳定性都更难控制。

Wiki 模式则是知识工程化沉淀：不是问一次答一次，而是把文档抽取成页面、链接和图谱。它的价值在于后续查询可以直接利用结构化知识，而不是每次从原始文档重新理解。

#### 技术栈特点与选型理由

RAG 链路要求检索性能和召回质量，所以项目支持向量、关键词、GraphRAG、rerank、MMR。Agent 链路要求可扩展工具能力，所以引入 MCP。Wiki 链路是长耗时生成任务，所以用 Asynq + pending ops + dead-letter 做可靠异步化。

#### 可直接复述的面试回答

这三个能力解决的是不同层次的问题。RAG 解决的是“我有一个明确问题，去知识库里找依据并回答”；Agent 解决的是“这个问题可能需要多步推理、搜索、调用工具，甚至先查 A 再查 B”；Wiki 解决的是“原始文档太散，应该沉淀成结构化、可维护、可链接的知识体系”。所以它们不是重复建设，而是查询、推理和沉淀三个层次。WeKnora 里普通问答走 RAG pipeline，复杂任务走 Agent/MCP，文档体系化沉淀走 Wiki 异步入库。

#### 常见追问

- Agent 比 RAG 成本高，什么时候不应该用 Agent？
- Wiki 自动生成会不会产生幻觉？
- 如果只能保留一个能力，你保留哪个？

#### 常见坑

不要说“Agent 更高级所以都用 Agent”。真实系统里，普通问答优先用 RAG，因为可控、快、便宜；Agent 应该用于复杂任务，不适合作为所有请求的默认入口。

### Q3：这个项目最核心的技术难点是什么？

#### 面试官为什么问

大厂面试希望看到你对复杂系统的判断力。一个真实项目的难点通常不是“调用模型 API”，而是数据质量、异步一致性、检索效果、权限隔离、成本和可观测性。

#### 先给结论

我认为这个项目最大的难点不在于调用大模型，而在于把非结构化知识稳定地变成可检索、可推理、可维护的资产。

#### 回答思路

可以从四类难点回答：

1. 数据入库难：文档格式复杂，解析质量不稳定，分块策略影响召回。
2. 检索效果难：向量检索、关键词检索、rerank、阈值和上下文窗口需要权衡。
3. 工程稳定性难：文档处理耗时长，必须异步、可重试、可排障。
4. 企业级能力难：多租户权限、数据隔离、私有化部署、敏感凭据加密。

#### 结合我的项目怎么答

WeKnora 里比较有代表性的难点包括：

- `knowledge_create.go` 做文件类型、重复文件、配额、存储、多模态配置校验。
- `knowledge_process.go` 在处理 chunks 前会删除旧 chunks、旧索引和图谱数据，体现了重入和幂等处理。
- `chat_pipeline` 中在线链路包括 query understand、parallel search、rerank、merge、filter、stream completion。
- `wiki_ingest.go` 为 Wiki 使用 pending ops、Redis active lock、tombstone、dead-letter，说明 Wiki 不是一次性任务，而是要处理并发、重试和删除一致性。
- `rbac.go` 里区分角色权限和资源 owner 权限，说明项目考虑了多人协作场景。

#### 技术原理 / 链路设计讲解

RAG 项目的质量问题通常来自“误差传递”。解析错了，分块再好也没用；分块太碎，召回没有上下文；分块太大，Embedding 表达不精确；召回 TopK 太少会漏，太多会污染；rerank 阈值太高会无结果，太低会引入噪音；上下文太长会增加成本并挤压有效信息。

工程上还存在最终一致性问题：上传接口返回时，文档可能只是 pending，并未完成解析和索引。因此系统必须通过状态机、异步任务、重试、幂等清理、dead-letter 和前端状态展示来管理用户预期。

#### 技术栈特点与选型理由

项目选择 Asynq 处理后台任务，是因为文档入库、摘要、问题生成、Wiki 生成都属于耗时任务；选择多检索引擎抽象，是为了适配不同私有化客户的基础设施；选择 Langfuse 和 trace，是为了能把模型调用、检索、重排、异步任务串起来排障。

#### 可直接复述的面试回答

我认为这个项目最大的难点不在于调用大模型，而在于把非结构化知识稳定地变成可检索、可推理、可维护的资产。比如上传一个 PDF 后，系统要保证解析、分块、Embedding、索引、摘要、Wiki 生成等异步环节都能失败可重试、重复执行不产生脏数据；在线问答还要在低延迟下兼顾召回率和准确率。WeKnora 里通过文档状态、Asynq 任务、幂等清理、多路检索、rerank、Langfuse trace 和 RBAC 来解决这些工程问题。
