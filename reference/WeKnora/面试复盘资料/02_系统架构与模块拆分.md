# 文件：02_系统架构与模块拆分.md

## 1. 本主题面试官想考什么

这个主题主要考察系统设计能力：你是否理解为什么项目拆成 Go 主服务、Python docreader、前端、异步 worker、检索引擎、存储、模型 provider 等模块；这些模块之间怎么通信；哪些地方是可插拔的；为什么不是简单堆代码。

基于仓库可确认的信息：后端使用 Go、Gin、GORM、dig 依赖注入；文档解析由 `docreader` Python 服务承担；前端使用 Vue 3 + Vite + TDesign；任务使用 Asynq + Redis；部署支持 Docker Compose、Helm、Lite、桌面端 Wails、CLI、小程序和 IM 适配。  
需要你补充的信息：你是否参与架构设计、是否做过模块拆分、是否处理过某个模块的线上瓶颈。

## 3. 问答与讲解

### Q1：请描述一下项目整体架构

#### 面试官为什么问

面试官想判断你是否能从系统视角理解项目，而不是只盯着一个接口。好的回答要能把核心组件、调用关系、数据流和部署形态讲清楚。

#### 先给结论

WeKnora 的架构可以看成一个模块化知识平台。

#### 回答思路

1. 先按层次讲：接入层、应用层、异步任务层、模型层、存储/检索层、观测层。
2. 再讲核心链路：文档入库链路和在线问答链路。
3. 最后讲可扩展点：模型、向量库、对象存储、数据源、IM、MCP。

#### 结合我的项目怎么答

项目主要由这些模块组成：

- `frontend`：Vue 3 + Vite 前端，通过 Nginx 代理后端，支持知识库管理、问答、Wiki、配置等。
- `cmd/server` + `internal/router`：Go API 服务入口，基于 Gin 注册 HTTP 路由和中间件。
- `internal/handler`：API 入参出参和 HTTP 适配。
- `internal/application/service`：核心业务逻辑，比如知识库、文档、会话、Wiki、模型、RBAC。
- `internal/application/repository`：数据库访问与检索仓储。
- `docreader`：Python 文档解析服务，处理 PDF、Office、网页、图片等格式。
- `router/task.go`：Asynq worker 注册入口，处理 document:process、faq:import、wiki:ingest、summary:generation 等任务。
- `internal/application/service/chat_pipeline`：在线问答流水线。
- `internal/application/service/retriever`：检索引擎抽象，适配 Postgres、Elasticsearch、Qdrant、Milvus、Weaviate、Doris 等。
- `internal/tracing/langfuse`：LLM/Embedding/Rerank/异步任务追踪。

#### 技术原理 / 链路设计讲解

整体架构可以抽象成：

```text
Web/CLI/IM/小程序/桌面端
        |
      Gin API
        |
Handler -> Service -> Repository
        |        |        |
        |        |        +-- DB / vector store / object storage
        |        +-- Model provider / docreader / MCP / web search
        |
      Asynq tasks
        |
document process / summary / wiki / FAQ import / datasource sync
```

这个架构的关键是同步接口和异步任务分离。用户上传文件时，接口只做必要校验、保存和入队，不在 HTTP 请求里完成解析和索引。在线问答则走独立 pipeline，保证请求延迟可控。

#### 技术栈特点与选型理由

Go 主服务适合作为高并发 API 和编排层；Python 适合处理文档解析生态；Vue 适合复杂后台管理 UI；Asynq 适合可靠后台任务；多检索引擎抽象适合私有化客户的异构基础设施。

#### 可直接复述的面试回答

WeKnora 的架构可以看成一个模块化知识平台。接入层包括 Web、CLI、IM、小程序等；后端是 Go + Gin，按 router、handler、service、repository 分层；文档解析单独由 Python docreader 承担；耗时任务通过 Asynq 和 Redis 异步处理；元数据存在数据库里，原文件走对象存储，索引写入可插拔的向量库或关键词检索引擎。在线问答则走 chat pipeline，把 query 理解、混合检索、图谱检索、rerank、上下文拼装和流式生成串起来。这样的设计让不同客户可以替换模型、向量库、存储和部署方式。

#### 常见追问

- 哪些模块是强依赖，哪些模块可以裁剪？
- 异步 worker 和 API 服务是同进程还是独立部署？
- 如果要做水平扩展，哪个模块最先扩？

#### 常见坑

不要只罗列组件名。面试官更关心组件之间为什么这样拆，以及拆分后带来的通信、状态和故障处理问题。

### Q2：为什么文档解析要拆成 Python docreader 服务？

#### 面试官为什么问

这是典型架构取舍问题。面试官想看你是否理解技术生态、隔离、性能和故障边界。

#### 先给结论

我理解 docreader 拆成 Python 服务主要是因为文档解析本身非常复杂，而且 Python 生态更成熟。

#### 回答思路

1. 文档解析格式复杂，Python 生态更成熟。
2. 解析依赖重，和主服务解耦可以降低 Go 服务复杂度。
3. 解析服务可能需要 OCR、Playwright、PDF/Office 库，独立容器更易部署。
4. 代价是多一次 RPC、部署多一个组件、故障链路变长。

#### 结合我的项目怎么答

`docreader/pyproject.toml` 中包含 `markitdown`、`pypdf`、`pypdfium2`、`python-docx`、`trafilatura`、`playwright`、`grpcio` 等依赖，说明它承担多格式解析、网页抽取、PDF/Office 处理等任务。主服务通过 `DOCREADER_ADDR` 和 gRPC 访问它。

#### 技术原理 / 链路设计讲解

文档解析具有几个特点：

- 输入不可控：PDF 扫描件、乱码、表格、图片、复杂 Word、网页。
- CPU/IO 密集：解析可能占用大量内存和 CPU。
- 依赖复杂：很多解析库不是纯 Go 生态强项。
- 失败率高：单个坏文件不应该拖垮主 API 服务。

因此拆成独立服务后，可以单独扩容、单独重启、单独限制资源。主服务只关心“给我结构化文本、图片、OCR、chunk 信息”，不用关心具体解析细节。

#### 技术栈特点与选型理由

Python 在文档解析、OCR、网页抽取方面生态强；Go 在 API、并发、任务编排方面强。这个项目采用“两种语言各做擅长的事”的方式，而不是强行统一技术栈。

#### 可直接复述的面试回答

我理解 docreader 拆成 Python 服务主要是因为文档解析本身非常复杂，而且 Python 生态更成熟。像 PDF、Office、网页抽取、图片 OCR 这类能力依赖比较重，如果都塞到 Go 主服务里，会增加构建和运行复杂度。拆成独立服务后，主服务只通过 gRPC 获取解析结果，解析服务可以单独部署、扩容、重启和限制资源。当然代价是多了一跳 RPC 和一个组件的运维成本，所以需要健康检查、超时和任务失败处理来兜底。

#### 常见追问

- 如果 docreader 超时，任务怎么处理？
- gRPC 和 HTTP 比有什么优势？
- docreader 是否应该做成无状态？

#### 常见坑

不要只说“Python 方便”。要讲清楚故障隔离、依赖隔离、资源隔离和扩展性。

### Q3：这个项目是单体还是微服务？为什么？

#### 面试官为什么问

面试官在考察架构判断力。很多候选人会下意识认为微服务更高级，但大厂面试更看重是否按复杂度和团队规模做合理取舍。

#### 先给结论

我不会把 WeKnora 简单定义成微服务。

#### 回答思路

1. 它不是传统大单体，也不是完全微服务。
2. Go 主服务是模块化单体，内部按领域分层。
3. 对依赖重、资源特征不同的能力拆独立服务，比如 docreader、sandbox、向量库、Neo4j。
4. 这样兼顾开发效率和部署灵活性。

#### 结合我的项目怎么答

从代码看，核心业务逻辑集中在 Go 主服务内部，按 handler/service/repository/module 分层；但文档解析、前端、向量库、Redis、Postgres、Neo4j、Langfuse、sandbox 等是独立组件。可以称为“模块化单体 + 外部基础设施组件 + 少量专业服务拆分”。

#### 技术原理 / 链路设计讲解

完全微服务会带来服务发现、链路追踪、跨服务事务、版本兼容、部署编排等复杂度。对于一个企业知识库平台，早期核心复杂度在数据链路和效果优化，不一定要把知识库、会话、模型、用户、RBAC 都拆成服务。模块化单体可以保持代码内聚，事务边界清晰，开发调试效率高。

但 docreader 这类模块具有不同的语言生态和资源特征，拆出去是合理的。向量库、对象存储、Redis、Neo4j 也是天然基础设施组件。

#### 技术栈特点与选型理由

Go 的模块化单体能支撑较高吞吐；dig 依赖注入让内部模块可替换；Docker Compose/Helm 又让外部组件可组合部署。

#### 可直接复述的面试回答

我不会把 WeKnora 简单定义成微服务。它的核心业务更像模块化单体，Go 主服务内部按 handler、service、repository 分层，通过接口和依赖注入隔离模块；但对于文档解析、向量库、Redis、Postgres、Neo4j、sandbox 这类资源特征和技术生态不同的能力，会作为独立组件部署。这样做的好处是核心业务开发和事务处理更简单，同时又能把重依赖、可替换、需要单独扩容的部分拆出去。

#### 常见追问

- 如果团队变大，哪些模块最值得服务化？
- 模块化单体如何避免代码耦合？
- 分布式事务问题目前有没有？

#### 常见坑

不要为了显得高级硬说“全是微服务”。面试官会继续追问服务边界、调用协议、部署和事务，一旦答不上来会扣分。

## 4. 本主题总结

架构回答的关键是：主服务负责业务编排，docreader 负责重解析，Asynq 负责异步任务，retriever/model/storage 通过接口可插拔，前端和多端接入通过 API/SSE/IM 适配完成。不要只讲组件，要讲边界和取舍。
