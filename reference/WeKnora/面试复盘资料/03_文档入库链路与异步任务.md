# 文件：03_文档入库链路与异步任务.md

## 1. 本主题面试官想考什么

这个主题考察你对 RAG 离线索引链路的理解。真实 RAG 系统的难点往往在“入库质量”和“后台任务可靠性”：文件校验、去重、存储、解析、分块、Embedding、索引、状态机、重试、幂等、删除一致性。

基于仓库可确认的信息：文件上传入口在 `knowledge_create.go`，处理任务通过 Asynq 的 `document:process` 投递，文档处理在 `knowledge_process.go`，分块配置有 adaptive 3-tier chunking、parent-child chunking，多模态图片和音频分别涉及 VLM/ASR 配置。  
需要你补充的信息：你实际优化过的文档类型、解析失败率、平均入库耗时、单个知识库最大文档量。

## 3. 问答与讲解

### Q1：上传一个文档到可问答，中间完整链路是什么？

#### 面试官为什么问

这是 RAG 项目最核心的问题。面试官想看你是否理解离线索引链路，而不是只知道在线问答。

#### 先给结论

上传文档不是同步完成全部处理。接口层会先做知识库配置、文件类型、hash 去重、存储配额、文件名安全、多模态或 ASR 配置校验，然后创建一条 knowledge 记录，初始状态是 pending/disabled，把原文件保存到对象存储或本地存储，最后投递 document:process 异步任务。

#### 回答思路

按状态流转回答：

1. HTTP 上传，校验文件类型、大小、存储配置、多模态/ASR 配置。
2. 计算 hash，做去重和配额检查。
3. 创建 knowledge 记录，状态为 pending、disabled。
4. 保存原文件到存储。
5. 投递 `document:process` 异步任务。
6. worker 调用 docreader 解析。
7. chunker 分块，生成 chunk 记录。
8. 调用 Embedding，写入向量/关键词索引。
9. 触发摘要、问题生成、Wiki/Graph 等后处理。
10. 状态更新为 completed/enabled 或 failed。

#### 结合我的项目怎么答

`CreateKnowledgeFromFile` 中能看到：先获取知识库配置，拒绝 FAQ 知识库直接文件上传，检查存储配置；图片文件会校验对象存储和 VLM 配置，音频文件会校验 ASR 配置；然后校验文件类型、计算 hash、查重、检查租户存储配额、校验文件名安全性；创建 knowledge 记录后保存文件，再构造 `DocumentProcessPayload` 并投递 Asynq 任务。

`processChunks` 中能看到：处理前会清理旧 chunks、旧索引和旧图谱数据；创建 parent/child chunks；保存 chunks；再构造 indexInfo 调用 embedding 和 retrieve engine 批量索引。

#### 技术原理 / 链路设计讲解

RAG 入库链路本质是一个异步数据管道：

```text
raw file
-> parsed document
-> chunks
-> embedding vectors / keyword index
-> searchable knowledge
```

每一步都可能失败，而且失败的处理策略不同。文件保存失败可以直接返回错误；任务入队失败时，项目当前逻辑会记录错误并返回 knowledge，因为文件和 DB 记录已经创建，这里需要后续通过重试/人工触发修复。解析失败应该把 parse_status 标成 failed 并记录 error_message。重入处理时要先删除旧 chunk 和旧索引，避免重复数据。

#### 技术栈特点与选型理由

Asynq 负责异步任务、重试和队列优先级；docreader 负责多格式解析；chunker 负责自适应分块；retriever engine 负责把索引写入不同后端；Langfuse/OTel 用于串起 HTTP 和 worker trace。

#### 可直接复述的面试回答

上传文档不是同步完成全部处理。接口层会先做知识库配置、文件类型、hash 去重、存储配额、文件名安全、多模态或 ASR 配置校验，然后创建一条 knowledge 记录，初始状态是 pending/disabled，把原文件保存到对象存储或本地存储，最后投递 document:process 异步任务。worker 收到任务后调用 docreader 解析文档，再根据知识库的 chunking 配置分块，保存 chunk，调用 Embedding 模型生成向量，并写入配置好的向量和关键词索引。处理完成后再启用该知识；如果失败，会更新错误状态，方便前端展示和排障。

#### 常见追问

- 为什么创建 knowledge 记录后才保存文件？
- 任务入队失败怎么补偿？
- 重试时如何避免重复 chunk 和重复向量？

#### 常见坑

不要把“上传成功”和“可问答”混为一谈。上传接口成功只代表接收和入队成功，真正可问答要等后台索引完成。

### Q2：为什么文档处理必须异步？直接同步处理不行吗？

#### 面试官为什么问

面试官想看你对耗时任务、用户体验、资源隔离、重试机制的理解。

#### 先给结论

文档处理不能同步做，因为它包含解析、分块、Embedding、索引、摘要、问题生成等步骤，耗时不可控，而且依赖外部模型和向量库。

#### 回答思路

同步处理的问题：

- HTTP 请求容易超时。
- 大文件解析和 Embedding 可能耗时数十秒到数分钟。
- 模型 API 和向量库调用不稳定。
- 资源密集任务会拖垮 API 服务。
- 无法很好做重试、限流、优先级和 dead-letter。

#### 结合我的项目怎么答

项目通过 `router/task.go` 注册了多种任务：`document:process`、`faq:import`、`summary:generation`、`question:generation`、`image:multimodal`、`knowledge:post_process`、`datasource:sync`、`wiki:ingest` 等。队列分为 critical/default/low 权重，说明任务有优先级和后台处理需求。

#### 技术原理 / 链路设计讲解

异步化的核心是把“请求生命周期”和“业务处理生命周期”解耦。上传请求只负责提交任务，文档处理由 worker 消费。这样可以：

- 控制并发：worker 数量和队列权重限制后台压力。
- 自动重试：对 transient error 使用重试和退避。
- 失败沉淀：最终失败写 dead-letter，便于运维查询。
- 状态可见：前端轮询或订阅知识状态。
- 支持扩展：worker 可独立水平扩容。

#### 技术栈特点与选型理由

Asynq 基于 Redis，适合 Go 项目的后台任务处理。项目还加了 `asynqdl` middleware，在任务耗尽重试后写入 `task_dead_letters` 表，避免失败只存在 Redis inspector 里。

#### 可直接复述的面试回答

文档处理不能同步做，因为它包含解析、分块、Embedding、索引、摘要、问题生成等步骤，耗时不可控，而且依赖外部模型和向量库。如果放在 HTTP 请求里，用户很容易遇到超时，也会让 API 服务被大文件拖垮。WeKnora 用 Asynq 把这些步骤异步化，上传接口只完成校验、保存和入队；后台 worker 控制并发、重试和队列优先级。最终失败会进入 dead-letter 表，方便排障和补偿。

#### 常见追问

- 哪些错误应该重试，哪些不应该？
- Asynq 的任务幂等怎么做？
- 如果 Redis 不可用，上传接口应该怎么表现？

#### 常见坑

不要说“异步就是为了快”。异步不一定让单个任务更快，它主要提升系统可用性、吞吐和用户体验。

### Q3：分块策略怎么设计？为什么需要 parent-child chunking？

#### 面试官为什么问

分块是 RAG 效果的关键。面试官想看你是否理解 chunk size、overlap、结构化分块和上下文召回之间的关系。

#### 先给结论

分块会直接影响 RAG 的召回质量。WeKnora 不是简单按固定长度切，而是支持 auto 策略：Markdown 这类结构清晰的文档优先按标题切，并把标题路径作为上下文；PDF 这类文档会根据页码、章节号、分隔线等启发式信号切；没有明显结构时再退回递归分隔。

#### 回答思路

1. 解释分块影响召回和生成质量。
2. 讲自适应三层策略：heading、heuristic、recursive/legacy。
3. 讲 chunk size、overlap、token limit。
4. 讲 parent-child：小 chunk 负责精确召回，大 parent 负责提供上下文。

#### 结合我的项目怎么答

项目文档 `docs/CHUNKING.md` 提到 adaptive 3-tier chunking：`auto` 会根据文档结构信号选择 heading-aware、heuristic 或 legacy/recursive。heading 分块会把标题路径作为 `ContextHeader` 拼到 embedding 内容里。`processChunks` 中 parent chunks 会先进 DB，但不进入向量索引；child/flat chunks 才用于索引。

#### 技术原理 / 链路设计讲解

小 chunk 的好处是语义集中，Embedding 更精确；坏处是缺上下文。大 chunk 的好处是上下文完整；坏处是语义稀释，向量相似度可能不准。parent-child 策略把两者结合：用 child chunk 做召回，用 parent chunk 或相邻上下文给 LLM 更完整的材料。

overlap 的作用是避免答案跨 chunk 边界时丢失信息，但 overlap 太大会增加存储和索引成本，也可能引入重复上下文。

#### 技术栈特点与选型理由

WeKnora 把 chunking 做成知识库级配置，而不是全局固定参数，说明它考虑了不同文档类型：FAQ、Markdown 文档、PDF 报告、长文、表格数据的最佳分块策略不同。

#### 可直接复述的面试回答

分块会直接影响 RAG 的召回质量。WeKnora 不是简单按固定长度切，而是支持 auto 策略：Markdown 这类结构清晰的文档优先按标题切，并把标题路径作为上下文；PDF 这类文档会根据页码、章节号、分隔线等启发式信号切；没有明显结构时再退回递归分隔。parent-child chunking 的思路是用小的 child chunk 做向量召回，保证匹配精度，再把更大的 parent chunk 作为上下文交给 LLM，兼顾召回准确性和回答完整性。

#### 常见追问

- chunk size 选 512 的依据是什么？
- overlap 太大会有什么问题？
- 表格和代码文档怎么切？

#### 常见坑

不要说“分块越小越好”或“越大越好”。正确答案是不同文档类型和模型上下文窗口下需要取舍。

### Q4：如何保证重复执行任务不会产生脏数据？

#### 面试官为什么问

这是工程可靠性问题。异步任务一定会遇到重试、超时、重复投递和用户删除并发。

#### 先给结论

异步任务必须按幂等来设计。WeKnora 在上传阶段会用文件名、大小、hash 做重复文件检测；在文档处理阶段，真正重建 chunk 和索引前，会先删除该 knowledge 旧的 chunk、向量/关键词索引和图谱数据，再写入新的结果。

#### 回答思路

1. 创建阶段用文件 hash、文件名、大小去重。
2. 处理阶段先清理旧 chunk、旧索引、旧图谱。
3. 写入阶段使用 knowledge_id、chunk_id 作为稳定关联。
4. 处理前和写库前检查 knowledge 是否正在删除。
5. 失败状态写回，避免用户误以为可用。

#### 结合我的项目怎么答

`processChunks` 里明确先执行 `DeleteChunksByKnowledgeID`，再调用 retrieve engine 删除旧索引，还会调用 graph engine 删除旧图谱数据。代码里也有 `isKnowledgeDeleting` 检查，避免删除和处理并发时继续写入。

#### 技术原理 / 链路设计讲解

异步任务的幂等设计通常有三种方式：

- 去重键：同一文件、同一知识 ID、同一 pending op 使用唯一约束或查重逻辑。
- 覆盖式写入：重建前先删除旧数据，再写新数据。
- 状态机：pending、processing、completed、failed、deleting 等状态控制可见性。

WeKnora 的处理更接近“以 knowledge 为粒度重建索引”。只要重试能先清理旧数据，再写入新数据，就不会出现同一个 knowledge 下重复 chunk 或重复向量污染检索结果。

#### 技术栈特点与选型理由

这种设计牺牲了一些性能，因为重试时会删除并重建；但换来更简单的一致性模型，适合文档级索引重建。

#### 可直接复述的面试回答

异步任务必须按幂等来设计。WeKnora 在上传阶段会用文件名、大小、hash 做重复文件检测；在文档处理阶段，真正重建 chunk 和索引前，会先删除该 knowledge 旧的 chunk、向量/关键词索引和图谱数据，再写入新的结果。处理过程中还会检查知识是否正在删除，避免删除和重建并发导致脏写。这样即使任务被重试，也更像一次以 knowledge 为粒度的全量重建，而不是追加写。

#### 常见追问

- 如果删除旧索引失败，应该继续还是终止？
- 删除旧数据和写入新数据是否需要事务？
- 任务重试次数怎么设置？

#### 常见坑

不要轻易承诺“强一致”。跨 DB、向量库、对象存储、模型调用的链路通常只能做到最终一致和可补偿。

## 4. 本主题总结

文档入库回答要围绕“异步、状态、幂等、分块、索引、失败处理”展开。最好能画出从 upload 到 searchable 的状态流，并能说明为什么每一步可能失败以及怎么兜底。
