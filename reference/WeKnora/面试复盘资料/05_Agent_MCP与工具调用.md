# 文件：05_Agent_MCP与工具调用.md

## 1. 本主题面试官想考什么

这个主题考察你是否理解 Agent 不是“更长 Prompt”，而是一个包含规划、工具选择、执行、观察、反思、权限控制和超时控制的系统。面试官会重点问：什么时候用 Agent，怎么避免不可控，MCP 工具如何接入，敏感工具如何审批。

基于仓库可确认的信息：项目支持 ReAct Agent、自定义 Agent、MCP 服务、web search、内置工具、Agent skills、数据分析工具、MCP Human-in-the-Loop Approval；`mcp_service.go` 中禁用了 stdio transport，建议 SSE 或 HTTP streamable；README 提到并行工具调用和工具审批。  
需要你补充的信息：你是否实现过某个 Agent 工具、审批流程、MCP server，或调过 Agent 成本/延迟。

## 3. 问答与讲解

### Q1：Agent 模式和普通 RAG 有什么区别？

#### 面试官为什么问

很多候选人会把 Agent 和 RAG 混为一谈。面试官想看你能否讲清楚“单次检索生成”和“多步任务编排”的差异。

#### 先给结论

普通 RAG 更像一次固定流水线：用户问题进来，系统检索知识库、重排、拼上下文、调用模型生成。

#### 回答思路

1. 普通 RAG：一次 query -> 检索 -> 生成。
2. Agent：模型可以多轮决定下一步动作，调用知识库、web search、MCP 工具。
3. Agent 适合复杂任务，但成本、延迟和风险更高。
4. 系统需要 max rounds、timeout、审批、权限和日志。

#### 结合我的项目怎么答

项目里普通知识问答走 `KnowledgeQA` 的 pipeline；Agent 能结合自定义 Agent 配置、MCP 服务、内置工具、web search 和技能系统。README 中提到 ReAct progressive multi-step reasoning，说明它是多步推理编排，不是简单检索。

#### 技术原理 / 链路设计讲解

ReAct 的典型循环是：

```text
Thought: 我需要先查知识库
Action: search_kb(...)
Observation: 返回若干文档片段
Thought: 还缺外部最新信息
Action: web_search(...)
Observation: 返回网页结果
Thought: 综合信息
Final Answer: ...
```

这个循环的优势是能处理复杂任务；缺点是每一步都可能出错，且 token 和延迟随着轮数增长。因此 Agent 需要工具白名单、最大轮数、超时、用户审批和可观测性。

#### 技术栈特点与选型理由

MCP 提供了一种标准化工具接入协议，让外部工具不必写死在主服务里。自定义 Agent 则把模型、工具、知识库范围和 Prompt 组合成可配置能力。

#### 可直接复述的面试回答

普通 RAG 更像一次固定流水线：用户问题进来，系统检索知识库、重排、拼上下文、调用模型生成。Agent 则是多步任务编排，模型可以根据当前观察结果决定下一步调用知识库、web search、MCP 工具或内置工具，最后再汇总答案。它适合复杂问题，比如需要跨知识库查询、调用外部系统、做数据分析的任务。但 Agent 成本和不确定性更高，所以项目需要控制最大轮数、超时、工具权限、审批和 trace。

#### 常见追问

- 普通问题是否应该默认走 Agent？
- Agent 如何防止死循环？
- Agent 的中间过程是否展示给用户？

#### 常见坑

不要把 Agent 描述成“更智能所以全用”。真实系统里要根据任务复杂度路由，普通问答优先用 RAG。

### Q2：MCP 工具为什么要做权限和审批？

#### 面试官为什么问

这是安全和平台化能力的结合题。工具调用一旦能读写外部系统，就不只是生成文本，而是会产生真实副作用。

#### 先给结论

MCP 工具一旦接入，就可能不只是读知识库，而是访问外部系统甚至产生写操作，所以必须做权限和审批。

#### 回答思路

1. MCP 工具可能访问外部系统、文件、网络、数据库。
2. 敏感工具需要 Human-in-the-Loop，防止误操作。
3. 工具服务本身要有租户隔离、凭据保护、传输限制。
4. 审批结果要可追踪，便于审计。

#### 结合我的项目怎么答

项目有 `mcp_tool_approval_service.go`，README 中也明确提到 MCP Human-in-the-Loop Approval。`mcp_service.go` 中创建和更新 MCP 服务时禁用了 stdio transport，提示使用 SSE 或 HTTP Streamable transport，这是典型安全取舍：stdio 容易引入本地命令执行风险。

#### 技术原理 / 链路设计讲解

工具调用风险可以分为：

- 读风险：泄露内部文档、凭据、用户数据。
- 写风险：删除数据、发送消息、修改配置。
- 执行风险：本地命令执行、网络访问、SSRF。
- 供应链风险：第三方 MCP server 行为不可控。

因此需要从工具注册、凭据管理、调用审批、运行隔离、日志审计多层防护。

#### 技术栈特点与选型理由

禁用 stdio 的好处是减少主服务直接拉起本地进程的风险；SSE/HTTP streamable 更适合服务化接入、鉴权、限流和网络隔离。

#### 可直接复述的面试回答

MCP 工具一旦接入，就可能不只是读知识库，而是访问外部系统甚至产生写操作，所以必须做权限和审批。WeKnora 里敏感 MCP 工具可以暂停 Agent，等待用户显式批准后再执行；MCP 服务层也禁用了 stdio transport，推荐通过 SSE 或 HTTP streamable 接入，降低本地命令执行风险。我的理解是，工具调用要按“最小权限 + 可审计 + 可中断”来设计，否则 Agent 很容易从问答系统变成不可控的自动执行器。

#### 常见追问

- 审批超时后如何处理？
- 工具调用日志记录哪些字段？
- API key/token 如何存储？

#### 常见坑

不要只讲“用户点确认”。审批只是最后一道门，前面还要有工具注册权限、凭据保护、租户隔离和运行时限制。

### Q3：Agent 工具调用失败如何处理？

#### 面试官为什么问

面试官想看你是否理解 Agent 的稳定性。真实工具调用会超时、断线、返回异常、返回空结果或返回不可解析内容。

#### 先给结论

Agent 工具调用失败不能简单吞掉。一般会给每次工具调用设置超时，对网络抖动这类 transient error 做有限重试；如果工具不可用，要把失败作为明确 observation 反馈给 Agent 或直接中止，不能让模型假装成功。

#### 回答思路

1. 给工具调用设置超时。
2. 可重试的网络错误做有限重试。
3. 不可重试错误作为 Observation 返回给模型或直接中止。
4. 记录 trace 和日志。
5. 对关键任务提供 fallback。

#### 结合我的项目怎么答

README 提到 MCP 自动重连、并行工具调用和 Agent LLM call timeout。`docker-compose.yml` 中有 `WEKNORA_AGENT_LLM_TIMEOUT` 和 `WEKNORA_AGENT_TOOL_APPROVAL_TIMEOUT` 环境变量，说明项目考虑了 Agent 调用和审批的超时控制。

#### 技术原理 / 链路设计讲解

Agent 稳定性难点是：工具调用失败后，模型可能继续基于错误信息胡编。因此系统要明确区分：

- 工具不可用：告知用户或切换工具。
- 工具返回空：允许模型解释“未查到”。
- 工具返回部分结果：让模型基于已有信息回答并标明不确定。
- 工具有副作用且失败：不能盲目重试，避免重复写。

#### 技术栈特点与选型理由

并行工具调用可以降低复杂任务延迟，但也会放大下游压力；需要 errgroup、限流和上下文取消来控制资源。

#### 可直接复述的面试回答

Agent 工具调用失败不能简单吞掉。一般会给每次工具调用设置超时，对网络抖动这类 transient error 做有限重试；如果工具不可用，要把失败作为明确 observation 反馈给 Agent 或直接中止，不能让模型假装成功。对于有副作用的工具，重试要特别谨慎，需要幂等键或用户确认。WeKnora 在配置里提供 Agent LLM 超时和工具审批超时，MCP 也支持重连和审批，这些都是为了控制 Agent 的不确定性。

#### 常见追问

- 并行工具调用失败一部分怎么办？
- 如何避免重复执行有副作用工具？
- 工具返回大文本如何截断？

#### 常见坑

不要让模型“自己判断工具是否成功”。系统层必须给出结构化成功/失败状态。

### Q4：数据分析 Agent 如何控制安全风险？

#### 面试官为什么问

数据分析涉及 SQL、文件、沙箱和代码执行，是安全高风险场景。

#### 先给结论

数据分析 Agent 的核心不是能不能生成 SQL，而是能不能安全执行。

#### 回答思路

1. 限制文件类型，比如 CSV/Excel。
2. 使用只读查询白名单。
3. 禁止 DDL/DML。
4. 用沙箱隔离执行环境。
5. 限制执行时间、内存、结果大小。

#### 结合我的项目怎么答

项目 FAQ 文档提到数据分析功能支持 CSV/Excel，并限制只读查询，比如 SELECT、SHOW、DESCRIBE、EXPLAIN、PRAGMA，禁止 INSERT、UPDATE、DELETE、CREATE、DROP 等。`docker-compose.yml` 也配置了 Agent Skills Sandbox。

#### 技术原理 / 链路设计讲解

自然语言转 SQL 的风险在于 prompt injection 和越权操作。即使用户说“帮我删除表”，系统也不能让 Agent 直接执行。更安全的方式是 SQL AST 校验、只读连接、临时数据库、沙箱执行、超时限制和结果脱敏。

#### 技术栈特点与选型理由

DuckDB 适合本地分析 CSV/Parquet/Excel 类数据，成本低、部署简单；沙箱可以隔离 Python/脚本执行风险。

#### 可直接复述的面试回答

数据分析 Agent 的核心不是能不能生成 SQL，而是能不能安全执行。WeKnora 对这类能力做了边界限制：主要面向 CSV/Excel，只允许 SELECT、SHOW、DESCRIBE、EXPLAIN、PRAGMA 等只读语句，禁止 INSERT、UPDATE、DELETE、CREATE、DROP 这类修改操作。更进一步还要配合沙箱、超时、内存限制和结果大小限制，避免 Agent 被 prompt injection 诱导执行危险操作。

#### 常见追问

- 只用字符串判断 SQL 安全够不够？
- 如何防止 SELECT 读取敏感列？
- 查询结果太大怎么办？

#### 常见坑

不要说“Prompt 里告诉模型不要执行危险 SQL 就可以”。安全必须在程序层校验。

## 4. 本主题总结

Agent 面试要强调“能力越强，约束越重要”。要讲清楚 Agent 和 RAG 的边界、MCP 的扩展价值、工具调用的安全风险、审批机制、超时重试和可观测性。
