# 文件：06_Wiki模式知识图谱与数据源同步.md

## 1. 本主题面试官想考什么

这个主题考察你对“知识沉淀”而不只是“问答”的理解。Wiki 模式、知识图谱和数据源同步体现的是长期知识资产维护能力：如何从原始文档生成结构化页面，如何维护页面链接和图谱关系，如何处理批量入库、并发、删除、失败和增量同步。

基于仓库可确认的信息：`wiki_ingest.go` 使用 `task_pending_ops` 存储 pending op，以 Redis active lock 控制同一知识库并发，以 tombstone 处理删除并发，以 `task_dead_letters` 记录失败；Wiki 入库有 debounce、batch size、LLM 重试和锁续期。项目支持 Neo4j 知识图谱和 Feishu/Notion/Yuque 数据源。  
需要你补充的信息：Wiki 生成效果、图谱 schema、数据源同步频率、增量同步策略和线上规模。

## 3. 问答与讲解

### Q1：Wiki 模式和普通 RAG 有什么区别？

#### 面试官为什么问

面试官想看你能不能区分“即时问答”和“长期知识结构化”。

#### 先给结论

普通 RAG 是查询时从原始文档 chunk 中召回依据，然后让模型回答；Wiki 模式则是在入库阶段把原始文档进一步沉淀成结构化 Markdown 页面、页面链接和知识图谱。

#### 回答思路

1. 普通 RAG 是查询时临时检索文档片段。
2. Wiki 是入库后生成结构化页面、链接和图谱。
3. Wiki 更适合知识沉淀、浏览、维护和体系化理解。
4. 它需要处理生成质量、增量更新和删除一致性。

#### 结合我的项目怎么答

项目 README 把 Wiki Mode 定义为 Agent-driven auto-generation of structured, interlinked markdown Wiki pages。`wiki_ingest.go` 说明 Wiki 不是同步功能，而是一个可批处理、可重试、可追踪的异步入库管道。

#### 技术原理 / 链路设计讲解

普通 RAG 的数据单位是 chunk，查询时临时取 TopK。Wiki 模式的数据单位是页面和页面关系，它会把多个 chunk 或文档信息综合成更高层次的知识页面。这样用户不仅能问答，还能像浏览知识库一样查看主题页面和关系图。

#### 技术栈特点与选型理由

Wiki 生成依赖 LLM，因此必须异步；它还依赖 DB 保存页面、日志和 pending ops，依赖 Redis 做短期锁，依赖 dead-letter 做失败沉淀。

#### 可直接复述的面试回答

普通 RAG 是查询时从原始文档 chunk 中召回依据，然后让模型回答；Wiki 模式则是在入库阶段把原始文档进一步沉淀成结构化 Markdown 页面、页面链接和知识图谱。它的价值是把散乱文档变成可浏览、可维护、可复用的知识体系，而不是每次都从原始文档重新理解。代价是生成过程更重，需要异步任务、批处理、去重、删除一致性和质量控制。

#### 常见追问

- Wiki 页面生成错误怎么办？
- Wiki 页面是否参与 RAG 检索？
- Wiki 和知识图谱的关系是什么？

#### 常见坑

不要说 Wiki 就是“自动摘要”。Wiki 更强调结构化、链接、页面生命周期和知识维护。

### Q2：Wiki 入库如何处理大规模文档和并发？

#### 面试官为什么问

这是稳定性和扩展性深挖。Wiki 生成是 LLM 重任务，不能简单每个文档一个立即执行的任务。

#### 先给结论

Wiki 入库是按知识库维度做批处理的。上传文档后，系统不是立刻并发生成 Wiki，而是先在 task_pending_ops 里写一条 pending op，再延迟 30 秒投递触发任务，用 debounce 合并短时间的上传。

#### 回答思路

1. 上传文档时写 pending op，而不是直接生成。
2. debounce 合并短时间内的多次上传。
3. worker 按知识库加 active lock，避免同 KB 并发冲突。
4. 每批限制文档数，剩余任务继续排队。
5. 失败进入 fail count 或 dead-letter。

#### 结合我的项目怎么答

`wiki_ingest.go` 里有几个关键常量：`wikiIngestDelay = 30s`、`wikiMaxDocsPerBatch = 5`、`wikiActiveLockTTL = 60s`、`wikiActiveLockRenew = 20s`、`wikiMaxFailRetries = 5`。注释明确说明 pending ops 取代了旧的 Redis pending list，避免大规模文档场景下 Redis TTL 或内存队列不可靠。

#### 技术原理 / 链路设计讲解

大规模 Wiki 入库的关键不是“更快调用 LLM”，而是“稳定推进”。对同一个知识库，多个文档生成页面时可能会写同一主题页面、同一链接关系。如果并发执行，很容易产生覆盖、重复或链接不一致。因此按 KB 加锁，批量处理，失败重排，是更稳的方式。

Redis active lock 是短期互斥，DB pending ops 是持久任务队列，两者职责不同：锁丢了可以恢复，pending op 不能丢。

#### 技术栈特点与选型理由

用 DB 保存 pending ops 的好处是可查询、可恢复、可和 dead-letter 关联；Redis 只承担短生命周期锁，避免把核心任务状态放在易失结构里。

#### 可直接复述的面试回答

Wiki 入库是按知识库维度做批处理的。上传文档后，系统不是立刻并发生成 Wiki，而是先在 task_pending_ops 里写一条 pending op，再延迟 30 秒投递触发任务，用 debounce 合并短时间的上传。worker 执行时会拿同一个 KB 的 active lock，避免多个批次同时改同一组 Wiki 页面。每批最多处理一定数量文档，失败会增加失败次数，超过阈值进入 dead-letter。这样即使是几万文档，也能稳定分批推进。

#### 常见追问

- 为什么不用 Redis list 保存 pending op？
- active lock 过期太短或太长有什么问题？
- 批大小为什么不能无限大？

#### 常见坑

不要只讲“加锁”。要说清楚持久队列和短期锁的职责分离。

### Q3：删除文档时，Wiki 和图谱如何保持一致？

#### 面试官为什么问

面试官想看你是否考虑到生命周期一致性。生成型系统常见问题是“原文删了，衍生内容还在”。

#### 先给结论

删除文档时不能只删原文件和 chunk，还要考虑异步任务可能仍在运行。

#### 回答思路

1. 删除文档要删除或撤回相关 chunk、索引、图谱、Wiki 页面引用。
2. 正在处理的任务要能感知删除。
3. 使用 tombstone 避免删除后旧任务重新写回。
4. 最终一致，不承诺强事务。

#### 结合我的项目怎么答

`wiki_ingest.go` 中有 `wikiDeletedKeyPrefix` 和 `WikiDeletedTombstoneKey`，用于标记最近删除的 knowledge。注释说明 tombstone TTL 要超过可能的 ingest 运行时间，让 in-flight 或 queued 的 wiki_ingest 快速跳过。`processChunks` 也会清理旧 graph 数据。

#### 技术原理 / 链路设计讲解

删除和异步生成并发时，最危险的场景是：

```text
T1: worker 开始处理文档 A
T2: 用户删除文档 A，并删除索引
T3: worker 处理完成，把 A 的 Wiki 页面/图谱重新写入
```

tombstone 的作用是让 T3 在写入前发现“这个文档最近被删除了”，从而跳过。它不是永久状态，而是覆盖 in-flight 任务窗口。

#### 技术栈特点与选型理由

Redis TTL 适合 tombstone，因为它是短期并发保护，不需要永久保留；真正的任务和失败记录则应该在 DB 中持久化。

#### 可直接复述的面试回答

删除文档时不能只删原文件和 chunk，还要考虑异步任务可能仍在运行。WeKnora 对 Wiki 入库设计了 deleted tombstone，删除某个 knowledge 时写入类似 wiki:deleted:{kbID}:{knowledgeID} 的短期标记，TTL 覆盖可能的任务运行窗口。这样已经排队或正在运行的 wiki_ingest 在写回前可以发现文档已删除并跳过，避免“删了又被异步任务写回来”。这类跨 DB、Redis、LLM 的链路一般是最终一致，重点是可恢复和可补偿。

#### 常见追问

- TTL 设置多长合适？
- 如果 tombstone 丢了怎么办？
- Wiki 页面被多个文档共同引用时怎么删？

#### 常见坑

不要承诺一次数据库事务能覆盖向量库、Neo4j、Redis 和 LLM 任务。这里必须讲最终一致。

### Q4：知识图谱在 RAG 中有什么价值？

#### 面试官为什么问

知识图谱是常见但容易被滥用的概念。面试官想看你是否能讲清楚它的适用场景和代价。

#### 先给结论

知识图谱不是替代向量检索，而是补充。向量检索擅长找语义相似片段，图谱擅长表达实体和关系，比如组件依赖、概念关联、组织人员关系。

#### 回答思路

1. 图谱适合实体关系、上下游依赖、概念网络。
2. 向量检索适合语义相似，图谱适合关系跳转。
3. 图谱需要实体抽取、关系抽取、消歧和更新。
4. 不是所有知识库都需要图谱。

#### 结合我的项目怎么答

项目支持 Neo4j，`PluginSearchParallel` 会在 chunk search 之外并行执行 entity search；如果 query understand 抽取到实体，就可以通过 graphRepo 找关联内容，再和 chunk search 结果合并。

#### 技术原理 / 链路设计讲解

向量检索能回答“语义相近的内容在哪里”，但不一定擅长回答“系统 A 依赖哪些组件”“某个人负责哪些项目”“某概念和哪些概念相关”。图谱通过节点和边表达关系，可用于补充召回和增强解释。

#### 技术栈特点与选型理由

Neo4j 使用图数据库模型，适合多跳查询和关系可视化；但它会增加抽取成本、存储成本和一致性维护成本。因此项目把 graph 作为 indexing strategy 的可选项是合理的。

#### 可直接复述的面试回答

知识图谱不是替代向量检索，而是补充。向量检索擅长找语义相似片段，图谱擅长表达实体和关系，比如组件依赖、概念关联、组织人员关系。WeKnora 的搜索 pipeline 里可以并行做 chunk search 和 entity search，再合并结果。这样当问题涉及实体关系时，图谱能补充向量检索召回不到的关系信息。但图谱抽取和维护有成本，不是所有知识库都应该默认开启。

#### 常见追问

- 实体抽取错了怎么办？
- 图谱多跳会不会引入噪声？
- 图谱数据如何更新？

#### 常见坑

不要把知识图谱说成万能增强。图谱质量差时会引入错误关系，反而降低回答质量。

## 4. 本主题总结
