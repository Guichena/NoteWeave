# 文件：08_存储向量库模型抽象与可扩展性.md

## 1. 本主题面试官想考什么

这个主题考察架构扩展能力：如何支持不同向量数据库、不同对象存储、不同模型 provider、不同租户配置，同时避免抽象过度和数据不一致。面试官会关注接口设计、工厂模式、配置管理、维度一致性、连接测试、迁移和降级。

基于仓库可确认的信息：项目支持 Postgres/SQLite、Elasticsearch、Qdrant、Milvus、Weaviate、Doris、Tencent VectorDB 等检索后端；`VectorStore` 支持 DB-managed store；`retriever/factory.go` 会验证 store ownership；`CompositeRetrieveEngine` 可按 retriever type 委托不同引擎；对象存储支持 local、MinIO、S3、COS、TOS、OSS、KS3 等；模型支持多 provider。  
需要你补充的信息：实际部署使用的向量库、模型供应商、Embedding 维度、存储成本和迁移经验。

## 3. 问答与讲解

### Q1：多向量库是怎么抽象的？

#### 面试官为什么问

这是架构可扩展性的核心问题。面试官想看你是否理解接口、工厂、注册表和租户隔离。

#### 先给结论

WeKnora 把向量库抽象成统一的 retrieve engine。

#### 回答思路

1. 定义统一 RetrieveEngineRepository/Service 接口。
2. 不同后端实现 Save、BatchSave、Retrieve、Delete 等能力。
3. Registry 管理 engine type 或 store id 到具体服务的映射。
4. Factory 根据 KB 的 VectorStoreID 或租户默认配置生成 CompositeRetrieveEngine。
5. Composite 根据 retriever type 路由到支持的后端。

#### 结合我的项目怎么答

`types/retriever.go` 定义 `RetrieverEngineType` 和 `RetrieverType`，包括 `vector`、`keywords`、`websearch`。`retriever/factory.go` 中 `CreateRetrieveEngineForKB` 会根据 `vectorStoreID` 决定走租户默认 effective engines 还是绑定的 DB store。`CompositeRetrieveEngine.Retrieve` 会遍历 engineInfos，找到支持当前 RetrieverType 的 engine 执行。

#### 技术原理 / 链路设计讲解

这个抽象把“检索能力”和“具体存储实现”解耦：

```text
业务层只关心：我要 vector 检索或 keywords 检索
工厂层负责：这个 KB 应该用哪个 store
registry 负责：store id / engine type 对应哪个服务实例
engine service 负责：调用具体 Qdrant/Milvus/ES/Postgres
```

这种设计适合私有化项目，因为不同客户已有基础设施不同。

#### 技术栈特点与选型理由

接口抽象的好处是扩展新向量库时不影响上层 RAG pipeline；代价是必须对齐不同后端的能力差异，比如索引命名、向量维度、过滤条件、删除语义、批量写性能。

#### 可直接复述的面试回答

WeKnora 把向量库抽象成统一的 retrieve engine。业务层不直接依赖 Qdrant、Milvus 或 Elasticsearch，而是通过 RetrieverType 表达我要做 vector 或 keywords 检索。工厂会根据知识库是否绑定 VectorStore 来解析具体后端：没有绑定时走租户默认 effective engines，有绑定时先校验 store 是否属于当前租户，再从 registry 取对应服务。最后 CompositeRetrieveEngine 根据 retriever type 把请求路由到支持该能力的引擎。这样新接一个向量库主要实现统一接口和注册，不需要改问答主链路。

#### 常见追问

- 如果一个后端只支持 vector 不支持 keywords 怎么办？
- registry 是进程内还是 DB 驱动？
- 多 store 同类型时怎么区分？

#### 常见坑

不要只说“用了接口”。要讲清楚接口如何被工厂、registry 和租户配置串起来。

### Q2：如何防止一个租户绑定另一个租户的 VectorStore？

#### 面试官为什么问

这是多租户隔离在基础设施配置层的深挖。向量库里存的也是知识数据，越权绑定会导致数据泄露。

#### 先给结论

VectorStore 本身是租户级资源，绑定知识库时不能相信前端传来的 store id。

#### 回答思路

1. VectorStore 有 tenant_id。
2. KB 绑定 vector_store_id 时必须校验 ownership。
3. 异步任务不能只信 payload，也要验证 store 属于 tenant。
4. 错误信息不能泄露 store UUID 是否存在。

#### 结合我的项目怎么答

`retriever/factory.go` 中 `VerifyBinding` 和 `resolveBoundEngine` 会调用 `ownership.StoreOwnedBy(storeID, tenantID)`。如果不属于当前租户，返回 `ErrVectorStoreForbidden`；如果 store 不可用，返回 `ErrVectorStoreNotFound`。注释还强调 user-facing response 不应泄露 store UUID，避免枚举。

#### 技术原理 / 链路设计讲解

如果只在前端限制用户选择自己的 store，攻击者可以直接构造 API 请求传入别人的 store id。真正安全的做法是在服务端绑定、检索、异步删除索引等所有路径都验证 tenant ownership。

异步任务尤其要注意，因为 worker 上下文可能没有完整 TenantInfo，所以项目提供 `CreateRetrieveEngineFromPayload`，显式传 tenantID 和 vectorStoreID，再验证绑定关系。

#### 技术栈特点与选型理由

把 ownership 校验放在 retriever factory 中，可以让所有调用路径共享同一套安全判断，减少业务层遗漏。

#### 可直接复述的面试回答

VectorStore 本身是租户级资源，绑定知识库时不能相信前端传来的 store id。WeKnora 在 retriever factory 里统一做 ownership 校验：根据 tenantID 和 storeID 查询这个 store 是否属于当前租户，不属于就返回 forbidden；store 不存在或未注册则返回 not found。异步任务也不能绕过，因为 worker 可能没有完整请求上下文，所以 payload 里带 tenantID 后仍要重新验证 store ownership。这样可以防止用户手工传别的租户 store id 导致数据越权。

#### 常见追问

- not found 和 forbidden 是否应该区分返回？
- 删除 KB 时如何删除绑定 store 中的索引？
- 绑定 store 被删除后，KB 怎么处理？

#### 常见坑

不要只在创建 KB 时校验一次。后续检索、重建、删除索引都要校验或使用安全快照。

### Q3：Embedding 模型维度变化会带来什么问题？

#### 面试官为什么问

这是 RAG 工程里非常实际的问题。很多候选人会忽略向量维度和索引 schema 的耦合。

#### 先给结论

Embedding 模型不是随便切的，因为向量库索引通常要求固定维度。

#### 回答思路

1. 向量库 collection/index 通常固定维度。
2. 换 Embedding 模型可能导致维度不一致。
3. 旧向量不能和新向量直接混查。
4. 需要重建索引、分 collection、或按 KB 绑定模型。
5. 配置阶段要校验模型维度。

#### 结合我的项目怎么答

`Knowledge` 记录有 `EmbeddingModelID`，`KnowledgeBase` 也有 `EmbeddingModelID`。`processChunks` 中删除旧索引时会传 `embeddingModel.GetDimensions()`；`.env.example` 也要求配置 `INIT_EMBEDDING_MODEL_DIMENSION`。这说明模型维度是入库和删除索引的重要参数。

#### 技术原理 / 链路设计讲解

向量相似度计算要求向量维度一致。假设旧模型输出 768 维，新模型输出 1536 维，写入同一个 collection 会失败，或者查询无法比较。即使维度相同，不同模型的向量空间也不一定兼容，混用会降低检索质量。

#### 技术栈特点与选型理由

把 EmbeddingModelID 绑定到 KB/Knowledge，可以支持不同知识库用不同模型，但也要求索引隔离和重建策略清晰。

#### 可直接复述的面试回答

Embedding 模型不是随便切的，因为向量库索引通常要求固定维度。比如旧模型是 768 维，新模型是 1536 维，旧 collection 不能直接写新向量；即使维度相同，不同模型的向量空间也不一定兼容，混查会影响相似度。WeKnora 在 knowledge 和 KB 上保存 EmbeddingModelID，并在索引删除等操作里使用模型维度。实际切换模型时，我会要求对受影响知识库重建索引，或者按模型/KB 使用独立 collection，避免新旧向量混用。

#### 常见追问

- 如果模型维度配置错了，会在哪里暴露？
- 是否可以在线平滑迁移？
- 旧索引删除失败怎么办？

#### 常见坑

不要说“换模型只改配置”。Embedding 模型切换通常意味着重建向量索引。

### Q4：对象存储如何选型？为什么不把文件直接存数据库？

#### 面试官为什么问

这是基础架构取舍题。知识库系统会处理大量文件、图片、附件，存储方式直接影响成本、性能和备份。

#### 先给结论

我不会把原始文档直接放数据库。数据库只保存文件元数据、hash、路径、状态和权限，真正的文件放对象存储或本地文件系统。

#### 回答思路

1. 原文件和图片体积大，数据库不适合存 blob。
2. 对象存储适合大文件、分片、签名 URL、生命周期管理。
3. 本地存储适合 Lite/开发，MinIO 适合私有化，云存储适合云部署。
4. DB 只保存元数据、路径、hash、状态和权限。

#### 结合我的项目怎么答

项目支持 local、MinIO、COS、TOS、S3、OSS、KS3 等存储。`CreateKnowledgeFromFile` 保存文件后只把 `FilePath` 写回 knowledge 记录。`serveFiles` 和 presigned files 负责文件访问代理和签名校验。

#### 技术原理 / 链路设计讲解

数据库擅长结构化事务和索引，不适合大量二进制文件。把文件放 DB 会导致备份膨胀、查询性能下降、扩容成本高。对象存储提供更好的吞吐、容量、访问控制和生命周期管理。

#### 技术栈特点与选型理由

本地存储降低单机部署门槛；MinIO 满足私有化 S3 兼容；云厂商存储满足生产高可用和容量扩展。

#### 可直接复述的面试回答

我不会把原始文档直接放数据库。数据库只保存文件元数据、hash、路径、状态和权限，真正的文件放对象存储或本地文件系统。这样数据库备份和查询不会被大 blob 拖垮，也更容易做签名 URL、生命周期和横向扩展。WeKnora 支持 local、MinIO 和多个云对象存储，local 适合 Lite 或开发，MinIO 适合私有化，云存储适合生产云部署。

#### 常见追问

- 文件删除和 DB 记录删除如何保持一致？
- presigned URL 如何防盗链？
- 图片在对话中如何展示？

#### 常见坑

不要忽略存储访问权限。对象存储 bucket 公开读写会导致严重泄露。

## 4. 本主题总结

扩展性回答要围绕“统一接口 + 工厂/注册表 + 租户隔离 + 配置校验 + 重建迁移”展开。多后端支持不是炫技，而是私有化项目适配不同客户基础设施的需要。
