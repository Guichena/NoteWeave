## 1. 本主题面试官想考什么

这个主题考察工程落地能力。大厂面试官会关注：系统如何发现问题、定位问题、恢复问题；异步任务失败如何追踪；LLM 调用超时如何避免拖垮 worker；如何部署、扩容、降级；如何处理线上故障。

基于仓库可确认的信息：项目支持 Langfuse、OpenTelemetry、Asynq dead-letter、健康检查、Docker Compose、Helm、Lite、日志级别、worker 队列权重；`langfuse/asynq.go` 会把 HTTP trace 注入异步 payload 并在 worker 中恢复；`asynqdl` 会把最终失败任务写入 `task_dead_letters`。  
需要你补充的信息：真实监控指标、日志平台、告警策略、SLO、故障复盘。

## 3. 问答与讲解

### Q1：项目如何做可观测性？

#### 面试官为什么问

RAG/Agent 系统调用链长，单靠日志很难定位问题。面试官想看你是否知道应该观察哪些阶段。

#### 先给结论

WeKnora 的可观测性分两层：普通服务层有 request id、结构化日志、recovery 和 error handler；LLM 应用层接入 Langfuse，记录 chat、embedding、rerank、VLM、ASR 等模型调用。

#### 回答思路

1. API 层有 request id、logger、recovery、error handler。
2. LLM/Embedding/Rerank/ASR/VLM 调用进入 Langfuse trace。
3. Asynq payload 注入 trace id，worker 恢复 trace。
4. pipeline 每阶段记录输入输出数量和错误。
5. dead-letter 记录最终失败任务。

#### 结合我的项目怎么答

`router/router.go` 中注册了 RequestID、Logger、Recovery、ErrorHandler 和 Langfuse GinMiddleware。`langfuse/asynq.go` 中 `InjectTracing` 会把 trace/span/user/session 信息写入 task payload，`AsynqMiddleware` 在 worker 侧恢复 trace 或创建独立 trace。`asynqdl` 会在最终重试失败时写入 `task_dead_letters`。

#### 技术原理 / 链路设计讲解

一次上传文档可能跨越 HTTP 请求、Redis 队列、worker、docreader、Embedding、向量库和摘要模型。没有 trace 时，排障只能查分散日志；有 trace 后，可以看到每个阶段耗时、输入、输出和错误。

#### 技术栈特点与选型理由

Langfuse 适合观测 LLM 应用的 prompt、response、token、generation 和 trace；OpenTelemetry 更通用；两者结合能覆盖模型链路和系统链路。

#### 可直接复述的面试回答

WeKnora 的可观测性分两层：普通服务层有 request id、结构化日志、recovery 和 error handler；LLM 应用层接入 Langfuse，记录 chat、embedding、rerank、VLM、ASR 等模型调用。比较关键的是异步任务也能接上同一条链路：入队前把 Langfuse trace 信息写到 payload，worker 消费时恢复 trace，并在 asynq task 外包一层 span。这样一次上传或问答可以从 HTTP 请求追到后台任务和模型调用。最终失败的异步任务还会写 task_dead_letters，方便 SQL 查询和补偿。

#### 常见追问

- trace payload 会不会泄露敏感数据？
- Langfuse 队列满了怎么办？
- 如何采样？

#### 常见坑

不要只说“看日志”。面试官会继续问如何关联一次请求的多个异步阶段。

### Q2：异步任务失败如何处理和排查？

#### 面试官为什么问

异步任务是文档入库、Wiki、摘要、FAQ 导入的生命线。面试官想看你是否理解重试、死信和补偿。

#### 先给结论

异步任务失败要先分类型。像模型网关超时、向量库短暂不可用可以重试；参数错误、权限错误、跨租户 store 绑定这类错误重试也没用，应该快速失败或跳过重试。

#### 回答思路

1. Asynq 负责重试和队列。
2. transient error 使用退避重试。
3. 非重试错误应跳过重试或快速失败。
4. 重试耗尽后写 dead-letter。
5. 通过 task type、tenant、scope、payload、last error 排查。

#### 结合我的项目怎么答

`router/task.go` 中 Asynq 配置 critical/default/low 队列权重。Wiki 并发锁冲突使用固定 15s retry delay，避免默认指数退避导致 orphan lock 后等待太久。`asynqdl` 只在最终 retry 失败时写 dead-letter，避免 transient error 每次都刷表。

#### 技术原理 / 链路设计讲解

不是所有失败都应该重试：

- 网络抖动、模型 5xx、向量库临时不可用：可重试。
- 参数错误、权限错误、vector store 不属于租户：不应重复重试。
- 并发锁冲突：短延迟重试。
- 数据损坏：进入 dead-letter 等人工处理。

#### 技术栈特点与选型理由

Asynq 的 retry/backoff 能解决大多数后台任务可靠性问题，但业务需要根据错误类型定制策略。dead-letter 入 DB 比只留 Redis 更利于运维查询。

#### 可直接复述的面试回答

异步任务失败要先分类型。像模型网关超时、向量库短暂不可用可以重试；参数错误、权限错误、跨租户 store 绑定这类错误重试也没用，应该快速失败或跳过重试。WeKnora 用 Asynq 管理任务，配置了不同队列权重，并用 dead-letter middleware 在最终重试失败时写入 task_dead_letters，记录 task type、tenant、scope、payload 和 last error。排查时可以先按任务类型和租户查死信，再结合 Langfuse trace 和 worker 日志定位具体阶段。

#### 常见追问

- 如何重新投递 dead-letter？
- dead-letter 表会不会无限增长？
- 如何避免同一个坏任务一直重试？

#### 常见坑

不要把重试当万能。对不可恢复错误反复重试只会放大系统压力。

### Q3：如果用户反馈问答很慢，你怎么定位？

#### 面试官为什么问

这是性能排障题。面试官想看你能否拆分端到端延迟。

#### 先给结论

我会先区分首 token 慢还是整体生成慢。

#### 回答思路

拆成阶段：

1. 前端请求和网络。
2. 后端 setup：权限、会话、模型、知识库解析。
3. query understand/rewrite。
4. 检索：向量库/关键词/图谱/web search。
5. rerank。
6. prompt 构造。
7. LLM 首 token 时间和总生成时间。
8. SSE/流式传输。

#### 结合我的项目怎么答

README 提到记录端到端 TTFB 和 LLM 调用超时；Langfuse spans 覆盖 retrieval/rerank/agent；`chat_pipeline` 各插件记录 input/output 数量；前端使用 `@microsoft/fetch-event-source` 做 SSE 流式接收。

#### 技术原理 / 链路设计讲解

用户感受到的慢通常分两类：

- 首 token 慢：检索、rerank、模型排队、prompt 太长、web search 慢。
- 总完成慢：模型生成慢、输出太长、网络传输慢。

优化方向不同：首 token 慢要优化检索和模型启动延迟；总完成慢要限制 max tokens、压缩上下文、使用更快模型或流式输出。

#### 技术栈特点与选型理由

流式输出不能减少总计算量，但能显著改善用户感知延迟。Langfuse 能区分各阶段耗时，不用猜。

#### 可直接复述的面试回答

我会先区分首 token 慢还是整体生成慢。首 token 慢通常发生在 query understand、检索、rerank、web fetch 或模型排队；整体慢更多是模型生成 token 多、上下文太长或网络传输。WeKnora 的 pipeline 和 Langfuse trace 可以看到 retrieval、rerank、chat model 等阶段耗时，前端通过 SSE 流式接收也能观察 TTFB。如果定位到检索慢，就看向量库和关键词后端；如果 rerank 慢，就降低候选数或换模型；如果 LLM 慢，就看 prompt 长度、max tokens、模型超时和供应商延迟。

#### 常见追问

- TopK 增大会对延迟有什么影响？
- web search 应该同步还是异步？
- 如何做超时降级？

#### 常见坑

不要说“加机器”。很多慢是外部模型、rerank 候选过多或 prompt 太长导致的，加 API 服务机器没有用。

### Q4：部署形态如何设计？私有化部署要注意什么？

#### 面试官为什么问

WeKnora 这种项目明显有私有化属性，面试官会关注部署复杂度、数据自主可控和组件裁剪。

#### 先给结论

WeKnora 支持多种部署形态。开发或试用可以用 Docker Compose，一条命令拉起 app、frontend、docreader、Redis、Postgres 和可选向量库；生产上可以用 Helm 部署到 Kubernetes；低门槛场景还有 Lite 和桌面端。

#### 回答思路

1. Docker Compose 适合快速部署。
2. Helm 适合 Kubernetes 生产化。
3. Lite/桌面端适合单机和低门槛体验。
4. 私有化要关注模型、存储、向量库、数据库、密钥和网络。
5. 可选组件要能裁剪。

#### 结合我的项目怎么答

`docker-compose.yml` 包含 frontend、app、docreader、redis、postgres，以及可选 sandbox、minio、qdrant、milvus、weaviate、neo4j、langfuse 等 profile。`helm` 目录支持 K8s；`cmd/desktop` 使用 Wails；README 提到 Lite 部署。

#### 技术原理 / 链路设计讲解

私有化部署的核心是“客户数据不出域”。这要求模型可以接本地 Ollama 或私有 API，向量库和对象存储可本地化，日志和 trace 也可自建或关闭。组件越多，部署越复杂，所以要提供不同 profile 和默认配置。

#### 技术栈特点与选型理由

Docker Compose 降低试用门槛；Helm 满足生产扩容、Secret、Ingress、存储卷；Lite/desktop 满足单机用户。

#### 可直接复述的面试回答

WeKnora 支持多种部署形态。开发或试用可以用 Docker Compose，一条命令拉起 app、frontend、docreader、Redis、Postgres 和可选向量库；生产上可以用 Helm 部署到 Kubernetes；低门槛场景还有 Lite 和桌面端。私有化部署要重点关注数据是否出域：模型、Embedding、向量库、对象存储、Langfuse 都要支持本地或私有云替换，同时密钥不能写死在配置里，生产环境要用 Secret 注入。

#### 常见追问

- Redis/Postgres 是否单点？
- 文档文件 volume 如何备份？
- 如何做滚动升级和数据库迁移？

#### 常见坑

不要只讲“docker compose up”。生产部署还要考虑持久化、备份、Secret、高可用、资源限制和升级回滚。

## 4. 本主题总结
