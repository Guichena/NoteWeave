# 文件：10_前端多端接入IM与工程交付.md

## 1. 本主题面试官想考什么

这个主题考察产品工程化能力：同一套知识问答能力如何通过 Web、CLI、IM、微信小程序、桌面端、MCP server 等多端交付；前端如何处理流式输出、引用、文档预览、权限；IM 如何做消息线程、限流和用户体验。

基于仓库可确认的信息：前端是 Vue 3 + Vite + Pinia + Vue Router + TDesign + fetch-event-source；支持 Markdown、KaTeX、Mermaid、文档预览；后端有 IM 适配目录 `internal/im`，覆盖 WeCom、Feishu、Slack、Telegram、DingTalk、Mattermost、WeChat；仓库包含 CLI、client SDK、miniprogram、desktop Wails、mcp-server。  
需要你补充的信息：你实际负责的端、是否做过 SSE 流式渲染、IM 适配、前端性能优化或 CLI 设计。

## 3. 问答与讲解

### Q1：前端问答为什么使用流式输出？

#### 面试官为什么问

面试官想看你是否理解大模型产品体验和接口协议取舍。

#### 先给结论

问答使用流式输出主要是为了降低用户感知延迟。

#### 回答思路

1. LLM 总生成时间较长，流式输出降低感知延迟。
2. 前端可以逐 token/逐 chunk 更新 UI。
3. 适合展示 Agent 工具调用过程和 references。
4. 需要处理断连、done、重试和状态一致性。

#### 结合我的项目怎么答

前端依赖 `@microsoft/fetch-event-source`，说明使用 SSE/fetch event stream 接收后端流式事件。后端 `CHAT_COMPLETION_STREAM` 插件会直接发 answer events，`KnowledgeQA` 还会通过 eventBus 发 references event。

#### 技术原理 / 链路设计讲解

SSE 是服务端到客户端的单向事件流，适合大模型回答这种“客户端发起请求，服务端持续推送结果”的场景。相比 WebSocket，SSE 更简单，天然基于 HTTP，适合文本流和代理链路；缺点是双向能力弱、某些代理可能缓冲。

#### 技术栈特点与选型理由

Vue + Pinia 适合管理会话状态、消息列表、引用和 loading 状态；marked、KaTeX、Mermaid、DOMPurify 负责富文本渲染和安全清洗。

#### 可直接复述的面试回答

问答使用流式输出主要是为了降低用户感知延迟。大模型完整生成可能要几秒到几十秒，如果等全部完成再返回，用户体验很差。WeKnora 前端用 fetch-event-source 接收 SSE 事件，后端 chat completion stream 会持续推送 answer chunk，检索引用也会通过事件返回。SSE 对这个场景比较合适，因为它是客户端请求后服务端单向推送，协议简单，能穿过大多数 HTTP 基础设施。

#### 常见追问

- SSE 和 WebSocket 怎么选？
- 流式输出如何保存到 DB？
- 如果连接断开，前端怎么恢复？

#### 常见坑

不要只说“更快”。流式输出不一定减少总耗时，它主要改善首屏和感知体验。

### Q2：前端如何安全渲染模型返回内容？

#### 面试官为什么问

LLM 返回内容可能包含 HTML、脚本、Markdown、Mermaid、链接，前端 XSS 风险很高。

#### 先给结论

模型返回内容不能当可信内容。WeKnora 前端支持 Markdown、代码高亮、公式、Mermaid 和文档预览，所以渲染链路必须做安全清洗。

#### 回答思路

1. 模型输出不能直接 innerHTML。
2. Markdown 渲染后要 DOMPurify 清洗。
3. 链接、图片、Mermaid、代码高亮都要限制。
4. 引用和附件链接要走后端鉴权或签名。

#### 结合我的项目怎么答

前端依赖中包含 `marked`、`dompurify`、`highlight.js`、`katex`、`mermaid`、`docx-preview` 等。说明项目支持复杂富文本渲染，也必须关注 XSS。后端还提供 presigned file access，用签名保护文件访问。

#### 技术原理 / 链路设计讲解

LLM 输出可能被用户 prompt injection 操控，比如让模型输出 `<script>` 或恶意链接。如果前端直接插入 HTML，就会执行脚本。Markdown 渲染器也可能生成 HTML，因此必须在渲染后清洗，限制危险标签和属性。

#### 技术栈特点与选型理由

DOMPurify 是前端 HTML sanitizer；marked 负责 Markdown；Mermaid 和 KaTeX 需要额外注意，因为它们会生成 HTML/SVG。

#### 可直接复述的面试回答

模型返回内容不能当可信内容。WeKnora 前端支持 Markdown、代码高亮、公式、Mermaid 和文档预览，所以渲染链路必须做安全清洗。一般做法是先把 Markdown 渲染成 HTML，再用 DOMPurify 去掉危险标签和属性；文件和图片链接也不能直接暴露存储地址，应该走后端鉴权代理或签名 URL。否则用户可以通过 prompt injection 让模型输出恶意 HTML，造成 XSS。

#### 常见追问

- Mermaid SVG 是否可能 XSS？
- 外链图片是否要代理？
- 代码块复制是否有安全风险？

#### 常见坑

不要认为“内容是模型生成的所以安全”。模型输出本质上是用户可控输入的一种变形。

### Q3：IM 接入和 Web 问答有什么不同？

#### 面试官为什么问

IM 适配是工程复杂度很高的多端场景。它涉及平台协议、消息去重、线程会话、流式体验、限流、身份映射。

#### 先给结论

IM 接入和 Web 最大区别是入口和会话模型不同。

#### 回答思路

1. Web 是用户主动请求，IM 是平台回调或长连接。
2. IM 要处理签名验证、消息去重、线程/群聊/私聊。
3. IM 回复可能不支持完整 SSE，需要编辑消息或卡片流。
4. IM 需要用户级限流和多实例协调。

#### 结合我的项目怎么答

仓库 `internal/im` 下有 dingtalk、feishu、mattermost、slack、telegram、wechat、wecom 等适配。README 提到 IM 支持 WebSocket/Webhook、thread-based sessions、slash commands、bounded QA worker pool、per-user rate limiting 和 Redis 多实例协调。

#### 技术原理 / 链路设计讲解

IM 平台通常会重复投递消息，要求服务端按 message_id 幂等。群聊中还要区分 thread_id/session_id，避免不同讨论串上下文串扰。流式回答在 IM 中也不统一：Slack/Telegram 可能通过编辑消息模拟流式，飞书/钉钉可能用卡片更新，企业微信可能有不同限制。

#### 技术栈特点与选型理由

把各平台适配放在 `internal/im/{platform}` 下，可以隔离协议差异；核心问答仍复用后端 session/QA service，避免每个平台重写 RAG。

#### 可直接复述的面试回答

IM 接入和 Web 最大区别是入口和会话模型不同。Web 是浏览器发起请求并接收 SSE；IM 多数是平台 webhook、WebSocket 或 long polling 回调，服务端要先做平台签名验证、消息去重、用户和租户映射，再把消息路由到系统 session。群聊还要处理 thread 维度，避免上下文串扰。回复方式也因平台不同，有的平台只能编辑消息模拟流式，有的平台用 AI 卡片或普通消息。所以 IM 层应该只做协议适配，核心问答逻辑仍复用统一的 session/RAG 服务。

#### 常见追问

- IM 重复投递如何幂等？
- 群聊里如何区分不同用户上下文？
- 用户发 `/stop` 怎么取消生成？

#### 常见坑

不要把 IM 当成“另一个前端”。IM 平台协议、重试、签名、消息限制和会话模型都不同。

### Q4：CLI、SDK、小程序、桌面端的工程价值是什么？

#### 面试官为什么问

面试官想看你是否理解平台化交付，而不是只做一个 Web 管理台。

#### 先给结论

这些多端不是重复建设，而是面向不同使用场景。

#### 回答思路

1. Web 适合普通用户和管理。
2. CLI 适合开发者、脚本、CI 和批量操作。
3. SDK 适合集成到第三方系统。
4. 小程序/IM 适合移动和即时协作场景。
5. 桌面端/Lite 降低本地部署门槛。

#### 结合我的项目怎么答

仓库中有 `cli`、`client`、`miniprogram`、`cmd/desktop`、`mcp-server`。CLI 有 auth、kb、doc、search、chat、agent 等命令；client 是 Go SDK；桌面端使用 Wails；小程序提供轻量聊天入口。

#### 技术原理 / 链路设计讲解

多端接入的关键是 API 契约一致。CLI、SDK、前端和 IM 不应该各自实现业务逻辑，而应该复用后端 API。这样权限、租户、审计、检索策略和模型配置都在服务端统一控制。

#### 技术栈特点与选型理由

CLI 使用 Go 便于分发单二进制；SDK 降低集成成本；Wails 可以复用 Go 后端和 Web 前端思路；小程序适合移动场景。

#### 可直接复述的面试回答

这些多端不是重复建设，而是面向不同使用场景。Web 适合知识库管理和可视化；CLI 适合开发者脚本、批量上传、搜索和调试；SDK 方便其他系统集成 WeKnora；IM 和小程序适合移动和团队协作；桌面端和 Lite 适合本地单机部署。关键是这些端都应该复用统一后端 API，这样权限、租户、审计、模型配置和检索策略不会分叉。

#### 常见追问

- CLI token 如何存储？
- SDK 如何保证兼容性？
- 多端 API 版本如何演进？

#### 常见坑

不要把多端能力讲成“做了很多入口”。重点是统一能力复用和一致的权限边界。

---

## 4. 本主题总结

多端接入回答要强调统一 API、协议适配、流式体验、安全渲染、消息幂等和会话隔离。Web、CLI、IM、小程序、桌面端的价值不同，但底层知识问答能力应该复用。
