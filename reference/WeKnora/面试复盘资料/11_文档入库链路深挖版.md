# 文件：11_文档入库链路深挖版.md

## 1. 本主题面试官想考什么

文档入库是 RAG 项目的地基。面试官问这一块，不是想听“上传后切块、Embedding、存向量库”这么一句话，而是想判断你是否理解一个真实文档系统要处理的复杂性：文件类型复杂、解析质量不稳定、异步任务会失败、索引要幂等、删除和重建会并发、Embedding 模型和向量库有强耦合、最终用户还要能看到处理状态。

一句话总结：文档入库不是一个上传接口，而是一条“非结构化数据 -> 可检索知识资产”的异步数据管道。

## 2. 高频问题清单

### 基础问题

- 用户上传一个文档后，系统内部完整链路是什么？
- 为什么文档入库不能同步完成？

- 文档解析、分块、Embedding、索引分别解决什么问题？

### 进阶问题

- chunk size 和 overlap 怎么选？

- Embedding 模型维度变了怎么办？
- 文件解析失败如何反馈给用户？

### 深挖追问

- 如果 DB chunk 写成功但向量库写失败怎么办？
- 如果用户删除文档时，后台任务还没结束怎么办？

- 大批量文档入库如何做限流和削峰？

## 3. 面试官视角的核心可问点

文档入库在这个项目里有几个很强的可问点：

- **状态机**：pending、processing、completed、failed、disabled/enabled 如何表达“上传成功”和“可问答”的区别。
- **异步化**：为什么用 Asynq，把 document:process、summary:generation、question:generation、wiki:ingest 拆成后台任务。
- **幂等性**：重试、重建、重复上传时，如何先清理旧 chunk、旧索引、旧图谱再写新结果。
- **分块策略**：adaptive 3-tier chunking、heading-aware、heuristic、legacy/recursive、parent-child。
- **多模态**：图片需要对象存储 + VLM/OCR，音频需要 ASR，表格可能触发数据表摘要。
- **一致性边界**：DB、对象存储、向量库、图谱库、模型调用无法放进一个本地事务，只能设计最终一致和补偿。

## 4. 深度问答与讲解

### Q1：请完整讲一下文档从上传到可被问答的链路

#### 面试官为什么问

这是最典型的 RAG 项目开场深挖题。面试官希望你能把文档入库讲成一个工程链路，而不是只讲“切 chunk 存向量库”。

#### 先给结论

文档入库我会把它理解成一条异步数据管道，而不是一个简单上传接口。

#### 回答思路

可以按照“接入校验 -> 元数据落库 -> 文件存储 -> 异步处理 -> 索引构建 -> 状态更新 -> 后处理”的顺序说。

#### 结合我的项目怎么答

在 WeKnora 里，用户上传文件后，后端不会马上同步完成所有解析和索引，而是先做一系列前置校验：

1. 读取知识库配置，判断这个 KB 是否允许文件型知识入库。比如 FAQ 类型知识库不能直接通过普通文件上传，要走 FAQ import。
2. 校验文件类型和文件名安全性，避免非法后缀、非法字符和潜在路径问题。
3. 对图片、音频做额外能力校验：图片要有对象存储和 VLM/OCR 配置，音频要有 ASR 配置。
4. 计算文件 hash，结合文件名、大小、hash 做重复文件检测。
5. 检查租户存储配额，防止某个租户无限上传占满资源。
6. 创建 knowledge 元数据记录，状态一般是 pending/disabled，表示文件已被接收，但还不能用于问答。
7. 将原文件保存到本地或对象存储，比如 local、MinIO、COS、S3 等。
8. 构造 `DocumentProcessPayload`，投递 `document:process` 异步任务。
9. worker 消费任务后调用 docreader 解析文档，得到文本、图片、OCR、位置信息等。
10. chunker 根据知识库配置进行分块，可能走 heading-aware、heuristic 或 recursive 策略，也可能生成 parent-child chunk。
11. 将 chunk 写入数据库，同时调用 Embedding 模型生成向量，并写入向量库/关键词索引。
12. 根据配置触发后处理，比如摘要生成、问题生成、多模态图片处理、Wiki 入库、知识图谱抽取。
13. 所有关键步骤完成后，knowledge 状态更新为 completed/enabled；失败则写 failed 和 error message。

#### 技术原理 / 链路设计讲解

这条链路本质上把一个非结构化文件变成三类资产：

- **原始资产**：原文件、图片、附件，保存在对象存储。
- **结构化元数据**：knowledge、chunk、状态、文件 hash、文件路径、租户 ID，保存在数据库。
- **检索资产**：向量索引、关键词索引、图谱节点/边、Wiki 页面。

为什么要拆成这些层？因为它们的生命周期不同。原文件用于预览和重新解析；chunk 用于展示和上下文拼接；向量索引用于召回；Wiki/图谱用于结构化沉淀。如果混在一起，会导致删除、重建和排障都很困难。

#### 可直接复述的面试回答

文档入库我会把它理解成一条异步数据管道，而不是一个简单上传接口。用户上传文件后，服务端先做知识库配置、文件类型、文件名安全、hash 去重、租户配额、多模态/ASR 配置校验，然后创建 knowledge 元数据，状态是 pending，并把原文件保存到对象存储。接着投递 document:process 异步任务。worker 消费任务后调用 docreader 解析文档，再由 chunker 根据知识库配置分块，保存 chunk，调用 Embedding 模型生成向量，并写入向量/关键词索引。最后根据配置触发摘要、问题生成、Wiki 和图谱等后处理，成功后把 knowledge 标记为 completed/enabled。这样上传成功和可问答是两个状态，用户体验和后台处理可以解耦。

#### 常见追问

- 为什么不能上传接口里直接解析并写索引？
- 如果任务入队失败怎么办？
- 文件保存成功但 knowledge 更新失败怎么办？
- 什么时候把 knowledge 设置为 enabled？

#### 常见坑

不要把“上传成功”说成“入库成功”。上传成功只代表系统接收了文件，真正能被问答要等解析、分块、索引全部完成。

### Q2：为什么文档处理要异步？异步后怎么保证可靠？

#### 面试官为什么问

这个问题考察你是否理解耗时任务和在线请求的边界，也考察你有没有可靠性意识。

#### 先给结论

文档处理必须异步，因为它不是一个稳定的短操作。

#### 回答思路

先讲为什么异步，再讲异步带来的问题，最后讲怎么解决。

#### 结合我的项目怎么答

文档处理包含 PDF/Word/图片/表格解析、分块、Embedding、向量库写入、摘要生成、问题生成、Wiki 生成等步骤。这些步骤有几个特点：

- 耗时不可控，大文件可能几十秒甚至几分钟。
- 依赖外部服务，比如 docreader、Embedding API、向量库、对象存储。
- 容易失败，比如 PDF 损坏、模型超时、向量库写入失败。
- 资源占用高，解析和 Embedding 都可能消耗 CPU、内存和网络。

如果同步做，HTTP 请求容易超时，并且 API 服务的 worker 会被大文件拖住。WeKnora 通过 Asynq 把这些任务放到后台处理。Asynq 可以提供队列、重试、优先级和 worker 并发控制。项目还通过 dead-letter middleware 把最终失败任务写入 `task_dead_letters`，避免失败只存在 Redis 或日志里。

#### 技术原理 / 链路设计讲解

异步化解决了请求超时和削峰问题，但引入了新问题：

- 任务可能重复执行。
- 任务可能执行到一半失败。
- 用户删除文档时，任务可能还在跑。
- 任务最终失败后需要可见、可查、可补偿。

所以异步任务一定要配合：

- **状态机**：pending、processing、completed、failed。
- **幂等处理**：重建前清理旧 chunk、旧索引、旧图谱。
- **重试策略**：网络抖动可重试，参数错误不应重试。
- **死信队列**：重试耗尽后沉淀失败上下文。
- **可观测性**：trace 贯穿 HTTP 请求和 worker。

#### 可直接复述的面试回答

文档处理必须异步，因为它不是一个稳定的短操作。解析 PDF、调用 Embedding、写向量库、生成摘要和 Wiki 都可能很慢，也可能依赖外部服务失败。如果同步放在上传请求里，用户请求容易超时，API 服务也会被大文件拖垮。WeKnora 用 Asynq 做后台任务，上传接口只负责校验、保存和入队，worker 再处理解析和索引。可靠性上，任务执行时会通过状态机让前端知道当前进度；重试时会先清理旧 chunk 和旧索引来保证幂等；最终失败会写 dead-letter，方便后续排查和补偿。

#### 常见追问

- 如果 Redis 不可用，上传接口是否应该返回成功？
- 如何判断一个错误是否可重试？
- dead-letter 之后如何人工恢复？
- worker 如何做限流？

#### 常见坑

不要说“异步就是为了更快”。异步并不会让单个文档更快解析，它的核心价值是解耦请求、削峰、重试和提升系统可用性。

### Q3：如何保证文档重复处理不会产生重复索引？

#### 面试官为什么问

这是大厂非常爱问的幂等性问题。异步系统一定会遇到重试、重复投递和用户重复点击。

#### 先给结论

我会把文档处理任务设计成以 knowledge 为粒度的幂等重建。

#### 回答思路

从两个层次回答：上传阶段防重复，处理阶段保证幂等。

#### 结合我的项目怎么答

上传阶段，系统通过文件名、文件大小和文件 hash 判断同一知识库下是否已有相同文件。如果存在，会返回 duplicate 类型错误，同时可以更新已有记录的创建时间。

处理阶段，真正关键的是“重建式幂等”。在 `processChunks` 里，系统在写新 chunk 和索引前，会先做清理：

- 删除该 knowledge 下已有 chunks。
- 删除该 knowledge 在向量/关键词索引里的旧数据。
- 删除该 knowledge 对应的图谱数据。
- 再基于最新解析结果重新写入 chunks 和索引。

这意味着任务重试不是追加写，而是“以 knowledge 为单位重建”。这样即使任务重复执行，也不容易出现同一个文档下多份 chunk 污染召回。

#### 技术原理 / 链路设计讲解

幂等性常用三种思路：

- **唯一键幂等**：用 file hash、dedup key、task id 防止重复创建。
- **状态机幂等**：同一状态下重复操作不会改变结果。
- **重建式幂等**：先删除旧产物，再写新产物。

RAG 入库比较适合重建式幂等，因为 chunk、向量、图谱都是由原文派生出来的产物。只要原始 knowledge ID 不变，就可以把派生产物清掉后重新生成。

但这里要注意：DB、向量库、图谱库不是同一个事务。如果删除旧向量成功、写新向量失败，系统可能处于中间态。所以需要把 knowledge 标记为 failed 或 processing，不要让用户误以为它可用，并且支持重新处理。

#### 可直接复述的面试回答

我会把文档处理任务设计成以 knowledge 为粒度的幂等重建。上传阶段先用文件名、大小和 hash 做重复检测，避免同一 KB 下重复创建同一文件。后台处理阶段更关键：每次重新处理前，先删除这个 knowledge 旧的 chunk、旧的向量/关键词索引和旧的图谱数据，然后再根据最新解析结果重新写入。这样任务即使因为超时或 worker 重启被重复执行，也不会变成追加写，避免同一文档产生多份重复索引。

#### 常见追问

- 删除旧索引失败时要不要继续？
- 如何处理向量库删除成功但 DB 删除失败？
- 有没有可能旧索引删除了，新索引没写成功？

#### 常见坑

不要承诺跨 DB、向量库、图谱库的强一致事务。真实回答要说最终一致、失败状态、重试和补偿。

### Q4：分块策略怎么讲才能显得专业？

#### 面试官为什么问

分块是 RAG 效果的关键，也是最能区分“会背概念”和“懂实践”的问题。

#### 先给结论

分块不是简单按固定长度切。它直接影响召回质量：chunk 太小，匹配精确但缺上下文；chunk 太大，上下文完整但语义会被稀释。

#### 回答思路

不要只说 chunk size。要讲：

- 为什么分块影响召回。
- 不同文档类型如何切。
- chunk size 和 overlap 的取舍。
- parent-child 如何兼顾精确召回和上下文完整性。
- 分块后如何调试和评估。

#### 结合我的项目怎么答

WeKnora 的 chunking 不是固定长度切割，而是自适应三层策略：

- **heading-aware**：适合 Markdown 或结构化标题文档，按 `#`、`##`、`###` 切，并把标题路径作为 context header 放到 embedding 内容里。
- **heuristic**：适合 PDF 风格文档，根据页分隔、编号章节、多语言章节标记、全大写标题、视觉分隔线等信号切分。
- **legacy/recursive**：兜底策略，按照分隔符递归切分，并控制 overlap。

parent-child chunking 进一步把索引粒度和上下文粒度拆开：child chunk 小，用于向量召回；parent chunk 大，用于给 LLM 提供完整上下文。项目里 parent chunk 会写 DB，但通常不进入向量索引，child/flat chunk 才参与索引。

#### 技术原理 / 链路设计讲解

chunk 太小：

- 语义集中，向量匹配准。
- 但上下文不足，答案可能缺前因后果。
- 容易把一个完整逻辑切断。

chunk 太大：

- 上下文完整。
- 但 embedding 表达被稀释，一个 chunk 里多个主题会互相干扰。
- 检索命中后塞给 LLM 的噪声更多。

overlap 的意义是减少边界信息丢失，但 overlap 太大会增加索引量、成本和重复结果。

#### 可直接复述的面试回答

分块不是简单按固定长度切。它直接影响召回质量：chunk 太小，匹配精确但缺上下文；chunk 太大，上下文完整但语义会被稀释。WeKnora 用自适应策略处理不同文档，Markdown 类文档优先按标题切，并把标题路径作为 context header；PDF 类文档根据页码、章节号、分隔线等启发式信号切；没有结构时再走 recursive fallback。对于长文档，还可以用 parent-child chunking：用小 child chunk 做召回，用大 parent chunk 给 LLM 提供上下文，这样兼顾匹配精度和答案完整性。

#### 常见追问

- chunk size 为什么默认 512 左右？
- overlap 为什么不是越大越好？
- PDF OCR 质量差时，分块能不能解决？
- 表格怎么分块？

#### 常见坑

不要说“chunk 越小越准”。小 chunk 只是召回粒度更细，不等于答案质量更好。

### Q5：如果用户上传成功但问不到内容，你怎么排查？

#### 面试官为什么问

这是非常真实的线上排障题。回答要按链路逐层定位。

#### 先给结论

如果用户说上传成功但问不到，我不会直接判断是模型问题。

#### 回答思路

按“状态 -> 解析 -> chunk -> embedding -> 索引 -> 检索范围 -> 查询参数”的顺序查。

#### 结合我的项目怎么答

我会这样排查：

1. 看 knowledge 状态是否 completed/enabled。如果还在 pending/processing，说明后台任务没完成。
2. 看 failed 状态和 error_message，判断是解析失败、模型失败还是索引失败。
3. 查 Asynq 任务和 `task_dead_letters`，看 `document:process` 有没有最终失败。
4. 查 chunk 表，确认是否生成了有效 chunk，内容是否为空、乱码或切得太碎。
5. 查 embedding 和向量库写入日志，确认维度是否匹配，索引是否写入成功。
6. 看知识库的 indexing strategy 是否启用了 vector/keyword。
7. 看问答时选中的知识库/知识条目是否包含这个文档，是否被租户权限或共享范围过滤。
8. 看 retrieval config 的 TopK、threshold 是否过严。
9. 用同样 query 做知识搜索，看是否能召回相关 chunk。
10. 看 Langfuse trace 和 pipeline 日志，判断是没召回，还是召回后 rerank/filter 掉了。

#### 可直接复述的面试回答

如果用户说上传成功但问不到，我不会直接判断是模型问题。我会先看 knowledge 状态是不是 completed/enabled；如果 failed，就看 error message 和 dead-letter。然后看 chunk 是否生成、内容是否正常，再看 embedding 和向量索引是否写入成功，特别是模型维度和向量库 collection 是否匹配。接着看用户问答时选择的知识库范围、租户权限和 indexing strategy 是否正确。最后看检索阶段的 TopK、threshold、rerank 日志和 Langfuse trace，判断是没召回、被 rerank 过滤，还是召回了但模型没用上下文回答。

#### 常见追问

- 如果 chunk 有但检索不到，怎么办？
- 如果检索到了但模型没答出来，怎么办？
- 如果 PDF 解析出来都是乱码，怎么办？

#### 常见坑

不要第一反应说“换模型”。RAG 问不到内容，经常是状态、索引、范围或阈值问题。

## 5. 本主题总结

文档入库要讲出这几个关键词：异步管道、状态机、幂等重建、分块策略、Embedding 维度、索引一致性、失败可见、最终一致。

最强的面试表达是：文档入库不是上传文件，而是把原始非结构化数据稳定地转成可检索、可追踪、可重建的知识资产。
