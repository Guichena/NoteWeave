# 文件：12_RAG在线问答深挖版.md

## 1. 本主题面试官想考什么

RAG 在线问答是项目最容易被问穿的一块。面试官会用连续追问判断你是不是真的理解：query 如何理解，为什么要混合检索，召回和排序如何分工，rerank 怎么调，为什么要 MMR，如何构造 prompt，如何降低幻觉，如何定位回答不准。

一句话总结：RAG 的关键不是“查向量库”，而是把用户问题、知识范围、召回策略、排序策略和生成约束组织成一条可调试的在线链路。

## 2. 高频问题清单

### 基础问题

- 为什么需要先检索再生成？

- 为什么需要 rerank？

### 进阶问题

- 如何控制 prompt 上下文长度？

### 深挖追问

- 如何减少 hallucination？

### 压力追问

## 3. RAG 链路总览

WeKnora 的在线 RAG 可以概括为：

```text
用户问题
-> 会话/租户/知识库范围解析
-> 加载历史和用户记忆
-> Query Understand / Rewrite / Expansion
-> 并行检索：Chunk Search + Entity/Graph Search + 可选 Web Search
-> 候选结果融合
-> Rerank
-> MMR / 去重 / TopK 过滤
-> Prompt 构造
-> LLM 流式生成
-> 返回答案 + references
```

面试里你要特别强调：RAG 是多阶段质量控制，不是单点模型能力。

## 4. 深度问答与讲解

### Q1：请你完整讲一下 RAG 在线问答链路

#### 面试官为什么问

这是检验你是否真正理解系统主链路的问题。回答越有层次，越能体现项目经验。

#### 先给结论

WeKnora 的 RAG 在线链路不是简单查向量库。

#### 回答思路

用“请求解析 -> 检索 -> 排序 -> 生成 -> 观测”五段回答。

#### 结合我的项目怎么答

在 WeKnora 里，用户发起问答后，后端首先会解析请求上下文：当前 session、tenant、用户选择的 knowledge base 或具体 knowledge、是否启用 web search、是否携带图片/附件、是否使用自定义 Agent 配置等。

然后系统会选择模型和检索参数，比如 chat model、embedding topK、vector threshold、keyword threshold、rerank topK、rerank threshold、fallback strategy 等。

如果没有知识库、也没有 web search，就可以走纯聊天链路；如果需要 RAG，就动态组装 pipeline：

- `LOAD_HISTORY`：加载多轮历史。
- `QUERY_UNDERSTAND`：判断查询意图、实体、是否需要检索。
- `CHUNK_SEARCH_PARALLEL`：并行做 chunk 检索和实体/图谱检索。
- `CHUNK_RERANK`：对候选结果重新排序和过滤。
- `WEB_FETCH`：如果启用 web search，抓取网页内容。
- `CHUNK_MERGE`：合并候选片段。
- `FILTER_TOP_K`：控制最终上下文数量。
- `DATA_ANALYSIS`：如果启用数据分析，执行结构化分析。
- `INTO_CHAT_MESSAGE`：把结果拼成模型上下文。
- `CHAT_COMPLETION_STREAM`：调用大模型流式生成。

最后，系统会把 references 作为事件返回给前端，让用户看到答案来源。

#### 技术原理 / 链路设计讲解

RAG 之所以不是“直接问模型”，是因为企业知识通常是私有的、更新频繁的、模型训练时不知道的。检索增强生成把“事实依据”从参数知识中移到外部知识库中。

在线链路每一层解决不同问题：

- query understand 解决“用户到底想问什么、需不需要检索”。
- search 解决“尽量召回相关内容”。
- rerank 解决“把真正相关内容排前面”。
- merge/filter 解决“去重、控长度、保多样性”。
- prompt 构造解决“让模型基于证据回答”。
- streaming 解决“降低用户感知等待”。

#### 可直接复述的面试回答

WeKnora 的 RAG 在线链路不是简单查向量库。请求进来后，系统先解析 session、租户、知识库范围、模型配置和检索参数。如果当前问题需要知识增强，就进入 RAG pipeline：先加载历史，再做 query understand，判断是否需要检索并提取实体；然后并行做 chunk 检索和实体/图谱检索，必要时加 web search；候选结果会经过 rerank、合并、去重和 TopK 过滤；最后把高质量上下文拼进 prompt，调用大模型流式生成答案，并把 references 返回给前端。这个链路的目标是把召回覆盖、排序精度、上下文质量和生成约束分层处理。

#### 常见追问

- 什么情况下不走 RAG？
- RAG pipeline 中哪一步最影响准确率？
- references 和最终答案如何对应？

#### 常见坑

不要说“RAG 就是向量库查 TopK”。这会让面试官认为你只停留在 Demo 层。

### Q2：为什么需要混合检索？向量检索不够吗？

#### 面试官为什么问

这是检索系统的经典问题。面试官想看你是否理解不同召回器的能力边界。

#### 先给结论

向量检索不够，因为它擅长语义相似，但对错误码、字段名、版本号、接口名这类精确匹配不一定稳定。

#### 回答思路

对比四种检索：

- 向量检索：语义相似。
- 关键词/BM25：精确词、字段、编号、报错。
- 图谱检索：实体关系、多跳关联。
- Web search：知识库外的外部信息。

#### 结合我的项目怎么答

WeKnora 支持 `vector`、`keywords`、`websearch` 等 retriever type，也支持 GraphRAG。检索配置里有 vector threshold、keyword threshold、RRF 权重、TopK 等参数。`CHUNK_SEARCH_PARALLEL` 中 chunk search 和 entity search 可以并行执行。

#### 技术原理 / 链路设计讲解

向量检索擅长处理同义表达，比如用户问“怎么接入统一登录”，文档写的是“OIDC 认证流程”。Embedding 可以把它们映射到相近语义空间。

但向量检索对这些内容不一定稳定：

- 错误码：`E1043`。
- 字段名：`vector_store_id`。
- 版本号：`000043 migration`。
- 产品名、人名、接口名。
- 短 query：`配置失败怎么办`。

关键词检索对精确匹配更好。图谱检索则适合实体关系，比如“某个模块依赖哪些服务”“这个 Agent 关联哪些知识库”。所以真实系统一般用多路召回，再通过融合和 rerank 控制精度。

#### 可直接复述的面试回答

向量检索不够，因为它擅长语义相似，但对错误码、字段名、版本号、接口名这类精确匹配不一定稳定。企业知识库里大量问题恰恰包含这些专有词。WeKnora 同时支持 vector 和 keywords 检索，还可以结合 GraphRAG 和 web search。我的理解是，第一阶段检索要追求召回覆盖，所以多路召回更稳；后面再用 RRF、rerank、MMR 和 TopK 过滤来控制噪声。

#### 常见追问

- 多路召回结果分数不可比怎么办？
- RRF 的作用是什么？
- 关键词检索结果很多噪声怎么办？

#### 常见坑

不要贬低关键词检索。企业场景中，关键词经常是召回关键事实的最好方式。

### Q3：Rerank 到底解决什么问题？怎么调？

#### 面试官为什么问

Rerank 是 RAG 效果优化的核心点。面试官通常会继续追问成本、延迟和阈值。

#### 先给结论

Rerank 解决的是第一阶段召回“覆盖够但排序不准”的问题。

#### 回答思路

先讲召回和排序分工：

- 第一阶段检索：快，覆盖广，但噪声多。
- Rerank：慢一些，但相关性判断更准，只对候选集做。

#### 结合我的项目怎么答

WeKnora 的 rerank 插件会对 SearchResult 构造 passage，跳过 DirectLoad 结果，调用 rerank 模型。对于空 passage 会过滤掉，避免模型报错。如果阈值过高导致无结果，并且原阈值大于 0.3，会做一次阈值降级重试。之后会计算 composite score，还支持 FAQ boost 和 MMR。

#### 技术原理 / 链路设计讲解

Embedding 检索通常是 bi-encoder：query 和 document 分别编码，查询时做相似度计算。它速度快，适合全库召回，但因为 query 和 passage 没有深度交互，排序不一定准确。

Rerank 通常更像 cross-encoder：把 query 和 passage 一起输入模型，让模型判断相关性。它更准，但成本更高，所以只能对前几十个候选做。

阈值取舍：

- 阈值太高：精度高，但可能无结果。
- 阈值太低：召回多，但噪声污染 prompt。
- TopK 太小：可能漏掉答案。
- TopK 太大：增加 rerank 成本和 prompt 噪声。

#### 可直接复述的面试回答

Rerank 解决的是第一阶段召回“覆盖够但排序不准”的问题。向量和关键词检索为了速度和召回，会先拿到一批候选片段，但这些候选里可能有语义相近却不真正回答问题的内容。Rerank 会用更强的相关性模型对 query-passage 重新打分，只对 TopK 候选做，所以成本可控。WeKnora 里还做了空 passage 过滤、阈值降级、composite score、FAQ boost 和 MMR，目的是在不显著牺牲延迟的情况下提高最终上下文质量。

#### 常见追问

- 如果 rerank 模型挂了怎么办？
- rerank 阈值怎么定？
- rerank 是否一定提升效果？

#### 常见坑

不要说“rerank 可以解决所有召回问题”。如果正确答案第一阶段没召回，rerank 没法凭空找出来。

### Q4：如果回答不准，你如何定位是哪个环节的问题？

#### 面试官为什么问

这是 RAG 项目的高频排障题。能不能分层定位，是面试加分点。

#### 先给结论

回答不准我会先把问题分成召回、排序和生成三类。

#### 回答思路

按 RAG 错误链路拆：

1. 文档是否解析正确。
2. chunk 是否合理。
3. embedding 是否成功。
4. 检索是否召回正确 chunk。
5. rerank 是否把正确 chunk 排前。
6. merge/filter 是否把正确 chunk 过滤掉。
7. prompt 是否包含正确依据。
8. LLM 是否遵循上下文。
9. 权限/知识库范围是否选错。

#### 结合我的项目怎么答

在 WeKnora 中，可以从 references、pipeline 日志、Langfuse trace、chunk 预览、knowledge 状态和 dead-letter 入手。

典型定位方法：

- 如果 references 没有正确文档：查检索范围、chunk、向量索引、关键词索引、threshold。
- 如果 references 有正确文档但排序靠后：查 rerank、MMR、TopK。
- 如果 references 正确但答案错：查 prompt 模板、上下文拼接、模型能力、fallback 策略。
- 如果只有某个用户问不到：查租户权限、共享范围、Agent 知识库授权。
- 如果所有用户都问不到：查索引、模型、向量库和配置。

#### 技术原理 / 链路设计讲解

RAG 错误可以分成三大类：

- **召回错误**：正确内容没进入候选集。
- **排序错误**：正确内容召回了，但没进入最终上下文。
- **生成错误**：正确上下文给了模型，但模型没基于上下文回答。

这三类错误的优化方向完全不同。召回错误调分块、Embedding、query rewrite、TopK 和混合检索；排序错误调 rerank、MMR、阈值；生成错误调 prompt、上下文压缩、模型和引用约束。

#### 可直接复述的面试回答

回答不准我会先把问题分成召回、排序和生成三类。第一看 references 有没有正确 chunk，如果没有，说明召回层有问题，要查文档解析、分块、Embedding、索引、知识库范围和检索阈值。如果正确 chunk 召回了但没进入最终上下文，就查 rerank、MMR、TopK 和过滤逻辑。如果正确上下文已经给到模型但答案仍然错，就看 prompt 是否约束模型基于资料回答、上下文是否太长太乱、模型是否忽略证据。这样排查比直接换模型更可靠。

#### 常见追问

- 正确 chunk 没召回时优先改什么？
- 召回正确但模型幻觉怎么办？
- 如何设计评测集证明优化有效？

#### 常见坑

不要所有问题都归因于 LLM。RAG 答错更多时候是检索和上下文问题。

### Q5：为什么不用长上下文模型直接塞全文？

#### 面试官为什么问

这是压力追问，考察成本意识和系统设计判断。

#### 先给结论

长上下文模型有价值，但不能替代 RAG。企业知识库可能有几万份文档，每次把全文塞给模型成本和延迟都不可接受，而且长上下文不保证模型一定能关注到正确位置。

#### 回答思路

承认长上下文有价值，但说明不适合作为唯一方案。

#### 结合我的项目怎么答

长上下文模型可以减少一部分检索复杂度，适合小文档、临时分析、上下文必须完整的场景。但企业知识库不能把全文都塞进去：

- 文档数量巨大，不可能每次塞整个知识库。
- 成本高，token 费用和延迟都会上升。
- 上下文越长，模型注意力不一定稳定，可能“看过但没用”。
- 权限过滤困难，必须先做知识范围控制。
- 引用和可解释性差，用户很难知道答案来自哪里。
- 文档更新频繁，每次请求重新塞全文浪费。

RAG 的价值是先用检索把候选范围缩小，再把高相关依据交给模型。

#### 可直接复述的面试回答

长上下文模型有价值，但不能替代 RAG。企业知识库可能有几万份文档，每次把全文塞给模型成本和延迟都不可接受，而且长上下文不保证模型一定能关注到正确位置。RAG 的思路是先通过权限和知识范围过滤，再用混合检索把相关内容缩小到几十个候选，rerank 后只把最相关证据放进 prompt。这样成本、延迟、可解释性和权限控制都更可控。长上下文更适合作为 RAG 后的上下文承载能力，而不是替代检索。

#### 常见追问

- 如果模型上下文 1M token 呢？
- 小知识库是否可以直接塞全文？
- 长上下文和 RAG 如何结合？

#### 常见坑

不要绝对否定长上下文。更成熟的说法是：长上下文和 RAG 是互补关系。

### Q6：如何减少 RAG 幻觉？

#### 面试官为什么问

RAG 系统最终被用户评价的是答案可信度。幻觉控制是落地关键。

#### 先给结论

RAG 幻觉要分层控制。首先检索层要保证证据相关，不能把一堆噪声塞给模型；其次 rerank 和 TopK 要过滤掉低质量片段；然后 prompt 要明确要求模型基于上下文回答，没有依据就说无法确定；如果没有命中结果，要走 fallback，而不是让模型自由发挥。

#### 回答思路

从四层控制：

- 检索层：提高证据相关性。
- Prompt 层：要求基于引用回答，不足则说明无法确定。
- 生成层：控制温度、max tokens、fallback。
- 产品层：展示 references，让用户可验证。

#### 结合我的项目怎么答

减少幻觉不是一句 prompt 能解决。可以从以下方面做：

1. 确保正确 chunk 能召回。
2. Rerank/filter 去掉明显无关内容。
3. Prompt 中明确要求“基于给定上下文回答，没有依据时说明不知道”。
4. 对低置信度或无检索结果使用 fallback response，而不是让模型自由发挥。
5. 展示 references 和引用来源。
6. 对用户问题做 query understand，避免不需要检索的问题强行拼噪声上下文。
7. 使用较低 temperature，降低创造性。
8. 对敏感领域增加人工审核或答案置信度提示。

#### 可直接复述的面试回答

RAG 幻觉要分层控制。首先检索层要保证证据相关，不能把一堆噪声塞给模型；其次 rerank 和 TopK 要过滤掉低质量片段；然后 prompt 要明确要求模型基于上下文回答，没有依据就说无法确定；如果没有命中结果，要走 fallback，而不是让模型自由发挥。产品上还要展示 references，让用户能看到答案来源。也就是说，减少幻觉不是只靠 prompt，而是召回、排序、上下文构造、生成参数和引用展示一起控制。

#### 常见追问

- 无结果时怎么回答？
- 如何判断答案是否有依据？
- 是否可以让模型自己打置信度？

#### 常见坑

不要说“加一句不要幻觉就行”。这会显得非常不工程化。

## 5. 本主题总结

RAG 面试要讲出四层：

- **召回**：vector、keywords、graph、web search。
- **排序**：rerank、RRF、MMR、threshold。
- **上下文**：merge、filter、prompt template、引用。
- **生成**：streaming、fallback、低幻觉约束。

最强表达是：RAG 的稳定性来自分层控制，而不是依赖某一个模型。
