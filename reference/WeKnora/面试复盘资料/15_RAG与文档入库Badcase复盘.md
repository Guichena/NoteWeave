# 文件：15_RAG与文档入库Badcase复盘.md

## 1. 本主题面试官想考什么

面试官问 badcase，不是在听你讲“系统理论上怎么设计”，而是在判断你有没有真实排障经验。大厂面试里，一个能讲清楚 badcase 的候选人，通常比一个只会背完整链路的人更可信。

这个主题重点考察：

- 你是否能把问题从现象拆到链路层。
- 你是否能区分解析、分块、召回、排序、生成、权限、异步一致性等不同错误来源。
- 你是否有修复方案和验证方式。
- 你是否能讲出“优化前后发生了什么变化”。

说明：以下 badcase 结合当前 WeKnora 项目链路整理，其中具体指标需要你替换成自己的真实数据。如果没有线上数据，可以在面试中明确说“这是我基于项目链路做的复盘模板，真实项目中会用 Recall@K、人工评测和 trace 数据验证”。

## 2. 高频问题清单

### 基础问题

- 你遇到过哪些 RAG 回答不准的 case？
- 用户上传成功但问不到内容，可能是什么原因？
- 文档解析失败会怎么影响后续链路？
- 如何判断是检索问题还是模型生成问题？

### 进阶问题

- 正确 chunk 没召回，你怎么优化？
- chunk 召回了但答案错，你怎么优化？
- Rerank 阈值过高导致无结果，怎么处理？
- 如何处理 PDF OCR 质量差导致的问答失败？

### 深挖追问

- 你怎么构造 badcase 评测集？
- 修复后怎么证明真的有效？
- 如何避免一个 badcase 的修复伤害其他场景？
- 如果 badcase 是权限过滤导致的，怎么定位？

### 压力追问

- 你是不是只会“换模型”？
- 为什么不是直接调大 TopK？
- 为什么不是直接降低 threshold？
- badcase 复盘有没有沉淀成自动化测试？
- 如果面试官现场给你一个错误回答，你会怎么排查？

## 3. Badcase 总体分类

建议你在面试中先给出一个分类框架，这会显得非常稳：

```text
RAG badcase
├─ 入库侧问题
│  ├─ 原文解析失败
│  ├─ OCR/表格/图片信息丢失
│  ├─ 分块不合理
│  ├─ Embedding/索引写入失败
│  └─ 文档状态未完成
├─ 检索侧问题
│  ├─ query rewrite 错误
│  ├─ 向量召回不到精确词
│  ├─ 关键词召回噪声过大
│  ├─ 知识库范围/权限过滤错误
│  └─ TopK/threshold 配置不合理
├─ 排序侧问题
│  ├─ rerank 阈值过高
│  ├─ rerank 模型误判
│  ├─ MMR 去重导致正确片段被挤掉
│  └─ FAQ/文档优先级不合理
├─ 生成侧问题
│  ├─ prompt 没有约束基于资料回答
│  ├─ 上下文太长或太乱
│  ├─ 模型忽略引用
│  └─ fallback 策略不合理
└─ 异步一致性问题
   ├─ 上传成功但索引未完成
   ├─ 删除和后台任务并发
   ├─ 旧索引未清理
   └─ dead-letter 未处理
```

面试中可以先说：“我一般不会把 badcase 直接归因于模型，而是按入库、召回、排序、生成、一致性五层定位。”

## 4. Badcase 复盘

### Case 1：上传成功但用户问不到内容

#### 现象

用户上传了一份 PDF，前端显示上传成功，但在对话中问文档里的内容时，系统回答“没有找到相关资料”或直接走 fallback。

#### 面试官为什么问

这是最真实的线上问题之一。它考察你是否知道“上传成功”和“索引完成”不是一回事。

#### 排查路径

1. 先查 knowledge 状态：
   - 如果是 `pending` 或 `processing`，说明异步任务还没完成。
   - 如果是 `failed`，看 `error_message`。
   - 如果是 `completed/enabled`，继续查索引链路。
2. 查 Asynq 任务：
   - `document:process` 是否执行。
   - 是否进入 `task_dead_letters`。
3. 查 chunk：
   - 是否生成 chunk。
   - chunk 内容是否为空、乱码、重复或过碎。
4. 查索引：
   - Embedding 是否成功。
   - 向量维度是否和 collection 一致。
   - vector/keyword indexing strategy 是否开启。
5. 查问答范围：
   - 当前 session 是否选中了该 KB。
   - 当前用户是否有该 KB 的 read 权限。
   - Agent 是否限制了知识库范围。
6. 查检索参数：
   - TopK 是否过小。
   - threshold 是否过高。
   - rerank 是否过滤掉正确结果。

#### 结合项目怎么答

WeKnora 的上传接口会创建 knowledge 记录并投递 `document:process`，但真正可问答要等后台解析、分块、Embedding、索引完成。项目里可以通过 knowledge 的 parse status、Asynq 任务状态、dead-letter、chunk 表、Langfuse trace 和 pipeline references 来定位。

#### 技术原理 / 链路设计讲解

这是典型的异步最终一致问题。HTTP 上传接口返回成功，只代表文件接收和任务提交成功，并不代表检索索引已经可用。为了避免用户误解，系统需要：

- 明确展示处理状态。
- 未完成时不允许误导为可问答。
- 失败时展示可理解错误。
- 提供重新处理入口。

#### 可直接复述的面试回答

这个 case 我会先强调上传成功不等于可问答。WeKnora 里上传接口只完成校验、保存文件、创建 knowledge 和投递异步任务，真正可问答要等 document:process 完成。排查时我会先看 knowledge 状态，如果还在 pending/processing，就是后台还没完成；如果 failed，就查 error message 和 dead-letter；如果 completed，就继续查 chunk 是否生成、Embedding 和向量索引是否写入、知识库范围和权限是否正确。最后再看检索阶段的 TopK、threshold 和 rerank 日志，判断是不是被过滤掉。

#### 修复方案

- 前端明确展示“解析中 / 索引中 / 可问答 / 失败”。
- 对 failed 状态提供重新处理入口。
- 对任务入队失败增加补偿或告警。
- 对 dead-letter 增加后台管理和重放能力。

#### 验证方式

- 构造上传后立即查询、处理完成后查询、失败后查询三类用例。
- 统计“上传成功但问不到”的用户反馈数量。
- 检查 knowledge 状态与搜索可见性是否一致。

#### 常见追问

- 如果任务入队失败，文件已经保存了怎么办？
- 如果索引写入失败但 chunk 写成功，状态应该是什么？
- 你如何让用户知道还能不能问？

#### 常见坑

不要说“上传成功后马上可以问”。这是异步系统里最容易被面试官抓住的问题。

### Case 2：PDF 解析乱码或内容为空，导致 RAG 无法召回

#### 现象

用户上传扫描版 PDF 或复杂排版 PDF，系统生成了 chunk，但 chunk 内容大量乱码、断行、空白，问答时找不到正确内容。

#### 面试官为什么问

这是文档解析系统的真实难点。面试官想看你是否知道 RAG 效果不只由检索决定，入库质量是上游根因。

#### 排查路径

1. 查看 docreader 解析结果。
2. 查看 chunk 内容预览。
3. 判断是文本型 PDF、扫描 PDF、图片 PDF 还是混合 PDF。
4. 查看 OCR/VLM 配置是否启用。
5. 查看 chunk 是否因异常换行被切碎。
6. 对比原文和解析文本，确认信息丢失点。

#### 技术原理 / 链路设计讲解

RAG 的输入是解析后的文本，不是原 PDF。如果 PDF 解析阶段已经丢失语义，后面的 chunk、Embedding、rerank 都救不回来。

常见问题：

- 扫描件没有 OCR，解析结果为空。
- 双栏 PDF 解析顺序错乱。
- 表格被拆成碎片。
- 页眉页脚大量重复。
- 中文 OCR 断字、空格异常。

#### 可直接复述的面试回答

如果 PDF 解析出来就是乱码或空内容，后面检索调参基本救不了。RAG 的基础是有效文本，所以我会先看 docreader 的解析结果和 chunk 预览，确认是扫描件、复杂排版还是 OCR 问题。扫描件需要启用 OCR 或 VLM，复杂 PDF 可能要优化解析策略，比如去页眉页脚、处理多栏顺序、对表格单独抽取。这个 case 的核心不是换 Embedding，而是先保证入库文本质量。

#### 修复方案

- 为扫描 PDF 启用 OCR/VLM。
- 对 PDF 解析结果做清洗：去页眉页脚、去重复页码、合并异常断行。
- 对表格单独走表格解析和摘要。
- 对空 PDF 禁止根据文件名生成摘要，避免幻觉。

#### 验证方式

- 抽样对比原文和解析文本覆盖率。
- 统计 chunk 空内容比例、乱码比例。
- 用固定问题集测试解析优化前后 Recall@K。

#### 常见追问

- OCR 成本高怎么办？
- 表格被解析坏了怎么办？
- PDF 多栏顺序错乱怎么处理？

#### 常见坑

不要把解析质量问题归因于向量库。上游文本坏了，下游只会更坏。

### Case 3：向量检索召回不到错误码、字段名、接口名

#### 现象

用户问“错误码 E1043 怎么处理”或“vector_store_id 是什么”，系统没有召回对应文档，或者召回了语义相近但不包含精确词的片段。

#### 面试官为什么问

这个问题考察你是否理解向量检索的边界，以及为什么需要混合检索。

#### 排查路径

1. 用原始 query 做向量检索，看是否命中。
2. 用关键词检索精确词，看是否命中。
3. 查看 query rewrite 是否把关键字改写掉。
4. 查看关键词索引是否启用。
5. 查看 RRF/融合权重。
6. 查看 rerank 是否过滤精确匹配结果。

#### 技术原理 / 链路设计讲解

向量检索擅长语义相似，但不一定擅长精确 token。错误码、字段名、接口名、版本号在 embedding 空间里可能没有足够语义，甚至被 tokenizer 切得很碎。

解决方案是混合检索：

- 向量召回语义相近内容。
- BM25/关键词召回精确词。
- RRF 融合排名。
- rerank 做最终相关性判断。

#### 可直接复述的面试回答

这个 case 很典型，说明纯向量检索不够。错误码、字段名、接口名这种精确词，向量检索可能认为它没有明显语义，从而召回不到。我的处理思路是保留关键词检索通道，对精确词用 BM25 或关键词索引召回，再和向量召回做融合。还要注意 query rewrite 不能把关键字段改没了。最后通过 rerank 让真正回答问题的片段排到前面。

#### 修复方案

- 开启关键词检索。
- query rewrite 保留专有词、错误码、字段名。
- 对精确词 query 提高关键词权重。
- 对接口文档、错误码文档使用特殊分块策略。

#### 验证方式

- 构造错误码、字段名、接口名专项评测集。
- 比较纯向量 vs 混合检索的 Recall@K。
- 检查 query rewrite 前后是否保留关键 token。

#### 常见追问

- 为什么不用纯 Elasticsearch？
- RRF 为什么比直接分数相加更稳？
- 关键词检索噪声太多怎么办？

#### 常见坑

不要说“换更好的 embedding 模型就够了”。混合检索仍然是企业知识库的稳定方案。

### Case 4：Rerank 阈值过高，正确结果被过滤

#### 现象

第一阶段检索已经召回正确 chunk，但最终 references 为空或没有正确片段，回答走 fallback。

#### 面试官为什么问

这个问题考察你是否理解召回和排序的分工，以及阈值调参的风险。

#### 排查路径

1. 查看第一阶段 SearchResult。
2. 查看 rerank input passage 是否为空或被清洗掉。
3. 查看 rerank score 分布。
4. 查看 rerank threshold 是否过高。
5. 查看 fallback 是否被触发。
6. 检查 MMR/TopK 是否把正确结果挤掉。

#### 结合项目怎么答

WeKnora 的 `PluginRerank` 中已经考虑了这个问题：当 rerank 阈值过高导致无结果，且原阈值大于 0.3 时，会把阈值降级重试，最低不低于 0.3。这是典型工程兜底。

#### 技术原理 / 链路设计讲解

rerank 阈值不是越高越好。阈值高能减少噪声，但也会把弱相关但有用的片段过滤掉。尤其在中文、专业术语、短 query 或模型不适配领域语料时，rerank 分数可能整体偏低。

#### 可直接复述的面试回答

如果第一阶段召回了正确 chunk，但最终没有进入上下文，我会重点看 rerank 和过滤阶段。Rerank 阈值太高会提高精度，但也可能直接把正确片段过滤掉。WeKnora 里有阈值降级机制：如果高阈值下没有结果，会降低阈值再尝试一次，避免直接 fallback。面试中我会强调，rerank 是排序增强，不应该成为召回结果的硬杀器，阈值要基于评测集和 score 分布调。

#### 修复方案

- 记录 rerank score 分布。
- 对不同知识库/租户支持不同阈值。
- 对无结果场景做阈值降级。
- 对 DirectLoad 或用户显式选择文档绕过 rerank。

#### 验证方式

- 对比不同 rerank threshold 下的准确率和无结果率。
- 统计 fallback 触发率。
- 分析 score 分布，选择合理阈值。

#### 常见追问

- 阈值降级会不会引入噪声？
- Rerank 模型不稳定怎么办？
- 是否可以不用 rerank？

#### 常见坑

不要说“阈值高更准所以越高越好”。系统需要平衡准确率和可回答率。

### Case 5：召回正确但模型仍然幻觉

#### 现象

references 中已有正确文档，但最终答案仍然编造了不存在的内容，或者没有引用文档中的关键限制条件。

#### 面试官为什么问

这考察你是否理解生成阶段的控制，而不是只会调检索。

#### 排查路径

1. 查看最终 prompt 是否包含正确上下文。
2. 查看上下文是否过长、噪声过多。
3. 查看 prompt 是否要求“基于资料回答”。
4. 查看 temperature、max tokens。
5. 查看是否存在多轮历史干扰。
6. 查看模型是否支持当前语言和专业领域。

#### 技术原理 / 链路设计讲解

召回正确不等于答案正确。LLM 可能因为：

- 上下文太长，注意力分散。
- prompt 约束弱。
- 历史对话误导。
- 检索结果互相冲突。
- 模型倾向补全常识。

#### 可直接复述的面试回答

如果 references 已经有正确资料但模型答错，我会把问题归到生成层。首先检查最终 prompt 里是否真的包含正确上下文，然后看上下文是否太长或混入太多无关片段。接着检查 prompt 是否明确要求基于资料回答、没有依据就说明无法确定。必要时降低 temperature，压缩上下文，减少噪声，并把引用要求做得更强。这里不能再盲目调召回，因为召回已经成功了。

#### 修复方案

- 强化 prompt：必须基于上下文，不能编造。
- 控制上下文长度，减少噪声。
- 对冲突资料做显式提示。
- 增加 citation-aware answer 格式。
- 无依据时走 fallback。

#### 验证方式

- 构造“资料中没有答案”的负样本。
- 检查答案引用是否能回溯到 chunk。
- 人工标注 hallucination rate。

#### 常见追问

- 如何判断答案每句话都有依据？
- 模型自评置信度可靠吗？
- 多轮历史污染怎么处理？

#### 常见坑

不要以为 RAG 有 references 就不会幻觉。RAG 只是降低幻觉概率，不是消灭幻觉。

### Case 6：Wiki 删除后又被异步任务写回

#### 现象

用户删除某个文档后，相关 Wiki 页面或链接短时间后又出现了旧内容。

#### 面试官为什么问

这是异步一致性和生命周期管理的高价值 badcase。

#### 排查路径

1. 查看删除时间点。
2. 查看是否有正在执行的 `wiki:ingest`。
3. 查看 pending ops 中是否还有该 knowledge 的 op。
4. 查看 tombstone 是否写入。
5. 查看 Wiki 写回前是否检查 tombstone。
6. 查看 retract 是否正确处理页面贡献关系。

#### 技术原理 / 链路设计讲解

竞态场景：

```text
T1: wiki worker 开始处理 knowledge A
T2: 用户删除 knowledge A
T3: 删除逻辑清理 chunk / index / wiki 引用
T4: worker 完成处理，把 A 的 Wiki 内容写回
```

解决方案是 deleted tombstone：删除时写短期删除标记，worker 写回前检查该标记，如果存在则跳过。

#### 可直接复述的面试回答

这个问题本质是删除和异步生成并发。旧 worker 拿到的是删除前的任务上下文，如果写回前不检查状态，就会把已删除文档的 Wiki 内容重新写回来。WeKnora 的思路是删除 knowledge 时写 deleted tombstone，例如按 KB 和 knowledge ID 生成短期 key，TTL 覆盖 in-flight 任务窗口。wiki_ingest 在处理或写回前检查 tombstone，发现已删除就跳过。因为 LLM 调用、DB、Redis、图谱库无法放进一个事务，所以这里必须按最终一致和补偿来设计。

#### 修复方案

- 删除时写 tombstone。
- 写回前检查 tombstone 和 knowledge 状态。
- 清理 pending ops。
- Wiki retract 保留贡献来源，精确撤回。

#### 验证方式

- 构造删除和生成并发测试。
- worker 人为 sleep，删除后确认不会写回。
- 检查 Wiki 页面和引用是否最终一致。

#### 常见追问

- TTL 多长合适？
- tombstone 丢了怎么办？
- 多文档共同贡献一个页面如何撤回？

#### 常见坑

不要说“删除时把 Wiki 页面一起删掉”。Wiki 页面可能由多个文档共同贡献。

## 5. Badcase 面试表达模板

你可以用这个固定结构回答任何 badcase：

```text
这个问题我会先描述现象，然后按链路定位。
第一步看状态和范围，确认是不是异步未完成或权限过滤。
第二步看入库质量，包括解析、chunk、embedding、索引。
第三步看在线检索，确认正确 chunk 是否进入候选。
第四步看 rerank/filter，确认是否被排序或阈值过滤。
第五步看最终 prompt 和模型输出，判断是不是生成层幻觉。
最后给出修复方案，并用评测集或 trace 指标验证。
```

## 6. 本主题总结

Badcase 复盘最重要的不是“我知道怎么修”，而是“我知道怎么定位”。建议你至少背熟 3 个真实案例：

- 上传成功但问不到。
- 正确资料没召回。
- 召回正确但模型幻觉。
- Wiki 删除后又写回。

这些案例最能体现你对工程链路的理解。

## 7. 面试前自查清单

- 我是否准备了 3 个真实 badcase？
- 每个 badcase 是否有现象、定位、根因、修复、验证？
- 我是否能说明不是简单换模型？
- 我是否能说出优化前后的指标？
- 我是否能把 badcase 分类到入库、召回、排序、生成、一致性中的某一层？
