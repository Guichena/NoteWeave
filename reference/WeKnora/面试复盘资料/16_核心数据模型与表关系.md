# 文件：16_核心数据模型与表关系.md

## 1. 本主题面试官想考什么

面试官问数据模型，是想确认你是否真的理解系统落地。一个 RAG 项目如果只会讲“文档切块存向量库”，但讲不清 tenant、knowledge_base、knowledge、chunk、vector index、wiki_page、pending_ops、dead_letter 的关系，就很容易被认为只停留在概念层。

这个主题重点考察：

- 你是否知道核心实体是什么。
- 你是否知道实体之间的生命周期关系。
- 你是否知道哪些数据在 DB，哪些在对象存储，哪些在向量库/图数据库。
- 你是否理解多租户隔离和资源归属如何落到数据模型。
- 你是否能用数据模型解释入库、检索、删除、重建、Wiki 生成。

## 2. 高频问题清单

### 基础问题

- knowledge_base、knowledge、chunk 分别是什么？
- 原文件、chunk、向量索引分别存在哪里？
- tenant_id 为什么几乎每张核心表都要有？
- knowledge 的状态字段有什么意义？

### 进阶问题

- chunk 和向量库里的 index 如何关联？
- parent-child chunking 在表里怎么表达？
- Wiki page 如何关联原始文档？
- pending ops 和 dead-letter 分别解决什么问题？
- VectorStore 为什么是租户资源？

### 深挖追问

- 删除 knowledge 时，需要删除哪些派生数据？
- KB 绑定 VectorStore 后，异步任务如何保证不跨租户？
- 用户拿到 chunk_id 能否越权访问？
- Wiki 页面由多个文档共同贡献，删除一个文档时怎么处理？

### 压力追问

- 你们如何保证 DB 和向量库一致？
- 为什么不把向量直接存在 chunk 表？
- 为什么不把原文件直接存在数据库？
- 如果修改 chunk，向量索引怎么同步？

## 3. 核心数据模型总览

可以在面试中先画这个简图：

```text
tenant
  ├─ tenant_members / audit_logs
  ├─ vector_stores
  ├─ models / credentials
  └─ knowledge_bases
       ├─ knowledge
       │    ├─ raw file path -> object storage
       │    ├─ chunks
       │    │    └─ vector/keyword index(source_id = chunk_id)
       │    └─ summaries / generated questions / image chunks
       ├─ wiki_pages
       │    ├─ wiki_log_entries
       │    └─ page links / graph relations
       ├─ tags / FAQ entries
       ├─ task_pending_ops
       └─ task_dead_letters
```

核心原则：

- DB 存元数据和业务关系。
- 对象存储存原文件和图片。
- 向量库/关键词引擎存检索索引。
- Neo4j 或图存储存实体关系。
- Redis 存任务队列、短期锁、tombstone。

## 4. 核心实体讲解

### 4.1 Tenant：租户

#### 面试官为什么问

租户是企业知识库的安全边界。面试官会关注数据隔离是否从数据模型开始设计。

#### 结合项目怎么答

Tenant 是系统的一级隔离单位。知识库、模型配置、向量库配置、成员、审计日志、数据源、MCP 服务等都围绕 tenant 展开。

关键点：

- `tenant_id` 用于数据隔离。
- `tenant_members` 记录用户在租户中的角色。
- API Key 调用也绑定到特定租户。
- RBAC 和共享空间都要先确定租户上下文。

#### 可直接复述的面试回答

在 WeKnora 里，tenant 是最核心的数据隔离边界。知识库、文档、chunk、vector store、模型配置、MCP 服务、审计日志都要挂在 tenant 下。请求进来后先解析 JWT 或 API Key，确定 tenant 和 user，再通过 tenant_members 判断角色权限。这样即使用户知道某个资源 ID，也必须在服务端校验它是否属于当前租户或是否通过共享授权可访问。

#### 常见追问

- 超级管理员跨租户怎么处理？
- API Key 调用时有没有 user_id？
- 租户删除会影响哪些资源？

#### 常见坑

不要只说“表里有 tenant_id”。真正的隔离还包括查询条件、权限中间件、资源 owner 校验和共享关系。

---

### 4.2 KnowledgeBase：知识库

#### 面试官为什么问

知识库是配置和权限的核心聚合根。很多 RAG 参数不是全局的，而是按知识库配置。

#### 结合项目怎么答

KnowledgeBase 可以理解为一组知识的容器，包含：

- 类型：Document、FAQ、Wiki 等。
- 模型配置：EmbeddingModelID、SummaryModelID、VLM/ASR 配置。
- ChunkingConfig：chunk size、overlap、strategy、parent-child。
- IndexingStrategy：vector、keyword、wiki、graph 是否开启。
- VectorStoreID：是否绑定指定向量库。
- CreatorID：用于 Contributor 资源归属权限。

#### 技术原理 / 链路设计讲解

为什么配置放 KB 级别？因为不同知识库的数据形态不同：

- FAQ 适合小 chunk、无 overlap、强关键词。
- Markdown 文档适合 heading-aware。
- PDF 报告适合 heuristic + parent-child。
- Wiki 知识库可能需要启用 wiki/graph indexing。

#### 可直接复述的面试回答

KnowledgeBase 不只是文档集合，它还是检索和入库策略的配置边界。比如一个 KB 会配置 embedding 模型、分块策略、是否启用 parent-child、是否开启 vector/keyword/wiki/graph indexing，以及是否绑定某个 VectorStore。权限上 KB 也有 creator_id，Contributor 可以管理自己创建的 KB，其他人需要 Admin+。所以 KB 是文档、索引、权限和策略的聚合根。

#### 常见追问

- FAQ 型 KB 和 Document 型 KB 数据模型有什么区别？
- KB 修改 chunking config 后，旧文档是否自动重建？
- KB 绑定 VectorStore 后，删除 KB 时怎么清索引？

#### 常见坑

不要把 KB 说成“文件夹”。它更像策略边界和权限边界。

---

### 4.3 Knowledge：知识条目 / 文档

#### 面试官为什么问

Knowledge 是入库状态机的核心。面试官会围绕上传、处理、删除、重建追问。

#### 结合项目怎么答

Knowledge 表示一个具体知识条目，可以来自：

- 文件上传。
- URL 导入。
- 手工录入。
- FAQ 导入。
- 数据源同步。

关键字段包括：

- `tenant_id`：租户。
- `knowledge_base_id`：所属 KB。
- `type`：file/url/manual/faq 等。
- `file_name`、`file_type`、`file_size`、`file_hash`。
- `file_path`：对象存储路径。
- `parse_status`：pending/processing/completed/failed。
- `enable_status`：enabled/disabled。
- `embedding_model_id`。
- `metadata`。

#### 技术原理 / 链路设计讲解

Knowledge 的状态机非常重要：

```text
create -> pending/disabled
worker starts -> processing
success -> completed/enabled
failed -> failed/disabled + error_message
delete -> deleting/cleanup -> removed
```

它解决的是异步处理可见性问题。没有状态机，用户无法知道“上传成功但未完成索引”的中间状态。

#### 可直接复述的面试回答

Knowledge 是文档级知识条目，它连接原文件、解析状态、chunk 和索引。用户上传文件后，系统会创建一条 knowledge，初始状态是 pending/disabled；后台 worker 处理时改成 processing；解析、分块和索引完成后才变成 completed/enabled。这个状态机非常关键，因为上传成功不代表可问答，只有索引完成并启用后，在线 RAG 才应该检索到它。

#### 常见追问

- 重复上传如何判断？
- 文件 hash 是否足够？
- 更新 knowledge 时如何重建 chunk 和索引？

#### 常见坑

不要忽略 `enable_status`。parse completed 也不一定代表业务上应该参与检索。

### 4.4 Chunk：分块

#### 面试官为什么问

Chunk 是 RAG 的最小检索和上下文单元。面试官会重点问 chunk 如何和原文、向量索引、parent-child 关联。

#### 结合项目怎么答

Chunk 表示 knowledge 解析后的文本块，关键字段通常包括：

- `id`
- `tenant_id`
- `knowledge_id`
- `knowledge_base_id`
- `content`
- `context_header`
- `chunk_index`
- `start_at`、`end_at`
- `pre_chunk_id`、`next_chunk_id`
- `parent_chunk_id`
- `chunk_type`
- `is_enabled`

#### 技术原理 / 链路设计讲解

Chunk 有几种作用：

- 用于向量/关键词索引。
- 用于检索结果展示。
- 用于拼接 LLM 上下文。
- 用于文档预览定位。
- 用于 Wiki/Graph 后处理。

parent-child chunking 中：

- parent chunk 内容更大，提供上下文。
- child chunk 更小，参与向量召回。
- child 通过 `parent_chunk_id` 关联 parent。

#### 可直接复述的面试回答

Chunk 是 RAG 的核心数据单元。它不是简单一段文本，还要保存所属 tenant、KB、knowledge、chunk_index、原文位置、前后 chunk 链接、context header、parent_chunk_id 等信息。向量索引通常以 chunk_id 作为 source_id，这样检索命中后可以回查 DB 拿完整 chunk 元数据。parent-child 模式下，小 child chunk 用于召回，大 parent chunk 用于补上下文，两者通过 parent_chunk_id 关联。

#### 常见追问

- 为什么 parent chunk 不一定进向量索引？
- chunk 更新后向量索引怎么同步？
- pre/next chunk 有什么用？

#### 常见坑

不要只说 chunk 是“一段文本”。真实系统里 chunk 还承载定位、权限、索引和上下文关系。

---

### 4.5 Vector Index / Keyword Index：检索索引

#### 面试官为什么问

面试官想看你是否理解 DB chunk 和向量库索引不是同一个东西。

#### 结合项目怎么答

项目中会构造 `IndexInfo`：

- `Content`：用于 embedding 的文本，可能包含标题前缀和 context header。
- `SourceID`：通常是 chunk ID。
- `ChunkID`
- `KnowledgeID`
- `KnowledgeBaseID`
- `SourceType`
- `IsEnabled`

向量库中保存 embedding，关键词引擎保存可检索文本。检索命中后，再通过 chunk_id 回查 DB。

#### 技术原理 / 链路设计讲解

为什么不直接把向量放 chunk 表？

- 不同向量库能力差异大。
- 专用向量库有 ANN 索引、过滤、扩展能力。
- 私有化客户可能使用已有向量基础设施。
- 向量维度、索引类型、collection 管理不适合都塞进业务表。

#### 可直接复述的面试回答

DB 里的 chunk 是业务事实数据，向量库里的 index 是检索加速数据。写索引时会用 chunk_id 作为 source_id，把 embedding 写入向量库；查询命中后，再根据 chunk_id 回查 DB 拿正文、标题、来源、权限和上下文。这样 DB 负责元数据和一致性，向量库负责相似度检索。两者不是强事务关系，所以重建和删除时要按最终一致和补偿设计。

#### 常见追问

- 向量库写成功但 DB 更新失败怎么办？
- 向量维度变化怎么办？
- 索引删除失败怎么办？

#### 常见坑

不要承诺 DB 和向量库强一致。跨系统只能尽量做到幂等、重试和补偿。

---

### 4.6 WikiPage / WikiLogEntry：Wiki 页面与日志

#### 面试官为什么问

Wiki 是衍生知识，面试官会问它如何追溯原始来源、如何处理用户编辑和自动生成冲突。

#### 结合项目怎么答

WikiPage 表示结构化 Markdown 页面，通常包含：

- 所属 tenant 和 KB。
- page slug / title。
- markdown content。
- 页面状态。
- 来源或引用信息。
- 创建/更新时间。

WikiLogEntry 用于记录 Wiki 生成、更新、撤回、人工修改等事件。

#### 技术原理 / 链路设计讲解

Wiki 页面可能由多个文档共同贡献。因此它不能简单和某个 knowledge 一对一绑定。更合理的是：

- 页面保留 source citation。
- 日志记录每次由哪个文档触发、生成了什么变更。
- 删除文档时根据贡献关系撤回，而不是直接删整页。

#### 可直接复述的面试回答

WikiPage 是从原始文档沉淀出来的结构化知识页面，它和 knowledge 不是简单一对一关系。一个页面可能由多个文档共同贡献，所以必须保留来源引用和变更日志。WikiLogEntry 的价值就是追踪自动生成、更新、撤回、人工编辑这些事件。这样当某个文档删除或重新入库时，系统才有机会判断应该撤回哪些内容，而不是粗暴删除整个页面。

#### 常见追问

- 用户人工编辑的 Wiki，下次自动生成是否覆盖？
- Wiki 页面和原文冲突怎么办？
- 页面 slug 重复怎么办？

#### 常见坑

不要把 WikiPage 建模成 knowledge 的简单摘要。它更像跨文档聚合结果。

### 4.7 TaskPendingOps / TaskDeadLetters：任务可靠性表

#### 面试官为什么问

这是区分 Demo 和工程系统的关键点。面试官想看你如何让异步任务可恢复、可审计。

#### 结合项目怎么答

`task_pending_ops` 用于保存待处理操作，特别是 Wiki 入库这类需要长期可靠处理的任务。字段通常包括：

- `task_type`
- `scope`
- `scope_id`
- `dedup_key`
- `payload`
- `fail_count`
- timestamps

`task_dead_letters` 用于记录最终失败任务：

- `tenant_id`
- `task_type`
- `scope`
- `scope_id`
- `related_id`
- `payload`
- `last_error`
- `fail_count`

#### 技术原理 / 链路设计讲解

为什么 pending ops 放 DB？

- Redis list 更适合短期队列，但不适合作为长期可靠业务状态。
- DB 可查询、可恢复、可审计。
- 失败次数、dedup、scope 查询更方便。

为什么还要 Asynq？

- Asynq 负责调度、重试、队列优先级。
- pending ops 负责业务级待处理集合。

两者不是重复，而是分工不同。

#### 可直接复述的面试回答

TaskPendingOps 和 TaskDeadLetters 体现的是异步任务可靠性。Asynq 负责调度和重试，但 Wiki 这种长期任务不能只靠 Redis 队列保存业务状态，所以项目把每个待处理文档操作写入 task_pending_ops。worker 触发时按 task_type 和 scope 拉一批处理。失败多次的 op 或最终失败的 Asynq 任务会进入 task_dead_letters，记录 payload 和 last_error，方便后续排查和重放。

#### 常见追问

- pending op 的 dedup_key 怎么设计？
- dead-letter 如何重放？
- dead-letter 表会不会无限增长？

#### 常见坑

不要把 dead-letter 只理解为“失败日志”。它还应该支持恢复和运维排查。

## 5. 数据生命周期：删除一个 Knowledge 要清理什么？

这是面试官很容易追的问题。

删除一个文档通常涉及：

1. knowledge 记录状态更新或删除。
2. 原文件从对象存储删除，或标记清理。
3. chunks 删除。
4. 向量/关键词索引删除。
5. 图谱中该文档 namespace 删除。
6. Wiki 页面引用撤回。
7. pending ops 清理。
8. tombstone 标记，避免 in-flight worker 写回。
9. 审计日志记录。

### 可直接复述的面试回答

删除 knowledge 不是删一行 DB。它会牵涉原文件、chunk、向量索引、关键词索引、图谱数据、Wiki 引用和后台任务。因为这些数据分布在 DB、对象存储、向量库、图数据库和 Redis 里，不能用一个本地事务保证强一致，所以更实际的做法是状态标记、异步清理、幂等删除、tombstone 防旧任务写回，以及失败后进入 dead-letter 或告警。

## 6. 本主题总结

核心数据模型要围绕四个原则讲：

- Tenant 是安全边界。
- KnowledgeBase 是策略和权限边界。
- Knowledge 是文档生命周期边界。
- Chunk 是 RAG 检索和上下文边界。
- Vector/Wiki/Graph 是派生资产，需要最终一致和可重建。
