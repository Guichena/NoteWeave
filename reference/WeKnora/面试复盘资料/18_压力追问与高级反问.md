# 文件：18_压力追问与高级反问.md

## 1. 本主题面试官想考什么

压力追问不是为了难为你，而是为了验证你是否真的理解项目边界。大厂面试官常用“质疑型问题”测试候选人的工程判断：

- 你是不是只是调用大模型 API？
- RAG 现在是不是过时了？
- 支持这么多向量库是不是过度设计？
- Wiki 自动生成是不是不可靠？
- 你怎么证明这块是你做的？

这个文件给你准备“被质疑时怎么稳住”的回答。重点不是强行反驳，而是承认边界、讲清取舍、给出证据。

## 2. 高频压力问题清单

### 项目真实性

- 这是不是只是套壳大模型？
- 这块真是你做的吗？
- 你在项目里到底负责什么？
- 你讲的这些是不是看 README 背的？

### RAG 质疑

- RAG 不就是向量库查 TopK 吗？
- 为什么不用长上下文模型塞全文？
- 为什么不用纯 Elasticsearch？
- 为什么不用纯向量检索？
- RAG 回答还是会幻觉，价值在哪里？

### 文档入库质疑

- 上传、解析、切块、Embedding，不就是流水线吗？难点在哪？
- 异步任务失败怎么办？
- DB 和向量库怎么保证一致？
- 重复处理会不会产生脏数据？

### Wiki 质疑

- Wiki 自动生成是不是很容易胡编？
- 为什么不让用户自己写 Wiki？
- 四万文档串行处理是不是太慢？
- 人工编辑和自动生成冲突怎么办？

### 架构质疑

- 支持这么多向量库是不是过度设计？
- 为什么用 Asynq，不用 Kafka？
- 为什么用 SSE，不用 WebSocket？
- 为什么 Go + Python，不统一技术栈？
- 为什么不是微服务？

### 安全质疑

- Agent/MCP 会不会太危险？
- 用户知道 chunk_id 能不能越权访问？
- URL 导入如何防 SSRF？
- API Key 怎么保护？

## 3. 压力问答

### Q1：你这个项目是不是只是套壳大模型？

#### 面试官为什么问

这是非常常见的质疑。面试官想看你能否证明项目有工程复杂度，而不是简单调 API。

#### 先给结论

大模型调用确实是项目的一部分，但 WeKnora 的复杂度不在“调一次模型 API”。

#### 回答思路

不要情绪化反驳。先承认模型调用是其中一环，再说明核心复杂度在知识入库、检索、权限、异步、观测和多端交付。

#### 可直接复述的面试回答

大模型调用确实是项目的一部分，但 WeKnora 的复杂度不在“调一次模型 API”。真正的工程量在前后的链路：前面要把 PDF、Word、图片、网页、数据源同步内容解析成可检索知识，要做分块、Embedding、向量/关键词索引、任务重试和状态管理；中间要做多路召回、rerank、MMR、权限过滤、上下文构造；后面还要做流式输出、引用展示、Langfuse trace、RBAC、MCP 审批、Wiki 沉淀和 dead-letter 排障。如果只是套壳模型，就不会需要这些入库、检索、权限和异步一致性设计。

#### 常见追问

- 那你觉得最核心的工程难点是什么？
- 如果不用 LLM，这个系统还有价值吗？
- 你负责的是哪一层？

#### 常见坑

不要只说“我们用了 RAG，所以不是套壳”。RAG 也可以很浅，要讲工程闭环。

---

### Q2：RAG 不就是向量库查 TopK 吗？

#### 面试官为什么问

面试官想看你是否理解 RAG 的完整在线链路。

#### 先给结论

如果只是 Demo，RAG 可以简化成向量库查 TopK。

#### 回答思路

强调 RAG 是多阶段质量控制：

- query understand。
- 混合检索。
- graph/web search。
- rerank。
- merge/filter。
- prompt 约束。
- references。

#### 可直接复述的面试回答

如果只是 Demo，RAG 可以简化成向量库查 TopK。但真实企业知识库里，这远远不够。用户问题可能很短、带上下文、带错误码或字段名，所以需要 query understand、rewrite 和混合检索；向量召回覆盖语义，关键词召回精确词，图谱补实体关系，web search 补外部信息。召回后还要 rerank、MMR、去重、TopK 过滤，再构造带引用的 prompt。最终还要能追踪每一步的耗时和结果。所以 RAG 不是一个向量查询，而是一条可调试的证据检索和生成链路。

#### 常见追问

- 哪一步最影响准确率？
- 混合检索怎么融合？
- rerank 一定有效吗？

#### 常见坑

不要把 RAG 说成“高级语义搜索”。RAG 还包括生成约束和引用可解释性。

---

### Q3：长上下文模型越来越强，为什么还需要 RAG？

#### 面试官为什么问

这是当前很现实的问题。面试官想看你有没有成本和系统边界意识。

#### 先给结论

长上下文模型确实能减少一部分检索复杂度，但不能完全替代 RAG。

#### 回答思路

承认长上下文价值，再讲不能完全替代 RAG。

#### 可直接复述的面试回答

长上下文模型确实能减少一部分检索复杂度，但不能完全替代 RAG。企业知识库可能有几万份文档，每次把全文塞进去成本和延迟都不可控；而且长上下文不等于模型一定会关注正确位置。RAG 的价值是先做权限过滤和知识范围控制，再用检索把候选范围缩到很小，最后只把高相关证据交给模型。它在成本、延迟、权限、引用可解释性和数据更新上都更可控。更合理的方向不是 RAG vs 长上下文，而是 RAG 负责选证据，长上下文负责承载更多证据。

#### 常见追问

- 如果只有几十页文档呢？
- 1M token 上下文是不是就够了？
- 长上下文和 RAG 怎么结合？

#### 常见坑

不要绝对否定长上下文。成熟表达是互补。

### Q4：支持这么多向量库，是不是过度设计？

#### 面试官为什么问

这是架构取舍题。面试官想看你是否能区分“炫技扩展”和“业务必要性”。

#### 先给结论

如果是内部单一业务，支持很多向量库可能是过度设计。

#### 回答思路

说明项目定位是私有化/企业级，客户基础设施不同，多后端是适配需求。但也要承认维护成本，并说明如何用统一接口控制复杂度。

#### 可直接复述的面试回答

如果是内部单一业务，支持很多向量库可能是过度设计。但 WeKnora 这类项目有私有化部署属性，不同客户可能已经有 Postgres、Elasticsearch、Milvus、Qdrant、Weaviate 或云厂商 VectorDB，强制绑定一个后端会增加落地成本。所以项目通过 RetrieveEngine 接口、registry、factory 和 VectorStore 绑定来抽象后端。上层 RAG pipeline 只关心 vector/keywords 检索，不直接依赖具体实现。代价是适配和测试成本更高，所以必须收敛接口能力，明确哪些后端是一等支持，哪些是可选支持。

#### 常见追问

- 新增一个向量库要改哪些地方？
- 不同后端能力不一致怎么办？
- 多后端测试怎么做？

#### 常见坑

不要只说“为了扩展性”。要说明私有化、客户基础设施和厂商锁定。

---

### Q5：DB 和向量库怎么保证一致？会不会脏数据？

#### 面试官为什么问

这是分布式一致性追问。面试官在看你是否会夸大强一致。

#### 先给结论

DB 和向量库无法用一个本地事务保证强一致。

#### 回答思路

承认不能强事务，讲最终一致和补偿：

- 状态机。
- 幂等重建。
- 删除旧索引再写新索引。
- failed 状态。
- retry/dead-letter。
- 定期校验和重建。

#### 可直接复述的面试回答

DB 和向量库无法用一个本地事务保证强一致。WeKnora 更实际的做法是最终一致和可重建。文档处理时以 knowledge 为粒度，重建前先删除旧 chunk、旧向量/关键词索引和旧图谱，再写新结果。如果中途失败，knowledge 不应该被标记为 enabled，而是进入 failed 或 processing，后续可以重试。删除也是幂等删除，失败任务进入 dead-letter。对于生产系统，还可以增加定期一致性校验，比如 DB chunk 存在但向量索引缺失时触发重建。

#### 常见追问

- 如果旧索引删了，新索引没写成功怎么办？
- 用户是否会搜到旧数据？
- 是否需要 outbox pattern？

#### 常见坑

不要说“我们用事务保证”。跨 DB、向量库、对象存储、图数据库基本不能这么说。

### Q6：Wiki 自动生成是不是不可靠？

#### 面试官为什么问

这是对 Wiki 模式最直接的质疑。你要承认风险并说明控制手段。

#### 先给结论

Wiki 自动生成确实不能当成绝对事实源，所以设计上不能让它无约束地产生内容。

#### 回答思路

承认 LLM 生成有幻觉风险，然后讲 Wiki 的定位和控制：

- 不是替代原文事实。
- 保留引用来源。
- 结构化输出。
- 后处理校验。
- 人工编辑和日志。
- 分层参与检索。

#### 可直接复述的面试回答

Wiki 自动生成确实不能当成绝对事实源，所以设计上不能让它无约束地产生内容。它的定位是帮助用户把散乱文档沉淀成结构化知识导航，而原始 chunk 仍然是事实依据。控制上，要只基于有效 chunk 生成，要求结构化 Markdown 输出，保留来源引用，做 slug、链接、格式和重复页面校验，并允许用户人工编辑和查看日志。如果 Wiki 参与 RAG，也应该标记 source_type，对事实型问题优先原文，对概览型问题提高 Wiki 权重。

#### 常见追问

- 用户编辑后自动任务会不会覆盖？
- Wiki 和原文冲突怎么办？
- 如何检测 Wiki 幻觉？

#### 常见坑

不要说“模型足够强就可靠”。这会显得不懂 LLM 风险。

### Q7：为什么用 Asynq，不用 Kafka？

#### 面试官为什么问

这是中间件选型题。面试官想看你是否知道任务队列和消息流系统的区别。

#### 先给结论

文档入库、摘要、Wiki 生成这类任务更像后台 job，而不是高吞吐事件流。

#### 回答思路

Asynq 更适合 Go 后台任务：

- 简单。
- 支持延迟、重试、队列优先级。
- 基于 Redis，部署轻。
- 适合文档处理这种任务语义。

Kafka 更适合高吞吐事件流：

- 消息持久化强。
- 消费组和流处理强。
- 运维复杂。
- 对单任务重试和延迟任务不如任务队列直接。

#### 可直接复述的面试回答

文档入库、摘要、Wiki 生成这类任务更像后台 job，而不是高吞吐事件流。它们需要延迟执行、重试、失败归档、队列优先级和任务 payload，Asynq 基于 Redis，和 Go 项目集成简单，部署成本也低。Kafka 更适合事件流、日志采集和高吞吐消费场景，但对这种单任务重试、延迟调度和 dead-letter 处理，需要额外封装。以 WeKnora 的任务形态，用 Asynq 更轻量。除非后续任务规模和事件流需求明显上升，才会考虑 Kafka。

#### 常见追问

- Redis 挂了怎么办？
- Asynq 任务会不会丢？
- 大规模任务 Kafka 是否更合适？

#### 常见坑

不要说 Kafka 不好。要说场景不同。

### Q8：为什么用 SSE，不用 WebSocket？

#### 面试官为什么问

这是前后端协议取舍题。

#### 先给结论

大模型问答的主链路是客户端发一个问题，服务端持续推送 answer chunk 和 references，基本是单向流。

#### 回答思路

问答场景多数是客户端发起请求、服务端单向推送回答，SSE 简单够用。

#### 可直接复述的面试回答

大模型问答的主链路是客户端发一个问题，服务端持续推送 answer chunk 和 references，基本是单向流。SSE 基于 HTTP，协议简单，天然适合文本事件流，也更容易通过常规网关和鉴权链路。WebSocket 适合强双向实时交互，比如多人协作、游戏、复杂控制通道，但连接管理、心跳、重连和负载均衡更复杂。所以 Web 问答流式输出用 SSE 是一个更简单的选择。当然 IM 平台或特殊实时场景可能会用 WebSocket 或平台自己的流式协议。

#### 常见追问

- SSE 中断怎么恢复？
- SSE 经过代理会不会缓冲？
- 多路并发对话怎么处理？

#### 常见坑

不要说 WebSocket 不行。要说 SSE 更匹配单向文本流。

### Q9：Agent/MCP 会不会太危险？

#### 面试官为什么问

Agent 一旦能调用工具，就从“回答系统”变成“执行系统”，风险明显上升。

#### 先给结论

Agent/MCP 的风险确实比普通 RAG 高，因为工具调用可能访问外部系统甚至产生副作用。

#### 回答思路

承认风险，讲控制：

- 工具白名单。
- 最小权限。
- 禁用 stdio。
- 审批。
- 超时。
- 沙箱。
- 审计日志。

#### 可直接复述的面试回答

Agent/MCP 的风险确实比普通 RAG 高，因为工具调用可能访问外部系统甚至产生副作用。所以不能让模型随便执行。WeKnora 的思路是多层限制：MCP 服务注册需要权限，敏感工具调用需要 Human-in-the-Loop 审批，stdio transport 被禁用，推荐 SSE/HTTP 接入，Agent 有最大轮数和超时，技能执行走 sandbox，工具凭据要加密存储，调用过程要有日志和 trace。也就是说，Agent 的能力必须和权限、审批、隔离、审计一起设计。

#### 常见追问

- prompt injection 诱导工具调用怎么办？
- 工具有副作用如何防重复执行？
- 审批超时怎么办？

#### 常见坑

不要说“相信模型不会乱调”。安全必须在程序层控制。

### Q10：这块真的是你做的吗？你怎么证明？

#### 面试官为什么问

这是真实性压力测试。如果你讲得太像架构文档，面试官会追问个人贡献。

#### 先给结论

模板一：如果你确实主导 这块我主要负责的是 xxx。

#### 回答思路

不要硬揽全部。按真实情况说：

- 我主导了什么。
- 我参与了什么。
- 我阅读和复盘了什么。
- 我解决过什么问题。
- 我还能指出代码/接口/配置细节。

#### 可直接复述的面试回答模板一：如果你确实主导

这块我主要负责的是 xxx。具体来说，我做了三件事：第一是 xxx，比如设计了文档入库的状态流和任务投递；第二是 xxx，比如处理了重复入库和索引幂等；第三是 xxx，比如补了 trace 和 dead-letter 排查能力。这里我能讲到代码层细节，比如任务 payload 里有哪些字段、失败时如何进入 dead-letter、reprocess 前为什么要先删旧索引。

#### 可直接复述的面试回答模板二：如果你不是主导

这块不是我从 0 到 1 主导的，我主要参与了 xxx，例如接口联调、问题排查或某个模块优化。但为了完整理解项目，我把文档入库、RAG pipeline 和 Wiki 入库链路都做过源码级复盘，所以我能讲清楚它的设计取舍。面试里如果问到具体 owner 级别的决策，我会明确区分哪些是我亲自做的，哪些是我通过源码和项目文档复盘出来的。

#### 常见追问

- 你改过哪个文件？
- 哪个 bug 是你修的？
- 有没有 PR 或 commit？
- 如果让你重写，你会怎么改？

#### 常见坑

不要把所有模块都说成自己做的。大厂面试非常容易通过细节追问识别夸大。

## 4. 高级反问

面试最后你也可以反问一些体现深度的问题：

### 关于 RAG

- 贵团队现在更关注召回准确率，还是答案可信度和引用可解释性？
- 你们是否有自动化 RAG 评测集，比如 Recall@K、faithfulness、citation accuracy？
- 对长上下文模型和 RAG 的结合，团队目前是怎么取舍的？

### 关于 Agent

- 团队内部对 Agent 工具调用的安全边界是怎么定义的？
- 对有副作用工具，是否引入审批、幂等键和审计？

### 关于工程落地

- 知识库入库链路里，当前瓶颈更多在解析、Embedding，还是向量库写入？
- 对异步任务失败，团队更依赖 dead-letter、告警，还是人工后台重放？

这些反问的价值是让面试官感觉你在以工程 owner 的视角思考。

## 5. 本主题总结

压力追问的核心策略：

- 先承认边界，不要硬刚。
- 再讲取舍，不要只讲优点。
- 最后给证据，包括链路、数据、代码细节、badcase、指标。

你要表现出来的是：我知道这个方案哪里强，也知道它哪里弱，并且知道弱点怎么兜底。
