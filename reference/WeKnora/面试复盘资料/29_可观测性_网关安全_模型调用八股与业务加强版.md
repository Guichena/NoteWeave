# 文件：29_可观测性_网关安全_模型调用八股与业务加强版.md

## 1. 本主题面试官想考什么

可观测性、网关安全和模型调用治理，是大厂面试里非常容易从“项目介绍”追问到“生产级工程能力”的部分。尤其 RAG/Agent 项目，最难排查的不是接口 500，而是：

- 用户说“回答不准”，但系统没有报错。
- 检索到了文档，但模型答偏了。
- 异步任务失败了，但只在 Redis archived queue 里。
- Agent 工具调用做了危险操作。
- 用户越权召回了其他知识库 chunk。
- Langfuse 记录了敏感 prompt，引发安全风险。

面试官想看你是否理解：

- HTTP middleware 的执行顺序和职责边界。
- JWT、RBAC、资源级权限的区别。
- Trace、Span、Log、Metric 的区别。
- OpenTelemetry 的上下文传播。
- Langfuse 相比普通 tracing 在 LLM/RAG 场景里的价值。
- 模型调用 wrapper 如何统一超时、重试、成本、脱敏和 fallback。
- RAG 安全不是只看 API 鉴权，还要看检索层过滤和 prompt 泄露。

## 2. 初学者先建立整体图

一次 WeKnora RAG 请求可以这样理解：

```text
HTTP 请求进入
  -> Recovery 防 panic
  -> Logger 记录请求
  -> Trace 建立链路
  -> Auth 解析 JWT
  -> RBAC 判断角色权限
  -> KB Access 判断知识库访问权限
  -> Handler 执行业务
  -> Retriever 检索 chunk
  -> Rerank 精排
  -> Model Wrapper 调 LLM
  -> Langfuse 记录 prompt/retrieval/generation
  -> SSE/stream 返回
```

异步任务也要进入观测：

```text
HTTP 上传
  -> enqueue Asynq
  -> payload 携带 trace context
  -> Worker 恢复或新建 trace
  -> docreader/embedding/vector write 记录 span
  -> 失败重试
  -> 最终失败写 dead-letter
```

## 4. 八股知识点 1：HTTP Middleware 洋葱模型

### 4.1 是什么

middleware 是 Web 框架里处理请求的中间层。它通常在业务 handler 前后执行，用于处理通用能力：

- panic recovery。
- 日志。
- trace。
- CORS。
- 鉴权。
- 权限。
- 限流。
- 错误处理。

Gin 的 middleware 可以理解为：

```go
func(c *gin.Context) {
    // before handler
    c.Next()
    // after handler
}
```

### 4.2 为什么顺序重要

middleware 是洋葱模型：

```text
Recovery(
  Logger(
    Trace(
      Auth(
        RBAC(
          Handler
        )
      )
    )
  )
)
```

请求进入时从外到内，返回时从内到外。

顺序错误会导致：

- Recovery 太内层，外层 panic 捕不到。
- Logger 太内层，鉴权失败没有日志。
- Trace 太内层，权限失败没有 trace。
- RBAC 在 Auth 前执行，拿不到用户身份。
- KB Access 不在 handler 前，业务里可能先查了越权数据。

### 4.3 WeKnora 怎么回答

WeKnora 有 recovery、logger、trace、auth、rbac、kb_access、error_handler、language 等中间件。面试可以这么讲：

- Recovery 放外层，保证 panic 不打挂服务。
- Logger/Trace 尽量包住完整链路。
- Auth 解析 token，注入用户上下文。
- RBAC 根据角色判断 action/resource 权限。
- KB Access 做具体知识库访问控制。
- Handler 里不重复散落权限判断，降低漏判风险。

### 4.4 可直接复述的面试回答

> Gin middleware 是典型洋葱模型，请求进来按注册顺序执行，调用 `Next()` 后进入下一层，返回时再反向执行收尾逻辑。顺序很重要，Recovery 和 Logger/Trace 应该尽量在外层，Auth 要在 RBAC 前，KB Access 要在业务 handler 前。WeKnora 里知识库数据比较敏感，所以不能只在 handler 里临时判断权限，而是通过 auth、rbac、kb_access 这些中间件把身份、角色和资源访问控制前置。

## 5. 八股知识点 2：JWT、鉴权、RBAC、资源权限

### 5.1 JWT 是什么

JWT 是 JSON Web Token，通常由三部分组成：

```text
header.payload.signature
```

Header：

- alg：签名算法。
- typ：JWT。

Payload：

- sub/user_id。
- exp 过期时间。
- iat 签发时间。
- iss 签发者。
- aud 受众。
- tenant_id/role 等业务声明。

Signature：

- 对 header + payload 做签名，防篡改。

### 5.2 JWT 能防什么，不能防什么

能防：

- token 内容被篡改。因为签名校验会失败。

不能防：

- token 被盗用。
- 用户角色变更后旧 token 继续有效。
- 服务端主动撤销，除非引入黑名单/版本号。

### 5.3 鉴权 vs 授权

Authentication 鉴权：

- 你是谁。

Authorization 授权：

- 你能做什么。

JWT auth 只解决第一步。RBAC 和资源权限解决第二步。

### 5.4 RBAC 是什么

RBAC 是 Role-Based Access Control：

```text
User -> Role -> Permission
```

WeKnora 里可以表达为：

```text
user -> tenant_member -> role(viewer/contributor/admin/owner) -> allowed actions
```

### 5.5 资源级权限

RBAC 只说角色能不能执行某类操作，但还要判断具体资源能不能访问。

例如：

- contributor 可以上传文档。
- 但只能上传到自己有权限的 knowledge_base。
- viewer 可以查看知识库。
- 但不能查看其他租户的私有知识库。

### 5.6 RAG 特别风险：检索层越权

普通系统越权多发生在 API：

```text
GET /kb/other-tenant-kb
```

RAG 系统还可能发生在检索层：

```text
用户问问题 -> retriever 忘记 tenant/kb filter -> 召回其他租户 chunk -> 塞进 prompt -> LLM 泄露
```

所以权限必须进入 retriever metadata filter：

```text
tenant_id = current_tenant
knowledge_base_id in allowed_kbs
status = ready
deleted_at is null
```

### 5.7 角色变更后旧 token 怎么办

方案：

- 短 access token + refresh token。
- token 中带 user_version/role_version，服务端校验版本。
- 黑名单/撤销列表，Redis 保存 jti。
- 重要操作实时查 DB 权限。

取舍：

- 全靠 JWT 无状态，性能好但撤销难。
- 每次查 DB 权限，准确但开销大。
- 版本号是折中方案。

### 5.8 可直接复述的面试回答

> JWT 由 header、payload、signature 三部分组成，签名能防篡改，但不能防 token 被盗，也不能天然支持服务端撤销。鉴权解决“你是谁”，授权解决“你能不能做这个操作”。WeKnora 里 JWT auth 解析用户身份，RBAC 判断用户在租户里的角色权限，KB Access 判断具体知识库能不能访问。RAG 场景还要把权限传到检索层，向量召回必须带 tenant_id、knowledge_base_id、status、deleted_at 这些 filter，否则 API 层看似安全，prompt 里仍可能混入越权 chunk。

## 6. 八股知识点 3：Log、Metric、Trace

### 6.1 Log

Log 是离散事件记录：

```text
2026-05-22 10:00:00 document process failed: timeout
```

适合：

- 记录错误。
- 记录关键业务事件。
- 排查细节。

不足：

- 分散。
- 不容易还原完整请求链路。
- 大量日志查询成本高。

### 6.2 Metric

Metric 是聚合指标：

- QPS。
- P95/P99 latency。
- error rate。
- queue length。
- token cost。
- model latency。

适合：

- 监控趋势。
- 告警。
- 容量规划。

不足：

- 只能看到“哪里异常”，不一定看到“某次请求为什么异常”。

### 6.3 Trace

Trace 是单次请求的调用链路。Trace 由多个 span 组成：

```text
Trace: RAG QA request
  Span: auth
  Span: retrieve
  Span: rerank
  Span: LLM generation
```

适合：

- 排查单次慢请求。
- 跨服务调用链。
- 观察每一步耗时和错误。

### 6.4 RAG 为什么更需要 trace

RAG 的问题常常不是报错，而是质量问题：

- 检索不到。
- 检索到了但排序错。
- prompt 太长被截断。
- LLM 幻觉。
- tool call 失败。

这些很难靠普通日志定位，需要 trace 看到完整链路。

### 6.5 可直接复述的面试回答

> Log、Metric、Trace 解决的问题不同。Log 记录离散事件，Metric 看整体趋势和告警，Trace 还原一次请求的完整链路。RAG 系统尤其需要 trace，因为很多问题不是 500，而是回答不准。我们需要看到 query、retrieval、rerank、prompt、LLM generation、tool call 每一步的输入输出、耗时和错误，才能判断是召回问题、排序问题还是生成问题。

## 7. OpenTelemetry 和 Langfuse

### 7.1 OpenTelemetry 是什么

OpenTelemetry 是可观测性标准，定义了：

- Trace。
- Metric。
- Log。
- Context propagation。
- Exporter。

核心概念：

- TraceId：一次请求的全局 ID。
- SpanId：某个步骤的 ID。
- ParentSpanId：父子关系。
- Baggage/Context：跨服务传播上下文。

### 7.2 Trace context 怎么传播

HTTP 场景：

- 通过 header 传递 traceparent。

异步任务场景：

- 通过 task payload 保存 trace context。
- Worker 执行时恢复 context。

如果不传播：

- HTTP 上传和后台文档处理会变成两条断裂链路。
- 排查时无法知道某个异步任务来自哪个用户请求。

### 7.3 Langfuse 是什么

Langfuse 是面向 LLM 应用的可观测平台。它比普通 trace 多关注：

- prompt。
- completion。
- model name。
- token usage。
- cost。
- retrieval context。
- tool call。
- feedback/score。

### 7.4 Langfuse 和 Jaeger 的区别

Jaeger/Zipkin：

- 通用分布式 trace。
- 关注服务调用、耗时、错误。

Langfuse：

- 面向 LLM/RAG。
- 关注 prompt、completion、token、retrieval、generation、agent step。

不是谁替代谁，而是关注点不同。

### 7.5 WeKnora 怎么用

项目里：

- HTTP 有 Langfuse middleware。
- Asynq 有 Langfuse middleware。
- chat/embedding/rerank/VLM/ASR 有 wrapper。
- Agent engine/tool 有 span。
- 工具输出会截断，避免 trace 爆炸。

### 7.6 可直接复述的面试回答

> OpenTelemetry 提供通用 trace/span/context 语义，Langfuse 则更适合 LLM/RAG 场景。普通 Jaeger 能告诉我哪个服务慢，但 Langfuse 能看到 prompt、completion、retrieval context、rerank、token 和 tool call。WeKnora 里 HTTP、Asynq、模型 wrapper 和 Agent tool 都接入 Langfuse，这样一次在线问答或异步文档处理可以串成完整 trace。异步任务要特别注意 trace context 传播，否则上传请求和后台处理会断开。

## 8. 隐私和安全：Langfuse 记录 prompt 的风险

### 8.1 风险

RAG prompt 里可能包含：

- 企业内部文档。
- 用户问题。
- 个人信息。
- API 返回结果。
- Agent 工具输出。
- 数据库查询结果。

如果全部原样记录，Langfuse 本身就变成敏感数据仓库。

### 8.2 处理策略

- 采样：不是所有请求都记录完整内容。
- 截断：超长 prompt/tool output 只保留前 N 字符。
- 脱敏：手机号、邮箱、token、API key 替换。
- 权限：Langfuse 项目访问控制。
- 环境隔离：dev/staging/prod 分开。
- 开关：可关闭输入输出记录。
- 合规：客户私有化时 Langfuse 自建在内网。

### 8.3 可直接复述的面试回答

> Langfuse 对排查 RAG 很有价值，但它也会记录 prompt、retrieval context 和模型输出，这些可能包含企业知识库内容，所以必须治理。我的做法是采样、截断、脱敏和权限隔离。工具输出和 prompt 不能无限记录，敏感字段要 redaction，生产环境要限制 Langfuse 项目访问。客户私有化可以自建 Langfuse 在内网；如果客户要求更严格，也可以关闭内容记录，只保留耗时、错误和 token 指标。

## 9. 模型调用 Wrapper

### 9.1 为什么需要 wrapper

模型调用不是普通函数调用，它有：

- 高延迟。
- 不稳定。
- 限流。
- 成本。
- token 限制。
- 隐私风险。
- 输出不确定。

如果业务代码直接到处调用模型 SDK，会导致：

- 超时策略不统一。
- 日志不统一。
- trace 断裂。
- 错误处理分散。
- 成本统计困难。
- 脱敏难。

### 9.2 wrapper 应该做什么

- 统一接口。
- 注入 trace/span。
- 记录模型名、耗时、token。
- 错误分类。
- timeout。
- retry。
- fallback。
- 输入输出截断/脱敏。
- 统一 provider 差异。

### 9.3 错误分类

可重试：

- 429 rate limit。
- 5xx。
- 网络超时。
- 临时连接失败。

不应盲目重试：

- 400 参数错误。
- context length exceeded。
- 权限/API key 错误。
- 内容安全拒绝。

### 9.4 降级策略

- rerank 失败：可降级为向量分数排序。
- embedding 失败：入库任务 retry，在线查询返回错误或提示稍后再试。
- chat 模型失败：切备用模型或返回友好错误。
- VLM/OCR 失败：保留文本解析结果，图片多模态降级。

### 9.5 可直接复述的面试回答

> 模型调用需要 wrapper，因为它涉及超时、限流、成本、trace、脱敏和 provider 差异。WeKnora 里 chat、embedding、rerank、VLM、ASR 都有 Langfuse wrapper，这样模型调用不会散落在业务代码里。wrapper 可以统一记录耗时、token、错误和输入输出摘要，也可以做 retry、fallback 和截断。比如 rerank 服务不可用时可以降级用向量分排序；embedding 入库失败适合重试；context 超长这种参数错误就不应该盲目重试。

## 10. SSE、WebSocket、Redis Stream/List 怎么取舍

### 10.1 SSE

Server-Sent Events：

- 服务端向浏览器单向推送。
- 基于 HTTP。
- 自动重连。
- 适合 LLM token 流。

不足：

- 客户端到服务端不能同连接双向通信。
- 某些代理可能缓冲。

### 10.2 WebSocket

WebSocket：

- 双向通信。
- 适合 IM、协作、实时控制。

不足：

- 连接管理复杂。
- 负载均衡、心跳、断线恢复要处理。

### 10.3 Redis List/Stream

用于服务端内部保存流式事件：

- 用户断线后可按 offset 读取。
- 多实例共享事件。
- TTL 自动清理。

List 简单，适合短期单用户事件。  
Stream 更适合可靠消费和 consumer group。

### 10.4 可直接复述的面试回答

> LLM token 流通常用 SSE 就够了，因为主要是服务端向客户端单向推送，HTTP 生态简单，还支持自动重连。WebSocket 更适合双向实时协作或 IM，但连接管理更复杂。Redis List/Stream 是服务端内部的事件缓冲，不是直接替代 SSE。WeKnora 这类场景可以用 Redis List 保存短期事件，客户端断线后按 offset 拉取；如果未来需要多消费者可靠消费，可以升级到 Redis Stream。

## 11. Agent 工具调用安全

### 11.1 风险

Agent/MCP 工具可能：

- 查询数据库。
- 调外部 API。
- 写 Wiki 页面。
- 删除页面。
- 读取源文档。
- 执行高风险操作。

风险包括：

- prompt injection。
- 越权工具调用。
- 敏感数据泄露。
- 危险写操作。
- 工具输出过大。

### 11.2 防护

- 工具权限和用户权限绑定。
- 高风险工具需要审批。
- 工具参数校验。
- 工具输出截断。
- 工具调用审计。
- prompt 中明确工具边界。
- 对外部内容做不可信输入处理。

### 11.3 可直接复述的面试回答

> Agent 工具调用不能只相信模型决策。模型可能受 prompt injection 影响去调用不该调用的工具，所以工具层要独立做权限判断。读操作和写操作要区分，高风险写操作可以走审批；工具参数要校验，输出要截断并记录审计。WeKnora 里 Agent tool span 进入 Langfuse，有助于排查工具调用链路，但同时也要注意敏感输出不能完整打进 trace。

## 12. 用户说“回答不准”怎么排查

### 12.1 排查路径

1. 看 trace 是否完整。
2. 看 query rewrite 是否改错。
3. 看 embedding 是否成功。
4. 看召回 chunk 是否相关。
5. 看 metadata filter 是否过窄或过宽。
6. 看 rerank 是否误杀正确 chunk。
7. 看 prompt 是否包含正确上下文。
8. 看 prompt 是否超长截断。
9. 看 LLM 是否遵循上下文。
10. 看工具调用是否失败。

### 12.2 可直接复述的面试回答

> 用户说回答不准，我会先看 Langfuse trace，而不是直接怀疑模型。先确认 query 有没有被 rewrite 错，再看向量召回的 chunk 是否相关，metadata filter 是否正确，rerank 有没有把正确 chunk 排掉。然后看 prompt 最终有没有包含正确上下文，是否因为 token 超限被截断。如果检索和 prompt 都没问题，再看 LLM 生成是否幻觉或没有遵循指令。这样可以把问题定位到入库、召回、排序、prompt 或生成某一层。

## 13. 本主题总结

这一主题面试要讲出：

1. middleware 洋葱模型和顺序。
2. JWT 只做鉴权，RBAC/KB Access 做授权。
3. RAG 权限必须进入检索层 metadata filter。
4. Log/Metric/Trace 各自解决不同问题。
5. OpenTelemetry 是通用标准，Langfuse 是 LLM/RAG 观测增强。
6. prompt/tool output 记录有隐私风险，需要采样、脱敏、截断。
7. 模型 wrapper 是治理模型调用的关键抽象。
8. Agent 工具调用要做权限、审批和审计。
