# NoteWeave v2 三模式知识工作台重构设计文档

> 版本：Simplified Three-Mode Refactor  
> 定位：在现有 NoteWeave 基础上进行功能收敛与架构重构，不重新设计成复杂 Agent 平台。  
> 核心目标：把知识工作台简化为三种清晰模式：问答、Wiki、资料调查。  
> 参考来源：腾讯 WeKnora 的高层模式划分思路；Marginalia 的 source-first 资料调查思路。  

---

## 0. 总体结论

NoteWeave v2 重构后采用“三种用户可见模式 + 一个独立 Deep Research 入口 + 一个右侧产物栏 + 一套门控式长期记忆机制”的整体结构：

```text
1. Chat / RAG Mode
   普通问答模式。
   以文档 RAG、Note 检索和当前会话上下文为核心。
   其中 Note 层可复用并轻量改造现有 Wiki 能力。

2. Wiki 模式（Full Wiki Mode）
   面向全量知识组织的 Wiki 模式。
   面向当前研究进程的 Wiki 页面、知识关系和缺口分析。

3. Library Investigation Mode
   资料调查模式。
   参考 Marginalia，先定位源文件，再读取原文窗口，最后形成调查结论。
```

三种模式是并列能力，不强行耦合成一个复杂流程。

它们共享底层资料、原始文件、解析结果、引用和权限能力，但在产品入口、检索策略、上下文组织和输出形态上保持相对独立。

整体结构：

```text
NoteWeave v2
  ├── Chat / RAG Mode
  │     ├── 当前会话上下文
  │     ├── 文档 RAG
  │     ├── Note 检索
  │     └── 引用溯源
  │
  ├── Wiki 模式（Full Wiki Mode）
  │     ├── Wiki 页面
  │     ├── Wiki 摘要
  │     ├── Wiki 关系
  │     ├── 覆盖度检查
  │     └── 缺口分析
  │
  ├── Library Investigation Mode
  │     ├── 资料 metadata
  │     ├── 资料 summary / tag / folder
  │     ├── SourceCard 候选资料卡
  │     ├── SourceWindow 原文窗口
  │     └── 调查结论 / Investigation Note
  
  ├── Deep Research
  │     ├── 独立按钮入口
  │     ├── Evidence-Gated Branchable Research Harness
  │     ├── Table-as-State / Loop Engineering
  │     └── Research Artifact
  
  ├── Artifact Actions Rail
  │     ├── 报告
  │     ├── 测验
  │     ├── 学习指南
  │     ├── FAQ
  │     └── Wiki 草稿
  
  └── Graduated Memory
        ├── Context Signal
        ├── Memory Candidate
        └── Memory Object
```

一句话：

```text
NoteWeave v2 重构为三模式知识工作台：问答模式解决日常 RAG 与 Note 检索，Wiki 模式解决全量知识组织，资料调查模式解决跨文件资料探索；同时通过独立 Deep Research、右侧产物栏和 Graduated Memory 机制承接重型研究、结构化生成与长期知识复用。
```

## 1. 设计参考

## 1.1 参考 WeKnora：高层模式清晰化

WeKnora 的产品思路对 NoteWeave 的启发是：用户感知的是高层任务模式，而不是底层检索算法。

WeKnora 中比较典型的高层能力包括：

```text
RAG-based Quick Q&A
ReAct Agent
Wiki Mode
Citation Popover
RAG Pipeline Progress
Knowledge Base / Wiki 管理
```

NoteWeave v2 不需要完全照搬这些能力，而是吸收其模式划分思想：

```text
用户选择自己要完成的工作：
  问答
  查看 Wiki
  调查资料

系统内部再决定如何检索：
  文档 RAG
  Note 检索
  Wiki 读取
  metadata 检索
  原文窗口回读
```

因此，NoteWeave v2 的用户入口保留三个：

```text
问答
Wiki
调查
```

底层具体使用 BM25、向量检索、Parent-child chunk、重排、原文回读等策略，不直接暴露给用户。

---

## 1.2 参考 Marginalia：source-first 资料调查

Marginalia 的核心不是普通 chunk RAG，而是 source-first investigation。

它的思想可以概括为：

```text
先定位资料
再读取原文窗口
最后形成带来源的调查结论
```

这对 NoteWeave v2 的资料调查模式很有价值。

普通 RAG 更适合回答：

```text
这个文件里怎么说？
这个概念是什么？
这句话有没有来源？
```

而 Marginalia 式资料调查更适合回答：

```text
和这个主题相关的资料有哪些？
这些资料之间有什么关系？
哪些资料支持或反对这个观点？
这批文件里有哪些值得看的材料？
```

因此，NoteWeave v2 将资料调查独立为第三种模式，而不是和普通 Chat RAG 混在一起。

# 2. 核心产品模型

## 2.1 Research Process

Research Process 是一个持续推进的研究主题。

示例：

```text
NoteWeave v2 重构设计
VLA 论文调研
课程论文资料整理
项目需求分析
```

一个 Research Process 下可以包含：

```text
ResearchProcess
  ├── Conversations
  ├── Files / Sources
  ├── Notes
  ├── Wiki Pages
  ├── Investigation Notes
  └── Citations
```

作用：

```text
1. 作为资料、会话、Note、Wiki、调查记录的组织边界。
2. 支撑一个主题下的持续研究。
3. 避免所有文件和对话混在全局空间里。
```

---

## 2.2 Conversation

Conversation 是 Research Process 下的一次或一组聊天。

它主要服务 Chat / RAG Mode。

保存内容：

```text
1. 用户消息。
2. 助手回答。
3. 当前会话附件。
4. 当前会话摘要。
5. 本会话用过的引用来源。
```

设计原则：

```text
Conversation 用来保证聊天连续性。
它不是长期知识结构。
高价值内容应沉淀到 Note 或 Wiki。
```

---

## 2.3 File / Source

用户上传或导入的资料统一称为 Source。

来源可以是：

```text
PDF
Word
Markdown
网页
图片
Excel
PPT
纯文本
代码文件
压缩包
```

系统内部需要保留：

```text
1. 原始文件。
2. 文件快照。
3. 解析文本。
4. 文档分块。
5. 原文定位信息。
```

---

## 2.4 Note

Note 是用户确认过的阶段性理解。

适合保存：

```text
1. 一次问答后的结论。
2. 一次讨论后的设计取舍。
3. 用户自己的理解。
4. 临时但有价值的研究笔记。
```

Note 在 Chat / RAG Mode 中会参与检索。

它的定位是：

```text
比会话摘要更稳定。
比 Wiki 更自由。
适合作为用户个人或团队的阶段性沉淀。
```

---

## 2.5 Wiki

Wiki 是结构化知识页。

适合保存：

```text
1. 概念定义。
2. 架构页面。
3. 方法总结。
4. 对比分析。
5. 研究主题总览。
6. 长期复用的稳定知识。
```

Wiki 是 Wiki 模式（Full Wiki Mode）的核心对象。

---

## 2.6 Investigation Note

Investigation Note 是资料调查模式产生的调查记录。

它保存：

```text
1. 调查问题。
2. 候选资料。
3. 实际阅读过的原文窗口。
4. 资料之间的关系。
5. 调查结论。
6. 未解决问题。
```

它和 Note 的区别：

```text
Note 更偏用户沉淀。
Investigation Note 更偏调查过程记录。
```

高质量 Investigation Note 可以再整理成普通 Note 或 Wiki 草稿。

---

# 3. 共享底座设计

三种模式不强耦合，但共享同一套资料底座。

## 3.1 原始文件保留

即使上传时采用分片上传，系统也必须在上传完成后形成并保留完整原始文件。

要区分三种对象：

```text
Upload Part
  上传过程中的临时分片，用于断点续传和失败重试。

Raw Object
  上传完成后的完整原始文件。

Document Chunk
  从 Raw Object 解析出来的知识分块，用于检索。
```

标准链路：

```text
Upload Parts
  ↓
Complete Upload
  ↓
Raw Object
  ↓
File Snapshot
  ↓
Parse
  ↓
Document Chunks
  ↓
Index
```

保留原始文件的原因：

```text
1. 可以重新解析。
2. 可以预览原文。
3. 可以回读原文窗口。
4. 可以做 citation 校验。
5. 可以证明回答来源。
```

---

## 3.2 文档解析与分块

文件进入系统后执行解析：

```text
Raw Object
  ↓
Parser
  ↓
Text / Page / Table / Image Extract
  ↓
Parent-child Chunking
  ↓
Index
```

推荐保留两级分块：

```text
Child Chunk
  用于精准召回。

Parent Chunk
  用于补充上下文。
```

当需要引用或调查时，再读取原文窗口：

```text
Chunk
  ↓
Parent Chunk
  ↓
SourceWindow
```

---

## 3.3 SourceWindow 原文窗口

SourceWindow 是从原始文件中读取的一段稳定原文。

它可以是：

```text
PDF 的某几页
Markdown 的某个标题段落
文本文件的某几行
Excel 的某个表格切片
代码文件的某个函数区域
压缩包中的某个成员文件
```

SourceWindow 的作用：

```text
1. 支撑引用。
2. 支撑原文核验。
3. 支撑资料调查模式中的“读资料”环节。
4. 支撑 Wiki 和 Note 的来源回溯。
```

---

## 3.4 Citation 引用记录

Citation 用来连接回答或知识结论与原始来源。

基本关系：

```text
Answer / Note / Wiki Claim
  ↓
SourceWindow
  ↓
Raw Object / File Snapshot
```

引用记录至少需要保存：

```text
1. 目标对象：回答、Note、Wiki Claim 或 Investigation Note。
2. 来源文件。
3. 原文窗口位置。
4. 原文片段。
5. 支撑强度。
```

支撑强度可以分为：

```text
直接支持
间接支持
弱支持
冲突
未找到来源
```

---

# 4. Mode 1：Chat / RAG Mode

## 4.1 模式定位

Chat / RAG Mode 是默认模式。

它用于日常问答、文件问答、会话追问和基于已有 Note 的整理。

用户使用方式类似普通 Chat。

适合问题：

```text
帮我总结这个文件。
这个概念是什么意思？
这个设计之前怎么定的？
刚才我们说了什么？
这个结论有来源吗？
根据已有笔记整理一下。
```

---

## 4.2 数据来源

Chat / RAG Mode 使用三类数据：

```text
1. 当前会话上下文
   当前问题、最近对话、当前附件、会话摘要。

2. 文档 RAG
   文件解析后的 chunk、parent chunk、必要时的 SourceWindow。

3. Note 检索
   用户保存过的笔记、阶段性结论、设计取舍。
```

这里不引入复杂路由，核心就是：

```text
Chat Context + Document RAG + Note Search
```

### 4.2.1 Note 与现有 Wiki 能力的关系

当前 NoteWeave 已经存在 Wiki 相关能力，因此 Chat / RAG Mode 中的 Note 不一定需要从零新建一套独立系统。更合理的做法是对现有 Wiki 能力进行轻量改造，将其中偏“草稿、阶段性结论、用户整理内容”的部分抽象为 Note 层使用。

也就是说，v2 中可以把现有 Wiki 能力拆成两种使用语义：

```text
Note 语义
  面向 Chat / RAG Mode。
  用于保存阶段性结论、会话沉淀、人工整理、设计取舍。
  结构可以更自由，不要求完整页面体系。

Wiki 语义
  面向 Wiki 模式（Full Wiki Mode）。
  用于保存结构化、较稳定、可长期复用的知识页面。
  更强调页面关系、知识地图、覆盖度和引用完整性。
```

工程实现上可以复用现有 Wiki 的存储、版本、引用和检索能力，通过字段或类型区分不同用途：

```text
content_type = NOTE / WIKI
status = DRAFT / REVIEWED / PUBLISHED
source = CHAT_SAVE / MANUAL_EDIT / INVESTIGATION / WIKI_GENERATION
```

这样可以避免重复建设两套内容系统，同时保留产品语义上的区别：

```text
Note 是轻量沉淀，服务 Chat / RAG。
Wiki 是结构化知识页，服务 Wiki 模式。
```

---

## 4.3 后端链路

```text
User Question
  ↓
Load Current Conversation Context
  ↓
Resolve Current Files / Process Scope
  ↓
Search Document Chunks
  ↓
Search Notes
  ↓
Merge Results
  ↓
Read SourceWindow if citation is needed
  ↓
Generate Answer
  ↓
Return Answer + Citations
```

---

## 4.4 功能设计

### 4.4.1 当前附件优先

如果用户在本轮上传了文件，默认优先回答当前附件。

例如：

```text
用户：总结一下这个 PDF。
系统：优先查当前 PDF，而不是查整个研究进程。
```

### 4.4.2 当前会话默认参与

系统默认读取最近对话和会话摘要。

例如：

```text
用户：这里不要搞复杂。
系统：知道“这里”指代前面正在讨论的设计。
```

### 4.4.3 Note 参与检索

用户保存过的 Note 可以参与问答。

例如：

```text
用户：我们之前保存的设计原则是什么？
系统：检索 Note，结合当前会话回答。
```

### 4.4.4 引用按需回源

普通回答可以只使用 chunk 和 Note。

当用户问来源，或者回答涉及关键事实时，系统回读 SourceWindow。

```text
Chunk Recall
  ↓
SourceWindow Read
  ↓
Citation
```

---

## 4.5 输出

Chat / RAG Mode 输出：

```text
1. 普通回答。
2. 引用来源。
3. 相关文件。
4. 相关 Note。
5. 保存为 Note。
6. 生成 Wiki 草稿。
```

---

# 5. Mode 2：Wiki 模式（Full Wiki Mode）

## 5.1 模式定位

Wiki 模式（Full Wiki Mode）是面向全量知识组织的 Wiki 模式。

它用于查看和整理当前 Research Process 的结构化知识体系。

它不是普通问答，也不是直接查文档。

它关注：

```text
当前已经形成了哪些知识页面？
页面之间是什么关系？
哪些页面缺少来源？
哪些页面重复或冲突？
还缺哪些关键主题？
```

---

## 5.2 数据来源

Wiki 模式主要使用：

```text
WikiPage
WikiSection
WikiSummary
WikiRelation
WikiCitation
OpenQuestions
```

可以辅助读取：

```text
Note
Citation
SourceWindow
```

但核心仍然是 Wiki。

---

## 5.3 后端链路

```text
User Wiki Request
  ↓
Load Wiki Page List
  ↓
Load Wiki Summaries
  ↓
Load Wiki Relations
  ↓
Analyze Coverage / Missing Topics
  ↓
Expand Selected Wiki Pages
  ↓
Check Citation if needed
  ↓
Generate Wiki Overview / Gap Analysis
```

---

## 5.4 功能设计

### 5.4.1 Wiki 总览

展示当前 Research Process 下的所有 Wiki 页面：

```text
页面名称
页面摘要
所属主题
最后更新时间
引用覆盖情况
相关页面
```

### 5.4.2 知识地图

根据 WikiRelation 展示页面之间的关系。

关系类型可以包括：

```text
包含
依赖
对比
补充
冲突
来源于
```

### 5.4.3 缺口分析

系统根据已有 Wiki 页面和 Note 判断缺少什么。

例如：

```text
已有“Chat / RAG Mode”页面。
已有“Library Investigation Mode”页面。
缺少“Wiki 模式”页面。
缺少“Citation 机制”页面。
```

### 5.4.4 重复和冲突检测

检测：

```text
多个页面是否描述同一概念。
同一概念是否存在不同定义。
某个结论是否和另一个页面冲突。
```

### 5.4.5 Citation Coverage

检查 Wiki 中的关键结论是否有来源。

输出：

```text
有来源
来源较弱
缺少来源
来源已过期
```

---

## 5.5 输出

Wiki 模式输出：

```text
1. Wiki 全局总览。
2. 知识地图。
3. 页面关系。
4. 缺口分析。
5. 重复 / 冲突提示。
6. Citation 覆盖情况。
7. 下一步整理建议。
```

---

# 6. Mode 3：Library Investigation Mode

## 6.1 模式定位

Library Investigation Mode 是资料调查模式。

它参考 Marginalia 的 source-first 思路。

它不直接做普通 chunk RAG，而是：

```text
先找资料
再读资料
最后形成调查结论
```

适合问题：

```text
和这个主题相关的资料有哪些？
这批文件之间有什么关系？
哪些材料支持这个观点？
这些资料有没有互相矛盾？
帮我调查一下这个方向。
```

---

## 6.2 数据来源

Library Investigation Mode 先查资料层信息：

```text
文件名
文件类型
文件摘要
标签
目录
上传时间
最近使用记录
相关资料关系
已有调查记录
```

然后再读取原文：

```text
SourceWindow
Page Window
Line Range
Table Slice
Section
```

---

## 6.3 后端链路

```text
User Investigation Request
  ↓
Analyze Investigation Topic
  ↓
Search Source Metadata
  ↓
Search Source Summary / Tags / Folder
  ↓
Expand Related Sources
  ↓
Build SourceCards
  ↓
Select Sources Worth Reading
  ↓
Read SourceWindows
  ↓
Generate Investigation Report
  ↓
Create Citations
  ↓
Optional Save Investigation Note
```

---

## 6.4 SourceCard 候选资料卡

调查模式先构建 SourceCard，而不是直接给模型全文。

```text
SourceCard
  source_id
  title
  type
  summary
  tags
  folder
  related_sources
  last_used_at
  reason
```

SourceCard 的作用：

```text
1. 让模型先判断哪些资料值得读。
2. 减少无关全文进入上下文。
3. 让调查过程可解释。
4. 方便前端展示候选资料列表。
```

---

## 6.5 SourceWindow 原文阅读

当系统选中某些 SourceCard 后，再读取原文窗口。

原则：

```text
小文件可以读全文。
大文件只读相关页面、段落、行或表格切片。
每个窗口都要能追溯到原始文件。
```

示例：

```text
SourceWindow
  source_id: 1001
  file: marginalia_README.md
  locator: lines 151-170
  reason: 该窗口描述 retrieval funnel 和 source-first investigation。
```

---

## 6.6 Investigation Report

调查模式的输出不是普通回答，而是结构化调查结果。

可以包括：

```text
1. 调查结论。
2. 相关资料列表。
3. 资料之间的关系。
4. 支持该结论的来源。
5. 反对或冲突的来源。
6. 不确定点。
7. 建议下一步阅读什么。
```

---

## 6.7 Investigation Note

用户可以把调查结果保存为 Investigation Note。

```text
InvestigationNote
  topic
  question
  candidate_sources
  read_windows
  findings
  citations
  open_questions
```

Investigation Note 后续可以：

```text
1. 被 Chat / RAG Mode 检索。
2. 被整理成普通 Note。
3. 被生成 Wiki 草稿。
```

但默认不自动发布到 Wiki，需要用户确认。

---

# 7. 三模式关系设计

## 7.1 共享底座

三种模式共享：

```text
1. 文件上传。
2. 原始文件存储。
3. 文档解析。
4. 文档分块。
5. 文件快照。
6. SourceWindow。
7. Citation。

```

## 7.2 模式链路独立

三种模式有独立入口：

```text

  /api/v2/chat/ask

Wiki 模式
  /api/v2/wiki/overview

  /api/v2/investigate
```

```text
Library Investigation Mode

```

## 7.3 结果可以轻量流转

模式之间不强耦合，但结果可以流转。

```text
Chat Answer
  → 保存为 Note
  → 生成 Wiki 草稿

Wiki 缺少来源
  → 回源到文档
  → 补充 Citation

Investigation Report
  → 保存为 Investigation Note
  → 整理成普通 Note
  → 生成 Wiki 草稿
```

这种关系是“结果流转”，不是“流程强耦合”。

## 7.4 Deep Research、Artifact 与 Memory 的位置

三模式之外，还需要明确三条重型能力：

```text
Deep Research
  独立按钮触发
  负责开放式、多步骤、可验证研究

Artifact Actions Rail
  右侧按钮触发
  负责报告、测验、学习指南、FAQ、Wiki 草稿等结构化产物生成

Graduated Memory
  不是独立模式
  负责把聊天、研究轨迹和已确认产物中的高价值内容门控晋升为长期复用知识
```

这样产品形态就是：

```text
三种模式负责日常工作
Deep Research 负责重型研究
Artifact Actions Rail 负责结构化产物生成
Graduated Memory 负责长期知识复用
```

# 14. 最终总结

NoteWeave v2 的新设计可以收敛为：

```text
第一种模式：Chat / RAG Mode
  文档 RAG + Note 检索 + 当前会话上下文。
  负责普通问答和轻量知识复用。

第二种模式：Wiki 模式
  全量 Wiki 页面 + Wiki 关系 + 缺口分析。
  负责结构化知识组织和全局知识视图。

第三种模式：Library Investigation Mode
  参考 Marginalia。
  先查 metadata / summary / relation 找源文件，再读 SourceWindow，最后形成调查结论。
  负责资料探索和跨文件关系发现。
```

三种模式的关系：

```text
共享底层资料、原始文件、SourceWindow 和 Citation。
不强行合并成一个复杂 Agent。
各自有独立入口、独立链路、独立输出。
结果可以轻量流转到 Note 或 Wiki。
```

最终一句话：

```text
NoteWeave v2 是一个三模式知识工作台：用 Chat / RAG 解决日常问答，用 Wiki 模式组织全量知识，用 Library Investigation 做资料调查；再通过独立 Deep Research、右侧产物栏和 Graduated Memory 机制承接研究、生成与长期复用，从而兼顾实现难度、产品清晰度和项目亮点。
```
