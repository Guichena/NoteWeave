## 0. 摘要

本轮做了两件「最小但正确」的改造：

1. **LLM 流式接入 `ChatService.stream`** —— 不再按行切分伪流式，
   真正调用 OpenAI 兼容的 `chat.completions` 接口，按 token 推送
   `chat.delta`；无 LLM 配置时自动回退到原模板 chunk 行为。
2. **`WikiIngestService` 真正走 outbox + Kafka** —— 移除
   `enqueueAndRunSourceIngest` 内部的同步 `ingestSource` 调用，
   让 worker 接管；worker 侧补齐 `startTask` / `completeTask`。

24 份 Flyway 迁移 + Python worker 的契约定义，整理出：

## 1. 本轮已落地的改造

### 1.1 LLM 流式接入 `ChatService.stream`

**修改文件**

- 新增 `backend/src/main/java/com/noteweave/chat/ChatLlmClient.java`
- 新增 `backend/src/main/java/com/noteweave/chat/HttpChatLlmClient.java`
- 修改 `backend/src/main/java/com/noteweave/chat/ChatService.java`
- 修改 `backend/src/main/java/com/noteweave/config/NoteWeaveProperties.java`
- 修改 `backend/src/main/resources/application.yml`

**变更点**

1. 新建 `ChatLlmClient` 接口（流式 token 回调）+ JDK `HttpClient`
   实现的 `HttpChatLlmClient`，协议为 OpenAI 兼容
   `chat.completions?stream=true` SSE。
2. 在 `NoteWeaveProperties` 增加 `Llm(enabled, endpoint, model,
   apiKey, timeoutSeconds)` 配置项；`application.yml` 增加
   `noteweave.llm.*` 五个环境变量。
3. `ChatService.stream` 重写：
   - `stripTemplateMarker` 去掉模板占位前缀，避免把 marker 喂给 LLM。
   - `ChatLlmClient.isEnabled()` 为真时构造 system + user 提示词
     调用 `streamChat`，每个 token 立即写入 SSE `chat.delta`。
   - LLM 不可用 / 抛错时回退到旧 `splitByLines` chunk（dev/测试
     体验不退化）。
   - 流式结束后把 LLM 真实输出回写 `conversation_message.content`。
4. 保留 `chat.citation` / `chat.completed` / `chat.failed` 事件。

**注意：本轮改造尚未经生产编译验证**（环境无可用 Maven）；同时
`HttpChatLlmClient` 同步一次性读取 SSE 流，对小到中等 token 量
（<2k tokens）够用，超长回答仍需后续优化为真正增量推送。

### 1.2 `WikiIngestService` 真正走 outbox + Kafka

**修改文件**

- `backend/src/main/java/com/noteweave/knowledge/WikiIngestService.java`
- `backend/src/main/java/com/noteweave/infra/KafkaTaskConsumer.java`
- `backend/src/main/java/com/noteweave/upload/UploadService.java`（注释）

**变更点**

1. `enqueueAndRunSourceIngest` 只做两件事：
   - `taskService.createTask` 写 task 主表
   - `insert into task_outbox` 写 outbox（status=READY）

   **不再**：
   - 同步调用 `ingestSource`
   - 把 `task_outbox` 直接 update 成 SENT（这是 poller 的工作）
   - 同步 `taskService.completeTask`（worker 做完才算完成）

2. `runSourceIngestNow` / `runSourceRetractNow` 接收新增的
   `taskId` 参数：
   - 进入时 `taskService.startTask(taskId)` 把任务标 RUNNING
   - 跑 `ingestSource` / retract 流程
   - 成功 `completeTask(...,'WIKI_INDEXED' / 'WIKI_RETRACTED',...)`
   - 失败 `completeTask(...,'WIKI_INDEXED_FAILED' / 'WIKI_RETRACTED_FAILED',...)`
     并重新抛出，让 `KafkaTaskConsumer.handle` 走错误日志

3. `KafkaTaskConsumer.onWikiIngest` / `onWikiRetract` 解析
   payload 中的 `taskId` 并透传给 worker。

4. 修掉 `UploadService` 里针对旧同步行为的注释。

**残留风险（不在本轮范围）**

- 现在 outbox 真的「出不去」了：`task_outbox` 表里的 READY 行必须
  等 outbox-poller（见 C-2）。`UploadService` 显式
  `kafkaPublisher.publishWikiIngest(...)` 的路径仍工作；
  一旦以后移除这个二次显式投递，会立即断流。

## 3. 跨模块值得单独写的设计 / 行为漂移

下面几条不属于上述表格，但属于「文档已定、实现严重偏离」级别。

### 3.1 `prefixWithTemplateMarker` 与 LLM 流式的衔接

A-1 / A-2 / A-3 描述的「模板字符串入库」问题，本轮用以下方式兼容：

- 流式时 `stripTemplateMarker` 去掉 marker，把真实 prompt 喂给 LLM。
- 流式成功后用 LLM 输出**整条覆盖** `conversation_message.content`。
- 流式失败时 marker 留在 content 里，下一次 stream 仍能正确处理。

**残留**：用户在聊天列表里看到的第一条 assistant 消息（stream 还没
  跑过）会带 marker 前缀。建议下一轮：
- 要么 stream 在用户进入聊天页时**自动触发一次**（idempotent）。
- 要么 sendMessage 入库前先 stream 一次再入库。
- 要么前端渲染时直接 strip marker。

### 3.2 `MemoryCompilerService` 的 `COMMON` 黑洞

`MemoryCompilerService.compilePack` 在 `allowedNeighborhoods` 里
**始终**包含 `"COMMON"`，因此 `matchesNeighborhood` 对任何
memory_object 都返回 true。这等价于让 Memory 全局生效，与
`docs/Memory机制详细设计.md` 的「显式 neighborhood 匹配」要求
直接冲突。

**最低修复**：移除 `"COMMON"` 常量或在 SQL 层硬过滤。

### 3.3 Wiki 改名/删除的 backlink 完整性问题

- `KnowledgeService.refreshWikiLinksAfterPageTitleChange` 用
  `lower(target_title)` 匹配，若两个不同页面 case-insensitive
  撞名，旧 target_item_id 会被错误改写。
- `deleteItem` 把 backlink 标 `UNRESOLVED` 而非删除，
  `autoFixWiki` 后续会基于 UNRESOLVED 自动创建占位页——多次删除
  → 占位页爆炸。

**建议**：在 `knowledge_item_link` 上加 `(workspace_id, target_item_id)`
唯一约束并在 `appendVersion` 时同步更新；删除改为物理删
link 行 + 在 `wiki_log_entry` 留审计。

### 3.4 `WorkerTaskCallback` 的幂等默认关闭

`worker_callback_receipt(task_id, idempotency_key)` 唯一约束已建，
但 `WorkerTaskCallbackService.registerCallback` 在
`idempotencyKey` 为空时直接返回 null；`WorkerTaskCallbackController`
header `required=false`。**当前 worker 大概率根本不发 header**，所以
幂等基本等于空。

**最低修复**：把 header 设为 `required=true`，并在 worker 端
生成稳定的 `idempotency_key = task_id + ":" + step_name`。

### 3.5 Java 投递到 Python worker 的 payload 几乎都是「占位」

`ResearchRunService` / `ArtifactJobService` 投递到 Kafka 的 outbox
payload 与 Python worker 实际读到的 input 是**两套东西**：
worker 是通过 `GET /internal/worker/{kind}-tasks/{taskId}/input`
回查 DB。`task_id / task_type / workspace_id / target_type /
target_id / payload_version / trace_id / created_at` 这七个字段
**只是 Kafka 端 router 用**，worker 端消费不到。

**结论**：Java / Python 之间的真契约在 `*TaskInputController.java`，
而不是在 Kafka payload。当前实现是对的（outbox poller + 回查），
但 Kafka payload 应该最小化（只保留 router 必需的 task_id 与
worker_kind）。

## 6. 关键判断与权衡

- **为什么 `sendMessage` 不直接干掉模板拼接**：模板生成在
  `buildAnswerDraft` 内部承担「把检索证据、引用、摘录组合成可读
  prompt」的角色。LLM 真正落地时，这一层会退化成「系统提示词 +
  资料证据上下文的拼装」，而不是被彻底删掉。**全文删除**会丢
  `ConversationContext` / `MemoryControlPackResponse` 的信号通路。
- **为什么 LLM 失败时不重试**：当前是同步流式，前端期待边推边收；
  重试会让首次响应延迟变高。改成「先返回 `chat.failed` 事件 +
  DB 记录，前端在用户点「重新生成」时再调一次 stream」更合适。
- **为什么不直接换 webflux**：webflux 的 reactor 改造成本远高于
  本次「先接到 LLM」目标；`HttpClient` + 同步 SSE 行解析已经把
  LLM 接通，下一阶段再升级为真正的流式推送。
- **`prefixWithTemplateMarker` 是否该删**：本轮**保留**——它
  现在的作用是 (a) 在 LLM 不可用时给客户端明显占位信号 (b) 让
  stream 阶段能正确区分「模板文本」和「真实 LLM 输出」。
  下次 LLM 全量稳定后再删。
- **为什么 `WikiIngestService` 不直接删 `enqueueAndRunSourceIngest`
  私有方法**：保留是为了让 outbox poller / worker 接入前代码可读。
  下次接入 worker 后这个方法体可以再瘦身（甚至合并到
  `enqueueAndRunSourceIngestIfEnabled`）。
