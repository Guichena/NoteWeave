## 3. 固定设计决策

- 保持 Java 模块化单体，Python Worker 仍是独立计算平面，本轮不拆业务微服务。
- 普通 QA/Note/Wiki 回答创建轻量 `AnswerRun`；只有长时、异步、可恢复流程才创建 `Execution`。
- 保留 Transactional Outbox，但只用于“数据库状态提交后必须可靠触发外部副作用”的场景。
- 不建立万能 Inbox。按场景采用 claim/fencing、唯一回执、版本化 upsert 或 command receipt。
- Outbox 当前采用 MySQL polling + lease/CAS，不引入 Debezium。
- Kafka 承担 Worker 命令和可靠投影事件，不承载普通聊天 token，也不直接作为浏览器事件通道。
- Redis 承担多实例 SSE 事件桥、限流/并发配额和可降级缓存，不保存业务真相。
- 线程池按负载隔离；增加线程池必须伴随有界队列、拒绝策略、超时、指标和容量依据。
- Flyway 历史迁移不可修改；所有修复只能增加新版本迁移。
- 开发、测试和演示以 Docker Compose 全容器环境为标准运行基线；生产部署复用镜像，但不得直接复用开发口令、端口暴露和单节点中间件配置。

## 4. 施工交付闭环

每个改造项按 Spec-first 方式形成连续证据链：

```text
problem/evidence
  -> design decision
  -> API/event/schema contract
  -> migration and implementation tasks
  -> fixture/unit/integration/smoke/benchmark
  -> rollout and rollback evidence
```

阶段文档不是完成证据。每个任务必须关联代码、自动测试、容器 smoke 结果和质量/性能指标；涉及模型行为时还必须关联固定样本、评测版本和成本/延迟结果。

## 5. 阶段门禁

后续阶段不得绕过前置门禁：

```text
P0 正确性基线 + P0A Docker 交付基线
  -> P1 身份权限与模块边界
  -> P2 Execution / Outbox / 并发设施
  -> P3 Source 与索引投影
  -> P4 AnswerRun 与真流式
  -> P5 三模式策略与检索
  -> P6 Knowledge / Memory / Frontend
```

每阶段只有同时满足以下条件才能关闭：代码与迁移完成、契约测试通过、故障路径验证、关键指标可观察、兼容开关和回滚步骤可执行、旧路径有明确删除时间。
