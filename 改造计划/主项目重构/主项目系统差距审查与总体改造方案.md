# NoteWeave v2 主项目系统差距审查与总体改造方案

> 版本：2026-07-12  
> 性质：主项目架构审查结论、目标设计补充与施工总纲  
> 排除项：Research、Artifact 的 Worker 内部算法、工具编排、报告生成和产物生成实现

## 1. 结论先行

当前项目已经具备 Workspace、资料上传、解析分块、三模式问答、Knowledge、Memory、长任务、Kafka、Elasticsearch、MinIO 和 Worker 回调等较完整的功能外形，但还不是一个边界清晰、可水平扩展、能在故障下保持正确的生产系统。

主要矛盾不是中间件数量不足，而是六类基础语义尚未统一：

1. **身份与租户边界缺失**：大量写入仍使用 `local-user`，多数接口只验证 Workspace 存在，不验证当前用户是否有权限。
2. **异步可靠性没有闭环**：业务事务既写 Outbox 又直接发 Kafka，Task 状态迁移缺少 CAS，消费者和 ES 投影吞错后却可能继续提交 offset。
3. **资料状态早于事实**：解析完成后直接把 Source 标为 `INDEXED/READY`，没有等待 ES 投影确认；通用 UTF-8 解码不能处理 PDF/DOCX。
4. **三种回答只有入口相似，运行模型并未统一**：`ChatService` 和 `RetrievalService` 继续承担模式分支、检索、提示组装、消息持久化和流式协议；当前 SSE 是一次性拼接字符串。
5. **Knowledge 与 Memory 是大服务和规则集合，而非稳定领域能力**：职责过多、依赖方向不合理、缺少基于使用结果的反馈闭环。
6. **前端与运维能力尚未生产化**：单个 `App.tsx` 约一万行以上；轮询、API、状态和视图耦合；Redis、隔离线程池和端到端可观测性尚未真正落地。

正确的方向不是一次性重写，也不是为了展示能力而让所有流程都经过 Kafka、Redis 和线程池。推荐方案是：**模块化单体 + 独立计算 Worker + 轻量 AnswerRun + 长任务 Execution + 可靠 Outbox + 场景化幂等 + 版本化投影 + 真 SSE/Redis Streams + 有界隔离线程池**。

## 2. 审查范围与证据边界

### 2.1 纳入审查

- 后端：`workspace`、`upload`、`source`、`chat`、`knowledge`、`memory`、`task`、`worker` 边界、`infra`、配置和数据库迁移；
- 前端：主工作台、上传、Conversation、QA/Note/Wiki、Knowledge、Memory、任务状态与 SSE；
- 中间件：MySQL、Flyway、Kafka、Elasticsearch、MinIO、Redis 计划、线程池、HTTP/SSE；
- 横切能力：鉴权、幂等、事务、并发、可观测性、测试、灰度和回滚。

### 2.2 排除审查

- Research Worker 和 Artifact Worker 内部流程是否最优；
- 它们的搜索、验证、生成、修复和工具运行算法；
- 它们专属 UI 的产品重设计。

主项目仍要统一管理这两个 Worker 的边界：创建 Execution、投递命令、attempt fencing、回调回执、文件元数据、结果引用、取消/恢复和审计。

## 3. 当前系统真实画像

### 3.1 可保留资产

- Spring Boot + JDBC + Flyway 的主应用基础适合继续演进为模块化单体；
- MySQL 已覆盖 Workspace、Task、Source、Conversation、Knowledge、Memory 和 Worker 基础数据；
- Source Snapshot、Chunk、Citation、Knowledge Version 等模型有继续演进价值；
- MinIO/ObjectStorage 抽象、Kafka 基础配置、ES Java Client、TaskEvent、Outbox 和 callback receipt 提供了原型；
- 前后端已经覆盖主要用户流程，适合渐进迁移而非推倒重写。

### 3.2 代码级证据

| 区域 | 当前证据 | 影响 |
| --- | --- | --- |
| Workspace | `WorkspaceService.LOCAL_USER_ID = "local-user"` | 无真实身份、成员权限和审计主体 |
| 控制器 | `WorkspaceController` 直接编排 Workspace 与 Wiki 服务 | 控制器跨领域协调，事务和权限边界不清 |
| Upload | `UploadService` 同时操作 JDBC、MinIO、Task、Outbox、Kafka、解析与 Wiki | 巨型应用服务、双写和长事务 |
| 上传合并 | 使用 `ByteArrayOutputStream` 合并全部分片 | 大文件内存峰值与 OOM 风险 |
| Outbox | 同一流程写 Outbox 后直接 `publishSourceParse` | 事务提交/消息发送存在双写窗口和重复来源 |
| Parser | 文件整体按 UTF-8 文本处理 | PDF、DOCX 等格式无法得到可信正文 |
| Source 状态 | 解析后直接写 `index_status='INDEXED', status='READY'` | ES 失败时对外谎报可检索 |
| ES consumer | 异常只记录日志，不向容器抛出 | offset 可提交，投影永久缺失 |
| Kafka group | `KafkaTaskConsumer` 与 `ElasticsearchIndexer` 以同一 group 监听 `source.index` | 同一事件只会落到其中一个竞争消费者 |
| Task | `completeTask`、`recordProgress`、`failTask` 未限制来源状态 | 迟到回调可把终态改回 RUNNING 或覆盖成功结果 |
| Chat | `ChatService` 约 1,222 行，内部按 QA/Note/Wiki 分支 | 回答运行、领域策略和持久化高度耦合 |
| Retrieval | `RetrievalService` 约 1,783 行 | QA/Note/Wiki 检索、排序、图和 DTO 混合 |
| SSE | Controller 返回完整 `String`；Task stream 同样拼接历史文本 | 不是流式，断线续传与背压无从实现 |
| Message seq | 通过 `max(message_seq)+1` 生成 | 并发发送可能产生重复序号 |
| ES 查询 | ES hit 后逐条查 Source 元数据 | N+1 查询 |
| Knowledge | `KnowledgeService` 约 1,915 行 | CRUD、版本、图、统计、lint、治理混为一体 |
| Memory | 固定阈值、固定效用、归一化文本精确相等 | 冲突、过期、优先级和实际效果判断不足 |
| 依赖方向 | `MemoryCompilerService` 直接依赖 Artifact Skill Catalog | 主域依赖专项 Worker 领域实现 |
| Redis | 有部署/依赖意图但主项目无稳定业务实现 | 多实例 SSE、限流、配额和缓存仍为空缺 |
| 线程池 | 无按负载隔离的业务线程池配置 | I/O、投影和推送可能互相拖垮 |
| 前端 | `App.tsx` 约 11,799 行 | 状态、API、定时器、格式化和视图难以独立测试 |

### 3.3 数据模型差距

- 尚无 `answer_run`、`message_revision`、统一 `execution`/`execution_attempt` 和投影 checkpoint；
- `source_chunk(source_snapshot_id, chunk_no)` 只有普通索引，没有唯一约束；
- Source 的解析状态与检索投影状态没有独立的版本/计数确认；
- Task 兼具 UI 任务、Worker 执行和领域状态含义，无法严格表达 attempt 和 fencing；
- 历史迁移文件已经存在变动风险。自本方案起必须把 V001-V024 视为不可变，修复使用新迁移。

## 5. 目标架构

### 5.1 进程和模块边界

```text
Browser
  -> API / SSE
Java modular monolith
  -> identity + workspace
  -> source + ingestion
  -> answer + retrieval
  -> knowledge + memory
  -> execution control plane
  -> infrastructure adapters
       -> MySQL (business truth)
       -> MinIO (binary truth)
       -> Kafka (reliable commands/projections)
       -> Elasticsearch (rebuildable search projection)
       -> Redis (ephemeral stream/cache/quota)
  -> Worker boundary adapters
       -> Research Worker
       -> Artifact Worker
```

模块之间通过应用端口、领域事件契约和只读查询端口协作。Controller 只做协议适配、鉴权上下文和请求校验；Application Service 负责用例编排；Domain Service 负责规则；Repository/Publisher/Storage 是端口；基础设施实现不能反向泄漏到领域层。

### 5.2 两种运行模型

| 模型 | 适用 | 数据 | 不适用 |
| --- | --- | --- | --- |
| `AnswerRun` | 秒级 QA/Note/Wiki 回答、可流式、通常单进程完成 | answer_run、message_revision、answer_event 摘要 | 不需要 Kafka/Attempt 的普通回答 |
| `Execution` | 解析、重建索引、Wiki 投影、Research/Artifact 边界等长时/异步/可恢复任务 | execution、attempt、event、outbox、receipt | 不应强迫每个聊天 token 经过它 |

AnswerRun 超过时限或需要外部 Worker 时可以升级并关联 `execution_id`，但二者不能合并成一个万能 Task。

### 5.3 统一回答管线

```text
AnswerApplicationService
  -> create AnswerRun
  -> resolve AnswerModeStrategy(QA | NOTE | WIKI)
  -> build RetrievalPlan
  -> RetrievalOrchestrator
       -> lexical / vector / graph / metadata adapters
       -> fusion -> rerank -> evidence budget
  -> EvidenceBundle
  -> PromptComposer + MemoryControlPack
  -> LlmGateway
  -> token/event stream
  -> CitationAssembler
  -> MessageRevision + AnswerRun terminal state
```

策略统一的是生命周期、输入输出、证据包和观测，不是强行让三种模式使用同一套召回算法。

### 5.4 Source 真相与投影

Source 状态至少区分：对象已保存、正文已解析、Chunk 已持久化、索引投影中、索引已确认、可回答、失败/删除。ES 是可重建投影，只有目标 snapshot/version 的全部 chunk 被确认后才能把 `index_status` 标为 `INDEXED`。

### 5.5 中间件职责

| 中间件 | 应做 | 不应做 |
| --- | --- | --- |
| MySQL | 业务真相、状态机、Outbox、幂等回执、checkpoint | 高频 token 广播 |
| Kafka | Worker 命令、可靠领域/投影事件、削峰 | 普通 QA 请求、浏览器直连、共享可变状态 |
| Elasticsearch | BM25/vector 检索、过滤、可重建投影 | 业务状态真相、权限唯一来源 |
| MinIO | 原文件、生成文件、大对象 | 工作流状态和小型 JSON 真相 |
| Redis | SSE Streams、令牌桶/并发配额、cache-aside、短协调锁 | 最终幂等、持久任务 claim、业务唯一真相 |

## 6. Outbox、Inbox 与幂等设计结论

### 6.1 Outbox 必须保留，但缩小适用范围

以下场景需要 Outbox：Source 解析命令、索引投影事件、Wiki 投影命令、外部 Worker 命令、不可丢的通知。业务事务只提交领域状态和 Outbox；Dispatcher 在事务外 claim、发送、记录结果。当前选择 MySQL polling + lease/CAS，满足现阶段规模且容易调试，不引入 Debezium 的运维复杂度。

### 6.2 不建设全局 Inbox

所有 Kafka 消息都先插同一张 Inbox 会增加写放大、清理成本和热点，并不能自动解决业务副作用幂等。采用场景化方案：

| 场景 | 最终保证 |
| --- | --- |
| Worker command | Execution claim + `attempt_no/fencing_token` |
| Worker callback | `(execution_id, attempt_no, callback_id)` 唯一回执 |
| ES chunk projection | 稳定 document id + aggregate/snapshot version |
| Wiki projection | source version + projection checkpoint |
| 无自然幂等的外部 command | domain-specific command receipt |
| Redis `SET NX EX` | 仅减少短期重复，不作为正确性保证 |

### 6.3 Dispatcher 基线

- `SELECT ... FOR UPDATE SKIP LOCKED` 或条件 UPDATE claim；
- `status/lease_owner/lease_until/attempt_count/next_attempt_at`；
- 指数退避 + jitter；
- 达上限进入 DEAD，可查询、告警和人工 redrive；
- Producer 开启 `acks=all`、幂等发送和合理 timeout；
- 指标覆盖 backlog age、publish latency、retry、dead count。

## 7. 线程池设计

为了体现并发控制能力，应实现真正隔离的有界执行器，而不是增加一个全局 `@Async`：

| 执行器 | 负载 | 初始原则 | 饱和策略 |
| --- | --- | --- | --- |
| `answerIoExecutor` | LLM、检索聚合等短 I/O | 小队列、按 Workspace 配额 | 快速拒绝/降级，不无限排队 |
| `sourceIoExecutor` | MinIO/解析调度 | 按文件并发限制 | 持久任务回到 Execution 重试 |
| `projectionExecutor` | ES/Wiki 投影 | 按分区/aggregate 保序 | Kafka 不 ack，稍后重试 |
| `sseDispatchExecutor` | 事件序列化和客户端发送 | 与业务池隔离 | 断开慢客户端，允许 resume |
| `maintenanceExecutor` | Outbox、清理、checkpoint | 低优先级、小并发 | 延迟执行并告警 |

每个池暴露 active、queue、completed、rejected 和 task latency；线程数由连接池、外部限额和压测确定。CPU 密集解析优先放 Worker 或专用有限池，不能用更多线程掩盖阻塞。

## 8. Redis 采用方案

Redis 分三步引入，且每一步可独立降级：

1. **Redis Streams 事件桥**：Java 实例将 Answer/Execution 事件写入 `stream:{workspace}:{run}`，网关实例消费并推送 SSE。MySQL 保存阶段快照/终态，客户端以 event id 续传，Stream 设置 `MAXLEN ~` 和 TTL 清理。
2. **限流与并发配额**：Lua 令牌桶限制 user/workspace/API；带 lease 的计数器控制 LLM、解析、导出并发。Redis 不可用时采用本机保守限额，而不是完全放开。
3. **Cache-aside**：缓存 Workspace 权限、Source metadata、Wiki summary、Memory/Skill 只读目录。必须有 TTL+jitter、写后失效、空值短 TTL、命中率和故障降级。

Redis 锁只用于索引 alias 切换、单次 rebuild 协调等短操作；持久任务 ownership 仍由 MySQL lease/CAS 保证。

## 9. 安全、可观测性和测试

### 9.1 安全

- 接入可替换的 `CurrentPrincipal`，开发模式可以映射 local-user，但生产配置禁止匿名回退；
- 所有 Workspace 资源查询同时带 `workspace_id`，并在应用服务入口执行成员角色校验；
- Worker 内部接口使用轮换凭据或 mTLS，回调校验 execution、attempt 和 scope；
- 凭据全部来自环境/secret，不在默认配置中提供可工作的生产口令；
- 日志和事件 payload 对 prompt、token、文件路径和个人信息做分级与脱敏。

### 9.2 可观测性

统一传播 `request_id`、`correlation_id`、`workspace_id`、`answer_run_id/execution_id`、`attempt_no`。HTTP、JDBC、Kafka、Redis、MinIO、ES 和 LLM 建立 trace；用 Micrometer 输出 RED/USE 指标；结构化日志不得依赖中文 message 解析。

建议 SLO：API 可用性、回答首 token 延迟、回答完成率、上传完成率、解析/索引成功率、Outbox 最大积压年龄、Kafka consumer lag、SSE 活跃连接与断线恢复率。

### 9.3 测试金字塔

- 单元测试：状态机、策略选择、配额、融合排序和 Memory gate；
- Repository/迁移测试：Testcontainers MySQL，验证唯一约束和 CAS；
- 中间件集成：Kafka 重复/乱序/DLT，ES 版本投影，Redis 故障与恢复，MinIO 大文件；
- 契约测试：API 和事件 schema 兼容；
- 端到端：上传到可检索、三模式回答、SSE 断线恢复、越权拒绝；
- 故障注入：Dispatcher 发送前后崩溃、迟到回调、ES 不可用、Redis 不可用、慢客户端。

## 10. 阶段路线与依赖

| 阶段 | 核心产出 | 前置 | 完成标志 |
| --- | --- | --- | --- |
| P0 | 正确性、安全、构建和迁移基线 | 无 | 不再双写、状态不误报、关键构建全绿 |

| P2 | Execution、Outbox、幂等、线程池、观测 | P1 | 长任务可 claim/retry/fence/redrive |
| P3 | 流式上传、Parser Registry、版本化 ES 投影 | P2 | 大文件稳定；Source READY 与投影事实一致 |
| P4 | AnswerRun、MessageRevision、真 SSE、Stream bridge | P1/P2 | 首 token 流式、断线续传、回答可审计 |

## 11. 兼容、灰度与删除规则

- 所有新表、新 API 和新事件先并行读或影子运行，写入者始终只能有一个；
- Feature flag 至少包括 `execution.v2`、`source.pipeline.v2`、`answer.run.v2`、`answer.sse.v2`、`retrieval.strategy.v2`、`redis.bridge.enabled`；
- 旧 API 在兼容层转换，新旧结果需记录差异率，不允许双边产生副作用；
- 回滚优先停新入口/Dispatcher，保留新数据，不执行破坏性逆迁移；
- 每个兼容适配器必须登记 owner、启用日期、删除条件和最迟删除版本。

## 12. 明确不做的方案

- 不为了“后端能力”拆成大量微服务；当前团队和领域成熟度更适合模块化单体；
- 不让普通 QA 经 Kafka 排队；它需要低延迟和直接取消；
- 不把 Task、AnswerRun、Execution 合并为万能状态表；
- 不建设所有消费者共享的万能 Inbox；
- 不用 Redis 锁代替数据库状态机、唯一约束和 fencing；
- 不在缺少离线评测集时直接堆叠向量库、reranker 和复杂图检索；
- 不为了统一风格把 JDBC 全量迁到 JPA；当前更需要明确 Repository 和 SQL 契约；
- 不修改已执行的 Flyway 历史文件。

## 13. 项目级验收标准

1. 任一用户无法读取、推送或修改非成员 Workspace 的资源；
2. Outbox 在发送前/后崩溃和重复投递下不丢任务、不重复产生不可逆结果；
3. 迟到 attempt/callback 不能覆盖新 attempt 或终态；
4. Source 只有目标 snapshot 的索引确认完成后才进入可检索状态；
5. QA、Note、Wiki 共用 AnswerRun 生命周期和 EvidenceBundle，但策略独立可测；
6. SSE 可看到增量 token/阶段事件，断线可以凭 cursor 恢复；
7. Redis、ES 或 Kafka 单点不可用时行为有定义，系统不会静默返回错误事实；
8. 五类线程池互相隔离且有容量、拒绝和指标；
9. 前端主流程不再依赖万行级 App 单文件，关键流程具备集成测试；
10. 任一 Execution/AnswerRun 能按 correlation id 查看入口、阶段、外部调用、事件和终态。

## 14. 方案与旧文档的关系

原 `改造计划/主项目检修与改造方案.md` 和 `docs/主项目系统设计与中间件全面审计及全新优化方案.md` 保留为审查过程与论证材料，不再作为逐项施工清单。本目录总纲负责“主项目差距与阶段依赖”，各阶段文档负责“怎么改和怎么验收”。目标系统定义仍以 `docs/NoteWeave-v2目标系统架构与功能中间件设计.md` 为权威源。

本方案不否定 Outbox、Redis、线程池等设计，而是收紧它们的职责：真正能展示后端能力的是在重复、并发、崩溃、慢消费者和多实例情况下仍然可证明正确，而不是中间件出现在依赖列表中。

## 15. 外部项目经验的筛选与吸收

根据同类 AI 全栈/Agent 项目经验，本项目只吸收能直接解决当前代码问题的工程方法，不照搬框架名称。当前正式纳入施工的重点只有三项：实时会话事件流、可恢复执行语义、固定样本质量/性能门禁；其余能力必须再次经过 ADR 评审。

| 候选经验 | 决策 | NoteWeave 落点 |
| --- | --- | --- |
| queue/state machine/lease/retry/replay | 采用 | Execution、Attempt fencing、Outbox、DLT redrive、运行时间线 |
| SSE/Socket.IO/WebSocket 统一事件协议 | 只采用 SSE | 会话回答、Citation 和 Execution 摘要使用统一 SSE；不引入 Socket.IO/WebSocket |
| checkpoint/HITL | 沿用已有需求 | 只用于高风险 Memory promotion 和已有长任务 approval，不扩大范围 |
| fixture/smoke/model judge/benchmark | 采用 | 固定样本、确定性校验优先、Judge 辅助、质量/成本/延迟回归门禁 |
| cold/warm 性能基线 | 采用 | API、检索、容器启动和首次模型调用分别记录 cold/warm p50/p95 |
| Spec-first 协作 | 采用 | evidence -> decision -> contract -> tasks -> tests -> rollout evidence |
| LangGraph/LangChain/Mastra | 不引入 | 使用现有 Java Execution 与 Python Worker 运行时，避免第二套状态机 |
| Bull/JS queue | 不引入 | 与 Kafka + MySQL Outbox/Execution 职责重复 |
| PostgreSQL/Next.js 服务端 | 不迁移 | 当前 MySQL + Spring Boot 可满足需求，迁移没有直接业务收益 |

当前新增三项正式系统能力：

1. **Replay 不是简单重新发消息**：从已验证 checkpoint/attempt 创建新执行，记录原 execution、原因、操作者和版本；不可逆副作用必须再次通过幂等或人工确认。
2. **版本化交互协议**：Answer/Execution 事件具有 schema version、sequence、cursor 和终态快照；前端 reducer 对重复、乱序和未知字段有定义。
3. **质量与成本共同门禁**：每次 prompt/model/retrieval 变更同时比较质量、输入/输出 token、首 token、总延迟和失败率；没有固定样本和基线的数据不能写成项目能力。

## 16. Docker 运行架构

开发、集成测试和演示以全容器 Compose 为标准基线，包含 Frontend/Nginx、Backend、两个 Worker 边界以及 MySQL、Kafka、Redis、MinIO、Elasticsearch。容器内依赖全部使用 Compose DNS；Frontend 以同源 `/api` 代理 Backend 并支持 SSE。

开发 Compose 与生产部署必须区分。当前单节点、明文协议、宿主机端口和开发口令不能被描述为生产能力。详细施工与验收见 `阶段0A-Docker全容器运行与交付基线.md`。
