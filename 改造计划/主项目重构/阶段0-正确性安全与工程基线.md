# 阶段 0：正确性、安全与工程基线

> 目标：在抽象和功能扩展前，先让现有系统的构建、数据、状态和消息行为可信。  
> 非目标：本阶段不引入统一 Execution、不升级检索算法、不拆分前端页面。

## 实施状态（2026-07-13）

本轮已完成：

| 编号 | 现状 | 风险 |
| --- | --- | --- |
| P0-01 | Source/Wiki 路径写 Outbox 后又直接发 Kafka | 丢消息或重复触发，Outbox 形同虚设 |

## 2. 施工包

### 2.1 恢复构建基线

1. 修复所有测试对 `NoteWeaveProperties` 的构造方式，优先提供 Test Builder/fixture，避免每增一个配置字段就修改大量测试。
2. 固定执行：`mvn test`、前端 test/build、主应用无 Kafka/ES/Redis 的最小启动测试。
3. 增加配置组合测试：Kafka on/off、ES on/off、Redis on/off、MinIO/local storage。
4. 校验所有条件 Bean 的依赖也条件化。`ElasticsearchIndexer` 应由 `@ConditionalOnProperty` 或 Noop Port 保证 ES disabled 时可启动。
5. 以 `阶段0A-Docker全容器运行与交付基线.md` 作为统一运行环境，CI 不再只验证宿主机进程组合。

验收：干净数据库可从 V001 迁移到最新版本；四种配置组合 ApplicationContext 均能启动；后端/前端测试无编译失败。

### 2.2 冻结迁移历史

- 将当前已发布环境认可的 V001-V024 checksum 导出到基线记录；
- 不再编辑 V001-V024，差异通过新迁移修正；
- CI 增加 Flyway validate 和“历史迁移文件 hash 不可变”检查；
- 新增迁移建议：
  - `V025__repair_main_project_constraints.sql`；
  - 为 `(source_snapshot_id, chunk_no)` 增加唯一约束，执行前先检测/清理重复数据；
  - Conversation 消息序号使用数据库唯一约束；
  - 若当前实际表缺 `conversation_message.updated_at`，只通过 V025 新增，不能回改 V005。

本地 V020 漂移已按安全顺序处理：先完成主库备份，确认 `verdict_used_llm` 无 NULL 数据，再将字段调整为 NOT NULL DEFAULT FALSE，最后把 schema history checksum 对齐当前权威文件。其他环境不得直接照抄 checksum；必须重复执行备份、结构/数据核对和验证流程。

### 2.3 停止伪 Outbox

在 `UploadService`、`SourceService`、`WikiIngestService` 等路径逐一列出：事务内写入、Outbox 记录、Kafka 直发、同步 fallback。对每个 command 选定且仅保留一个入口：

```text
DB transaction
  -> update aggregate
  -> insert outbox READY
commit
  -> existing minimal dispatcher publishes
```

Kafka disabled 的本地开发模式不能在业务 Service 内悄悄改为同步执行；应使用明确的 `DomainCommandPublisher` 实现：生产为 Outbox，测试/本地可为可观察的 InMemory adapter。

临时 Dispatcher 至少保证条件 claim、失败重试和发送成功后标记；P2 再抽成通用实现。

### 2.4 修复 Kafka/ES 语义

- 删除 `KafkaTaskConsumer.onSourceIndex` 空监听，或使用独立 observer group；投影消费者必须使用专属 `noteweave-es-projector-v2` group；
- ES 写入失败必须抛异常，由 `DefaultErrorHandler` 重试并进入 DLT；
- DLT payload 保留原 topic/partition/offset、event id、aggregate id/version 和异常分类；
- 提供受权的 redrive 管理操作，不允许直接改 offset 猜测恢复；
- 对无效 schema 立即送不可重试 DLT，对网络/429/5xx 执行退避重试；
- P0 暂时把 Source 状态停在 `PARSED/INDEXING`，不能在 ES consumer 确认前写 INDEXED。

### 2.5 收紧 Task 状态机

先为旧 Task 增加允许迁移矩阵：

```text
PENDING -> RUNNING | FAILED | CANCELLED
RUNNING -> WAITING | COMPLETED | FAILED | CANCELLED
WAITING -> RUNNING | COMPLETED | FAILED | CANCELLED
terminal -> terminal (no-op only when identical)
```

所有 UPDATE 使用 `where id=? and task_status in (...)`，检查 affected rows；状态未迁移时不得写一条虚假的成功事件。进度更新不得把 COMPLETED/FAILED/CANCELLED 改回 RUNNING。重复 complete 只有 result_ref 相同才幂等，否则记录冲突并拒绝。

P0 不尝试给旧 Task 补齐完整 attempt，P2 再用 Execution 接管长任务。

### 2.6 修复消息序号

推荐为 Conversation 增加 `next_message_seq`，在事务内执行：

```sql
update conversation
set next_message_seq = last_insert_id(next_message_seq + 1)
where id = ? and workspace_id = ?;
```

也可使用带行锁的 sequence repository。无论哪种方式，都必须保留 `(conversation_id, message_seq)` 唯一约束，并对插入冲突进行有限重试。不能继续依赖 `max+1`。

### 2.7 安全止血

- 生产 profile 启动时，若内部 token、JWT key、数据库/MinIO 密码为空或等于示例值则 fail fast；
- 所有 Worker callback 默认要求内部认证，开发绕过只能显式开启；
- 在 P1 完整 RBAC 前，至少通过统一 `WorkspaceAccessGuard` 验证请求用户与 Workspace owner/member；
- 资源查询必须带 workspace 条件，防止“先按 id 查到再判断”的遗漏；
- 上传文件名、MIME、大小、路径和 archive 内容执行安全校验。

## 4. 测试与故障验证

- 并发 50 次插入 Conversation message，序号唯一且连续；
- complete 后发送 progress/fail，终态不变且产生冲突指标；
- Outbox 插入后停进程，重启后仍发布；发送成功但标记前停进程，重复消费不产生重复副作用；
- ES 断开时 Source 不进入 READY，消息重试并最终进入 DLT；恢复并 redrive 后投影完成；
- 同一批 `source.index` 事件全部到达 ES projector；
- 非成员访问任意 Source/Conversation/Knowledge 返回 403，不能用 404/500 掩盖实现遗漏；
- Kafka/ES/Redis 关闭时 Context 启动行为符合配置说明。

## 5. 观测与验收

新增指标：非法状态迁移次数、Outbox backlog/oldest age、Kafka retry/DLT、ES projection failure、Source 各状态数量、消息序号冲突、403 数量。所有日志带 workspace、task/source、event id 和 correlation id。

完成门禁：P0-01 至 P0-09 均有自动测试；没有业务路径既写 Outbox 又直发同一命令；历史迁移冻结；Source 不再误报 INDEXED；生产弱凭据无法启动。

同时建立 cold/warm 基线：容器冷启动、首个 API、首个 ES 查询、首个模型请求分别记录 p50/p95。阶段 0 只建立可信基线和回归阈值，不承诺脱离硬件、样本和并发条件的孤立性能数字。

## 6. 回滚

- 代码回滚可恢复旧读取，但不得回滚已新增的约束/列；
- 新 Dispatcher 出现问题时暂停 claim，不删除 READY 数据；
- ES 投影修复可暂停并保留 DLT，恢复后 redrive；
- 状态机 CAS 不提供“关闭正确性”的开关，只允许临时增加合法来源状态。
