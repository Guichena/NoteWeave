# 阶段 3：资料上传、解析与索引投影

> 目标：建立可处理大文件、多格式、可重试且状态真实的 Source 数据管线。  
> 前置：阶段 0 的状态修复、阶段 2 的 Execution/Outbox。

## 1. 目标链路

```text
init upload
  -> direct multipart upload to MinIO
  -> complete + verify object metadata
  -> DB: Source/Snapshot=STORED + Execution + Outbox(ParseRequested)
  -> parser selects by detected content type
  -> normalized document + passages batch commit
  -> Outbox(IndexProjectionRequested)
  -> ES bulk versioned projection
  -> projection checkpoint confirms expected passage count
  -> SourceSnapshot=SEARCHABLE, Source=READY
  -> optional WikiProjectionRequested
```

对象存储调用不放在长数据库事务中。任何一步失败都保留可诊断状态和可重试 Execution，不能通过同步 fallback 偷偷绕过状态机。

## 2. Source 状态模型

建议把 Source 稳定身份与 Snapshot 处理状态分开：

| 维度 | 状态 |
| --- | --- |
| object | INITIATED, UPLOADING, STORED, VERIFIED, FAILED |
| parse | PENDING, PARSING, PARSED, FAILED |
| projection | PENDING, INDEXING, INDEXED, FAILED, STALE |
| lifecycle | ACTIVE, DELETED |

`Source=READY` 是派生结果：active snapshot 已 VERIFIED + PARSED + INDEXED。删除采用 tombstone/version 事件，ES/Wiki 各自确认撤回；删除过程中可以显示 DELETING。

每个 Snapshot 保存：object key/version/etag/size/hash、media type、parser id/version、content hash、passage count、projection version、错误码。相同内容可按 Workspace + hash 去重，但不能跨 Workspace 泄漏存在性。

## 3. 上传重构

### 3.1 API

- `POST /workspaces/{id}/uploads`：校验配额并创建 multipart upload；
- 客户端使用 presigned URL 直传分片；
- `POST /uploads/{id}:complete`：提交 part etag，服务端调用 MinIO complete 并 HEAD 验证；
- `GET /uploads/{id}`：返回上传与后续 Execution 状态；
- `DELETE /uploads/{id}`：终止未完成 multipart，清理孤儿分片。

后端不再用 `ByteArrayOutputStream` 合并完整文件。无法直传时，使用临时文件/流式 copy，设置单请求/Workspace 大小和并发限制。

### 3.2 事务边界

1. 短事务创建 upload record；
2. 事务外完成 MinIO multipart；
3. HEAD/hash 验证后，短事务写 Source/Snapshot、Execution 和 Outbox；
4. complete API 的 Idempotency-Key + upload status 保证重复请求返回同一 Source。

MinIO 成功、DB 失败时由 orphan reconciler 依据 upload id 清理或补偿；不能在 DB 回滚里假设对象存储会回滚。

## 4. Parser Registry

```java
interface DocumentParser {
    boolean supports(DetectedMedia media);
    ParsedDocument parse(ParseContext context, InputStream content);
}
```

首批实现：PlainText/Markdown、HTML、PDF、DOCX。格式以 magic bytes + MIME 检测为准，不信任扩展名。PDF/DOCX 可使用 Apache Tika/PDFBox/POI 或交给专用解析 Worker；扫描 PDF 明确进入 OCR_UNSUPPORTED/OCR_PENDING，而不是输出乱码。

`ParsedDocument` 包含 title、正文 block、页码/section/offset、语言和 parser warning。解析输出先标准化再切 Passage，保留从 Passage 回到原文件页码/字符范围的引用定位。

安全要求：压缩炸弹限制、页数/解压大小/解析时间上限、临时目录隔离、宏与外部实体禁用、异常文件隔离。Parser 版本变化可以触发新 Snapshot projection version，不覆盖旧证据引用。

## 5. Passage 与批量写入

不要继续逐行插 Chunk 和逐条发索引事件。建议 Passage 字段：id、workspace/source/snapshot、ordinal、content、token_count、section_path、page_start/end、char_start/end、content_hash、metadata。

- 使用 JDBC batch，每批按数据库 packet 和事务时长压测确定；
- `(snapshot_id, ordinal)` 唯一；
- passage id 稳定可重算，便于 ES 幂等；
- 窗口在查询时按邻接关系组装，或存轻量邻接，不重复大段正文；
- 一个 Snapshot 完成后发布一条 projection command（含 version/expected_count），投影器自行批量拉取；不为每个 chunk 制造 Kafka 消息风暴。

## 6. Elasticsearch 投影

### 6.1 索引与 alias

采用版本化索引模板，例如 `noteweave_passage_v2_000001` + 读写 alias。Workspace 作为 routing/filter 字段，是否每 Workspace 独立索引要根据数量与规模决定；大量小 Workspace 不适合一 Workspace 一物理索引。

文档 id 为稳定 passage id，字段包含 snapshot/projection version。Bulk API 部分失败必须逐项分类重试；不能把整个 bulk 的 HTTP 200 当成全成功。

### 6.2 Checkpoint

`search_projection_checkpoint(snapshot_id, projection_version, expected_count, indexed_count, failed_count, status, last_error, timestamps)` 使用唯一约束。只有 indexed_count == expected_count 且 failed_count == 0 才发布 `SourceSearchable` 并更新 Source。

迟到的旧 version 不能覆盖新 snapshot；删除使用 versioned tombstone/delete-by-query 后确认。提供按 snapshot、source、workspace 重建，alias switch 用短 Redis lock/MySQL lease 协调，但 checkpoint 才是事实。

## 7. Wiki 投影边界

Source 模块只发布 `SourceSearchable`/`SourceDeleted`。Wiki 是否启用、如何生成页面由 Knowledge 模块的 projector 决定。以 `(source_id, snapshot_version, projection_type)` checkpoint 保证重复事件不会重复创建页面。`SourceService` 和 `GeneratedSourceService` 不直接调用 `WikiIngestService`。

## 8. 性能、配额与线程池

- `sourceIoExecutor` 只负责 I/O 编排；CPU/高风险 parser 使用专用 Worker 或受限池；
- `projectionExecutor` 受 ES bulk 并发与 heap 限制；
- Redis 令牌/lease 控制 Workspace 同时上传、解析和重建数量，但 Execution/MySQL 是最终 ownership；
- MinIO/HTTP/ES 连接池分别设 connect/read/request timeout；
- 记录文件大小、解析时长、passage 数、bulk 大小与失败率，按 p95 调参。

## 9. 测试与验收

- 1GB 文件上传过程后端 heap 不随文件大小线性增长；
- 重复 complete 只生成一个 Source/Snapshot/Execution；
- PDF、DOCX、HTML、Markdown fixture 的正文与页码引用正确；
- 解析超时、损坏文件、压缩炸弹有稳定错误码；
- batch 中单条 ES 失败时 checkpoint 不完成，重试后最终 READY；
- 旧 snapshot 的迟到事件不覆盖新 snapshot；
- Source 删除后 MySQL、ES、Wiki 最终一致且可审计；
- Kafka/ES/MinIO 短暂故障可恢复，无静默 READY。

## 10. 灰度与回滚

`source.pipeline.v2` 按 Workspace 灰度。先对同一输入做影子解析/投影并比较 passage 数、正文 hash、检索召回，不产生双写业务结果。回滚时关闭 v2 新入口和 projector，保留新 Snapshot；读路径切回旧 active snapshot。索引使用 alias 回切，不删除新索引直到观察期结束。
