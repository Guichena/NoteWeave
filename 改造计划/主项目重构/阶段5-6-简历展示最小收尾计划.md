# 阶段 5-6：简历展示最小收尾计划

> 定位：这是当前剩余工作的唯一施工计划。目标是让 NoteWeave-v2 能稳定演示、能清楚说明架构和功能边界，而不是把本地项目扩展成生产发布工程。

## 1. 已确认的取舍

- `NoteWeave-v2` 是当前项目名称；QA 运行时只展示并使用最新 `qa-retrieval-v2`。
- Workspace 继续是权限、会话、资料、检索、Knowledge、AnswerRun 与引用的隔离边界；取消的只是“不同 Workspace 选择不同 QA 算法版本”的开关语义。
- 既有 Flyway 历史字段、旧 AnswerRun 读取兼容和已落地 API 不做破坏性删除；新代码不再为 baseline 新增功能、测试、指标或文档口径。
- 普通用户仍直接看到回答与引用。离线评测人工审核只用于开发验证，不进入用户流程。

## 2. 只做四件事

### 2.1 QA 固定为 V2

将新 QA AnswerRun、检索、离线导出和演示口径固定为：

```text
qa-retrieval-v2
qa-passage-v2
qa-lexical-sufficiency-v2
qa-source-diverse-budget-v2
```

`workspaceId`、Source scope、ownership/latest Snapshot 校验、ES -> MySQL fallback、EvidenceBundle 与 citation 边界继续保留。`retrieval_strategy_v2_enabled` 不再参与新回答的运行时决策；其数据库历史和旧接口不强制清除，避免无收益的 schema/API 重构。

验收只需证明：任意 Workspace 的新 QA 回答都生成上述 V2 plan/profile，并保留 Workspace 隔离与引用。

### 2.2 一条可复现的本地演示链路

使用已有的本地基础设施和受控资料，固定一条演示路径：

```text
创建 Workspace
  -> 上传资料并完成索引
  -> QA 提问
  -> 展示直接回答、EvidenceBundle 与 citation
  -> 可选演示 Note / Wiki 的既有能力
```

只补演示真正阻塞的脚本、文档或小缺陷；不为演示新增复杂前端工作台、运营后台或 Worker 内部能力。Research/Artifact 若展示，只使用现有页面/接口显示结果，不修改两个独立 worker。

### 2.3 简洁但成熟的前端演示体验

前端不追求复杂运营控制台，但必须适合展示：

- QA 对话直接展示回答、引用来源、加载/空态/错误态和 Workspace 资料范围；
- Note、Wiki、Memory、Research、Artifact 使用现有能力给出清晰入口和结果展示；
- 视觉与交互保持类似 Gemini/GPT/MiroThinker 的“结果优先”界面，不暴露开发侧 gold、评测、复杂审计或人工审核流程；
- 复用已经拆分的 feature/state owner，只做演示实际可见的布局、文案、状态和交互修正，不为代码形式继续机械拆组件。

### 2.4 简历材料与验收说明

交付一份简洁的项目说明，包含：

- 架构边界：Java/Spring Boot 主系统、MySQL/Kafka/Redis/MinIO/Elasticsearch、独立 Python worker；
- 可展示功能：资料上传解析与索引、QA/Note/Wiki、AnswerRun/SSE、EvidenceBundle/citation、Workspace 隔离；
- 真实技术点：V2 QA 统一检索策略、ES 主检索 + MySQL fallback、Source scope/ownership 防线、可复验 r6 离线评测；
- 可运行证据：核心回归、演示步骤和截图/短视频占位；
- 明确边界：不把离线小样本写成生产质量证明，不宣称未实现的 vector、RRF、rerank 或通用 AI 审核能力。

简历可使用已经实际执行并可追溯的指标，不额外虚构 production 指标：

- Backend Surefire：`106` 个 suite、`495 tests / 0 failures / 0 errors / 2 skipped`；
- r6 离线 QA：`8` 个 case（`6` 答、`2` 拒）、`5` 轮稳定 ranking signature、`0` scope violation；
- r6 指标：Recall@K `0.9306`、MRR `1.0`、NDCG@K `1.0`、citation precision `0.8889`、citation coverage `0.9306`、refusal accuracy `1.0`；
- 受控评测语料：`3` 个 Source、`16` 个 projected chunk；
- V2 的统一预算：最多 `6` 条 evidence、`8,000` 字符。

这些必须标注为“本地受控离线评测/测试结果”，不能改写为真实生产用户指标。

## 3. 保留能力与新增工作边界

以下已有能力都保留，不删除、不降级，也可以在简历或演示中展示：

- 现有 Memory 生命周期、版本、review、Control Pack 与缓存能力；
- 当前 QA/Note/Wiki 页面、Research/Artifact 结果展示、SSE 与 Workspace 隔离；
- Backend/Frontend 自动化测试、Docker Compose、本地基础设施与 r6 离线评测证据；
- Research Worker、Artifact Worker 与主项目的现有调用边界。

Memory 的后续设计、展示与重构从本计划移出，单独立项；当前只保持既有代码可编译和可运行，不因简历收尾继续修改其模型、流程或页面。

本轮只是不再把下列事项作为新的必做收尾或阶段完成阻塞：

- baseline/V2 的生产质量对比、灰度/回切观测和 production policy；
- 新增 cost、faithfulness、answer relevance 等运营型评测模块；
- 真实线上 AnswerRun 样本采集、CI 四层调度、定时 benchmark 与生产级容器 smoke；基础 Backend/Frontend 测试、构建和本地 Docker 演示继续保留；
- 继续拆分前端已有面板，或新增复杂 Memory 规则；Memory 后续统一在独立重构计划中处理；
- 为了“代码更干净”而删除 Flyway 历史、旧 AnswerRun 兼容字段或无关模块；
- Research Worker、Artifact Worker 的内部实现与前端重做。

## 4. 完成标准

剩余工作完成即满足：

1. 新建 QA AnswerRun 无论所属 Workspace，均固定使用 V2；Workspace 数据/权限/scope 隔离仍通过。
2. 一条本地资料 -> 索引 -> QA -> citation 演示链路可重复执行。
3. 前端关键页面具备清晰的加载、空态、失败和结果呈现。
4. Backend/Frontend 基础编译与核心定向测试通过；不要求补建生产监控或大规模评测。
5. 简历项目说明、架构图/截图清单和演示步骤齐全，表述与实际代码一致。

完成后阶段 5-6 按“简历展示版”收尾；任何生产化、运营指标或大规模前端重构另开需求，不隐含在本计划中。
