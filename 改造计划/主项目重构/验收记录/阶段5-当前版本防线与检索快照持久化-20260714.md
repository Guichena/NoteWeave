# 阶段 5：当前版本防线与检索快照持久化验收

- 日期：2026-07-14
- 范围：QA/Note Source Snapshot current 防线、Wiki Knowledge Version current 证明、RetrievalPlan/EvidenceBundle 持久化、Provider token budget 契约、online trace 到 shadow schema 映射
- 算法约束：未修改 QA 排序、Note recall/rank/window、Wiki 页面召回/图扩展或原回答模板算法

## 发现的缺口

1. QA ownership 只校验 Source/Snapshot/Passage 状态，没有证明 Snapshot 是该 Source 最新版本；MySQL fallback 与 Note window hydrate 同样可能读取仍保持 INDEXED 的历史 Snapshot。
2. Evidence 的 `freshAt` 为空，无法证明本轮把证据作为 current 使用的时间边界。
3. AnswerRun 只保存 plan version 与 `evidence-bundle:*` 字符串引用，没有保存完整 RetrievalPlan 或可审计的 EvidenceBundle 身份快照。
4. `ChatLlmClient` 带输出 token budget 的方法是默认实现，未来 Provider 可以编译通过但静默忽略预算。
5. online trace 与 `retrieval-shadow-v1` 缺少明确的结构化转换边界。

## 已完成实现

- `RetrievalHydrator.hydratePassageOwnership`、`hydrateNoteWindows` 和 QA MySQL fallback 增加最新已索引 Snapshot 条件：`version_no = max(indexed version_no)`；并继续要求 Source READY/INDEXED、Snapshot INDEXED、Passage PROJECTED。
- QA/Note/Wiki Evidence 写入 `freshness_status=CURRENT_AT_RETRIEVAL` 和非空 `freshAt`；该状态只表达本轮检索时验证为当前版本，不会把历史 AnswerRun 永久解释为当前仍有效。Wiki 召回继续由 `knowledge_item.latest_version_id` 锁定当前版本。
- 新增 V032：`answer_run.retrieval_plan_json` 与 `answer_run.evidence_bundle_json`。
- 新增 `evidence-bundle-snapshot-v1`：保留 bundle、证据身份、版本、排序分数、scope、freshness、选择原因与成本；不保存 title、excerpt、content 或 opaque metadata。
- `ChatLlmClient.streamChat(system,user,maximumOutputTokens,onToken)` 改为抽象方法，Provider 必须显式实现；三参数兼容方法只注入 1200 默认值。
- 新增 `RetrievalExecutionShadowExporter`，把持久化 trace/bundle 映射为 `retrieval-shadow-v1`，并对 case/evidence/source/citation ID 做 HMAC 假名化。
