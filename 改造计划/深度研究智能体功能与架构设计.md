# NoteWeave 深度研究智能体功能与架构设计文档

## 1. 功能定位

Deep Research Agent 是 NoteWeave 系统中的一个独立功能模块。用户在系统中发起一个开放式研究问题后，Deep Research Agent 自动完成问题拆解、资料搜索、目标导向阅读、动态表格填充、证据绑定、置信度判断、冲突处理和最终研究报告生成。

该功能不被设计成普通 Chat 的附属功能，也不绑定某一个具体业务页面。它作为系统中的“深度研究能力”存在，内部维护独立的 Agent 状态、研究表格、证据链和执行轨迹。最终产物可以进入 NoteWeave 的知识沉淀链路，例如 Artifact、知识卡片、Wiki、长期记忆或团队知识库。

一句话定义：

> Deep Research Agent = Table-as-Search + Goal-conditioned Reading + Cell-level Evidence Verification + Research Artifact Generation。

核心目标不是让模型直接生成一篇报告，而是让系统具备“可追踪、可验证、可沉淀”的研究能力。

---

## 2. 总体设计思路

传统 RAG 或普通搜索问答通常是：

```text
用户问题 -> 检索资料 -> 生成回答
```

Deep Research Agent 的流程是：

```text
用户研究问题
  -> 生成研究计划
  -> 构建动态研究表格
  -> Wide Search 候选发现
  -> Deep Reading 目标导向阅读
  -> Cell Extraction 字段抽取
  -> Cell Verification 字段级验证
  -> Conflict Resolution 冲突与低置信处理
  -> Report Writing 生成研究报告
  -> 流入知识沉淀
```

它把“研究”从一次性生成任务，拆成一个可观测、可恢复、可审计的多阶段 Agent 工作流。

## 2.1 Loop Engineering 设计理念

在 Deep Research Agent 中，可以进一步引入 **Loop Engineering** 的设计理念。

这里的 Loop Engineering 不是简单让 Agent 无限循环，也不是让模型反复自我反思，而是把深度研究拆成一组可控、可观测、可中断、可恢复的闭环执行单元。

传统 Prompt Engineering 更关注：

```text
如何写一个更好的 prompt，让模型一次性输出更好的结果。
```

Loop Engineering 更关注：

```text
如何设计一个稳定的循环，让 Agent 在目标、工具、状态、反馈和约束之间持续迭代，直到达到可接受的完成条件。
```

在本功能中，Loop Engineering 可以被定义为：

> 以 Research Table 为外部状态，以 Evidence / Verifier / Budget 为反馈信号，驱动 Agent 在 Search、Read、Extract、Verify、Revise 之间进行受控循环。

也就是说，Deep Research Agent 不是一次性执行：

```text
搜索 -> 总结 -> 输出
```

而是执行一个研究闭环：

```text
Plan
  -> Search
  -> Read
  -> Extract
  -> Verify
  -> Revise
  -> Stop / Continue
```

### 2.1.1 为什么需要 Loop Engineering

深度研究任务天然不是一次性任务，而是一个不断补全和修正的过程。

例如：

1. 第一次搜索可能只找到部分候选对象；
2. 某个 cell 填入后可能证据不足；
3. 不同来源之间可能冲突；
4. 某些字段需要二次搜索；
5. 报告生成前需要检查哪些结论还不可靠。

如果只依赖一次性 prompt，系统很容易出现：

```text
- 搜索不充分
- 缺字段
- 证据和结论不对齐
- 明明低置信却被写成确定结论
- 任务失败后无法恢复
```

Loop Engineering 的价值就在于：  
让 Agent 不只是“生成答案”，而是围绕一个显式目标不断观察、行动、验证和修正。

### 2.1.2 Deep Research 中的核心 Loop

Deep Research Agent 内部可以抽象出四类 loop：

| Loop | 作用 | 反馈信号 | 停止条件 |
|---|---|---|---|
| Planning Loop | 修正研究计划和表格 schema | schema 是否覆盖问题 | schema 完整且用户/系统接受 |
| Search Loop | 不断寻找候选对象和资料 | 候选数量、相关性、多样性 | 达到候选数量或搜索预算耗尽 |
| Cell Completion Loop | 针对每个 cell 搜索、阅读、抽取 | cell 是否 FILLED / VERIFIED | cell verified 或达到重试上限 |
| Verification Loop | 验证和修正低置信内容 | verifier 结果、冲突状态 | 无关键冲突或转人工确认 |

这四类 loop 共同构成 Deep Research Agent 的内部执行机制。

### 2.1.3 Loop Engineering 与 Table-as-Search 的关系

Table-as-Search 解决的是：

```text
如何把开放式搜索任务转化为表格补全任务。
```

Loop Engineering 解决的是：

```text
表格中每个 row / cell 应该如何被持续补全、验证和修正。
```

两者结合后，系统形成：

```text
Table-as-Search 提供外部状态；
Loop Engineering 提供执行节奏；
Verifier 提供反馈信号；
Budget Controller 提供停止约束。
```

### 2.1.4 Loop Engineering 与普通 Agent Loop 的区别

普通 Agent Loop 通常是：

```text
Think -> Act -> Observe -> Think -> Act
```

Deep Research 中的 Loop Engineering 更强调工程约束：

```text
Goal -> State -> Action -> Evidence -> Verification -> Revision -> Stop Condition
```

它有几个关键特征：

1. **有外部状态**：Research Table 记录所有中间结果；
2. **有反馈信号**：Verifier 判断是否支持、冲突或证据不足；
3. **有预算约束**：Profile / Budget Controller 控制成本；
4. **有停止条件**：不是无限循环，而是达到 verified、partial completed 或 retry limit；
5. **有产物沉淀**：循环结果最终生成 Artifact 或进入知识沉淀。

### 2.1.5 设计边界

需要注意，Loop Engineering 不应该设计成无约束自治系统。

本项目中的 loop 必须满足：

```text
- 每个 loop 有明确目标
- 每个 loop 有最大重试次数
- 每个 loop 有预算限制
- 每个 loop 的动作必须通过工具执行
- 每个 loop 的结果必须写入 Research Trace
- 每个 loop 都可以被中断和恢复
```

这样才能把“循环”从不稳定的模型自嗨，变成可控的工程能力。

## 4. 内部 Agent 总体架构

Deep Research Agent 内部采用分层多 Agent 架构：

```text
DeepResearchOrchestrator
  ├── Loop Engine
  ├── Plan Agent
  ├── Table State Manager
  ├── Wide Search Agent
  ├── Source Reader Agent
  ├── Cell Extraction Agent
  ├── Cell Verifier Agent
  ├── Conflict Resolver
  ├── Profile / Budget Controller
  ├── Research Trace Logger
  └── Report Writer Agent
```

### 4.1 核心协作方式

不推荐让多个 Agent 通过自然语言对话协作，例如：

```text
Agent A: 我找到了这些资料。
Agent B: 好的，我继续分析。
```

推荐使用结构化中间对象协作：

```text
ResearchPlan
CandidateEntity
SourceEvidence
CellCandidate
VerificationResult
ConflictResolution
ResearchTrace
FinalReport
```

这样每一步都有稳定输入和输出，方便持久化、恢复、审计和调试。

## 5. 功能一：DeepResearchOrchestrator

### 5.1 功能说明

DeepResearchOrchestrator 是整个 Deep Research Agent 的主控器。它不负责具体搜索和写作，而是负责协调所有 Agent，控制阶段状态，管理失败恢复，并决定什么时候进入下一步。

### 5.2 核心职责

1. 接收用户研究问题；
2. 调用 Plan Agent 生成研究计划；
3. 初始化动态研究表格；
4. 调用 Wide Search Agent 发现候选对象；
5. 调用 Source Reader Agent 读取资料；
6. 调用 Cell Extraction Agent 填充表格；
7. 调用 Cell Verifier Agent 验证字段；
8. 调用 Conflict Resolver 处理冲突和低置信；
9. 调用 Report Writer Agent 生成最终研究报告；
10. 将最终产物流入知识沉淀链路。

### 5.3 状态设计

Deep Research 的任务状态可以设计为：

| 状态 | 含义 |
|---|---|
| CREATED | 已创建研究任务 |
| PLANNING | 正在生成研究计划 |
| TABLE_READY | 研究表格已生成 |
| WIDE_SEARCHING | 正在进行候选发现 |
| READING | 正在阅读资料 |
| EXTRACTING | 正在抽取字段 |
| VERIFYING | 正在验证证据 |
| RESOLVING | 正在处理冲突和低置信字段 |
| WRITING | 正在生成报告 |
| COMPLETED | 全部完成 |
| PARTIAL_COMPLETED | 部分字段未完成，但可以生成报告 |
| FAILED | 任务失败 |
| CANCELLED | 用户取消 |

其中 `PARTIAL_COMPLETED` 是研究类任务非常重要的状态。真实研究任务不一定所有字段都能找到证据，系统应该允许部分完成，并在最终报告中明确标记“证据不足”或“需要人工确认”的内容。

### 5.4 设计亮点

DeepResearchOrchestrator 的亮点是：

> 用显式状态机管理长程研究任务，而不是依赖一次性大模型上下文。

优势：

1. **可恢复**：某个阶段失败后，可以从失败阶段继续；
2. **可观测**：用户可以看到当前在搜索、阅读、验证还是写作；
3. **可审计**：每一步都有 trace，不是黑盒生成；
4. **可扩展**：后续可以接更多工具，例如 GitHub Reader、arXiv Reader、PDF Reader。

### 5.5 借鉴来源

- 借鉴 Table-as-Search 的层级多 Agent 编排思想；
- 借鉴 Marco-Agent-DeepResearch 中围绕工具调用、runner 和 profile 的执行风格；
- 在 NoteWeave 中将其作为系统级深度研究引擎，而不是普通 Chat 的一部分。

## 6. 功能二：Plan Agent

### 6.1 功能说明

Plan Agent 负责将用户的开放式研究问题转化为结构化研究计划。

例如用户输入：

```text
帮我调研几个 NotebookLM 类搜索研究 Agent，分析它们的功能、架构、可借鉴点和不足。
```

Plan Agent 不直接回答，而是生成：

1. 研究类型；
2. 目标实体类型；
3. 表格 schema；
4. 初始搜索 query；
5. 字段证据要求；
6. 推荐执行 profile。

### 6.2 ResearchPlan 结构

```text
ResearchPlan
- research_type: 研究类型
- target_entity_type: 研究对象类型
- table_schema: 表格字段
- search_queries: 初始搜索 query
- required_columns: 必填字段
- optional_columns: 可选字段
- evidence_policy: 证据要求
- suggested_profile: 推荐执行模式
```

### 6.3 研究类型模板

系统可以内置几类常见模板：

| 模板 | 适用场景 | 典型字段 |
|---|---|---|
| PAPER_SURVEY | 论文综述 | Paper、Problem、Method、Base Model、Benchmark、Result、Code、Limitation |
| GITHUB_REPO_ANALYSIS | GitHub 项目调研 | Project、Problem、Architecture、Core Feature、Tech Stack、Reusable Design、Limitation |
| PRODUCT_COMPARISON | 产品竞品分析 | Product、Positioning、Core Feature、Search Mechanism、Pricing、Reusable Idea |
| TECH_SOLUTION_COMPARISON | 技术方案对比 | Solution、Scenario、Architecture、Pros、Cons、Risk、Implementation Cost |
| CONCEPT_RESEARCH | 概念研究 | Concept、Definition、Key Idea、Related Work、Example、Limitation |

### 6.4 例子：GitHub 项目调研 Schema

| 字段 | 含义 | 是否必须 | 证据要求 |
|---|---|---|---|
| Project | 项目名称 | 必须 | GitHub Repo / README |
| Problem | 解决的问题 | 必须 | README / Paper / Docs |
| Architecture | 架构设计 | 必须 | README / Docs / 代码结构 |
| Core Feature | 核心功能 | 必须 | README / Docs |
| Tech Stack | 技术栈 | 可选 | README / package / pom / requirements |
| Reusable Design | 可借鉴设计 | 必须 | 证据 + 迁移分析 |
| Limitation | 局限 | 可选 | 证据或分析判断 |
| Evidence | 证据 | 必须 | URL / chunk / quote |
| Confidence | 置信度 | 必须 | 基于证据质量 |

### 6.5 设计亮点

Plan Agent 的亮点是：

> 先定义研究空间，再执行搜索。

普通搜索 Agent 容易边搜边跑偏，最后变成松散总结。Plan Agent 先确定“要研究哪些对象、哪些字段、哪些证据”，后续所有 Agent 都围绕这个计划执行。

### 6.6 借鉴来源

- 借鉴 Table-as-Search 中 Main Agent 的任务拆解和表格规划；
- 借鉴 Marco-Agent-DeepResearch 的 profile 思想，在规划阶段就选择 FAST / STANDARD / HIGH_CONFIDENCE。

## 7. 功能三：Table State Manager

### 7.1 功能说明

Table State Manager 是 Deep Research Agent 的核心状态层。它将研究过程显式表示为动态表格。

核心映射：

```text
Row = 一个候选研究对象
Column = 一个研究维度
Cell = 某对象在某维度下的结论
Evidence = 支撑该 cell 的证据
Status = 当前 cell 的可信状态
```

例如调研“Deep Research Agent 项目”时：

| Project | Problem | Architecture | Reusable Design | Evidence | Confidence | Status |
|---|---|---|---|---|---|---|
| Table-as-Search | 复杂信息搜索 | 表格中心多 Agent | 动态表格状态 | README / Paper | 0.86 | VERIFIED |
| Marco-Agent-DeepResearch | 深度研究 Agent | Search + Visit + Verifier | goal-conditioned visit | README / Code | 0.82 | VERIFIED |

### 7.2 Cell 状态

每个 cell 都维护独立状态：

| 状态 | 含义 |
|---|---|
| EMPTY | 尚未处理 |
| SEARCHING | 正在搜索证据 |
| FILLED | 已填入候选值，但未验证 |
| VERIFIED | 证据验证通过 |
| LOW_CONFIDENCE | 证据不足或不够直接 |
| CONFLICT | 多来源存在冲突 |
| FAILED | 多次尝试后无法填充 |
| NEED_HUMAN_CHECK | 需要人工确认 |

### 7.3 Cell 内部信息

一个 cell 不只是文本，而是一个结构化研究单元：

```text
Cell
- value: 字段结论
- status: 当前状态
- confidence: 置信度
- evidence_list: 证据列表
- source_count: 支持来源数量
- verifier_note: 验证说明
- update_history: 更新历史
```

### 7.4 为什么用表格作为 Agent 状态

深度研究任务最常见的问题是：

1. 搜了很多资料，但不知道哪些已经处理；
2. 某些对象信息完整，某些对象缺字段；
3. 最后报告看起来完整，但无法知道哪些结论有证据；
4. 模型上下文过长后容易遗忘前面的计划。

表格状态可以解决这些问题：

```text
每个对象是否已处理，看 row；
每个维度是否完整，看 cell；
每个结论是否可信，看 evidence + status；
每个任务是否可继续，看 table state。
```

### 7.5 设计亮点

Table State Manager 是最核心的亮点：

> 将 LLM Agent 的隐式研究过程外显为动态表格，实现长程研究的状态管理、证据追踪和局部恢复。

### 7.6 借鉴来源

- 主要借鉴 Table-as-Search 的“表格即搜索过程”思想；
- 在 NoteWeave 中将其扩展为 cell 级 evidence、confidence 和 verification 状态。

## 8. 功能四：Wide Search Agent

### 8.1 功能说明

Wide Search Agent 负责广泛候选发现。它的目标是“找全”，不是“读深”。

例如用户要研究 NotebookLM 类产品和开源项目，Wide Search Agent 负责找到：

```text
NotebookLM
Perplexity Spaces
Elicit
Scite
Genspark
Table-as-Search
Marco-DeepResearch
Open Deep Research 类项目
```

这些候选对象会被写入 Research Table 的 row。

### 8.2 输入

Wide Search Agent 接收：

```text
- 用户原始研究问题
- Plan Agent 生成的 search queries
- 目标实体类型
- 表格 schema
- 搜索范围限制
- 最大候选数量
```

### 8.3 输出

Wide Search Agent 输出 CandidateEntity：

```text
CandidateEntity
- entity_name
- entity_type
- source_url
- source_title
- snippet
- relevance_score
- reason
```

### 8.4 搜索策略

Wide Search Agent 应采用多 query 搜索：

```text
Query 1: NotebookLM alternative AI research assistant
Query 2: deep research agent github table search
Query 3: AI research assistant citation evidence
Query 4: Table-as-Search Marco DeepResearch agent
```

然后进行：

1. URL 去重；
2. 标题近似去重；
3. domain 去重；
4. 实体归并；
5. relevance rerank；
6. Top-K 写入表格 row。

### 8.5 候选筛选规则

候选对象进入表格前需要判断：

| 判断维度 | 说明 |
|---|---|
| 相关性 | 是否与研究问题直接相关 |
| 来源可信度 | 是否来自官网、GitHub、论文、文档或可靠报道 |
| 信息密度 | 是否有足够内容支持后续分析 |
| 多样性 | 是否避免同质化结果 |
| 可读性 | 是否能被系统读取和抽取 |

### 8.6 设计亮点

Wide Search Agent 的关键设计原则是：

```text
Wide Search 优先 recall；
Deep Reading 优先 precision。
```

它只负责“找可能相关的对象”，避免模型过早下结论。

### 8.7 借鉴来源

- 借鉴 Table-as-Search 的 Tabular Search Agent：负责候选实体发现；
- 借鉴 Marco-Agent-DeepResearch 的 Search Tool：多 query 搜索、结果格式化、失败重试。

## 9. 功能五：Source Reader Agent

### 9.1 功能说明

Source Reader Agent 负责读取网页、GitHub README、PDF、文档、已有知识库 Source 或搜索结果页面。

它不是普通摘要器，而是执行 goal-conditioned reading。

普通读取：

```text
总结这个网页。
```

目标导向读取：

```text
从这个网页中提取当前 row 的 Architecture 字段证据。
```

### 9.2 Goal-conditioned Reading

Source Reader Agent 的读取目标由 row 和 column 共同决定。

示例：

```text
当前 row：Marco-DeepResearch
当前 column：Verifier Design
读取目标：查找该项目是否包含 verifier、answer verification、多候选选择或 test-time scaling 相关设计。
```

### 9.3 输出结构

```text
ReadingResult
- found: true / false
- relevant_content: 相关内容
- quote: 可作为证据的原文片段
- source_url: 来源 URL
- source_title: 来源标题
- evidence_type: 来源类型
- suggested_cell_value: 推荐填入 cell 的值
- confidence: 读取置信度
```

### 9.4 资料类型适配

| 资料类型 | 阅读策略 |
|---|---|
| 普通网页 | 提取正文，按 goal 找相关段落 |
| GitHub README | 优先读项目定位、架构、使用方式、功能列表 |
| GitHub 代码结构 | 读目录和关键文件名，辅助判断架构 |
| PDF / 论文 | 按章节、标题、摘要、实验部分抽取 |
| 已上传文档 | 使用已有 chunk / Source 内容 |
| 知识库资料 | 通过检索结果定位相关 chunk |

### 9.5 设计亮点

Goal-conditioned Reading 的亮点是：

> 每次阅读都有明确目标，只抽取和当前 row / column 相关的信息。

这能减少无关信息污染，提升 evidence 和 cell value 的对齐程度。

### 9.6 借鉴来源

- 主要借鉴 Marco-Agent-DeepResearch 的 Visit Tool；
- Marco 的 Visit Tool 接收 URL 和 goal，并根据 goal 抽取信息；
- 在 NoteWeave 中扩展为对 URL、Source、Chunk、README、PDF 都统一使用 goal-conditioned reading。

## 10. 功能六：Cell Extraction Agent

### 10.1 功能说明

Cell Extraction Agent 负责将 Source Reader Agent 读取到的证据转化为表格 cell 的候选值。

它处理的是：

```text
Evidence -> Cell Candidate
```

而不是：

```text
Question -> Final Answer
```

### 10.2 输入

```text
- 用户研究问题
- 当前 row
- 当前 column
- Source Reader 返回的 evidence
- 当前 cell 已有值
- 字段要求
```

### 10.3 输出

```text
CellCandidate
- column_key
- value
- evidence_id
- confidence
- extraction_reason
```

### 10.4 字段抽取策略

不同字段适合不同抽取方式：

| 字段类型 | 抽取方式 |
|---|---|
| 项目名称 / 论文名称 | 精确抽取 |
| 方法 / 架构 | 摘要式抽取 |
| benchmark / 数据集 | 列表抽取 |
| 训练资源 / 参数量 | 数值抽取 |
| 代码地址 | URL 抽取 |
| 局限 | 证据 + 分析判断 |
| 可借鉴点 | 证据 + 面向系统的迁移分析 |

### 10.5 候选值合并

如果多个 source 对同一个 cell 给出候选值，需要合并：

```text
相同结论 -> 合并 evidence，提高 confidence
互补结论 -> 合并成更完整 value
冲突结论 -> 交给 Conflict Resolver
证据不足 -> 标记 LOW_CONFIDENCE
```

### 10.6 设计亮点

Cell Extraction Agent 将信息抽取细化到字段级别。

普通 RAG：

```text
检索若干 chunk -> 生成一段答案
```

Deep Research：

```text
读取资料 -> 针对某个字段生成 cell candidate -> 绑定 evidence -> 进入 verifier
```

### 10.7 借鉴来源

- 借鉴 Table-as-Search 的 Deep Search Agent：对具体实体做属性填充；
- 借鉴 Marco-Agent-DeepResearch 的结构化输出思想，要求抽取结果以 JSON / schema 形式返回，而不是自由文本。

## 11. 功能七：Cell Verifier Agent

### 11.1 功能说明

Cell Verifier Agent 是 Deep Research 的关键可信度模块。它负责判断 cell value 是否真的被 evidence 支持。

验证粒度是 cell 级，而不是整段报告级。

### 11.2 输入

```text
- 用户研究问题
- row 实体
- column 字段
- cell value
- evidence quote
- source metadata
```

### 11.3 输出

```text
VerificationResult
- support_status: SUPPORTS / PARTIALLY_SUPPORTS / CONTRADICTS / NOT_ENOUGH_INFO
- confidence
- verifier_note
- suggested_revision
```

### 11.4 验证规则

| Verifier 结果 | 处理方式 |
|---|---|
| SUPPORTS | cell 状态改为 VERIFIED |
| PARTIALLY_SUPPORTS | 保留 value，但标记 LOW_CONFIDENCE |
| CONTRADICTS | 标记 CONFLICT |
| NOT_ENOUGH_INFO | 标记 LOW_CONFIDENCE |
| 证据缺失 | 回退给 Deep Reading 继续搜索 |

### 11.5 多证据验证

对于关键字段，Verifier 不只看单个 evidence，而是看证据集合：

```text
- 多个 evidence 是否一致
- 是否来自不同来源
- 是否直接支持 cell value
- 是否存在时间冲突
- 是否存在范围冲突
```

### 11.6 例子

```text
Cell value:
该项目使用 verifier-guided test-time scaling。

Evidence A:
README 明确提到 verifier-guided test-time scaling。

Evidence B:
配置文件中存在 verify_answers / multi-rollout 相关字段。

Verifier Result:
SUPPORTS, confidence = 0.88。
```

### 11.7 设计亮点

Cell Verifier Agent 的亮点是：

> 从“答案级引用”升级为“字段级证据验证”。

普通 RAG 通常只能告诉用户答案引用了哪些文档；Deep Research 可以告诉用户表格中每一个字段是否被证据支持。

### 11.8 借鉴来源

- 借鉴 Marco-Agent-DeepResearch 的 verification-centric 设计；
- 借鉴其 verifier-guided test-time scaling、多候选答案和验证选择思想；
- 在 NoteWeave 中改造成 cell-level verifier。

---

## 12. 功能八：Conflict Resolver

### 12.1 功能说明

Conflict Resolver 负责处理冲突、低置信和证据不足的 cell。

深度研究不是所有问题都有明确答案。系统不应该强行生成确定结论，而应该保留不确定性。

### 12.2 冲突类型

| 冲突类型 | 示例 |
|---|---|
| 值冲突 | 一个来源说支持，另一个来源说不支持 |
| 时间冲突 | 旧文档和新文档描述不同 |
| 版本冲突 | 开源版不支持，商业版支持 |
| 范围冲突 | 某功能只在特定场景支持 |
| 证据不足 | 没有直接证据 |
| 推理过度 | evidence 只能暗示，不能直接支持结论 |

### 12.3 处理策略

Conflict Resolver 可以采用三种策略：

1. **保守修正**  
   只保留 evidence 明确支持的内容。

2. **并列展示**  
   保留多个来源说法，并说明差异。

3. **人工确认标记**  
   将该 cell 标记为 NEED_HUMAN_CHECK，放入最终报告的“待确认问题”。

### 12.4 输出结构

```text
ConflictResolution
- final_value
- conflict_status
- explanation
- evidence_used
- evidence_ignored
- need_human_check
```

### 12.5 设计亮点

Conflict Resolver 体现的是研究系统的“保守性”和“可信性”。

普通生成式系统倾向于给出确定答案；Deep Research Agent 则允许输出：

```text
当前证据不足
不同来源存在冲突
需要人工确认
```

这更符合真实研究流程。

### 12.6 借鉴来源

- 借鉴 Marco-Agent-DeepResearch 的 verifier 思想；
- 借鉴 Table-as-Search 的表格状态机制；
- 在 NoteWeave 中扩展出 LOW_CONFIDENCE、CONFLICT、NEED_HUMAN_CHECK 等研究状态。

## 13. 功能九：Profile / Budget Controller

### 13.1 功能说明

Profile / Budget Controller 控制 Deep Research 的搜索深度、验证强度、成本和耗时。

系统提供三种执行模式：

```text
FAST
STANDARD
HIGH_CONFIDENCE
```

### 13.2 FAST 模式

适合快速了解。

特点：

```text
- 搜索 query 数少
- 候选对象少
- 每个 cell 最多一次抽取
- 不做复杂 verifier
- 低成本，快速返回
```

### 13.3 STANDARD 模式

适合常规研究。

特点：

```text
- 多 query 搜索
- Top-K 候选对象
- cell 级 evidence
- 基础 verifier
- 输出低置信字段
```

### 13.4 HIGH_CONFIDENCE 模式

适合生成正式报告、技术调研、论文综述。

特点：

```text
- 更大搜索范围
- 每个关键 cell 尽量收集两个以上 evidence
- 低置信 cell 触发二次搜索
- 冲突检测
- verifier 必须执行
- 最终报告包含可信度说明
```

### 13.5 Budget 控制维度

| 维度 | 说明 |
|---|---|
| max_search_queries | 最大搜索 query 数 |
| max_candidates | 最大候选对象数 |
| max_sources_per_entity | 每个对象最多读取多少来源 |
| max_retry_per_cell | 每个 cell 最大重试次数 |
| max_llm_calls | 最大模型调用次数 |
| max_execution_time | 最大执行时间 |
| enable_verifier | 是否启用 verifier |
| enable_conflict_resolver | 是否启用冲突处理 |
| min_evidence_count | 关键 cell 最少证据数量 |

### 13.6 设计亮点

Profile / Budget Controller 体现成本感知 Agent 设计：

> 不让 Agent 无限搜索，而是根据模式控制搜索深度、验证强度和模型调用成本。

### 13.7 借鉴来源

- 借鉴 Marco-Agent-DeepResearch 的 efficiency / accuracy profile；
- 在 NoteWeave 中改造成 FAST / STANDARD / HIGH_CONFIDENCE 三种面向研究任务的模式。

## 14. 功能十：Research Trace

### 14.1 功能说明

Research Trace 记录 Deep Research 的外部行为和中间决策。它不是暴露模型隐式推理，而是记录可审计的执行过程。

### 14.2 Trace 内容

Research Trace 应记录：

```text
- 搜索了哪些 query
- 每个 query 返回了哪些候选
- 访问了哪些 source
- 哪些 source 被采用
- 哪些 evidence 支持了哪些 cell
- 哪些 cell 被 verifier 标记为低置信
- 哪些字段触发了二次搜索
- 最终报告每个 section 来源于哪些 table row / cell
```

### 14.3 Trace 类型

| 类型 | 内容 |
|---|---|
| SEARCH_QUERY | 搜索 query 和返回结果 |
| CANDIDATE_SELECTED | 候选对象被选入表格 |
| SOURCE_VISIT | 访问 URL / Source |
| EVIDENCE_EXTRACT | 抽取到 evidence |
| CELL_UPDATE | 更新某个 cell |
| VERIFY_RESULT | verifier 结果 |
| CONFLICT_DETECTED | 冲突检测 |
| RETRY_TRIGGERED | 触发重试 |
| REPORT_SECTION | 报告段落生成依据 |

### 14.4 设计亮点

Research Trace 让系统具备可解释性和工程可观测性。

用户看到的不只是最终报告，还可以看到：

```text
这个结论是从哪里来的？
为什么这个字段低置信？
为什么某个来源被采用？
哪些字段没有找到直接证据？
```

### 14.5 借鉴来源

- 借鉴 NoteWeave 已有 RetrievalTrace、AuditLog、LLM 日志等可观测思想；
- 借鉴 Marco-Agent-DeepResearch 的工具调用日志和多轮执行记录；
- 在 Deep Research 中将 trace 扩展到搜索、阅读、抽取、验证、写作全过程。

## 15. 功能十二：Loop Engine

### 15.1 功能说明

Loop Engine 是 Deep Research Agent 中用于管理闭环执行的核心模块。

它不直接搜索、不直接阅读、不直接写报告，而是负责回答一个问题：

> 当前研究任务是否需要继续循环？如果需要，下一步应该循环哪个阶段？

Loop Engine 管理的是 Deep Research 中的循环节奏。

它根据 Research Table 的状态、Verifier 的反馈、Budget 的剩余量和用户目标，决定下一步动作：

```text
继续搜索？
继续阅读？
重新抽取？
重新验证？
进入冲突处理？
停止并生成报告？
```

### 15.2 Loop Engine 的输入

Loop Engine 接收以下信息：

```text
- ResearchPlan
- ResearchTable 当前状态
- Cell 状态分布
- Verifier 反馈
- Conflict Resolver 反馈
- Research Trace
- Budget 剩余量
- 当前执行 profile
```

例如：

```text
当前状态：
- 10 个 row
- 80 个 cell
- 50 个 VERIFIED
- 18 个 FILLED
- 8 个 LOW_CONFIDENCE
- 4 个 CONFLICT
- 剩余 LLM 调用预算 30 次
- 当前模式 HIGH_CONFIDENCE
```

Loop Engine 需要判断：

```text
是否继续处理 LOW_CONFIDENCE？
是否对 CONFLICT 进行二次搜索？
是否直接进入报告生成？
是否将部分 cell 标记为 NEED_HUMAN_CHECK？
```

### 15.3 Loop Engine 的输出

Loop Engine 输出下一步动作：

```text
LoopDecision
- next_action: SEARCH / READ / EXTRACT / VERIFY / RESOLVE / WRITE / STOP
- target: row / cell / column / source
- reason: 为什么选择这个动作
- priority: 优先级
- budget_to_use: 分配预算
- stop_reason: 如果停止，说明原因
```

### 15.4 核心闭环一：Search Loop

Search Loop 负责候选发现和资料补充。

```text
Search Loop
  -> 生成 query
  -> 搜索候选 source
  -> 去重和筛选
  -> 写入 candidate / source
  -> 判断是否继续搜索
```

#### 反馈信号

```text
- 候选数量是否足够
- 候选多样性是否足够
- 搜索结果相关性是否下降
- 是否还有关键字段缺少 source
- 搜索预算是否耗尽
```

#### 停止条件

```text
- 达到 max_candidates
- 连续几次搜索没有新增高质量候选
- 关键对象已经覆盖
- 搜索预算耗尽
```

#### 设计亮点

Search Loop 不是盲目多搜，而是根据表格缺口搜索。

例如：

```text
如果大多数 row 的 Code 字段缺失，
Loop Engine 可以生成更针对性的 query：
"{project name} GitHub code repository"
```

这比一次性搜索更适合研究任务。

### 15.5 核心闭环二：Cell Completion Loop

Cell Completion Loop 是 Deep Research 的核心循环。

它围绕每个 cell 执行：

```text
Cell Completion Loop
  -> 判断 cell 是否为空或低置信
  -> 找相关 source
  -> goal-conditioned reading
  -> evidence extraction
  -> cell update
  -> cell verification
  -> 判断是否继续
```

#### 反馈信号

```text
- cell 是否 FILLED
- cell 是否 VERIFIED
- evidence 是否直接支持
- confidence 是否达到阈值
- 是否存在冲突
```

#### 停止条件

```text
- cell 状态变为 VERIFIED
- cell 达到最大重试次数
- 没有更多 source 可读
- budget 不足
- 标记 NEED_HUMAN_CHECK
```

#### 设计亮点

Cell Completion Loop 使系统可以做到字段级修正。

普通 Agent 生成报告后，无法知道哪句话有问题；  
Deep Research 可以定位到具体 cell：

```text
Marco-DeepResearch / Verifier Design 这个 cell 证据不足，需要二次阅读。
```

### 15.6 核心闭环三：Verification Loop

Verification Loop 负责对已填充 cell 进行验证和修正。

```text
Verification Loop
  -> 读取 cell value
  -> 读取 evidence
  -> verifier 判断支持关系
  -> 根据结果更新状态
  -> 必要时触发重新搜索或修正
```

#### 反馈信号

```text
SUPPORTS
PARTIALLY_SUPPORTS
CONTRADICTS
NOT_ENOUGH_INFO
```

#### 对应动作

| Verifier 结果 | Loop Engine 动作 |
|---|---|
| SUPPORTS | 停止该 cell 的循环，标记 VERIFIED |
| PARTIALLY_SUPPORTS | 触发一次补充搜索或保守修正 |
| CONTRADICTS | 进入 Conflict Resolver |
| NOT_ENOUGH_INFO | 回到 Search / Read 阶段 |
| 多次失败 | 标记 NEED_HUMAN_CHECK |

#### 设计亮点

Verifier 不只是最后检查，而是作为 loop 的反馈信号。

这让系统具备“发现问题 -> 重新搜索 -> 修正结果”的能力。

### 15.7 核心闭环四：Report Refinement Loop

Report Writer Agent 生成初稿后，Loop Engine 可以进行一次报告级检查。

```text
Report Refinement Loop
  -> 生成报告草稿
  -> 检查是否引用未验证 cell
  -> 检查是否遗漏关键冲突
  -> 检查低置信内容是否标注
  -> 修正报告
  -> 输出最终 Artifact
```

#### 检查规则

```text
- 报告中的关键结论必须来自 VERIFIED cell
- LOW_CONFIDENCE 内容必须标注
- CONFLICT 内容必须单独列出
- NEED_HUMAN_CHECK 不得写成确定结论
- 报告不能新增表格中没有的事实
```

#### 设计亮点

这个 loop 可以防止最终报告“看起来很完整，但偷偷编了没有证据的内容”。

### 15.8 Loop Engine 与 Budget Controller 的关系

Loop Engine 决定“要不要继续做”。  
Budget Controller 决定“最多还能做多少”。

两者关系：

```text
Loop Engine:
当前 cell 低置信，应该继续搜索。

Budget Controller:
当前模式是 STANDARD，该 cell 已重试 2 次，达到上限，不允许继续。
```

最终决策：

```text
标记 LOW_CONFIDENCE，并在报告中说明证据不足。
```

### 15.9 Loop Engine 与 Research Trace 的关系

每一次 loop 决策都应该写入 Research Trace：

```text
LoopDecision Trace
- 当前状态
- 触发原因
- 选择动作
- 使用预算
- 结果
```

例如：

```text
Cell "Marco-Agent / Verifier Design" 被标记为 NOT_ENOUGH_INFO，
Loop Engine 触发二次搜索，
query = "Marco-Agent-DeepResearch verifier guided test time scaling"。
```

这样面试展示时可以讲：

> 我没有只展示最终结果，而是记录 Agent 为什么继续搜索、为什么停止、为什么标记低置信。

### 15.10 Loop Engineering 的简历价值

加入 Loop Engine 后，这个功能的亮点可以从：

```text
Table-as-Search 深度研究 Agent
```

升级为：

```text
基于 Loop Engineering 的可验证 Deep Research Agent
```

可以这样表达：

> 引入 Loop Engineering 设计，将深度研究拆解为 Search、Read、Extract、Verify、Revise 多个受控闭环，以 Research Table 作为外部状态、Verifier 作为反馈信号、Budget Controller 作为停止约束，实现长程研究任务的自动补全、证据验证和局部修正。

这句话会给面试官留下几个明显追问点：

```text
什么是 Loop Engineering？
你的 loop 怎么停止？
怎么避免 Agent 无限循环？
Verifier 如何作为反馈信号？
Budget 如何控制成本？
Research Table 为什么适合作为 loop state？
```

### 15.11 设计边界

Loop Engine 必须避免几个问题：

| 风险 | 解决方式 |
|---|---|
| 无限循环 | 每个 loop 设置 max retry 和 budget |
| 成本失控 | Profile / Budget Controller 控制 LLM 调用 |
| 反复搜索低质量来源 | 记录已访问 source，避免重复 |
| 模型自我确认偏差 | 依赖 evidence 和 verifier，而不是自我感觉 |
| 报告过度生成 | Report Loop 检查所有关键结论是否来自 verified cell |

最终，Loop Engineering 在本系统中的作用是：

> 把 Agent 从一次性生成器，升级为一个带状态、反馈、约束和停止条件的研究执行引擎。


## 16. 功能十三：Report Writer Agent

### 15.1 功能说明

Report Writer Agent 负责根据 Research Table、verified cells、low-confidence cells、conflict cells 和 evidence 生成最终研究报告。

它不重新发明结论，而是基于已经填充和验证的表格进行写作。

### 15.2 输入

```text
- 用户原始研究问题
- Research Table
- VERIFIED cells
- LOW_CONFIDENCE cells
- CONFLICT cells
- Evidence list
- Research Trace 摘要
```

### 15.3 输出结构

最终报告可以包含：

```text
1. 研究问题
2. 总体结论
3. 结构化对比表
4. 重点对象分析
5. 可借鉴点总结
6. 低置信 / 冲突信息
7. 待人工确认问题
8. 参考证据
9. 后续建议
```

### 15.4 写作约束

Report Writer Agent 必须遵守：

```text
- 不使用没有 evidence 的结论
- 低置信内容必须标注
- 冲突内容必须单独列出
- 表格中没有的信息不得强行补全
- 最终建议必须和 evidence 对齐
```

### 15.5 设计亮点

Report Writer Agent 的亮点是：

> 基于 verified table 写报告，而不是基于自由上下文直接生成报告。

普通 Agent：

```text
搜索 -> 总结
```

Deep Research Agent：

```text
搜索 -> 表格化 -> 证据验证 -> 基于验证表格生成报告
```

这条链路更加可信，也更适合作为 NotebookLM-like 搜索研究功能的核心卖点。

### 15.6 借鉴来源

- 借鉴 Table-as-Search 的结构化输出思想；
- 借鉴 Marco-Agent-DeepResearch 的 verifier 约束；
- 在 NoteWeave 中将输出报告流入 Artifact 和知识沉淀体系。

## 17. 工具层设计

### 16.1 工具列表

Deep Research Agent 内部可以抽象出以下工具：

| 工具 | 作用 |
|---|---|
| WebSearchTool | 根据 query 搜索网页 |
| WebVisitTool | 读取网页正文 |
| SourceReadTool | 读取系统已有资料、文档 chunk 或知识库内容 |
| GitHubReadTool | 读取 GitHub README、目录和关键文件 |
| PaperReadTool | 读取论文 PDF、摘要、实验章节 |
| EvidenceStoreTool | 保存 evidence |
| TableUpdateTool | 更新 row / cell 状态 |
| VerificationTool | 验证 cell 是否被 evidence 支持 |
| ArtifactTool | 生成最终研究报告 |

### 16.2 工具调用原则

工具调用必须结构化，避免 Agent 只输出自然语言。

推荐原则：

```text
- 每次工具调用都记录 trace
- 每次工具调用都有明确输入和输出
- 读取工具必须带 goal
- 写入工具必须指定 row / column / evidence
- verifier 必须返回 support_status 和 confidence
```

### 16.3 设计亮点

工具层的亮点是：

> 所有外部行为都通过工具调用显式记录，使研究过程可追踪、可重试、可审计。

### 16.4 借鉴来源

- 借鉴 Marco-Agent-DeepResearch 的 Search / Visit 工具设计；
- 借鉴 Table-as-Search 的搜索、网页访问和表格管理工具生态。

## 18. Agent 间数据流

### 17.1 数据对象流转

```text
UserQuery
  -> ResearchPlan
  -> ResearchTable
  -> CandidateEntity[]
  -> SourceEvidence[]
  -> CellCandidate[]
  -> VerificationResult[]
  -> ConflictResolution[]
  -> FinalReport
```

### 17.2 每个对象的作用

| 对象 | 作用 |
|---|---|
| ResearchPlan | 定义研究任务边界 |
| ResearchTable | 承载研究状态 |
| CandidateEntity | 记录候选研究对象 |
| SourceEvidence | 记录来源证据 |
| CellCandidate | 记录字段候选值 |
| VerificationResult | 记录字段验证结果 |
| ConflictResolution | 记录冲突处理结果 |
| FinalReport | 最终报告产物 |

### 17.3 设计亮点

这种数据流设计使 Deep Research Agent 不只是 prompt chaining，而是一个有明确中间状态和可审计对象的 Agent 系统。

面试时可以这样解释：

> 我不是让多个 prompt 串起来生成报告，而是把研究过程拆成多个可持久化的中间对象，每个 Agent 只处理自己负责的输入输出。

## 19. 与 NoteWeave 系统的结合方式

Deep Research Agent 与 NoteWeave 主系统保持轻耦合。

### 18.1 入口结合

Deep Research 作为系统中的一个功能入口：

```text
用户输入研究问题 -> 启动 Deep Research
```

不强制绑定某个具体业务页面，也不作为 Chat 的内部逻辑。

### 18.2 资料结合

Deep Research 可以读取：

```text
- 用户上传文档
- 系统已有知识库
- 外部网页
- GitHub 项目
- 论文 PDF
- 历史 Artifact 或知识卡片
```

### 18.3 证据结合

Deep Research 内部维护 cell 级 evidence。

它和普通 RAG 的区别是：

```text
普通 RAG：答案级 citation
Deep Research：cell 级 evidence
```

### 18.4 产物结合

最终产物可以流入 NoteWeave 的知识沉淀链路：

```text
FinalReport -> Artifact
Verified Insight -> Knowledge Card
Stable Conclusion -> Wiki
Important Preference / Method -> Memory
Research Entity -> Knowledge Graph
```

第一版只需要保证最终报告和证据可以沉淀，不必强行打通所有模块。

## 20. 核心亮点总结

Deep Research Agent 的亮点可以总结为六个：

### 20.1 Table-as-State

用动态研究表格作为 Agent 外部状态，避免长程研究中的上下文遗忘和状态混乱。

### 20.2 Wide-to-Deep Search

先广泛发现候选对象，再对每个对象进行字段级深度阅读。

### 20.3 Goal-conditioned Reading

每次阅读都有明确字段目标，只抽取和当前 row / column 相关的信息。

### 20.4 Cell-level Evidence Verification

不是只给最终答案加引用，而是给每个表格单元格绑定 evidence、confidence 和 verification status。

### 19.5 Profile-based Budget Control

支持 FAST / STANDARD / HIGH_CONFIDENCE 三种模式，在速度、成本和可信度之间做权衡。

## 21. 简历表达建议

推荐写法：

> 设计 Deep Research Agent 功能：基于 Table-as-Search 将开放式研究问题转化为动态表格补全任务，引入 Loop Engineering、Wide Search、Goal-conditioned Reading、Cell-level Evidence Verification 和 Profile-based Budget Control，实现字段级证据回溯、低置信修正与研究报告沉淀。

这句话包含多个面试钩子：

1. Table-as-Search 如何落地？
2. 为什么用表格作为 Agent 外部状态？
3. Wide Search 和 Deep Reading 如何分工？
4. Loop Engineering 如何避免无限循环？
5. Goal-conditioned Reading 如何减少噪声？
6. Cell-level Evidence Verification 如何判断可信度？
7. Profile-based Budget Control 如何控制成本？
8. 研究报告如何流入知识沉淀？

## 22. 最终边界

Deep Research Agent 应聚焦解决：

```text
开放式研究任务如何被结构化、搜索、验证和沉淀。
```

它不是：

```text
- 普通聊天机器人
- 简单网页搜索
- 单次 RAG 问答
- 自动 Wiki 生成器
- 复杂知识图谱系统
```

它是系统中的一个独立深度研究能力：

```text
输入：研究问题
过程：规划、搜索、阅读、抽取、验证、报告
输出：研究表格 + 研究报告 + 证据链
沉淀：Artifact / Card / Wiki / Memory / Knowledge Base
```

最终核心卖点：

> Deep Research Agent 将复杂研究任务从“不可控的一次性生成过程”转化为“带状态、反馈、验证和停止条件的循环式研究工作流”，让系统具备 NotebookLM-like 的搜索研究能力，同时提供更强的字段级证据验证、低置信修正和知识沉淀能力。
