# NoteWeave 项目主述题

> 本文件为 2026-06-01 重构版，依据当前代码、测试和 Flyway 迁移整理。不要再按旧阶段计划或旧题库口径背。

## 1. 15 秒版
NoteWeave 是面向团队知识协作和个人研究沉淀的 AI 知识工作台，核心是把资料进入、可信问答、成果生成和长期知识沉淀连成闭环。

## 2. 1 分钟版
NoteWeave 是一个 AI 知识工作台，核心不是简单聊天，而是把团队知识协作和个人研究沉淀做成闭环。团队侧从知识库上传、解析、索引开始，进入 Hybrid RAG 问答、Citation 追踪和 Wiki 发布；个人侧从 ResearchProject、Source 导入开始，编译成 ArticleCard、ConceptCard，再生成 Artifact，最后用户确认后沉淀成 SynthesisCard。底层共用 Space 权限、Task/Outbox/Kafka 异步任务、MinIO、Elasticsearch、Redis runtime、LLM 日志、RAG Eval 和 Admin/Ops。这样能回答“资料从哪里来、证据怎么追、结果怎么沉淀、坏答案怎么查”。

## 3. 2 到 3 分钟版
我会先把 NoteWeave 讲成一个双空间 AI 知识工作台。团队侧从知识库上传开始，经过分片上传、解析、chunk、索引，再进入 Hybrid RAG 问答、Citation 追踪和 Wiki 发布；个人侧从 ResearchProject 和 Source 导入开始，编译成 ArticleCard、ConceptCard，再通过 Methodology 生成 Artifact，最后用户确认后沉淀成 SynthesisCard。技术上我主打三条线：第一是 Task/Outbox/Kafka/Worker 的异步骨架，解决上传、解析、索引、生成、评测这类长任务的一致性和可恢复；第二是 evidence-first 的 RAG 链路，保证回答有检索、证据和引用；第三是 WebSocket runtime、Memory、Admin/Eval 这些可运营能力，让它不是一次性 Demo，而是可排查、可演进的系统。

## 4. 最能体现 ownership 的三条故事
### 故事一：统一异步骨架
我会把这条链路讲成 NoteWeave 的工程地基。系统里很多动作都不是瞬时完成的，比如文档解析入索引、Source 编译、Artifact 生成、RAG Eval 和资源清理。我的设计是业务接口不直接把任务塞给某个临时线程，而是创建统一 Task，并在同一个事务里写 task_outbox。事务提交后由 outbox 调度器投递 Kafka，消费者拿到消息后只信 taskId，再回查数据库判断状态和幂等。Worker 执行时记录 TaskAttempt 和 TaskEvent，失败可以重试，运行中可以通过 cancel_requested 在安全点停止。这个方案牺牲了一点链路长度，但换来的是最终一致、可恢复和可观测。

### 故事二：Evidence-first RAG
RAG 这块我不会只说“接了向量库”。NoteWeave 的目标是 evidence-first。一次团队问答先经过 Space 权限和 session scope 判断，只在可见知识库内检索。检索层有 BM25、向量和 Wiki recall，并用 Weighted RRF 融合排序，避免单一召回方式漏掉关键词或语义相关内容。之后 EvidencePostProcessor 会对 chunk 做去重、相邻合并、每文档限流和上下文截断，避免 prompt 被重复证据撑爆。TeamRagPromptBuilder 再把证据以受控格式注入，明确文档内容不是系统指令，无证据时返回兜底。最后 CitationService 把回答和证据关系落到 citation/message_citation 等关系里，并保留 page、offset、quoteHash、snapshotObjectKey 这类字段，方便后续审计和二次权限校验。

### 故事三：Artifact 到 Synthesis 的受控沉淀
Artifact 我会强调它不是 chat message 的一个字段，而是独立生命周期。一次生成通过 Studio 或 PersonalGeneration 创建 ARTIFACT_GENERATE 任务，结果保存为 Artifact 和 ArtifactVersion，来源用 ArtifactSource，引用用 ArtifactCitation。MethodologyCard 的价值是把 workflow、outputStructure、qualityChecklist 作为可管理的输出方法论注入 prompt，而不是在代码里写死一堆模板。最关键的边界是 Artifact 默认不进入 Wiki，因为生成内容可能只是阶段性草稿。个人侧要沉淀时，PersonalArtifactDistillationService 先生成 proposal，用户确认后再绑定最新 artifactVersionId，创建 SynthesisCard、artifact_card_relation 和 synthesis_card_citation。Skill 在当前项目里更像可控生成步骤和执行日志，不要夸成完全自主 Agent 平台。

## 5. 面试官常问
- 你先介绍一下 NoteWeave 这个项目。
- 这个项目和普通 RAG 问答系统最大的区别是什么？
- 你在项目里最有 ownership 的模块是什么？
- 如果只能讲一个技术亮点，你会讲哪条链路？
- 这个项目当前哪些已经实现，哪些不能说满？

## 6. 不要踩的坑
- 不要说已经有真实线上规模指标。
- 不要把 MCP、Bibtex、完全自主 Agent 说成主链路已完成能力。
- 不要只讲 AI，必须讲权限、任务、证据、运维。

## 7. 面试官质疑“这不就是套 RAG”时怎么答
我会先承认它表面上看起来像 RAG，再把问题拉回工程闭环：NoteWeave 不是单点问答，而是围绕知识从资料进入系统、被检索引用、生成成果、再沉淀为长期知识这一整条链路设计的。团队侧我做的是权限约束下的 upload -> parse -> chunk -> index -> hybrid retrieval -> evidence -> citation -> wiki；个人侧我做的是 source -> compile -> card -> artifact -> confirm -> synthesis。真正难的不是“接模型”，而是检索质量、证据可信、权限隔离、状态恢复和可观测排障。

如果面试官继续追问，我会顺着说：
- 为什么不用 grep / LIKE 直接查。
- 为什么 BM25 和向量要混合。
- 为什么 Citation 不能只拼在回答文本里。
- 为什么 Artifact 不能自动进入 Wiki。
- 如果坏答案出现，我先看哪一层，再看哪一层。

## 8. 2 分钟后还能继续展开的点
1. Task/Outbox/Kafka/Worker 解决的不是“异步”本身，而是失败可恢复和状态可追踪。
2. EvidencePostProcessor 解决的不是“截断文本”，而是证据去重、相邻合并和上下文预算控制。
3. Wiki 解决的不是“再存一份内容”，而是把人工确认后的长期知识重新接回检索链路。
4. Memory 解决的不是“记住一切”，而是按边界、按价值、按风险写回。
