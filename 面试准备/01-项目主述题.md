# NoteWeave 项目主述题

## 0. 本篇定位

这篇用于准备所有“请介绍一下项目”“项目亮点是什么”“你负责什么”“这是不是 demo”“有没有闭环”一类开场题。目标是让你从产品问题自然讲到系统设计，而不是只说“我做了一个 RAG 项目”。

## 1. 本主题面试官想考什么

面试官问项目主述时，真正想验证四件事：

1. 你是否能把业务问题讲清楚，而不是堆技术栈。
2. 你是否理解系统边界，知道团队知识、个人研究、Artifact、Wiki、Memory 各自负责什么。
3. 你是否真的参与过工程落地，能先说清链路、状态和取舍，被追问时再补实现兜底锚点、测试和验收点。
4. 你是否能诚实区分已验收能力和未来扩展，不编造生产规模。

## 2. 高频问题清单

基础问题：

- 请用 1 分钟介绍一下 NoteWeave。
- 这个项目解决什么问题，核心价值是什么？
- 你在项目里负责哪些模块？

进阶问题：

- 为什么它不是普通 RAG demo？
- 项目最大的亮点是什么？
- 团队空间和个人空间为什么要拆开？

深挖追问：

- 你最有 ownership 的模块是哪一个？为什么？
- 如果只能讲一个技术故事，你会讲哪个？
- 项目现阶段完成到什么程度？如何验收？

压力追问：

- 这个项目有没有上线？没有生产指标怎么证明价值？
- 里面哪些能力容易被你讲过头？
- 如果面试官质疑只是包装，你怎么回应？

## 3. 问答与讲解

### Q1：你先用 1 分钟介绍一下 NoteWeave。

#### 面试官为什么问

这是热身题，但面试官会用它判断你有没有系统感。如果你只讲“上传文档后问答”，后面很容易被当成普通 RAG demo。

#### 回答思路

先一句话定义产品，再讲双空间，再讲两条主链路，最后落到工程底座。

#### 结合 NoteWeave 怎么答

NoteWeave 是一个 AI 知识工作台。团队侧负责知识库、RAG 问答、Citation 和 Wiki 沉淀；个人侧负责 Source 导入、卡片编译、Artifact 生成、Synthesis 沉淀和长期记忆。底层通过权限、Task/Outbox/Kafka、存储、检索、LLM 调用和可观测性复用一套工程底座。

#### 技术原理 / 链路设计讲解

这个回答的关键不是介绍功能多，而是讲出“知识进入系统、被检索引用、生成成果、再沉淀为长期知识”的闭环。双空间是业务边界，Task 是可靠执行边界，Citation 是可信边界，Artifact/Wiki/Synthesis 是知识生命周期边界。

#### 实现兜底锚点

- `com.noteweave.space`
- `com.noteweave.task`
- `com.noteweave.team.rag`
- `com.noteweave.chat.runtime`
- `com.noteweave.personal.generation`
- `com.noteweave.admin`
- `Phase15AdminOpsIntegrationTest`

#### 可直接复述的面试回答

NoteWeave 是一个面向团队知识协作和个人研究沉淀的 AI 知识工作台。它不是单纯的聊天机器人，而是把 `TEAM` 和 `PERSONAL` 两类空间放在同一套权限、任务、检索和证据底座上。团队侧主要做知识库上传、解析、索引、Hybrid RAG 问答、Citation 溯源和 Wiki 发布；个人侧主要做 Source 导入、ArticleCard/ConceptCard 编译、Methodology 驱动的 Artifact 生成，以及用户确认后的 SynthesisCard 沉淀。工程上我重点关注的是统一异步任务、权限隔离、证据链、WebSocket runtime、长期记忆、Eval 和 Admin/Ops，让它从“能问答”变成一个可追踪、可验收、可维护的 AI 知识系统。

#### 常见追问

- 你说的“可维护”具体体现在哪些模块？
- 和普通知识库问答最大的差异是什么？
- 哪条链路最能证明你真的做过？

#### 常见坑

- 不要只说“用了大模型、ES、Kafka、Redis”。
- 不要说成已经有真实线上 QPS 或 P99。
- 不要把 MCP、Bibtex、完整开放 Agent 放进 1 分钟主介绍。

### Q2：如果展开到 3 分钟，你会怎么讲？

#### 面试官为什么问

面试官想看你能不能把项目从功能介绍讲成架构说明。

#### 回答思路

按五层展开：产品边界、通用底座、团队主链路、个人主链路、运维与验收。

#### 结合 NoteWeave 怎么答

产品边界是 `TEAM / PERSONAL`；通用底座是 Auth、Permission、Task、Storage、Search、LLM、Observability；团队链路是 upload -> parse -> chunk -> index -> retrieve -> answer -> citation -> wiki；个人链路是 Source -> Card -> Artifact -> Synthesis；运维层是 PromptVersion、LLMCallLog、RetrievalTrace、RagEvalRun、SystemHealth、Cleanup 和 AuditLog。

#### 技术原理 / 链路设计讲解

这套组织方式能让面试官听到三类能力：产品抽象、系统设计、工程治理。AI 项目最容易被质疑是 demo，破局点就是讲清楚失败、权限、重试、证据、评测和运维这些非 happy path。

#### 实现兜底锚点

- `TaskService` / `TaskOutboxService`
- `DocumentProcessingService`
- `HybridRetriever` / `EvidencePostProcessor` / `TeamRagPromptBuilder`
- `ChatRuntimeService` / `ChatRuntimeStateStore`
- `WikiCompilerService` / `PersonalGenerationService` / `PersonalArtifactDistillationService`
- `Phase14ObservabilityEvaluationIntegrationTest`
- `Phase15AdminOpsIntegrationTest`

#### 可直接复述的面试回答

如果展开讲，我会先讲产品边界。NoteWeave 的核心不是“把文档塞给模型”，而是把团队知识协作和个人研究沉淀拆成两类空间。团队空间关注共享知识库、权限下的检索问答、引用溯源和 Wiki 沉淀；个人空间关注资料导入、卡片化组织、结构化生成、Synthesis 沉淀和长期记忆。第二层是技术底座，所有长任务都统一走 `Task + Attempt + Event + Outbox + Kafka + Worker`，比如上传解析、索引、Source 编译、Artifact 生成、Eval 和 Cleanup，这样状态、重试、取消和审计是一套模型。第三层是团队主链路，文档分片上传后异步解析、切 chunk、写 ES，问答时走 BM25、向量召回、Wiki recall 和 Weighted RRF，再通过 EvidencePostProcessor 选证据，最后保存 Citation 和 RetrievalTrace。第四层是个人主链路，Source 导入后编译成 ArticleCard、ConceptCard，再结合 MethodologyCard 生成 Artifact，用户确认后才沉淀为 SynthesisCard。最后是可观测和后台，项目补了 PromptVersion、LLM 日志、RAG Eval、健康检查、清理和审计，所以现阶段已经形成了一个本地可验收的 AI 知识工作台闭环。

#### 常见追问

- 如果只让你讲一个最复杂接口，你讲哪个？
- 这套系统怎么从单体演进到多服务？
- 现阶段验收如何证明不是只在文档里？

#### 常见坑

- 不要把“阶段已验收”说成“已有真实生产流量验证”。
- 不要说所有链路都是完全智能规划，当前 Skill 更像受控生成流水线。

### Q3：这个项目的核心价值是什么？

#### 面试官为什么问

面试官想确认你不是为了堆技术而做项目，而是知道系统在解决什么问题。

#### 回答思路

用“资料进入系统、被检索引用、生成成果、沉淀知识、可观测治理”这条闭环回答。

#### 结合 NoteWeave 怎么答

团队侧解决共享知识“难进入、难检索、难追溯、难沉淀”；个人侧解决研究资料“难结构化、难复用、难产出、难长期积累”。

#### 技术原理 / 链路设计讲解

价值来自分层：原始资料不是知识，生成结果也不天然是知识。NoteWeave 用 Source/Document 承接输入，用 Chunk/Card 承接结构化，用 Citation 承接可信证据，用 Artifact 承接生成产物，用 Wiki/Synthesis 承接长期沉淀。

#### 实现兜底锚点

- `Document` / `DocumentChunk`
- `Citation` / `message_citation`
- `ArticleCard` / `ConceptCard` / `SynthesisCard`
- `Artifact` / `ArtifactVersion`

#### 可直接复述的面试回答

我觉得 NoteWeave 的核心价值是把“资料很多、知识很散、回答不稳定、生成结果不沉淀”这几个问题收口成一个闭环。团队侧让资料可以可靠进入知识库，被权限约束地检索，被 Citation 回溯，最后沉淀成 Wiki；个人侧让文件、文本和 URL 这类 Source 先结构化成卡片，再生成 Artifact，最后由用户确认沉淀成 Synthesis。它的重点不是让模型临时回答一次，而是让知识从输入、检索、生成到长期沉淀都有状态、有证据、有权限和有排障路径。

#### 常见追问

- 生成结果为什么不能直接进 Wiki？
- 个人 Source 和团队 Document 为什么不共用同一套模型？
- Citation 对业务价值有什么帮助？

#### 常见坑

- 不要把“功能多”当成核心价值。
- 不要忽略权限和证据，否则项目会听起来像普通问答工具。

### Q4：你在这个项目里的亮点是什么？

#### 面试官为什么问

面试官想找到后续深挖入口。你应该主动给出一个自己能扛追问的模块。

#### 回答思路

最好讲两类亮点：一条系统底座，一条 AI 主链路。

#### 结合 NoteWeave 怎么答

系统底座讲统一异步任务，AI 主链路讲 evidence-first RAG 或 Artifact/Synthesis 分层。

#### 技术原理 / 链路设计讲解

统一异步任务体现工程可靠性；evidence-first RAG 体现 AI 系统可信性；Artifact/Synthesis 体现知识生命周期治理。

#### 实现兜底锚点

- `TaskService`、`TaskExecutionCoordinator`、`TaskKafkaConsumer`
- `HybridRetriever`、`EvidencePostProcessor`、`CitationService`
- `ArtifactService`、`PersonalArtifactDistillationService`

#### 可直接复述的面试回答

我会讲两个亮点。第一个是统一异步任务底座，因为 NoteWeave 里上传解析、索引、Source 编译、Artifact 生成、Eval 和清理都不是短请求，如果每个模块自己写异步会很散，所以我把它们收口到 `Task + Attempt + Event + Outbox + Kafka + Worker`，统一状态、重试、取消和审计。第二个是 evidence-first RAG，团队问答不是简单把 top-k chunk 拼给模型，而是权限约束下的 BM25、向量、Wiki 多路召回，再用 Weighted RRF 和 EvidencePostProcessor 做证据治理，最后把 Citation 和 RetrievalTrace 落下来。这样项目的亮点不是“用了大模型”，而是把 AI 回答做得可追踪、可排障、可沉淀。

#### 常见追问

- 统一异步底座为什么不用 MQ 自带重试就够了？
- EvidencePostProcessor 具体处理了哪些问题？
- 如果 Citation 不准，你怎么排查？

#### 常见坑

- 不要一次讲太多亮点，面试官会抓不到主线。
- 亮点必须先能讲清系统问题、设计取舍和失败处理，被追问时再落到表名、实现锚点和测试。

### Q5：如果被质疑是 demo，怎么回应？

#### 面试官为什么问

AI 项目很容易被质疑只是调 API。这个问题考的是你能不能用工程闭环证明项目成熟度。

#### 回答思路

先承认不是商业生产系统，再说明现阶段已验收的工程闭环。

#### 结合 NoteWeave 怎么答

可以讲本地验收完整，但不编造生产流量；可以讲工程骨架成熟，但不说已经商业化上线。

#### 技术原理 / 链路设计讲解

demo 通常只覆盖 happy path；NoteWeave 覆盖了认证、权限、任务、重试、取消、上传、解析、索引、检索、引用、记忆、评测、后台、审计、前端验收等系统性能力。

#### 实现兜底锚点

- `src/test/java/com/noteweave/**/Phase*IntegrationTest.java`
- `tools/playwright-smoke`
- `docker-compose.yml`
- `src/main/resources/static`

#### 可直接复述的面试回答

我会先承认它不是一个已经有真实生产流量的商业系统，但它也不是只接了模型的 demo。因为现阶段已经验收的是一整套工程闭环：有登录和空间权限，有统一异步任务和 Outbox，有分片上传、解析、索引，有团队 Hybrid RAG、Citation 和 Trace，有 WebSocket runtime 和长期记忆，有个人 Source/Card/Artifact/Synthesis，有 Prompt 版本、LLM 日志、RAG Eval、健康检查、清理和审计，也有前端工作台可以本地走通。我的回答会很明确：我不编造 QPS、P99 或线上 token 消耗，但我能说明系统用哪些测试、Trace、Eval 和验收路径证明每条主链路是能跑、能查、能定位问题的。

#### 常见追问

- 如果没有线上指标，怎么衡量效果？
- 本地验收和真实生产差距在哪里？
- 如果要上线，第一批要补哪些能力？

#### 常见坑

- 不要硬说“已经生产验证”。
- 不要用“功能很多”替代“关键工程闭环已经验收”。
