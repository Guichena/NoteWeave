# NoteWeave 模块深问题

## A. 权限与空间模型

Q: 为什么要分 `TEAM` 和 `PERSONAL` 两种空间？

A:
因为这两类场景的权限模型和知识生命周期完全不同。团队空间强调多人协作、共享检索和团队沉淀；个人空间强调 owner-only、个人研究过程和个人知识组织。如果不拆开，后面在 Artifact、Wiki、Memory、Citation 这些地方很容易串权限，也很难定义什么内容应该长期沉淀、什么内容只是个人过程资料。

Q: 为什么 `systemRole` 和 `space role` 要分开？

A:
因为它们解决的是两层不同的问题。`space role` 解决的是业务空间内谁能看、谁能改、谁能上传；`systemRole` 解决的是谁能看全局日志、健康、任务重试、清理这些后台能力。如果混成一套，就很容易出现“团队 OWNER 其实不该看全局后台，但因为权限模型混乱看到了”的问题。

## B. Task / Outbox / Kafka

Q: 为什么你们要统一成 `Task + TaskOutbox + Kafka + Worker`？

A:
因为这个项目的长任务很多，而且类型很杂：上传后解析、索引、个人 Source 编译、Artifact 生成、Wiki 入索引、评测、清理任务都属于失败率不低、需要重试和审计的后台流程。如果每个模块自己写一套，就会出现状态机不统一、日志不统一、取消重试行为不统一的问题。所以我统一成一套 Task 模型，把幂等、状态流转、attempt、event、retry、cancel_requested 都收口。

Q: 为什么不直接在事务里发 Kafka？

A:
因为那样业务写库和消息发送很容易出现不一致。最典型的问题是数据库成功了但消息没发出去，或者消息发出去了但事务回滚了。Outbox 的意义就是先把“待发送事实”作为数据库记录写下来，等事务成功后再补偿投递 Kafka，这样最终一致性更可控，失败也更好排查。

## C. 上传、解析、索引

Q: 团队文档上传链路怎么走？

A:
先是 init upload，拿到 uploadId 和上传配置；然后按 chunk 分片上传，同时用 Redis bitmap 跟踪上传进度；merge 时校验 chunk 完整性，计算内容哈希，合并到对象存储，再绑定 `FileObject` 和 `Document`；之后创建 `DOCUMENT_PROCESS` 任务异步做解析、切 chunk、写 ES 索引、必要时补 embedding，最终把文档状态切成可检索。

Q: 为什么 `FileObject` 复用限制在同一个 `spaceId`？

A:
因为“内容相同”不等于“权限可以共享”。如果跨空间共用对象引用，很容易把一个空间的对象权限含义带到另一个空间。把复用限定在同一 space，可以保留去重收益，同时不破坏权限边界。

Q: 为什么文档删除先 soft delete？

A:
因为文档不是单点资源，它后面还有 chunk、ES 索引、citation、任务状态和对象引用关系。直接物理删除很容易把链路打断，排查和补偿都很困难。先 soft delete 可以先把业务可见性拿掉，再通过后续清理流程做真正回收。

## D. Hybrid RAG

Q: 你说的 Hybrid RAG 具体是什么？

A:
在这个项目里，Hybrid RAG 不是一句口号，而是一条真实检索链路。团队问答时会先按权限和 scope 做约束，再走 BM25、向量召回和 Wiki recall 这些多路召回，之后用 Weighted RRF 做融合排序，再经过 `EvidencePostProcessor` 做相邻 chunk 合并、低分过滤、单文档限流，最后把证据交给 PromptBuilder 生成 grounded answer。

Q: 为什么不用纯向量检索？

A:
因为企业知识场景里有很多专有名词、关键词约束、过滤条件和权限限制。纯向量语义相似度在召回模糊问题时很有用，但在精确术语和强过滤场景里不稳定。Elasticsearch 把全文、过滤、排序、向量能力放在一起，更适合这种“语义 + 关键词 + 权限”的混合场景。

Q: 向量召回失败怎么办？

A:
这个项目里是可以降级的。如果向量检索异常，系统仍然可以回到 BM25 主链路，不会因为某一路失败导致整个问答完全不可用。这种降级能力是面向真实系统设计的，不是只为理想路径服务。

## E. Citation 与 Trace

Q: 为什么 citation 不放在 message JSON 里？

A:
因为 citation 不是一个纯展示字段，而是一个需要权限校验、回溯 source、关联 retrieval trace、支持后续 Wiki/Artifact 复用的正式证据对象。放 JSON 会让查询、审计和权限二次校验都很难做，所以我把它落成正式关系表。

Q: retrieval trace 的价值是什么？

A:
它回答的是“系统为什么会拿到这些证据”。如果一次回答不好，我可以沿着 trace 看 query、召回结果、融合结果、哪些证据被选中；而 citation 更偏向“最终回答引用了什么证据”。两者一起才能把问题定位清楚。

## F. WebSocket Runtime 与长期记忆

Q: 为什么还要做 WebSocket runtime？

A:
因为 HTTP 非流式问答只能解决“问完给你一个答案”，但无法处理长回答的流式体验、中断、恢复、partial content 保留这些事情。WebSocket runtime 解决的是会话执行态，不是简单换一种传输协议。

Q: 为什么要区分 `DRAFT` 和 `FORMAL`？

A:
因为用户很多时候是在探索，不希望这些临时讨论直接污染长期记忆和正式沉淀。`DRAFT` 更偏运行时态和短期上下文，`FORMAL` 才进入长期 Memory、正式消息和后续可追踪链路。

Q: 为什么长期记忆要分层？

A:
因为会话历史、空间上下文和用户偏好不是一个粒度。最近消息是短期连续性问题，session summary 是当前会话的压缩表示，space memory 是这个空间里长期有效的上下文，user memory 是更稳定的用户偏好。分层之后既能保持连贯，也能控制 token 成本和噪声。

## G. 个人研究、卡片、方法论

Q: 个人研究链路怎么走？

A:
先从文件、文本、URL 导入 Source，导入后保证可读文本存在；然后通过 WikiCompiler 把 Source 编译成 ArticleCard、ConceptCard、alias、relation，并做 evidence backtrace；之后再结合 MethodologyCard 和精选 evidence 生成 Artifact；如果用户确认结果有长期价值，再把 Artifact 沉淀成 SynthesisCard。

Q: 为什么还要做 MethodologyCard？

A:
因为同样是“生成一个结果”，研究报告、学习指南、对比分析、工作准备这些输出结构完全不同。如果把结构完全写死在 prompt 里，很难演进，也难解释“为什么这次输出长这样”。MethodologyCard 把 workflow、output structure、quality checklist 显式建模出来，更利于复用和后续扩展。

Q: 为什么个人 Artifact 不直接写进个人 Wiki？

A:
因为生成结果不一定稳定，也不一定值得长期沉淀。Artifact 更像工作过程中的版本化产物，Wiki 更像长期稳定知识。先分离，再经过用户确认沉淀成 SynthesisCard，可以减少知识污染。

## H. Admin / Ops / Eval

Q: 为什么这类项目还要做后台和评测？

A:
因为 AI 系统最大的工程难点之一就是“出了问题你怎么知道为什么”。PromptVersion、LLMCallLog、RetrievalTrace、AnswerFeedback、RagEvalRun、CleanupJob、SystemHealth、AuditLog 这些能力，都是为了把系统从“看起来能用”变成“出了问题能定位、能复现、能修”。

Q: Eval 为什么不能复用正式聊天会话？

A:
因为评测本质上是离线验证，不应该污染真实用户聊天历史和长期记忆。它可以复用部分检索和生成能力，但运行上下文必须隔离，这样才能保证评测结果和线上真实会话都干净。
