# NoteWeave 模块深问题

## 0. 本篇定位

这篇是根目录里最核心的技术主文档，专门负责模块级深挖和最高频技术题标准答。

现在的整理原则是：

- 技术模块的主答案尽量收敛在这篇里。
- 同一个知识点不再在根目录多个文件里反复写一遍。
- 系统总串讲放在 `09-重点系统功能QA深入版.md`。
- 单条链路的专题深挖放在 `重点系统功能链路/*/README.md`。
- 原本单独存在的高频技术题精简稿，已经并回这篇，不再单独维护。

如果只能重点准备一篇技术文档，优先准备这篇。

## 1. 本主题面试官想考什么

模块深挖考的不是你能不能背出组件名，而是：

- 能不能说清模块为什么存在。
- 能不能把请求、任务、状态和存储链路讲完整。
- 能不能解释权限、一致性、失败恢复和边界。
- 能不能给出真实源码、表结构、测试或验收锚点。
- 能不能把扩展方向和当前事实分开。

## 3. 问答与讲解

### Q1：为什么要分 `TEAM` 和 `PERSONAL` 两种空间？

#### 面试官为什么问

这是领域建模和权限边界题。面试官想看你是不是先把知识场景拆对了，而不是先堆技术组件。

#### 回答思路

先讲团队协作和个人研究的权限模型、生命周期、沉淀方式不同，再讲底层能力复用、上层模型分治。

#### 结合 NoteWeave 怎么答

`TEAM` 承接团队知识库、团队 Chat、团队 Wiki、团队 Artifact 和成员协作；`PERSONAL` 承接 ResearchProject、Source、Card、Artifact、Synthesis 和用户记忆。

底层不是两套系统，认证、权限、任务、存储、检索、LLM 和可观测能力都是复用的。

#### 源码与验收锚点

- `com.noteweave.space`
- `com.noteweave.permission`
- `Space.type = TEAM | PERSONAL`
- `SpaceMember.role = OWNER | EDITOR | VIEWER`

#### 可直接复述的面试回答

我把 `TEAM` 和 `PERSONAL` 做成一级空间边界，不是为了产品上多一个分类，而是因为这两类场景在权限模型、知识生命周期和沉淀目标上天然不同。团队空间解决多人共享知识，强调成员权限、统一检索、Citation 溯源和 Wiki 沉淀；个人空间解决个人研究过程，强调 owner-only、Source 编译、卡片化组织、Artifact 生成和 Synthesis 沉淀。如果不在最外层拆开，后面在 Citation、Memory、Artifact、Wiki 这些地方很容易串权限，也很难定义什么内容应该进入长期知识。底层我没有做成两套系统，认证、任务、存储、检索、LLM 和可观测能力都是复用的，只是在上层资源模型和沉淀方式上分治。

#### 常见追问

- 为什么不先共用一套内容模型？
- 个人研究成果如何共享给团队？
- `systemRole` 和 `space role` 为什么要分开？

#### 常见坑

- 不要把 PERSONAL 讲成普通私有文件夹。
- 不要忽略 Citation 和 Memory 的跨边界风险。

### Q2：为什么统一成 `Task + Outbox + Kafka + Worker`？

#### 面试官为什么问

这是可靠性、一致性和系统设计题，通常会继续追问事务边界、重复消费、重试和取消。

#### 回答思路

先讲长任务很多，再讲统一 Task 状态机，最后讲 Outbox 解决业务事务和消息投递的最终一致。

#### 结合 NoteWeave 怎么答

文档解析、索引、Source 编译、Artifact 生成、Wiki 入索引、RAG Eval、Cleanup 都复用同一套任务模型。

#### 源码与验收锚点

- `TaskService`
- `TaskOutboxService`
- `TaskKafkaPublisher`
- `TaskKafkaConsumer`
- `TaskExecutionCoordinator`
- `TaskServiceIntegrationTest`

#### 可直接复述的面试回答

NoteWeave 里的长任务很多，像文档解析、切 chunk、建索引、Source 编译、Artifact 生成、Eval 和清理都不是同步 HTTP 里应该直接做完的事情。这些任务有共同特点：耗时长、依赖外部组件、失败概率不低、需要重试、需要审计，甚至需要取消。如果每个模块自己写异步逻辑，状态、幂等、日志和失败处理会很散。所以我统一成 `Task + Attempt + Event + Outbox + Kafka + Worker`。`Task` 记录主状态，`Attempt` 记录每次执行，`Event` 记录状态流转，`Outbox` 把业务提交和消息投递解耦，Kafka 和 Worker 负责分发和执行。Worker 消费时回查 DB 状态，配合幂等键处理重复消费。它不是追求强一致，而是把最终一致、补偿投递和消费侧幂等这套路径做清楚。

#### 常见追问

- 为什么不直接在事务里发 Kafka？
- Outbox 会不会重复投递？
- `cancel_requested` 为什么不是强杀？

#### 常见坑

- 不要说 Outbox 保证绝不重复。
- 不要说 Redis 是主任务队列。

### Q3：团队文档上传到可检索的完整链路是什么？

#### 面试官为什么问

这是端到端链路题，容易追到对象存储、状态流转、索引版本和权限边界。

#### 回答思路

按上传、合并、任务投递、解析、切块、索引、版本切换讲，不要只讲“上传成功”。

#### 结合 NoteWeave 怎么答

团队文档先进入 KnowledgeBase，再通过 `DOCUMENT_PROCESS` Worker 变成可检索证据。

#### 源码与验收锚点

- `DocumentUploadService`
- `DocumentProcessingService`
- `ChunkService`
- `VectorIndexerService`
- `Phase2UploadFlowIntegrationTest`
- `Phase3DocumentProcessingIntegrationTest`

#### 可直接复述的面试回答

团队文档上传到可检索，我会拆成六步。第一步 init upload，服务端创建上传会话并返回 uploadId。第二步 chunk upload，客户端分片上传，后端记录分片进度，支持断点续传和取消。第三步 merge，校验分片完整性，把文件合并到对象存储，计算内容 hash，并创建 `FileObject` 和 `Document`。第四步创建 `DOCUMENT_PROCESS` 任务，通过 Outbox 和 Kafka 交给 Worker。第五步 Worker 做解析、保存 parsed text、切 `DocumentChunk`、写 Elasticsearch 索引和必要的 embedding。第六步是 active index version 切换，只有新版本完整可用后才进入可检索状态。这个设计的重点是上传和处理解耦、对象复用不越权、索引重建失败不影响旧版本查询。

#### 常见追问

- 为什么 merge 后不直接同步解析？
- 为什么要保存 parsed text？
- 为什么 soft delete 更稳？

#### 常见坑

- 不要说 hash 相同就跨空间共用权限。
- 不要说重建索引时直接覆盖旧索引。

### Q4：团队侧 `Hybrid RAG` 怎么做，为什么不是简单“几路召回拼一下”？

#### 面试官为什么问

这是 AI 主链路深挖，考的是 RAG 工程化能力。

#### 回答思路

权限和 scope 先行，多路召回后用 RRF 融合，再做证据治理和可追踪落库。

#### 结合 NoteWeave 怎么答

团队问答走 BM25、向量召回、Wiki recall、Weighted RRF、EvidencePostProcessor、PromptBuilder、Citation 和 RetrievalTrace。

#### 源码与验收锚点

- `HybridRetriever`
- `EvidencePostProcessor`
- `TeamRagPromptBuilder`
- `TeamChatService`
- `CitationService`
- `Phase4TeamRagIntegrationTest`
- `Phase9HybridRetrievalIntegrationTest`

#### 可直接复述的面试回答

NoteWeave 的 Hybrid RAG 不是把几路 top-k 简单拼接。用户提问后，系统先做权限和 session scope 约束，确保检索范围正确；然后走 BM25、向量召回和 Wiki recall。BM25 适合术语、编号、关键词和精确匹配，向量召回适合语义近似，Wiki recall 补充人工沉淀的稳定知识。多路结果通过 Weighted RRF 融合，因为不同通道的分数不一定同尺度，直接加权分数不稳。融合后再进入 `EvidencePostProcessor`，处理相邻 chunk 合并、低分过滤、去重和同文档限流。最后 PromptBuilder 只把治理后的 evidence 给模型，回答完成后保存 Citation、RetrievalTrace 和 LLMCallLog。它真正解决的是权限、召回、证据质量、可解释和排障这几个问题同时成立。

#### 常见追问

- 为什么不用纯向量库？
- 向量召回失败怎么降级？
- RRF 和 reranker 区别是什么？

#### 常见坑

- 不要把 Hybrid RAG 讲成算法名词堆叠。
- 不要说 Citation 高就必然正确。

### Q5：为什么 `Citation` 不直接塞进 message JSON？

#### 面试官为什么问

这是证据建模、权限和可观测题。

#### 回答思路

Citation 是正式证据对象，不是展示字段。

#### 结合 NoteWeave 怎么答

Message、Artifact、Card、Wiki、Synthesis 都会复用证据关系，返回 Citation 前要二次权限校验。

#### 源码与验收锚点

- `CitationService`
- `message_citation`
- `artifact_citation`
- `synthesis_card_citation`
- `Phase4TeamRagIntegrationTest`

#### 可直接复述的面试回答

我没有把 Citation 放进 message JSON，是因为在 NoteWeave 里它不是前端展示字段，而是正式证据对象。用户点击引用时要重新校验权限；后台排查坏回答时要从回答追到 source、chunk、snapshot 和 retrieval trace；后续 Artifact、Wiki、Synthesis 也要带着证据链继续流转。如果只是 JSON，查询、权限、版本、统计和跨模块复用都会很困难。所以我把 Citation 落成关系模型，保存 sourceType、sourceId、chunkId、offset、quoteHash、snapshotObjectKey 等字段。这样建模更复杂，但换来的是证据链可追踪、可审计、可复用。

#### 常见追问

- Citation 指向无权限资源怎么办？
- RetrievalTrace 和 Citation 分别怎么排障？

#### 常见坑

- 不要说 Citation 只是引用角标。
- 不要把 Citation 等同于答案准确率。

### Q6：为什么要做 WebSocket Runtime，runtime state 为什么放 Redis？

#### 面试官为什么问

这是实时交互和状态管理题。

#### 回答思路

HTTP 解决结果查询，WebSocket Runtime 解决执行态；Redis 存短生命周期高频状态，MySQL 存正式数据。

#### 结合 NoteWeave 怎么答

Runtime 覆盖 ws-ticket、`chat.delta`、stop、resume、partial content、DRAFT/FORMAL 和事件 buffer。

#### 源码与验收锚点

- `ChatRuntimeService`
- `ChatRuntimeStateStore`
- `ActiveExecutionRegistry`
- `Phase5WorkspaceChatRuntimeIntegrationTest`

#### 可直接复述的面试回答

HTTP 非流式问答能解决“问完给答案”，但不能很好处理长回答的流式输出、中断、断线重连和 partial content 恢复。NoteWeave 的 WebSocket Runtime 负责会话执行态，比如一次性 ticket、`chat.delta`、stop、resume、ack 和 event replay。Redis 用来保存这些短生命周期、高频更新的 runtime state，包括执行状态、事件缓冲、partial content 和停止信号；正式消息、Citation、Artifact 和长期 Memory 仍然落 MySQL。这里要强调，Redis 不是主异步任务队列，主后台任务还是 Task、Outbox 和 Kafka。Redis 只是承接实时会话运行态，让用户体验和正式数据边界分开。

#### 常见追问

- 为什么不用 SSE？
- Redis 挂了如何降级？
- DRAFT 为什么不写长期 Memory？

#### 常见坑

- 不要把运行态说成长期数据。
- 不要把 Redis 扩大成主任务系统。

### Q7：个人研究为什么做成 `Source -> Card -> Artifact -> Synthesis`？

#### 面试官为什么问

这是知识加工和长期沉淀题。

#### 回答思路

原始输入、结构化知识、生成产物、长期沉淀四层职责不同。

#### 结合 NoteWeave 怎么答

Source 导入后由 Wiki Compiler 编译卡片，再用 Methodology 生成 Artifact，最后用户确认沉淀 SynthesisCard。

#### 源码与验收锚点

- `SourceImportService`
- `WikiCompilerService`
- `EvidenceBacktraceService`
- `PersonalGenerationService`
- `PersonalArtifactDistillationService`

#### 可直接复述的面试回答

个人研究链路分层，是因为原始资料、结构化知识、生成产物和长期沉淀不是同一种东西。`Source` 承接文件、文本和 URL，导入完成必须有可读文本；`Card` 把资料编译成 ArticleCard、ConceptCard、ConceptRelation，并通过 evidence backtrace 保留来源；`Artifact` 是版本化工作产物，比如报告、学习指南和对比分析；`Synthesis` 是用户确认后沉淀的长期知识。这样做能让 LLM 帮用户加工资料，但不会把一次生成结果自动污染个人知识库。它也给后续 query-aware retrieval、notebook notes 和 source discovery 留了清晰扩展位。

#### 常见追问

- Evidence backtrace 为什么不能省？
- 为什么不直接改 ConceptCard？
- URL 导入怎么防 SSRF？

#### 常见坑

- 不要把它说成完整开放 Agent。
- 不要说 Artifact 自动进入长期知识。

### Q8：为什么 `Artifact` 和 `Wiki / Synthesis` 要分离？`MethodologyCard` 又解决什么问题？

#### 面试官为什么问

这是生成产物治理题。

#### 回答思路

Artifact 是工作产物，Wiki 和 Synthesis 是确认后的长期知识；MethodologyCard 把生成方法显式建模。

#### 结合 NoteWeave 怎么答

团队侧 Artifact 可人工发布为 Wiki；个人侧 Artifact 经 proposal 和 confirm 后沉淀为 SynthesisCard。MethodologyCard 有预置、匹配和管理能力。

#### 源码与验收锚点

- `ArtifactService`
- `MethodologyCardService`
- `MethodologyMatcher`
- `PersonalArtifactDistillationService`
- `Phase13MethodologyCardIntegrationTest`

#### 可直接复述的面试回答

Artifact 和 Wiki 必须分离，因为生成结果不等于长期可信知识。Artifact 更像用户工作过程中的版本化产物，可能是报告、学习指南、对比分析或草稿；Wiki 和 Synthesis 更像确认后的长期知识。如果生成后自动写入知识库，会把很多不稳定内容污染进去。MethodologyCard 解决的是另一个问题：不同产物的生成方法不同，研究报告、学习指南、工作准备和对比分析的 workflow、output structure、quality checklist 都不一样。如果全写死在 Prompt 里，后续难维护、难解释、难复用。MethodologyCard 把生成方法显式化，让系统既可控又能扩展。

#### 常见追问

- Distillation 为什么绑定 artifactVersionId？
- Methodology 匹配优先级怎么设计？
- 固定 workflow 会不会不智能？

#### 常见坑

- 不要把 Methodology 讲成只是 prompt 字符串。
- 不要把 Artifact 当成 Wiki。

### Q9：长期 Memory 为什么要分层，而不是把会话历史都塞给模型？

#### 面试官为什么问

这是上下文工程和隐私治理题。

#### 回答思路

全量历史会带来 token 成本、噪声、隐私和旧信息干扰；分层读取和策略写回更稳。

#### 结合 NoteWeave 怎么答

最近消息、session summary、space memory、user memory 分层；DRAFT、寒暄、敏感信息、低价值内容不写入。

#### 源码与验收锚点

- `ContextReadRouter`
- `MemoryWritebackService`
- `MemoryWritebackStrategy`
- `Phase12LongTermMemoryIntegrationTest`

#### 可直接复述的面试回答

长期记忆不是把所有历史都存起来再全塞给模型。那样会带来 token 成本、噪声污染、旧上下文干扰和隐私风险。NoteWeave 把上下文分成最近消息、session summary、space memory 和 user memory。最近消息解决短期连续性，session summary 压缩当前会话，space memory 保存空间内长期有效上下文，user memory 保存稳定偏好。写回也不是所有内容都写，DRAFT、寒暄、敏感信息和低价值内容会被策略过滤。这个设计的核心是：Memory 最大风险不是没有记忆，而是写太多、召回太脏，最后反而降低回答质量。

#### 常见追问

- 怎么判断内容值得写入？
- Memory 写脏后怎么治理？
- DRAFT 为什么严格排除？

#### 常见坑

- 不要说记忆越多越好。
- 不要把用户私有 Memory 讲成团队共享 Memory。

### Q10：为什么还要做 `Observability / Eval / Admin / Ops`？

#### 面试官为什么问

这是工程成熟度和上线意识题。

#### 回答思路

AI 系统出了问题不能靠猜，要能从回答反查检索、证据、Prompt、模型、任务和依赖健康。

#### 结合 NoteWeave 怎么答

PromptVersion、LLMCallLog、RetrievalTrace、RagEvalRun、SystemHealth、Cleanup、AuditLog 和 Admin/Ops 都是已验收能力。

#### 源码与验收锚点

- `AdminObservabilityController`
- `AdminOpsController`
- `SystemHealthService`
- `Phase14ObservabilityEvaluationIntegrationTest`
- `Phase15AdminOpsIntegrationTest`

#### 可直接复述的面试回答

我做 Observability、Eval 和 Admin/Ops，是因为 AI 系统最难的不是第一次跑通，而是回答错了、引用不对、任务卡住、依赖异常时怎么定位。NoteWeave 通过 PromptVersion 管理提示词演进，通过 LLMCallLog 看模型调用，通过 RetrievalTrace 看召回和融合，通过 Citation 看最终证据，通过 RagEvalRun 做离线评测，通过 SystemHealth 拆分检查 MySQL、Redis、MinIO、Kafka、ES 和 LLM Provider，通过 Cleanup 的 scan 和 execute 控制删除风险，通过 AuditLog 记录关键后台操作。这些能力让系统从“能演示”变成“能验收、能排查、能治理”。

#### 常见追问

- 一次坏回答你怎么排查？
- Eval 为什么不能污染正式会话？
- 没有生产 QPS 怎么回答？

#### 常见坑

- 不要编造线上准确率或 P99。
- 不要把日志当成 Eval。

## 4. 边界和不能说满的地方

- 可以坚定讲：双空间、统一异步底座、Hybrid RAG、Citation、WebSocket Runtime、个人研究链路、长期 Memory、Observability、Eval、Admin/Ops。
- 不要讲成当前已落地：真实生产 QPS/P99/token/day、完整开放式 MCP 平台主链路、完整开放 Agent、GraphRAG 主链路、Bibtex 端到端、微服务拆分、分库分表。
