# NoteWeave 追问题库

> 本文件为 2026-06-01 题组版，依据当前代码、测试和 Flyway 迁移整理。不要按模块孤立背，面试时先识别问题类型，再把相似问题放在一起答。

## 0. 使用方式

把每个起手问题都当成链路题。回答时按“为什么、怎么做、失败怎么办、怎么验证、怎么扩展”五层往下走。

建议按这八组练：

- 边界与隔离：Space、Permission、Citation、Artifact、Wiki、Memory、Admin。
- 外部输入受控：上传文件、URL Source、Bilibili MCP、用户 prompt。
- 一致性与恢复：Task、Outbox、Kafka、Worker、WIKI_INDEX、RAG_EVAL_RUN、CLEANUP_RESOURCE。
- 证据可信：Hybrid RAG、Wiki recall、EvidencePostProcessor、Citation、RetrievalTrace、RAG Eval。
- 生成与沉淀：ChatMessage、Artifact、Methodology、SynthesisCard、Wiki、AutoWikiMaintenance、Memory。
- 工具与 Agent 边界：StudioMcpToolRegistry、Bilibili MCP、ArtifactPlanExecutor、SkillExecutionLog。
- 表结构与中间件落位：MySQL 表、Redis key、MinIO object、ES index、Kafka topic/Outbox。
- 可观测、扩展与排障：PromptVersion、LLMCallLog、AnswerFeedback、Admin/Ops、cleanup、health、audit、压测方案。

## 1. 边界与隔离类追问

起手问法合并：
- 你先介绍一下 NoteWeave，为什么不是普通 RAG Demo？
- 为什么要有 TEAM/PERSONAL 双空间？
- systemRole 和 SpaceMember.role 为什么拆开？
- Citation、Memory、Artifact、Wiki 为什么都要考虑权限？
- Admin 能不能绕过所有边界？

连续追问路径：
1. 为什么需要边界：AI 知识系统最怕串数据，二次读取比普通 CRUD 更危险。
2. 当前怎么实现：Space 是一级容器，TEAM/PERSONAL 生命周期不同；SpaceMember 管空间协作，users.system_role 管平台管理。
3. 哪些链路要复用边界：RAG 召回、Citation 读取、Artifact 查看、Memory 写入、Admin 查询、Wiki 发布。
4. 失败时怎么处理：成员退出、文档删除、空间归属变化后，读取时仍要做权限判断。
5. 怎么扩展：可加资源级 ACL、审计和更细的 Admin 授权，但不能说当前已经无限细。

强答要点：
- Controller 校验不够，Service/Worker/异步任务和二次读取入口也要校验关键资源。
- Admin 是运维管理角色，不等于可以无审计读取所有个人私有知识。
- Citation 保存引用关系，但展示时仍要回到当前资源权限。

高压追问：
- 如果用户退出 Space，历史 ChatMessage 里的 Citation 还能展示吗？
- 如果 Artifact 同时引用团队文档和个人 Source，可见性怎么判断？
- 如果 ES 里还有旧 chunk，会不会绕过权限？

坑点：
- 不要把团队 OWNER 说成系统 ADMIN。
- 不要说权限靠前端按钮隐藏。
- 不要说 Admin 可以天然绕过全部数据边界。

## 2. 外部输入受控类追问

起手问法合并：
- 从上传到可检索经历哪些阶段？
- URL Source 为什么要做安全抓取？
- Bilibili MCP 怎么进入 Chat 或 Artifact？
- 用户 prompt、文档内容、视频字幕里有注入指令怎么办？
- 外部工具结果为什么不能直接写长期知识？

连续追问路径：
1. 为什么需要受控入口：外部输入可能大、慢、不可信、不可解析，也可能包含 prompt injection。
2. 当前怎么实现：上传走 MinIO、Document、Task、chunk、ES；URL Source 走 SafeUrlContentFetcher 和 READY 文本校验；Bilibili MCP 走 registry 和本地/远程 tool service。
3. 状态落在哪里：业务事实落 MySQL，大对象落 MinIO，短期运行态落 Redis，检索索引落 ES，长任务落 Task。
4. 失败时怎么处理：解析失败、MCP 超时、ES 写失败、URL 不可读都要进入任务状态或明确错误，不吞掉失败。
5. 怎么验证：看 Phase11_6ChatMcpIntegrationTest、RemoteBilibiliMcpToolServiceTest、上传/索引集成测试、TaskEvent 和日志。

强答要点：
- 上传成功不等于可检索，只有解析、chunk、索引和 activeIndexVersion 正常后才可用。
- SafeUrlContentFetcher 不是普通 HTTP 下载器，它限制 http/https、禁止 userInfo、拦截 localhost/.local/内网/链路本地/多播地址、限制重定向和响应大小，用来降低 SSRF 和异常大页面风险。
- Bilibili MCP 当前是受控工具扩展：StudioMcpToolRegistry、Local/RemoteBilibiliMcpToolService、BilibiliMcpCoreService、LoadMcpToolContextSkill。
- 外部工具结果只能作为上下文或证据进入生成，不能自动写 Wiki、Memory 或 ConceptCard。

高压追问：
- 秒传能否跨 Space 复用？会不会泄露文件存在性？
- 远程 Bilibili MCP 返回空 promptContext 怎么办？
- 文档里写“忽略系统提示”时，PromptBuilder 怎么约束？

坑点：
- 不要说 MCP 是完整 marketplace。
- 不要说 URL/视频字幕进入系统后天然可信。
- 不要说工具结果会自动沉淀成长期知识。

## 3. 一致性与恢复类追问

起手问法合并：
- 为什么不直接在业务事务里发 Kafka？
- Outbox 解决的核心问题是什么？
- Worker 重复消费如何保证幂等？
- 任务取消为什么是 cancel_requested？
- WIKI_INDEX、RAG_EVAL_RUN、CLEANUP_RESOURCE 失败怎么办？

连续追问路径：
1. 为什么需要统一骨架：上传解析、Source 编译、Artifact 生成、Wiki 入索引、RAG Eval、cleanup 都是耗时任务。
2. 当前怎么实现：业务事务先写 Task 和 TaskOutbox，调度器投 Kafka，Consumer 只拿 taskId 回查 DB，Worker 通过 TaskExecutionCoordinator 推进状态。
3. 一致性边界：DB 内强一致，DB 到 Kafka/Worker 是可重试的最终一致。
4. 幂等边界：任务状态、attempt/event、业务唯一键、indexVersion、artifactVersionId、runId 等共同兜底。
5. 人工介入：AdminTaskService 和 AdminTaskRetryValidator 处理重试、标记失败和目标对象校验。

强答要点：
- Outbox 防的是“DB 成功但消息没发”或“消息先到但 DB 未提交”这类跨系统不一致。
- 重复消费不能只依赖 Kafka，Worker 必须回查 Task 当前状态。
- cancel_requested 是协作式取消，只能在安全点停止。

高压追问：
- Kafka 已投递但 Worker 执行一半失败，业务表和 Task 怎么对齐？
- Wiki 发布成功但 WIKI_INDEX 失败，用户还能看到什么？
- cleanup execute 失败会不会误删？

坑点：
- 不要说 Outbox 是分布式强一致。
- 不要说 Redis 是主任务队列。
- 不要说取消能强杀所有外部 IO。

## 4. 证据可信与防幻觉类追问

起手问法合并：
- Hybrid RAG 具体 hybrid 在哪里？
- BM25、向量、Wiki recall 各解决什么问题？
- Weighted RRF 为什么比简单拼接稳？
- 没有证据为什么要兜底？
- 用户说 Citation 不准或回答错了，怎么查？

连续追问路径：
1. 为什么需要证据链：RAG 最大风险不是不能回答，而是答得像真的但证据不可查。
2. 当前怎么实现：HybridRetriever 多路召回，WeightedReciprocalRankFusion 融合，EvidencePostProcessor 做证据包，PromptBuilder 约束回答。
3. 结果怎么追踪：CitationService 保存引用，RetrievalTrace 记录召回、融合、后处理和 prompt 信息，LLMCallLog 保存模型调用。
4. 错误怎么排查：先查权限和 scope，再查 trace，再查 evidence post-process，再查 prompt/version/log，最后查 citation 展示。
5. 怎么验证：RAG Eval 用 case/run/result 看 recallAtK、MRR、citationCoverage，但不能包装成线上准确率。

强答要点：
- Wiki recall 是长期人工确认知识的一路补充，不等于完整 GraphRAG。
- Citation 不能只靠模型输出编号，必须持久化到可回溯资源。
- Prompt injection 不能靠一句提示解决，要结合权限、证据格式、兜底和 trace。

高压追问：
- 如果向量召回挂了，系统能否用 BM25/Wiki 降级？
- 如果 EvidencePostProcessor 截断掉关键证据，怎么发现？
- 如果用户反馈答案错，怎么把样本变成 Eval case？

坑点：
- 不要编造 recall@k、准确率、线上 A/B。
- 不要把 Hybrid RAG 说成完整 GraphRAG。
- 不要说模型自己能判断权限。

## 5. 生成与长期沉淀类追问

起手问法合并：
- Artifact 为什么独立于 ChatMessage？
- Wiki、SynthesisCard、Memory 为什么不能混在一起？
- MethodologyCard 解决什么问题？
- DRAFT/FORMAL 为什么影响长期记忆？
- AutoWikiMaintenance 会不会替代人工确认？

连续追问路径：
1. 为什么要分层：临时回答、阶段性产物、团队长期知识、个人综合沉淀、长期记忆的风险和生命周期不同。
2. 当前怎么实现：ChatMessage 记录对话，Artifact/ArtifactVersion 记录产物，WikiPage/WikiPageVersion 记录团队知识，SynthesisCard 记录个人确认沉淀，MemoryWritebackStrategy 控制记忆写回。
3. 方法论怎么控制：MethodologyCard 管 workflow、outputStructure、qualityChecklist，不是模型训练。
4. 自动化边界：AutoWikiMaintenance 和 WikiGraph 辅助维护长期知识，但不能替代人工治理。
5. 失败怎么兜底：proposal/confirm、artifactVersionId、citation、version、WIKI_INDEX、Trace 共同保证可追溯。

强答要点：
- Artifact 默认不进 Wiki，因为生成内容可能是草稿或未验证结论。
- SynthesisCard 要用户确认，避免把模型草稿永久化。
- Memory 写入要过滤 DRAFT、短问候、敏感内容和低价值上下文。

高压追问：
- 如果 Artifact 生成后又 regenerate，用户 confirm 的到底是哪版？
- 如果生成结果没有 citation，可以沉淀吗？
- 如果 WikiGraph 关系错了，会不会影响 RAG 回答？

坑点：
- 不要说 Artifact 自动进入 Wiki/Memory/ConceptCard。
- 不要说 MethodologyCard 是 RL 或训练。
- 不要说 AutoWikiMaintenance 已经实现复杂审批流。

## 6. 工具、Skill 与 Agent 边界类追问

起手问法合并：
- Skill 在项目里是什么，不是什么？
- ArtifactPlanExecutor 是不是 Agent？
- Bilibili MCP 和普通函数调用有什么区别？
- SkillExecutionLog 记录什么价值？
- 未来要做真正 Agent 还缺什么？

连续追问路径：
1. 为什么需要工具边界：外部工具能扩展上下文，但也带来超时、权限、成本、审计和可信度问题。
2. 当前怎么实现：StudioMcpToolRegistry 解析工具参数，Bilibili 本地/远程服务返回结构化上下文，ArtifactPlanExecutor 把 LoadMcpToolContextSkill 放进生成计划。
3. 怎么观察：SkillExecutionLog 记录 skillName、输入输出、状态、promptVersion，RetrievalTrace 记录 evidence 和工具上下文影响。
4. 为什么不是完整 Agent：当前是受控步骤编排，不是开放式规划器、任意工具、自动预算和多 Agent 协作。
5. 怎么扩展：补工具 schema、权限、沙箱、超时、预算、回滚、人工确认和审计。

强答要点：
- MCP 当前最稳口径是“受控工具扩展路径”，不是主链路万能协议。
- ArtifactPlanExecutor 强在可控和可追踪，弱在自主规划能力有限。
- SkillExecutionLog 是排障和审计材料，不要说成训练闭环已经完成。

高压追问：
- 如果模型要求调用未授权工具，系统怎么拒绝？
- 如果 Bilibili MCP 返回内容太长，怎么截断和留证据？
- 如果工具上下文和已有 Source 冲突，谁优先？

坑点：
- 不要说完整多 Agent 平台已落地。
- 不要说 MCP 工具能自动绕过业务权限。
- 不要把工具结果等同于权威知识。

## 7. 可观测、评测、运维与扩展类追问

起手问法合并：
- 一次坏答案怎么排查？
- PromptVersion、LLMCallLog、AnswerFeedback 有什么用？
- RAG Eval 为什么不能污染正式 ChatSession？
- cleanup 为什么 scan 和 execute 分开？
- 没有生产 QPS/P99，怎么回答性能？
- 面试官问“怎么证明这个项目真的跑过”，怎么把测试、trace、eval 串起来？

连续追问路径：
1. 为什么需要运营面：AI 系统不能只演示成功回答，还要能解释坏答案、失败任务和资源残留。
2. 当前怎么实现：AdminObservability 管 prompt/log/trace，AdminRagEval 管 eval，AdminOps 管 cleanup/health/dashboard/audit，AdminManagement 管用户/空间/task。
3. 排障顺序：权限和 scope -> Task/Event -> RetrievalTrace/Citation -> PromptVersion/LLMCallLog -> Feedback/Eval -> 组件 health。
4. 资源治理：cleanup 先 scan 再 execute，降低误删；health 按 MySQL/Redis/MinIO/Kafka/ES/LLM 拆。
5. 验证闭环：纯逻辑用单测，例如 RRF、EvidencePostProcessor、PromptBuilder、SafeUrlContentFetcher、MethodologyMatcher；端到端用 MockMvc 和 ContainerizedIntegrationTest 连 MySQL/Redis/Kafka/MinIO/ES；异步任务看 TaskAttempt、TaskEvent、TaskOutbox、业务表副作用。
6. 扩展口径：按瓶颈拆 Worker、RAG、LLM、Artifact、Eval/Ops；不编造生产指标。

强答要点：
- RAG Eval 是离线评估和回归验证，不是正式用户聊天。
- PromptVersion 让同一问题能追溯“当时用的是哪版提示词”。
- AnswerFeedback 能把用户反馈转成后续评测样本或排查入口。
- Testcontainers/local Docker 集成测试能证明组件协作和状态落库，但不能替代线上压测或真实用户效果指标。

高压追问：
- 如果 Kafka 堆积、ES 慢、LLM 超时同时发生，先怎么定位？
- 如果普通用户看到了 Admin trace，是哪个边界出问题？
- 如果文档量上升 10 倍，你先优化哪条链路？
- 如果一个测试只 mock 了 Service，哪些链路仍然没有被证明？

坑点：
- 不要说已有真实线上 QPS、P99、token/day。
- 不要说 Eval 等于线上 A/B。
- 不要说 cleanup 可以无风险自动删除所有残留。
- 不要把本地集成测试说成生产级压测。

## 8. 表结构与中间件落位类追问

起手问法合并：
- 这个项目核心表结构怎么设计？
- 为什么不用一张大 JSON 表存所有 AI 结果？
- MySQL、Redis、MinIO、ES、Kafka 各自解决什么问题？
- 为什么当前迁移很少显式 foreign key？
- 如果 ES、Kafka、Redis、MinIO 任一组件出问题，怎么回到 MySQL 事实源？

连续追问路径：
1. 为什么需要拆表：不同数据生命周期不同，长期事实、短期运行态、大对象、检索读模型、消息事件不能混在一起。
2. 当前怎么实现：MySQL 存 users/space/task/document/citation/artifact/wiki/memory/eval/ops 等事实，Redis 存 ticket/runtime/bitmap，MinIO 存文件和 snapshot，ES 存 chunk 和 wiki read model，Kafka 传任务。
3. 索引怎么讲：`space_id/status`、`task_type/task_status`、`document_id/index_version`、`retrieval_trace(scene,created_at)`、`rag_eval_run(space_id,created_at)`、`system_health_snapshot(component,checked_at)`。
4. 失败时怎么处理：Task/Outbox/Event、Trace/Citation、cleanup、Admin/Ops、重建索引和软删除。
5. 怎么扩展：如果换 MQ 或存储，只换适配层，不改权限、版本、事实源和排障抽象。

强答要点：
- `citation`、`retrieval_trace`、`llm_call_log`、`answer_feedback` 分开，是为了证据链和排障链拆清楚。

- `artifact_version`、`wiki_page_version`、`artifact_distillation_proposal`、`rag_eval_run/result` 都是“版本”和“批次”的事实。
- Redis 不存长期知识，ES 不存最终权限，Kafka 不存业务事实，MySQL 不存大对象。

高压追问：
- 为什么当前迁移里很少显式 foreign key？
- `artifact_source` 和 `artifact_citation` 为什么要分表？
- 如果用户说“我明明能搜到但看不到”，先查哪一层？

坑点：
- 不要说分库分表已经落地。
- 不要说 Redis/Kafka/ES 任一组件能替代 MySQL。
- 不要说一张 JSON 大表更简单就足够。

## 9. 题组串联练习

练习时用下面八个组合题自测：

1. 外部输入怎么受控进入系统：上传文件、URL Source、Bilibili MCP、用户 prompt。
2. 临时内容怎么变成长期知识：ChatMessage、Artifact、Wiki、SynthesisCard、Memory。
3. 长任务失败怎么恢复：Task、Outbox、Kafka、Worker、Admin 重试、TaskEvent。
4. 回答错了怎么查：Hybrid RAG、EvidencePostProcessor、Citation、RetrievalTrace、PromptVersion、LLMCallLog。
5. MCP、Skill、Agent 怎么讲才不被追穿：Bilibili MCP、ArtifactPlanExecutor、SkillExecutionLog、未来扩展边界。
6. 表结构和中间件怎么串起来答：MySQL 表结构、Redis key、MinIO object_key、ES index、Kafka topic/outbox。
7. 新增特性带来的性能压力怎么答：Bilibili MCP 超时、AutoWikiMaintenance 维护、RAG Eval 批量运行、Admin/Ops 资源清理。
8. 怎么证明不是纸上谈兵：单测、MockMvc、ContainerizedIntegrationTest、TaskEvent、RetrievalTrace、Citation、RAG Eval。

## 10. 把所有题都拉回项目主线
如果面试官问法很散，优先拉回这条主线：

1. 这题问的是哪个链路。
2. 这个链路解决什么真实问题。
3. 当前实现的边界是什么。
4. 如果不用当前方案，备选方案是什么。
5. 当前方案的主要代价是什么。
6. 如果出问题先查哪几层。
7. 后续准备往哪一步演进。

这个顺序几乎可以覆盖项目介绍、权限、上传、RAG、Wiki、Artifact、Memory、Eval、Ops 和表结构追问。
