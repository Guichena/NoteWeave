# NoteWeave 简历风险点与优化口径

## 0. 本篇定位

这份文件专门解决“简历里写什么、面试里怎么讲、哪些词容易讲过头”三个问题。原则是：

- 能被当前仓库、测试、接口和验收支撑的能力，可以坚定主讲。
- 已经做了但边界容易模糊的能力，要主动降级表达。
- 只能作为后续演进的能力，不要包装成当前主链路事实。

当前总口径是：NoteWeave 现阶段已经形成了本地可运行、链路可验收的 AI 知识工作台闭环；MCP 这块不再只是停留在概念层，而是已经把 B 站解析能力拆成远程 MCP tool service 并接到产物入口和对话触发链路。但不要把它夸大成完整开放协议生态或多 Agent 平台。

## 1. 面试官真正想验证什么

面试官看到 `Hybrid RAG`、`长期记忆`、`Skill`、`MCP`、`Redis runtime state` 这些词时，通常不是想听概念定义，而是想追四件事：

1. 仓库里到底落在哪些类、表、接口和测试。
2. 主链路做到什么程度。
3. 和常见方案相比有什么取舍。
4. 有没有把未来规划包装成当前事实。

## 2. 可以坚定主讲的已验收能力

### 2.1 Hybrid RAG

推荐讲法：

> 我做的是权限约束下的团队混合检索链路，不是简单 top-k 拼接。链路里有 BM25、向量召回、Wiki recall、Weighted RRF、EvidencePostProcessor、Citation 和 RetrievalTrace。它解决的是企业知识问答里语义、关键词、权限、版本、证据和排障要同时成立的问题。

实现兜底锚点：

- `HybridRetriever`
- `EvidencePostProcessor`
- `TeamRagPromptBuilder`
- `CitationService`
- `Phase9HybridRetrievalIntegrationTest`

面试官继续追时要补：

- 为什么不能只用向量检索。
- 为什么 RRF 比简单分数相加更稳。
- Citation 解决的是来源可追踪，不是答案绝对正确。

常见坑：

- 不要说 Hybrid RAG 等于“多个搜索结果拼一起”。
- 不要说 citation coverage 高就等于答案一定正确。

### 2.2 长期记忆

推荐讲法：

> NoteWeave 的长期记忆不是把所有聊天历史都塞进 prompt，而是分成 session summary、space memory 和 user memory。读取时通过上下文路由分层装配，写入时通过策略过滤 DRAFT、寒暄、敏感信息和低价值内容。

实现兜底锚点：

- `MemoryWritebackService`
- `MemoryWritebackStrategy`
- `ContextReadRouter`
- `Phase12LongTermMemoryIntegrationTest`

面试官继续追时要补：

- 为什么 DRAFT 不写长期 Memory。
- 写回策略如何防止噪声污染。
- Memory 读取为什么不能全量历史直接塞进上下文。

常见坑：

- 不要把 Memory 讲成无脑保存所有聊天记录。
- 不要说 DRAFT 会写长期记忆。

### 2.3 Task / Outbox / Kafka

推荐讲法：

> 项目里的长任务统一走 `Task + Attempt + Event + Outbox + Kafka + Worker`，覆盖上传解析、索引、Source 编译、Artifact 生成、Eval 和 Cleanup。Outbox 负责业务事务和消息投递的最终一致，Worker 侧再做状态回查和幂等执行。

实现兜底锚点：

- `TaskService`
- `TaskOutboxService`
- `TaskKafkaConsumer`
- `TaskExecutionCoordinator`
- `TaskServiceIntegrationTest`

面试官继续追时要补：

- 为什么不在事务里直接发 Kafka。
- 为什么 Outbox 不是“绝不重复”。
- 取消为什么用 `cancel_requested` 而不是强杀线程。

常见坑：

- 不要说 Outbox 保证绝不重复。
- 不要把 Redis 讲成主任务队列。

### 2.4 Artifact / Wiki / Synthesis 分层

推荐讲法：

> Artifact 是版本化工作产物，Wiki 和 Synthesis 才是用户确认后的长期知识。团队侧通过人工发布进入 Wiki，个人侧通过 distillation proposal/confirm 沉淀为 SynthesisCard，避免 LLM 生成结果自动污染知识库。

实现兜底锚点：

- `ArtifactService`
- `PersonalArtifactDistillationService`
- `WikiPageVersion`
- `SynthesisCard`

面试官继续追时要补：

- 为什么 Artifact 不直接写入长期知识。
- 为什么要保留版本化和确认环节。
- 团队 Wiki 和个人 Synthesis 的差异是什么。

常见坑：

- 不要说 Artifact 生成后自动进入长期知识。

### 2.5 Observability / Eval / Admin / Ops

推荐讲法：

> 项目已经补了 PromptVersion、LLMCallLog、RetrievalTrace、RagEvalRun、SystemHealth、Cleanup、AuditLog 和 Admin/Ops。它们的价值不是“功能更多”，而是让坏回答、任务失败、依赖异常和清理风险能被定位、复现和治理。

实现兜底锚点：

- `AdminObservabilityController`
- `AdminOpsController`
- `SystemHealthService`
- `Phase14ObservabilityEvaluationIntegrationTest`
- `Phase15AdminOpsIntegrationTest`

面试官继续追时要补：

- Trace、Log、Eval、Health 各自看什么。
- 为什么 Eval 不能污染正式聊天和长期记忆。
- Cleanup 为什么要 scan/execute 两阶段。

常见坑：

- 不要把日志说成 Eval。
- 不要编造生产准确率。

## 3. 已做但必须讲清边界的能力

### 3.1 Skill

不要讲成：

- “我们做了一个完全开放的 Agent Skill 平台。”

推荐讲法：

> NoteWeave 里的 Skill 更接近受控生成流水线。系统会按 artifactType 选择固定计划和步骤，做上下文加载、证据选择、内容生成、版本保存，并记录 SkillExecutionLog 方便排查。它有编排思想，但当前不是完整开放式 Agent 插件生态。

实现兜底锚点：

- `ArtifactPlanExecutor`
- `SkillExecutionLog`
- `MethodologyMatcher`
- `PersonalGenerationService`

常见追问：

- 为什么不直接做开放 Agent？
- 固定 workflow 会不会不够智能？

稳妥回答：

> 当前优先保证的是知识生成的可控性、证据链和版本化。更开放的 Agent 能力可以后续接在工具协议和计划执行层，但不是现在的主线。

### 3.2 Redis runtime state

不要讲成：

- “我们主链路靠 Redis 跑异步任务队列。”

推荐讲法：

> 主异步任务还是 Task/Outbox/Kafka。Redis 在 NoteWeave 里主要承载 WebSocket runtime state，例如 ws-ticket、短期事件缓冲、执行状态、partial content、stop/resume 和断线恢复。

实现兜底锚点：

- `ChatRuntimeStateStore`
- `ChatRuntimeService`
- `WsTicketService`

常见追问：

- 为什么不全部落 MySQL？
- Redis 挂了会怎样？

稳妥回答：

> Redis 里的状态偏短生命周期和运行态协调；正式消息、Citation、Artifact、Memory 仍然落 MySQL。生产化时可以继续补更强的持久化和降级策略。

## 4. 已做但仍要守住边界的扩展能力

### 4.1 MCP

当前口径：

> 当前没有做完整开放式 MCP 平台，但已经把 B 站解析能力拆成独立远程 MCP tool service。主系统负责显式工具注册、产物入口、对话触发和后续 artifact workflow 编排，工具服务本身可以单独部署和演进。

不要讲成：

- “MCP 已经覆盖整个系统并成为所有主链路的统一协议。”
- “我们已经实现完整通用 MCP 工具生态或 marketplace。”

### 4.2 Bibtex

当前口径：

> Bibtex 很适合补在个人 Source 导入层，用来解析论文元数据、作者、年份和引用关系，但当前主输入仍是 file、text、url、source，不要说 Bibtex 已经端到端落地。

不要讲成：

- “学术引用链路已经完整实现。”

### 4.3 GraphRAG / 多 Agent / 微服务拆分

当前口径：

> NoteWeave 有 Wiki graph、ConceptRelation、受控 Skill pipeline 和模块化边界，但当前主检索链路不是 GraphRAG，当前系统也不是完整多 Agent 平台或已拆分微服务架构。

不要讲成：

- “主链路已经是 GraphRAG。”
- “已经有成熟多 Agent 编排。”
- “已经上线微服务和注册中心。”

## 5. 简历写法建议

适合写在简历上的表达要尽量具体，避免大词空转。

更稳的写法：

- “设计并实现权限约束下的 Hybrid RAG 链路，包含 BM25、向量召回、Wiki recall、Weighted RRF、Citation 与 RetrievalTrace。”
- “抽象统一异步任务底座，基于 Task、Outbox、Kafka、Worker 支撑文档处理、生成、评测和清理。”
- “实现 WebSocket runtime state、stop/resume、DRAFT/FORMAL 会话态与长期记忆写回策略。”
- “构建 Artifact、Wiki、Synthesis 分层沉淀模型，避免生成结果直接污染长期知识。”
- “补齐 PromptVersion、LLMCallLog、RagEvalRun、SystemHealth、Cleanup、AuditLog 等可观测与运维能力。”

容易出风险的写法：

- “构建企业级 Agent 平台。”
- “自研 GraphRAG 主链路。”
- “落地远程 MCP tool service，并接入 Studio 产物入口与对话触发链路。”
- “生产级高并发系统，准确率提升 xx%。”

## 6. 没有生产指标时怎么说

推荐讲法：

> 这个项目现阶段是本地可验收的工程工作台，不会编造真实生产 QPS、P99 或 token/day。当前已经有可观测和评测基础，比如 TaskEvent、RetrievalTrace、LLMCallLog、RagEvalRun、SystemHealth 和 AuditLog。如果要给出指标，我会先定义压测环境和评测集，再看任务成功率、重试率、索引耗时、检索 recall@k、MRR、citation coverage、端到端延迟和错误率。

不要讲成：

- “线上准确率 92%。”
- “P99 已经优化到 xx ms。”
- “每天 token 消耗多少我有真实统计。”

## 7. 最稳总原则

对外回答时尽量用这个句式：

> 这块当前已经做到 A，代码和验收在 B；它解决的问题是 C；如果继续生产化，我会补 D；但我不会把 D 说成当前已经落地。

这个句式既能体现工程深度，也能把诚实边界守住。
