# NoteWeave 高频题标准深答

这份文件默认按大厂面试场景来写，回答粒度按 2 分钟起步。

使用方式：

- 先把每道题的主逻辑背顺
- 再把其中的类名、链路名、权衡点记牢
- 最后结合 `03-追问题库.md` 和 `05-mock-面试记录.md` 做追问训练

## 1. 为什么要把 `TEAM` 和 `PERSONAL` 做成一级空间边界？

标准深答：

我当时把 `TEAM` 和 `PERSONAL` 做成一级空间边界，不是为了产品上看起来更完整，而是因为这两类场景在权限模型、知识生命周期和沉淀方式上天然不同，如果不在最外层拆开，后面很多能力都会混掉。

`TEAM` 空间本质上解决的是多人共享知识的问题，它强调的是共享上传、统一检索、可引用、可沉淀到 Wiki，而且所有内容都要受空间成员权限约束。`PERSONAL` 空间解决的是个人研究过程问题，它更强调资料导入、概念组织、结构化生成和长期知识积累，很多中间产物只对 owner 自己可见，也不应该直接进入团队知识库。

所以我在架构上把这两条主链路一开始就拆开了，但又不是完全两套系统。底层像鉴权、任务、存储、检索、LLM、可观测性这些能力是复用的；上层在实体模型、权限校验、沉淀目标上做分流。这样做的收益是后面在 Artifact、Wiki、Memory、Citation 这些能力上边界会比较清晰，不容易出现“个人探索内容污染团队知识库”或者“团队引用绕过权限看到个人内容”这种问题。

如果不这样拆，短期看开发会快一点，但长期会出现两个问题：第一是权限模型越来越难解释；第二是知识沉淀模型会越来越混，最后既不像团队知识库，也不像个人研究系统。所以我会把它看成这个项目最重要的边界设计之一。

面试官可能追问：

- 为什么不先共用一套内容模型，后面再补权限？
- 为什么 `Artifact` 不能直接等价于 `Wiki`？

## 2. 为什么统一成 `Task + Outbox + Kafka + Worker` 这套异步底座？

标准深答：

这个项目里长任务非常多，而且都不是纯计算型小任务。像文档上传后的解析、切 chunk、建索引、个人 Source 编译、Artifact 生成、评测、后台清理，这些任务都具备几个共同点：执行时间长、失败概率不低、要重试、要审计、还可能被取消。如果每个模块自己写一套异步机制，很快就会出现状态机不统一、日志不统一、幂等策略不统一的问题。

所以我把这些后台流程都收口到统一的 `Task` 模型里。`Task` 承载任务主状态，`TaskAttempt` 记录每次执行尝试，`TaskEvent` 记录状态流转和关键事件，`TaskOutbox` 负责把业务事务和消息投递解耦。消息侧再通过 Kafka 和 Worker 去消费执行。这样一来，不同模块虽然业务逻辑不同，但调度、重试、取消、审计这些横切能力是一套统一机制。

这里最关键的设计点其实是 Outbox。因为如果你在业务事务里直接发 Kafka，就会遇到典型的一致性问题：数据库成功了但消息没发出去，或者消息发出去了但事务回滚了。Outbox 的意义就是先把“待发送事实”落到数据库里，等事务真正提交后，再由分发器做异步投递，这样最终一致性更可控，排障路径也更清晰。

这套设计的收益是，后面你新增任何长任务能力，都不用重新发明一套后台执行模型。代价是模型会稍微重一点，状态流转也更规范化，但对于这种 AI 工作台项目来说，我觉得这是值得的，因为它本来就不是一个只跑 happy path 的 demo。

面试官可能追问：

- 为什么不直接用 MQ 自带重试能力？
- `cancel_requested` 为什么比强杀更稳？

## 3. 你讲讲文档上传到可检索的完整链路。

标准深答：

团队知识库这条链路我会拆成六步来讲：初始化上传、分片上传、合并落对象、异步解析、切块索引、最终检索可用。

第一步是 init upload，服务端先创建上传会话，生成 uploadId 和必要的上传配置。第二步是 chunk upload，客户端按 chunk 分片上传，后端用 Redis bitmap 这类轻量状态结构跟踪每个 chunk 是否已经到齐，这样可以支持断点续传，也方便在 merge 前做完整性校验。第三步是 merge，确认所有 chunk 齐了之后，把分片合并成对象文件，算内容 hash，并绑定 `FileObject` 和 `Document`。这里内容去重只限制在同一个 `spaceId` 内，因为“内容相同”不等于“权限可以跨空间复用”。

第四步开始进入异步处理。系统会创建 `DOCUMENT_PROCESS` 之类的任务，后面由 Worker 去做解析、抽取文本、切 chunk、写 Elasticsearch 索引，必要时补 embedding。第五步是索引版本切换，这里不能简单粗暴覆盖旧索引，否则新索引失败时会把当前可检索版本也搞坏，所以一般会保留 active version 的概念，等新版本完整就绪再切换。第六步才是把文档状态切成可检索，前台问答链路才会真正看到它。

我比较看重这条链路里的三个设计点。第一是上传态和处理态分离，保证大文件上传不会阻塞后续处理；第二是对象复用和权限边界并存，既拿到去重收益，又不破坏空间隔离；第三是索引切换而不是原地覆盖，避免重建索引过程把线上查询路径搞坏。

面试官可能追问：

- 为什么 merge 后不直接同步解析？
- 为什么 soft delete 比直接物理删除更合适？

## 4. 你讲讲团队侧 `Hybrid RAG` 是怎么做的，为什么不是简单“几路召回拼一下”？

标准深答：

我理解这个项目里的 `Hybrid RAG` 不是一个名词标签，而是一条真实的工程检索链路。用户提问后，系统不是直接把问题扔给模型，而是先做权限和 scope 约束，然后走多路召回，包括 BM25、向量召回和 Wiki recall。多路召回的结果不会简单拼接，而是通过 Weighted RRF 做融合排序，再经过 `EvidencePostProcessor` 做证据清洗，最后才把高质量 evidence 交给 prompt builder 去生成 grounded answer。

这里每一路召回解决的问题不一样。BM25 更适合精确术语、关键词和过滤条件明确的场景；向量召回更适合语义近似和表达不一致的问题；Wiki recall 则补充结构化沉淀知识。Weighted RRF 的价值在于它不要求不同召回通道的分数完全同尺度，但能比较稳定地融合多路排序结果。后面的 `EvidencePostProcessor` 也很关键，它解决的是真实系统里的脏问题，比如相邻 chunk 合并、低分噪声过滤、单文档结果过多导致答案偏置等。

为什么我最后选 Elasticsearch 作为检索中枢，而不是只用向量库？因为这个场景既有语义检索需求，也有全文、过滤、权限、排序和可调试需求。单纯向量库对强过滤和精确术语支持没那么自然；只用 MySQL 做全文和复杂召回又太吃力。ES 把这些能力放在一个检索中枢里，更适合企业知识问答这种“语义 + 关键词 + 权限”的混合场景。

所以这条链路真正的工程难点不在“调个 embedding 接口”，而在于怎么把多路召回、证据治理、权限边界、降级策略和可追踪性真正串成一个稳定系统。

面试官可能追问：

- 如果向量召回失败，怎么降级？
- Weighted RRF 和简单拼接相比为什么更稳？

## 5. 为什么 `citation` 不直接塞进 message JSON，而要单独做正式关系？

标准深答：

因为在这个项目里，`citation` 不是一个纯展示字段，而是正式证据对象。它后面要承接的不只是“前端把引用渲染出来”，还包括权限校验、回溯 source、和 retrieval trace 联动、后续 Wiki/Artifact 复用以及审计排查。如果把它简单放进 message JSON，短期开发是快，但后面查询、权限二次校验、统计和复用都会很难做。

我这里把 `citation` 单独建成正式关系，核心是为了让“答案引用了什么证据”成为可追踪、可校验、可复用的数据，而不是一次性生成内容的一部分。比如用户点击引用时，系统要重新校验他有没有权限访问原文；如果一次回答质量不好，后台要能顺着 citation 和 retrieval trace 倒查到底是召回错了、过滤错了还是生成错了；如果后面要把某段结果沉淀到 Wiki 或 Artifact，也希望证据链还能被正式带过去。

另外，`citation` 和 `retrieval trace` 我也故意拆开了。前者回答的是“最终引用了什么”，后者回答的是“系统为什么拿到了这些候选证据”。这两个问题在排障时差别很大。如果混成一个结构，你最后既不利于解释最终答案，也不利于分析中间召回过程。

所以这个设计的收益是证据链更正式、权限边界更稳、后续可观测性和复用性更强。代价是建模会复杂一些，但对于一个强调 grounded answer 的系统来说，我觉得这是必须付出的复杂度。

面试官可能追问：

- 如果 citation 指向无权限文档怎么办？
- retrieval trace 和 citation trace 各自怎么用？

## 6. 为什么要做 `WebSocket runtime`，以及为什么 runtime state 放 Redis？

标准深答：

如果只是做一个最简单的问答 demo，HTTP 一问一答其实就够了。但这个项目后面想解决的不只是“给你一个答案”，还包括流式输出、中断、恢复、运行态控制、`DRAFT` / `FORMAL` 会话隔离这些问题。到这个阶段，系统需要的已经不是单次请求处理，而是一个会话执行框架，所以我才引入了 `WebSocket runtime`。

在这套设计里，HTTP 更偏稳定的资源访问和最终结果查询，WebSocket 负责承接执行态。比如 token 流式下发、用户 stop、断线重连、partial content 恢复，这些都更像 runtime concern，而不是单次 API concern。为了管理这些执行态，我把 runtime state 放在 Redis 这一层，而不是完全落 MySQL。原因是这些状态更短生命周期、更新频繁、需要低延迟读写，而且很多只是会话执行期状态，不适合按正式消息模型持久化。

但这里我不会把 Redis 讲成主任务队列。主异步任务链路还是 `Task/Outbox/Kafka`。Redis 这边更适合讲成 `runtime state`，比如当前执行中的会话状态、stop/resume 控制、断线恢复上下文，以及一些短期执行协调信息。这样边界更清楚，也更符合当前仓库事实。

另外，`DRAFT` 和 `FORMAL` 分离也很关键。因为用户探索阶段很多内容并不值得永久沉淀，如果 DRAFT 直接写长期 memory，系统很快会被噪声污染。所以我把 DRAFT 更偏运行态和短期上下文，FORMAL 才进入正式链路和长期沉淀，这样用户既有探索体验，又不至于把知识库和记忆体系污染掉。

面试官可能追问：

- stop / resume 的一致性在哪保证？
- 为什么 runtime state 不完全持久化到 MySQL？

## 7. 个人研究主线为什么要做成 `Source -> Card -> Artifact -> Synthesis`？

标准深答：

个人研究这条链路我当时是故意做分层的，因为研究过程和最终知识沉淀不是一回事。如果把导入资料之后的所有结果都直接写成最终知识，系统很快会被临时想法、低质量抽取和不稳定生成污染掉。

第一层是 `Source`，负责统一承接文件、文本、URL 等输入。这里最重要的是导入完成后要保证有“可读文本”，因为后面的编译、抽卡片、证据回溯都依赖这个基础。第二层是 `Card`，包括 `ArticleCard`、`ConceptCard`、`ConceptRelation` 等，它解决的是“把研究资料结构化”。第三层是 `Artifact`，它更像带版本的工作产物，比如报告、学习指南、分析稿，不等于最终稳定知识。第四层才是 `Synthesis`，也就是用户确认后沉淀下来的长期知识结果。

这个分层的价值在于，每一层的职责不一样。`Source` 是原始输入，`Card` 是结构化中间层，`Artifact` 是生成产物，`Synthesis` 是长期知识沉淀。这样一来，你既能保留研究过程中的灵活性，又能避免“生成一次就自动进知识库”的污染问题。

从实现上看，这条链路也不是简单调用大模型。中间还有 `WikiCompilerService` 做结构化编译，`ConceptMergeService` 做概念去重合并，`EvidenceBacktraceService` 做证据回溯，后面再结合 `MethodologyCard` 和精选 evidence 去生成 Artifact。也就是说，它更像一个分层知识加工链，而不是“上传资料然后让 LLM 帮我写篇文章”。

面试官可能追问：

- 为什么 Synthesis 不直接改写已有 ConceptCard？
- 为什么 evidence backtrace 不能省？

## 8. 为什么 `Artifact` 和 `Wiki` 要分离？`MethodologyCard` 又解决了什么问题？

标准深答：

`Artifact` 和 `Wiki` 分离，是我觉得这个项目里另一个很关键的知识边界设计。因为生成结果不等于长期可信知识。很多时候用户只是想先得到一个草稿、分析稿、学习提纲或者工作产物，这些内容可能很有用，但它还没到可以直接进入长期知识库的程度。如果不分层，系统会把大量一次性生成内容直接沉淀进去，最后知识库可信度会越来越差。

所以我把 `Artifact` 设计成版本化工作产物，它强调的是生成过程、版本演进和用户编辑；`Wiki` 或 `Synthesis` 更强调长期稳定知识。中间通过显式确认和 distillation 去衔接，而不是自动覆盖。这样做虽然多了一步确认成本，但换来的是知识库污染显著下降，也更符合真实研究工作流。

`MethodologyCard` 解决的则是“同样是生成，为什么输出结构应该不一样”的问题。比如研究报告、学习方案、对比分析、工作准备，这些产物的结构差异很大。如果把输出结构全部硬编码在 prompt 里，系统后续很难演进，也很难解释为什么某次结果长这样。`MethodologyCard` 把 workflow、output structure、quality checklist 这些东西显式建模出来，相当于把生成方法本身也变成可管理资产。

所以这两个设计合在一起，解决的是“生成”和“沉淀”如何解耦，以及“生成逻辑”如何显式化。前者保证知识边界，后者保证生成过程可复用、可解释、可扩展。

面试官可能追问：

- 为什么 distillation 要绑定 `artifactVersionId`？
- 为什么用户确认是必要步骤？

## 9. 长期记忆为什么要分层，而不是把会话历史都塞给模型？

标准深答：

长期记忆这块我没有把它理解成“把所有历史都存起来”，而是把它看成上下文治理问题。因为如果你简单把全部历史塞给模型，短期可能看起来连续性更强，但很快会遇到 token 成本高、噪声越来越多、旧上下文干扰当前任务这些问题。

所以我把记忆分成了几个层次。最近消息负责短期连续性；session summary 是当前会话的压缩表示；space memory 记录某个空间里长期有效的上下文；user memory 更偏稳定偏好或者跨会话规律。这样读取上下文时，不是无脑全塞，而是通过类似 `ContextReadRouter` 这类机制按层挑选最有价值的上下文。

写回也不是所有内容都进 memory。像 DRAFT 轮次、寒暄、低价值重复内容、敏感信息，都不应该自动写回，所以我又加了 `MemoryWritebackStrategy` 这类规则，控制哪些内容值得沉淀。这样做的收益是既能保留连续性，又能控制噪声污染和 token 成本。

这个设计的核心不是“我有长期记忆”这句话，而是我知道 memory 系统最大的风险其实是过度写入和低质量召回。如果没有分层读取和规则化写回，memory 很容易从加分项变成系统噪声源。

面试官可能追问：

- 怎么判断一段内容值不值得写回？
- DRAFT 为什么严格不写长期 memory？

## 10. 为什么这个项目还要做 `Observability / Eval / Admin / Ops`？

标准深答：

因为 AI 系统真正难的地方往往不是第一次跑通，而是出了问题以后你怎么定位、怎么复现、怎么修。一个只有问答接口的 demo 看起来也能工作，但一旦用户说“这次回答不准”“这次引用不对”“这次任务卡住了”，如果系统没有观测和运维能力，你基本只能靠猜。

所以我在这个项目里比较重视这几类能力：`PromptVersion` 管理 prompt 演进，`LLMCallLog` 记录模型调用，`RetrievalTrace` 记录检索链路，`RagEvalRun` 做离线评测，`CleanupJob` 做后台清理，`SystemHealth` 做依赖健康检查，`AuditLog` 做关键操作审计。它们的共同目标就是把系统从“表面能用”变成“出了问题能定位、能验证、能治理”。

这里我尤其看重的是链路隔离。比如 Eval 不能污染正式聊天会话，因为评测本质上是离线验证，不是真实用户交互；清理任务要 scan/execute 两阶段分离，因为直接执行删除类操作风险太高；健康检查要按 MySQL、Redis、MinIO、Kafka、Elasticsearch、LLM provider 拆开，因为这些依赖的故障模式根本不一样。也就是说，这一层不是锦上添花，而是系统能不能长期维护的关键。

所以如果面试官问我这个项目为什么不像普通 demo，我一般不会只讲 RAG，而会把观测、评测、后台治理也拿出来，因为这部分最能体现工程成熟度。

面试官可能追问：

- 一次回答不准，你会沿着哪几层往回查？
- 为什么 eval 不能直接复用正式聊天链路？
