# NoteWeave 个人链路升级与竞品思考

## 0. 本篇定位

这份文件用于回答“你怎么看 NotebookLM 这类产品”“个人研究链路还能怎么升级”“你是否有产品和技术演进思考”一类开放题。

默认口径：

- NoteWeave 当前个人研究链路已经完成验收，可以坚定讲 `Source -> Card -> Artifact -> Synthesis`、Evidence backtrace、MethodologyCard、Artifact distillation 和 Memory。
- 竞品对比不要变成“复述 NotebookLM”，而要讲清 NoteWeave 当前已做到什么、下一步为什么要升级、升级接在哪些模块。
- query-aware retrieval、notebook 中间层、adaptive answering、agentic source discovery 都作为后续优化方向讲，不说成当前已落地主链路。

## 1. 这个主题在 NoteWeave 里解决什么问题

个人研究场景和团队知识库不一样，难点不是“把文档传进去”，而是如何把资料结构化、把生成结果和长期知识分层、把证据保留下来，并让用户围绕研究问题持续沉淀。

NoteWeave 当前个人链路解决的是四件事：

- 原始资料怎么进入系统并变成可加工对象。
- 资料怎么编译成 ArticleCard、ConceptCard 和关系网络。
- 生成产物怎么版本化，而不是和聊天记录混在一起。
- 用户确认后的内容怎么沉淀成长期知识，而不是让 LLM 结果自动污染知识库。

## 2. 本主题面试官想考什么

面试官问竞品和演进时，真正想验证的是：

1. 你是否理解自己项目的真实边界。
2. 你是否能从竞品抽象出工程启发，而不是只说“别人做得好”。
3. 你是否知道下一步应该优先改哪一层。
4. 你是否不会把优化方向包装成当前事实。

## 3. 高频问题清单

基础问题：

- 当前个人研究链路已经做到什么程度？
- 和 NotebookLM 相比，NoteWeave 的个人链路差在哪里？

进阶问题：

- 为什么下一步优先做 query-aware retrieval，而不是直接做大 Agent？
- Notebook / Notes 中间层解决什么问题？

深挖追问：

- 如果 evidence 不足，系统应该继续生成还是拒答？
- personal answering trace 应该记录哪些信息？

压力追问：

- 你是不是在把未来规划说成已实现？
- 当前个人链路如果已经验收，为什么还说要升级？

## 4. 问答与讲解

### Q1：你怎么看 NotebookLM 这类产品，对你当前个人链路有什么启发？

#### 面试官为什么问

这个问题考的是产品理解和技术抽象能力。好的回答应该先讲自己当前已验收的基础，再讲竞品启发和后续演进。

#### 回答思路

先给总判断：NotebookLM 的核心启发是 source-grounded answering。再讲 NoteWeave 已经有分层个人研究骨架，但下一步要从 compile-first 升级到 query-aware answering。

#### 结合 NoteWeave 怎么答

当前 NoteWeave 已验收的是 `Source -> Card -> Artifact -> Synthesis` 主链路，以及 Methodology、Evidence backtrace 和长期记忆。后续优化重点不是推翻这条链路，而是补个人侧围绕当前问题动态 narrowing、选证据、回答、回流的能力。

#### 技术原理 / 链路设计讲解

NotebookLM 值得学的不是一个具体算法名，而是 source 范围约束、evidence locating、citation binding、回答回流和资料不足时的控制策略。NoteWeave 当前已有稳定知识加工链，但个人侧回答可以继续从“按项目装配上下文”升级为“按问题检索和证据组织”。

#### 实现兜底锚点

- `SourceImportService`
- `WikiCompilerService`
- `ResearchContextService`
- `PersonalEvidenceService`
- `PersonalGenerationService`
- `PersonalArtifactDistillationService`
- `Phase11PersonalGenerationIntegrationTest`
- `Phase11_5PersonalArtifactDistillationIntegrationTest`

#### 可直接复述的面试回答

> 我觉得 NotebookLM 最值得参考的，不是它做了多少花哨输出，而是它把“基于资料回答”做成了一个 source-grounded 的研究工作台。它不是简单把文档切 chunk 做传统 top-k RAG，而更像是先把 source 归一化，再根据当前问题做 source narrowing 和 evidence locating，最后依托长上下文模型去生成 grounded answer，并且强绑定 citation 回到原文。对比之下，NoteWeave 当前个人链路已经完成验收，骨架是对的，比如 `Source -> Card -> Artifact -> Synthesis`、证据回溯、MethodologyCard、Artifact 显式 distillation 这些边界都比较清楚；但在“针对当前问题动态组织资料并回答”这件事上，还可以从 compile-first 的受控生成继续升级成 query-aware 的个人研究工作台。

#### 常见坑

- 不要说当前已经完整复刻 NotebookLM。
- 不要把 source discovery、adaptive answering 说成已验收能力。

### Q2：当前个人研究链路已经做到什么程度？

#### 面试官为什么问

面试官想先知道你的起点，否则一听“升级”，很容易误以为当前什么都没做。

#### 回答思路

先讲现在不是裸聊天，而是一条分层知识加工链，再讲这条链已经解决了哪些核心问题。

#### 结合 NoteWeave 怎么答

用户先导入 `Source`，再通过 `WikiCompilerService` 编译成 `ArticleCard`、`ConceptCard`、`ConceptRelation`，并保留 evidence backtrace；之后通过 `MethodologyCard` 和个人生成链路产出 `Artifact`，最后只有用户确认过的内容才会通过 distillation 进入 `SynthesisCard`。

#### 实现兜底锚点

- `SafeUrlContentFetcher`
- `WikiCompilerService`
- `ResearchContextService`
- `PersonalEvidenceService`
- `ArtifactPlanExecutor`
- `PersonalArtifactDistillationService`

#### 可直接复述的面试回答

> 我现在的个人链路不是裸聊天，而是一条分层知识加工链。用户先导入 `Source`，然后通过编译链路把资料转成 `ArticleCard`、`ConceptCard` 和概念关系，并保留 evidence backtrace；之后结合 `MethodologyCard` 和个人生成链路产出 `Artifact`，最后只有用户确认过的内容才会通过 distillation 进入 `SynthesisCard`。所以当前系统已经解决了原始资料怎么结构化、生成产物和长期知识怎么分层、证据链怎么保留、研究方法怎么显式化这四个关键问题。

#### 常见坑

- 不要把 Card、Artifact、Synthesis 讲成同一层东西。

### Q3：如果继续升级，你先改哪一层？

#### 面试官为什么问

这个问题考的是优先级判断，不是让你把所有流行词都列出来。

#### 回答思路

先讲最核心短板是“当前更像全项目上下文生成，不够 query-aware”，再给出分层升级顺序。

#### 结合 NoteWeave 怎么答

第一步先补 personal answering retrieval，把现在 `ResearchContextService + PersonalEvidenceService` 的全量装配方式升级成问题驱动的 narrowing；第二步再补 notebook 中间层；第三步才考虑 adaptive answering 和 source discovery。

#### 可直接复述的面试回答

> 如果现在继续升级，我会先改个人侧 answering retrieval，而不是先改 Artifact 产物层。当前最核心的问题，是回答当前问题时没有明确 narrowing 步骤，更像按项目把上下文全装进来再生成。所以第一步我会先把检索对象拆成 `Source chunk / ArticleCard / ConceptCard / SynthesisCard` 四层，再补一个轻量 query classifier 去判断当前问题更偏事实、总结、比较还是研究型，然后做对象级混合召回和 evidence pack。这个做完，个人链路才真正从 compile-first 升级成 query-aware，后面再补 notes 和 adaptive retrieval 才有意义。

#### 常见坑

- 不要一上来就说“先做大 Agent”。
- 不要说当前已经有完整 personal answering retrieval。

### Q4：为什么不是先做大 Agent？

#### 面试官为什么问

这是典型的风险词追问，考你是否会为了显得前沿而忽略系统的可控性。

#### 回答思路

先讲当前目标是提高 grounded answering 和研究沉淀质量，再讲开放 Agent 会带来的不确定性。

#### 结合 NoteWeave 怎么答

个人研究场景里，source 污染和错误沉淀的成本很高，所以要先把 query-aware retrieval、notebook 中间层、answering trace 和用户确认边界做稳，再考虑更强的 agentic 能力。

#### 可直接复述的面试回答

> 我不会先做大 Agent，因为个人研究场景最重要的不是“系统能不能自己多走几步”，而是回答是否 grounded、证据是否清楚、错误内容会不会污染长期知识。当前 NoteWeave 已经把 Source、Card、Artifact、Synthesis 这套分层做出来了，下一步更应该先把 query-aware retrieval、notebook 中间层和 answering trace 补稳。等这些边界清楚之后，再把 agentic 能力接在 source discovery、retrieval planning、output revision 这类位置会更合理，也更可控。

#### 常见坑

- 不要把“当前没做开放 Agent”讲成“不会做 Agent”。

## 5. 建议的升级顺序

如果面试官追问“那你具体会怎么改”，推荐按下面顺序讲：

1. 先补 Personal Answering Retrieval：
   把 `ResearchContextService + PersonalEvidenceService` 从“全量装配器”改成“问题驱动的检索入口”。
2. 再补 Notebook / Notes 中间层：
   新增用户确认过的摘录、问题、观点和中间结论，形成比 raw source 更高价值的研究上下文。
3. 再补 Adaptive / Corrective Answering：
   让系统根据问题复杂度决定是否需要 query rewrite、source expansion 或明确拒答。
4. 再补 Graph / Hierarchical Retrieval：
   利用 `ConceptCard`、`ConceptRelation`、分层摘要索引处理宏观研究问题。
5. 最后再做 Agentic Source Discovery：
   当资料不足时生成候选来源，但以 proposal + confirmation 方式引入，不让系统自动污染资料池。

## 6. 3 分钟总答版

> 我觉得 NoteWeave 当前个人链路的骨架已经是成立的，不是裸聊天，而是 `Source -> Card -> Artifact -> Synthesis` 这条分层知识加工链。它已经解决了原始资料怎么结构化、生成产物和长期知识怎么分层、证据链怎么保留、研究方法怎么显式化这几个关键问题。和 NotebookLM 这类产品相比，当前最大的差距不在“有没有 source”，而在“围绕当前问题动态组织资料并回答”这件事上还不够 query-aware。所以如果继续升级，我不会先去追一个大而全的 Agent，而会先补 personal answering retrieval、notebook 中间层和 answering trace，把个人链路从 compile-first 的受控生成，升级成围绕研究问题做 narrowing、选证据、再回答的工作台。更强的 agentic source discovery 可以作为后续扩展，但应该放在 proposal 和用户确认边界之后，而不是让系统自由入库。

## 7. 边界和不能说满的地方

- 可以坚定主讲：`Source -> Card -> Artifact -> Synthesis`、Evidence backtrace、MethodologyCard、Artifact distillation、Memory。
- 可以作为优化方向讲：query-aware retrieval、Notebook 中间层、Adaptive Answering、Graph / Hierarchical Retrieval。
- 只能作为扩展方向讲：完整 NotebookLM 能力复刻、开放式 Agent、自主 source discovery 直接入库。
