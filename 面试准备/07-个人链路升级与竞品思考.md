# NoteWeave 个人链路升级与竞品思考

这份文件只做一件事：

帮你在面试里把“我不仅做了项目，还思考过市面产品和下一步演进”讲出来。

对应的纯技术改造方案，单独放在：

- `docs/个人Wiki链路技术改造方案.md`

默认口径：

- 不吹成“我已经全做了”
- 讲成“当前链路已经做到了什么，我为什么觉得还不够，以及我会怎么升级”
- 回答粒度按 2 分钟深答准备

---

## 1. 先给面试里的总判断

如果面试官问：

“你怎么看目前市面上像 NotebookLM 这类产品？你自己的项目还能怎么升级？”

你可以先给一个总判断：

我觉得 NotebookLM 最值得参考的，不是它做了多少花哨输出，而是它把“基于资料回答”做成了一个 source-grounded 的研究工作台。它不是简单把文档切 chunk 做传统 top-k RAG，而更像是先把 source 归一化，再根据当前问题做 source narrowing 和 evidence locating，最后依托长上下文模型去生成 grounded answer，并且强绑定 citation 回到原文。  
对比之下，NoteWeave 当前个人链路的骨架已经是对的，比如 `Source -> Card -> Artifact -> Synthesis`、证据回溯、MethodologyCard、Artifact 显式 distillation 这些边界都比较清楚；但在“针对当前问题动态组织资料并回答”这件事上，还更像 compile-first 的受控生成，而不是 query-aware 的个人研究工作台。  
所以如果继续升级，我不会先追求一个大而全的 agent，而会优先补个人侧 query-aware retrieval、notebook 中间层和 answering trace，把个人链路从“基于全项目上下文生成”升级成“基于当前研究问题做 narrowing、选证据、再回答”。

这个开场很重要，因为它同时体现了：

- 你理解竞品
- 你理解自己项目
- 你不是泛泛说“我们也能做”
- 你知道真正该升级的是哪一层

## 2. 当前个人链路已经做到什么程度

你要先把自己的起点讲清楚，不然后面一说升级，容易让面试官以为你当前什么都没做。

建议口径：

我现在的个人链路不是裸聊天，而是一条分层知识加工链。用户先导入 `Source`，然后通过 `WikiCompilerService` 把资料编译成 `ArticleCard`、`ConceptCard`、`ConceptRelation`，并保留 evidence backtrace；之后通过 `MethodologyCard` 和个人生成链路去产出 `Artifact`，最后只有用户确认过的内容才会通过 distillation 进入 `SynthesisCard`。  
所以当前系统已经解决了几个关键问题：第一是原始资料怎么结构化；第二是生成产物和长期知识怎么分层；第三是证据链怎么保留；第四是研究方法怎么显式化。这个骨架我觉得是合理的，它和 NotebookLM 的差距不在“有没有 source”，而在“回答当前问题时，系统怎么动态组织这些 source”。

你心里要知道对应代码锚点：

- `SafeUrlContentFetcher`
- `WikiCompilerService`
- `ResearchContextService`
- `PersonalEvidenceService`
- `PersonalGenerationService`
- `ArtifactPlanExecutor`
- `PersonalArtifactDistillationService`

## 3. 当前链路的核心短板是什么

这里不要说得太散，面试里最稳的是抓 3 个核心问题。

### 3.1 问题一：当前更像全量上下文生成，不是 query-aware retrieval

建议讲法：

我现在个人侧最核心的短板，是上下文装配更偏“按项目把 article card、concept card、synthesis card 全拿出来，再汇总 citation 做生成”，而不是先根据当前问题做 narrowing。这样做的好处是简单稳定，但问题也很明显：不同复杂度的问题没有差异化策略，所有回答都更像基于全项目上下文的一次生成，而不是基于当前问题的自适应研究回答。

对应代码观察：

- `ResearchContextService` 是按 project 全量 load
- `PersonalEvidenceService` 是聚合 card 上挂着的 citation

### 3.2 问题二：缺少 notebook 中间层

建议讲法：

NotebookLM 一个很关键的产品点，是用户可以围绕 source 持续保存 note、提炼观点、回收回答，最后形成比 raw source 更高价值的 notebook 上下文。NoteWeave 当前有 `Source / Card / Artifact / Synthesis`，但还缺一个“用户研究过程中主动确认过的中间层”，比如 saved notes、research questions、highlighted excerpts。没有这层，系统后续 retrieval 只能从 source/card/synthesis 里拿，缺少人工精选层。

### 3.3 问题三：回答链路缺少 answering trace 和质量兜底

建议讲法：

团队侧已经有 retrieval trace 这种思路，但个人侧如果要往 NotebookLM 靠，回答能力不能只是生成结果，还要能解释“这次为什么用了这些资料、哪些论断证据不足、证据不够时该拒答还是建议补资料”。当前个人侧在这方面还偏弱，所以如果继续升级，我会补个人 answering trace 和 evidence coverage check。

## 4. 结合 NotebookLM，我会怎么升级当前个人链路

这是最核心的一段，面试里最好按“分层升级”讲，而不是甩一串技术名词。

### 4.1 第一层：把个人生成升级成 Personal Answering Retrieval

建议讲法：

第一步我会先补一个个人侧 answering retrieval 层，把现在“全项目上下文直接生成”的方式改成“先按当前问题做 narrowing，再回答”。  
具体来说，检索对象不只是一类 chunk，而是四层对象一起参与：`Source chunk`、`ArticleCard`、`ConceptCard`、`SynthesisCard`。  
事实型问题更偏 source chunk 和 concept，归纳型问题更偏 article/synthesis，比对型问题可能需要多 source、多 concept 联动。这样做完以后，个人链路才真正从 compile-first 升级成 query-aware。

你可以补一句工程落点：

这一步本质上是把 `ResearchContextService + PersonalEvidenceService` 从“全量装配器”改成“问题驱动的检索入口”。

### 4.2 第二层：补 Notebook / Notes 中间层

建议讲法：

第二步我会补 Notebook 中间层。因为个人研究里最有价值的，往往不是原始资料本身，而是用户在研究过程中确认过的摘录、问题、观点和临时结论。  
所以我会新增类似 `NotebookNote`、`SavedResponse`、`ResearchQuestion` 这类对象，让用户能把回答和材料沉淀成研究中间层。这样后面的回答就不是只依赖 raw source 和 compile cards，还能利用“用户已经确认过的研究结果”。

### 4.3 第三层：补 Adaptive / Corrective Answering

建议讲法：

第三步我会补 adaptive answering。不是所有问题都值得进复杂检索链路，所以系统应该先判断问题复杂度：简单事实问题可能单步 narrowing 就够了，比较型和研究型问题可能需要多步 retrieval。  
如果初始 retrieval 质量不够，我会借鉴 Corrective RAG 的思路，不让系统硬生成，而是先做 query rewrite、source expansion，实在不够就明确告诉用户当前材料不足。这个点我觉得比盲目追求“什么都能答”更重要，因为个人研究工具的可信度比覆盖率更关键。

### 4.4 第四层：补 Graph / Hierarchical Retrieval

建议讲法：

因为个人资料经常是长文、多 source、强概念关系场景，所以我会再补两类增强：第一类是层级摘要索引，也就是 source chunk、section summary、source summary、project summary 分层；第二类是 graph-enhanced retrieval，因为我当前已经有 `ConceptCard` 和 `ConceptRelation`，如果继续往下做，可以把它从展示关系升级成检索和摘要输入。这样回答宏观研究问题时，不需要永远从零散 chunk 拼。

### 4.5 第五层：最后再做 agentic source discovery

建议讲法：

真正到第五步，我才会做类似 NotebookLM `Discover Sources` 的能力，也就是当项目资料不足时，系统能围绕用户研究主题生成搜索子问题、拉候选来源、做相关性和去重，最后以 proposal 形式让用户确认导入。  
这里我不会让 agent 直接自动入库，因为个人研究场景里 source 污染成本很高，proposal + confirmation 的边界要保留。

## 5. 面试里怎么评价 NotebookLM，而不是变成“复读竞品”

这段很容易说飘，所以要克制。

### 稳妥版本

我觉得 NotebookLM 最强的不是“它用了什么模型”，而是它把 source-grounded answering 这件事产品化得很好。它会让用户天然感受到：回答是在我这批资料范围内做的，而且引用能直接回到原文，这种可信感非常强。  
但如果从工程角度看，我不觉得它给我们的启发是“照着做一个传统 RAG”，而是“先做 source narrowing，再做 grounded answering，再把回答回流成 notebook 中间层”。这个系统观比具体算法名更有参考价值。

### 稍强版本

我觉得 NotebookLM 给人的感觉不像典型的 vector top-k RAG，而更像 long-context model 加 source-grounding architecture。它当然有 retrieval 的味道，但重点不是从向量库捞几段 chunk，而是 notebook 范围约束、source narrowing、evidence locating 和 citation binding。  
对我自己的项目来说，这意味着升级重点不该是“换一个更强 embedding”，而是先把个人侧从全量上下文生成改成 query-aware narrowing。

## 6. 面试官问“那你具体会怎么改”时的答法

### 问法一：如果让你现在就改，你先改哪？

标准答法：

我会先改个人侧 answering retrieval，而不是先改 Artifact 产物层。因为当前最核心的问题，是回答当前问题时没有明确 narrowing 步骤。  
具体上我会先把检索对象拆成 `Source chunk / ArticleCard / ConceptCard / SynthesisCard` 四层，再补一个轻量 query classifier 去决定当前问题更偏事实、总结、比较还是研究型，然后做对象级混合召回和 evidence pack。这个做完，个人链路质量会先上一个台阶，后面再补 notes 和 adaptive retrieval 才有意义。

### 问法二：为什么不直接做 agent？

标准答法：

因为当前真正的短板不是缺一个 agent，而是缺 answering retrieval 和 notebook 中间层。如果没有这两层，agent 也只能在错误的上下文装配方式上乱规划，最后只是把系统复杂度做高了，但回答质量和可信度未必真正提升。  
所以我会先把 retrieval 和 grounding 做稳，再把 agent 放在 source discovery、retrieval planning 和 output revision 这些边界清晰的地方。

### 问法三：你这和普通 RAG 的区别是什么？

标准答法：

普通 RAG 更像“文档切片后查 top-k 再生成”，而我想升级后的个人链路会更像“personal research answering system”。  
它的区别在于：第一，检索对象不只是 chunk，还有 card、concept、synthesis、后续的 note；第二，它会根据当前问题动态决定怎么 narrowing；第三，它的回答必须带 evidence trace 和 citation binding；第四，它允许回答结果回流成 notebook 中间层，变成后续研究上下文。

---

## 7. 最适合你在面试里主动抛出的升级观点

如果面试官让你自由发挥，你最值得主动抛的不是“我要做大 agent”，而是下面这 5 个观点：

1. 当前个人链路最大的短板不是没有 LLM，而是没有 query-aware narrowing。
2. NotebookLM 最值得学的是 source-grounded answering，不是它那些花样输出。
3. 个人研究场景必须有 notebook 中间层，否则回答无法沉淀成更高价值上下文。
4. 比起盲目提高回答覆盖率，更重要的是 evidence coverage、citation binding 和材料不足时的兜底策略。
5. agent 应该放在 source discovery、retrieval planning、output revision 这些边界清晰的位置，而不是一开始就做万能编排。

## 8. 一段可以直接背的 2 分钟答案

Q: 你怎么看 NotebookLM 这类产品，对你当前个人链路有什么启发？

A:
我觉得 NotebookLM 最值得参考的，不是它做了多少表层功能，而是它把“基于资料回答”做成了一个 source-grounded 的研究工作台。它给人的感觉不像典型的 top-k chunk RAG，而更像先把 source 归一化，再根据当前问题做 source narrowing 和 evidence locating，最后依托长上下文模型生成 grounded answer，并且强绑定 citation 回到原文。  
对比之下，我当前个人链路的骨架其实已经有了，像 `Source -> Card -> Artifact -> Synthesis`、证据回溯、MethodologyCard、Artifact 显式 distillation 这些边界都是清楚的，所以我不觉得问题在于“还没做个人研究系统”，而在于“还没把它做成 query-aware 的 answering system”。  
如果继续升级，我不会先去追一个大而全的 agent，而会先做三件事。第一，把 `ResearchContextService + PersonalEvidenceService` 从全量装配改成问题驱动的 retrieval 层，让 `Source chunk / ArticleCard / ConceptCard / SynthesisCard` 共同参与 narrowing。第二，补一个 notebook 中间层，把用户确认过的摘录、问题和 saved responses 沉淀下来，形成比 raw source 更高价值的研究上下文。第三，再补 adaptive/corrective answering，也就是证据不够时先做 query rewrite、source expansion，实在不够就明确告诉用户材料不足。  
我觉得这样升级之后，个人链路就不是“基于全项目上下文生成一篇东西”，而更接近一个真正的个人研究工作台，这也是我从 NotebookLM 身上学到的最重要的一点。
