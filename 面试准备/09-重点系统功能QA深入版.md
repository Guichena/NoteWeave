# NoteWeave 重点系统功能 QA 深入版

> 本文件为 2026-06-01 重构版，依据当前代码、测试和 Flyway 迁移整理。不要再按旧阶段计划或旧题库口径背。

## 0. 使用方式
本文件不再按模块单独列题，而是把相似追问合并成题组。面试时先判断问题属于哪一组，再从共性设计切入，最后落到 NoteWeave 的具体代码链路。

统一答题顺序：

1. 共性问题：这一类追问到底在考什么。
2. 当前方案：NoteWeave 如何实现。
3. 失败处理：坏了、重试、删除、断线、越权时怎么办。
4. 验证方式：看哪些日志、trace、测试或指标。
5. 边界口径：哪些不能说满。

## 1. 边界与隔离类问题

### 放在一组的问题
- 为什么要区分 TEAM 和 PERSONAL？
- systemRole 和 SpaceMember.role 为什么分开？
- Citation、Artifact、Wiki、Memory 为什么都要重新校验权限？
- Bilibili MCP、URL Source、上传文件这些外部输入如何避免污染系统？
- Admin 能不能直接查看用户私有资料？

### 组合深答
这类问题本质都在考“AI 系统会不会串数据”。NoteWeave 的第一层边界是 Space：TEAM 承载团队知识库、RAG Chat、Wiki、Graph、Admin/Ops 可见资源；PERSONAL 承载 ResearchProject、Source、Card、Artifact、Synthesis、个人 Memory。第二层边界是角色：systemRole 只表示平台管理身份，SpaceMember.role 才表示某个团队空间里的 OWNER/EDITOR/VIEWER。第三层边界是资源读取：Citation 返回、Artifact 详情、Wiki 发布、Memory 写入、MCP 工具结果进入 Artifact 时，都不能绕过 space/user 归属。

外部输入要特别讲清楚：Bilibili MCP 只是提供工具上下文，URL Source 只是个人研究来源，上传文件只是团队知识源，它们都不能直接写长期 Wiki、Memory 或 ConceptCard。要进入长期知识，必须经过 Artifact/Wiki/Synthesis 的确认或自动维护边界。

### 追问压法
- 如果 citation 指向用户已经无权访问的文档怎么办？
- 如果 Admin 想排查坏答案，看到的是原文、摘要还是脱敏 trace？
- 如果 Bilibili 工具返回恶意内容，会不会变成系统指令？
- 如果团队成员被移出 Space，历史 Artifact 还能不能看？

### 不能说满
- 不要说 Admin 可以无边界看所有私有内容。
- 不要说工具结果或模型输出会自动进入长期知识。
- 不要说只靠 Controller 校验一次就够。

## 2. 一致性、异步与重试类问题

### 放在一组的问题
- 为什么不用同步接口直接做解析、索引、生成、评测？
- 为什么业务事务里不直接发 Kafka？
- Worker 重复消费怎么幂等？
- WIKI_INDEX、RAG_EVAL_RUN、CLEANUP_RESOURCE、ARTIFACT_GENERATE 失败怎么重试？
- Admin 重试任务为什么要先校验目标对象？

### 组合深答
这类问题本质是在考“长任务怎么可靠执行”。NoteWeave 把文档解析、Source 编译、Artifact 生成、Wiki 索引、RAG Eval、资源清理都统一到 Task/Outbox/Kafka/Worker。业务事务先写 Task 和 TaskOutbox，事务提交后由调度器投递 Kafka；Consumer 拿到消息后只信 taskId，再回查 MySQL 的 Task 状态和业务目标。Worker 执行时记录 TaskAttempt、TaskEvent、失败原因、取消状态和进度。

新增特性也复用这套骨架：Bilibili MCP 失败会体现在 ARTIFACT_GENERATE 的 LoadMcpToolContextSkill；AutoWikiMaintenance 生成页面后仍走 WIKI_INDEX；RAG Eval 独立走 RAG_EVAL_RUN；cleanup 走 CLEANUP_RESOURCE。AdminTaskRetryValidator 会按任务类型检查目标是否还存在，例如 Document 对象是否还在 MinIO、Source 是否 READY、Wiki 是否 PUBLISHED、RagEvalRun 是否存在。

### 追问压法
- Kafka 已投递但 Worker 执行失败，系统如何恢复？
- Kafka 短暂不可用，业务接口应该失败还是返回任务已创建？
- 自动 Wiki 生成成功但索引失败，用户看到什么状态？
- Bilibili MCP 远程服务超时，任务和 Skill 日志怎么记录？

### 不能说满
- 不要说 Kafka 保证业务幂等。
- 不要说所有失败都能自动恢复。
- 不要把 Redis 说成主任务队列。

## 3. 证据、检索与防幻觉类问题

### 放在一组的问题
- 为什么做 Hybrid RAG？
- BM25、向量、Wiki recall、Weighted RRF 各解决什么问题？
- EvidencePostProcessor 为什么不能省？
- Citation 和 RetrievalTrace 各有什么价值？
- RAG Eval 怎么验证效果？

### 组合深答
这类问题本质是在考“模型回答为什么可信”。NoteWeave 的 RAG 先做 Space/KnowledgeBase 权限过滤，再做 BM25、向量、Wiki recall 多路召回。BM25 擅长精确关键词和标题，向量擅长语义相似，Wiki recall 擅长团队长期确认知识。Weighted RRF 用排序融合避免单一路径漏召回，EvidencePostProcessor 再做去重、相邻合并、每文档限流和上下文截断，最后 TeamRagPromptBuilder 要求模型基于证据回答，CitationService 和 RetrievalTrace 保存证据关系和召回过程。

新增能力要自然融进去：AutoWikiMaintenance 能把文档或个人 Source 同步成 WikiPage，进入 Wiki recall；Bilibili MCP 不是团队 RAG 证据源，而是 Artifact 生成的外部上下文；RAG Eval 是隔离评测链路，用 eval case/run/result、trace、LLM log 验证 recall、citation coverage 和 prompt 版本差异。

### 追问压法
- 如果模型引用不准，先查 Citation 还是 RetrievalTrace？
- 如果向量召回挂了，能否降级 BM25/Wiki？
- 如果 Wiki recall 召回了过期页面，如何以 DB 状态为准？
- 如果没有证据，为什么不能让模型自由发挥？

### 不能说满
- 不要说 RAG 能完全消灭幻觉。
- 不要把 Bilibili MCP 的工具上下文说成已入库知识库证据。
- 不要编造 recall@k、MRR、线上准确率。

## 4. 生成、沉淀与长期知识类问题

### 放在一组的问题
- Artifact 为什么独立于 ChatMessage？
- ArtifactVersion、ArtifactSource、ArtifactCitation 解决什么问题？
- MethodologyCard 为什么不写死在 prompt 里？
- Artifact、Wiki、SynthesisCard、Memory 的边界是什么？
- 为什么用户确认后才能沉淀长期知识？

### 组合深答
这类问题本质是在考“AI 生成内容如何从草稿变成可信知识”。NoteWeave 把 ChatMessage 当交互过程，把 Artifact 当可版本化产物，把 Wiki 当团队长期知识，把 SynthesisCard 当个人确认后的综合沉淀，把 Memory 当会话和用户偏好的长期上下文。它们不能混在一起：Artifact 可以重生成和导出，但默认不自动污染 Wiki；Wiki 需要草稿、发布、版本和 WIKI_INDEX；SynthesisCard 要 proposal/confirm，并绑定具体 artifactVersionId；Memory 要区分 DRAFT/FORMAL 并经过过滤。

MethodologyCard 是新增重点。它把 workflow、outputStructure、qualityChecklist 做成 PRESET/SPACE/PROJECT 作用域的方法论，而不是硬编码在 prompt 里。Bilibili MCP 或 Source/Card 提供材料，Methodology 决定输出结构，ArtifactPlanExecutor 通过 Skill 步骤把它们合成产物。

### 追问压法
- 为什么不直接把 Artifact 写进 ConceptCard？
- 如果生成结果没有 citation，能不能沉淀？
- MethodologyCard 是不是模型训练或 RL？
- SynthesisCard 绑定 artifactVersionId 有什么价值？

### 不能说满
- 不要说生成结果自动进入知识库。
- 不要把 MethodologyCard 说成模型训练。
- 不要说当前已经有复杂审批流。

## 5. 外部工具、MCP 与 Agent 边界类问题

### 放在一组的问题
- Bilibili MCP 具体怎么落地？
- 本地/远程 MCP 工具为什么都支持？
- `/mcp bilibili` 和 `/artifact` 聊天命令怎么进入任务链路？
- Skill 是不是 Agent？
- 如果未来要做 Agent，还缺什么？

### 组合深答
这类问题本质是在考“你有没有把潮流词说过头”。NoteWeave 当前有受控工具扩展路径：StudioMcpToolRegistry 解析参数，本地模式走 LocalBilibiliMcpToolService，远程模式走 RemoteBilibiliMcpToolService 调 `/api/v1/mcp/bilibili/invoke`，聊天里 `/mcp bilibili <url>` 会由 StudioMcpChatTriggerService 创建 ARTIFACT_GENERATE 任务。工具结果作为 `MCP Tool Context (bilibili)` 进入 Artifact prompt，后续仍走 SkillExecutionLog、ArtifactVersion、ArtifactSource、ArtifactCitation。

Skill 也要讲稳：ArtifactPlanExecutor 的 Skill 是受控生成步骤，例如 LoadGenerationContext、LoadMcpToolContext、SelectEvidence、GenerateReport、SaveArtifact。它具备 Agent 化地基，但不是完全自主 Agent，因为没有开放规划器、任意工具调用、沙箱、预算、回滚和自动执行闭环。

### 追问压法
- 远程 MCP 服务超时或返回空上下文怎么办？
- 为什么工具结果不能直接写数据库？
- 如果模型想调用未注册工具，系统怎么处理？
- 为什么不让模型自己决定要不要发 Wiki、写 Memory？

### 不能说满
- 不要说完整 MCP marketplace 已实现。
- 不要说所有工具调用都基于 MCP。
- 不要说当前是完全自主多 Agent 平台。

## 6. 自动化、人工确认与可控性类问题

### 放在一组的问题
- AutoWikiMaintenance 会不会替代人工 Wiki？
- 自动 Wiki 如何避免反复刷新或污染长期知识？
- Wiki Graph 和完整 GraphRAG 有什么区别？
- 自动化生成和人工确认的边界在哪里？

### 组合深答
这类问题本质是在考“自动化有没有失控”。AutoWikiMaintenance 可以从已处理 Document 或个人 Source 自动同步 WikiPage，计算 sourceFingerprint 判断是否需要刷新，创建 WikiPageVersion、WikiPageCitation、WIKI_INDEX 任务，并触发 WikiGraphSyncService 重建空间图谱。它适合做长期知识初稿、索引入口和图谱节点，但不能替代人工确认、编辑和质量判断。

Wiki Graph 也要讲边界：它表达 Wiki 页面、链接、关系、未解析链接等结构，WikiRetriever 可以把 Wiki 作为 Hybrid RAG 的一路召回；但完整 GraphRAG 还需要实体抽取、路径推理、社区摘要等更复杂主链路。

### 追问压法
- sourceFingerprint 如何避免自动页面无限刷新？
- 自动 Wiki 里的 citation 怎么维护？
- Wiki 链接指向不存在页面怎么办？
- 图谱关系错了怎么修？

### 不能说满
- 不要说 AutoWikiMaintenance 能替代人工知识治理。
- 不要把 Wiki Graph 说成完整 GraphRAG。
- 不要说自动生成内容天然可信。

## 7. 可观测、评测与运维类问题

### 放在一组的问题
- 一次坏答案如何排查？
- PromptVersion、LLMCallLog、RetrievalTrace、AnswerFeedback 各有什么用？
- RAG Eval 为什么不能污染正式会话？
- cleanup scan/execute 为什么拆两步？
- health 和 audit 在 AI 项目里为什么重要？
- 怎么证明异步、RAG、WebSocket、外部工具这些链路真的经过验证？

### 组合深答
这类问题本质是在考“项目是不是只能 Demo”。NoteWeave 通过 PromptVersion 管提示词版本，通过 LLMCallLog 记录模型调用，通过 RetrievalTrace 记录召回，通过 Citation 关联证据，通过 AnswerFeedback 收集用户反馈，通过 RAG Eval 做隔离评测，通过 AdminTask 支持取消/重试/标记失败，通过 cleanup scan/execute 管资源残留，通过 health 看 MySQL、Redis、MinIO、Kafka、ES、LLM provider，通过 audit 记录关键操作。

排查坏答案时，不要只说看日志。要沿链路查：用户问题和 Space scope、RetrievalTrace 的召回源、EvidencePostProcessor 是否截断、PromptVersion、LLMCallLog、Citation 指向、AnswerFeedback，最后把样本沉淀到 RAG Eval。

如果面试官继续追问“你怎么证明不是纸上谈兵”，要把验证也按层讲：RRF、EvidencePostProcessor、PromptBuilder、SafeUrlContentFetcher、MethodologyMatcher 这类纯逻辑用单元测试；上传、文档处理、RAG、Memory、MCP、Admin/Ops 这类跨组件链路用 MockMvc + ContainerizedIntegrationTest，把 MySQL、Redis、Kafka、MinIO、Elasticsearch 跑起来验证状态落库、消息投递、对象存储和索引读模型；异步任务重点断言 TaskAttempt、TaskEvent、TaskOutbox、业务表副作用和重试/取消边界；RAG 还要用 RetrievalTrace、Citation、LLMCallLog、RAG Eval 做回归样本。

### 追问压法
- 用户说引用不准，先查哪几张表或哪几个服务？
- RAG Eval 的样本从哪里来，如何避免污染 Memory？
- cleanup 为什么不能直接删除 MinIO 对象？
- 如果没有生产指标，如何诚实说明验证方式？
- 如果集成测试通过了，为什么仍然不能说已经有生产级压测？

### 不能说满
- 不要编造线上 QPS、P99、准确率。
- 不要说 RAG Eval 等于线上 A/B。
- 不要让普通用户访问全局运维日志。
- 不要把本地/容器化集成测试等同于真实线上稳定性数据。

## 8. 表结构、索引与中间件设计类问题

### 放在一组的问题
- 这个项目核心表结构怎么设计？
- 为什么不用一张大 JSON 表保存 Chat、Citation、Trace、Artifact？
- MySQL、Redis、MinIO、ES、Kafka 分别承担什么职责？
- 为什么 `space_id/status`、`task_type/task_status`、`document_id/index_version` 这些索引重要？
- ES 和 MySQL 不一致、MinIO 残留、Kafka 重复消费、Redis 丢运行态分别怎么处理？

### 组合深答
这类问题本质是在考“你是不是真的设计过系统状态”。NoteWeave 的表结构按生命周期拆：`users/space/space_member` 管身份和边界，`task/task_attempt/task_event/task_outbox` 管异步状态，`knowledge_base/document_upload/file_object/document/document_chunk` 管资料摄取，`chat_session/chat_message/citation/message_citation/retrieval_trace/llm_call_log/answer_feedback` 管问答和证据，`artifact/artifact_version/artifact_source/artifact_citation` 管生成产物，`methodology_card` 管生成方法论配置，`wiki_page/wiki_page_version/wiki_page_citation/wiki_page_link` 管团队长期知识，`artifact_distillation_proposal/synthesis_card/memory_item/rag_eval_result/audit_log` 管个人沉淀、评测和运维。

中间件也按数据形态分层：MySQL 是最终事实源；Redis 只存 `chat:ws-ticket:*`、`chat:{sessionId}:runtime/short_term/stream/events`、`upload:{uploadId}` 这类短期状态；MinIO 存上传分片、原文件、解析文本、citation snapshot；ES 存 document chunk、向量索引和 Wiki 索引；Kafka 只做任务触发，业务 exactly-once 要靠 Task 状态、幂等键和业务约束。表和中间件不是孤立知识点，要和权限、版本、任务、证据、cleanup 串起来讲。

### 追问压法
- 为什么当前迁移里很少显式 foreign key？
- `citation`、`retrieval_trace_item`、`llm_call_log` 为什么要分开？
- `artifact_version` 和 `wiki_page_version` 为什么都有唯一版本号？
- Kafka topic 如果投递重复，哪些表保证幂等？
- 如果 ES 还能搜到软删除文档，怎么通过 MySQL 和索引版本兜底？

### 不能说满
- 不要说当前已经做了分库分表、读写分离或多活。
- 不要说 Redis/ES/Kafka 能替代 MySQL 事实源。
- 不要说 object_key、ES doc、Kafka message 本身就是权限凭证或业务事实。

## 9. 性能、扩展与降级类问题

### 放在一组的问题
- 文档量、Wiki 页面、Artifact 任务、RAG Eval 增长后哪里先成为瓶颈？
- Bilibili MCP 慢怎么办？
- Kafka backlog 怎么排查？
- ES、MinIO、LLM provider 挂了如何降级？
- 未来要拆服务，先拆哪条边界？

### 组合深答
这类问题本质是在考“有没有真实工程判断”。不要编造压测结果，要按链路说瓶颈：上传看 MinIO、分片和解析 Worker；检索看 ES query、RRF、EvidencePostProcessor；生成看 LLM 超时、prompt 长度、Methodology/MCP 上下文；任务看 Kafka backlog、Worker 并发、DB 锁；Wiki 看 WIKI_INDEX 和 graph rebuild；Eval 看批量 LLM 调用；WebSocket 看连接数、Redis runtime 和消息序列。

降级要按组件职责讲：MySQL 挂核心业务不可用；Redis 挂影响短期 runtime 但正式结果仍在 DB；MinIO 挂影响对象读取和解析；ES 挂时 RAG 不应无证据编造；Kafka 挂时 Outbox 可积压；LLM/MCP 挂时生成任务失败并记录原因。

### 追问压法
- Bilibili MCP 如何做超时、缓存和限流？
- AutoWikiMaintenance 是否会拖慢文档解析？
- RAG Eval 如何低峰执行，避免影响正式问答？
- 如果要先拆服务，是拆 remote MCP、LLM 调用、索引 Worker 还是 Admin/Ops？

### 不能说满
- 不要说已验证生产级高并发。
- 不要把单体项目包装成微服务已落地。
- 不要说所有组件都有完美降级。
