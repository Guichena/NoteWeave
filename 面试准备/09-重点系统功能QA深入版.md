## 0. 本篇定位

这份文档按“重点系统功能”来组织 NoteWeave 的面试讲法，参考 Austin 通知平台那种连续深挖风格，但不照搬通知平台的事务通知、RabbitMQ、渠道发送、滑动窗口去重口径。

```text
空间权限
-> 异步任务
-> 文档摄取
-> Hybrid RAG
-> Citation / Trace

-> 个人研究链路

-> Memory
```

## 2. 先把 Austin 主线替换成 NoteWeave 主线

Austin 通知平台可以按“可靠触达”讲，NoteWeave 要按“可信知识生产闭环”讲。

| Austin 通知平台主线 | NoteWeave 对应主线 |
|---|---|
| 消息从入口到发送成功 | 知识从资料进入系统，到检索引用、生成成果、沉淀为长期知识 |
| 可靠通知 | 可靠知识摄取、可追溯回答、可恢复生成任务 |
| 消息状态机 | `Task + Attempt + Event + Outbox + Kafka + Worker` |
| RabbitMQ 异步发送 | Kafka 承载统一后台任务执行 |
| traceId / 锚点日志 | `RetrievalTrace`、`LLMCallLog`、`TaskEvent`、`Citation`、`AuditLog` |
| 去重、限流、死信、补偿 | 权限过滤、任务幂等、重试取消、索引版本切换、无证据兜底、清理任务 |
| 渠道成功不等于用户收到 | LLM 回答不等于事实正确，必须有证据、引用和评测 |

面试时可以这样收口：

> Austin 的核心是把通知发送治理成可追踪、可补偿的消息链路。NoteWeave 的核心是把知识生产治理成可权限隔离、可检索、可引用、可评测、可沉淀的闭环。两者都不是简单调中间件，而是在业务链路上设计状态、幂等、失败恢复和可观测。

## 2. 总体功能与项目定位

### Q1：从重点系统功能角度，怎么介绍 NoteWeave？

**答：**

NoteWeave 是一个面向团队知识协作和个人研究沉淀的 AI 知识工作台。它不是只做一次性的 RAG 问答，而是把资料进入系统、被解析索引、被检索引用、生成结构化成果，再沉淀成 Wiki 或个人知识卡片这一整条链路做成闭环。

从系统功能上，我会分成三层讲。

第一层是基础治理能力，包括认证、`TEAM / PERSONAL` 双空间、成员角色、资源权限、统一 API 响应和后台任务模型。这个层负责保证后面所有知识、会话、引用和成果都有清晰的归属边界。

第二层是知识处理主链路。团队侧是 `KnowledgeBase -> DocumentUpload -> Document -> DocumentChunk -> Hybrid Retrieval -> Citation -> Chat / Wiki`；个人侧是 `ResearchProject -> Source -> ArticleCard / ConceptCard -> Artifact -> SynthesisCard`。也就是说，团队侧偏共享知识库和证据问答，个人侧偏研究资料整理、卡片化和成果生成。

第三层是可运营能力，包括 `TaskEvent`、`RetrievalTrace`、`LLMCallLog`、`AnswerFeedback`、`RagEvalRun`、`SystemHealth`、`Cleanup` 和 `AuditLog`。这些能力让它不是一个黑盒 AI demo，而是可以追踪一次回答为什么这么答、检索了什么、用了哪个 Prompt、任务失败在哪里、资源是否需要清理。

**追问：一句话总结呢？**

一句话就是：NoteWeave 是一个权限感知、证据优先、可观测的 AI 知识工作台，核心价值是把团队资料和个人研究从“散落文件”变成“可检索、可引用、可生成、可沉淀”的知识闭环。

### Q2：这个项目最大的系统难点是什么？

**答：**

最大的难点不是接一个 LLM 接口，也不是写一个文档上传接口，而是把 AI 知识工作台做成一条“可信知识生产链路”。

这个链路里同时有几个问题。第一，权限问题，团队知识、个人研究、Artifact、Citation、Memory 不能互相越权。第二，一致性问题，上传、解析、索引、生成、评测和清理都是长任务，不能每个模块各写一套异步模型。第三，可信度问题，RAG 回答必须能回到具体证据，而不是把引用塞进一段 JSON 里糊弄过去。第四，运行态问题，WebSocket 流式输出有 stop、resume、DRAFT / FORMAL 生命周期，和普通 HTTP 请求不是一回事。第五，运营问题，AI 系统出错后不能只说“模型不稳定”，要能看 Prompt、Trace、Citation、LLM 日志、Eval 和任务状态。

所以我会把最大难点总结成：如何让一个 AI 知识应用从“能回答”升级为“权限清楚、证据可查、任务可恢复、输出可沉淀、问题可排查”的系统。

**追问：如果只能讲一个最有含金量的点呢？**

我会讲 Evidence-first RAG 和可观测闭环。因为普通 RAG demo 很容易做到“召回几段文本然后问模型”，但 NoteWeave 更强调检索前后的权限过滤、BM25/向量/Wiki 多路召回、Weighted RRF 融合、EvidencePostProcessor、Citation 关系表、RetrievalTrace、LLMCallLog 和反馈评测。这个链路能解释一次回答的来源和失败原因，更接近真实系统。

### Q3：为什么说它不是普通 RAG demo？

**答：**

普通 RAG demo 通常只有上传、切片、向量检索、拼 Prompt、问模型这几个步骤。NoteWeave 的区别在于它围绕“知识工作台”做了更多系统边界。

第一，它有空间和权限边界。`TEAM` 和 `PERSONAL` 是一级业务容器，团队资源按成员角色访问，个人资源默认 owner-only。检索、Citation 查询、Artifact、Memory 都要回到这个边界。

第二，它有统一异步底座。文档解析、Source 导入、Source 编译、Artifact 生成、Wiki 入索引、Embedding backfill、RAG Eval、Cleanup 都复用 `Task + Outbox + Kafka + Worker`，而不是散落在各自模块里。

第三，它有证据链和可观测。回答不只是文本，还会保存 `Citation`、`message_citation`、`RetrievalTrace`、`LLMCallLog` 和 `AnswerFeedback`，管理员还能做 Eval run 来评估 recall、MRR、citationCoverage 等指标。

第四，它有知识沉淀。团队侧可以把稳定内容发布为 Wiki，个人侧可以把 Artifact 确认沉淀为 SynthesisCard。生成内容默认不直接污染长期知识，必须经过确认。

**追问：那如果面试官说“你不就是套了 RAG 吗”？**

可以回答：RAG 是其中一条能力链，但项目重点不是“调用模型回答问题”，而是围绕 RAG 做权限约束、异步摄取、索引版本、一致性、引用追溯、运行态恢复、评测和运维。真正工程化的部分在 RAG 前后的系统治理。

### Q4：高并发、高可靠、高可用、功能难点四类怎么映射到 NoteWeave？

**答：**

这四类不能空讲，要落到项目真实能力上。

高并发可以讲上传和任务削峰。大文件上传支持分片、断点续传和 merge；解析、索引、生成、评测、清理都进入 Kafka Worker，不让用户请求同步等待长任务。检索侧通过 Elasticsearch 承担 BM25 / vector / wiki recall，不把全文检索压到 MySQL。

高可靠可以讲任务状态收敛。业务写入和消息投递通过 outbox 解耦，Worker 执行写 `TaskAttempt` 和 `TaskEvent`，失败可以 retry、cancel、mark failed，长任务统一有状态和错误原因。

高可用可以讲降级和隔离。向量检索失败时可以降级 BM25；DRAFT 会话不写长期 Memory，避免污染；清理任务先 scan 再 execute，避免误删；Admin 健康检查按 MySQL、Redis、MinIO、Kafka、Elasticsearch、LLM Provider 拆开。

功能难点可以讲可信知识闭环。团队侧从上传到 Citation 问答再到 Wiki，个人侧从 Source 到 Card 再到 Artifact 和 Synthesis，每一步都有证据和权限边界。

**边界：**

不要说已经有真实生产压测数据，也不要说已经做了微服务级高可用部署。可以说项目具备本地可验证的系统设计和可观测入口，真实生产 SLA 需要压测和线上监控数据支撑。

## 3. 空间、权限与资源边界

### Q5：为什么要把 `TEAM` 和 `PERSONAL` 做成一级空间？

**答：**

因为团队知识协作和个人研究沉淀的权限、生命周期和知识沉淀方式不一样。

团队侧的重点是共享知识库、团队 Chat、团队 Wiki、团队 Artifact 和成员协作。这里需要 `SpaceMember.role` 来区分 `OWNER / EDITOR / VIEWER`，比如 Viewer 可以问答但不能上传文档或发布 Wiki。

个人侧的重点是 ResearchProject、Source、ArticleCard、ConceptCard、SynthesisCard、个人 Artifact 和 UserMemory。这些内容默认只有 owner 能访问，因为个人研究里可能包含草稿、偏好、未公开资料和临时结论。

所以 `Space` 不是简单的文件夹，而是后续知识、任务、引用、会话、记忆和成果的最高隔离边界。

**追问：为什么不只用 userId 和 teamId 两个字段？**

这样会让后续模块不断分叉。比如 ChatSession、Artifact、Memory、Citation、Task 都同时需要归属团队或个人，如果每个模块都自己判断 userId/teamId，权限逻辑会很散。统一成 `Space` 后，资源访问都可以回到 `spaceId + spaceType + membership`，系统边界更稳定。

**实现兜底锚点：**

- `Space`
- `SpaceMember`
- `SpacePermissionService`
- `ResourceAccessService`
- `SpaceControllerTest`
- `SpacePermissionServiceTest`

### Q6：`users.system_role` 和 `SpaceMember.role` 为什么要分开？

**答：**

这两个角色解决的问题不同。

`users.system_role` 是系统后台权限，比如 ADMIN 能访问 `/api/v1/admin/**`，查看系统健康、任务、用户、审计日志、RAG Eval 和清理任务。

`SpaceMember.role` 是某个团队空间内的业务角色，比如 OWNER 可以管理成员和发布内容，EDITOR 可以上传和编辑，VIEWER 只能查看和问答。

如果把两者混在一起，会出现权限语义混乱。比如一个团队 OWNER 不应该天然拥有全系统 Admin 权限，一个系统 Admin 也不应该被当成某个团队空间的知识 owner。

**追问：Admin 能不能看所有用户个人研究？**

当前面试口径不要夸大。Admin 主要用于系统管理、健康、任务、日志、评测和清理，不要讲成可以随意读取所有个人私密知识。涉及敏感日志和 Prompt 时，也要强调脱敏和权限边界。

### Q7：资源访问为什么不能只在接口入口判断一次？

**答：**

因为 NoteWeave 的资源是链式关联的。一次问答可能从 ChatSession 关联到 Space，再到 KnowledgeBase、DocumentChunk、Citation、Snapshot；一次 Artifact 可能关联 Source、Card、Citation、MethodologyCard；一次 Admin 查询也可能跨任务、用户、空间。

如果只在接口入口按 id 判断一次，很容易出现后续链路绕过权限的问题。更稳的方式是关键资源读取时都回到统一资源访问校验或模块内权限服务做二次确认。

典型例子是 Citation 查询。即使用户能看到某条 message，也不能直接把 citationId 返回出去，而要根据 Citation 的 `spaceId / sourceType / sourceId` 回查资源所属空间，确认当前用户仍然有权限。

**追问：检索时权限怎么保证？**

检索前，ES 查询会带 `spaceId / knowledgeBaseId / status` 等 filter；检索后，还会通过 MySQL 校验文档状态、删除状态和 activeIndexVersion。也就是前置过滤加后置校验，避免索引滞后导致越权或召回脏数据。

## 4. 统一异步任务、Outbox 与 Kafka

### Q8：为什么要统一成 `Task + Outbox + Kafka + Worker`？

**答：**

因为 NoteWeave 里很多核心操作都是长任务或易失败任务。如果每个模块各写一套后台执行逻辑，后续重试、取消、进度、错误排查和 Admin 管理都会碎掉。

统一任务模型后，文档解析、Source 导入、Source 编译、Artifact 生成、Wiki 入索引、Embedding backfill、RAG Eval、资源清理都可以用同一套生命周期：

```text
创建 Task
-> 写 TaskOutbox
-> Kafka 投递
-> Worker 回查 Task 状态
-> 写 TaskAttempt / TaskEvent
-> 成功、失败、取消或重试
```

这样做的收益是：用户请求可以快速返回 taskId；后台任务有统一状态；失败有统一错误记录；Admin 可以统一查看、取消、重试和 mark failed；后续新增长任务也不用重新设计一套执行框架。

**追问：这和 Austin 的可靠通知有什么相似？**

Austin 里消息任务进入 MQ 后，通过状态机、重试、死信和补偿让发送链路收敛。NoteWeave 这里不是通知发送，而是知识处理任务。相似点是都接受异步中间态，并用状态、幂等、事件和补偿让任务最终收敛。

- `TaskServiceIntegrationTest`

### Q9：为什么不在业务事务里直接发 Kafka？

**答：**

直接发 Kafka 最大的问题是业务 DB 写入和消息投递很难放在一个强事务里。

比如上传 merge 成功后，需要创建 Document、绑定 FileObject、创建 Task，然后让 Worker 去解析。如果 DB 已提交但 Kafka 发送失败，任务就没人执行；如果 Kafka 发出去了但 DB 回滚，Worker 拿到 taskId 又查不到任务。

Outbox 的思路是：业务事务内只写本地数据库，包括业务状态和 `task_outbox`。事务提交后再由 dispatcher 把 outbox 消息投递到 Kafka。投递失败不会让业务数据回滚，而是保留 outbox 为 PENDING 或 FAILED，后续可以补偿投递。

**追问：Outbox 发送成功是否代表任务成功？**

不代表。Outbox 发送成功只代表任务进入异步执行链路，后面还要看 Kafka 消费、Worker 执行、任务状态和结果写回。面试时要区分 DB 创建成功、Kafka 投递成功、Worker 执行成功和业务结果成功。

### Q10：后台任务长时间没有结果怎么办？

**答：**

先根据 `task_status`、`task_attempt` 和 `task_event` 定位它卡在哪里。

如果任务还在 PENDING，要看 outbox 是否已投递、Kafka 是否正常、dispatcher 是否工作。如果任务 RUNNING 很久，要看 Worker 是否超时、是否支持 cancel safe point、外部依赖是否卡住。如果任务 FAILED，要看错误类型，是临时依赖故障、参数错误、对象不存在，还是代码逻辑问题。如果是清理、评测、生成这类任务，还要看关联资源是否已经变更。

处理方式上，不能简单“看到没成功就重跑”。要先查任务当前状态，再按任务类型决定是否 retry、cancel、mark failed 或人工修复。Admin 侧已经提供任务查询、事件查询、取消、重试和 mark failed 入口。

**追问：重试怎么避免重复副作用？**

依赖三层控制。第一是 task 的 `idempotency_key`，避免重复创建相同任务。第二是 Worker 执行前回查 DB 状态，只有允许执行的状态才推进。第三是具体业务表要有唯一约束或版本约束，比如 DocumentChunk 按 `documentId + indexVersion + chunkIndex` 去重，ArtifactVersion 按版本号追踪，不直接覆盖历史。

### Q11：任务取消和 stop 是一回事吗？

**答：**

不是。

Task cancel 是后台任务生命周期控制，比如文档解析、Artifact 生成、Eval、Cleanup 这种任务可以通过 `cancel_requested` 通知 Worker 在安全点停止。

WebSocket stop 是会话运行态控制，用户在流式输出中要求停止当前回答。它会通过 `ActiveExecutionRegistry` 标记当前执行停止，停止继续推送 delta，并保留 partialContent 和 runtime state，便于恢复。

两者都体现了“长任务不能只靠同步请求等待”，但作用层不同：Task cancel 面向后台任务，chat stop 面向实时会话执行。

## 5. 团队知识库上传、解析与索引

### Q12：团队文档从上传到可检索的完整链路是什么？

**答：**

团队文档链路可以分成上传、合并、任务投递、解析、切片、索引几个阶段。

用户先在某个 TEAM Space 的 KnowledgeBase 下初始化上传，服务端创建 `DocumentUpload`，记录 fileMd5、文件名、大小、chunkSize、totalChunks 等信息。分片上传时，分片对象写入 MinIO，并通过 `UploadBitmapService` 在 Redis 里记录已上传块。上传完成后 merge，服务端把分片合并成最终对象，按 `spaceId + contentHash` 查找或创建 `FileObject`，再创建 `Document` 和 `DOCUMENT_PROCESS` Task。

后台 Worker 消费任务后，用 `DocumentParserService` 解析 PDF、Markdown、TXT 等文本，保存 parsed text，再通过 `ChunkService` 切成 `DocumentChunk`。最后 `VectorIndexerService` 把 chunk 写入 Elasticsearch，并更新 document 的 activeIndexVersion。检索时只召回当前 activeIndexVersion 且未删除、未归档的文档。

**追问：为什么上传要异步解析？**

解析、切片、写索引都可能耗时，也可能依赖 MinIO、ES、Tika 等外部组件。如果放在用户请求里同步做，大文件会导致接口超时，失败也难以恢复。异步任务可以返回 taskId，让用户查看处理状态，失败后也能重试或排查。

- `DocumentUploadService`
- `UploadBitmapService`
- `DocumentProcessingService`
- `DocumentParserService`
- `ChunkService`
- `VectorIndexerService`
- `Phase2UploadFlowIntegrationTest`

### Q13：为什么 `FileObject` 复用要按 Space 隔离？

**答：**

文件内容可以相同，但权限不能共享。

如果两个团队上传了相同 hash 的文件，底层对象内容理论上可以复用，但业务元数据必须分开。A 团队能看到这个文件，不代表 B 团队也能看到 A 的 Document、Chunk、Citation 或检索结果。

所以 NoteWeave 里 `FileObject` 按 `spaceId + contentHash` 建唯一约束。这样既能在同一空间内复用对象，减少重复存储，又不会因为 hash 相同导致跨空间权限污染。

**追问：删除 Document 时为什么不立刻减少 refCount 或物理删除？**

删除在当前链路里主要是软删除。这样可以避免索引、引用、任务和对象回收之间出现竞态。物理清理更适合放到 Admin/Ops 的 cleanup scan/execute 中，先扫描可清理资源，再确认执行，避免误删仍被引用的对象。

### Q14：解析和索引怎么保证一致性？

**答：**

核心是 indexVersion 和 activeIndexVersion。

文档处理时不会先把旧索引删掉再写新索引，而是创建新的 indexVersion。新版本解析、切片、写 ES 成功后，再把 Document 的 activeIndexVersion 切到新版本。如果新版本处理失败，旧版本仍然可用，检索链路不会被破坏。

此外，检索时不是只相信 ES。ES 召回后还会回查 MySQL，确认文档没有删除、KnowledgeBase 没有归档、chunk 的 indexVersion 等于文档 activeIndexVersion。这样可以处理 ES 索引滞后或脏数据问题。

**追问：重复消费 DOCUMENT_PROCESS 会怎样？**

当前链路按幂等目标处理。Worker 执行前会回查 task 和 Document 状态，chunk 侧也有版本和唯一约束，用来避免重复创建 active chunk 或重复切换错误版本。重复消费最多应该变成状态确认或安全跳过，而不是产生多份可召回内容。

### Q15：为什么不用 MySQL 全文检索，或者只用向量库？

**答：**

MySQL 更适合保存业务事实和事务状态，不适合作为团队知识库的全文召回主力。文档 chunk 检索需要文本相关性、过滤、分页、后续向量字段和调试能力，Elasticsearch 更合适。

只用向量也不够。向量检索对语义相近问题有效，但对精确词、专有名词、标题、版本号、错误码这类召回不一定稳定。所以 NoteWeave 采用 BM25、vector、wiki recall 再通过 Weighted RRF 融合，兼顾关键词和语义召回。

**边界：**

不要说当前已经接入独立向量数据库。当前实现以 Elasticsearch 承担 BM25 和向量索引能力。

## 6. Hybrid RAG、Citation 与证据链

### Q16：团队侧 RAG 的完整处理流程是什么？

**答：**

用户在 TEAM_CHAT 会话里提问后，系统先保存 USER message，再根据 ChatSession 的 scope 解析可检索范围，比如某些 KnowledgeBase。然后 HybridRetriever 在权限过滤下进行召回，EvidencePostProcessor 做去重、相邻 chunk 合并、低分过滤、同文档限流和长度截断。

如果没有证据，系统返回明确的无证据兜底，不编造答案。如果有证据，TeamRagPromptBuilder 会把证据编号后放进 Prompt，并加入 grounded-answer 和 prompt injection 防护规则。LLM 返回后，系统保存 ASSISTANT message，再把引用写入 `citation` 和 `message_citation`，同时记录 RetrievalTrace 和 LLMCallLog。

所以这条链路不是“检索文本然后问模型”，而是：

```text
权限范围
-> 多路召回
-> 证据后处理
-> 受约束 Prompt
-> 答案
-> Citation 持久化
-> Trace / Log / Feedback
```

- `TeamChatService`
- `HybridRetriever`

- `VectorRetriever`
- `WikiRetriever`
- `WeightedReciprocalRankFusion`

### Q17：Hybrid RAG 具体 hybrid 在哪里？

**答：**

NoteWeave 的 hybrid 不是简单把几路结果拼起来，而是分成召回、融合和后处理三层。

召回层包括 BM25、向量召回和 Wiki recall。BM25 适合关键词和精确匹配，向量召回适合语义相似，Wiki recall 适合已经沉淀的团队长期知识。

融合层使用 Weighted RRF。它不直接比较不同召回器的原始分数，因为 BM25 分数和向量相似度分布不一样，而是根据各召回列表里的排名做 reciprocal rank 融合，再加权。

后处理层通过 EvidencePostProcessor 控制证据质量，比如去重、相邻 chunk 合并、同文档限流、低分过滤和上下文截断，避免 Prompt 被重复或低质量证据撑爆。

**追问：向量检索失败怎么办？**

不能让整个问答失败。当前更稳的设计是向量召回失败时降级到 BM25 或其他可用召回，并在 trace 或日志里记录降级原因。这样保证核心问答链路可用，同时保留排查入口。

### Q18：为什么 Citation 不直接放在 message JSON 里？

**答：**

因为 Citation 是正式证据关系，不是展示字段。

如果只把 citationIds 或引用片段塞进 message JSON，会有几个问题。第一，权限不好二次校验，用户拿到 message 就可能看到不该看的引用。第二，引用无法跨 Message、Artifact、Card、Wiki 复用。第三，文档重处理后无法记录 quoteHash、sourceVersion、snapshotObjectKey 等防漂移信息。第四，后续做检索 Trace、Eval、Admin 查询时很难关联。

所以 NoteWeave 把 `citation` 作为独立表，Message、Artifact、ArticleCard、ConceptCard、SynthesisCard、WikiPage 都通过关联表绑定 Citation。这样证据可以独立审计、查询、权限校验和复用。

**追问：Citation 里保存 quote_text 会不会有风险？**

有风险，所以要注意权限和脱敏。quote_text 是为了证据快照和引用稳定性服务的，返回前必须做权限校验。Admin 日志和 Prompt 也要避免直接暴露完整私有原文。

### Q19：如何防止模型幻觉？

**答：**

NoteWeave 不是靠一句“不要幻觉”的 Prompt 解决，而是从链路上做约束。

第一，检索范围受权限和 session scope 限制，避免召回无关或越权资料。第二，EvidencePostProcessor 提高证据质量，减少重复、低分、过长上下文。第三，PromptBuilder 明确要求基于证据回答，证据不足时要说明无法确认。第四，回答后保存 Citation 和 RetrievalTrace，用户和管理员可以反查来源。第五，RAG Eval 可以用预设 case 检查 recall@k、MRR、citationCoverage 和 latency。

**追问：如果没有证据但模型很想回答怎么办？**

系统应该返回无证据兜底，而不是让模型自由发挥。面试时可以强调：无证据回答不是失败，而是可信系统必须有的拒答能力。

### Q20：线上出现一条坏回答，怎么排查？

**答：**

我会按链路排查，而不是直接说“模型问题”。

第一，看 ChatMessage 和 AnswerFeedback，确认用户问题、回答内容和反馈原因。第二，看 RetrievalTrace，确认实际检索了哪些 chunk、分数、是否 selectedAsEvidence、是否命中正确文档。第三，看 Citation，确认回答引用是否真实存在、是否越权、是否引用旧版本。第四，看 LLMCallLog，确认 PromptVersion、模型、token、latency、是否调用成功。第五，如果是系统性问题，可以用 RagEvalCase 复现并跑 Eval，看 recall、MRR、citationCoverage 是否下降。

这样可以把坏回答拆成召回问题、证据后处理问题、Prompt 问题、模型输出问题、权限问题或数据本身问题。

## 7. WebSocket Runtime、DRAFT / FORMAL 与 Redis 运行态

### Q21：为什么要做 WebSocket Runtime，不只用 HTTP 问答？

**答：**

HTTP 问答适合非流式、请求响应式的场景，但真实 AI 工作台需要流式输出、停止生成、刷新恢复、DRAFT 临时探索等能力。

WebSocket Runtime 解决的是会话执行过程中的运行态问题。用户发出消息后，服务端会推送 `chat.started`、多个 `chat.delta`、最后 `chat.completed`，如果用户中途 stop，就发 `chat.stopped` 并停止后续 delta。如果浏览器刷新，可以通过 ack/resume 恢复事件和 partialContent。

这些都不是普通 HTTP 接口擅长的，所以 NoteWeave 单独设计了 ws-ticket、事件 envelope、seq、ack、resume 和 Redis runtime state。

**实现兜底锚点：**

- `WebSocketTicketService`
- `ChatWebSocketHandler`
- `ChatRuntimeService`
- `ChatRuntimeStateStore`
- `ActiveExecutionRegistry`
- `Phase5WorkspaceChatRuntimeIntegrationTest`

### Q22：Redis 在 Runtime 里承担什么职责？

**答：**

Redis 在这里主要承载短期运行态，不是主业务事实源，也不是后台任务队列。

具体包括一次性 WebSocket ticket、当前 session runtime status、partialContent、事件 buffer、seq/ack/resume 状态、stop 标记等。这些状态有明显临时性，适合 TTL 过期，不适合全部落 MySQL。

正式 ChatMessage、Citation、Task、Artifact、Memory 这些长期事实仍然在 MySQL。Redis 只是让实时交互体验更顺滑，比如断线恢复和 stop/resume。

**追问：Redis 丢了会怎样？**

短期体验会受影响，比如不能恢复最近 delta 或 partialContent，但正式落库的历史消息、Artifact、Citation、Task 不应该丢。面试时要强调 Redis runtime state 不是系统唯一事实来源。

### Q23：为什么要区分 DRAFT 和 FORMAL？

**答：**

因为用户在 AI 工作台里有两类行为：一类是正式知识生产，一类是临时探索。

FORMAL 会话适合长期保留，可以写 ChatMessage、Citation、Memory，总结后影响后续上下文。DRAFT 会话更像临时草稿，用户可能随便试问题、改方向、探索不成熟想法。如果 DRAFT 也写长期 Memory，很容易污染用户画像和空间记忆。

所以 NoteWeave 把 DRAFT 生命周期设计为 `DRAFT_ACTIVE / DRAFT_EXPIRED / CONVERTED / DISCARDED`。用户可以把有价值的 DRAFT 转成 FORMAL，也可以丢弃。DRAFT 默认不写长期 Memory。

**追问：DRAFT 的回答会不会保存？**

可以保留短期运行态和必要的临时消息，但面试重点是它不会进入长期 Memory 写回，也不会默认沉淀为稳定知识。

## 8. 长期 Memory 与上下文加载

### Q24：长期记忆为什么要分层？

**答：**

因为不同记忆的作用域不同，不能把所有历史会话都塞进 Prompt。

NoteWeave 里 Memory 分成 session summary、space memory、user memory 和 memory item 等层。SessionSummary 记录某次正式会话的摘要；SpaceMemory 记录当前用户在某个空间里的工作上下文；UserMemory 记录跨空间的稳定偏好；MemoryItem 则承载具体偏好或空间上下文条目。

这样做有两个好处。第一，Prompt 不需要每次塞全部历史，减少 token 和噪声。第二，记忆可以按作用域、置信度、过期时间、pin、禁用开关来控制，避免低价值或敏感内容污染后续回答。

**追问：Memory 写入怎么避免污染？**

通过 `MemoryWritebackStrategy`。DRAFT 不写，短问候不写，包含 password、token、secret、api-key 等敏感信号的不写，低置信度偏好不覆盖高置信度偏好。用户还可以禁用 memory writeback。

**实现兜底锚点：**

- `MemoryWritebackStrategy`
- `MemoryWritebackService`
- `MemoryContextService`
- `ContextReadRouter`
- `Phase12LongTermMemoryIntegrationTest`

### Q25：为什么不能直接把聊天历史都传给模型？

**答：**

直接传全量历史有三个问题。

第一是成本和性能，历史越长 token 越多。第二是噪声，早期错误结论、临时探索、无关闲聊都会影响回答。第三是隐私和边界，DRAFT、敏感内容或其他空间的信息不能随便进入当前 Prompt。

所以更合理的是分层加载：近期历史保留短期连续性，SessionSummary 提供压缩上下文，SpaceMemory 和 UserMemory 提供稳定偏好，再结合当前检索证据回答。

**追问：Memory 和 RAG 证据哪个优先？**

对于事实性问题，RAG 证据优先。Memory 更适合用户偏好、长期上下文和工作方式。不能用 Memory 替代文档证据，更不能让 Memory 里的旧偏好覆盖当前知识库证据。

## 9. 个人研究 Source、Card、Artifact 与 Synthesis

### Q26：个人研究链路为什么设计成 `Source -> Card -> Artifact -> Synthesis`？

**答：**

因为个人研究不是一次问答，而是从资料理解到成果生成再到长期沉淀的过程。

`Source` 是原始资料入口，可以来自文件、URL 或文本。`ArticleCard` 和 `ConceptCard` 是对 Source 的结构化理解，把文章摘要、关键点、概念、别名、关系和证据提取出来。`Artifact` 是基于这些卡片和证据生成的阶段性成果，比如报告、学习指南、对比分析、Work Prep、Reading Notes。`SynthesisCard` 是用户确认后沉淀下来的长期个人知识。

这样分层的好处是：原始资料、结构化理解、生成成果、长期沉淀互相分开，不会让模型生成内容自动污染个人知识库。

**追问：为什么不直接 Source 问模型生成报告？**

可以做最简单版本，但不利于复用和追溯。Source 直接塞给模型会导致上下文过长、证据不稳定、重复生成成本高。Card 层可以把资料压缩成可复用结构，Artifact 生成时按需引用卡片和证据。

### Q27：URL Source 导入为什么要做安全限制？

**答：**

因为 URL 抓取容易引入 SSRF 风险。用户如果提交 localhost、内网 IP、metadata 地址或非法协议，服务端去抓取就可能访问不该访问的内部资源。

所以 SafeUrlContentFetcher 需要限制协议、解析 host、阻止 localhost/private network 等危险地址，并且抓取失败时不能把 Source 标成 READY。Source 只有在 raw text 或 parsed text 可读取时，才应该进入后续 compile。

**追问：为什么 READY 必须有文本？**

后续 Wiki Compiler 和个人生成都依赖可读文本。如果只保存 URL 元数据就标 READY，后面编译任务会变成隐性失败，用户也不知道资料到底有没有进入系统。

### Q28：个人 Wiki Compiler 做了什么？

**答：**

它把 Source 编译成结构化知识卡片。

对文章类内容，会生成 ArticleCard，包括标题、摘要、关键点、标签、证据摘录。对概念类内容，会生成 ConceptCard，包括规范化名称、别名、定义、解释、使用场景、误解点、置信度等。系统还会建立 ConceptAlias、ConceptRelation、ArticleConceptRelation，并通过 EvidenceBacktraceService 把卡片证据回溯到 Source 原文。

它的重点不是“让 LLM 输出一段 JSON”这么简单，而是把输出落到关系表和 Citation 里，支持后续搜索、合并、证据查看和 Artifact 生成。

**追问：如何避免同项目里概念重复？**

通过 normalizedName、alias、项目内唯一约束和 ConceptMergeService。不能完全指望模型不重复，应用层要做归一化和合并。

### Q29：Personal Generation 为什么要求 SOURCE-backed citation？

**答：**

因为个人 Artifact 也应该是 evidence-grounded 的，而不是只根据卡片摘要自由生成。

PersonalGenerationService 会加载 ResearchProject、ArticleCard、ConceptCard、SynthesisCard 和 MethodologyCard，但证据必须能回溯到 Source。如果卡片没有正式 Citation，或者 Citation 不能回到 SOURCE 资源，生成任务应该失败，而不是生成一个看起来很完整但没有证据支撑的 Artifact。

这和团队 RAG 的理念一致：生成内容可以更自由，但关键结论要能回溯证据。

**追问：没有证据就失败会不会体验不好？**

短期看是更严格，但长期看能保护知识质量。用户需要先补充 Source、重新 compile 或修复证据链，而不是得到一篇无法追溯的报告。

### Q30：Artifact 和 Wiki / Synthesis 为什么要分开？

**答：**

Artifact 是生成成果或工作产物，Wiki / Synthesis 是长期知识。两者可信度和生命周期不同。

Artifact 可能只是一次生成草稿，可以编辑、再生成、导出，有版本历史。团队 Wiki 和个人 SynthesisCard 则代表用户确认过、愿意沉淀的长期内容。如果生成完成就自动进入 Wiki 或个人知识库，会把错误、半成品和临时内容污染长期知识。

所以 NoteWeave 采用显式确认。团队侧 Artifact 可以发布为 Wiki 草稿再发布入索引；个人侧 Artifact 通过 distill-to-personal-wiki 两步 proposal/confirm 流程沉淀为 SynthesisCard。

**追问：为什么个人侧不直接合并 ConceptCard？**

当前 MVP 只沉淀为 SynthesisCard，不自动改 ConceptCard 或 MethodologyCard。因为 Concept 合并会影响长期知识结构，风险更高，适合做成后续 merge proposal，而不是自动写入。

### Q31：MethodologyCard 解决什么问题？

**答：**

MethodologyCard 解决的是生成结构和方法论一致性问题。

同样是生成报告，不同场景可能需要不同 workflow、outputStructure 和 qualityChecklist。把这些全部写死在代码里会很僵硬；完全交给用户 Prompt 又不可控。MethodologyCard 把方法论抽象成可匹配、可管理的卡片，支持系统预置、个人空间、项目级卡片，并在 Personal Generation 时注入 Prompt。

它让生成结果不只是“模型自由发挥”，而是按场景选择方法框架，比如 Report、StudyGuide、Comparison、WorkPrep 等。

**追问：Phase 13 做到了什么？**

被追问实现时可以补充：当前已经有 MethodologyCard 创建、查询、更新、归档、版本递增、owner-only 权限，以及自定义卡片优先于 preset 的匹配逻辑，相关测试锚点是 `Phase13MethodologyCardIntegrationTest`。

### Q32：项目里的 Skill 是不是完整 Agent 平台？

**答：**

不能这么讲。

当前项目里的 Skill 更像可控的生成步骤编排和执行日志。ArtifactGenerateTaskWorker 会按固定 plan 执行 LoadContext、GenerateDraft、PersistArtifact 等步骤，并记录 SkillExecutionLog。它不是开放式插件生态，也不是完全自主规划 Agent。

稳妥口径是：NoteWeave 现在实现了 plan-based generation pipeline 和 skill execution logging，为后续扩展更复杂的 Agent 或工具调用留下边界，但当前主链路不依赖完整开放 Agent 平台。

## 10. 团队 Wiki、知识图谱与长期知识

### Q33：团队 Wiki 在系统里承担什么职责？

**答：**

团队 Wiki 承担的是人工确认后的长期团队知识。

团队文档和 RAG 适合从原始资料里找证据，但团队长期协作还需要把稳定结论整理成 WikiPage。NoteWeave 支持手动创建 Wiki 草稿，也可以从 ChatMessage 或 Artifact 生成 Wiki Draft。发布后生成 WikiPageVersion，并通过 WIKI_INDEX Task 入索引，成为后续 RAG 的一个召回来源。

这样团队知识从“原始文档片段”升级到“人工整理后的长期页面”，同时保留版本、引用和关系。

**追问：为什么 Wiki 发布也要异步入索引？**

因为入索引依赖 ES，可能失败，也可能需要处理引用、链接和图关系。异步任务能记录状态、重试和错误，不影响草稿和发布记录本身。

### Q34：Wiki Graph 是当前主检索链路吗？

**答：**

不要把它说成 GraphRAG 主链路。

当前可以讲的是 Team Wiki 支持页面关系、链接解析、graph 展示和 WikiRetriever 作为 hybrid recall 的一部分。它增强团队长期知识的组织和召回，但不要夸大成完整 GraphRAG 推理系统。

**稳妥表达：**

当前图谱更偏 Wiki 页面关系和可视化探索，以及作为 Wiki recall 的辅助来源；完整 GraphRAG、多跳推理、图算法排序可以作为后续扩展。

## 11. Observability、Eval、Admin 与 Ops

### Q35：为什么 AI 项目还要做 Observability 和 Eval？

**答：**

因为 AI 系统的失败不一定是接口报错，更多时候是回答不准、证据不对、召回缺失、Prompt 版本不合适、模型输出不稳定。如果没有可观测能力，很难定位问题。

NoteWeave 的 Observability 包括 PromptVersion、LLMCallLog、RetrievalTrace、AnswerFeedback 和 RAG Eval。PromptVersion 让 Prompt 变更可管理；LLMCallLog 记录模型、token、latency、promptHash、success 等；RetrievalTrace 记录召回和证据选择；AnswerFeedback 收集用户反馈；RAG Eval 用 case 跑 recall@k、MRR、citationCoverage、latency 等指标。

**追问：Eval 会不会污染正式聊天历史？**

不会。RAG Eval 走独立 task 和 scene，记录自己的 trace 和 llm log，不写正式 chat_session、chat_message 或 long-term memory。这点在 `Phase14ObservabilityEvaluationIntegrationTest` 里有覆盖。

### Q36：Admin / Ops 做了哪些系统能力？

**答：**

Admin / Ops 主要解决系统上线后的管理、排障和资源治理。

AdminManagement 能查询用户、空间、任务和任务事件，支持用户 disable/enable、任务 retry/cancel/mark failed、空间管理等。AdminOps 支持 cleanup scan/execute、cleanup job 查询、系统健康检查、dashboard summary、audit logs。SystemHealth 会拆分 MySQL、Redis、MinIO、Kafka、Elasticsearch、LLM Provider 等组件，帮助定位依赖问题。

它的价值是让系统问题从“只能查日志”变成“可以通过后台看到任务、依赖、资源残留和审计记录”。

**追问：清理任务为什么要先 scan 再 execute？**

因为资源清理有误删风险。比如上传残留分片、过期 upload、对象存储文件都可能被任务或文档引用。先 scan 能让系统记录候选项和原因，再 execute 执行实际清理，并写 AuditLog。这样比直接删除安全。

**实现兜底锚点：**

- `AdminManagementController`
- `AdminObservabilityController`
- `AdminRagEvalController`
- `AdminOpsController`
- `SystemHealthService`
- `ResourceCleanupService`
- `AuditLogService`
- `Phase15AdminOpsIntegrationTest`

### Q37：如果面试官问 SLA 或指标，怎么不夸大？

**答：**

不要编线上数字。更稳的方式是说项目已经有指标采集和验证入口，但没有真实生产流量时不报 QPS、P99 或准确率。

可以拆成几类指标：

- 任务指标：Task 成功率、失败率、重试率、平均耗时、卡在 PENDING/RUNNING 的数量。
- 检索指标：recall@k、MRR、citationCoverage、无证据率、低分证据比例。
- LLM 指标：latency、token、失败率、模型错误类型。
- 运行态指标：WebSocket stop/resume 成功率、断线恢复率。
- 运维指标：组件健康、cleanup 数量、审计事件、ES/Kafka/Redis/MinIO 异常。

面试回答可以说：当前仓库提供 Trace、Log、Eval 和 Admin health 的验证入口，真实 SLA 需要在压测和生产环境中用这些指标持续采集。

## 12. 可靠性、一致性与排障追问

### Q38：异步链路里如何保证一致性？

**答：**

NoteWeave 不追求跨 MySQL、Kafka、MinIO、Elasticsearch、LLM 的强事务，而是通过本地事实表、Outbox、幂等和补偿实现最终一致。

业务状态先落 MySQL，比如 Document、Source、Artifact、Task。需要异步执行时，同事务写 TaskOutbox。Kafka 投递只是推进执行，Worker 拿到消息后必须回查 DB 状态。执行结果再写回 TaskAttempt、TaskEvent 和业务状态。

对于 ES 这类外部索引，用 activeIndexVersion 和后置 MySQL 校验降低不一致风险。对于 MinIO 对象，用 FileObject、refCount、soft delete 和 cleanup scan/execute 管理生命周期。

**追问：有没有分布式事务？**

没有，也不应该硬讲。这个项目更适合最终一致。外部 LLM、ES、MinIO、Kafka 都不适合放进一个强事务里。可靠性靠状态、幂等、重试、版本和可观测收敛。

### Q39：幂等怎么做？

**答：**

幂等要按链路分层。

入口幂等主要靠 task `idempotency_key`、上传 uploadId、FileObject 的 `spaceId + contentHash` 唯一约束、Card 的项目内唯一约束等，避免重复创建同一业务任务或资源。

消费幂等主要靠 Worker 回查 Task 状态、TaskAttempt 记录和业务表唯一约束。比如重复消费 DOCUMENT_PROCESS 不应该重复创建 active chunk；重复确认 Artifact distillation 不能重复生成多个 SynthesisCard。

补偿幂等主要靠状态条件和 Admin 操作记录。retry、cancel、mark failed、cleanup execute 都要基于当前状态推进，并写 AuditLog。

**追问：幂等是不是 Redis key 就够了？**

不够。Redis 可以做短期快判或运行态控制，但 MySQL 里的唯一约束、状态机和业务事实才是最终兜底。尤其是文档、引用、Artifact、Task 这些长期资源，不能只靠 Redis。

### Q40：如何回答“你这个项目是不是过度设计”？

**答：**

我会说它不是为了堆技术，而是因为 AI 知识工作台的风险点天然比较多。

如果只是个人玩具，可以上传文件、向量检索、问模型就结束。但 NoteWeave 的目标是团队和个人两类空间共存，要处理权限、异步任务、证据引用、运行态恢复、生成成果版本、长期记忆污染、RAG 评测和运维排障。这些问题如果一开始完全不设计，后面会很难补。

同时项目也不是所有地方都上重方案。比如 Redis 只承载 runtime state，不当主任务队列；DRAFT 不写长期 Memory；个人 Artifact 不自动改 ConceptCard；清理先 scan 再 execute；Bibtex 仍只是扩展方向，而 MCP 这块已经先落了一个远程 B 站 tool service。这些都是有边界的设计，不是无限复杂化。

### Q41：如果中间件异常，系统怎么降级？

**答：**

要按依赖分开讲。

MySQL 异常时，业务事实无法可靠读写，核心 API 应该失败并暴露健康状态。Redis 异常会影响 WebSocket ticket、runtime state、resume 和短期状态，但不应该丢失已落库的正式消息和任务。MinIO 异常会影响上传、解析和 citation snapshot，任务应失败并可重试。Elasticsearch 异常会影响检索和索引，RAG 可以返回无证据兜底或失败提示，不能编造。Kafka 异常会影响后台任务推进，outbox 可以保留待投递。LLM Provider 异常会影响生成，任务或回答应记录失败，不能吞掉错误。

**追问：能不能所有异常都自动重试？**

不能。临时网络抖动、ES/MinIO/LLM 短期失败可以重试；权限错误、参数错误、Source 没有文本、Citation 不可回溯这类确定性错误不应该无限重试。失败要分类。

### Q42：如何定位“用户看不到某条资料”的问题？

**答：**

按资源链路排查。

第一看用户是否属于对应 Space，角色是否允许查看。第二看 KnowledgeBase 是否 ACTIVE，Document 是否未删除、是否 INDEXED。第三看 DocumentChunk 是否存在，activeIndexVersion 是否匹配。第四看 ES 里是否有对应索引文档，spaceId/knowledgeBaseId/status filter 是否正确。第五看 RAG session scope 是否包含该 KB。第六看 RetrievalTrace 是否召回过该 chunk，如果没有召回，再看 query、BM25/向量/wiki recall、RRF 和 EvidencePostProcessor 的过滤。

这样可以把问题定位到权限、文档处理、索引、检索范围、召回质量或后处理。

## 13. 和 Austin 项目的类比与替换话术

### Q43：当前项目和 Austin 那类通知平台怎么类比？

**答：**

可以类比系统治理思路，但不能类比业务功能。

Austin 的主线是消息可靠触达：事件进入平台后，经过去重、限流、MQ、发送、重试、死信、补偿和锚点日志，最终让通知链路可追踪、可恢复。

NoteWeave 的主线是知识可信生产：资料进入系统后，经过上传、解析、chunk、索引、Hybrid RAG、Citation、Trace、Artifact、Wiki/Synthesis、Memory 和 Eval，最终让知识链路可权限隔离、可引用、可沉淀、可排查。

两者相似的是系统设计方法：都要处理异步、状态、幂等、失败恢复和观测。不同的是 Austin 面向消息触达，NoteWeave 面向 AI 知识工作台。

### Q44：哪些 Austin 问题可以替换成 NoteWeave 问法？

**答：**

可以这样替换：

| Austin 原问法 | NoteWeave 替换问法 |
|---|---|
| 什么是可靠通知？ | 什么是可信知识回答和可追溯生成？ |
| MQ 投递失败怎么办？ | TaskOutbox 投递 Kafka 失败怎么办？ |
| 消息卡在中间态怎么办？ | 文档解析、生成、Eval 任务长时间没有结果怎么办？ |
| 消费端怎么幂等？ | Worker 重复消费怎么保证不重复写 chunk、Artifact、Synthesis？ |
| traceId 和锚点日志怎么设计？ | RetrievalTrace、LLMCallLog、TaskEvent、Citation 怎么串起一次回答？ |
| 死信重放注意什么？ | 失败任务 retry / mark failed / cleanup execute 注意什么？ |
| 渠道成功等于用户收到吗？ | LLM 生成答案等于事实正确吗？ |
| 高可用怎么讲？ | 依赖 MySQL/Redis/MinIO/Kafka/ES/LLM 异常时怎么降级和定位？ |

### Q45：哪些 Austin 口径不能照搬？

**答：**

不要照搬这些：

- 不要把 NoteWeave 讲成通知平台、渠道平台或生产事件触达平台。
- 不要讲 RabbitMQ，当前后台任务主链路是 Kafka。
- 不要讲滑动窗口业务去重、多维优先级限流、短信/企业微信渠道路由，除非只是类比。
- 不要讲 TCC / Prepare / Commit / Cancel 是当前核心能力。
- 不要讲 XXL-Job 是当前任务补偿主链路。
- 不要说第三方渠道成功率或 P0 告警 SLA。

应该替换为：

- TaskOutbox + Kafka + Worker。
- 文档解析、索引、Artifact 生成、Eval、Cleanup 的后台任务治理。
- RetrievalTrace / LLMCallLog / Citation / AuditLog。
- Evidence-first RAG 和无证据兜底。
- Artifact / Wiki / Synthesis 的显式确认沉淀。

## 14. 最终收口话术

### Q46：如果让你用 30 秒讲重点系统功能，怎么说？

**答：**

NoteWeave 的重点不是单次 RAG 问答，而是一个 AI 知识工作台的系统闭环。它用 `TEAM / PERSONAL` 空间做权限边界，用 `Task + Outbox + Kafka + Worker` 承接上传解析、生成、索引、评测和清理，用 Hybrid RAG、Citation 和 RetrievalTrace 保证回答可追溯，用 WebSocket Runtime 和 Memory 支持连续工作流，再通过 Artifact、Wiki、Synthesis 把生成结果沉淀为长期知识。

### Q47：如果让你用 2 分钟讲重点系统功能，怎么说？

**答：**

我会从五个重点系统功能讲。

第一是空间权限。NoteWeave 把 `TEAM` 和 `PERSONAL` 作为一级业务容器，团队知识按 SpaceMember 角色控制，个人研究默认 owner-only。后续文档、RAG、Citation、Artifact、Memory 都回到这个边界。

第二是统一异步任务。文档解析、Source 导入、Source 编译、Artifact 生成、Wiki 入索引、Embedding backfill、RAG Eval、Cleanup 都复用 `Task + Attempt + Event + Outbox + Kafka + Worker`。这样长任务有统一状态、幂等、重试、取消和 Admin 排查入口。

第三是团队知识闭环。团队侧从 KnowledgeBase 上传文档，经过分片上传、MinIO、解析、Chunk、ES 索引，再通过 BM25、向量和 Wiki recall 做 Hybrid RAG，答案保存 Citation 和 RetrievalTrace，稳定内容还能发布为 Wiki。

第四是个人研究闭环。个人侧从 ResearchProject 和 Source 开始，把资料编译成 ArticleCard、ConceptCard，再基于卡片、证据和 MethodologyCard 生成 Artifact。Artifact 默认只是版本化成果，用户确认后才沉淀为 SynthesisCard，避免自动污染长期知识。

第五是可观测和运维。系统记录 LLMCallLog、RetrievalTrace、AnswerFeedback、RagEvalRun、TaskEvent、AuditLog，并提供 Admin health、cleanup、dashboard、任务管理等接口。这样出问题时可以定位是权限、索引、召回、Prompt、模型还是任务执行问题。

### Q48：最后一句最稳的项目价值是什么？

**答：**

NoteWeave 的价值不是“我接了一个大模型”，而是把知识从资料进入系统、被检索引用、生成成果、沉淀为长期知识这一整条链路，做成了权限清晰、任务可恢复、证据可追溯、结果可评测、问题可排查的系统。

## 15. 最推荐主打的三个系统设计亮点

### 亮点 1：用 `Outbox + Kafka` 治理 AI 系统里的长任务一致性

**答：**

我觉得这个项目里比较有工程含量的一点，是把 AI 系统里的长任务统一治理了。因为文档解析、索引、向量回填、Artifact 生成、RAG Eval、资源清理这些任务都可能耗时，也可能依赖外部组件，如果放在同步请求里，用户体验和失败恢复都会很差。

我的设计是用 MySQL 记录任务事实，用 Outbox 保证业务状态和待投递消息在本地事务内一起落库，再用 Kafka 推动后台 Worker 执行。这样不会追求跨 MySQL、Kafka、MinIO、Elasticsearch 的强事务，而是用最终一致模型：任务先有状态，再异步推进，失败可重试，执行过程可追踪。

这个亮点最适合带出下面这些点：

- 本地消息表 / Outbox 模式。
- MQ 最终一致。
- 消费幂等。
- 任务状态机。
- 失败重试和补偿。

### 亮点 2：Evidence-first Hybrid RAG，而不是简单向量检索

**答：**

RAG 这块我没有只做向量检索，因为企业知识库里很多问题是关键词、专有名词、版本号、术语匹配，单纯向量召回不一定稳定。所以我做的是 Hybrid RAG：BM25 负责关键词和精确匹配，向量检索负责语义相似，Wiki recall 负责已经沉淀的长期知识。

多路召回之后不能直接拼在一起，因为不同召回器分数不可比，所以我用 weighted RRF 这类基于排名的融合思路。融合后还要做证据后处理，比如去重、相邻 chunk 合并、限制同一文档占比和控制上下文长度，避免 Prompt 被重复证据撑爆。

更重要的是，我把 Citation 和 Trace 当成系统能力，而不是 UI 装饰。模型回答后会记录引用证据和检索过程，坏回答可以反查：是没召回、召回了没选中、证据质量差，还是 Prompt 或模型输出问题。

这个亮点最适合带出下面这些点：

- BM25 vs 向量检索。
- Hybrid Search。
- RRF 融合。
- grounding / citation。
- recall@k、MRR、citationCoverage。

### 亮点 3：把 Agent 能力收敛成可控的 Skill Pipeline

**答：**

个人研究和 Artifact 生成这块，我没有把它包装成完全自主 Agent。因为开放式 Agent 在真实系统里会带来几个问题：路径不可控、成本不可控、失败难复现、结果不好评测。

所以我做的是更收敛的 Skill Pipeline。系统先把 Source 编译成结构化卡片，再根据任务类型选择 MethodologyCard，生成时按步骤加载上下文、选择证据、生成草稿、保存 Artifact 版本。这样它有一点 Agent 的分步骤执行能力，但每一步都可观察、可记录、可失败恢复。

Artifact 生成后也不会自动变成长期知识。团队侧要发布成 Wiki，个人侧要用户确认后沉淀成 SynthesisCard。这个设计牺牲了一点自动化，但避免了大模型把不可靠草稿直接写进知识库。

这个亮点最适合带出下面这些点：

- Agent vs Workflow / Pipeline。
- 工具调用可控性。
- 生成结果版本化。
- 人工确认闭环。
- 自动化和可靠性的 trade-off。
