# RAG 优化专题与 NoteWeave 项目落点

> 更新时间：2026-06-09  
> 这份文档只做一件事：把 RAG 优化相关的知识点单独整理出来，并且明确哪些可以落到 NoteWeave 当前项目，哪些属于下一阶段演进方向。  
> 这不是通用论文综述，也不是单纯的术语表，而是面向面试表达和项目深挖的知识整理。

---

## 1. 先给一个总框架

如果面试官问你“RAG 一般可以从哪些地方优化”，推荐你不要直接开始报名词，而是先给一个全局框架：

我理解 RAG 优化不是只优化检索器，而是从知识进入系统开始，一直到 query 预处理、召回融合、重排裁剪、可信生成和过程评测，整条链路都可以做优化。前半段更偏知识工程，中间更偏召回与排序，后半段更偏生成可信度和诊断闭环。

可以把它拆成六类：

1. 知识工程优化
2. Query 改写优化
3. 检索召回优化
4. Rerank 和截断优化
5. 可信生成优化
6. 过程评测优化

---

## 2. 第一类优化：知识工程优化

这类优化的核心思想是：**垃圾进，垃圾出。**  
如果知识进入系统之前就质量不高，后面的检索和生成再强，也是在错误材料上工作。

### 2.1 自动化知识生产

#### 它解决什么问题

- 知识录入太慢
- 人工整理成本高
- 文档上传后只是“存起来”，没有真正变成可计算知识

#### 可以怎么讲

更成熟的知识系统不会停留在“上传文件 + 建索引”，而是会做自动化知识生产。也就是把解析、清洗、切分、标签提取、候选摘要、候选关系、候选 Wiki 页面生成等动作串起来，把原始资料逐步变成结构化知识对象，再交给人确认。

#### 和项目怎么挂

NoteWeave 当前最适合挂这个点的是：

- 上传、解析、切分、索引这一条文档摄取链
- `AutoWikiMaintenance` 自动生成长期知识草稿
- 个人侧 `Source -> Card -> Artifact -> Synthesis` 的知识编译链

#### 面试里更强的说法

我会把自动化知识生产理解成从“资料存储系统”走向“知识生产系统”的关键一步。当前项目已经从纯文档管理走到了自动生成 Wiki 草稿和结构化知识对象，后续还可以继续增强标签提取、关系抽取和冲突治理。

### 2.2 Chunk 切分优化

#### 它解决什么问题

- chunk 过大，召回噪声太多
- chunk 过小，语义断裂
- 标题、定义、结论、限制条件被切散

#### 常见方法

- 固定长度切分
- 递归切分
- 结构感知切分
- 语义切分
- 按文档类型自适应切分

#### 应该怎么讲差异

固定长度实现最简单，但最粗糙。递归切分会优先保留较大的结构边界，再逐步细分。结构感知切分更适合有标题层级、段落、表格的正式文档。语义切分更追求语义完整，但成本更高，也更依赖模型或规则质量。

#### 和项目怎么挂

当前 NoteWeave 已经有：

- `DocumentChunk`
- Hybrid 检索
- `EvidencePostProcessor`

这说明它不是“切完就完”，而是已经形成了“切分 -> 召回 -> 后处理合并”的链路。也就是说，即便当前切分策略还不是最先进的，后处理层也在弥补切分副作用。

#### 更成熟的答法

我理解 chunk 优化不能脱离后处理来看。切分只是第一步，真正决定最终上下文质量的，是切得是否保结构、召回后是否能重组、重复内容是否能去掉。当前项目更偏实用路线，后续很适合往结构感知切分和按文档类型切分走。

### 2.3 元数据 Tag 优化

#### 它解决什么问题

- 正文内容可检索，但检索范围太宽
- 召回结果语义相似，但业务不相关
- 很难做权限过滤、路由、排序加权

#### 常见元数据类型

- 空间 / 知识库归属
- 文档类型
- 来源渠道
- 作者 / 部门
- 时间 / 版本 / 生效状态
- 标签 / 主题词 / 业务域
- 可信等级 / 权威级别

#### 为什么它重要

metadata 不只是过滤字段，它本身就是检索信号。很多企业问答场景里，先用 metadata 缩小范围，再做正文召回，效果会比直接全文语义检索稳定很多。

#### 和项目怎么挂

NoteWeave 当前已经天然有很多强元数据：

- `Space`
- `KnowledgeBase`
- `Document`
- `WikiPage`
- 版本、状态、归属关系
- Citation 和 Trace 里的来源信息

后续可以继续增强：

- 业务域标签
- 时效标签
- 来源权威度
- 别名字典
- 文档质量标签

### 2.4 知识冲突治理

#### 它解决什么问题

- 新旧版本冲突
- 团队口径不一致
- 草稿和正式版混用
- 个人记录和团队共识冲突

#### 面试里怎么讲

成熟的 RAG 不只是“找到相关内容”，还要识别冲突内容。否则模型会把互相矛盾的片段一起吸收，最后输出模糊折中答案，或者答错却看起来有依据。

#### 常见治理手段

- 版本优先级
- 来源权威优先级
- 时效性控制
- 冲突标记
- 生成时显式说明冲突

#### 和项目怎么挂

NoteWeave 现在已经有适合继续延伸这个能力的基础：

- Wiki / Artifact / Memory 分层
- 版本化对象
- Citation / Trace 可回溯

所以这块很适合作为“下一步优化方向”来讲。

## 3. 第二类优化：Query 改写优化

这类优化的核心思想是：**很多检索失败，不是库里没有，而是用户没问对。**

### 3.1 为什么要做 Query 改写

常见问题包括：

- 错别字
- 口语表达
- 简称、别名、缩写
- 省略上下文
- 多跳问题混成一句
- 问题意图不清

#### 一个高质量说法

Query 改写本质上是在缩小“用户表达”和“索引表达”之间的差距。知识库里的内容往往是规范化表达，但用户问题常常是口语化、模糊化甚至错误表达，所以在进入召回前增加 rewrite、纠错、分解和路由，往往比盲目加强向量模型更划算。

### 3.2 多路 Query 改写

#### 核心思路

不是只生成一个 rewrite，而是生成多个查询视角，再并行召回。

常见方式包括：

- 原始 query
- 术语化 rewrite
- 别名扩展 rewrite
- 子问题拆分 query
- HyDE 假设性答案 query

#### 为什么有价值

- 能提升复杂问题覆盖率
- 降低单次 rewrite 失败的风险
- 对模糊和多跳问题更友好

#### 和项目怎么挂

当前 NoteWeave 还不是重度 query rewrite 系统，这一点要诚实。但从架构上讲，它已经有非常适合继续接入 rewrite 的位置：

- 检索前处理层
- HybridRetriever 前的 query enrich
- route 到 TEAM / PERSONAL / Wiki / direct answer 的选择逻辑

### 3.3 改写模型微调

#### 它适合什么场景

- 企业内部固定问答
- 术语很稳定的垂类知识库
- 高查询量、可积累历史 query 数据

#### 和 prompt 改写的差异

- prompt 改写启动快，成本低
- 轻量微调更稳定，更贴业务词表
- 代价是要构造训练集和做回归评测

#### 面试时怎么讲

当前项目还没有做到 rewrite 模型微调，但这个方向我会把它理解成“当 query 量足够大、场景足够稳定之后的下一阶段优化”，目标不是让模型更会聊天，而是让它更会翻译成适合当前知识库的检索语言。

---

## 4. 第三类优化：检索召回优化

### 4.1 从单路检索到混合检索

#### 单路检索的问题

- 纯 BM25：术语好，但语义弱
- 纯 dense：语义好，但精确术语和标题编号场景不稳定
- 纯图检索：结构强，但建设成本高

#### 为什么要混合

因为不同召回器解决的是不同失败模式。混合检索不是重复建设，而是用不同召回器覆盖不同类型的相关性。

#### 和项目怎么挂

NoteWeave 当前已经是标准的 Hybrid RAG 主链，这个点是你最能讲稳的一块：

- BM25
- dense
- Wiki recall
- Weighted RRF

### 4.2 双路并行检索

#### 核心思路

并行不是为了炫技，而是为了减少复杂 query 的漏召回。

常见并行方式：

- sparse + dense 并行
- 主文档库 + Wiki 库并行
- 原始 query + rewrite query 并行

#### 项目怎么挂

当前 NoteWeave 已经有多路召回和融合，所以你完全可以往这个方向解释：

我现在的检索已经不是单召回器线性链路，而是并行拿多个候选集，再融合排序。后面如果继续加 rewrite 或子问题分解，也可以自然扩展成多 query 并行召回。

### 4.3 GraphRAG 优化

#### 它更适合什么问题

- 跨文档关系问题
- 多实体关联问题
- 全局主题总结
- 图路径推理问题

#### 不适合怎么吹

不要把它说成“GraphRAG 一定比普通 RAG 强”。它不是通用替代方案，而是特定问题类型上的结构增强能力。

#### 和项目怎么挂

当前 NoteWeave 可以讲：

- `WikiGraph`
- `KnowledgeGraph`
- `AutoWikiMaintenance`

可以说已经做了“图增强基础设施”，但主链仍是 Hybrid RAG。

## 5. 第四类优化：Rerank 和截断优化

### 5.1 Rerank 的作用

#### 最推荐的口径

召回的目标是尽量不漏，rerank 的目标是尽量更准。也就是说，前者偏 coverage，后者偏 precision。

#### 常见方法

- RRF 做粗融合
- cross-encoder 做精排
- 文档级 / chunk 级 rerank
- 多特征混合 rerank

#### 和项目怎么挂

当前项目已经有 `Weighted RRF`，所以可以说：

现在项目已经做了多路融合，但 rerank 还属于下一阶段增强。这种说法最稳，因为既体现你知道 rerank 的价值，又不会把还没完全落地的能力说满。

### 5.2 证据截断

#### 它解决什么问题

- prompt 长度有限
- 召回结果重复
- 相关证据很多，但不能全塞
- 模型容易被冗余内容淹没

#### 正确理解

证据截断不是简单按 token 长度砍掉尾部，而是做上下文预算分配。要优先保：

- 核心定义
- 关键结论
- 限制条件
- 来源信息
- 冲突说明

#### 和项目怎么挂

当前项目已经有 `EvidencePostProcessor`，这是很好的落点。你可以说，项目当前已经有去重、相邻合并、每文档限流、上下文裁剪这些动作，本质上就是在做证据筛选和证据截断优化。

## 6. 第五类优化：可信生成优化

这一类优化的目标不是“更会说”，而是“更可信、更可审计、更少幻觉”。

### 6.1 为什么会出现不可信生成

常见原因有：

- 检索漏了
- 检索到了，但截断错了
- 证据冲突
- 模型忽略证据，靠参数知识自由发挥

### 6.2 常见优化方式

- 强约束 prompt
- 无证据拒答或降级回答
- 强制 citation
- groundedness 检测
- self-check / self-reflection
- conflict-aware answer

### 6.3 和项目怎么挂

当前 NoteWeave 已经有很好的“可信生成骨架”：

- `Citation`
- `RetrievalTrace`
- `PromptVersion`
- `LLMCallLog`
- `RagEval`

所以下一步最自然的优化，不是重新发明链路，而是在现有骨架上继续加 groundedness、自检和冲突感知生成。

### 6.4 一个成熟说法

我理解可信生成不是只靠 prompt 限制，而是要靠检索、证据、引用、日志和评测一起收口。当前项目已经把 Citation、Trace、PromptVersion 和 Eval 串起来了，所以后续如果做 groundedness 和 self-check，会比较顺。

---

## 7. 第六类优化：过程评测优化

这个点非常重要，因为它最能体现你不是只会“调模型”。

### 7.1 为什么不能只看最终答案

因为 RAG 是多模块系统。最终答错可能是：

- 解析错
- chunk 错
- metadata 不够
- query rewrite 失败
- 召回漏了
- rerank 排错
- 截断截掉关键证据
- 模型没按证据回答

所以只看“最终对不对”，很难知道该优化哪里。

### 7.2 推荐的评测拆法

把评测拆成三层：

- 检索层：是否命中正确文档 / 正确 chunk
- 证据层：送给模型的上下文是否足够、是否有噪声
- 生成层：回答是否 grounded、是否完整、是否引用正确

### 7.3 项目怎么挂

当前 NoteWeave 已经有这些支点：

- `RetrievalTrace`
- `Citation`
- `LLMCallLog`
- `RagEvalRun`
- `AnswerFeedback`

所以你可以非常自然地说：

当前项目已经不是只能看最终聊天结果，而是能按检索、证据、生成三层去定位问题。后面如果继续做过程评测细化，只是在现有日志和评测骨架上再拆指标。

### 7.4 一个高质量答法

我理解过程评测的价值不是打总分，而是定位瓶颈。如果 trace 显示召回已经命中了正确文档，但 groundedness 低，那问题大概率在证据装配或生成约束；如果 trace 里压根没召回到正确内容，那应该优先回到 chunk、metadata、query rewrite 或召回器配置，而不是先怪模型。

## 8. 一些和这些优化强相关的具体方法

这一节专门补“方法名”，方便你面试时展开。

### 8.1 HyDE

HyDE 的核心思路是先让模型根据 query 生成一个假设性答案或假设文档，再拿这个“假设文本”去做 dense retrieval。它更适合用户 query 很短、很模糊、直接向量化效果差的场景。

在 NoteWeave 里，它最适合被讲成“未来 query 增强能力”，不要说当前已落地。

### 8.2 RRF

RRF 的核心价值是对多路召回做稳健融合，而不依赖不同召回器分数在同一量纲上可直接比较。这一点特别适合稀疏检索、dense 检索、Wiki recall 这种来源不同的候选集。

### 8.3 HNSW / ANN

这类方法属于向量检索底层优化。它们解决的是“如何在大规模向量中尽快找近邻”，不是直接解决业务相关性、权限或可信性。

### 8.4 groundedness

这个词可以简单理解为“回答有没有真的被给定证据支撑”。它非常适合和 Citation / RetrievalTrace 结合来讲，是可信生成和评测里的关键概念。

### 8.5 conflict-aware generation

当证据冲突时，不是强行输出一个唯一答案，而是明确说“存在冲突、当前按哪个来源优先、哪些点尚不确定”。这类能力在企业知识系统里非常有价值。

## 9. 把这些优化和 NoteWeave 当前项目绑定起来

### 9.1 当前已经落地的

- 双空间和权限优先边界
- 上传、解析、切分、索引的统一异步链路
- Hybrid RAG
- Weighted RRF
- EvidencePostProcessor
- Citation / RetrievalTrace
- Wiki 长期知识层
- AutoWikiMaintenance
- PromptVersion / LLMCallLog / RagEval / AdminOps

### 9.2 已经有基础、但还可以继续做深的

- OCR / 复杂 PDF / 多模态解析
- 结构感知 chunking
- metadata enrichment
- query rewrite / typo correction / route
- rerank
- conflict-aware retrieval / generation
- groundedness / self-check
- 细粒度过程评测

### 9.3 最适合作为下一步演进的

如果面试官问你“如果继续做，优先做什么”，最推荐答这三个：

1. `query rewrite + route`
2. `rerank + context truncation`
3. `metadata enrichment + conflict governance`

因为这三个点和现有架构结合最自然，也最像真实项目下一阶段迭代。

---

## 10. 面试里可以直接背的总结

如果面试官让你总结 RAG 优化，你可以直接这样说：

我理解 RAG 优化可以分成六层。第一层是知识工程，解决资料进库质量问题，比如解析、切分、metadata 和冲突治理；第二层是 query 增强，解决用户问题表达不适合检索的问题；第三层是召回优化，从单路检索走向混合检索、并行检索和必要的图增强；第四层是 rerank 和上下文截断，解决“找到很多但给模型喂错了”的问题；第五层是可信生成，靠 citation、groundedness 和自检减少幻觉；第六层是过程评测，把问题定位到解析、检索、证据还是生成层。  
放到 NoteWeave 里，当前已经把 Hybrid、RRF、Evidence、Citation、Trace、Wiki、Eval 这条主骨架搭起来了，下一阶段最值得继续做的是 query rewrite、rerank、metadata enrichment 和 conflict-aware generation。
