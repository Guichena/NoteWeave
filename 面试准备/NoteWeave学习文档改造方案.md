# NoteWeave 面试准备目录改造执行文档

## 0. 本文定位

本文用于改造 `D:\java-projects\NoteWeave\面试准备` 目录下的全部面试学习材料。参考标准来自 `D:\java-projects\austin\学习\学习文档统一写法与改造标准.md`，但不照搬 Austin 口径，而是改成适配 NoteWeave 的执行规范。

改造目标不是把文档重新排版，也不是把已有内容简单合并，而是把整套材料统一成“问题驱动、可直接复述、能结合 NoteWeave 真实链路、能守住边界、能扛住连续追问”的面试资料库。

一句话原则：

> 先讲问题，再讲方案；先讲已验收事实，再讲扩展方向；先给结论，再展开链路、实现兜底锚点、取舍、失败处理和边界。

---

## 1. 参考标准转译成 NoteWeave 口径

Austin 标准强调“不要写知识点清单，而要写回答型学习资料”。迁移到 NoteWeave 后，每个核心问题必须回答七件事：

1. 面试官到底想验证什么能力。
2. 面试时第一句话怎么直接回答。
3. NoteWeave 的真实业务场景是什么。
4. 请求、任务、存储、检索、生成或沉淀链路怎么走。
5. 能用哪些类、表、接口、测试、配置或验收入口作为证据。
6. 这个设计背后的工程价值、取舍、失败处理是什么。
7. 哪些能说成已验收能力，哪些只能说成后续演进。

所有文档都要避免四种写法：

- 只列技术栈：`Spring Boot、MySQL、Redis、Kafka、Elasticsearch、MinIO`。
- 只列流程：`上传 -> 解析 -> 切块 -> 索引 -> 问答`。
- 只列实现名称：`TaskService -> TaskKafkaConsumer -> TaskExecutionCoordinator`。
- 只写结论：`用 Outbox 保证一致性，用 Hybrid RAG 提高效果`。

合格写法必须能回答“为什么这么设计、在 NoteWeave 哪里落地、失败时怎么办、哪些话不能说满”。

## 3. NoteWeave 统一主口径

当前面试材料按“NoteWeave 已完成本地验收的 AI 知识工作台”来组织。可以坚定主讲的已验收能力包括：

- `TEAM / PERSONAL` 双空间和权限边界。
- `systemRole`、`space role`、资源访问校验。
- `Task + TaskAttempt + TaskEvent + TaskOutbox + Kafka + Worker` 统一异步底座。
- 团队文档上传、分片、断点续传、合并、解析、chunk、索引、版本切换。
- 团队 Hybrid RAG：BM25、向量召回、Wiki recall、Weighted RRF、EvidencePostProcessor、Citation、RetrievalTrace。
- WebSocket Runtime：ticket、stream、stop、resume、DRAFT/FORMAL、Redis runtime state。
- 个人研究链路：Source、ArticleCard、ConceptCard、Evidence backtrace、Artifact、SynthesisCard。
- Methodology：预置、匹配、用户管理、生成注入。
- Memory：session summary、space memory、user memory、写入策略、DRAFT 排除。
- Observability / Eval / Admin / Ops：PromptVersion、LLMCallLog、RagEvalRun、SystemHealth、Cleanup、AuditLog。
- 静态前端工作台：登录、Space、Chat、Wiki、Graph、Artifact、Memory、Admin 等本地验收入口。

必须守住的边界：

- 不编造真实生产 QPS、P99、token/day、线上准确率、Kafka lag、ES 集群规模。
- 不把完整开放式 MCP 平台说成当前主链路强依赖。
- 不把 Bibtex 说成端到端已落地。
- 不把 GraphRAG 说成当前主检索链路。
- 不把完整开放式 Agent 平台说成已实现。
- 不把模块化单体说成已经微服务拆分、注册中心、配置中心、分库分表。
- 不把 Redis 说成主业务事实源或主异步任务队列。

稳妥表达模板：

> 当前已经验收的是 NoteWeave 的本地工程闭环，包括双空间、权限、统一任务、上传解析索引、Hybrid RAG、Citation、Runtime、个人研究沉淀、Eval 和 Admin/Ops。MCP 这块要更精确地讲：当前已经把 B 站解析能力拆成远程 MCP tool service，并接到产物入口和对话触发链路；但完整开放平台主链路、GraphRAG、开放 Agent 和微服务拆分仍然要作为扩展方向讲，说明它们应该接在哪一层、解决什么问题，而不能说成当前已落地事实。

## 4. 统一回答骨架

所有项目题尽量按下面顺序组织：

```text
场景：这个问题来自 NoteWeave 的哪个真实业务场景。
结论：第一句话直接回答，不绕。
链路：请求、任务、状态、存储、检索、生成或沉淀怎么流转。
证据：对应哪些类、表、接口、测试、配置或验收入口。
原理：背后的技术原理和工程价值是什么。
取舍：为什么不用更简单或更重的方案。
边界：哪些是已验收事实，哪些只是扩展方向。
追问：失败、重复、越权、无证据、断线、脏数据、重试时怎么办。
```

如果一个回答少了“证据、取舍、边界、追问”中的任意两个，就不能算改造完成。

## 5. 主答型文档改造标准

适用文件：

- `01-项目主述题.md`
- `02-模块深问题.md`
- `大厂深挖题库/11_通用问题按NoteWeave深答.md`

标准结构：

```md
# 文件标题

## 0. 本篇定位

说明这篇解决什么问题，适合回答哪些面试题。

## 1. 本主题面试官想考什么

说明面试官真正想验证什么能力，不只列技术名词。

## 2. 高频问题清单

按基础问题、进阶问题、深挖追问、压力追问分层。

## 3. 问答与讲解

### Q1：问题

#### 面试官为什么问

#### 回答思路

#### 结合 NoteWeave 怎么答

#### 技术原理 / 链路设计讲解

#### 实现兜底锚点

#### 可直接复述的面试回答

#### 常见追问

#### 常见坑
```

改造要求：

- `可直接复述的面试回答` 必须是一段自然语言，不能只是 bullet list。
- `实现兜底锚点` 至少给出 2 到 3 个类、表、接口、测试、配置或页面入口。
- `技术原理 / 链路设计讲解` 要解释为什么这么做，不只说用了什么。
- `常见追问` 至少 2 个，能自然承接面试官连续深挖。
- `常见坑` 必须写清哪些话不能说太满。

### 6.1 追问题库模板

```md
## 主题：Task / Outbox / Kafka

### 起手问题

面试官可能这样问：为什么要引入 Outbox？

### 推荐回答方向

先讲长任务和外部依赖，再讲业务写库和消息投递不能放在一个强事务里，最后讲 Outbox + 补偿投递 + Worker 幂等。

- `TaskService`
- `TaskOutboxService`
- `TaskKafkaConsumer`
- `TaskExecutionCoordinator`

不要说 Outbox 保证绝不重复；它解决的是最终一致和可补偿，消费侧仍然要幂等。
```

适用文件：

专项文档不要写成百科，而要写成“通用原理 + NoteWeave 链路 + 面试表达”。

标准结构：

```md
# 主题标题

## 0. 本篇定位

## 1. 这个主题在 NoteWeave 里解决什么问题

## 2. 面试官真正想考什么

## 3. 核心链路

## 4. 原理讲解

## 5. 实现兜底锚点

## 6. 可直接复述的深答

## 7. 连续追问与回答

## 8. 边界和不能说满的地方
```

### 中间件专项额外要求

每个中间件都必须写清“承担什么、不承担什么”。

| 中间件 | 必须讲清 | 不能说成 |
|---|---|---|
| MySQL | 业务事实、状态机、权限、任务、证据、审计 | 不说成高并发下无限承载一切 |
| Redis | 短期运行态、上传进度、ticket、runtime state | 不说成主事实源或主任务队列 |
| MinIO | 文件对象、合并文件、解析文本、快照、导出对象 | 不说成权限系统 |
| Elasticsearch | BM25、向量索引、Wiki/Document 检索、RRF 支撑 | 不说成业务事实源 |
| Kafka | 后台任务分发、Outbox 后的异步触发 | 不说成业务强一致保证 |

### RAG 专项额外要求

RAG 文档必须把下列问题讲透：

- 权限过滤为什么前置。
- BM25、向量召回、Wiki recall 各自补什么短板。
- Weighted RRF 为什么比直接分数相加更稳。
- EvidencePostProcessor 解决什么证据质量问题。
- Citation 和 RetrievalTrace 为什么要落库。
- 无证据、弱证据、错误证据时怎么处理。
- 为什么 GraphRAG 只能作为扩展方向，不是当前主链路。

## 9. 去重和合并规则

为了避免资料越写越多但越难背，后续改造按下面规则去重：

1. `01-项目主述题.md` 只放开场题和项目整体叙事，不展开所有模块细节。
2. `02-模块深问题.md` 放模块级完整深答，是主力材料。
3. 不再单独保留高频精简稿；最高频技术题直接收敛在 `02-模块深问题.md`。
4. `03-追问题库.md` 不再重复完整答案，只记录追问路径和推荐答法。
5. `大厂深挖题库/11_通用问题按NoteWeave深答.md` 如果继续变长，应拆到 `通用问题分主题深答`。
6. `通用问题分主题深答_加深版` 只保留普通版没有的压力题、极端场景和八股下钻。
7. RAG 相关内容统一归口到 `rag专项题 (1).md` 和 ES 专项，其他文件只保留必要引用。
8. 中间件八股不要散落在主答文件里，主答文件只讲和项目强相关的部分。

## 10. 改造执行顺序

### 第一阶段：统一口径和主线

目标：先保证开场题、主模块和高频题能稳定回答。

1. 更新 `00-使用说明.md`，明确复习路径和边界。
2. 更新 `01-项目主述题.md`，形成 1 分钟、3 分钟、5 分钟版本。
3. 更新 `02-模块深问题.md`，补失败、权限、幂等、状态、追问。
4. 更新 `02-模块深问题.md`，让高频技术题也能直接开口，不再额外拆精简稿。

验收方式：随机抽 5 个问题，每个问题都能用 1 段直接回答 + 1 条链路 + 2 个实现兜底锚点 + 1 个边界说明回答。

### 第二阶段：补专项和追问

目标：把中间件、RAG、个人链路和实际问题补成可深挖材料。

1. 改 `中间件专项`，每篇都写“承担什么、不承担什么”。
2. 改 `rag专项题 (1).md`，集中处理 RAG 原理、幻觉治理、Citation、Eval。
3. 改 `07`、`08`，把竞品和帖子观点回扣 NoteWeave 链路。
4. 改 `03-追问题库.md` 和 `实际问题.md`，沉淀连续追问路径。

验收方式：对 Task、RAG、Memory、Artifact、中间件各做一组连续 3 问，答案不互相矛盾。

### 第三阶段：整理大厂深挖题库

## 12. 示例：把清单式答案改成深答

### 不合格写法

> NoteWeave 用 Kafka 做异步任务，用 Outbox 保证一致性。相关类有 TaskService、TaskOutboxService、TaskKafkaConsumer。

问题：这段话只列了组件和类名，没有解释为什么需要、链路怎么走、失败怎么办，也没有边界。

### 合格写法

> NoteWeave 统一使用 `Task + Attempt + Event + Outbox + Kafka + Worker`，不是单纯为了异步，而是因为文档解析、索引、Source 编译、Artifact 生成、Eval 和 Cleanup 都是耗时长、容易失败、需要审计和重试的后台任务。业务入口先在数据库里创建 Task、Attempt、Event 和 TaskOutbox，把“业务事实”和“待投递事实”放进同一个事务；事务提交后再由投递器把 Outbox 消息发到 Kafka。Worker 消费时不会只相信消息体，而是回查 DB 状态和幂等键，再决定是否执行。这样即使 Kafka 重复投递、Worker 中途失败或投递器短暂不可用，也能靠 Outbox 补偿、任务状态机和消费侧幂等恢复。这里不能说 Outbox 保证绝不重复，它解决的是最终一致和可补偿，重复消费仍然要靠 Worker 幂等处理。

这段回答包含：

- 场景：多个长任务。
- 结论：统一 Task/Outbox/Kafka/Worker。
- 链路：写库、Outbox、投递、消费、回查。
- 证据：`TaskService`、`TaskOutboxService`、`TaskKafkaConsumer` 等。
- 原理：最终一致、补偿投递、消费侧幂等。
- 边界：不能说绝不重复。

## 13. 最终目标

整套目录改造完成后，应达到下面效果：

1. 30 分钟能背出项目整体介绍和三条主故事。
2. 2 小时能覆盖权限、Task、RAG、Runtime、个人链路、Memory、Eval、中间件八大主题。
3. 每个主题都有一段可直接复述的标准回答。
4. 每个主题都能拿出至少 2 到 3 个实现或验收锚点。
5. 每个主题都能回答失败、重复、越权、无证据、断线、脏数据、重试等追问。
6. 所有材料对“已验收事实”和“扩展方向”的表达一致。
7. 面对“是不是 demo”“有没有生产指标”“是不是过度包装”这类压力题时，能稳住边界而不是硬编。
