# 中间件专项使用说明与总览

> 本文件为 2026-06-01 加深版，依据当前代码、测试和 Flyway 迁移整理。中间件题不要背概念，要回答“这个组件在 NoteWeave 的哪条链路里承担什么职责，为什么不让它承担别的职责，失败时怎么查”。

## 0. 总原则

所有中间件问题都要回到四个判断：

1. 事实源在哪里：最终业务状态以 MySQL 为准，ES、Redis、MinIO、Kafka 都不是最终权限和业务事实。
2. 状态分几层：长期事实、短期运行态、大对象、检索读模型、消息流要分开。
3. 失败怎么对齐：跨组件失败回到 Task、Outbox、TaskEvent、Trace、Admin/Ops，而不是说“中间件保证”。
4. 哪些不能说满：不编造生产 QPS/P99，不把 Redis 说成主队列，不把 ES 说成事实源，不把 Kafka 说成业务 exactly-once。

## 1. 职责地图

- MySQL：业务事实源、事务边界、状态机、表关系、唯一约束、审计和评测结果。
- Redis：WebSocket ticket、runtime/short_term/stream/events、上传 bitmap、TTL 短期状态。
- MinIO：上传分片、合并文件、解析文本、citation snapshot、导出文件和外部 Source 原文对象。
- Elasticsearch：文档 chunk BM25、向量索引、Wiki 索引、Hybrid RAG 候选召回和检索 debug。
- Kafka：Task 消息通道、削峰、异步 Worker 触发；真实执行状态仍在 MySQL Task 表。
- LLM/Embedding Provider：外部计算能力，必须通过 PromptVersion、LLMCallLog、RetrievalTrace、SkillExecutionLog 留痕。

## 2. 面试官会怎么追

- 表结构题：哪些表是核心事实表，哪些是关系表，哪些是日志/读模型？为什么不用一张大 JSON 表？
- 索引题：为什么 `space_id/status`、`task_type/task_status`、`document_id/index_version`、`scene/status` 这些索引很关键？
- 一致性题：MySQL 写成功、Kafka 投递失败、ES 写失败、MinIO 残留对象分别怎么恢复？
- 中间件替换题：Kafka 换 RabbitMQ、ES 换 Milvus/OpenSearch、MinIO 换 OSS/S3，会影响哪些抽象？
- 性能题：文档量、Wiki 页面、Artifact 任务、RAG Eval 增长后，哪个组件先成为瓶颈，怎么观测？

## 4. 一句话总收束

NoteWeave 的中间件设计不是堆技术名词，而是把不同数据形态放到合适的位置：MySQL 存可事务化业务事实，Redis 存短期运行态，MinIO 存大对象，ES 存检索读模型，Kafka 只做异步触发，最终用 Task、Trace、Citation、Admin/Ops 把跨组件失败重新串回可排查链路。
