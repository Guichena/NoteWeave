# NoteWeave 中间件专项使用说明

## 0. 本篇定位

这组文档专门准备 NoteWeave 项目里 5 个核心中间件的面试问题：MySQL、Redis、MinIO、Elasticsearch、Kafka。写法按 `面试准备/NoteWeave学习文档改造方案.md` 执行，不写成中间件百科，而是围绕 NoteWeave 的真实流程、功能职责、实现兜底锚点、八股追问和不能说满的边界来组织。

## 1. 中间件总览

| 中间件 | NoteWeave 中的职责 | 面试主线 |
|---|---|---|
| MySQL | 保存业务事实、状态机、权限、任务、证据、Memory、Eval 和 Admin 数据 | 关系建模、事务、索引、状态一致性、审计 |
| Redis | 保存短期运行态和轻量进度状态 | Bitmap、TTL、runtime state、stop/resume、缓存边界 |
| MinIO | 保存文件对象、分片合并文件、解析文本、快照和导出对象 | 对象存储、分片上传、对象 key、幂等、清理 |
| Elasticsearch | 承载 BM25、向量索引、Wiki/Document 检索和 Hybrid RAG | 倒排索引、过滤、向量、RRF、版本切换 |
| Kafka | 承载后台任务分发，与 Task/Outbox/Worker 配合 | MQ、Outbox、最终一致、重复消费、重试、取消 |

## 2. 推荐复习顺序

1. `01_MySQL_业务事实与事务边界.md`：先理解哪些数据必须落成业务事实。
2. `05_Kafka_TaskOutbox与异步任务.md`：再理解长任务为什么异步、Outbox 为什么必要。
3. `03_MinIO_对象存储与上传链路.md`：接着看文件如何进入系统。
4. `04_Elasticsearch_HybridRAG检索链路.md`：然后看文档如何变成可检索证据。

## 3. 面试统一回答骨架

遇到“你项目里为什么用某个中间件”时，按下面结构回答：

```text
场景：这个中间件解决 NoteWeave 里的什么问题。
职责：它承担哪些数据或流程，不承担哪些。
链路：一次真实业务请求中它在哪里参与。
实现锚点：对应哪些模块、配置、测试或表。
原理：背后的八股知识点是什么。
取舍：为什么不用更简单或更重的方案。
边界：不能说成什么，生产化还要补什么。
```

## 4. 最容易被追问的点

- MySQL 和 Kafka 怎么保证最终一致？
- Redis 为什么不是主业务事实源？
- MinIO 对象和 MySQL 元数据怎么绑定？
- Elasticsearch 里权限过滤为什么要前置？
- Kafka 重复消费怎么保证幂等？
- 如果中间件挂了，系统怎么降级或排查？
- 没有生产 QPS/P99 时怎么诚实回答？

## 5. 总口径边界

可以坚定主讲：

- 5 个中间件都在 Docker Compose 和配置里明确存在。
- Admin/Ops 里有 MySQL、Redis、MinIO、Kafka、Elasticsearch 的健康检查。
- 业务链路已经验收：上传、解析、索引、RAG、WebSocket runtime、Artifact、Eval、Cleanup 都会用到这些中间件。

不要说太满：

- 不要编造生产 QPS、P99、Kafka lag、Redis 内存或 ES 集群规模。
- 不要说 Redis 是主任务队列。
- 不要说 MinIO 保存权限，权限仍在 MySQL 和业务服务里。
- 不要说 Elasticsearch 是业务事实源，它是检索索引。
- 不要说 Kafka 保证业务强一致，当前设计是 Outbox + Worker 幂等下的最终一致。
