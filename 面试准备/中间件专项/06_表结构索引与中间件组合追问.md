# 表结构、索引与中间件组合追问

> 本文件为 2026-06-01 新增加深版。它专门覆盖面试中常被追但旧题库容易漏掉的问题：表怎么拆、索引怎么建、中间件怎么选、跨组件失败怎么对齐。

## 0. 总答题框架

遇到表结构和中间件问题，按这五句回答：

1. 先说明这类数据是什么形态：长期事实、短期状态、大对象、检索读模型、消息事件、外部计算结果。
2. 再说明落在哪里：MySQL、Redis、MinIO、ES、Kafka、LLM/Embedding。
3. 再说明关键表或 key：状态字段、唯一索引、版本字段、引用关系。
4. 再说明失败怎么对齐：Task、Outbox、Trace、Citation、cleanup、Admin/Ops。
5. 最后说明不能说满：没有生产指标、没有完整微服务、没有完整 GraphRAG/Agent。

## 1. 表结构为什么这样拆？

常见问法：
- 你项目里核心表有哪些？
- 为什么不是一张 message 表或一张 JSON 表？
- Citation、Trace、LLM log、Feedback 为什么要分开？
- Artifact、Wiki、SynthesisCard、Memory 为什么不是同一张表？

组合答法：

NoteWeave 的表不是按页面拆，而是按生命周期和风险拆。`users/space/space_member` 解决边界；`task/task_outbox/task_event` 解决异步执行；`document_upload/file_object/document/document_chunk` 解决资料摄取；`chat_message/citation/retrieval_trace/llm_call_log/answer_feedback` 解决可信问答和排障；`artifact/artifact_version/artifact_source/artifact_citation` 解决生成产物；`methodology_card` 解决生成方法论配置；`wiki_page/wiki_page_version/wiki_page_citation/wiki_page_link` 解决团队长期知识；`artifact_distillation_proposal/synthesis_card/synthesis_concept_relation/synthesis_card_citation` 解决个人确认沉淀；Memory 分 `session_summary/space_memory/user_memory/memory_item` 是为了区分会话摘要、空间偏好、用户偏好和可过期条目。这样比一张大 JSON 表复杂，但能回答权限、版本、证据、失败和追溯。

追问压法：
- 如果表很多，会不会过度设计？
- 哪些表是事实表，哪些是关系表，哪些是日志表？
- 如果要加审批流，你会接在哪些表上？

## 2. 哪些索引是面试必须讲的？

常见问法：
- 你设计过哪些索引？
- 为什么 `space_id` 几乎到处都有？
- 为什么 Task、Outbox、DocumentChunk、PromptVersion 要有组合索引或唯一索引？

组合答法：

索引要按访问路径讲。空间隔离是最高频过滤，所以 `space_id/status` 出现在 KnowledgeBase、Document、Wiki、Artifact、Memory 等表上。任务调度要查积压，所以 `task_type/task_status`、`space_id/task_status`、`task_outbox(status,next_retry_at,created_at)` 很关键。文档索引要避免旧版本污染，所以 `document_id/index_version/chunk_index` 唯一，`document.active_index_version` 用来切换可用版本。生成链路会匹配方法论，所以要能讲 `methodology_card(space_id,card_scope,status)`、`methodology_card(space_id,research_project_id,card_scope,status)`。RAG 排障要按 trace 看候选和 evidence，所以 `retrieval_trace(scene,created_at)`、`retrieval_trace_item(trace_id,rank_no)` 重要。评测和运维按时间查，所以 Eval、Audit、Health 都按 scene/status/component + created/checked 时间建索引。

追问压法：
- 为什么不是给所有字段都建索引？
- 组合索引顺序怎么判断？
- 如果查询慢了，你先看 SQL、ES 还是业务状态？

## 3. MySQL、ES、Redis 的边界怎么讲？

常见问法：
- 为什么 ES 不能代替 MySQL？
- 为什么 Redis 不存长期 Memory？
- 为什么 MySQL 不做全文/向量检索？

组合答法：

MySQL 是事实源，解决事务、状态、权限、版本、审计；ES 是读模型，解决 BM25、向量和 Wiki 召回；Redis 是短期运行态，解决 ticket、runtime、events、upload bitmap。三者不是互相替代，而是分层。比如一次 RAG 查询先用 MySQL 权限确定 scope，再用 ES 召回候选，再用 MySQL/Citation/Trace 做证据和可见性追溯；WebSocket 中 Redis 能恢复 delta，但正式消息仍以 MySQL 为准。

追问压法：
- ES 里旧 chunk 没删，会不会泄露？
- Redis 宕机时 Chat 能恢复到什么程度？
- MySQL 宕机时系统还能不能回答？

## 4. MinIO 和 MySQL 怎么配合？

常见问法：
- 文件为什么不放 DB？
- object_key 泄露是否越权？
- FileObject 复用怎么避免跨空间泄露？
- MinIO 残留对象怎么清？

组合答法：

MinIO 保存字节内容，MySQL 保存归属、状态、hash、object_key 和引用关系。上传链路里，分片对象进入 MinIO，`upload_chunk` 记录每个 chunk；合并后 `file_object` 记录 content_hash、object_key、ref_count；`document` 记录业务状态，`document_chunk` 记录可检索分片。object_key 不是权限凭证，下载和 snapshot 读取必须走后端权限判断。残留对象不直接自动删，而是 cleanup scan 登记 `ops_cleanup_item`，再 execute 清理，降低误删风险。

追问压法：
- merge 成功但 DB 失败怎么办？
- 删除 Document 后 Citation snapshot 怎么办？
- 如果用户没有权限但猜到 object_key 怎么办？

## 5. Kafka 和 Outbox 怎么配合？

常见问法：
- Kafka 已经可靠了，为什么还要 Outbox？
- Kafka 消息重复或丢失怎么办？
- 为什么 DocumentProcess 单独 topic？

组合答法：

Kafka 是消息通道，Outbox 是 DB 里的消息事实。业务事务写 Task 和 TaskOutbox，调度器再投 Kafka；投递失败会更新 outbox 状态和 next_retry_at；投递成功后 Worker 消费 taskId，回查 Task 并加锁，只执行 PENDING。DOCUMENT_PROCESS 单独进 `noteweave.document`，因为文档解析和索引资源重，后续能独立扩容；其他任务统一进 `noteweave.task`，复用 TaskExecutionCoordinator。`noteweave.index` 在环境里初始化过，但当前不要说成主链路 topic。

追问压法：
- Kafka 投递成功但 Worker 失败，任务如何恢复？
- Outbox SENT 了但 Kafka 实际没收到怎么办？
- 如果一个任务执行两次，业务表如何兜底？

## 6. 中间件健康和排障怎么讲？

常见问法：
- 系统坏了先看哪个中间件？
- Admin health 为什么拆 MySQL/Redis/MinIO/Kafka/ES/LLM？
- 一次坏答案如何定位是检索、模型还是数据问题？

组合答法：

按链路排，不按组件乱猜。权限问题先看 MySQL Space/Resource；任务问题看 Task、Outbox、Kafka 和 TaskEvent；检索问题看 ES health、RetrievalTrace、EvidencePostProcessor；模型问题看 PromptVersion、LLMCallLog 和 provider health；文件问题看 MinIO bucket、object_key 和 cleanup；实时体验问题看 Redis runtime 和 WebSocket event seq。SystemHealthService 会分别探测 MySQL select 1、Redis echo、MinIO bucket/object count、Kafka topic、ES cluster/vector alias、LLM provider，并把结果写入 system_health_snapshot。

追问压法：
- 如果 ES 和 LLM 都慢，如何避免误判？
- 如果 health 是 UP 但业务失败，下一步查什么？
- 如果 Kafka 堆积但 MySQL 正常，怎么定位 consumer 问题？

## 7. 表结构和中间件综合模拟题

### 题 1：用户说“我明明上传了文档，为什么 RAG 搜不到？”

答题路径：
1. 查权限和范围：space、knowledge_base、chat_session_scope。
2. 查业务事实：document.status、parse_status、index_status、active_index_version。
3. 查任务：DOCUMENT_PROCESS Task、TaskEvent、Outbox、Kafka 消费。
4. 查 chunk 和 ES：document_chunk 是否有当前 index_version，ES 是否有 active version doc。
5. 查 RAG：RetrievalTrace 是否召回，EvidencePostProcessor 是否截断。

### 题 2：用户说“引用里的内容我现在不应该能看”

答题路径：
1. 查 citation 的 source_type/source_id/chunk_id。
2. 查当前用户是否仍有 Space/Resource 权限。
3. 查资源是否 soft delete 或 status 变化。
4. 查 message_citation 是否绑定 retrieval_trace。
5. 修复时不要删历史消息，先修权限展示和 citation 读取逻辑。

### 题 3：Artifact 生成失败，但页面上留下了半成品怎么办？

答题路径：
1. 查 ARTIFACT_GENERATE Task 状态和 TaskEvent。
2. 查 SkillExecutionLog，看哪一步失败：加载上下文、MCP、生成、保存。
3. 查 `artifact.status` 和 `artifact_version` 是否已写入。
4. TaskExecutionCoordinator 会在 Artifact 失败时做 reconcile。
5. Admin 可重试，但要校验目标 Artifact 是否仍可重试。

### 题 4：RAG Eval 运行很多 case，会不会影响正式用户？

答题路径：
1. RAG Eval 使用 rag_eval_case/run/result 和 RAG_EVAL_RUN Task。
2. scene 是 RAG_EVAL，不污染正式 ChatSession 和 Memory。
3. 但它会消耗 ES、LLM、Kafka/Worker 资源。
4. 可通过任务队列、低峰执行、限流和独立 worker 隔离。
5. 不能说已经有真实线上 A/B 或压测数据。

## 8. 不能说满

- 不要说已经做了分库分表、读写分离或多活。
- 不要说 Kafka/ES/Redis 任一组件能替代 MySQL 事实源。
- 不要说当前中间件设计已经支撑真实大规模生产指标。
- 不要说所有跨组件失败都能自动恢复；有些需要 Admin/Ops 介入。
