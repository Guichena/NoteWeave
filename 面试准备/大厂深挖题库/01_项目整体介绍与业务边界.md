## 1. 本主题面试官想考什么

这个主题主要考察你能不能把 NoteWeave 从“我做了一个 RAG 项目”讲成“我设计并落地了一个权限约束下、可追踪、可运维的 AI 知识工作台”。大厂面试官通常不会只听功能列表，而会追问业务边界、核心链路、技术含量、你负责的部分、真实完成度，以及哪些能力只是后续规划。

需要提前说明的事实边界：

- 已实现：`TEAM/PERSONAL` 双空间、认证与权限、Task/Outbox/Kafka Worker、团队文档上传解析索引、团队 RAG、Citation、WebSocket Runtime、个人 Source/Card/Artifact/Synthesis、长期记忆、Methodology、观测评测、Admin/Ops、静态工作台前端。
- 基于当前代码和测试可说：Phase 13/14/15 已有迁移、控制器和集成测试，`docs/PROJECT_STATUS.md` 部分阶段状态存在滞后。
- 不要夸大：不要说已实现完整自主 Agent、多服务拆分、商业级 QPS、GraphRAG 主链路、完整开放式 MCP 平台主链路、Bibtex 主链路。

## 3. 问答与讲解

### Q1：你先用 1 分钟介绍一下 NoteWeave。

#### 面试官为什么问

这是开场题，但不是闲聊。面试官想快速判断你有没有项目全局观，能不能从业务问题、技术架构、核心难点三个层次组织表达，而不是直接罗列 Spring Boot、MySQL、Redis。

#### 回答思路

先讲产品定位，再讲核心链路，然后讲技术底座，最后点出你的 ownership。推荐结构是：一句话定义项目、两条主线、三个技术支撑、一个难点。

#### 结合我的项目怎么答

NoteWeave 是一个 AI 知识工作台，面向团队知识协作和个人研究沉淀。团队侧关注知识库上传、解析、检索、RAG 问答、Citation 和 Wiki 发布；个人侧关注 Source 导入、ArticleCard/ConceptCard 编译、Artifact 生成，以及用户确认后的 SynthesisCard 沉淀。底层复用统一的 Space/Permission、Task/Outbox/Kafka Worker、MinIO、Elasticsearch、Redis Runtime、MySQL、LLM 日志和评测观测。

#### 技术原理 / 链路设计讲解

项目的主链路可以拆成两个闭环：

- 团队闭环：`Document -> DocumentChunk -> Elasticsearch/BM25/Vector/Wiki Recall -> Evidence -> Citation -> Chat Answer -> WikiPage`。
- 个人闭环：`Source -> ArticleCard/ConceptCard -> Artifact -> 用户确认 -> SynthesisCard`。

面试时要强调“闭环”而不是“功能堆叠”。普通 RAG 项目通常做到上传文档和提问就结束，而 NoteWeave 继续处理权限、引用、运行态、长期记忆、Artifact 版本、可观测与后台运维。

#### 技术栈特点与选型理由

Java 17 + Spring Boot 3.3 适合做强工程约束的后端；MySQL 存业务状态和审计关系；MinIO 存原文、解析文本、引用快照；Elasticsearch 同时承担 BM25、向量检索和 Wiki 检索；Kafka 配合 outbox 承载长任务；Redis 只承载 WebSocket runtime、ticket、短期运行态，不把它吹成主任务队列。

#### 可直接复述的面试回答

NoteWeave 是我做的一个 AI 知识工作台，目标不是简单把文档丢给大模型，而是把资料进入系统、被检索引用、生成成果，再沉淀为长期知识做成完整闭环。项目分成团队和个人两条主线：团队侧有知识库上传、解析切片、混合检索、RAG 问答、Citation 和 Wiki 发布；个人侧有 Source 导入、卡片化编译、Artifact 生成和用户确认后的 SynthesisCard 沉淀。底层我做了统一的 Space/Permission 权限边界、Task/Outbox/Kafka 异步骨架、MinIO 对象存储、Elasticsearch 检索、Redis WebSocket 运行态，以及 LLM 日志、RetrievalTrace、Eval 和 Admin/Ops 能力。这个项目技术含量主要在工程闭环和可运维性，而不只是调一个大模型接口。

#### 常见追问

- 你觉得这个项目最核心的技术难点是什么？
- 团队空间和个人空间的数据边界怎么保证？
- 这个项目现在做到什么程度了？
- 如果只挑一个亮点展开，你会讲哪个？

#### 常见坑

不要开头就说“我用了 Spring Boot、Redis、Kafka、Elasticsearch”。技术栈不是项目价值。也不要说“实现了完整 Agent 平台”或“线上支撑多少 QPS”，当前仓库没有这些事实证据。

### Q2：这个项目和普通 RAG 问答项目最大的区别是什么？

#### 面试官为什么问

面试官想过滤“套模板项目”。如果你的回答只是“我用了向量库和大模型”，很容易被认为项目深度不够。

#### 回答思路

对比普通 RAG 的最小链路：上传、切片、检索、回答。然后指出 NoteWeave 增加了权限边界、异步任务一致性、混合召回、证据后处理、Citation 持久化、运行态恢复、长期记忆、Artifact/Wiki 分层和可观测能力。

#### 结合我的项目怎么答

NoteWeave 不是只做“文档问答”，而是做“可信知识工作流”。例如团队回答不是直接让模型发挥，而是经过 `HybridRetriever`、`EvidencePostProcessor`、`TeamRagPromptBuilder`、`CitationService` 和 `RetrievalTraceService`，并且 Citation 返回前还有权限复核。个人侧也不是直接总结文档，而是先把 Source 编译成 ArticleCard/ConceptCard，再通过 Artifact 生成，最后由用户确认后沉淀成 SynthesisCard。

#### 技术原理 / 链路设计讲解

普通 RAG 最常见的问题是：召回不稳定、答案无法审计、权限容易穿透、生成结果自动污染知识库、失败任务不可追踪。NoteWeave 用几个工程边界来控制这些问题：

- 用 `Space` 作为最高业务容器，检索和 Citation 都带空间约束。
- 用 `Task + Attempt + Event + Outbox + Kafka + Worker` 管理长任务。
- 用 Citation 关系表保存 evidence，不把证据只塞在 message JSON。
- 用 Artifact 和 Wiki/Card 分层，生成结果默认不是长期知识。
- 用 Trace、LLM 日志、Eval、Admin/Ops 支持排障。

#### 技术栈特点与选型理由

Elasticsearch 的优势是可以同时做关键词过滤、BM25、向量字段和结构化 filter；MySQL 负责强关系和权限复核；Kafka 负责任务削峰和异步执行；Redis 负责临时运行态。这个组合比“一个向量库 + 一个接口”复杂，但换来更可控的工程边界。

#### 可直接复述的面试回答

普通 RAG 项目通常做到文档切片、向量召回、拼 prompt 回答就结束了。NoteWeave 的区别是我把它做成了一个可追踪的知识工作流：上传解析走统一异步任务，检索有 BM25、向量和 Wiki recall 的融合，证据会经过后处理并持久化为 Citation，回答可以通过 RetrievalTrace 和 LLMCallLog 反查；同时所有资源都在 Space 权限下访问。更重要的是，生成结果不会自动污染长期知识库，团队侧要发布成 Wiki，个人侧要确认后才沉淀成 SynthesisCard。所以它的重点不是“接了大模型”，而是把 AI 输出变成可审计、可回溯、可运维的知识资产。

#### 常见追问

- Citation 为什么不能只放在回答 JSON 里？
- 为什么 Artifact 不直接变成 Wiki？
- 为什么 Redis 不作为主异步队列？
- 如果检索没有证据怎么办？

#### 常见坑

不要把“混合检索”说成纯算法亮点。面试官更关心权限过滤、失败降级、trace、citation、证据生命周期这些工程问题。

### Q3：你在这个项目里最有 ownership 的模块是什么？

#### 面试官为什么问

这是项目真实性和个人贡献验证题。面试官希望听到你能讲清楚某个模块的设计背景、具体实现、坑点和验证，而不是“大家一起做了很多”。

#### 回答思路

不要贪多。可以选三块主讲：统一异步骨架、团队 RAG/Citation、个人研究闭环。每块都用“场景、方案、收益、取舍、验证”来讲。

#### 结合我的项目怎么答

建议优先讲：

- 异步骨架：`TaskService`、`TaskOutboxService`、`TaskDispatcher`、Kafka Worker、Attempt/Event。
- 团队 RAG：`HybridRetriever`、`EvidencePostProcessor`、`TeamChatService`、Citation、RetrievalTrace。
- 个人闭环：`SafeUrlContentFetcher`、`WikiCompilerService`、`PersonalGenerationService`、Artifact distillation。

#### 技术原理 / 链路设计讲解

一个很好的 ownership 表达是：上传、解析、索引、Source 编译、Artifact 生成、Eval 和清理都是长任务，如果每个模块各写一套后台线程，就会出现状态枚举、重试、取消、审计、失败补偿不一致。统一 Task 模型以后，业务模块只需要定义任务输入和 Worker 处理逻辑，任务创建、outbox 投递、attempt 记录、event 追踪、重试取消都复用一套机制。

#### 技术栈特点与选型理由

Kafka 适合异步任务分发；Outbox 用来解决业务事务提交和消息投递之间的不一致；MySQL 的 `TaskAttempt/TaskEvent` 保证可审计；Worker 通过 taskId 回查 DB，避免只信任消息体。

#### 可直接复述的面试回答

我最有 ownership 的部分会讲两块。第一块是统一异步任务骨架，因为上传解析、索引、Source 编译、Artifact 生成和 Eval 都是长任务，我没有让每个模块各写一套后台逻辑，而是收敛成 `Task + Attempt + Event + Outbox + Kafka + Worker`。这样能统一处理幂等、重试、取消、失败记录和前端进度查询。第二块是 RAG 和证据链路，团队问答不是直接调用 LLM，而是先走混合检索，再做证据去重、相邻 chunk 合并、同文档限流、prompt 构造，最后把 Citation 和 RetrievalTrace 持久化，便于后续审计和排障。

#### 常见追问

- Outbox 怎么保证最终一致？
- Worker 重复消费怎么办？
- 你怎么证明 Citation 没有越权？
- 个人 Artifact 为什么要确认后才沉淀？

#### 常见坑

不要说“我负责了整个项目所有模块”然后每个模块都讲不深。大厂面试更喜欢你选一个真实深水区讲透。

## 6. 整条链路深讲：如何把项目讲成一个完整系统

面试中最稳的讲法不是从技术栈开始，而是先把项目抽象成“知识流转闭环”。NoteWeave 的完整链路可以按四层讲：

第一层是资料进入系统。团队侧是 KnowledgeBase 下的 Document 上传、分片、合并、解析、切片、索引；个人侧是 ResearchProject 下的 Source 导入，包括 TEXT、FILE、URL。这个阶段的关键不是“能上传”，而是资料进入系统后要有可读文本、可追踪来源、可异步处理状态和权限归属。

第二层是资料变成可检索证据。团队侧 Document 会被解析成 DocumentChunk，进入 Elasticsearch 的 BM25/Vector/Wiki 检索链路；个人侧 Source 会被编译成 ArticleCard、ConceptCard，并通过 citation 回溯到 Source 原文。这里要强调“证据单元”的概念：团队侧是 chunk，个人侧是 card + citation。

第三层是证据参与生成。团队问答会经过 HybridRetriever、EvidencePostProcessor、TeamRagPromptBuilder，再调用 LLM；个人 Artifact 生成会加载 ResearchProject、ArticleCard、ConceptCard、SynthesisCard、MethodologyCard 和 SOURCE-backed evidence，再进入 ArtifactPlanExecutor。也就是说，模型不是直接面对原始资料，而是面对经过权限、检索、证据筛选和方法论组织后的上下文。

第四层是生成结果沉淀。团队侧稳定内容需要发布为 WikiPage，个人侧 Artifact 默认只是成果，只有用户确认后才沉淀为 SynthesisCard。这里体现了项目最重要的产品原则：生成不等于知识，长期知识必须经过确认、版本绑定和证据关系保存。

面试官如果追问“你这个项目到底难在哪”，可以这样收束：难点不在调用 LLM，而在把资料、证据、权限、异步任务、生成结果和长期沉淀串成一个可追踪的工程闭环。

## 7. 原理与设计原因速查

- 为什么先讲业务闭环：因为大厂面试官更关心你是否理解系统解决的问题，而不是堆了多少中间件。
- 为什么双空间是核心抽象：团队知识和个人研究的权限、生命周期、可信度和沉淀规则不同，不能只靠一个 content 表硬撑。
- 为什么强调 evidence-first：AI 生成结果不可完全信任，必须能回到 source、chunk、version、snapshot。
- 为什么 Artifact 不等于 Wiki：Artifact 是生成成果，Wiki 是长期共享知识；二者可信级别不同。
- 为什么没有生产指标也能讲得稳：可以说已有 Trace、LLMCallLog、Eval、TaskEvent、HealthSnapshot 等观测面，后续会用它们验证，而不是编造数字。

## 8. 3 到 5 分钟深答模板

如果面试官给我比较长的时间介绍项目，我会从完整链路讲。NoteWeave 解决的是知识从资料进入系统，到被检索引用，再到生成成果，最后沉淀为长期知识的闭环问题。团队侧从 KnowledgeBase 和 Document 开始，文件先经过分片上传、合并、FileObject 复用，再通过统一 Task/Outbox/Kafka Worker 做解析、切片和索引；查询时通过 BM25、向量和 Wiki recall 做混合检索，经过证据后处理和 Citation 持久化后再让 LLM 生成回答。个人侧从 ResearchProject 和 Source 开始，Source 必须导入出可读文本，然后由 WikiCompiler 编译成 ArticleCard 和 ConceptCard，并把证据回溯到 Source；后续 Artifact 生成会加载这些卡片、证据和 MethodologyCard，生成结果默认只作为 Artifact 保存，用户确认后才沉淀为 SynthesisCard。整个系统底层复用 Space/Permission、Task/Outbox、MinIO、Elasticsearch、Redis Runtime、MySQL、LLM 观测和 Admin/Ops。所以我会把这个项目定位成一个可追踪、可运维的 AI 知识工作台，而不是简单的文档问答 Demo。
