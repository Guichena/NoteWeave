# 文件：02_空间权限与资源边界.md

## 0. 本篇定位

这篇负责空间、权限和资源边界的深挖问题。它适合回答 `TEAM / PERSONAL` 为什么拆开、`systemRole` 和 `space role` 如何分工、检索和 Citation 为什么也要受权限约束，以及 Admin、个人研究、团队知识之间的越权风险怎么控制。

## 1. 本主题面试官想考什么

这个主题考察你是否理解多租户、资源隔离、权限模型和 AI 场景下的二次权限校验。NoteWeave 的权限设计是很好的深挖点，因为 RAG 系统不是只要检索准，还必须保证“用户只能看到自己有权看的证据”。

## 3. 问答与讲解

### Q1：为什么要把 `PERSONAL` 和 `TEAM` 做成一等业务边界？

#### 面试官为什么问

面试官想知道你有没有领域建模能力。双空间会增加复杂度，如果你讲不清收益，就会被认为是过度设计。

#### 回答思路

先讲两类场景的差异：团队知识强调协作、共享、权限和发布；个人研究强调私有、探索、卡片化和确认沉淀。再讲如果混在一起会导致权限污染、知识污染和产品语义混乱。

#### 结合我的项目怎么答

NoteWeave 中 `Space.type = PERSONAL | TEAM`。团队侧资源包括 KnowledgeBase、Document、DocumentChunk、WikiPage、团队 Chat、团队 Artifact 和 SpaceMemory；个人侧资源包括 ResearchProject、Source、ArticleCard、ConceptCard、MethodologyCard、SynthesisCard 和 UserMemory。这个边界让后续上传、检索、Citation、Artifact 生成、Memory 写入都能先判断资源属于哪个业务域。

#### 技术原理 / 链路设计讲解

团队和个人的“知识可信度”不同。团队 Wiki 是人工确认后进入共享知识库，个人 Artifact 则默认只是个人产物，只有用户确认后才沉淀为 SynthesisCard。如果把二者混成一个 content 表，短期看少建几张表，长期会在权限、生命周期、索引策略和审计上变得难以维护。

#### 技术栈特点与选型理由

MySQL 适合表达这种强关系边界：资源表带 `space_id`、`user_id`、`research_project_id` 等隔离字段；Spring Service 层通过 `ResourceAccessService` 和 `SpacePermissionService` 统一校验；Elasticsearch 检索时也带 `spaceId/knowledgeBaseId/status` 过滤。

#### 可直接复述的面试回答

我把 `PERSONAL` 和 `TEAM` 设计成一等边界，是因为它们的权限语义和知识沉淀语义完全不同。团队侧强调共享知识库、成员角色、Wiki 发布和团队可见的 Citation；个人侧强调 owner-only 的研究资料、Source 编译、卡片化和用户确认后的沉淀。如果混成一套模型，短期代码看起来少，但检索过滤、Citation 权限、Memory 写入和 Artifact 发布都会互相污染。所以我用 Space 作为最高业务容器，让后续所有资源访问、检索和沉淀都先落在明确的空间边界里。

#### 常见追问

- 双空间是否会导致重复代码？
- 个人 Artifact 能不能直接发布到团队 Wiki？
- 如果一个用户同时在多个团队空间，检索怎么隔离？

#### 常见坑

不要只说“为了区分个人和团队”。要说出权限、生命周期、索引、沉淀和审计边界。

### Q2：为什么 `systemRole` 和 `space role` 要分开？

#### 面试官为什么问

这是典型权限模型题。面试官想看你是否能区分系统级权限和业务空间权限。

#### 回答思路

说明 `systemRole=ADMIN/USER` 是系统后台权限；`SpaceMember.role=OWNER/EDITOR/VIEWER` 是某个团队空间内的业务权限。二者维度不同，不能混用。

#### 结合我的项目怎么答

项目里 `ResourceAccessService` 对 Admin、Space 管理、上传、提问、Wiki 编辑、任务查看和任务操作做了区分。Admin 可以访问后台管理能力，但不应该被自然理解为某个团队的业务 OWNER；团队 OWNER 能管理团队资源，但不应该天然访问系统后台日志、健康检查、全局用户管理。

#### 技术原理 / 链路设计讲解

权限模型常见错误是把“平台管理员”和“空间管理员”混在一起。混用后会出现两个问题：第一，系统后台权限可能越权读取业务私有数据；第二，业务 OWNER 可能误获得系统管理能力。正确做法是 RBAC 分层：系统角色控制 `/admin/**`，空间角色控制空间内资源动作。

#### 技术栈特点与选型理由

Spring Security 负责认证入口，业务权限放在 Service 层而不是只靠 URL 拦截。这样 Citation 查询、任务操作、检索后置过滤等非 controller 入口也能复用同一套判断。

#### 可直接复述的面试回答

`systemRole` 和 `space role` 我是刻意分开的。`systemRole` 只描述用户是不是系统管理员，控制 Admin/Ops、健康检查、全局日志这类后台能力；`space role` 描述用户在某个团队空间里的业务身份，比如 OWNER、EDITOR、VIEWER。它们不是同一维度。团队 OWNER 不应该天然能看全局 LLM 日志，系统 ADMIN 也不能被简单等同为某个业务空间的协作者。分开以后，系统后台和业务资源访问的边界会更清晰，后续审计也更容易。

#### 常见追问

- Admin 能不能看所有空间任务？
- VIEWER 能不能提问？能不能上传？
- 如果一个用户是 A 空间 OWNER、B 空间 VIEWER，怎么判断？

#### 常见坑

不要说“Admin 权限最大所以什么都能看”。真实系统里管理员权限也要最小化和可审计。

### Q3：Citation 为什么要返回前二次权限校验？

#### 面试官为什么问

AI 系统最容易忽略的是“证据泄露”。回答本身可能看起来没有暴露原文，但 Citation、Trace、Snapshot 可能泄露敏感资料。

#### 回答思路

先说明检索前有权限 filter，但不能完全依赖前置 filter；再说明 Citation 是可回溯证据，读取时必须重新校验当前用户对 session、space、source 的访问权。

#### 结合我的项目怎么答

项目中团队 RAG 检索会按 `spaceId` 和 scoped `knowledgeBaseIds` 过滤，检索后还通过 MySQL 复核 Document 生命周期和 activeIndexVersion。Citation 查询时也不会只按 messageId 返回，而是通过 session/space 关系和 citation 指向资源做二次校验，避免旧 citation 在权限变化后继续泄露。

#### 技术原理 / 链路设计讲解

权限校验要覆盖资源生命周期。用户提问时有权限，不代表以后查询 citation 时仍有权限；文档被删除、知识库归档、成员被移除、版本切换后，旧引用都可能变成不可见资源。所以 Citation 不应该是“生成时塞进 message JSON 的静态字段”，而应该是关系表 + 查询时动态权限判断。

#### 技术栈特点与选型理由

MySQL 关系表适合保存 Citation、MessageCitation、ArtifactCitation、CardCitation 等正式关系；MinIO 可以保存 snapshot，但 snapshot 的 object key 不能绕过权限服务直接暴露；Elasticsearch 召回结果也要回查 MySQL 确认资源状态。

#### 可直接复述的面试回答

Citation 是证据，不只是展示字段，所以我会把它当成独立受保护资源处理。检索阶段虽然已经按 `spaceId`、知识库范围和状态做了过滤，但这只能保证当时召回尽量正确；用户后续查看 citation 时，成员角色、文档状态、知识库状态都可能变化。因此 Citation 查询必须二次校验 session 和 citation 指向资源的权限，不能简单从 message JSON 里把证据吐出来。这样可以避免用户被移出团队后仍通过历史回答看到原文证据。

#### 常见追问

- 如果 ES filter 漏了怎么办？
- Citation snapshot 存在 MinIO，object key 泄露怎么办？
- 如果用户保留了旧 answer 文本，是否还能完全阻止信息泄露？

#### 常见坑

不要只回答“因为安全”。要说出权限变化、旧引用、检索前置过滤不可靠、关系表动态校验这些具体点。

## 4. 本主题总结

权限主题最重要的是讲清楚：Space 是最高业务容器，系统角色和空间角色分离，资源访问走统一服务，检索和 Citation 都要做权限约束，生成内容进入长期知识前要有确认边界。

## 6. 整条链路深讲：一次资源访问如何被权限保护

面试官问权限时，可以把链路拆成“认证、空间归属、动作权限、检索过滤、证据回查、后台隔离”六步。

第一步是认证。用户通过 Spring Security 和 JWT 进入系统，请求里解析出当前用户身份。此时只能证明“你是谁”，不能证明“你能访问哪个资源”。

第二步是空间归属。NoteWeave 把 Space 作为最高业务容器，所有团队资源都挂在 TEAM Space 下，个人资源挂在 PERSONAL Space 或 ResearchProject 下。空间是后续权限判断的起点。

第三步是动作权限。不同动作需要不同权限：查看空间、上传文档、提问、编辑 Wiki、发布 Wiki、操作任务、访问 Admin 后台并不是同一种权限。项目通过 `ResourceAccessService` 和 `SpacePermissionService` 收口，而不是在 controller 里散落 if 判断。

第四步是检索前置过滤。团队 RAG 检索时，Elasticsearch 查询必须带 `spaceId`、`knowledgeBaseId`、资源状态等 filter。这样可以在召回阶段尽量把越权资源排除。

第五步是检索后置复核。ES 是检索视图，不是权威事实源，所以召回结果还要回到 MySQL 看 Document 是否删除、KnowledgeBase 是否归档、chunk 的 indexVersion 是否仍是 active。Citation 查询同理，不能因为历史 message 里有引用就直接返回证据。

第六步是 Admin 与业务权限分离。系统管理员能看 Admin/Ops 能力，但它不等价于某个团队的业务 OWNER；团队 OWNER 能管理团队空间，也不代表能访问全局 LLM 日志或系统健康详情。

这一整条链路背后的原则是：认证只解决身份，授权必须跟具体资源和动作绑定；检索系统只能做性能优化，最终权限事实必须由业务数据复核。

## 7. 原理与设计原因速查

- RBAC 为什么要分层：`systemRole` 控制系统后台，`space role` 控制空间内业务动作，二者混用会导致越权。
- 为什么权限不只放 controller：异步 Worker、Citation 查询、检索后处理、Admin 查询都可能绕过 controller，需要 service 层统一收口。
- 为什么 Citation 需要二次校验：用户生成回答时有权限，不代表后来查看证据时仍有权限。
- 为什么 ES filter 不够：ES 可能有索引延迟、旧版本 chunk、软删除残留，MySQL 才是业务状态事实源。
- 为什么个人资源 owner-only：个人研究资料、记忆和成果具有更强隐私性，不能简单继承团队共享模型。

## 8. 3 到 5 分钟深答模板

如果面试官问我权限怎么做，我会先说 NoteWeave 不是只做接口鉴权，而是围绕 Space 做资源级权限保护。用户登录后只能得到身份，真正访问资源时还要看资源属于哪个 Space、用户在这个 Space 里是什么角色，以及当前动作是查看、上传、提问、编辑还是发布。比如团队 RAG 问答时，先由 `ResourceAccessService.requireAskQuestion` 校验提问权限，再根据 session scope 得到可见知识库，ES 检索时带 `spaceId` 和 `knowledgeBaseId` 过滤，召回后再用 MySQL 复核文档状态和 activeIndexVersion。Citation 查询时也不会直接从历史 message JSON 返回，而是重新检查 session、space 和 citation 指向资源的权限。这样即使成员角色变化、文档被删除或知识库归档，旧引用也不会继续泄露证据。系统后台又通过 `systemRole=ADMIN` 单独控制，不和团队 OWNER 混用，避免把业务管理权限扩大成全局管理权限。
