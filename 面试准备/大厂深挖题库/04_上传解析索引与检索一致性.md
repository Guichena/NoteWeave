## 3. 问答与讲解

### Q1：团队文档上传链路是怎么走的？

#### 面试官为什么问

面试官想看你是否真的做过文件链路，而不是只写了一个 MultipartFile 接口。

#### 回答思路

按阶段讲：init upload、chunk upload、status、merge、FileObject、Document、Task、Worker parse、chunk、index、active version。

#### 结合我的项目怎么答

项目中 `DocumentUploadService` 负责 init、分片上传、状态查询、merge 和 cancel。init 时校验 content type、文件信息和上传权限；分片上传会把 chunk 存到 MinIO，同时用 Redis bitmap 记录完成分片；merge 时校验所有 chunk 存在，计算 SHA-256 contentHash，合并到最终对象，创建或复用同空间 FileObject，创建 Document，增加 refCount，再创建 `DOCUMENT_PROCESS` Task。

#### 技术原理 / 链路设计讲解

链路可以表达为：

```text
initUpload -> uploadChunk -> Redis bitmap/status -> merge chunks
-> FileObject(contentHash/objectKey/refCount)
-> Document(PENDING_PROCESS)
-> TaskOutbox -> Kafka -> DocumentProcessingService
-> parse -> chunk -> ES bulk index -> activeIndexVersion switch
```

这个设计把上传、对象存储、业务元数据和异步解析解耦。HTTP 请求只负责把文件可靠进入系统，不把解析索引放在同步链路里阻塞用户。

#### 技术栈特点与选型理由

MinIO 适合存分片、最终对象和 parsed text；Redis bitmap 适合记录短期上传进度；MySQL 保存上传、FileObject、Document、Chunk 等业务状态；Kafka Worker 处理解析和索引；Elasticsearch 承载检索。

#### 可直接复述的面试回答

团队文档链路不是一个简单上传接口。我把它拆成 init、chunk upload、status、merge 和异步处理几个阶段。init 会校验文件类型和上传权限；chunk 上传时分片对象进 MinIO，同时用 Redis bitmap 记录哪些分片完成；merge 时先校验 DB 记录、bitmap 和 MinIO chunk 都完整，再计算服务端 SHA-256，合并成最终对象。然后在 MySQL 中创建或复用同空间的 FileObject，创建 Document，并通过 Task/Outbox/Kafka 投递 `DOCUMENT_PROCESS`。Worker 再做解析、切片、保存 parsed text、写 ES 索引，成功后切换 activeIndexVersion，让文档进入可检索状态。

#### 常见追问

- 为什么 Redis bitmap 不能作为唯一事实？
- merge 重复调用怎么保证幂等？
- 为什么 contentHash 用服务端算？

#### 常见坑

不要说“前端传 md5 就相信它”。项目 merge 阶段会服务端计算 SHA-256，前端 fileMd5 只能辅助上传流程。

### Q2：为什么 FileObject 复用要限制在同一个 `spaceId`？

#### 面试官为什么问

这是权限和存储复用结合题。面试官想看你是否知道“内容相同”不代表“权限相同”。

#### 回答思路

说明对象内容可以复用，但 Document 元数据和权限必须独立。同空间复用可以节省存储；跨空间复用会带来权限推断和生命周期耦合风险。

#### 结合我的项目怎么答

`DocumentUploadService` 中 FileObject 通过 `spaceId + contentHash` 查找。即使文件内容一样，不同 Space 也会创建各自的 Document 元数据和 FileObject 记录。这样可以避免 A 团队上传过某个文件后，B 团队通过秒传行为推断 A 团队资料存在。

#### 技术原理 / 链路设计讲解

跨租户去重有隐私风险：用户可以通过上传某个敏感文件的 hash，看系统是否秒传，从而推断其他租户是否拥有该文件。即使 objectKey 物理上可复用，业务上也必须隔离权限、引用计数、删除生命周期和审计。

#### 技术栈特点与选型理由

MySQL 的 `FileObject` 不是纯物理文件表，而是带空间边界的对象引用表。MinIO 存储层可以相对简单，权限不下沉到 object key 本身，而在业务层控制。

#### 可直接复述的面试回答

我把 FileObject 复用限制在同一个 `spaceId`，核心原因是内容相同不代表权限相同。秒传只能复用对象内容，不能复用业务可见性。如果跨空间按 hash 复用，用户可能通过秒传结果推断其他团队是否上传过某份敏感文件，而且删除、refCount、审计也会耦合。当前设计是同空间内用 contentHash 节省存储，不同空间即使内容一样，也有独立的 FileObject/Document 元数据和权限生命周期。

#### 常见追问

- 这样是否浪费存储？
- 如果未来要做全局去重，怎么防推断攻击？
- soft delete 后 refCount 为什么不立刻减？

#### 常见坑

不要只从节省空间角度回答。这个问题重点是多租户隔离和侧信道风险。

### Q3：为什么需要 `activeIndexVersion`？重建索引失败怎么办？

#### 面试官为什么问

这是检索一致性和可用性题。面试官想知道你是否考虑过重索引期间的新旧版本切换。

#### 回答思路

说明不能先删旧索引再写新索引。正确做法是创建新 indexVersion，写成功后切 active；失败则旧版本仍可用。

#### 结合我的项目怎么答

`DocumentProcessingService` 每次处理会计算 nextVersion，解析切片后创建对应 indexVersion 的 chunks，写入 ES。成功后更新 Document 的 `activeIndexVersion`、parsedTextObjectKey、parseStatus、indexStatus，并同步 ES chunk 状态。失败时如果旧 active 版本存在，文档仍保持 INDEXED 和旧索引可用；如果没有旧版本，才标记 FAILED。

#### 技术原理 / 链路设计讲解

这是一种版本化索引切换策略。它避免“重建失败导致线上不可检索”。检索时不仅按 `documentStatus` filter，还会通过 MySQL 复核 activeIndexVersion，确保召回 chunk 对应当前有效版本。

#### 技术栈特点与选型理由

MySQL 保存 authoritative active version，Elasticsearch 保存可检索副本。ES 是搜索视图，不是最终事实源，所以关键状态要回查 MySQL。

#### 可直接复述的面试回答

`activeIndexVersion` 是为了解决重建索引期间的一致性问题。我不会先删旧索引再写新索引，因为新索引一旦失败，用户就完全搜不到了。当前做法是每次处理生成新的 indexVersion，解析、切片、bulk index 都成功后，再把 Document 的 activeIndexVersion 切到新版本。如果失败且旧版本存在，就保留旧的 INDEXED 状态和旧索引可用；只有没有可用旧版本时才把文档标记失败。检索时 ES 召回后还会结合 MySQL 的 activeIndexVersion 和文档状态做复核。

#### 常见追问

- 旧版本索引什么时候清理？
- 如果 ES 写成功但 DB 切换失败怎么办？
- 如何避免删除文档后旧 chunk 被召回？

#### 常见坑

不要说“ES 写完就是最终状态”。ES 只是检索视图，MySQL 的文档状态和 active version 才是权威状态。

## 6. 整条链路深讲：文件如何从上传变成可检索证据

第一步是初始化上传。用户选择知识库后调用 init upload，服务端先校验 KnowledgeBase 是否 active，再通过 `ResourceAccessService.requireUploadDocument` 判断用户是否能上传。然后创建 DocumentUpload，记录文件名、content type、fileMd5、totalSize、chunkSize、totalChunks、expiresAt。

第二步是分片上传。每个 chunk 会先校验 chunkIndex、文件大小和上传状态，再写入 MinIO 的临时 chunk object。Redis bitmap 记录某个 uploadId 下哪些 chunk 已完成，UploadChunk 表记录 chunkMd5、size、objectKey。Redis 只做进度加速，DB 和 MinIO 才是最终校验依据。

第三步是 merge。服务端会确认所有 chunk 都上传完成，且 MinIO 里的 chunk object 存在，然后从 chunk 计算服务端 SHA-256 contentHash，合并成最终 objectKey。这里不完全相信前端 fileMd5，因为安全和一致性必须由服务端确认。

第四步是对象复用。系统按 `spaceId + contentHash` 查找 FileObject，同一个空间内相同内容可以复用，节省对象存储；不同空间不复用业务对象，避免跨租户通过秒传推断文件存在。Document 创建成功并绑定 FileObject 后，才增加 refCount。

第五步是创建异步解析任务。Document 初始状态是 PENDING_PROCESS，merge 后创建 `DOCUMENT_PROCESS` Task，经 outbox/Kafka 进入 Worker。

第六步是解析和切片。`DocumentProcessingService` 读取 MinIO 最终对象，使用 `DocumentParserService` 解析文本，再由 `ChunkService` 切片，保存 DocumentChunk。解析后的完整文本会保存为 parsedTextObjectKey，方便后续重处理、调试或其他生成链路复用。

第七步是索引写入与版本切换。每次处理都会生成新的 indexVersion。Worker 先写新版本 chunk 和 ES 索引，全部成功后才更新 Document.activeIndexVersion。这样重建失败时旧版本仍然可检索。

第八步是检索时复核。RAG 检索不是只相信 ES，召回后还要看 Document 是否 DELETED、KnowledgeBase 是否 ACTIVE、chunk.indexVersion 是否等于 activeIndexVersion，避免旧索引或软删除资源被返回。

## 7. 原理与设计原因速查

- 为什么分片上传：大文件一次上传失败成本高，分片支持断点续传、进度展示和失败重试。
- 为什么 Redis bitmap 不能作为唯一事实：Redis 有 TTL 和丢失风险，最终完整性必须由 DB 记录和 MinIO object 存在性确认。
- 为什么 FileObject 复用按 space 限制：跨空间秒传会造成隐私侧信道和生命周期耦合。
- 为什么 soft delete：Citation、Trace、ArtifactSource 可能还引用旧资源，直接物理删除会破坏审计链。
- 为什么 parsed text 要保存：chunk 是检索粒度，parsed text 是完整中间产物，便于重切片、重新索引、证据回查和排障。
- 为什么 activeIndexVersion 必要：避免新索引失败把旧索引也破坏，保证检索链路有最后一个可用版本。

## 8. 3 到 5 分钟深答模板

文档链路我会从上传可靠性和检索一致性两部分讲。上传时先 init，记录上传元数据和过期时间，分片进 MinIO，Redis bitmap 只做进度记录，UploadChunk 表保存每个分片的 objectKey 和校验信息。merge 时服务端会确认所有 chunk 记录、bitmap 和 MinIO 对象都完整，再计算 SHA-256 contentHash 并合并最终对象。然后在同一个 Space 内按 contentHash 复用 FileObject，但不同 Space 不复用，避免跨租户推断。Document 创建后通过 Task/Outbox/Kafka 进入解析 Worker。Worker 读取对象，解析成文本，保存 parsed text，再切成 DocumentChunk 并写入 ES。索引不是覆盖式，而是每次生成新的 indexVersion，成功后才切换 activeIndexVersion；失败时如果旧版本存在，就继续保持旧版本可检索。查询时 ES 只是搜索视图，最终还要用 MySQL 文档状态和 activeIndexVersion 复核，避免软删除文档或旧版本 chunk 被 RAG 召回。
