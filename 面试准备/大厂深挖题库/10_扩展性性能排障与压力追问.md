# 文件：10_扩展性性能排障与压力追问.md

## 0. 本篇定位

这篇负责扩展性、性能、排障和压力追问。它适合回答没有生产指标时怎么稳住、文档量上升后哪里先瓶颈、如果拆微服务先拆哪里、引用不准或召回差时怎么排查，以及哪些高级能力已经有落地样例、哪些仍然只能作为扩展方向讲。

## 1. 本主题面试官想考什么

这个主题模拟大厂后半场压力面：扩展性、性能瓶颈、线上故障、容量增长、数据一致性、安全边界和未来演进。重点不是让你编造线上指标，而是看你能否基于当前实现诚实推演。

## 3. 问答与讲解

### Q1：如果文档量扩大一个数量级，当前系统哪里最先成为瓶颈？

#### 面试官为什么问

面试官想看你是否能做容量推演，而不是只说“加机器”。

#### 回答思路

从上传、解析、索引、检索、生成、观测表几个层面分析。不要编造具体 QPS；讲会监控哪些指标和如何优化。

#### 结合我的项目怎么答

当前最可能先遇到瓶颈的是文档处理 Worker、ES 索引写入与查询、Embedding backfill、Citation/Trace 日志表增长、以及 evidence context 的 token 长度。Task/Outbox/Kafka 已经给异步扩展留下入口，但还需要队列分区、Worker 水平扩容、索引分片策略、日志归档和评测指标。

#### 技术原理 / 链路设计讲解

文档量增长会带来三类压力：

- 写入压力：parse/chunk/index/embedding 任务堆积。
- 查询压力：ES filter、BM25、vector recall、RRF、post-process 耗时增加。
- 存储压力：DocumentChunk、Citation、RetrievalTrace、LLMCallLog 膨胀。

优化顺序应先度量：task latency、queue lag、ES query latency、retrieval hit quality、citation coverage、LLM latency、token usage。

#### 技术栈特点与选型理由

Kafka 可以通过 topic partition 和多 worker 扩展；ES 可以通过 shard、alias、index lifecycle 优化；MySQL 大表需要归档、索引和分页；LLM 成本通过 evidence topK、contextMaxChars 和 prompt version 控制。

#### 可直接复述的面试回答

如果文档量扩大一个数量级，我不会先说加机器，而是先看链路指标。最可能先成为瓶颈的是异步处理任务堆积、ES 索引写入和查询延迟、embedding backfill 成本，以及 Trace/Citation/LLM 日志表增长。当前 Task/Outbox/Kafka 已经让 Worker 水平扩展有基础，但还要看 Kafka lag、task attempt 耗时、ES query latency、召回质量和 token 使用。优化上会先做 Worker 分组和限流、ES shard/alias 和索引生命周期、Trace/Log 归档，再根据 Eval 的 recall@k、MRR、citation coverage 判断是否调整 RRF 权重和 chunk 策略。

#### 常见追问

- ES 查询慢怎么定位？
- Worker 扩容会不会重复执行任务？
- Trace 表太大怎么办？

#### 常见坑

不要编造“当前 QPS 多少、P99 多少”。仓库没有生产压测数据，应该说会测什么、在哪里已有观测入口。

### Q2：如果要拆成多服务，你会先从哪里拆？

#### 面试官为什么问

这是架构演进题。面试官不一定希望你现在就微服务，而是看你能否按边界拆。

#### 回答思路

先说明当前单体合理性：开发效率、事务简单、原型阶段。再说未来可按异步任务、检索、LLM 观测、Admin 等边界拆。

#### 结合我的项目怎么答

当前 NoteWeave 是 Spring Boot 单体，但模块边界较清晰：auth/space/permission、task、team document、rag/search、personal、artifact、memory、admin。若拆分，优先考虑把 Worker 执行侧、检索/索引侧、LLM gateway/eval 侧拆出去，因为它们资源特征和扩展需求不同。

#### 技术原理 / 链路设计讲解

拆服务应遵循“高资源差异、高变更隔离、低事务耦合”。不建议先拆 auth 或空间权限，因为大量业务需要强依赖权限判断。Worker 和检索服务更适合先拆，因为它们本来通过 Task/Kafka 和 ES 边界解耦。

#### 技术栈特点与选型理由

Task/Kafka 是天然服务边界；ES/MinIO/MySQL 需要重新设计数据所有权；权限服务拆出后要注意调用延迟和缓存一致性。

#### 可直接复述的面试回答

当前我会先保持单体，因为项目还处于工程工作台和产品原型阶段，单体能保证事务和迭代效率。但如果未来要拆，我不会按 controller 包机械拆，而是按资源特征拆。第一优先级是 Worker 执行侧，因为文档解析、embedding、Artifact 生成、Eval 和 cleanup 都已经通过 Task/Kafka 解耦，适合独立扩容。第二是检索/索引服务，因为 ES 查询和索引写入资源特征明显。第三是 LLM gateway/eval/observability。权限和 Space 我会更谨慎，因为它们是所有业务访问的基础边界，过早拆会带来大量远程调用和一致性问题。

#### 常见追问

- 拆 Worker 后如何共享 DB？
- 权限服务如果远程调用失败怎么办？
- 微服务后 outbox 还怎么做？

#### 常见坑

不要说“拆成用户服务、订单服务、商品服务”这种和项目无关的电商模板。要贴 NoteWeave 边界。

### Q3：如果 Citation 被用户质疑不准确，你怎么排查？

#### 面试官为什么问

这是从结果倒查链路的压力题。考察你对 RAG 每层的可观测理解。

#### 回答思路

按 citation -> evidence item -> retrieval trace -> source chunk -> document/source version -> prompt answer 逆向排查。

#### 结合我的项目怎么答

先查 `message_citation` 和 `citation` 记录，确认 sourceType、sourceId、chunkId、sourceVersion、quoteHash 和 snapshotObjectKey；再查 RetrievalTraceItem，看这个 evidence 来自 BM25、Vector 还是 Wiki，fusion rank 和 score 如何；再回查 DocumentChunk 或 Source text，确认 offset/内容是否一致；最后看 TeamRagPromptBuilder 构造的 evidence 编号和 LLM 输出是否引用错编号。

#### 技术原理 / 链路设计讲解

Citation 不准可能有四类原因：

- 召回错：retriever 找错 chunk。
- 后处理错：相邻合并或截断导致上下文错位。
- 持久化错：citation 绑定了错误 chunk/sourceVersion。
- 生成错：模型引用编号和文本不匹配。

排查需要把“证据是否正确”和“模型是否正确使用证据”分开。

#### 技术栈特点与选型理由

关系化 Citation、RetrievalTrace、LLMCallLog 让这条排查路径可执行。如果 citation 只在 JSON 里，就很难定位。

#### 可直接复述的面试回答

我会把 citation 不准拆成几层查。第一步查 citation 关系本身，看 sourceType、sourceId、chunkId、sourceVersion、quoteHash 和 snapshot 是否对得上。第二步查 RetrievalTraceItem，看这个证据来自哪一路召回，fusion rank 和 score 是什么。第三步回到 DocumentChunk 或 Source 原文，看内容、版本和 offset 是否一致。第四步看 prompt 里的证据编号和最终 answer，判断是不是模型引用错编号。这样可以区分是召回问题、后处理问题、持久化问题，还是生成阶段没有按证据回答。

#### 常见追问

- 如果原文已经更新，旧 citation 怎么办？
- 如果 snapshot 和 source 不一致，以哪个为准？
- 如何在 Eval 里发现 citation 错误？

#### 常见坑

不要直接说“调大 topK”。citation 不准不一定是召回少，也可能是证据处理和生成对齐问题。

### Q4：MCP 和 Bibtex 如果被追问，怎么诚实回答？

#### 面试官为什么问

这是简历风险控制题。面试官会故意追你简历里的高级词，看你是否夸大。

#### 回答思路

要把 MCP 和 Bibtex 分开讲。Bibtex 当前确实还是扩展方向；MCP 则已经有一个落地样例，但不是完整开放平台。然后说明它们分别接在哪个模块。

#### 结合我的项目怎么答

MCP 当前已经有一个真实落地样例：B 站解析能力被拆成远程 MCP tool service，主系统通过产物入口和对话显式触发来调用它，后面仍然走受控 artifact workflow。Bibtex 可以作为一种 Source importer，解析论文元数据、引用关系和 PDF 链接，进入 `Source -> ArticleCard/ConceptCard` 链路。当前仓库主链路已实现 TEXT/FILE/URL，不要说 Bibtex 已端到端实现。

#### 技术原理 / 链路设计讲解

好的回答不是删除这些词，而是把它们收敛成工程扩展点：

- MCP：当前已经先落了远程 B 站 tool service 这个样例，更广义的工具协议/外部上下文接入还需要权限、沙箱、审计、超时和输出 schema。
- Bibtex：学术资料元数据 importer，需要 DOI/title/authors/year/venue/file link，并映射为 Source metadata。

#### 技术栈特点与选型理由

当前 SourceService、Task、ArtifactPlanExecutor、SkillExecutionLog 都能承接扩展，但还缺具体 parser、权限声明和工具调用安全边界。

#### 可直接复述的面试回答

如果被问到 MCP 和 Bibtex，我会诚实区分当前实现和扩展方向。当前仓库主链路里，Source 导入已经支持 text、file 和 URL，但 Bibtex 还不是端到端能力；它很适合作为后续 Source importer，解析论文元数据和 PDF 链接后进入现有 Source 编译链路。MCP 则不能再说成“完全没做”，因为当前已经把 B 站解析能力拆成远程 MCP tool service，并接到 Studio 产物入口和对话显式触发链路；但项目里的 Skill 仍然是受控生成 pipeline，不是完整开放 MCP 工具体系。这样讲既体现我理解扩展方向，也不夸大现状。

#### 常见追问

- 如果接 MCP，如何做权限和审计？
- Bibtex 导入如何和 PDF 解析关联？
- 外部工具调用失败如何影响 Artifact？

#### 常见坑

不要硬说“已经实现 MCP/Bibtex”。面试官一追实现位置、接口、测试就会露馅。

## 4. 本主题总结

压力追问的核心不是背答案，而是保持诚实边界：能基于当前实现推演瓶颈、扩展和故障；能说明已有观测入口；不编造生产数据；不把扩展方向说成已实现事实。

## 6. 整条链路深讲：如何做容量、性能和稳定性推演

第一步是明确不编造指标。当前仓库是工程工作台和可本地验收原型，没有真实线上 QPS、P99、token/day。面试中应该说“我会这样测和这样优化”，而不是给虚构数字。

第二步是按链路拆瓶颈。资料进入阶段看 upload success rate、chunk merge latency、MinIO object 操作耗时；处理阶段看 Task pending/running 数、Kafka lag、Worker attempt latency、parse failure rate、embedding backfill latency；检索阶段看 ES query latency、BM25/vector/wiki 命中量、fusion latency、post-process latency；生成阶段看 LLM latency、token usage、timeout、no-evidence rate；沉淀阶段看 Artifact generation success rate、distillation stale proposal rate；运维阶段看 cleanup job failure 和 health snapshot。

第三步是按资源类型优化。CPU 密集的是解析、切片、embedding；IO 密集的是 MinIO 读写、ES bulk index、MySQL 日志写入；外部依赖慢的是 LLM provider。不同瓶颈不能都用“加缓存”回答。

第四步是按风险降级。ES 不可用时，RAG 应返回明确检索失败或无证据兜底，不能让模型自由发挥；LLM 不可用时，检索和证据可以仍然展示，但生成失败要有可恢复状态；Kafka 不可用时，Task 已落库和 outbox 已落库，等待补偿投递；Redis 不可用影响 WebSocket ticket/resume，但不应破坏已持久化消息。

第五步是按边界扩展。Worker 是最适合先水平扩展或独立部署的边界；检索/索引服务是第二边界；LLM gateway/eval/observability 是第三边界；权限和 Space 是基础域，过早拆分会引入远程调用和一致性问题。

## 7. 原理与设计原因速查

- 为什么不能只说加机器：不同阶段瓶颈不同，解析、ES、LLM、MySQL、Kafka 的优化手段完全不一样。
- 为什么先看 Task/Kafka：长任务堆积是资料进入系统后最容易暴露的吞吐瓶颈。
- 为什么看 no-evidence rate：它能反映召回质量、权限 filter 过严、索引缺失或 query 表达问题。
- 为什么看 citation coverage：它衡量生成结果是否被证据支撑，但不等价于答案一定正确。
- 为什么微服务先拆 Worker：Worker 天然通过 Kafka 和 Task 解耦，事务耦合比权限域低。
- 为什么要把 MCP 和 Bibtex 分开讲：Bibtex 当前没有主链路实现；MCP 已有远程 tool service 落地样例，但仍然不能夸大成完整开放平台。

## 8. 3 到 5 分钟深答模板

如果面试官问扩展性，我会先明确当前没有生产 QPS/P99，不会编造数字，但系统已经有可以度量的面。容量推演我会按链路拆：上传看分片成功率、merge 延迟和 MinIO 操作；异步处理看 Task 状态分布、Kafka lag、Worker attempt 耗时和失败率；检索看 ES query latency、BM25/Vector/Wiki 命中量、RRF fusion latency 和 no-evidence rate；生成看 LLM latency、token usage、timeout 和 citation coverage；运维看 health snapshot 和 cleanup job。优化上，长任务堆积先扩 Worker、分 topic 或调 partition；ES 慢就看 shard、filter、索引 alias、向量维度和查询 DSL；LLM 慢就控制 evidence topK、contextMaxChars、超时和降级；日志表膨胀就做归档和保留期。如果未来拆服务，我会先拆 Worker 执行侧和检索索引侧，因为它们资源特征明显且已经有 Kafka/ES 边界；权限和 Space 不会过早拆，因为它们是全局访问控制的基础域。
