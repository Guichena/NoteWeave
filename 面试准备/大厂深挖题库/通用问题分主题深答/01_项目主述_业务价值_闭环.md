## 2. 架构视角怎么切入

NoteWeave 不应该讲成“我做了一个 RAG 问答系统”，而应该讲成“我做了一个权限约束下、可追踪、可沉淀、可运维的 AI 知识工作台”。这句话里有四个面试官会关心的点：

- `权限约束`：团队知识和个人资料不能混用，检索和 citation 都必须守住空间边界。
- `可追踪`：回答、Artifact、Card、Wiki 都能追溯到 Source、DocumentChunk、Citation、Snapshot、Trace。
- `可沉淀`：生成结果不是一次性文本，而能经确认进入 Wiki 或 SynthesisCard。
- `可运维`：坏回答能通过 RetrievalTrace、LLMCallLog、Eval、Admin/Ops 排查。

## 3. 完整链路深讲

### 3.1 团队知识闭环

团队侧的主线是：

```text
KnowledgeBase
-> DocumentUpload
-> FileObject / Document
-> DOCUMENT_PROCESS Task
-> Parsed Text / DocumentChunk
-> Elasticsearch BM25 / Vector Index
-> HybridRetriever
-> EvidencePostProcessor
-> TeamRagPromptBuilder
-> LLM Answer
-> Citation / RetrievalTrace
-> Wiki Draft / WikiPageVersion
```

这条链路解决团队知识问答的可信问题。用户上传文档后，系统不会同步阻塞解析，而是进入统一 Task/Outbox/Kafka Worker。解析后的 chunk 进入检索系统，问答时先检索证据，再让 LLM 基于证据回答。回答产生 Citation，后续稳定结论可以沉淀为 Wiki。

### 3.2 个人研究闭环

个人侧的主线是：

```text
ResearchProject
-> Source(TEXT / FILE / URL)
-> SOURCE_IMPORT
-> readable raw/parsed text
-> SOURCE_COMPILE
-> ArticleCard / ConceptCard / Citation
-> Artifact Generation
-> ArtifactVersion
-> user confirmation
-> SynthesisCard
```

这条链路解决个人研究资料从“杂乱资料”到“结构化知识”和“可复用成果”的问题。Source 只有在有可读文本后才能 READY；Card 的 evidence 要回溯 Source；Artifact 不是自动进入长期知识，而是确认后沉淀。

### 3.3 共用底座

两条主线共用这些底座：

- `Space / Permission`：所有资源先落到空间边界。
- `Task / Outbox / Kafka / Worker`：长任务统一执行。
- `MinIO`：存原文、解析文本、snapshot。
- `Elasticsearch`：团队 RAG 检索和 Wiki 检索。
- `Redis`：WebSocket runtime、ticket、短期状态。
- `MySQL`：业务状态、关系、citation、memory、trace、admin。
- `ObservedLlmGateway`：LLM 调用日志、prompt version、token、latency。

## 5. 为什么这么设计

### 5.1 为什么不是普通 RAG Demo

普通 RAG 往往只做：

```text
上传文档 -> 切片 -> 向量检索 -> 拼 prompt -> 回答
```

NoteWeave 做的是：

```text
权限 -> 异步处理 -> 多路检索 -> 证据后处理 -> 生成 -> 引用持久化 -> 评测观测 -> 长期沉淀
```

差异在于普通 RAG 只关注“能不能答”，NoteWeave 关注“能不能可信地答、能不能追踪、能不能运维、能不能沉淀”。

### 5.2 为什么团队和个人要分开

团队知识和个人研究的生命周期不同：

- 团队侧重共享、权限、Wiki 发布、团队可见证据。
- 个人侧重私有、探索、Source 编译、Card 和 Artifact。

如果混用一套模型，会导致个人探索污染团队知识、团队权限泄露个人资料、Artifact 自动进入长期知识库等问题。

### 5.3 为什么生成不直接成为知识

LLM 生成结果不一定稳定可信。如果自动进入 Wiki 或 Card，会污染长期知识。NoteWeave 用 Artifact 作为中间层，团队侧要发布，个人侧要 confirm，才能进入长期知识。

## 6. 可直接复述的深答

NoteWeave 是一个 AI 知识工作台，核心不是单次问答，而是知识从资料进入系统、被检索引用、生成成果，再沉淀为长期知识的闭环。团队侧从 KnowledgeBase 和 Document 开始，文件经过分片上传、FileObject 复用、异步解析、切片和索引后进入 Hybrid RAG；用户提问时，系统先做权限过滤，再用 BM25、向量和 Wiki recall 召回证据，用 RRF 融合并做证据后处理，最后让 LLM 基于证据回答，并保存 Citation 和 RetrievalTrace。个人侧从 ResearchProject 和 Source 开始，Source 必须导入出可读文本，再由 WikiCompiler 编译成 ArticleCard 和 ConceptCard，后续 Artifact 生成读取这些卡片和证据，用户确认后才沉淀为 SynthesisCard。底层复用 Space/Permission、Task/Outbox/Kafka、MinIO、ES、Redis、MySQL 和可观测体系。所以这个项目的技术含量不在“接了大模型”，而在把 AI 输出放进一个权限清晰、证据可追、状态可恢复、质量可评估的工程闭环里。

## 7. 追问兜底

### 如果问“项目没上线，价值怎么体现”

可以回答：当前没有真实生产流量，所以我不会编造 QPS 或用户量。阶段价值体现在可本地验收的端到端闭环、完整集成测试、可观测链路、Admin/Ops 和可扩展架构。上线前会进一步补压测、Eval case、灰度和告警。

### 如果问“你具体负责什么”

不要说“全部都是我”。可以说主讲 ownership 在三块：统一异步骨架、evidence-first RAG/Citation、Artifact 到长期知识的沉淀边界。

### 如果问“最大难点是什么”

回答重点：不是模型调用，而是权限、一致性、证据、运行态和长期知识之间的边界控制。
