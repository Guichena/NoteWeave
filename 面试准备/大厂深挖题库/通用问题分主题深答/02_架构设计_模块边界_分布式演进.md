# 文件：02_架构设计_模块边界_分布式演进.md

## 1. 本主题覆盖的通用问题

- 项目整体架构是怎样设计的？
- 为什么这么设计，为什么不用别的方案？
- 如果把单体项目扩展成分布式架构，你会做哪些改动？
- 项目有没有微服务，为什么当时这么拆或为什么先没拆？
- HTTP SDK 改 RPC 会怎么改？
- 有没有网关、注册中心、配置中心，为什么这么选？

## 2. 架构视角怎么切入

NoteWeave 当前是模块化单体，而不是微服务。这个回答要讲得坚定，不要把“没拆微服务”说成短板。正确切入是：

当前阶段更需要清晰领域边界、快速迭代和本地事务一致性；因此采用模块化单体。模块边界已经按未来可拆服务的方向组织，包括：

- 身份与权限域：auth、user、space、permission。
- 异步任务域：task、worker、outbox。
- 团队知识域：team document、kb、wiki、rag。
- 个人研究域：personal source、card、compiler、generation。
- 生成成果域：artifact、studio、methodology。
- 运行态与记忆域：chat runtime、memory。
- 观测运维域：prompt、llm、rageval、admin。

## 3. 完整链路深讲：从模块化单体到可拆分架构

### 3.1 请求入口

```text
Browser / Static Workbench
-> Spring MVC API / WebSocket
-> Security / CurrentUser
-> Controller
-> Service
-> Repository / External Client
```

普通业务 API 走 `/api/v1`，WebSocket 走 `/ws/chat/{ticket}`。认证由 Spring Security/JWT 处理，但资源权限在 service 层继续校验。

### 3.2 数据与中间件职责

```text
MySQL: 业务状态、任务、引用、关系、memory、trace、admin
MinIO: 原文件、分片、parsed text、snapshot、导出文件
Elasticsearch: BM25 / Vector / Wiki 检索视图
Kafka: 长任务分发
Redis: WebSocket runtime、ticket、上传 bitmap、短期事件状态
LLM Provider: 生成能力
```

面试中要强调：每个中间件都有边界，不要把 Redis 说成主队列，也不要把 ES 说成业务事实源。

### 3.3 未来拆分路径

如果项目要走分布式，不建议按 controller 包名拆，而要按资源特征拆。

第一阶段拆 Worker：

```text
API Service
-> MySQL Task / Outbox
-> Kafka
-> Worker Service
-> MinIO / ES / LLM
```

理由：Worker 天然通过 Kafka 解耦，解析、embedding、Artifact 生成、Eval、cleanup 都是资源消耗型任务，适合独立扩容。

第二阶段拆 Search/RAG：

```text
API Service
-> Search/RAG Service
-> Elasticsearch
-> RetrievalTrace
```

理由：检索查询、RRF、rerank、SearchDebug 和索引管理有独立性能和演进需求。

第三阶段拆 LLM Gateway / Eval：

```text
Business Service
-> LLM Gateway
-> Provider adapters
-> LLMCallLog / PromptVersion / Eval
```

理由：模型路由、token 统计、超时重试、prompt version 和评测可以统一治理。

权限域不建议第一批拆，因为几乎所有资源访问都依赖权限判断，过早拆会带来远程调用、缓存一致性和故障传播。

## 4. 关键实现锚点

- `ResourceAccessService`：资源权限收口。
- `TaskService` / `TaskDispatcher`：异步边界。
- `ObservedLlmGateway`：LLM 调用收口。
- `SearchIndexService` / `HybridRetriever`：检索边界。
- `SystemHealthService`：中间件健康检查边界。
- `RequestIdHolder`：请求追踪基础。

## 5. 为什么这么设计

### 5.1 为什么不一开始微服务

一开始微服务会带来：

- 分布式事务复杂度。
- 服务间鉴权和权限一致性问题。
- 部署、注册、配置、日志链路复杂度。
- 本地开发和测试成本上升。

当前项目更需要先把业务闭环、数据模型和权限边界打稳。模块化单体并不等于无架构，它只是把服务拆分延后到有真实容量压力和团队规模之后。

### 5.2 为什么保留可拆边界

虽然当前是单体，但 Task/Kafka、ES、LLM Gateway、Admin/Eval 都已经天然形成边界。未来拆服务时，可以复用这些边界，而不是重写业务模型。

### 5.3 HTTP 改 RPC 怎么看

外部 API 保持 HTTP/REST 更合适；内部高频服务间调用在微服务阶段可以引入 RPC。但要处理：

- 超时和重试。
- 幂等和 requestId。
- 错误码映射。
- 鉴权上下文传递。
- 链路追踪。
- 降级和熔断。

## 6. 可直接复述的深答

NoteWeave 当前是模块化单体，不是一开始就微服务。这个选择是有意的，因为项目还在快速迭代阶段，权限、Task、Citation、Artifact、Memory 之间有很多强关系，单体可以让事务边界和本地测试更简单。但我在设计上保留了未来拆分边界：长任务通过 Task/Outbox/Kafka 解耦，Worker 最适合第一批拆；检索通过 Elasticsearch 和 HybridRetriever 收口，后续可以拆 Search/RAG 服务；LLM 调用通过 ObservedLlmGateway 收口，后续可以拆 LLM Gateway 和 Eval 服务。权限和 Space 是所有资源访问的基础域，我不会一开始拆出去，因为那会让每次资源访问都变成远程调用，还要处理缓存一致性和权限变更问题。整体来说，当前阶段选择模块化单体是为了快速打通闭环，未来按资源特征拆，而不是按包名机械拆。

## 7. 追问兜底

### 如果问“单体是不是不够高级”

回答：架构不是越分布式越高级。没有真实规模和团队协作压力时，模块化单体更利于迭代和一致性。关键是边界是否清晰，是否能平滑演进。

### 如果问“拆 Worker 后 DB 怎么办”

回答：第一阶段可以共享业务 DB，但通过 taskId 和状态机控制执行；进一步演进时再考虑数据所有权和服务数据库拆分。

### 如果问“是否需要网关和注册中心”

回答：当前单体不需要。拆服务后才需要 API Gateway、服务注册、配置中心、服务间鉴权和链路追踪。
