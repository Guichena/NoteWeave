# 文件：08_指标效果_压测_可观测.md

## 1. 本主题覆盖的通用问题

- 项目优化后效果提升多少？
- 有没有压测？QPS、RT、P95、P99 是多少？
- 错误率、超时率、成功率有没有变化？
- 数据库、Redis、MQ 的真实流量和容量是多少？
- 模型效果怎么判断？
- 准确率、召回率、citation coverage 怎么证明可靠？
- 每日 token 消耗是多少？

## 2. 架构视角怎么切入

NoteWeave 当前没有生产流量和真实线上指标。因此指标题的回答重点是：不编造数字，讲清楚已有观测面和未来验证方法。

可以从四类指标回答：

- 系统吞吐：Task、Kafka、Worker、HTTP、WebSocket。
- 检索质量：recall@k、MRR、no-evidence rate、fallbackUsed。
- 生成质量：citation coverage、answer feedback、LLM error、token、latency。
- 运维稳定性：health snapshot、cleanup、audit、失败重试。

## 3. 完整链路深讲：从业务链路到指标观测

### 3.1 任务链路指标

关注：

- Task PENDING/RUNNING/SUCCESS/FAILED 数。
- TaskAttempt latency。
- retry count。
- cancel count。
- timeout count。
- Kafka lag。
- outbox failed count。

用途：判断后台任务是否堆积，Worker 是否需要扩容。

### 3.2 上传与索引指标

关注：

- chunk upload success rate。
- merge latency。
- parse failure rate。
- ES bulk index latency。
- activeIndexVersion switch success。
- embedding backfill latency。

用途：判断资料进入系统是否稳定。

### 3.3 RAG 检索指标

关注：

- retrieval latency。
- bm25Count/vectorCount/wikiCount/fusionCount。
- fallbackUsed。
- no-evidence rate。
- final evidence count。
- per-document evidence distribution。

用途：判断召回是否有效，是否过度依赖某一路。

### 3.4 生成与证据指标

关注：

- LLM latency。
- inputTokens/outputTokens。
- timeout/error rate。
- citation coverage。
- source-backed evidence ratio。
- answer feedback positive/negative。

用途：判断生成成本、质量和证据可信度。

### 3.5 Eval 指标

RAG Eval 可看：

- recall@k。
- MRR。
- citation coverage。
- latency。
- bad case 类型。

要强调：这些指标需要固定 case 集、标注标准、版本记录和可重复运行。

## 5. 为什么不能编造指标

大厂面试官很容易追问：

- 样本量是多少？
- 压测环境几核几 G？
- 数据量多大？
- 指标怎么定义？
- 是否包含冷启动？
- P99 是客户端还是服务端？
- 准确率是谁标注的？

如果数字没有依据，很容易被追穿。更好的回答是承认当前没有生产数字，并给出可执行的验证方案。

## 6. 可直接复述的深答

当前 NoteWeave 没有真实生产 QPS、P99 或每日 token 消耗，我不会编造这些数字。但项目已经有比较完整的观测面，能支撑上线前验证。任务侧可以看 Task 状态分布、TaskAttempt 耗时、retry、cancel、Kafka lag 和 outbox failed；上传和索引侧可以看 merge latency、parse failure、ES bulk index latency 和 activeIndexVersion 切换；RAG 侧可以看 retrieval latency、BM25/vector/wiki 命中量、fusionCount、fallbackUsed 和 no-evidence rate；生成侧可以看 LLM latency、token、timeout、citation coverage 和 answer feedback；运维侧有 SystemHealthSnapshot、CleanupJob 和 AuditLog。如果要证明模型效果，我会建立固定 Eval case 集，定义标准证据和评分口径，用 recall@k、MRR、citation coverage、latency 和 bad case 分类做版本对比，而不是只说感觉效果好。

## 7. 追问兜底

### 如果面试官一定要数字

回答：当前没有生产环境数字。我能给出的是本地测试通过情况和应监控指标。为了准确，我不会把本地 demo 数字包装成生产指标。

### 如果问“怎么证明 92% 准确率”

必须说明样本来源、标注标准、评测任务、统计口径和置信度。当前没有这个数字，不应说。

### 如果问“优化收益最大的是哪一步”

可以基于工程判断说：最有价值的不是单次 prompt 优化，而是 evidence-first 链路、Citation/Trace 和异步任务骨架，因为它们提升可控性和可排障性。但具体收益要通过 Eval 和压测验证。
