# 文件：01_业务闭环与项目主述加深版.md

## 1. 这个主题要回答什么

面试官问“介绍一下项目”“项目解决什么问题”“亮点和难点是什么”，表面是开放题，实际是在考察你能不能把项目从功能列表讲成一个完整系统。

对于 NoteWeave，最好的定位是：

```text
NoteWeave 是一个面向团队知识协作和个人研究沉淀的 AI 知识工作台。
它解决的是知识从资料进入系统、被检索引用、生成成果，再沉淀为长期知识的完整闭环问题。
```

## 2. 面向初学者：这个项目到底在做什么

你可以把 NoteWeave 想象成一个“会追溯证据的知识工作台”。

普通知识库通常只能存文档、搜文档；普通 AI 问答通常只能回答问题。但 NoteWeave 想做的是：

1. 用户把资料放进系统。
2. 系统把资料解析成可以检索的片段或卡片。
3. 用户提问或生成报告时，系统先找证据。
4. 大模型基于证据生成答案或成果。
5. 生成结果保留引用，能追溯来源。
6. 用户确认后，把稳定内容沉淀成 Wiki 或个人知识卡片。

这就形成了一个闭环：

```text
资料 -> 证据 -> 生成 -> 引用 -> 沉淀 -> 再利用
```

## 3. 业务闭环深讲

### 3.1 团队侧闭环

团队侧解决“团队资料怎么变成可信问答和 Wiki”。

完整链路：

```text
用户上传文档
-> 分片上传到 MinIO
-> merge 后生成 FileObject 和 Document
-> 创建 DOCUMENT_PROCESS Task
-> Worker 解析文档
-> ChunkService 切片
-> DocumentChunk 落 MySQL
-> SearchIndexService 写 Elasticsearch
-> 用户在 TEAM_CHAT 里提问
-> HybridRetriever 召回证据
-> EvidencePostProcessor 处理证据
-> TeamRagPromptBuilder 构造 prompt
-> LLM 生成回答
-> CitationService 保存引用
-> 稳定内容发布为 WikiPage
```

这条链路里最重要的不是“LLM 生成回答”，而是回答有证据、证据有权限、证据能追踪。

### 3.2 个人侧闭环

个人侧解决“个人研究资料怎么变成结构化知识和成果”。

完整链路：

```text
用户创建 ResearchProject
-> 导入 Source(TEXT / FILE / URL)
-> Source 必须有 readable text 才能 READY
-> WikiCompilerService 编译 Source
-> 生成 ArticleCard / ConceptCard
-> EvidenceBacktraceService 回溯证据
-> PersonalGenerationService 加载卡片和证据
-> ArtifactPlanExecutor 生成 Artifact
-> ArtifactVersion 保存成果
-> 用户确认 distill
-> SynthesisCard 沉淀进个人 Wiki
```

这个链路的重点是：个人研究不是直接“总结一篇文档”，而是把资料变成卡片、概念、证据和成果。

## 4. 项目中的核心业务抽象

### 4.1 Space

`Space` 是项目最高业务容器。

- `TEAM Space`：团队知识库、团队 Wiki、团队 Chat、团队 Artifact。
- `PERSONAL Space`：个人研究项目、Source、Card、Artifact、Memory。

为什么要有 Space？因为资源权限、检索过滤、Citation 查询、Memory 写入都需要先知道资源属于哪个空间。

### 4.2 Evidence / Citation

Evidence 是“模型回答所依据的证据”。Citation 是“证据和回答/成果之间的正式引用关系”。

普通项目可能把引用写在 message JSON 里。NoteWeave 不这么做，而是用关系表存 citation。原因是：

- 可以做权限二次校验。
- 可以追踪 sourceVersion。
- 可以被 Message、Artifact、Card、Wiki 复用。
- 可以做 Eval 和排障。

### 4.3 Artifact

Artifact 是生成成果，比如报告、学习指南、对比分析、Wiki 草稿。

它和 ChatMessage 不同：

- ChatMessage 是对话记录。
- Artifact 是可编辑、可版本化、可导出、可沉淀的成果。

它和 Wiki/Card 也不同：

- Artifact 是生成结果。
- Wiki/Card 是长期知识。
- 生成结果必须确认后才能进入长期知识。

## 5. 八股知识点：为什么面试官喜欢问“闭环”

### 5.1 什么是业务闭环

业务闭环指一个功能不是做到某一步就结束，而是能完成完整价值链路。

例如普通上传功能只做到“文件存进系统”，但知识系统的闭环是：

```text
上传 -> 解析 -> 检索 -> 引用 -> 生成 -> 沉淀 -> 复用
```

面试官问闭环，是为了判断你是否只做了一个接口，还是理解整个产品价值。

### 5.2 什么是领域模型

领域模型是业务中的核心概念和它们之间的关系。NoteWeave 的领域模型包括：

- `Space`
- `KnowledgeBase`
- `Document`
- `DocumentChunk`
- `ChatSession`
- `Citation`
- `ResearchProject`
- `Source`
- `ArticleCard`
- `ConceptCard`
- `Artifact`
- `SynthesisCard`

面试官如果追问“为什么这么设计表”，本质是在问你对领域模型的理解。

### 5.3 什么是边界

边界就是“这个东西应该负责什么，不应该负责什么”。

例子：

- Redis 负责短期运行态，不负责长期 memory。
- ES 负责检索视图，不负责业务事实源。
- Artifact 负责生成成果，不直接等于长期知识。
- Task 负责长任务状态，不等于 Kafka 消息本身。

能讲清边界，会显得你不是单纯堆技术。

## 6. 为什么这么设计，而不是简单 RAG

简单 RAG 的链路是：

```text
文档 -> 切片 -> 向量库 -> prompt -> 回答
```

它的问题是：

- 权限容易穿透。
- 证据不易追踪。
- 文档更新后 citation 容易失效。
- 生成结果容易污染知识库。
- 坏回答难排查。
- 长任务状态不可见。

NoteWeave 的设计是为了补这些工程缺口。

## 7. 底层原理补充：闭环背后的系统设计思想

### 7.1 分层思想

NoteWeave 的闭环不是把所有功能写在一个大 service 里，而是分层：

```text
接入层：HTTP / WebSocket
权限层：Space / ResourceAccessService
任务层：Task / Outbox / Kafka / Worker
存储层：MySQL / MinIO / Redis / Elasticsearch
AI 层：Retriever / PromptBuilder / LLM Gateway
证据层：Citation / Trace / Snapshot
沉淀层：Wiki / Card / Artifact / Synthesis
运维层：Admin / Eval / Health / Audit
```

分层的好处是每层职责清晰。比如检索层只负责找候选证据，证据层负责追踪来源，沉淀层负责长期知识治理。如果这些混在一起，后期排障和扩展会很困难。

### 7.2 状态机思想

项目里大量对象都有状态：

- Task: `PENDING / RUNNING / SUCCESS / FAILED / CANCELLED / TIMEOUT`
- Document: `PENDING_PROCESS / PROCESSING / INDEXED / FAILED / DELETED`
- Source: `PENDING / READY / FAILED`
- Chat runtime: `RUNNING / STOPPED / FAILED / IDLE`
- Artifact: `GENERATING / READY / FAILED / DISTILLED`

状态机的好处是避免“只靠布尔值”描述复杂生命周期。面试官常问“失败了怎么办、重复了怎么办、取消了怎么办”，本质都要靠状态机回答。

### 7.3 事实源与视图分离

NoteWeave 里 MySQL 是事实源，ES 是检索视图，Redis 是短期运行态，MinIO 是对象内容。这个设计背后的原则是：

```text
需要强关系、审计、权限判断的数据放 MySQL。
需要全文检索和相关性排序的数据放 ES。
需要临时高频状态的数据放 Redis。
大对象和快照放 MinIO。
```

面试时如果能讲清“谁是事实源”，就能回答很多一致性问题。

## 8. 可直接复述的深答

NoteWeave 是一个 AI 知识工作台，核心解决的是知识从资料进入系统，到被检索引用，再到生成成果，最后沉淀为长期知识的闭环问题。团队侧从 KnowledgeBase 和 Document 开始，用户上传文档后，系统通过分片上传、FileObject 复用、异步解析、切片和索引，把文档变成可检索的 DocumentChunk。用户提问时，系统不是直接调大模型，而是先按权限和 session scope 做混合检索，再经过证据后处理，把证据组织进 prompt，最后生成带 Citation 的回答。个人侧从 ResearchProject 和 Source 开始，Source 导入后必须有可读文本，再编译成 ArticleCard 和 ConceptCard，后续 Artifact 生成读取这些卡片和证据，用户确认后才沉淀为 SynthesisCard。整个项目的技术含量在于把权限、异步任务、检索、证据、生成、记忆、沉淀和可观测串成一个完整工程闭环，而不是只做一次问答。

## 9. 面试官可能继续追问

### 9.1 这个项目最大难点是什么

最大难点不是模型调用，而是边界控制：

- 权限边界：用户只能看到有权资源。
- 证据边界：回答必须回到 evidence。
- 异步边界：长任务要可重试、可取消、可观测。
- 知识边界：生成成果不能自动污染长期知识。

### 9.2 如果项目没上线，价值怎么体现

不能编造线上数据。可以说：

- 已有本地可验收闭环。
- 有集成测试覆盖核心链路。
- 有演示数据和静态工作台。
- 有 Trace、Eval、Admin/Ops 观测能力。
- 后续上线前会补压测、灰度和告警。

### 9.3 如果只能讲一个亮点

推荐讲 `Task/Outbox/Kafka` 或 `Hybrid RAG/Citation`。

前者体现后端系统设计；后者体现 AI 工程深度。
