# 文件：02_整体架构与分布式演进加深版.md

## 0. 本篇定位

这篇是 `02_架构设计_模块边界_分布式演进.md` 的加深版，只补“为什么这样拆、以后怎么拆、拆了以后会变难在哪里”。

因此这里不再重复保存标准版里的整体架构主答。普通版 `02` 负责你在面试里直接把当前架构讲顺；这篇只负责把模块化单体、服务拆分、RPC/HTTP、网关注册中心这些问题讲到更深的系统设计层。

## 1. 这篇只补哪些深度

普通版 `02` 已经覆盖：

- 当前为什么是模块化单体。
- 模块边界大概怎么划。
- 未来为什么优先拆 Worker、Search/RAG、LLM Gateway。

这篇额外补的是：

- 为什么当前阶段不拆微服务不是“还没来得及”，而是有意选择。
- 服务拆分真正的判断标准是什么，不是按包名机械拆。
- 一旦进入分布式，哪些一致性、鉴权、调用语义和排障复杂度会马上出现。

## 2. 为什么当前坚持模块化单体是有意选择

### 2.1 当前最核心的矛盾不是部署规模，而是业务边界还在快速收敛

NoteWeave 现在最难的是把这些强关系边界打稳：

- Space / Permission
- Task / Outbox / Worker
- Citation / RetrievalTrace
- Artifact / Synthesis
- Runtime / Memory

这些对象之间关系非常强，如果一开始拆服务，很多本地调用会立刻变成远程调用，问题会从“业务没想清楚”升级成“业务和分布式一起没想清楚”。

### 2.2 本地事务仍然是当前阶段最划算的工程手段

当前项目里大量关键动作都需要先把本地事实落稳，例如：

- 创建 Task 同时创建 Outbox。
- 生成回答后保存 Message、Citation、Trace。
- Distill 时校验 artifactVersion，再写入 SynthesisCard 关系。

这些动作在单体里还能优先用本地事务和清晰状态机处理；如果过早拆分，就会提前引入 Saga、补偿、远程幂等和跨服务排障。

### 2.3 “没有微服务”不是短板，前提是边界先清楚

模块化单体真正的价值不在于部署形式，而在于：

- 领域对象是否清晰。
- 依赖方向是否可控。
- 状态和事实源是否分明。
- 是否为后续拆分保留了自然边界。

只要这些成立，单体就是当前阶段更合理的工程选择。

## 3. 服务拆分真正应该看什么

面试官如果继续问“以后怎么拆”，不要答成“controller 多了就拆”。更稳的标准是下面四个：

### 3.1 是否有独立资源消耗特征

例如 Worker 天然是 CPU/IO/外部依赖消耗型任务，和普通 API 请求不是一类压力。

### 3.2 是否有独立吞吐和扩容诉求

例如检索侧的 ES 查询、RRF、rerank、索引维护，未来可能需要单独调优和扩容。

### 3.3 是否已经形成相对稳定的输入输出契约

如果一个模块的输入输出还在频繁变，拆出去后会放大联调和版本管理成本。

### 3.4 是否值得承受远程调用的额外复杂度

拆分不是白赚，拆出去后要立刻承担：

- 超时和重试。
- 鉴权上下文传递。
- requestId 和 traceId 贯通。
- 远程幂等。
- 降级和熔断。

所以拆分必须先证明收益大于这些成本。

## 4. 为什么拆分顺序是 Worker -> Search/RAG -> LLM Gateway

### 4.1 Worker 最适合第一批拆

因为它天然已经通过 `Task + Outbox + Kafka` 与主请求链路隔离：

- API 负责创建任务和状态。
- Kafka 负责异步分发。
- Worker 负责执行耗时动作。

这意味着它本来就是弱耦合、高资源消耗、易独立扩容的边界。

### 4.2 Search/RAG 适合第二批拆

检索层未来会形成独立复杂度：

- 多路召回。
- RRF 融合。
- Query rewrite。
- Search debug。
- 索引版本治理。

如果后续检索压力和调优复杂度明显上升，把它收成独立服务是自然演进。

### 4.3 LLM Gateway 适合第三批拆

因为它更像横切能力：

- provider 适配。
- 模型路由。
- token / latency 记录。
- timeout / retry。
- prompt version。
- 统一审计和脱敏。

当多个业务链路都开始复用模型能力时，LLM Gateway 的独立治理价值才会足够明显。

### 4.4 为什么 Permission 不应该第一批拆

权限域几乎参与每次资源访问。如果太早远程化，会把每次查询和生成都变成跨服务鉴权，马上带来：

- 远程调用放大。
- 权限缓存一致性问题。
- 权限变更后的失效问题。
- 故障传播链更长。

所以权限域更适合作为强内聚核心域，而不是最早拆出去的基础设施。

## 5. 分布式以后会立刻变难的四件事

### 5.1 远程调用语义不再等于本地方法调用

拆服务后，“调用成功”至少有几层含义：

- 请求有没有发到对端。
- 对端有没有执行。
- 对端执行后响应有没有回来。
- 客户端超时后是否会重试。
- 重试后会不会重复副作用。

所以微服务不是把 `serviceA.call()` 改成 RPC 这么简单。

### 5.2 鉴权上下文需要显式传递

单体里可以直接从上下文拿 CurrentUser；分布式里就要考虑：

- userId / spaceId / requestId 怎么传。
- 下游是否需要二次鉴权。
- 哪些服务只接受系统身份调用。
- 怎么避免把权限逻辑散落到每个下游服务里。

### 5.3 数据所有权要重新定义

单体阶段多个模块共享 MySQL 还能接受；拆服务后就得问：

- Task 数据归谁。
- Citation 和 RetrievalTrace 谁负责。
- 索引写入失败由谁补偿。
- Artifact distill 失败由谁回滚或重试。

如果不先定义数据所有权，拆完只会得到“多个服务共用一堆表”的伪微服务。

### 5.4 排障链路会更长

单体时很多问题还能在一个进程里排；拆分后就要看：

- 网关日志。
- API 服务日志。
- MQ 投递。
- Worker 日志。
- 搜索服务 trace。
- LLM Gateway trace。

所以没有足够收益时，不值得为了“更高级”提前进入这套复杂度。

## 6. RPC、HTTP、网关、注册中心怎么讲更稳

### 6.1 HTTP 和 RPC 不是高低之分，而是适配问题

- 对外 API 更适合 HTTP/REST，因为资源语义清晰、调试友好、前端天然兼容。
- 内部高频调用如果未来变多，可以考虑 RPC，但前提是服务边界已稳定。

### 6.2 网关和注册中心是分布式后的配套，不是现在硬凑的亮点

当前单体不需要独立 API Gateway、注册中心、配置中心，强行说出来反而显得在背概念。

更合理的口径是：

- 进入多服务阶段后，才需要统一入口、服务发现、集中配置、链路追踪和限流灰度。
- 当前阶段把这些当成未来扩展点，而不是现状包装。

## 7. 边界、不能说满和扩展方向

- 这篇只补架构演进判断标准和分布式复杂度，不再重复标准版整体架构主答。
- 当前可以坚定讲：模块化单体、任务解耦、检索边界、LLM Gateway 预留边界。
- 当前不要讲成已落地：微服务化、RPC 主链路、网关注册中心配置中心、分库分表、跨服务权限系统。
- 扩展方向可以讲成：如果 Worker、检索或模型调用先出现独立容量压力，就沿现有边界平滑拆分。

## 8. 继续追问怎么接

如果面试官继续往下压，这一题最稳的承接顺序是：

```text
先讲为什么当前单体是主动选择
-> 再讲拆分判断标准
-> 再讲优先拆 Worker / Search / LLM Gateway 的顺序
-> 最后讲远程调用、一致性、鉴权和排障复杂度
```

这样会显得你不是在背“微服务八股”，而是真的理解演进成本。
