# 文件：02_整体架构与分布式演进加深版.md

## 1. 这个主题要回答什么

这个主题对应面试中的架构类问题：

- 项目整体架构是什么？
- 为什么当前是单体，而不是微服务？
- 如果未来扩展成分布式，怎么拆？
- 有没有网关、注册中心、配置中心？
- HTTP 和 RPC 怎么取舍？

## 2. 面向初学者：什么是架构

架构不是“用了哪些技术”，而是系统如何分层、模块如何协作、数据如何流动、失败如何处理。

对于 NoteWeave，可以用这句话概括：

```text
NoteWeave 是一个模块化单体架构，内部按领域边界拆分模块，外部通过 MySQL、Redis、MinIO、Elasticsearch、Kafka 和 LLM Provider 组成完整 AI 知识系统。
```

## 3. NoteWeave 的整体架构

### 3.1 接入层

```text
Browser / Static Workbench
-> HTTP API /api/v1
-> WebSocket /ws/chat/{ticket}
```

HTTP API 负责普通业务请求，比如登录、上传、创建任务、查询文档、查询 Artifact。WebSocket 负责流式 Chat Runtime，比如 delta、stop、resume。

### 3.2 应用层

应用层是 Spring Boot，按领域包拆分：

- `auth / user / space / permission`
- `task`
- `team.document / team.kb / team.rag / team.wiki`
- `personal.source / personal.compiler / personal.card`
- `artifact / studio / methodology`
- `chat / websocket / memory`
- `prompt / llm / rageval / admin`

这叫模块化单体：部署是一个应用，但代码和领域边界是清晰的。

### 3.3 数据层和中间件

```text
MySQL: 业务状态和关系
Redis: 短期状态和 runtime
MinIO: 对象存储
Elasticsearch: 检索视图
Kafka: 异步任务分发
LLM Provider: 模型生成
```

面试中要强调每个组件的职责边界：

- MySQL 是事实源。
- ES 是检索视图。
- Redis 是短期状态。
- Kafka 是长任务分发。
- MinIO 是对象内容。

## 4. 八股知识点：单体、模块化单体、微服务

### 4.1 单体架构是什么

单体架构是所有业务模块打包部署在一个应用里。

优点：

- 开发简单。
- 部署简单。
- 本地事务好处理。
- 调试方便。

缺点：

- 代码边界容易混乱。
- 所有模块一起发布。
- 单个模块高负载可能影响整体。
- 团队大了协作容易冲突。

### 4.2 模块化单体是什么

模块化单体仍然是一个应用，但内部按领域清晰拆包，控制依赖方向。

它的优点是：

- 保留单体开发效率。
- 又能保持业务边界。
- 未来可以按模块拆服务。

NoteWeave 当前就是这个阶段。

### 4.3 微服务是什么

微服务是把系统拆成多个独立部署、独立扩容、独立演进的服务。

优点：

- 独立扩容。
- 独立发布。
- 技术栈可异构。
- 团队边界更清晰。

缺点：

- 分布式事务复杂。
- 网络调用失败不可避免。
- 链路追踪复杂。
- 部署运维复杂。
- 数据一致性更难。

所以不是越早微服务越好，而是规模、团队和性能需求到了才拆。

## 5. 为什么 NoteWeave 当前不一开始微服务

原因有四个：

第一，项目处于工程工作台和产品原型阶段，需要快速迭代。单体更容易改模型、改表、改接口、跑集成测试。

第二，权限、Citation、Artifact、Memory、Task 之间关系紧密。一开始拆服务会让一次业务操作跨多个服务，带来分布式事务和远程调用问题。

第三，当前没有生产级容量数据证明必须拆。没有指标时过早拆，是为了架构而架构。

第四，项目已经保留可拆边界。Task/Kafka、ES、LLM Gateway 都是未来天然边界。

## 6. 如果未来拆分，怎么拆

### 6.1 第一阶段：拆 Worker

为什么先拆 Worker？因为它天然异步。

```text
API Service
-> MySQL Task / Outbox
-> Kafka
-> Worker Service
-> MinIO / ES / LLM
```

适合拆到 Worker 的任务：

- DocumentProcessingWorker
- SourceCompileWorker
- ArtifactGenerateWorker
- WikiIndexWorker
- RagEvalWorker
- CleanupWorker

拆 Worker 的收益：

- 独立扩容。
- 不影响 API 响应。
- 可以按任务类型分 worker group。
- 资源隔离更清楚。

### 6.2 第二阶段：拆 Search/RAG 服务

检索服务可以独立出来：

```text
API Service
-> Search/RAG Service
-> Elasticsearch
-> RetrievalTrace
```

拆它的原因：

- ES 查询和索引优化有独立复杂度。
- RRF、rerank、query rewrite 可以独立演进。
- 检索服务可能需要独立缓存和限流。

### 6.3 第三阶段：拆 LLM Gateway

LLM Gateway 负责：

- provider adapter。
- 模型路由。
- token 统计。
- 超时和重试。
- prompt version。
- LLMCallLog。
- 安全脱敏。

拆出来后，多个业务模块可以统一调用模型。

### 6.4 哪些不急着拆

`Space / Permission` 不急着拆。因为它是所有资源访问的基础。如果拆成远程服务，每次访问都要远程鉴权，会引入性能和可用性问题。

## 7. 八股知识点：RPC、HTTP、网关、注册中心

### 7.1 HTTP 和 RPC 区别

HTTP/REST：

- 面向资源。
- 对外开放友好。
- 浏览器和前端适配好。
- 调试方便。

RPC：

- 面向方法调用。
- 内部服务间调用效率和类型约束更好。
- 常见实现有 gRPC、Dubbo 等。

如果 NoteWeave 拆服务，对外仍适合 HTTP；内部高频服务调用可以考虑 RPC。

### 7.2 网关是什么

API Gateway 通常负责：

- 统一入口。
- 鉴权。
- 路由。
- 限流。
- 灰度。
- 日志。
- 跨域。

当前 NoteWeave 是单体，不需要独立网关。未来拆微服务后才有必要。

### 7.3 注册中心是什么

注册中心用于服务发现。服务启动时注册地址，调用方从注册中心发现服务实例。

常见注册中心：

- Nacos。
- Eureka。
- Consul。
- ZooKeeper。

当前单体不需要注册中心。

### 7.4 配置中心是什么

配置中心用于集中管理配置，如模型 provider、开关、限流、灰度策略。当前 NoteWeave 主要通过 Spring 配置和环境变量管理。未来多服务后可引入配置中心。

## 8. 底层原理补充：分布式系统为什么复杂

### 8.1 网络调用不是本地调用

本地方法调用失败通常是代码异常；远程调用可能出现更多情况：

- 请求没发出去。
- 请求发出去了但超时。
- 服务端执行成功但响应丢了。
- 服务端执行失败。
- 客户端重试导致重复执行。

这就是为什么微服务里必须考虑超时、重试、幂等和链路追踪。

### 8.2 CAP 和一致性直觉

CAP 说的是分布式系统无法同时完美满足：

- Consistency：一致性。
- Availability：可用性。
- Partition tolerance：分区容错。

实际业务里很少直接背 CAP，而是要理解：一旦拆服务，就不能像单体事务一样假设所有数据同时更新成功。NoteWeave 当前很多业务强关系还在单体内，能减少不必要的分布式一致性问题。

### 8.3 服务拆分原则

服务拆分一般看：

- 是否有独立扩容需求。
- 是否有独立数据所有权。
- 是否和其他模块事务耦合低。
- 是否由不同团队维护。
- 是否故障影响面需要隔离。

按这个原则，Worker、Search、LLM Gateway 比 Permission 更适合先拆。

### 8.4 RPC 要关注什么

如果未来内部用 RPC，要关注：

- 接口版本兼容。
- 超时设置。
- 重试策略。
- 幂等 key。
- requestId 透传。
- 鉴权上下文透传。
- 熔断降级。
- 序列化协议。

这些都是面试官从“HTTP 改 RPC”继续追问时会问到的点。

## 9. 可直接复述的深答

NoteWeave 当前是模块化单体架构，不是一开始就做微服务。它部署上是一个 Spring Boot 应用，但内部按领域拆成 auth、space、permission、task、team rag、personal source、artifact、memory、admin 等模块。这样做是因为项目还在快速迭代阶段，权限、Citation、Artifact、Memory 和 Task 之间关系比较强，单体可以减少分布式事务和远程调用复杂度。但我在设计上保留了未来拆分边界：长任务通过 Task/Outbox/Kafka 解耦，最适合第一批拆成 Worker 服务；检索通过 ES 和 HybridRetriever 收口，未来可以拆 Search/RAG 服务；LLM 调用通过 ObservedLlmGateway 收口，未来可以拆 LLM Gateway。权限和 Space 我不会过早拆，因为它们是所有资源访问的基础域，一旦拆出去，每次访问都要远程鉴权，还要处理缓存一致性和故障降级。整体来说，这是先用模块化单体打通闭环，再按真实瓶颈演进到分布式。

## 10. 面试官可能追问

### 10.1 单体会不会不利于扩展

会有上限，但当前阶段更重要的是领域边界清晰。NoteWeave 的 Task/Kafka、ES、LLM Gateway 已经是可拆边界，未来可以平滑演进。

### 10.2 拆服务后如何保证一致性

先避免跨服务强事务。能异步的通过 Task/Kafka 最终一致；必须同步的通过明确接口、幂等、重试、补偿和状态机处理。

### 10.3 是否需要网关

当前不需要独立网关。未来多服务后，网关可以统一做鉴权、路由、限流、灰度和日志。
