## 2. 面向初学者：常见性能指标是什么

### 2.1 QPS

QPS 是 Queries Per Second，每秒请求数。

例如 QPS=100 表示系统每秒处理 100 个请求。

### 2.2 RT

RT 是 Response Time，响应时间。

### 2.3 P95 / P99

P95 表示 95% 请求的响应时间小于等于这个值。

P99 表示 99% 请求的响应时间小于等于这个值。

为什么看 P99？因为平均值可能掩盖长尾。

例子：

```text
99 个请求 100ms
1 个请求 10s
平均值看起来还行，但用户体验可能很差
```

### 2.4 错误率和超时率

错误率：

```text
错误请求数 / 总请求数
```

超时率：

```text
超时请求数 / 总请求数
```

## 5. 八股知识点：压测怎么做

压测要说明：

- 压测目标。
- 压测环境。
- 数据规模。
- 请求模型。
- 并发数。
- 持续时间。
- 指标采集。
- 瓶颈定位。

NoteWeave 可以分链路压测：

### 5.1 上传压测

模拟多用户分片上传，观察：

- MinIO 写入延迟。
- Redis bitmap 操作。
- MySQL UploadChunk 写入。
- merge 耗时。

### 5.2 检索压测

构造查询集，观察：

- ES latency。
- BM25/vector/wiki 耗时。
- RRF 耗时。
- EvidencePostProcessor 耗时。

### 5.3 WebSocket 压测

模拟多连接、多 session，观察：

- Redis event buffer。
- partialContent 写入。
- active execution。
- stop/resume 成功率。

### 5.4 LLM 压测

真实 LLM 压测要谨慎，因为成本高、provider 有限流。可以用 stub 或 mock 先压后端链路，再单独测 provider 延迟。

## 6. 八股知识点：RAG 效果指标

### 6.1 recall@k

标准答案证据是否出现在 topK 召回里。

例子：

```text
标准证据 chunk 在 top5 里 -> recall@5 命中
```

### 6.2 MRR

Mean Reciprocal Rank，平均倒数排名。

如果正确结果排第 1，得 1。
排第 2，得 1/2。
排第 10，得 1/10。

越高说明正确结果越靠前。

### 6.3 citation coverage

答案中的关键结论有多少被 citation 覆盖。

注意：citation coverage 高不代表一定正确，因为 citation 可能引用错或不能支撑 claim。

### 6.4 no-evidence rate

系统无法召回证据的比例。

过高可能说明：

- 文档没索引。
- query 改写差。
- 权限 filter 太严。
- chunk 切分不合理。
- embedding 质量差。

## 7. 坏回答排障

排查链路：

```text
AnswerFeedback / messageId
-> ChatMessage
-> RetrievalTrace
-> RetrievalTraceItem
-> Citation
-> DocumentChunk / Source / WikiPageVersion
-> LLMCallLog
-> PromptVersion
```

归因：

- 没召回。
- 召回错。
- RRF 排序问题。
- evidence 截断问题。
- prompt 约束不足。
- 模型不遵循证据。
- citation 绑定错误。
- 权限过滤错误。

## 8. 技术沟通怎么讲

### 8.1 给产品讲 Citation

不要说：

```text
我要建 citation 表。
```

要说：

```text
用户看到 AI 回答后，需要知道依据来自哪里。
管理员遇到坏回答时，需要反查是资料问题、检索问题还是模型问题。
权限变化后，不能让用户继续看到无权证据。
所以引用要独立保存并可校验。
```

### 8.2 给业务讲异步任务

不要说：

```text
我用了 Kafka 和 outbox。
```

要说：

```text
上传成功不代表解析立刻完成。
解析、索引、生成都可能耗时或失败。
所以系统返回 taskId，用户可以看进度，失败可以重试，管理员可以排查。
```

## 9. AI Coding 怎么回答

合理口径：

- 用 AI 做代码阅读、测试补充、文档整理、方案比较。
- 不盲信 AI 生成。
- 权限、事务、幂等、安全、异常处理自己重点 review。
- 小步 patch。
- 看 diff。
- 跑测试。

和 NoteWeave 的理念一致：AI 输出需要证据和约束。

## 10. 底层原理补充：为什么 P99、Eval 和 Trace 很重要

### 10.1 平均值为什么不够

平均 RT 容易掩盖长尾问题。AI 系统里 LLM provider、ES 查询、MinIO IO 都可能产生长尾。如果只看平均值，少量极慢请求会被掩盖。P95/P99 更能体现用户体验。

### 10.2 压测要避免哪些坑

常见坑：

- 用太少数据压测，ES 索引太小，不真实。
- 只压 HTTP，不压 Worker。
- 用 stub LLM 后忘了单独评估真实 provider 延迟。
- 只看平均 RT，不看 P99。
- 不记录错误率和超时率。
- 没有区分冷启动和热身后结果。

### 10.3 Eval 为什么要版本化

RAG 效果会受很多因素影响：

- chunk 策略。
- embedding 模型。
- RRF 权重。
- prompt version。
- topK。
- rerank 策略。

如果没有版本记录，就不知道效果变化来自哪里。

### 10.4 Trace 为什么是排障核心

Trace 把一次回答拆成可观察步骤：

```text
query -> recall -> fusion -> evidence -> prompt -> LLM -> citation
```

没有 Trace，只能凭感觉猜问题；有 Trace，才能定位到底是检索错、证据错还是生成错。

## 11. 可直接复述的深答

当前 NoteWeave 没有真实生产 QPS、P99 或每日 token 消耗，我不会编造数字。但项目已经有比较完整的观测面，可以支撑上线前验证。任务侧可以看 Task 状态分布、attempt latency、retry、cancel、outbox failed 和 Kafka lag；上传侧看 chunk success rate、merge latency、MinIO error；检索侧看 BM25/vector/wiki 命中量、fusionCount、fallbackUsed、no-evidence rate 和 retrieval latency；生成侧看 LLM latency、token、timeout 和 citation coverage；运维侧看 SystemHealthSnapshot、CleanupJob 和 AuditLog。模型效果不能只说感觉好，要用固定 Eval case 集评估 recall@k、MRR、citation coverage 和 bad case。遇到坏回答时，我会从 messageId 查 RetrievalTrace、Citation、DocumentChunk、LLMCallLog 和 PromptVersion，定位是召回问题、证据问题还是模型生成问题。
