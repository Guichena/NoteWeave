# NoteWeave 实际面试问题

> 本文件为 2026-06-01 重构版，依据当前代码、测试和 Flyway 迁移整理。不要再按旧阶段计划或旧题库口径背。

## 0. 使用方式
每题先练 30 秒结论，再扩展到 2 分钟。零基础同学不要背术语堆砌，要按“场景 -> 方案 -> 收益 -> 失败怎么处理 -> 不能说满”来答。

## Q1: 你先介绍一下 NoteWeave 这个项目。
参考答法：

NoteWeave 是一个双空间 AI 知识工作台。团队侧从知识库上传、解析、chunk、索引开始，进入 Hybrid RAG 问答、Citation 追踪和 Wiki 发布；个人侧从 ResearchProject、Source 导入开始，编译 ArticleCard、ConceptCard，再用 Methodology 生成 Artifact，最后由用户确认沉淀成 SynthesisCard。技术上我会重点讲三条线：第一是 Task/Outbox/Kafka/Worker 的异步骨架，承接解析、索引、生成、评测、清理这些长任务；第二是 evidence-first 的 RAG 链路，用 BM25、向量、Wiki recall、RRF、EvidencePostProcessor 和 Citation 保证回答有证据；第三是 WebSocket runtime、Memory、Admin/Eval/Ops，让系统可恢复、可观测、可运营。

继续追问：
- 为什么要同时支持 TEAM 和 PERSONAL？
- 为什么说它不是一个普通聊天 Demo？

## Q2: 这个项目和普通 RAG 问答系统最大的区别是什么？
参考答法：

普通 RAG 项目通常讲“上传文档，然后向量检索，最后问模型”。NoteWeave 的区别是把 RAG 放进完整知识工作台里：入口有 Space 权限和 KnowledgeBase 边界；检索不是单路向量，而是 BM25、向量、Wiki recall 融合；回答后不是只返回文本，还会落 Citation、RetrievalTrace、LLMCallLog；临时回答可以进入 Artifact，人工确认后再发布 Wiki 或沉淀成 SynthesisCard。这样面试时能讲清楚“资料从哪来、证据怎么追、结果怎么沉淀、错误怎么排查”。

## Q3: 你最有 ownership 的模块怎么讲？
参考答法：

我会选异步任务骨架和 RAG 证据链来讲，因为它们横跨多个业务模块。异步骨架里，我把文档解析、Source 编译、Artifact 生成、Wiki 索引、RAG Eval、资源清理统一成 Task、TaskAttempt、TaskEvent、TaskOutbox，再通过 Kafka 和 Worker 执行。RAG 证据链里，我把权限过滤、混合召回、证据后处理、Prompt 约束、Citation 持久化和 Trace 串起来。这样讲 ownership 不只是“我写了接口”，而是讲清楚自己把系统可靠性和可追溯性做成了公共能力。

## Q4: Space 为什么要做成一级业务边界？
参考答法：

AI 知识系统最怕串数据，所以 NoteWeave 先把业务容器定义清楚。TEAM Space 承载团队知识库、团队 Chat、Wiki、Graph 和 Admin 可见的团队资源；PERSONAL Space 承载个人 ResearchProject、Source、Card、Artifact、Synthesis 和个人 Memory。系统角色 `systemRole` 只决定是否是平台 Admin，空间角色 `SpaceMember.role` 决定某个团队空间里的 OWNER/EDITOR/VIEWER 权限。这样后续 RAG 召回、Citation 查询、Artifact 读取、Memory 写入都能回到统一边界判断。

## Q5: 为什么 Citation 返回前还要二次权限校验？
参考答法：

因为 citation 是“回答引用了什么证据”，它可能指向 Document、WikiPage、Artifact 或个人 Source。如果只在生成回答时校验一次，后续资源权限变化、文档删除、空间成员退出时就可能出现历史引用泄露。更稳的做法是 citation 持久化保存证据关系，但每次读取 citation 或 snapshot 时仍然回到资源归属和 Space 权限做二次判断。这样即使检索索引或历史消息里还留有引用，也不会把用户现在无权看的内容直接返回。

## Q6: 为什么不直接在业务事务里发 Kafka？
参考答法：

业务事务和消息发送不是一个原子操作。如果先写 DB 后发 Kafka，发消息失败会导致任务没人执行；如果先发 Kafka 后提交 DB，Worker 可能读不到任务或业务状态。NoteWeave 用 Outbox：在同一个事务里写 Task 和 TaskOutbox，事务提交后再由调度器投递 Kafka。Consumer 收到消息后不信消息里的复杂业务数据，只拿 taskId 回查 MySQL。这样把强一致事务限制在 DB 内，把跨系统部分做成可重试的最终一致。

继续追问：
- Kafka 已投递但 Worker 执行失败怎么办？

## Q7: Worker 重复消费如何保证幂等？
参考答法：

Worker 不能假设 Kafka 只投一次。它拿到 taskId 后要先查 Task 状态，如果已经 SUCCESS、CANCELED 或不满足执行条件，就不能重复执行副作用。执行中通过 TaskExecutionCoordinator 记录 attempt 和 event，业务侧也要用 idempotencyKey 或目标状态兜底，比如 Artifact 生成绑定 task/版本，Wiki 索引绑定 pageId/versionId，文档处理绑定 document/indexVersion。面试时要强调：幂等不是 Kafka 帮你做完的，而是任务状态、业务唯一键和 Worker 逻辑一起做。

## Q8: 从上传到可检索，中间经历哪些阶段？
参考答法：

用户在 TEAM Space 的 KnowledgeBase 下发起 init upload，系统先校验 OWNER/EDITOR 权限，再创建上传会话。文件分片写入 MinIO，Redis/DB 记录上传状态；merge 后根据内容 hash 管理 FileObject 和 Document 元数据，同时创建 DOCUMENT_PROCESS 任务并写 Outbox。Worker 执行时解析文本、切 chunk、保存 page/offset/contentHash，并写入 ES 索引。重建索引时要用 indexVersion/activeIndexVersion 控制切换，不能让新索引失败破坏旧可用版本。

## Q9: 为什么删除文档用 soft delete？
参考答法：

文档删除不是简单删一行。Document 关联 FileObject、chunk、ES 索引、citation、trace、历史消息和可能的 snapshot。如果直接物理删除，历史回答的引用会断，排查也困难。Soft delete 可以先让业务查询和检索过滤掉该文档，同时保留审计和恢复空间；后续再由 cleanup job 扫描确认没有引用或过了保留期，再清理对象和索引。这样设计更符合知识系统的可追溯要求。

## Q10: 为什么要做 Hybrid RAG？
参考答法：

单纯向量检索容易漏掉精确术语，单纯 BM25 又不擅长语义表达，Wiki recall 则适合团队长期确认知识。NoteWeave 的 HybridRetriever 把 BM25、vector、wiki 多路召回合并，再用 Weighted RRF 做融合排序，之后 EvidencePostProcessor 做去重、相邻 chunk 合并、每文档限流和上下文截断。这个设计不是为了显得复杂，而是为了让召回既覆盖关键词又覆盖语义，并且把 prompt 控制在可用长度内。

## Q11: EvidencePostProcessor 解决什么问题？
参考答法：

检索返回的原始 chunk 不能直接塞给 LLM。它们可能来自同一文档的相邻片段、内容重复、某个文档占比过高，或者总长度超过 prompt budget。EvidencePostProcessor 的职责是把“召回结果”变成“可喂给模型的证据包”：去重、相邻合并、限制每个文档数量、截断总 token，并保留来源信息。这样既降低 prompt 噪声，也方便 Citation 指回原文。

继续追问：

## Q12: Prompt 怎么防止文档注入和幻觉？
参考答法：

NoteWeave 的 TeamRagPromptBuilder 不是简单拼接资料，而是把证据放在受控格式里，明确文档内容不是系统指令，要求模型只基于证据回答；没有证据时返回兜底，不鼓励自由编造。再结合 Citation 和 RetrievalTrace，后续可以反查“当时给了哪些证据、模型用了哪些引用”。面试时可以承认这不是绝对防御，但它把风险从不可见的模型自由发挥，降到可观察、可评估、可迭代的工程链路。

## Q13: WebSocket 已经有 HTTP 替代，为什么还要做？
参考答法：

HTTP 可以完成一次问答，但知识工作台需要流式输出、停止、刷新恢复和运行态同步。NoteWeave 先用 HTTP 申请 ws-ticket，再建立 WebSocket 连接，后端发送 connected、started、delta、completed、stopped、failed、restored 等事件。运行中的 partialContent、event seq、stop 标记放 Redis，正式消息和最终结果落 MySQL。这样用户刷新页面或网络短断时，可以从正式数据和 runtime state 里恢复体验。

## Q14: DRAFT 和 FORMAL 为什么要区分？
参考答法：

DRAFT 是临时探索，FORMAL 是正式知识工作。临时草稿里可能有无效问题、敏感信息、测试输入或用户还没确认的想法，不应该写长期 Memory。FORMAL 会经过 MemoryWritebackStrategy，对短问候、低价值输入、敏感内容做过滤，再决定写 session summary、space memory 或 user memory。这个边界能避免“用户随便试一句，系统就永久记住”的问题。

## Q15: 个人研究链路和团队知识库有什么不同？
参考答法：

团队知识库面向多人共享知识，重点是 KnowledgeBase、Document、Wiki、RAG 和权限；个人研究面向个人学习或研究项目，重点是 ResearchProject、Source、ArticleCard、ConceptCard、Artifact、Synthesis。个人链路里 Source 可以是 FILE、URL、TEXT，READY 状态必须有可读文本；编译时抽 ArticleCard 和 ConceptCard，并通过 EvidenceBacktraceService 把 quote 回到原文位置。团队侧更强调共享和权限，个人侧更强调结构化理解和长期沉淀。

## Q16: ConceptCard 为什么要做合并和 alias？
参考答法：

同一个概念可能在多个 Source 里用不同名字出现，比如“RRF”和“Reciprocal Rank Fusion”。如果每次抽取都新建卡片，个人知识库会碎片化，后续生成也会重复引用。ConceptMergeService 通过名称、alias、语义线索和关系去做归并，ArticleConceptRelation 记录概念和文章之间的关系。这样用户后续生成学习指南或报告时，可以拿到更稳定的概念网络。

继续追问：

## Q17: Artifact 为什么不直接写进 Wiki 或 ConceptCard？
参考答法：

Artifact 是生成产物，Wiki 或 ConceptCard 是长期知识。生成产物可能只是草稿、阶段性总结或有待验证的报告，如果自动写入长期知识，会把模型错误永久化。NoteWeave 的设计是 Artifact 先作为版本化成果存在，用户确认后可以发布成 Wiki 草稿，或在个人侧通过 proposal/confirm 沉淀成 SynthesisCard。这个设计把 AI 生成效率和人的确认责任分开。

## Q18: MethodologyCard 解决什么问题？
参考答法：

MethodologyCard 让输出方法论从硬编码 prompt 变成可管理配置。不同 artifact type 对结构、步骤和质量检查要求不同，比如学习指南、技术报告、事故复盘、工作准备不应该共用一段固定提示。项目用 MethodologyCard 保存 workflow、outputStructure、qualityChecklist，并区分 PRESET、SPACE、PROJECT 作用域，生成时匹配最合适的方法论注入 prompt。这样既能保持输出稳定，又能给用户定制空间。

## Q19: Skill 在项目里是什么，不是什么？
参考答法：

Skill 是可观察的生成步骤，不是完全自主 Agent。ArtifactPlanExecutor 会按 artifact type 选择固定步骤，例如加载上下文、加载 MCP 工具上下文、选择 evidence、生成报告、保存 Artifact，每一步都记录 SkillExecutionLog。它的价值是让一次生成可以排查：上下文是什么，证据选了哪些，模型输出什么，保存是否成功。当前不能说成开放式多 Agent，因为没有任意规划、任意工具调用和自动执行闭环。

## Q20: Bilibili MCP 工具具体怎么落地？
参考答法：

## Q21: Wiki 为什么要从 ChatMessage 或 Artifact 中单独沉淀？
参考答法：

ChatMessage 是对话过程，Artifact 是阶段性生成成果，Wiki 是团队确认后的长期知识。团队 RAG 的回答可能对当前问题有用，但不一定适合作为团队知识沉淀。NoteWeave 允许从 ChatMessage 或 Artifact 创建 Wiki 草稿，人工编辑后发布为 WikiPageVersion，再通过 WIKI_INDEX 任务进入检索。这样能保留来源和版本，也避免模型生成内容自动污染团队长期知识。

## Q23: Admin/Ops 在这个项目里不是后台 CRUD，它解决什么问题？
参考答法：

Admin/Ops 解决的是 AI 系统可运营性。管理员需要看到 prompt version、LLMCallLog、RetrievalTrace、AnswerFeedback、RAG Eval、Task 状态、cleanup job、health 和 audit。比如一次错误回答出现后，可以沿着 session/message 找 citation 和 trace，再看检索召回、prompt、模型调用和用户反馈；任务失败可以在 AdminTaskService 里重试或标记失败；资源清理先 scan 再 execute，避免误删。这些能力让项目从 Demo 变成可排查系统。

## Q24: RAG Eval 怎么讲？
参考答法：

RAG Eval 是评估链路，不是正式聊天。它会用 eval case/run/result 管理评测样本和执行结果，调用检索、LLM、trace 和 log 记录，但 scene 是 RAG_EVAL，不能污染正式 ChatSession 和用户长期 Memory。面试时可以讲它用于观察 recall、citation coverage、答案质量和 prompt 版本差异，但不要编造没有测出来的 QPS、P99 或线上指标。

## Q25: 如果面试官问“项目抗压和扩展性”，怎么答不夸大？

## Q26: 如果模型回答错了，你怎么排查？
参考答法：

按链路从前到后查。第一看权限和 scope：问题是否查了正确 Space/KnowledgeBase。第二看 RetrievalTrace：BM25、vector、Wiki 各自召回了什么，RRF 排序是否合理。第三看 EvidencePostProcessor：证据是否被去重、合并或截断掉关键内容。第四看 Prompt 和 LLMCallLog：提示是否要求基于证据，模型是否成功调用。第五看 Citation：答案引用和原文是否对应。最后把错误样本加入 RAG Eval 或反馈闭环。

## Q28: 你怎么总结这个项目的最大工程价值？
参考答法：

最大价值不是“接了大模型”，而是把 AI 能力放进一个有边界、有证据、有沉淀、有运营能力的知识系统。边界来自 Space/Permission，证据来自 Hybrid RAG/Citation/Trace，沉淀来自 Artifact/Wiki/Synthesis，运营来自 Task/Admin/Ops/Eval。这个总结能把项目从功能列表提升到架构设计，也能自然接住大厂常问的一致性、权限、幂等、检索质量、可观测和边界取舍。

继续追问：
- 如果只能保留一个技术亮点，你保留哪个？
- 这个项目下一步最值得做的优化是什么？

## Q29: 面试官问“你这个项目表结构怎么设计的”，怎么答？
参考答法：

我不会从所有表名开始背，而是按生命周期讲。第一层是边界表：`users`、`space`、`space_member`，解决谁属于哪个空间、系统角色和空间角色怎么分开。第二层是长任务表：`task`、`task_attempt`、`task_event`、`task_outbox`，解决异步执行、重试、取消和消息最终一致。第三层是资料表：`knowledge_base`、`document_upload`、`file_object`、`document`、`document_chunk`，解决上传、解析、chunk 和索引版本。第四层是证据表：`chat_message`、`citation`、`message_citation`、`retrieval_trace`、`retrieval_trace_item`、`llm_call_log`、`answer_feedback`，解决回答为什么可信、错了怎么查。第五层是生成和沉淀表：`artifact`、`artifact_version`、`methodology_card`、`wiki_page`、`wiki_page_version`、`artifact_distillation_proposal`、`synthesis_card`、`memory_item`，解决方法论配置、临时产物、用户确认和长期知识的边界。

继续追问：
- 为什么不用一张 JSON 表保存 AI 相关内容？
- 当前迁移里为什么很少显式 foreign key？

## Q30: 表索引设计你怎么讲？
参考答法：

我会按查询路径讲索引。权限边界高频按空间过滤，所以很多表都有 `space_id/status` 或 `space_id/created_at`。任务调度要查积压和重试，所以 `task_type/task_status`、`space_id/task_status`、`task_outbox(status,next_retry_at,created_at)` 很关键。文档索引要避免旧 chunk 污染，所以 `document_chunk(document_id,index_version,chunk_index)` 唯一，`document.active_index_version` 用于切换可用版本。生成链路要按作用域选方法论，所以 `methodology_card(space_id,card_scope,status)`、`methodology_card(space_id,research_project_id,card_scope,status)` 也值得讲。证据排障要按 trace 看候选，所以 `retrieval_trace(scene,created_at)`、`retrieval_trace_item(trace_id,rank_no)` 重要。评测和运维按时间查，所以 RAG Eval、audit、health 都围绕 status/component/action + time 建索引。

继续追问：
- 为什么不是所有字段都建索引？
- 如果 RAG 查询慢，你先看 SQL 索引还是 ES？

## Q31: MySQL、Redis、MinIO、ES、Kafka 的职责边界怎么答？
参考答法：

我会先明确：MySQL 是事实源，Redis 是短期运行态，MinIO 是大对象，ES 是检索读模型，Kafka 是任务消息通道。比如文档上传时，MySQL 记录 upload/document/file_object/chunk 状态，MinIO 存分片和原文，Redis 用 bitmap 快速标记分片上传，Kafka 触发 DOCUMENT_PROCESS，ES 只保存可检索 chunk。RAG 时也是这样：MySQL 确定 Space 和 scope，ES 召回候选，MySQL/Citation/Trace 记录证据和排障事实。任何组件都不能单独决定用户权限或最终业务状态。

继续追问：
- 为什么 Redis 不做主任务队列？
- ES 里还有旧 chunk 会不会泄露？

## Q32: ES 和 MySQL 状态不一致怎么办？
参考答法：

先以 MySQL 为准。查 `document.status`、`parse_status`、`index_status`、`active_index_version` 或 `wiki_page.index_status`、`published_version_id`，确认业务事实。再看 ES doc 里的 `documentStatus`、`lifecycleStatus`、`indexVersion` 是否和 MySQL 对齐。正常检索会过滤 space、knowledgeBase、lifecycleStatus、documentStatus，并要求 indexVersion 等于 activeIndexVersion。如果不一致，可以重跑 DOCUMENT_REINDEX/WIKI_INDEX 或 cleanup 删除孤儿 ES doc。面试时要强调：ES 是读模型，不能反过来当事实源。

继续追问：
- 如果 ES 写成功但 DB 更新失败怎么办？
- 如果向量 alias 没切成功，系统怎么降级？

## Q33: 为什么 Kafka 还要配 Outbox 表？
参考答法：

Kafka 只是消息系统，不能和 MySQL 业务事务天然原子。NoteWeave 在业务事务里先写 Task 和 TaskOutbox，提交后由 TaskDispatcher 投递 Kafka。投递成功后 outbox 标记 SENT；失败就标记 FAILED、增加 retryCount、设置 nextRetryAt。Consumer 收到消息后只拿 taskId 回查 MySQL，并由 TaskExecutionCoordinator 锁住 PENDING 任务执行。这样就把“业务事实创建”和“消息投递”拆成可重试的最终一致链路。

继续追问：
- Kafka 重复消费怎么保证幂等？
- 为什么 DOCUMENT_PROCESS 单独一个 topic？

## Q34: 如果面试官问“怎么证明不是纸上谈兵”，怎么答？
参考答法：

我不会只说“我写了代码”，而是按验证层次回答。第一层是纯逻辑单测，比如 Weighted RRF、EvidencePostProcessor、PromptBuilder、SafeUrlContentFetcher、MethodologyMatcher、MemoryWritebackStrategy，这些不依赖外部组件，能证明排序融合、证据截断、安全 URL、方法论匹配和记忆过滤的规则正确。第二层是接口和跨组件集成测试，项目里用 MockMvc 结合 ContainerizedIntegrationTest，把 MySQL、Redis、Kafka、MinIO、Elasticsearch 都接起来，验证上传、解析、索引、RAG、MCP、Memory、Admin/Ops 的真实状态变化。第三层是异步链路验证，不只看接口返回 200，还要看 Task、TaskAttempt、TaskEvent、TaskOutbox、业务表副作用，以及失败、重试、取消、幂等是否符合预期。第四层是 AI 效果回归，用 RetrievalTrace、Citation、LLMCallLog、AnswerFeedback 和 RAG Eval case/run/result 去沉淀坏样本和对比 prompt 版本。

边界也要讲清楚：这些测试能证明本地和集成环境下的关键链路，不等于已经有生产 QPS、P99 或真实用户准确率；如果要进一步生产化，还要补压测、限流、容量规划、告警阈值和线上灰度指标。

继续追问：
- 只 mock Service 的测试能证明 Kafka、MinIO、ES 的真实协作吗？
- RAG Eval 和单元测试分别验证什么？
- 为什么集成测试通过也不能说已经做过生产压测？

## 组合追问训练区：把相似问题放在一起答

### 题组 1：外部输入怎么受控进入系统？
常见问法：
- Bilibili MCP、URL Source、上传文件有什么共同风险？
- 为什么工具结果不能直接写数据库？
- 用户上传的文档或视频字幕里有 prompt 注入怎么办？

组合答法：

这类问题都在考外部输入边界。NoteWeave 里外部输入有三类：团队上传文件、个人 URL/TEXT/FILE Source、Bilibili MCP 工具上下文。它们都只能作为材料进入系统，不能直接变成长期知识。团队文件要经过 Space 权限、MinIO、解析、chunk、索引；个人 URL 要经过 SafeUrlContentFetcher，READY 状态必须有可读文本；Bilibili MCP 要通过 StudioMcpToolRegistry 和本地/远程工具服务拿到结构化 promptContext，再进入 ARTIFACT_GENERATE。真正沉淀时还要经过 Artifact、Wiki、Synthesis 或 Memory 的边界。

### 题组 2：临时内容怎么变成长期知识？
常见问法：
- Artifact、Wiki、SynthesisCard、Memory 为什么不能混在一起？
- 为什么 Artifact 不自动写 Wiki？
- AutoWikiMaintenance 是否替代人工确认？

组合答法：

这类问题都在考知识沉淀边界。ChatMessage 是交互过程，Artifact 是可版本化产物，Wiki 是团队长期知识，SynthesisCard 是用户确认后的个人综合沉淀，Memory 是会话或用户偏好的长期上下文。Artifact 可以重生成和导出，但默认不自动污染 Wiki；SynthesisCard 要 proposal/confirm 并绑定 artifactVersionId；Memory 要区分 DRAFT/FORMAL 并经过过滤；AutoWikiMaintenance 可以生成自动维护 WikiPage，但仍要保留版本、citation、sourceFingerprint、WIKI_INDEX 和图谱同步，不能说它替代人工知识治理。

### 题组 3：长任务失败怎么恢复？
常见问法：
- Kafka 挂了怎么办？
- Bilibili MCP 超时怎么办？
- WIKI_INDEX 或 RAG_EVAL_RUN 失败怎么办？
- Admin 重试为什么要校验？

组合答法：

这类问题都回到 Task/Outbox/Kafka/Worker。业务事务写 Task 和 TaskOutbox，投递失败可以后续补投；Worker 重复消费要查 Task 状态和业务目标幂等；Bilibili MCP 失败会落到 LoadMcpToolContextSkill 和 ARTIFACT_GENERATE 任务失败；AutoWikiMaintenance 生成页面后索引失败只影响 WIKI_INDEX，不应该破坏 WikiPageVersion；Admin 重试前要用 AdminTaskRetryValidator 检查 Document、Artifact、Source、WikiPage、RagEvalRun 等目标对象是否仍然可重试。

### 题组 4：回答错了怎么查？
常见问法：
- Citation 不准先查什么？
- RAG 召回错了怎么定位？
- Eval 和正式聊天怎么隔离？

组合答法：

这类问题按证据链查。先看用户所属 Space、session scope 和 KnowledgeBase 范围；再看 RetrievalTrace，确认 BM25、向量、Wiki recall 各自召回了什么；再看 EvidencePostProcessor 是否去重、合并或截断了关键证据；然后看 PromptVersion 和 LLMCallLog；最后看 Citation 和 AnswerFeedback。RAG Eval 用独立 case/run/result 和 RAG_EVAL scene，不污染正式 ChatSession、Memory 和用户对话。

### 题组 5：MCP、Skill、Agent 怎么讲才不被追穿？
常见问法：
- Bilibili MCP 是不是完整 MCP 平台？
- Skill 是不是 Agent？
- 未来做 Agent 还缺什么？

组合答法：

当前最稳的说法是：NoteWeave 有受控工具扩展和可观察生成工作流。Bilibili MCP 支持本地/远程工具服务、聊天显式触发和 Artifact promptContext 注入，但不是完整 MCP marketplace。Skill 是 ArtifactPlanExecutor 里的固定步骤，如 LoadGenerationContext、LoadMcpToolContext、SelectEvidence、GenerateReport、SaveArtifact，并通过 SkillExecutionLog 记录。它具备 Agent 化基础，但还没有开放规划器、任意工具调用、沙箱、预算、回滚和自动执行闭环。

### 题组 6：新增特性带来的性能压力怎么答？
常见问法：
- Bilibili MCP 慢怎么办？
- AutoWikiMaintenance 会不会拖慢文档处理？
- RAG Eval 会不会影响正式链路？

组合答法：

不要编造 QPS 或 P99，要按链路分析。Bilibili MCP 慢，先看远程工具超时、缓存、字幕长度限制和任务失败日志；AutoWikiMaintenance 增加 WikiPageVersion、citation、WIKI_INDEX 和 graph sync，后续可做增量同步和低峰处理；RAG Eval 是独立任务和 scene，可以限流、排队、低峰执行。核心原则是：外部依赖和批量评测不能阻塞正式问答主链路。

### 题组 7：表结构怎么讲才像真做过？
常见问法：
- 你设计了哪些核心表？
- 为什么不用一张大 JSON 表？
- 哪些唯一索引和组合索引最关键？

组合答法：

这类问题要按生命周期讲。边界表是 `users/space/space_member`；任务表是 `task/task_attempt/task_event/task_outbox`；资料表是 `knowledge_base/document_upload/file_object/document/document_chunk`；证据表是 `citation/message_citation/retrieval_trace/retrieval_trace_item/llm_call_log/answer_feedback`；产物和沉淀表是 `artifact/artifact_version/methodology_card/wiki_page/wiki_page_version/artifact_distillation_proposal/synthesis_card/memory_item`；运营表是 `prompt_version/rag_eval_case/rag_eval_run/rag_eval_result/audit_log/ops_cleanup_job/system_health_snapshot`。核心不是表多，而是每张表回答一个面试追问：权限、状态、版本、证据、失败、审计。

### 题组 8：中间件设计怎么讲才不空？
常见问法：
- MySQL、Redis、MinIO、ES、Kafka 为什么这么分工？
- 如果某个中间件挂了，系统怎么降级？
- Kafka、ES、Redis 能不能替代 MySQL？

组合答法：

这类问题要先说数据形态。MySQL 保存长期事实，Redis 保存短期 runtime 和 bitmap，MinIO 保存文件和 snapshot，ES 保存检索读模型，Kafka 保存任务触发消息。任何中间件都不能单独决定权限和最终状态。排障时按链路走：任务看 Task/Outbox/Kafka，检索看 ES/Trace，文件看 MinIO/object_key/cleanup，实时体验看 Redis/WebSocket，最终业务状态回 MySQL。
