# 实际问题转答清单

## 0. 本篇定位

这份文件用于处理真实面试里那些“不按题库出牌”的问题。原始问题可能来自 Java 后端、RAG、Agent、实习项目、指标、沟通、AI Coding 等方向。使用时不要逐题硬背，而是把问题快速转成 NoteWeave 当前仓库和验收能够支撑的回答。

总原则：

- 能落到 NoteWeave 已验收链路的，转成项目深答。
- 不能落到当前仓库事实的，转成“如果继续扩展，我会怎么接入”。
- 涉及生产 QPS、P99、token/day、准确率的，不编造数字。
- 涉及分库分表、注册中心、配置中心、微服务拆分、完整开放 Agent、Bibtex 的，不说成当前已实现。MCP 这块要更精确：已经落了一个远程 B 站 tool service，但不能夸大成完整开放平台。

## 1. 使用方式

遇到真实杂问题时，先做这三个动作：

1. 先判断这题本质在问什么，是项目主述、模块链路、技术取舍、指标边界，还是扩展设计。
2. 再把问题映射到 NoteWeave 的真实场景、链路和锚点。
3. 最后补一句边界，说明哪些是当前事实，哪些是后续方向。

回答尽量按下面骨架：

```text
这题本质在问什么
-> NoteWeave 当前怎么做
-> 链路和锚点在哪里
-> 为什么这么设计
-> 当前边界和扩展方向
```

## 2. 项目宽泛问题

### Q1：请介绍一下这个项目

#### 这题本质在问什么

面试官想先判断你有没有项目全局观，而不是看你会不会堆技术栈。

#### 转答方向

直接切到 `01-项目主述题.md` 的 1 分钟或 3 分钟版本。核心是 `TEAM / PERSONAL` 双空间、团队 RAG、个人研究、统一任务、证据链、运行态、记忆和运维。

#### 推荐回答骨架

一句话定义产品，再讲双空间，再讲团队和个人两条主链路，最后落到统一底座。

#### NoteWeave 锚点

- `com.noteweave.space`
- `TaskService`
- `HybridRetriever`
- `ChatRuntimeService`
- `PersonalGenerationService`

#### 常见坑

- 不要只说“RAG 知识库”。
- 不要讲成已经有真实生产流量。

### Q2：这个项目解决了什么问题？业务价值是什么？

#### 这题本质在问什么

面试官想确认你是不是只做了技术演示，还是能把产品价值讲清楚。

#### 转答方向

团队侧解决共享知识难进入、难检索、难追溯、难沉淀；个人侧解决研究资料难结构化、难复用、难产出、难长期积累；工程侧用 Task、Citation、Trace、Eval、Admin/Ops 把 AI 系统从 demo 做成可验收工作台。

#### 可直接复述的回答

> NoteWeave 解决的是知识从资料进入系统、被检索引用、生成成果、再沉淀为长期知识的闭环问题。团队侧通过上传解析索引、Hybrid RAG、Citation 和 Wiki 解决共享知识问答；个人侧通过 Source、Card、Artifact、Synthesis 解决研究资料结构化和长期沉淀；底层再用统一任务、权限、Trace、Eval 和 Admin/Ops 保证系统可追踪、可验收、可维护。

#### 常见坑

- 不要只讲“提高效率”这种空话。
- 不要把产品价值和工程价值混成一句泛话。

### Q3：你负责哪一部分？最有亮点的是哪里？

#### 这题本质在问什么

面试官想看你的 ownership 和技术判断，不是让你随便挑几个功能念一遍。

#### 转答方向

优先讲统一异步底座和 evidence-first RAG。如果面试官偏 AI 产品，也可以讲个人研究链路和 Artifact/Synthesis 分层。

#### NoteWeave 锚点

- `TaskService`
- `TaskExecutionCoordinator`
- `HybridRetriever`
- `EvidencePostProcessor`
- `ChatRuntimeService`
- `AdminObservabilityController`

#### 常见坑

- 不要泛泛说“我都参与了”。
- 最好讲 1 到 2 条自己最能扛住追问的故事。

### Q4：这个项目有没有上线？有没有打通闭环？

#### 这题本质在问什么

面试官在试探你会不会把本地验收说成生产上线。

#### 转答方向

可以坚定说工程闭环已验收，但不能讲成已有真实生产规模。

#### 可直接复述的回答

> 这个项目现阶段已经完成本地验收闭环，包括登录、Space、上传解析索引、团队 RAG、Citation、WebSocket、个人研究、Artifact、Memory、Eval、Admin/Ops 和前端工作台。但我不会把它说成已经有真实生产 QPS 的商业系统。更准确的说法是：工程链路已验收，生产化指标还需要在真实数据和压测环境下继续验证。

#### 常见坑

- 不要把“已验收”偷换成“已商用”。

## 3. 架构、异步和中间件问题

### Q5：为什么项目里要用 MQ / Kafka？

#### 这题本质在问什么

考的是长任务治理、一致性和失败恢复，不是考你会不会背“削峰填谷”。

#### 转答方向

结合 NoteWeave 的长任务：文档解析、Source 编译、Artifact 生成、Eval、Cleanup。重点讲统一任务模型和 Outbox。

#### 可直接复述的回答

> NoteWeave 用 Kafka 不是为了炫技，而是因为很多任务不适合在 HTTP 请求里同步完成，比如文档解析索引、Source 编译、Artifact 生成、RAG Eval 和资源清理。这些任务执行时间长、失败概率高、需要重试、取消和审计。所以我把它们统一抽象成 Task，通过 Outbox 保证业务写库和消息投递最终一致，再由 Kafka/Worker 执行。

#### NoteWeave 锚点

- `TaskService`
- `TaskOutboxService`
- `TaskKafkaConsumer`
- `TaskExecutionCoordinator`

#### 常见坑

- 不要只说“为了削峰”。
- 不要说 Kafka 成功就等于业务成功。

### Q6：为什么不直接写数据库，而是异步写入？

#### 这题本质在问什么

面试官在看你能不能区分业务事实和副作用执行。

#### 转答方向

注意区分：正式业务状态先写 DB，长任务副作用异步执行。不是所有写都异步，关键状态仍在事务里落库。

#### 常见坑

- 不要说所有数据都最终异步写。
- 不要把异步说成天然更一致。

### Q7：Redis 在项目里怎么用？

#### 这题本质在问什么

考的是中间件边界和运行态设计。

#### 转答方向

上传进度、ws-ticket、runtime state、event buffer、partial content、stop/resume。不要讲成主异步任务队列。

#### NoteWeave 锚点

- `ChatRuntimeStateStore`
- `ChatRuntimeService`
- `WsTicketService`

#### 常见坑

- 不要把 Redis 说成主事实源或主任务队列。

### Q8：有没有做微服务？如果要拆怎么拆？

#### 当前口径

当前是模块化单体或工程工作台，不讲成已拆微服务。

#### 扩展答法

> 如果未来拆服务，我会优先按稳定边界拆：认证权限、任务执行、检索/RAG、文件处理、Artifact/个人研究、Admin/Ops。第一刀我更倾向拆任务执行和文档处理，因为它们耗时长、依赖外部组件、扩缩容需求和主 API 不一样。

#### 常见坑

- 不要把“有模块边界”说成“已经微服务化”。

### Q9：有没有分库分表？

#### 当前口径

当前主链路没有分库分表。

#### 扩展答法

> 如果未来数据量上升，我会先看瓶颈在业务表、chunk/索引、citation 还是日志表。业务表可以先做索引和归档，检索压力交给 ES 扩容和索引分片，日志和 trace 更适合按时间归档。只有单库容量和写入压力成为明确瓶颈时，再讨论分库分表和分片键。

#### 常见坑

- 不要为了显得高级临场编分片策略。

## 4. RAG / Agent / 模型问题

### Q10：大模型会出现幻觉吗？项目里怎么处理？

#### 这题本质在问什么

考的是你有没有把 RAG 做成可信工程，而不是“让模型自己发挥”。

#### 转答方向

Evidence-first RAG、无证据兜底、Citation、Trace、Eval、Prompt 约束。

#### 可直接复述的回答

> 会，所以 NoteWeave 不让模型直接自由回答知识库问题。团队问答先走权限约束下的 Hybrid RAG，再经过 EvidencePostProcessor 选证据，PromptBuilder 要求 grounded answer；没有证据时明确兜底。回答后保存 Citation、RetrievalTrace 和 LLMCallLog，用于排查是检索错、证据过滤错还是生成错。

#### 常见坑

- 不要把 Citation 讲成绝对正确证明。

### Q11：你们实际用什么模型？为什么选它？

#### 这题本质在问什么

考的是模型抽象和选型思路，不是强迫你报一个仓库里没有固定绑定的线上型号。

#### 转答方向

如果仓库没有固定生产模型，不编造。讲 `LLMClient` 抽象、stub 验收、本地可切 provider。

#### 稳妥答法

> 当前工程把模型调用抽象成 LLMClient，本地验收可以用 stub 或 OpenAI-compatible provider。模型选择我不会编造固定线上型号，真正生产化会按中文能力、上下文长度、成本、延迟、稳定性和工具或结构化输出能力做对比。

### Q12：这是 Agent 项目吗？

#### 转答方向

主线是 AI 知识工作台和实用型增强 RAG。Skill 是受控 pipeline，不是完整开放 Agent。

#### 常见坑

- 不要把受控生成流水线说成多 Agent 平台。

### Q13：MCP / Bibtex / GraphRAG 怎么讲？

#### 转答方向

- MCP：当前没有做完整开放式 MCP 平台，但已经把 B 站解析拆成远程 MCP tool service，并接到 Studio 产物入口和对话显式触发链路。
- Bibtex：适合补在个人 Source 导入层，不是当前端到端能力。
- GraphRAG：当前有 Wiki graph 和 ConceptRelation，但主检索链路不是 GraphRAG。

## 5. 指标 / 效果类问题

### Q14：项目优化完之后效果提升多少？

#### 这题本质在问什么

考的是你能否在没有生产数字时仍然给出可信的验证路径。

#### 转答方向

不编造生产提升，讲已有观测面和将要测的指标。

#### 可直接复述的回答

> 这个项目现阶段是本地验收闭环，不适合编造线上提升数字。能说的是我已经把验证和观测面补出来了，比如 TaskEvent、RetrievalTrace、LLMCallLog、RagEvalRun、SystemHealth 和 AuditLog。真正要量化收益，我会按链路测任务成功率、重试率、解析耗时、索引耗时、检索 recall@k、MRR、citation coverage、端到端延迟和错误率。

#### 常见坑

- 不要没有评测集就报百分比。

### Q15：准确率、召回率、citation coverage 怎么证明？

#### 转答方向

先构造评测集，再用 RagEvalRun 记录 run/result，拆成检索层、生成层和端到端层。

#### 常见坑

- 不要说 citation coverage 高就等于答案正确。

### Q16：Redis、数据库、MQ 真实 QPS / P99 大概多少？

#### 稳妥答法

> 当前仓库没有真实生产流量数字，我不会编造。可以讲压测方案：用固定数据集、固定并发、固定模型 stub 或真实 provider，分别压上传、任务执行、检索、WebSocket runtime 和 Admin 查询，再看 P50/P95/P99、错误率、积压、重试率和资源占用。

## 6. 沟通 / AI Coding / 个人经历问题

### Q17：怎么把复杂技术方案讲给业务方？

#### 转答方向

少讲技术名词，多讲风险和收益。比如 Citation 对业务是“答案能追到来源”；Task/Outbox 对业务是“长任务可查进度、失败可重试”。

### Q18：AI Coding 用得多吗？代码是自己写的吗？

#### 稳妥答法

> 我会用 AI 辅助梳理方案、生成测试草稿、做代码审查和文档整理，但不会把生成结果直接当最终答案。我会用项目契约、测试、实现兜底锚点和本地验收去校验它，尤其是权限、一致性、数据迁移和边界场景。

### Q19：AI 生成代码不符合预期怎么办？

#### 转答方向

收敛需求、补测试、缩小改动范围、用代码事实校验，而不是让 AI 一次性大改。

## 7. 不适合按 NoteWeave 主线硬答的问题

下面这些问题如果出现，不要说成当前项目事实：

- 分库分表分的什么表，分片键是什么。
- 注册中心、配置中心、RPC 网关当前怎么落。
- 真实线上 QPS、P99、token/day。
- 完整开放 Agent、多 Agent 协议、RL 训练。
- Bibtex 端到端、完整开放式 MCP 平台主链路。
- 本地缓存 + Redis 二级缓存真实生产策略。

统一转答模板：

> 当前 NoteWeave 主链路没有把这块作为已验收能力。我可以从扩展设计角度说，如果未来要做，会接在某某边界，并优先验证某某风险。
